### 1. Agent、普通模型调用与 Workflow 的关键区别是什么？

> **来源**：[S022 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L187-L187) 问 Agent 与普通模型调用的区别；[S045 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L289-L289) 追问复杂任务何时仍适合固定 Workflow。

**回答：**
它们最关键的区别，就在于**下一步由谁决定**：

1. **普通模型调用**：就是最基础的单次 API 请求。给一个 Prompt，模型返回一次结果，没有工具调用交互，也没有后续流程推进。
2. **Workflow（工作流）**：**执行流程是由代码提前写死的**。不管中间有没有调模型、有没有条件分支甚至循环，每一步该往哪走、什么时候结束，都是程序规则预先定好的。
3. **Agent（智能体）**：**执行流程是由大模型动态决定的**。它是一个循环：模型根据当前目标和上一步工具返回的实际结果，自己判断下一步是继续调某个工具、补问用户，还是给出最终答案。

**追问：复杂任务中，什么时候依然应该选择固定 Workflow 而非 Agent？**
**回答：**
只要业务规则明确、步骤可以提前穷举，就应优先用 Workflow。因为由代码控制的系统稳定性最高、延迟和成本可控，也最容易测试和排错。只有在业务场景开放、无法提前穷举所有步骤，必须由模型根据动态观察自适应调整策略时，才适合使用 Agent。生产中通常采用混合架构：用 Workflow 约束核心流程和涉资操作，仅在模糊理解和动态规划节点引入局部 Agent。

### 2. 模型外面为什么还需要 Runtime / Harness？

> **来源**：[S001 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L19-L19) 问可靠 Harness 的核心能力；[S003 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L60-L60) 问从零搭建 Agent 的各个工程模块。

**回答：**
因为模型本质上只是概率文本生成器，它输出的只是“行动建议”，外部程序（Runtime / Harness）才负责把这些建议变成安全、可信的事实。

一个可用的 Agent 运行时至少承担以下工程责任：
1. **上下文管理与组装**：维护会话历史、检索证据、工具说明，并控制 Token 预算；
2. **工具解析与安全执行**：解析模型输出的 Tool Call，进行参数校验、权限鉴权与沙箱执行，并将执行回执回填给模型；
3. **状态机推进与持久化**：管理运行生命周期，处理超时、中断审批、断点恢复（Resume）与任务取消；
4. **最终验收与防死循环**：依据外部客观事实裁定任务是否完成，并对异常循环进行熔断。

**追问：随着大模型能力越来越强，外部 Runtime 会被淘汰吗？**
**回答：**
不会。模型再强，也无法替代身份授权、业务幂等性、数据库事务、物理沙箱隔离和成本熔断。这些确定性的工程约束绝不能交给概率输出的黑盒来保证。

### 3. 一个最小 Agent Loop 应怎样实现？

> **来源**：[S036 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L92-L92) 涉及最小 Loop 与 ReAct 在循环中的作用，补齐完成、等待与失败分支。

**回答：**
最小 Agent Loop 的核心是一个由状态驱动的 `while` 循环，标准流转如下：

1. **装配上下文**：读取任务目标、历史对话与工具执行结果，检查取消信号与 Token 预算，构造本轮请求；
2. **模型推理**：调用大模型获取响应候选；
3. **分支判定**：
   * **若模型返回 Tool Call**：进行参数合法性与权限校验；调用真实函数执行；将工具执行结果作为 Observation 附带对应的 `tool_call_id` 回填至上下文，进入下一轮循环；
   * **若模型请求澄清或人工审批**：持久化当前状态至挂起队列，释放执行资源，等待外部唤醒；
   * **若模型返回最终文本回答**：由宿主程序核对客观验收条件（如必要产物是否生成），验收通过则标记任务成功并跳出循环。

**追问：为什么不能仅凭模型输出“任务已完成”，就直接标记成功退出？**
**回答：**
因为模型容易产生自欺幻觉。例如代码修改任务中模型宣称“已修复”，但实际可能根本没跑通单元测试；或者文件写入工具抛出了权限拒绝，模型却直接回复“文件已成功保存”。任务完成必须由宿主程序校验客观事实（如测试退出码、数据库真实记录）。

### 4. ReAct、Plan-and-Execute、Plan-and-Solve 是一回事吗？

> **来源**：[S148 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L123-L123) 明确比较 ReAct 与 Plan-and-Solve；[S150 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L160-L160) 比较 ReAct 与 Plan-and-Execute。

**回答：**
不是一回事，它们处于不同的技术范畴与执行模式：

* **ReAct（Reason + Act）**：是一种交替推进的循环模式。每一步模型先进行显式推理（Thought），然后调用工具采取行动（Act），拿到外部环境反馈（Observation）后，再决定下一步行动。适合步骤未知、高度依赖外部实时反馈的探索型任务。
* **Plan-and-Execute**：是一种两阶段架构。先由规划器（Planner）生成完整的显式子步骤计划，再由执行器（Executor）逐步执行各子任务。中途若环境变化推翻了初始假设，需触发重新规划（Re-plan）。适合目标明确、依赖清晰的长流程复杂任务。
* **Plan-and-Solve**：本质上是一种 Prompting 提示工程技巧（针对大模型单次复杂推理提出的两阶段提示法），要求模型先输出解决计划再分步计算答案，而非一套包含多工具调用的系统运行时架构。

### 5. 怎样判断任务完成，怎样阻止死循环？

> **来源**：[S228 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-16.md#L82-L82) 询问如何确认完成并可靠停止；[S043 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L246-L246) 追问重复调用与循环防范。

**回答：**
* **任务完成判断**：将业务目标转化为可核验的客观条件。代码任务看单元测试是否通过，查询任务看是否获取到权威系统回执，生成任务看是否覆盖必要引用。最大步数和超时时间是安全兜底，不能作为成功标志。
* **阻止死循环**：
  1. **硬约束兜底**：设置最大执行轮数（如最多 15 步）、Token 消耗上限与全局执行超时（Deadline）；
  2. **动作指纹检测**：记录最近几步的动作签名（`工具名 + 参数哈希 + 结果哈希`），当检测到相同参数连续调用同一失败工具、反复读取同一文件而无新信息、或在两个分支间震荡时，强制中断并请求人工介入。

**追问：分页查询也会重复调用同一个工具，如何避免被误判为死循环？**
**回答：**
检查动作的游标（Cursor）或偏移行（Offset）是否在单调推进，以及每次返回的数据是否产生实际增量。只有在入参完全相同、或连续多轮查询均无新信息推进时，才判定为死循环。

### 6. 工具从定义到调用，完整链路是什么？

> **来源**：[S012 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L290-L290) 要求从用户请求讲到真实函数执行；[S205 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-12.md#L17-L17) 从 Registry/Schema/Execution/Result 追问工具框架。

**回答：**
完整链路包含五个标准环节：

1. **工具注册（Registry）**：向系统声明工具的唯一标识、自然语言描述以及参数的 JSON Schema 契约；
2. **上下文装配（Prompting）**：运行时将当前任务允许使用的工具列表注入大模型 API（如 `tools` 字段）；
3. **生成调用意图（Tool Call）**：模型根据需求输出结构化的调用候选，包含 `tool_name`、入参 JSON 和本次调用的 `call_id`；
4. **宿主拦截与执行（Execution）**：程序拦截模型输出，执行格式校验（Schema 验证）、业务合法性校验与权限鉴权；校验通过后在受控环境中调用底层函数；
5. **结果回填（Observation）**：将执行返回的结构化结果或明确错误，附带对应的 `call_id` 构造成工具消息回传给模型，推进下一轮决策。

### 7. Schema 校验通过，为什么仍可能越权？

> **来源**：[S288 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-29.md#L28-L28) 明确限定 Schema 只能校验格式，并继续追问对象级读写鉴权与用户确认。

**回答：**
因为 Schema 校验只回答**“参数格式长得对不对”**，无法回答**“当前用户能不能操作该对象”**。

Schema 只能约束字段类型、数值范围和必填项。例如调用 `refund(order_id, amount)`，参数符合正整数格式只能通过类型校验；但程序必须进一步核实：该订单是否属于当前登录用户、订单当前是否处于可退状态、退款金额是否超出余额。

权限校验必须在工具执行层依靠可信上下文（如 Token 解析出的当前用户 ID）和业务数据库做对象级权限判定（BOLA 防护），工具声明的 `readOnly` 等元数据只是调度提示，绝不能代替权限鉴权。

### 8. 工具太多、名字相似、参数总错，分别怎么处理？

> **来源**：[S001 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L21-L21) 问大量工具的按需发现；[S162 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-09.md#L60-L60) 问参数幻觉与格式自动修复。

**回答：**
这是三个不同维度的工程问题，分层处理：

* **工具太多**：采用两阶段渐进发现。初始只向模型暴露高层目录或通过工具检索（基于意图向量或分类）召回 Top-K 候选工具，再将命中工具的完整定义注入上下文，避免占用窗口并减少干扰。
* **名字相似**：建立统一的命名空间（如 `github__create_issue`），并在描述中明确各自的功能边界和典型反例，消除重叠模糊性。
* **参数总错**：完善 Schema 中的枚举值（Enum）与边界说明；同时在运行时引入有限的自动重试机制，当捕获到 Schema 校验报错时，将具体错误字段回填给模型让其自愈重试一次。

### 9. Tool Failure 应怎样分类，哪些可以重试？

> **来源**：[S003 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L61-L61) 涉及超时分类、重试与降级；[S043 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L242-L242) 涉及文件不存在、超时与权限不足的区别。

**回答：**
工具失败必须按性质分类处理，不能统一盲目重试：

1. **入参格式错误**：可将具体校验报错信息回填给大模型，允许模型重新修正入参一次；
2. **权限不足或对象不存在**：属于确定性不可逆失败，应直接终止工具调用或向用户报错，严禁重试；
3. **瞬态网络超时或接口限流**：可采用退避策略进行程序级重试，但前提是该操作具备**幂等性**（只读请求或带有唯一业务防重键的写请求）。

**追问：对于写操作（如转账、扣款），超时后为什么不能直接调用重试？**
**回答：**
因为网络超时只代表未收到响应，下游系统可能已经成功执行了扣款。在没有通过业务操作 ID 进行对账确认前盲目重试，会导致重复扣款。必须先调用查询接口确认状态，或依赖下游提供的强幂等键保证安全。

### 10. 工具已经成功，但响应或 Checkpoint 丢了怎么办？

> **来源**：[S042 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L217-L217) 明确给出外部任务已成功、但 Checkpoint 尚未写入便崩溃的窗口与幂等对账。

**回答：**
这是典型的分布式状态未知问题，解决核心在于**业务唯一操作身份（Operation ID）与先查后做**：

1. 执行任何外部副作用之前，宿主程序必须生成全局唯一的业务操作 ID，并持久化到本地待办状态；
2. 当发生系统崩溃、断电导致响应丢失时，系统重启后严禁生成新请求盲目重试；
3. 系统必须先持原操作 ID 查询下游系统的真实执行记录：若下游已执行成功，则补全本地 Checkpoint 继续推进；若下游确认未执行，则持原 ID 再次调用；若无法确认，挂起任务转人工对账。

### 11. Checkpoint、Resume 与重放聊天记录有什么区别？

> **来源**：[S087 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L285-L285) 问检查点持久化与断线后执行恢复；[S214 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-14.md#L51-L51) 问 Checkpoint 在压缩和长任务中的职责。

**回答：**
三者承担完全不同的系统职责：

* **聊天记录（History）**：仅保存面向用户的对话文本消息，不包含图引擎的执行步数、局部变量、权限令牌或未决副作用。
* **检查点（Checkpoint）**：保存的是**完整的可执行状态快照**（包括执行到的图节点位置、状态机数据、已执行动作的权威回执引用）。
* **恢复执行（Resume）**：是从持久化 Checkpoint 中反序列化执行状态，核对未决操作，并从中断的节点继续调度；而不是从第一句重新把历史发给模型跑一遍。如果直接重放历史 Prompt，模型可能会再次发出已经执行过的写操作。

### 12. 五分钟工具还在运行，用户又说话或点取消，怎么处理？

> **来源**：[S205 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-12.md#L19-L19) 问工具未结束时用户继续对话的处理；[S036 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L93-L93) 涉及任务取消信号与副作用核对。

**回答：**
必须将**HTTP 连接生命周期**与**后台长任务执行生命周期**解耦：

1. **运行机制**：长耗时工具必须由独立的后台 Worker 异步执行，向主循环返回异步任务句柄，前端通过轮询或长连接监听事件。
2. **用户追加新消息**：判断新消息是“补充条件”还是“修改目标”。若工具无依赖可继续运行；若目标冲突，向后台任务发送中断信号，由调度器重新规划。
3. **用户点击取消**：下发取消信号给可中断任务（如停止 Shell 进程）；同时立即停止向后派发新动作，并如实记录已发生动作的最终状态。已在外部生效的动作不能因为 UI 显示取消就当成未发生。

### 13. HITL 为什么不是一个确认弹窗？

> **来源**：[S146 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L70-L70) 问人工介入与中断恢复；[S253 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-21.md#L188-L188) 限定支付等高风险动作的人在回路审批。

**回答：**
前端弹窗只是 UI 交互，真正的 HITL（人在回路）是**后端可持久化的中断与安全恢复状态机**：

1. **精准绑定**：审批必须严格绑定待执行动作的唯一指纹（工具名、操作对象 ID、具体入参及上下文版本），不能笼统地给 Agent 授权；
2. **持久挂起与释放**：遇到高风险操作，图引擎必须保存 Checkpoint 挂起任务，释放内存和模型并发槽位，进入等待状态；
3. **安全复核**：恢复执行时必须复核审批记录的有效性，防止展示给用户的是操作 A，恢复后模型却被注入执行了操作 B。

### 14. Context、State、History、Memory 怎样区分？

> **来源**：[S017 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L82-L82) 直接问 Context 与长期 Memory 边界；[S214 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-14.md#L51-L51) 问 Checkpoint 职责。

**回答：**
四者具有明确的系统职责划分：

1. **Context（上下文）**：当前这一轮实际发送给模型的所有输入内容（系统提示词、工具定义、检索材料、裁剪后的历史等），受限于模型窗口大小。
2. **State（状态）**：程序推进任务所需的当前事实数据结构（当前节点、已收集参数、计数器），保存在内存或数据库中驱动流程。
3. **History（历史）**：用户与模型之间过去所有交互的完整时间序日志。
4. **Memory（记忆）**：从历史中提取提炼、经过持久化维护、用于未来跨轮次或跨会话复用的知识与用户偏好。

<a id="q15"></a>

### 15. 上下文很长时，怎样压缩且证明没压坏？

> **来源**：[S017 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L79-L79) 要求超窗压缩并保留必要信息；[S043 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L243-L243) 要求验证压缩后任务未被破坏。

**回答：**
* **压缩策略**：优先治理源头（大文件和工具返回仅保留引用，不将海量原始文本推入上下文）；再采用结构化摘要，压缩早期对话，保留**当前任务目标、未决问题、用户硬约束与关键实体引用**。
* **验证没压坏的标准**：不能仅看“Token 数量下降了、文本读起来通顺”。必须在基准评测集上，对比压缩前后继续执行任务的成功率、约束遵循率和工具调用准确率。

### 16. 长短期记忆怎样设计，错误记忆怎么删除？

> **来源**：[S003 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L63-L63) 涉及长短期记忆分层；[S236 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-18.md#L22-L22) 问错误结论写入 Memory 后的修复与防传播。

**回答：**
* **分层设计**：短期记忆负责当前会话或任务的局部连贯性（维护在内存 State 或滑动窗口中）；长期记忆负责跨会话复用（提取为结构化实体或向量存入持久库），写入时必须附带用户 ID、时间戳、原始数据源与版本。
* **错误记忆删除**：删除记忆必须实现**全链路失效**。不仅要删除文档数据库中的原文，还必须同步删除向量数据库中对应的 Embedding 记录，并使相关内存缓存失效。如果只删数据库而不删向量索引，后续语义检索仍会召回脏数据。

### 17. LangGraph State 为什么会膨胀？Session 能代替 Checkpoint 吗？

> **来源**：[S162 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-09.md#L56-L56) 问 State 膨胀与 OOM；[S189 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-10.md#L311-L311) 问会话记录存储、Resume 与 Checkpoint 区别。

**回答：**
* **State 膨胀原因**：节点中直接追加了未经裁剪的长消息列表、工具返回的大体积数据（如长文档、大 JSON），或者 State Reducer 规则被配置成了无脑 `list.extend`。解决方案是大文件存储于对象存储，State 中仅保留 URI 引用。
* **Session 不能代替 Checkpoint**：Session 仅用于维护用户维度的聊天消息列表，让用户能翻看历史；而 Checkpoint 是图引擎在特定节点执行时的完整状态机镜像（包含节点位置、分支条件、局部变量），用于节点崩溃恢复和人在回路挂起。

### 18. MCP、Function Calling、Skill 各解决什么问题？

> **来源**：[S014 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L15-L15) 直接比较 Function Calling、MCP 与 Skill 的层级与分工。

**回答：**
三者处于不同层级，解决不同阶段的连接与组织问题：

1. **Function Calling**：是模型厂商 API 级别的能力，解决大模型输出结构化参数调用的能力，将自然语言转化为函数入参规范。
2. **MCP（Model Context Protocol）**：是标准化的开放连接协议，解决大模型客户端与外部工具、数据源之间的解耦与通用互通，统一了工具发现、调用与资源访问标准。
3. **Skill**：是面向特定任务领域的指导规范资产包（包含指令规则、最佳实践和脚本），解决大模型在特定垂直业务场景中“如何规范完成任务”的方法沉淀。

<a id="q19"></a>

### 19. MCP 的初始化、SSE、Streamable HTTP，版本怎么回答？

> **来源**：[S033 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L33-L33) 比较 SSE 与 Streamable HTTP；[S231 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-17.md#L16-L16) 比较 stdio 与 Streamable HTTP 传输协议。

**回答：**
* **规范生命周期演进**：早期规范（2025-11-25）依赖显式的 `initialize` 握手进行能力协商；后续新版规范（2026-07-28）转向基于请求头元数据与每请求版本控制的轻量化流程。
* **传输层区别**：本地子进程通常走 `stdio` 管道传输；远程传输早期采用 HTTP + SSE（SSE 负责下行流事件，POST 负责上行指令），后续进一步演进为更加统一的 Streamable HTTP。断流仅代表传输层中断，不等于远端操作失败，传输层与业务状态必须解耦。

### 20. Skill 怎样渐进披露，为什么不能保证百分之百触发？

> **来源**：[S039 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L157-L157) 问 Skill 渐进披露实现；[S247 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-20.md#L63-L64) 明确追问能否保证 100% 正确触发。

**回答：**
* **渐进披露机制**：系统默认仅向模型注入 Skill 的名称与精简描述；只有当用户意图匹配到该 Skill 时，宿主程序才动态加载其正文指令、参考文档及脚本依赖，最大化节省上下文窗口并降低相互干扰。
* **无法保证 100% 触发的原因**：因为 Skill 匹配本质上仍是基于自然语言语义或概率模型的意图路由。当不同 Skill 描述语义相近、或用户输入模糊时，模型必然存在误判与漏判概率。对于高合规的关键路径，必须通过硬编码代码规则强制触发，不能单靠自然语言 Prompt 驱动。

### 21. 为什么要拆多 Agent，怎样证明不是徒增复杂度？

> **来源**：[S001 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L22-L22) 问什么任务值得拆子 Agent；[S151 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L183-L183) 要求证明单、多 Agent 取舍的实际收益。

**回答：**
* **拆分依据**：只有当复杂任务能够解耦为上下文独立、具备专业分工差异、且可并行执行的子任务时才值得拆分多 Agent；否则单 Agent 加上良好的工具定义往往更简单高效。
* **证明收益的量化指标**：必须在同一评测集上与单 Agent 基线进行对照试验，证明多 Agent 架构在**任务全流程成功率**上有明显提升，且**端到端延迟（并发收益覆盖协调开销）**与**总 Token 成本**在可接受范围内。如果多 Agent 带来的是延迟翻倍、开销暴涨而成功率无改善，就属于过度工程。

### 22. 多 Agent 怎样传状态，怎样避免互相覆盖代码？

> **来源**：[S001 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L23-L23) 涉及多 Agent 通信组织；[S032 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L15-L15) 追问并行修改同文件的冲突、锁和工作区隔离。

**回答：**
* **状态传递规范**：子 Agent 之间应按需传递精简的目标、约束和产物引用契约，严禁向所有 Agent 全量广播完整的对话历史，避免上下文膨胀与越权泄密。
* **避免覆盖代码**：
  1. 架构上设立**单一合并协调者（Synthesizer）**，子 Worker 仅生成各自的代码补丁（Git Diff）提交审核，由主协调者集中合并；
  2. 运行环境物理隔离，为每个并行编码的 Worker 分配独立的 Git Worktree 或容器沙箱，严禁多个 Agent 并发向同一个本地目录执行写操作。

### 23. Prompt Injection、权限、批准与 Sandbox 怎样协同？

> **来源**：[S027 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L295-L295) 问 Prompt 注入绕过与防护；[S228 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-16.md#L91-L91) 给出必须读内部代码却不能泄密的架构约束。

**回答：**
采用纵深防御体系协同防护：

1. **Prompt 防注入**：将所有外部资料（网页、用户文档、工具输出）视为不可信数据，无论内容如何声称“这是系统指令”，均不做提权处理；
2. **权限管理（Permission）**：在系统层按操作人身份严格管控工具和接口权限，越权调用在程序拦截层直接拒绝；
3. **审批机制（Approval）**：对写操作、发信和敏感删除动作引入人在回路强制确认；
4. **沙箱隔离（Sandbox）**：代码执行工具必须在受限容器内运行，严格限制网络出站、文件挂载与系统调用，将单次越权的潜在破坏锁定在沙箱内。

### 24. 意图路由和模型路由怎样设计？

> **来源**：[S122 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L165-L165) 比较规则、小模型与 LLM 意图分类；[S240 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L15-L15) 问多模型路由及错误分类。

**回答：**
* **意图路由（业务分类）**：按成本从低到高分流：明确命令走代码规则；高频标准意图走轻量小分类模型；开放模糊表达走大模型。置信度不足时主动向用户澄清，避免误路由。
* **模型路由（算力分级）**：根据任务复杂度梯级分配模型。简单信息提取和总结分流至轻量快速模型；复杂多步逻辑规划分流至主力推理模型。同时配置超时降级与多模型故障自动重试。

### 25. Agent Eval 应怎样构建，几个真实案例反复跑够不够？

> **来源**：[S078 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L83-L83) 问评测体系和覆盖；[S242 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L106-L106) 质疑重复跑约 20 个真实案例是否足够。

**回答：**
* **Eval 构建体系**：不能依靠模型自评。必须以客观可执行事实为验证标准（单元测试通过率、数据库落库结果、接口回执有效性）。数据集应分层覆盖正向主链路、边界异常、工具重试和安全注入场景。
* **为什么反复跑几个案例不够**：大模型生成具有随机波动性，重复跑少量案例只能观测随机方差，无法验证不同业务场景的泛化覆盖率。评测必须拥有规模化、版本固定的 Benchmark，并在修改前后进行盲测对照。

### 26. Agent 变慢或答错，Trace 应怎样帮忙？

> **来源**：[S074 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L483-L483) 涉及执行观测设计；[S129 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L400-L400) 涉及 Trace Replay 用于可靠性调试与副作用边界。

**回答：**
Trace 必须通过全局链路 ID 将用户请求、模型调用 Span 和工具执行 Span 串联起来：

* **变慢排查**：通过瀑布流查看耗时占比，快速定位瓶颈是在请求排队、模型首字延迟（TTFT）、工具执行网络阻塞，还是 Agent 陷入了无进展的重试循环；
* **答错排查**：回溯问题发生那一步的具体 Context 输入和工具返回的真实 Observation，精准确认是 Prompt 指令缺陷、模型参数解析错误，还是外部工具返回了脏数据。

### 27. Coding Agent 怎样证明可交付，怎样安全“自进化”？

> **来源**：[S282 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-27.md#L196-L196) 问 AI 代码遗漏坏例后的发现与回滚；[S082 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L173-L173) 问自进化如何防止错误经验积累。

**回答：**
* **可交付证明**：代码改动必须通过原有测试套件与新编写的针对性测试用例，并由自动化流水线进行静态语法检查与 Git Diff 安全审查，绝不能凭模型回复文本认定交付。
* **安全自进化**：从错误案例中沉淀经验规则时，生成的候选规则必须经过独立回归测试验证，保留版本与回滚机制，并经过人工审核后方可并入系统的长期 Prompt 或知识库中，防止错误经验污染生产环境。

### 28. LangGraph、SDK、自研 Loop 最后怎么选？

> **来源**：[S004 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L91-L91) 涉及自研 Runtime 与成熟框架的取舍；[S054 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L54-L54) 涉及 LangGraph 与 LangChain 的工程差异。

**回答：**
根据任务拓扑复杂度与工程维护成本选型：

1. **自研 Loop**：适用于流程较短、逻辑简单（5 步以内工具调用）、对依赖体积和启动延迟有极致要求的业务，开发与排错成本最低；
2. **商业 SDK（如 OpenAI Agents SDK）**：适用于与特定模型生态深度绑定、追求极简开发与开箱即用多 Agent 转交（Handoff）的轻量级场景；
3. **LangGraph**：适用于具有复杂循环网络、多条件分支、以及需要生产级状态持久化（Checkpointing）和深度人在回路（Interrupt）中断恢复的复杂企业级系统。
