### 1. 拿到陌生系统设计题，为什么不先画微服务架构图？

> **来源**：[S121 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L142-L142) 要求根据给定业务场景从零拆解 Agent 或 Workflow 系统架构。

**回答：**
脱离业务规模、延迟约束与容错底线直接堆砌 Redis、Kafka、微服务，属于盲目套模板。标准的系统设计推演应按以下四步展开：

1. **澄清功能边界与成功定义**：明确核心用户动作、输入输出形式，以及“什么状态算任务真正完成”（例如异步研报生成系统中，“HTTP 202 受理成功”与“最终生成可下载且引用校验通过的 PDF”是两个完全不同的完成边界）；
2. **确认非功能性约束与底线不变量**：量化日活（DAU）、峰值 QPS、数据增长规模、端到端延迟 SLA（如在线对话 TTFT $< 1.5\text{s}$，后台批处理 10 分钟内完成），以及**绝对不能突破的业务底线**（如支付/退款系统严禁重复扣款，多租户知识库严禁跨租户越权泄露）；
3. **跑通最小端到端主链路与权威存储**：先给出由 API 接入、核心业务处理、权威数据库（Source of Truth）组成的最小闭环，明确每一份核心状态存放在哪里；
4. **针对瓶颈与故障点定向演进架构**：顺着高并发读引入缓存，顺着耗时异步任务引入消息队列与 Worker 池，顺着单点崩溃与网络超时补齐幂等键、租约续期与死信补偿。只有当不同模块存在独立的扩缩容比例、异构硬件需求（如 GPU 推理 vs CPU 业务）或故障隔离要求时，才做服务拆分。

### 2. SLI、SLO 与“接口可用”怎样关联到用户目标？

> **来源**：教学补足（基于 [Google SRE 的 SLO 方法](https://sre.google/workbook/implementing-slos/)补齐系统设计的可用性、质量与尾延迟验收口径）。

**回答：**
* **SLI（Service Level Indicator，服务等级指标）与 SLO（Service Level Objective，服务等级目标）**：
  SLI 是以**用户真实可感知的成功结果**为准的量化测量口径，SLO 是在指定时间窗口内 SLI 必须达到的目标阈值（及对应的错误预算 Error Budget）。
  * **为什么“HTTP 200 比例”不等于真正的服务可用率**：在 AI 应用或异步任务系统中，网关返回 `HTTP 200` 往往只代表“请求已入队”或“流式连接已建立”。如果后续 Worker 因 OOM 崩溃、模型输出截断乱码或检索超时导致用户最终没拿到有效结果，从用户视角看该次服务是失败的。因此 AI 系统的核心 SLI 必须拆分为：**请求受理成功率、端到端任务有效完成率、首字延迟（TTFT P95/P99）以及生成结果合格率**。
* **错误预算（Error Budget）计算**：
  假设周合格请求量为 $100\text{ 万}$ 次，SLO 设定为 $99.9\%$ 的请求在 $3\text{s}$ 内返回合格响应，则每周允许的失败或超时预算为 $100\text{ 万} \times (1 - 99.9\%) = 1,000$ 次。统计时不能把因自身容量不足而触发限流（HTTP 429）或超时的请求从分母中剔除。
* **多阶段尾延迟叠加原则**：
  一条请求串联经过网关、检索、重排、生成四个阶段时，**端到端 P99 延迟绝不等于四个阶段 P99 的简单相加**（四个独立阶段同时撞上各自 $1\%$ 最差情况的概率远低于 $1\%$），工程上必须以全链路端到端实测的分布分位数为准。

### 3. Agent 服务怎样估容量？给一个带单位的例子。

> **来源**：[S004 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L89-L89) 给出用户量与日请求条件要求估算资源；[S007 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L152-L152) 问 DAU、数据量和任务量怎样影响架构设计。

**回答：**
Agent 服务的容量估算核心在于：**入口任务 QPS 不等于底层模型调用 QPS，单次请求连接时长远大于传统毫秒级 Web 接口**。

**带单位的完整推演示例**：
假设业务峰值入口为 **每秒 $10$ 个 Agent 任务（Task QPS $= 10\text{ tasks/s}$）**，每个任务平均执行 $4$ 轮 ReAct 循环（即调用 $4$ 次大模型、$3$ 次外部工具），单次模型调用平均耗时 $2\text{s}$，每次模型调用平均输入 $3,000\text{ Tokens}$、输出 $500\text{ Tokens}$：
1. **模型层调用频率（LLM RPS）**：
   $$\text{LLM RPS} = 10\text{ tasks/s} \times 4\text{ calls/task} = 40\text{ calls/s}$$
2. **平均在途并发槽位（由利特尔法则 Little's Law $L = \lambda W$ 推导）**：
   * 模型层常驻在途并发请求数：$40\text{ calls/s} \times 2\text{s} = 80$ 个并发推理槽位；
   * 若算上工具耗时，单个 Agent 任务端到端耗时 $10\text{s}$，则网关与运行时层需同时维持 $10\text{ tasks/s} \times 10\text{s} = 100$ 个并发活跃会话状态；
3. **Token 吞吐率（TPM / TPS）与配额预算**：
   * 输入吞吐：$40\text{ calls/s} \times 3,000\text{ Tokens} = 120,000\text{ input Tokens/s}$（即 $7.2\text{M TPM}$）；
   * 输出吞吐：$40\text{ calls/s} \times 500\text{ Tokens} = 20,000\text{ output Tokens/s}$（即 $1.2\text{M TPM}$）；
4. **工程安全水位**：
   上述计算仅反映稳态均值。考虑到长尾复杂任务（可能循环 10 轮以上）、工具异常重试以及流量尖峰，实际连接池、Worker 并发槽位与商业 API TPM 配额必须预留 **$2 \sim 3$ 倍的安全水位**，并配置单任务最大轮次与 Token 熔断上限。

### 4. Source of Truth、缓存、索引、操作记录怎样分工？

> **来源**：[S097 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-06.md#L64-L64) 问 Redis 能否承担持久存储；[S331 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1614-L1614) 问 MySQL、Redis、MQ 在系统中的分层职责。

**回答：**
多存储系统的核心设计原则是**单一权威事实源（Single Source of Truth）与派生视图（Derived Views）严格分离**：

1. **权威事实源（Source of Truth，通常为关系数据库 MySQL / PostgreSQL）**：
   承担 ACID 事务、唯一性约束与最终业务状态裁定（如订单状态、账户余额、任务状态机、知识库元数据主表）。当任何组件发生数据不一致或崩溃恢复时，一律以权威库为准；
2. **检索索引（Search Index，如 Elasticsearch / Milvus）**：
   从权威数据异步构建的**只读查询加速视图**，专门服务全文检索与向量近邻召回。索引损坏或模型升级时，可随时根据权威库原文全量重建，绝不能把向量库当作唯一原文存储；
3. **高速缓存与瞬态协调层（Cache & Coordination，如 Redis）**：
   存储可回源的热点读取副本、分布式限流计数与短期租约。注意：若将唯一防重幂等键仅存于 Redis，一旦发生主从切换丢数据或内存淘汰，就会丧失防重保护，因此核心业务幂等状态仍需落入持久化数据库；
4. **操作账本与事件流（Operation Ledger & MQ）**：
   操作记录表（Action Log）持久化每一次外部工具调用或涉资操作的唯一操作 ID、入参摘要与回执状态，用于崩溃后对账恢复；消息队列（MQ）负责异步解耦与削峰填谷，在任务已持久落库后再返回 [HTTP 202 Accepted](https://www.rfc-editor.org/rfc/rfc9110.html#name-202-accepted)。

### 5. 持久任务怎样抗 Worker 崩溃，为什么 Lease 还需要 Fencing？

> **来源**：[S325 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1133-L1133) 先问分布式长任务中 Lease（租约）的含义，随后在 [S325 后续记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1137-L1137) 追问 Fencing Token 的具体实现机制。

**回答：**
* **为什么需要 Lease（带过期时间的租约）**：
  长耗时任务（如执行数分钟的 Agent 或文档解析）运行期间，Worker 进程可能因 OOM、宿主机断电或网络分区而静默死亡。若采用无期限锁定，任务将永久卡死在 `RUNNING` 状态。引入 **Lease（租约）**后，Worker 领取任务时获得一个有限期的执行租约（如 30 秒），并在存活期间通过后台心跳定期续租（Renew）；一旦 Worker 崩溃停止续租，租约到期后调度器即可安全识别并将该任务重新派发给新的 Worker 接管。
* **为什么有了 Lease 还必须配合 Fencing Token（防护令牌）**：
  **租约到期只能通知调度器“允许派发新 Worker”，却无法物理杀死那个假死的旧 Worker**。
  * **经典并发脑裂场景**：Worker 1 领取任务后，在准备写库或调外部接口前发生了长达 40 秒的进程级停顿（如 JVM Full GC、容器 CPU 严重限流或网络拥塞）；第 30 秒租约到期，调度器将任务派给 Worker 2；第 35 秒 Worker 2 完成任务并写入新状态；第 40 秒 Worker 1 终于恢复，毫不知情地继续发出写请求，用脏数据覆盖了 Worker 2 的结果。
  * **Fencing Token 的实现机制**：每次派发或续签任务租约时，数据库或协调服务原子递增任务的代际版本号 `epoch / fencing_token`（如 Worker 1 拿到 `token=1`，Worker 2 接管时递增为 `token=2`）。当任何 Worker 向数据库提交状态或向存储系统写入产物时，必须携带自己的 `token`，由存储层执行原子条件校验：
    ```sql
    UPDATE task_state SET status = 'DONE', result = ... 
    WHERE task_id = ? AND fencing_token = 2;
    ```
    当迟到的 Worker 1 带着过期的 `token=1` 来写库时，因不满足 `fencing_token = 2` 被存储层直接拒绝，从而彻底根除脑裂覆盖[（参考 Redis 分布式锁与 Fencing 说明）](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。

### 6. 幂等与锁有什么区别，幂等表应该怎样设计？

> **来源**：[S011 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L273-L273) 询问重复支付的幂等设计；[S021 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L166-L166) 询问本地锁与分布式锁的职责边界。

**回答：**
* **分布式锁与业务幂等的本质区别**：
  * **锁（Lock）**解决的是**空间/同一时刻的并发互斥**（防止两个请求在同一个时间窗口内同时进入临界区修改数据）；
  * **幂等（Idempotency）**解决的是**全生命周期内同一业务意图的防重复执行**。一旦第一个请求执行完毕并释放了锁，5 秒后客户端因为网络超时重发同一个扣款请求，此时锁早已释放，新的重试请求依然会顺利拿到锁并造成**二次重复扣款**。因此**锁绝不能替代业务幂等**。
* **生产级幂等表（Idempotency Table）的设计规范**：
  1. **联合唯一索引**：以 `(tenant_id, action_type, idempotency_key)` 建立数据库唯一索引（`UNIQUE KEY`），由客户端或上游在发起意图时生成全局唯一的 `idempotency_key`；
  2. **核心状态机与防篡改校验字段**：表结构包含 `status`（`IN_PROGRESS` 执行中、`SUCCEEDED` 已成功、`FAILED_RETRYABLE` 可重试失败、`FAILED_FATAL` 不可重试失败）、`request_params_hash`（请求关键参数的哈希值）、`response_snapshot`（成功响应结果快照）以及过期清理时间；
  3. **标准执行流转（参考 [Stripe 幂等接口设计](https://docs.stripe.com/api/idempotent_requests)）**：
     * 请求到达先尝试插入幂等记录；若触发唯一键冲突，读取已有记录：
     * 先比对 `request_params_hash`，若同一个幂等键两次传了不同的金额/参数，直接报错 `422 Unprocessable Entity`；
     * 若状态为 `SUCCEEDED`，直接原样返回保存的 `response_snapshot`；若为 `IN_PROGRESS`，返回处理中或等待结果，绝不重复触发下游副作用。

### 7. Outbox 能否把消息和业务做到端到端 Exactly Once？

> **来源**：[S154 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L249-L249) 明确问 Local Outbox（本地消息表）与长任务恢复；[S147 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L99-L99) 问分布式消费者的业务幂等。

**回答：**
* **Transactional Outbox（本地事务消息表）解决什么问题**：
  解决“修改本地业务数据库”与“向 MQ 发送消息”无法在同一个原子事务内完成的双写不一致难题。做法是在本地数据库开启事务，**将业务表更新与向 `outbox_events` 表插入待发事件放在同一个数据库本地事务中原子提交**；提交成功后，再由后台 Relay 进程轮询或通过 CDC（如 Canal / Debezium 监听 binlog）异步将事件投递给 MQ，投递成功后标记 Outbox 记录为已发送。
* **为什么仅靠 Outbox 不能实现端到端 Exactly Once，而必须配合消费端幂等**：
  因为 Relay 派发器向 MQ 发送消息成功后，可能在把本地 `outbox_events` 状态更新为“已发送”之前发生进程崩溃或网络闪断；重启后派发器会再次扫描并重发该条消息。因此 **Outbox 实现的是可靠的不丢消息（At-Least-Once 至少投递一次）**[（参考 AWS Outbox 模式说明）](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)。
* **如何构成端到端业务“精确生效一次（Effectively Once）”闭环**：
  必须由 **生产者本地事务 Outbox（保证不漏发） + MQ 持久化确认（保证不丢消息） + 消费者基于唯一 `event_id` 的幂等去重表与下游业务更新同事务提交（保证重复投递只生效一次）** 三者共同闭环（注：[Kafka 自身的 Exactly-Once Semantics](https://kafka.apache.org/41/design/design/) 仅覆盖“从 Kafka 读 $\rightarrow$ 计算 $\rightarrow$ 写回 Kafka”的内部流处理闭环，无法自动跨越外部 MySQL 或第三方 HTTP 接口）。

### 8. 消息重复、乱序、ACK 丢失时怎么处理？

> **来源**：[S079 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L106-L106) 同时问消息发送可靠性与重复消费处理；[S007 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L161-L162) 问异步队列如何防丢与异常恢复。

**回答：**
1. **消息重复与 ACK 丢失处理**：
   * 消费者严禁开启自动确认（Auto-ACK），必须在**本地业务落库完成之后**再显式向 Broker 发送手动 ACK；
   * 若业务已提交成功，但发出的 ACK 因网络闪断或消费者重启而丢失，Broker 会将该消息重新投递给其他消费者。因此消费逻辑必须以消息内的全局唯一业务键（`event_id`）做幂等校验，使重投消息直接幂等跳过；
   * 针对反复消费报错的“毒丸消息（Poison Pill）”，设置最大重试次数（如指数退避重试 3 次），超限后转入**死信队列（DLQ）**落库告警，严禁无限阻塞主消费分区。
2. **消息乱序处理（如“订单已支付”比“订单已创建”先到，或旧修改晚于新修改到达）**：
   * **分区保序**：生产端将同一业务实体（如 `order_id` 或 `doc_id`）作为 Partition Key 路由到同一个队列分区，单分区内由单消费者线程串行消费；
   * **状态机与版本号兜底（最核心防线）**：因为跨网络重试或死信重投仍可能打破顺序，下游数据库更新必须校验**业务状态机合法迁移规则**（如已处于 `PAID` 状态的订单拒绝回退到 `CREATED`）或校验**单调递增版本号**（`WHERE id = ? AND version < ?`）。若前置状态尚未到达（如收到支付事件但订单未落库），可触发短暂延迟重投或主动反查上游。

### 9. 更新数据库后删除缓存，为什么仍会读到旧值？

> **来源**：[S292 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-32.md#L25-L25) 要求完整设计商品改价后的缓存更新、失效链路与一致性保障。

**回答：**
在标准的 Cache-Aside（先更新数据库，再删除缓存）模式下，仍可能读到旧值的三种原因及工程治理方案：

1. **主从复制延迟导致回填旧值**：
   写请求更新了 MySQL 主库并删了 Redis 缓存；紧接着读请求未命中缓存，去读了**尚未同步完成的 MySQL 从库**，把旧价格重新写回了 Redis。
   * **治理**：对刚发生修改的核心业务或强制强一致读取路径走主库，或通过订阅主库 binlog（CDC）在从库/主库确认推进后再异步更新/删除缓存；
2. **极端并发读写交错（旧读者晚写回）**：
   缓存恰好过期瞬间，读请求 A 从数据库读到了旧值 $V_1$ 后发生线程卡顿；期间写请求 B 将数据库更新为新值 $V_2$ 并执行了 `DEL` 缓存；随后读请求 A 恢复，将手里的旧值 $V_1$ 写回缓存。
   * **治理**：缓存回填时不直接无条件 `SET`，而是带上数据的数据库版本号 `version`（或使用 Redis Lua 脚本校验仅当缓存不存在/缓存内版本低于当前版本时才允许写入），并为所有缓存设置保底 TTL；
3. **删除缓存操作本身失败**：
   数据库提交成功后，调用 Redis `DEL` 时网络超时。
   * **治理**：结合本地消息表或直接监听数据库 binlog（如 Canal）投递 MQ 异步重试删除缓存，保证最终一致性；而在真正下单扣款、校验可退金额等底线环节，**必须直接读取权威数据库**，绝不信任缓存中的价格做最终资金结算。

### 10. 热键、击穿、雪崩怎样与扩容联系起来？

> **来源**：[S013 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L315-L315) 问缓存穿透、击穿和雪崩治理；[S253 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-21.md#L168-L168) 问爆款内容导致的数据偏斜与热分区如何处理。

**回答：**
在分布式架构中，不能笼统回答“加 Redis 分片”，必须先区分**全局雪崩、单点读热点与单点写热点**，因为分片集群中同一个 Key 永远只落在一个分片节点上，盲目给集群加机器无法分担单 Key 热点：

1. **缓存雪崩（大面积 Key 同时过期或整个缓存集群宕机）**：
   * **治理**：给基础 TTL 叠加随机抖动值分散过期时间；核心词条采用后台异步刷新（逻辑过期，永不物理失效）；并在应用层配置回源数据库限流与降级兜底；
2. **缓存击穿与极致读热点（Hot Key，如顶流爆款商品/热搜词每秒数十万次读取打穿单个 Redis 分片）**：
   * **防回源风暴**：采用互斥锁（Mutex）或进程内 `SingleFlight` 合并并发回源请求（使单实例百个并发只发 1 次查库）；
   * **分摊单分片读压力**：一是启用**应用进程本地二级缓存（Local Cache，如 Caffeine，设数秒短 TTL + 广播失效）**，将 90% 以上的读流量直接拦截在应用内存；二是对 Key 追加随机分片后缀（`hotkey#1`～`hotkey#N`）将副本打散到所有 Redis 分片节点；
3. **写热点与数据偏斜（如爆款帖子每秒数万条点赞/评论，或大促同商品扣库存）**：
   * **计数/评论类写热点**：通过本地内存或消息队列做**微批聚合（Micro-batching / Write-behind）**，将每秒上万次 `+1` 合并为每百毫秒一次批量更新；
   * **强守恒库存类写热点**：将总库存拆分为 $N$ 个子桶（Sub-buckets，如 `stock_sku_1`～`stock_sku_10`）分散到不同分片独立原子扣减，单桶扣空后触发余量调拨或回退扫描其他非空分桶。

### 11. 为什么加 MQ 不等于解决过载？

> **来源**：[S097 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-06.md#L65-L66) 给出高并发 Producer 与 Consumer 场景下的队列积压、背压与资源治理追问。

**回答：**
消息队列（MQ）本质上只是**用空间换时间的缓冲区，它本身不创造任何下游消费吞吐量**：

1. **稳态过载必死定律**：
   只有当**波谷期平均消费速率 $\mu >$ 平均生产到达速率 $\lambda$** 时，MQ 才能平滑短时脉冲尖峰（例如生产峰值持续 1 分钟多涌入 $600$ 个任务，平时到达 $24\text{ 个/s}$、消费能力 $30\text{ 个/s}$，则峰值过后需要 $\frac{600}{30 - 24} = 100\text{s}$ 消化完毕）。如果长期平均到达率 $\lambda \ge \mu$，队列积压会单调无限增长，直到磁盘撑爆或所有任务在队内等待超时失效；
2. **只看队列长度不够，必须监控“最老消息等待年龄（Queue Age / Oldest Message Age）”**：
   如果一个队列积压了 1 万条消息，其中混入了耗时长达数分钟的超大 PDF 解析或长视频任务，即使消息条数看着不多，队尾新任务的实际等待时间也可能已经超过业务 SLA 上限；
3. **完整的过载保护闭环（[参考 Google SRE 过载处理](https://sre.google/sre-book/handling-overload/)）**：
   * **入口有界队列与准入控制（Load Shedding）**：当队列积压年龄超过阈值时，在网关层果断触发限流（HTTP 429）或降级，拒绝超出系统承载能力的请求；
   * **快慢任务与租户隔离**：将轻量短任务与重型长任务拆分到独立 Topic 与独立 Worker 池，按租户实行公平调度（Fair Queuing），防止单个大租户一次批量导入一万个文件阻塞全站实时请求；
   * **消费端拉取背压（Pull Backpressure）**：消费者根据自身内存水位与下游大模型/数据库并发配额按需拉取，并跳过已在排队期间被用户主动取消的过期任务。

### 12. 重试、限流、熔断、降级怎样协同？

> **来源**：[S079 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L107-L107) 要求区分限流、熔断、降级；[S274 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-25.md#L100-L100) 追问突发流量下的下游保护与协同机制。

**回答：**
四个韧性组件分别在调用链的不同位置承担不同职责，若缺乏协同（尤其是无节制的多层重试）反而会引爆雪崩：

1. **职责边界**：
   * **限流（Rate Limiting）**：部署在**服务端入口**，拦住超出本服务承载能力的过多上游流量（保护自己）；
   * **熔断（Circuit Breaking）**：部署在**客户端调用侧**，当检测到下游依赖错误率或超时率超过阈值（如最近 20 秒失败率 $>50\%$）时，自动跳闸进入 `Open` 状态，后续请求在本地立即快速失败（Fail-fast），既释放本方线程连接池，也给下游留出喘息恢复时间；
   * **降级（Degradation / Fallback）**：当触发限流、熔断或非核心依赖超时时，关闭次要功能或返回有损但可用的兜底结果（如跳过 Rerank 直接用粗召回生成、主力大模型故障切备用轻量模型）；
   * **重试（Retry）**：仅针对**瞬态抖动且具备幂等性**的请求做补充尝试。
2. **协同防放大原则（[参考 AWS 超时、重试与抖动退避规范](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf)）**：
   * **严禁多层嵌套重试**：若网关重试 3 次、业务服务重试 3 次、SDK 重试 3 次，下游出现抖动时流量会被瞬间放大 $3 \times 3 \times 3 = 27$ 倍！全链路应规定**仅在最贴近故障边界的单一层执行重试**；
   * **指数退避加随机抖动（Exponential Backoff with Jitter）**：防止同一秒失败的成千上万个请求在完全相同的整秒时刻再次齐刷刷砸向下游；
   * **全局重试预算（Retry Budget）与熔断联动**：限制单实例的重试请求占比不超过总请求量的 $10\%$；一旦下游触发熔断器跳闸，立即短路所有重试直接走降级分支。

### 13. 多租户 AI 平台怎样防越权和 Noisy Neighbor？

> **来源**：[S254 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-21.md#L207-L207) 问企业级权限与安全隔离设计；[S276 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-26.md#L44-L44) 追问单个恶意或异常用户如何防止拖垮整个模型服务。

**回答：**
多租户 AI 平台必须同时构筑**数据安全隔离边界（防越权）**与**多维资源配额围栏（防吵闹邻居 Noisy Neighbor）**：

* **一、防越权（全链路服务端身份传递）**：
  1. 网关验签 JWT Token 提取不可伪造的 `(tenant_id, user_id, roles)` 注入内部 RPC 上下文；
  2. 关系库查询、对象存储签名 URL、向量库/ES 检索 Pre-filter、Checkpoint 状态读写以及语义缓存 Key 全部由底层中间件自动拼入 `tenant_id` 约束，严禁让大模型通过 Prompt 或函数入参自行指定租户 ID；
  3. 代码沙箱执行在独立受限容器与网络命名空间内运行，禁止跨租户挂载卷或访问内网元数据服务[（参考 Kubernetes 多租户安全指南）](https://kubernetes.io/docs/concepts/security/multi-tenancy/)。
* **二、防 Noisy Neighbor（避免单一租户耗尽全局算力与连接）**：
  1. **多维度联合限流（不能只限 QPS）**：在 AI 场景下，1 个包含 100K Token 超长上下文或多轮并发子 Agent 的请求，消耗的 GPU 算力顶得上普通短请求的上百倍。因此必须按租户同时限制：**并发在途任务数（Max In-flight Runs）、每分钟请求数（RPM）、每分钟 Token 消耗量（TPM）以及每日金额预算**；
  2. **队列分桶与公平调度（Weighted Fair Queuing / Shuffle Sharding）**：异步任务调度器不为所有租户共用单一 FIFO 队列，而是按租户分队列轮询调度（Round-Robin / DRR），确保某个租户突发塞入一万个批处理任务时，其他租户的实时请求依然能被即刻调度；
  3. **舱壁隔离（Bulkhead）**：将高 SLA 付费核心租户与免费试用/离线批处理租户隔离在不同的 Worker 组与模型 API Key 池中，防止单点配额耗尽波及全局。

### 14. LLM Gateway 为什么不能只转发 HTTP？

> **来源**：[S208 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-12.md#L89-L89) 直接要求设计统一 LLM Gateway；[S209 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-13.md#L21-L21) 追问实际输出 Token 尚未知时，10 个并发请求怎样防止预算超卖。

**回答：**
传统 API 网关（如 Nginx）只感知请求次数与字节流，而企业级 **LLM Gateway** 必须感知模型能力协议、流式 Token 计量与多供应商容灾：

1. **LLM Gateway 的核心职责**：
   * **协议归一化与动态路由**：抹平 OpenAI、Anthropic、vLLM 等不同后端的参数与错误码差异，按任务特征（是否含视觉输入、上下文长度、工具支持）路由至匹配的模型池；
   * **多活健康检查与无感 Fallback**：当主供应商返回 `429 Rate Limit`、`503 Overloaded` 或首字 TTFT 超时，网关自动切换至备用供应商/备用区域同级模型；
   * **统一审计、PII 脱敏与可观测性**：记录每次调用的 Trace、TTFT、TPOT、Prompt/Completion Token 明细与成本归属。
2. **当请求尚未结束、实际输出 Token 数未知时，10 个高并发请求如何防止把租户余额超卖（两阶段预占结算机制 Reserve-and-Settle）**：
   如果等流式生成全部结束才去扣减余额，10 个并发请求在进入网关那一刻都会读到“当前余额充足”，最终导致严重超支透支。正确做法是利用 **Redis + Lua 脚本执行两阶段原子预扣**：
   * **第一阶段：请求准入时原子预占（Reserve）**：
     网关先用分词器算出精确的输入 Token 数 $T_{\text{in}}$，并加上该请求声明的 `max_tokens`（或业务统计的 P95 保守输出上限 $T_{\text{max\_out}}$），折算为最大可能消耗额度 $\Delta C_{\text{max}}$。在 Redis 中通过 Lua 脚本原子判断 `当前可用余额 >= ΔC_max`，满足则立即扣减可用余额并写入一条带超时 TTL 的预占记录 `reservation:{req_id}`；不满足则直接在网关层拒绝该并发请求；
   * **第二阶段：流式结束或中断时精确结算（Settle / Refund）**：
     当流式响应正常结束（拿到 `usage` 实际输出 Token 数 $T_{\text{actual\_out}}$）或中途断连截断时，计算真实花费 $\Delta C_{\text{actual}}$，通过 Lua 脚本原子删除 `reservation:{req_id}` 并将多预扣的差额 $(\Delta C_{\text{max}} - \Delta C_{\text{actual}})$ 退回可用余额，同时落库计费流水。

### 15. SSE 断线后，怎样恢复交付而不重做任务？

> **来源**：[S035 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L73-L73) 问 SSE 断线、心跳、重连与断点续传；[S330 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1524-L1524) 问客户端断网是否会停止后台 Agent 运行。

**回答：**
核心架构原则是**将“后台 Agent 任务执行生命周期（Run）”与“前端 HTTP/SSE 传输连接生命周期（Connection）”彻底解耦**：

1. **提交与订阅分离**：
   客户端发起任务时，服务端生成全局唯一的 `run_id` 交由后台 Worker 异步执行。Worker 产出的每一个增量事件（Token 分片、工具调用状态、节点进度）都分配单调递增的序号 `seq_id`，一边写入 **Redis Stream（或内存环形缓冲区 + 数据库快照）**，一边推送给当前挂载的 SSE 订阅连接；
2. **网络闪断与页面刷新时不中断后台任务**：
   当用户手机切后台或 Wi-Fi 闪断导致 SSE TCP 连接断开时，仅销毁网关层的订阅转发协程，**后台 Worker 继续正常完成模型推理与工具执行**（只有用户显式调用 `POST /runs/{run_id}/cancel` 接口时才真正终止后台任务）；
3. **基于 `Last-Event-ID` 的无损断点续传**：
   * 服务端下发的每帧 SSE 事件均携带标准 `id: <seq_id>` 字段，并每 $15\text{s}$ 发送 `: ping\n\n` 注释心跳帧防止 Nginx/SLB 掐断空闲连接；
   * 客户端断线重连时，通过请求头 `Last-Event-ID: <last_seq_id>`（或查询参数）上报最后收到的事件序号；
   * 服务端校验用户权限后：若 `last_seq_id` 仍在 Redis Stream 缓存窗口内，先顺序补发 `(last_seq_id, current_seq_id]` 之间的缺失增量事件，再无缝挂载到实时事件流；若断线太久已超出流缓存窗口，则先从数据库读取最新已落库的 Checkpoint 状态快照下发，再接续之后的实时增量事件。

### 16. 长任务平台的最小架构怎样拆？

> **来源**：[S288 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-29.md#L22-L22) 要求说明长任务管理中 Plan/Todo、Harness 与 Backend API 各自的职责与协作架构。

**回答：**
面向数分钟至数小时长任务（如深度研究 DeepResearch、全自动代码库重构）的平台，按**控制面、调度面、执行面与存储面**拆分为五个核心模块：

1. **Backend API（控制面与接入层）**：
   负责身份鉴权、配额预检、任务创建（`POST /tasks`）、状态查询、人工审批注入（`POST /tasks/{id}/approve`）、主动取消以及 SSE 事件流分发。API 层完全无状态，绝不在 Web 请求线程里直接跑长任务；
2. **Task & Checkpoint Store（权威状态与账本层，PostgreSQL / MySQL）**：
   持久化任务主表（状态机、租约持有者、`fencing_token`）、结构化 **Plan/Todo 进度树**、每一步的图状态快照（Checkpoint）以及外部副作用操作账本（Operation Ledger）；
3. **Scheduler & Queue（调度与背压队列，Kafka / Redis Streams）**：
   负责按租户优先级派发待执行任务、监听租约超时并触发僵尸任务重派、以及在人在回路（HITL）审批通过后投递唤醒事件；
4. **Agent Harness / Worker Pool（无状态执行面）**：
   拉取任务并持有租约续期，驱动 `Plan -> Act -> Observe` 循环：管理上下文窗口压缩、在安全沙箱（Sandbox）内执行工具、校验验收条件，并在每个关键节点完成后持久化 Checkpoint。当遇到需要等待人工审批或长耗时外部回调时，主动持久化状态并**立即释放当前 Worker 槽位**；
5. **Artifact Store（大体积产物存储，S3 / OSS）**：
   保存任务过程中抓取的网页原文、生成的长篇报告、图表或代码补丁文件，数据库中仅传递轻量 URI 引用，防止撑爆数据库与消息队列。

### 17. 分片、全局 Top-K 和热点数据怎样取舍？

> **来源**：[S167 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-09.md#L160-L160) 问大规模广告库分片扩展；[S150 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L168-L168) 问分布式多节点 Top-10 汇总设计。

**回答：**
* **分片键（Shard Key）选择的取舍**：
  * **按记录主键 ID 哈希分片**：数据分布最均匀，绝无单分片存储倾斜，但任何按租户或业务维度的范围查询都必须**广播扇出（Scatter-Gather）**扫描全部 $S$ 个分片，尾延迟受最慢的那个分片（Straggler）拖累；
  * **按业务维度（如 `tenant_id` / `advertiser_id`）分片**：同租户查询只需路由到单个分片，局部性极佳，但超级大租户会导致严重的**单分片热点倾斜**。生产中常采用**复合路由（Salted Shard Key）**：普通中小租户按 `tenant_id` 哈希进单分片，头部超大租户自动拆分为 `tenant_id#0..N` 跨越多个虚拟桶。
* **各分片分别取局部 Top-K 再汇总，什么时候等于全局 Top-K，什么时候会失效？**
  * **成立条件**：当**同一个实体的计分完全收敛在单一分片内**（无跨分片数据累加），且各分片使用完全一致的确定性排序与前置过滤时，每个分片取局部 Top-K 交给协调节点归并取前 $K$ 名，必然严格等于全局 Top-K；
  * **失效反例（高频考点）**：如果同一个实体的统计值散落在多个分片上（例如按轮询分片日志，要统计全局出现总次数前 10 的商品或 IP），**各分片局部 Top-10 的并集绝不等于全局 Top-10**（假设某元素在 10 个分片里都排第 11 名、各出现 100 次，总计 1000 次本该是全局第 1，但在所有分片的局部 Top-10 里都被截断丢弃了）。此类聚合必须**先按实体 Key 哈希路由（Shuffle by Key）将同一实体的计数汇总到同一分区，再取局部 Top-K 归并**。

### 18. 十万 QPS，实时统计最近一小时 Top-10 IP，怎样设计？

> **来源**：[S150 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L168-L168) 给出了 10 万 QPS、最近 1 小时滑动窗口、实时统计 Top-10 IP 与跨实例汇总的完整条件。

**回答：**
针对 $10\text{ 万 QPS}$、1 小时滑动窗口（总计 $3.6\text{ 亿}$ 次请求事件）的实时 Top-10 统计，核心设计要点是**“按 IP 哈希分区汇聚 + 环形时间桶（Sliding Window Buckets）+ 最小堆维护局部 Top-K”**：

1. **接入层本地预聚合与按 IP 一致性哈希路由**：
   网关或日志 Agent 在本地内存先按 $1\text{s}$ 微批对 `(ip -> count)` 做一次预合并（大幅削减网络包数量），随后以 `hash(ip) % N` 作为 Partition Key 发往 Kafka 或流处理节点（如 $N=16$ 个计算分片），保证**同一个 IP 的所有流量 100% 落入同一个计算分片**（彻底避免跨分片计数割裂）；
2. **分片内滑动时间桶设计（秒级/十秒级环形数组）**：
   若维护精确到每条请求的 3.6 亿个时间戳，内存会直接爆炸。在每个分片内部，将 1 小时（3600 秒）切分为 **60 个 1 分钟时间桶**（或 360 个 10 秒时间桶）构成的环形数组：
   * 维护一张当前分片的活跃哈希表 `total_counts[ip]`（记录该 IP 最近 1 小时总次数）以及每个时间桶的 `bucket[t][ip]`；
   * 新事件到来时：`bucket[current_slot][ip] += delta`，同时 `total_counts[ip] += delta`；
   * 时间指针每推进一格（如进入下一分钟），将 60 分钟前那个过期旧桶遍历清零，并从总表中扣减：`total_counts[ip] -= bucket[expired_slot][ip]`（若归零则删除该键回收内存）；
3. **局部 Top-10 与全局归并**：
   每个分片利用 `total_counts` 动态维护一个大小为 10 的**最小堆（Min-Heap）**或跳表；查询时协调节点从 $N=16$ 个分片拉取各自的 Top-10（仅 $160$ 条记录），在内存中做一次归并排序即可在毫秒级返回精确的全局最近 1 小时 Top-10 IP（若活跃独立 IP 达数亿且允许极小误差，也可在分片内配合 HeavyKeeper / Count-Min Sketch 进一步固定内存上限）。

### 19. 秒杀、库存、购买后立即退款，正确性先讲什么？

> **来源**：[S134 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L501-L501) 同时要求防止超卖和少卖；[S212 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-13.md#L87-L87) 增加购买后立即退款时的库存与订单状态一致性追问。

**回答：**
库存系统的核心是守住**“可售库存 + 锁定预占库存 + 已售核销库存 = 总库存”**的恒等式，并处理好异步链路中的异常悬挂：

1. **如何同时防超卖与防少卖**：
   * **防超卖**：Redis 侧使用 Lua 脚本原子判断 `available_stock >= buy_num` 并扣减，同时在同一脚本内写入幂等预占集合 `reserved:{order_id}`（防同一请求重试重复扣减）；数据库落单与最终核销时带乐观锁条件 `WHERE sku_id = ? AND available_stock >= ?` 兜底；
   * **防少卖（库存泄露）**：若 Redis 预扣成功，但应用在发 MQ 或写数据库订单前崩溃，这笔库存就会变成永久无法释放的死库存（少卖）。因此必须在 Redis 预扣同时记录带时间戳的预占流水，后台定时对账任务扫描超过 5 分钟仍未在 MySQL 生成有效订单的孤儿预占记录，确认无订单后安全回补 Redis 库存；同时未支付订单通过延迟消息（如 15 分钟到期）关单并释放库存。
2. **“购买后立即取消/退款”与“异步下单/支付回调”并发到达时如何保证一致性**：
   * **订单状态机 CAS 互斥**：取消/退款请求与支付成功回调在数据库层竞争同一行订单记录（`SELECT ... FOR UPDATE` 或基于当前状态的原子更新 `UPDATE orders SET status = 'CANCELLED' WHERE order_id = ? AND status = 'UNPAID'`）；
   * **库存回补幂等流水表**：无论是由“超时未付关单”触发释放库存，还是由“支付后立即退款”触发回补库存，都必须先在同一事务内向 `stock_operation_log` 插入唯一流水记录 `(order_id, op_type='RELEASE')`。只有插入流水成功，才允许向 Redis 和数据库加回库存，严防“超时关单”和“用户手动取消”并发执行导致**同一笔订单被退回两次库存（造成超卖）**。

### 20. 通知平台怎样做到可靠投递而不过度承诺？

> **来源**：[S161 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-09.md#L41-L41) 直接要求设计多渠道通知平台的可靠投递、重试与去重机制。

**回答：**
企业级通知平台（覆盖短信、邮件、App Push、企微/飞书 Webhook）的核心是**分层状态机 tracking、分级限流隔离与防重复骚扰用户**：

1. **严格区分四级投递状态（不把 HTTP 200 当成用户已读）**：
   通知记录状态机必须明确拆分为：`ACCEPTED`（平台已落库入队）$\rightarrow$ `SUBMITTED`（已成功调用第三方通道商 API，拿到通道商回执 `vendor_msg_id`）$\rightarrow$ `DELIVERED`（收到通道商异步 Webhook 状态报告确认已送达用户终端）$\rightarrow$ `READ`（客户端埋点上报用户已点击/打开）；
2. **防重复轰炸（幂等与退避策略）**：
   * 业务方调用通知平台时必须传入唯一的 `biz_idempotency_key`（如 `order_paid_notify_10086`），平台在规定时间窗口内去重；
   * 当调用短信通道商 A 超时未收到响应时，**不能立即无脑重发或立刻切换通道商 B**（否则用户可能收到两条一模一样的扣款短信）。应先持批次号调用通道商状态查询接口核实，或对非紧急营销类通知放弃超时重发，仅对验证码等强时效通知允许跨通道切换；
3. **优先级队列与通道配额保护**：
   将通知拆分为**高优实时通道（验证码、交易告警）**与**低优批量通道（营销推送、周报）**两套完全隔离的 MQ Topic 与 Worker 池，并在出口按各第三方供应商配额做令牌桶限流，防止百万级营销推送阻塞登录验证码下发。

### 21. Feed 流和搜索联想的核心瓶颈有什么不同？

> **来源**：[S191 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-11.md#L19-L19) 要求设计关注流（Feed）；[S188 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-10.md#L292-L292) 要求设计商品搜索框实时联想（Autocomplete）并与点击搜索做对比。

**回答：**
两者虽然都是高频读取场景，但核心架构矛盾截然不同：

* **一、关注 Feed 流（核心矛盾是“大 V 写放大”与“多关注源读放大”的权衡）**：
  * **推模式（Push / Fan-out on Write）**：作者发帖时异步将帖子 ID 写入所有粉丝的收件箱（Inbox ZSet）。读取极快（$O(1)$ 直接读自己的收件箱），但若一个拥有 5,000 万粉丝的大 V 发帖，会产生 5,000 万次写放大与严重的投递延迟；
  * **拉模式（Pull / Fan-out on Read）**：作者只写自己的发件箱（Outbox ZSet）；粉丝刷 Feed 时实时拉取所关注的几百人的发件箱在内存做多路归并。发布极轻，但读取开销大；
  * **生产标准解法（推拉结合 Hybrid）**：普通创作者走**推模式**写在线活跃粉丝收件箱；粉丝数超阈值的大 V 走**拉模式**只写自身发件箱；粉丝读取时将“个人收件箱 + 所关注大 V 的发件箱”实时归并，并基于 `(timestamp, post_id)` 游标分页（避免传统 `OFFSET` 翻页在插入新帖时出现重复或漏帖）。
* **二、搜索框实时联想 Autocomplete（核心矛盾是“极致低延迟 $< 20\text{ms}$、多形态前缀匹配与前端乱序响应”）**：
  * **多层匹配索引**：英文前缀可用内存前缀树（Trie / FST）；中文支持汉字前缀、全拼、拼音首字母缩写与模糊纠错，工程上通常基于 Elasticsearch 的 `completion suggester` 或 `edge_ngram` 分词倒排索引，并按历史搜索热度（Popularity Score）离线预计算每个前缀的 Top-10 候选缓存在 Redis 中；
  * **前后端交互防乱序**：用户连续快速敲击 `c -> ca -> car` 时，前端除做 $100\sim 150\text{ms}$ 防抖（Debounce）外，必须为每次请求递增序号 `req_seq`（或使用 `AbortController` 取消在途旧请求），防止网络慢的 `ca` 响应晚于 `car` 返回并覆盖掉最新下拉列表。

### 22. 一亿订单要逐批 RPC 更新，怎样让离线任务可靠？

> **来源**：[S387 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L58-L59) 明确给出一亿子订单、逐批调用外部 RPC 与状态更新的工程设计题。

**回答：**
处理一亿量级（$10^8$）数据的批处理任务，绝不能写成“单机大循环 `LIMIT offset, size` + 开多线程调 RPC”，必须按**分片切片、游标扫描、限流背压、水位线断点续传與失败隔离**设计：

1. **按主键范围分片 + 游标扫描（Keyset Pagination）**：
   先查询全表最大最小 `order_id`，将一亿订单按 ID 区间切分为例如 $1,000$ 个互不重叠的子分片任务（Sub-tasks，每片约 10 万条）存入分片进度表。每个 Worker 领取一个分片后，内部严格使用 `WHERE order_id > last_id AND order_id <= shard_end_id ORDER BY order_id ASC LIMIT 500` 游标读取，避免深分页全表扫描；
2. **并发水位线（Watermark）推进陷阱防护**：
   如果分片内开启并发协程同时调用第 $101\sim 200$ 批和第 $201\sim 300$ 批 RPC，当第 $201\sim 300$ 批先返回成功、而第 $101\sim 200$ 批仍在执行时，**绝不能把分片的 `checkpoint_last_id` 直接更新到 300**，否则此时进程崩溃重启就会永久漏掉 $101\sim 200$ 批！必须按连续全部确认完成的最高位点（Contiguous Low Watermark）推进游标，或逐条记录完成状态；
3. **保护下游 RPC 与在线业务（限流与错峰）**：
   一亿次调用若在 3 小时（约 $10,000\text{s}$）内跑完，平均 RPS 高达 $10,000\text{ QPS}$。必须通过全局令牌桶严格限制批处理调用下游 RPC 的最高并发速率，并监控下游在线接口 P99 延迟与数据库主从延迟——一旦发现主从延迟飙升或下游报警，自动动态调低批处理并发度；
4. **单条失败隔离与死信重试**：
   某几条订单因数据异常或下游超时失败时，不能卡住整批进度，应将该订单 ID 与错误原因写入独立的 `batch_failed_records` 补偿表，主游标继续推进，最后单独对失败表做退避重试与人工核对。

### 23. 600GB 至 1TB PDF 知识库怎样做不停服更新？

> **来源**：[S217 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-15.md#L17-L17) 给出 600GB–1TB 金融 PDF 知识库设计场景，并在 [S217 后续记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-15.md#L20-L20) 追问全量 Embedding 成本优化与增量不停服更新。

**回答：**
1. **离线处理管线解耦与算力降本**：
   * **多阶段异步流水线**：将 `文件哈希去重 -> PDF 版面解析/OCR -> 结构化切块 -> Embedding 向量编码 -> 索引写入` 拆解为由消息队列连接的独立阶段，使 CPU 密集型解析与 GPU 密集型 OCR/Embedding 各自按瓶颈独立扩缩容；
   * **内容级哈希缓存（节省 70%+ 重复 Embedding 成本）**：金融文档改版或全量重跑时，绝大多数段落并未修改。以 `(embedding_model_version, normalized_chunk_text_sha256)` 作为键值缓存已计算的向量，增量更新或重建索引时直接命中复用，仅对真正发生文字变动的 Chunk 调用 GPU 编码。
2. **在线零停机更新（读写物理隔离 + 双代际别名切换）**：
   * **文档级日常增量更新**：先写入带新版本号 `doc_version` 的新 Chunk 记录并完成索引可见，再切换主表有效版本指针并异步清理旧版本 Chunk，确保用户查询任何时刻都不会搜到“删了一半的空窗期”；
   * **全库级模型升级或分块规则重构**：新建独立的蓝绿集合/索引（`kb_index_v2`），后台低优批量构建完成后，回放期间的增量变更与权限撤回事件直至完全追平；验证无误后通过集合别名（Alias）毫秒级原子切流。注意：**权限撤销（ACL Revocation）与合规删除列表必须独立于索引版本实时强制生效**，即使紧急回滚到旧索引 `v1`，也绝不能让已被撤权下线的敏感文档重新暴露。

### 24. 多实例刷新第三方 Token，怎样防风暴与旧结果覆盖？

> **来源**：[S268 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-23.md#L53-L53) 给出多实例共享第三方 Token 缓存刷新的设计题，并在 [S268 后续记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-23.md#L56-L56) 连续追问刷新失败、迟到旧 Token 覆盖、持锁实例崩溃与锁超时场景。

**回答：**
当后端部署了数十个实例共用同一个第三方平台（如企业微信、支付网关或 OAuth 服务商）的 `access_token` 时，如果等到期那一秒所有实例各自去调第三方刷新接口，不仅会引发**并发刷新风暴触发第三方限流**，更会因为**第三方每次签发新 Token 即作废上一个刚签发的 Token（或 Refresh Token 单次轮换作废，参考 [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14)）**导致大批实例拿着刚刷出来就被顶掉的失效 Token 全线报错。

**高可靠防风暴与防覆盖完整设计**：
1. **逻辑提前刷新（Soft TTL + 后台单点主動刷新）**：
   假设第三方 Token 物理有效期为 $7200\text{s}$（2 小时），在 Redis 缓存中设置逻辑刷新阈值为 $6000\text{s}$。在到期前 20 分钟，由定时任务或首个发现到达逻辑阈值的实例尝试获取 Redis 分布式刷新锁 `lock:token_refresh`，**其余所有正常业务实例无需阻塞等待，直接继续使用当前仍在物理有效期内（剩余 20 分钟）的旧 Token 正常发请求**；
2. **Double-Check（双重检查）防止持锁崩溃或锁超时后的重复刷新**：
   当某实例抢到刷新锁后，**必须再次读取 Redis 中的 Token 版本/签发时间**。如果发现其他实例刚刚已经刷新成功（例如前一个持锁实例虽然慢但刚写完新 Token），则直接释放锁返回最新 Token，不再重复调用第三方；
3. **单调版本号/过期时间 CAS 写回（防迟到旧结果覆盖新结果）**：
   写回 Redis 时通过 Lua 脚本原子校验：仅当待写入 Token 的签发序号/过期时间戳严格大于缓存中现有记录时才执行覆盖，防止网络卡顿的旧刷新响应晚到覆盖了新 Token；
4. **Refresh Token 轮换（Rotation）防丢响应保障**：
   若第三方启用了 Refresh Token 用一次即作废的轮换机制，刷新前必须先在数据库记录“正在使用 `rt_v1` 刷新”的事务状态；若网络超时未收到新 `rt_v2`，重启后不能盲目重发 `rt_v1` 触发第三方安全封禁，而应先走查询接口或告警触发重新授权兜底。

### 25. 二维码登录怎样防重复交换、过期与跨会话串用？

> **来源**：[S188 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-10.md#L293-L293) 要求讲清 PC 端展示二维码、手机端扫码授权与 Token/Session 签发的完整安全链路。

**回答：**
扫码登录的本质是**用手机端已登录的合法身份，为特定 PC 浏览器的匿名会话完成一次受控的跨端授权绑定**：

1. **四阶段标准状态机流转**：
   * **生成挑战（`PENDING`）**：PC 浏览器请求生成二维码，服务端生成高熵不可预测的唯一标识 `qr_token`（存入 Redis，TTL 设为 120 秒），同时向 PC 浏览器下发一个 `HttpOnly` 的临时设备绑定凭证 `pc_device_secret`（防止其他人仅凭截获的 `qr_token` 在别的电脑上冒领登录态）。注意：**二维码图片内容里只包含 `qr_token`，绝不包含任何账号密码或最终 Token**；
   * **手机扫码待确认（`SCANNED`）**：手机 App 扫码后，携带**手机端自身的登录态 Token** 与 `qr_token` 请求服务端。服务端校验手机登录态有效后，将 Redis 中该 `qr_token` 状态原子更新为 `SCANNED` 并记录扫码人 `user_id`，PC 端通过长轮询或 SSE 感知并展示“已扫码，请在手机上点击确认”；
   * **手机点击确认授权（`CONFIRMED`）**：用户在手机上点击确认，服务端携带一次性防重令牌校验该 `qr_token` 当前确实处于 `SCANNED` 且属于同一 `user_id`，将其状态原子更新为 `CONFIRMED` 并生成一个一次性授权码 `auth_ticket`；
   * **PC 端原子兑换正式会话（`CONSUMED`）**：PC 端持 `qr_token + pc_device_secret` 请求兑换接口，服务端通过 **Redis Lua 脚本原子校验**：`状态 == CONFIRMED` 且 `未过期` 且 `pc_device_secret 匹配`，校验通过后**立即将状态置为 `CONSUMED`（一次性消费作废）**，为该 PC 浏览器签发正式的登录 Session / JWT。
2. **关键安全防线**：
   * **防重复兑换（Replay）**：兑换接口必须使用 CAS / Lua 原子将 `CONFIRMED` 改为 `CONSUMED`，保证同一个二维码绝不可能换出两份登录态；
   * **防跨会话劫持（Session Fixation / QRLJacking）**：兑换时强制核对初始生成二维码的 `pc_device_secret`，并在手机确认页展示 PC 端的请求地理位置与浏览器机型供用户核验。

### 26. SGX 题给出单用户 1GB、EPC 约 512MB，怎样回答而不套普通容器？

> **来源**：[S244 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L167-L167) 给出 SGX 机密计算多租户与单用户约 1GB 数据的场景，并在 [S244 后续记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L168-L168) 追加 EPC 约 512MB 及频繁换页（Paging）的性能与安全保护追问。

**回答：**
Intel SGX（Software Guard Extensions）属于硬件级可信执行环境（TEE / Enclave），其威胁模型假设**宿主机操作系统、Hypervisor 和云平台管理员均不可信**，这与共享宿主机内核的普通 Docker 容器有本质区别：

1. **为什么单用户 1GB 数据、硬件 EPC（Enclave Page Cache）仅 512MB 时，直接运行会导致性能雪崩**：
   EPC 是处理器通过内存加密引擎保护的专用物理安全内存区。当 Enclave 内部活跃内存超过 512MB EPC 上限时，系统并不会直接崩溃，而是触发 **EPC 安全换页（Secure Paging）**：将超出的内存页经过 AES-GCM 加密、计算完整性校验树（完整性与防重放计数器更新）后换出到普通不可信宿主内存，需要时再解密验签换回。每次安全换页的开销比普通操作系统内存访问高出数个数量级，若多个 1GB 租户并发常驻，会引发剧烈的 **EPC 换页抖动（Thrashing）**，导致吞吐彻底归零[（参考 Intel SGX EPC 换页机制说明）](https://www.intel.com/content/www/us/en/support/articles/000088228/software/intel-security-products.html)；
2. **架构破局设计（最小化可信计算基 TCB + 流式分块加载 + 调度准入控制）**：
   * **热工作集裁剪与流式分块（Streaming Chunk Processing）**：不把单用户 1GB 原始数据全量一次性解密加载进 Enclave。将 1GB 数据在宿主普通内存/磁盘中按例えば $16\text{MB}$ 分块加密存储（附带 Merkle Tree 防回滚校验），Enclave 每次仅按需流式拉取当前正在计算的几十兆活跃分块解密处理，使单个任务的 Enclave 常驻工作集严格压在 $50\sim 100\text{MB}$ 以内；
   * **将非敏感外围逻辑剥离出 Enclave**：网络 I/O、任务排队、公开元数据路由留在不可信宿主侧（Untrusted Host），仅将核心密钥管理与敏感明文计算放入 Enclave，同时批量合并跨边界调用（减少昂贵的 `ECALL / OCALL` 上下文切换）；
   * **以 EPC 预算为核心的调度器**：调度器不再按主机总内存（如 64GB）放行并发，而是严格按 **EPC 水位（512MB）** 限制同时活跃进入 Enclave 的并发任务数（如最多同时运行 $4\sim 6$ 个分块任务），从源头杜绝 EPC 换页抖动。

### 27. 灾备切换为什么必须给 RTO、RPO 和演练结果？

> **来源**：[S019 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L119-L119) 询问服务宕机后如何保障业务连续性与数据不丢失。

**回答：**
高可用与灾备设计必须量化两个核心目标（[参考 AWS 灾备架构指南](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/plan-for-disaster-recovery-dr.html)）：
* **RTO（Recovery Time Objective，恢复时间目标）**：故障发生后，从系统中断到**服务完全恢复对外正常可用**所允许的最长时间（决定采用冷备、热备还是多活架构）；
* **RPO（Recovery Point Objective，恢复点目标）**：故障发生时，系统最多允许**丢失多长时间窗口内产生的数据**（决定存储层采用异步复制、半同步复制还是跨机房强同步）。

**为什么“配了主从副本和每日定时备份”不等于满足了灾备要求**：
1. **未经恢复演练的备份等于没有备份**：定时备份文件可能损坏、缺少解密密钥，或者全量恢复 2TB 数据加上重建向量索引实际耗时高达 4 小时（远超承诺的 $15\text{ 分钟}$ RTO）；
2. **主从异步复制下的脑裂与未决副作用**：主库宕机瞬间，尚未同步到从库的最后几秒已提交事务在从库升主后丢失（RPO $>0$）。在 Agent 系统中，如果这几秒恰好包含“已调用外部支付接口但 Checkpoint 未同步到从库”的记录，故障切流后新主节点必须先对未决状态（`IN_PROGRESS`）执行外部对账，防止灾备恢复后发生二次重复扣款。

### 28. 怎样验证设计，而不是只说“压测一下”？

> **来源**：[S379 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L4293-L4294) 问并发测试、失败定义与性能优化；[S268 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-23.md#L58-L58) 要求证明方案不只覆盖正常路径（Happy Path）。

**回答：**
验证一套分布式或 AI 系统设计，需要分别从**并发不变量验证、故障注入演练（Chaos Engineering）与真实分布压测**三个维度给出可证伪的测试方案：

1. **业务不变量对账测试（Invariant Verification）**：
   并发发起包含重复重试、中途取消、立即退款的混合请求流，压测结束后运行自动化对账脚本，验证硬性不变量是否 100% 成立（如：`总扣减库存 == 有效已支付订单数`、同一个幂等键绝无两条成功扣费流水、跨租户检索 0 越权命中）；
2. **定向故障注入（专测非 Happy Path 边界）**：
   * 在工具执行成功返回后、写本地 Checkpoint 之前强杀 Worker 进程（`kill -9`），验证重启后是否走幂等对账而非重复执行；
   * 通过代理注入第三方大模型 API 50% 超时或 `429` 限流，验证熔断器、备用模型切换以及预占 Token 预算是否准确退还无泄漏；
   * 模拟 Worker 进程暂停（`SIGSTOP`）直到租约过期后再恢复（`SIGCONT`），验证数据库的 `fencing_token` 是否成功拦截旧 Worker 的脏写；
3. **符合线上长尾分布的容量压测**：
   压测输入不能用同一条短 Prompt 反复打（这会被缓存 100% 命中，测不出真实瓶颈），必须按线上真实的输入输出长度分布（含 10% 超长上下文与多轮工具调用）回放，同时观测有效任务吞吐、排队年龄（Queue Age）与 P99 尾延迟拐点。

### 29. 客服、财务分析、游戏助手这类垂直 Agent 如何迁移设计思路？

> **来源**：[S240 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L31-L31) 考察上市公司毛利率财务分析链路设计；[S260 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-22.md#L134-L134) 考察游戏智能客服与助手架构设计。

**回答：**
面对任何垂直领域的 AI 系统设计题，均可通过**“拆解权威事实源 + 划定确定性计算与模型推理边界 + 设定风险拦截点”**三步迁移：

1. **智能电商/游戏客服系统**：
   * **知识与实时状态分离**：退换货政策、游戏攻略走 RAG 知识库检索；玩家当前装备状态、订单物流、封号原因走确定性业务 API 实时查询（绝不相信历史对话里缓存的旧状态）；
   * **风险拦截**：安抚情绪与解答规则由模型自主生成；一旦涉及补发道具、阶梯退款或解封账号，必须由代码规则引擎硬性校验资格，大额操作转人工客服工单审批（HITL）。
2. **金融研报/上市公司财务分析系统（如毛利率变动归因）**：
   * **取数、计算与解读严格分离**：财报附注文本走表格保真解析与混合检索；各季度营业收入、营业成本等原始科目数值从结构化财务数据库（Text-to-SQL 或受控指标 API）提取；**同环比増速与毛利率计算公式（$\frac{\text{营收}-\text{成本}}{\text{营收}}$）100% 交给 Python 代码沙箱或指标引擎精确计算**，绝不允许大模型心算浮点数；
   * **可追溯审计**：最终生成的分析报告中，每一个财务数字和归因结论都必须绑定财报原页码与数据库查询回执，无数据支撑的推测强制拦截。

### 30. 分布式限流怎样兼顾硬上限、可用性和突发？

> **来源**：[S201 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-11.md#L229-L229) 要求分别设计单机、分布式与全局限流；[S270 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-24.md#L27-L28) 追问限流的一致性、性能开销和中心故障降级策略。

**回答：**
1. **限流算法选型（解决边界突发与平滑控制）**：
   * **固定窗口计数器**：实现最简单，但在窗口交界处（如第 0.9 秒和第 1.1 秒各打满 100% 配额）会出现**2 倍速率的临界双倍突发**；
   * **滑动窗口（如 Redis ZSet 或多细粒度时间子桶）**：消除临界双倍突发，精确控制时间窗内的总请求量；
   * **令牌桶（Token Bucket）**：以恒定速率生成令牌存入桶中（有最大桶容量 $B$），既能限制长期平均速率，又允许业务在桶满时合法吸收最高为 $B$ 的瞬态突发流量，是网关限流的首选。
2. **集中式 Redis 限流 vs 本地预分配步长（Batch Quota Leasing，兼顾硬上限与极致性能）**：
   * 若每秒数十万次请求全部同步调用中心 Redis Lua 脚本，既增加每次请求 $1\sim 2\text{ms}$ 的网络 RTT，又容易把中心 Redis 单 Key 打成热点；
   * **守恒配额批量批发方案**：中心 Redis 维护全局总配额（例如每秒 10,000 次）。各网关节点每次向中心 Redis **批量申请一小块带有效期的本地配额（如一次批发 100 个令牌）**，之后在网关本地内存中原子扣减这 100 个令牌（零网络开销），用完或到期再去中心续领。只要中心发出的配额总和不超过 10,000，就能在降低 99% Redis 访问压力的同时，**严格守住全局不超发的硬上限**。
3. **中心 Redis 故障时的降级策略（Fail-open vs Fail-closed）**：
   * **面向内部服务保护的普通接口限流**：采用 **Fail-open（或退化为单机本地兜底限流，即每台网关按 `全局限额 / 网关节点数` 独立限流）**，优先保障主业务可用性；
   * **面向高昂商业 API 预算或活动奖金发放的硬额度限制**：必须采用 **Fail-closed（拒绝放行或仅允许消耗完节点已批发到本地的剩余安全额度）**，防止缓存故障期间预算被无限打穿。
