## 1. 从 URL 到响应，怎样说清一条请求链？

> **来源**：[S294](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-33.md#L22-L23)实际涵盖URL链路、握手及网关和重定向状态码；下文把这些问题放回请求时间线。

**回答：**
从浏览器输入 URL 到最终获取响应，完整请求生命周期分为五个标准阶段：

1. **URL 解析与 DNS 查询**：解析协议、域名与端口。依次查询浏览器缓存、操作系统 hosts、本地 DNS 递归服务器，最终向根/顶级/权威域名服务器解析得到目标服务器 IP 地址；
2. **传输层建连与安全握手**：
   * TCP 三次握手建立可靠传输连接；
   * 若为 HTTPS，进行 TLS 握手（校验证书有效性与域名、协商对称加密密钥）；
3. **网关路由与协议解析**：请求到达负载均衡与 API 网关（如 Nginx / Envoy），网关完成 SSL 卸载、动态鉴权、限流、并将请求转发至内部微服务；
4. **后端应用处理与 I/O 调用**：Web 框架解析 HTTP 协议，调度线程池或异步事件循环执行业务逻辑，按需访问 Redis 缓存、MySQL 数据库或外部 RPC 服务；
5. **响应封装与客户端渲染**：服务端组装 HTTP 响应头与数据体并写回 Socket，客户端浏览器解析响应体完成页面渲染，若为 Keep-Alive 则复用该 TCP 连接。

**追问：网关返回 502 Bad Gateway 和 504 Gateway Timeout 有什么本质区别？**
**回答：**
* **502 Bad Gateway**：网关作为代理，尝试连接上游服务失败（如上游服务挂掉、进程崩溃、端口未监听），或者上游服务提前异常关闭连接返回了无效响应；
* **504 Gateway Timeout**：网关成功连接上了上游服务，但在网关配置的超时时间内（如 60 秒），上游服务一直卡在耗时计算或数据库慢查询中，未能及时向网关返回任何响应体。

## 2. TCP 为什么握手要三次、挥手要四次？为什么会有 2MSL 等待？

> **来源**：[S175](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-09.md#L322-L322)把关闭追到最后ACK丢失，[S214](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-14.md#L63-L63)把已连接场景改为一端崩溃；握手与关闭原理是理解这些追问的基础。

**回答：**
* **为什么握手必须三次**：
  核心在于**双方同步初始序列号（ISN）并防止历史失效连接被误建立**。两次握手无法防止历史延迟的旧 SYN 报文到达服务端时被错误初始化连接，导致服务端单方面空耗资源；三次握手允许客户端在收到旧 SYN+ACK 时发送 RST 终止连接。
* **为什么挥手通常需要四次**：
  因为 TCP 是**全双工通信**，两个方向的通道必须独立关闭。当主动方发送 `FIN` 表达“我不再发送数据”时，被动方回复 `ACK` 表示“确认收到你停止发送，但我可能还有数据要发给你（半关闭状态）”；只有当被动方自己的数据全部发完后，才会单独发送 `FIN` 给主动方。因此 `ACK` 与 `FIN` 往往分开发送，需要四次交互。
* **TIME_WAIT 状态为什么要等待 2MSL（两倍最大报文生存时间）**：
  1. **保证最后一个 ACK 能够可靠到达被动方**：若主动方最后的 ACK 丢失，被动方会重发 FIN，主动方在 2MSL 内可以捕获重发的 FIN 并重新发送 ACK；
  2. **使网络中残留的所有旧连接数据包彻底消亡**：防止该四元组被立即复用于新连接时，迟到的旧报文干扰新连接。

## 3. TLS 证书和加密各做什么？

> **来源**：[S117](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L64-L66)问Body加密与TLS版本，[S269](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-23.md#L82-L83)问机密完整性和CA信任链；不能只答“有证书”。

**回答：**
TLS 采用**非对称加密完成身份鉴权与密钥协商，对称加密完成传输数据保护**：

1. **数字证书与身份鉴权（CA 信任链）**：解决“中间人伪造服务器”问题。服务器将其公钥与域名信息由受信任的 CA 机构私钥进行数字签名。客户端用操作系统/浏览器内置的受信任根证书公钥解密并验签，确认服务器的真实身份；
2. **密钥协商与非对称加密**：握手阶段通过 ECDHE / RSA 算法，在不可信网络上安全协商出临时的会话共享密钥（Pre-Master Secret）；
3. **对称加密传输数据**：握手成功后，所有的 HTTP 请求体和响应体均使用协商出的对称密钥（如 AES-GCM 或 ChaCha20-Poly1305）进行加解密。对称加密速度极快，保证了传输的机密性与防篡改完整性。

## 4. HTTP/2、HTTP/3 为什么仍不能保证应用层实时性？

> **来源**：[S224](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-15.md#L189-L189)对比HTTP各版本并追内部HTTP2选择，[S149](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L139-L139)追QUIC相对HTTP2/TCP的改进；应用排队是取舍说明。

**回答：**
* **协议层演进解决了什么**：
  * **HTTP/2**：引入多路复用（Multiplexing），单 TCP 连接并发传输多个流，解决了 HTTP/1.1 的应用层队头阻塞；但底层依然基于 TCP，一旦单个 TCP 数据包丢失，由于 TCP 严格保序，会阻塞该连接上**所有其他并发流的交付（传输层队头阻塞）**；
  * **HTTP/3（基于 UDP 的 QUIC）**：将流独立化，单个流丢包只影响该流自身，彻底消除了传输层的队头阻塞，且支持 0-RTT 建连与连接迁移。
* **为什么仍不能保证应用层绝对实时**：
  网络传输优化只消除了网络层排队。在真实业务系统中，**延迟瓶颈往往在应用服务端**：
  1. 服务端线程池打满导致的请求排队；
  2. 数据库连接池排队与慢 SQL 查询；
  3. 复杂大模型推理等待时间（首字延迟 TTFT）；
  传输协议再快，也无法缩短服务端的实际运算与 I/O 阻塞时间。

## 5. SSE、WebSocket 和轮询怎样选？断线怎样恢复？

> **来源**：[S083](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L191-L191)明确比较SSE与WebSocket，[S397](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L748-L750)明确追Room和重连恢复；事件保留协议是完成任务所需的设计展开。

**回答：**
* **技术选型权衡**：
  * **轮询（短轮询/长轮询）**：适合低频、状态变化稀疏的后台任务查询。缺点是频繁建连、头部开销大、实时性差；
  * **SSE（Server-Sent Events）**：**单向持续推流的首选**（如大模型 Token 流式吐字、构建状态推送）。基于标准 HTTP 协议，实现最轻量，天然穿透 CDN 和企业代理，浏览器原生支持断线自动重连；
  * **WebSocket**：**高频全双工实时交互的首选**（如多人实时协同白板、实时语音对讲、网络游戏）。缺点是维护有状态长连接成本高，心跳保活和网关负载均衡复杂。
* **断线恢复标准方案**：
  1. **稳定事件游标与重放**：每个推送事件附带全局单调自增的序列号（SSE 为 `id`）。客户端断线重连时携带最后成功接收的游标（如 `Last-Event-ID`）；
  2. **服务端环形缓冲区**：服务端保留一定时间窗口内的事件缓存。若重连游标在窗口内，直接重发增量事件；若游标严重过时，则推送当前状态全量快照，再衔接增量流。

## 6. Java 线程池怎么接任务？core 为 4 时进来 8 个任务会怎样？

> **来源**：[S145](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L50-L50)要求解释接单复用，[S214](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-14.md#L56-L56)给出core为4、8任务及队满分支；未披露的队列和max不能自行补定。

**回答：**
* **ThreadPoolExecutor 任务接纳四步标准流转**：
  1. 若当前运行线程数 `< corePoolSize`，立即创建核心工作线程执行新任务；
  2. 若当前运行线程数 `>= corePoolSize`，尝试将任务放入阻塞队列（`workQueue.offer()`）；
  3. 若队列已满且当前运行线程数 `< maximumPoolSize`，创建非核心临时工作线程执行该任务；
  4. 若线程数已达 `maximumPoolSize` 且队列仍满，触发拒绝策略（`RejectedExecutionHandler`）。
* **分析“core=4，进来 8 个任务”的行为**：
  **答案取决于工作队列容量与最大线程数配置**（前 4 个任务会立即占用 4 个核心线程执行）：
  * **若使用的是无界队列（或容量 >= 4 的有界队列）**：后 4 个任务全部进入队列排队等待，当前线程数保持为 4；
  * **若使用的是容量为 2 的有界队列且 max=6**：第 5、6 个任务入队，第 7、8 个任务触发创建 2 个非核心线程执行，总线程数扩充到 6；
  * **若队列已满且无法再创建新线程**：超出容量的任务直接触发拒绝策略（如抛出 `RejectedExecutionException`）。

## 7. 线程数、队列和下游连接池怎样协同配置？

> **来源**：[S216](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-14.md#L132-L135)要求按CPU/IO资源配置线程池，[S147](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L100-L100)给出生产与下游容量不匹配；虚拟线程用于补充Java版本边界。

**回答：**
必须按任务特性、系统瓶颈与下游承载力协同匹配：

1. **线程数配置**：
   * **CPU 密集型**：线程数设为 `CPU 核心数 + 1`，避免多线程频繁上下文切换争抢 CPU；
   * **I/O 密集型**：线程数设为 `CPU 核心数 * (1 + 等待时间/计算时间)`。在 I/O 等待期间充分利用 CPU。
2. **队列容量严禁无界**：
   使用无界队列（如默认 `LinkedBlockingQueue`）会导致任务无限堆积，最终直接引发 OOM，且无法触发最大线程数扩容与拒绝策略背压。队列大小应根据最大可容忍排队延迟配置（`队列长度 = 最大容忍等待时长 * 处理 QPS`）；
3. **与下游连接池匹配（防止下游雪崩）**：
   服务实例的并发工作线程总数绝不能超过其数据库连接池（如 HikariCP）的上限。在集群部署时，`单机连接池上限 * 服务实例总数` 必须严格小于数据库服务器所能承受的最大并发连接数，防止服务一扩容就打死数据库。

## 8. 超时、取消和真正结束为什么不同？

> **来源**：[S036](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L93-L93)直接追长任务取消是否实现测试，[S110](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-06.md#L375-L376)要求100个ID最多3个并发API；区分本地终结与远端状态是正确性展开。

**回答：**
三者是异步任务不同层级的生命周期状态，不可等同：

1. **超时（Timeout）**：仅代表**调用方单方面停止了同步等待**。被调用的后台线程或远端服务此时极有可能仍在继续执行；
2. **取消（Cancellation）**：是向执行方发送**中断停止的协作信号**（如 Java 的 `thread.interrupt()` 或 Go 的 `ctx.Done()`）。这要求执行方代码主动感知该信号并协作退出；如果代码正在执行不可中断的同步阻塞 I/O，任务依然会继续运行；
3. **真正结束（Termination）**：代表任务内部的所有计算与 I/O 已经彻底退出，持有的物理连接、文件句柄和外部状态均已完成安全释放或落库回滚。

**追问：遇到“100 个任务最多允许 3 个并发调用外部 API”时，如何设计？**
**回答：**
使用容量为 3 的信号量（Semaphore）严格控制发放。每个任务必须在获得许可后才能发起调用，并在 `finally` 块中确保释放许可。若任务中途超时，不能仅在本地单方面归还许可，必须确保已发起的外部网络请求已彻底终止或在超时后被安全关闭，防止由于远端仍在执行而超额消耗下游配额。

## 9. 异步任务怎样避免异常被吞和互相等死？

> **来源**：[S313](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L526-L526)问Future异常传递，[S137](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L561-L561)问Worker异常和业务感知；同池等待子任务是资源饥饿的教学反例。

**回答：**
* **防止异常被静默吞掉**：
  使用 `executor.submit()` 提交的任务，若内部抛出未捕获异常，异常会被保存在返回的 `Future` 对象中，不会直接打印到标准错误。调用方必须显式调用 `future.get()`（或在 `CompletableFuture.exceptionally()`）中捕获异常；若使用 `execute()` 提交，必须为线程池配置 `UncaughtExceptionHandler`。
* **防止线程池互相等死（线程饥饿死锁）**：
  严禁**父任务占用线程池的工作线程，并在函数内部同步阻塞等待同一个线程池处理其子任务**。
  如果线程池核心数为 4，同时进来了 4 个父任务占满了全部 4 个工作线程，它们生成的子任务全都在队列中排队等待空闲线程，导致父任务永远在等子任务完成，子任务永远拿不到线程执行，引发死锁。
  *解法*：实行线程池物理隔离，父任务与子任务分配到不同的独立线程池。

## 10. ThreadLocal 为什么会泄漏和串用户？

> **来源**：[S339](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L2113-L2115)问Key强弱引用及理由，[S262](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-22.md#L187-L188)问泄漏与异常清理；不能把弱Key推导成Value立即释放。

**回答：**
* **底层原理**：每个 `Thread` 对象内部持有一个 `ThreadLocalMap`。Map 中的条目（Entry）继承了 `WeakReference<ThreadLocal<?>>`，其 **Key 是弱引用，但 Value 是强引用**。
* **内存泄漏原因**：当外部强引用被置为 null 后，垃圾回收期会回收弱引用的 Key，此时 Map 中出现了 `Key 为 null，但 Value 依然强引用着业务对象` 的条目。如果当前线程长期不销毁（如 Web 容器的复用线程池），这条强引用链 `Thread -> ThreadLocalMap -> Entry -> Value` 就会一直存在，导致 Value 对象永远无法被垃圾回收，引发内存泄漏。
* **串用户数据原因**：Web 容器（如 Tomcat）采用线程池复用工作线程。如果请求处理完毕后没有显式清理 ThreadLocal，当同一个线程被复用来处理下一个用户的请求时，若代码直接读取 ThreadLocal，就会读取到上一个用户的会话信息，发生严重的数据串号。
* **规避铁律**：必须在请求拦截器或业务处理的最外层使用 `try-finally`，在 `finally` 块中强制调用 `threadLocal.remove()` 清理。

## 11. Go GMP、Channel 和 Mutex 怎样回答？

> **来源**：[S110](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-06.md#L369-L370)实际比较Channel/Mutex并追GMP空队列取任务；流水线退出是机制应用的教学展开。

**回答：**
* **GMP 调度模型**：
  * **G（Goroutine）**：用户态轻量级协程，栈内存动态伸缩（初始仅 2KB）；
  * **M（Machine）**：操作系统的真实物理线程；
  * **P（Processor）**：执行 Go 代码所需的逻辑处理器与上下文资源（数量由 `GOMAXPROCS` 决定），每个 P 持有一个本地就绪队列（Local Run Queue）。
  * *调度与工作窃取（Work Stealing）*：当 P 本地队列无任务时，优先从全局队列拉取，若全局队列为空，从其他 P 的本地队列尾部随机“偷取”一半的 G 过来执行；当 G 进行阻塞系统调用时，M 会与 P 解绑，P 转去寻找其他 M 继续工作。
* **Channel 与 Mutex 选型原则**：
  * **选 Channel**：用于**数据传递、控制流协调、以及所有权的转移**（“通过通信共享内存”）。例如工作分发流水线、退出广播（`select + context`）；
  * **选 Mutex**：用于**保护进程内部的细粒度共享内存状态**。例如缓存字典保护、计数器更新。结构简单时用互斥锁性能和内存开销更优。

## 12. 重试、熔断、降级怎样共同守住失败预算？

> **来源**：[S079](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L107-L107)辨析熔断降级限流，[S359](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3169-L3172)要求重试实现并追工具失败；首次尝试是否计入上限的缺失条件必须保留。

**回答：**
三者是分布式系统稳定性建设的纵深防御三板斧：

1. **重试（Retry）**：针对**偶发性、短暂的网络抖动或限流**。必须遵循三原则：仅对幂等或只读操作重试、采用指数退避加随机抖动、严格限制最大重试次数（通常最多 2 次），严禁多层微服务级联重试放大流量；
2. **熔断（Circuit Breaker）**：针对**持续不可用的下游故障**。监控下游失败率或慢调用比例：一旦达到阈值，熔断器打开，后续请求直接快速失败，不再向故障下游发送流量，防止线程池被拖死；经过熔断冷却期后进入半开状态，放行少量金丝雀流量探测恢复；
3. **降级（Fallback）**：针对**熔断触发或系统过载时的兜底保障**。当核心依赖不可用时，执行备选策略（如返回默认兜底值、本地旧缓存数据、或直接异步排队提示“系统繁忙请稍后查看”），保证核心主链路不中断。

## 13. 消息队列在哪些地方会丢消息？为什么确认后仍可能重复？

> **来源**：[S104](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-06.md#L208-L208)考RabbitMQ消费与可靠性，[S207](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-12.md#L57-L57)明确给出落库成功而发送失败；Outbox作为解法说明，不冒充另一道已披露原题。

**回答：**
* **丢消息的三个阶段与防御**：
  1. **生产端丢失**：网络抖动导致消息未到达 Broker。*解法*：开启生产端同步 Confirm 确认机制，失败重试；
  2. **Broker 存储丢失**：消息停留在操作系统 PageCache，尚未刷盘服务器掉电，或主从异步复制时主节点宕机。*解法*：开启多副本同步复制与同步刷盘配置；
  3. **消费端丢失**：消费者配置了自动 ACK，刚拉取到消息就向 Broker 发送了确认，随后业务处理发生异常崩溃。*解法*：关闭自动 ACK，必须在业务处理成功并落库后，才显式发送手动 ACK。
* **为什么确认后仍可能重复（At-Least-Once 语义）**：
  因为**业务处理成功与发送 ACK 并非分布式原子操作**。消费者成功完成了业务数据落库，但在发送 ACK 给 Broker 时网络闪断、或消费者进程刚好崩溃，Broker 在超时后未收到 ACK，会将该消息重新投递给集群中其他消费者，发生重复消费。因此消费端必须具备业务幂等性。

## 14. 跨机器重复消息怎样保证业务只生效一次？

> **来源**：[S326](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1188-L1190)要求跨A/B机器处理重复消息，[S342](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L2264-L2264)要求避免重复回调扣费；锁不能替代业务幂等。

**回答：**
单机的内存 Set 或线程锁无法跨物理节点生效，必须在**共享存储层通过分布式原子约束**实现严格幂等：

1. **关系型数据库去重表（唯一主键索引）**：
   建立一张消费流水表，以业务唯一标识（如 `order_sn` 或 `biz_id`）设置唯一主键索引。业务处理与向流水表插入记录**放在同一个本地数据库事务中执行**。若重复消息到达，数据库抛出唯一键冲突异常，事务自动回滚并向 MQ 返回成功 ACK；
2. **状态机前置条件跃迁（单向条件更新）**：
   业务订单状态遵循单向流转（如 `INIT -> PAID -> DELIVERED`）。更新操作强制附带前置条件：
   ```sql
   UPDATE orders SET status = 'PAID' WHERE id = ? AND status = 'INIT';
   ```
   若受影响行数为 0，说明该状态已被其他并发节点修改过，直接丢弃该消息；
3. **Redis 分布式锁防瞬态重入**：
   在消息处理入口使用 `SET biz_id:lock unique_val NX EX 30` 抢占排他锁，防止同毫秒内的极高并发请求同时穿透到数据库。

## 15. Kafka 的顺序、积压和 Exactly-Once 怎么讲边界？

> **来源**：[S165](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-09.md#L122-L122)问Kafka积压归因，[S279](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-26.md#L143-L143)问消费可靠与业务幂等；exactly-once作为保证范围的教学辨析，不新增原题。

**回答：**
* **严格保序的边界**：
  Kafka **只保证单个 Partition（分区）内部的消息局部有序，无法保证跨分区的全局有序**。若要保证特定业务对象的处理顺序，生产端发送时必须指定相同的 Message Key（按 Key 哈希路由到同一 Partition）。消费端在单个 Partition 内必须单线程串行处理，如果在消费端内部引入线程池多线程并发，顺序性依然会被打乱。
* **积压排查与治理**：
  先通过监控确认是**生产速率突增**还是**消费端变慢（下游慢 SQL、GC 停顿、死锁）**。治理手段包括：扩充 Topic 分区数并增加消费组实例、批量消费合并处理、或针对耗时的下游 I/O 改写为受控并发。
* **Exactly-Once（精确一次）的适用边界**：
  Kafka 官方的 Exactly-Once 仅覆盖 **Kafka 内部的读-处理-写闭环（Kafka 到 Kafka）**，由幂等生产者与事务协调器（Transaction Coordinator）共同保证。一旦下游写入的是外部 MySQL 或调用外部第三方接口，必须依靠业务系统的幂等性与两阶段对账才能实现全局的一致性。

## 16. RocketMQ 事务消息怎样减少本地事务与发消息的不一致？

> **来源**：[S010](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L223-L223)与[S363](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3431-L3431)均直接询问RocketMQ事务消息机制；回查和下游边界来自官方机制解释。

**回答：**
RocketMQ 采用**两阶段提交与事务反查机制**实现最终一致性：

1. **第一阶段：发送半消息（Half Message）**：生产者发送事务消息给 Broker。Broker 将该消息保存在内部特殊的不可见主题中，此时消费者完全无法消费该消息；
2. **第二阶段：执行本地事务并提交二次确认**：
   * 生产者执行本地数据库事务；
   * 若本地事务提交成功，向 Broker 发送 `Commit` 指令，半消息转为可见状态，消费者开始消费；
   * 若本地事务失败，向 Broker 发送 `Rollback` 指令，Broker 丢弃该半消息。
3. **补偿机制：事务状态反查（Check Transaction）**：
   若生产者在提交本地事务后、发送二次确认前发生网络断开或进程崩溃，Broker 会在超时后主动向生产者集群发起反查。生产者反查本地数据库持久化状态决定补发 Commit 还是 Rollback，从而彻底闭合了一致性漏洞。

## 17. 长任务和批量导入如何可靠恢复？

> **来源**：[S232](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-17.md#L46-L46)指定中途导入失败后的防重恢复，[S293](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-32.md#L51-L51)指定视频合并失败后的文件清理；两者在此合为恢复训练，不宣称同场连续题。

**回答：**
核心在于**状态外置、分批提交与断点重放设计**：

1. **任务元数据持久化**：生成全局唯一的 `task_id`，将任务状态（`PENDING / RUNNING / FAILED / SUCCESS`）、已处理游标（`last_processed_id` 或 `batch_index`）持久化至数据库；
2. **批次幂等提交**：严禁单一大事务执行上万条导入。必须切分为小型批次（如每批 500 条），在同一事务中完成“业务数据插入”与“推进处理游标”。即使第 10 批失败崩溃，重启后可直接从第 9 批的完成游标继续执行；
3. **临时文件与产物隔离**：多媒体或长文件处理时，中间切片文件以 `task_id` 建立独立目录隔离。全部步骤验证通过后才执行原子重命名发布；任务失败时执行清理回调删除孤儿临时文件。

## 18. SQL 已优化但接口仍慢，CPU 不高为何系统 Load 也会很高？

> **来源**：[S293](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-32.md#L54-L55)保留SQL已优化后仍慢的时间前提，[S070](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L399-L399)明确追低CPU高Load；容器配额用于进一步排障的教学展开。

**回答：**
* **SQL 变快但接口仍慢的排查方向**：
  说明主要瓶颈不在 SQL 执行本身。应通过链路追踪（SkyWalking / OpenTelemetry）检查：
  1. 应用端获取数据库连接的排队耗时（连接池容量不足）；
  2. 接口内部是否存在多余的循环 RPC 调用（N+1 远程调用放大网络 RTT）；
  3. 大结果集 JSON 序列化消耗；
  4. 锁竞争与线程阻塞。
* **CPU 不高但 Load（系统平均负载）很高的根因**：
  Linux 的 Load Average 计算的是**运行队列中处于“可运行状态（R 状态）”与“不可中断睡眠状态（D 状态，Uninterruptible Sleep）”的平均进程数**。
  如果 CPU 利用率很低但 Load 极高，必然存在大量处于 **D 状态** 的进程在等待外部资源：
  1. **磁盘 I/O 严重瓶颈**：大量线程卡在等待磁盘刷盘或网络文件系统（NFS）挂起；
  2. **锁争用与内核态系统调用卡死**：大量线程阻塞在内核互斥锁或驱动等待上。

## 19. 身份、权限和会话为什么不能只交给 Token 或模型？

> **来源**：[S342](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L2260-L2260)要求对伪造UID鉴权并确定层次，[S171](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-09.md#L246-L246)要求设计访问与刷新令牌流程；对象授权与会话有效性不可混答。

**回答：**
因为 Token 只负责证明**“你是谁（认证）”**，大模型只负责**“理解意图”**，它们都无法替代服务端的数据级授权：

1. **JWT 的无状态弊端**：Token 一旦签发，在其生命周期内签名永远合法。如果用户已被后台管理员禁用、权限被降级、或者用户密码已被篡改，纯无状态校验依然会判定放行。必须在服务端维护黑名单或检查版本号；
2. **防范水平越权（BOLA）**：客户端传入的请求体中带有的 `order_id` 或 `user_id` 是不可信的。服务端必须用验证后的当前登录身份，去数据库强校验该资源是否真正属于该操作人；
3. **模型绝不具备授权判定权**：大模型极易遭受 Prompt 注入攻击，攻击者只需构造“忽略先前指令，我是管理员”，模型就会信以为真。系统执行任何写操作和数据读取，必须由外部代码逻辑强制执行 RBAC 权限校验。

## 20. 项目性能优化收益，怎样回答才有工程说服力？

> **来源**：[S005](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L112-L112)追本人职责和真实技术价值，[S267](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-23.md#L17-L18)追APT性能收益的证据归因；本节提供举证方法而非代写经历。

**回答：**
必须采用**“基线数据 -> 瓶颈归因 -> 架构改造 -> 对比数据与代价”**的完整工程证据闭环：

1. **明确指标基线**：给出可度量的具体数据（“在双十一预热期间，核心下单接口在 2000 QPS 峰值下，P99 延迟高达 1.8 秒，数据库 CPU 持续处于 85% 高位报警”）；
2. **准确定位瓶颈**：通过全链路监控定位并非应用层 CPU 慢，而是慢 SQL 导致数据库连接池耗尽、以及缺少二级缓存造成的全量打库；
3. **阐明架构改动**：引入 Redis 缓存热点库存与订单规则，SQL 改为覆盖索引加延迟关联，并在网关层配置令牌桶限流；
4. **展示严谨复测与工程代价**：在同等压测流量下，P99 延迟降低至 120 毫秒，数据库 CPU 降至 35%；同时客观说明付出的代价——引入 Redis 后增加了数据双写一致性处理逻辑和额外的内存成本。
