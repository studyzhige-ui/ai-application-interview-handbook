## 1. Redis 在系统里应该承担什么？数据丢了怎么办？

> **来源**：[S097](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-06.md#L63-L64)比较数据库与Redis职责及持久存储能力，[S329](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1371-L1373)继续追缓存必要性、重启后果和实际内容；必须先说数据角色。

**回答：**
在现代系统架构中，必须将 Redis 中的数据清晰划分为三类不同职责：

1. **可回源的加速缓存（如商品详情、用户信息）**：权威数据在 MySQL，Redis 仅用于分担高频读取压力。数据丢失或缓存击穿时，由应用层重新查库回填，系统容忍其丢失；
2. **短期协调状态（如分布式锁、滑动窗口限流、验证码）**：利用 Redis 的原子命令与 TTL 过期机制做瞬态状态同步。丢失后租约自然失效，依赖重试或降级兜底；
3. **关键业务暂存（如秒杀库存预扣、去重幂等键、未持久化会话）**：承担了强业务防重责任。此类数据绝对不能简单视为“可随时丢失的缓存”。

**数据丢失应对策略**：
对于关键业务状态，不能单靠 Redis 内存兜底，必须辅以持久化机制（AOF 每秒刷盘 `appendfsync everysec`）和主从复制。若遇到严重故障导致数据丢失，必须依赖权威数据库中的持久化账本（如流水表、已支付订单）进行逆向异步对账与状态回补。

## 2. 单线程为什么仍快？Redis 6 的 I/O 多线程改变了什么？

> **来源**：[S387](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L67-L67)保留Redis6的IO多线程前提，[S274](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-25.md#L95-L95)询问单线程命令执行为何仍快；不能抹掉版本和执行层次。

**回答：**
* **单线程依然极致快的原因**：
  1. **纯内存操作**：所有数据均在内存中，没有磁盘随机 I/O 寻道开销；
  2. **高效的数据结构**：SDS、跳表、压缩列表等专门优化了内存布局与访问时间复杂度；
  3. **I/O 多路复用模型**：基于 epoll 监听海量 Socket 连接，单个线程即可非阻塞处理并发事件；
  4. **无线程上下文切换与锁竞争**：核心命令串行执行，完全避免了多线程间的死锁、互斥锁竞争和 CPU 上下文切换消耗。
* **Redis 6 I/O 多线程的本质**：
  Redis 6 引入多线程**只负责网络 I/O 读写与协议解析（读取 Socket 数据并解析为命令、把执行结果写入 Socket）**。
  **核心业务命令的实际执行依然在单主线程中严格串行执行**。因此多线程 I/O 既突破了单核网络处理带宽的瓶颈，又完美保留了命令天然原子的优势，无需对数据结构加锁。

## 3. String、Hash、Set、ZSet 怎样按任务选？

> **来源**：[S010](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L230-L232)从结构用途追到Set和ZSet底层，[S397](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L752-L754)把Set参与者与ZSet排行落到业务；内部编码变化按官方版本解释。

**回答：**
根据业务语义、访问粒度与排序需求精准选型：

1. **String**：最通用结构。适用于整体序列化存储的对象（如 JSON 字符串）、分布式锁、原子计数器（`INCR/DECR`）、以及 Bitmap 签到打卡；
2. **Hash**：适用于**需要频繁读取或更新局部字段的对象**（如用户信息 `user:{id} -> name/age/level`）。相比全量序列化 String，节省序列化开销与网络带宽；
3. **List**：双向链表。适用于有序的消息队列（`LPUSH/RPOP`）或保留最新固定数量记录的流水展示；
4. **Set**：无序且唯一的集合。适用于好友关系去重、抽奖参与者池、以及集合交集/并集计算（`SINTER` 共同关注）；
5. **ZSet（有序集合）**：每个元素绑定一个浮点数分值（Score）。底层采用**哈希表 + 跳表（SkipList）**，适合**实时动态排行榜**、以及按时间戳作为 Score 实现的**滑动窗口限流器**。

## 4. Cache Aside 怎样更新？为什么删缓存后仍会出现旧值？

> **来源**：[S171](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-09.md#L247-L247)询问Cache Aside，[S352](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L2833-L2834)要求处理缓存查库回填的并发问题；下述时间线用于说明失败窗口。

**回答：**
* **Cache Aside 标准流程**：
  * **读请求**：先读缓存；若命中直接返回；若未命中，读取 MySQL 并写回缓存，最后返回数据。
  * **写请求**：**先更新数据库，再删除缓存**（Cache Invalidation）。
* **为什么删缓存后仍可能产生脏数据（经典并发交错时间线）**：
  1. 缓存刚好失效；
  2. 读请求 A 查缓存未命中，转去查 MySQL，读到了旧值 $V1$；
  3. 写请求 B 更新 MySQL 为新值 $V2$，并成功执行 `DEL cache` 删除了缓存；
  4. 读请求 A 因网络或垃圾回收卡顿，在写请求 B 完成之后，才把旧值 $V1$ 写入 Redis。
  此后直到该缓存过期前，Redis 中将一直保存脏数据 $V1$。
* **防护原则**：为所有缓存强制配置合理的 TTL 兜底；对于极高一致性要求的核心业务，可引入延迟双删或基于 Canal/CDC 监听 binlog 异步失效缓存。

## 5. 延迟双删、CDC 和两级缓存各增加什么责任？

> **来源**：[S171](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-09.md#L247-L247)追延迟双删窗口，[S280](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-27.md#L71-L72)追DB更新后的两级缓存；CDC在本节作为可比较方案的教学展开。

**回答：**
三者是提升缓存一致性与吞吐的不同技术方案，各自伴随着新的工程代价：

1. **延迟双删**：写数据库前删一次，写库成功后 sleep 一定毫秒数再次删除。
   * *代价与责任*：睡眠时间的预估不可靠（慢查询或网络毛刺会打破假设）；同步 sleep 会阻塞业务线程，必须引入异步任务队列执行二次删除。
2. **CDC 异步失效（如 Canal / Debezium 监听 binlog）**：业务代码只负责写 MySQL，由独立服务解析 binlog 后调用 Redis 删除缓存。
   * *代价与责任*：将一致性责任移交给了消息队列与 CDC 组件，需保障消费幂等、监控 binlog 解析延迟与消费积压。
3. **两级缓存（本地内存 Caffeine + 分布式 Redis）**：
   * *代价与责任*：多实例本地内存天然存在数据不一致风险。必须通过 Redis Pub/Sub 或 MQ 广播广播失效通知，并强制设置极短的本地缓存 TTL（如 3~5 秒）作为安全兜底。

## 6. 穿透、击穿、雪崩怎样用不同措施治理？

> **来源**：[S234](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-17.md#L95-L95)明确要求治理三类缓存故障，[S148](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L115-L115)给出高QPS热点失效保护MySQL的条件；措施不能互换。

**回答：**
三者是不同的故障类型，应对方案不可混淆：

* **缓存穿透（查不存在的数据）**：大量请求查询数据库中根本不存在的 key，导致缓存永远无法命中，直接打穿到数据库。
  * *对策*：参数基础格式校验、布隆过滤器（Bloom Filter）前置快速拦截、或者对空结果做**短期空值缓存（Cache Null Object，TTL 设为 1~2 分钟）**。
* **缓存击穿（单个热点 Key 过期）**：某一个超高并发的热点 Key 在到期的瞬间，成千上万的并发请求同时发现缓存失效，瞬间全部回源查库。
  * *对策*：互斥锁回填（查库前使用分布式锁，只放行一个请求查库回填，其余请求重试或等待），或者对核心热点 Key 采用**逻辑过期（数据永不物理过期，后台异步线程定时探测并刷新）**。
* **缓存雪崩（大面积 Key 同时过期或 Redis 宕机）**：大量 Key 在同一时间点集中过期，或 Redis 集群整机故障，导致全量流量涌向数据库引发雪崩。
  * *对策*：在基础 TTL 上增加**随机抖动时间（如基础 30 分钟 + 随机 1~5 分钟）**分散过期点；部署多可用区高可用集群；并在服务端配置熔断限流（Sentinel）保护数据库底座。

## 7. 布隆过滤器为什么不能做精确存在判断或唯一幂等保证？

> **来源**：[S267](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-23.md#L14-L15)追不存在ID攻击与布隆误判，[S326](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1188-L1188)把布隆放到重复消息幂等方案中追问；概率筛查不能替代业务提交证明。

**回答：**
核心原因在于其数学原理中的**假阳性（False Positive，误判率）**：

布隆过滤器由一个大型 Bit 数组和多个独立哈希函数组成。一个元素添加时，多个哈希函数计算出多个索引槽位并将对应 Bit 置为 1。
* 当判定“某个元素不存在”时，只要有一个槽位为 0，该元素**必定 100% 不存在**；
* 但当判定“元素存在”时，所有的 1 可能是由其他多个元素各自计算后巧合拼凑出来的，因此**“可能存在”并不等于“一定存在”**。

因此，布隆过滤器绝不能用来做支付扣款或消息消费的严格唯一幂等判定（误判会导致真实合法的消息被误当成重复消息而丢弃）。精确幂等必须依赖强一致的唯一约束（如数据库唯一索引、或 Redis 的 `SET NX`）。

## 8. TTL、逻辑过期和内存淘汰怎样区分？

> **来源**：[S181](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-10.md#L124-L124)问Hash字段独立TTL，[S262](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-22.md#L184-L184)问内存不足的淘汰选择；字段TTL答案需保留版本，不能沿用旧限制。

**回答：**
三者属于不同层面的数据清理机制：

1. **物理 TTL（Time To Live）**：由 Redis 内核原生管理。通过**惰性删除（访问到该 Key 时判断过期才删除）**与**定期删除（每隔 100ms 随机抽样检查并清理）**结合回收，到期后数据直接物理消失；
2. **逻辑过期（Logical Expiration）**：由应用层自定义数据结构。物理上该 Key 永不过期，但在 Value 的 JSON 中包裹一个 `expire_time` 字段。读请求命中后比对该字段，若发现已过期，则先返回旧值，同时在后台异步启动线程查库刷新；
3. **内存淘汰（Eviction Policy）**：当内存使用达到 `maxmemory` 上限时触发的主动清理机制。常见策略包括 `volatile-lru`（仅在设置了过期的 Key 中淘汰最近最少使用）、`allkeys-lru`（在所有 Key 中淘汰）、以及 `noeviction`（禁止淘汰，写入报错）。带 TTL 的数据如果遇到内存吃紧，可能在 TTL 到期前就被策略提前淘汰。

## 9. BigKey 与 HotKey 怎样区分？大 Key 迁移为什么不只是拆开？

> **来源**：[S262](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-22.md#L182-L183)直接考大Key发现和迁移一致性，[S148](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L116-L116)直接考HotKey检测治理；大小与热度是不同维度。

**回答：**
* **区分本质**：
  * **BigKey（大体积）**：单个 Key 占用内存过大（如 String 超过 5MB，或 Hash/Set 包含数万个元素）。危害是读取耗时高、网络带宽打满、删除时阻塞主线程（需用 `UNLINK` 异步释放）；
  * **HotKey（高访问频率）**：单个 Key 的访问 QPS 极高（如突发热点新闻）。危害是单个 Redis 节点的 CPU 负载瞬间打满，集群无法通过加分片分担（因为同一个 Key 必定落在同一个分片槽位）。
* **大 Key 治理与迁移的工程责任**：
  不能简单粗暴在应用层把一个大 Hash 拆成 10 个小 Key，因为拆分会带来新的架构代价：
  1. **破坏原子操作**：原本针对单个 Hash 的批量操作或事务无法原子执行；
  2. **双写迁移一致性**：存量数据迁移过程中必须开启双写，设置数据版本或对比修改时间戳，避免迁移过程中的新写被旧迁移数据覆盖；
  3. **集群槽位分散与聚合开销**：拆成多个子 Key 后它们会分散在不同节点槽位，跨 Key 聚合查询会产生多次网络往返。

## 10. 命令原子为什么不等于业务原子？

> **来源**：[S387](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L65-L74)连续区分事务、命令串行、多步竞态及Pipeline；WATCH作为可选并发机制补足，不补成该场新题。

**回答：**
因为单条 Redis 命令是原子的，但**由多条命令组成的业务读改写逻辑并不具备隔离性**。

典型并发竞态：
1. 客户端 A 发送 `GET count`，读取结果为 5；
2. 客户端 B 同时发送 `GET count`，读取结果同样为 5；
3. 客户端 A 计算 `5 - 1 = 4`，发送 `SET count 4`；
4. 客户端 B 计算 `5 - 1 = 4`，随后发送 `SET count 4`。
两次扣减后结果依然是 4，发生了丢失更新。虽然每一步 `GET` 和 `SET` 在 Redis 内部都是单线程原子执行的，但两个客户端的执行交错破坏了业务原子性。

**解决原则**：
必须将检查与修改合并为**单条原子操作**（如使用 `DECR`、`SET NX`），或者将多步判断逻辑编写为 **Lua 脚本**交给 Redis 一次性执行。

## 11. Lua 适合做什么？为什么不能把整个订单系统塞进去？

> **来源**：[S313](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L530-L530)问Lua失败回滚，[S397](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L742-L745)问脚本顺序及为何不在Lua内写MySQL；答案必须说清原子执行的边界。

**回答：**
* **Lua 适合的场景**：适合**短小、精悍、纯内存操作且要求原子性的复合逻辑**。例如秒杀扣库存（先判断库存是否大于 0，再做原子扣减，并记录用户购买列表）、以及复杂的多维度滑动窗口限流。
* **不能把复杂订单业务塞入 Lua 的原因**：
  1. **严重阻塞全服请求**：Lua 脚本执行期间，Redis 单主线程会被完全占用，无法响应其他客户端的任何读写请求，耗时超过数毫秒就会引发全服延迟飙升；
  2. **不具备关系型数据库事务回滚**：Lua 脚本执行期间如果中途语法报错或抛异常，**之前已经执行成功的写命令不会被自动回滚**，缺乏 ACID 保证；
  3. **集群环境槽位限制**：在 Redis Cluster 中，Lua 脚本操作的所有 Key 必须映射在同一个哈希槽（Slot）内，否则会直接报错，无法处理跨分片数据。

## 12. 分布式锁怎样安全取得和释放？

> **来源**：[S387](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L70-L71)追获取后为什么不能直接DEL，[S148](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L118-L118)限定不用Redisson设计锁生命周期；示例仍需满足各自前提。

**回答：**
* **安全加锁**：必须使用具备原子性的复合参数命令，且 Value 必须是当前客户端生成的唯一凭证（UUID/Request Token）：
  ```text
  SET lock:resource_id {unique_token} NX PX {lease_time_ms}
  ```
  * `NX` 保证仅在锁不存在时才能成功设置；
  * `PX` 设置自动过期毫秒数，防止持锁进程意外崩溃导致死锁；
  * `unique_token` 标识当前持有者的唯一身份。
* **安全释放（严禁直接 DEL）**：
  若业务执行耗时超出租期导致锁自然过期，其他客户端获取了新锁；如果当前客户端执行完毕后直接无脑 `DEL`，就会把别人的锁错误释放。
  **必须使用 Lua 脚本保证“比对 Token 并删除”的原子性**：
  ```lua
  if redis.call("get", KEYS[1]) == ARGV[1] then
      return redis.call("del", KEYS[1])
  else
      return 0
  end
  ```

## 13. Watchdog、RedLock、Fencing 和幂等怎样划清边界？

> **来源**：[S116](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L36-L36)问看门狗和无限续期风险，[S212](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-13.md#L88-L88)问RedLock使用边界；fencing是处理旧工作者风险的教学补足，不计成来源另一道题。

**回答：**
四者处于不同层级，不可相互替代：

* **Watchdog（看门狗自动续期）**：Redisson 提供的机制。当未显式设置 `leaseTime` 时，启动后台异步定时任务，每隔一段时间检查持锁状态并重置过期时间，防止长任务尚未结束锁提前过期。但遇到 Full GC 长暂停或网络假死时仍可能失效。
* **Fencing Token（防护令牌）**：用于防御“旧客户端因 GC 假死恢复后覆盖新客户端写入”。获取锁时返回单调递增的数字序号，下游存储系统校验版本号，拒绝低于当前版本的写操作。
* **RedLock**：针对多独立 Redis Master 节点的多数派（Quorum）加锁算法。但它高度依赖各节点的系统时钟单调性，运维复杂且成本高。
* **业务幂等性**：任何分布式锁本质上都是**提高系统性能的并发调度手段，绝不是保证数据正确性的最后防线**。涉及资产扣费等不可逆操作，最终必须在数据库层依靠唯一业务索引或状态机前置判定保证绝对幂等。

## 14. RDB、AOF 和复制各保证什么？

> **来源**：[S251](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-21.md#L114-L114)比较持久化机制，[S191](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-11.md#L16-L16)问主从同步；WAIT用于辨析确认边界，属教学补足。

**回答：**
三者承担不同的容灾与恢复职责：

1. **RDB（全量物理快照）**：在指定时间间隔内通过 `bgsave` fork 子进程将当前全部内存数据写入压缩二进制文件。优势是文件体积小、恢复速度极快；缺点是无法做到实时持久化，服务器宕机会丢失最后一次快照后的全部数据；
2. **AOF（增量指令追加日志）**：以文本格式将每条写命令追加到文件末尾。通过 `appendfsync everysec` 配置实现每秒异步刷盘。数据安全性极高（最多丢失 1 秒数据），配合后台重写（AOF Rewrite）压缩文件；
3. **主从复制（Replication）**：主要保证**读性能水平扩展与高可用热备**。采用异步复制机制，主节点向从节点同步数据存在微小时间差，因此主节点宕机切换时，未同步的数据仍然存在丢失窗口。

生产标准方案通常采用 **RDB + AOF 混合持久化**：RDB 负责大版本快速全量加载，AOF 负责增量精准对齐。

## 15. Sentinel 与 Cluster 怎样回答才不混？

> **来源**：[S188](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-10.md#L288-L288)问Sentinel机制，[S195](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-11.md#L100-L100)问Cluster槽、分片与迁移；不能把高可用与分片混答。

**回答：**
两者的核心目标完全不同：**Sentinel 解决的是高可用故障自动切换，Cluster 解决的是海量数据分片横向扩容**。

* **Redis Sentinel（哨兵模式）**：
  * 面向**单个主从架构**（1 主 N 从）。所有节点保存全量相同数据；
  * 哨兵集群通过心跳监控主节点存活，当主节点主观下线并达成客观下线共识（Quorum）后，自动选举新主节点并通知客户端。它无法突破单机内存上限。
* **Redis Cluster（分布式分片集群）**：
  * 面向**数据横向切分（Sharding）**。整个集群拥有固定 **16384 个哈希槽（Hash Slot）**；
  * Key 经过 CRC16 计算后对 16384 取模，路由到对应的 Master 分片节点；
  * Cluster 内部每个 Master 自带从节点，节点间通过 Gossip 协议互相通信，自身兼具故障发现与自动主备切换能力，完全不需要独立的哨兵集群。

## 16. 共享限流怎样同时守住请求数和 Token 预算？

> **来源**：[S209](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-13.md#L20-L20)明确给出请求次数与Token双预算，[S198](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-11.md#L157-L157)追令牌桶原子性和网络抖动；预留结算是围绕未知最终用量的教学设计。

**回答：**
针对大模型 API 特有的“请求次数（RPM）”与“Token 用量（TPM）”双重配额，采用**双维度原子判定与预留结算机制**：

1. **双维度令牌桶（Lua 脚本实现）**：
   在同一个 Lua 脚本中同时维护两个桶：一个放请求许可（RPM 桶），一个放大模型 Token 许可（TPM 桶）。在请求发起时，一次性原子检查两个桶是否均有余额并扣减；
2. **预留与差额多退少补机制**：
   由于请求发起时无法获知模型最终生成的具体 Output Token 数量，客户端先按经验上限（如预估 2000 Tokens）在 Redis 中执行**预扣减（Reserve）**；模型调用完毕后拿到实际使用的 Token 总数，再通过单条原子命令执行**差额多退少补（Reconcile）**。
   整个过程必须绑定唯一的 Request ID，确保重试时不会重复扣减或重复返还。

## 17. Pub/Sub、Streams 和专业 MQ 选型怎样说明可靠性？

> **来源**：[S053](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L39-L39)问Pub/Sub边界，[S397](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L746-L746)问Stream相对Kafka/RocketMQ的选型；消费恢复细节用于解释选择代价。

**回答：**
根据可靠性与消息持久化要求选型：

1. **Redis Pub/Sub**：**纯内存实时广播，无持久化**。发布即遗忘（Fire and Forget）。如果消费者此时断线，重连后无法获取离线期间丢失的消息。仅适用于低价值的集群节点配置刷新或 WebSocket 在线通知广播；
2. **Redis Streams**：**轻量级持久化消息流**。基于内存追加日志，支持持久化存储、全局单调递增 ID、消费组（Consumer Groups）以及未确认待处理列表（PEL，Pending Entries List），支持故障崩溃后的 ACK 确认与重新认领（`XCLAIM`）。适合中小规模的异步任务解耦；
3. **专业 MQ（Kafka / RocketMQ）**：当系统面临**海量吞吐（数十万 QPS）、超大容量磁盘积压、严格顺序消费、分布式事务消息（Half-message）或死信队列治理**时，必须选专业 MQ。Redis Streams 受限于内存容量，大规模积压会导致 Redis OOM。

## 18. Redis 很慢或不一致时怎样结束答案？

> **来源**：[S036](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L98-L98)要求辨认Redis之外的瓶颈，[S262](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-22.md#L182-L183)要求大Key诊断与迁移；观测流程不等于已替读者做过故障演练。

**回答：**
给出标准工程闭环与排查路径作为强有力的收尾：

1. **排查慢查询链路**：
   * 先用 `SLOWLOG GET` 检查是否有 $O(N)$ 高复杂度命令或大 Key 传输；
   * 检查内存使用是否触顶触发了淘汰机制，以及是否有频繁的 AOF 重写（AOF Rewrite）引发的磁盘 I/O 阻塞；
   * 排除客户端连接池耗尽与网络往返（RTT）抖动。
2. **数据一致性修复链路**：
   * 确认问题发生在主从延迟还是缓存双写交错；
   * 核心业务强制路由权威主库读；
   * 依托数据库 binlog CDC 异步消费者进行对账补偿，并在缓存层设置 TTL 兜底收敛脏数据生命周期。
