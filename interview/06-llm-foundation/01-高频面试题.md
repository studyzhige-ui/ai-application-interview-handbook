### 1. Token 是什么，为什么一个词可能被拆开？

> **来源**：[S193 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-11.md#L56-L56) 问 Token 的定义；[S002 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L41-L41) 追问为什么一个单词会被拆成多个 Token，以及按字符与按单词切分的取舍。

**回答：**
Token 是分词器（Tokenizer）按照预设词表与合并规则（如 BPE、BBPE）对原始文本切分后得到的最小处理单元，模型实际接收的是每个 Token 在词表中对应的整数 ID。一个 Token 可能对应完整的常见词、子词词根、单个字符，甚至 UTF-8 字节片段。

之所以一个词可能被拆成多个 Token，是因为主流大模型普遍采用**子词切分（Subword Tokenization）**来平衡词表大小与序列长度：
* **若按字符/字节切分**：词表极小、不会出现未登录词（OOV），但序列会被拉得极长，导致自注意力计算开销暴增且单步语义密度过低；
* **若按完整单词切分**：序列短，但面对词形变化、专业术语、拼写错误与多语言组合时词表会急剧膨胀，且遇到词表外新词无法表示；
* **子词方案（如 BPE）**：将高频词保留为单个 Token，将低频词、罕见复合词拆解为多个高频子词或字节片段，从而在固定词表规模下兼顾编码效率与任意文本覆盖。

**追问：已经把用户正文截短了，为什么请求仍然报上下文超限？**
**回答：**
因为模型的上下文窗口上限统计的是**完整输入序列 + 预留最大输出（`max_tokens`）**的总和，而非仅包含用户正文。系统提示词（System Prompt）、对话历史、注入的检索块、工具定义的 JSON Schema，以及聊天模板（Chat Template）自动拼接的角色标记都会占用输入 Token。排查时应直接对最终拼装完成的请求消息或服务端返回的 `usage` 字段做精确计数，且切换模型时必须使用对应模型的 Tokenizer 重新计算，不能按固定的“字符折算系数”估算。

### 2. 窗口很长，为什么仍需要上下文工程？

> **来源**：[S002 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L43-L43) 将 Lost in the Middle 与长窗口取舍放在一起追问；[S246 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-20.md#L30-L30) 进一步追问长上下文不能替代哪些上下文工程。

**回答：**
上下文窗口“装得下”不代表模型“用得好、算得快、花得省”，长窗口无法替代上下文工程的核心原因有三点：

1. **注意力退化与噪声干扰**：当大量无关、重复或过期历史混入长上下文时，会稀释有效证据的注意力权重，引发指令遗忘或跨段落张冠李戴；
2. **首字延迟（TTFT）与显存成本**：Prefill 阶段的计算量与 KV Cache 显存占用随输入长度增长，无节制塞满长窗口会显著拉高单次调用延迟与 Token 计费；
3. **状态一致性管理**：长对话或多步任务中，旧状态（如已废弃的计划、旧版文件内容）与新状态同时存在于上下文中会导致模型判断冲突。

因此工程上仍必须筛选高信噪比证据、结构化维护当前任务状态与未决约束，并将大体量工具输出存入外部存储，仅向模型暴露摘要与按需回读句柄。

**追问：Lost in the Middle 是不是意味着放在中间的内容模型一定读不到？**
**回答：**
不是。Lost in the Middle（[Liu et al., 2023](https://arxiv.org/abs/2307.03172)）观察到的是在多文档问答等任务中，关键证据位于长上下文首尾时的提取准确率往往高于位于中部，属于注意力分布与位置偏置带来的性能波动，而非硬性的物理屏蔽规则。排查长文本漏读时，应先确认目标片段未被截断，再固定问题、总长度与干扰项，仅移动目标证据的位置做对照验证。

### 3. 从 Prompt 到回答，底层经历哪些步骤？

> **来源**：[S258 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-22.md#L79-L79) 要求完整解释从 Prompt 到输出 Token 的底层路径；[S241 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L61-L62) 追问模型是否天然具有跨请求记忆。

**回答：**
一次标准自回归生成在底层经历四个阶段：

1. **模板封装与分词（Tokenization）**：将系统指令、对话历史、工具定义与用户输入按模型的 Chat Template 拼接，经 Tokenizer 编码为输入 Token ID 序列；
2. **预填充阶段（Prefill）**：输入 ID 经 Embedding 层映射为连续向量，并行流经多层 Transformer Block（因果自注意力 + FFN）。此阶段一次性计算并缓存整个输入前缀在各层的 Key 和 Value 张量（KV Cache），并由最后一个位置的隐藏状态经 LM Head 投影得到词表维度的 Logits，采样产生首个输出 Token；
3. **自回归解码阶段（Decode）**：将新生成的 Token 作为下一步输入，复用已缓存的历史 KV，仅计算当前新位置的 Q、K、V 并追加写入 KV Cache，逐步生成后续 Token；
4. **停止判定与反分词（Detokenization）**：当生成命中结束符（EOS）、预设停止词（`stop`）或达到最大长度限制（`max_tokens`）时终止循环，将生成的 Token ID 序列解码为文本或结构化事件流返回。

**追问：大模型本身天然记得上一次 HTTP 请求的内容吗？**
**回答：**
不记得。在线推理阶段模型的权重参数完全冻结，每次推理请求对模型本身都是无状态的。所谓“多轮对话记忆”，是由应用程序或服务端会话层显式将历史消息、状态摘要或检索到的记忆片段重新拼入当前请求的输入序列中实现的（服务端 Prefix KV Cache 仅用于加速相同前缀的张量计算，不改变无状态语义）。

### 4. Encoder、Decoder、Decoder-only 分别是什么？

> **来源**：[S321 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L957-L957) 要求说明两类结构；[S365 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3520-L3521) 分别问 Encoder/Decoder 区别与 Decoder-only 成为主流的原因。

**回答：**
* **Encoder（编码器，如 BERT）**：采用**双向自注意力**，每个位置都可以同时看到序列前后的所有上下文，适合文本分类、序列标注、双塔 Embedding 编码与重排（Cross-Encoder）等理解类任务；
* **Encoder-Decoder（编码-解码架构，如原始 Transformer、T5）**：Encoder 对输入序列做双向编码，Decoder 采用因果自注意力读取已生成前缀，并通过**交叉注意力（Cross-Attention）**读取 Encoder 的输出表示，适合机器翻译等存在明确源序列到目标序列映射的任务；
* **Decoder-only（纯解码器架构，如 GPT、LLaMA、Qwen）**：去掉独立 Encoder 与交叉注意力层，所有位置统一采用**因果自注意力（Causal Mask）**，只能关注当前位置及之前的上下文，以“根据前缀预测下一个 Token”统一所有任务。

**为什么主流生成大模型普遍采用 Decoder-only**：
1. **预训练目标高效统一**：Next-Token Prediction 在海量无标注文本上每个位置都能产生密集的监督信号，无需人工构造掩码策略，具备极强的规模化扩展性（Scaling Law）；
2. **推理工程与 KV Cache 友好**：输入前缀与输出生成共用同一套因果注意力结构，天然支持 KV Cache 增量解码与跨轮次前缀缓存（Prefix Caching）。

### 5. Q、K、V 从哪里来，Attention 怎样算？

> **来源**：[S321 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L958-L959) 连续问 QKV 计算过程和除以 $\sqrt{d_k}$ 的理由。

**回答：**
在自注意力（Self-Attention）层中，输入隐藏状态矩阵 $H \in \mathbb{R}^{n \times d_{\text{model}}}$ 分别乘以三个可学习的线性投影矩阵 $W_Q, W_K, W_V$，得到查询（Query）、键（Key）和值（Value）：
$$Q = H W_Q, \quad K = H W_K, \quad V = H W_V$$
（若在 Cross-Attention 中，则 $Q$ 来自解码器隐藏状态，$K$ 和 $V$ 来自编码器输出表示。）

得到 $Q, K, V$ 后，缩放点积注意力的计算公式为：
$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{Q K^T}{\sqrt{d_k}} + M\right) V$$
1. 计算 $Q K^T$ 得到各位置之间的原始相关性点积分数；
2. 除以缩放因子 $\sqrt{d_k}$（$d_k$ 为单个注意力头的键向量维度）；
3. 加上注意力掩码矩阵 $M$（可见位置为 $0$，屏蔽位置为 $-\infty$）；
4. 按行执行 $\text{softmax}$ 归一化为概率权重，最后对 $V$ 加权求和输出。

**追问：为什么要除以 $\sqrt{d_k}$？**
**回答：**
为了防止维度较大时点积数值过大导致 Softmax 梯度消失。假设 $q$ 和 $k$ 的各分量相互独立且均值为 $0$、方差为 $1$，则它们的点积 $q \cdot k = \sum_{i=1}^{d_k} q_i k_i$ 均值为 $0$，方差会放大为 $d_k$。当 $d_k$ 较大时，点积结果的绝对值容易变得很大，进入 Softmax 函数的饱和区（正大值趋近 $1$，其余趋近 $0$），导致反向传播时梯度接近于 $0$。除以 $\sqrt{d_k}$ 可以将点积方差重新拉回 $1$ 附近，保持数值与梯度稳定。

### 6. Mask、多头、FFN 和残差各做什么？

> **来源**：[S272 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-25.md#L44-L44) 明确要求手写带 Mask 的多头注意力；[S126 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L333-L336) 分别追问多头存在的理由与 FFN 的作用。

**回答：**
* **Mask（掩码）**：控制位置可见性。Causal Mask（上三角置为 $-\infty$）阻止当前位置在训练或 Prefill 时偷看未来 Token；Padding Mask 屏蔽批处理补齐的无效位置。注意屏蔽必须在 Softmax **之前**将对应 logits 置为极小负数（$-\infty$），不能置为 $0$，因为 $e^0 = 1$ 仍会分走注意力权重。
* **Multi-Head（多头注意力）**：将特征切分为多个低维子空间，用多组独立的投影矩阵并行计算注意力，最后拼接并做输出线性投影（$W_O$）。它允许模型在同一层内同时关注不同距离、不同语义侧面的上下文关联，避免单一注意力分布被某一个强相关位置完全垄断。
* **FFN（前馈网络 / MLP）**：对每个位置独立执行非线性特征变换（如 SwiGLU 激活）。Attention 负责**跨位置的信息聚合与路由**，而 FFN 负责对聚合后的表示做**逐位置的特征加工与知识映射**，占据了模型绝大部分参数量。
* **残差连接与归一化（Residual & Norm）**：残差连接（$x + \text{SubLayer}(x)$）构建梯度直通路径，防止深层网络梯度消失；归一化（主流大模型常采用 **Pre-Norm + RMSNorm**）稳定各层激活尺度，保障深层训练收敛。

### 7. Transformer 怎样知道顺序，RoPE 怎样工作？

> **来源**：[S388 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L301-L301) 问 Transformer 怎样保留序列位置信息；[S272 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-25.md#L45-L46) 明确要求手写 RoPE（旋转位置编码）。

**回答：**
不含位置信息的自注意力对输入顺序是置换等价的（打乱词序仅同步打乱输出顺序，不改变计算出的表示），因此必须显式注入位置编码。早期方案（如原始正余弦编码、可学习绝对位置 Embedding）直接加在输入词向量上；现代主流大模型普遍采用 **RoPE（Rotary Position Embedding，旋转位置编码）**。

**RoPE 的核心原理**：
1. 在每一层计算 Attention 时，对投影后的 $Q$ 和 $K$ 向量（不对 $V$ 操作）按维度两两分组，构成多个二维平面向量；
2. 位置为 $m$ 的向量，在第 $i$ 个二维子平面上乘以旋转矩阵 $R_{\Theta, m}$，旋转角度为 $m \theta_i$（不同维度组对应从高频到低频的不同旋转角速度 $\theta_i = \text{base}^{-2i/d}$）；
3. **以绝对位置旋转实现相对位置感知**：由于正交旋转矩阵满足 $(R_m q)^T (R_n k) = q^T R_m^T R_n k = q^T R_{n-m} k$，位置 $m$ 的 Query 与位置 $n$ 的 Key 的内积天然只取决于它们的内容以及**相对距离 $m - n$**，同时兼容线性注意力与 KV Cache（历史 Token 缓存旋转后的 $K$ 即可，无需随新 Token 到来而重算）。

**追问：使用了 RoPE 就能直接无限长外推吗？**
**回答：**
不能。当推理长度超出预训练见过的最大长度范围时，高频与低频旋转角度组合会出现训练未见过的相位分布（Out-of-Distribution），导致注意力分数异常发散、困惑度陡增。长窗口扩展通常需要结合调整旋转基频（如增大 `rope_theta`）、位置插值（PI）或分频缩放（如 NTK-aware Scaling、YaRN）并辅以长文本继续训练。

<a id="llm-q08"></a>

### 8. Temperature、Top-k、Top-p 分别改变什么？

> **来源**：[S079 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L110-L110) 把 Temperature、Top-k、Top-p 及温度为 0 时的确定性放在同一条追问中。

**回答：**
三者均作用于每步解码时的输出概率分布，控制生成的随机性与候选截断范围：

1. **Temperature（温度 $T > 0$）**：在计算 Softmax 之前将 logits 除以 $T$（即 $p_i = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$）。它**不改变各候选 Token 的相对大小排序**，只改变分布的陡峭程度：$T \to 0$ 时分布极度尖锐，高分项概率趋近 $1$；$T > 1$ 时分布趋于平缓，低分候选被采样到的概率增加；
2. **Top-k 采样**：仅保留概率排名前 $k$ 个候选 Token，将其余候选剔除后重新归一化采样。缺点是固定数量 $k$ 无法适应分布形态变化（分布极确定时可能混入离谱低分词，分布很平缓时又截断过严）；
3. **Top-p（Nucleus 核采样）**：按概率从高到低累加，动态保留累计概率刚达到阈值 $p$ 的最小候选集合，再重新归一化采样，能根据当前步模型确定性自适应调整候选池大小。

**追问：将 `temperature=0`（贪心解码）就一定能保证每次请求输出 100% 一致吗？**
**回答：**
不一定。虽然数学上贪心解码每次都取最大 logit，但在工程生产环境中仍可能出现输出不一致：一是 GPU 浮点并行归约计算的非确定性（如动态 Batching 下不同批次大小触发不同的矩阵乘法 CUDA Kernel，微小的浮点舍入误差可能使原本并列接近的 Top-1 与 Top-2 翻转）；二是 MoE 架构下的专家容量竞争或服务端负载均衡落到不同量化精度的实例。

### 9. KV Cache 为什么加速，缓存的是什么？

> **来源**：[S152 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L202-L202) 问 KV Cache 为何加速；[S312 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L452-L452) 进一步追问动态卸载 Skill 对缓存命中的影响。

**回答：**
* **缓存的内容**：KV Cache 缓存的是**每一层 Transformer 自注意力模块中，历史已处理 Token 对应的 Key 张量和 Value 张量**。它不是文本答案缓存，也不是向量数据库的 Embedding。
* **为什么能加速**：在因果自注意力（Causal Mask）下，位置 $t$ 的 Key 和 Value 只依赖于位置 $\le t$ 的输入，不会因为后续生成了位置 $t+1$ 的 Token 而发生任何改变。如果没有 KV Cache，每生成 1 个新 Token 都要把整个长度为 $s$ 的前缀重新做一遍前向传播；有了 KV Cache 后，Decode 阶段每步只需计算最新 1 个 Token 的 $q_t, k_t, v_t$，将 $k_t, v_t$ 追加进缓存，再用 $q_t$ 与缓存中的历史 $K, V$ 计算注意力，将单步投影与 FFN 计算复杂度从 $O(s)$ 降至 $O(1)$，以显存空间换取计算时间。

**追问：在多轮运行中动态卸载或修改头部的 Skill/系统提示词，为什么会破坏缓存命中？**
**回答：**
因为跨请求的前缀缓存（Prefix Caching）依赖**精确的前缀 Token 序列匹配**。由于因果注意力中后面每一个位置的 K/V 都受其前面所有 Token 的影响，一旦头部或中前部的 System Prompt、工具列表或 Skill 定义发生删除、插入或顺序重排，从改动点往后的所有 Token 位置与上下文依赖全部失效，无法复用原有 KV Cache，必须重新执行 Prefill 计算。因此工程上应将稳定不变的系统指令与固定工具置顶，把动态变化的材料放在上下文尾部。

### 10. 怎样估算显存，为什么权重能放下仍会 OOM？

> **来源**：[S095 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-06.md#L17-L17) 问参数规模与显存/推理资源的关系；[S255 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-21.md#L239-L239) 问四张 GPU 如何分布式部署。

**回答：**
推理显存占用主要由四部分构成：**模型权重 + KV Cache + 前向激活值（Activations）+ 框架/CUDA 上下文开销**。

1. **模型权重显存**：约为 $\text{参数量} \times \text{每个参数字节数}$（例如 7B 模型在 FP16/BF16 下约占 $7 \times 2 = 14\text{ GB}$，INT4 量化下约占 $3.5\sim 4\text{ GB}$）；
2. **KV Cache 显存**：随并发请求数（Batch Size $B$）和序列长度（$S$）线性增长：
   $$\text{KV Cache 字节数} = 2 \times \text{层数 } L \times \text{KV 头数 } n_{\text{kv}} \times \text{头维度 } d_k \times \text{精度字节数} \times (B \times S)$$
   （采用 GQA/MQA 的模型这里乘的是 KV 头数而非 Query 头数。）

**为什么权重能放进显存仍然会 OOM**：
因为权重是静态固定的，而 **KV Cache 和 Prefill 阶段的临时激活张量是随并发数与上下文长度动态膨胀的**。当并发请求增加或出现超长 Prompt 时，KV Cache 和激活峰值加上显存碎片会迅速撑爆剩余显存。

**追问：四张 GPU 部署大模型时，显存是简单相加吗？应该怎么切分？**
**回答：**
不是简单相加，因为多卡通信缓冲区（NCCL Buffer）、CUDA Context 和冗余结构在每张卡上都有独立开销。切分方式取决于单机还是多机及延迟目标：单机多卡（如 4 张卡）若单卡放不下模型，通常采用**张量并行（Tensor Parallelism, TP=4）**，将每层的权重矩阵按列/行切分到 4 张卡上协同计算，能同时降低单请求延迟并分摊显存；若单卡完全放得下模型且追求高并发吞吐，则优先采用**数据并行（多实例副本负载均衡）**，避免跨卡 All-Reduce 通信开销。

### 11. Prefill、Decode、TTFT、TPOT 怎样用于排障？

> **来源**：[S071 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L421-L421) 问 Prefill/Decode 分离及 KV 资源影响；[S257 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-22.md#L46-L46) 要求确认优化是否主要改善 TTFT 及如何定位瓶颈。

**回答：**
* **Prefill 与 TTFT（Time To First Token，首字延迟）**：Prefill 并行处理全部输入 Token，属于**计算密集型（Compute-bound）**阶段。TTFT 衡量从请求发出到收到第一个输出 Token 的耗时。若 **TTFT 过高**，瓶颈通常在：请求排队等待调度、输入 Prompt 过长、Prefix Cache 命中率低，或上游检索/工具前置耗时过长。
* **Decode 与 TPOT（Time Per Output Token，单步生成耗时）**：Decode 每次只生成 1 个新 Token，却要从显存读取全部模型权重和历史 KV Cache，属于**显存带宽密集型（Memory-bandwidth-bound）**阶段。TPOT 衡量后续每个 Token 的平均生成间隔。若 **TTFT 正常但整体完成极慢**，瓶颈通常在：输出 Token 数量过多（如冗余思维链）、并发 Batch 过大导致显存带宽饱和（TPOT 退化），或流式网关缓冲阻塞。

**追问：为什么要做 Prefill/Decode（P/D）分离架构？它有什么代价？**
**回答：**
当 Prefill 和 Decode 混在同一批实例上调度时，一个长 Prompt 的计算密集型 Prefill 会阻塞同批次正在进行的 Decode 请求，导致流式生成出现明显卡顿（TPOT 尖刺）。P/D 分离将两阶段拆分到不同实例池，分别针对计算吞吐（Prefill）和显存带宽/低延迟（Decode）独立扩缩容与配比；代价是 Prefill 完成后必须通过高速网络（如 RDMA / NVLink）将生成的庞大 KV Cache 传输给 Decode 节点，增加了跨节点传输带宽压力与调度复杂度。

### 12. PagedAttention、推理引擎和吞吐优化是什么关系？

> **来源**：[S255 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-21.md#L240-L240) 明确追问 PagedAttention 为何改善内存管理；[S184 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-10.md#L203-L203) 比较 SGLang、vLLM 与 PagedAttention。

**回答：**
* **PagedAttention 解决的核心问题**：传统实现因为无法预知每个请求最终生成多少个 Token，必须按最大长度提前分配一大块**连续显存**，导致严重的内部碎片（预留未用完的空间）和外部碎片，极大限制了并发 Batch Size。PagedAttention 借鉴操作系统虚拟内存分页思想，将每个请求的 KV Cache 切分为固定大小的物理块（Block），通过块表将逻辑连续的 Token 映射到非连续物理显存上，按需动态分配并支持相同前缀物理块共享，几乎消除了显存预留浪费。
* **算法与推理引擎的关系**：PagedAttention 只是 KV 显存管理与注意力算子层面的核心机制；而 **vLLM、SGLang** 等完整推理服务引擎在此基础上，还集成了 **Continuous Batching（迭代级动态批处理，已完成的请求立即腾出槽位插入新请求）**、Chunked Prefill、Prefix Caching（如 SGLang 的 RadixAttention 前缀树自动复用）以及结构化解码约束等完整调度能力。它们共同通过减少显存浪费、提高最大并发 Batch Size 来大幅提升系统吞吐量。

### 13. 模型怎样选，怎样回答“为什么用小模型而不是大模型”？

> **来源**：[S151 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L187-L187) 询问 7B 与 32B 的具体比较与选型依据；[S382 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L4456-L4456) 问为何采用自训练小模型（如 TinyBERT），并追问评测集规模。

**回答：**
模型选型不看通用榜单排名，而是由**任务复杂度边界、延迟 SLA、单次成功成本与私有化硬件约束**共同决定：

1. **何时选择小模型（如判别式 BERT 类模型，或 7B/8B 生成模型）**：当任务边界清晰、模式固定（如意图路由、敏感词/安全分类、实体抽取、固定 Schema 槽位提取）且具备领域标注数据时，经过微调的小模型在任务准确率上往往能逼近甚至持平通用大模型，同时将推理延迟从秒级降至十毫秒/百毫秒级，显存与算力成本降低一个数量级；
2. **何时必须用大模型（如 32B/70B+ 或旗舰商业 API）**：当任务涉及开放域多步推理、复杂代码生成、长文档跨段落综合或低频异常恢复，且缺乏充足训练样本时，必须依赖大模型的泛化与推理能力；
3. **验证口径**：必须在与线上分布一致的独立测试集（涵盖正常、边界、拒答与噪声样本）上，综合对比准确率、P95/P99 延迟以及**包含失败重试在内的单次任务成功总成本**。

### 14. HTTP 成功、合法 JSON 和任务成功有什么区别？

> **来源**：[S060 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L179-L179) 追问怎样判断模型调用真正成功；[S263 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-22.md#L230-L230) 限定下游强制要求 JSON 输出契约的场景。

**回答：**
在生产系统中，一次模型调用的验收必须严格拆分为四个逐层递进的契约层级：

1. **传输层成功（HTTP 200）**：仅代表网络请求送达且未发生鉴权失败、限流（429）或服务端崩溃（5xx）；
2. **生成完整度（Finish Reason）**：检查 `finish_reason` 是否为正常停止（`stop` 或 `tool_calls`），而非因达到 `max_tokens` 被半途截断（`length`）或因安全策略被拦截（`content_filter`）；
3. **语法与 Schema 契约（合法 JSON）**：输出能够通过 `json.loads` 解析，且字段名称、数据类型、必填项与枚举值完全通过 Pydantic / JSON Schema 校验；
4. **业务语义与事实正确性（任务成功）**：结构合法不代表内容正确。还必须由宿主程序校验跨字段逻辑约束（如起止时间合理性）、实体真实性与归属权限（如返回的订单号确实存在且属于当前用户），以及关键结论是否有上下文证据支撑。

**追问：如何工程化保证模型稳定输出符合 Schema 的 JSON？**
**回答：**
不能仅靠 Prompt 文字叮嘱。应优先启用模型服务端的**结构化输出能力（Structured Outputs / Constrained Decoding，底层在解码阶段通过有限状态机或上下文无关文法直接屏蔽违反 JSON Schema 的 Token）**；同时在客户端配备 Pydantic 严格校验与带错误信息的有限次数自愈重试，并设置保底降级分支。

### 15. 一个可靠 Prompt 怎样设计和迭代？

> **来源**：[S071 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L422-L422) 问 Prompt 设计与迭代方法；[S372 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3922-L3923) 要求现场检查、修改提示词并判断注入风险。

**回答：**
* **结构化设计要素**：
  1. **明确任务边界与输出契约**：清晰定义输入来源、判定规则、输出字段格式，以及**信息缺失或证据冲突时的显式拒答/澄清行为**（防止模型强行脑补）；
  2. **指令与外部数据严格隔离**：使用明确的边界标记或独立消息角色封装不可信的用户输入与检索片段，声明外部数据内的任何指令性语句均不具备控制权；
  3. **高代表性 Few-shot 示例**：示例不仅包含标准正例，更要覆盖易混淆边界与缺省拒答反例，且示例格式必须与指令规则严格一致。
* **工程化迭代闭环**：
  将 Prompt 视为版本化代码资产。每次针对线上 Bad Case 修改提示词时，必须先分析指令是否存在互相矛盾或歧义，修改后在固定的**回归评测集**上全量验证，确保修复当前 Bad Case 的同时没有导致历史正常样本退化（跷跷板效应），并同步监控 Token 消耗与延迟变化。

### 16. 模型为什么会幻觉，应该在哪一层干预？

> **来源**：[S329 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1417-L1417) 同时问幻觉成因与降低手段；[S394 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L616-L616) 追问项目中的预防和兜底机制。

**回答：**
* **幻觉成因**：大模型的本质是最大化条件概率分布 $P(x_t \mid x_{<t})$ 的序列续写器，而非事实数据库。当参数知识过时或缺失、外部检索未召回关键证据或发生截断、提示词强制要求回答而未给拒答出口、或面对精确数值计算时，模型就会顺着高概率语言模式生成看似通顺但违背事实的内容。
* **分层干预体系**：
  1. **输入与知识层（RAG 与工具）**：针对时效性与私有事实，通过高质量检索注入权威外部证据；针对数学计算、数据库状态查询，强制路由给确定性代码工具执行；
  2. **指令与生成层**：在 Prompt 中要求“仅依据给定上下文作答，每一条关键结论必须标注对应证据块 ID，证据不足时直接回答不知道”，并降低采样温度；
  3. **输出后置校验层（Guardrails）**：用确定性程序校验输出中的实体 ID、数值范围与引用存在性，对高风险场景对照原文做忠实度（Faithfulness）核验，不通过则拦截或降级。

**追问：通过严格限制让拒答率大幅上升，能算幻觉治理成功吗？**
**回答：**
不能单看“已作答准确率”。如果把所有稍有难度的合法问题全部拒答，已作答准确率虽接近 100%，但系统的**有效回答覆盖率（Coverage）**会严重崩溃。幻觉治理必须同时监控两个对立指标：**已作答事实忠实度（Faithfulness）**与**可回答问题的误拒率（False Refusal Rate）**。

### 17. 如何验证 LLM-as-a-Judge，而不是再找一个模型就相信它？

> **来源**：[S052 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L16-L16) 问 Judge 自身正确率与一致性如何验证；[S356 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3022-L3023) 明确追问只查低分时怎样发现误获高分的劣质样本。

**回答：**
LLM-as-a-Judge 自身同样存在幻觉与偏置（如偏爱长篇幅、偏爱特定格式、成对比较时的位置偏置），因此上线前必须把 Judge 本身当作一个待评测分类器进行校准：

1. **可编程规则优先剥离**：凡是能用代码确定性校验的维度（JSON 格式、必填字段、引用 ID 真实性、精确数值），一律用代码校验，不交给 LLM 打分；
2. **细化二值/分档评分准则（Rubric）**：避免让 Judge 直接打 1～10 的笼统主观分，而是拆解为明确的二值判定项（如“是否包含未出现在上下文中的数字”），并要求先输出证据比对过程再给结论；
3. **与人工金标准对齐**：构建由领域专家标注的校准集，计算 Judge 与人类专家的一致率（如 Cohen's Kappa、精确率与召回率），并通过交换 A/B 顺序测试消除位置偏置。

**追问：如果日常只抽检 Judge 打低分的样本，会漏掉什么致命问题？**
**回答：**
会完全漏掉**假阳性（False Positive，即回答其实是错的或有严重幻觉，但因为语气自信、排版漂亮被 Judge 误打了高分）**。工程抽检必须采用**分层抽样**：同时从高分池、低分池和临界分值区间按比例盲抽人工复核，并定期注入已知错误答案的“探针负例（Golden Negative）”检验 Judge 能否稳定识别。

### 18. Embedding 为什么能检索语义，模型怎样选？

> **来源**：[S178 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-10.md#L57-L57) 问 Embedding 为什么能表示语义及向量空间怎样理解；[S074 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L487-L487) 明确问 Embedding 模型选型依据。

**回答：**
* **为什么能表示语义**：Embedding 模型基于对比学习（Contrastive Learning，如 InfoNCE Loss）在海量正负样本对上训练，优化目标是拉近语义相关或问答匹配的文本对在向量空间中的距离，同时推远不相关文本（硬负例）。因此最终经池化（Pooling）与归一化输出的稠密向量，其空间几何距离反映了训练任务定义的语义相关性。
* **Embedding 模型选型维度**：
  1. **语言与领域匹配度**：通用中文/多语言能力，以及在垂直领域专有词汇上的表征质量；
  2. **最大输入长度（Max Sequence Length）**：必须大于业务设计的 Chunk 最大 Token 长度，否则超出部分会被静默截断丢弃；
  3. **非对称检索支持**：短 Query 检索长 Document 时，确认模型是否需要特定的查询指令前缀（Instruction Prefix）；
  4. **向量维度与存储/检索成本**：结合语料规模权衡维度（如 512 / 768 / 1024 维）及是否支持 Matryoshka（MRL）弹性降维，最终以业务真实检索评测集上的 Recall@K 为准。

### 19. Bi-Encoder 与 Cross-Encoder 为什么常分成召回和重排？

> **来源**：[S211 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-13.md#L63-L63) 要求比较 Bi-Encoder 与 Cross-Encoder 的结构与复杂度成本；[S272 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-25.md#L41-L41) 询问 BGE Reranker 与 Embedding 的作用和推理方式。

**回答：**
两者在“特征交互深度”与“在线计算复杂度”上存在根本取舍，因此分别承担第一阶段粗召回与第二阶段精排：

* **Bi-Encoder（双塔模型，即 Embedding 检索）**：Query 和 Document 分别独立输入编码器，各自压缩为一个固定维度的向量，最后仅通过向量点积或余弦计算相似度。
  * **优势**：海量文档向量可以**离线预先计算并构建 ANN 索引**，在线查询只需编码一次 Query 并在毫秒级内从百万/千万级库中召回 Top-K 候选；
  * **局限**：Query 和 Document 的各个 Token 之间没有发生跨序列自注意力交互，信息被强行压缩进单个向量，细粒度语义判别力受限。
* **Cross-Encoder（单塔交互模型，即 Reranker）**：将 `[CLS] Query [SEP] Document [SEP]` 拼接后联合送入 Transformer，让 Query 与 Document 的每一个 Token 在每一层都进行全量交叉注意力交互，最后直接输出相关性得分。
  * **优势**：细粒度语义匹配精度显著高于双塔；
  * **局限**：无法离线预计算文档表征，每次查询若有 $N$ 个候选就必须在线执行 $N$ 次完整前向推理，计算开销极大，因此只能对粗召回筛出的数十个候选（如 Top-50）做重排。

### 20. 多模态输入怎样排障？

> **来源**：[S257 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-22.md#L47-L47) 询问图文多模态输入链路；[S144 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L21-L21) 追问视频场景下 ASR、OCR 与抽帧融合及参数实验。

**回答：**
主流视觉语言模型（VLM）通过视觉编码器（如 ViT）将图像切分为 Patch 并编码为视觉特征，再经投影层（Projector / Adapter）对齐到语言模型的词嵌入空间，作为视觉 Token 与文本 Token 一并送入 LLM 计算。

当多模态问答出错时，按以下三个环节逐层定位：
1. **感知层失真（看不清/漏帧）**：检查图像分辨率缩放或分块裁剪（Dynamic High-Resolution）是否导致密集小字、表格线条模糊，或者视频抽帧间隔过大漏掉了关键瞬态画面；
2. **跨模态对齐错位（张冠李戴）**：在多图或长视频（视频帧 + ASR 语音转写 + OCR 字幕）场景下，检查是否正确绑定了时间戳与空间坐标元数据，防止模型把不同时间点的语音和画面强行拼成同一个事件；
3. **推理与计算错误（看得见但算错）**：若模型能准确复述图中文字与数字，但最终汇总计算或逻辑判断出错，说明瓶颈不在视觉分辨率，而在推理链或缺乏代码计算工具辅助，此时盲目调高图像分辨率只会徒增视觉 Token 开销。

### 21. 什么时候用 Prompt、RAG、工具，什么时候值得 SFT？

> **来源**：[S233 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-17.md#L72-L72) 问先改 Prompt 还是微调，以及何时值得微调；[S126 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L329-L329) 比较 RAG 与微调的适用边界。

**回答：**
四者解决的是完全不同维度的工程问题，应按**“先定上下文与外部能力，最后才动模型权重”**的顺序选型：

1. **Prompt 工程**：解决**任务规则表达与少量示范引导**。成本最低、迭代最快，是所有任务的基线起点；
2. **RAG（检索增强生成）**：解决**动态外部知识、时效性事实、长尾私有文档与可追溯引用**。凡是数据会频繁更新、需要按用户权限隔离或要求严格对应原文出处的问题，必须用 RAG 而非微调；
3. **确定性工具（Tools）**：解决**精确数学计算、实时数据库读写与外部系统副作用执行**；
4. **SFT（监督微调）**：解决**模型行为模式、特定输出格式、垂直领域语言风格，或将高频复杂 Prompt 蒸馏内化到小模型以降低推理延迟与 Token 成本**。只有当 Prompt + RAG 已经达到上限，且存在稳定的行为缺陷、充足的高质量标注样本与明确的评测基准时，才值得引入 SFT。

### 22. 一次 SFT 怎样产生学习信号，如何判断该停止？

> **来源**：[S151 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L188-L188) 问微调完整流程；[S334 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1816-L1816) 追问收敛判断依据是看 Loss 还是看训练轮数（Epoch）。

**回答：**
* **学习信号怎么产生**：
  将指令（Prompt）与期望回答（Response）按 Chat Template 拼接为完整 Token 序列。在计算交叉熵损失（Cross-Entropy Loss）时，**通常将 Prompt 部分和 Padding 位置的标签置为 `-100`（Mask 掉不计入 Loss），仅对模型需要生成的 Response（含工具调用与结束符 EOS）位置计算预测下一 Token 的监督损失**，通过反向传播更新可训练参数。
* **如何判断停止训练**：
  不能机械按固定轮数（Epoch）停止，也不能只看训练集 Loss 降到最低（训练 Loss 过低往往意味着过拟合与通用能力灾难性遗忘）。正确做法是：
  1. 监控独立**验证集（Validation Set）Loss**，当验证集 Loss 不再下降甚至开始回升时，说明已出现过拟合；
  2. 在各个 Checkpoint 上运行**下游业务任务评测集与通用能力回归集**，选择业务指标达标且未破坏通用指令遵循能力的最佳 Checkpoint 停止。

### 23. LoRA 为什么参数少，低秩限制的是谁？

> **来源**：[S321 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L963-L963) 明确问 LoRA 的数学表达；[S375 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L4110-L4110) 问 LoRA 微调与低秩原理。

**回答：**
LoRA（Low-Rank Adaptation）的核心假设是：模型在下游任务适配时，**权重更新矩阵 $\Delta W$ 具有很低的“内在秩（Intrinsic Rank）”**。注意，低秩限制的是**权重的增量 $\Delta W$**，而不是假设预训练基座权重 $W_0$ 本身是低秩的。

**数学原理与参数量对比**：
对于基座中的线性层权重 $W_0 \in \mathbb{R}^{d_{\text{out}} \times d_{\text{in}}}$，训练时冻结 $W_0$ 不更新梯度，并在旁路引入两个低秩矩阵 $A \in \mathbb{R}^{r \times d_{\text{in}}}$ 和 $B \in \mathbb{R}^{d_{\text{out}} \times r}$（其中秩 $r \ll \min(d_{\text{in}}, d_{\text{out}})$，例如 $d=4096$ 而 $r=8$ 或 $16$）：
$$h = W_0 x + \Delta W x = W_0 x + \frac{\alpha}{r} B A x$$
* **初始化策略**：矩阵 $A$ 采用高斯随机初始化，矩阵 $B$ 全零初始化，保证训练刚开始时 $\Delta W = B A = 0$，不破坏基座初始输出；
* **显存与推理优势**：可训练参数量从 $d_{\text{out}} \times d_{\text{in}}$ 骤降至 $r(d_{\text{in}} + d_{\text{out}})$，大幅省去了全量参数的梯度与 Adam 优化器状态显存；单任务部署时可将 $\frac{\alpha}{r} B A$ 直接合并加回 $W_0$，实现**零额外推理延迟**。

### 24. SFT、PPO、DPO 分别从什么反馈中学习？

> **来源**：[S002 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L45-L45) 要求区分这些训练/对齐方法及应用工程理解范围；[S222 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-15.md#L139-L139) 进一步追问 DPO 的 chosen/rejected 数据构造和评测局限。

**回答：**
三者处于后训练（Post-training）的不同阶段，利用的监督反馈信号完全不同：

1. **SFT（监督微调）**：从**单条高质量示范答案 $(x, y)$** 中学习，通过最大化示范序列似然进行模仿学习，教会模型基本的任务格式与指令遵循，但不会直接利用负例信号区分“好回答与坏回答的边界”；
2. **PPO（基于强化学习的对齐 RLHF）**：从**在线采样 + 奖励模型（Reward Model）标量打分**中学习。需同时维护四个模型（Actor 策略模型、Reference 参考模型、Reward 奖励模型、Critic 价值模型），在 KL 散度约束下通过在线生成探索最大化期望奖励，上限高但显存开销大、训练对超参极敏感；
3. **DPO（Direct Preference Optimization，直接偏好优化）**：利用奖励函数与最优策略之间的数学解析映射，直接从**成对偏好数据 $(x, y_{\text{chosen}}, y_{\text{rejected}})$** 中学习，无需单独训练 Reward Model 和运行在线强化学习采样，直接拉大模型在参考策略下对 $y_{\text{chosen}}$ 与 $y_{\text{rejected}}$ 的相对对数概率差，训练稳定且成本低。

**追问：构建 DPO 的 chosen/rejected 数据时有什么常见陷阱？**
**回答：**
如果 $y_{\text{chosen}}$ 普遍比 $y_{\text{rejected}}$ 更长、排版更华丽，DPO 极易学到**长度偏置与形式迎合（Verbosity Bias）**，导致模型不管事实对错都傾向于输出冗长啰嗦的回答。此外，若 chosen/rejected 分布与当前待优化模型的输出分布差距过大（严重的 Off-policy），会导致偏好挤压失效。因此正负样本对必须控制无关变量（如长度相当），聚焦于真实的事实准确性、工具参数正确性与安全边界差异。

### 25. GRPO 相对 SFT 可能提供什么，为什么不能承诺一定提升？

> **来源**：[S334 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1813-L1813) 明确问 GRPO 相对 SFT 的增益条件与机制区别。

**回答：**
* **GRPO（Group Relative Policy Optimization）的核心机制与相对 PPO/SFT 的优势**：
  1. **相对 PPO 省去 Critic 模型**：针对同一个输入问题 $q$，由当前策略采样一组（Group，如 $G$ 个）候选输出 $\{o_1, \dots, o_G\}$，通过奖励函数获取各输出的奖励 $\{r_1, \dots, r_G\}$，直接用**组内均值和标准差归一化得到的相对分数作为优势（Advantage）**，省去了与策略模型同规模的 Critic（Value）网络，大幅降低训练显存与计算开销；
  2. **相对 SFT 具备可验证结果驱动的自我探索能力**：SFT 只能死记硬背给定的单条参考轨迹；而在数学推理、代码生成或工具调用等**结果可通过规则/编译器/测试集精确验证（RLVR）**的任务中，GRPO 能通过组内采样自主探索并强化那些最终能跑通验证的推理路径，同时直接惩罚格式错误或执行失败的负向轨迹。
* **为什么不能无条件承诺提升**：
  1. **高度依赖奖励信号质量**：若业务任务缺乏客观可验证的规则奖励（如开放文本写作），粗糙的奖励函数极易被模型钻空子（Reward Hacking）；
  2. **受限于基座采样分布**：如果某个难题基座模型采样 $G$ 次全错（组内奖励全为 $0$，标准差为 $0$），组内相对优势无法产生有效梯度信号，仍需先靠高质量 SFT 冷启动补齐基础能力。

### 26. 如何证明提升来自 SFT，而不是增加检索轮次？

> **来源**：[S337 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1985-L1985) 直接追问 SFT 与增加检索轮次的收益归因。

**回答：**
必须通过**控制变量的严谨消融实验（Ablation Study）**来剥离模型微调与检索策略的贡献，不能把“换了微调模型同时放开了多轮检索”的混合结果全部归功于 SFT：

在同一份冻结的测试集、相同工具与相同成功判定标准下，构造 $2 \times 2$ 四组对照实验：
1. **基线组**：原始基座模型 + 单轮固定检索预算；
2. **仅扩检索组**：原始基座模型 + 多轮检索预算（验证纯粹增加检索机会带来的召回与准确率增益）；
3. **仅 SFT 组**：SFT 微调后模型 + 单轮固定检索预算（验证在完全相同的上下文输入下，微调对证据理解、格式遵循和推理准确率的独立增益）；
4. **组合组**：SFT 微调后模型 + 多轮检索预算（验证微调是否提升了模型在多轮检索中改写 Query、识别缺失证据和及时停止的能力）。

同时分别记录四组的端到端准确率、平均检索轮次、总 Token 消耗与 P95 延迟，才能给出可信的工程归因。

### 27. 应用工程师对蒸馏、MoE 和训练细问需要掌握到哪里？

> **来源**：[S152 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L204-L204) 问知识蒸馏概念及应用侧理解深度；[S062 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L223-L223) 追问项目采用蒸馏或特定架构的工程动机。

**回答：**
AI 应用工程师重点掌握机制原理、数据闭环与线上资源取舍：

* **知识蒸馏（Knowledge Distillation）**：
  * **两种主流方式**：一是**黑盒数据蒸馏**（用高成本旗舰大模型生成高质量思维链或结构化输出，经过确定性校验、执行过滤与去重后，作为 SFT 数据训练小模型，应用落地最广）；二是**白盒 Logits 蒸馏**（让学生模型直接拟合教师模型输出层的概率分布，最小化 KL 散度）；
  * **核心工程防线**：严禁将教师模型的原始输出未经清洗直接喂给学生，必须通过单元测试、规则校验或交叉验证剔除教师幻觉，否则会把教师的错误固化到小模型中。
* **MoE（Mixture of Experts，混合专家架构）**：
  * **计算与显存特征**：将 Transformer 中的稠密 FFN 替换为多个专家子网络（Experts）和门控路由（Router），每个 Token 仅激活 Top-$k$ 个专家参与计算。因此 MoE 模型具有**“大总参数量、小激活参数量”**的特点——单次推理的**计算量（FLOPs）接近小模型**，但**显存占用必须加载全部专家的总参数量**（不能按激活参数量估算显存），在推理服务上适合高并发大吞吐场景，单请求本地受限显存部署则不如同激活规模的稠密模型紧凑。
