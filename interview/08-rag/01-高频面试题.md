## 1. RAG 从文档进入到回答生成，完整链路是什么？

> **来源**：[S063 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L246-L246) 同时追问 RAG 完整链路与 Embedding / Vector Retrieval 的具体工程实现。

**回答：**
生产级 RAG 系统由**离线文档摄取链路（Ingestion Pipeline）**与**在线检索生成链路（Retrieval & Generation Pipeline）**两条闭环组成：

* **离线摄取链路（把非结构化文档变成可检索、可回源的索引记录）**：
  1. **文档解析与清洗**：提取 PDF、Word、网页或 Markdown 的正文、多级标题层级、表格与图表结构，过滤页眉页脚噪点；
  2. **结构化分块（Chunking）**：按文档标题树与 Token 预算切分为语义完整的 Chunk，并为每个 Chunk 绑定稳定主键 `chunk_id`、所属 `doc_id`、章节路径、版本号及租户/权限 ACL 标签；
  3. **多路索引构建**：调用 Embedding 模型批量编码稠密向量写入向量库（构建 HNSW 等 ANN 索引），同时分词写入全文检索引擎（构建 BM25 倒排索引），原文与父级章节存入关系库或文档库。
* **在线查询链路（在权限范围内找准证据并受控生成）**：
  1. **身份鉴权与查询理解**：从登录态解析用户权限过滤条件，结合对话历史对用户问题做指代消解与 Query 改写；
  2. **多路召回与融合（Hybrid Search）**：并行执行向量语义检索与 BM25 词法检索（均带权限 Pre-filter），通过 RRF（倒数秩融合）去重合并候选集；
  3. **精排与上下文扩展（Rerank & Context Packing）**：使用 Cross-Encoder Reranker 对粗召回候选精细打分截取 Top-K，按需回取父块或相邻块补全上下文，并在 Token 预算内按证据编号拼装 Prompt；
  4. **受控生成与引用校验**：大模型基于给定证据生成带 `[doc_id/chunk_id]` 引用标记的回答，后置校验引用真实性与忠实度后流式返回。

## 2. 为什么需要 RAG？长上下文、微调、文件搜索和业务工具怎么选？

> **来源**：[S109 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-06.md#L348-L348) 直接比较 RAG 与微调的边界；[S218 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-15.md#L37-L37) 追问大上下文下为何仍需 RAG，以及直接文件搜索的优缺点。

**回答：**
五种方案各自对应明确的知识形态与工程边界，不能互相替代：

1. **RAG vs 微调（SFT）**：
   * **RAG** 解决**外部动态知识注入与可追溯性**。知识更新只需秒级更新索引，天然支持按用户行级权限隔离、文档撤回删除以及精确到段落的原文引用；
   * **微调（SFT）** 解决**模型输出格式、特定领域任务风格或指令遵循能力**。微调无法记住高频变化的事实，无法做细粒度权限隔离，更无法在某篇文档下线时从模型权重里精准抹除该条知识。
2. **RAG vs 超长上下文（Long Context）**：
   即使模型支持 1M Token 窗口，也不可能把企业数万篇知识库在每次请求时全量塞进 Prompt：一是全量 Prefill 会导致极高的首字延迟（TTFT）与高昂的 Token 费用；二是海量无关文档混入上下文会引发注意力分散（[Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)）降低准确率。RAG 负责在毫秒级内从海量库中筛出最相关的千字证据送入上下文。
3. **预建索引 RAG vs Agent 在线文件搜索（Grep / Glob / Read）**：
   * **在线文件搜索**无需预建向量索引，天然读取最新本地文件（常见于本地代码仓库 Agent），但依赖多轮工具往返扫描，延迟高且面对跨表述语义问题容易漏检；
   * **预建索引 RAG** 通过离线构建倒排与向量索引，保证在线高并发下的毫秒级单次召回与语义泛化。
4. **RAG vs 确定性业务工具（API / SQL）**：
   实时订单状态、账户余额、库存查询与退款写操作必须调用受控的数据库接口或业务 RPC 工具，绝不能靠检索静态文档来回答实时交易状态。

## 3. PDF 有扫描页、表格和图片，怎样证明解析是正确的？

> **来源**：[S207 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-12.md#L63-L63) 问混合文档与扫描 PDF 的多模态解析；[S087 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L277-L277) 进一步要求解释 OCR、表格抽取难点及识别质量如何评估。

**回答：**
* **混合 PDF 的分层解析架构**：
  1. **版面分析与阅读顺序恢复（Layout Analysis）**：先通过文档版面检测模型（如基于视觉检测的 [MinerU](https://github.com/opendatalab/MinerU) / LayoutLM）识别标题、正文段落、多栏排版、表格、公式与插图的边界框，按人类阅读顺序重排，剔除页眉页脚与水印干扰；
  2. **分类提取**：原生可信文本层直接提取字符；扫描页或乱码字库层路由至 OCR；复杂表格（含跨行跨列合并单元格）转换为 **HTML `<table>` 或结构化 Markdown**，并把表头、计量单位（如“单位：百万元”）和表注与表格强绑定；跨页断表通过比对上页末与下页首的列数和表头延续性自动拼接；图表/架构图除了用多模态模型生成文本摘要参与检索外，必须保存原图切片 URI 供生成阶段多模态回看。
* **如何量化评估解析质量（证明解析没出错）**：
  不能只看“提取出了非空文本”，必须构建版面解析黄金测试集分层评估：
  1. **文本与顺序**：计算字符错误率（CER / WER）与多栏阅读顺序编辑距离；
  2. **表格结构保真度**：使用 **TEDS（Tree-Edit-Distance-based Similarity）** 评估 HTML 表格行列拓扑与单元格内容准确性；
  3. **端到端事实探针检验**：针对表格中的特定行列交叉数值、跨页表格末行、带单位/负号金额构造问答探针，验证解析产物能否支撑 100% 精确问答。

## 4. Chunk 为什么这样切？200–500、固定长度和语义切分怎么解释？

> **来源**：[S002 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L40-L40) 要求依据数据与评测确定块大小和策略；[S275 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-26.md#L22-L22) 追问多级标题切分与 200–500 块大小的配置依据。

**回答：**
分块（Chunking）的核心矛盾在于**“向量表征的信噪比（宜小）”**与**“上下文语义的完整性（宜大）”**：

* **为什么块不能太小也不能太大**：
  * **块太小（如 $< 100$ Token）**：虽然单句向量匹配极精准，但极易丢失主语、前提条件、适用范围或但书条款（例如只切出了“可全额退款”，丢了前一句“仅限未拆封商品”）；
  * **块太大（如 $> 1000$ Token）**：一段包含多个不同主题，池化生成的单个 Embedding 向量会被多主题平均稀释（导致细节检索召回率下降），同时还会超出部分 Embedding / Reranker 模型的最大输入窗口（如 512 Token），并浪费生成阶段的上下文预算。
  * **200–500 Token 的工程意义**：通常对应 $1 \sim 3$ 个自然段落，既能装进主流 Embedding 和 Reranker 的 512 窗口而不被截断，又能保持单一集中主题，是工程上最常用的经验起点（具体数值需按评测集 Recall 与 Faithfulness 曲线确定）。
* **三种切分策略对比与生产组合**：
  1. **固定长度切分**：完全无视句子和段落边界，容易把一句话或一张表从中间劈开，仅用作基线；
  2. **结构感知 + 递归字符切分（生产主力）**：先按 Markdown/文档多级标题树（`#`, `##`, `###`）和表格/代码块边界切分；对超长章节再按 `["\n\n", "\n", "。", " "]` 分隔符层级递归细分至目标预算（如 300–500 Token），并将完整父级标题路径拼在每个 Chunk 头部以防丢失主语；
  3. **语义切分（Semantic Chunking）**：计算相邻句子的 Embedding 相似度，在相似度骤降谷底处切开。切分质量好，但离线入库时每个句子都要调一次模型，构建成本远高于结构化递归切分。

## 5. Overlap、父子块和邻居扩展分别解决什么？尾块不足怎么办？

> **来源**：[S402 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L987-L987) 直接问父子分块的实现；[S287 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-28.md#L48-L48) 给出 1000 Token 按 400 切、尾段 200 如何处理的具体追问。

**回答：**
这三种机制分别在不同粒度上解决“切分边界信息断裂”问题：

1. **Overlap（滑动窗口重叠，通常设为块长的 $10\% \sim 20\%$）**：让相邻两个 Chunk 在交界处共享一小段文本，防止刚好跨在切分点上的单句话或核心实体词被一刀切碎；但它只能兜底交界处的一两句话，无法补齐相隔几百字的前提条件；
2. **父子分块（Parent-Child Chunking / Small-to-Big）**：**把“检索粒度”与“阅读粒度”彻底解耦**。将文档先切成较大的父块（Parent Chunk，如 1000–1500 Token 或完整小节），再将每个父块细切成多个子块（Child Chunk，如 200–300 Token）。**子块生成向量负责高精度检索定位；命中子块后，通过 `parent_id` 回取对应的完整父块（并在同一父块被多个子块命中时按 `parent_id` 去重）送给大模型阅读**；
3. **邻居窗口扩展（Neighbor Expansion）**：命中第 $k$ 号 Chunk 后，按文档内连续序号 `chunk_index` 动态把同文档的 $k-1$ 和 $k+1$ 号相邻块一并拉出拼接。

**追问：1000 Token 的文本按 `chunk_size=400` 切分，最后剩下的 200 Token 尾块怎么处理？**
**回答：**
先看是否配置了 `overlap`（例如若 `overlap=100`，步长为 $300$，切出的区间是 $[0,400], [300,700], [600,1000]$，恰好是 3 个满 400 的块，不存在 200 尾块）。若不设 `overlap`（步长 $400$），最后剩余的 200 Token 尾块有三种标准处理方式：
1. **独立保留并补充章节标题头**：200 Token 已具备独立段落语义，直接补上文档/章节标题前缀作为独立 Chunk 入库（最常用）；
2. **向前借用回填（Backward Padding）**：从前一个块的末尾向前借 100～200 Token 拼满上下文，保证尾块语义不单薄；
3. **极短尾块合并（Merge into Previous）**：若尾块极短（例如不足最小阈值 `min_chunk_size=50` Token，只剩一句结语），且并入前一块不会超过 Embedding 模型最大窗口上限（如 512），则直接合并进前一个块。

## 6. Query Rewrite、Multi-query、分解和 HyDE 有什么区别？

> **来源**：[S376 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L4149-L4149) 用“我要退了”的歧义追问改写后效果变差怎么办；[S184 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-10.md#L201-L201) 问 HyDE 的含义与适用条件。

**回答：**
四种检索前查询增强策略针对不同的用户提问缺陷：

1. **Query Rewrite（对话指代消解与规范化改写）**：结合多轮对话历史，将含有代词或省略的口语提问（如上文聊完某型号手机后问“它的保修期多久？”）改写为自包含的独立查询（“XX 型号手机的保修期是多久？”），并映射领域黑话与标准术语；
2. **Multi-Query（多视角同义扩展）**：针对表述模糊的单一意图，生成 $2 \sim 3$ 个不同措辞的同义查询并行检索再做 RRF 融合，降低单一表述的词法/向量偏差；
3. **Query Decomposition（复杂子问题拆解）**：针对对比类或多跳复合问题（如“A 方案和 B 方案在退款手续费上有什么区别？”），拆解为多个独立的原子子查询分别检索，避免单次检索只召回其中一方的材料；
4. **HyDE（Hypothetical Document Embeddings，假设性文档嵌入）**：针对“简短提问与长篇专业文档之间表征空间不对称”的问题，先让 LLM 生成一段假设性的标准回答文档，再用这段假设文档去编码向量检索真实文档（利用“答案到答案”的相似性[，Gao et al., 2023](https://aclanthology.org/2023.acl-long.99/)）。注意：当模型对该领域专有名词完全未知时，HyDE 胡编的假设文档反而会把检索带偏，且延迟与成本较高。

**追问：像用户输入“我要退了”（可能是退货、仅退款、退会员或注销账号）这类强歧义查询，为什么改写后检索效果反而变差？怎么解决？**
**回答：**
因为改写模型在缺乏上下文依据时，强行替用户“猜”了一个具体方向（例如擅自改写成“如何办理会员退费”），导致检索完全偏离用户真实意图。工程解决手段有两条：
1. **始终保留原始 Query 参与双路融合检索**：将 `原始 Query + 改写 Query` 共同检索并融合，绝不丢弃原始输入保底；
2. **引入歧义检测与澄清分支（Clarification）**：当意图分类置信度过低或识别出多义词且历史上下文无指向时，不盲目发起窄化改写，而是先向用户反问澄清，或对主要候选分支各取 Top-2 证据做分情况回答。

## 7. BM25 和向量检索为什么互补？IDF 起什么作用？

> **来源**：[S240 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L27-L27) 追问 BM25 与向量检索各补什么短板；[S275 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-26.md#L23-L23) 明确追问 BM25 机制和 IDF 的作用。

**回答：**
* **为什么 BM25 与向量检索天然互补**：
  * **稠密向量检索**擅长**跨字面的语义泛化与同义理解**（如搜“电脑蓝屏死机”能召回“Windows 系统崩溃排查”），但将整段压缩为单个定长向量后会丢失精确的字面局部特征，对**产品型号（如 `RTX-4090D` vs `RTX-4090`）、错误码（`ERR_5024`）、专有人名/函数名、精确数字**极不敏感；
  * **BM25 词法倒排检索**基于精确词项匹配，恰好在**专有编号、代码符号、罕见实体词与精确关键词定位**上具备极高准确率，但无法处理同义词替换。两者结合（Hybrid Search）能同时守住精确符号匹配与语义泛化。
* **BM25 的核心评分机制与 IDF 的作用**：
  $$\text{BM25}(Q, D) = \sum_{t \in Q} \text{IDF}(t) \cdot \frac{f(t, D) \cdot (k_1 + 1)}{f(t, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{\text{avgdl}}\right)}$$
  1. **IDF（逆文档频率，Inverse Document Frequency）**：衡量查询词 $t$ 在整个文档库中的**稀有度与信息区分力**。像“的、是、如何、系统”这类在几乎所有文档中都出现的高频词，IDF 趋近于 $0$；而像特定报错码、专有产品名这类只在极少数文档中出现的罕见词，IDF 极高，从而赋予关键专有词主导性的排序权重；
  2. **词频饱和（由 $k_1$ 控制）**：同一个词在文档中出现次数 $f(t, D)$ 越多得分越高，但增长会渐近趋于上限 $k_1 + 1$，防止某篇文档靠无意义重复刷屏垄断高分；
  3. **文档长度归一化（由 $b \in [0,1]$ 控制）**：通过当前文档长度与全库平均长度之比 $\frac{|D|}{\text{avgdl}}$ 惩罚冗长文档，避免长文档仅因篇幅大、包含词项多而获得不公平优势。

## 8. RRF 怎么算？为什么不用分数平均？

> **来源**：[S240 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L29-L29) 同时问 RRF 如何融合、为何不简单线性加权，以及平滑常数怎样确定。

**回答：**
* **为什么不直接把 BM25 分数和向量分数做算术平均或简单线性相加**：
  因为两路检索器的**分数量纲、数值区间与概率分布完全不同**：向量余弦相似度固定在 $[-1, 1]$（且常密集分布在 $0.6 \sim 0.9$），而 BM25 分数是无上界的累加值（可能在 $0 \sim 50+$ 之间随查询词数量与 IDF 剧烈波动）。如果直接相加，BM25 的大数值会完全吞没向量分数；如果对每次查询做动态 Min-Max 归一化，一旦某一路出现一个极端离群高分或全路皆为不相关低分，又会严重扭曲整批候选的相对比例。
* **RRF（Reciprocal Rank Fusion，倒数秩融合）的计算公式**：
  RRF 彻底绕开原始分数量纲，仅利用候选文档在各路检索结果中的**名次（Rank，从 $1$ 开始计数）**进行融合（[参考 Elasticsearch RRF 说明](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)）：
  $$\text{RRF\_Score}(d) = \sum_{i=1}^{M} \frac{1}{k + \text{rank}_i(d)}$$
  （若文档 $d$ 未出现在第 $i$ 路检索的前 $N$ 名候选列表中，则该路贡献记为 $0$。）
  * **计算示例**：设常数 $k=60$。若文档 A 在向量检索排第 1、在 BM25 排第 3，则得分为 $\frac{1}{60+1} + \frac{1}{60+3} \approx 0.0323$；若文档 B 仅在向量检索排第 1、在 BM25 未召回，则得分为 $\frac{1}{60+1} \approx 0.0164$。可见**被多路共同认可的文档会自然排到最前面**；
  * **平滑常数 $k$（经典默认值 $k=60$）的作用**：抑制单一路径第 1 名与第 2、3 名之间过大的倒数差距（若 $k=0$，第 1 名是 $1.0$，第 2 名骤降到 $0.5$，单路第一名会压倒双路第 2 名），使融合排序更稳健。

## 9. 为什么召回后重排？加 Rerank 反而变差怎么查？

> **来源**：[S211 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-13.md#L63-L63) 比较 Bi-Encoder 与 Cross-Encoder 的成本；[S249 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-21.md#L58-L58) 明确追问加 Rerank 后效果变差如何定位。

**回答：**
* **为什么需要召回后重排（Retrieve-then-Rerank）**：
  第一阶段的多路召回（BM25 + 双塔 Embedding + RRF）为了追求毫秒级遍历百万级文档，牺牲了 Query 与 Document 之间的细粒度 Token 交互，且 RRF 融合为了擴大召回面会混入大量字面擦边但语义无关的噪声块。第二阶段引入 **Cross-Encoder Reranker**，对粗筛出的数十个候选（如 Top-50）做深层交叉注意力精排，截取高置信度的 Top-5 送入大模型，从而在控制延迟的同时显著提升送入生成阶段的上下文信噪比。
* **加上 Rerank 后效果反而变差的五大定位方向**：
  1. **输入长度截断（最常见隐患）**：许多开源 Reranker 的最大序列长度仅为 512 Token。如果传入的是扩展后的长父块（如 1000 Token），后半段包含核心答案的内容在送入 Reranker 时被静默截断丢弃，导致包含答案的块被打低分淘汰；
  2. **送入 Rerank 的 Query 丢失上下文**：多轮对话中，向量检索用的是指代消解后的改写 Query，但调用 Reranker 时误传了未改写的原始短句（如“那第二种呢？”），导致 Reranker 无法判断相关性；
  3. **垂直领域专有符号水土不服**：通用预训练 Reranker 对内部代码符号、特殊工单号或行业缩写缺乏认知，把原本被 BM25 精准召回排在第 1 名的专有编号文档给压到了后面；
  4. **单证据垄断与多跳证据被挤出**：多跳问题需要文档 A 和文档 B 拼在一起才能作答，但 Reranker 按单文档独立打分，前 5 名全被与问题前半句高度相似的同质化段落占满，挤掉了另一半关键证据；
  5. **粗召回阶段根本未命中**：若正确文档连粗召回 Top-50 都没进去，怎么调 Reranker 都无济于事（可通过对比粗召回 Recall@50 与精排后 Recall@5 立即区分）。

## 10. 系统里到底有几个 Top-K？全部交给大模型重排行不行？

> **来源**：[S115 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L20-L20) 问为何不把全部召回候选交给大模型重排；[S147 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L93-L93) 要求用评测解释为何最终 Top-K 选 6 / 8 而非 3。

**回答：**
* **RAG 漏斗链路中的四级 Top-K**：
  不能用一个笼统的 $K$ 概括整条链路，生产系统中存在四级递减的候选窗口：
  1. **各路粗召回窗口 $K_{\text{recall}}$**（如向量检索取 Top-50，BM25 取 Top-50）：目标是最大化**召回覆盖率（Recall）**，宁可多召回不可漏掉真证据；
  2. **RRF 融合去重后送入 Reranker 的窗口 $K_{\text{rerank\_in}}$**（如取合并后的前 40～60 条）：直接决定 Cross-Encoder 的在线推理耗时与 GPU 算力开销；
  3. **精排截断数 $K_{\text{final}}$**（如 Rerank 后保留前 5～8 条，并结合最低相关性阈值过滤）；
  4. **最终装包 Token 预算 $B_{\text{context}}$**（如最多不超过 4,000 Token）：父块回取或邻居扩展后按实际 Token 数封顶。
* **为什么最终 $K_{\text{final}}$ 选 6～8 而不是 3（如何用评测解释）**：
  当 $K=3$ 时，对于单点事实查询足够，但面对**跨段落综合题、对比题或存在重复近似文档**时，前 3 条往往被同一篇文档的相邻块占满，导致 Recall@3 明显低于 Recall@8；而继续放大到 $K=15\sim 20$ 时，Recall 边际增益见顶，反而因引入低相关噪声导致生成 Faithfulness 下降、TTFT 延迟增加。因此选择 Recall 曲线拐点且端到端回答准确率最高的位置（如 6～8）。
* **为什么不能把粗召回的几十上百条候选全部交给大模型重排（Listwise LLM Rerank）**：
  1. **延迟与成本过高**：将 50～100 个 Chunk 塞给大模型做排序，单次输入动辄数万 Token，TTFT 高达数秒，成本比专用小参数 Cross-Encoder（如数百兆的 BGE-Reranker）高出一个数量级；
  2. **长列表位置偏置与输出截断**：LLM 对长列表中间位置的候选同样存在注意力衰减（Lost in the Middle），且输出几十个 ID 排序极易漏项或格式出错。

## 11. 证据怎样装进上下文？引用和拒答怎么保证？

> **来源**：[S240 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L32-L32) 要求验证结论并把引用映射回证据；[S067 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L334-L334) 追问证据不足怎样判断和拒答。

**回答：**
* **上下文证据装包（Context Packing）规范**：
  1. **去重与同文合并**：同一文档的相邻或重叠 Chunk 按原文阅读顺序合并，避免碎片化重复占用 Token；
  2. **结构化元数据头封装**：每个证据块必须显式附带短引用编号（如 `[1]`, `[2]`，比长 UUID 更不易被模型抄错）、文档标题、章节路径、生效日期与权威等级，帮助模型处理新旧政策冲突；
  3. **相关性排序布局**：将得分最高的核心证据置于证据区头部（或首尾两端），降低长上下文中部遗忘风险。
* **如何工程化保证引用真实性与无证据拒答**：
  1. **检索层硬性熔断（Pre-generation Gate）**：若 Reranker 最高分低于设定的拒答下限阈值，或召回结果为空，**直接由代码拦截并返回“知识库中暂无相关依据”或触发澄清**，根本不调用生成大模型，从源头杜绝无中生有；
  2. **生成层结构化引用约束**：要求模型输出的每条事实陈述必须紧跟 `[编号]`，并在系统指令中给出明确的“证据缺少关键条件时如何拒答/部分作答”的 Few-shot 示范；
  3. **后置引用校验（Post-generation Verification）**：正则提取模型回答中的所有 `[k]` 编号，核验其是否真实存在于本轮注入的证据集合中（防捏造编号），并在高敏场景下校验该编号对应的原文是否确实蕴含（Entailment）该句结论。

## 12. Recall、Precision、MRR、NDCG 和答案准确率怎么区分？

> **来源**：[S052 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L18-L18) 明确问 Recall、Faithfulness 等指标的定义与计算；[S153 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L230-L230) 问检索评测指标体系。

**回答：**
RAG 评测必须严格拆分为**检索层指标（Retrieval Metrics）**与**生成层指标（Generation Metrics）**：

* **一、检索层指标（衡量“找得全不全、排得准不准”）**：
  1. **Recall@K（召回率）**：$\frac{\text{前 } K \text{ 个结果中命中的相关文档数}}{\text{该问题在全库中所有相关文档总数}}$。衡量**有没有把所需证据漏掉**，是粗召回阶段最重要的核心指标；
  2. **Precision@K（精确率 / Context Precision）**：$\frac{\text{前 } K \text{ 个结果中命中的相关文档数}}{K}$。衡量返回的前 $K$ 条里**掺杂了多少无关噪声**（注：若某题只需 1 篇文档即可回答，即使排在第 1 名，Precision@10 也只有 $0.1$，因此不能脱离分母单看 Precision@K）；
  3. **Hit Rate@K（命中率）**：前 $K$ 个结果中**只要包含至少 1 个**相关文档即记为 $1$，否则为 $0$。适合单证据问答，但无法衡量多跳问题是否集齐了全部证据；
  4. **MRR（Mean Reciprocal Rank，平均倒数秩）**：$\frac{1}{|Q|} \sum \frac{1}{\text{首个相关文档的名次}}$。只关心**第一个相关文档出现得有多靠前**；
  5. **NDCG@K（归一化折损累计增益）**：同时支持**多级相关性打分**（如完全相关 2 分、部分相关 1 分、无关 0 分）与**位置折损权重**（排越靠前权重越高，按 $\frac{1}{\log_2(i+1)}$ 衰减），是衡量 Rerank 精排质量最全面的排序指标。
* **二、生成层指标（衡量“答得忠不忠实、对不对”，[参考 RAGAS 框架](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)）**：
  1. **Faithfulness（忠实度 / 无幻觉度）**：回答中拆解出的每条事实声明，有多少比例能由**本轮检索出的上下文**直接推导出来（衡量模型有没有脱离上下文乱编）；
  2. **Answer Relevance（回答相关性）**：回答是否切题、有没有答非所问或遗漏子问题；
  3. **Answer Correctness（端到端答案准确率）**：最终生成的回答与人工标注的**标准答案（Ground Truth Answer）**在事实与语义上的一致程度。

## 13. 评测集从哪里来，怎样证明优化有效？

> **来源**：[S084 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L217-L217) 问评测维度与数据集构建；[S065 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L296-L296) 要求说明实际调过的参数及调优有效性的判断依据。

**回答：**
* **黄金评测集（Golden Dataset）的三大来源与构造标准**：
  1. **真实线上日志与历史 Bad Case 脱敏抽样**（最具代表性，覆盖用户真实的口语省略与错别字）；
  2. **业务专家与客服高频 FAQ 整理**（覆盖核心高价值业务规则与红线问题）；
  3. **基于文档逆向合成 + 人工审核（Synthetic Data）**：针对长尾冷门章节、复杂表格和跨段多跳逻辑，用大模型基于原文反向生成问答对，但**必须经过人工或规则质检过滤**，剔除脱离原文的伪问题。
  * **关键工程细节**：评测集的标准证据标注应绑定**原文稳定锚点（如文档 ID + 字符起止偏移或核心事实句）**，而不要写死某次切分的 `chunk_id`；否则一旦调整了分块大小（Chunk Size），原有的 `chunk_id` 全部改变，检索评测就会彻底失效。此外还必须包含 $10\% \sim 15\%$ **知识库中无答案的拒答样本**。
* **如何证明某项优化（如改分块、加 BM25、换 Reranker）真正有效**：
  遵循**单变量消融实验**：冻结评测集、知识库版本与生成模型，每次只改动一个模块（例如对比“纯向量 Top-10” vs “BM25+向量 RRF Top-10” vs “RRF Top-50 + Rerank Top-5”），同时汇报**检索 Recall@K、生成 Faithfulness、端到端 Correctness、拒答准确率以及 P95 延迟变化**，确保总体指标提升且核心切片无回退。

## 14. 回答差时怎样快速判断问题在检索还是生成？

> **来源**：[S280 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-27.md#L59-L60) 直接问回答差时如何区分检索和生成问题；[S253 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-21.md#L178-L178) 追问 Answer Relevance 偏低时的归因排查。

**回答：**
通过**检查最终送入 LLM 的上下文证据快照（Context Snapshot）**并配合**Oracle 黄金证据替换实验**，可在 1 分钟内精确定位故障层级：

1. **第一步：看最终喂给 LLM 的 Top-K 证据里有没有完整、正确的答案依据？**
   * **如果已经包含完整正确证据，但模型依然答错、漏答或编造** $\rightarrow$ **100% 属于生成层问题（Generation Failure）**：
     排查 Prompt 指令是否冲突、证据是否被过多无关噪声淹没（Context Precision 过低）、新旧文档冲突未标明时间戳，或模型算术/逻辑推理能力不足。
   * **如果最终喂给 LLM 的 Top-K 里根本没有正确证据** $\rightarrow$ **属于上游摄取或检索层问题（Retrieval / Ingestion Failure）**，继续向上游顺藤摸瓜：
2. **第二步：在检索链路内部逐级回溯证据是在哪一步丢失的**：
   * **看 Rerank 之前的粗召回池（如 Top-50）里有没有？** 若粗召回里有、Rerank 后没了 $\rightarrow$ **重排层误杀**（排查 Rerank 512 长度截断或领域不适配）；
   * **若粗召回 Top-50 里也没有**：去底层库用关键词搜原文。若库里压根没这段文字或表格错位 $\rightarrow$ **文档解析与分块层故障（PDF 解析丢字、跨页表断裂、块切太碎丢了主语）**；若库里有完整 Chunk 但没召回 $\rightarrow$ **检索层故障**（专有名词未走 BM25、Query 指代未消解、或标量过滤条件过严）。

## 15. 知识库怎样增量更新？旧任务晚完成、删除和回滚怎么办？

> **来源**：[S081 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L152-L152) 追问持续更新时的向量索引、缓存失效和旧文档召回；[S107 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-06.md#L288-L288) 问文档版本控制与错误版本回滚。

**回答：**
企业知识库增量更新的核心挑战是保证**关系库、向量库、BM25 倒排索引与缓存之间的跨存储最终一致性**，并防止幽灵旧块（Orphan Chunks）残留：

1. **基于内容哈希的增量 Diff 更新**：
   文档修订时，对比新旧 Chunk 的内容哈希（`content_hash`）。未发生变化的 Chunk 跳过 Embedding 计算直接复用原向量；仅对新增或修改的 Chunk 调用编码器，大幅节省算力；
2. **防止“幽灵旧块”与并发乱序覆盖**：
   * 当一篇长文档被改短（原本有 10 个 Chunk，新版只有 6 个 Chunk）时，若只 Upsert 前 6 个块，第 7～10 号旧块会永久残留在向量库中继续被错误召回。因此必须通过**先写入带新版本号 `doc_version` 的新块，再删除同 `doc_id` 且版本号 $< \text{new\_version}$ 的所有旧块**来彻底清理；
   * 异步 Worker 消费任务时，必须在写库前原子校验数据库中的最新 `doc_version`，若发现当前任务的 `version` 小于已落库版本（旧任务因重试晚到），直接丢弃，防止旧任务覆盖新结果；
3. **文档下线删除与缓存同步失效**：
   权限撤回或文档删除时，先在主库将文档状态置为不可见（在线检索回表校验时立即拦截），同步清理向量库、ES 倒排记录，并使关联该 `doc_id` 的问答缓存失效；
4. **版本回滚机制**：
   元数据表保留文档的历史版本快照指针。回滚时生成一个新的递增修订号指向目标历史快照内容，触发标准增量发布流水线切换生效（索引级蓝绿迁移详见 [Vector DB 问答](../07-vector-db/01-高频面试题.md)）。

## 16. 多租户知识库怎样防越权？相同内容能共享缓存吗？

> **来源**：[S254 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-21.md#L211-L211) 明确要求防止员工越权读取知识库；[S373 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3972-L3972) 问不同知识库的数据隔离。

**回答：**
* **多租户与细粒度权限（ACL / RBAC）防越权闭环**：
  1. **入库绑定权限标签**：离线摄取时，将文档的 `tenant_id`、部门角色列表或允许访问的用户组 ID 同步写入向量库与 ES 的标量元数据字段；
  2. **检索前服务端强制注入 Pre-filter**：在线请求到达时，由后端鉴权中间件根据用户登录 Token 查询权限中心，构造不可篡改的过滤表达式（如 `tenant_id == current_tenant AND role IN user_roles`）直接下推至向量检索与 BM25 检索底层，绝不允许先全库无过滤检索再靠 Prompt 让模型“不要透露无权限内容”；
  3. **父块扩展与按 ID 回取二次鉴权**：在执行父子块回取、邻居块扩展或点击引用链接下载原文时，必须再次校验目标文档是否属于当前用户合法权限集。
* **为什么相同问题或相同内容不能跨租户/跨权限直接共享问答缓存**：
  如果缓存 Key 仅对 `Query 文本`（或语义向量）做哈希，当高管用户 A 提问“今年部门薪酬调整方案是什么？”并写入缓存后，普通无权限员工 B 问出同样的问题就会直接命中缓存拿到机密答案，造成严重的**缓存侧信道越权泄漏**。
  * **正确做法**：问答缓存的 Key 必须包含 **`(tenant_id, user_permission_scope_hash, kb_version, query)`**；只有离线阶段对完全相同文本计算的纯数学 Embedding 向量（不含业务归属状态）才可以在底层按内容哈希安全复用。

## 17. 百万商品或 TB 级 PDF 怎样估算规模和定位慢查询？

> **来源**：[S217 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-15.md#L17-L17) 给出 600GB–1TB 金融 PDF 的设计场景；[S277 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-26.md#L85-L85) 给出百万 / 千万商品问答场景。

**回答：**
* **第一步：把原始文件体积/记录数换算为向量规模与资源量级**：
  不能直接拿“1TB PDF 文件”去算向量库内存，因为 PDF 体积绝大部分是高分辨率扫描图片、内嵌字体和流对象。
  1. **抽样折算**：假设 1TB 金融 PDF 包含约 $20\text{ 万}$ 份研报/财报（平均每份 5MB、约 30 页），总计约 $600\text{ 万}$ 页；按每页提取约 $600\text{ Token}$、每块 $400\text{ Token}$ 计算，实际约产生 **$900\text{ 万} \sim 1000\text{ 万}$ 个 Chunk**（与“一千万商品库，每商品一条向量”同处 **$10^7$（千万级）** 向量规模）；
  2. **存储与内存估算**：$10^7$ 条 $1024$ 维 float32 向量，裸向量占 $10^7 \times 1024 \times 4 \approx 41\text{ GB}$；若采用全内存 HNSW 索引加上副本与冗余，需约 $100\sim 120\text{ GB}$ 内存；若采用 `HNSW_PQ` / `DiskANN` 或按年份/行业分区冷热分层，内存可压缩至 $20\sim 30\text{ GB}$ 以内。
  3. **离线构建吞吐瓶颈**：1TB PDF 真正的耗时大头在 **OCR / 版面解析与 Embedding 推理**，需通过消息队列 + 多 GPU Worker 池并行批处理，并按内容哈希去重跳过重复附件。
* **第二步：在线慢查询定位与加速**：
  对在线链路打点拆分耗时（Query 改写 $\rightarrow$ Embedding 编码 $\rightarrow$ 多路并行检索 $\rightarrow$ Rerank $\rightarrow$ LLM 首字 TTFT）：
  * 通常最慢的两个环节是**前置 LLM 串行改写**（耗时 500ms+）与 **Cross-Encoder 重排候选过多**（如一次重排 100 条长文本耗时 400ms+）；
  * **优化手段**：首轮无指代问题跳过 LLM 改写；向量与 BM25 严格异步并发请求；利用商品类目、年份或租户 Partition Key 缩小检索范围；将送入 Reranker 的候选数控制在 30～40 条以内并开启 FP16 动态批处理。

## 18. 什么时候用 GraphRAG 或 Agentic RAG？

> **来源**：[S272 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-25.md#L42-L42) 比较 GraphRAG 与普通 RAG 的适用场景；[S222 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-15.md#L135-L135) 比较主动检索（Agentic RAG）与固定流水线 RAG。

**回答：**
普通固定流水线 RAG（Naive / Advanced RAG）适合**单跳事实查询或证据集中在少数几个段落内**的问题；当遇到关系跨度大或信息需求动态演化的场景时，分别评估 GraphRAG 与 Agentic RAG：

* **GraphRAG（图增强检索）的适用场景与代价**：
  * **适用场景**：
    1. **跨多文档的显式关系与多跳路径查询**（例如“A 公司的实控人通过哪些关联方持有 B 项目？”或复杂故障依赖链追踪）；
    2. **全库宏观主题归纳（Global Sensemaking）**：如 [Microsoft GraphRAG](https://arxiv.org/abs/2404.16130) 通过从文档中抽取实体-关系图谱，运行 Leiden 社区发现算法并预先生成各层级社区摘要（Community Summaries），专门解决普通 Top-K 检索无法回答的“过去一年全库所有研报的核心风险趋势有哪些？”这类全局总结问题。
  * **工程代价**：离线需要调用大模型对全量块做实体关系抽取与社区摘要，Token 构建成本极高，且实体消歧错误、文档增量更新与删除维护远比普通向量库复杂。
* **Agentic RAG（智能体主动迭代检索）的适用场景与边界**：
  * **适用场景**：**下一轮该搜什么高度依赖上一轮搜出的中间结果**（例如先搜出某报错对应的模块名，发现该模块调用了内部配置项 X，再发起第二轮检索查配置项 X 的定义）。由模型自主决定调用哪种检索工具（向量、全文、SQL、图查询）、动态改写 Query 并评估当前证据是否充分；
  * **工程边界**：必须设置最大检索轮次（如最多 3 轮）与超时预算，对日常 80% 简单明确的事实查询仍走固定单次检索快路径，避免所有请求都承受多轮 Agent 循环的高延迟与高成本。

## 19. Code RAG 为什么不能只把代码当普通文本切？

> **来源**：[S398 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L823-L823) 追问超长方法是否仍整体切块；同一面经的 [S398 后续记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L827-L827) 又给出用户搜“数据权限”而代码只有 RBAC 命名时的表达错位场景。

**回答：**
代码具有严格的语法作用域与跨文件调用拓扑，如果按固定字符数切分，会把函数签名、局部变量定义和内部逻辑腰斩，导致切出的代码片断既无法理解也无法编译。

* **Code RAG 的语法感知切分与超长函数处理**：
  1. **基于 AST（抽象语法树，如 Tree-sitter）切分**：以类（Class）、函数/方法（Function/Method）、接口定义作为天然切分边界；
  2. **超长函数处理**：当单个巨型函数超过窗口预算（如上千行）必须拆分时，不能裸切内部代码块，必须**在每个子块头部强制保留完整的文件路径、`import` 依赖、所属类名、函数签名及 Docstring 注释**，并记录父函数 ID 以便命中后按需回读上下文。
* **如何解决“自然语言业务词（如‘数据权限’）”与“代码标识符（如 `check_rbac_scope`）”之间的表达鸿沟**：
  1. **离线代码摘要双索引**：入库时为每个函数/类生成简短的自然语言功能摘要（结合注释、提交记录与函数体），检索时同时匹配“自然语言摘要向量”与“原始代码向量”；
  2. **领域术语词典映射 + 混合检索**：在 Query 改写层将业务黑话（“数据权限”）扩展映射为代码库对应的技术术语与符号（`RBAC`, `acl`, `tenant_filter`），结合精确符号检索（BM25 / Grep）与向量检索；
  3. **调用图（Call Graph / LSP）关联扩展**：命中入口函数后，顺着 AST 符号引用或静态调用图自动拉取其调用的核心子函数签名与数据结构定义（代码修改与沙箱验证闭环见 [Agent 面试准备](../09-agent/README.md)）。
