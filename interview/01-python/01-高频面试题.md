## 1. 线程、进程、协程分别解决什么问题？

> **来源**：[S064 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L271-L271)、[S358 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3100-L3100) 分别涉及线程/进程选择及线程与异步的比较。

**回答：**
三者是不同层级的并发与资源调度单位，核心分工如下：

1. **进程（Process）**：拥有独立的内存空间和系统资源，由操作系统调度。主要用于资源隔离和多核并行计算（如多 Worker 部署或 CPU 密集型任务）。缺点是进程间创建和通信开销大。
2. **线程（Thread）**：同一进程内的多个线程共享内存地址空间，由操作系统抢占式调度。适合处理没有异步支持的阻塞 I/O 任务。缺点是需要加锁保护共享状态，且在 CPython 中受 GIL 限制，纯 Python 代码无法利用多核并行。
3. **协程（Coroutine）**：运行在单线程内的用户态轻量级调度，基于事件循环实现协作式调度。适合处理海量高并发的网络 I/O 请求（如模型调用、HTTP 请求）。缺点是不能有同步阻塞或 CPU 密集计算，否则会直接卡死主事件循环。

**追问：遇到“一千个并发网络请求”时，应该开一千个线程还是用协程？**
**回答：**
优先用协程。创建一千个线程会带来极高的操作系统上下文切换成本和内存开销（每个线程默认占用数兆栈空间），极易耗尽系统资源；而一千个协程只是事件循环管理的轻量级对象，内存占用极小。但无论用哪种，生产环境中都必须通过信号量或连接池设置最大并发上限，防止瞬间打垮下游服务。

## 2. GIL 意味着 Python 线程完全不能并行吗？

> **来源**：[S008 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L184-L185) 直接问 GIL 机制与多线程并行边界。

**回答：**
不是。GIL（全局解释器锁）限制的是：在 CPython 解释器中，同一时刻只有一个线程能执行 Python 字节码。

但在以下场景中，多线程依然可以实现真正的并行：
1. **I/O 阻塞阶段**：当线程进入网络传输、磁盘读写或 `time.sleep` 等等待时，解释器会主动释放 GIL，允许其他线程运行。
2. **底层 C/C++ 扩展计算**：NumPy、PyTorch、OpenCV 等科学计算库在执行底层密集计算时，会在 C 代码层主动释放 GIL，此时多线程可以充分利用多核 CPU。

此外，从 Python 3.13 开始引入了可选的无 GIL 构建（Free-threaded CPython）。但需要注意，即使在没有 GIL 或 GIL 被释放的场景下，应用层的共享数据依然需要开发者显式加锁保护，GIL 从不等于业务代码天然线程安全。

## 3. async 函数调用后会立即执行吗？await 做了什么？

> **来源**：[S357 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3066-L3066) 追问协程内同步阻塞；此处先说明协程对象、调度与 await 机制。

**回答：**
不会立即执行。直接调用 `async def` 函数只会返回一个协程对象（Coroutine Object），并没有启动执行。只有将该协程提交给事件循环调度（例如通过 `await`，或者 `asyncio.create_task()` 创建任务），代码才会开始运行。

`await` 的核心作用是**挂起当前协程，把 CPU 控制权交还给事件循环**：
事件循环可以转去处理其他已经就绪的任务；当被 `await` 的操作（如网络响应返回）完成时，事件循环再在后续的循环周期中唤醒当前协程继续往下执行。

**追问：连续执行 `await a()` 和 `await b()`，它们是并发运行的吗？**
**回答：**
不是，它们是严格串行执行的。必须等 `a()` 完全执行完毕返回后，才会开始调度并执行 `b()`。如果需要让两个独立的 I/O 操作并发进行，必须使用 `asyncio.gather(a(), b())` 或 `asyncio.TaskGroup` 显式组织并发。

## 4. gather、as_completed 和 TaskGroup 怎样选？

> **来源**：[S064 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L272-L272) 比较 gather 与 as_completed；TaskGroup 作为结构化并发与异常处理对照。

**回答：**
根据结果获取方式和异常处理需求进行选择：

1. **`asyncio.gather`**：适合需要**等待全部任务完成并按传入顺序收集结果**的场景。默认情况下，一旦某个子任务报错，`gather` 会立刻向外抛出异常，但其他未完成的任务默认仍会在后台继续运行，不会自动取消。
2. **`asyncio.as_completed`**：返回一个迭代器，适合**谁先完成就先处理谁**的流式消费场景，不需要等待所有任务全部结束才开始处理。
3. **`asyncio.TaskGroup`（Python 3.11+）**：推荐用于需要**结构化并发**的场景。在 `async with TaskGroup()` 退出时会等待所有任务；只要组内任何一个任务抛出未捕获异常，它会自动取消组内其余尚未完成的任务，彻底避免孤儿任务。

**追问：在多路模型召回场景下，如果允许个别模型接口失败，`gather` 应该如何处理？**
**回答：**
传入 `return_exceptions=True` 参数。这样即使某个模型调用超时或报错，异常对象会直接作为该位置的结果放入返回列表中，不会中断整个收集流程，调用方遍历列表过滤掉异常结果即可。

## 5. 为什么可变默认参数会导致跨请求污染？

> **来源**：基础补足（解释跨请求可变状态污染的底层共享语义）。

**回答：**
因为 Python 函数的默认参数只在**函数定义阶段被求值并创建一次**，并作为属性绑定在函数对象上。后续所有省略该参数的调用，都会共享访问同一个对象。

如果默认参数是列表或字典等可变对象（如 `def add_item(item, items=[])`），在函数内部做 `items.append(item)` 原地修改后，该改动会永久保留在函数对象上。在 FastAPI 等常驻进程的 Web 服务中，下一个请求再次调用该函数时，就会读到上一个请求写入的数据，导致跨请求状态污染。

正确写法是用 `None` 作为默认占位符，在函数体内进行动态初始化：
```python
def append_event(event, events=None):
    if events is None:
        events = []
    events.append(event)
    return events
```

## 6. 赋值、浅拷贝与深拷贝有什么区别？

> **来源**：基础补足（以对象引用关系解释深浅拷贝与并发状态隔离边界）。

**回答：**
三者的核心区别在于对原对象及其内部嵌套对象的引用复制程度：

1. **赋值（`b = a`）**：只是创建了对原对象的全新引用名称，不创建任何新对象。对 `b` 的任何修改都会直接反映在 `a` 上。
2. **浅拷贝（`copy.copy`）**：创建了一个新的最外层容器对象，但容器内部引用的所有子元素依然指向原来的对象。修改最外层容器（如增删元素）互不影响；但修改内部嵌套的可变子对象（如修改嵌套列表里的值），仍会互相影响。
3. **深拷贝（`copy.deepcopy`）**：递归复制整个对象图中的所有层级，生成完全独立的副本。修改任何层级均互不影响。

**追问：深拷贝是不是解决数据并发隔离的通用解法？**
**回答：**
不是。深拷贝性能开销大，更关键的是很多系统级资源（如数据库连接、网络套接字、文件句柄、锁和模型实例）根本不能也无法被深拷贝。工程上应当通过清晰的数据结构划定可变状态边界，而不是无节制地使用深拷贝。

## 7. 装饰器是什么？闭包又是什么？

> **来源**：[S054 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L63-L64)、[S032 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L21-L22) 分别问装饰器机制、闭包与运行时场景。

**回答：**
* **装饰器**：是一种在不修改原函数代码的前提下，动态为其添加额外功能的语法糖（本质是一个接收函数并返回新函数的高阶函数）。常见用于日志打点、接口计时、权限校验和缓存。
* **闭包**：是一个能够记住并访问定义该函数时所在的外部作用域变量的函数对象，即使外部函数已经执行完毕退出，内部函数依然保留对这些变量的引用。

装饰器通常利用闭包来实现：外层装饰器函数接收目标函数，内层包装函数引用该目标函数并在调用前后执行附加逻辑。

**追问：自定义装饰器时，为什么必须在包装函数上添加 `@functools.wraps(func)`？**
**回答：**
因为装饰器返回的是内层包装函数，这会导致原函数的元信息（如 `__name__`、`__doc__`、类型注解和参数签名）被包装函数覆盖。使用 `@functools.wraps` 可以自动将原函数的元数据完整复制到包装函数上，避免破坏反射机制、日志追踪以及框架（如 FastAPI）对参数依赖的解析。

## 8. with 和上下文管理器为什么适合资源管理？

> **来源**：[S032 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L21-L22) 问上下文管理器与 with 语句的运行时资源管理。

**回答：**
因为上下文管理器通过实现 `__enter__` 和 `__exit__` 协议，将资源的获取与释放绑定在了一起。

无论 `with` 代码块是正常执行结束、提前 `return`，还是内部发生了未捕获的异常，Python 运行时均保证一定会执行 `__exit__` 方法。这杜绝了手动调用 `close()` 时因遗漏或异常导致的文件句柄泄漏、数据库连接悬挂或死锁问题。在异步场景中，通过 `__aenter__` 和 `__aexit__` 协议支持 `async with`，同样保证异步连接与事务的可靠回收。

## 9. 迭代器、生成器与列表有什么区别？

> **来源**：[S226 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-16.md#L39-L39) 涉及迭代器/生成器区别及惰性求值状态。

**回答：**
核心区别在于**求值时机与内存占用**：

1. **列表（List）**：是已经分配完整内存的数据容器，所有元素预先保存在内存中，支持随机索引访问，但处理大规模数据时内存消耗大。
2. **迭代器（Iterator）**：是实现了 `__iter__` 和 `__next__` 协议的对象，只能按顺序通过 `next()` 单向获取下一个元素。
3. **生成器（Generator）**：是实现迭代器的一种轻量级语法（包含 `yield` 关键字的函数或生成器表达式）。采用惰性求值（Lazy Evaluation），只有在被遍历消费时才即时计算并返回数据，内存占用恒定为 $O(1)$，非常适合处理日志流和大模型流式输出（Streaming Token）。

**追问：生成器遍历完一次之后，可以直接遍历第二次吗？**
**回答：**
不能。生成器是一次性消费的流，遍历结束后内部指针停留在终止状态，再次遍历只会得到空结果。如果后续需要多次使用，必须在首次消费时存入列表，或者重新调用生成器函数创建新的生成器实例。

## 10. list 与 tuple 有何区别，dict 如何组织数据？

> **来源**：[S054 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L63-L64)、[S035 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L79-L79) 分别问 list/tuple 区别与 dict 底层哈希存储机制。

**回答：**
* **list 与 tuple 的区别**：list 是可变序列，支持动态扩容与原地修改；tuple 是不可变序列，内存占用更紧凑，创建速度更快。只包含不可变对象的 tuple 是可哈希的，可以作为 dict 的键或 set 的元素，而 list 不能。
* **dict 的底层组织**：CPython 中的 dict 底层基于哈希表实现，采用分离的紧凑存储结构（一个稀疏哈希索引表 + 一个按插入顺序连续存放键值对的条目数组）。定位数据时先计算 key 的 hash 值，映射到索引槽位；如果发生哈希冲突，采用开放寻址法探测下一位置，最终匹配相同的 hash 和 key。平均查询时间复杂度为 $O(1)$。作为 key 的对象必须可哈希，且在其生命周期内哈希值保持不变。

## 11. Python 怎样管理内存？内存一直涨应如何排查？

> **来源**：[S329 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1476-L1477) 直接涉及 Python 引用计数、分代垃圾回收与内存泄漏排查。

**回答：**
* **内存管理机制**：主要依靠**引用计数机制**，每个对象维护一个引用计数器，计数归零时立即释放。针对循环引用（A 引用 B，B 引用 A）导致计数无法归零的问题，辅以**分代垃圾回收器（Generational GC）**，分为 0、1、2 三代，定期通过标记清除算法扫描并回收循环引用对象。底层通过内存池（PyMalloc）管理小内存对象，减少系统内存碎片。
* **内存泄漏排查思路**：
  1. 使用标准库 `tracemalloc` 在不同时间点抓取内存快照做 diff，定位持续增长的对象类型与分配源码行；
  2. 重点排查全局变量（如无淘汰策略的本地全局缓存、长生命周期字典）、未显式取消并持续挂起的异步后台任务、以及闭包中捕获的大对象；
  3. 若涉及 C 扩展或调用外部原生库，需检查原生层是否存在未释放的内存，因为原生内存分配不受 Python GC 管辖。

## 12. 异常应该在哪里捕获？为什么不能一把 except 后继续？

> **来源**：[S359 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3169-L3172) 基础补足（澄清异常捕获层级与裸 except 破坏控制流的缺陷）。

**回答：**
异常应当在**具备恢复能力、或者需要进行跨层错误转换（如将底层异常封装为对外稳定错误码）的边界层**捕获。如果当前层无法处理，应让异常继续向上传播，或使用 `raise ... from err` 保留原始调用链抛出。

盲目写 `except Exception:` 或裸写 `except:` 吞掉异常会导致两个严重问题：
1. **掩盖真实 Bug**：会吞掉未预期的类型错误、网络中断或逻辑缺陷，导致系统在脏数据或损坏状态下继续运行，引发更大故障；
2. **破坏系统控制流**：裸写 `except:` 甚至会捕获到 `KeyboardInterrupt` 和 `asyncio.CancelledError`，导致服务无法正常响应停机信号或协程取消机制失效。

## 13. 现场实现 retry(fn, max_times=3)，核心边界怎么处理？

> **来源**：[S359 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3169-L3172) 披露 retry 现场编码任务，重点考察次数边界与异常透传。

**回答：**
核心在于**明确重试次数定义、成功立即返回、并在最后一次尝试失败后原样抛出原始异常**，避免吞掉错误堆栈：
```python
def retry(fn, max_times=3):
    if max_times < 1:
        raise ValueError("max_times must be at least 1")
    for attempt in range(max_times):
        try:
            return fn()
        except Exception:
            if attempt == max_times - 1:
                raise
```

**追问：在生产环境的 Web 或 Agent 体系中，这样简单的重试逻辑有什么缺陷？**
**回答：**
存在三个生产缺陷：
1. **无退避机制**：连续紧密重试会导致重试风暴，应引入指数退避与随机抖动（Exponential Backoff with Jitter）；
2. **未区分错误类型**：只有网络短暂抖动或限流等可恢复错误才适合重试，参数错误或鉴权拒绝重试毫无意义，应直接报错；
3. **缺乏幂等保证**：对具有副作用的写操作，网络超时并不代表远端未执行，盲目重试可能导致重复扣费或重复创建资源。

## 14. 参数形式中，*args 与 **kwargs 怎样区分？

> **来源**：[S226 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-16.md#L36-L36)、[S226 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-16.md#L37-L37) 涉及函数参数形式与 *args/**kwargs 变长参数语义。

**回答：**
* `*args` 用于收集多余的**位置参数**，在函数体内部打包为一个 `tuple`；
* `**kwargs` 用于收集多余的**关键字参数**，在函数体内部打包为一个 `dict`。

在调用函数时，它们可用于解包容器：`*list` 解包为独立位置参数，`**dict` 解包为独立关键字参数。
工程实践上，除了通用装饰器和透传中继场景外，业务接口应尽量使用显式命名参数，避免过度依赖变长参数导致函数契约模糊和静态类型检查失效。

## 15. 鸭子类型和类型注解，会自动保证接口安全吗？

> **来源**：[S226 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-16.md#L38-L38) 问鸭子类型机制与类型注解在运行时的真实表现。

**回答：**
不会。
* **鸭子类型（Duck Typing）**关注对象是否具备所需的方法或行为，而不关注其具体类型。优势是松耦合与灵活，缺点是如果对象缺失对应方法，错误只能在运行时暴露。
* **类型注解（Type Hints）**在原生 Python 中仅作为静态文档和类型提示，**运行时默认不做任何类型强制检查**，传入错误类型的入参函数依然会直接运行。

要保证工程接口安全，必须依靠静态检查工具（如 `mypy`、`pyright`）在 CI 阶段拦截，或在运行时借助数据校验框架（如 Pydantic）在数据入口做显式的 Schema 校验与格式转换。

## 16. 切片为什么可能引入隐藏成本？

> **来源**：[S226 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-16.md#L40-L40) 涉及切片机制底层复制成本与性能开销。

**回答：**
因为对 Python 原生列表执行切片（如 `lst[start:end]`）**并不是创建数据视图，而是会创建一个全新的列表对象**，并将对应范围内的元素引用逐一复制过去。

切片的时间与内存复杂度均为 $O(k)$（$k$ 为切片长度）。如果在循环中频繁对大列表做切片（如滑动窗口场景），容易导致累计时间复杂度恶化为 $O(n^2)$，并产生大量临时小对象。高性能场景下，应优先通过传递起始与结束索引游标处理，或针对支持零拷贝切片的对象使用 `memoryview`。

## 17. Lock、RLock 和 Semaphore 怎样选？

> **来源**：[S008 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L184-L185) 分别涉及互斥锁、重入锁与信号量选型，以及协程同步边界。

**回答：**
* **Lock（互斥锁）**：最基础的排他锁，同一时刻仅允许一个线程持有。同一个线程未释放时如果再次申请，会发生死锁。
* **RLock（可重入锁）**：允许**同一个线程多次获取同一把锁**，内部维护计数器，释放次数需与获取次数匹配。适用于递归函数或内部方法互相调用的临界区保护。
* **Semaphore（信号量）**：内部维护许可计数器，允许多个线程（最多 $N$ 个）同时访问资源。适用于**限制并发访问容量**（如限制同时访问下游服务的最大连接数）。

**追问：在 asyncio 异步协程中，可以直接使用 `threading.Lock` 吗？**
**回答：**
绝对不能。在协程中调用 `threading.Lock.acquire()`，一旦锁被占用，会直接阻塞底层的操作系统线程，导致整个主事件循环彻底卡死。异步代码中必须使用 `asyncio.Lock` 或 `asyncio.Semaphore`，并通过 `async with lock:` 协作式挂起。

## 18. 为什么 AI 应用常选 Python，与 Java、Go 相比怎样取舍？

> **来源**：[S015 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L33-L33)、[S400 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L911-L912) 分别比较 Python/Java，以及 AI 项目为何选 Python 而非 Go/JavaScript。

**回答：**
核心原因在于**AI 软件生态集中度与快速迭代效率**。主流的大模型 SDK、训练推理框架（PyTorch/HuggingFace）、向量库客户端以及智能体编排工具（LangChain/LlamaIndex）均首发并深度绑定 Python，算法实验与工程打通的摩擦力最小。

三者工程选型取舍如下：
* **选 Python**：适用于 AI 业务编排层、Agent 调度、数据清洗与算法落地。网络 I/O 瓶颈可通过异步框架（FastAPI/AsyncIO）搞定，底层密集计算下沉至 C/C++ 原生库，Python 作为“胶水层”性能完全够用。
* **选 Go**：适用于高并发 API 网关、长连接代理、资源调度中台。Go 具有轻量级协程并发、极低的内存基线和单二进制文件易部署特性。
* **选 Java**：适用于成熟企业级大型系统，当需要与既有庞大的微服务治理（Spring Cloud/Dubbo）、复杂分布式事务、大数据流式计算深度融合时，Java 具备极高的系统稳定性和维护规范。

生产落地通常采用分层混合架构：Go 或 Java 负责外层网关与高并发业务底座，Python 专注于具体的 AI 服务与 Agent 调度执行。
