## 高频追问的短答

完整回答与样本范围见[第2题](01-高频面试题.md#fastapi-q02)、[第4题](01-高频面试题.md#fastapi-q04)、[第6题](01-高频面试题.md#fastapi-q06)、[第7题](01-高频面试题.md#fastapi-q07)、[第9题](01-高频面试题.md#fastapi-q09)。

| 问法 | 先答什么 | 再补哪个边界 |
|---|---|---|
| async为什么还卡？ | 协作式等待不等于自动卸载 | 同步helper、CPU计算、线程池与连接池也会堵 |
| def怎样执行？ | 框架调用的同步路由/依赖在线程池 | 你直接调用的helper不自动转线程 |
| SSE还是WebSocket？ | 看单向推送还是持续双向交互 | 两者都需鉴权、断线处理和明确业务终态 |
| 流为什么一次性到达？ | 沿服务端→代理→客户端定位缓冲 | 生成器存在不等于网络实时交付 |
| yield什么时候清理？ | 看版本和function/request作用域 | 响应生成器是否仍依赖资源 |
| lifespan做什么？ | 管当前应用实例启动与退出 | 多worker不等于集群单例 |
| 参数合法能执行吗？ | 还要业务约束和对象级授权 | 模型输出同样是外部输入 |
| BackgroundTasks可靠吗？ | 适合响应后的小型同进程任务 | 不天然持久、不可代替可靠队列 |
| 如何扩容？ | 先量出瓶颈与资源预算 | worker数会放大内存、连接数和下游请求 |

上表是口述压缩，不代表每一项在样本里具有相同频率；证据与教学补充的边界见问答页和综合分析。

## 场景：流式接口一忙就超时

完整回答与样本范围见[第2题](01-高频面试题.md#fastapi-q02)、[第3题](01-高频面试题.md#fastapi-q03)、[第10题](01-高频面试题.md#fastapi-q10)。

1. 明确慢的是排队、鉴权、检索、模型首token还是流传输。
2. 看事件循环延迟，排除同步阻塞和长CPU步骤。
3. 看连接/线程/数据库池等待，检查多worker后的总量。
4. 给下游超时与总预算，限制排队和并发，避免重试放大。
5. 查代理缓冲与空闲超时，确认慢客户端不会无限占资源。
6. 验证取消、资源关闭、错误终态与恢复路径，再复测p95/p99。
