## 1. 一次请求如何经过 Uvicorn、Starlette、FastAPI 和 Pydantic？

> **来源**：[S238 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-18.md#L86-L86) 直接问 Web Server、ASGI 组件与请求生命周期链。

**回答：**
四者不是独立的微服务，而是由底层网络到上层业务逻辑层层封装的请求流水线：

1. **Uvicorn（ASGI 服务器）**：监听网络 Socket，解析 HTTP/WebSocket 协议，将网络连接封装为 ASGI 的 `scope` 字典，并通过事件循环将请求交给应用；
2. **Starlette（Web 基础底座）**：提供基础的 HTTP/WebSocket 处理能力。负责请求中间件链（Middleware Stack）的流转、基础 URL 路由匹配、异常处理和请求上下文包装；
3. **FastAPI（API 框架层）**：继承自 Starlette。负责高级 API 抽象：基于类型注解解析路径/查询参数、解析并执行依赖注入系统（`Depends`）、管理安全鉴权与自动生成 OpenAPI 规范；
4. **Pydantic（数据校验引擎）**：在进入路由前执行请求体（Body）的结构化校验与类型转换；在路由执行完毕后，执行响应数据的序列化与敏感字段过滤。

**追问：ASGI 的 `scope`、`receive`、`send` 分别承担什么角色？**
**回答：**
`scope` 是一个描述连接元信息的字典（包含请求方法、路径、Headers、客户端 IP 等）；`receive` 是一个异步可调用对象，应用通过 `await receive()` 读取客户端传来的请求体事件分片；`send` 也是异步可调用对象，应用通过 `await send(...)` 异步向客户端写回响应头和响应体数据。

## 2. 为什么写了 async def，接口仍然会卡住？

> **来源**：[S241 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L75-L75)、[S357 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3066-L3066) 分别追问模型等待时 CPU/线程行为与协程内同步阻塞。

**回答：**
根本原因在于：**`async def` 只是单线程内的协作式调度**，它不会自动把耗时操作移到后台线程。只要协程内没有通过 `await` 让出控制权，主事件循环就会被一直占死。

常见卡死原因有两个：
1. **调用了同步阻塞 I/O**：在异步函数中调用了同步的 `requests`、同步数据库驱动或 `time.sleep`，导致事件循环同步挂起等待；
2. **执行了耗时的 CPU 密集计算**：如本地复杂正则表达式匹配、大文件加解密或超大 JSON 解析，CPU 被持续占用，事件循环无法调度其他就绪任务。

机制陷阱在于：FastAPI 对普通 `def` 路由会自动丢进内置外部线程池异步执行；但对 `async def` 路由会直接放在主事件循环运行。因此在 `async def` 中误写同步阻塞代码，反而更容易瞬间拖死整个服务。

**追问：遇到无法替换的第三方同步阻塞 SDK，在 `async def` 中应该如何调用？**
**回答：**
使用 `anyio.to_thread.run_sync`（或 `asyncio.to_thread`）显式将该同步函数包装后丢到线程池执行，主协程通过 `await` 协作式等待其返回，从而避免阻塞主事件循环。

## 3. 一个请求要并发调用多个模型，怎样避免把服务打满？

> **来源**：[S110 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-06.md#L375-L376) 给出 100 个任务最多 3 个并发外部 API 的资源控制约束，此处场景迁移至多模型并发接口。

**回答：**
必须将并发任务编排与流量控制解耦，实行多层防御：

1. **并发槽位控制**：严禁无上限使用 `gather` 并发。必须通过 `asyncio.Semaphore` 限制单进程内同时执行的模型调用数量；
2. **连接池与限流保护**：为异步 HTTP 客户端配置连接池上限（如 `httpx.Limits(max_connections=...)`），并在网关层配置令牌桶限流；
3. **严格超时与指数退避**：每个模型请求必须配置硬性读取超时与总超时；重试必须限制总次数并采用指数退避加抖动，防止失败重试引发级联流量风暴。

**追问：多 Worker 部署时，进程内的 `asyncio.Semaphore` 能控制住全局并发吗？**
**回答：**
不能。进程内的信号量只对当前进程有效。如果有 4 个 Worker，全局最大并发会放大到 4 倍。如果下游模型供应商有严格的账号级 QPS 或并发限制，必须使用 Redis 分布式信号量，或通过中心化的任务队列进行统一调度。

## 4. LangGraph 节点中间结果怎样通过 FastAPI/SSE 交付？SSE 与 WebSocket 怎么选？

> **来源**：[S087 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L283-L283) 直接问 FastAPI/SSE 交付 LangGraph 节点结果；展开流式协议选型。

**回答：**
* **SSE 交付实现**：使用 FastAPI 的 `StreamingResponse(media_type="text/event-stream")`。将 LangGraph 的流式事件（如 `graph.astream_events`）接入异步生成器，将图节点的运行阶段、Token 或中间状态包装为标准 SSE 格式（`event: node_progress\ndata: {...}\n\n`）持续推送到前端。
* **协议选型边界**：
  * **优先选 SSE**：大模型对话、知识库检索进度和 Agent 状态展示是典型的“服务端单向推流”场景。SSE 基于标准 HTTP 协议，实现简单，天然支持断线重连，穿透企业防火墙和代理的兼容性好。
  * **选 WebSocket**：只有在需要**客户端与服务端高频双向实时通信**（如实时语音对讲、协作白板）时才选择 WebSocket。WebSocket 的连接状态管理、心跳保活与负载均衡成本显著高于 SSE。

## 5. 客户端断开以后，后台的模型和工具调用应怎么办？

> **来源**：[S330 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1524-L1524)、[S333 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1776-L1776) 分别追问断网是否停止 Agent 与 SSE 流中途断开时的业务生命周期处理。

**回答：**
必须按业务语义分类处理，将连接生命周期与任务生命周期解耦：

1. **只读与纯文本生成请求**：客户端断开后应立刻停止。在异步流式生成器中捕获断开信号（或定期检查 `request.is_disconnected()`），及时取消正在运行的协程任务，避免浪费昂贵的模型算力；
2. **具有外部副作用的长耗时任务**：如代码重构或报表生成任务，必须与当前 HTTP 连接解耦，由后台 Worker 按照唯一的任务 ID 继续执行，客户端断线重连后通过该 ID 轮询或长连查取状态。

**追问：对于包含写操作的工具（如转账、发信），断网后客户端重连重复发起请求，如何防止重复执行？**
**回答：**
依赖请求初次生成并在全链路透传的**全局唯一业务幂等键（Idempotency Key）**。服务端收到相同幂等键时先查状态：若已成功直接返回历史回执；若正在处理中返回处理中状态；只有在确认未发生或失败时才允许执行。

## 6. yield 依赖什么时候释放资源？流式响应为什么容易踩坑？

> **来源**：教学补足（依据官方版本说明展开依赖生命周期与流式连接释放边界，作为可靠流式接口的前提）。

**回答：**
* **资源释放时机**：带 `yield` 的依赖项，其 `yield` 之前的代码在进入路由函数前执行，`yield` 之后的清理逻辑在**整个 HTTP 响应完全发送给客户端之后**执行。
* **流式响应中的陷阱**：在 `StreamingResponse` 场景下，整个流式传输可能持续几十秒甚至数分钟。如果依赖中持有数据库连接（如 `yield db_session`），该连接会在整个流式输出期间一直被占着无法归还连接池，慢客户端极易引发数据库连接池耗尽。
* **解决原则**：严格隔离依赖生命周期。鉴权等前置检查应在路由执行前完成并立即关闭连接；流式生成器内部若需读写数据库，应在生成器局部显式打开和关闭。

## 7. lifespan、依赖（Depends）和中间件（Middleware）分别放什么？

> **来源**：[S064 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L270-L270) 比较中间件与依赖；lifespan 用于管理应用级单例资源。

**回答：**
三者属于不同的应用层级，分工明确：

1. **Lifespan（应用生命周期事件）**：负责**整个进程启动与退出时的全局单例资源管理**。例如创建和关闭全局异步 HTTP 客户端池（`httpx.AsyncClient`）、Redis 连接池、数据库 Engine，或加载本地静态模型；
2. **中间件（Middleware）**：位于最外层请求管道，负责**与具体业务解耦的通用 HTTP 拦截**。例如全链路追踪的 Request-ID 注入、接口全局耗时打点、CORS 跨域头配置以及全局未捕获异常兜底；
3. **依赖注入（Depends）**：绑定在具体路由上，负责**与业务强相关的上下文装配与鉴权**。例如解析当前登录用户身份、提取租户上下文、注入数据库会话事务，并可在单元测试中通过 `app.dependency_overrides` 进行快速 Mock。

## 8. Pydantic 校验通过，为什么仍不能直接执行工具？

> **来源**：[S238 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-18.md#L76-L76) 问 Python 怎样校验模型 JSON；进一步展开 Pydantic 与业务对象级鉴权边界。

**回答：**
因为 Pydantic 只负责**入参格式与数据类型的结构校验**（回答“参数长得对不对”），完全无法验证**业务规则的合法性与数据访问权限**（无法回答“当前用户能不能动这个对象”）。

例如大模型生成的参数 `{ "order_id": "12345", "amount": 100 }` 符合正整数和字符串校验，但在工具执行前必须进行两层业务防御：
1. **业务规则校验**：该订单当前是否处于可退款状态？可退金额是否还剩 100 元？
2. **对象级水平越权校验（BOLA）**：该订单是否真正属于当前登录用户？必须结合 Token 解析出的当前用户身份与数据库实际记录进行核验。

## 9. BackgroundTasks 能当可靠的任务队列吗？

> **来源**：教学补足（剖析进程内后台函数与可恢复分布式任务队列的故障边界）。

**回答：**
不能。FastAPI 的 `BackgroundTasks` 只是在当前 Worker 进程内、响应返回之后利用协程或线程执行的轻量级任务。

其生产局限包括：
1. **无持久化，容易丢任务**：任务存储在当前进程内存中，一旦服务器重启、容器崩溃或 Worker 被 Gunicorn 回收，内存中的待办任务直接丢失；
2. **缺乏可靠治理能力**：没有内置的指数退避重试、死信队列、任务状态查询与失败告警机制；
3. **无法独立水平扩容**：后台计算与 Web 服务抢占同一进程的 CPU 和内存资源。

生产环境中耗时长（超过数秒）、对可靠性和最终一致性有要求的任务，必须使用专业的外部分布式任务队列（如 Celery、ARQ 或 Redis Stream）。

## 10. 如何回答 FastAPI 的性能与扩容设计？

> **来源**：[S184 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-10.md#L204-L204) 涉及 asyncio 支撑高并发 API 的性能与扩容设计。

**回答：**
从**单进程异步底座、多进程利用多核、集群横向扩容**三个层级展开：

1. **单进程高并发**：FastAPI 基于 Starlette 和 Uvicorn（基于 uvloop 和 httptools），在纯 I/O 等待场景下单 Worker 即可维持海量并发连接；
2. **单机多进程利用多核**：生产环境中通过 Gunicorn 托管 Uvicorn 工作进程（`gunicorn -k uvicorn.workers.UvicornWorker -w (2*CPU+1)`），充分发挥多核 CPU 计算能力；
3. **集群容器化扩容**：将服务打包为无状态容器部署在 Kubernetes 中，基于 CPU/内存利用率或 HTTP QPS 指标配置 HPA 自动横向扩缩容。

在 AI 场景下，核心瓶颈往往不是 FastAPI 本身，而是外部大模型 API 限流或数据库连接池瓶颈。盲目增加 Web Worker 无法突破外部账号配额，反而会成倍消耗数据库连接。

## 11. 鉴权、跨域与租户隔离应该怎样回答？

> **来源**：[S051 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L438-L438) 问跨域 CORS；进一步展开服务端身份鉴权与多租户数据隔离。

**回答：**
三者属于不同的安全维度，分工清晰：

* **跨域（CORS）**：是**浏览器的同源安全策略**，用于防止恶意脚本跨站读取当前域的敏感资源。跨域放行绝不等于通过鉴权，它只决定浏览器是否允许向服务端发起请求；
* **身份鉴权（AuthN & AuthZ）**：在服务端校验“你是谁”与“你有什么权限”。通过 OAuth2 / JWT 依赖注入在路由入口完成 Token 解析、过期检查与 RBAC 权限判断；
* **多租户隔离**：租户 ID 必须**从受信任的 JWT 凭据中解析**，严禁信任客户端自行传入的参数。在底层数据库操作中，所有 SQL 必须显式携带租户过滤条件（或借助 PostgreSQL 的行级安全 RLS），确保数据在存储、检索与缓存键维度完全隔离。

## 12. 面试官问怎么测试，给出什么具体方案？

> **来源**：教学补足（组织针对接口契约、依赖覆盖与流式输出的完整自动化测试方案）。

**回答：**
推荐使用 `pytest` 配合 `httpx.AsyncClient` 进行三层测试：

1. **接口契约与功能测试**：使用 `AsyncClient(transport=ASGITransport(app=app))` 直接调用应用，无需启动真实网络端口，运行速度极快；
2. **解耦外部依赖（依赖覆盖）**：充分利用 FastAPI 的 `app.dependency_overrides` 机制，在测试中将真实的数据库会话替换为测试内存库，将真实的大模型 API 替换为 Mock 函数，保证测试确定性且不消耗 Token；
3. **流式接口专项测试**：针对 SSE 流式接口，使用测试客户端逐分片拉取响应，断言事件格式、数据顺序、错误事件回传以及客户端中断时的连接释放。

## 13. 只会 GET/POST，离支撑长任务 Agent 还差什么？

> **来源**：[S238 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-18.md#L85-L85) 明确追问 GET/POST 之外支撑类似 Claude Code 长任务体系所欠缺的架构能力。

**回答：**
传统的 GET/POST 是**短生命周期的无状态同步请求**，而支撑长任务 Agent 还需要以下核心架构能力：

1. **长生命周期状态机与持久化**：HTTP 请求仅作为触发入口（立即返回 Task ID），底层由后台任务引擎驱动多步流转，支持任务暂停、持久化 Checkpoint 与崩溃恢复；
2. **持续的下行流式事件（SSE / WebSocket）**：Agent 内部的多步思考过程、工具调用参数与阶段反馈，必须以结构化事件流实时推送给前端，而非等全部完成一次性返回；
3. **人在回路（HITL）交互协议**：遇到敏感写操作时，系统能够主动向客户端发出审批挂起信号，用户确认后再通过独立审批接口恢复执行；
4. **幂等对账与执行沙箱**：工具调用包含外部副作用，必须有全局唯一的业务操作 ID 进行防重对账，并在隔离的容器沙箱中安全执行代码与命令。
