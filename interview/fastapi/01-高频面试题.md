## 1. 一次请求如何经过 Uvicorn、Starlette、FastAPI 和 Pydantic？

[S238的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-18.md#L86-L86)直接问Web Server、ASGI组件与请求链。

先把职责分开：Uvicorn 是 ASGI 服务器，负责网络连接并向应用传递事件；Starlette 提供路由、中间件、请求响应等 Web 基础；FastAPI 在其上组织路由参数、依赖与接口契约；Pydantic 负责模型的校验和序列化。它们不是四个顺序调用的独立服务。

口述链路可以是“服务器接入 → 中间件和路由 → 输入校验与依赖求值 → 业务调用 → 响应发送”。随后补充失败路径：参数不合法可能在业务执行前结束；流式响应的发送会持续到路由函数返回以后；中间件外层还会观察到异常和关闭事件。

**追问准备：** ASGI 的 `scope` 描述连接上下文，`receive` 与 `send` 交换事件。它是服务器与应用的接口，不是事件循环本身，也不保证业务函数不会阻塞。

## 2. 为什么写了 async def，接口仍然会卡住？

[S241的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L75-L75)、[S357的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3066-L3066)分别追问模型等待时CPU/线程行为和协程内同步阻塞。

`async def` 允许协作式调度，不会把函数体自动搬到后台线程。调用同步 HTTP 客户端、同步数据库驱动、`time.sleep`，或者长时间执行 CPU 计算，仍可能占住事件循环。先看等待发生在哪一层，再选择异步客户端、明确的线程卸载，或进程/独立任务服务。

FastAPI 自己调用的普通 `def` 路由与同步依赖会在线程池运行；在异步路由里直接调用的普通 helper 不会获得这种待遇。线程池也有容量，转线程只能移动阻塞位置，不能使下游服务无限扩容。

真正异步等待远端模型时，当前协程可挂起，事件循环继续处理其他就绪任务；远端GPU的计算不是本地CPU在做，也不意味着整个进程的CPU始终空闲。[FastAPI 并发说明](https://fastapi.tiangolo.com/async/)

**排查回答：** 观察事件循环延迟、请求排队、线程池等待、连接池占用和下游耗时。不能只看到高延迟就增加 worker，更不能只用 CPU 利用率判断是否健康。

## 3. 一个请求要并发调用多个模型，怎样避免把服务打满？

教学迁移：[S110的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-06.md#L375-L376)给出100任务最多3个并发外部API的约束；这里把资源控制放到模型接口场景，不增加FastAPI原题频数。

并发组合和流量控制是两件事。`gather` 或任务组负责组织任务；并发上限限制正在执行的调用数；速率限制约束一定时间内的请求量；连接池限制连接资源。还需要总预算、每次调用超时、失败后取消或降级策略。

同一进程里的信号量不代表跨多个 worker 的总配额。如果上游提供的是账号级配额，应在共享限流层或调度层协调。重试要计算进同一个预算，并只对适合重试的错误使用退避；不能每个请求一失败就再扇出一轮。

**边界：** 取消等待不一定取消远端已开始的推理或工具副作用。需要业务操作 ID、幂等处理和可查询状态。

## 4. LangGraph节点中间结果怎样通过FastAPI/SSE交付？SSE与WebSocket怎么选？

[S087的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L283-L283)直接问FastAPI/SSE交付LangGraph节点结果；协议选择是相关教学展开。

先区分图节点/状态更新与模型token：不是所有节点事件都对应一段可展示文本。把图的流式输出适配成有运行ID、节点/阶段、事件类型和顺序的业务事件，再交给HTTP流。LangGraph支持不同流模式，具体API和事件结构按锁定版本验证。[LangGraph Streaming](https://docs.langchain.com/oss/python/langgraph/streaming)

SSE 适合服务端持续向客户端推送文本事件，可表达 token、阶段进度和终态。WebSocket 支持双向消息，适用于需要持续双向交互的场景，但连接管理、鉴权和恢复协议也更复杂。选择取决于交互方向与协议需求，不是“WebSocket 一定更快”。

实现时要把模型 chunk 转成明确的业务事件，而不是假定每个网络分片就是一个完整 token 或 JSON。事件可以有类型、序号、操作 ID 和终止原因。传输结束不等于业务成功，必须区分成功、取消、失败与断线。

**追问准备：** 先测服务端真正发出第一字节的时间，再检查反向代理缓冲、客户端读取方式和空闲超时。后端使用生成器，并不自动保证用户立即看到输出。

## 5. 客户端断开以后，后台的模型和工具调用应怎么办？

[S330的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1524-L1524)、[S333的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L1776-L1776)分别问断网是否停止Agent与SSE中途断开，帮助区分业务运行和连接生命周期。

先明确业务语义：纯聊天请求通常可以取消；已经提交的长任务可能继续执行，并由用户稍后查询。无论选哪种，都应释放当前连接、迭代器和请求资源，记录终态，避免遗留无法追踪的任务。

对于有副作用的工具，不能把“断线后再发一次请求”当作安全恢复。操作应有稳定 ID，重连先查状态；只有明确可重试的阶段才重试。客户端关闭、应用取消和上游取消是不同事件，需要显式传递或补偿。

## 6. yield 依赖什么时候释放资源？流式响应为什么容易踩坑？

教学补足：依赖释放是可靠流式接口的前提，这里依据官方版本说明，不冒充直接原题。

`yield` 把资源提供给调用方，退出阶段负责清理。关键不是记住一个永恒的时间点，而是确认所用 FastAPI 版本、依赖作用域，以及响应生成器是否仍使用该资源。

FastAPI 0.121.0 起支持 `scope="function"`：在处理函数结束后、响应发送前执行退出逻辑；带 `yield` 的默认 `request` 作用域覆盖响应发送周期。流还需要数据库会话时，不能先关闭会话；如果会话只用于验证身份，也不该无意义地占着连接等慢客户端。[依赖生命周期与版本说明](https://fastapi.tiangolo.com/advanced/advanced-dependencies/)

**回答落点：** 用 `try/finally` 表达清理，异常不要无意吞掉。请求结束后的后台任务取得自己的资源，不依赖已经结束的请求作用域。

## 7. lifespan、依赖和中间件分别放什么？

[S064的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L270-L270)比较中间件与依赖；lifespan用于补齐应用级资源边界。

- `lifespan` 管应用实例的启动与退出，例如创建和关闭共享 HTTP 客户端、加载配置。多 worker 通常有多个进程实例，不能把它当成集群唯一初始化。
- 依赖提供路由所需的身份、租户、连接或输入，可以组成依赖图并在测试中替换。
- 中间件包装请求/响应过程，适合关联 ID、通用计时和必要的头处理。

把数据库事务放在哪一层，要按业务原子性决定；把权限放在哪一层，要按受保护资源决定。不能为了“统一”把具体业务状态都藏进中间件。[Lifespan 文档](https://fastapi.tiangolo.com/advanced/events/)

## 8. Pydantic 校验通过，为什么仍不能直接执行工具？

教学迁移：[S238的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-18.md#L76-L76)问Python怎样校验模型JSON；Pydantic和授权是本栈实现与安全边界的展开。

类型与字段校验只说明输入满足结构契约。`user_id` 是字符串，并不证明当前用户有权访问它；金额为正，并不证明余额或额度足够；工具参数合法，也不证明操作符合当前业务状态。

执行链需要区分结构校验、业务约束、身份鉴别、对象级授权和执行后的结果校验。模型生成参数与普通外部输入一样，都不应越过这些边界。对外返回也要控制字段，避免把内部对象或敏感字段直接序列化出去。

## 9. BackgroundTasks 能当可靠的任务队列吗？

教学补足：解释进程内后台函数与可恢复任务的故障边界，不新增实问计数。

它适合响应之后执行的小型同进程任务，例如不要求严格持久性的通知。它没有天然提供跨进程持久化、崩溃恢复和多 worker 调度保证。任务耗时长、必须可恢复，或要独立扩容时，应使用持久任务机制，并让接口返回任务 ID。

仍需考虑“任务创建”和“业务提交”之间的一致性：数据库事务回滚时不能发布一个已经生效的任务；任务可能重复投递，消费者也要幂等。不能只把函数从路由挪到后台就声称问题解决。[FastAPI Background Tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/)

## 10. 如何回答 FastAPI 的性能与扩容设计？

[S184的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-10.md#L204-L204)涉及asyncio支撑高并发API；worker、预算与压测是框架工程展开。

先拆成本：校验与序列化、业务 CPU、数据库、外部模型等待和流式连接占用。给出吞吐、并发、p95/p99 延迟、首字节/首 token 时间以及失败率，再说明压测负载和瓶颈。

加 worker 可以利用更多进程，但会放大模型、连接池和缓存的内存占用，也不能提高外部账号配额。扩容后必须检查共享状态、会话路由、全局限流和幂等约束。对于长流式响应，还要单独看活跃连接、慢客户端和滚动退出策略。

## 11. 鉴权、跨域与租户隔离应该怎样回答？

[S051的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L438-L438)问跨域/CORS；身份、对象权限与租户隔离说明其之外仍需解决的边界。

鉴权回答“你是谁、可执行什么”；CORS 是浏览器控制页面跨来源访问的机制，不能替代服务端授权。带凭据请求要明确可信来源，不把放开跨域当作安全修复。

租户隔离必须贯穿请求身份、数据库条件、检索过滤、缓存键、对象存储和工具执行。客户端传来的 tenant ID 只是输入，要与经过验证的身份绑定。一个“所有请求都带 tenant_id”的约定，不能证明每条数据路径都实施了隔离。

## 12. 面试官问怎么测试，给出什么具体方案？

教学补足：把契约与失败路径转成测试，不增加原题计数。

先验证成功与失败契约：输入错误、未授权、资源不存在、上游超时、重试和取消。依赖覆盖可替换外部模型或数据库访问，测试不需要真实消耗模型配额。

流式接口要验证事件顺序、终态、错误事件和资源关闭，而不只断言 HTTP 200。性能测试再覆盖慢上游、慢客户端、连接池耗尽和并发取消。单元测试证明的是局部行为，不能替代真实代理链路下的流式交付验证。

## 13. 只会GET/POST，离支撑长任务Agent还差什么？

[S238的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-18.md#L85-L85)明确追问GET/POST之外支撑Claude Code式体系还缺什么能力。

HTTP路由只是入口。还需要明确运行ID、会话与任务状态、持久执行、工具权限和副作用、超时取消、事件流、重连查询以及最终结果。请求生命周期可能只有几十秒，业务任务却持续更久；把全部状态放在路由局部变量或一个后台协程里，进程重启后就可能丢失。

可以把接口理解成对运行时的控制与观察：创建任务返回ID；执行器按状态推进；事件以稳定身份和顺序暴露；客户端断线后查询当前状态。哪些状态要持久化、哪种工具可重试、何时需要人工确认，必须由业务语义定义，不能由Web框架替你决定。

**追问准备：** 多worker时会话状态不能只藏在一个进程里；上游已产生副作用但本地超时时，先确认结果再恢复，避免重新提交操作。流式文本只是交付形式，不能代替任务状态机。
