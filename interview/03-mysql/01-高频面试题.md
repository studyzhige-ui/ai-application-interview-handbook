## 1. 一条 SQL 怎样执行？为什么先看结果语义再看索引？

> **来源**：[S119 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L99-L99) 直接问从 Server 到返回结果的完整执行链与优化器职责。

**回答：**
一条 SQL 的执行链分为 Server 层与存储引擎层：

1. **连接与鉴权**：连接池建立通信，完成握手与权限认证；
2. **分析与解析（Parser）**：词法与语法分析，生成解析树，检查表名与列名合法性；
3. **优化器（Optimizer）**：基于统计信息生成多种执行路径，计算代价（Cost），决定多表 Join 顺序与索引选择；
4. **执行器（Executor）与存储引擎**：调用 InnoDB 存储引擎的读写接口（Handler API），通过 Buffer Pool 检索或读盘获取数据并返回客户端。

优化慢 SQL 时，**必须先确认结果集的业务语义正确性**：
如果过滤条件、关联关系、NULL 值处理或分页排序本身逻辑有误，即使强行通过索引让查询变快也没有意义。例如错误地把 `WHERE` 条件挪动位置，可能将原本的 `LEFT JOIN`（保留左表全部记录）隐式退化为 `INNER JOIN`，破坏业务数据完整性。

**追问：接口响应变慢，就一定是 SQL 慢吗？**
**回答：**
不一定。接口耗时包含：应用连接池等待（获取连接排队）、网络往返延迟（RTT）、数据库行锁/表锁等待、以及大结果集反序列化开销。必须通过 APM 链路追踪或数据库的 Slow Query Log 将网络排队、锁等待与 SQL 真实执行耗时分段度量。

## 2. 为什么选 B+Tree？聚簇索引和二级索引各存什么？

> **来源**：[S010 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L238-L241) 连续问索引结构、树容量和 B 树取舍；[S387 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L51-L51) 追问 InnoDB 主键聚簇索引与二级索引存储差异。

**回答：**
* **选 B+Tree 的原因**：
  1. **磁盘 I/O 效率高**：非叶子节点只存储索引键和子节点指针，不存储整行数据，单页（16KB）扇出（Fanout）极大，树高极低（通常 3~4 层即可存储千万级数据），大幅减少磁盘随机 I/O 次数；
  2. **天然支持高效范围查询**：所有叶子节点按键值顺序排列，并通过双向链表相连，区间遍历与排序取前 N 条极其高效；
  3. **Hash 与二叉树的缺陷**：Hash 索引仅支持等值查询，无法做范围查询和排序；二叉平衡树树高随数据量增加急剧增长，且节点在磁盘上物理分散，局部性极差。
* **聚簇索引 vs 二级索引**：
  * **聚簇索引（Clustered Index）**：以主键构建，叶子节点直接存放**完整的整行数据记录**，表中数据物理上按主键顺序组织；
  * **二级索引（Secondary Index）**：以非主键列构建，叶子节点存放的是**索引列的值 + 对应的主键值**。如果查询的列不在二级索引中，需先查二级索引拿到主键，再回聚簇索引查找整行（回表）。

## 3. ABC 联合索引怎样逐条件分析？

> **来源**：[S368 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3724-L3729) 逐一改变 ABC 条件追问最左前缀；[S214 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-14.md#L59-L59) 给出 A 范围与 B 等值联合索引条件分析。

**回答：**
联合索引 `(A, B, C)` 底层是严格按 `先按 A 排序，A 相同按 B 排序，B 相同再按 C 排序` 的复合顺序构建的。核心分析规则如下：

1. **`A = 1 AND B = 2`**：能精确命中 `(A, B)` 前缀进行等值定位，`WHERE` 中书写的先后顺序不影响优化器识别；
2. **`A = 1 AND C = 3`**：A 列用于快速定位区间；但由于跳过了 B 列，C 列无法参与 B+Tree 的连续区间定位，只能在索引叶子节点中作为下推过滤条件（ICP），无法构成完整连续前缀；
3. **只有 `B = 2 AND C = 3`**：缺失最左列 A，无法走索引范围查找，通常走全表扫描（但在返回字段被完全覆盖时可走全索引扫描 Index Full Scan）；
4. **`A > 1 AND B = 2`**：A 列走范围查找后，后续列 B 在整个范围区间内不再全局有序，因此 B 列无法用于缩小索引查找边界，只能用于过滤。

## 4. 覆盖索引、回表和 ICP 怎样区分？

> **来源**：[S368 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3722-L3723) 涉及覆盖索引与返回字段的关系；进一步展开回表与 ICP（索引条件下推）的本质区别。

**回答：**
三者是二级索引查询路径中不同层级的优化机制：

* **回表（Table Lookup）**：通过二级索引查到匹配行后，由于查询所需的某些列不在该二级索引中，必须拿着主键 ID 再次访问聚簇索引读取完整行数据；
* **覆盖索引（Covering Index）**：查询所需的所有字段（`SELECT` 和 `WHERE` 涉及的列）都包含在所使用的索引中。执行器直接从索引叶子节点拿到全部数据，**完全不需要回表**（EXPLAIN 的 Extra 显示 `Using index`）；
* **ICP（索引条件下推，Index Condition Pushdown）**：当需要回表时，把原本在 Server 层过滤的二级索引条件**下推到存储引擎层**。存储引擎在遍历二级索引时，先用索引内包含的字段过滤掉不满足条件的行，只对真正符合条件的记录执行回表，从而大幅减少回表次数（Extra 显示 `Using index condition`）。

## 5. 索引为什么失效？命中了为什么仍然慢？

> **来源**：[S005 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L106-L106) 连续追问“索引为何快、何时失效、命中后为何仍慢”三种不同机制。

**回答：**
* **索引失效（优化器放弃索引）的常见原因**：
  1. **索引列被函数或计算包裹**：如 `WHERE DATE(create_time) = ?`，导致无法走 B+Tree 有序定位；
  2. **隐式类型转换**：如字符串类型列传入整型数字，MySQL 会隐式对列调用转换函数导致失效；
  3. **左模糊匹配**：如 `LIKE '%abc'`，由于前缀不确定无法利用索引有序性；
  4. **优化器代价估算选择全表扫描**：当查询需要回表的数据量占全表比例较大（如超过 20%~30%），优化器判定顺序读全表代价低于大量随机回表，主动放弃索引。
* **命中索引但仍然慢的原因**：
  1. **大量回表**：命中了非覆盖索引，扫描出十万行符合条件的主键并执行了十万次聚簇索引随机 I/O；
  2. **扫描行数过多**：索引选择性（Cardinality）极差（如状态字段），虽然走了索引但几乎扫描了整棵树；
  3. **存在大代价的外部排序**：未利用索引消除 `ORDER BY`，产生额外的内存或临时文件排序（`Using filesort`）。

## 6. 怎样读 EXPLAIN 并证明优化有效？

> **来源**：[S025 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L248-L248) 要求说明调优维度与 EXPLAIN 重点；[S293 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-32.md#L53-L53) 要求定位并优化耗时慢 SQL。

**回答：**
读懂 EXPLAIN 重点关注 5 个核心指标：

1. **`type`（访问类型）**：性能从优到劣为 `system > const > eq_ref > ref > range > index > ALL`。生产环境至少应优化到 `ref` 或 `range`，严禁关键接口出现全表扫描 `ALL`；
2. **`key` 与 `key_len`**：确认实际命中的索引名称，以及联合索引中被实际利用的前缀长度字节数；
3. **`rows` 与 `filtered`**：`rows` 是预估扫描行数，`filtered` 是该阶段条件过滤后留下的行数百分比，相乘得到传递给下一阶段的预估行；
4. **`Extra`**：关注是否出现 `Using index`（覆盖索引，极佳）、`Using index condition`（下推过滤，良好）、`Using filesort`（额外文件排序，需警惕）、`Using temporary`（产生临时表，需优化）。

**证明优化有效的量化依据**：
使用 `EXPLAIN ANALYZE` 执行真实语句，对比优化前后的真实耗时（Actual time）、真实循环次数与扫描行数；并在生产压测环境下对比 P95/P99 延迟分位数和数据库 CPU 负载。

## 7. 订单过滤和排序怎样共同设计索引？

> **来源**：[S387 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L52-L55) 追问排序、独立索引与最新订单访问；[S148 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L120-L120) 指定 user_id 与 create_time 联合索引设计。

**回答：**
设计原则遵循**“等值过滤字段在前，排序字段紧随其后”**。

典型场景：查询某用户的特定状态订单并按创建时间倒序获取：
```sql
SELECT id, amount FROM orders 
WHERE user_id = ? AND status = ? 
ORDER BY created_at DESC LIMIT 20;
```
* **最优联合索引**：`(user_id, status, created_at)`。
  * `user_id` 和 `status` 等值定位缩小范围；
  * `created_at` 紧随其后，利用索引节点天然的有序性直接倒序读取前 20 条，彻底消除 `Using filesort`；
  * 若要避免回表，可将 `amount` 加入索引末尾变为 `(user_id, status, created_at, amount)` 实现覆盖索引。
* **避坑要点**：若查询包含范围过滤（如 `amount > 100`），范围字段后面的排序字段将无法利用索引消除排序，此时应将排序字段放在范围过滤字段之前。

## 8. 深分页为什么慢？延迟关联和游标各解决什么？

> **来源**：[S025 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L249-L249) 给出大表深分页和回表放大问题；[S387 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L56-L57) 追问游标分页为什么需要唯一键。

**回答：**
* **深分页慢的原因**：执行 `LIMIT 1000000, 20` 时，MySQL 并不是直接跳到第一百万行，而是必须从磁盘连续读取并排序 1,000,020 行数据，再丢弃前 1,000,000 行，回表开销和 I/O 成本呈线性暴增。
* **解法一：延迟关联（子查询覆盖索引）**：
  先用子查询在二级索引中完成分页获取主键 ID（纯走覆盖索引，无回表），再通过主键关联原表获取完整列：
  ```sql
  SELECT o.* FROM orders o
  JOIN (SELECT id FROM orders WHERE user_id = ? ORDER BY id DESC LIMIT 1000000, 20) t
  ON o.id = t.id;
  ```
  *解决点*：将前一百万行的整行回表开销降低为纯索引扫描，大幅缩短 I/O 耗时。
* **解法二：游标分页（Seek Method）**：
  针对无限滚动的瀑布流场景，改用上一页末尾的唯一排序键作为过滤条件：
  ```sql
  WHERE user_id = ? AND id < last_seen_id ORDER BY id DESC LIMIT 20;
  ```
  *解决点*：直接通过 B+Tree 等值定位到起始行，执行耗时与分页深度彻底脱钩（恒定毫秒级）。

## 9. RC、RR 和 MVCC 应怎样连起来回答？

> **来源**：[S010 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L233-L235) 连问 MVCC 机制、用途及 RC 与 RR 隔离级别的可见性差异。

**回答：**
MVCC（多版本并发控制）通过**Undo Log 版本链**和**一致性读视图（Read View）**实现读写不互相阻塞：

1. **底层机制**：每行记录带有隐藏的 `trx_id`（最近修改该行的事务 ID）和 `roll_pointer`（指向 undo 日志中旧版本的指针），形成版本链；
2. **Read View 可见性判断**：事务在读取时生成 Read View，记录当前活跃且未提交的事务 ID 列表。通过对比版本链中每条记录的 `trx_id` 与该列表，判断哪些版本对当前事务可见；
3. **RC 与 RR 的本质差异**：
   * **RC（读已提交）**：事务中的**每一次 SELECT 语句都会重新生成一个最新的 Read View**，因此能读到其他事务刚刚提交的最新修改（不可重复读）；
   * **RR（可重复读）**：事务只在**第一次执行 SELECT 时生成 Read View，整个事务生命周期内一直复用该视图**，因此即使其他事务提交了修改，当前事务读到的快照依然恒定不变。

## 10. RR 是否彻底解决了幻读？

> **来源**：[S201 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-11.md#L223-L223) 明确要求 RR 下不升级 Serializable 地治理幻读；[S148 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L121-L121) 解释 MVCC 快照读与当前读的边界。

**回答：**
在绝大多数日常场景下解决了，但**没有在所有情况下 100% 杜绝**：

* **快照读场景（普通 SELECT）**：通过 MVCC 的静态 Read View 完全避免了幻读，事务内多次查询看到的行数完全一致；
* **当前读场景（SELECT FOR UPDATE / UPDATE）**：通过 **Next-Key Lock（记录锁 + 间隙锁 Gap Lock）** 锁住记录本身及其前后的间隙，阻止其他并发事务向该间隙插入新记录，从而防止了幻读。
* **仍会发生幻读的特殊边界（混用快照读与写入）**：
  事务 A 先执行普通快照读未查到记录；事务 B 随后插入该记录并提交；此时事务 A 执行了一条针对该记录的 `UPDATE` 语句（UPDATE 属于当前读，强制读取最新物理版本并将其更新），更新成功后该记录的 `trx_id` 被更新为事务 A 本身。随后事务 A 再次执行普通快照读，就会读到这条新记录，发生幻读。

## 11. 有事务为什么仍可能超扣？怎样做条件更新？

> **来源**：[S093 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L410-L410) 询问扣库存与订单事务一致性；[S010 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L229-L229) 追问库存并发更新中的乐观条件更新。

**回答：**
因为事务只保证 ACID 的原子性和隔离性，**无法自动识别“库存不能小于 0”这种应用级业务规则**。

典型错误是“先读再改写”：在应用层 `SELECT stock`，判断大于 0 后，再在应用层做减法并执行 `UPDATE stock = ?`。在并发请求下，两个事务读到相同的库存，计算后依次覆盖写入，导致超扣（丢失更新）。

**正确解法：利用数据库行锁与原子条件更新（带行级保护的乐观更新）**：
```sql
UPDATE stock
SET available = available - 1
WHERE sku_id = ? AND available >= 1;
```
利用 InnoDB 执行单条 `UPDATE` 时的行级排他锁保证原子性。应用层检查受影响行数（Affected Rows）：若等于 1 表示扣减成功；若等于 0 说明库存已被扣尽，抛出库存不足异常并回滚业务事务。

## 12. 死锁和锁等待超时怎样处理？

> **来源**：教学补足（围绕 InnoDB 死锁产生机理、检测日志分析与应用层有界重试展开）。

**回答：**
* **成因**：两个或多个事务按相反的顺序对相同的行加排他锁，形成闭环互等。
* **排查与诊断**：
  1. 通过 `SHOW ENGINE INNODB STATUS` 查看最近一次死锁日志（LATEST DETECTED DEADLOCK），定位冲突的 SQL、锁类型（X/S 锁、Gap 锁）与持锁事务；
  2. 开启 `innodb_print_all_deadlocks=1` 将所有死锁记录输出至 MySQL 错误日志进行持续监控。
* **生产预防与治理原则**：
  1. **严格统一加锁顺序**：涉及多表或多行更新时，应用层严格按照统一维度（如主键升序 ID）排序后再依次加锁；
  2. **缩短事务生命周期**：避免在事务内部包含耗时操作（如调用第三方外部 API、文件读写），减少持锁时间窗口；
  3. **确保更新语句走高效索引**：如果 `UPDATE` 没走索引会升级为锁全表的所有记录与间隙，极大增加死锁概率；
  4. **应用层有界重试**：当捕获到 MySQL 1213 死锁异常时，InnoDB 会自动回滚代价较小的事务，应用层应捕获该异常并在指数退避后发起有限次数的整单重试。

## 13. undo log、redo log、binlog 为什么不能互相替代？

> **来源**：[S003 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L69-L69) 明确比较 undo log、redo log、binlog 各自的恢复用途与底层职责。

**回答：**
三者属于不同层级，解决不同场景的数据可靠性：

1. **undo log（回滚日志，InnoDB 独有）**：记录逻辑相反的逆向操作（如 INSERT 对应记录 DELETE）。用于保证**事务原子性（失败回滚）**与支撑**MVCC 多版本读**；
2. **redo log（重做日志，InnoDB 独有）**：记录物理页级别的修改。用于保证**事务持久性与崩溃恢复（Crash Recovery）**。采用 WAL 机制顺序刷盘，当数据库异常掉电重启时，重做已经提交但尚未刷回磁盘数据页的修改；
3. **binlog（归档/逻辑日志，Server 层通用）**：记录所有对数据库执行更改的 SQL 逻辑事件。用于**主从复制**以及基于历史备份进行**任意时间点的数据恢复（Point-in-Time Recovery）**。它不具备物理崩溃恢复能力，因此无法替代 redo log。

## 14. 两阶段提交协调什么？提交成功意味着什么？

> **来源**：[S003 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L70-L71) 直接问两阶段提交必要性；[S090 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L342-L345) 追事务提交回滚与 binlog 刷盘时机。

**回答：**
* **协调目的**：协调 **InnoDB redo log** 与 **Server 层 binlog** 的写入顺序，防止单机崩溃导致主库数据与从库/备份数据不一致。
* **执行阶段**：
  1. **Prepare 阶段**：InnoDB 将修改写入 redo log，并标记状态为 `prepare`，刷盘；
  2. **Write binlog 阶段**：Server 层将事务事件写入 binlog，刷盘；
  3. **Commit 阶段**：InnoDB 将 redo log 标记为 `commit` 状态。
* **崩溃恢复逻辑**：
  若在写入 binlog 前崩溃，redo log 处于 prepare 且 binlog 无记录，直接回滚；若在 binlog 写入后崩溃，重启时发现 redo log 处于 prepare 但 binlog 存在完整事务记录，则判定该事务合法并推进为提交。
* **提交成功（强一致配置）**：
  在生产强持久化配置（`innodb_flush_log_at_trx_commit=1` 且 `sync_binlog=1`，即双 1 配置）下，COMMIT 成功意味着该事务已安全持久化到磁盘日志中，即使物理掉电数据也绝不丢失。

## 15. 主从复制与读写分离怎样说明一致性？

> **来源**：[S090 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L344-L349) 把主从延迟、批量同步与主库故障一致性串起来考察。

**回答：**
* **异步复制导致的主从延迟**：主库执行完事务立即返回，binlog 异步传输至从库的中继日志（Relay Log）并由从库 SQL 线程重放。从库重放存在时间差，如果用户刚写完立即读取从库，极易读到旧数据（数据不一致）。
* **业务解决方案**：
  1. **核心关键业务强制读主库**：对数据新鲜度敏感的场景（如支付后查余额、登录鉴权、下单后查订单），路由中间件强制读主库；
  2. **基于 GTID 等待位点（Wait for GTID）**：写操作返回全局事务 GTID，读请求附带该 GTID 发给从库，从库等待直到重放到该位点再返回结果；
  3. **半同步复制（Semi-sync Replication）**：主库必须等待至少一个从库接收并写入 Relay Log 确认后才向客户端返回提交成功，保证主库宕机时数据不丢失。

## 16. 数据量大就必须分库分表吗？

> **来源**：[S093 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L403-L404) 追跨分片查询与分页；[S127 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L355-L357) 追分布均衡与分库分表决策阶梯。

**回答：**
绝不盲目分片。分库分表是**最后的架构手段**，伴随着跨库事务、跨分片分页排序、数据迁移和运维复杂度剧增的巨大代价。

在考虑分库分表前，必须按顺序穷尽以下更低成本的优化：
1. **冷热数据分离与历史归档**：将 3 个月以前的历史订单归档至冷库或对象存储，只保留近期活跃数据；
2. **读写分离与缓存卸载**：引入 Redis 缓存高频热点读，从库分担复杂查询；
3. **硬件与配置扩容**：升级更高 IOPS 的 NVMe SSD、扩大 InnoDB Buffer Pool（使其能够覆盖热点索引工作集）。

**真正必须分片的临界点**：
单机写入 TPS 达到物理瓶颈、或单表数据量突破数千万行导致 B+Tree 树高增加且工作集无法完全装入内存导致频繁磁盘 I/O。分片键的选择必须与核心业务查询模式绑定（如按 `user_id` 分片）。

## 17. 大批量读取导入怎样兼顾吞吐和恢复？

> **来源**：[S094 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L429-L430) 要求大表分批读取并跨接口发送；[S232 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-17.md#L46-L46) 指定批量导入中途失败后的断点防重恢复。

**回答：**
核心在于**分批受控提交与断点可恢复设计**：

* **读侧控制**：严禁一次性读取整表入内存。必须按自增主键分批（如每次 `WHERE id > last_id LIMIT 1000`），保证内存占用恒定并实施下游背压。
* **写侧优化**：
  1. 采用多值批量插入（`INSERT INTO ... VALUES (...), (...)`）或 `LOAD DATA INFILE`，大幅降低网络往返与解析开销；
  2. 控制每批事务大小（通常每批 500~2000 条），严禁单一大事务导入数百万行（会导致 undo/redo log 撑爆、长事务锁竞争与主从复制严重延迟）。
* **中途崩溃防重恢复**：
  在单独的调度表中持久化当前导入批次的进度（`batch_index`、`last_processed_id`），并要求业务表包含唯一业务键或支持 `ON DUPLICATE KEY UPDATE`，保证即使中途挂掉重启重跑，也不会产生重复脏数据。

## 18. 怎样回答个人项目的优化收益？

> **来源**：[S005 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L113-L113) 直接质疑简历中数据库优化百分比的测量依据，重点考察工程举证闭环。

**回答：**
必须给出**严谨的量化对照与代价说明**，杜绝空洞的百分比吹嘘：

1. **说明具体业务场景与初始瓶颈**：清晰阐述是哪张核心业务表（数据量多大）、哪个核心接口在高峰期面临慢查询超时（如 P99 达到 1.2 秒）；

4. **展示严谨的测试对照与付出代价**：在同等数据量与相同并发压力下复测，P99 降低至 50 毫秒以内；同时客观说明代价——新增联合索引带来了约 5% 的写入维护延迟和额外的磁盘占用。

## 19. AI 生成 SQL 或使用 ORM 后还要验证什么？

> **来源**：[S316 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L664-L664) 要求校验 AI 生成 SQL 的正确性与性能；[S232 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-17.md#L42-L42) 要求说明预编译防注入边界。

**回答：**
必须经过三层关键防线验证：

1. **语义正确性校验**：检查多表关联是否因缺少条件造成笛卡尔积或行数指数放大；检查 `LEFT JOIN` 的过滤条件是否放置错误导致语义偏差；检查 `NULL` 值与 `COUNT(*)` / `COUNT(col)` 的计算边界；
2. **安全与防注入防护**：严禁将 AI 生成的 SQL 或用户输入未经预编译直接拼接到数据库执行。参数值必须通过驱动的参数化查询（Prepared Statements）进行绑定；动态表名或排序字段必须通过白名单校验；AI 执行账号必须被严格授予只读权限并设置单次查询超时；
3. **性能执行计划审查**：自动抓取生成的 SQL 执行 `EXPLAIN`，检查是否存在全表扫描（`ALL`）或文件排序（`filesort`），防止低效 SQL 在高并发生产库引发连接池耗尽。
