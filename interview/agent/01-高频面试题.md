### 1. Agent、普通模型调用与 Workflow 的关键区别是什么？

[S022](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L187-L187)问Agent与普通模型调用的区别，[S045](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L289-L289)追问复杂任务何时仍适合固定Workflow；本题把两个判断连成一次选型回答。

我会看“下一步由谁决定”。普通调用把输入变成输出；固定 Workflow 由程序预先规定路径，路径中也可以有模型、分支和循环；Agent 根据执行中的观察选择下一步工具或子任务。自主性是程度，不要求所有决策都交给模型。[Anthropic 的架构分类](https://www.anthropic.com/engineering/building-effective-agents)采用的也是控制路径区别。

例如退款客服可以让模型理解模糊诉求、补问订单，再由确定性规则判断退款资格和金额，经过批准后调用退款接口。理解阶段需要灵活，资金动作需要强约束，这是一种混合设计。若规则已经清晰、输入稳定，固定工作流通常更容易测试；不能因为任务复杂就直接上多 Agent。

面试问“你为什么用 Agent”，还要说清业务中哪一步无法提前穷举、什么指标证明灵活性有收益。

### 2. 模型外面为什么还需要 Runtime / Harness？

[S001](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L19-L19)问可靠Harness的核心能力，[S003](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L60-L60)问从零搭Agent的模块；模块名之外，还需说明每项工程责任。

模型提出行动候选，程序负责让行动成为可核验事实。一次可用系统至少要完成输入组织、模型调用、工具解析与执行、状态推进、停止和结果验收；生产环境还需要权限、预算、持久化、取消、重试和追踪。

Runtime 通常强调执行推进，Harness 强调包围模型的运行支撑。术语没有跨产品统一的进程边界，不必画成两个微服务。模型更强以后，可以减少脆弱的提示补丁，但授权、业务幂等、执行回执和资源隔离仍不能交给概率输出保证。

项目介绍应画出一条真实链：用户请求如何变成任务，程序在哪里调用模型，工具在哪里执行，结果在哪里落地，哪里判断完成。只报 LangGraph、MCP、Redis 的名字，无法解释这些责任。

### 3. 一个最小 Agent Loop 应怎样实现？

最小Loop与ReAct在循环中的作用，对应[S036](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L92-L92)的实际提问；这里补齐了完成、等待和失败的可实现分支。

先读取任务目标、当前状态与取消信号，装配本轮上下文；模型可能返回工具请求、需要澄清的信息或最终结果候选。程序解析候选，校验后执行工具，把结果按调用身份回填，再进行下一轮。最终文本是候选结果，还要通过任务验收才能将 Run 标成成功。

```text
读取状态 → 检查取消、权限、期限和预算 → 装配上下文 → 调模型
  ├─ 工具候选：校验 → 执行 → 记录结果 → 回填观察 → 继续
  ├─ 缺输入或批准：持久化等待 → 释放执行资源
  └─ 完成候选：核对产物或外部事实 → 成功 / 继续 / 失败
```

工具结果只打印日志而没有回填，下一轮模型可能仍认为工具没执行。反过来，模型写“已发送”也不证明宿主真的调用过发送接口。等待、取消、预算停止、失败必须有不同终止原因。

Session、Run、Turn、Step 的命名应先声明口径。例如 Session 是会话，Run 是一次目标执行；一次 Run 可以有多轮模型与工具交互。产品中的 Turn 可能覆盖多次调用，不能用名词推断执行次数。

### 4. ReAct、Plan-and-Execute、Plan-and-Solve 是一回事吗？

[S148](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L123-L123)明确比较ReAct与Plan-and-Solve；[S150](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L160-L160)比较ReAct与Plan-and-Execute。两种Plan称谓应分别保留，技术解释以原论文为准。

ReAct 将推理、行动与观察交替组织，环境反馈能够改变下一步。[ReAct 原论文](https://arxiv.org/abs/2210.03629)讨论的就是推理与行动结合，不要求产品向用户展示完整内部推理文本。

Plan-and-Execute 常指先形成显式计划，再执行；若观察改变前提，还应重新规划。适合可以拆阶段、描述依赖和验收条件的任务，但最初计划不是永远正确的脚本。Planner、Executor、Critic 是职责划分，可组合进这类流程；Critic 应按可检查标准验收，不能靠同一个模型再说一次“正确”。

[Plan-and-Solve 原论文](https://arxiv.org/abs/2305.04091)首先是一种先制定计划再求解的提示方法。面试原文若只说 Plan、Plan-and-Solve 或 Plan–Execute–Replan，应保留原称并确认实现，不能替它们补成同一套运行时。

### 5. 怎样判断任务完成，怎样阻止死循环？

[S228](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-16.md#L82-L82)询问如何确认完成并可靠停止，[S043](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L246-L246)追问反复读文件和重复工具调用；成功判定与止损不能混为一谈。

先把目标改写为可验证条件。代码任务看必要文件和测试行为，报告任务看覆盖范围与引用，退款任务看权威系统回执。最大步数、Token 上限和 deadline 是停止保险，不是成功标准。

检测循环时同时看动作、参数、观察和进展：重复读取同一版本文件却没有新信息，重复调用同一失败工具，或在两条路径之间震荡，都值得触发改路、澄清或退出。合法分页虽然重复工具名，却在推进游标，不能误杀。可以记录最近动作签名和任务里程碑，但判断窗口与阈值应由实际坏例校准。

若没有可靠的完成判据，应返回部分结果或请求确认，而不是让模型无限自评。

## 二、工具可靠性要落到执行边界

<a id="q06"></a>

### 6. 工具从定义到调用，完整链路是什么？

[S012](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L290-L290)要求从天气请求讲到真实函数执行，[S205](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-12.md#L17-L17)从Registry、Schema、Execution和Result追问工具框架；本题沿这条链组织答案。

工具注册表保存稳定身份、实现入口与契约；模型只看到当前任务允许使用的说明。模型返回调用候选后，宿主解析参数，进行 Schema、业务语义、授权和必要批准检查，调用实现，再校验结果并关联原调用 ID 回填。模型生成调用与程序执行是两个步骤。

通用 Tool Call 可以由不同协议或框架表示，不应自动当成某一种 Function Calling API。MCP 的 `tools/list` 是发现，`tools/call` 才是请求执行；宿主还需将模型的调用表示转换为协议请求。JSON-RPC 请求 ID 用于匹配响应，不能直接当业务幂等键。

结果至少区分成功、空结果、输入错误、权限拒绝和执行状态未知。字符串可以是合法结果，结构化对象则更适合让程序可靠区分状态、产物引用和错误原因。[MCP Tools 规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)还明确区分服务端结构化结果与模型的结构化生成。

### 7. Schema 校验通过，为什么仍可能越权？

[S288](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-29.md#L28-L28)明确限定Schema只能校验格式，[S288](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-29.md#L38-L38)继续问读写鉴权与用户确认；退款例子是教学演示，不是该项目的已知实现。

Schema 回答“参数长得对不对”。它可以约束类型、必填、枚举和数值范围，却无法单凭声明证明订单属于当前用户、金额仍可退、目标文档允许外传。执行前还要查询业务事实，并用可信身份做对象级授权。

例如 `refund(order_id, amount)` 的金额是正数，只能通过数值规则；程序还要核对订单、已退金额、币种和退款权限。批准记录应绑定实际对象、参数与版本。用户批准了订单 A 的 100 元退款，模型后来改成订单 B，旧批准不能沿用。

工具标注 `readOnly` 或 `destructive` 是调度提示，不是安全证明。只读导出也会泄密；第三方工具描述更不能自行授予权限。

<a id="q08"></a>

### 8. 工具太多、名字相似、参数总错，分别怎么处理？

[S001](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L21-L21)问大量工具的按需发现，[S162](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-09.md#L60-L60)问参数幻觉和格式修复；候选召回、选择和参数校验因此分开排查。

先拆开三个问题：候选工具有没有被找出来，模型有没有选对，参数有没有构造对。前者优化目录、权限过滤和工具检索；第二个改善名称、用途边界与反例，减少重叠能力；第三个完善 Schema、参数说明、有效对象查找和有限修复。

目录较小时可以直接暴露允许的工具；目录很大时先召回候选，再加载完整说明。要分别测工具候选召回率、选择正确率和参数有效率。工具根本没进入候选集时，反复改主模型 Prompt 通常无效。

同名工具必须有稳定命名空间，不能静默覆盖；目录更新后旧 Schema、权限与缓存也要检查。把目录压得很短但使正确工具无法发现，Token 变少不代表系统变好。

### 9. Tool Failure 应怎样分类，哪些可以重试？

超时分类、重试和降级见[S003](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L61-L61)，文件不存在、命令超时与权限不足的区别见[S043](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L242-L242)。

分类是为了决定下一步：格式错误可有限修参数；权限拒绝应停止或请求正确授权；对象不存在要澄清或刷新事实；短暂限流和网络故障才可能适合退避重试。程序 Bug、用户拒绝和预算耗尽不能统一当临时失败。

重试还要看副作用。读请求也可能消耗配额；写请求超时后，远端可能已经成功。只有动作可安全重复、或下游提供有效幂等契约，才在剩余 deadline 和总预算内重试。加随机扰动可以避免大量调用同时再次冲击依赖；具体重试层和次数必须统一，避免 SDK、工具层、Agent 各重试一遍。[AWS 的重试指南](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_limit_retries.html)强调了幂等与重试放大的约束。

向模型回填错误要足够行动，例如“对象已删除，不能按原 ID 重试”，而不是一大段堆栈或永远相同的“失败，请再试”。

### 10. 工具已经成功，但响应或 Checkpoint 丢了怎么办？

[S042](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L217-L217)明确给出外部任务已成功、Checkpoint尚未写入便崩溃的窗口，不能把它改写为普通工具失败。

这是跨系统的结果未知窗口。先保留稳定的业务操作身份，查询下游回执；确认成功就补齐本地状态，不能创建一个新操作再做。查询暂时未找到也不一定证明失败，旧请求可能仍在途。

幂等身份要在首次执行前由可信程序确定，绑定租户、业务动作和参数；重试仍使用同一身份，下游也必须真正识别它。网络 request_id 每次不同很正常，业务 operation_id 不应因此变化。[Stripe 的幂等契约](https://docs.stripe.com/api/idempotent_requests)展示了参数一致性和保存期限等限制，不能把某服务的契约当成所有工具的默认能力。

如果既不能查询又没有防重契约，就保留未知并转人工核对。增加检查点频率只能缩小部分损失，不能把外部动作纳入本地事务。

<a id="q11"></a>

### 11. Checkpoint、Resume 与重放聊天记录有什么区别？

[S087](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L285-L285)问检查点持久化与断线后执行恢复，[S214](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-14.md#L51-L51)问Checkpoint在压缩和长任务中的职责；History、Fork边界是为完整回答补充的工程解释。

Checkpoint 保存的是可继续的执行状态：当前任务、输入版本、计划进度、待处理工作、产物引用及必要的控制信息。不可盲重做的外部操作另有可靠记录。聊天 History 只是过去交互，不一定包含最新取消信号、批准范围、执行权或迟到回执。

Resume 应先确认当前身份、状态版本和执行权，再核对未决副作用，恢复必要环境和产物，最后重建模型输入。切模型或升级图结构时还要检查状态与消息协议兼容；不能把旧状态不经迁移直接交给新代码。

Fork 则要重新定义继承范围：新分支可以复制上下文或产物引用，却不能复制旧授权、把已发生动作当未发生，或让两个分支共用同一个“新动作”身份。

<a id="q12"></a>

### 12. 五分钟工具还在运行，用户又说话或点取消，怎么处理？

工具未结束时用户继续对话对应[S205](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-12.md#L19-L19)；取消及是否真正实现测试对应[S036](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L93-L93)。异步返回和取消回执必须分别处理。

把任务寿命与一次模型调用、HTTP 连接分开。长工具返回任务句柄或由 Worker 异步执行；Runtime 记录状态和关联身份，完成事件到达后在安全决策点写入观察。用户新消息先归属到正确任务，区分补充信息、修改目标、新任务和取消，再决定是否重规划。

已经发出的模型请求通常不能原地修改；已产生的外部效果也不会随取消消失。取消应停止派发新动作，传播给支持取消的活动，并记录取消请求和最终结果。若远端迟到成功，应如实记账，必要时启动单独获准的补偿。

Pause 是等待可继续条件，Cancel 是终止意图，Fail 是错误，三者都不是成功。等待批准不应一直占着模型并发槽位。

<a id="q13"></a>

### 13. HITL 为什么不是一个确认弹窗？

[S146](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L70-L70)问人工介入与中断恢复，[S253](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-21.md#L188-L188)限定支付等高风险动作；SDK的具体恢复行为另由官方文档核实。

真正的批准要绑定待执行动作的身份、对象、参数和版本，持久记录同意或拒绝，并在恢复后再次检查执行时仍有权限、对象未发生实质变化。UI 展示 A、恢复状态却执行 B，是必须防住的批准失配。

框架能承担部分流程，但语义要核对。按当前[OpenAI Agents SDK HITL 文档](https://openai.github.io/openai-agents-python/human_in_the_loop/)，暂停由 interruptions 暴露，可序列化 RunState；handoff 或嵌套 `Agent.as_tool()` 的批准也可在外层 RunState 处理，并恢复原顶层运行。不能只批准外层委派就假定内层所有写动作都获准。

[LangGraph interrupt 文档](https://docs.langchain.com/oss/python/langgraph/interrupts)要求 Checkpointer 和稳定 thread_id；恢复会从被中断节点开头重执行，所以中断之前的副作用必须移出、去重或做成幂等。当前文档的接口能力不能反推本地旧 SDK 也支持。

## 三、上下文与记忆要能纠错、能恢复

### 14. Context、State、History、Memory 怎样区分？

教学归纳：[S017](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L82-L82)直接问Context与长期Memory边界，[S214](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-14.md#L51-L51)问Checkpoint职责；四个术语的统一对照是本文的解释框架，并非一条原题的逐字内容。

Context 是本轮实际给模型的信息；State 是程序推进任务所需的当前事实；History 是过去发生的交互；Memory 是为未来复用而维护的信息。它们可以引用同一事实，但职责不同：数据库里保存了某条记忆，不表示模型这一轮看到了；模型收到摘要，也不表示程序可以据此裁定退款已成功。

装配上下文时，我先固定目标、最新约束和可信控制说明，再选择相关历史、工具契约、检索证据和观察。每项检查权限、时效、重复与预算，保留输出余量。工具说明可能通过 API 的 tools 字段单独传入，仍然消耗模型处理上下文的资源。

授权记录、操作回执和任务状态不能只存在于可被模型改写的自然语言摘要中。

<a id="q15"></a>

### 15. 上下文很长时，怎样压缩且证明没压坏？

[S017](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L79-L79)要求超窗压缩并保留必要信息，[S043](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L243-L243)要求验证任务未被压坏；答案不能止于更短的摘要。

先治理输入，再考虑摘要：缩小文件读取范围、去掉重复观察、外部化大产物，只为当前任务取必要片段。真正 Compaction 要将下一次请求中的输入换成更短视图；保留完整历史并在末尾再追加摘要，没有减少输入。

摘要至少保留当前目标、硬约束、已确认事实与来源、完成进度、未决问题和可回读引用。关键约束可由程序单独维护。验证包括结构检查、抽样核对原文，以及压缩前后继续执行的回归；“字段齐、读起来通顺、Token 降了”都不足以证明任务未受损。

若每个字符都重要，不能承诺有损摘要无损。应保留原件，按索引分段读取和校验，或分任务处理；长输出被截断则从可验证边界续写并检查拼接结果。[上下文工程实践](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)也区分了即时检索、压缩和结构化笔记的用途。

### 16. 长短期记忆怎样设计，错误记忆怎么删除？

长短期分层来自[S003](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L63-L63)，错误结论写入Memory后的修复与防传播来自[S236](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-18.md#L22-L22)。

短期记忆服务当前会话或任务连续性；长期记忆保存跨会话有用、允许保存且有依据的信息。是否增加工作记忆或中期层，应根据访问模式决定，不是每个系统都必须有三层数据库。

一条长期记忆要带用户或租户范围、来源、更新时间、有效条件和必要版本。写入前做相关性判断与去重，召回时检查时效和权限。用户明确的新要求、权威业务系统的当前记录，不应被旧摘要覆盖。向量相似度只帮助找到候选，不能裁定真伪或授权。

错误记忆需要回到原来源修正，并使派生摘要、索引和缓存失效；删除文本却继续命中旧向量，问题仍在。过时文件摘要要与仓库版本关联，不能只按 FIFO 淘汰或永久追加每轮观察。

### 17. LangGraph State 为什么会膨胀？Session 能代替 Checkpoint 吗？

State膨胀与OOM对应[S162](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-09.md#L56-L56)，会话记录存储及Resume对应[S189](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-10.md#L311-L311)；Session与Checkpointer的产品语义按所引官方文档区分。

节点反复追加全文消息、大文档和工具结果，或者合并规则重复累加列表，都可能让状态和检查点快速增长。先明确每个字段的写入者、覆盖或合并规则；大文件放产物存储，状态保存引用。不要让每个子图拿到所有原始材料，再将全量内容回写父图。

[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)将线程级图状态的 Checkpointer 与跨线程数据 Store 区分。内存实现不保证进程重启后保存；生产需要匹配恢复目标的持久后端与保留策略。

[Agents SDK Session](https://openai.github.io/openai-agents-python/sessions/)管理会话历史的读取和新增交互保存；它不能自动替代业务事务、操作账本或工作流检查点。能续聊、能恢复图执行、能证明外部只写一次，是三个不同承诺。

## 四、协议、技能与协作

<a id="q18"></a>

### 18. MCP、Function Calling、Skill 各解决什么问题？

[S014](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L15-L15)直接比较Function Calling、MCP与Skill；这里保留三个对象，不用其中一个概念代替另一个。

Function Calling 通常描述模型 API 中的调用表示；真实函数仍由宿主执行。MCP 标准化 Host 经 Client 与 Server 发现和访问工具、资源、提示模板的协议。Skill 组织某类任务的方法、说明及资源，可以指导模型使用本地工具或 MCP 工具。

因此，Skill 文档可以告诉代理怎样排查订单，却不能凭文字完成数据库更新；MCP 接好了工具，也不会自动提供任务规划和记忆。Host 负责模型与任务，Client 是协议组件，不是使用产品的人；Server 负责自己的资源授权。`clientInfo` 是软件身份元数据，不是用户凭证。

不要把第三方工具或资源内容提升为系统命令。[MCP 的三类原语](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)中，发现某个工具也不等于当前请求已获执行授权。

<a id="q19"></a>

### 19. MCP 的初始化、SSE、Streamable HTTP，版本怎么回答？

SSE与Streamable HTTP比较见[S033](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L33-L33)，stdio与Streamable HTTP比较见[S231](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-17.md#L16-L16)。2026与旧版生命周期的区分属于官方规范核对后的教学补充。

先报协议版本和实际 SDK。本文核对的 **2026-07-28** 规范采用每请求版本与能力元数据，不再要求旧初始化握手；Server 实现 `server/discover`，Client 可以先发现。**2025-11-25 及更早的旧生命周期**则使用 initialize 协商。不能将两代流程拼成同一次必经链。[官方兼容说明](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)明确区分了这两类。

stdio 通常连接本地子进程；Streamable HTTP 用 HTTP 承载协议，可以涉及 SSE 流。旧 HTTP+SSE 传输和 Streamable HTTP 不能只因为都出现 SSE 就当同一个协议。连接认证、版本兼容和业务幂等仍分别处理，断流不代表远端工具没执行。实现细节按相应[传输规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)核对。

协议请求无状态，不代表业务任务无状态，也不能推导 MCP 永远不支持长任务。不同 SDK、产品固定版本可能只支持其中一代。

### 20. Skill 怎样渐进披露，为什么不能保证百分之百触发？

[S039](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L157-L157)问渐进披露实现，[S247](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-20.md#L63-L64)明确追问能否保证100%正确触发；按需加载与执行约束因此分开回答。

先让模型或路由层看到名称、描述等轻量元数据；选中后加载主体，再按需读取 references、scripts、assets。这样降低默认上下文占用，也减少无关说明相互干扰。[Agent Skills 规范](https://agentskills.io/specification)给出了目录结构与渐进披露约定；具体加载策略仍由宿主实现。

描述相近会误选，描述不足会漏召回。要用真实任务测“找没找到、选没选对、读没读全、执行是否成功”，必要时合并重复技能、增加反例和受控路由。只加载文档不能保证模型遵守，也不证明脚本已经运行。

高合规流程应由执行器强制验证必要步骤和权限。规则负责必须遵守的约束，Skill 提供任务方法；Hook 在生命周期事件触发程序，Plugin 负责打包启用。后置 Hook 可以拦结果，却不能撤销已经发送的邮件，可选插件不能是唯一安全门。

### 21. 为什么要拆多 Agent，怎样证明不是徒增复杂度？

[S001](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L22-L22)问什么任务值得拆子Agent，[S151](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L183-L183)要求证明单、多Agent取舍的收益；不能仅凭角色数量论证架构有效。

先做单 Agent 或固定流程基线。只有子任务可相对独立、上下文可隔离、结果可验收，且并行或专业分工能带来可测收益时，再拆。多个名字不同的 Prompt 共用同一混乱上下文，不一定有真正分工。

Manager/Worker 便于集中控制任务和预算；Agent-as-Tool 把子结果返回父级；Handoff 转移当前处理权；平级协作更灵活，但更难管理循环、冲突与最终责任。按角色划分后保留 Agent Pool，可以复用实例或管理容量，是否需要取决于实例状态和并发成本，不是角色数量直接决定进程数量。

比较相同任务的成功率、每个合格任务的总成本、P95 延迟和故障恢复。局部 Agent 都成功，仍可能遗漏需求或互相矛盾，父级必须做整体验收。

### 22. 多 Agent 怎样传状态，怎样避免互相覆盖代码？

通信组织来自[S001](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L23-L23)，并行修改同文件的冲突、锁和工作区隔离来自[S032](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-03.md#L15-L15)；独立工作树的行为另引Git文档。

子任务消息应说明目标、输入引用与版本、约束、输出契约和截止时间；返回结果、证据与明确失败原因。不要把所有历史广播给所有代理，既增加成本也扩大信息暴露。共享状态要有写入者或合并规则，数据库更新用事务或条件更新拒绝过时提交。

改代码时可让单个整合者写入，或给各 Worker 真正独立的 checkout/worktree，再按明确基线收集补丁。仅不同分支名但共用同一目录，并没有隔离文件。[Git worktree 文档](https://git-scm.com/docs/git-worktree)解释了独立工作树的机制；合并无文本冲突仍需行为回归。

跨独立 Agent 系统可用 A2A 表达消息、任务状态和产物。[A2A v1.0.1](https://a2a-protocol.org/v1.0.1/specification/)中的 Task 完成是协议状态，不自动证明调用方业务验收通过。协议名称也不保证认证、取消和重试语义已经实现。

### 23. Prompt Injection、权限、批准与 Sandbox 怎样协同？

[S027](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-02.md#L295-L295)问注入绕过与防护边界，[S228](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-16.md#L91-L91)给出必须读内部代码却又不能泄密的架构约束。

注入防护先从信任边界做：检索文档、网页、工具结果和旧记忆是资料，不因为内容写着“系统指令”就获得权限。程序决定工具可见范围、资源权限与批准要求，执行环境限制文件、网络和资源，输出与记忆写入再做相应保护。

例如代理必须阅读内部代码排障，可以在只读受限工作区完成分析，并限制联网外传；不能先让子代理看全部秘密，再寄希望于主代理把回答过滤干净。只读也能泄密，环境变量也可能通过 Shell 或堆栈暴露。

Permission 决定身份能做什么，Approval 确认具体动作，Sandbox 限制代码实际接触什么。三者缺一都可能扩大单次错误影响。[OWASP 的防注入建议](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)采用分层防护，检测器并不是可替代授权的完美分类器。

### 24. 意图路由和模型路由怎样设计？

[S122](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L165-L165)比较规则、小模型与LLM意图分类，[S240](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L15-L15)问多模型路由及错误分类；两种路由的对象不同。

意图路由先定义类别与误分后果。明确命令用规则，标签稳定且有标注可用小分类器，开放表达再考虑模型；低置信度应澄清或保守回退。分类只决定路径，不能授予新的权限。

模型路由先满足模态、工具协议、上下文、数据地域和结构输出等硬条件，再比较质量、延迟与每个合格任务的总成本。小模型便宜但重试多，可能更贵。切后端时必须适配消息角色、调用关联、错误与流式语义，不能只凭“OpenAI-compatible”认定全兼容。

参数错误、上下文超限和临时限流不能套同一种重试。已流出部分回答后切模型，要明确新尝试和输出边界；未完成的工具参数片段不能拿去执行。

<a id="q25"></a>

### 25. Agent Eval 应怎样构建，几个真实案例反复跑够不够？

[S078](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L83-L83)问评测体系和覆盖，[S242](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L106-L106)质疑约20个真实案例重复多轮是否足够；重复次数不能代替场景覆盖。

先定义任务成功与禁止事件，再按常见任务、困难输入、失败恢复、越权、无答案和长链任务分层采样。可执行结果用测试、文件、数据库或外部回执验收；开放内容再用模型评审与人工抽查。评测环境、模型、Prompt、工具和数据版本要能定位。

同一个案例多跑几次能观察随机波动，不能代替新的场景覆盖。比较改动时用相同案例与配置口径，留出未参与调参的集合，报告各类退化，而不只报告总均分。耗时、成本和安全指标也要和任务成功一起看。

LLM Judge 要有明确评分规则、代表性人工校准和失败检查；它可能偏好文风，也可能与被测模型共享错误。评估代理自己幻觉时，应回到可验证环境事实。[Agent 评测实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)区分了任务、尝试、轨迹、结果与评分器，适合用来检查自己的评测是否只测到了“说得像完成”。

### 26. Agent 变慢或答错，Trace 应怎样帮忙？

执行观测设计见[S074](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L483-L483)，Trace Replay用于可靠性与调试见[S129](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L400-L400)；真实副作用重放的风险是必须补齐的实现边界。

将用户请求、Run、模型调用和工具调用关联起来，记录阶段时长、重试、状态变化、Token 用量与必要版本。先区分排队慢、模型慢、工具慢、重复循环或恢复重跑，再调具体层。总耗时不能告诉你哪个阶段是瓶颈；少一个 Span 也不能让业务回执丢失。

[OpenTelemetry 的 Trace/Span 模型](https://opentelemetry.io/docs/concepts/signals/traces/)适合关联分布式执行；[Agents SDK tracing](https://openai.github.io/openai-agents-python/tracing/)提供了相应运行追踪入口。是否记录完整输入输出需要另做脱敏、权限和保留设计，不应默认保存全部敏感 Context。

Replay 要声明是在看证据、重建状态、重演模型，还是重新执行外部动作。诊断默认用已记录结果或隔离环境；重放历史退款、发信工具会产生新副作用，不能当普通调试按钮。

### 27. Coding Agent 怎样证明可交付，怎样安全“自进化”？

[S282](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-27.md#L196-L196)问AI代码遗漏坏例后的发现、回滚与补测，[S082](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L173-L173)问自进化如何防错误经验积累；案例验证与版本治理共同支撑这一节。

先定位真实调用路径和失败条件，再做最小完整修改；用能暴露原问题的测试验证，再运行相关回归，审查 diff、依赖、安全与用户已有修改。生成测试也可能把错误实现当期望，要检查断言和测试数据来源。

自进化可以从坏例中形成候选 Skill、Prompt 或工具改动，但应先在隔离评测上比较、保留版本与回滚，再灰度应用；不能把一次偶然成功或模型自评直接写成长期规则。错误反馈还可能污染记忆与技能，需要来源审核和去重。

面试中说清哪些是本人设计、哪些来自框架、哪些由 AI 生成，给出真实修改、验证结果和仍未覆盖的范围。没有生产用户就说没有，不能用教学设计替换个人经历。

### 28. LangGraph、SDK、自研 Loop 最后怎么选？

自研Runtime与框架的取舍来自[S004](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L91-L91)，LangGraph与LangChain工程差异来自[S054](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L54-L54)；选型要落到需求和失败实验。

我会用同一组需求和失败实验比较：状态与控制流能否表达，等待批准如何恢复，工具副作用怎样处理，模型切换是否兼容，追踪与部署成本是多少。只需要短流程时，自研小循环可能足够；复杂图、持久中断和生态集成可能使框架更划算。

选框架并不免除理解其恢复单位、合并规则和版本迁移；自研也不等于所有基础设施都重写。可以让框架承担成熟部分，自己控制权限、业务操作账本或特殊调度。回答产品源码问题时，明确读过的仓库版本与模块；未读过的实现不要凭名称猜。
