## 1. 你的 RAG 从文档进入到回答生成，完整链路是什么？

例如 [S063 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L246-L246) 同时追问完整链路与 Embedding / Vector Retrieval 的具体实现；下面将两层回答展开。

先说明答案依赖什么外部知识，再分离摄取和查询两条链。摄取负责取得有权使用的文档，解析结构、清洗、切块，生成嵌入并写入索引，同时保存原文位置、内容版本和访问范围。查询先确定问题与身份，在允许范围内召回，融合候选、重排和补全证据，再组织上下文生成回答，最后检查引用和结论的支持关系。

向量数据库只承担其中的表示存储、近邻查询等能力；整个系统还要处理词法检索、原文回取、权限、更新和评测。模型生成的是回答，不会因这次检索而自动把知识写进参数。[RAG 原论文](https://arxiv.org/abs/2005.11401)把参数化模型与外部检索记忆结合；工程中的模块边界可以不同，但必须说清楚证据从哪里来、如何进入回答。

追问到实现时，应继续解释文档和查询分别如何编码、嵌入版本如何绑定、索引返回的是 ID 还是内容、原文如何回取。只背“切块→向量库→大模型”还不足以说明一条请求真正怎样完成。

## 2. 为什么需要 RAG？长上下文、微调、文件搜索和业务工具怎么选？

[S109 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-06.md#L348-L348) 直接比较 RAG 与微调的边界；[S218 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-15.md#L37-L37) 追问大上下文下为何仍需 RAG，以及直接文件搜索的优缺点。这些比较对象要分别回答。

RAG 适合让回答使用外部、可更新、可回源的材料。材料很少且请求范围明确时，直接给上下文可能更简单；材料多、经常变化或需要按权限选择时，检索可以控制进入模型的证据范围。长窗口扩大容量，却不保证模型同样善用每个位置的信息；[Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/)展示了长上下文利用与信息位置有关的现象，不能据此断言所有新模型具有相同表现。

微调适合改变行为、格式或领域任务能力，不能独自承担事实即时更新、撤权和逐条引用。Agent 直接搜索文件或仓库可以减少预建索引，代价是在线扫描、工具往返和上下文选择；即使暂时不计 Token 费用，两者仍有预处理、查询延迟、更新路径与可观测性差异。

订单状态、库存或退款执行要使用受控业务接口。政策知识库能够解释规则，不能代替读取实时订单，更不能把“生成了退款建议”当成“完成退款”。选型时分别比较事实新鲜度、任务质量、延迟和运维成本，不把这些不同方案混成一个笼统的“AI 更强就行”。

## 3. PDF 有扫描页、表格和图片，怎样证明解析是正确的？

[S207 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-12.md#L63-L63) 问混合文档与扫描 PDF 的多模态解析；[S087 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L277-L277) 进一步要求解释 OCR、表格抽取难点及识别质量如何评估。

先区分可用文字层、扫描图像与布局结构。文字层可靠时直接抽取；扫描区域再使用 OCR 或文档模型。产物需要保留标题层次、阅读顺序、表头、单位、脚注、图片及回源位置。字符提取成功只是第一步：两列文字串错、金额和单位分离、跨页表头丢失，都可能让后续检索“相关但答错”。

对跨页表，检查表头、列结构、页间连续关系再决定合并；对同文档的两张关联表，应保存关系，不能因为相邻就拼成一张。HTML 或结构化单元格适合表达合并单元格、表头归属等结构，但选择表示的目的在于保真和可使用，不是换个格式就自动提高效果。[MinerU 的官方实现](https://github.com/opendatalab/MinerU)说明了文档解析的多种输出与处理能力；具体版本仍要用自己的语料抽样验收。

验收应从原页抽取关键事实做对照，包含否定词、时间、数字、跨页表和图片关系。图片摘要是派生描述，重要结论仍需回到图像验证。解析失败的文档进入失败队列或人工复核，不发布为“空内容的成功版本”。

## 4. Chunk 为什么这样切？200–500、固定长度和语义切分怎么解释？

[S002 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-01.md#L40-L40) 要求依据数据与评测确定块大小和策略；[S275 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-26.md#L22-L22) 则追问多级标题与约 200–500 的配置依据。后一个数值只属于该样本。

先明确长度单位，再解释结构和任务。字符、字节与 Token 不能混用。优先保留标题、段落、表格和代码边界；超长部分逐层细分，固定窗口作为可复现基线。递归切分可以只按分隔符层级执行，不必调用语义模型；[LangChain 的递归切分说明](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter)也明确了分隔符、块大小和长度函数的职责。

小块有利于定位局部事实，却容易丢掉对象、条件和例外；大块保留上下文，却会混入多个主题、增加计算，还可能被嵌入或重排模型截断。语义切分能利用主题变化，但话题相似不代表业务依赖完整，仍要限制最大输入长度。

参数应在同一问题集、文档版本、权限和下游预算下比较：既看证据覆盖与最终答案，也看块数、索引成本和延迟。原面经中的数值是候选人需要解释的配置，不是通用最佳范围。应回答依据与验证方式，而非背一个数字。

## 5. Overlap、父子块和邻居扩展分别解决什么？尾块不足怎么办？

[S402 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L987-L987) 直接问父子分块的实现；[S287 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-28.md#L48-L48) 给出 1000 Token 按 400 切、尾段 200 如何处理的具体追问。下面同时解释边界补全的几种机制。

Overlap 让相邻窗口共享局部内容，减轻边界截断；它增加重复存储和候选，不能补齐远处的定义或例外。父子块把定位粒度和阅读粒度分开：小块参加检索，通过稳定的父标识回取较完整章节。邻居扩展则按文档位置补取上下文。回填时要维持同文档版本，并重新检查父块和邻居的授权范围。

若“充分必要条件”或两张相关表被切开，要追踪这条依赖是否在上下文装包中重新合上。扩大所有块不是唯一解，也不能按文档 ID 去重到只剩一块，否则同文档中不同证据会被误删。

固定块长的尾部不足时，可以保留短块、向前回填上下文或在不超过模型预算的条件下并入前块。选择取决于内容边界与验证结果；不要为了凑齐长度复制出假的语义。对于 1000 Token 按 400 切、尾部 200 的情境，先问是否有 overlap、单位与边界规则，再说明取舍，不能只写整除公式。

## 6. Query Rewrite、Multi-query、分解和 HyDE 有什么区别？

[S376 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L4149-L4149) 用“我要退了”的歧义追问改写后效果变差怎么办；[S184 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-10.md#L201-L201) 问 HyDE 的含义与适用条件。改写和假设文档不能混为同一操作。

改写将原问题中的省略补成独立表达，保留已确认的对象、时间、否定和状态。Multi-query 为同一意图生成少量表达变体；问题分解则拆开不同的信息需求，可能需要先查一部分再决定后续查询。存在“退了”指退货还是退款之类歧义时，应结合可靠上下文或澄清，不由改写器替用户猜答案。

HyDE 先生成假设性文档，再利用其向量检索真实材料。[HyDE 论文](https://aclanthology.org/2023.acl-long.99/)讨论了这种检索表示方式；假设文档可能有虚构细节，不能直接作为证据引用。

保留原 Query 与改写结果用于回归和回退。改写后召回变差，应比较意图约束、实体和时间是否漂移，再检查各路新增与丢失的证据。多次模型调用需要证明比单次联合输出更有收益；不能把“多生成几种说法”当成总会有效的优化。

## 7. BM25 和向量检索为什么互补？IDF 起什么作用？

[S240 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L27-L27) 追问 BM25 与向量检索各补什么短板；[S275 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-26.md#L23-L23) 明确追问 BM25 机制和 IDF 的作用。

词法检索保留精确术语、编号与罕见词的信号，向量检索适合表达不同但语义接近的查询。相似语义不保证型号、金额或状态正确；字面相同也不保证意图一致。混合检索的目的，是在评测中补齐单路遗漏，随后控制新增噪声。

BM25 按查询词累加贡献，综合逆文档频率、词频饱和与文档长度归一化。IDF 描述词项在集合中的区分能力；同一词多出现几次不会线性增加贡献。`k1` 控制词频饱和，`b` 控制长度归一化强度，具体实现和默认值应对照 [Elasticsearch 的 BM25 参数说明](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)。中文分词、同义词和领域术语处理也会改变词法召回。

常见 BM25 写法为 `Σ IDF(t) × f(t,d)(k1+1) / [f(t,d)+k1(1−b+b×|d|/avgdl)]`：`f` 是词频，`|d|` 和 `avgdl` 是文档长度与平均长度。IDF 的平滑形式、查询词处理及可省略常数按实现核对，例如 [Lucene BM25Similarity](https://github.com/apache/lucene/blob/main/lucene/core/src/java/org/apache/lucene/search/similarities/BM25Similarity.java)。这解释了词频增加会饱和、长文会被归一化，而不是只按出现次数排序。

证明互补要固定问题集、合法候选范围和候选预算，分别跑关键词、向量与融合方案。既检查新增找回的正确材料，也检查“召回十段只有两段有效”一类精确率退化，不能只汇报命中更多。

## 8. RRF 怎么算？为什么不用分数平均？

[S240 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L29-L29) 同时问 RRF 如何融合、为何不简单线性加权，以及常数怎样确定；下面的算例用于解释这一机制。

不同检索器的分数通常不在同一量纲。RRF 使用排名：对候选 `d`，累加它在各路出现时的 `1/(c + rank_i(d))`，名次从 1 开始，未进入该路候选窗口则该路贡献为零。相同候选按稳定身份归并，不把重复文本当成多份独立证据。[Elasticsearch 的 RRF 文档](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)给出了该计算方式。

`c` 调整不同名次的相对影响；它不是各路召回数，也不是最终送给模型的 K。RRF 无需直接比较原分数，但也放弃了分数间隔的信息。经校准的加权融合可能更适合某些业务，应该通过相同预算的对照决定，而不是把一个默认常数背成最优值。

例如候选 A 在两路分别排第 1、3，B 只在一路排第 1：给定正的常数，A 获得两项贡献，B 获得一项。这个算例只解释计算，不证明 A 必然更真实、更完整或更有权被访问。

## 9. 为什么召回后重排？加 Rerank 反而变差怎么查？

[S211 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-13.md#L63-L63) 比较 Bi-Encoder 与 Cross-Encoder 的成本；[S249 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-21.md#L58-L58) 则明确追问加 Rerank 后效果变差如何定位。

初召回用相对低成本方法取得候选，重排再对问题与候选做更细判断。常见双编码器分别产生表示，文档向量可预计算；Cross-Encoder 联合输入问题和文档，交互更充分，在线成本也更高。这种职责分工可参照 [Sentence Transformers 的检索与重排说明](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)。

先查正确材料是否进入重排输入。没有进入，重排无法找回。进入后才检查领域适配、输入截断、分数排序方向、长文偏差，以及相关性标签是否等同于本任务需要的证据。还要检查正确候选是否在后续去重或上下文预算中被删除。

重排降级应事先评测：超时时可以在业务允许的情况下返回已验证的融合候选，或者明确本次能力不完整。不同模型、缓存或无重排路径如何构成“三级降级”，必须按实际项目说明；不能替原帖补写一个固定顺序。

## 10. 系统里到底有几个 Top-K？全部交给大模型重排行不行？

[S115 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-07.md#L20-L20) 问为何不把全部召回候选交给大模型重排；[S147 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L93-L93) 要求用评测解释 Top-K 为 6 / 8 而非 3。这些配置不构成通用推荐值。

至少要区分各路召回数、融合保留数、重排输入数，以及最终上下文中的候选数和 Token 预算。前级 K 影响覆盖，后级预算影响噪声、推理费用与模型是否真正读到关键内容。K 太小会漏必要证据，太大可能增加延迟和互相干扰，不能用一个 K 表示整条链。

把全部候选交给大模型，还要承担成对或列表推理、输入长度、截断和失败重试的代价。先用便宜方法建立足够覆盖，再比较精排的边际收益。可按问题难度分层，但需要验证困难度判断本身，避免把难问题误判后过早结束。

相似度、RRF 分数和重排分数都不能未经校准解释为“答案正确概率”。证据充分性还取决于是否覆盖每个必要条件，而不是最高分是否超过某个听起来合理的阈值。

## 11. 证据怎样装进上下文？引用和拒答怎么保证？

[S240 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-19.md#L32-L32) 要求验证结论并把引用映射回证据；[S067 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L334-L334) 追问证据不足怎样判断和拒答。下面把引用与充分性分开检查。

先去重和补全关系，再为系统指令、用户问题、历史与输出预留预算。证据标明文档版本、来源位置和受控引用 ID；尽量保留对象、日期、单位、否定及例外。对有冲突的材料，明确适用对象、有效时间和权威来源，不能默认最后上传的文档正确。

生成后分三步验引用：ID 来自本次证据集合；当前用户仍可访问对应来源；原文确实支持该条结论。引用存在不等于支持成立，忠实引用过期材料也会答错。[Ragas 的 Faithfulness 定义](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)关注回答是否受给定上下文支持，这与材料本身是否真实、当前适用是不同判断。

知识缺失、证据冲突、检索超时应分别处理。前者可以澄清、补查或给出有支持的有限结论；后者不能伪装成“知识库没有答案”。不能凭模型自报有把握就越过拒答边界。

## 12. Recall、Precision、MRR、NDCG 和答案准确率怎么区分？

[S052 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L18-L18) 明确问 Recall、Faithfulness 等指标的定义与计算；[S153 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-08.md#L230-L230) 问检索评测指标。下面的完整指标对照是教学展开，不表示原记录逐项点名了所有指标。

先确定相关性标签与统计单位。业务 Recall@K 看前 K 覆盖了多少已标注相关证据；Precision@K 看返回结果中有多少相关。Hit 关注是否至少命中一个，MRR 关注首个相关结果出现多早，NDCG 还考虑分级相关性和位置。它们衡量的目标不同，尤其不能用“第一条命中”代替多证据覆盖。[信息检索教材的排序评测章节](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-ranked-retrieval-results-1.html)给出了这些排名指标的基本口径。

无相关证据的查询，Recall 分母为零，应单列为不可回答任务，不强行记为 1。Precision@K 通常以 K 为分母；不足 K 时若另报按实际返回数计算的 Precision，应明确名称和口径，不与前者混报。

答案还要单独评价事实正确性、忠实性、引用支持、任务完成和拒答。ANN 对精确近邻的 Recall 则是索引层指标，和这里人工标注的业务相关性不是一回事。宣称“Recall@5 达到某值”时，必须给出 K、分母、相关性标准、数据版本与样本范围。

## 13. 评测集从哪里来，怎样证明优化有效？

[S084 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L217-L217) 问评测维度与数据集构建；[S065 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-04.md#L296-L296) 要求说明实际调过的参数及调优有效性的判断依据。

组合真实用户问题、专家设计问题和历史 Bad Case，覆盖精确术语、口语改写、多跳、表格、时效、冲突、无答案及权限边界。为问题标明所需事实、可用来源与有效时间。切块方案变化时，应从稳定原文片段或事实标签映射到新块，避免旧 Chunk ID 使评测失效。

训练、调参和最终测试按文档、来源、主题或时间做合理隔离，防止同源改写泄漏。随机生成或模型生成的题可以补覆盖，但需审核，不能由同一模型生成题和答案，再独自证明自己正确。LLM Judge 要与人工判断对照，检查位置、长度、模型偏好和随机波动；[RAGAS 论文](https://arxiv.org/abs/2309.15217)提供了自动评测的分解思路，工具输出仍是测量结果而非真值保证。

实验一次尽量只改变可解释因素，保持语料、权限、查询和下游预算一致，做基线、消融和回归。报告总体与关键切片、样本数、百分点或相对比例、重复运行波动、延迟和成本。项目名或“样本从几十增到几百”本身不能证明覆盖充足，关键是目标分布和失败边界是否被测到。

## 14. 回答差时怎样快速判断问题在检索还是生成？

[S280 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-27.md#L59-L60) 直接问回答差时如何区分检索和生成问题；[S253 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-21.md#L178-L178) 将同一归因任务放在 Answer Relevance 偏低的场景中。

沿证据消失的位置排查：权威原文是否有答案；解析与切分是否保住；索引和权限范围是否可见；召回是否进入候选；重排、去重或预算是否删掉；最终模型是否错误解释或引用。

做受控替换比盲调参数更有价值：把人工确认的完整证据直接交给同一生成链，若仍答错，优先看提示、任务能力和输出验证；若能够正确作答，再向上游定位。也可以固定候选只换重排器、固定检索只换生成模型。一个请求可能同时有两处故障，发现首个缺口后仍要验证修复后的整链。

若召回本来正确，继续调向量索引往往没有针对性；若纯向量检索找不到精确报错，先检查词法路线、分词与标识处理。若改写误改意图，回退原问题并测约束保留。不要把每种失败都解释成“模型不够强”。

## 15. 知识库怎样增量更新？旧任务晚完成、删除和回滚怎么办？

[S081 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-05.md#L152-L152) 追问持续更新时的向量索引、缓存失效和旧文档召回；[S107 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-06.md#L288-L288) 问文档版本控制与错误版本回滚。旧任务竞争和发布协议是为回答这些问题补足的工程机制。

以稳定文档身份、源修订号和内容哈希识别变化，记录解析、切分、嵌入、索引及发布状态。哈希可发现内容变化，但不能替代文档身份或授权。队列提供重试、背压和异步解耦；事件通知与定时核对可共同补漏。

幂等键解决重复执行，还需原子比较源版本，防止旧任务晚完成覆盖新结果。文档缩短时要清理失效旧块。新版本先构建和验证，再通过受控发布记录选择一致的正文、词项索引、向量索引和缓存版本。单个产品的别名切换并不构成跨系统事务。

删除与撤权优先阻止可见，不能等待整批重建。内容回滚也不能恢复已经撤销的权限。回滚前要确认旧版本是否接到了切换后的增量；保留一份旧索引不等于它已能安全接管。模型或嵌入协议变化时，编码器和索引要作为兼容组合迁移，具体索引生命周期见 [Vector DB 问答](../vector-db/01-高频面试题.md)。

## 16. 多租户知识库怎样防越权？相同内容能共享缓存吗？

[S254 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-21.md#L211-L211) 明确要求防止员工越权读取知识库；[S373 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-37.md#L3972-L3972) 问不同知识库的数据隔离。缓存与间接提示注入防护是沿同一授权边界的教学补足。

从认证身份推导允许的租户、空间和文档范围，服务端强制应用于检索、按 ID 回取、父块扩展、引用、下载和缓存。用户输入的 tenant_id 只能是待校验参数，不能成为授权依据。缓存键应包含决定答案的查询、内容版本和授权相关上下文；内容相同不代表有权共享。

文档本身是外部输入，可能包含要求忽略规则或执行工具的指令。提示词分隔可以辅助，但权限与动作边界应由确定性代码执行。[OWASP 的提示注入说明](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)也强调间接注入和分层防护。知识检索成功，不自动授予执行文档中命令的权限。

逻辑分区、独立集合与物理隔离需要按数据量、运维和风险选择。即使物理分库，持有跨库凭证的应用仍需鉴权；为了召回更多结果而取消租户过滤不是可接受的降级。

## 17. 百万商品或 TB 级 PDF 怎样估算规模和定位慢查询？

[S217 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-15.md#L17-L17) 给出 600GB–1TB 金融 PDF 的设计场景；[S277 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-26.md#L85-L85) 给出百万 / 千万商品问答场景。规模不同，但都要把输入规模换算为可测的资源与请求负载。

先把“文件多少 GB”换成页数、OCR 比例、实际 Token、Chunk 数和更新量，再通过代表性抽样估算嵌入计算、索引与元数据成本。存量构建、持续增量和在线查询要分别限流；增加并发前先看模型配额、CPU、内存或存储瓶颈。

在线追踪改写、编码、排队、各路检索、融合、重排和生成。独立检索可并行，但端到端延迟还包含排队、序列化、网络和合并，因此两路分别 300ms、500ms，不保证并行后严格等于 500ms；各阶段 P95 也不能直接相加。

降低成本可从去重摄取、批量嵌入、增量处理、缓存和分层候选预算入手。答案缓存要区分日期、否定、用户状态与权限。最终比较质量、尾延迟、失败率和每成功任务成本，不能只用单请求平均耗时宣布方案胜出。

## 18. 什么时候用 GraphRAG 或 Agentic RAG？

[S272 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-25.md#L42-L42) 比较 GraphRAG 与普通 RAG 的适用场景；[S222 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-15.md#L135-L135) 比较主动检索与固定 RAG。这是两条独立比较轴，不能互相替代。

需要沿实体关系找路径、连接分散事实，或做跨语料主题总结时，可以评估图增强。图构建还要处理实体消歧、边的方向、出处、有效期和更新；LLM 抽出的关系与社区摘要都要验证。[Microsoft GraphRAG 的论文](https://arxiv.org/abs/2404.16130)重点讨论全局总结任务，不能把其收益推广成所有问答都优于普通 RAG。[官方查询说明](https://microsoft.github.io/graphrag/query/overview/)区分多种查询方式，面试中应说清具体实现。

下一次检索依赖中间证据时，Agentic RAG 可以动态决定查询和继续步骤。要记录目标、已取得证据、缺失事实、已试查询与预算，并检测重复与无新增信息。达到步骤或费用上限意味着停止，不能宣称任务已完成。固定事实问题若一次检索足够，确定链路更容易控制时延和回归。

证明复杂方案值得引入，应使用同一任务集对照，单独观察多跳、全局总结和简单查询切片。不要因为只有一个复杂例子成功，就忽略普通问题的成本退化。图方案、主动检索和参数调整是不同变化，应分别消融。

## 19. Code RAG 为什么不能只把代码当普通文本切？

[S398 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L823-L823) 追问超长方法是否仍整体切块；同一面经的 [S398 的记录](https://github.com/studyzhige-ui/ai-application-interview-handbook/blob/b7da1d9a91c761b48a27ba951bb01cd33a15ffed/market/interview-experience/01-data/raw/batch-38.md#L827-L827) 又给出“数据权限”与 RBAC 的表达错位场景。

函数、类、符号引用与调用关系决定代码的可解释范围。可以用语法结构辅助切分，并保存文件、符号、版本和关联元信息；超长方法仍要受模型输入限制，细切后保留方法级回取关系。AST 帮助恢复语法结构，不等于已经解决运行时语义和跨仓库依赖。

用户说“数据权限”、代码却只有 RBAC 时，纯字面匹配可能漏掉；向量、术语映射、符号搜索和关系导航可以互补。反过来，语义相似的两段代码也可能有不同副作用或适用版本。先判断缺的是表达映射、局部证据还是调用关系，再选择方法。

这里训练的是代码知识检索。代码修改、工具执行与 Agent Runtime 的安全和生命周期，应继续在 [Agent 面试准备](../agent/README.md) 中展开，不把个人项目故事补成通用事实。
