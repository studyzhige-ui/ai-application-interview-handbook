<a id="part-1"></a>

## 1. 先选择控制方式，再选择框架

使用 LLM 不自动意味着采用自主 Agent。固定流程里的一个分类、摘要或抽取节点，仍可以由程序决定全部后续路径。Agentic 区域允许模型根据新观察动态选择下一步。

```text
确定性程序 → 含模型节点的 Workflow → 有限动态路由 → 受控 Agent Loop
```

这是控制权配置的连续变化，不是从低级产品到高级产品的排名。简单、可验证的方案应成为比较基线。Anthropic 的 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 强调从简单可组合模式出发。

<a id="part-2"></a>

## 2. 为每项能力分配决策权、执行权与验收权

| 能力 | 模型可以做什么 | 程序必须控制什么 | 验证依据 |
|---|---|---|---|
| 理解与澄清 | 提取诉求、识别缺失信息 | 身份绑定、输入约束、澄清状态 | 任务契约是否明确 |
| 获取证据 | 选择查询和调查方向 | 数据权限、预算、结果来源 | 证据适用性与覆盖率 |
| 规划与行动选择 | 提出计划、选择工具、调整路线 | 可用动作集合、依赖、停止条件 | 进度与约束是否满足 |
| 外部写入 | 形成操作候选 | 真实授权、参数校验、确认、幂等 | 业务回执与最终状态 |
| 结果验证 | 解释证据、发现可能遗漏 | 验收规则、独立检查、失败状态 | 真实结果，而非自称完成 |
| 长任务与协作 | 建议拆分或继续方向 | 持久化、调度、取消、资源所有权 | 恢复和隔离测试 |

模型的“行动选择权”不等于最终授权权。后端不能从模型生成的 user_id、tenant_id 或“用户已同意”文字建立可信身份和批准记录。

<a id="part-3"></a>

## 3. 自主权不是一个全局开关

按动作和任务阶段规定授权范围，可以只建议、只读调查、生成待确认方案，或在已授权边界内自主执行。这里是教学设计选项，不是某个产品的固定权限枚举。

自主权决定要与可逆性、可观测性、错误代价及验证能力一起做。任务很长不必然需要更高权限；一个很短的外部写操作也可能需要强约束。

生产系统常把确定性流程包在 Agentic 区域外：入口校验与身份固定；中间允许探索；关键动作经过业务规则与必要确认；交付前验证结果。这不是“半成品 Agent”，而是明确的不确定性边界。

<a id="part-4"></a>

## 4. 从最小方案演进，避免提前堆模块

先建立单模型、少量受控工具和明确停止条件的基线，再用失败案例决定是否增加能力。

信息找不到，先检查检索与工具接口，不直接增加 Agent 数量。上下文太大，先检查选择、去重、外部化与压缩，不自动加入长期记忆。操作重复，先检查状态和副作用协议，不靠更长 Prompt。任务确有独立子目标且接口明确，才比较多 Agent 的收益和额外成本。

能力设计的产物应包含选择理由、未采用的替代方案、触发升级的证据。模型、框架与数据库选型在职责清楚后再落定。

## 继续推导｜同一个任务，三种最小方案

沿用01章的只读文件报告。先做可以比较的基线，而不是一次上齐所有能力。

| 方案 | 谁决定下一步 | 适用前提 | 需要验证的代价 |
|---|---|---|---|
| 固定读取→生成→校验 | 程序 | 输入固定且可以一次装入 | 是否漏掉冲突、引用是否准确 |
| 固定阶段中加入动态检索 | 程序规定阶段，模型选查询 | 大部分流程已知，局部需要探索 | 动态检索是否增加有效证据 |
| 有限Agent Loop | 模型提候选，程序约束执行 | 后续调查明显依赖新观察 | 额外时延、调用数、越界及不停止风险 |

最后一种不是“最高级答案”。若三种方案质量接近，优先更简单、易验证的一种。比较时用相同输入、验收与预算，记录完成率、证据覆盖、违规动作、成本和耗时；这里不给虚构的提升百分比。

### 把决策权、执行权、验收权填到动作上

| 动作 | 模型可提出 | 可信程序/资源必须保证 | 是否允许自动执行 |
|---|---|---|---|
| 读授权清单内文件 | 选择读取对象与范围 | 身份、清单版本、路径与返回大小 | 允许范围内读取，但仍防敏感数据外传 |
| 增加资料来源 | 提出信息缺口 | 不得悄悄改变契约或联网 | 缺授权先澄清 |
| 生成报告草稿 | 组织材料、表达不确定性 | 保存版本、引用与产物访问控制 | 可以生成，但不自动视为已验证 |
| 改原件或对外发送 | 提出候选方案 | 新契约/具体批准、动作核对与审计 | 原契约禁止，不是“模型觉得安全就行” |
| 宣告完成 | 提交完成候选 | 验收引用、必需字段、原件未变等证据 | 由验收结果决定状态 |

如果用户后来要求修改原件，应先形成新契约版本，明确具体对象、改动范围与确认方式。旧的只读许可不会自动变成写入许可；未授权不是可通过多次重试解决的临时故障。

### 未采用方案也要能解释

当前没有跨任务复用需求，所以先不建长期Memory；没有清晰独立的子任务，所以先不建多Agent；没有任意代码执行需求，所以不为凑架构增加代码沙箱。以后出现规模或失败证据时再升级，并把新的正确性责任一起算进去。

Harness负责兑现循环、状态、工具与约束；Orchestrator描述任务/执行单元之间的组织责任；Workflow Engine可承载确定性或持久流程。这些名称可能在同一个库内重叠，不能把框架标签再当成四层之外的新层。

## 本章自测

<details>
<summary>模型判断某动作安全，能直接执行吗？</summary>

不能。模型建议不建立身份、授权或业务合法性；可信程序与后端须实施相应控制。

</details>

<details>
<summary>什么时候增加长期记忆或多 Agent？</summary>

当任务契约与失败证据显示跨任务信息复用或可分工协作确有价值，并能验证收益及额外风险时。

</details>

<!-- enrichment: scenario-checks -->
<details>
<summary>相同输入下Workflow与Agent质量接近，该如何选？</summary>

在相同验收、预算下比较时延、成本、风险和维护复杂度，优先更简单且可验证的方案。

</details>

<details>
<summary>用户新增“顺便修改原文件”时能沿用只读授权吗？</summary>

不能；更新契约并绑定具体动作审批和资源权限，不能从原许可或模型文字推导写权限。

</details>
