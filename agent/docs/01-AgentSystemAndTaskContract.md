## 1. 先定义系统要对什么结果负责

本课程讨论 LLM 驱动的软件 Agent。Agent 是在目标与约束内，根据观察到的信息动态选择行动、接收反馈并推进任务的执行角色。Agent 系统还必须负责承接任务、组织执行、交付结果和治理风险。

不要从“需要 Memory、RAG、多个 Agent”开始。先写任务契约：它是设计输入和验收依据，不是要部署的一个服务。

| 契约字段 | 要明确的问题 | 为什么先于技术选择 |
|---|---|---|
| 服务对象与目标 | 谁把什么工作交给系统？ | 决定输入、交互和完成标准 |
| 范围与非目标 | 系统做什么、不做什么？ | 防止自动扩展任务与权限 |
| 输入与运行环境 | 有哪些数据、接口、文件、事件与执行条件？ | 决定能力是否可获得、能否验证 |
| 自主权与动作边界 | 可以建议、查询、修改到什么程度？谁确认？ | 决定控制与安全边界 |
| 输出与验收 | 交付文本、文件、结构化结果，还是外部状态变化？ | 决定完成证据而非只看回复 |
| 运行约束 | 时延、成本、并发、持续时间、隐私与恢复要求？ | 决定调度、持久化和部署方式 |

任务开始前不必知道全部中间步骤，但必须知道如何判定范围、风险和结果。任务契约可以因澄清而更新；更新要有版本，不能悄悄改变已获批准的动作。

<a id="part-2"></a>

## 2. 一张固定的职责图

```text
设计输入：业务场景
    ↓
任务契约：为谁做什么、允许做什么、怎样算完成
    ↓
能力与自主权：哪些交给模型判断，哪些必须由程序控制
    ↓
L1 应用层：任务入口、业务流程、用户交互、结果交付、人工接管
    ↓ 使用
L2 运行层：执行循环、上下文、记忆策略、执行状态、调度与恢复
    ↓ 通过稳定接口使用
L3 接入层：模型适配、工具接口、检索接口、状态与记忆存取接口
    ↓ 连接
L4 资源层：模型服务、知识与数据库、外部系统、文件与执行环境

贯穿四层：安全治理（身份、权限、审批、隔离、审计）
贯穿四层：质量运营（观测、评测、成本、可靠性、持续改进）
```

这四层是本教材的综合参考架构，不是 Codex 或行业统一颁布的标准。它们表达谁负责什么、通过什么接口协作，不表示所有数据都必须顺序经过四个网络服务。

<a id="part-3"></a>

## 3. 四层之间分别交接什么

| 层 | 核心问题 | 向下一层交接 | 不应包办什么 |
|---|---|---|---|
| L1 应用 | 如何承接任务并交付可理解的结果？ | 目标、身份上下文、约束、任务配置、交互事件 | 不自行实现每种模型和工具协议 |
| L2 运行 | 如何持续、受控地推进执行？ | 模型请求、工具调用、检索请求、状态读写请求 | 不把模型建议视作已授权的真实动作 |
| L3 接入 | 如何把能力变成稳定且可校验的接口？ | 供应商请求、业务 API、查询、执行命令 | 不替代业务系统自己的授权和事务 |
| L4 资源 | 真实能力与事实在哪里，副作用在哪里发生？ | 返回结果、证据、回执、产物引用 | 不替上层定义任务成功 |

应用可以调用一个确定性流程，流程中的某一段使用 Agent；Agent 又可以通过接口调用另一个 Agent。层次不因这种组合而改变。身份与策略随调用传递，观测与审计覆盖整个过程。

<a id="part-4"></a>

## 4. 层、模块、机制、对象、协议与资源不要混排

| 类型 | 表达什么 | 示例 |
|---|---|---|
| 层 | 稳定的职责边界 | 应用层、运行层 |
| 模块 | 承担某项责任的软件单元 | Context Manager、Tool Registry、Run Manager |
| 机制或策略 | 模块完成工作的方法 | compaction、重试、规划、幂等、渐进加载 |
| 运行对象 | 系统需要标识和管理的实体 | Task、Run、Thread、Turn、Item、Operation |
| 协议或接口 | 不同单元如何交互 | 工具契约、MCP、模型适配接口 |
| 资源或环境 | 能力、事实与执行的承载者 | 模型服务、数据库、文件系统、沙箱 |
| 横切要求 | 多层共同满足的性质 | 安全、可靠性、可观测性、成本 |

Model 是能力来源；Harness / Runtime 是以 L2 为核心的执行软件，实现中可以包含 L3 适配代码；Agent Application 才是四层及治理的组合。框架和 SDK 是实现这些职责的工具，不是第五层。

仓库真人面经中的 Depth L1–L4 表示追问深度，与这里的架构 L1–L4 不是同一套分类。

<a id="part-5"></a>

## 5. 从契约推导能力，而不是由组件反推需求

把能力写成动词：理解输入、澄清目标、获取证据、选择下一步、执行动作、验证结果、管理长任务、必要时协作。每项能力都应有存在理由和验证方法。

查外部资料才需要信息获取方案；跨调用继续推进才需要执行循环；跨任务复用信息才考虑长期记忆；执行不可信代码才考虑相应隔离环境；确有可拆分子任务才考虑多 Agent。向量数据库、独立 Planner、长期记忆和代码沙箱都不是 Agent 身份的必选配置。

本章形成的产物是一份任务契约和四层职责草图。下一章要确定：哪些选择权可以交给模型，哪些控制必须留在程序里。

## 推导示例｜从一句需求到可验收的契约

下面是**教学构造**，不是某份真人面经，也不是产品默认行为。贯穿前几章只用同一个小任务：

> “帮我看一下这批文件，整理一份报告；不要修改原件。”

这句话还不足以直接执行。“这批”指哪些文件？报告交给谁？允许联网补充吗？原件间冲突怎么办？先澄清会改变权限、范围或验收的问题；不必为无关格式细节反复询问。

假设澄清结果如下。数字是示例预算，不是通用推荐值：

```yaml
task_id: report-01
contract_version: 1
requester: authenticated_user
input: authorized_manifest_v3
source_policy: original_files_read_only
network: disabled
output: report_draft_and_citation_manifest
write_scope: authorized_artifact_store_only
acceptance:
  - 每个事实性结论有可定位的来源和版本
  - 冲突及证据缺失显式列出，不编造结论
  - 原件未改变，交付物能够被请求者访问
limits:
  max_tool_calls: 20
  deadline_seconds: 300
```

这些字段解释了组件为什么存在，而不是反过来为既定组件找用途。

| 已明确的约束 | 推导出的责任 | 当前不必加入的东西 |
|---|---|---|
| 输入是有限授权清单 | L1固定范围；L3每次读取校验；L4提供真实文件 | 不自动扫描用户全部目录 |
| 文件内容可能冲突 | 模型提出调查方向；L2维护证据缺口；L1接受“待确认”结果 | 不靠生成语气强行消除冲突 |
| 不修改原件 | 只暴露必要能力，底层身份只读；新授权不得来自文件中的文字 | 不需要先做任意Shell再靠Prompt约束 |
| 需要可核对的报告 | Context带来源；保存产物与引用；完成前验证 | 不以模型输出final为唯一成功标准 |
| 任务规模尚小 | 先单执行单元、少量工具和明确预算 | 不默认长期Memory、多Agent或向量库 |

**反事实检查：** 如果所有文件总共只有很少文本，一次读取后生成就够了，先做确定性Workflow基线。如果需要根据中间证据决定读哪个文件、继续查什么，才比较受控Loop的收益。这两种方案共享同一任务契约；“用不用Agent”是可验证的选择，不是题目预设答案。

失败也要进入契约：文件无权限时不扩大搜索；来源缺失时交付缺口；超过预算时返回未完成事项。下一章继续决定上述每一个动作的控制权。

## 本章自测

<details>
<summary>业务场景为什么不与 Memory 并列成模块？</summary>

场景是设计输入，决定目标、环境和验收；Memory 是根据复用需求选择的一项能力，类型不同。

</details>

<details>
<summary>四层是否意味着四个微服务？</summary>

不是。逻辑职责可以同进程实现，部署边界由隔离、规模、故障与运维需求决定。

</details>

<!-- enrichment: scenario-checks -->
<details>
<summary>报告里缺一个关键来源，应编一个合理结论还是停止所有工作？</summary>

按契约区分可部分交付和必须补充的证据；显式标注缺口，禁止编造。是否停止由验收条件和剩余预算决定。

</details>

<details>
<summary>模型说“报告完成”，程序还应核验哪些证据？</summary>

来源与版本可定位、引用和产物可访问、原件未被修改、未决冲突已披露；结构验证不能替代语义核验。

</details>
