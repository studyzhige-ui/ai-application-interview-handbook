### 1. Agent 和普通 LLM Application / Workflow 有什么区别？

<details>
<summary>参考答案</summary>

核心是主要控制路径由谁决定。工作流按程序预定义的阶段与分支推进，可以包含模型节点；Agent 允许模型根据观察动态选择行动。实际应用常混合：外围固定控制身份、提交和验收，中间授权有限探索。应根据质量收益、成本、风险和可验证性选型，而不是按步骤多少分类。

[回到第02章的完整讲解、面试表达与自测](../docs/02-WorkflowAutonomyAndRuntimeBoundary.md)。

</details>

### 2. 什么是 Agent Harness / Runtime？为什么 Model 外面还要这一层？

<details>
<summary>参考答案</summary>

Agent 的关键是允许模型依据中间观察动态选择后续行动，且这种选择受目标和约束限制。工具只是让动作能发生的一种方式；固定程序也能调用工具。要交付可靠系统，还需要程序负责执行、校验、停止和必要状态管理，但长期记忆、多 Agent 和代码沙箱不是身份必选项。

[回到第01章的完整讲解、面试表达与自测](../docs/01-AgentSystemAndResponsibilities.md)。

</details>

### 3. 一个 Minimal Agent Loop 怎么写？

<details>
<summary>参考答案</summary>

程序构造上下文并调用模型，分辨工具、澄清或完成候选。工具经过受控执行后形成观察，更新进展再请求下一次决策；完成候选经过任务验收后才能成功。循环还应有停止原因，不能把等待用户、预算耗尽和成功都当作同一种 done。

[回到第03章的完整讲解、面试表达与自测](../docs/03-AgentLoopAndExecutionScopes.md)。

</details>

### 4. Run / Turn / Step 怎么区分？

<details>
<summary>参考答案</summary>

我会先声明项目定义：Session 是会话，Run 是一次目标执行，Turn 可定义成一次决策反馈周期，Step 是内部操作。但 Codex 的 Turn 是一次用户请求及后续工作，可含多次模型调用，并使用 Item 表示类型化项目。应映射职责，不强制给所有产品套同一棵树。

[回到第03章的完整讲解、面试表达与自测](../docs/03-AgentLoopAndExecutionScopes.md)。

</details>

### 5. Runtime Message 和 Event 有什么区别？

<details>
<summary>参考答案</summary>

模型消息表达输入输出内容；运行事件还包括排队、授权、执行开始和检查点等程序事实。一个工具调用可能对应多个事件。用调用标识关联并发结果，而不是依赖文本或时间顺序；诊断事件也不必全部加入模型上下文。

[回到第03章的完整讲解、面试表达与自测](../docs/03-AgentLoopAndExecutionScopes.md)。

</details>

### 6. Agent 为什么会 Dead Loop？怎么防？

<details>
<summary>参考答案</summary>

结合最近动作签名、相同错误和实际进展，而不是禁止重复工具。分页有新数据可以继续；反复同查询无结果应计为无进展，要求换策略、澄清或停止。总时间和费用预算兜底，但不能只加大步数掩盖循环。

[回到第08章的完整讲解、面试表达与自测](../docs/08-PlanningGoalAndControl.md)。

</details>

### 7. Tool Calling 完整链路是什么？

<details>
<summary>参考答案</summary>

先由应用把工具的稳定身份和处理器加入注册目录，再为本次模型请求选择并序列化允许工具的说明。模型返回名字和参数后，路由器按身份找到处理器，经校验与授权后执行，最后规范化结果回填。MCP工具的处理器通常是一个远程调用代理，并不是把远端代码下载进模型。

[回到第05章的完整讲解、面试表达与自测](../docs/05-ToolRegistrationAndDiscovery.md)。

</details>

### 8. Tool schema 为什么不等于安全？

<details>
<summary>参考答案</summary>

结构校验检查字段和类型；语义校验检查业务含义，例如ID存在、行号范围合理；权限校验检查可信用户是否能对该对象执行动作。一个字符串ID可以完全符合Schema，却指向别人的文件。三种检查串联，不是后面的安全章节取代前面的参数检查。

[回到第04章的完整讲解、面试表达与自测](../docs/04-ToolContractAndValidation.md)。

</details>

### 9. Tool Result 应返回字符串还是结构化对象？

<details>
<summary>参考答案</summary>

优先把执行状态、可用内容、必要引用和错误类别分开。模型收到足够继续决策的安全摘要，宿主可以保留必要内部标识，完整大结果按权限存产物。不是所有结果都必须复杂JSON，也不应把原始堆栈和密钥一并回填。

[回到第04章的完整讲解、面试表达与自测](../docs/04-ToolContractAndValidation.md)。

</details>

### 10. Tool Failure 怎么分类？

<details>
<summary>参考答案</summary>

不是。可修复参数或业务信息不足，可以提供简短反馈让模型选择合法下一步；临时传输故障通常先由程序有限恢复；权限拒绝、取消和宿主故障由控制系统处理。必须区分模型、运行状态、用户界面与诊断通道，并脱敏，不能让模型拿内部堆栈无限重试。

[回到第06章的完整讲解、面试表达与自测](../docs/06-ToolExecutionAndFailure.md)。

</details>

### 11. 哪些 Tool 可以自动 Retry？

<details>
<summary>参考答案</summary>

这只说明请求层完成，工具结果契约未满足。程序应检查预期产物或业务状态，再把明确的失败或缺口回填；不能把HTTP200、退出码0与任务验收成功混在一起。也不应随意重复有副作用的动作来碰运气。

[回到第06章的完整讲解、面试表达与自测](../docs/06-ToolExecutionAndFailure.md)。

</details>

### 12. Tool 已成功但响应超时怎么办？

<details>
<summary>参考答案</summary>

外部成功与本地存档不是同一事务，仍有响应丢失或本地崩溃窗口。需要操作意图、下游幂等/查询以及回执来核对；不能只靠提高检查点频率，也不能每次重试换业务ID。

[回到第13章的完整讲解、面试表达与自测](../docs/13-CheckpointResumeAndRecovery.md)。

</details>

### 13. 为什么 Tool 需要 read-only / destructive / concurrency-safe metadata？

<details>
<summary>参考答案</summary>

这些元数据帮助程序按资源冲突、风险和中断能力安排执行，不是授权本身，也不会自动全部送给模型。只读仍可能泄密；是否并发看实际资源，不看async或工具名。

[回到第07章的完整讲解、面试表达与自测](../docs/07-ToolConcurrencyAndCancellation.md)。

</details>

### 14. 用户在 Tool 执行中发新消息怎么办？

<details>
<summary>参考答案</summary>

已发送请求通常不能原地插入。应用先接收输入，区分新任务、补充、约束变更或取消，再排队、在下一决策点追加，或中断。需要绑定目标执行身份，防止误送；已发生的副作用不会因为新消息自动撤销。

[回到第03章的完整讲解、面试表达与自测](../docs/03-AgentLoopAndExecutionScopes.md)。

</details>

### 15. Tool 很多时怎么处理？

<details>
<summary>参考答案</summary>

目录可能很大，而一次任务只需少量工具。先发现候选能节省上下文并降低歧义，但会引入漏召回和额外延迟；候选进入后模型才选择具体调用，执行时仍检查合法性。评估要分别看正确工具能否被找到、找到后能否正确选择，而非只看最终成功率。

[回到第05章的完整讲解、面试表达与自测](../docs/05-ToolRegistrationAndDiscovery.md)。

</details>

### 16. ReAct 是什么？和 Plan-and-Execute 区别？

<details>
<summary>参考答案</summary>

### 18. Agent Context 由什么组成？

<details>
<summary>参考答案</summary>

先区分来源与API载体：稳定指令、用户目标、选定历史、证据和工具结果形成本次消息视图，工具Schema与基础指令可能独立传入。日常保持历史次序并追加变化，权限/新鲜度检查和总预算先于发送；大结果外部化，超限才按策略压缩。不能把编排理解为每轮重新排序整个对话。

[回到第09章的完整讲解、面试表达与自测](../docs/09-ContextAssemblyAndCache.md)。

### 19. Prompt Engineering、Context Engineering、Harness Engineering 区别？

<details>
<summary>参考答案</summary>

Prompt Engineering（提示设计）调整指令和示例；Context Engineering（上下文工程）选择本次模型可见的全部相关信息；Harness Engineering（执行系统工程）还组织跨轮工具、状态、安全和恢复。三者有关联但不是同一个层级。

[回到第02章的完整讲解、面试表达与自测](../docs/02-WorkflowAutonomyAndRuntimeBoundary.md)。

</details>

### 20. Context Window 大了还需要 Compaction 吗？

<details>

### 22. Compaction 后怎么保证关键约束没丢？

<details>
<summary>参考答案</summary>

关键授权和操作回执不能只存在有损摘要中，程序独立保存必要状态。摘要检查目标、约束和待办，引用必须可解析；再做压缩前后继续执行和长任务回归。文字通顺和Token变少都不是正确性的充分证据。

### 23. Tool Result 太长怎么办？

<details>
<summary>参考答案</summary>

保存必要完整结果到有权限和保留策略的产物存储，模型只收到摘要、来源和相关片段，后续按需重读；可丢弃噪声才直接截断。接着检查输入总预算，而不是把所有日志反复附加或让摘要成为唯一证据。

[回到第09章的完整讲解、面试表达与自测](../docs/09-ContextAssemblyAndCache.md)。

</details>

### 24. Stale Context / Stale Memory 怎么处理？

<details>
<summary>参考答案</summary>

先查来源、范围与时间，区分真正冲突和不同场景。当前明确约束不能被旧偏好覆盖；错误记录应纠正并失效索引缓存，无法确定就澄清或回权威来源核对。不能仅按最新时间或者模型自评置信度自动决定。

### 25. Context、Memory、State、History 有什么区别？

<details>
<summary>参考答案</summary>

Context是本次模型输入，Memory是未来任务可复用的经过选择的信息，State是程序为了继续或停止需要知道的当前情况，History是发生过的交互。读完A但B待上传属于State，不是只要存起来都叫Memory。

[回到第12章的完整讲解、面试表达与自测](../docs/12-StateHistoryAndPersistence.md)。

</details>

### 28. Checkpoint 保存什么？

<details>
<summary>参考答案</summary>

检查点保存可继续的状态位置，不回滚外部世界。两点间的纯计算可重做；已知成功的写入凭可靠回执补齐；未知写入先靠稳定操作ID查询或按下游幂等契约重试。关键动作记录可以比检查点更细，没有可核对依据就承认未知并请人处理。

[回到第13章的完整讲解、面试表达与自测](../docs/13-CheckpointResumeAndRecovery.md)。

</details>

### 29. Resume 为什么不能只重放 messages？

<details>
<summary>参考答案</summary>

Resume恢复执行；Compaction缩减当前模型输入；Replay可能是用事件重建状态、重新请求模型或重做外部动作，三种风险不同。恢复可以使用摘要构建输入，但不能仅凭摘要决定是否重复写入。

### 31. Pause、Cancel、Fail 有什么区别？

<details>
<summary>参考答案</summary>

Pause（暂停）表示等待并可能恢复；Cancel（取消）是明确终止意图，要传播并核对在途动作；Fail（失败）表示没达到目标的错误状态，是否可重试由具体契约决定。不能因为循环退出就统一记completed。

### 32. Fork / Branch 需要决定哪些继承语义？

<details>

### 33. Permission、Approval、Sandbox 区别？

<details>
<summary>参考答案</summary>

它们回答不同问题：参数格式和业务含义正确，仍可能是当前身份不允许的动作；允许的高风险动作可能需要具体批准；执行环境再限制代码实际可触及的范围。多道门不是重复检查，也不能彼此替代。

[回到第14章的完整讲解、面试表达与自测](../docs/14-PermissionApprovalAndSandbox.md)。

### 34. HITL 为什么不是一个 confirm 弹窗？

<details>

<details>
<summary>参考答案</summary>

模型输入可能被输出、工具或日志复制，也会受注入影响。凭证应尽量由受控工具代持，绑定范围和身份；只把业务参数交给模型。环境变量同样可能被Shell读取，不能当成绝对安全。

[回到第15章的完整讲解、面试表达与自测](../docs/15-InjectionAndContainment.md)。

</details>

### 38. 怎样限制 Agent blast radius？

<details>
<summary>参考答案</summary>

它们回答不同问题：参数格式和业务含义正确，仍可能是当前身份不允许的动作；允许的高风险动作可能需要具体批准；执行环境再限制代码实际可触及的范围。多道门不是重复检查，也不能彼此替代。

[回到第14章的完整讲解、面试表达与自测](../docs/14-PermissionApprovalAndSandbox.md)。

</details>

### 39. MCP 是什么？解决什么？

<details>
<summary>参考答案</summary>

MCP是连接AI应用与外部系统的开放协议标准，定义能力发现、工具调用、资源读取和提示模板等交互。它减少重复接入代码，不规定Agent怎么规划，也不自动提供业务授权。Host仍负责把协议能力接到模型与执行循环。

[回到第16章的完整讲解、面试表达与自测](../docs/16-MCPArchitectureAndLifecycle.md)。

</details>

### 40. MCP Tool、Resource、Prompt 怎么区分？

<details>
<summary>参考答案</summary>

Tools暴露可请求执行的能力，Resources提供可读取上下文，Prompts提供交互模板。Host通过各自协议方法发现和获取，再决定如何使用；不是全部都自动加入System Prompt，也不是Tool一定有副作用。

[回到第16章的完整讲解、面试表达与自测](../docs/16-MCPArchitectureAndLifecycle.md)。

</details>

### 41. MCP 和 A2A 区别？

<details>
<summary>参考答案</summary>

MCP主要标准化AI应用到工具、资源和模板的能力接入；A2A主要标准化独立Agent系统间的任务委派和产物交付。都有异步或长任务可能，不要用是否能返回Task作绝对区分。内部子Agent也可以不用两者。

[回到第18章的完整讲解、面试表达与自测](../docs/19-MultiAgentAndA2A.md)。

</details>

### 42. Tool、Skill、MCP、Command 有什么区别？

<details>
<summary>参考答案</summary>

Tool是动作接口，Skill是如何完成任务的指引/资源包，MCP是外部能力连接协议，Command（命令入口）通常由用户显式触发应用行为。它们可以组合，不能按名字互相等同。

[回到第16章的完整讲解、面试表达与自测](../docs/16-MCPArchitectureAndLifecycle.md)。

</details>

### 43. Hook / Plugin 在 Runtime 里怎么定位？

<details>
<summary>参考答案</summary>

Hook是在运行生命周期事件触发的扩展处理，Plugin是可打包交付工具、技能或钩子等的载体。可选Hook失效不能使核心权限门消失，升级应核对影响契约的变化。

[回到第16章的完整讲解、面试表达与自测](../docs/16-MCPArchitectureAndLifecycle.md)。

</details>

### 44. Intent Routing 怎么实现？

<details>
<summary>参考答案</summary>

入口意图路由选择业务流程，模型路由选择满足能力与质量约束的模型，能力路由把请求分发到工具处理器。它们输入、输出和风险不同，应分别评估，不用一个LLM分类节点包办所有责任。

[回到第17章的完整讲解、面试表达与自测](../docs/18-RoutingAndProviderResilience.md)。

</details>

### 45. Model Routing 看哪些因素？

<details>
<summary>参考答案</summary>

先分类错误并限制重试和总时限，选择满足工具、上下文和输出契约的后备，保留现有历史与已执行动作。不能只换model name，也不能重跑整个任务。降级需可见并用回归任务确认质量边界。

[回到第17章的完整讲解、面试表达与自测](../docs/18-RoutingAndProviderResilience.md)。

</details>

### 46. Multi-Agent 什么时候值得？

<details>
<summary>参考答案</summary>

当子任务独立、可并行、上下文可隔离且结果可验证时，分工可能有收益；还需计算Token、协调、错误和汇聚成本。强依赖同一工作区、反复互等时，单Agent或简单工具并行可能更好，应与基线比较。

[回到第18章的完整讲解、面试表达与自测](../docs/19-MultiAgentAndA2A.md)。

</details>

### 47. Manager、Agent-as-Tool、Handoff 区别？

<details>
<summary>参考答案</summary>

Agent-as-Tool通常保留父级控制，子任务返回结果后父级继续；Handoff把当前处理权交给另一个Agent。Manager/Worker还要负责多任务调度和最终验收。它们是控制关系，不自动决定通信协议或部署进程。

[回到第18章的完整讲解、面试表达与自测](../docs/19-MultiAgentAndA2A.md)。

</details>

### 48. 多 Agent 同时修改 Repo 怎么办？

<details>
<summary>参考答案</summary>

分开Context只隔离信息，不隔离资源。应明确写入所有权，采用单写者、独立工作区或版本检查加合并验证。结果汇聚验证来源与冲突，而不是把两个答案拼起来当成功。

[回到第18章的完整讲解、面试表达与自测](../docs/19-MultiAgentAndA2A.md)。

</details>

### 49. A2A 需要哪些关键语义？

<details>
<summary>参考答案</summary>

先用Agent Card发现能力、接口版本和认证，发送消息发起或继续工作，简单请求可直接回Message，长任务用Task跟踪状态与Artifact。调用方查询、订阅或补充输入，最终独立验收；取消需确认终态，不等于外部动作回滚。协议不规定远端内部Loop。

[回到第18章的完整讲解、面试表达与自测](../docs/19-MultiAgentAndA2A.md)。

</details>

### 50. Agent Trace 应记录什么？

<details>
<summary>参考答案</summary>

先记录能定位阶段和关联调用的ID、耗时、状态、错误类别及必要引用，按问题决定是否增加授权的脱敏输入快照。关键业务回执和恢复状态单独可靠保存。全量Trace有成本、隐私与噪声，也不能保证精确重演模型或外部世界。

[回到第19章的完整讲解、面试表达与自测](../docs/20-TraceReplayAndDiagnosis.md)。

</details>

### 51. Replay 时为什么不能直接重执行所有 Tool？

<details>
<summary>参考答案</summary>

应先说明Replay指状态重建、证据回看、模型重演还是外部动作重放。前两者通常不执行真实工具，模型重演应隔离下游；外部动作需独立授权、幂等和核对，不能凭历史调用直接再做。

[回到第19章的完整讲解、面试表达与自测](../docs/20-TraceReplayAndDiagnosis.md)。

</details>

### 52. Agent Eval 和普通 LLM Eval 有什么不同？

<details>
<summary>参考答案</summary>

除了最终文本，还要检查行动过程、工具选择与参数、环境产物、恢复和安全预算。可确定性验证的优先用程序检查，开放语义再用校准Judge或人工；结果不以模型自称完成为准。

[回到第20章的完整讲解、面试表达与自测](../docs/21-EvaluationBenchmarkAndImprovement.md)。

</details>

### 53. LLM Judge 可以作为唯一 Agent Grader 吗？

<details>
<summary>参考答案</summary>

通常不合适。它对开放语义有价值，但可能偏好风格、受提示和模型影响；文件、测试、权限与实际副作用应由相应程序或环境证据验证，Judge需和人工校准并报告局限。

[回到第20章的完整讲解、面试表达与自测](../docs/21-EvaluationBenchmarkAndImprovement.md)。

</details>

### 54. Coding Agent 怎样证明 Patch 可交付？

<details>
<summary>参考答案</summary>

先定位需求与失败条件，读真实仓库和调用路径，做最小修改，运行相关测试及必要构建/类型检查，再审查Diff与用户已有修改。交付时列出实际验证和未验证范围，不能只看代码语法或模型自评。

[回到第21章的完整讲解、面试表达与自测](../docs/22-CodingAgentDelivery.md)。

</details>

### 55. Production Agent Runtime 怎么拆？

<details>
<summary>参考答案</summary>

从任务时长、恢复、并发和权限承诺出发，分清入口交互、可靠任务状态、Worker循环、模型/工具接入、执行环境与产物。长任务用任务ID和独立进度查询；关键副作用有核对依据；容量按模型、工具和存储分别控制。不是一开始把所有责任拆微服务。

[回到第22章的完整讲解、面试表达与自测](../docs/23-ProductionRuntime.md)。

</details>

### 56. LangGraph / Agents SDK / 自研 Loop 怎么选？

<details>
<summary>参考答案</summary>

先定义任务状态、控制流、工具、人工参与、恢复和部署要求。Agents SDK以Agent与Runner循环为核心，LangGraph显式管理状态图与检查点，LangChain当前create_agent提供基于LangGraph的高层集成。自研适合范围小或特殊控制，但要承担可靠性。用相同任务和故障验证比较，而不是按热度选。

[回到第23章的完整讲解、面试表达与自测](../docs/24-FrameworkSelection.md)。

</details>
