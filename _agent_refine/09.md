# 09. 上下文编排：模型这一刻到底收到什么

程序已经保存“读完 A，B 无权限”，模型却仍然要求从头读 A。问题未必是模型忘性大，也可能是这些信息根本没有进入这一次请求。

上下文编排，就是从已有信息中选择本次需要的部分，按模型接口组织成可用输入。先看真实发送什么，再讨论预算、缓存和裁剪。

## 1. 保存的信息，不等于模型已经知道

**Context（上下文）**是本次模型可用的输入。**State（状态）**是程序推进工作需要的当前情况；**History（历史）**是已经发生的交互记录；**Memory（记忆）**是为以后复用而维护的信息。

例如“A 已读”是进度状态，读取内容可以留在历史，用户“报告先写结论”的偏好可以成为记忆。它们只有被本次请求提供，或通过本次可调用能力取得，才会影响模型判断。

因此，持久保存一万条消息，不意味着每次都应该发送一万条；保存用户偏好，也不意味着把所有人的偏好放进当前输入。

## 2. 跟着三次请求观察输入增长

下面 P 是稳定指令，T 是当前工具说明；U 是用户消息，A 是模型消息，R 是对应工具结果。它是消息关系示意，不是某家 API 的完整请求体。

```text
请求 1：P + T + [U1：读取 A/B，核对日期并整理报告]
模型 A1：read_document(A)，调用标识 c1
工具 R1：A 的内容及来源，关联 c1

请求 2：P + T + [U1, A1, R1]
模型 A2：read_document(B)，调用标识 c2
工具 R2：无权限，关联 c2

请求 3：P + T + [U1, A1, R1, A2, R2]
模型 A3：说明 B 受阻，请求用户补充资料
```

第三次请求之所以能处理 B 受阻，是因为模型收到了 R2。若程序吞掉 R2，模型就可能误以为仍在等待，或再次请求同一工具。

信息来源与 API 载体不同：工具说明可能在 `tools` 参数，基础指令可能独立传入，消息则放在 `input` 或 `messages`。**不在 messages 里，不代表不占模型输入预算。** 要核对实际 API 的编码和计量方式。

## 3. 怎样从多个来源选择本次内容

常见来源包括指令、用户请求、近期历史、目标与计划、相关记忆、检索证据、工具说明、工具结果和环境信息。不是每次都要齐备，而是看它是否影响当前决策。

可以按下面顺序处理：

1. 核对身份和权限，排除本任务不能使用的材料。
2. 区分当前约束、已确认事实和未验证猜测，不能给它们相同权重。
3. 检查来源与版本，刷新会影响当前动作的陈旧信息。
4. 去掉重复证据，选择足以支持下一步的片段。
5. 检查总预算，编码成符合供应商协议的输入。

这个过程有时叫 Context Compiler（上下文编译器），强调有规则的选择和转换，并不是必须另写一个编译器框架。小系统用清楚的函数也可以完成。

去重应保留来源关系。两个独立来源报告同一事实，可能是交叉验证；同一个工具结果被历史、记忆和检索三次注入，则可能只是重复。不能仅凭文字相同就删除来源差异。

## 4. 当前计划变化，不代表每次重排历史

计划由 P1 改为 P2，可以通过新消息或更新计划的工具调用告知模型，同时更新宿主当前视图。旧历史里存在 P1 不必自动删除，但要明确 P2 才是当前安排。

编排不是每次重新排序所有消息。工具调用和结果应保持对应关系，不能为了把新计划放最前面，留下无对应请求的工具结果。某些 API 还有额外的消息顺序要求，要按接口检查。

文件更新也类似：原历史记录了读到 A:v1，重新读取以后追加 A:v2 及旧版已失效说明。历史记录可以解释过去发生什么，当前动作却应该使用适用的新版本。

## 5. 预算是为下一步留下空间

假设教学模型窗口按输入与输出合计 128k 计算：

| 用途 | 教学预算 |
|---|---:|
| 指令 | 8k |
| 目标与状态 | 6k |
| 近期历史 | 20k |
| 记忆与检索证据 | 24k |
| 工具说明 | 14k |
| 工具结果 | 28k |
| 输入小计 | 100k |
| 输出预留 | 20k |
| 安全余量 | 8k |
| 合计 | 128k |

这些不是产品推荐默认值。不同模型对窗口和输出上限的规则不同；工具返回新内容以后，也要重新计算下一次请求，而不是认为一次分区就永远够用。

软预算用于安排取舍，最终仍以实际请求计量为准。资料较多时可以缩小读取范围，先保留当前目标、禁止事项和决策关键证据。不能为了填满某个类别配额，把用户关键约束挤掉。

## 6. 大结果外部化，要留下可取回路径

测试产生三万行日志，直接全部回填会挤占预算；只保留前五千字符，又可能删掉末尾真正的错误。

**Offloading（结果外部化）**是把完整必要结果保存在受控存储，模型输入保留摘要、相关片段和引用。需要更多信息时，再按范围读取或搜索。这与不可逆截断不同。

```text
完整测试日志 → 按权限和期限保存为 log7
                    ↓
模型输入：失败摘要 + 关键断言 + log7 引用
                    ↓
仍需证据 → 读取 log7 的相关区段
```

引用必须能够解析，读取仍要校验权限。把全文丢进诊断 Trace，不自动等于做了可回读的产物库。可以丢弃的噪声也不必永久保存，保存范围由任务和验证需要决定。

## 7. 前缀缓存省计算，不替你保存事实

模型前缀缓存复用重复输入的部分计算，不是直接返回以前的答案。[OpenAI 的前缀缓存文档](https://developers.openai.com/api/docs/guides/prompt-caching)说明了相同前缀与缓存的关系；具体命中条件应按供应商核对。

尾部追加消息有利于保留不变前缀，但不是命中保证。模型、工具序列化、指令、缓存有效期和路由都可能影响复用。工具 Schema 缓存、应用回答缓存与模型前缀缓存也不是同一个对象。

如果计划更新只是追加一次工具调用，前面字节可能仍相同；若每轮把最新计划插到开头，则可能改变后面大片前缀。**这只影响复用机会，不应决定哪条事实正确。** 必要的授权、文件和指令更新不能为了缓存被忽略。

## 本章小结

上下文是程序为本次模型请求选择的输入，不是全部存储。先检查权限、时效与信息价值，再维护调用关联和总预算；大结果可回读，缓存只复用计算，不能保留错误事实。

## 🎯 面试怎么回答

### Agent 上下文怎样组装？

先区分信息来源和 API 载体，选择当前目标、约束、相关历史、证据与工具说明；检查权限、新鲜度和重复，再计量预算并按协议发送。宿主状态不自动变成模型输入。

### 工具结果过大怎么办？

先缩小读取范围；必要完整结果存入可授权回读的产物，输入中保留摘要、引用和关键片段。可丢弃噪声可以截断，但不要不可逆删除后续验证需要的证据。

### 计划更新怎样影响缓存？

取决于请求怎样变化。尾部追加可以保留旧前缀，重写前部可能降低复用；缓存还有模型和服务端条件。当前计划正确性优先，不能为了命中保留过期信息。

## ⚠️ 易错点

> ⚠️ 数据存在于数据库或记忆里，不意味着模型本次已经知道。

> ⚠️ 重复事实不一定来自独立证据，去重时要保留真实来源关系。

> ⚠️ 前缀缓存不是回答缓存，命中也不保证引用、权限或答案正确。

<details><summary>1. 程序记录 B 无权限，但没有把这个结果放入下一次请求，模型可能怎样误判？</summary>

它可能仍认为 B 未读取、尚在等待或可以继续请求。必须提供足以影响下一步的观察，同时由程序继续落实权限。

</details>

<details><summary>2. 128k 表里输入为 100k、输出预留 20k，剩余多少？</summary>

8k。合计 128k；这只是给定窗口口径下的算例，不是所有模型的默认配置。

</details>

<details><summary>3. 为了提高缓存命中，继续使用已失效的 A:v1，可以吗？</summary>

不可以。应取得适用版本并明确旧信息失效。缓存是成本优化，不是事实选择规则。

</details>

<details><summary>4. 日志末尾才有失败断言，应该只截取前 5000 字符吗？</summary>

不宜不可逆截断。保存必要日志，提供失败摘要和可读取引用，再按需取关键区段。

</details>
