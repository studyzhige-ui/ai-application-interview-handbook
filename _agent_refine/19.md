# 19. 多 Agent 协作：交出去的是任务，不是全部控制权

一份报告需要查资料和检查引用。让两个助手分别处理，可能更快；但如果两者同时改同一个文件，或者都认为自己负责发送报告，就可能得到互相覆盖的修改和重复发送。

多 Agent 的起点是明确分工、输入、交付与责任。先把这些关系讲清，再决定是否并行、怎样通信。

## 1. 什么时候值得拆成多个 Agent

查不同来源、研究相对独立的问题、用不同权限或独立上下文检查结果，都可能适合分工。一个五步线性任务，每步都依赖前一步，拆成五个 Agent 却可能只是多了五次交接。

以报告为例：资料助手检查事实，引用助手检查来源位置，主助手负责整合与最终验收。收益是可以独立推进部分工作，代价是任务说明、上下文传递、结果核对和失败处理都要增加。

应与单 Agent 或普通工具并行比较：子任务是否独立，结果是否可检查，并行节省的时间是否足以覆盖额外模型调用与协调。不能只凭任务“复杂”就增加角色。[Anthropic 的多 Agent 研究系统文章](https://www.anthropic.com/engineering/multi-agent-research-system)也把并行探索与额外成本一起讨论。

## 2. 委派以后，谁继续接用户的任务

| 控制方式 | 工作怎样交出去 | 谁负责继续 |
|---|---|---|
| Agent as Tool（子 Agent 作为工具） | 父级给一个子任务，等待返回结果 | 父级继续原任务 |
| Handoff（控制权交接） | 当前处理权转给另一角色 | 新角色承接后续交互 |
| Manager / Worker（协调者与工作者） | 协调者安排多个子任务并汇总 | 协调者负责总体交付 |

它们不是不同数量的聊天机器人，而是不同控制关系。调用一个审查助手并拿回意见，与把用户接下来的对话交给客服专家，不是同一个操作。

每个子任务至少要能说清负责人、目标、允许范围、输入、预算与输出要求。这里的负责人是程序管理的任务归属，不是让模型各自声明“我是总负责人”。

## 3. 传递足够的信息，不复制整个会话

引用助手通常需要待核查报告、相关资料引用、允许读取范围和检查标准，不需要主助手全部历史，更不需要数据库密码。

```text
父任务：交付已核实报告
    ↓ 委派
子任务：核查报告 v3 的引用
输入：报告 v3、允许材料 A/B、引用规则
输出：有效引用、缺失位置、检查范围和未决项
    ↓ 返回
父级核对结果，决定修订、补充或交付
```

上下文隔离可以减少无关内容和信息泄露，却不能隔离实际资源。两个助手拿到不同消息，仍可能同时写同一个文件。

因此还要区分**任务所有权**和**工作区写入权**。研究者可以并行给建议，由一个整合者真正修改文件；也可以各用独立工作目录，再检查基线、合并差异并测试。

> ⚠️ Git 分支名称不同，不代表两个进程已经拥有独立文件系统。共享同一工作目录时切分支仍会互相影响；需要独立 checkout 或 worktree 等实际工作区隔离。

## 4. 共享资源、部分失败与无限委派

如果 A 修改文件，B 基于旧版本生成补丁，合并前要检查适用基线。即使 Git 没有文本冲突，两份修改也可能在行为上互相矛盾，仍需验收与测试。共享任务状态同样需要单写者、排队或版本检查，不能随意覆盖一个 JSON。

假设三个子任务中 A 成功、B 超时、C 返回没有来源的结论：保留 A 的有效结果，对 B 判断是否能有限重试，对 C 要求补证据或拒绝使用。只有任务允许缺少这些部分时，才可明确部分交付，不能把拼接后的文字当完整结果。

递归委派也有成本。父级每次派五个子任务，子级再各派五个，很快放大到几十上百个调用。应限制总预算、委派深度和同时活动数量，并检查 A 等 B、B 又等 A 的循环等待。

父任务取消时，要通知仍由它负责的子工作，核对迟到结果并停止后续动作。子任务失败不自动等于父任务失败，是否继续由任务验收与剩余资源决定。

## 5. A2A 解决独立系统之间的交付协议

一个进程里的子 Agent 可以直接用函数或框架对象通信。独立组织或不同框架的 Agent 系统协作，则可能需要共同协议，而不必了解对方内部提示词和工具实现。

**A2A（Agent2Agent）**标准化能力发现、消息、任务状态与产物等交互。本节依据官方 **1.0.0 发布规范**；协议字段中的版本表达和具体 SDK 支持，应分别按官方绑定核对。

| 协议对象 | 主要用途 | 引用审查例子 |
|---|---|---|
| Agent Card | 声明能力、接口与认证要求 | 哪个服务提供引用检查 |
| Message | 交换带类型的任务内容 | 报告与核查要求 |
| Task | 跟踪尚未结束的工作 | 审查任务标识及状态 |
| Artifact | 表达交付产物 | 审查表或修订建议 |
| Context 标识 | 关联后续交互 | 补充材料仍属于原审查 |

一次调用可以这样发生：

```text
发现并核对 Agent Card、接口版本与认证
→ SendMessage 提交目标和必要材料
→ 简单请求直接返回 Message；长工作返回 Task
→ 按支持能力查询 GetTask 或接收流式更新
→ 需要输入时补充并关联原任务
→ 取得 Artifact，调用方独立验收
→ 需要取消时请求 CancelTask，再确认实际结果
```

方法名和传输表示按 1.0 的具体绑定使用，不能把旧版 JSON-RPC `message/send` 不标版本地混进来。流式更新和推送是需确认支持的能力。断线后先查询已有任务，不要直接创建另一份重复委派。[A2A 官方规范](https://a2a-protocol.org/latest/specification/)说明了这些对象和操作。

Agent Card 不是认证凭证，远端返回 completed 也不等于满足调用方全部验收；取消远端任务更不保证回滚已经发生的动作。

## 6. A2A、MCP 与内部协作怎样选择

| 比较点 | MCP | A2A |
|---|---|---|
| 常见公共接口 | 调用工具、读取资源、获取模板 | 把工作交给独立 Agent 系统 |
| 调用者主要关心 | 能力参数与结果 | 目标、状态、补充输入与产物 |
| 是否规定内部 Agent 循环 | 不规定 | 不规定远端内部实现 |
| 是否只能同步返回 | 不是，需按版本和扩展核对 | 不是，可直接消息或跟踪任务 |

可以用 MCP 工具封装 A2A 委派，A2A 服务内部也可以使用 MCP。选择取决于公共接口与责任边界，不是看到多个 Agent 就必须上 A2A，也不是用“一个同步、一个异步”简单区分。

## 本章小结

多 Agent 增加的是分工与交接责任。控制权、输入范围、资源写入权和最终验收需要分别明确；部分失败与总预算不能忽略。A2A 用于独立系统互操作，不代替内部调度或业务授权。

## 🎯 面试怎么回答

### 多 Agent 什么时候有价值？

子任务相对独立、可并行、上下文能够隔离且结果可验证时，分工可能有收益。还要与单 Agent 比较成本、协调、共享资源和失败处理，不能因任务复杂就默认拆分。

### Handoff 与 Agent as Tool 有什么区别？

后者把子工作结果返回父级，父级继续；Handoff 转移当前处理权，需要明确后续用户消息和状态由谁承接。它们是控制关系，不自动决定部署或通信协议。

### 多个 Agent 同时改文件怎么办？

先明确写入权，可用单整合者或独立工作区；并发补丁检查基线并验证合并结果。上下文隔离和不同分支名称本身不能保证文件隔离。

### A2A 与 MCP 怎样区分？

MCP 侧重应用接入能力、资源和模板，A2A 侧重独立 Agent 系统的任务委派与产物交互。它们可以组合，都不规定完整内部循环，也不能用是否支持长任务作绝对区别。

## ⚠️ 易错点

> ⚠️ 子任务成功只证明局部要求，父级还要检查缺口、冲突、来源和总体验收。

> ⚠️ 独立上下文不等于独立工作区，文本合并无冲突也不等于行为兼容。

> ⚠️ 能力卡片与任务状态是声明和协议对象，真实认证、授权与产物质量需另外核对。

## 本章自测

<details><summary>1. 五步任务每步强依赖前一步，拆成五个 Agent 一定更快吗？</summary>

不一定。没有可利用的并行性，却增加上下文传递和交接成本，应与简单循环比较。

</details>

<details><summary>2. A 成功、B 超时、C 无证据，主助手应该直接拼接三个回答吗？</summary>

不应。保留 A 的有效产物，按预算处理 B，要求 C 补证据或拒绝使用；不能完成全部验收时明确缺口。

</details>

<details><summary>3. 两个进程在同一目录里使用不同分支名，是否已隔离修改？</summary>

没有。工作目录仍共享，切换分支也可能影响对方。需要独立 checkout/worktree 或明确单写者。

</details>

<details><summary>4. A2A 流断开后，为什么先查询原 taskId 而不是重新委派？</summary>

远端工作可能仍在执行或已经完成，重新委派可能重复动作。应关联原任务取得状态与产物，再判断下一步。

</details>
