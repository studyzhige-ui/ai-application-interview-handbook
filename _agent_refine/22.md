# 22. Coding Agent：从理解仓库到交付可验证修改

用户说“重试时会创建两份报告，请修复”。模型很快生成了一段看起来合理的补丁，但它改的函数并不在真实调用路径上。单元测试通过，线上问题仍然存在。

代码任务的难点，不只有生成代码，还包括找对位置、保护现有工作、验证真正的需求和清楚交付。

## 1. 先确认任务，再缩小阅读范围

从错误现象、期望行为和当前仓库出发。先看入口与目录，搜索具体错误、符号或配置，再沿调用方与测试确认改动位置。不要一开始把整个仓库塞进模型输入。

| 方法 | 适合回答 | 不能自动保证 |
|---|---|---|
| 目录与配置阅读 | 项目怎样组织、怎样构建测试 | 已理解业务调用链 |
| 文本搜索，例如 ripgrep | 哪些位置出现符号或错误文字 | 同名函数就是实际执行位置 |
| AST（抽象语法树） | 代码的语法结构 | 任意运行行为和动态调用都能解析 |
| LSP（语言服务器协议）能力 | 定义、引用、类型等语言工具信息 | 所有语言或配置都支持完整结果 |
| 语义检索 | 不知道关键词时寻找可能相关实现 | 检索相似就代表应该修改 |
| 依赖与调用关系 | 修改可能影响哪些调用者 | 已覆盖全部动态依赖 |

它们是互补工具，不是“文本搜索落后、向量检索先进”的排序。报告重复创建问题可以先搜创建入口和重试包装，读调用方、操作 ID 的生成位置，再看是否有失败恢复测试。

## 2. 修改之前，先保护工作区

程序需要知道基线提交、当前分支、已修改和未跟踪文件，以及相关进程是否还在运行。用户已经写了一半的内容，不能被当作“脏数据”清掉。

模型读到 A 版本后生成补丁，文件可能被另一个人改成 B。应用补丁时要检查基线或匹配上下文，冲突则重新阅读、协调，不能直接覆盖。

独立 worktree、单写者或明确的变更所有权，可以降低并发风险；只创建不同分支名而共享同一目录并不构成隔离。[多 Agent 协作](19-MultiAgentAndA2A.md)解释这些控制关系。

**补丁应该是足以解决任务的最小完整修改。** “最小”不是只改一行，而是不顺便重构无关模块，不为了让差异小而遗漏调用方与必要测试。

## 3. 先能暴露错误，再证明改对

对于重复创建报告，可以用受控下游模拟第一次已创建、响应丢失的窗口，验证重试是否沿用同一逻辑操作。测试应能够在旧实现中暴露问题，再在修订后通过。

| 证据 | 说明什么 | 仍需注意 |
|---|---|---|
| 原实现复现故障 | 测试确实命中问题 | 环境应与任务条件相关 |
| 新实现通过回归用例 | 这个条件下行为改善 | 不代表所有路径都正确 |
| 相关原有测试通过 | 已覆盖行为未发现退化 | 测试可能遗漏调用者 |
| 差异和调用链审查 | 改动范围与需求一致 | 仍不能代替必要集成运行 |

选择验证由便宜到较昂贵：语法或编译、类型与静态检查、针对性测试、相关测试集，再按风险增加集成或端到端测试。不是每次都跑全部系统，也不能只跑一个无关测试就宣布完成。

> ⚠️ 没有网络、依赖或数据库导致测试没运行，应记为环境或未验证项，不写成“全部通过”。

## 4. 测试失败时，先分类而不是一律改到绿

失败可能来自原有缺陷、新补丁、偶发不稳定、环境缺失或合法需求变化。先比较基线与修改后的条件，确认错误究竟在哪。

删除断言、放宽权限或硬编码结果可以让测试变绿，却破坏任务。若需求确实改变，应说明为什么旧期望不再成立，并新增覆盖新要求的验证，而不是为了通过而改答案。

同样，模型不应该反复随机改代码。每次变更应关联一个可检验假设，例如“重试包装每次生成了新的业务操作 ID”，再通过具体调用和结果验证它。

## 5. 差异审查检查测试没有说明的内容

测试通过后，仍要检查实际 diff：是否改到了正确调用路径，是否出现无关删除、泄露凭证、放宽验证、修改用户原有工作，或者只修补表面症状。

```text
读任务与当前仓库
→ 定位调用链与失败条件
→ 在适用基线上作必要修改
→ 运行针对性验证与相关回归
→ 审查差异、范围和安全
→ 对照任务验收并交付
```

测试结果和差异是两类证据，不能互相取代。代码修复任务通常需要实际差异，但调查任务也可能得出无需修改的结论；不能为了制造 diff 而修改正确代码。

测试命令也是代码执行，要有工作区、网络、凭证和时间边界。仓库里的测试脚本不因叫测试就天然可信，不能默认接生产数据库。

## 6. 交付不是一句“已修复”

交付时说明改变了哪些文件、验证了哪些条件、还有哪些未验证项，并提供实际提交或补丁。创建 Git 对象、创建分支、打开 PR、合并以及远端 main 回读，是不同状态。

用户要求合并时，发布前重新检查 main 和同期修改；合并后核对远端结果。没有合并权限或验证被阻断，应如实报告实际停在哪，而不是把 PR 链接当成已经发布。

回退也要按本次拥有的范围进行。Git 回退不会撤销已经执行的数据库迁移或外部请求，更不能用 `reset --hard` 抹掉用户不属于本任务的修改。

[SWE-bench](https://www.swebench.com/)提供的一个重要启发，是在真实仓库和测试条件中验证修改结果。它不是“补丁看起来对”的文字评价，也不保证通过某个基准就能直接用于任意企业项目。

## 本章小结

Coding Agent 的交付依赖真实仓库理解、受控修改、针对性验证与差异审查。保护用户工作，区分代码错误与环境问题；发布和回退都以实际状态为准，不以自然语言自述代替证据。

## 🎯 面试怎么回答

### AI Coding 怎样保证质量？

先明确任务与基线，沿目录、搜索、调用关系和测试定位；作最小完整修改，运行相关验证并审查 diff、影响和安全。最后按需求验收，说明未验证范围，而不是只相信模型生成或测试变绿。

### 仓库理解为什么不能只靠向量检索？

语义检索适合寻找可能相关实现，精确符号、类型、调用关系和构建配置还需要文本与语言工具。相似代码不一定在真实执行路径上，应把检索候选落实到调用和测试证据。

### 测试没通过，为什么不能一直让模型改？

要区分原有失败、新回归、环境问题和合法需求变化。每次修改应验证具体原因，不能删断言或硬编码让它变绿；环境缺失也不能当作代码必错。

## ⚠️ 易错点

> ⚠️ 搜到相似函数不等于找到真实调用方，应确认入口和相关测试。

> ⚠️ 自动合并无文本冲突不代表行为兼容，合并后的结果仍需验证。

> ⚠️ 创建 PR 不等于合并到 main，Git 回退也不等于撤销外部副作用。
