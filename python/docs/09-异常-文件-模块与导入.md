# 09. 异常、文件、模块与导入

[← 上一章：对象与协议](08-面向对象-魔术方法.md) · [模块主页](../README.md) · [下一章：结构化数据校验 →](10-结构化数据-JSON与校验.md)

程序不只存在“算出正确结果”这一条路径。输入可能不合法，文件可能不存在，模块初始化也可能失败。本章把三个问题接起来：**错误怎样传播，资源怎样收尾，代码怎样按模块组织**。

```text
先区分正常返回与异常
→ 在有能力处理的边界捕获
→ 不能处理时保留原因并向外传播
→ 用明确生命周期读写文件
→ 再理解模块加载与初始化为什么也会失败
```

## 1. 异常：从发生位置向外寻找处理者

### 1.1 报错信息不是一段随意的字符串

```python
text = "20"                  # 外部输入先是一段字符串
age = int(text)              # 转为整数；如果 text 是 'abc' 就不能完成转换
print(age + 1)               # 21
```

当 `int("abc")` 无法转换时，会抛出 `ValueError（值错误）`。如果当前位置没有处理代码，异常会沿函数调用关系向外传播；最终无人处理时，这次执行会显示异常类型、消息与 **Traceback（回溯）**。

异常类型说明错误属于哪一类；消息描述当前情况；回溯帮助定位经过哪些调用。只留下一个 `"failed"` 字符串，会丢掉这些不同层次的信息。

### 1.2 try、except、else、finally 分别放什么

```python
text = "20"                  # 改成 'abc' 可以观察错误分支
try:                         # 只包住需要在这里处理失败的操作
    age = int(text)          # 可能抛出 ValueError
except ValueError as error:  # 捕获指定异常，error 引用这次异常对象
    print("年龄不是合法整数", error)  # 处理无法转换的情况
else:                        # try 正常完成、没有进入异常分支时执行
    print("解析成功", age)   # 本例输出：解析成功 20
finally:                     # 正常结束或异常传播等退出路径都执行
    print("本次解析结束")    # 常用来安排清理，不代表解析一定成功
```

| 关键字 | 职责 | 不应误解为 |
|---|---|---|
| `try` | 标出可能需要处理失败的范围 | 把整个程序包住即可安全 |
| `except` | 处理匹配类型的异常 | 默认忽略失败 |
| `else` | try 正常完成后执行 | finally 的另一种写法 |
| `finally` | 安排退出时清理 | 无论如何都代表业务成功 |

`else` 内发生的新异常，不会再被同一组前面的 `except` 捕获。让 `try` 范围尽量聚焦，有助于避免把别处的编程错误当成预期输入错误。

### 1.3 为什么不能滥用裸 except

裸 `except:` 连 `KeyboardInterrupt（用户中断）`、`SystemExit（退出请求）` 等都可能捕获。普通业务错误多属于 `Exception`，它只是更大的 `BaseException` 异常体系中的一支。

错误思路是捕获后什么也不说，伪装成成功：`except Exception: pass`。正确做法是根据具体语义选择“恢复、转换成明确失败、记录后继续传播”，只有明确可以忽略的异常才忽略。

```python
def parse_integer(text):     # 这个边界只负责将字符串解析成整数
    try:                     # 聚焦转换操作
        return int(text)     # 成功时返回结果
    except ValueError:       # 只处理无效整数文本
        return None          # 明确约定 None 表示解析失败，不伪装成数值 0

print(parse_integer("abc")) # None：调用者需要处理这个失败标记
```

返回标记不是所有函数都应采用的方案；必须保证调用者知道约定。需要失败中止后续流程时，继续抛异常常常更清楚。

## 2. 主动拒绝、重新抛出与保留因果链

### 2.1 raise 表达“当前条件不允许继续”

```python
def set_age(age):            # 输入已经是可比较的数值，本例检查非负约束
    if age < 0:              # 发现不满足业务条件
        raise ValueError("age must be >= 0")  # 主动报告无效值
    return age               # 合法时才返回

print(set_age(20))           # 20
# set_age(-1)               # 错误示例：应提供非负值，而不是忽略这次拒绝
```

### 2.2 记录后重新抛出，不丢掉当前失败

```python
import logging               # 标准库日志工具
logger = logging.getLogger(__name__)  # 获取以当前模块命名的日志记录器


def parse_required_integer(text):  # 解析失败时必须向调用方报告
    try:                           # 只处理转换步骤
        return int(text)           # 正常结果直接返回
    except ValueError:             # 记录已知解析失败
        logger.exception("整数解析失败")  # 记录消息和当前异常回溯
        raise                      # 不带表达式：继续抛出当前异常
```

日志不是恢复行为。记录完还要明确程序能不能继续；不要因为写了一条日志，就默认可以继续执行依赖解析结果的步骤。记录真实输入时还要考虑隐私与敏感字段。

### 2.3 转换错误类型时，用 from 保留底层原因

```python
class BusinessInputError(Exception):  # 自定义异常，表示业务输入不可接受
    pass                             # 继承异常行为，不添加新成员


def parse_age(text):                 # 把底层解析错误转换成上层能理解的错误
    try:                             # 尝试完成格式转换
        age = int(text)              # 转换失败会抛 ValueError
    except ValueError as error:      # 保存原始异常对象
        raise BusinessInputError("invalid age") from error  # 保留明确因果关系
    if age < 0:                      # 再检查业务范围
        raise BusinessInputError("age must be >= 0")         # 业务拒绝
    return age                       # 只有所有检查成功才返回

try:                                 # 演示调用方处理明确的业务错误
    parse_age("abc")                 # 触发解析失败
except BusinessInputError as error:  # 在业务边界捕获
    print(str(error))                 # invalid age
    print(type(error.__cause__).__name__)  # ValueError：底层原因仍可追踪
```

`raise ... from error` 建立显式因果链；它不是“把错误改名以后删除现场”。对外展示可以简洁，对内排障仍保留必要原因。

### 2.4 错误分类决定后续策略

| 错误语义 | 示例名称 | 上层要决定的问题 |
|---|---|---|
| 输入不合法 | ValidationError（校验错误） | 返回输入错误，还是允许修正后再提交 |
| 无权限 | PermissionError（权限错误） | 拒绝，不应靠无限重试绕过 |
| 下游等待过久 | ProviderTimeout（模型服务超时） | 是否还有重试／替代路径预算 |
| 资源不存在 | NotFound（未找到） | 是预期缺失，还是调用前提被破坏 |
| 状态不允许执行 | BusinessRejected（业务拒绝） | 终止还是转人工流程 |

这些名字里有些是内置或库异常，有些是应用自行定义的类别；命名必须落实到具体项目，不能假定所有名字都已经存在。上层可以据此选择 HTTP 4xx／5xx 状态、Retry（重试）、Alert（告警）或 Fallback（替代路径），而不是所有错误都只用一个 RuntimeError。

### 2.5 assert 只适合可移除的内部断言

```python
result = 2 + 3               # 程序内部计算结果
assert result == 5, "内部计算假设不成立"  # 开发期检查内部假设
```

**Assertion（断言）** 可以在优化模式下被移除，因此不能作为外部输入、权限、金额等关键校验的唯一实现。需要始终执行的约束，用明确的 `if` 和 `raise`。

`finally` 也不要随意写 `return`：它可能覆盖原返回值，甚至掩盖正在传播的异常。清理逻辑应尽量简单，并保留主操作失败的可见性。

## 3. 文件：先理解字节、文本与生命周期

### 3.1 str 与 bytes 不是同一种数据

**Text（文本）** 是字符内容，Python 常用 `str` 表示；**Binary Data（二进制数据）** 是字节序列，常用 `bytes` 表示。**Encoding（编码）** 是字符与字节之间的转换规则。

```python
text = "你好"                 # 字符串：文本意义
raw = text.encode("utf-8")   # 按 UTF-8 编码成字节
restored = raw.decode("utf-8")  # 按相同规则解码回文本
print(type(raw).__name__)    # bytes
print(restored)              # 你好
```

`open(path, "r", encoding="utf-8")` 读取文本；`open(path, "rb")` 读取字节，不传文本编码。图片、音频、PDF 等常先以字节交给 Parser（解析器）、模型或存储服务；不要把任意二进制数据当作 UTF-8 文本直接解码。

### 3.2 一个可以独立运行的创建、读取、关闭实验

下面只在临时目录中创建演示文件，不覆盖你工作目录已有的文件。

```python
from pathlib import Path             # 用对象表达文件路径
from tempfile import TemporaryDirectory  # 自动管理临时目录的标准库工具

with TemporaryDirectory() as folder: # 创建临时目录，退出时清理
    path = Path(folder) / "data.txt"  # / 在 Path 上表示拼接路径部分，不是数值除法
    path.write_text("第一行\n第二行\n", encoding="utf-8")  # 创建并写入文本，\n 是换行符

    with path.open("r", encoding="utf-8") as file:  # 以文本方式打开
        content = file.read()                      # 读取全部文本，得到 str
    print(file.closed)                             # True：离开内层 with 后文件已关闭
    print(content.splitlines())                    # ['第一行', '第二行']：按行拆分文本

    with path.open("rb") as file:   # 同一文件也能以二进制方式读取
        raw = file.read()           # 此时得到 bytes，不是 str
    print(isinstance(raw, bytes))   # True
```

模式 `"w"`／`write_text` 可能创建或覆盖文件，`"a"` 表示追加，`"r"` 不会自动创建不存在的文件。对真实业务文件使用写模式前必须确认意图。

### 3.3 大文件逐行或分块处理，避免一次保存全部内容

```python
def count_lines(path):                    # path 是需要读取的文件路径
    total = 0                             # 只保存计数，不保存所有行
    with open(path, "r", encoding="utf-8") as file:  # 管理读取资源
        for line in file:                 # 文件对象按行提供迭代接口
            total += 1                    # 每取得一行就累计
    return total                          # 文件关闭后返回计数
```

这把第 06 章的迭代与第 07 章的资源管理接起来：输入按需取得，处理完成就不再保留整份中间结果。单行极大的文件仍会有较大的单行内存，因此二进制大块、上传流等场景还可按固定块大小读取。

```python
def count_bytes(path, chunk_size=65536):   # 每块最多读取 64 KiB
    if chunk_size <= 0:                   # 防止无效块大小
        raise ValueError("chunk_size 必须大于 0")  # 明确拒绝无效配置
    total = 0                             # 累计读取字节数
    with open(path, "rb") as file:        # 二进制读取
        while True:                       # 持续取块
            chunk = file.read(chunk_size) # 读取下一块，末尾返回空 bytes
            if not chunk:                 # 空块表示已经读到末尾
                break                     # 退出循环
            total += len(chunk)           # 处理当前块，不保存全部块
    return total                          # 返回累计值
```

RAG Ingestion（知识入库）、CSV／JSONL Processing（逐记录处理）、大文件上传、Streaming Pipeline（流式流水线）都需要考虑同样的峰值内存问题。

### 3.4 pathlib 解决路径表达，不保证操作永远成功

```python
from pathlib import Path      # 标准库路径对象
path = Path("data") / "input.json"  # 组合目录与文件名，避免手写平台分隔符
if path.exists():             # 当前这一刻检查是否存在
    text = path.read_text(encoding="utf-8")  # 读取时仍可能遇到权限或并发删除等错误
```

`exists()` 与后面的读取是两次操作，中间状态可能改变。不要把事前检查当成对后续 I/O 成功的保证；真正有能力恢复的边界仍需处理读取异常。

## 4. 模块与包：组织名字，也组织初始化边界

### 4.1 import 与 from import 的绑定不同

一个 `.py` 文件通常可以作为 **Module（模块）**；**Package（包）** 用来分层组织模块。普通包常用带 `__init__.py` 的目录表达，命名空间包等形式还有不同规则，因此不是所有包都必须来自同一种目录布局。

```python
import math                  # 导入模块，并在当前作用域绑定名字 math
print(math.sqrt(4))          # 通过模块名访问平方根函数，输出 2.0

from math import sqrt        # 将模块里的 sqrt 对象绑定到当前名字 sqrt
print(sqrt(4))               # 2.0：此时可以直接使用这个名字
```

工程里通常分清 Standard Library（标准库）、Third-party Package（第三方包）与 Local Application Package（本项目代码）。安装第三方包和导入包是两件事；导入失败时，要先确认当前解释器环境和依赖是否匹配。

### 4.2 __main__：模块被执行，还是被别人导入

```python
def main():                  # 将直接运行时才需要做的工作集中起来
    print("run")             # 脚本入口行为

if __name__ == "__main__":   # 直接作为入口运行时成立；被 import 时通常不成立
    main()                   # 只有入口运行才调用
```

直接执行文件时，`__name__` 是 `"__main__"`；正常作为模块导入时，是相应模块名。把测试请求、启动进程等操作放进明确入口，避免别人只是导入一个工具函数就触发副作用。下一阶段的多进程示例尤其需要这个保护。

### 4.3 import 的准确顺序：先放入模块缓存，再执行顶层代码

```text
先检查 sys.modules 是否已有可复用的模块
→ 没有时寻找模块定义与加载器
→ 创建模块对象并初始化必要信息
→ 在执行模块顶层代码前，将模块放入 sys.modules
→ 执行模块顶层代码，逐步建立其中的名字
→ 导入成功，在调用方作用域绑定相应名字
```

**`sys.modules`（模块缓存）** 保存已加载或正在初始化的模块对象。提前登记可以避免重复递归创建同一个模块，但也意味着其他代码可能遇到一个**还没有执行完的模块**。加载失败时，失败模块的缓存条目通常会被移除，不能把“已登记”理解成“已成功初始化”。

普通重复 import 通常复用缓存，不每次重跑全部顶层代码；显式重载、手动修改缓存等属于不同情况。不要把 `.pyc` 字节码缓存与 `sys.modules` 的模块对象缓存混成同一机制。

### 4.4 循环导入为什么看到“部分初始化”

```text
a.py 开始导入 → 顶部又导入 b.py
b.py 执行途中 → 反过来访问 a.py 里尚未定义的名字
→ a 模块对象已经存在，但预期成员尚未创建
→ 出现 partially initialized（部分初始化）相关错误
```

**Circular Import（循环导入）** 不一定每次都失败，但互相过早访问未就绪名字会失败。修复首先看职责：把共享定义提取到独立模块，减少高层之间的双向依赖；必要时局部导入可以延迟访问，但不能用它永久掩盖混乱的模块边界。

## 5. 把错误边界应用到一次 AI 请求

```text
读取文件 → 解析 JSON → 调用模型 → 校验结构化输出 → 写入状态
```

不同阶段可能分别遇到 FileNotFoundError（文件缺失）、JSONDecodeError（JSON 解析失败）、ValidationError（结构校验失败）、Timeout（超时）、PermissionError（权限错误）、BusinessRejected（业务拒绝）。它们不应无差别地被转换成“服务器错误，再试一次”。

Python 层负责保留清晰的类型、原因与资源清理；后续 FastAPI／Backend 层再根据这些语义建立稳定的 Error Contract（错误契约）。下一章会把“外部文本成功解析”继续推进到“数据是否满足结构与业务要求”。

## 6. 🎯 面试怎么回答

### 为什么推荐 `with open()`

> 因为 Context Manager 把资源获取和释放绑定到明确生命周期，即使内部抛异常也能执行退出清理，比手工 open/close 更不容易泄漏资源。

### `finally` 是否一定执行

> 正常异常控制流中，`finally` 用于保证清理逻辑执行；但进程被强杀、解释器崩溃、机器掉电等极端情况不能承诺物理意义上的“一定”。

### import 为什么不会每次都重新执行

> 已加载模块通常会存在 `sys.modules` 中，后续 import 会优先复用模块对象；第一次导入时顶层代码可能执行，因此模块 import 本身也可能有副作用。

## 7. ⚠️ 易错点

- 裸 `except` 容易吞错误；
  正确做法：尽量捕获自己知道怎样处理的具体异常类型。
- `except Exception: pass` 会让排障非常困难；
  正确做法：明确恢复、返回失败或继续抛出，不假装成功。
- `assert` 不能当安全校验；
  正确做法：必要约束使用不会因优化模式消失的 if／raise。
- 大文件不要无脑 `read()`；
  正确做法：按行或按块消费，避免所有中间内容同时驻留。
- import 会执行顶层代码，模块初始化也可能失败；
  正确理解：缓存登记在顶层执行前，模块存在不代表所有成员已经就绪。
- 循环导入通常意味着职责边界需要重新设计；
  正确做法：拆出公共依赖，必要时才延迟导入。
- Error Type 应影响 Retry / HTTP Status / Alert，而不是所有错误统一一个字符串。
  正确理解：错误类别分别影响重试、响应状态和告警，也需要保留必要因果链。
