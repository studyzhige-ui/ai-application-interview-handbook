# 02. 核心数据类型、容器、Hash 与切片成本

Python 面试里 `list / tuple / set / dict / str` 很基础，但真实追问不会只停在“谁可变谁不可变”。

这一章要建立三层理解：

```text
容器语义
→ 底层数据结构直觉
→ 时间 / 空间 / 复制成本
```

---

## 1. 总体对比

| 类型 | 有序 | 可变 | 重复 | 典型访问 | 常见用途 |
|---|---|---|---|---|---|
| `list` | ✅ | ✅ | ✅ | index | 动态序列 |
| `tuple` | ✅ | ❌ | ✅ | index | 固定记录 |
| `set` | 不应依赖顺序 | ✅ | ❌ | membership | 去重 / 集合运算 |
| `dict` | ✅ 保留插入顺序 | ✅ | key 不重复 | key | 映射 |
| `str` | ✅ | ❌ | ✅ | index / slice | 文本 |

⚠️ “有序”要说清楚：现代 Python 的 `dict` 保留插入顺序；`set` 的遍历顺序不应成为业务逻辑依赖。

---

## 2. list：动态数组 Mental Model

```python
nums = [1, 2, 3]
nums.append(4)
nums.extend([5, 6])
nums.insert(0, 100)
```

常见复杂度：

| 操作 | 典型复杂度 |
|---|---:|
| `lst[i]` | O(1) |
| `append()` | 均摊 O(1) |
| 尾部 `pop()` | O(1) |
| 中间插入/删除 | O(n) |
| `x in lst` | O(n) |

为什么中间插入贵？

```text
连续/紧凑存储的引用槽位
→ 插入后需要移动后续引用
```

为什么 append 是“均摊 O(1)”而不是绝对 O(1)？因为偶尔扩容时要搬移已有引用。

---

## 3. `append` vs `extend`

```python
a = [1, 2]
a.append([3, 4])
# [1, 2, [3, 4]]

b = [1, 2]
b.extend([3, 4])
# [1, 2, 3, 4]
```

- `append(x)`：把 `x` 整体作为一个元素；
- `extend(iterable)`：把 iterable 中元素逐个加入。

---

## 4. tuple：不可变的是“槽位绑定”

```python
t = (1, 2, 3)
# t[0] = 100  # TypeError
```

但：

```python
t = ([1, 2], 3)
t[0].append(4)
```

可以修改 tuple 内部引用指向的 list。

所以准确说法是：

> tuple 自身保存的元素引用不能被重新赋值，但引用指向的对象仍可能是可变对象。

只有所有元素都可哈希时，tuple 才可能可哈希。

---

## 5. set：成员判断和集合运算

```python
a = {1, 2, 3}
b = {3, 4, 5}

print(a | b)
print(a & b)
print(a - b)
```

适合：

- 去重；
- membership；
- 集合关系。

`remove` vs `discard`：

```python
s.remove(x)   # 不存在抛 KeyError
s.discard(x)  # 不存在不报错
```

如果要“保序去重”，不要直接依赖 `set`：

```python
unique = list(dict.fromkeys(items))
```

## 6. dict：不只要会说“Hash Table”

字典查找的核心流程可以抽象成：

```text
key
→ hash(key)
→ 根据 hash 定位候选槽位
→ 如果冲突则继续探测候选位置
→ 用 equality 判断真正 key
→ 找到 value
```

所以平均 lookup 很快，但“平均 O(1)”不等于最坏情况绝对 O(1)。

---

## 7. Hash 和 `__eq__` 必须一致

哈希容器要求：

> 如果两个对象相等，那么它们的 hash 必须一致。

也就是：

```text
a == b
→ hash(a) == hash(b)
```

反过来不成立：两个不同对象可以产生相同 hash，这就叫 Hash Collision。

因此哈希表还必须处理冲突，不能只靠 hash 值本身判断 key 是否相同。

---

## 8. Python dict 怎样处理 Hash Collision

面试应用深度不需要背 CPython 每个探测公式，但要知道：

```text
hash collision
≠ 覆盖旧 key
```

dict 会继续寻找其它候选槽位，并结合 key equality 判断真正目标。

所以：

```python
hash(a) == hash(b)
```

不代表：

```python
a == b
```

哈希碰撞只是“候选位置冲突”。

---

## 9. 删除 dict key 后为什么不是“什么都没发生”

开放寻址类哈希表不能随便把中间槽位恢复成“从未使用”，否则可能破坏后续 key 的探测链。

因此从数据结构思想看，删除通常需要保留某种“这里以前有元素”的状态，让查找知道：

```text
这个位置虽然已删除
但探测不能在这里直接停止
```

具体 CPython 内部布局会随版本演进；面试重点是理解**删除不能破坏 probe chain**，不要把某个版本字段名背成永久实现规范。

---

## 10. Resize 为什么是哈希表的重要成本

当哈希表越来越满时：

```text
collision 增多
→ probe 变长
→ lookup / insert 性能下降
```

因此 dict 需要保持一定空闲空间，并在必要时扩容 / 重建表结构。

这意味着：

> 单次 insert 不是永远固定成本，但从平均/均摊角度仍然非常高效。

---

## 11. dict key 为什么要求可哈希

key 进入哈希表后，定位依赖 hash 与 equality 关系保持稳定。

如果一个对象作为 key 后内部内容还能任意改变，可能造成：

```text
插入时 hash = A
修改对象
查询时 hash = B
→ 原位置找不到
```

所以 list / dict / set 这类可变容器通常不可哈希；`str`、`int` 等不可变对象通常可哈希。

---

## 12. `d[key]` vs `d.get(key)`

```python
value = d[key]
```

key 不存在：`KeyError`。

```python
value = d.get(key, default)
```

不存在返回默认值。

选择取决于语义：

- “不存在就是 bug” → `d[key]` 更清晰；
- “不存在是正常分支” → `get` 更自然。

不要为了“不报错”无脑全部用 `get()`。

---

## 13. str：不可变与大量拼接

```python
s = "hello"
# s[0] = "H"  # TypeError
```

大量片段拼接通常：

```python
result = "".join(parts)
```

比循环里不断构造新字符串更自然，因为字符串不可变，反复 `+=` 可能产生额外分配/复制成本。

---

## 14. Slicing 的语义和成本

```python
nums = [0, 1, 2, 3, 4, 5]
part = nums[1:5:2]
```

切片格式：

```text
sequence[start:stop:step]
```

对 `list / tuple / str` 这类常见内建序列来说，普通切片会产生新的序列对象，而不是“零拷贝 view”。

因此切出 `k` 个元素时，通常要考虑：

```text
Time  O(k)
Space O(k)
```

这和 NumPy 等支持 view 的对象不同，不能把其它库行为套到 Python 内建 list 上。

---

## 15. `[::-1]` 为什么要注意空间

```python
reversed_copy = items[::-1]
```

它很简洁，但通常会创建一个新的序列。

如果只是遍历反向元素：

```python
for x in reversed(items):
    ...
```

可能更符合“只迭代、不复制整份数据”的需求。

这就是面试里问 Slicing 时应该继续想到的：

> **语法简洁不代表没有时间/空间成本。**

## 17. 🎯 面试怎么回答

### dict 为什么快

> Python dict 基于哈希表思想，通过 key 的 hash 快速定位候选槽位，冲突时继续探测并用 equality 判断真实 key，因此平均查找、插入、删除接近 O(1)。但不是最坏情况绝对 O(1)，扩容和冲突都会影响单次成本。删除也不能简单破坏探测链，所以实现通常需要保留删除状态。

### list vs tuple

> list 可变，适合动态序列；tuple 自身元素绑定不可修改，更适合固定记录。tuple 是否可哈希取决于内部元素是否都可哈希。

### Slicing

> 对常见 Python 内建序列，切片通常会创建新对象，切出 k 个元素大致要 O(k) 时间和空间。`[::-1]` 很简洁，但也通常意味着复制；只想反向迭代时可以考虑 `reversed()`。

---

## 18. ⚠️ 易错点

- dict 平均 O(1) ≠ 最坏情况绝对 O(1)；
- Hash 相同 ≠ 对象相等；
- 相等对象必须有一致 Hash；
- 删除槽位不能随意破坏 probe chain；
- tuple 不一定可哈希；
- set 不要依赖遍历顺序；
- list 切片通常会复制；
- `[::-1]` 简洁但通常不是零额外空间。

## 19. 本章自测

<details>
<summary>1. 两个不同 key 的 hash 一样时，dict 为什么还能同时保存它们？</summary>

Hash 只用于快速定位候选位置；发生碰撞时哈希表会继续探测其它槽位，并使用 key equality 区分真正的 key。

</details>

<details>
<summary>2. 为什么删除一个 dict key 不能简单理解成把槽位恢复成“从未使用”？</summary>

因为其它发生过碰撞的 key 可能依赖这条探测链；如果查找在这里提前停止，就可能错误地认为后续 key 不存在。

</details>

<details>
<summary>3. `items[:]` 通常有什么成本？</summary>

对于常见内建序列，它通常会创建一个新序列并复制引用/元素视语义而定，因此与结果长度相关，通常需要 O(k) 时间和额外空间。

</details>
