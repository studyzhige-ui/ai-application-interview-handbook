# 面经来源质量准入规则

更新日期：2026-09-09

本项目的目标不是追求“收集数量最大”，而是建立一个能够真实校准 **AI 应用开发 / Agent 开发** 求职知识体系的数据集。

> **平台不是质量标准。来源可以来自牛客、小红书、知乎、脉脉、Bilibili、抖音、CSDN、个人博客或其他公开平台，但无论来自哪里，都必须满足完全相同的 HUMAN-A 硬门槛。**

宁可漏掉一些真实面经，也不能让自动化面试、二次加工、低信息密度、疑似虚构或无法稳定核验的内容污染正式样本。

## 1. 正式样本唯一标准：HUMAN-A

新的正式 `Sxxx` 来源必须同时满足以下三道硬门槛：

1. **Human Interviewer Gate**：明确属于真人面试官参与的技术面 / Leader 面 / 项目深挖。AI 自动面试、AI 模拟面试、自动化题库筛选不进入正式样本。
2. **A-grade First-person Gate**：候选人本人第一人称复盘，真实性和信息密度达到 A 级。
3. **Role Scope Gate**：岗位属于 `role-scope-policy.md` 定义的 AI Application / Agent / RAG / AI Backend / AI Full-stack / Agent Runtime 等目标方向。

```text
任意公开平台
      ↓
真人面试官？
      ↓
候选人本人高质量第一人称？
      ↓
目标 AI Application / Agent 岗？
      ↓
可稳定核验且非转载重复？
      ↓
HUMAN-A
```

任意一项不满足，都不进入正式 Batch、canonical question、真人面试频率和课程优先级分析。

## 2. HUMAN-A 的硬性判断标准

正式来源原则上应同时具备：

- **可追溯页面**：稳定 URL 或可稳定核验的公开页面；
- **公司 / 岗位明确**：最好还能确认日期、轮次、时长或业务团队；
- **真人互动痕迹**：例如“面试官追问 / 引导 / 打断 / 反问 / 现场讨论 / 手撕 / 画图”等自然互动；
- **第一人称结果痕迹**：例如“答得不好 / 被追问住 / 约二面 / 挂了 / OC”等；
- **技术问题具体且有上下文**：通常至少 5～8 个有信息量的问题，或少量但非常深入、独特的连续追问；
- **问题顺序具有真实面试流**：项目 → 追问 → 基础 → 场景 / Coding，而不是异常整齐的题库分类；
- **正文不是答案驱动**：候选人的面试经历和问题是主体，而不是“标准答案 / 高手答法 / 解析”包装出来的内容。

### 平台无差别原则

以下判断全部与平台无关：

- 牛客上的整理帖不会因为是牛客就升级；
- 小红书上的第一人称高质量长文可以进入 HUMAN-A；
- 知乎 / CSDN 的候选人真实复盘也可以进入 HUMAN-A；
- 抖音 / Bilibili 若能稳定核验候选人本人、真人技术面和完整具体问题，也可以进入 HUMAN-A；
- 任何平台只要只能看到标题、截图、二次转述或标准答案，一律不进入正式样本。

**平台只影响“是否容易核验”，不影响准入标准。**

## 3. 非 HUMAN-A 内容如何处理

从现在起，不再把 B/C/D/E 等低质量或非核心内容作为“问题发现层”持续保留在活跃研究数据里。

- **低信息密度第一人称**：排除；
- **整理 / 合集 / 搬运**：若能帮助找到原始 HUMAN-A 帖，只作为临时搜索线索；找不到原帖则丢弃；
- **二次创作 / 高频题 / 标准答案 / 模拟题**：直接排除；
- **只有标题的平台线索**：可以短暂用于寻找原帖，但不能进入 canonical question 或课程 Gap Analysis；
- **自动化 AI 面试**：直接排除；
- **岗位方向不匹配**：直接排除。

临时 Lead 的唯一目的，是定位一个真正符合 HUMAN-A 的原始来源。**Lead 本身不贡献题目。**

## 4. 默认排除项

以下内容即使搜索排名很高，也不进入正式样本，也不贡献 canonical question：

- AI 自动面试 / AI 模拟面试 / 自动化题库；
- 水短视频：只有“面了几轮、很难、挂了”，没有具体技术追问；
- SEO / 题库博客：关键词堆砌、固定标准答案、没有真实现场信息；
- `三年面试五年模拟 / 含完整答案 / XX 面试宝典 / 40 题全解析 / 高手答案` 等二次加工；
- 从其他平台搬运但无法找到候选人原帖；
- 多家公司题目拼成一篇，无法判断每个问题来自哪一场；
- 只有评论区传言、截图标题或平台搜索标题，无法验证正文；
- AI 批量生成痕迹明显、问题排列异常规整、没有候选人现场经历；
- 付费墙只露出很短片段，无法验证来源真实性与问题上下文；
- 虽然是第一人称，但只有 1～3 个泛泛问题、没有足够技术信息的低密度复盘。

## 5. 去重与交叉验证

同一候选人可能把同一场面试同步到牛客、小红书、CSDN 等多个平台：

- 公司 / 日期 / 问题高度一致 → 视为同一场，不增加频率；
- 评论页、推荐页、镜像页指向同一正文 → 只保留一个 canonical URL；
- 二次文章引用第一人称原帖 → 正式证据只保留原帖；
- 两个独立候选人遇到语义相同的问题 → canonical question 增加两个独立 HUMAN-A 命中。

## 6. canonical question 的唯一来源

canonical question 不是独立知识体系，而是**高质量真人面经对课程的血肉补充**。

因此从现在起：

1. 新 canonical question 必须至少有一个 HUMAN-A 来源；
2. 如果一个历史 canonical question 的全部来源在回审后都被排除，则该 canonical question **从活跃题库中删除**；
3. 不因为某个低质量来源提出了“看起来很高级的问题”就保留；
4. 如果这个知识本来属于 MySQL / Redis / RAG / Agent Harness 等完整知识体系，它应由对应模块正文覆盖，而不是依赖低质量面经为它保留一个“面试题 ID”；
5. 只有真正被 HUMAN-A 面经问到的内容，才进入“真实面经问题层”。

也就是说：

```text
完整知识体系 = 自己从 0 搭建
真人高质量面经 = 校准重点 + 提供真实问法
低质量来源 = 不参与课程和题库
```

## 7. canonical question 新增门槛

新增 canonical question 至少满足之一：

1. HUMAN-A 来源出现此前面经题库未覆盖的独立问题；
2. 已有主题被真人面试追到明显不同的工程层次，值得独立学习；
3. 多个独立 HUMAN-A 来源反复出现，说明应提升为独立问题；
4. 单个 HUMAN-A 来源中的问题对 Runtime / Reliability / Security / Production 面试表达确实具有独立价值。

否则优先记录为已有 canonical question 的新 HUMAN-A 命中，不为了题量创建新 ID。

## 8. 搜索优先级

1. 最近 30～60 天的 HUMAN-A 第一人称技术面；
2. 目标公司 / 目标岗位的完整一面、二面、三面或 Leader 面复盘；
3. 同一场同时覆盖 Agent / RAG 与 Python / FastAPI / MySQL / Redis / Backend 的高质量样本；
4. Agent Harness / Runtime / Coding Agent 等少见深挖；
5. 任何平台都必须通过同一 HUMAN-A 标准。

**平台覆盖率、Batch 数量、`Sxxx` 数量和 canonical question 数量都不能高于来源质量。正式研究只认 HUMAN-A。**
