# LLM Foundation｜面试易错点

> 这些错误大多不是“完全不会”，而是把一个只在局部成立的说法讲成绝对规律。

## Token / Context

1. ❌ 一个汉字就是一个 Token。  
   ✅ Token 数取决于具体 Tokenizer。

2. ❌ Context Window 就是模型长期记忆。  
   ✅ 它只是单次推理输入容量；长期 Memory 属于应用状态系统。

3. ❌ 128k Context 就应该尽量塞满 128k。  
   ✅ 更长输入会增加 Prefill、成本、噪声和 KV Cache。

4. ❌ Long Context 可以完全替代 RAG。  
   ✅ RAG 还解决检索、权限、新鲜度、引用和大规模语料治理。

5. ❌ Lost in the Middle 表示中间 Token 完全不可见。  
   ✅ 它描述利用率 / 位置敏感，不是硬截断。

## Transformer / Attention

6. ❌ Transformer 就是 Attention。  
   ✅ 还包括 FFN、Residual、Norm、Position 等关键结构。

7. ❌ Q/K/V 是三个不同 Token。  
   ✅ 通常是同一 hidden state 经过三组投影得到。

8. ❌ Attention Weight 就是模型因果解释。  
   ✅ 它只是内部计算的一部分。

9. ❌ Multi-Head 的每个 Head 都有固定可解释功能。  
   ✅ 不应过度人类化解释 Head。

10. ❌ Causal Mask 是为了屏蔽 Padding。  
    ✅ Causal Mask 屏蔽未来位置，Padding Mask 屏蔽无效补齐位置。

11. ❌ Transformer 可以并行，所以生成整段答案也能完全并行。  
    ✅ 训练 / Prefill 可高度并行，自回归 Decode 仍逐 Token。

12. ❌ FFN 用来再次做跨 Token Attention。  
    ✅ FFN 通常对每个位置独立做非线性变换。

13. ❌ Residual 只是为了让网络“更快”。  
    ✅ 更核心是帮助深层信息与梯度传播。

14. ❌ RoPE 就是在 Token Embedding 上加一个位置序号。  
    ✅ 经典 RoPE 通过旋转 Q/K 把位置关系带入 Attention。

15. ❌ 修改最大长度就等于获得可靠 Long Context。  
    ✅ 还和训练长度、位置机制、Serving 内存与质量相关。

## Generation / Sampling

16. ❌ Logit 就是 Probability。  
    ✅ Logit 是未归一化分数，Softmax 后才是概率分布。

17. ❌ Token 概率高就说明事实置信度高。  
    ✅ Next-token likelihood 不等于事实正确率。

18. ❌ Temperature 越低答案越正确。  
    ✅ 它主要减少采样随机性。

19. ❌ Temperature=0 保证端到端完全确定。  
    ✅ Provider、模型版本、并行计算和上下文变化都可能影响结果。

20. ❌ Top-k 和 Top-p 是同一件事。  
    ✅ Top-k 固定候选数；Top-p 按累计概率动态选候选。

21. ❌ Streaming 会减少模型总计算量。  
    ✅ 主要改善感知延迟，不自动减少 Decode 工作。

## KV Cache / Serving

22. ❌ KV Cache 缓存的是最终输出文本。  
    ✅ 缓存历史 Token 的 Attention K/V 状态。

23. ❌ KV Cache 只提升速度，没有成本。  
    ✅ 主要代价是显存和内存带宽。

24. ❌ KV Cache 就是 Agent Memory。  
    ✅ 一个是推理中间状态，一个是应用长期状态语义。

25. ❌ 输入 Token 和输出 Token 对延迟影响一样。  
    ✅ 输入主要影响 Prefill，输出需要逐 Token Decode。

26. ❌ TTFT 低就说明生成速度快。  
    ✅ 后续 TPOT 仍可能很高。

27. ❌ QPS 就能代表 LLM Serving Throughput。  
    ✅ 请求 Token 长度差异很大，应结合 input/output tokens/s。

28. ❌ Batch 越大单请求越快。  
    ✅ Throughput 与 Latency 常需要权衡。

29. ❌ Continuous Batching 是 Backend 合并 HTTP 请求。  
    ✅ 这里主要指 Model Server 内部动态推理调度。

30. ❌ PagedAttention 是新的 Attention 数学公式。  
    ✅ 核心是 KV Cache 的分页式内存管理。

31. ❌ 用 vLLM 就不需要限流、超时和取消。  
    ✅ Serving Engine 与业务 Backend 职责不同。

32. ❌ INT4 模型所有计算都用 4 bit。  
    ✅ 具体量化范围、计算精度和 Kernel 因方案而异。

33. ❌ Quantization 一定更快。  
    ✅ 取决于硬件、Kernel、反量化和 workload。

34. ❌ 权重量化后显存问题就解决了。  
    ✅ Long Context / 高并发下 KV Cache 仍可能是主要显存消费者。

## Model API / Selection

35. ❌ Chat Message 就是字符串拼接。  
    ✅ 模型通常有特定 Chat Template / Special Token。

36. ❌ Provider Adapter 能让不同模型行为完全一致。  
    ✅ 它只能统一接口，不能抹平模型能力差异。

37. ❌ 最大模型一定是最优业务模型。  
    ✅ 要比较质量、延迟、成本、Context、Tool、风险和可用性。

38. ❌ API 单价最低的模型总成本最低。  
    ✅ 失败率、重试、输出长度和调用次数都会影响成功任务成本。

## Embedding / Reranker

39. ❌ Embedding 维度越高效果一定越好。  
    ✅ 还受训练目标、数据、领域和成本影响。

40. ❌ Reranker 能补救 Retriever 完全没召回正确文档。  
    ✅ 它只能重排已有候选。

41. ❌ Cosine Score 和 Rerank Score 可以直接比较。  
    ✅ 不同模型分数标度通常不同。

## Prompt / Hallucination / Fine-tuning

42. ❌ Prompt 越长越详细效果一定越好。  
    ✅ 过长会占 Context、引入冲突与噪声。

43. ❌ Few-shot 越多越好。  
    ✅ 要权衡 Context、覆盖和 Bias。

44. ❌ Prompt 改完几个 Demo 变好就说明优化有效。  
    ✅ 必须做固定 Evaluation Set 的 Regression。

45. ❌ RAG 文档中的指令可以直接服从。  
    ✅ 外部 Context 是不可信数据，Prompt Injection 要做边界治理。

46. ❌ Temperature=0 就没有 Hallucination。  
    ✅ 稳定输出也可能稳定地错。

47. ❌ 有 RAG 就不会幻觉。  
    ✅ Retrieval、Context 和 Generation 都可能失败。

48. ❌ Fine-tuning 最适合维护频繁变化的企业知识。  
    ✅ 动态事实通常优先 RAG / Tool。

49. ❌ Fine-tuning 后不需要 Prompt。  
    ✅ 当前任务、Context 和 Output Contract 仍需要表达。

50. ❌ LoRA = Fine-tuning。  
    ✅ LoRA 是 PEFT 的一种实现。

51. ❌ LoRA Rank 越高一定越好。  
    ✅ 适配容量与成本要用 Eval 权衡。

52. ❌ RLHF = PPO。  
    ✅ PPO 只是 RLHF 中可能使用的策略优化算法。

53. ❌ DPO 不需要偏好数据。  
    ✅ 它依赖 chosen / rejected 等 Preference Pair。

54. ❌ Distillation 能完整复制 Teacher。  
    ✅ Student 容量和训练数据会限制可迁移能力。

55. ❌ Reward 越高 Production 一定越好。  
    ✅ 可能存在 Reward Hacking，需要独立 Evaluation / Verification。

---

# 使用方式

复习时不要只看“正确答案”。每一个错误说法都应该能继续解释：

```text
为什么错
→ 哪些场景局部成立
→ 更准确的工程表述是什么
→ 如果线上出问题怎么验证
```
