# 17｜TTFT / TPOT / Throughput / Cost

> “模型很慢”不是一个可操作的诊断。应用工程要把延迟和成本拆成可以观测、比较和优化的指标。

## 1. 一次 LLM 请求的延迟组成

可以拆成：

```text
Client Network
→ API Gateway / Backend Queue
→ Provider Queue
→ Prefill
→ First Decode
→ Decode × N
→ Streaming / Network
```

所以总时延只是结果，不是原因。

---

## 2. TTFT

TTFT = Time To First Token。

用户点击发送，到看到第一个 Token 的时间。

常受影响：

- 排队；
- 输入 Token 数；
- Prefill；
- 模型大小；
- Batch / Scheduler；
- 网络；
- Provider 负载。

交互式 Chat 对 TTFT 很敏感。

---

## 3. TPOT / Inter-token Latency

TPOT = Time Per Output Token。

它衡量 Decode 阶段每个新 Token 的生成速度。

用户看到第一个字很快，但后面像“挤牙膏”，通常就是 TPOT 较高。

---

## 4. Tokens Per Second

常见另一种表达：

```text
output tokens / second
```

它和 TPOT 近似互为倒数关系，但统计口径可能不同。

做 Benchmark 时必须统一：

- 是否包含 TTFT；
- 是否统计平均 / P50 / P95；
- 单请求还是并发；
- 输入 / 输出长度。

---

## 5. Throughput

系统吞吐可能用：

- Requests / second；
- Input tokens / second；
- Output tokens / second；
- Total tokens / second。

LLM workload 长度差异大，所以单纯 QPS 很容易误导。

例如：

```text
100 个短分类请求
和
100 个长报告生成请求
```

QPS 相同，GPU 工作量完全不同。

---

## 6. Cost 从哪里来

### API 模式

常见成本由：

```text
Input Tokens
Output Tokens
Cached Input
Model Tier
Extra Tool / Modality
```

共同决定，具体价格看 Provider。

### Self-hosted

成本更像：

```text
GPU 数量
× 占用时间
+ 运维
+ 空闲率
+ 网络 / 存储
```

所以不能只比较“每 Token 单价”。

---

## 7. 为什么模型越大不一定业务效果越好

更大模型可能：

- 准确率更高；
- Reasoning 更强；

但也可能：

- TTFT 更高；
- TPOT 更慢；
- 单价更贵；
- 并发更低。

如果一个任务小模型已经稳定达到目标，换大模型可能只增加成本。

因此 Model Selection 必须结合业务指标。

---

## 8. Latency Budget

Production 系统最好把目标拆成预算：

```text
Total 3s
├─ Retrieval 300ms
├─ Rerank 200ms
├─ Provider Queue 200ms
├─ TTFT 800ms
└─ Streaming Decode ...
```

这样优化才知道应该动哪一层。

---

## 9. P50 / P95 / P99

平均延迟不能代表尾延迟。

用户体验常被慢请求决定，因此要观察：

```text
P50
P95
P99
```

还要按：

- 模型；
- Region；
- Tenant；
- Prompt Length；
- Output Length；
- Provider；

分桶。

---

## 10. 成本优化常见方向

- 缩短无效 Prompt；
- RAG 只注入高价值 Context；
- Prompt / Prefix Cache；
- 控制 Max Output；
- 小模型处理简单任务；
- Model Routing；
- Batch；
- Quantization；
- 提高 GPU 利用率；
- 避免用户取消后继续生成。

---

## 11. 🎯 面试怎么回答

> LLM 延迟不能只看总耗时。我会至少拆 TTFT、TPOT 和 Queue Time。TTFT 更受输入长度和 Prefill 影响，TPOT 更体现 Decode 速度；吞吐则要结合 token/s 而不是只看 QPS。成本还要区分输入、输出和缓存 Token，或者自部署的 GPU 利用率。Production 优化应该先建立 latency / cost budget，再按 Prompt、模型、Serving、Backend 分层定位。

---

## 12. ⚠️ 易错点

错误：

> tokens/s 越高，TTFT 就一定越低。

不是同一指标。

错误：

> API 单价低的模型总成本一定低。

如果输出更长、失败重试更多或效果不足导致多次调用，总成本可能更高。

---

<details>
<summary>自测：用户第一字很慢，但后续输出很流畅，优先看什么？</summary>

优先拆 Queue、Network、输入 Token 和 Prefill，重点看 TTFT，而不是先怀疑 Decode TPOT。

</details>
