## 核心问题与处理

上一稿把“可复现”过多实现成正文中连续的操作块，同时沿用原来的细粒度章节。读者尚未建立基本模型，就必须在 SQL、配置、结果、边界和应用驱动之间来回切换。仅调整字数或把全部代码折叠，都不能解决这个组织问题。

本轮先明确每章的完整问题，再决定例子和文件边界。数据库身份、单表操作、关系约束、关联统计分别展开；索引中反复出现的树、回表与主键关系合并；隔离与 MVCC 用一条可见性时间线贯穿。分页、结构演进与批量写入放在单库机制之后，复制、CDC 与分片按传播和迁移前置排列。原第 20 章缓存一致性从 MySQL 主线删除，只在应用建模末尾保留“本地事务到哪里结束”的责任边界。

全文不以 Python、Java 或某种应用框架为入门条件。应用参数讲结构和值的分离，驱动写法不进入主线。SQL、少量结果表、逻辑结构和并发时间线仍在解释需要它们的位置；环境、索引创建清理、完整双连接步骤放在 `examples/`。

本轮重点是教学重组，沿用上一稿基于同一仓库快照建立的正式面经对应，不新增来源，也不把本轮称为重新打开 297 个原帖。冻结 S001–S279 的 26 个 MySQL 主责主题、55 个关联独立来源 ID 均保留；S280–S297 的既有适用性判断按新章重新映射。[证据对应表](mysql-evidence-map-2026-09-27.json)同时保留前稿位置与新去向。

面经不是目录发生器。本轮固定使用以下 Gate：

```text
真人问题 → 抽象共同机制 → 判断主责与必要前置 → 检查主线是否已覆盖
        → 已覆盖则加深因果/边界；未覆盖才判断是否真的需要加入
        → 正文只留下知识模型，不保留来源编号、原题措辞或某一场面试叙事
```

例如 `(A,B,C)` 的范围条件、ORDER BY、回表和“索引失效”表面是多道题，正文只建立“联合索引的字典序以及定位、过滤、覆盖、排序四种作用”；学完以后应能自然推导具体题目。`S293` 等来源编号只保留在本维护记录/证据映射，已从正式正文删除。缓存一致性虽然是真实追问，但 Primary 已移到 Backend，因此不因面经频繁就让未学 Redis 的读者提前学习 Cache Aside。SQL 注入和数据库协调锁则在其前置已建立的位置补足共同机制。
