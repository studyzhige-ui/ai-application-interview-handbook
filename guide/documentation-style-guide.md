# Documentation Style Guide｜README 与状态描述规范

[← Handbook 总目录](../README.md) · [Knowledge Map](knowledge-map.md) · [Final Quality Audit](audits/final-quality-audit.md) · [Terminology Glossary](terminology-glossary.md) · [Progress](../interview/canonical/progress.md)

> 目标：让任何人打开任意一级模块或核心状态页，都能使用同一种信息架构理解“这是什么、职责是什么、从哪里开始、边界在哪里”。

## README 的正式身份

README 是仓库或目录的 **canonical entry document（正式入口文档）**。它描述当前有效的定义、职责、结构、使用方式、边界和权威入口，不承担 Changelog、迁移日志或聊天纪要的职责。

README 主体应优先回答：

```text
这是什么？
→ 为谁服务、解决什么问题？
→ 由哪些部分组成？
→ 各部分职责和边界是什么？
→ 应该怎样进入和使用？
→ 哪些文档是权威入口？
```

以下内容默认不写入 README 主体：

```text
以前是什么 / 原来怎样
这次为什么重构
本轮改了什么
从旧目录迁到哪里
哪些句子刚刚被重写
阶段性 PR / 聊天决策过程
```

这类信息进入 `guide/project/`、`guide/audits/`、专门的 migration / revision record 或 Changelog。

### 语言规则

README 采用稳定陈述式语言，优先写：

- “本模块负责……”
- “目录包含……”
- “课程按……组织”
- “技术事实以……为准”
- “统计基线：S001–S279”

避免把项目建设过程写成主体叙事，例如：

- “现在……”
- “不再……”
- “原来 / 以前 / 之前……”
- “本轮 / 这次 / 这一版改成……”
- “已经从 A 迁到 B……”

“当前”并非绝对禁词，但只在语义确实需要“运行时当前状态”或“明确时间基线”时使用。版本敏感事实优先写明 **版本 / commit / 核验日期**，而不是使用模糊的“现在”。

### 状态表达

状态使用名词化、可核验的元数据，而不是过程叙事：

```text
课程版本：V1
教材状态：✅ 完整
统计基线：S001–S279
资料核验日期：2026-09-11
```

不要写成：

```text
我们现在已经完成……
这次终于重构完……
原来的内容已经迁走……
```

### 例外

`guide/project/` 与 `guide/audits/` 的职责本身就是记录历史演进与审计，因此可以描述迁移、修订和历史状态；但其 README 仍应先定义“这个目录是什么”，具体过程进入目录中的记录文件。

## 一级模块 README 固定结构

```text
# Module｜一句话角色
上一模块 · Handbook 总目录 · Learning Path · 下一模块
课程版本 / 教材规模 / Canonical / Source Coverage

1. 这个模块解决什么
2. 在十板块中的位置
3. 固定课程原则
4. 正式学习主线
5. 正式课程目录
6. HUMAN-A 怎样影响本模块
7. 模块边界
8. Review / Interview / Evidence 入口
9. 推荐学习方式
10. 教材状态
```

- Learning Path 是推荐使用方式，不是模块元数据；一级模块 README / Review README 只保留简洁入口，不写死 Week / Session，避免绑定某一种学习节奏。

## Review README 固定结构

- 顶部必须能返回模块主页和 Handbook；
- 可提供 Learning Path 作为可选入口，但不在 Review 中写死 Week / Session；
- 明确它属于第二遍复习，不重复正文；
- 自测答案默认使用 `<details>` 折叠；
- 图解优先使用保守 GitHub Mermaid。

## 根 README / Knowledge Map

- 十个一级模块名称必须直接可点击；
- 所有模块使用同一列信息：角色、Blocks、Canonical、状态；
- 根 README 只定义仓库、信息架构、主要入口和层级关系，不写迁移过程；
- 详细内容进入模块 README。

## 状态源优先级

```text
当前仓库文件
> Progress / Knowledge Map / Module README
> 历史审计记录
> 聊天摘要 / 旧 PR 描述
```

## 同步规则

模块状态改变时，至少核验：根 README、模块 README、Review README、Knowledge Map、Progress、Module Index、Canonical README、自动生成 Analysis README 的生成源、本地 Markdown 链接，以及是否需要更新 Final Quality Audit / Terminology Glossary 中的跨模块边界。

## 正文可理解性与证据规则

从具体任务和中文解释开始，首次重要英文名给中文含义。字段清单之前说明每项信息服务什么决定；不把“运行事实”“结构化”当不需解释的答案。每章就地保留“面试怎么答、易错点、章节自测”，不能仅链接到集中题库。产品过程用可选折叠承载，明确快照、入口函数、触发、输入、变更、输出和限制；不虚构所有版本相同。

相同故障在不同章节出现时说明当前责任，把完整机制链接回主责章。Trace 与恢复数据分开，记录策略由业务需要和隐私约束决定，不以全量收集替代设计。结构/字数/折叠检查只验证文档形式，不作为初学者理解或真实系统可靠性的证明。

## Writer like a reader：先设计阅读路径，再写正文

### 整体架构先于局部修补

先明确目标读者、进入课程时已具备的知识、最终需要独立完成的任务，再建立知识依赖和章节职责。每个概念有明确的主要教学位置。章节顺序由前置关系决定，不由资料收集顺序、API 名字顺序或反馈出现顺序决定。

读者反馈是发现设计缺陷的样本。发现一次“先用后讲”，要审查同级内容和后续依赖；发现一道题缺输入，要审查全部练习契约；发现某章只有原则没有例子，要检查整条路线是否实际提供了练习与验收。不能把用户点名的位置当作唯一修改范围。

审查结论可以是保留、局部重写、整章重组或跨章迁移，不要求每章改动量相同。跨章调整要保留知识覆盖，更新所有受影响的前置说明、导航和题目映射。不能为了保持旧目录或小节编号而保留错误教学顺序，也不能以“新增文档更多”替代清晰主线。

### 引入、正文与收束都要帮助理解

引入先给读者一个能够想象的具体问题，让他知道为什么值得学、要解决什么困难，再进入术语与代码。不能刚进入第一章就要求“保存 main.py”，却没有说明代码是什么、为何要运行。入口知识可以自然承接，但不把治理术语、知识归属声明或操作清单当作引入。

正文按实际理解需要展开。问题动机、核心规则、执行过程、结果和边界应形成清楚的关系，不强制每个小节套同一组标题。解释核心处愿意多写：为什么变量这样变化，为什么选择这种容器，为什么分支或循环不会遗漏。生动不是增加形容词，而是用读者能手算的小情境和连续动作，使抽象关系看得见。表格用于对照，代码用于观察，不用密集断言和方法目录代替讲解。

章末保留小结、面试怎么答、易错点与默认折叠自测，知识课程回看须说明能解决什么疑问。不能在结构重组时只留下一个 Exit Gate 而删掉学习收束。不同章节的实例与问题按实际需要选择，不机械复制相同问答。

### 小节内部先让规则清楚，再用例子落实

目录顺序合理，不代表每个知识点已经讲清。逐节审查时，先找出读者最需要知道的一句话：这个操作是什么，在什么条件下执行，输入和结果是什么。不要让示例暗示这句话，却始终不明确说出它。

例如，`input()` 要明确说明成功读取一行后始终返回字符串，再用 `18` 和 `"18"` 的对照说明现象，随后才解释 `int` 转换。`if` 要先说条件为真才进入分支，为假就跳过，再展示两种路径。例外和深入机制不能抢在基本规则前面，稀释初次理解。

执行过程复杂时，在代码前交代变量的职责，在代码后用具体输入追踪关键步骤。不要先放一整段实现，再让读者回头寻找变量定义。已经能自然递进的内容直接继续，不加无关场景、刻意设问或没有新信息的过渡句。

### 排版表达关系，不在列表与长段落之间走极端

根据内容的逻辑选择格式：

- **有先后顺序的动作**用编号，例如读取、转换、计算。每一步说明做什么以及得到什么。
- **并列职责、选择或检查项**用简短项目符号，不把三四个独立结论压进一个长句。
- **需要逐项对应的结果**用表格，例如真假分支、输入类型、每轮变量变化。
- **动机、因果和推导**用自然段。列表不能把解释删成几个关键词，也不需要把每句话都列成一项。

中文正文使用清楚的句号、逗号和冒号。分号只连接关系明确的分句，不用它承载一整组本应分点的步骤。行内代码用于名字、表达式和实际值，不把一大段中文解释包进反引号。箭头只表达真实步骤或状态变化。多行输入输出用真实换行，不用斜杠代替；代码块中的标点仍服从语言语法。

### 提醒就地说明触发条件与后果

在容易误解的规则或代码下方，使用独立的 `> ⚠️` 提醒。说明“哪种情况下会错、为什么、应怎样检查”，例如 `append` 返回 `None`，不能把返回值当成新列表。

提醒不应只是“这里很重要”，也不把正常定义全部变成警告。章末易错点用于回顾，不能代替学习当下的说明。自测的问题要能逐项辨认，折叠答案要与题目对应；转换成 Notebook 后也要保留列表、段落和提醒，不能将解释压成单个 HTML 段落。

自动检查只能核对代码、生成结果和部分格式。小节规则是否明确、例子是否足以解释规则、衔接是否多余，仍要人工逐节阅读，不能通过增加列表数或警告数宣称已经易读。

### 核心讲透，不以穷举接口冒充基础完整

“基础完整”指读者具备完成当前主线任务的核心模型，而不是每种类型的全部 API。对 list、tuple、str、dict、set 等同级概念，要在各自位置讲清高频基础操作，但不强求同样的方法数量、同样的目录长度，更不能给不可变类型机械补“增删”目录。

内容分三种责任：反复需要的核心操作在所属概念处讲透并练习；某个任务才需要的低频工具在出现时简洁解释输入、结果、修改行为与必要边界；底层实现与完整接口范围留给知识课程或官方文档。高频选择以目标任务与实际练习需求为依据，不伪称完成了全平台使用频率统计。

例如，字典的 get/keys/values/items、列表的遍历/切片/append/pop/sort、集合的成员查询/add/remove 应形成清楚的基础模型。heapreplace 可在第 K 大的固定大小堆场景解释，bytes 可在大量输入场景解释，异或可在成对数字抵消场景解释。不因为出现了一个新方法，就把该库的全部同类接口前移给初学者。

删去低频清单不意味着把核心内容缩成速查卡。节省下来的认知负担应投入关键概念的情境、逐步解释和练习。审查必须同时防止两个极端：只修点名位置导致同级缺口，以及为补齐同级而扩成百科。

### 跨章提示必须传递新信息

页首的上一章/下一章负责导航。正文不要反复写“算法应用在第 07 章”“以后会讲”这类只指路不解释的语句。确有意义的比较或铺垫可以保留，例如“两个名字指向同一可变列表时，修改对象会被两边观察到”，因为它在建立概念联系，而不只是宣布未来有内容。

跨章迁移后同步受影响的先修说明与练习解释，但不要为了形式上的“先用后讲检查”，把所有特殊知识都提前集中。未知操作允许就地讲明，未知的核心模型则要补回合理的主要教学位置。

### 示例、练习与答案形成可验证闭环

示例应给足初始数据，或者明确属于同一个连续程序；每个可独立运行的代码块应能冷启动执行。分别说明原对象变化、返回值和屏幕输出，避免注释暗示不存在的输出。伪代码、未实现编写区、故意报错示例与可运行实现必须有可见区别。

练习题在答案之外提供任务、输入或初始数据、预期结果、允许的边界、修改与返回约定。参考答案默认折叠，测试本身不能依赖未展开答案才知道的题意。Notebook 应能填写和运行，隐藏 Markdown 答案不能被假装成自动执行代码；空白练习失败与参考答案通过要分开报告。

每章的学习验收应有实际任务与可核对依据。结构、链接、示例执行、测试和生成文件同步是回归检查；读者能否建立正确模型仍需内容审查和真实阅读验收。不能只加一段“遵循这些原则”的声明，就宣称正文已经符合原则。

## Agent 章末固定形式

HUMAN-A 信号提供来源关联；面试回答以 Q 和 🎯 可见引用块展示；高频易错点用 ⚠️ 逐条提醒；自测以题目本身作为折叠标题。不能把四者统一成“查看参考答案”按钮。正文保留引入、分层解释、例子和失败推演；源码对照可选折叠，不用来源清单代替讲解。

## 时间语义与生成文件

仓库中的数字和状态必须先区分时间语义，再决定是否同步：

```text
Current State
= 运行中的当前事实，例如 Market HUMAN-A 总数、当前目录结构

Frozen Baseline
= 明确冻结的统计口径，例如 Canonical S001–S279 / 235 ACTIVE

Historical Snapshot
= 某次审计、迁移或阶段分析在当时的真实结论

Rolling Log
= Daily Log / Batch 等按时间追加的过程记录
```

规则：

- Current State 发生变化时同步当前入口文件；
- Frozen Baseline 只在正式 periodic review 后更新，不能因为 Market 新增来源机械扩展；
- Historical Snapshot 不改写旧数字，应归档到 `history/` 或 Project Records 并明确日期；
- Rolling Log 保留当时事实，不使用今天的总量回写过去。

自动生成文件以生成源为权威。修改 `market/analysis/README.md`、Global Index、Coverage / Validation 等生成结果时，必须同步修改对应 `tools/*.py`；CI 通过“重新生成后无 diff”检查防止人工文案被下一次 Action 覆盖。
