# 交付与复盘｜把事件还原成任务结果

[← 上一章](06-cross-session-knowledge.md) · [本产品目录](README.md)

一轮循环正常结束、后台进程退出和分页实现正确需要不同证据。本章把观测事件的生产者与消费者接起来，再用已有例子整理面试表达和条件推演，不增加实现作业。

<a id="event-trace"></a>
## 沿一项后台测试读完事件链

下面是静态教学推演，省略无关事件；事件落在内存、完成 flush、显示在界面又是不同时间点。

```text
turn/start → pre-step 接纳 → step/start → 路由准备
    → user/message → 按需 request/header/context → 模型流结算为 assistant/message
    → tool/call：Bash 启动作业 J
    → tool/result：promoted，包含 J 和当前输出
    → 下一步骤或本轮结束
作业 J 结算 → 完成消息进入拥有者 Inbox
    → 忙碌者下一步领取，空闲者按唤醒策略新开轮次
    → job_output 返回终态与增量 → 模型判断 → turn/end
```

Session 是顺序事实记录；Surface 选择当前模型使用的节点；流事件为界面提供即时显示；作业注册表拥有活跃进程和输出游标。这四个生产者/消费者相连，却不能互相替代。若界面显示过文字但流未结算就崩溃，持久记录未必包含全部文字；若后台进程已经退出但通知未被模型消费，任务总结也可能还不知道终态。

基础组合装配独立 OTel 插件，会话日志导出默认使用 FEEDBACK_ONLY：普通活动不自动触发这类日志前缀上传，明确用户反馈才释放相应前缀。按字节分批后可能有多次串行请求；关闭有总截止时间，不能据“开始导出”承诺所有记录已送达。这里讲的是该会话遥测配置，不是对全部网络请求的总隐私声明。[组合中的观测配置](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/bundle/base/cordis.patch.yml)

<a id="verification"></a>
## 从工具结果走到任务完成

无论单 Agent 还是父子协作，最终都要核对分页任务：第一页 `[10, 20]`，第二页 `[30]`，其他既有边界符合约定，测试没有被修改。模型最终回答或 Turn 标为 `completed`，只是控制流程结束。[主循环][loop]

| 验证层 | 要检查什么 | 不能单独证明什么 |
|---|---|---|
| 单次操作 | 文件路径、编辑结果、测试命令是否实际执行 | 整项任务满足要求 |
| 过程约束 | 是否改了测试、越权或取消后继续写 | 功能一定正确 |
| 最终结果 | 实现 diff、对应版本的测试、未覆盖边界 | 中间每步都合规 |

一个结构正确的 `{ "passed": true }` 也可能没有真实测试支撑。父任务必须核对结果来源和共享资源变更，不能把子任务“成功”直接升级成整体完成。

<details>
<summary>子任务结构化结果何时正式提交</summary>

共享驱动先验证并暂存 `structured_output` 工具提供的值，等权威最终工具结果成功后提交；PTC 路径还要考虑外层 `run_code` 结果。提交后用守卫阻止继续调用。要求结构化输出却只返回自然语言时，不会自动重新询问并假装成功。[结果生命周期][driver]

</details>

<a id="trace"></a>
## 用一条轨迹找回出错的位置

Trace（执行轨迹）将相关请求、工具和状态变化连起来。先用调用 ID 对应某个工具请求和结果，再用 Step 找到它属于哪次模型请求，Turn 确定轮次，事件序号还原记录顺序，Session 确定会话。[主循环][loop]

分页结果不对，可以从三条路径排查：

1. **执行者没收到限制。** 查实际请求、当前视图和子任务输入，确认“不能改测试”是否传入。
2. **输入正确但执行错误。** 查调用参数、编辑结果与文件 diff，定位错误公式怎样被写入。
3. **实现与验收不一致。** 查是否只测试第一页，以及模型为何把部分通过当成整体正确。

实时界面、会话日志和外部监控各能证明一部分。显示过的流片段未必已持久化，请求记录不证明服务商收到，重放日志也不表示重新执行工具。结果未知时，应写出证据缺口，而不是拼一个看似连贯的根因故事。

<a id="evaluation"></a>
## 优化是否值得保留，要在相同标准下比较

要把单 Agent 改成父子协作，或使用 Skill、PTC，先固定任务集合、权限和成功标准。任务应包含正常修改，也包含长输出、取消、依赖错误、模型限额和工具不可用；不能改完架构再只挑成功例子。

同时观察最终完成、过程违规、端到端耗时和成本。阶段耗时与用户等待不同，模型 Token 与外部 API 费用不同；失败与取消样本不能从报告中悄悄消失。

**教学假设：** 同分布 100 个任务，A 成功 70 个，B 成功 90 个，每任务多用 60 秒。样本成功率提高 20 个百分点，不是相对提高 20%，也不保证未来相同。是否值得采用，还要看失败后果、可接受等待、成本与重复试验的不确定性。

若 B 通过修改测试才提高成功率，就没有遵守相同标准。多阶段 Skill 也要检查阶段之间的输入传递与最终整合，不能把多个局部成功相加当成系统成功。

这里是基于前述执行边界的评测方法，不声称 DSH 内置全部业务门禁或自动进化。完整评测体系仍由[通用 Agent 课程](../../../curriculum/09-agent/README.md)与相关实践承接。

<a id="test-layers"></a>
## 验证报告应对应真正做过的层次

| 层次 | 保留什么 | 不能扩大成什么 |
|---|---|---|
| 源码与静态检查 | 固定提交、文件、命令与规则 | 真实服务已经执行 |
| 上游单元测试 | 环境、目标测试、通过失败与跳过数 | 所有产品路径通过 |
| 模拟集成 | 替身、初始状态、注入故障 | 真实模型和文件系统保证 |
| 真实服务 | 路由、有效配置、请求与结果证据 | 所有平台和权限组合可靠 |
| 生产或跨平台 | 平台、负载、持续时间与失败边界 | 未测环境也成立 |

本轮仅做源码核验。产品测试、模型运行和故障注入没有执行，不能计为通过；正文示意用于理解实际检查的边界。

<a id="self-test"></a>
## 多角度回顾与自测

### 循环与上下文：本章小结

先用一次修复理解 Turn 与 Step，再跟踪输入从队列、规则和历史汇合成请求。Session 保存事件，Surface 选择当前有效内容，实际路由决定请求形状；工具结果更新后续历史，压缩再控制继续携带多少内容。

排错时依次问：信息是否被接纳，是否仍在当前视图，是否进入实际请求，模型收到后是否正确使用。它们是不同问题。

### 循环与上下文：🎯 面试怎么回答

**Q：DSH 怎样让一次请求的上下文可解释？**

> 它先领取输入和组装提示，在真实路由准备完成后提交消息及请求条件，再从 Session 的当前 Surface 派生并冻结请求。工具结果进入后续历史，压缩留下替换记录。因此可以追踪输入来源，但日志本身不证明远端已经收到或执行，持久化与外部结果需要分别核验。

**Q：为什么不能直接删除最早的几条消息？**

> 消息有依赖关系。工具调用要对应结果，用户约束和未完成工作也不能只按时间丢弃。DSH 先计量压力，尝试裁剪大结果，再选择平衡区间摘要并保留近期尾部。替换的是当前可见历史，不是抹去原日志；结构检查通过以后仍要验证摘要语义。

### 循环与上下文：⚠️ 常见误区

| 误解 | 正确判断 |
|---|---|
| 入队就会改写当前模型输出 | 只能参与后续可接纳的请求，`inject` 不单独唤醒 |
| Session 有原文，模型就始终收到 | 还要看 Surface 与请求派生 |
| 请求已记录就证明远端执行 | 接纳、持久化、发送和远端结果是不同边界 |
| 所有取消都只留下不可见失败 | 有可保留内容时可能形成中断回复 |
| 压缩变短就保证没有丢任务信息 | 仍需核对约束、已完成工作与未决状态 |

### 循环与上下文：自测：先写出判断，再展开答案

**任务 A：输入与唤醒。** 空闲 Agent 先收到 `inject(项目背景)`，再收到 `followup(修复分页)`。第一次操作后是否必须请求模型？背景在哪里获得参与机会？

<details>
<summary>任务 A｜提示</summary>

队列中的 `next-step` 决定领取边界；再检查这次操作是否唤醒 Agent。

</details>

<details>
<summary>任务 A｜参考答案与解释</summary>

第一次只入队；第二次唤醒后，背景在输入处理阶段与任务一起获得接纳机会。是否实际进入还受输入处理及取消约束。

</details>

**任务 B：日志、视图与请求。** 旧读取调用和结果已被摘要替换，原事件仍在日志，近期测试结果保留。下一次模型默认读取哪一份？界面能展开旧文件全文，能否证明模型也收到了全文？

<details>
<summary>任务 B｜参考答案与解释</summary>

模型使用由当前 Surface 派生的摘要与近期内容，原日志可供审计。界面展现与模型请求不是同一个视图；需检查派生消息和实际请求，不能由界面可读推断原文仍被发送。

</details>

**任务 C：改变故障点。** 用户消息和 `request/header` 已记录，进程在调用模型流之前崩溃。能否报告服务端已经处理？下一步缺哪类证据？

<details>
<summary>任务 C｜参考答案与解释</summary>

不能。记录说明本地接纳与构造，不证明发送或远端结果。应核对持久化边界、请求发送与服务端状态，不得编造上次回复；工具副作用还需另查外部状态。

</details>

**任务 D：摘要没有进展。** 系统提示和工具定义占据大部分窗口，剩余历史只有一个不可分的大调用。为什么继续摘要可能无效？

<details>
<summary>任务 D｜参考答案与解释</summary>

没有可安全缩减的普通历史区间；不能任意删系统头或拆坏调用关系。应减少提示与工具说明成本、控制输入输出，或外置可重新读取的内容、选择容量合适的模型，不能对相同超限请求无限重发。

</details>

### 工具与扩展：本章小结

普通调用先确认身份和可见性，再经过策略、批准、guard、参数校验与业务执行，最后处理结果。规范值、模型文字与外部状态要分别核对；并发和取消则改变时间关系，不改变这些责任。

PTC 编排调用，Skill 提供指令，MCP 接入服务。排障时始终回到：停在哪一层，业务是否已经开始，副作用是否可能发生，下一步有什么证据。

### 工具与扩展：🎯 面试怎么回答

**Q：为什么工具调用不能只有模型输出 JSON，再调用函数？**

> JSON 只是意图。程序还要核对当前工具视图、固定身份和参数，经过策略、批准、守卫与校验，才能执行。结果区分程序值与模型内容，并按调用关系回填。取消、后处理失败不自动撤销副作用；单次工具链与多调用调度器分别承担执行规则和并发收尾。

**Q：Skill、MCP、PTC 分别解决什么问题？**

> Skill 提供如何完成任务的指令；MCP 接入外部能力；PTC 用程序组织调用和处理中间值。三者都不替代权限与结果验证。按需加载只减少一部分上下文成本，目录、工具定义、输出和历史仍需分别管理。

### 工具与扩展：⚠️ 常见误区

| 误解 | 正确判断 |
|---|---|
| 用户批准后必定执行 | 后续取消、guard 或参数检查仍可阻止 |
| `never` 自动批准 | 它拒绝需要审批的请求，已允许动作另论 |
| 参数冻结就是结构正确 | 不可变快照与工具结构校验不同 |
| 展示打码就保护所有通道 | 程序仍可能取得原规范值 |
| 顺序回填就没有文件竞争 | 执行体可能重叠，共享资源需协调 |
| MCP 名称可见就是服务正常 | 故障期间可能保留名称，但调用失败 |

### 工具与扩展：自测：用状态判断，不只说术语

**任务 A：批准后被拒绝。** 编辑进入 `ask`，用户批准；guard 随后否决，业务函数未调用。审批、工具结果和文件应怎样解释？

<details>
<summary>任务 A｜提示</summary>

沿审批、guard、业务函数的顺序，分别标出哪些步骤已执行。

</details>

<details>
<summary>任务 A｜参考答案与解释</summary>

有本次允许的审批事实，但后续条件失败。工具返回拒绝或失败，本次业务函数没有修改文件；不是先写后回滚，也不是审批记录丢失。

</details>

**任务 B：展示没有秘密。** 后处理只把 `content` 改成“已隐藏”，程序调用方随后输出原规范值。为什么仍可能泄漏，应在哪个位置处理？

<details>
<summary>任务 B｜参考答案与解释</summary>

只改展示保留了原值。入口阻止不应读取的数据，结果侧控制程序可取得的值或拒绝结果，并检查其他输出通道；模型截图不足以验证防泄漏。

</details>

**任务 C：两个读取反序完成。** 模型提出 A、B；允许并行，B 在 20 毫秒、A 在 100 毫秒完成。回填顺序是什么？能否因此把任意写操作并行？

<details>
<summary>任务 C｜参考答案与解释</summary>

按 A、B 回填，B 等 A 可提交。执行重叠与提交有序不同，任意写入仍可能竞争；毫秒是题设，不是产品性能实测。

</details>

**任务 D：一百个技能仍然很长。** 正文按需加载、每项描述已限长，但请求仍含大量名称与历史目录变更。已经节省什么，尚未解决什么？

<details>
<summary>任务 D｜参考答案与解释</summary>

节省的是未使用技能的完整正文，不是全部目录及更新历史。应检查实际请求和任务作用域；延迟加载是否有效还需核对路由，不能假定已有通用搜索自动解决。

</details>

### 恢复与交付：本章小结

单任务恢复先取得可信日志，再补齐未结束历史的解释，并核验未知副作用；检查点缩小不确定窗口，不建立跨系统事务。委派增加历史、权限、寿命与释放责任，不能替父任务取消验收。

最后同时验证过程和结果，再用可比较样本判断成本收益。恢复成功、子任务结束与业务完成，分别需要证据。

### 恢复与交付：🎯 面试怎么回答

**Q：文件已改，工具结果没保存，重启后怎么办？**

> 先保留结果未知的判断。DSH 对打开尾部中已有调用而缺少结果的情况补 `TOOL_OUTCOME_UNKNOWN`，不是自动重做。文件操作先只读核验，远端写入依赖查询、幂等或对账。动作前刷写提供本地记录依据，但本地日志与外部系统没有因此成为共同事务。

**Q：怎样验证多 Agent 改造有效？**

> 固定任务、授权与成功条件，比较完成率、违规、耗时和成本。检查新要求是否传入子任务，权限是否匹配，父任务是否正确整合，失败后资源是否收束。局部成功不能替代整体验收；源码判断、单元测试和真实服务记录分开报告。

### 恢复与交付：⚠️ 常见误区

| 误解 | 正确判断 |
|---|---|
| 恢复历史就是从崩溃行继续 | 活动对象重建，外部结果可能未知 |
| 合成错误是重试工具的回执 | 它只是根据已保存事实补中断标记 |
| 新格式读不懂就退旧代最安全 | 可能遗漏后续事件，必须明确失败 |
| fork 带走当前轮全部新要求 | 进程内子 fork 取已完成 Turn 的前缀 |
| 没在请求模型就不占活动容量 | 等待、队列和收尾也可能占用 |
| 完成标记或合法 JSON 证明修复正确 | 仍需文件、测试与过程约束证据 |

### 恢复与交付：综合自测：从证据推导下一步

**任务 A：只有调用，没有结果。** 持久记录有编辑调用，无结果；磁盘文件已经包含预期修复。恢复标记、下一步动作与不能自动采取的动作分别是什么？

<details>
<summary>任务 A｜提示</summary>

先区分日志中的结果缺口，与只读检查已经能观察到的外部状态。

</details>

<details>
<summary>任务 A｜参考答案与解释</summary>

标为 `TOOL_OUTCOME_UNKNOWN`。先只读核对内容或差异，再检查是否仍需编辑与测试；不能自动重复写，也不能因结果缺失擅自恢复成旧文件。

</details>

**任务 B：新限制未进入种子。** 前两轮完成，第三轮用户说只审查；父 Agent 此时 fork，只传“继续处理分页”。子任务必然知道新限制吗？

<details>
<summary>任务 B｜参考答案与解释</summary>

不能保证。当前轮不在已完成前缀中，父任务应明确传入只审查要求，并配置子作用域与资源限制，而不只依赖历史种子。

</details>

**任务 C：同时存在 V3、V4、V5。** 本构建支持并写 V4，却发现同一会话更高的规范 V5 代。能否忽略 V5，以 V4 报告恢复成功？

<details>
<summary>任务 C｜参考答案与解释</summary>

不能。V5 可能保存更晚事件。应报告选中代不受支持并保留文件，用兼容构建或明确迁移方案处理；不能静默回退诱发重复动作。

</details>

**任务 D：成功率提高但违反约束。** A 的 100 个任务成功 70 个；B 报告 90 个，其中 15 个修改了被禁止修改的测试。能否直接报告提高 20 个百分点？

<details>
<summary>任务 D｜参考答案与解释</summary>

不能。B 未按相同成功标准统计。逐项重验约束，保留违规和失败，检查其他样本、重复运行与成本；不能机械减 15 后就假定余下全部已严格验收。

</details>

### 恢复与交付：第二遍复习：把三段过程接起来

画出一次任务中的输入、持久化、外部动作、子任务与最终验收边界；在各处标出正常推进条件、中断时已知事实和仍需查询的状态。再改成“只生成建议，不得写文件”，检查你的图能否根据新授权改变允许路径。
