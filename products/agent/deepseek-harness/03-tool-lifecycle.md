# 03｜一次工具调用怎样从建议变成可检查的执行

[← 记忆生命周期](02-memory-lifecycle.md) · [模块入口](README.md) · [下一章：工程与验证 →](04-engineering-evaluation.md)

模型提出：“读取分页文件，然后修改公式。”你看见了工具名，但磁盘上的文件可能还没被读取。调用还要通过程序检查，真正执行以后才有结果。

本章先跟完一次普通调用，再改变权限、取消与并发条件。最后看程序化调用（PTC）、任务技能（Skill）与外部能力协议（MCP）怎样扩展这条路径。**模型提出动作、程序允许动作、工具完成动作、结果被模型使用，是四件相连但不同的事。** 示例是教学推演，不是产品实测回执。

<a id="definition"></a>
## 1. 先看一次读取：说明、实现与结果怎样相连

工具有两个基本部分：给模型看的说明，以及宿主中真正执行的函数。说明告诉模型可以请求什么；执行函数负责操作文件或服务。

| 时点 | 分页任务中发生什么 | 此时已经知道什么 |
|---|---|---|
| 请求包含读取工具说明 | 模型得知可读取文件以及参数要求 | 能提出读取，不代表已经读过 |
| 模型返回读取调用 | 给出工具名、调用 ID 和参数 | 知道本次请求要读哪个目标 |
| 程序检查并执行 | 检查是否允许，校验参数，读取文件 | 才可能获得真实文件内容或错误 |
| 结果写回历史 | 下一步模型获得内容或失败说明 | 可据此修改，或调整读取目标 |

DSH 的 `defineTool()` 将作者写的参数声明、业务函数和输出定义整理成可注册工具。**输出定义**说明返回值应满足什么结构，以及怎样渲染给模型。它连接说明、执行和结果，但不会把“声明会读文件”变成成功证据。[定义源码][schema]

参数结构正确也不代表目标存在或调用者有权读取。接下来先确定本次 Agent 能看见哪个工具，再沿执行链判断是否真的可用。

<a id="visibility"></a>
## 2. 当前 Agent 为什么只看见一部分工具

Scope（作用域）是插件与 Agent 使用服务的上下文层级。全局可以注册通用工具，Agent 的局部层可以限制继承来的能力，或注册自己的工具。

假设全局有读取与写入，审阅 Agent 只继承读取：

| 配置变化 | 审阅 Agent 的情况 |
|---|---|
| 全局存在写工具，本层限制继承写入 | 不能只因全局存在就直接调用写入 |
| 宿主又在本层注册一个写工具 | 必须重新审查本层新增能力，不能继续笼统称为只读 |
| 工具插件卸载 | 旧请求见过的名称不保证此刻仍可执行 |

因此，工具可见性取决于**当前生效的视图**，不是某个目录里存在的全部包。子 Agent 有独立作用域，也不自动证明继承了父级全部限制。[工具视图实现][tools]

> ⚠️ **限制继承项，不等于不可突破的只读边界。** 本层注册与底层文件权限也要检查。请求构造时的工具说明和执行时的实际实现不能被混为一谈；失败时不能暗中改用更高权限实现。

<details>
<summary>核对 `view(scope)` 的合并顺序</summary>

实现先收集全局及祖先层贡献，应用沿途限制，得到允许继承的工具；再加入当前层自己的注册，同名时本层覆盖。本层注册不受这组继承过滤处理，所以 `restrict()` 不能被描述为所有后续注册都无法突破的万能白名单。[源码][tools]

</details>

<a id="pipeline"></a>
## 3. 沿调用顺序判断：到底停在哪一层

下面仍以一次文件读取或编辑为例。`pre` 是执行前策略，`post` 是执行后策略，guard（守卫）是在执行前还能否决动作的检查。

```text
模型提出工具名、调用 ID、参数文本
        ↓
解析参数，保留调用身份与不可变参数快照
        ↓
执行前策略：允许、拒绝、取消，或要求批准
        ↓  要求批准时，先等待本次批准
再次检查取消与 guard
        ↓
调用 execute 包装器：校验参数，再调用业务函数
        ↓
校验返回值，生成模型内容，执行结果后处理
        ↓
冻结最终结果，按调用关系写回历史
```

正常允许且参数合法时，业务函数执行；中途拒绝则返回失败，不会“先执行再问”。模型看到失败后，可以在后续步骤修正参数或选择其他动作。[工具运行链][tools]、[多调用调度器][calls]

### 参数能传递，不等于适合这个工具

执行器保存参数快照，避免等待期间有人改变已经记录的输入；工具自己的结构校验则判断这些输入是否符合声明。两者不是同一次检查。

例如，字符串可以是合法 JSON 值，但读取工具可能需要一个含路径的对象。即使对象结构正确，文件也可能已经不存在。**传递格式、参数结构、业务条件与权限要分别成立。**

`defineTool()` 的参数检查位于业务函数之前，但晚于执行前策略和批准流程。策略代码不能未经检查就假定某个参数字段一定存在。[校验包装][schema]

<details>
<summary>空参数、错误 JSON 与并发分类怎样处理</summary>

`parseArguments()` 解析有效 JSON；空文本变成空对象，解析失败则保留原字符串，使调用仍能携带身份与错误输入。随后执行器要求参数可无损表示为 JSON，并冻结快照。

`defineTool()` 检查失败会抛出带 `INVALID_ARGS` 的 `ToolArgsError`，通过后才调用业务函数。其并发分类包装也先检查参数；无效参数按不安全并发处理。[解析入口][calls]、[包装实现][schema]

</details>

> ⚠️ **结构校验不能替代未表达的业务条件。** Schema 可以声明整数及范围，但接口究竟从 0 还是 1 开始、文件当前版本是否仍与编辑依据一致，要由相应业务与权限逻辑核对。给工具设计版本检查是应用方案，不是 DSH 自动替所有工具实现的保证。

### 批准以后仍可能不执行

一次编辑先进入 `ask`，用户同意；等待期间任务被改为禁止写入，随后 guard 否决。正确解释是：**本次审批通过，但另一个执行条件不成立，业务函数没有运行**，不是文件写完后又回滚。[`prepareExecution()` 与审批调用][tools]

取消也可阻止继续执行。guard 只能否决，不能扩大批准范围或悄悄改写参数。需要审批却缺少审批服务，或调用没有所属 Agent 时，审批分支失败关闭；这不等于所有没有 Agent 的普通调用都必然被拒绝。

<a id="approval"></a>
## 4. 策略、批准与沙箱各守住什么

| 机制 | 回答的问题 | 分页任务中的含义 |
|---|---|---|
| 执行策略 | 当前动作允许、拒绝，还是需要询问 | 编辑是否应进入审批 |
| 单次批准 | 这个具体请求能否继续 | 同意这次编辑，不是所有后续写入 |
| 沙箱 | 执行期间实际可访问哪些资源 | 是否能写测试文件或访问网络 |
| 模型提示 | 怎样向模型说明任务规则 | 告诉模型不得改测试，但不能替代系统权限 |

一次写入要同时满足适用条件。沙箱允许写工作区，不代表用户要求你改所有文件；提示里禁止改测试，也不自动形成文件系统层的不可写保证。

审批服务的策略为 `ask` 与 `never`。`ask` 交给配置的回答者，回答者可由界面中的人或受控机器决策端承担；服务本身不会自动创建人工界面。回答者不可用或报错时，动作失败关闭。

**`never` 表示不交互，并拒绝需要批准的请求，不是自动批准。** 它也不禁用原本已经被策略允许的普通工具。基础组合将 `danger-full-access` 与 `approval: never` 配对，不表示靠审批再追加授权；实际访问仍取决于该权限预设及工具配置。[审批语义][approval]、[组合配置][base]

<details>
<summary>单次批准的日志与迟到回答</summary>

允许结果为 `allowed-once`，不是永久授权仓库或后续同名命令的通行证。审批请求处于打开的 Turn 中，`approval/asked`、`approval/decided` 写入日志；模型一般获得工具最终结果与当前策略，不会获得人工界面的全部内容。取消后到达的迟答不能复活已取消操作。[生命周期][approval]

</details>

<a id="outputs"></a>
## 5. 返回给程序的值、模型看到的文字、真实文件状态

工具业务函数先返回供程序使用的结构化结果，DSH 称为 **canonical value（规范值）**；渲染器再把它变成给模型看的 **content（内容块）**。两者又都应来自实际操作，而不能凭空证明外部状态。

下面只展示关系，不是可直接注册的 SDK 对象：

```text
程序返回值：   { changed: true, file: "pagination.py", testCount: 4 }
模型可见文字： “已修改 pagination.py；执行了 4 项测试。”
实际证据：     文件差异、测试命令、退出状态与输出
```

如果 `testCount` 只是工具作者随手填的 4，通过结构检查也不会变成真实测试证据。规范值是执行局部数据，不作为独立字段原样写入会话工具结果，不能假定重放历史就能恢复原程序对象。[输出设计][tools-readme]

### 只修改展示，会发生什么

工具返回含测试秘密的规范值，后处理把模型文字改为“已隐藏”。模型看不到原文，但程序化调用方可能仍得到原规范值，并通过另一条路径输出。

**控制模型展示与控制程序取得的数据，是两个安全目标。** 不该读取的数据应在入口阻止；程序也不该取得的结果，需要处理规范值或拒绝结果，并核对其他输出通道。仅检查模型截图不能证明所有通道都安全。[后处理链][tools]

### 结果被拦截，不等于操作被撤销

若编辑函数已经写入磁盘，后处理再阻止模型看到结果，文件不会自动恢复。防止未授权写入要在执行前约束；补偿已经发生的修改，需要业务提供可验证的恢复操作，且补偿也可能失败。

> ⚠️ **结果失败与副作用失败不等价。** 外部操作可能已完成，只是返回或保存失败。恢复后的安全核验在[工程章](04-engineering-evaluation.md#semantic-recovery)继续分析。

<details>
<summary>后处理顺序与替换规则</summary>

成功规范值先经过结构检查和渲染。`projectContent` 准备执行相关内容，然后进入执行后策略；策略可保留、替换规范值、替换展示内容或拦截结果。替换规范值会重新校验与渲染，只替换 `content` 则保留原值。`finalizeContent` 最后处理内容，再冻结结果并通知观察者。[源码][tools]

</details>

### 长输出应该留下可继续工作的证据

测试输出很长时，可把完整结果外置，内联保留退出状态、关键失败信息和取回入口。外置资料可能过期或保存失败，必须明确反馈不可用，不能伪造永久有效路径。

结果外置控制这次进入会话的体积；第一章的历史压缩控制后续请求继续携带多少旧内容，两者不是同一动作。基础溢出策略的内联预算为 12,500 Token；另有按字符保留头尾的压缩辅助组件，二者的单位不能互换。[配置][base]

<a id="cancellation"></a>
## 6. 超时与取消：先定位时点，再判断结果

超时表示等待预算耗尽，取消表示调用方要求停止。它们都不能单独证明业务尚未开始或外部操作已经撤销。

| 时点 | 应作出的判断 |
|---|---|
| 调度前取消 | 该调用未分派；其他调用是否开始仍要另查 |
| 已分派，正在等待外部系统 | 传递取消并等待已启动工作收尾，不能假定外部已撤销 |
| 文件已经修改，结果回填前取消 | 文件可能已改，验证可能未完成；应分别记录 |

DSH 使用取消信号协调已启动工作的结算，不把“不再等待 Promise”当成工作已经消失。普通工具错误可回填供模型调整，不一定结束整轮；但内部重试不能绕过已经生效的取消。[取消与收尾][tools-readme]、[执行实现][tools]

> ⚠️ **声明超时还需要实际执行策略。** `timeoutMs` 本身不是注册表内置计时器，截止时间由 `dsh-tool-call-timeout-policy` 包装策略实施。核对定义的同时，要检查所用组合是否挂载了它。

<a id="concurrency"></a>
## 7. 并发执行与有序回填，是两个维度

同一步读取实现和测试文件，可以允许重叠执行；先写文件、再读修改后的内容，则有前后依赖。DSH 根据工具的并发安全分类使用有界并行池；未明确安全或分类失败的调用走保守独占路径。[分类与调度][tools]、[调用调度器][calls]

```text
模型提出： A 读取实现       B 读取测试
实际完成： B               A
结果回填： A               B
```

B 先完成，也不能越过 A 改变模型历史中的调用顺序。独占调用形成屏障；后续调用实际启动前重新分类，所以等待期间的注册或策略变化可能影响它们。

按序回填便于重建历史，**不保证外部执行顺序固定，更不自动解决共享文件竞争**。两个写工具若错误声明并发安全，仍可能互相覆盖。

<details>
<summary>哪些部分按序，取消后怎样收尾</summary>

执行前策略、规定的结果后处理与提交维持顺序，允许重叠的是执行体；调度器不是把整批调用直接交给 `Promise.all()`。取消后停止补充新工作，已启动调用先收尾，未启动调用获得相应失败结果。内部调度故障保留已记录事实，不伪造正常结果。[完整实现][calls]

</details>

## 8. 扩展能力：程序编排、任务指令与外部服务

到这里已经建立普通调用的主线。下面三种机制改变的是工具怎样被组织、发现或接入，**不会替代前面的权限、参数与结果责任**。

| 机制 | 新增的能力 | 沿哪条既有路径执行 |
|---|---|---|
| PTC | 用程序组合多次调用并处理中间值 | 程序内仍调用受控工具 |
| Skill | 按需提供某类任务的具体工作指令 | 需要动作时仍实际调用工具 |
| MCP | 接入外部服务提供的能力 | 发现并注册后进入相同工具链 |

<a id="ptc"></a>
### 8.1 PTC：把中间处理留在一次程序里

PTC 是 Programmatic Tool Calling（程序化工具调用）。普通原生模式由模型输出结构化调用；PTC 通过 `run_code` 写程序，在程序内调用工具、筛选结果，再输出需要的部分。

```text
本次 run_code：读取若干结果 → 程序筛选 → 输出小结果
下次 run_code：重新取得必要状态，不依赖上次内存变量
```

基础组合提供 Node 运行环境，每次调用有新的执行状态，不是永久保留变量的 REPL（交互式解释器会话）。程序化调用仍经过工具链；一段任意代码不是已经批准的超级工具。[PTC 规则][tools-readme]

收益来自减少某些中间结果和模型轮次，但代码、工具说明、错误修复与最终输出仍有成本。是否更省应在相同任务与成功标准下比较。

> ⚠️ **不能自动重放整段程序。** 超时预算包含嵌套工具与批准等待；后面失败时，前面的副作用可能已完成，应先核验。

<details>
<summary>工具呈现模式与恢复边界</summary>

`native`、`ptc`、`both` 是工具呈现模式。`ptc` 将模型直接入口收束为 `run_code`，底层工具通过程序内受控入口使用，并没有消失；猜旧工具名不能绕过模式限制。执行局部规范值不能靠会话日志原样恢复。Node 是该组合选择，不是 PTC 概念只能使用 JavaScript。[模式实现][tools]、[说明][tools-readme]

</details>

<a id="skills"></a>
### 8.2 Skill：先发现任务指令，再按需读全文

Skill（技能）是可复用的任务指令，可能附带资源或脚本。DSH 将来源、注册表和模型加载器分开：来源提供技能，注册表整理可用项，`tool-skill` 先展示名称与截短描述；模型需要时再用 `skill` 工具加载全文。[技能服务][skill]、[加载器][skill-tool]

这节省了把所有技能正文一次塞进请求的成本。它仍会产生目录成本；加载指令既不等于运行脚本，也不授予额外文件或网络权限。

用户显式输入允许用户调用的 `/name` 是另一条入口：插件识别被领取的直接用户消息，把技能全文注入当前步骤，不必再让模型重复加载。

<details>
<summary>目录更新与两类可见性</summary>

只有存在可被模型调用的技能，且加载器的 `skill` 工具确实可见时，才发布目录。合格步骤检查目录变化；新增、删除、描述或可见性改变时，追加完整替代目录。先前发布过目录后即使变空，也要发布空目录退役旧名称。

只允许用户调用、不允许模型自主调用的技能，不通过模型目录和工具泄漏；未知 `/name` 可保留为普通文字。每项描述限长不能消除总数量成本，历史目录更新也会占请求空间。[实现边界][skill-tool]

</details>

<a id="mcp"></a>
### 8.3 MCP：把外部工具接进同一条链

MCP 是外部能力接入协议。客户端连接服务、协商协议、发现工具，再将其注册进 DSH；不是把外部函数名直接拼到提示词里。

模型通常看到 `mcp__服务名__工具名`。两个服务都提供 `search`，也有各自身份；调用远端时使用原始工具名。调用仍携带 Agent、参数、取消与超时，返回值进入同一后处理链。连接成功不等于某次业务调用成功。[MCP 客户端][mcp]

连接丢失后按退避策略重连；故障期间旧工具名可暂时保留，但调用失败。恢复预算耗尽后注销工具，等待重新加载或重启。判断外部记忆是否写成，应查本次调用结果，而不是只看目录。

> ⚠️ **接入外部服务也是信任决策。** 会话引用是不可信快照；MCP 服务器指令却作为文字参与已记录的系统提示。不能声称所有外部文本都被统一降权。服务自身的部署、权限和数据安全也不由客户端自动完成。[服务器上下文][mcp]

<details>
<summary>工具代际、卸载和传输环境</summary>

同一作用域重复注册同一服务名会失败。工具列表按完整代际切换：拉取失败保留上一代，注册冲突回滚本次变更，避免混杂半套工具。公共名称与远端原名分别保存，不通过反向拆字符串猜身份。

卸载时取消重连，关闭客户端，等待连接尝试和同步收束，再注销注册项，避免旧异步回调把工具重新挂回。

本地 stdio（标准输入输出）服务是真实子进程。接入会过滤名称匹配密钥、密码、秘密、令牌模式及 `DSH_*` 的环境项，再合并显式配置，并非传入空环境。HTTP 服务有独立部署与权限。图片能否进入请求还取决于模型输入能力和附件功能；不支持时要明确诊断。[生命周期与环境规则][mcp]

</details>

<a id="scale"></a>
## 9. 工具变多以后，分别控制哪一类负担

| 负担 | 可以采取的办法 | 不能忽略什么 |
|---|---|---|
| Skill 正文 | 目录与按需加载 | 目录数量、单项描述和历史更新仍有成本 |
| 不相关工具集合 | 按任务与作用域限制 | 不能丢必需能力，本层注册还要单独检查 |
| 工具定义 | 根据路由能力使用适当呈现与延迟加载 | 标记不保证后端支持 |
| 大工具结果 | 外置、关键证据保留、按需取回 | 原件必须可访问，错误证据不能消失 |
| 长会话历史 | 合法区间压缩，保留近期尾部 | 系统头和不可分单元另有边界 |

分页任务只需文件与测试相关能力时，不必同时暴露全部业务写工具；但精简应以任务覆盖和实际请求为依据。只调一个压缩阈值不能解决所有层面的增长。

<details>
<summary>`deferLoading` 能证明什么</summary>

定义与相关投影保留 `deferLoading: true`，表示请求延迟加载工具说明；它不证明工具已经被历史事件激活，也不证明实现了通用语义工具搜索。路由拒绝、忽略或按普通工具呈现的实际行为，需要核对对应适配器。[定义源码][schema]、[能力说明][tools-readme]

</details>

## 本章小结

普通调用先确认身份和可见性，再经过策略、批准、guard、参数校验与业务执行，最后处理结果。规范值、模型文字与外部状态要分别核对；并发和取消则改变时间关系，不改变这些责任。

PTC 编排调用，Skill 提供指令，MCP 接入服务。排障时始终回到：停在哪一层，业务是否已经开始，副作用是否可能发生，下一步有什么证据。

## 🎯 面试怎么回答

**Q：为什么工具调用不能只有模型输出 JSON，再调用函数？**

> JSON 只是意图。程序还要核对当前工具视图、固定身份和参数，经过策略、批准、守卫与校验，才能执行。结果区分程序值与模型内容，并按调用关系回填。取消、后处理失败不自动撤销副作用；单次工具链与多调用调度器分别承担执行规则和并发收尾。

**Q：Skill、MCP、PTC 分别解决什么问题？**

> Skill 提供如何完成任务的指令；MCP 接入外部能力；PTC 用程序组织调用和处理中间值。三者都不替代权限与结果验证。按需加载只减少一部分上下文成本，目录、工具定义、输出和历史仍需分别管理。

## ⚠️ 常见误区

| 误解 | 正确判断 |
|---|---|
| 用户批准后必定执行 | 后续取消、guard 或参数检查仍可阻止 |
| `never` 自动批准 | 它拒绝需要审批的请求，已允许动作另论 |
| 参数冻结就是结构正确 | 不可变快照与工具结构校验不同 |
| 展示打码就保护所有通道 | 程序仍可能取得原规范值 |
| 顺序回填就没有文件竞争 | 执行体可能重叠，共享资源需协调 |
| MCP 名称可见就是服务正常 | 故障期间可能保留名称，但调用失败 |

## 自测：用状态判断，不只说术语

**任务 A：批准后被拒绝。** 编辑进入 `ask`，用户批准；guard 随后否决，业务函数未调用。审批、工具结果和文件应怎样解释？

<details>
<summary>任务 A｜提示</summary>

沿审批、guard、业务函数的顺序，分别标出哪些步骤已执行。

</details>

<details>
<summary>任务 A｜参考答案与解释</summary>

有本次允许的审批事实，但后续条件失败。工具返回拒绝或失败，本次业务函数没有修改文件；不是先写后回滚，也不是审批记录丢失。

</details>

**任务 B：展示没有秘密。** 后处理只把 `content` 改成“已隐藏”，程序调用方随后输出原规范值。为什么仍可能泄漏，应在哪个位置处理？

<details>
<summary>任务 B｜参考答案与解释</summary>

只改展示保留了原值。入口阻止不应读取的数据，结果侧控制程序可取得的值或拒绝结果，并检查其他输出通道；模型截图不足以验证防泄漏。

</details>

**任务 C：两个读取反序完成。** 模型提出 A、B；允许并行，B 在 20 毫秒、A 在 100 毫秒完成。回填顺序是什么？能否因此把任意写操作并行？

<details>
<summary>任务 C｜参考答案与解释</summary>

按 A、B 回填，B 等 A 可提交。执行重叠与提交有序不同，任意写入仍可能竞争；毫秒是题设，不是产品性能实测。

</details>

**任务 D：一百个技能仍然很长。** 正文按需加载、每项描述已限长，但请求仍含大量名称与历史目录变更。已经节省什么，尚未解决什么？

<details>
<summary>任务 D｜参考答案与解释</summary>

节省的是未使用技能的完整正文，不是全部目录及更新历史。应检查实际请求和任务作用域；延迟加载是否有效还需核对路由，不能假定已有通用搜索自动解决。

</details>
