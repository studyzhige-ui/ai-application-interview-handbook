# 04｜中断以后怎样安全继续，又怎样证明任务真的完成

[← 工具生命周期](03-tool-lifecycle.md) · [模块入口](README.md) · [源码阅读与验证实验](labs/README.md)

分页实现已经修改，测试刚开始，宿主突然退出。重启后看见上一轮对话，应该再编辑一次，还是先检查文件？

先找到可信记录，再判断外部世界已经发生什么。**能打开历史、能继续对话、能避免重复副作用、能证明任务完成，需要分别成立。** 本章先解决单个任务的恢复，再扩展到父子协作，最后把二者放进同一验收标准。故障时点与耗时例子均为教学条件，不是实测成绩。

| 阅读阶段 | 要解决的事 | 得到什么判断 |
|---|---|---|
| 一：恢复单个任务 | 可信记录、未知结果、安全重试 | 中断后下一步能做什么 |
| 二：委派给子 Agent | 历史、权限、寿命、结果归属 | 父子各自知道什么、负责什么 |
| 三：验收与诊断 | 文件、过程约束、测试、成本 | 是否完成，改造是否值得保留 |

## 一、恢复：先判断下一步，再追保存机制

<a id="semantic-recovery"></a>
### 1. 已经改了文件，却没有结果，先检查什么

先假定存储层已读出可信日志，尾部停在一个尚未结束的 Turn。模型提出了编辑，但没有可靠的最终工具结果。恢复组件会补上用于解释中断的标记，使后续模型能读到结构完整的历史。[恢复源码][repair]

| 打开的执行尾部中留下什么 | 恢复标记 | 下一步判断 |
|---|---|---|
| 助手提出调用，但未记录对应 `tool/call` | `TOOL_NOT_STARTED` | 在该受控中断路径没有启动记录；仍按任务是否需要决定继续 |
| 已有调用记录，缺少对应 `tool/result` | `TOOL_OUTCOME_UNKNOWN` | 结果未知，先检查外部状态 |
| 调用与结果成对保存 | 保留原结果 | 根据结果与任务约束继续核验 |

这些补出的错误是**合成结果**，不是恢复程序重新执行工具取得的回执。`openTurnClosers()` 处理打开的尾部，并补步骤与轮次结束；它不随意修复所有已闭合历史里的缺失结果，也不替代存储损坏检测。

回到分页文件，安全的次序是：

1. 只读检查 `pagination.py` 的内容或差异，确认预期修改是否已经存在。
2. 若修改已存在，继续检查测试，而不是因为没有结果就重复编辑。
3. 若文件与预期不同，结合原任务、实际差异和授权决定补充修改；证据不足时保留未知。

远端创建记录则需要服务端查询、请求幂等键或业务对账。**幂等**指同一逻辑请求重复提交不产生额外业务效果，不是每次重试换个随机请求号。完整跨系统协议由[后端课程](../../../curriculum/03-backend-engineering/README.md)主讲。

> ⚠️ **没有结果不等于没有执行。** 自动重试有副作用的动作前，先证明未执行，或证明可安全重复；不能确定时请求核验或人工介入。本地会话日志与外部系统不是共同事务。

Inbox 也可从已保存增删事件恢复待处理输入，但“仍在队列”“已领取”“已进入请求历史”是不同阶段。恢复需要重建 Agent 活动对象，不能从进程停止的任意一行原地继续。输入调度本身见[第一章](01-context-lifecycle.md#input)。

<details>
<summary>截取历史形成分叉时，为什么“未启动”也要查父会话</summary>

`openTurnClosers()` 支持中断与分叉两类原因。若分叉截取了父会话尚未结束的区间，子分支看不到调用记录，不代表父分支在截取后没有执行。因此分叉的恢复提示要求核验父历史和外部副作用。

这与下文进程内子 Agent 的 fork 提供方不同：后者专门选择父会话已完成 Turn 的前缀，不携带当前未完成轮次。不能因为都叫 fork，就合并两种截取规则。[修复原因分支][repair]、[子 Agent fork][fork]

</details>

<a id="durability"></a>
### 2. 哪些记录可以作为恢复依据

上一节依赖“可信日志”这个前提。Session 在内存中追加事件，只说明程序记录了它；持久化后端完成写入，才有进程退出后的恢复依据。**检查点**是在关键动作前等待这些记录保存完成的边界。

基础组合装配 `session-checkpoint-policy`：带会话身份的模型流进入下游前等待刷写，带 Agent 的顶层工具业务执行前也等待刷写；下一次输入处理边界再刷写前一步已提交结果。[检查点源码][checkpoint]

```text
记录模型提出的工具调用
        ↓
flush 成功，记录具备相应持久化依据
        ↓
检查取消，再进入工具业务执行
        ↓
外部文件发生变化
        ↓
返回并记录结果，再完成相应持久化
```

刷写失败时，该受控路径不会继续启动下游模型适配器或工具业务函数。这缩小了“做过动作却完全没有依据”的窗口，但图中外部修改与结果保存之间仍可能中断，所以结果未知仍需外部核验。

> ⚠️ **保障依赖实际组合和入口。** 插件未装配或调用绕开它的链路时，不能套用这项保证。嵌套工具复用外层的持久化边界，不为每个子调用机械增加相同检查点。

模型请求也是同样的顺序：先记录准备发送的输入，再刷写，然后构造和消费下游模型流。刷写成功证明本地记录可依赖，不证明网络已送达。[检查点源码][checkpoint]

<a id="storage-recovery"></a>
### 3. 日志文件损坏与历史格式不兼容，怎样处理

存储恢复首先回答“哪些记录可信”，不猜工具业务结果。末尾未写完与完整记录内部损坏不能混为一谈：可识别的撕裂尾部按规则恢复；完整帧的校验、解压或结构失败则拒绝读取，不能一律当作可忽略尾巴。[后端恢复规则][persistence]

格式升级也不能静默倒退。该快照的格式目录指定写入 V4，并提供相邻旧格式迁移链。若会话目录存在更高的规范代，而本构建无法解释，不能偷偷退回旧代后报告成功；新代可能包含后来发生的调用与结果。[格式目录][catalog]

**可信记录尚未取得时，先解决存储或版本问题；取得以后，才进行上一节的语义恢复和外部核验。**

<details>
<summary>存储实现：JSONL、批量同步与尾部修复</summary>

JSONL 表示逻辑上每行一条 JSON 记录；默认物理编码使用带校验和的 Zstandard 压缩帧，不是可以直接用普通逐行文本读取器读取的裸文件。

`create(header)` 可先返回写句柄而不建文件。第一次追加连同头信息以不覆盖既有目标的方式发布并同步；显式 `flush()` 也可实体化只有头信息的会话。

后续事件分批追加，每批完成 `fsync`（请求操作系统同步文件数据）后确认追加；捕获写入或同步失败时尝试恢复此前文件长度。不是每个事件无条件单独刷盘。

末行或末帧撕裂时，后端保留可完整解码的记录，首次新追加前截去破损部分，并可靠重写可恢复记录。完整提交帧的内部损坏不能按同一方式忽略。[持久化与崩溃语义][persistence]

</details>

<details>
<summary>格式迁移与单写者：完整实现的适用范围</summary>

当前目录为 V4，装配 V0 至 V4 的相邻迁移链。只读旧格式时，在内存迁移并验证，不发布新文件；写入时准备当前代、验证、重新核对源文件版本，再不覆盖地发布，旧文件保持原样。物理压缩编码转换与逻辑事件格式迁移不同，后端不自动混用两种编码根目录。[生成目录][catalog]、[后端说明][persistence]

同一会话写句柄有进程内所有权和平台锁。它保护会话日志，不阻止两个不同 Session 的工具修改同一个文件。POSIX 路径依赖原生扩展、文件锁与硬链接等能力；网络文件系统锁可能不可靠；Windows 内核信号量名称又有登录会话范围。这不是已经验证的跨主机分布式锁。[平台限制][persistence]

</details>

<a id="retry"></a>
### 4. 重试必须针对失败原因

| 失败层 | 下一次需要什么条件 | 为什么不能简单再来一次 |
|---|---|---|
| 模型暂时性请求失败 | 实际错误策略允许，预算与取消状态符合要求 | 不能重复注入相同用户输入 |
| 工具参数错误 | 修正不符合要求的参数 | 原样重试仍然错误 |
| 已确认窗口溢出 | 合法压缩真正改变当前历史 | 同一超限请求不会因重发自动变小 |
| 外部副作用结果未知 | 只读核验、幂等协议或对账依据 | 原操作可能已经完成 |

同一步模型重试保留组装结果，不重新执行 `preStep()`；错误链决定哪些失败可重试，具体策略由有效组合决定。窗口恢复要求有效历史替换前进；不可压缩的系统头或巨大单元仍可能使恢复失败。[主循环][loop]、[压缩恢复][compaction]

取消优先于重试。重试记录应能解释失败层、可重试理由、输入或状态变化和剩余预算，而不是把重试次数多当作恢复更好。

## 二、协作：把同一任务交给子 Agent 时，再增加哪些责任

<a id="subagent"></a>
### 5. 先走一次委派，再区分子任务的四个维度

父 Agent 可以让子 Agent 审阅分页边界，再整合结果。只有分工带来收益时才值得委派；多一个角色会增加传递、等待和冲突成本。

一次可理解的委派过程是：**父任务明确目标与限制 → 选择子任务的初始历史和能力 → 子任务执行并返回 → 父任务核对与整合 → 结束或保留可继续的会话。** DSH 的不同提供方在这些阶段各有实现，不能只凭“子 Agent”一个名称推断全部行为。[子任务服务][subagent]

| 维度 | 需要作出的选择 | 与其他维度的区别 |
|---|---|---|
| 历史 | 从新会话开始，还是带父会话前缀 | 不决定权限 |
| 能力 | 模型、预设、工具限制和资源权限 | 不等于复制全部父级局部状态 |
| 寿命 | 一次性返回，还是后续继续收消息 | 不由 spawn 或 fork 的名字单独决定 |
| 所有权 | 谁管理活动对象、结果与释放 | 持久会话不等于常驻进程对象 |

### 5.1 初始历史：spawn 与 fork

Spawn 从不带父会话种子的子会话开始，需要父任务明确传入背景。进程内 fork 捕获父会话截至最后一个 `turn/end` 的完整前缀；父会话没有完成过一轮时，前缀可为空。[共享驱动][driver]、[fork 提供方][fork]

例如，父会话已完成前两轮，第三轮用户刚说“只审查，不改代码”。在第三轮 fork，种子不会自动包含尚未完成的这一轮。父任务应明确传入新限制，并核对子任务权限。

> ⚠️ **fork 是快照，不是实时共享。** 父会话后续事件不自动同步。子任务答案必须来自子 Agent 自己的输出，不能把继承的父消息当成子任务已经完成的结果。

### 5.2 能力：继承组合，不等于继承全部权限

创建与冷恢复时，子 Agent 加入父 Agent 实际使用的预设组合，再安装自己的角色指导与工具限制。父级临时局部注册和限制并非全部自动复制；要让审阅子任务只读，仍需检查子作用域和底层资源权限。[子 Agent 组装][child]

进程内委派在审批能力存在时把子会话审批固定为 `never`。它表示子任务不能自行通过新审批扩大授权，不是禁止一切已允许工具，也不是继承父任务的一次性批准。需要超出范围时，应向父任务报告。

<details>
<summary>委派配置怎样捕获与恢复</summary>

模型选项优先来自父会话最近实际请求路由，尚未请求时才回退创建选项。更换模型路由但未明确推理强度，会清除旧路由的强度，让新模型解析默认值。

进程内委派在第一次异步等待前捕获显式沙箱覆盖；父级为 Auto 或 Full access 时保留相应权限预设身份，避免 fork 种子的旧身份覆盖新委派状态。相关事实追加在种子后，可由子日志重建；其他外部提供方仍需核对自身权限系统。[配置与政策源码][child]

</details>

### 5.3 寿命：会话可以保留，活动对象可以释放

One-shot（一次性）子任务产生结果后结束；continuable（可继续）子任务保留稳定身份和持久会话，后续还能接收消息。历史来源与持续寿命是两个维度，支持哪些组合取决于提供方和工具配置。[生命周期][subagent]

Activation（活跃执行实例）是在进程里实际工作的一组对象。可继续会话在需要时创建或冷恢复活动实例，空闲后可以释放；这不等于删除持久文件。当前消息授权以直接父子相邻关系为边界，不是拿到任意 Agent ID 就能跨会话发消息。

**没有正在进行的模型请求，也不一定空闲。** 实例可能有待处理消息、正在等待子任务或尚未收尾；这些活动也影响容量。对应限制仅针对特定可继续实例池，不是所有一次性与外部子任务的统一并发上限。

<details>
<summary>容量与空闲释放的具体检查</summary>

`maxActiveSubagents` 默认 8，控制连续可继续父子链中的活跃实例池。等待子任务、队列未清或正在停止的实例仍占槽位；冷恢复先取容量，给驻留子实例发消息复用槽位。容量不足接纳失败，而不是无限排队，避免父任务占槽等后代、后代却一直拿不到槽位。

释放前等待活动结束、队列清空、所属子任务收束并刷写最终状态；随后在锁内重新核对唤醒代、会话序号和队列，同步关闭新输入接纳，防止空闲判断与新消息竞争。深度、活跃数量、累计历史和 Token 成本是不同限制。[容量与收束][subagent]

</details>

### 5.4 所有权：谁负责半成品和最终收尾

启动成功返回前，创建者负责尚未发布资源，失败应清理半成品；成功交出运行句柄后，调用方承担释放责任。卸载提供方阻止后续启动，不直接撤销已接受任务。[共享驱动][driver]

释放要取消等待、停止循环、等已启动工作收束、关句柄并撤销局部注册，不是只删除一个字典项。移除活动会话也不自动删除持久化文件；当前 JSONL 服务不提供自动清理所有会话文件的保证。[存储边界][persistence]

> ⚠️ **独立 Session 不是独立操作系统或工作区。** 进程内子 Agent 不自动获得进程崩溃隔离、独立文件目录或跨文件事务；共同修改资源仍需限定范围与协调。

## 三、验收：循环结束以后，回到用户真正要求的结果

<a id="verification"></a>
### 6. 从工具结果走到任务完成

无论单 Agent 还是父子协作，最终都要核对分页任务：第一页 `[10, 20]`，第二页 `[30]`，其他既有边界符合约定，测试没有被修改。模型最终回答或 Turn 标为 `completed`，只是控制流程结束。[主循环][loop]

| 验证层 | 要检查什么 | 不能单独证明什么 |
|---|---|---|
| 单次操作 | 文件路径、编辑结果、测试命令是否实际执行 | 整项任务满足要求 |
| 过程约束 | 是否改了测试、越权或取消后继续写 | 功能一定正确 |
| 最终结果 | 实现 diff、对应版本的测试、未覆盖边界 | 中间每步都合规 |

一个结构正确的 `{ "passed": true }` 也可能没有真实测试支撑。父任务必须核对结果来源和共享资源变更，不能把子任务“成功”直接升级成整体完成。

<details>
<summary>子任务结构化结果何时正式提交</summary>

共享驱动先验证并暂存 `structured_output` 工具提供的值，等权威最终工具结果成功后提交；PTC 路径还要考虑外层 `run_code` 结果。提交后用守卫阻止继续调用。要求结构化输出却只返回自然语言时，不会自动重新询问并假装成功。[结果生命周期][driver]

</details>

<a id="trace"></a>
### 7. 用一条轨迹找回出错的位置

Trace（执行轨迹）将相关请求、工具和状态变化连起来。先用调用 ID 对应某个工具请求和结果，再用 Step 找到它属于哪次模型请求，Turn 确定轮次，事件序号还原记录顺序，Session 确定会话。[主循环][loop]

分页结果不对，可以从三条路径排查：

1. **执行者没收到限制。** 查实际请求、当前视图和子任务输入，确认“不能改测试”是否传入。
2. **输入正确但执行错误。** 查调用参数、编辑结果与文件 diff，定位错误公式怎样被写入。
3. **实现与验收不一致。** 查是否只测试第一页，以及模型为何把部分通过当成整体正确。

实时界面、会话日志和外部监控各能证明一部分。显示过的流片段未必已持久化，请求记录不证明服务商收到，重放日志也不表示重新执行工具。结果未知时，应写出证据缺口，而不是拼一个看似连贯的根因故事。

<a id="evaluation"></a>
### 8. 优化是否值得保留，要在相同标准下比较

要把单 Agent 改成父子协作，或使用 Skill、PTC，先固定任务集合、权限和成功标准。任务应包含正常修改，也包含长输出、取消、依赖错误、模型限额和工具不可用；不能改完架构再只挑成功例子。

同时观察最终完成、过程违规、端到端耗时和成本。阶段耗时与用户等待不同，模型 Token 与外部 API 费用不同；失败与取消样本不能从报告中悄悄消失。

**教学假设：** 同分布 100 个任务，A 成功 70 个，B 成功 90 个，每任务多用 60 秒。样本成功率提高 20 个百分点，不是相对提高 20%，也不保证未来相同。是否值得采用，还要看失败后果、可接受等待、成本与重复试验的不确定性。

若 B 通过修改测试才提高成功率，就没有遵守相同标准。多阶段 Skill 也要检查阶段之间的输入传递与最终整合，不能把多个局部成功相加当成系统成功。

这里是基于前述执行边界的评测方法，不声称 DSH 内置全部业务门禁或自动进化。完整评测体系仍由[通用 Agent 课程](../../../curriculum/09-agent/README.md)与相关实践承接。

<a id="test-layers"></a>
### 9. 验证报告应对应真正做过的层次

| 层次 | 保留什么 | 不能扩大成什么 |
|---|---|---|
| 源码与静态检查 | 固定提交、文件、命令与规则 | 真实服务已经执行 |
| 上游单元测试 | 环境、目标测试、通过失败与跳过数 | 所有产品路径通过 |
| 模拟集成 | 替身、初始状态、注入故障 | 真实模型和文件系统保证 |
| 真实服务 | 路由、有效配置、请求与结果证据 | 所有平台和权限组合可靠 |
| 生产或跨平台 | 平台、负载、持续时间与失败边界 | 未测环境也成立 |

[实验页](labs/README.md#first-test)给出一个真实上游恢复测试的最小入口，再扩展到模型和外部系统。记录实际 Node、pnpm 与源码 SHA；缺少凭据或环境而未执行，不计为通过。版本目标见[模块入口](README.md#source-version)。

## 本章小结

单任务恢复先取得可信日志，再补齐未结束历史的解释，并核验未知副作用；检查点缩小不确定窗口，不建立跨系统事务。委派增加历史、权限、寿命与释放责任，不能替父任务取消验收。

最后同时验证过程和结果，再用可比较样本判断成本收益。恢复成功、子任务结束与业务完成，分别需要证据。

## 🎯 面试怎么回答

**Q：文件已改，工具结果没保存，重启后怎么办？**

> 先保留结果未知的判断。DSH 对打开尾部中已有调用而缺少结果的情况补 `TOOL_OUTCOME_UNKNOWN`，不是自动重做。文件操作先只读核验，远端写入依赖查询、幂等或对账。动作前刷写提供本地记录依据，但本地日志与外部系统没有因此成为共同事务。

**Q：怎样验证多 Agent 改造有效？**

> 固定任务、授权与成功条件，比较完成率、违规、耗时和成本。检查新要求是否传入子任务，权限是否匹配，父任务是否正确整合，失败后资源是否收束。局部成功不能替代整体验收；源码判断、单元测试和真实服务记录分开报告。

## ⚠️ 常见误区

| 误解 | 正确判断 |
|---|---|
| 恢复历史就是从崩溃行继续 | 活动对象重建，外部结果可能未知 |
| 合成错误是重试工具的回执 | 它只是根据已保存事实补中断标记 |
| 新格式读不懂就退旧代最安全 | 可能遗漏后续事件，必须明确失败 |
| fork 带走当前轮全部新要求 | 进程内子 fork 取已完成 Turn 的前缀 |
| 没在请求模型就不占活动容量 | 等待、队列和收尾也可能占用 |
| 完成标记或合法 JSON 证明修复正确 | 仍需文件、测试与过程约束证据 |

## 综合自测：从证据推导下一步

**任务 A：只有调用，没有结果。** 持久记录有编辑调用，无结果；磁盘文件已经包含预期修复。恢复标记、下一步动作与不能自动采取的动作分别是什么？

<details>
<summary>任务 A｜提示</summary>

先区分日志中的结果缺口，与只读检查已经能观察到的外部状态。

</details>

<details>
<summary>任务 A｜参考答案与解释</summary>

标为 `TOOL_OUTCOME_UNKNOWN`。先只读核对内容或差异，再检查是否仍需编辑与测试；不能自动重复写，也不能因结果缺失擅自恢复成旧文件。

</details>

**任务 B：新限制未进入种子。** 前两轮完成，第三轮用户说只审查；父 Agent 此时 fork，只传“继续处理分页”。子任务必然知道新限制吗？

<details>
<summary>任务 B｜参考答案与解释</summary>

不能保证。当前轮不在已完成前缀中，父任务应明确传入只审查要求，并配置子作用域与资源限制，而不只依赖历史种子。

</details>

**任务 C：同时存在 V3、V4、V5。** 本构建支持并写 V4，却发现同一会话更高的规范 V5 代。能否忽略 V5，以 V4 报告恢复成功？

<details>
<summary>任务 C｜参考答案与解释</summary>

不能。V5 可能保存更晚事件。应报告选中代不受支持并保留文件，用兼容构建或明确迁移方案处理；不能静默回退诱发重复动作。

</details>

**任务 D：成功率提高但违反约束。** A 的 100 个任务成功 70 个；B 报告 90 个，其中 15 个修改了被禁止修改的测试。能否直接报告提高 20 个百分点？

<details>
<summary>任务 D｜参考答案与解释</summary>

不能。B 未按相同成功标准统计。逐项重验约束，保留违规和失败，检查其他样本、重复运行与成本；不能机械减 15 后就假定余下全部已严格验收。

</details>
