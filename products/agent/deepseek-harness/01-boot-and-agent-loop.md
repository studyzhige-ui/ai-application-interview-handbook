# 启动与循环｜组合怎样变成正在工作的 Agent

[← 产品入口](README.md) · [本产品目录](README.md) · [下一章 →](02-tools-files-and-jobs.md)

先选出实际启动的组合，再建立 Agent 与 Session，最后才接受输入并请求模型。分页任务仍是教学场景；本章中的表格描述事件关系，不是产品实测日志。

<a id="boot"></a>
## 从配置到可运行服务，再到 Agent

DSH 使用 Cordis 插件框架。**Plugin** 实现一个职责并把接口注册到应用上下文 `ctx`；**Bundle** 分发一组插件配置；**Profile** 选择这次启动的组合和覆盖层。这里的 `ctx` 供程序取得服务，不等于送给模型的上下文。主循环也由插件提供，不能先假设“框架启动后所有能力都在”。

启动器先载入环境和 Profile，按 Bundle 顺序与用户覆盖层得到有效配置，再加载插件。替换某行 `config` 是整行替换，不是逐字段深合并；YAML 中先写某插件，也不保证它先启动，真正激活取决于服务依赖。插件注册撤销后，相应工具和监听器也退出当前组合。

可选插件启动失败时，保留能工作的插件并输出诊断；启用且必需的执行或界面入口启动失败，则释放整个应用并以失败结束。配置中原本没有某必需入口，或它明确禁用，不因为在全局必需名单里就强迫所有 Profile 装配。Bundle 加载失败可以跳过，但剩余组合能否提供必需服务仍须检查。[启动合同](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/boot/app-boot/README.md)

本次快照还在受启动器管理的装配边界，检查插件声明的 DSH peer 版本范围。普通不兼容条目在运行副本中禁用，不兼容 Bundle 被跳过；不会改写用户保存的配置来伪装已安装成功。这是兼容性准入，不是隔离恶意插件代码的安全沙箱。

基础组合包括主循环、会话、文件观察、作业、计划、目标、子 Agent 与工作流等能力。`web`、`headless`、`acp`、`sdk` 使用各自组合；`sdk-minimal` 是不套用 base 的独立组合。因此本章之后提到“基础组合默认装配”时，不能直接外推到最小 SDK。[有效基础组合](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/bundle/base/cordis.patch.yml)

服务就绪后，创建或恢复 Session，以它记录事件；再建立 Agent 活动对象、作用域和 Inbox。Session 可以跨进程保留，活动中的请求、取消信号、文件观察缓存和进程句柄不能靠读日志原样复活。

<a id="request-chain"></a>
## 先走完一次修复：一次任务为什么要请求多次模型

假设每一步只提出一个工具调用，所有工具正常返回，期间没有取消：

| 步骤 | 这次请求已有的依据 | 模型提出什么 | 程序执行后新增什么 |
|---:|---|---|---|
| 1 | 修复要求、不得修改测试的规则 | 读取 `pagination.py` | 实现文件的内容 |
| 2 | 原有要求，加上读取结果 | 修正实现 | 编辑工具的结果 |
| 3 | 原有历史，加上编辑结果 | 运行测试 | 退出状态与测试输出 |
| 4 | 相关修改与测试证据 | 给出结论，不再请求工具 | 助手回复，本轮可以结束 |

**工具结果通常供后续模型请求使用，不会倒流进已经发出的请求。** 因此第二步可以根据真实代码提出修改，第一步却不能假定自己已经读过文件。[主循环与工具调度][loop]

DSH 为这两层进度分别命名：

- **Turn（轮次）**：Agent 被唤醒后的一段工作，可能包含多次模型请求。
- **Step（步骤）**：其中一次逻辑模型请求，以及该回复提出的工具调用。请求失败时，一个 Step 可以有多次尝试；重试不自动成为新 Step。

表中的四步是一种可能过程，不是产品固定计划。模型可在一步提出多个调用，工具也可要求结束轮次。**循环停止只说明这一轮不再继续，不证明分页已经修复；结论仍需对照文件和测试。**

<a id="views"></a>
## 有记录，为什么不等于每次都会发给模型

Session（会话）按顺序追加事件。用户输入、模型回复、工具结果属于其中一部分；步骤开始、失败尝试、压缩决定也会留下记录。这些事件用途不同，不能把整份日志直接当成模型消息数组。

**Surface（当前消息视图）**从事件中确定仍有效的消息及顺序。`deriveMessages()` 再把这个视图转成请求使用的消息。可以先用一组具体变化理解：

| 内容 | 压缩前的当前视图 | 成功压缩后的当前视图 | 原事件日志 |
|---|---|---|---|
| 任务及不能改测试的约束 | 可见 | 应在保留内容或摘要中继续表达 | 保留已记录事件 |
| 较早的一段完整读取调用与结果 | 原文可见 | 被该区间的摘要替换 | 原调用、结果仍在 |
| 近期的测试调用与结果 | 原文可见 | 作为近期尾部保留 | 原调用、结果仍在 |
| 一次失败尝试的诊断 | 不作为普通助手回复发送 | 仍不是普通助手回复 | 可供排错检查 |

表中假定压缩器找到了合法区间，并成功保留了约束。它不表示任意选几条消息都可压缩，也不保证模型摘要天然无遗漏。

这里实际有四层：**事件日志保存记录；Surface 决定当前有效历史；派生消息提供本次消息列表；完整请求还包括模型路由、参数和工具定义。** 同一份日志可以保留旧内容，同时不再把旧内容原文发送。[Surface 派生规则][surface]

用户的历史界面、模型请求和排错程序因此有不同需要。界面仍可展开旧文字，不表示模型这次仍收到它；模型看见摘要，也不表示审计原件已删除。

<details>
<summary>读源码时：哪些事件不产生模型消息</summary>

空的系统节点可以保留位置，却不产生空系统消息。`assistant/attempt` 保存失败尝试，不作为新的助手回复进入历史；`turn/start`、`step/end` 是执行边界，不是聊天文字。核对一个事件是否可见，要看 `deriveEventMessage()` 和 Surface 对它的处理，不只看记录里有没有一段文本。[源码][surface]

</details>

<a id="input"></a>
## 运行中补充要求：等下一步，还是留给下一轮

模型正在分析代码时，用户补充“第二页应返回 `[30]`”。已经发出的请求无法被追溯改写。DSH 用 Inbox（待处理输入队列）保存补充，再在后续边界领取。

| 入口 | 放到哪里 | Agent 空闲时是否唤醒 | 适合怎样理解 |
|---|---|---|---|
| `followup(message)` | 下一轮 `next-turn` | 是 | 排入下一轮任务 |
| `steer(message)` | 下一步 `next-step` | 是 | 让新要求参与后续步骤 |
| `inject(message)` | 下一步 `next-step` | 否 | 先放背景，等任务唤醒后使用 |

例如，空闲时先 `inject(项目背景)`，不会仅因此发起一次模型请求；后来 `followup(修复分页)` 唤醒 Agent，这份背景才获得在输入处理阶段参与的机会。最终是否被接纳，还取决于输入处理与取消状态。[三个入口及共同的 `send()`][loop]

> ⚠️ **入队、领取、成为请求输入，是三个时点。** 看到“已加入队列”不能推断模型已经收到；队列恢复与领取中断的问题在[会话与恢复章](05-session-and-recovery.md#semantic-recovery)结合持久化分析。

<details>
<summary>输入处理的变体：取消、插件拒绝与没有 Step 的 Turn</summary>

三个方法最终都调用 `send()`；`inject()` 的唤醒参数为 `false`。取消默认清空 Inbox，显式保留需使用 `keepInbox`。已取消的活动不能被新唤醒消息原地复活。

循环先记录 `turn/start`，再处理首次输入。`agent/pre-step` 是可串联的输入处理入口；处理器通过 `next()` 交给后续插件，不调用可能截断处理链。若拒绝进入步骤，或首次接受结果变为空，Turn 可以结束而没有 Step，也就没有这一步的模型用量。[`preStep()` 与 `turn()`][loop]

Inbox 用 `agent/inbox/spliced` 记录增删，领取也会移除队列项。已保存事件可用于重建队列，但不能把它扩大成“领取到请求提交之间的每次中断都已实现恰好一次”。[队列源码][inbox]

</details>

### 忙碌、维护和取消收束期间，唤醒怎样落地

活跃循环会在允许边界领取排队消息。维护任务或已取消但尚未收束的活动不能直接接管新唤醒，先记下唤醒请求；回到 idle 且队列仍有待处理内容时才重放。卸载不保留这个自动唤醒，避免清理流程又启动新模型任务。

每轮先写 `turn/start`，再领取输入并通过 `agent/pre-step`。拒绝进入形成 `blocked`；首步骤接纳后变为空，则可以零次模型请求正常结束。循环不是“每次 send 都必定调用一次模型”。某一步达到输出上限后，`max-tokens` 结果保持到本轮结束，后续普通完成不会把它覆盖成无异常成功。

没有工具后续时先执行 `agent/turn-stopping`，插件仍可加入下一步输入；队列仍为空才关闭本轮。这正是后台作业通知和目标驱动需要接到明确边界的原因。[活动阶段与继续条件](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/core/agent-loop/src/agent.ts)

<a id="assembly"></a>
## 组装请求：任务、规则、历史和工具说明在哪里汇合

在一次步骤开始前，主循环领取输入，并收集当前系统提示与工具定义，再让运行背景和输入插件参与处理。模型最终需要的不是“程序里的所有对象”，而是经过这些步骤形成的消息和调用说明。

| 来源 | 告诉模型什么 | 在分页任务中的例子 |
|---|---|---|
| 系统提示片段 | 角色与行为约束 | 编码助手的工作方式 |
| 当前作用域的工具定义 | 可请求哪些操作、参数怎样组织 | 读取工具需要文件路径 |
| 用户输入与项目背景 | 本次目标及适用规则 | 只修改实现、不能改测试 |
| Session 派生历史 | 前面已发生的相关事情 | 读取结果、修改结果、测试失败 |

工具定义只有名称、用途和参数结构，不包含业务执行函数。第一步里出现 `read` 的说明，表示模型可以提出读取，不表示文件已经读取。可见性与真实执行规则在[工具章](02-tools-files-and-jobs.md#visibility)继续展开。

Cordis 的 `ctx` 则是**程序访问服务的应用上下文**。连接、配置或凭据挂在 `ctx` 上，不会因此自动进入模型提示词。不要把这两个“上下文”混为一谈。[请求组装][loop]、[服务分工][architecture]

### 项目规则从哪些目录来

假设当前工作目录是项目根，根目录与 `backend/` 各有一份 `AGENTS.md`。首次请求得到用户全局说明，以及项目根到当前工作目录的适用链；**不会先装入整个仓库所有子目录规则**。

成功的第一方 `read`、`write`、`edit` 会产生结构化文件活动。访问更深目录后，指令插件据此发现适用规则，并在后续请求中反映新增、变化、删除或重复。未变化的规则抑制重复注入；恢复会话时重新对齐基线。[发现与刷新规则][instructions]

这些项目说明作为带来源的用户角色消息进入历史；即使文本由 `<system-reminder>` 包裹，也不因此获得系统角色或写入权限。

> ⚠️ **嵌套规则应在修改前核对。** 写后能够发现规则，不能替代事前阅读与授权。任意 Shell 字符串中的 `cd backend` 也不等于结构化文件发现；插件不是持续监视所有外部编辑的文件监听器。

<details>
<summary>规则过长时：按整个消息的字节预算取舍</summary>

基础组合给完整渲染后的规则消息分配 65,536 字节，即 64 KiB。它不是 Token 数，也不是每个文件各有一份预算。超限时先省略更宽泛的整份规则，再考虑截断最具体规则，并显示遗漏提示。规则没被遵守时，应核对适用范围、发现时机、预算提示和实际消息，不能立即归因为模型不听话。[预算规则][instructions]、[基础组合][base]

</details>

<a id="admission"></a>
### 从“接受任务”到“发出请求”，还要准备真实模型路由

路由在这里表示本次由哪个适配器、模型和有效参数处理请求。准备它可能需要异步解析凭据，所以输入插件接受任务之后，仍可能因取消或准备失败而没有实际发送。

1. **领取与组装。** `preStep()` 领取输入，`systemPrompt.assemble()` 组装提示与工具，输入插件接纳或拒绝消息。
2. **开始步骤。** 接纳后记录 `step/start`。
3. **准备路由。** `prepareRequest()` 执行 `agent/request`，再由 `llm.prepareCall()` 绑定实际能力；异步阶段后检查取消。
4. **提交输入。** 协调系统提示，首次尝试追加已接受的用户消息，按需记录请求条件。
5. **构造请求。** 从会话派生消息，冻结请求数据，再调用已绑定的模型流。

冻结防止已经构造好的请求被共享引用悄悄改写；取消信号仍保持活动。准备阶段取消，不提交这批系统与用户消息。[`step()`、`prepareRequest()`、`buildRequest()`][loop]

> ⚠️ **本地记录不等于远端确认。** 第 4 步后、网络发送前崩溃，远端可能一次也没收到；远端已处理而本地没保存结果，也可能发生。逻辑日志能否持久恢复，还要看[检查点](05-session-and-recovery.md#durability)。

<details>
<summary>请求头、同一步重试与辅助请求的边界</summary>

`request/header` 保存解析后的配置和活动工具定义；`request/context` 保存窗口容量、系统提示更新方式等路由能力，不是再复制全部聊天。

同一步的尝试循环用 `firstAttempt` 控制用户消息只提交一次。重试重新准备路由和请求，不重新调用 `preStep()`；恢复插件若改变了 Surface，后续构造才会读到变化。

上述输入可重建约束针对 Agent Loop 主请求。压缩器有辅助请求，不能推导成进程中每个辅助模型请求的每个字都以同样方式保存。[主循环][loop]

</details>

<a id="stream"></a>
## 回复和工具结果怎样回到下一步

模型流开始后，界面逐步显示文字。流结算时，主循环保存对应回复；若回复提出工具调用，程序进入工具执行链，结果再按调用关系写回历史。下一步从这份更新后的历史组织请求。

因此正常循环是：**请求读取文件 → 得到真实读取结果 → 下一次请求依据结果修改**，而不是模型说了工具名就直接拥有结果。工具附带的 `additionalContexts`（额外背景）也按来源进入下一步输入，不修改已发送请求。[流与结果处理][loop]

没有工具调用时可以结束本轮；成功工具也可明确结束轮次。最终是否满足任务仍由实际文件差异、测试和授权约束决定。

<details>
<summary>流中断时：已经显示的文字是否一定能恢复</summary>

`agent/assistant-stream` 发出进程内开始、片段和结束事件；一次流结算后，再保存紧凑流及消息或失败尝试。硬崩溃发生在结算前，不能保证所有已显示片段都有持久副本。

取消后已有可保留内容时，可能形成带 `interrupted` 的 `assistant/message`；无内容或失败尝试则使用只记日志的 `assistant/attempt`。两者进入模型历史的规则不同，不能把所有取消都画成同一种消息。[流结算源码][loop]

</details>

<a id="prompt-update"></a>
## 提示发生变化时，怎样让下一次请求使用新规则

项目可能更换提示片段或工具集合。下一次请求需要使用有效规则，而不是让新旧说明同时互相矛盾。DSH 根据实际路由能力协调系统节点：支持历史中更新的路由可接收后续更新；不支持时，就把有效系统提示放回请求头部。[提示协调][architecture]

这里的目标是形成适配器能够表达的一份一致请求，而不是假定所有模型接口支持相同消息形状。工具变化也可能产生有记录的开发者消息，便于重建声明增减。

<details>
<summary>继续追实现：空提示、请求序列与缓存前缀</summary>

主循环预留首个系统节点。路由支持历史更新时，非空变化可追加在已缓存历史后；不支持或开始新请求序列时，把有效提示协调到首节点，清空后续失效系统节点。空提示表示清除旧有效提示，不是沿用旧提示。

请求序列标记可连续解释的一组请求条件，不等于用户新建会话。压缩替换、图像外置等历史变化会开启新序列；普通恢复若视图未改，不必丢弃可复用前缀。

相同前缀有机会利用模型服务的 KV Cache（键值缓存）减少重复计算。能否命中仍取决于服务端、路由、工具顺序及序列化，不能保证命中或免费。[协调实现入口][loop]、[架构说明][architecture]

</details>
