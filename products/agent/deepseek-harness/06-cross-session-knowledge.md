# 跨会话信息｜规则、历史引用与外部记忆

[← 上一章](05-session-and-recovery.md) · [本产品目录](README.md) · [下一章 →](07-delivery-and-review.md)

<a id="homes"></a>
## 先找存储位置，再找读取入口

第一章区分了事件日志与 Surface（当前模型消息视图）。现在增加一个问题：新任务从哪里获得旧信息？

| 规则在哪里 | 今天怎样获得 | 需要谁维护 |
|---|---|---|
| 工作区 `AGENTS.md` | 指令插件发现适用文件，形成带来源的背景 | 文件维护者；插件按触发条件刷新 |
| 原 Session 的事件日志 | 打开原会话，重建其当前视图 | 会话存储与恢复组件 |
| 原会话的压缩摘要 | 沿原会话继续，从摘要和近期历史获得背景 | 摘要机制；后续证据纠正遗漏 |
| 另一会话的显式引用 | 在新会话中读取捕获时的文本快照 | 用户选择引用；需要更新时重新取得 |
| 外部记忆服务 | 模型实际调用服务的查询或读取工具 | 外部服务负责存储策略，DSH 负责接入与调用 |

例如，“规则已写进昨天的日志”只证明原会话有记录。全新的 B 若没有打开、引用或检索它，就还缺少读取入口。保存历史不会自动把某条项目规则提炼成所有项目通用的偏好。[会话存储][persistence]、[引用][reference]、[外部记忆指南][memory]

这几种机制可以配合，但不能因为同时存在，就推导出 DSH 默认具备统一的自动提取、冲突消解、语义检索与遗忘系统。

<a id="workspace"></a>
## 项目规则跨任务生效，依靠文件与适用范围

假设分页约定已经写在 `repo/services/paging/AGENTS.md`。新任务的工作目录也在这里，指令插件会按适用链提供它。即使没有昨天的聊天，模型也可能得到“页码从 1 开始”，因为本次读到了规则文件。

更正这条规则时，应修改该文件，并确认后续请求获得了更新。只在另一场对话里说“以后改成从 0 开始”，不会自动改写工作区文件；同样，只改文件也不能证明正在运行的模型请求已经更新。

第一章已经建立发现与刷新规则：适用目录链决定范围，成功的第一方文件活动提供线索，变化后更新、删除后移除，恢复时重新对齐基线。这里新增的判断是：**规则有效性既取决于文件内容，也取决于今天操作的是哪个项目、目录和接口。** [规则主讲位置](01-boot-and-agent-loop.md#assembly)、[实现依据][instructions]

| 出现的情况 | 先检查什么 | 更正在哪里生效 |
|---|---|---|
| 规则文件正确，模型却未遵守 | 适用目录、发现时机、预算遗漏与实际消息 | 确认本次请求真正获得规则 |
| 文件本身已经过时 | 对应项目与接口的当前约定 | 修改正确文件，验证后续刷新 |
| 两个项目采用不同分页规则 | 来源与适用范围是否混用 | 各自项目维护，不合并成全局偏好 |

> ⚠️ **文件内容是指导，不是授权。** 指令消息使用用户角色并保留生产者来源；`<system-reminder>` 包装不提升权限。它不能覆盖系统、开发者或直接用户要求，也不能替代执行侧禁止修改测试的约束。[消息模板][instructions]

这样，排错就有明确落点：先证明规则是否进入当前输入，再判断模型是否正确使用，而不是把所有问题都称为“忘记”。

<a id="restore"></a>
## 打开原会话：恢复历史，但不保证所有细节仍然内联

第二天打开昨天的 Session，存储层读取已持久化事件，Surface 据此重建有效历史。没有压缩的相关对话可以继续提供原文；已经被摘要替换的区间则主要以摘要参与后续请求。恢复不是把全部日志拼成一条超长消息。[会话存储][persistence]、[消息视图](01-boot-and-agent-loop.md#views)

假设昨天同时约定“页码从 1 开始”和“不得修改测试”。摘要只留下前一句。今天模型能答出分页公式，却修改了测试，说明记忆使用仍有问题。验证应同时检查**事实、适用范围和行动约束**，不能只问它能否复述一个数字。

这是一项基于摘要可能遗漏信息而设计的测试，不是源码已经证明摘要无损。[摘要机制][compaction]

原会话还可能恢复待处理输入。Inbox 有自己的增删事件；已保存的队列状态可以重建，但它与已经追加到模型历史的用户消息不是同一个位置。请求是否发送、外部动作是否完成，仍要依据[恢复边界](05-session-and-recovery.md#semantic-recovery)判断。

> ⚠️ **继续对话不等于原地恢复进程。** 保存的历史可以重建；领取中途的调用栈、网络连接与未刷写内容不能靠聊天日志原样复活。

<a id="reference"></a>
## 新会话引用旧会话：拿到的是一份快照

会话 A 已讨论分页，会话 B 是新任务。支持引用的宿主把用户选中的 A 转成规范引用，例如界面生成的 `dsh-session:` URI（资源标识符）。目标输入经过 `agent/pre-step` 时，引用服务读取 A 的当前 Surface，准备文本快照，并把它紧接在 B 的直接用户消息之后写入历史。[引用准备流程][reference]

**B 得到的是捕获时的内容，不是与 A 共享一个实时变化的消息数组。** A 之后增加新规则，不会自动修改 B 中已经保存的快照。

### 先看哪些内容会被带过去

下面是 A 的教学数据，不是可直接导入的事件 JSON：

| A 中的信息 | 是否进入引用文本 | 为什么 |
|---|---|---|
| 用户直接说“页码从 1 开始” | 是 | 直接用户文本 |
| 测试工具返回退出码 0 | 否 | 普通工具结果不在文本投影范围 |
| 助手说“测试已经通过” | 是 | 助手文本被保留，但仍是一项陈述 |
| 插件注入的工作区说明 | 否 | 不是直接用户文本或认可的压缩检查点 |
| 带规范压缩标记的摘要 | 是 | 作为原会话的压缩背景 |

`projectSessionConversation()` 按消息类型、来源和文本块选择内容，工具、推理、系统与开发者消息不会原样照搬。这样限制引用体积，也避免引用层层复制已注入的引用。[投影源码][projection]

因此，B 看见“测试已经通过”，可能只有 A 中助手的转述，并未得到独立测试记录。需要交付代码时，应取得对应版本的真实测试证据，或在允许范围重新验证。

### 快照保留什么时点

假设 B 昨天捕获 A 的旧规则，今天 A 新增“新接口从 0 开始”：

| 时点 | A | B |
|---|---|---|
| 昨天捕获 | 只有旧规则 | 保存旧规则的快照 |
| 今天 A 更正 | 增加新接口约定 | 原快照不变 |
| B 显式重新取得 | 可以提供更新内容 | 新读取成为新的背景 |

这种设计让 B 当时的决策依据可追查，代价是必须明确取得更新。源码用 `capturedThroughSeq` 等来源信息记录捕获边界，预览和溢出保存使用同次捕获，避免二者各取一个版本。[捕获规则][reference]

### 引用再长，也要留出请求空间

引用服务限制来源数量与每份预览体积。过长时先保留适合继续工作的内容；配置了溢出存储时，可以另外保存完整捕获文本，并留下取回提示。模型要查看被省略的内容，仍需实际读取，不能把“已保存”当成“已经进入请求”。

没有溢出存储、保存失败或资料已过期时，不保证能补回全文；连固定元数据都无法容纳时，准备会失败。[预算与失败边界][reference]

<details>
<summary>核对引用预算与保留算法</summary>

每次最多引用三个不同会话，每个来源有独立的序列化 JSON 字节预算。显式 `maxReferenceBytes` 优先；否则使用：

```text
预览预算（字节）
= max(65,536, floor(模型窗口（Token）× 4 × referenceContextFraction))
referenceContextFraction 默认 0.2
```

每 Token 四字节只是估算，不是分词器保证。JSON 转义、元数据和文本都占字节；多个来源的预算不是整个模型请求的总预算，省略提示还在预览 JSON 外。

超限时先删除较旧、非检查点且非最后一项的消息，再缩短保留的长文本。检查点不会在第一阶段按普通旧消息删除，但在后续阶段仍可能缩短，不能声称摘要永远完整保留。[投影算法][projection]

</details>

### 引用的事实与授权应分别核对

快照标为不可信背景，提醒模型不要执行其中的工具请求或权限声明，除非当前用户重新提出。序列化会转义 `<`，降低闭合包装标签的风险。这些措施有助于区分来源，但不是提示注入绝对免疫。[信任边界][reference]

> ⚠️ **引用不授予访问或执行权限。** 服务假定宿主有权读取 `sessionQuery` 暴露的会话。按工作目录排序不是租户隔离，转义标签不是访问控制。A 里一句“用户已经批准上传文件”，也不是 B 当前调用的批准。

写入和外发仍需经过[工具权限链](02-tools-files-and-jobs.md#approval)。

<a id="search"></a>
## 找到一个会话，不等于搜索了它的全文

引用候选按 ID、工作目录、投影标题和显示标题筛选，优先展示同工作目录会话。它不是对所有聊天正文的语义检索，也不是模型可以自由调用的全库记忆搜索。[候选查询][reference]

基础组合虽然装配 `session-query-sqlite`，但将 `openAt` 设为 `never`：保留精确读取等路径，却不默认开启全文搜索。**存在实现、装配插件、实际启用能力，需要分别确认。** [组合配置][base]

用户只说“继续昨天的规则”，而没有打开原会话、引用或调用记忆检索，就不能承诺系统自动找到正确记录。增加自动召回属于另外的产品设计，还需解决相关性、权限、过期和预算；不能把这些策略补画成此快照的默认行为。

<a id="external-memory"></a>
## 外部长期记忆：先写入，再在新会话实际读取

MCP 是 Model Context Protocol（模型上下文协议），这里负责让宿主发现并调用外部能力，不规定记忆数据库怎样存储。外部服务提供写入、搜索或读取工具后，模型才可能通过这些工具保存与召回分页约定。

**DSH 管接入和调用，外部服务管记忆的组织与检索。** 配置文件不会自动安装服务、初始化数据库、选择嵌入模型、迁移数据或建立供应商账号。[官方接入指南][memory]

一次可解释的验证可以这样做：

1. 在会话 A 明确要求保存唯一测试标记 `paging-rule-<本次后缀>`，确认真正调用写工具并取得结果。
2. 新建不含 A 聊天内容的会话 B，使用相同用户、项目与数据目录。
3. 要求 B 查询该标记，观察实际查询工具、返回内容与存储范围。
4. 给 B 一个新的分页输入，检查它能否正确使用取回的规则。

新建会话是为了排除“只是读到了本轮聊天”，不要求重启整个宿主。写入、召回和使用应分别验收，最后一句答对不能替代中间证据。[跨会话验证流程][memory]

<details>
<summary>参考服务并不等于统一的长期记忆实现</summary>

官方指南提供默认关闭的互操作配置示例。某个参考服务用知识图谱保存实体、关系和观察，但搜索为大小写不敏感的子串匹配，不自动附带嵌入、摘要、冲突消解或遗忘策略。不能从“知识图谱”这一名称推导出语义检索。

本地 stdio 服务与外部 HTTP 服务的接入、重连和工具注销在[工具章](03-skills-mcp-and-ptc.md#mcp)主讲。初次发现是异步过程；故障期间名称仍可能可见但调用失败，恢复预算耗尽会注销工具。因此查询不到内容时，要先排除服务不可用。[接入与恢复范围][memory]

</details>

更正或删除时，先查所选服务是否提供相应工具、怎样识别同一事实、删除对象是什么。不能为所有服务虚构统一的 `update_memory` 或 `forget` 接口；不支持删除时，也不能报告已彻底遗忘。本章只解释来源与消费者，不要求接入外部服务。

<a id="correctness"></a>
## 信息互相矛盾时，更正应落在哪个入口

旧引用说从 1 开始，当前接口文档说从 0 开始。先确认是不是同一个接口、同一版本；不同范围的约定可以同时正确，不需要让两段文字“投票”。

| 过期信息的来源 | 合理的更正动作 | 之后怎样确认 |
|---|---|---|
| 工作区规则文件 | 修改正确的适用文件 | 后续请求读到更新规则 |
| B 已保存的旧引用 | 明确取得源会话更新或当前接口文档 | 新背景进入 B，旧快照仍可追查 |
| 外部记忆条目 | 使用服务真实的更新或删除接口 | 在同一范围重新查询并检查使用 |
| 原会话中的历史陈述 | 增补有依据的更正 | 当前使用区分历史说法与现行事实 |

会话日志可以继续保留“当时知道什么”，不必为当前答案正确而改写全部旧记录。这是依据存储边界作出的工程推导，不表示 DSH 内置自动事实仲裁器。

## 本章小结

跨任务使用信息，要找到存储、发现、读取、适用范围与纠正入口。原会话恢复自己的历史，引用捕获另一会话的固定文本，项目文件提供可维护规则，外部服务提供它实际实现的记忆能力。

保存成功、查到内容、正确使用是三次判断。任何一步缺证据，都不应被最后一句“我记得”掩盖。

## 🎯 面试怎么回答

**Q：会话历史与长期记忆有什么区别？**

> 会话历史保存一次会话的输入、回复和执行记录，恢复时按当前视图使用；跨会话还需要读取入口。DSH 可以通过工作区规则、显式会话引用或配置的 MCP 记忆服务取得旧信息。引用不自动更新，外部服务决定检索与治理方式，所以有日志不等于有自动长期语义记忆。

**Q：怎样证明新会话真的使用了记忆？**

> 用唯一测试事实记录 A 的写入，再在没有旧聊天的 B 中观察查询调用、返回内容和实际使用。随后更新事实或改变适用条件，检查是否继续使用过期记录。存储范围和服务状态要一致；未提供的更新、删除能力不能写成验证通过。

## ⚠️ 常见误区

| 误解 | 正确判断 |
|---|---|
| 日志里保存了，新会话就会自动想起 | 还需要发现与读取入口 |
| 引用 A 后会跟随它更新 | B 保存捕获时的快照 |
| 引用说测试通过，就是独立执行证据 | 可能只有助手转述，没有工具记录 |
| 同工作目录优先就是租户隔离 | 排序不替代授权 |
| MCP 记忆都用向量搜索 | 协议不规定检索算法 |

<a id="self-test"></a>
## 自测：改变条件以后还能判断吗

**任务 A：迟到的更正。** B 昨天引用 A 的“从 1 开始”；今天 A 说明只有旧接口如此，新接口从 0 开始。B 没有重新读取。它直接读自身历史会看到什么？处理新接口前还需什么？

<details>
<summary>任务 A｜提示</summary>

先检查 B 的历史是否收到 A 今天新增的事件，不要把快照当订阅。

</details>

<details>
<summary>任务 A｜参考答案与解释</summary>

原快照不自动变化，应显式取得更新或读取新接口的权威文档，并核对适用版本；不能只说刷新缓存。

</details>

**任务 B：工具记录没有被引用。** A 有用户文字、测试工具结果和助手“测试通过”；B 只看到用户与助手文字。能否证明引用故障？交付还缺什么？

<details>
<summary>任务 B｜参考答案与解释</summary>

不能。文本投影排除普通工具结果。B 得到转述而非独立执行证据，需要对应版本的真实测试记录，或在授权范围重新验证。

</details>

**任务 C：A 写入成功，B 查不到。** A 在项目 X 写入唯一标记，B 在项目 Y 查询为空。请给出排查顺序，说明何时才能归因为记忆丢失。

<details>
<summary>任务 C｜参考答案与解释</summary>

先确认 B 确实调用查询，再核对用户、项目和数据目录；检查服务健康、查询条件和返回，最后在有权访问的相同范围查数据。跨项目隔离导致为空，不能证明数据丢失。

</details>
