# 01｜上下文生命周期：模型这一轮究竟看见什么

[← 模块入口](README.md) · [下一章：记忆](02-memory-lifecycle.md) · [源码版本](README.md#source-version)

分页函数的错误很小，但模型不能凭空知道文件内容。用户说“只改实现”，项目规则说“不要修改测试”，读取工具返回了函数，前一轮还有一次失败的测试结果。这几类信息从不同入口到来。**本章要解释的不是怎样拼一个更长的提示词，而是这些信息何时进入请求、以什么形式进入，以及哪些信息不会进入。**

先把分页任务当作一次正常交互：用户发来需求，Agent 读取实现，模型根据读取结果提出修改，最后查看测试结果。下面的时间线都是按源码规则推演的教学示例，不是模型服务的真实运行日志。

<a id="input"></a>
## 1. 收到输入，不表示正在运行的请求已经改变

Agent 有一个 Inbox（待处理消息队列）。队列解决的是“下次在什么边界消费消息”，不是把文字追加到正在传输的请求中。假设模型正在分析 `pagination.py`，用户补充“页码从 1 开始”。程序不能回到过去修改已经发出的请求，只能决定这条补充何时参与后续工作。

源码提供三种入口，它们的区别同时包含**进入位置**与**是否唤醒执行**：

| 入口 | 待处理位置 | Agent 空闲时是否启动工作 | 对分页任务的含义 |
|---|---|---|---|
| `followup(message)` | 下一轮 `next-turn` | 是 | 作为下一轮用户任务处理 |
| `steer(message)` | 下一步 `next-step` | 是 | 让补充需求参与后续步骤，不改写正在运行的请求 |
| `inject(message)` | 下一步 `next-step` | 否 | 先补充背景，等有实际任务唤醒后使用 |

这三个方法最终都调用 `send()`。比如 `inject()` 传入的第三个参数是 `false`；因此“背景已经进入队列”和“为背景单独调用了一次模型”不是同一件事。取消默认会清空 Inbox；显式保留队列需要 `keepInbox`。已经取消的活动接到新的唤醒消息时，也不能把它塞回已中止的运行中。[源码：`ReactLoopAgent.send/followup/steer/inject/cancel`](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/agent-loop/src/agent.ts)。

待处理队列也不是纯粹的临时数组。它通过 `agent/inbox/spliced` 记录队列的增删，恢复时可以重新派生待处理消息。但“仍在队列中”“被当前步骤领取”“已追加为模型可见用户消息”是三个不同位置：领取会移除队列项，而请求输入的提交更晚。不能只看到队列有持久化，就推断领取到请求提交之间的每一个中断窗口都自动具备恰好一次处理语义。[源码：Inbox 的入队、领取与恢复](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/agent-loop/src/inbox.ts)。

### Turn 与 Step 为什么要分开

**Turn（轮次）**是一次被唤醒的工作边界；**Step（步骤）**是其中一次模型请求及其提出的工具调用。一个步骤可能因请求失败产生多次尝试，重试并不自动增加步骤编号。一次修复往往需要多个步骤：先读文件，再修改，最后解释测试结果。

Turn 可以没有 Step。循环先记录 `turn/start`，再处理首次输入；若 `agent/pre-step` 拒绝进入，或者首次接受结果被改为空，轮次会结束，却不会发起该步骤的模型请求。这能解释“界面存在一轮活动，但没有模型用量”的合法情况。`agent/pre-step` 是可串联的输入处理入口；插件通过 `next()` 委托后续处理，不调用就可能截断处理链。[源码：`preStep()` 与 `turn()`](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/agent-loop/src/agent.ts)。

## 2. 先分清记录、当前视图和请求

读源码时最容易误把 Session 当成一个消息数组。它实际上保留按顺序追加的事件：输入、回复、工具调用、工具结果、步骤开始结束、失败尝试等都可以成为记录。事件的职责不同，不能把所有事件序列化后直接交给模型。

**Surface（当前消息视图）**表示哪些事件在当前版本中产生模型可见消息，以及这些消息的顺序。可以把它理解成“从完整记录中按规则取出的当前阅读页”。`deriveMessages()` 再把这个视图派生成请求使用的消息。这里只是解释名称，不要求读者先学习数据库投影框架。

| 层次 | 包含什么 | 分页例子 |
|---|---|---|
| Session 事件日志 | 已记录的输入、输出、执行边界、替换决定和诊断事实 | 记录模型曾请求读文件，也记录一次失败尝试 |
| Surface | 当前仍有效的消息节点及其替换关系 | 被摘要替换的旧读取结果不再原样出现 |
| 派生消息 | 本次要发送的有序消息 | 项目规则、用户需求、相关历史、工具结果 |
| 请求整体 | 派生消息，加上路由、模型参数、工具定义等 | 同一段历史可以交给不同模型，但适配与容量未必相同 |

并非所有消息形状的记录都贡献内容：空的系统节点保留位置，却不产生空系统消息；`assistant/attempt` 记录失败尝试，不作为新的助手回复进入历史；`turn/start`、`step/end` 则是边界事实，不是自然语言对话。[源码：`deriveEventMessage()`、Surface 类型判断](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/session/src/surface.ts)。

这里还有三个不同读者。用户的历史界面希望保留“当时真的展示过什么”；下一次模型请求需要受预算约束的当前视图；排错程序需要包括失败和边界的完整记录。因此不能拿压缩后的 Surface 当作完整的人类会话历史，也不能把界面上仍能展开的旧文字当作模型仍会收到的文字。

## 3. 请求组装：谁在什么时候提供内容

一次步骤开始前，`preStep()` 先领取队列输入，再通过 `systemPrompt.assemble()` 收集当前可用的提示片段和工具定义，随后处理运行背景及 `agent/pre-step` 插件。这里的 **Cordis `ctx` 是程序访问服务的应用上下文**；它不是要发送给模型的全部“上下文”。服务可以持有连接、配置和凭据，这些对象不会因为挂在 `ctx` 上就自动进入提示词。[源码：`preStep()`](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/agent-loop/src/agent.ts)、[架构中的能力分工](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/docs/architecture.md)。

组装时有三种主要来源：

**系统提示片段**给出角色和行为约束。插件登记片段，组装器依据当前作用域选择有效内容、处理提示变量并保持顺序；渲染后的系统文字通过 `system/message` 进入历史，而不是在请求外偷偷叠加一份不可解释的提示。

**工具定义**告诉模型可调用的名称、用途和参数结构。定义不包含真正的执行函数。工具是否在当前 Agent 的视图中可见，由工具注册与限制共同决定；仅隐藏某段说明而仍保留执行入口，不是完整的能力限制。第三章再追到执行端。

**运行背景和输入**来自用户、项目说明、引用或工具。背景的生产者负责内容与来源说明，经过输入处理后才被接纳。它们不是因为叫“系统提醒”就拥有系统消息的优先级。例如项目说明插件使用有来源的用户角色消息。角色、文本包装和真正权限是不同层面的事情。[系统提示与轮次说明](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/docs/architecture.md)、[项目说明的模型可见形状](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/context/agent-instructions/README.md)。

### 项目规则何时被发现

假设当前工作目录是项目根目录，根目录有 `AGENTS.md`，`backend/` 还有自己的 `AGENTS.md`。首次请求会得到用户全局说明以及项目根到当前工作目录的适用链，**不会先扫描并装入整个仓库每一个子目录的规则**。成功的第一方 `read`、`write` 或 `edit` 访问更深目录后，插件追踪这些结构化文件活动，让新增或变化的规则参与后续请求。单纯在 Shell 命令字符串中出现 `cd backend`，不等于结构化文件发现已经发生。

规则变化有自己的生命周期：内容未变时抑制重复注入；改变时发布更新；删除或与已有文件重复时发布移除信息；恢复会话时重新对齐基线。它不是无时无刻监控外部文件编辑的文件监听器。**需要先遵守嵌套规则再修改时，应先检查适用规则和文件，而不是把“写后能发现规则”当作安全的事前授权。**

基础组合把完整规则消息的预算设为 **65,536 字节，即 64 KiB**。预算不足时先省略更宽泛的整份规则，再考虑截断最具体规则，并附上省略提示。这个预算不是 65,536 Token，也不是每个规则文件各自拥有同样的总注入预算。[规则发现、刷新与预算](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/context/agent-instructions/README.md)、[基础配置](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/bundle/base/cordis.patch.yml)。

## 4. 两道边界：允许进入步骤，允许成为实际请求输入

输入插件接受了“修复分页”，还不代表真实模型路由已经准备完成。实际请求可能需要异步解析凭据、确定适配器及有效参数。源码把这段过程放在 `prepareRequest()`：先执行 `agent/request`，再调用 `llm.prepareCall()`；每个异步阶段之后检查取消信号。

在分页任务中，完整顺序如下：

1. **领取与组装。** 领取输入，组装提示和工具，允许 `agent/pre-step` 处理或拒绝这批消息。
2. **记录步骤开始。** 接受后写入 `step/start`，开始这个步骤的工作。
3. **准备真实路由。** `agent/request` 提出请求配置，`prepareCall()` 解析实际适配器及能力。准备期间取消，不提交这批系统与用户消息。
4. **提交本次输入。** 用实际路由能力协调系统提示，首次尝试追加已接受的用户消息，按需记录 `request/header` 与 `request/context`。
5. **派生并固定请求。** 从会话得到消息，将已构造的请求数据冻结，再调用已绑定的模型流。

`request/header` 记录解析后的请求配置和活动工具定义；`request/context` 记录路由相关的上下文能力，例如窗口容量及系统提示更新方式。它们不是把整段用户聊天再复制一次。冻结则防止请求构造完成后，插件通过共享引用悄悄改变“原本说要发送的内容”；取消信号仍保持活动。[源码：`step()`、`prepareRequest()`、`buildRequest()`](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/agent-loop/src/agent.ts)。

### 请求记录能证明到哪一步

假设程序刚完成第 4 步，尚未把网络请求交给远端就崩溃。日志可能已经包含用户消息和请求相关事实，但远端可能一次也没收到。反过来，远端已经处理请求而本地还没保存结果，也可能发生。

> ⚠️ **记录不等于远端确认。** 主循环“模型可见输入能够由日志重建”的约束，保证的是输入来源可解释；它不证明远端收到了请求、成功生成了回复，也不保证外部操作恰好执行一次。持久化完成还需看第四章的检查点边界。

这个约束也有作用范围：本章讨论的是 Agent Loop 的主请求。压缩器有自己的辅助模型请求，不能把主循环的不变量扩大成“整个进程所有辅助模型请求的每个字都必定作为会话输入保存”。

### 同一步重试为什么不重复加入用户输入

`step()` 内部有尝试循环。它保存本次组装结果，用 `firstAttempt` 控制用户消息只提交一次；后续尝试重新准备路由与构造请求，但不重新运行 `preStep()`。因此，请求失败重试不是把相同用户消息再追加一遍，也不是已经进入下一步。若恢复插件改变了当前 Surface，重建请求时才会看到这个变化。[源码：`step()` 中的尝试循环](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/agent-loop/src/agent.ts)。

<a id="prompt-update"></a>
## 5. 系统提示变化为什么要看适配器能力

项目运行中可能更换提示片段或工具集合。简单地把新系统提示放在任意历史位置，某些模型接口能表达，另一些不能；把旧系统提示留着不清理，又会让旧规则继续可见。

本实现先为系统提示保留头部节点。若路由支持历史中的系统更新，非空变化可以追加在已缓存历史之后；不支持这种更新，或者进入新的请求序列时，就把有效提示协调到首个系统节点，并把后续失效的系统节点清空。空提示的意思是清除有效旧提示，而不是“保留上一份以防没有提示”。工具变化还可能产生有记录的开发者消息，使声明增减能够被适配和重建。[请求与提示协调规则](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/docs/architecture.md)、[`SystemPromptProjection` 的调用位置](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/agent-loop/src/agent.ts)。

这里的 **请求序列**用于标记可连续解释的一组请求条件，不等于用户点击了“新会话”。压缩替换、图像外置等改变历史内容的决定会开启新序列；普通恢复若视图未改变，则不必假装所有旧前缀都失效。

保持前缀相同有机会复用模型服务的 **KV Cache（键值缓存）**，减少重复计算；但是否命中仍取决于服务端、模型路由、工具顺序和实际序列化。**本产品尽量保留复用条件，不承诺一定命中，更不保证免费。**

<a id="compaction"></a>
## 6. 上下文过长：先知道在缩减哪一层

假设工具返回了一份很长的测试日志。把它完整保留能便于排错，却会增加后续每次模型请求的输入。解决这个问题需要区分三种动作：

| 动作 | 改变的对象 | 适合的情况 | 代价 |
|---|---|---|---|
| 结果裁剪 | 当前视图中的过长工具内容 | 大量重复输出，头尾更有价值 | 中间细节不再直接可见 |
| 历史摘要替换 | 一个可安全选择的旧历史区间 | 多次交互累计占满窗口 | 额外模型请求；摘要可能漏掉事实 |
| 内容外置或引用 | 大内容本体与当前可见表示 | 需要保留原件，却不宜一直内联 | 后续必须有读取入口，且原件仍可访问 |

基础组合挂载了工具结果裁剪器，配置是 `thresholdChars=8192`、`headChars=4096`、`tailChars=1024`。这些配置按字符量描述裁剪策略，不是 Token 预算。裁剪是在压缩触发后尝试的步骤；不是所有低于压力阈值的对话每次都先被剪短。若裁剪后已经低于阈值，就可以不再请求模型做摘要。[基础配置](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/bundle/base/cordis.patch.yml)、[压缩触发与裁剪](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/compaction/compaction-basic/README.md)。

### 先给输出留空间，再决定何时压缩

窗口不只装输入，还要为输出及额外余量留空间。压缩器使用同一 Token 计量服务，为路由对应的消息、工具及其他请求成本定价。默认触发阈值为：

```text
W：当前路由的上下文窗口，单位 Token
O：本次有效的输出预留，单位 Token
B：额外安全余量，默认 65,536 Token

触发阈值 = floor(min(W × 0.8, W − O − B))
保留近期历史的比例预算 = (W − O) × 0.16
```

**教学假设**：`W=128000`，`O=8000`，`B=65536`。两项候选阈值分别为 `102400` 和 `54464`，所以触发阈值是 `54464 Token`，近期比例预算是 `19200 Token`。若当前计量为 `60000 Token`，就已经超过阈值，不能因为“窗口有 128000”而继续无条件追加。

这也解释了小窗口模型为什么不能照搬默认余量。若 `W=32768`、`O=4096`，默认 `B` 会使 `W−O−B` 非正。需要配置适合该路由的余量与保留量，而不是把错误容量当成普通对话压力。无效的路由容量配置会使主动压缩警告并跳过；手动压力路径会报配置错误，已确认的窗口溢出恢复仍有自己的路径。[公式、默认值与失败边界](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/compaction/compaction-basic/README.md)。

### 摘要不是删除旧账，而是替换当前阅读区间

压缩器选取较老、能够保持消息关系平衡的区间，保留近期尾部。不能从工具调用和对应结果之间随意切断，也不能指望它拆开一个不可分割的巨大调用。首个系统节点不在普通待压缩区间中；系统提示或工具定义本身太大，需要减少这些输入，而不是反复摘要聊天历史。

选择好区间后，压缩过程先记录 `compaction/start`，再请求摘要。摘要完成后还要核验取消、区间是否仍稳定，以及新内容是否真正缩短；成功才记录摘要和 Surface 替换，并尝试关闭压缩边界。摘要过程失败，不等于可以拿半段输出覆盖旧内容；一个没有成功关闭的压缩标记也不能被当作已完成压缩。

辅助请求复用可兼容的系统提示、工具及选中历史，并附加摘要指令。只有适合继续工作的文本进入检查点，不能把推理流、工具调用或不支持的图像输出偷偷混入摘要。原事件仍在日志里，但后续主请求主要读取“摘要加近期尾部”。**记录保留不代表模型继续自动记住所有旧细节。**[区间处理、摘要验证与辅助请求](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/compaction/compaction-basic/README.md)、[Surface 的替换语义](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/session/src/surface.ts)。

### 窗口溢出后的重试必须有变化

普通主动压缩在请求前依据压力判断；远端确认 `CONTEXT_WINDOW_EXCEEDED` 后，则尝试更大的安全头部缩减。这里授权立即重试的重要条件是 Surface 的替换代数发生推进，而不是“已经打印了压缩开始”。默认溢出恢复次数有上限，不能对同一份过长请求无限重发。

`/compact` 允许在合适的空闲边界主动压缩；正在执行轮次或已有压缩活动时，不应假装能够任意并发改写历史。等待期间的新任务有自己的队列与唤醒处理。该命令不能证明摘要语义完全正确，仍应检查用户约束、已完成修改、待验证步骤和未决错误是否保留。[自动、手动与溢出路径](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/compaction/compaction-basic/README.md)。

<a id="stream"></a>
## 7. 流式输出与工具回填怎样进入下一步

用户看到的是逐渐出现的文字，存储层却不需要把每个瞬时显示片段都当作独立的完整回复。主循环通过 `agent/assistant-stream` 发出进程内的开始、片段和结束事件；一次流结算后，再保存完整的紧凑流及其对应消息或失败尝试。硬崩溃发生在结算之前时，不能保证已经显示的所有片段都有持久副本。

也不能把“取消”一律画成 `assistant/attempt`：源码在取消后已有可保留内容时，可能记录带 `interrupted` 的 `assistant/message`；没有内容，或者属于失败尝试时，使用 log-only 的 `assistant/attempt`。两者是否进入模型历史不同。[源码：`step()` 中的流结算](https://github.com/deepseek-ai/deepseek-harness/blob/477b4f420553e8a52c2fbccc464d7561b239c443/packages/core/agent-loop/src/agent.ts)。

如果正常回复包含工具调用，程序才会进入工具执行链。结果按调用关系回填，工具附带的 `additionalContexts`（额外背景）按来源进入下一步输入，不是修改已经发出的请求。如果回复没有工具调用，可以结束本轮；成功工具也可以明确结束轮次。**轮次结束只说明执行循环停止，不说明分页已经修复。** 修改是否正确，要结合实际文件差异与测试证据判断。

回到起点，完整信息流已经连起来：用户输入进入队列，项目规则在请求前被提供，主循环记录并派生请求，模型提议读取，工具结果成为后续历史，超长内容通过有记录的替换缩减。下一章讨论其中哪些信息值得在另一个任务中重新使用。

## 小结

上下文不是所有“存在于程序里”的信息，而是经过来源处理、接纳、视图派生和请求适配后，本次模型实际准备读取的内容。队列解释时机，日志解释来源，Surface 解释当前有效历史，路由能力解释请求形状，压缩解释在有限预算下保留什么。掌握这条链，才能区分“没有发进去”“发进去但被替换”“模型看见却没正确使用”这三类问题。

## 🎯 面试怎么回答

**Q：DeepSeek Harness 怎样保证一次请求的上下文可解释？**

> 🎯 它把主循环的模型输入建立在 Session 日志上，而不是从隐藏的临时字符串随意拼装。步骤先领取输入和组装提示，再允许输入插件处理；真实路由准备完成后，才协调系统提示、提交用户输入并记录请求条件。随后从当前 Surface 派生并冻结请求。这样可以解释消息来源和替换关系，但不能由此证明网络已经送达；持久化检查点、远端结果和外部副作用还要分别验证。

**Q：为什么上下文压缩不能简单删除最早的若干条消息？**

> 🎯 因为消息有关系：工具调用需要对应结果，用户约束和未完成工作不能只按时间丢弃。这个实现先按路由计量压力，尝试裁剪过大的工具结果，再选择平衡的旧区间生成摘要并保留近期尾部。成功的压缩是有记录的 Surface 替换，不是抹去审计日志；摘要缩短了输入，却仍可能漏掉语义，所以还要检查任务状态与约束。


## ⚠️ 常见误区

| 误解 | 正确判断 |
|---|---|
| 消息加入 Inbox 就会立即改变模型输出 | 只能影响后续可接纳的请求；`inject` 甚至不会独立唤醒 |
| Session 有这段文字，模型就会一直收到 | 还要看当前 Surface、替换关系和派生结果 |
| 请求已记录，远端肯定已执行 | 记录、发送、远端处理、持久结果是不同边界 |
| 所有取消都不留下模型可见内容 | 已有内容的取消可能结算成中断回复 |
| 压缩成功就保证任务细节完全没丢 | 结构、缩减和稳定性检查不能替代语义验证 |

## 自测：先写出判断，再展开答案

**任务 A：注入与唤醒。** 一个 Agent 空闲，队列为空。先执行 `inject(项目背景)`，之后才执行 `followup(修复分页)`。判断第一次操作后是否必须出现模型请求，以及第二次操作后背景应在哪个阶段参与。检查结果应同时解释队列位置和唤醒条件。

<details>
<summary>任务 A：注入与唤醒｜提示</summary>

把 `next-step` 与“立即执行”分开；回看三个方法共同调用的 `send()` 参数。

</details>

<details>
<summary>任务 A：注入与唤醒｜参考答案与解释</summary>

第一次操作只加入下一步背景，不单独唤醒。后续任务唤醒循环时，待处理背景在请求输入处理阶段与任务一起获得进入机会；它不应被解释为第一次操作已经发出了一个隐藏模型请求。是否最终进入还受输入处理和取消等条件约束。

</details>

**任务 B：改变故障点。** 已经记录用户输入和 `request/header`，进程在调用模型流之前崩溃。有人据此说“服务端处理过，可以从结果继续”。指出证据缺口，并说明下一步应检查哪类事实。不能只回答“加重试”。

<details>
<summary>任务 B：改变故障点｜参考答案与解释</summary>

这些记录说明本地接纳了输入并构造了请求条件，不证明远端送达，更没有可用结果。应区分请求发送证据、服务端状态或响应、持久化结果及恢复后的会话边界。模型请求可以依据其恢复策略重新进行，但不能假造先前结果；涉及工具副作用还必须另查外部状态。

</details>

**任务 C：摘要没有解决超限。** 当前系统提示与工具定义本身已占据大部分窗口，聊天历史只剩一个巨大且不可分割的工具调用。解释为什么“继续压缩并重试”可能没有进展，并给出不同于重试的处理方向。

<details>
<summary>任务 C：摘要没有解决超限｜参考答案与解释</summary>

压缩器不能随意压缩首个系统提示、所有工具定义或拆坏调用关系。没有可安全缩减区间时，Surface 不会产生有效替换。应减少提示与工具暴露成本，控制工具输入输出规模，必要时外置可重新读取的内容或选择容量适合的模型。不能把“运行过压缩函数”当作恢复条件已经满足。

</details>
