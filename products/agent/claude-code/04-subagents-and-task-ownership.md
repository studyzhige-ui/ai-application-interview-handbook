<a id="4-子智能体怎样分工哪些东西仍然共享"></a>
## 1. 子智能体怎样分工，哪些东西仍然共享

分页任务可以拆成定位缺陷、检查测试、审查接口三项子任务。子智能体有各自的任务输入与上下文，避免主任务携带每条探索细节；代价是额外模型调用、结果汇总与协调。

镜像通过 AgentTool 与 `runAgent.ts` 组织子任务并进入查询执行。复用 `query` 并不表示各自持有同一份完整消息，也不自动创建独立操作系统进程。[子任务入口][agent-tool] 与 [执行接入][run-agent]

| 边界 | 需要作出的明确安排 |
|---|---|
| 消息上下文 | 传给子任务哪些目标、约束和证据 |
| 执行权限 | 提供哪些工具，允许读取还是修改 |
| 工作文件 | 使用共同目录还是独立工作树 |
| 生命周期 | 谁收集结果，父任务取消后谁清理 |

给两个角色不同提示，只处理了消息输入的一部分，没有完成文件和安全隔离。

### Worktree 隔离工作副本，集成仍需共同验证

Git Worktree（工作树）为任务提供独立检出的目录，减少直接覆盖文件的机会；它不自动限制网络，也不替代权限沙箱。

假设 A 修改了分页参数，B 按旧参数补测试。两份补丁可以没有文本冲突，合在一起却不兼容。正确集成顺序是：确认共同基线，检查双方差异，合入同一最终状态，再运行接口与测试验证。**两个子任务各自通过，不等于合并后的结果通过。**


<a id="2-创建时先固定子任务的输入和能力边界"></a>
## 2. 创建时先固定子任务的输入和能力边界

AgentTool 根据 agent 定义、父任务允许范围和本次提示选择模型、工具与初始消息，再交给 `runAgent()` 执行。普通子任务从较小的任务输入开始；fork 历史则需要处理父级消息，不把未配齐的调用和结果直接带进去，读取缓存也按对应路径复制。[创建参数][agent-create]、[上下文构造][agent-context]

把分页任务委派给“接口审查”角色时，主任务应交代“不能改公开参数和返回类型”、共同基线与要审的差异。否则子任务即使局部推理正确，也可能回答另一个问题。这是输入合同，不是多几个角色名称就会自动完成的协作。

子任务的只读或可写能力来自实际工具与权限配置。定义文本可以限制目标，却不能替代执行层的边界；不同消息历史也不会阻止两个 agent 写同一份文件。

<a id="3-前台等待与后台启动返回的是两种结果"></a>
## 3. 前台等待与后台启动，返回的是两种结果

同步执行与父任务的取消控制相连，父级中断可以传递给它；后台路径使用独立控制器，不应概括成“父任务停止就一定停止全部子任务”。后台先登记 task 与名称路由，再返回启动标识和输出位置，真正完成以后另行通知。

| 主任务拿到的返回 | 此时可确认 | 尚不能确认 |
|---|---|---|
| 同步执行的汇总结果 | 这次等待已收束并取得结果内容 | 集成代码已经通过全部测试 |
| 后台启动标识、输出位置 | 子任务已登记并启动相应流程 | 子任务已经完成 |
| 后续完成通知 | 状态进入对应终态，结果有指定入口 | 父任务已经读过并验收 |

主任务可以继续独立工作，但仍拥有取得结果、判断适用性和汇总交付的责任。任务标识不是测试通过凭据，输出路径也不是主任务已经消费的证据。[后台登记与转换][agent-background]

<a id="4-运行中发消息与恢复空闲任务不是同一步"></a>
## 4. 运行中发消息，与恢复空闲任务不是同一步

发送工具先找到接收者。对仍运行的 agent，消息进入队列，在后续工具轮次消费，不会强行把任意文本插进正在形成的模型响应。停止但保留内存记录的 agent 可沿后台恢复路径继续；内存任务已移除时，可以尝试从 transcript 恢复，失败则返回明确结果。[消息消费与恢复][agent-resume]

因此“发送成功”应先读成路由或入队结果。子任务可能尚未消费，消费后也未必完成用户要求。反过来，不能认为所有发消息动作都仅仅入队：针对已停止对象的恢复路径可能启动新的执行。

例子：审查 agent 仍在查接口时，主任务补充“还要检查空列表”。消息排队后，在可消费边界进入其后续工作；主任务需要最终报告说明是否覆盖空列表，不能把发出的补充消息当作已完成检查。

<a id="5-完成通知与清理要有明确顺序"></a>
## 5. 完成、通知与清理要有明确顺序

在已核验的“同步转后台”路径中，程序先把任务标为完成、失败或取消，让 TaskOutput 等待者解除等待，再进行工作树清理和通知。若反过来先等耗时清理，实际任务已结束却会一直表现为运行中。这是该路径的具体顺序，不能未经核验扩展成所有后台实现的统一协议。[状态终结与清理][agent-background]

工作树处理也有条件：能够判断的 Git 工作树没有变更时可以移除；有变更时保留，并把路径等信息随结果交回。Hook 创建的工作树有不同保留边界，不能套用普通 Git 工作树判断。[执行收尾][agent-cleanup]

清理的目标是释放归自己所有、已经不再需要的资源，而不是删除所有看见的临时目录。Fork 或 resume 还需区分工作树的使用权和清理所有权，第七章会展开。失败进入终态不意味着部分编辑已回滚；主任务仍要核对实际差异。
<a id="5-后台任务和团队消息怎样走到完成"></a>
## 6. 后台任务和团队消息怎样走到完成

后台工具返回稳定任务标识，供后续查询、通知或取消。标识说明工作已登记，不说明成果已经可用；主任务仍要消费结果，失败时保留可诊断状态。

团队通信同样有阶段：发送、入队、接收、执行和返回结果。镜像的 `SendMessageTool` 负责路由到执行对象，接收者状态与相关能力条件影响后续工作。[团队消息入口][send-message]

例如审查子任务回复“准备检查接口”，主任务只能据此确认计划，不能宣布接口兼容。需要的是检查了哪些差异、发现什么，以及结论是否针对当前最终代码。

> ⚠️ 注意：清理工作树、进程或临时文件前，先确认归属、运行状态和结果位置。不能为了消除残留而删掉另一会话仍在使用的成果。


<a id="7-结果真正被消费时主任务才继续作决定"></a>
## 7. 结果真正被消费时，主任务才继续作决定

设后台审查返回“未改参数，但第二页仍返回错误结果”，主任务消费后应把这个结论连到当前代码版本，重新修改或补充验证。若它针对旧工作树，先检查新差异是否使结论失效。子结果压缩了探索历史，但不能失去对象、证据和未确认事项。

压缩主会话时，系统会重注入运行中或完成未领取的子任务及输出位置，避免主模型忘掉待收结果。该材料不是重复运行子任务的指令，而是继续承担结果领取责任的线索。后台任务生命周期由登记、执行、终态、通知、领取和清理共同组成。

## 本章小结

子任务有自己的输入与工具范围；前台与后台的取消、等待及回报不同。消息入队、恢复执行、任务完成、结果领取和工作树清理不是同一状态。父任务最终负责对齐共同版本并消费结果。

## 🎯 面试怎么回答

**问：Claude Code 后台子 agent 返回任务 ID 后，协作还剩什么？**

ID 只说明任务已登记。子任务继续运行，接收者在安全边界消费消息；终态结果通过记录和通知回到父级，父级要读取、核对版本并决定下一步。清理按资源归属与变更状态进行，独立控制器和工作树不等于自动安全隔离，也不免除集成验证。

## ⚠️ 高频易错点

- “已发消息”不表示接收者已经执行其中的要求
- 父级中止不一定终止使用独立控制器的后台 agent
- 子任务无文本冲突，不证明接口或行为兼容
- 完成状态先解除等待，不能由此推断所有资源已清理

## 本章自测

**问题：** 接口审查已经完成，但它的工作树仍有变更；主任务收到通知却未读输出。能否删除工作树并宣布完成？

<details><summary>参考答案</summary>
不能。先读取结果和保留差异，确认工作树归属、当前任务是否仍依赖它，并在共同最终状态验证。有变更的保留路径本来就是交付的一部分；通知不替代结果消费。
</details>

**问题：** 正在运行的子任务收到补充检查要求，父任务随后压缩。什么材料必须保持连续？

<details><summary>参考答案</summary>
子任务身份、状态和输出位置，以及尚待取得的结论。压缩可重注入运行中或未领取任务的线索；父任务仍需查证补充要求是否已被消费和落实，不能从发消息成功推导检查完成。
</details>
