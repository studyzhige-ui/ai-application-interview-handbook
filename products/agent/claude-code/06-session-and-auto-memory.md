# 06. 会话摘要与自动记忆｜两种连续性怎样生产和消费

> 本章依据[私有学习快照及核验边界](README.md#学习对象与版本边界)。示例对象、数字与时间线为教学推演，不是产品运行记录。

<a id="1-同一句记住可能是三种要求"></a>
## 1. 同一句“记住”，可能是三种要求

分页修复进行到一半，用户说：“接口不能改；测试前先告诉我准备验证什么。”几天后，用户又开始另一项任务。哪些信息还应起作用？

“分页改到了哪个文件”主要服务当前任务；“这个仓库公开接口不能随意改变”可能是项目约定；“测试前先说明验证范围”则可能是希望后续继续采用的协作方式。

把三者都保存成长期偏好，会把已完成任务带到新任务里，也可能把一个项目的限制推广到所有项目。**先确定信息服务谁、适用哪里和何时失效，再决定保存方式。**

<a id="2-按用途区分五种信息"></a>
## 2. 按用途区分五种信息

| 信息形态 | 主要用途 | 本例中的内容 |
|---|---|---|
| `CLAUDE.md` 等项目指令 | 人维护的工作约定 | 保留原测试、遵守公开接口 |
| Transcript，会话记录 | 恢复实际交互与执行过程 | 用户输入、读取结果、修改及测试消息 |
| Session Memory，会话摘要 | 当前长任务的连续执行 | 已改偏移，测试结果尚待确认 |
| Auto Memory，自动记忆 | 后续会话可复用的信息 | 本项目测试前应说明验证范围 |
| 子智能体的作用域记忆 | 特定执行角色可复用的经验 | 某类审查任务的反馈 |

子智能体是承担独立子任务的执行角色，可以有自己的输入、上下文和记忆范围。同样是文件，工作摘要与长期记忆的用途仍不同；落盘不是二者的分界。[会话摘要][session-memory]、[自动记忆规则][memory-rules] 分别处理这两类需要。

会话摘要可以写“已经验证了哪些部分”，但原始测试结果仍是证据。长期记忆应优先保留无法直接从当前项目状态重新获取的有用反馈，而不是复制一份很快过时的代码清单。


<a id="3-session-memory-先生产摘要再由压缩器消费"></a>
## 3. Session Memory 先生产摘要，再由压缩器消费

Session Memory 服务当前长任务，不是用户偏好库。适用的主交互路径注册 post-sampling Hook，满足启用和初始化条件后，观察消息增长：**增量 token 阈值始终必需**，还需工具调用数量达标，或者最新助手轮已无工具调用、到达自然断点。并非每次模型回答完都写摘要。[会话摘要生产][session-produce]

提取器为摘要文件建立隔离读取上下文，再运行 fork 辅助查询；权限回调只允许 Edit 到指定摘要文件，避免把整理权限推广到整个项目。成功完成且消息边界安全时，才更新 `lastSummarizedMessageId`。它描述“这份摘要已经覆盖到哪里”，不是简单“提取被启动过”。

接着看压缩器怎样消费：

1. 若有提取仍在进行，先等待它结束，避免读取半成品
2. 拒绝不存在的摘要、空模板，或找不到完成游标的状态
3. 从游标之后保留新消息，并往前扩展以维持足够的直接上下文
4. 调整边界以保住工具调用/结果配对，以及同一 `message.id` 的流片段
5. 摘要加保留历史仍超阈值时，退回普通压缩

默认向前扩展希望至少保留 10,000 token、5 个含文本的消息，40,000 是停止继续扩展的阈值。随后为了工具配对和流片段完整性还可能向前移动，所以 **40,000 不是最终历史的绝对硬上限**。[保留范围][session-consume]、[消费与回退][session-boundary]

### 用摘要游标重建一次后续输入

假设摘要 S 已安全覆盖到 M6；M7 是 Edit 提议，M8 是结果，M9 是新增用户要求。压缩时至少保留 M7…M9，若数量或 token 不足，再向前扩展。若选择边界落在某个工具结果上，还必须带回它匹配的调用；若助手同一响应拆成多个流片段，也要连同需要归并的片段保留。

最终不是“读 S 后丢掉其余所有消息”，而是 S 与合法尾部共同支撑下一请求。S 若只有模板，或者 M6 已无法对应，程序不会凭猜测裁剪；回到普通摘要路径建立新的继续条件。

Session Memory 的完成游标与后面的 Auto Memory 提取游标承担不同职责：前者连接摘要与保留历史边界，后者控制哪些新对话还需整理成长期间可复用的文件。相同的“memory”名称不能掩盖这两套消费者。
<a id="3-一条反馈怎样真正保存下来"></a>
## 4. 一条反馈怎样真正保存下来

把用户要求收窄为一句明确的长期反馈：

> 在这个分页项目里，以后运行测试前，先说明本次准备验证哪些条件。

这里采用需要入口索引的保存路径。短入口 `MEMORY.md` 帮助发现主题，主题文件保存完整内容，二者有不同职责：

```text
memory/
├── MEMORY.md            主题入口
└── feedback_testing.md  具体反馈及适用说明
```

`feedback_testing.md` 可以保存为以下教学内容。文件头的 `name`、`description`、`type` 对应镜像的记忆组织方式；正文中的“范围、来源、要求”只是易读的内容安排，不是新增的产品字段协议。

```markdown
---
name: 测试前说明验证范围
description: 在分页项目运行测试前，先交代准备检查的条件
type: feedback
---
适用范围：当前分页项目。
来源：用户在本项目协作中明确提出。
要求：执行测试前，简短说明将检查哪些条件。
使用时：结合本次改动确定测试范围，不跳过实际验证。
```

`MEMORY.md` 中只需一条可定位入口：

```markdown
- [测试协作](feedback_testing.md) — 分页项目测试前先说明验证范围。
```

保存过程包含三项检查：

1. 查已有记忆，确认是新增反馈还是修改旧反馈，避免重复文件。
2. 写主题文件，取得工具结果，确认内容实际存在。
3. 在需要索引的路径中更新入口，确认指针指向正确文件。

主题写入成功而入口未更新，可能影响沿索引发现；入口存在而主题被删，则是失效引用。**“模型说记住了”“提出写入”“写入成功”是三个阶段。** 镜像的 `buildMemoryLines()` 明确给出主题文件加索引的两步指引，同时也有跳过索引的配置分支。[保存规则][memory-rules]

镜像还使用 `user`（用户信息）、`feedback`（反馈）、`project`（项目背景）、`reference`（资料线索）等类型。类型帮助选择与维护，不意味着所有 Agent 都要建立四张同名表。

<a id="4-下一次任务怎样读到这条反馈"></a>
## 5. 下一次任务，怎样读到这条反馈

新任务是：“修复另一个分页边界问题，并完成测试。”系统可以通过两种方式取得主题内容。

| 方式 | 先得到什么 | 如何继续取得正文 |
|---|---|---|
| 加载入口索引 | `MEMORY.md` 中的标题和指针 | 模型按需要提出读取主题文件 |
| 相关记忆预取 | 扫描到的文件名、描述等头部信息 | 辅助模型选择相关文件，附件层再读取与注入 |

第一种路径让模型知道“有这条反馈，必要时去哪读”；第二种主动寻找与新任务有关的材料。二者都不需要把全部主题正文预先放进每次请求。主会话的记忆行为指令与入口内容还有不同装配位置：`loadMemoryPrompt` 提供行为指导，入口内容经指令加载材料进入用户上下文；子智能体的 `buildMemoryPrompt` 则可直接包含入口内容。[记忆提示构造][memory-build] 与 [上下文生产][context-source]

沿第二种路径，这条反馈会经历：

```text
新任务 + 候选文件的名称与描述
  ↓
辅助查询选出 feedback_testing.md
  ↓
用真实文件集合过滤返回的文件名
  ↓
附件层读取正文，检查预算与重复
  ↓
正文进入后续某次模型请求
  ↓
模型据此先说明验证范围，再执行测试
```

这里的辅助查询是另一次专门做选择的模型请求。`findRelevantMemories()` 扫描头部，再调用选择模型；它返回有效路径与修改时间，不是直接把全部文件正文塞给主模型，也不是在这个函数里进行向量检索。[选择函数][memory-select]

已呈现路径会先被过滤，最近使用工具的信息也参与选择：普通工具说明可能没有必要重复召回，但该工具的警告和已知问题仍可能有用。文件修改时间是新鲜度线索，事实是否可靠还要结合来源和当前项目证据。

### 入口短，不等于正文无限加载

短入口有行数与长度预算，主题正文进入请求时也有附件预算。关键限制应放在短入口能够表达的位置，完整背景留在主题中；进入上下文的实际内容才决定本轮能否使用它。[入口处理][entrypoint] 与 [附件处理][attachments]

<details><summary>源码细节：行数、字符串长度与选择数量</summary>

`truncateEntrypointContent()` 先限制到 200 行，再执行长度限制。`MAX_ENTRYPOINT_BYTES = 25_000` 虽然含有 BYTES，实际计数使用 `trimmed.length`，截取使用字符串 `slice()`，即 JavaScript 的 UTF-16 代码单元，而非 UTF-8 字节数。

例如忽略换行，20,000 个基本汉字占 20,000 个代码单元，UTF-8 约为 60,000 字节。因此不能仅凭后一个数字断言该函数触发 25,000 的限制。这里解释固定快照的函数；[公开文档][official-memory] 的产品容量描述不改变这份实现。

选择提示要求最多 5 个文件，但返回结构只约束字符串数组，函数随后按有效文件名过滤，没有在这里统一截断到 5。实际注入仍受消费者预算约束。提示要求与程序强制限制要分别核对。[选择及返回过滤][memory-select]

这些细节用于源码复核，不是理解“反馈怎样进入下一次任务”的前置。

</details>


### 选择完成后，附件消费者还要作一次实质筛选

提及具有记忆范围的 agent 时，预取按相应记忆目录搜索；否则使用自动记忆目录。多个目录的结果先展平，再过滤 `readFileState` 已读路径和本轮历史已呈现的路径，最后才 `slice(0, 5)`。因此“提示最多选 5 个”与消费者“真正最多取 5 个”是两个不同限制。[附件消费者][attachments]

例如目录 A 返回 a、b、c，目录 B 返回 d、e、f、g；a 已被 Read，d 已在记忆附件中出现。展平后过滤，实际可选 b、c、e、f、g，正好 5 个。若 b 读取失败，它不产生附件，但这不意味着再让选择模型任意补满全部空位。

每文件最多读取 200 行、4,096 字节；被截断时保留已读内容，并附用 Read 获取全文的说明。这是真正文件读取的 byte cap，与前面入口采用 JavaScript 字符串长度的 25,000 限制不同。累计已注入内容则按 `content.length` 统计，达到 `60 * 1024` 后停止发起预取；这个数字同样不能直接称 UTF-8 总字节硬限制。

累计量来自当前消息中的记忆附件。压缩移除旧附件后，已呈现集合和累计计数自然随历史重建，不是永久禁止以后再召回同一文件。这使记忆能在丢失详细上下文后重新参与，也要求后续继续核对新鲜度。
<a id="5-为什么召回可能晚于第一次请求"></a>
## 6. 为什么召回可能晚于第一次请求

若用户每次输入都等待记忆搜索完成，首个请求就会更慢。镜像在用户轮次开始时调用 `startRelevantMemoryPrefetch()`，让搜索与主任务重叠；只在工具后的消费点检查已就绪结果；未就绪则不等待。去掉两端空白后不含空白分隔的输入不启动该预取（代码按空白判断，并不做中文分词），整轮无后续工具消费点时也不保证结果会进入请求。[查询启动位置][prefetch-start] 与 [附件消费者][attachments]

设定一个只用于理解时序的例子：

| 时刻 | 主任务 | 记忆检索 |
|---|---|---|
| t0 | 准备用户新任务 | 启动搜索 |
| t1 | 第一次模型请求已发出 | 尚未选出主题 |
| t2 | 正在处理模型或工具结果 | 选中并返回主题路径 |
| t3 | 组织后续请求 | 有机会读取并注入正文 |

在 t1 的请求里，不能使用 t2 才返回的正文；选中文件也不等于 t3 必然完成注入，还要通过附件读取、预算和去重。

> ⚠️ 注意：协作偏好迟到可能只影响体验；禁止外发文件这类硬约束若迟到，可能已无法挽回动作。它应在请求和执行之前可靠加载，并由权限机制约束，不能只依赖机会性的后台召回。

预取句柄通过 `using` 管理退出清理。这里把它理解为“离开这段查询生命周期时清理预取资源”即可，不需要先掌握完整语言特性。

<a id="6-谁负责把对话整理成记忆"></a>
## 7. 谁负责把对话整理成记忆

主智能体可以直接调用文件工具保存。另一条路径是后台提取：符合入口与功能条件时，在完整查询循环结束阶段考虑提取可复用信息，不必等整个进程退出。

`initExtractMemories()` 为提取器维护自己的工作状态。游标 `lastMemoryMessageUuid` 记录已经处理到哪条消息，避免每轮重新整理所有对话；它属于本次提取器初始化出来的状态，不是跨进程共享数据库。[提取器实现][extractor]

一次后台提取的顺序是：

1. 确认初始化、记忆开关和入口条件允许。
2. 从游标后找新消息；计数时若旧游标已被压缩移除，就回退到当前可见消息。
3. 检查主对话是否出现过针对记忆目录的写入调用，符合条件时跳过重复提取并推进游标。
4. 通过节流检查后，用 `runForkedAgent()` 建立辅助查询，整理当前材料和已有记忆。
5. 正常返回后推进游标；抛出异常时不按成功路径推进。

Fork（分叉）在这里是辅助查询上下文，不自动表示独立操作系统进程。它使用缓存安全的参数组织方式，避免把整理过程无必要地插入主任务历史。

### 写入调用去重的边界

`hasMemoryWritesSince()` 只检查 assistant 消息中的 Write/Edit `tool_use` 和目标路径，没有在这个判断里核对成功的 `tool_result`。[调用检测][extract-write-check]

回到主题文件：模型发出了 Write，但工具返回权限错误；检测仍可能认为主对话已写过，从而跳过辅助提取。**因此，去重标记不证明文件落盘。** 实际排查要读取工具结果和主题文件，再处理权限、补写及入口；不能凭一条跳过日志宣布记忆已保存。

<a id="7-后台权限与调度各自解决什么问题"></a>
## 8. 后台权限与调度，各自解决什么问题

辅助查询需要读项目背景、写记忆文件，两类范围不必相同。`createAutoMemCanUseTool()` 在这个回调内允许 Read/Grep/Glob；Bash 需通过只读判断；Write/Edit 限于自动记忆路径；其他不符合条件的工具被拒绝。REPLTool 是代码执行工具，和终端交互界面 REPL 不同，其内部原语仍需经过检查。[权限回调][extractor]

> ⚠️ 注意：允许读取不等于适合把内容保存为长期记忆，更不等于内容不会进入模型请求。该回调限制写入范围，但不是完整的操作系统沙箱或多租户隔离。

一次提取尚未完成，新一轮又结束时，`inProgress` 与 `pendingContext` 避免无限叠加提取；节流控制频率，游标控制已经处理的范围。几项状态分别处理“有没有人在做”“多久做一次”和“从哪里继续”。

Auto Dream（跨会话整理）则面向积累的长期文件，处理重复、过期和分散的信息。它检查入口、时间、新会话数量与整理锁，和每轮提取新反馈不是同一件事。[整理入口][auto-dream]

<details><summary>调度细节与失败后的状态</summary>

该快照默认要求距上次整理至少 24 小时、至少 5 个符合条件的其他会话；配置可改变数值，功能启用条件也要满足。当前会话不计入新增会话数量，避免它反复更新时间戳造成误触发。会话扫描还会节流，跨进程竞争由整理锁协调。

整理失败可能回退锁的时间标记以便后续重试；用户取消有独立处理。回退调度标记不回滚已经写入的文件。同样，提取异常时游标未推进，也不证明此前文件操作全部撤销。重试前仍需核对已完成的写入。

</details>

<a id="8-用户纠正以后怎样停止传播旧结论"></a>
## 9. 用户纠正以后，怎样停止传播旧结论

假设主题里另存了一条“本项目默认用 pytest”。用户明确纠正：“这是另一个项目的约定，本项目以 unittest 为准。”只在新文件末尾追加更正，旧主题仍可能被选中。

应沿保存和读取的同一路径检查：

1. 读取原主题和当前项目证据，确认错误是内容还是作用域。
2. 修改或删除旧结论，同步名称、描述和必要索引。
3. 检查当前会话是否已注入旧内容，必要时补充明确更正。
4. 在后续相关任务中验证不再选中或使用错误约定。

主题正文的“适用范围：当前分页项目”应继续存在，不能把 unittest 推广成所有项目的规则。镜像提示要求更新、删除错误或过期记忆；具体冲突判定仍依赖模型判断、工具结果和外部证据。[维护指引][memory-rules]

> ⚠️ 注意：删除主题文件主要停止未来从该文件召回。已经进入当前消息或历史记录的副本，需要分别处理；删除一个文件不等于让所有正在运行的会话立刻忘记。

子智能体记忆也要核对用户、项目或本地等作用域。文件分组说明复用范围，不自动提供用户之间的强制安全隔离。[子智能体接入][agent-tool]

<a id="9-判断记忆是否有用要回到任务结果"></a>
## 10. 判断记忆是否有用，要回到任务结果

以相同的初始分页代码做对照：

| 条件 | 应观察什么 | 不能只看什么 |
|---|---|---|
| 新会话，有正确反馈 | 测试前说明范围，且实际完成测试 | 只复述了偏好 |
| 旧测试约定已纠正 | 使用本项目真实验证入口 | 只多保存了一条更正 |
| 不相关项目 | 不使用错误范围的反馈 | 为提高召回数强行加入记忆 |

解释比较结果时还应对齐模型、权限、记忆初始文件与注入时序。保存正确、范围正确、及时召回和任务改善，需要逐层检查；这里给的是评测设计，不是产品实测成绩。

## 本章小结

先按用途决定保存什么，再核对主题文件与入口。新任务可以沿索引读取，也可以由相关性预取选择主题，再经附件进入请求。后台提取与长期整理控制重复和维护成本，但保存成功、召回及时和内容仍然正确，最终都要有相应证据。

<a id="面试怎么回答"></a>
## 🎯 面试怎么回答

**问：Claude Code 的记忆为什么不只是一个 `CLAUDE.md`？**

`CLAUDE.md` 主要承载人工指令，会话记录与摘要维持恢复和当前任务连续性，自动记忆把可复用反馈保存成主题。需要索引时同时维护 `MEMORY.md`，新任务再沿索引或相关性选择读取正文。分析时还要确认写入结果、注入时机和纠错范围：提出写入不等于保存，启动检索也不等于首个请求已收到内容。

<a id="高频易错点"></a>
## ⚠️ 高频易错点

- 当前任务进度不应自动升级为所有会话的长期规则。
- 索引帮助发现，主题保存正文；主题被选中与进入请求仍是两步。
- 调度游标和整理锁解决重复与竞争，不验证事实，也不回滚文件。
- 提示要求的数量上限，要与代码和实际注入预算分别核对。

## 本章自测

**任务一：完整保存。** 新反馈只存在于主题文件，索引没有条目；另一个任务通过相关性选择仍找到了它。能够确认什么？还缺哪项维护？

<details><summary>参考答案与解释</summary>

可确认主题存在且该次选择找到它，不能据此断言入口索引正确，也不能确认正文已注入。在要求索引的保存路径中应补齐有效指针，再核对附件和实际请求；其他路径一次成功不能替代索引维护。

</details>

**任务二：保存失败。** 主对话向记忆路径提出 Write，工具返回权限错误，后台提取却检测到这条调用。应该如何处理？

<details><summary>参考答案与解释</summary>

它可能跳过辅助提取并推进游标。应核对错误结果、实际文件和索引，解决权限或使用获准路径后补写验证。不能把写入调用或跳过日志当作保存成功。

</details>

**任务三：召回迟到。** 禁止改公开接口的长期约定在第一次请求发出后才返回，能保证第一次编辑遵守它吗？应放在哪里更可靠？

<details><summary>参考答案与解释</summary>

不能。约定应进入可靠加载的当前任务输入或项目指令，并由必要的权限、受保护范围和验收检查配合。后台记忆可以辅助，不应独立承担必须在动作前生效的硬限制。

</details>
