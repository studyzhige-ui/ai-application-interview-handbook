## 1. 先沿一次修复认清运行对象

用户要求：“修复分页错误，不改公开接口、不删除原测试，最后说明实际运行了什么测试。”页码从 1 开始，列表 `[10, 20, 30]` 每页两个元素，前三页应分别为 `[10, 20]`、`[30]`、`[]`。后文一直用这个任务观察产品运行，不另加安装或编码作业。

Claude Code 的宿主接收输入、提供工具、维护会话并显示结果；模型只在宿主发起请求时判断下一步。终端交互入口通常称为 REPL，程序化入口由 `QueryEngine` 管理会话；两者可进入同一查询执行链，却不具有完全相同的界面和保存策略。

| 对象 | 谁持有、维持多久 | 本例中是什么 |
|---|---|---|
| 会话状态 | 宿主跨用户轮次持有 | 消息、读取缓存、已加载指令、发现过的技能和累计用量 |
| 用户轮次 | 一次输入触发的处理过程 | 从接收修复要求到返回本次结果 |
| 模型请求 | 查询循环的一次采样 | 依据已有证据决定读文件、编辑、测试或答复 |
| 工具调用 | 执行层按调用标识管理 | 某一次 Read、Edit 或 Bash |
| 持久记录 | 会话存储在退出后保留 | 能重新选择有效历史的 transcript |

因此“一轮修复”可以有四次请求、多个工具调用。文件修改是另一份真实状态，不会因为内存消息被丢弃而撤销。`QueryEngine` 持有的跨轮次对象与 `query()` 输出的事件要分开看。[会话入口][engine-input]

<a id="2-输入先经过分流不保证调用模型"></a>
## 2. 输入先经过分流，不保证调用模型

输入并不只是一条字符串。它可能包含文本与图片块、粘贴内容、IDE 选区、文件附件或斜杠命令。基础处理先规范化材料：图片按路径调整尺寸及字段，保留处理后的内容块；文本与前置非文本块仍需要一起交给后续处理。只处理图片却继续发送原始数组，会让规范化失去意义，快照明确把新数组沿普通提示路径传下去。[输入规范化][input-normalize]

随后根据入口和命令类型分流：

| 输入情况 | 处理结果 | 是否进入模型循环 |
|---|---|---|
| 普通修复要求 | 用户消息及适用附件 | 通常进入，仍需输入 Hook 放行 |
| 本地命令能直接完成 | 命令输出、可能的会话状态变化 | 可以 `shouldQuery=false` |
| 需要模型执行的命令或技能 | 展开正文，并产生允许工具、模型等设置 | 采用展开后的材料进入 |
| 输入 Hook 阻止 | 警告或停止说明 | 不进入 |
| 桥接入口的斜杠文本 | 受远端安全命令规则处理 | 不可任意当成本地命令执行 |

`skipSlashCommands` 可以让以 `/` 开头的文字按普通文本处理；桥接来源又有明确的安全命令例外。已知但不支持远程执行的命令可直接返回说明，而不是暗中执行本地功能。普通文本和命令各自取得附件，不能假定所有输入先走同一附件分支。

这解释了一个看似反常的结果：宿主可以返回 SDK `success`，但这一轮没有向模型发请求。例如本地命令已产出 `resultText`。这里的成功是输入处理协议完成，既不是模型一定参与，也不是分页一定修好了。[零模型结果分支][engine-input]

<a id="3-输入-hook-的不同反馈会留下不同历史"></a>
## 3. 输入 Hook 的不同反馈，会留下不同历史

基础处理已经判定无需查询时，直接返回，不再为它执行通常的 `UserPromptSubmit` 查询前处理。需要查询时，输入 Hook 才有机会参与：

- `additionalContexts` 变成附加上下文消息，后续请求可以使用
- `blockingError` 返回系统警告；该路径的返回消息替换普通输入结果，警告中仍显示原提示
- `preventContinuation` 保留已经处理的原提示，再追加停止说明并将 `shouldQuery` 置为 false
- 临时 `progress` 不当成需要注入的结果消费

“Hook 阻止了”因此不是唯一一种历史形状。恢复后只见警告，和仍见原提示但未执行，是不同分支的预期结果。[输入 Hook 消费][input-accept]

SDK 接收处理后的消息后，先把它们加入会话并记录 transcript，再进入模型循环。这避免用户发出要求后、模型尚未回应时进程被杀掉，恢复却找不到已接纳的任务。是否等待刷写受入口和配置影响，[第七章](07-persistence-and-resume.md) 再展开。命令产生的允许规则及模型选择也在这一时点进入后续执行设置，而不是只停留在命令输出中。

<a id="4-第一次请求准备了什么"></a>
<a id="3-一轮用户任务可以包含多次模型请求"></a>
## 4. 第一次请求准备了什么

进入查询以后，宿主组织项目指令、系统提示、用户上下文、有效消息和本轮工具定义。它们不是一份巨大字符串：`system`、`messages`、`tools` 分别承担系统块、会话内容和工具定义的职责。具体装配与缓存见[第五章](05-context-and-compaction.md)。现在只记住，第一次请求只能使用已经进入这些字段的材料。

| 请求 | 已有证据 | 模型输出 | 宿主动作 |
|---|---|---|---|
| 1 | 任务与指令 | `tool_use(read_1)` | 读取真实实现 |
| 2 | 新增 `tool_result(read_1)` | `tool_use(edit_1)` | 校验、批准并修改 |
| 3 | 新增修改结果 | 测试工具调用 | 执行并收集结果 |
| 4 | 新增测试证据 | 解释修复和验证范围 | 检查能否停止并交付 |

这是正常主线的教学缩写；一个请求也可能提出多个工具。模型说“我将测试”只是文字，只有结构化调用被执行，才有真实测试结果。

<a id="5-模型流与工具执行可以重叠但结果必须收齐"></a>
## 5. 模型流与工具执行可以重叠，但结果必须收齐

`query()` 是异步生成器，逐个向调用方产出事件；`queryLoop()` 持有迭代状态，在循环内继续请求，不是每个工具结果回来便递归开启一个新会话。

启用流式工具执行时，一段完整的工具提议可在模型流尚未结束时登记给执行器。执行器依工具的并发安全声明安排工作，完成的进度与结果可以陆续交付。流结束并不意味着工具结束：查询层还需要收完这一批结果，再取得执行器更新后的上下文。[流中派发][query-stream]

接下来发生的顺序同样重要：

```text
模型流结束
  → 收集待完成工具结果
  → 采用执行器更新后的程序上下文
  → 添加本轮可消费附件、通知、已就绪的记忆
  → 刷新可用工具
  → 检查轮数等边界
  → 带着新消息进入下一次请求
```

普通通知不能任意插入还没闭合的工具调用与结果之间。新连接工具在后续刷新后才能成为新的调用候选；后台记忆若尚未完成，也不会为这个消费点无限等待。[工具后续处理][query-continue]

<a id="6-停止不是没有工具一个条件"></a>
## 6. 停止不是“没有工具”一个条件

没有工具调用时，循环还要处理响应错误、输出上限与停止 Hook。下面区分外部事件和宿主的实际去向：

| 事件 | 宿主如何改变本轮状态 | 后果 |
|---|---|---|
| 正常文字且停止检查放行 | 接受本次结束 | 返回本轮结果 |
| Stop Hook 提供阻塞反馈 | 把反馈加入后续输入，并维护防重复状态 | 再迭代，未完成交付 |
| 到达输出长度上限 | 按适用配置升级输出预算或追加续写条件 | 可继续，但不是无限重试 |
| 达到轮数、费用等限制 | 返回对应限制结果 | 停止不等于任务目标完成 |
| 用户取消流 | 收束在途调用；必要时补取消用的合成工具结果 | 保持调用配对，不证明副作用未发生 |
| API 错误 | 走错误或可恢复分支，绕过常规 Stop 评估 | 避免错误反馈不断扩大请求 |

请求过大时，可见路径先尝试耗尽适用的折叠能力，再考虑反应式压缩。对应内部模块并未全部取得，不能从调用点推断它完整的裁剪算法。输出续写、Stop 阻塞、请求重试各有条件和状态，不能合并成“失败就让模型再试一次”。[继续与终止分支][query-stop]

若模型流失败后切换尝试，已经产生的旧助手片段可用 tombstone 标记失效，旧工具执行器被丢弃，避免旧结果混入新尝试。但已经编辑的文件仍在，下一章会解释这种结果隔离为何不是事务回滚。

## 本章小结

先接纳和规范化输入，再决定本地完成还是进入查询。进入后，模型流提出动作，工具层执行并交回结果，查询层更新状态、消费后续材料，再决定续轮或停止。会话、用户轮次、模型请求和调用各有寿命。

## 🎯 面试怎么回答

**问：为什么一次 Claude Code 输入可以零次或多次调用模型？**

输入先经过命令分流和输入 Hook，本地完成或被阻止时无需调用模型。需要推理时进入查询循环；模型可流式提出工具，宿主执行、回填并更新上下文，多次请求共同完成一个轮次。没有工具也须检查错误、输出上限和停止 Hook，最后的 SDK 结果描述运行状态，不直接证明业务验收。

## ⚠️ 高频易错点

- 界面已经显示输入，不等于它已进入模型或完成持久刷写
- 模型流结束，不等于在途工具已结束
- `success` 可以来自本地命令，不能反推模型参与或任务正确
- 合成取消结果维护消息关系，不撤销磁盘或远端动作

## 本章自测

**问题：** 测试工具已启动，模型流断开，重试又发出相同测试调用。能否只凭旧结果被丢弃，就认为旧测试没运行？

<details><summary>参考答案</summary>
不能。结果隔离改变查询接收什么，取消信号只请求工具停止。先核对原进程、输出和副作用，再判断新的执行是否必要。对写操作尤其不能把调用 ID 当业务防重键。
</details>

**问题：** 输入处理返回 `shouldQuery=false`，SDK 随后返回 `success`。最小可确认事实是什么？

<details><summary>参考答案</summary>
该入口完成了这次输入的非查询处理并返回协议结果。还应看命令输出或 Hook 说明；不能确认发生过模型采样，也不能确认修复、测试或保存均已成功。
</details>
