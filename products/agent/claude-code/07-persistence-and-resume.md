# 07. 持久化与恢复｜有效历史怎样重新接回真实工作

[← 上一章](06-session-and-auto-memory.md) · [本产品目录](README.md) · [下一章 →](08-observation-and-delivery.md)

> 本章依据[私有学习快照及核验边界](README.md#学习对象与版本边界)。示例对象、数字与时间线为教学推演，不是产品运行记录。

<a id="1-保存不是在最后说一句已记录"></a>
<a id="1-把任务停在最容易误判的位置"></a>
## 1. 保存不是在最后说一句“已记录”

分页源码已改，测试还在运行，宿主关闭进程。恢复需要知道用户要求、已经发生的修改以及尚未确认的结果；仅有最后一段助手文字不够。

`QueryEngine` 的保存发生在多个交接点：

| 时点 | 保存目的 | 不能混同的事实 |
|---|---|---|
| 输入处理后、查询前 | 让已经接纳的用户任务可恢复 | 界面显示不等于刷写完成 |
| 消费助手、用户及边界等查询事件时 | 记录执行产生的有效历史 | 临时进度不是全部持久记录 |
| 保存压缩边界前 | 补齐将保留的消息，使 segment 引用可解析 | 内存中存在不代表旧消息都已落盘 |
| 交付最终 SDK result 前 | 适用宿主条件下 flush 尾部写入 | result 不是所有入口的无条件同步落盘保证 |

当启用会话持久化时，普通 SDK 输入路径会等待记录；bare/SIMPLE 路径可非阻塞发起写入。需要 eager flush 或相应 Cowork 宿主条件时会显式刷写。最终 result 之前的 flush 避免宿主收到结果便立即杀掉 CLI，导致尾部消息丢失。[输入持久化][engine-input]、[边界前补写][engine-boundary]、[结果前 flush][engine-result]

因此保存合同由入口、持久化选项与刷写条件共同决定，不能把一个已核验入口的时序外推给所有运行方式。
<a id="2-恢复先找正确历史再核对执行对象"></a>
## 2. 恢复先找正确历史，再核对执行对象

镜像的消息使用 `uuid` 标识，用 `parentUuid` 表示接续关系。恢复时要选择有效链，不是把记录文件中的所有行依次拼起来。压缩摘要、历史裁剪和工具结果替换，都可能影响应该接回哪段历史。[会话存储][storage]

例如修改消息已持久化，测试只有“已启动”的进度。恢复时应该保留“文件已修改、验证待确认”，而不是补出一次从未记录的测试成功。

进度显示、记录入口和有效父链也要分开：SDK 会把 `progress` 与附件及时交给记录入口，避免延迟补写扰乱去重位置；存储层另行区分进度与正常链节点，并处理临时进度类型。旧记录已有进度节点时，加载器还有跨越旧节点的兼容处理。因此既不能把每个进度 tick 当作恢复主链，也不能笼统说所有 progress 都从不交给存储。[事件记录与链边界][engine-events]。

恢复可以按三个对象分别进行：

| 步骤 | 本例要确认什么 | 得到的下一步条件 |
|---|---|---|
| 恢复有效历史 | 原约束、修改结果、尚未确认的测试 | 知道任务做到哪里 |
| 恢复执行环境 | 仓库、工作目录、工作树、代理和可用工具 | 知道接下来会操作哪份代码 |
| 核对真实状态 | 当前 diff、测试进程或输出、必要远端记录 | 决定继续等、重测还是修复 |

`sessionRestore.ts` 不只恢复消息，还处理文件历史、任务、代理、工作树和相关元数据；受功能控制的折叠状态也需在首次查询前恢复。[恢复入口][restore]

同一个 `src/pagination.py` 在两个目录里可以是不同文件。切换工作树后沿用旧目录的指令或缓存，可能让程序继续操作错误对象。恢复环境后重新核对实际文件，正是为了解决这个问题。

<details><summary>不同入口与文件历史的边界</summary>

交互式任务状态与部分非交互入口从旧 TodoWrite 消息恢复的路径不同，不能描述成统一的任务持久化策略。恢复记录需按实际入口解释。

文件历史快照可以帮助处理文件变更，不是整个系统的通用检查点。远端写入、后台进程、凭据等仍需要各自的查询与恢复办法。

</details>


<a id="3-为什么压缩后不能直接重写旧消息的父指针"></a>
## 3. 为什么压缩后不能直接重写旧消息的父指针

消息用 `uuid` 标身份，`parentUuid` 表示前驱。保留消息可能已经写入 JSONL，后续记录会因为去重跳过它；只改内存中的父指针，不会自动改掉磁盘旧记录。因此压缩边界另存 `preservedSegment`，包含 `headUuid`、`anchorUuid`、`tailUuid`。[接链实现][restore-chain]

看一个后缀保留的教学例子，箭头表示“后一个消息的父节点是前一个”：

```text
原磁盘链：U → A → K1 → K2
新增记录：B → S → N
边界 B 的 segment：head=K1，tail=K2，anchor=S
```

K1、K2 是需要保留的尾部，S 是摘要；它们在磁盘仍然连着旧链，N 暂时跟在摘要后。加载器验证 K2 能沿父链走到 K1 后，在内存中执行两步：K1 的父节点接到 S；S 的其他子节点（这里的 N）接到 K2。重建后得到：

```text
有效历史：B → S → K1 → K2 → N
旧的未保留部分 U、A 不进入这条有效历史
```

保留区间内部 K1→K2 原本完整，只需修两端。前缀保留时 anchor 可以是边界自身，而不是最后摘要，不能把 S 的角色写死。

加载器只对最后仍有效的 segment 接链；若其后已有不带 segment 的新边界，旧 segment 已失效，不应变成另一条幽灵叶子。然后剪除最后边界之前未被保留的项。若 tail→head 走不通，程序保守退出，不进行那次剪除，避免损坏元数据让历史进一步丢失。

保留助手消息的旧 usage 还需清零，因为磁盘 usage 可能记录压缩前的大窗口。若直接复用，就可能刚恢复又因旧用量立即触发压缩。这是恢复估算基线的修正，不是抹去真实费用记录。

<a id="4-消息恢复以后还要恢复环境与所有权"></a>
## 4. 消息恢复以后，还要恢复环境与所有权

普通 resume 可沿用会话身份并恢复费用等状态；fork 则不继承原工作树的清理所有权，工具结果 replacement 状态需要按对应路径复制。这使新会话可以继续使用材料，而不擅自删除原会话拥有的资源。[恢复环境和 fork][restore-environment]

工作树恢复先看是否已有新建工作树；存在时新对象优先。旧目录不存在则清掉陈旧状态，避免再次把失效路径写回元数据。成功切换工作目录后，清理记忆文件缓存、系统提示分区和计划目录缓存，使后续材料对应新环境。

会话中途 `/resume` 切换与进程启动时 `--resume` 还有不同前置状态。前者可能先退出上一恢复工作树，再选择下一会话，不能因为旧缓存还在就阻止切换。目录变化不自动改变项目的所有锚点，恢复逻辑有意维持需要稳定的项目归属。

恢复到“知道任务做到哪里”以后，仍要检查当前 diff、真实测试进程或输出、必要的远端记录。消息恢复不复活所有旧进程，文件历史也不是整个外部世界的事务检查点。
<a id="3-重试之前先定位失败发生在哪一层"></a>
## 5. 重试之前，先定位失败发生在哪一层

| 失败位置 | 已知事实 | 继续之前要确认什么 |
|---|---|---|
| 模型 API 没取得有效响应 | 模型通信失败 | 可否重试、剩余预算与等待条件 |
| 模型流开始后中断 | 部分工具可能已经启动 | 哪些动作发生过，怎样隔离旧结果 |
| MCP 认证或会话失效 | 连接条件出现问题 | 刷新认证、重建会话还是修正地址 |
| 工具返回业务错误 | 已取得一个错误结果 | 是否部分修改，应该换参数还是停止 |
| 工具可能成功但响应丢失 | 业务结果未知 | 查询真实状态，判断能否安全重复 |

模型 API 的分类与等待见 [`withRetry.ts`][retry]。前台用户等待与后台工作可以采用不同预算，容量错误与非法参数也需要不同处理。增加重试次数，只能帮助适合重试的故障，不能解决缺少授权或错误参数。

流失败后的旧执行器处理见 [工具篇](02-tool-execution-and-permissions.md)：丢弃迟到结果防止消息混入新尝试，真实文件和外部写入仍需核对。

### 结果未知时，怎样决定是否重做

设远端工具创建了缺陷记录，但响应返回前断网。会话只有调用，没有成功结果。此时有三种合理去向：

1. 服务支持按业务唯一键查询：先查是否已经创建。
2. 服务提供可靠的幂等键语义：在有效范围内复用同一业务请求键。
3. 既不能确认，又不能安全重复：保留未知状态，取得必要人工判断。

Tool Call ID 用于配对模型调用与结果；只有远端服务将某个键持久地用于业务去重，才可能支持相应幂等。换一个调用标识再次创建，不会自动防重。这是从前述状态分层推导的工程处理原则，不声称镜像为所有服务实现了通用事务。


## 本章小结

输入、查询事件、压缩边界和最终结果有各自保存点。压缩后的保留区间靠边界元数据在加载时接链，还要修正旧用量；resume/fork 则分别处理身份、缓存、工作树与所有权。最后以真实文件和外部状态决定下一步。

## 🎯 面试怎么回答

**问：为什么 transcript 完整也不能直接保证安全恢复？**

首先要选对有效链，处理压缩保留区间和结果替换；其次要恢复工作目录、工具条件与资源归属；最后核对真实副作用。磁盘记录可能带旧父指针或旧 usage，结果前 flush 又受入口条件控制。因此记录存在、有效历史可构建和真实任务可安全继续是三层不同保证。

## ⚠️ 高频易错点

- 对内存父指针的修改，不会重写被持久化去重跳过的旧消息
- 损坏的保留区间不能靠猜测强行剪枝
- 清零旧消息 usage 是修正压缩估算，不等于费用账单归零
- fork 可以复制材料，不能据此继承他人工作树的销毁权
- 没有收到成功结果可能是结果未知，而不是动作未发生

## 本章自测

**问题：** K1、K2 已落盘，压缩希望把它们接到摘要 S 后；直接修改内存 parentUuid 后保存却被去重跳过。怎样让 resume 仍构建正确历史？

<details><summary>参考答案</summary>
在新边界记录 head=K1、tail=K2、anchor=S 的保留区间元数据。加载时先验证区间，再接 head→anchor、将 anchor 其他子节点接到 tail，并处理旧 usage 和边界前未保留消息。不是把所有 JSONL 行按写入顺序直接拼成聊天。
</details>

**问题：** 恢复记录写着测试已启动，但旧进程已不存在，代码已修改。能否直接报告失败或通过？

<details><summary>参考答案</summary>
都不能。先查是否留下可信的完成输出，确认对应目录与代码版本；无法建立结果时保持未确认，再在授权范围内判断是否重新验证。历史启动事件不包含退出状态。
</details>
