# 三种委派｜原生子任务、持久批次和外部 Agent

[← 上一章](03-skills-and-mcp.md) · [本产品目录](README.md) · [下一章 →](05-delivery-and-goals.md)

三种委派有不同的保存和恢复单位。普通 task 保存本次结果与事件，batch_task 保存可重新领取的任务项，ACP 启动外部 Agent 进程。不能用一个“后台子 Agent”名称替代它们的生命周期。

<a id="native-task"></a>
<a id="7-子智能体隔离的是什么又共享了什么"></a>

## 普通子任务：有自己的推理过程，不一定有独立文件世界

主智能体可以把“只分析指定监控证据，返回异常原因，不修改文件”交给 `task`。这段委派至少要给出任务、必要输入与结果要求；否则子级没有足够信息独立完成。

```text
父级：形成委派说明 → 调用 task ─────────→ 收到结果，再判断是否可用
                         │                        ↑
子级：                   └→ 模型 → 工具 → 模型 ───┘
```

子级有自己的消息、模型调用、工具约束和预算。原生子图使用 `checkpointer=False`，避免继承父检查点并污染父会话；普通子任务的模型内部步骤不默认作为跨用户轮次可恢复的子会话保存。执行事件仍可记录，父级也可保存委派摘要，这些不等于完整子图检查点。[子执行][s3-executor] · [子任务约定][s3-subagents]

<a id="71-isolated-与-snapshot-是信息选择不是两个独立物理世界"></a>

### 上下文怎样交给子级

| 模式 | 子级怎样获得背景 | 需要注意什么 |
|---|---|---|
| `isolated` | 依赖完整的委派说明 | 说明必须自包含，不能默认子级知道父对话 |
| `snapshot` | 派发时复制父级必要历史 | 固定的是当时背景，不随父级后续消息变化 |

快照可包含摘要、真实用户与可见助手消息，以及已配对完成的工具历史。父工具历史会表示成静态文本，不冒充子级自己的调用协议；父系统提示、秘密和权限声明也不能原样复制为子模型授权。原生 document 内容块可保留媒体或引用，文本、标题及引文中的不可信标签则中和后作为历史数据传递，不直接丢掉整份文档，也不把其文本升格为指令。[上下文快照][s3-snapshot]

用户身份、知识范围与受控执行约束仍通过明确运行路径传递。隔离模型输入，不等于把子级变成没有身份或限制的匿名进程。

### 共享资源会带来什么后果

子级通常仍可共享父线程工作区与沙箱。两个子任务同时改同一文件，依然可能冲突。独立只读证据收集容易拆分；有输入依赖或重叠可变状态时，应先安排顺序、目录或输出责任，而不是只增加智能体数量。

普通 `task` 可在派发时复制有效的本轮上传状态。空列表明确表示本轮没有新上传，不该换成旧会话全部文件；缺少或损坏状态也不能假装可用。延迟执行的批任务没有同样的父运行上传边界。[上传与共享资源][s3-subagents]

> ⚠️ **上下文隔离不等于文件隔离。** `snapshot` 也不是冻结整个文件系统；同一份文件仍可能被其他参与者修改。

<a id="72-所有子任务共享一个持久隔离循环不是每个子任务都开一个循环"></a>

<a id="73-子消息压缩以后步骤记录不能继续相信旧长度"></a>

<details>
<summary>子任务的事件循环与步骤记录怎样连接父级</summary>

原生子任务被送到进程内专用、持久的异步事件循环，与父请求循环分开；不是每个子任务都新建一个循环。跨循环可以传递合适的上下文，却不能直接借用绑定父循环的 Journal、连接池或 Future（尚未完成结果的对象）。

需要写父级事件时，子任务通过窄范围代理把记录动作调度回父循环，而不是直接修改父 Journal。源码过滤相应循环绑定回调，同时保留适合传递的流式语义。[代理][s3-task-tool] · [循环约定][s3-subagents]

一个工具步骤可能新增多条 ToolMessage，只看最后一条会漏记。历史压缩后长度还会缩短，扫描游标要相应调整，并结合稳定身份或内容去重。开始、步骤、结束事件分别记录，界面按子任务展开，不把全部中间消息塞回父对话。[步骤捕获][s3-steps]

</details>

### 原生 task：接纳、运行、部分结果和释放

先取得进程级执行容量，任务才从 pending 进入 running；容量不足属于接纳失败，不应当作已执行模型失败消耗同样的尝试预算。运行期间收集每步助手消息、所有新增工具结果、用量与收据，父级通过 task 返回和委派账本消费有界结果。

取消采用协作式检查：流返回一个已执行状态块后先保留其工具收据，再观察取消，避免丢掉取消在途时刚完成的动作。随后等待流关闭，才写取消终态和释放沙箱租约；一个长工具调用内部尚未返回时，不能只因为按了取消就宣称资源已释放。

还有一种正常结束没有新的助手正文：最后一批调用全部属于 return_direct 工具，且每个调用都有匹配结果。执行器从实际编译后的工具注册表识别这类工具，按调用顺序取返回文字作为最终结果；其中任一结果为 error，子任务即为 failed，不能把工具错误文字包装成 completed。未满足完整直接返回条件时，才沿普通助手文本提取路径判断。

轮数耗尽时，如果末尾有可用助手文本，可以返回 completed 并附 turn_capped；没有可用部分成果则 failed。被标记的提供方错误兜底文字不能冒充部分成果。token 或循环上限也可通过停止原因传给父级。父级必须一起读状态、原因、结果与证据，而非只检查 completed。

超时和取消可能早于图的下一次状态发布，收尾仍从用量收集器补最后记录；不能因没收到最后 values 块就把已消耗的模型请求记为零。[原生执行状态与收尾](https://github.com/bytedance/deer-flow/blob/4d5607229ef1ebe8a66c9b9644b91da9082c3221/backend/packages/harness/deerflow/subagents/executor.py)

<a id="8-委派总量执行容量与持久批任务是三层控制"></a>

## 长任务需要区分总量、并发与持久调度

假设同时最多执行三个子任务，却允许模型不停创建新批次，最终仍可能运行一百批。这些数值只为说明控制维度，不是默认配置。

| 限制 | 控制什么 |
|---|---|
| 本次 Run 的委派总量 | 这一轮最多交出去多少工作 |
| 同时执行容量 | 此刻最多有多少子任务占用资源 |
| 单个子任务预算 | 每项最多用多少轮次、时间或 token |

本次 Run 的总委派量从运行覆盖或配置解析，显式 null 也回退配置，再钳制到实现支持的范围；并发同时受实际进程槽位约束。

模型看到的能力说明应与启动时固定的执行容量一致，不能文案热更新了，实际控制器仍执行另一套限制。[容量与总量][s3-subagents]

<a id="81-普通-task-与-batch_task-的持久边界不同"></a>

### batch_task 保存的是可接管任务，不是每一步模型现场

| 对象 | 保存什么 | 故障恢复的含义 |
|---|---|---|
| 普通子图 | 本次内存状态与事件证据 | 不默认从某个子模型步骤续跑 |
| `batch_task` | 批次、任务项、说明、租约和有界结果 | 未完成项可由批服务重新接管 |
| 父检查点 | 父级继续状态与子任务摘要账本 | 父级知道曾委派什么，不等于拥有子图检查点 |

批模式通过明确工具选择进入，不是提示很长就自动转成持久队列。工作器领取任务项并续租；租约表示一段时间内由谁处理它，完成时按拥有者身份写结果。进程停止、租约过期以后，其他工作器可在尝试预算内接管。接纳失败与实际执行失败也有不同计数语义。[接纳与续租][s3-batch]

> ⚠️ 重新领取任务项，不等于从子模型上一条消息原地继续，也不保证外部动作精确执行一次。重试前仍需根据动作与证据判断重复风险。

### 批任务从领取到结算，为什么要反复核对租约

批服务先持久化任务说明、稳定任务项身份和执行配置，再领取并装配工具。MCP 装配可能等待很久，因此真正启动前重新续租并检查取消；等待期间任务已取消或租约失效时，不再启动迟到工作。

执行后定期续租，丢失租约请求取消当前原生执行。容量准入失败重新排队，与已经执行后的失败尝试分开。成功结果有总长度和预览预算，并记录是否截断；配置验收条件时可调用 advisory 检查，等待验收期间继续续租。

验收检查不可用时，保留有用结果并标为未检查，不自动丢弃或重跑。工作器关闭时请求取消，却不抢先写终态；让租约过期后的新工作器按稳定任务项接管。这个身份可帮助业务幂等，但不会自动使外部操作恰好执行一次。[批服务全过程](https://github.com/bytedance/deer-flow/blob/4d5607229ef1ebe8a66c9b9644b91da9082c3221/backend/packages/harness/deerflow/subagents/batch_service.py)

<a id="acp"></a>
## ACP：启动外部进程，与原生子图分开管理

`invoke_acp_agent` 从已配置清单选外部 Agent，解析本线程 ACP 工作目录及可传递的 MCP 配置，启动对应进程，完成协议握手，再建立新会话并发送自包含任务。它收集外部文本流，提示返回后退出进程上下文，最后把文本交回父模型；没有文本时返回明确空响应。

外部产物通过 ACP 工作区的只读映射读取，不应把父级 `/mnt/user-data` 路径直接当成对方可访问路径。线程目录无效或缺失时，工作目录解析有回退边界，因此“独立工作目录”不是所有文件访问都受操作系统隔离的承诺。

权限请求默认答复 cancelled；只有显式 `auto_approve_permissions` 配置，才在可用选项中优先选 allow_once，再选 allow_always。它不自动复用原生 task 的批准流程。超时退出外部进程上下文，错误返回父模型；这个新建会话调用也不等于拥有原生子图或批任务的恢复合同。[启动、权限与返回](https://github.com/bytedance/deer-flow/blob/4d5607229ef1ebe8a66c9b9644b91da9082c3221/backend/packages/harness/deerflow/tools/builtins/invoke_acp_agent_tool.py)

<a id="82-什么时候值得委派"></a>

委派有启动、重复发现与汇总成本。只有并行时延、专长或上下文隔离收益值得这些成本，才应使用；每批重新判断，不因上次委派有效就把全部后续工作交给子级。
