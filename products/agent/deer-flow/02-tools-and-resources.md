# 工具与执行资源｜检查、修改、回填和释放

[← 上一章](01-run-and-model-loop.md) · [本产品目录](README.md) · [下一章 →](03-skills-and-mcp.md)

模型提出修改以后，要经过的是一串可提前拒绝的处理器，最后才到真实文件或沙箱。这里把同一资源的取得、使用、结果与释放放在一起解释。

<a id="4-从一个调用提议到真实执行要经过哪些检查"></a>

## 执行侧每一层分别负责什么

沿前面的文件修改轨迹，再把检查职责展开：

| 层次 | 需要确认的问题 |
|---|---|
| 参数与业务输入 | 参数可解析，目标和操作有意义吗？ |
| 发现与技能限制 | 已展开且当前技能允许吗？ |
| 产品授权与护栏 | 当前身份可使用这项能力，策略是否拒绝？ |
| 沙箱与路径 | 操作实际落在哪里，能接触哪些资源？ |
| 文件新鲜度 | 修改前是否读过当前版本？ |
| 结果规范化与收据 | 发生了什么，下一次调用和产品记录怎样理解它？ |

这些是不同责任，不是所有组件无条件依次运行。实际安装由配置决定，外层可提前拒绝。授权提供者通过适配器复用 GuardrailMiddleware 的拒绝与错误语义，护栏和沙箱仍分别承担自己的边界。[实际构建顺序][s1-wrappers]

### 选一条实际组装路径，看进入与返回的顺序

假设本次开启工具收据、产物句柄解析、授权、先读后写和进度记录，未配置额外外部护栏。调用从外往内经过：收据包装 → 解析产物句柄 → 产品授权 → 沙箱审计 → 文件新鲜度 → 进度记录 → 工具错误规范化 → 实际工具。若配置额外护栏，它在产品授权之后参与；关闭可选组件，则不安装相应层。

外层收据包住整条链，是因为授权、沙箱审计或先读后写都能提前返回错误。若收据放在最内层，提前拒绝的动作就会从账本消失。句柄先解析成实际对象，再让策略检查参数，避免授权检查一个名字、执行另一个目标。

允许的调用进入工具，错误处理把异常规范成错误 ToolMessage；进度层消费这个有类型的结果，再由外层收据记录。若先读后写已经拒绝，业务函数和进度槽位都不进入，但外层仍得到拒绝收据。若实际写入后，后续结果处理失败，文件可能已变，不能据错误回执宣称“未执行”。[组装顺序与提前返回](https://github.com/bytedance/deer-flow/blob/4d5607229ef1ebe8a66c9b9644b91da9082c3221/backend/packages/harness/deerflow/agents/middlewares/tool_error_handling_middleware.py)

工具结果返回还经过内容处理包装层。启用个人信息脱敏时，先处理敏感字段，再处理中和注入标签、结果预算与外置；这样外置副本也不应写下脱敏前原文。检查点、模型内联结果、原始服务输出与外置文件因此可能不是同一份字节，排查应定位它们各自在哪一层产生。

<a id="12-本地沙箱的名字不等于安全隔离"></a>

### LocalSandbox 不等于安全隔离环境

`LocalSandboxProvider` 在宿主环境执行，本身不是安全隔离边界。默认隐藏这条模式下的宿主 Bash，只有明确允许才暴露；不是已经有了安全的本地 Sandbox Bash，再删去多余 Host Bash。

允许命令前必须知道执行位置、可访问文件与网络。AIO、E2B、OpenSandbox 等提供者各有实现限制，更换提供者不能默认安全与持久语义不变。[本地 Bash 门控][s1-security]

<a id="5-先读后写怎样防止基于旧文件反复修改"></a>

## 先读后写怎样防止基于旧文件修改

文件是版本 A，模型执行 `read_file`，工具结果保存完整当前内容的 SHA-256。稍后要 `write_file` 或 `str_replace`，门控重新计算当前哈希：仍是 A 才能沿已读路径继续；已被改成 B，则旧依据失效，需要重读。

一次写入不会替模型更新“已读”标记。成功写入改变字节后，下次修改需要重读；若字节完全相同，哈希未变，不能概括成“任何写调用都无条件废除全部标记”。部分区间读取也可记录文件版本，但不代表模型读过每一行。[读取与版本检查][s1-read-write]

### 两个并发写为什么还需要锁

若两个修改都检查到了 A，再同时写入，单次检查都正确也挡不住整体覆盖。DeerFlow 用相同作用域和规范化路径的进程内锁，把检查与执行放在同一保护范围；读取与标记也使用相应保护。

```text
写入 1：取得锁 → 检查 A → 写成 B → 释放锁
写入 2：等待锁 → 检查时已经是 B → 旧读取依据不再匹配
```

这段推演假设两次写入确实经过同一把锁，且第一次改变了字节。外部编辑器、其他进程或未接入路径不受它约束，不能扩大成跨进程文件事务。[锁与执行][s1-read-write]

<a id="52-这道门不是普遍的-fail-closed-安全边界"></a>

### 无法检查时，不是一律拒绝

| 门控观察到什么 | 该实现怎样处理 |
|---|---|
| 文件存在、可检查，但没有当前版本读取标记 | 返回错误，不进入写工具正文 |
| 文件不存在 | 放行，创建或替换是否可行由工具判断 |
| 普通检查故障，或返回 `Error:` 等不可检查内容 | fail-open，即检查失败时放行，由工具产生结果 |
| 沙箱授权明确拒绝 | 返回授权错误，不当成普通检查故障 |

**这是有适用范围的新鲜度检查，不是普遍的 fail-closed 安全边界。** fail-closed 指无法确认时拒绝；这里的普通 I/O 故障并非采用这种策略。真正被拦的大写入参数可在后续模型视图中缩短，原参数仍作为相应证据保留，不能因此声称文件已改变。[实际分支与参数裁剪][s1-read-write]

<a id="6-沙箱是需要管理的资源不是每次调用的装饰对象"></a>

## 沙箱复用时，谁负责释放

沙箱中间件负责取得、复用与释放环境；状态存标识，不存不可序列化的提供者对象。默认 `lazy_init=True` 时，普通共享视图可推迟到工具调用才取得环境；需要按策略投影技能文件时，可能提前取得，防止旧宽权限视图继续被使用。[沙箱生命周期][s1-sandbox]

主智能体与子任务可以同时用一个环境，因此每个使用者各持有一份执行租约，即“我仍在使用这个资源”的持有记录。

| 动作 | 仍在使用的参与者 | 能否因这一步关闭整个环境 |
|---|---|---|
| 主任务与子任务都已取得租约 | 主、子 | 不能 |
| 子任务结束并释放自己的租约 | 主 | 不能，主任务仍在使用 |
| 最后一个使用者释放 | 无 | 按提供者策略回收，可能放回暖池复用 |

暖池是保留可复用环境的集合，release 不一定销毁容器或删除文件；提供者最终关闭又是另一层清理。取消时，已交给工作线程的同步操作可能仍在运行，必须等待自己的操作结束再释放持有资源。取消等待者不会自动杀掉线程，租约也不会回滚命令副作用。

## 先处理大工具结果，再考虑历史摘要

<a id="61-工具返回时的外置可能改变将要保存的-toolmessage"></a>

### 工具返回时，短结果可以进入保存状态

假设监控工具返回很大的日志。`ToolOutputBudgetMiddleware` 可先把全文保存为文件，再返回有类型的摘要、预览与路径；保存失败时，退化为带标记的头尾截断。远程沙箱没有宿主挂载时，必须写到沙箱可见的位置，并核对文件存在且 UTF-8 字节数与预期完全一致，避免磁盘满或管道失败只写出部分内容。

预算在这里约束的是**字符数**，不是 token 数或 UTF-8 字节数。20000 个中文字符既不意味着 20000 字节，也不保证 20000 token。

工具返回阶段替换的是结果消息，新的 `ToolMessage` 可以进入状态。因此“全文始终保存在检查点，模型只看短版”不成立。全文能否找回，要看外置是否成功，以及收据和日志捕获了哪一阶段。[返回结果预算与外置][s0-output]

<a id="62-请求阶段的裁剪才是原状态不变的另一条路径"></a>

### 请求阶段裁剪，才可能保持原状态不变

请求阶段还会防御性缩短历史大结果。对已经成功的 `write_file`，若后来成功读取或修改了同一路径，且不属于需要保留的近期写入，可以在模型视图中省去旧的大 `content` 参数；保存的原参数不被原地修改。

同一条模型响应里的并发读取不能冒充“写入之后已经读过”，因为执行顺序未必如此。源码按调用位置与配对结果判断，不只用调用 ID 全局查找。被先读后写门控拦下的大参数，则由对应中间件单独缩短。[成功旧写入的裁剪][s0-output] · [被拦写入的裁剪][s0-read-write]
