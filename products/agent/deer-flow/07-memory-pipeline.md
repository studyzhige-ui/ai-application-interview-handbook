# 长期记忆｜筛选、提取、提交与后续读取

[← 上一章](06-history-and-recovery.md) · [本产品目录](README.md) · [下一章 →](08-observation-and-review.md)

<a id="1-先分清记忆接口记忆实现与会话历史"></a>

## 从一次对话走到下一次读取

DeerFlow 的 `MemoryManager` 是主系统调用记忆能力的接口；DeerMem 是默认实现，负责筛选、排队、提取、保存和检索。接口不是存储文件，模型请求中那段记忆文本也只是一次读取结果。[记忆接口][s2-manager]

以下固定为：用户 `u1`、明确指定的智能体 `assistant-a`、新会话 `t1`；使用 DeerMem 自动模式，记忆与自动注入都开启。假设模型把长期习惯正确识别出来，后续验证和提交成功。这是为了追踪过程的教学假设，不是实测提取结果。

| 阶段 | 交给下一步什么 | 此刻可以断言什么 |
|---|---|---|
| 本轮对话完成 | 用户原话与适合提取的助手消息 | 对话已发生，尚未产生长期事实 |
| 筛选并入队 | 带用户、智能体、会话身份的待处理输入 | 后台接收了工作，不代表已保存事实 |
| 模型提取 | “用户偏好先解释风险”的候选及分类信息 | 有一个建议，还需程序检查 |
| 程序验证 | 合法且适用的更新建议 | 通过相应检查，仍需存储提交 |
| 存储提交 | 所选智能体桶里的事实及相关摘要变化 | 这次写入才有持久结果 |
| 后续新会话读取 | 该用户与智能体范围内、有预算的记忆文本 | 模型得到保存内容的一个读取视图 |

最后一步特意使用**新会话**。同一会话已经成功注入的记忆可能继续冻结复用，后端刚保存新事实，不等于下一次模型调用立刻看见它。

`messages` 和 `summary_text` 仍负责继续当前任务。将任务摘要保存到检查点，不等于已经提取成跨会话的用户知识。沿这张表检查“卡在哪一步”，比把全部状态都称为“记住了”更准确。[自动写入入口][s2-middleware] · [DeerMem 实现][s2-deermem]

<a id="2-谁的记忆属于哪个智能体"></a>

## 谁的记忆，存到哪里

### 用户身份与智能体范围分别约束什么

`u1` 的偏好不能被 `u2` 召回。同一用户使用多个智能体时，也要明确当前读写哪一组事实。这里把按智能体划分的事实集合称为**桶**，它不是消息队列，也不是模型上下文窗口。

默认 DeerMem 分开保存用户级摘要和智能体级事实：摘要提供跨智能体的高层背景，具体事实属于选定智能体桶。本例写入目标是 `u1 / assistant-a`。[作用域与存储][s2-deermem]

队列输入携带 `user_id`、`agent_name`、`thread_id` 和可用追踪身份。后台线程或计时器因此不必重新从全局变量猜当前用户。身份要从接纳请求的可信路径传递，不能由模型自由填写后就视为有效。[队列输入][s2-queue]

<a id="6-保存兼容-api-的-json-形状不等于全部事实都在一个-json-文件"></a>

### 文件保存与 API 返回是两个层次

默认文件存储中，用户级 `memory.json` 保存用户与历史摘要；智能体事实各自保存成 Markdown 文件。`get_memory` 等接口仍可以返回带 `facts` 数组的 JSON 形状，方便调用者读取。

所以 API 返回 JSON，不意味着所有事实都在一个 JSON 文件里。事实文件与摘要是规范数据，即可作为重建依据的数据；搜索索引是派生表示，可以重建。[文件布局与存储职责][s2-storage]

<details>
<summary>调用没有指定 agent_name 时，为什么不能一律理解成全局</summary>

普通读取未指定 `agent_name` 时，DeerMem 解析到默认智能体桶。清空用户全部记忆等管理入口对 `None` 的处理可以不同。必须按入口判断：默认桶操作与遍历全部智能体，不是同一种含义。[默认桶与管理操作][s2-deermem]

</details>

## 自动模式下，哪些开关决定读写

先保持本章主例的 `middleware` 自动模式。运行结束后，`MemoryMiddleware.after_agent` 把适合处理的对话提交给后端，后端异步提取；会话需要背景时，自动注入读取有预算的记忆。

| 配置或条件 | 控制什么 |
|---|---|
| `memory.enabled` | 是否启用共享记忆机制 |
| `memory.injection_enabled` | 是否自动把记忆加入模型输入 |
| `memory.mode` | 选择自动模式还是工具模式 |
| 智能体自身记忆设置 | 本智能体是否允许相应读写 |

这些不是同一个开关。关闭自动注入，不应被读成“任何路径都不再写记忆”；反过来，某个智能体关闭记忆，也不能从共享配置开启推断它仍启用。该快照共享配置的模式默认值为 `middleware`，真实链路还要看后端能力与组装条件。[共享配置][s2-config] · [组装条件][s2-assembly]

工具模式会改变读写触发者，但不会改变“候选检查不等于提交成功”这些基本边界。先把自动写入走通，在召回一节再比较两种模式。

<a id="4-自动写入先筛选再排队不让每次工具往返都提取记忆"></a>

## 筛选与排队：先决定处理什么，再决定何时处理

### 不是每次工具往返都要提取记忆

DeerMem 先保留适合提取的用户与最终助手消息，过滤内部轨迹及无信息量的确认；缺少用户或助手一方时，也可能跳过。这样不会每读一次文件，就让记忆模型重新解释整段过程。

偏好、纠正、确认等信号帮助队列接纳和提示构造。例如“好的”通常没有独立提取价值，“以后一直先解释风险”更值得处理。“这次结果不错”也不该自动成为终身偏好。**识别出信号只是值得检查，不是已确认真相。**[预处理][s2-deermem]

<a id="41-去抖合并的是哪一份输入"></a>

### 去抖：用最新完整输入合并尚未开始的工作

去抖（debounce）表示短时间连续收到更新时，先等一个间隔，将它们合并后处理。DeerMem 用 `(thread_id, user_id, agent_name)` 识别同一目标。

假设第一次提交 `[A, B]`，第二次提交 `[A, B, C, D]`。若第一份仍在等待，就以第二份完整上下文替换它，并合并已识别信号，而不是把两份简单拼成 `[A, B, A, B, C, D]`。[去抖与接纳][s2-queue]

普通队列深度达到限制时，可以拒绝新的无信号更新；同键合并不增加深度，带信号与紧急更新仍可被接纳。因此普通深度限制不是所有任务类型都绝不突破的内存硬上限。拒绝普通更新不直接让主任务失败；只有后续重新提交仍含原消息且水位未前进，才有再次提取机会，不能保证永远自动补回。

<details>
<summary>实现定位：身份键不等于每个会话一个计时器</summary>

上述三元组决定哪些待处理输入可以合并。计时器属于队列实现，不能从身份键直接推导每个会话拥有独立计时器。需要调试调度时，分别追待处理字典与计时器的创建和重置。[队列实现][s2-queue]

</details>

<a id="42-为什么水位不能只记上次处理到第-20-条"></a>

### 水位：用消息身份记住处理到了哪里

**水位**是“正常提取已经处理到哪条消息”的记录。为什么不只记下标 20？因为压缩会删掉历史开头，新的第 20 条可能已是另一条消息。

DeerMem 记录最后提取消息的身份，优先用消息 ID，没有 ID 才退回类型与内容。找到这条消息，就处理其后的输入；找不到则重新提供完整列表，宁可重复判断，不静默越过未处理内容。[消息身份与水位][s2-updater]

水位是有界的进程内缓存，重启或淘汰会失去它。它减少重复工作，不是跨进程的精确一次提取记录。

<a id="43-紧急路径为什么与普通待处理项共存"></a>

### 紧急提取：保存即将离开历史的输入机会

压缩前提交的只是待删除历史的一个子集，不能替换队列里仍含尾部新消息的正常完整输入。因此紧急项用 `bypass_watermark` 与普通项区分，不读取或推进正常水位。

> ⚠️ 普通项与紧急项都在进程内存里。`add_nowait` 表示立即安排处理，不是等事实写完；退出时尽力排空也不会把队列变成持久任务系统。[紧急队列][s2-queue]

### 可选预筛选：决定是否值得提取，不直接决定事实真假

记忆宿主可插入 prescreen 和信号分类，两项配置默认都为 off。shadow 只记录判断，不改变提取；prescreen 的 enforce 才可能跳过提取，信号 hints 给提取提示增加线索，也可在 prescreen 为 enforce 时否决一次预筛选跳过；它不会独立决定提取，也不能直接删除或确认事实。

后台工作先按水位取未处理消息，形成提取器本来会看到的同一份文本，再交给注入的 judge；不会在主交互路径多阻塞一次判断。允许跳过时，这一批不构造提取提示、不调用提取模型、不应用变更，但会推进水位并记录本次判断，避免以后每轮重复判断同一批。

判断失败按“没有意见”处理，继续原提取流程；关闭时排空队列禁用这项成本优化，优先保存。明确反馈等整批信号参与跳过保护，模型增加的提示标签仍不能作为确认事实的确定性证据。自动提取、候选门控和存储版本检查仍是独立后续步骤。[配置默认值](https://github.com/bytedance/deer-flow/blob/4d5607229ef1ebe8a66c9b9644b91da9082c3221/backend/packages/harness/deerflow/config/memory_config.py)、[工作者消费点](https://github.com/bytedance/deer-flow/blob/4d5607229ef1ebe8a66c9b9644b91da9082c3221/backend/packages/harness/deerflow/agents/memory/backends/deermem/deermem/core/updater.py)

<a id="5-提取模型判断语义程序检查它提交的候选"></a>

## 提取：模型判断语义，程序检查候选

模型结合对话和既有记忆，提出摘要变化、新事实、删除、确认或合并建议。程序验证输出结构并检查适用范围，之后才提交。

两种错误要分开：把“一次性要求”误判成长期偏好，是语义错误；输出半截 JSON 或非法置信度，是结构错误。修好 JSON 不会自动修好语义。

### 一条候选事实怎样被挡下

自动候选用三个字段说明分类：`scope` 是适用范围，`durability` 是保存期限类别，`authority` 是信息角色。这里的 `scope=user` 表示跨任务的用户信息，不代替前面隔离存储所需的真实用户 ID。

下面保留固定快照的实际门控函数。输入是一个候选字典，返回拒绝原因或 `None`；**没有写文件，也没有修改输入字典**。

<!-- source-example: fact_scope_gate -->
```python
from typing import Any

_FACT_CLASSIFICATION_FIELDS = ("scope", "durability", "authority")

def _normalize_gate_label(value: Any) -> str | None:
    """Normalize a model-produced scope-gate label without validating policy."""
    if not isinstance(value, str):
        return None
    normalized = value.strip().lower()
    return normalized or None

def _fact_scope_gate_reason(fact: dict[str, Any]) -> str | None:
    """Return the deterministic rejection reason for a model-extracted fact."""
    if any(_normalize_gate_label(fact.get(field)) is None for field in _FACT_CLASSIFICATION_FIELDS):
        return "missing"
    if _normalize_gate_label(fact.get("scope")) != "user":
        return "scope"
    if _normalize_gate_label(fact.get("durability")) != "durable":
        return "durability"
    if _normalize_gate_label(fact.get("authority")) != "descriptive":
        return "authority"
    return None
```

先按字段顺序检查是否缺少可用字符串，再逐项比对标签；一旦不符合就返回相应原因。规范化函数只去两端空格并转小写，不判断自然语言是真是假。[原函数][s2-updater]

| 输入标签 | 返回值 | 含义 |
|---|---|---|
| `thread / durable / descriptive` | `scope` | 只属于当前会话，不作为长期用户事实接收 |
| `user / temporary / descriptive` | `durability` | 临时信息，不满足长期保存条件 |
| `user / durable / instruction` | `authority` | 指令角色，不作为描述性事实接收 |
| `user / durable / descriptive` | `None` | 这道分类检查未拒绝 |

最后一行不代表整条事实通过所有验证，更不代表已经落盘。标签由模型产生，模型仍可能把一次性原话错误标成长期信息；低权威记忆与独立工具授权因此不可省略。

<a id="52-删除和替换不能只执行一半"></a>

### 替换必须一起检查旧内容与新内容

替换偏好时，不能只看删除项格式正确，就先删掉旧事实。新事实为空、类型错误、置信度非法或替换项损坏，都可能要求拒绝对应变化，避免“旧的删除了，新的却没有合法写入”。

摘要更新与矛盾删除也有各自门控。既有记忆进入提取提示前做转义，防止其中标签破坏分区；新增检查不能代替所有破坏性操作的检查。[结构规范化与提取提示][s2-updater]

## 保存：提交时再核对最新状态

<a id="61-并发更新为什么要检查版本"></a>

### 为什么提取完成以后还可能冲突

假设提取器基于版本 10 给出更新建议；提交前用户手工纠正了一条事实，存储已变为版本 11。直接写回版本 10 的整份结果，会抹掉用户的新修改。

DeerMem 区分共享清单版本冲突与事实版本冲突。**清单**可理解为本次读取的一组记忆及其版本依据。对应提取提交路径遇到清单冲突时，重新读取最新记忆，再把同一组已解析的建议应用上去，有限次重试。删除、合并和容量判断因此重新基于新状态计算。[提取提交][s2-updater]

```text
读版本 10 → 模型提出建议
                   │
用户修改并提交版本 11
                   │
提取器提交时发现冲突
                   ↓
读版本 11 → 重新应用同一组建议 → 再尝试提交
```

这里重做的是读取、应用与提交，不是这个循环重新调用模型；也不是任意版本冲突都无条件重试。

### 调用前查重不能代替提交保证

两个新增调用都可能先看到“没有重复”，然后同时尝试保存。提前查重能省工作，存储提交路径仍要针对最新状态复核。若新事实被容量策略立刻淘汰，也不能返回一个已不存在的 ID 并声称“记住了”。[新增的复核与返回结果][s2-updater]

<a id="7-召回自动注入和主动搜索有不同任务"></a>

## 召回：默认背景与主动搜索各做什么

### 先给多少背景，再决定要不要继续找

`get_context` 回答“默认给模型多少长期背景”。DeerMem 按注入预算组织摘要与事实；启用查询相关排序时，可结合词项相关度、置信度和多样性，没有查询则保留相应默认排序。词项排序不等于已经调用语义向量模型。

`search` 回答“此刻还需要找哪些事实”。该快照启用相关性策略时，走作用域内的确定性排序；否则尝试检索适配器，无结果或可降级故障时退回不区分大小写的子串匹配。这是条件分支，不是所有策略必经的固定三级流水线。[注入与检索][s2-deermem]

规范事实可读而搜索索引故障，可以考虑替代检索；规范存储本身损坏则不能返回空数组，冒充用户没有记忆。要求记忆可用才允许继续的后端，也可以让读取失败中止运行。[错误分类][s2-manager]

<a id="3-自动模式和工具模式改变的是读写路径"></a>

### 工具模式改变触发者，不改变确认责任

| 模式 | 写入怎样开始 | 模型通常先得到什么 |
|---|---|---|
| `middleware` 自动模式 | 运行结束提交对话，后台提取 | 允许注入时得到用户摘要与有界事实 |
| `tool` 工具模式 | 模型显式调用 `memory_add`、`memory_update`、`memory_delete` 等 | DeerMem 默认注入用户摘要，详细事实通过 `memory_search` 获取 |

工具模式避免详细事实既被自动注入，又被搜索重复返回。修改或删除通常先搜索得到事实 ID，再操作它。返回结果仍要区分没找到、不支持、版本冲突与真正提交成功。[记忆工具][s2-memory-tools]

显式 `memory_add` 不是先虚构一段对话，再原样经过自动提取。它按自己的参数、身份和存储校验执行，不能把自动分类函数的全部行为直接套上去。

<a id="62-旧配置和旧文件不是直接丢弃的理由"></a>

<details>
<summary>替换后端或迁移旧配置时再读</summary>

OpenViking、Honcho、Mem0、Noop 等可以实现同一接口，但接口不要求所有后端采用向量库或保存同一种事实对象。工具模式需要真实搜索能力，事实增删改属于可选能力，不支持时应明确返回错误。某些依赖会话提取的后端通过 `requires_passive_writes_in_tool_mode` 声明工具模式仍需要被动写入，因此不能把 DeerMem 的触发方式推广到所有后端。[能力接口][s2-manager] · [模式组装][s2-assembly]

共享配置保留启用、模式、注入、退出预算和后端选择；DeerMem 的容量、提取模型、去抖等放在 `memory.backend_config`。已知旧顶层字段有带警告的兼容迁移，不是立即全部失效。旧 `storage_path` 指向 `.json` 文件时，与新配置根目录含义不同，程序特别处理并警告。已有摘要损坏或无法安全合并，不能当成空记忆覆盖。[配置迁移][s2-config] · [存储冲突][s2-storage]

</details>

<a id="8-维护纠正确认合并过期和容量不是同一种操作"></a>

## 维护：纠正、确认与淘汰有不同依据

已经保存的事实不是永远正确。先确定变化的含义，再选择操作。

| 变化 | 应考虑的处理 | 不能机械推断什么 |
|---|---|---|
| “以后不用先列风险” | 检查与长期偏好的冲突，必要时替换 | 不能只新增相反事实却继续召回两者 |
| “这次赶时间，直接给方案” | 当前任务采用例外 | 不代表长期习惯被撤销 |
| 再次确认同一偏好 | 更新最近确认时间与次数 | 不必新建同义事实 |
| 多条事实近重复 | 去重或合并，核对来源及适用范围 | 相似措辞不等于可无条件合并 |
| 到了预期有效期 | 进入复查候选 | 不等于到期立即自动删除 |
| 事实数超过容量 | 按所选策略淘汰 | 不等于语义错误或用户撤销 |

提取可先做同类近重复判断，合并还需要合法来源标识与适用条件。手工事实会在提示中被标为较高信任，但不保证模型绝不误解。[确认、合并与提取提示][s2-updater]

过期复查仍受保护类别与单次移除上限约束。容量由每个作用域的 `max_facts` 等配置控制，策略可考虑置信度、确认和访问。访问热度是辅助信息，记录失败不能让已经查到的事实反而不可用。[维护候选与容量策略][s2-updater]

临时上传路径也有寿命。“本次上传某路径的 PDF”通常属于会话，“经常处理 PDF”才可能成为长期背景。提取提交会清理上传相关的会话性描述，不能把临时路径当长期可靠证据。

<a id="9-删除清空和退出要追到队列与资源"></a>

## 清空与退出：还要管住没做完的写入

清空作用域时，DeerMem 在清空前后取消相同作用域的待处理提取，减少旧计时器把已清事实重新写回的机会。这里能从调用链确认的是**待处理项取消**；是否阻止所有已经运行的写入，仍要看存储和调用方的并发保证，不能凭两个取消调用作全局承诺。[清空入口][s2-deermem]

正常退出给 `shutdown_flush` 一个有上限的排空预算，已在处理的工作也计入。成功应意味着预算内真正排空；超时或强制终止仍可能丢掉尾部，之后还要关闭派生检索资源。

> ⚠️ 主任务完成、队列为空、后端关闭、全部事实已保存，是不同观察点。尤其不要把一次“已入队”回复当成持久提交回执。[退出与清理][s2-deermem]

<a id="10-怎样验证记忆有用而不是只验证存得更多"></a>

## 验证记忆有用，而不是只验证存得更多

围绕同一场景检查：长期习惯被保留，一次性“不要发布”没有被误当永久偏好；`u2` 搜不到 `u1` 的事实；更正后不继续召回冲突旧事实；索引故障不谎报规范数据丢失；未提交的队列项不宣称已保存。

还要看使用效果：是否减少无谓询问，是否引入过期偏好，额外输入、提取调用与等待是否值得。记忆开关对照是评测设计，没有实测就不报告提升比例。源码中的确定性门控测试也不能替代模型语义提取、多用户服务和真实效果的验证；本章只解释这些证据分别支持什么。

## 本章小结

正常路径先筛选对话，再排队、提取、验证、提交，最后按范围和预算读取。用户身份、适用范围与信息角色是不同条件；自动和工具模式改变触发方式，不改变提交确认责任。纠正、去重、过期、容量与删除分别维护事实的含义和寿命。

## 🎯 面试怎么回答

**Q：怎样设计短期到长期记忆的晋升？**

> 先区分本次任务状态和跨任务仍有价值的用户信息。DeerMem 过滤对话，由模型提出候选，再检查范围、持久性和角色，经过存储版本检查后提交。之后按作用域与预算召回，并支持纠正、确认、合并和复查。模型分类可能错，所以门控标签不能当成语义真理，记忆也不能变成授权。

**Q：用了后台队列，更新就可靠吗？**

> 要说明介质与确认点。默认 DeerMem 是进程内去抖队列，接收不代表落盘；紧急路径给待压缩消息一次提取机会。正常退出可限时排空，崩溃仍可能丢工作。需要更强保证时要额外设计持久接收、幂等和恢复，而不是把这条队列称为精确一次。

## ⚠️ 高频易错点

- **把后端事实和已注入副本混用。** 保存新偏好不保证同一会话下一次模型调用刷新。
- **把用户 ID 与候选 scope 混用。** 一个识别实际用户，另一个分类内容适用范围。
- **把 JSON 返回值当成文件布局。** API 形状与规范数据的实际存储可以不同。
- **把通过门控当成已保存。** 分类、完整验证和存储提交是不同阶段。
