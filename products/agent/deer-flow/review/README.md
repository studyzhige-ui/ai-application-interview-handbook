# DeerFlow 回顾｜用状态变化重建系统

[← 产品总览](../README.md) · [工程与评测](../04-engineering-evaluation.md) · [源码小实验](../labs/README.md)

先不看答案，拿一张纸画出“用户提出任务，工具产生副作用，连接中断，之后重新进入会话”的过程。每一个箭头旁写清：谁在操作、依据什么状态、改变了什么，以及失败后还有什么未知。

## 1. 用四个问题重新画主线

**模型此刻看见什么？** 从 ThreadState 出发，区分冻结记忆、独立摘要、工具展开状态和本次项目快照；再画请求时投影。不要直接把一整个状态字典连到模型。

**长期信息何时真正存在？** 从对话筛选、进程内队列、语义提取、确定性检查画到存储提交。把“进队列”和“写成事实”分成两个点，再标出崩溃窗口。

**动作在哪一刻发生？** 从工具目录、完整说明和展开状态画到执行侧检查、沙箱或外部服务。再画返回消息、收据和预算处理，避免把“提议执行”画成“已经完成”。

**恢复到底恢复什么？** 分开 Run 记录、Checkpoint、Journal、工作区和长期记忆，标出哪些可恢复、哪些需要额外核对。恢复模型协议，不代表外部世界已经一致。

## 2. 容易混淆的状态对照

| 看见的信号 | 可以支持什么 | 还不能支持什么 |
|---|---|---|
| `promoted` 中有工具名 | 对应目录版本下记录了展开状态 | 当前技能或用户允许执行 |
| 事实分类函数返回 `None` | 该候选未被这道分类检查拒绝 | 语义正确、全部验证通过、已经落盘 |
| `add_nowait` 返回 | 按该后端路径完成了提交或安排 | 长期事实已提交到存储 |
| 有读取哈希标记 | 对应消息保留了某次读取的版本依据 | 所有外部写入者都遵守同一把锁 |
| 子任务 `completed` | 执行结果进入该终态 | 没有被截断，或业务目标完全满足 |
| `file:report.md exists` 成立 | 指定范围内文件存在 | 文件非空或论证正确 |
| 已恢复检查点 | 可以从恢复的状态继续 | 外部发送、文件或数据库全部撤销 |

这些结论由四篇正文中的实现链建立，回顾不再增加新机制。出现不能解释的行，回到相应主章，而不是把右列背成口号。

## 3. 综合任务：模型说已经完成，哪些证据够用

**初始条件。** 一个新会话使用默认 DeerMem 自动模式，已经注入用户偏好“先解释风险”。项目配置在运行开始时固定。主智能体可以委派子任务，子任务共享线程工作区。用户要求只分析并修复文件，不发布。

**随后发生。** 子任务读取了一个技能并生成报告。报告文件真实存在但为空；子任务状态是 `completed`，同时带有 `turn_capped`。父级对话触发摘要压缩，紧急记忆更新已入队但未落盘；这时进程退出。重启后项目文档目录对应的某文件已移入回收站，客户端还发现事件流有缺口。

请交付一段给用户的状态说明，并画出恢复顺序。必须分别回答：报告交付到了哪一步、长期记忆保存到了哪一步、项目文档为什么可能读不到、事件流怎样恢复，以及重启后能否忽略“不要发布”。可检查结果是五个对象各有明确状态与理由，不能用一句“任务失败了”代替。

<details>
<summary>提示</summary>

把执行终态、停止原因、文件内容、记忆提交和流式恢复分开。项目目录固定与内容实时读取不矛盾。

</details>
<details>
<summary>参考答案与解释</summary>

状态说明可以是：已得到一份空报告文件，但子任务受轮次限制结束，不能宣称报告或修复已通过验收；长期记忆仅完成进程内入队，退出前没有提交证据；项目文档虽然曾出现在固定目录中，读取时仍受实时文档状态限制；事件流有缺口，需要重新读取持久状态后恢复界面。

恢复时先确认会话归属与检查点模式，读取可继续状态和运行事件，再核对工作区与必要外部动作。重新组装请求时仍应保留当前任务约束；长期记忆丢失或摘要发生，都不是获得发布权限的理由。对子任务结果应检查停止原因、必要文件内容与测试证据，不因 `completed` 就直接交付。

</details>

## 4. 换条件，检验能否迁移

**场景 A：工具升级。** 昨天目录 A 中展开过 `monitor_search`，今天目录 B 改变其参数，但名字没变。用户并没有新增授权。请区分旧展开状态的处理、重新发现以及实际执行许可。

<details>
<summary>场景 A 答案与解释</summary>

旧目录的展开状态不能自动给新目录复用；合并和过滤都以目录哈希约束。重新发现只让模型获得当前定义，用户权限和技能限制仍独立生效。名字相同不等于能力身份和许可都相同。

</details>

**场景 B：记忆更正。** 已保存“先解释风险”，用户说“这次赶时间，直接给方案”。请决定当前请求怎样处理、是否应删除长期事实，以及为什么“最后一句覆盖全部旧记忆”不合理。

<details>
<summary>场景 B 答案与解释</summary>

当前任务按这次明确要求组织答案，但一次性要求不等于长期偏好被撤销。需要先判断范围与持久性，再决定是否修改长期事实；自动门控的标签也依赖语义判断，不能只按时间先后覆盖。

</details>

**场景 C：执行证据。** 记录的命令只是输出了一段含 `pytest` 的说明文字，报告里说“测试通过”。请说明为什么字符串出现不够，以及需要什么额外证据。

<details>
<summary>场景 C 答案与解释</summary>

需要对应测试命令真正执行的记录、命令结构匹配、状态和有效测试摘要，不能以 echo 或注释包含关键词证明执行。还要区分测试是否覆盖目标行为；执行证据成立也不自动证明全部业务质量。

</details>

**场景 D：部署切换。** 进程以 full 模式启动，却遇到 delta 检查点。请说明能否把缺失消息当空列表继续，以及允许迁移的方向为什么不是完全对称。

<details>
<summary>场景 D 答案与解释</summary>

不能把增量表示误读成空消息，应经过兼容检查并拒绝不安全读取。delta 可用旧 full 状态作为重建起点；反向切换需要物化与转换。模式和频率按进程固定，不能在一条运行中临时换解释方式。

</details>

## 5. 面试前重建一段完整表达

不用先罗列组件。先说用户任务和风险，再说状态与输入怎样产生、动作怎样受控、失败后怎样恢复、最终怎样证明。一个合格的表达应能自然接住“工具很多”“历史很长”“进程崩溃”“子任务说完成但文件不对”这些不同追问，因为它们共享同一套已经建立的对象与生命周期。

练习记录只需要写下自己混淆的边界和回读位置。不要把读过多少页面、认得多少类名当成学习完成。
