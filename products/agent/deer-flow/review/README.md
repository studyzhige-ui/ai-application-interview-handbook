## 1. 用四个问题重新画主线

1. **模型此刻看见什么？** 从 ThreadState 区分冻结记忆、独立摘要、工具展开状态与本次项目快照，再画请求投影。不要把整个状态字典直接连到模型。
2. **长期信息何时真正存在？** 从筛选、队列、提取、检查画到存储提交，把入队与写成事实分开，标出崩溃窗口。
3. **动作在哪一刻发生？** 从目录、完整定义画到执行检查，再到沙箱或外部服务；最后画返回消息、收据与预算处理。
4. **恢复到底恢复什么？** 分开 Run、Checkpoint、Journal、工作区与长期记忆。恢复消息协议，不代表外部世界一致。

第一张图可对照[一次运行轨迹](../01-context-lifecycle.md#run-trace)，恢复图可对照[检查点亲缘与线性恢复](../04-engineering-evaluation.md#checkpoint-recovery)。先自己推演，再回看，不要求凭记忆默写类名。

## 2. 容易混淆的状态对照

| 看见的信号 | 可以支持什么 | 还不能支持什么 |
|---|---|---|
| 同 ID 的普通消息更新 | 更新对应消息 | 整份历史已被替换 |
| 摘要配置启用 | 允许尝试组装相应机制 | 模型构造成功、阈值有效且本次已压缩 |
| `promoted` 中有工具名 | 对应目录下记录了展开状态 | 当前技能与用户允许执行 |
| 分类函数返回 `None` | 这道标签检查未拒绝 | 语义正确、全部验证通过、已落盘 |
| `add_nowait` 返回 | 按该路径提交或安排了工作 | 长期事实已提交 |
| 有读取哈希标记 | 对应消息保存了读取版本依据 | 所有外部写入者遵守同一把锁 |
| 子任务 `completed` | 执行进入该终态 | 没有被截断，目标已满足 |
| `file:report.md exists` 成立 | 指定范围内文件存在 | 文件非空、论证正确 |
| 恢复检查点 | 可从相应状态继续 | 外部发送、文件与数据库都已撤销 |

这些区别来自正文中的具体过程。解释不出某一行时，回到对应主章，而不是把右列背成免责声明。

## 3. 综合任务：模型说已经完成，哪些证据够用

**初始条件。** 新会话使用默认 DeerMem 自动模式，记忆与自动注入开启，已注入“先解释风险”。项目配置在 Run 开始时固定。主智能体可委派共享线程工作区的子任务。用户要求分析和修复文件，不发布。本次摘要中间件已成功组装，触发阈值有效。

**随后发生。** 子任务读取技能并生成报告。文件存在但为空，状态为 `completed`，停止原因是 `turn_capped`。父对话达到摘要阈值；摘要成功，旧消息已更新，紧急记忆只入队、未落盘，随后进程退出。重启后，项目目录曾列出的一份文档已移入回收站，客户端还发现事件流缺口。

请写一段给用户的状态说明，再画恢复顺序。必须分别回答报告、长期记忆、项目文档和事件流到了哪一步，以及能否忽略“不要发布”。不能只写“任务失败了”。

<details>
<summary>提示</summary>

区分终态、停止原因、文件内容、事实提交和事件续读。固定项目目录与读取实时文档不是矛盾。

</details>
<details>
<summary>参考答案与解释</summary>

目前只有空报告文件，子任务因轮次上限结束，不能宣称报告或修复已通过验收。长期记忆只有进程内接收证据，没有事实提交证据；项目文档读取受实时状态限制；事件流有缺口，应先重新读取持久状态建立界面。

恢复时确认会话归属与检查点模式，读取继续状态和事件，再核对工作区与必要外部动作。组装请求时仍须保留任务约束；记忆丢失或发生摘要不是获得发布权限的理由。子任务结果要结合停止原因、文件内容和测试证据，而不是只看 completed。

</details>

## 4. 换条件，检验能否迁移

**场景 A：工具升级。** 昨天目录 A 展开过 `monitor_search`，今天目录 B 改了参数但名称不变，用户未新增授权。说明旧展开状态、重新发现和执行许可的关系。

<details>
<summary>场景 A 答案与解释</summary>

合并和过滤受目录哈希约束，旧目录展开不能直接复用。重新发现只提供新定义，不改变技能或用户许可。名字相同不代表定义与权限都相同。

</details>

**场景 B：记忆更正。** 长期事实是“先解释风险”，用户说“这次赶时间，直接给方案”。是否修改长期事实？

<details>
<summary>场景 B 答案与解释</summary>

当前任务按本次要求处理，但一次性例外不等于撤销长期偏好。先判断范围与寿命，再决定存储变更；自动标签也依赖语义判断，不能仅按时间覆盖。

</details>

**场景 C：执行证据。** 命令只是打印含 `pytest` 的说明文字，报告却说“测试通过”。还缺什么？

<details>
<summary>场景 C 答案与解释</summary>

缺对应测试命令实际执行、命令结构匹配、状态与有效测试摘要等证据。字符串出现不证明执行，执行过也不证明覆盖全部业务。

</details>

**场景 D：部署切换。** full 进程遇到 delta 检查点，能否把缺失消息当空列表继续？

<details>
<summary>场景 D 答案与解释</summary>

不能。需经模式检查，拒绝不安全读取；delta 可用旧 full 状态作起点，反向需要物化与转换。模式与频率按进程固定，不能随单条运行临时改解释方式。

</details>

**场景 E：历史很长却没有摘要。** `enabled=true`，模型可构造，但 `trigger=None`。该现象能否直接判成故障？

<details>
<summary>场景 E 答案与解释</summary>

不能直接判定为故障。这是可以构造中间件但不会按阈值自动触发的配置形态。先核对实际配置与触发条件，而不是直接调低模型窗口或删除消息。手动压缩是否可用另看构造与调用路径。

</details>

**场景 F：旧回复为何又出现。** delta 根会话从旧检查点重答，旧回复可能经共享祖先的待处理增量混入。用本模块固定实现解释怎样避免。

<details>
<summary>场景 F 答案与解释</summary>

先物化所选旧检查点，在当前头部写入完整恢复状态，归并通道使用 Overwrite，重置仅当前头部有的新字段，再继续线性执行。不直接从共享祖先新开兄弟分支。状态回到过去的值，历史亲缘仍向前，外部文件不自动回滚。

</details>

## 5. 面试前重建一段完整表达

先说任务和风险，再说状态如何进入模型、动作怎样受控、故障后如何恢复、最终凭什么交付。不必先背组件列表。合格表达应能自然接住工具很多、历史很长、进程崩溃、子任务报告不可靠等不同追问。

练习记录只写自己混淆的边界与回读位置。认得类名、读过页面或通过局部测试，都不能单独代表已掌握整套机制。
