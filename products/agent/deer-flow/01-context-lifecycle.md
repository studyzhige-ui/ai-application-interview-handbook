# 01｜上下文：从会话状态到模型真正看到的内容

[← DeerFlow 总览](README.md) · [下一篇：记忆 →](02-memory-lifecycle.md)

修复支付页时，第一条用户消息只有几句话；查日志、读代码、试修复以后，历史可能已经很长。用户最初说过“不要发布”，模型还需要遵守，但没有必要在每轮重读整份日志。

问题因此不是简单的“提示词怎么拼”，而是：**下一次模型调用需要哪些信息，这些信息从哪里来，哪些能缩短，哪些必须保留原来的意义与权限等级？** 先走通一次短运行，再改变条件，观察历史变长以后发生什么。

## 1. 保存下来的东西，不等于模型每次都要看见

`ThreadState` 是程序继续工作时使用的会话状态。`ModelRequest` 是某一次真正发给模型的请求。前者可以保存很多工作线索，后者只取本次需要的内容，还可以临时加入项目说明。

| 内容 | 保存在哪里或从哪里取得 | 模型怎样使用 |
|---|---|---|
| 用户要求、模型响应、工具结果 | `ThreadState.messages`，可由检查点保存 | 近期工作历史；请求阶段仍可能裁剪 |
| 历史摘要 | 独立的 `summary_text` | 请求时作为历史数据加入，不冒充新用户要求 |
| 子任务记录、技能引用 | `delegations`、`skill_context` | 提醒做过什么、结果或技能在哪里 |
| 项目配置及文档目录 | 网关在本次运行开始时固定的快照 | 临时加入请求，不重复写进历史 |
| 已查看图片 | 状态中的路径、大小、哈希等引用 | 发送模型请求时再读取图片字节 |
| 长期用户偏好 | 记忆后端 | 读取有预算的背景，不是每轮全量搬入 |

从状态中选择并重新表示信息，本文称为**请求投影**。例如程序保存日志路径，模型先看摘要与路径，需要细节时再读文件。投影没有另造一份权威事实，也不意味着请求里有的内容都会写回检查点。[状态结构][state]

> ⚠️ **路径不等于内容永远存在。** 引用可以保存下来，文件字节仍受沙箱寿命、同步和权限影响。恢复路径后还要核对文件可读。

<a id="run-trace"></a>

### 1.1 跟踪一次“读文件，再决定怎样修复”的运行

以下是教学轨迹，不是实测日志。固定条件：新会话 `t1`，本次 Run 为 `r1`；记忆允许注入且读取成功；项目已选定；`read_file` 可见并获准执行；文件存在。历史很短，本例不触发摘要。

用 `D`、`M`、`U` 分别缩写日期消息、记忆数据、用户原话。它们不是实际消息 ID；项目说明记为 `P`，基础系统指令记为 `S`。

| 时点 | 保存的消息或更新 | 模型看到什么、外部发生什么 |
|---|---|---|
| 用户提交 | 一条原始用户消息 | 文件尚未改变，也没有工具执行 |
| 运行开始的注入完成 | 消息成为 `[D, M, U]` | `M` 是此次读到的长期偏好副本，`U` 仍包含“不要发布” |
| 第一次模型调用 | 不因项目投影而增加历史消息 | 请求使用 `S`、上述消息、临时的 `P` 及当前工具说明；具体角色排列按供应商适配 |
| 模型提出读取 | 追加助手消息 `A1`，含 `read_file` 调用 `c1` | 参数指定支付页文件；**提出调用还没有读取文件** |
| 程序执行读取 | 追加工具结果 `T1`，其 `tool_call_id=c1` | 返回文件内容及适用的读取标记；读取没有修改文件 |
| 第二次模型调用 | 已有 `[D, M, U, A1, T1]` | 模型多看到了真实读取结果，可以判断怎样修复 |
| 后续修改与结束 | 按实际调用继续追加配对消息，最后形成回答 | 只有写工具真正执行后文件才可能改变；读回与测试仍需单独核对 |

这里有两个容易混淆的 ID：**消息 ID** 用于更新消息本身；**工具调用 ID** 用于把一次调用和它的返回结果配对。`A1` 是助手消息的教学标号，`c1` 标识它提出的那次工具调用，不是同一个对象。

检查点在执行过程中的相应位置保存继续状态，Journal 记录事件；启用自动记忆写入时，运行结束还会提交对话给记忆后端。它们不是等文件写完以后一起完成的一笔事务。本例的第二次模型调用仍属于 `r1`，也没有因此重新检索全部长期记忆。[主智能体组装][assembly] · [动态注入][inject] · [工具结果处理][tool-errors]

## 2. 中间件在什么时点改变了什么

中间件是插在执行流程中的处理程序。例如模型调用前加入项目说明，工具执行前检查权限。先认清时点，再看组件名。

| 时点 | 处理对象 | 本例中的作用 |
|---|---|---|
| `before_agent` | 本次运行的初始状态 | 准备目录、上传信息、日期与记忆注入 |
| `before_model` | 下一次模型调用前的状态 | 捕获工作线索，必要时压缩历史 |
| `wrap_model_call` | 本次模型请求 | 临时加入项目、展开摘要、筛选工具说明 |
| `after_model` | 模型刚返回的结果 | 处理安全终止、截断、重复循环与预算 |
| `wrap_tool_call` | 一次工具执行及结果 | 检查许可、规范错误、处理大结果 |
| `after_agent` | 运行结束后的状态 | 提交后台记忆更新及相应结束处理 |

“包装调用”可以用两个处理程序理解。假设按 A、B 注册，它们都继续调用内部处理器，过程是：

```text
A：进入时处理请求
  B：进入时处理请求
    模型或工具实际执行
  B：拿到结果，处理后返回
A：拿到结果，处理后返回
```

因此，**先注册的包装器在外层，进入顺序与返回顺序相反**。若 A 提前拒绝，B 和实际工具都不会运行。这是包装关系的示意，不代表所有钩子都按同一种顺序工作；该快照的 `after_model` 还存在逆序分发，要另外确认。

顺序为何重要？捕获技能引用必须发生在摘要删除旧消息之前；内层工具结果先规范成成功或错误，外层进度记录才能理解它。只列出组件而不看调用方向，无法确认行为。[实际组装与顺序][assembly] · [共同工具构建器][tool-errors]

## 3. 稳定指令、日期和记忆为什么分开放

基础系统提示描述主智能体的行为、目录和工具规则，通常比较稳定。日期和用户记忆会变，把它们频繁插到系统提示开头，会改变本可复用的前缀。分开组织有利于前缀缓存，但是否命中仍取决于供应商与实际请求，不能据此承诺固定节省比例。

信息角色也不同：日期由程序提供；记忆来自过去对话，可能误解、过期或含不可信文本。**被保存过，不会使用户数据升级为系统指令。**

<a id="31-第一次注入怎样保留用户原话"></a>

### 3.1 先理解消息合并，再看第一次注入

程序返回的消息更新，不总是整份替换历史。这里使用的 `add_messages` 会按消息 ID 合并：同 ID 更新已有消息，新 ID 追加消息。专门的删除或整值替换是另一些操作。[框架消息合并规则][graph-api]

`DynamicContextMiddleware` 利用这条规则：日期使用 `SystemMessage`（系统消息），记忆使用单独的 `HumanMessage`（用户级数据消息），用户原话也是另一条 `HumanMessage`。

```text
原状态：
  h1          HumanMessage：分析支付页……不要发布。

本次提交给合并器的更新：
  h1          SystemMessage：程序提供的日期
  h1__memory  HumanMessage：先解释风险，再给方案。
  h1__user    HumanMessage：分析支付页……不要发布。

合并结果：
  原位置的 h1 被日期消息替换
  两个新 ID 追加，记忆与用户原话各自保留
```

这里固定为只有一条原始用户消息的初次注入。**ID 决定怎样合并，角色决定怎样解释内容。** 若只替换 `h1` 而不保存 `h1__user`，用户原话就丢了。源码还保留原用户消息的相关属性，不是把用户要求改写成程序指令。[消息构造与注入][inject]

程序注入消息带有来源标记。不能只凭文本含 `<memory>` 或 `<system-reminder>` 就认定是程序生成；用户自己写的同名标签不能冒充这个标记。

<a id="32-记忆是冻结的会话快照不是每次-run-都重新召回"></a>

### 3.2 成功注入后，记忆怎样被复用

第一次注入用当前用户原文构造查询，最多取 1000 个字符；有上传说明时优先取保存的原始输入，避免查询被文件描述占满。这是该快照的具体界限，不是通用最佳值。

随后记忆文本作为会话里的冻结副本复用。同一天后端事实即使被修改，后续 Run 也不会仅因为再次调用模型而重新召回。跨日主要补日期提醒。因此要区分**后端最新事实、会话中已注入的副本、本次模型请求**。[查询与冻结分支][inject]

<a id="33-注入超时与关闭记忆不是同一件事"></a>

<details>
<summary>注入失败、关闭记忆与日期时区怎样处理</summary>

前一次注入失败、历史已积累多轮时，补注入选择最后一条合适的用户输入，避免把早期问题追加到末尾，令模型误答旧问题。日期默认使用服务器本地时区，也可由 `DEER_FLOW_DATE_TIMEZONE` 指定 IANA 时区，例如 `Asia/Shanghai`，不是自动跟随浏览器。

异步注入把阻塞读取交给工作线程，调用方约等待 5 秒。允许降级时，本轮可缺少新的记忆与日期更新；要求必须读取记忆的后端则传播 `MemoryReadError`。超时后连失败策略都无法确认，也不能静默当成允许降级。等待超时不保证底层线程已停止。

关闭该智能体的记忆能力时，程序另行移除自己注入的冻结记忆，不把清理寄托在可能超时的读取上。移除会话里的副本，不是清空后端所有事实。[超时、清理与时区实现][inject]

</details>

## 4. 项目和图片为什么只在请求中展开

<a id="41-项目快照固定的是本次配置不是整个文档库的历史版本"></a>

### 4.1 项目快照固定的是本次配置

运行开始时，网关固定项目身份、配置和有预算的文档目录。中间件每次据此构造临时项目消息，不把它作为消息状态更新返回，所以检查点不会累积多份项目配置。

项目文字保持用户角色，不能越过系统规则或工具授权。目录固定也不意味着文件内容冻结：项目文档工具按固定项目身份读取实时文档状态。目录中曾有的文件若已被移入回收站，实际读取可以失败；不能用旧目录继续提供已移除内容。[项目边界][architecture] · [请求构造][inject]

<a id="42-图片保存可验证引用发送时读取字节"></a>

### 4.2 图片保存引用，发送时核对字节

每个检查点都保存整张 base64 图片，会反复复制大数据。DeerFlow 保存 MIME 类型、大小、路径、SHA-256 与来源沙箱标识；`ViewImageMiddleware` 在模型请求时读取活动沙箱，或核对同步副本的大小和哈希后使用。

这减少的是重复表示，不是撤销存储需求。若路径指向的字节变了，不能把新图悄悄当成上次看见的图。[图片引用][state] · [图片展开][image]

## 5. 历史缩短后，工作线索怎样继续存在

只留最后几条消息，可能忘记“子任务已经查过这份日志”或“刚才用过哪个技能”。保留全部旧消息又不能解决长度压力。不同线索因此有不同保存方式。

| 状态 | 保留什么 | 不保留什么 |
|---|---|---|
| `summary_text` | 旧历史的语义摘要 | 不承诺逐字还原历史 |
| `delegations` | 子任务类型、状态、有界结果引用 | 不复制完整子对话 |
| `skill_context` | 技能名、路径与简述 | 不长期复制完整 `SKILL.md` |

`DurableContextMiddleware` 在旧消息仍在时捕获线索，在请求时把这些状态重新表示为历史数据。描述如何使用历史的规则可以是系统指令，但摘要、子任务结果与工具文本不能因此获得系统权威。过去网页里的一句“忽略规则”不能经摘要变成新命令。[捕获与投影][durable]

技能引用留下后，真正应用技能时仍应读取当前文件，避免使用过时正文。子任务账本还需要同时区分运行身份和工具调用 ID，因为调用 ID 可能跨 Run 重复。任务笔记、`task_history`、工具产物句柄等扩展状态按开关接入，字段存在不代表本次已启用。[状态合并][state]

> ⚠️ 读取标记随对应工具消息保存。压缩删掉那条消息，先读后写的依据也会失效。重新读取是恢复成本，不应让模型已经忘掉内容，却仍永久持有“读过当前版本”的资格。[读取标记][read-write]

## 6. 先处理大工具结果，再考虑历史摘要

<a id="61-工具返回时的外置可能改变将要保存的-toolmessage"></a>

### 6.1 工具返回时，短结果可以进入保存状态

假设监控工具返回很大的日志。`ToolOutputBudgetMiddleware` 可先把全文保存为文件，再返回有类型的摘要、预览与路径；保存失败时，退化为带标记的头尾截断。远程沙箱没有宿主挂载时，必须写到沙箱可见的位置，并核对文件存在。

预算在这里约束的是**字符数**，不是 token 数或 UTF-8 字节数。20000 个中文字符既不意味着 20000 字节，也不保证 20000 token。

工具返回阶段替换的是结果消息，新的 `ToolMessage` 可以进入状态。因此“全文始终保存在检查点，模型只看短版”不成立。全文能否找回，要看外置是否成功，以及收据和日志捕获了哪一阶段。[返回结果预算与外置][output]

<a id="62-请求阶段的裁剪才是原状态不变的另一条路径"></a>

### 6.2 请求阶段裁剪，才可能保持原状态不变

请求阶段还会防御性缩短历史大结果。对已经成功的 `write_file`，若后来成功读取或修改了同一路径，且不属于需要保留的近期写入，可以在模型视图中省去旧的大 `content` 参数；保存的原参数不被原地修改。

同一条模型响应里的并发读取不能冒充“写入之后已经读过”，因为执行顺序未必如此。源码按调用位置与配对结果判断，不只用调用 ID 全局查找。被先读后写门控拦下的大参数，则由对应中间件单独缩短。[成功旧写入的裁剪][output] · [被拦写入的裁剪][read-write]

## 7. 摘要压缩怎样同时保留语义和协议

### 7.1 先确认启用，再确认触发条件

**历史变长不会自动使所有 DeerFlow 运行进入摘要。** 先看实际加载的配置，再看是否成功构造中间件、是否有可用阈值。[配置类][summary-config] · [摘要工厂][summary]

| 条件 | 自动路径的结果 |
|---|---|
| 配置未启用摘要 | 工厂不安装摘要中间件 |
| 已启用，但无法构造可用摘要模型 | 本次组装没有可用摘要中间件，并记录警告 |
| 已启用且构造成功，但 `trigger=None` | 可以有中间件，但不会按阈值自动触发 |
| 有可用触发条件且达到阈值 | 尝试压缩；仍要检查可压缩历史、保护消息并成功生成摘要 |

该快照的**配置类默认值**是 `enabled=False`、`trigger=None`、保留最近 20 条消息。部署加载的配置可以覆盖它们，因此不能把类默认值说成所有部署的实际行为。

下面只是教学配置片段，不是完整部署配置：

```yaml
summarization:
  enabled: true
  trigger:
    type: messages
    value: 8
  keep:
    type: messages
    value: 4
```

`trigger` 回答“什么时候开始尝试”，`keep` 回答“希望保留多少近期原消息”。假设检查时计数为 7，不满足这个触发条件；达到 8 时具备触发资格。它不意味着把每组八条固定砍成四条，更不意味着已经腾出某个精确 token 空间：工具配对、当前用户请求等仍受保护；没有可压缩历史时，也不能硬删。

多个触发条件采用“任一满足”。按 token 判断时已有摘要也要计入。比例条件依赖摘要锚定模型的可用输入窗口；`0.8` 表示八成，不是 `80`。缺少窗口时，工厂警告并去掉不可用比例条件，绝对阈值可继续生效；所有触发项都失效时不自动触发，但构造成功的手动压缩路径仍可工作。比例保留量无法计算时回退到消息保留默认值。[阈值适配与手动路径][summary]

### 7.2 达到阈值以后，哪些消息留下

固定为已经启用并成功触发、且存在可压缩历史的运行。处理过程是：

1. 选择旧历史，同时保留近期消息、系统消息、程序动态提醒和最新真实用户请求。
2. 用已有摘要与待压缩历史生成替代摘要。
3. 摘要成功后，调用删除前钩子，再形成消息与 `summary_text` 的状态更新。
4. 下一次请求重新加入摘要及必要工作引用，模型据此继续。

例如历史里有两组已完成的调用：`A1(c1), T1(c1)` 与 `A2(c2), T2(c2)`。前一组若已进入摘要，后一组仍保留，那么下一次请求不能只留下 `A2(c2)` 却没有 `T2(c2)`。调用与结果配对是协议要求，不是文字摘要能替代的内容。[切分与消息保护][summary]

最新用户要求也必须保留。早期已经完成的问题则不能只因 ID 带 `__user` 后缀就永久占据上下文。摘要应保住任务意义，但仍需检查实际内容；不能从安装了压缩器推导约束绝不会丢失。

<a id="71-摘要失败为什么不能删除原消息"></a>

### 7.3 摘要失败时，原消息为什么不能删除

新摘要没有生成成功，就没有足够依据用它替换旧历史。自动路径保留原状态；手动压缩应报告失败，不能把失败伪装成“无需压缩”。未配置专用摘要模型时使用本次运行实际模型；专用模型生成失败时，可尝试不同的运行模型。构造失败和生成失败是两个阶段。[模型选择、生成与失败处理][summary]

摘要自身也是模型调用。输入中的旧摘要与旧消息做分区及 XML 转义，并考虑个人信息脱敏，因为这条辅助路径未必经过主请求的全部包装层。转义和角色分离是防护，不是绝无提示注入的证明。

<a id="72-紧急记忆-flush-到底保证了什么"></a>

### 7.4 删除前提交记忆，保证的是机会而不是落盘

自动记忆可能尚未处理即将删除的旧消息。因此摘要成功后、删除之前，`memory_flush_hook` 把这一批消息交给 `add_nowait`。默认 DeerMem 立即安排处理，绕过普通水位，并让紧急项与同会话正常待处理项共存。

```text
摘要生成成功
    ↓
紧急记忆更新入队      ← 到这里仍可能没有长期事实
    ↓
会话消息与摘要更新

后台另一条路径：提取 → 验证 → 存储提交
```

> ⚠️ 默认队列在进程内存里，钩子失败会被记录但不必阻止压缩。成功入队后崩溃，事实仍可能未保存。这不是“长期记忆提交成功以后才删除历史”的跨存储事务。[删除前钩子][summary] · [队列][queue]

## 8. 手动压缩与恢复为什么经过检查点层

Checkpoint（检查点）保存让智能体以后继续的状态。手动压缩先通过 `CheckpointStateAccessor` 读出状态，再写入摘要和保留消息，形成新检查点。

此时不能直接把“只剩 A、B”当普通消息更新：按 ID 合并可能保留旧 C、D。`Overwrite` 表示用给定值整体替换，而不是再次合并。这与前面初次注入利用同 ID 更新，是两种不同目的。[手动压缩][compact] · [访问器][checkpoint]

允许向哪个智能体记忆桶提交历史，要看检查点里服务端记录的绑定。绑定缺少或无法确认时，可以允许上下文压缩，但跳过不能授权的记忆写入，不能相信客户端随意传来的 `agent_name`。

恢复状态以后还要重新组装请求。底层保存为完整状态还是增量，由访问器统一解释，不能直接把原始字段当完整消息。最终系统消息还要按供应商协议归并到请求头。[系统消息适配][coalescing]

## 本章小结

一次运行会多次组装模型请求：状态保存工作线索，请求挑选当下所需，工具执行再带来新观察。消息 ID 管合并，调用 ID 管工具配对。历史过长时先处理大结果，再在已启用且有有效阈值的条件下尝试摘要；压缩必须同时照顾任务含义、协议与信息角色。

## 🎯 面试怎么回答

**Q：上下文快满了，怎样压缩而不影响继续执行？**

> 先确认本次运行实际启用了什么、触发条件是否可用，再区分当前约束、近期工具往返和可外置的大数据。DeerFlow 可先预算工具结果，再把旧对话压成独立摘要，保留当前请求及必要消息配对。下一次由中间件重新加入摘要与技能、委派引用。验收不仅看输入缩短，还要核对约束、协议和文件可读性。

**Q：压缩前调用记忆 flush，就不会丢长期信息了吗？**

> 不能保证。它在摘要成功后给待删除消息一次紧急提取机会，但默认队列在进程内存里，入队与事实落盘不同，钩子失败也不必阻止压缩。需要更强保证时，应额外设计可确认的持久接收与恢复，而不能把它写成上游已有能力。

## ⚠️ 高频易错点

- **把模型视图当成检查点。** 项目投影不一定持久；工具返回阶段的裁剪却可能直接进入状态。
- **把同 ID 更新当成整份历史替换。** 未涉及的消息可继续保留，压缩必须明确删除或整值替换。
- **把启用摘要当成必然自动触发。** 还要看模型能否构造、阈值是否有效及有没有可压缩历史。
- **把记忆当成授权。** 偏好和历史摘要只提供背景，不能创建发布权限。

## 本章自测

**任务 A：** 第一轮成功注入“先解释风险”；后端后来改了这条事实，日期未变，记忆仍开启。第三轮是否必然读到新事实？请区分三个观察对象。

<details>
<summary>任务 A 提示与答案</summary>

比较后端事实、会话冻结消息与本次模型请求。正常同日路径复用已注入副本，不必然重新召回；项目投影不能当成记忆刷新。新会话或其他明确刷新路径需另外核验。

</details>

**任务 B：** 摘要已成功，紧急更新入队，旧消息已删除，队列尚未提取时进程退出。能否宣称长期偏好已保存？

<details>
<summary>任务 B 提示与答案</summary>

把摘要更新、队列接收、事实提交拆开。前两项发生不代表第三项发生；进程内队列会丢失。其他历史副本可能存在，但这条路径没有自动恢复保证。

</details>

**任务 C：** 原消息只有 `h1`。更新包含日期 `h1` 和用户原话 `h1__user`。合并后有几条消息？随后配置 `enabled=true, trigger=None`，能否仅因历史变长就断言会自动摘要？

<details>
<summary>任务 C 提示与答案</summary>

有两条：同 ID 替换，新 ID 追加，原话由新 ID 保存。即使中间件构造成功，没有触发条件也不会按阈值自动摘要。不要把消息合并、摘要启用和阈值判断混成一个动作。

</details>
