# 观察与复盘｜用证据区分停止、交付和达标

[← 上一章](07-memory-pipeline.md) · [本产品目录](README.md)

最后把同一次 Run 的调用、收据、检查点、输出和终态放在一起读。表格与轨迹为教学推演，不是产品实测日志；无需新建项目或实施故障实验。

<a id="11-怎样知道两次运行用了同一套系统"></a>

<a id="complete-trace"></a>
## 用同一 run_id 连起整个结果

| 事实 | 生产者 | 支持什么结论 |
|---|---|---|
| 接纳与拥有者 | RunManager | 请求属于哪个用户/线程，哪个工作器有权执行 |
| 模型与工具消息 | 主图及中间件 | 哪次调用产生了哪份输入和结果 |
| 工具收据 | 外层收据包装器 | 执行、提前拒绝与结果状态可被统一检查 |
| 子任务步骤和停止原因 | 原生执行器与父循环代理 | 子任务做了什么、是否只交付部分结果 |
| 输出路径与交付收据 | 工作器收尾 | 本次 Run 实际交了什么产物 |
| 检查点 | 状态图与存储器 | 下次可以从哪份状态继续 |
| 持久终态 | RunManager 与存储 | 收尾后的运行结果，而不只是模型说完 |

例如子级 completed + turn_capped 返回一段排查结论，父级还生成了报告文件；这不等于报告验证完成。先看子级说明的未决范围，再读文件与收据，最后检查终态是否因交付失败变成 error。消息配对、运行状态和业务验收各有证据，不把其中一个成功词扩展成全链成功。

## 比较两次运行以前，先确认实际组件

相同模型名不等于相同系统。提示、工具定义、技能、中间件顺序、上下文政策与配置都可能不同。`AssemblyDescriptor`（组装描述）记录相关身份与哈希，帮助解释差异；昂贵部分在有需要的观察者时才计算，避免无人使用的诊断开销。[组装描述][s3-assembly]

扩展中间件要在完整链组装后合并并检查顺序，否则观察者可能看不到最终请求，或者错误规范化与进度记录的先后被倒置。[顺序约束][s3-ordering]

哈希适合判断内容是否不同，不能从哈希还原完整输入。真正回放还需要对应请求、状态与执行证据，不能把一个摘要标识当成完整回放数据。

<a id="9-收据可判定条件和业务质量为什么不能合成一个通过"></a>

## 验收：执行过、文件存在和业务正确是三件事

子任务说“报告写好了”，先检查动作声明是否有对应收据，再检查目标文件，最后判断内容质量。

| 检查 | 能确认什么 | 仍不能确认什么 |
|---|---|---|
| 收据引用有效 | 声明有对应执行记录 | 记录的动作已满足全部要求 |
| 文件存在 | 指定目标存在 | 文件非空、论证正确 |
| 文件非空或写入读回 | 满足相应可判定条件 | 业务推理无误 |
| 测试执行证据成立 | 对应测试命令与结果有依据 | 测试覆盖全部业务 |

`acceptance_checks.py` 对存在、非空、写入读回及特定测试执行证据等叶条件作检查。叶条件是能单独判断的一项要求；无法判断的自然语言条件标为 `UNVERIFIED`，不能自动算通过。源码区分 `checked`（是否完成检查）与 `holds`（条件是否成立）。[验收检查器][s3-acceptance]

例如输出中出现 `pytest` 不证明真执行了测试，零测试也不是测试通过；读取应有字节界限，目录、符号链接或不能安全确定的目标不随意当普通文件。

批任务这里的附加验收具有建议性。检查器故障或自然语言条件未验证，不自动把可用执行结果变成应重试的执行失败。是否阻断交付，要继续看调用方与任务要求；不能推出系统没有其他强制门禁。[批服务调用方][s3-batch] · [验收资源管理][s3-batch-acceptance]

<a id="12-评测应围绕故障窗口而不是只数测试文件"></a>

## 用故障窗口检验整条过程

先定义支付修复任务的验收：没有发布；文件修改有依据；能说明做过和未做过的验证。再改变一个条件，看系统能否正确解释状态。

| 变化或故障 | 应核对什么 | 单靠什么不够 |
|---|---|---|
| 多轮后摘要压缩 | 当前约束、工具配对与后续可执行性 | token 数下降 |
| 副作用完成后响应丢失 | 先查真实状态，不盲目重放 | 一条错误 ToolMessage |
| 子任务输出到一半取消 | 停止原因、部分结果和资源持有 | 界面显示取消 |
| 从旧轮次分支 | 祖先正确，不引入未来文件 | 分支接口成功 |
| 事件区间丢失 | 重新读取持久状态建立视图 | 前后端各自单测通过 |
| 记忆索引坏了或队列未提交 | 区分可降级检索与未持久写入 | 没有抛异常 |

测试也分层：纯函数检查状态合并与候选门控；中间件测试检查角色、拒绝和错误；检查点与数据库集成检查恢复；确定性回放复现给定模型与工具轨迹；浏览器端到端检查服务、流与界面组合。真实模型、MCP、远程沙箱和生产部署还需各自条件。[上游回放指南][s3-replay]

同时观察任务结果、失败位置与资源开销：完成多少，在哪层失败，模型、工具与委派调用多少，花多少 token、时间与存储。拒绝率高但所有任务都做不成，不是有效系统；成本低但约束丢失，也不是优化成功。没有实测时，这些是评测设计，不是已经取得的提升结果。

## 多角度回顾

### 上下文：本章小结

一次运行会多次组装模型请求：状态保存工作线索，请求挑选当下所需，工具执行再带来新观察。消息 ID 管合并，调用 ID 管工具配对。历史过长时先处理大结果，再在已启用且有有效阈值的条件下尝试摘要；压缩必须同时照顾任务含义、协议与信息角色。

### 上下文：🎯 面试怎么回答

**Q：上下文快满了，怎样压缩而不影响继续执行？**

> 先确认本次运行实际启用了什么、触发条件是否可用，再区分当前约束、近期工具往返和可外置的大数据。DeerFlow 可先预算工具结果，再把旧对话压成独立摘要，保留当前请求及必要消息配对。下一次由中间件重新加入摘要与技能、委派引用。验收不仅看输入缩短，还要核对约束、协议和文件可读性。

**Q：压缩前调用记忆 flush，就不会丢长期信息了吗？**

> 不能保证。它在摘要成功后给待删除消息一次紧急提取机会，但默认队列在进程内存里，入队与事实落盘不同，钩子失败也不必阻止压缩。需要更强保证时，应额外设计可确认的持久接收与恢复，而不能把它写成上游已有能力。

### 上下文：⚠️ 高频易错点

- **把模型视图当成检查点。** 项目投影不一定持久；工具返回阶段的裁剪却可能直接进入状态。
- **把同 ID 更新当成整份历史替换。** 未涉及的消息可继续保留，压缩必须明确删除或整值替换。
- **把启用摘要当成必然自动触发。** 还要看模型能否构造、阈值是否有效及有没有可压缩历史。
- **把记忆当成授权。** 偏好和历史摘要只提供背景，不能创建发布权限。

### 上下文：本章自测

**任务 A：** 第一轮成功注入“先解释风险”；后端后来改了这条事实，日期未变，记忆仍开启。第三轮是否必然读到新事实？请区分三个观察对象。

<details>
<summary>任务 A 提示与答案</summary>

比较后端事实、会话冻结消息与本次模型请求。正常同日路径复用已注入副本，不必然重新召回；项目投影不能当成记忆刷新。新会话或其他明确刷新路径需另外核验。

</details>

**任务 B：** 摘要已成功，紧急更新入队，旧消息已删除，队列尚未提取时进程退出。能否宣称长期偏好已保存？

<details>
<summary>任务 B 提示与答案</summary>

把摘要更新、队列接收、事实提交拆开。前两项发生不代表第三项发生；进程内队列会丢失。其他历史副本可能存在，但这条路径没有自动恢复保证。

</details>

**任务 C：** 原消息只有 `h1`。更新包含日期 `h1` 和用户原话 `h1__user`。合并后有几条消息？随后配置 `enabled=true, trigger=None`，能否仅因历史变长就断言会自动摘要？

<details>
<summary>任务 C 提示与答案</summary>

有两条：同 ID 替换，新 ID 追加，原话由新 ID 保存。即使中间件构造成功，没有触发条件也不会按阈值自动摘要。不要把消息合并、摘要启用和阈值判断混成一个动作。

</details>

### 工具与扩展：本章小结

先注册能力，再按需展示，执行侧仍检查许可与实际资源。文件版本保护、沙箱租约和 MCP 会话所有者分别解决不同问题；它们不能互相代替。最后还要分清模型观察、执行记录与业务验收。

### 工具与扩展：🎯 面试怎么回答

**Q：Skill 或 MCP 数量太多，怎样避免上下文膨胀？**

> 分开目录、完整定义和实际执行。DeerFlow 通过搜索或路由按需展开 MCP 定义，技能正文也按需加载；展开状态绑定目录哈希，升级后不能沿用旧状态。执行时仍检查发现状态、技能限制、授权和沙箱，发现入口不能恢复被禁止工具。

**Q：修改前强制读文件，能解决并发与安全问题吗？**

> 它减少基于旧内容的修改。DeerFlow 用读取哈希检查新鲜度，进程内锁覆盖检查和执行。但只保护接入路径，普通检查故障还有放行分支，不能当成跨进程事务或完整隔离。权限、外部写入者及最终文件结果仍需单独核对。

### 工具与扩展：⚠️ 高频易错点

- **只隐藏说明，不检查执行。** 模型可能从历史或猜测得到工具名。
- **把技能声明并集说成交集。** slash 优先、声明合并和保留工具按该版本区分。
- **把 LocalSandbox 当安全容器。** 名称不能证明宿主命令已隔离。
- **把释放资源当回滚动作。** 环境清理不撤销外部操作，重连也不等于安全重试。

### 工具与扩展：本章自测

**任务 A：** 旧展开状态为目录 A 的 `read`，新状态为目录 B 的 `export`；技能只允许 `read`。分别预测合并结果和执行许可。

<details>
<summary>任务 A 提示与答案</summary>

合并只保留 B 的 `export`。它满足的只是发现状态；技能不允许，仍应在可见性与执行阶段限制。合并函数不会替用户授予权限。

</details>

**任务 B：** 文件没有读取标记，检查时出现普通 I/O 故障，没有授权拒绝。此时工具正文尚未执行。预测门控结果，以及什么仍未知。

<details>
<summary>任务 B 提示与答案</summary>

走普通检查失败放行分支。文件是否改变仍未知，需核对工具结果、收据和目标文件。不能说已写成，也不能说被新鲜度门控拒绝。

</details>

### 运行与恢复：本章小结

正常 Run 驱动模型与工具，普通子任务有独立推理但可共享工作区，持久批任务另有接管边界。检查点保存继续状态，事件记录历史，文件与外部服务保有真实结果。恢复时先找对祖先与模式，再核对外部动作；验收始终区分停止、执行证据与业务质量。

### 运行与恢复：🎯 面试怎么回答

**Q：Agent 崩溃后怎样恢复，避免重复副作用？**

> 先恢复可继续状态，再查尚不确定的外部动作。DeerFlow 通过检查点访问器适配 full 与 delta，恢复时按通道语义替换，保留真实扩展字段。该快照的 delta 根会话恢复还要避免共享祖先增量混入，所以在当前头部写回物化状态。检查点不撤销文件或外部服务，仍需收据、日志和外部状态核对，业务再提供幂等或补偿。

**Q：子 Agent 不保存检查点，是不是无法做可靠长任务？**

> 普通子图是一次性执行，不继承父检查点，但步骤事件与结果仍可留证据，父级可保留委派账本。显式 batch_task 则持久保存任务项、租约和预算，允许未完成项重新接管。调度恢复不等于从子模型某一步续跑，也不保证外部动作精确一次。

### 运行与恢复：⚠️ 高频易错点

- **把回滚状态当成撤销全部动作。** 外部世界可能已经改变。
- **把最近时间当成正确祖先。** 兄弟分支不是彼此的历史。
- **把 completed 当成目标满足。** 还要看停止原因、结果和验收条件。
- **把共享沙箱当成全部上下文共享。** 信息选择和资源隔离不同。
- **把条件成立当成论证正确。** 文件与测试证据有各自证明范围。

### 运行与恢复：本章自测

**任务 A：** 第二轮才生成报告，第三轮修改它；用户从第一轮分支，没有文件系统历史快照。消息与工作区分别应怎样处理？

<details>
<summary>任务 A 提示与答案</summary>

消息沿正确祖先恢复。不能复制当前报告冒充第一轮文件；缺少历史文件快照，就承认不能完整还原该时刻的工作区，而不是判断消息恢复一定失败。

</details>

**任务 B：** 批任务已完成，空文件满足 `file:report.md exists`，另一个条件是“论证正确”，没有质量检查结果。能否交付为全部通过，是否自动按执行失败重试？

<details>
<summary>任务 B 提示与答案</summary>

在路径和读取条件有效的前提下，空文件满足存在，不满足非空；论证正确应标未验证。不能宣称业务验收通过，也不能把建议性检查未验证自动转成执行失败重试。补充质量验证后再决定交付或返工。

</details>

**任务 C：** 当前链是 `C0 → C1 → C2`，要在 delta 根会话路径恢复到 `C0`。为什么不直接在 C0 旁边再开一条链？请写出新头内容与亲缘关系。

<details>
<summary>任务 C 提示与答案</summary>

共享祖先的待处理增量可能带入被放弃分支的写入。先物化 C0，再在 C2 后写新头 C3，按实际状态结构恢复全部通道并重置新字段。C3 内容恢复到所选状态，亲缘继续为 C0、C1、C2、C3。它没有删除旧历史，也没有回滚外部文件。

</details>
