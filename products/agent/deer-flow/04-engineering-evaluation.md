# 04｜工程与评测：怎样继续、恢复并证明结果

[← 工具](03-tool-lifecycle.md) · [DeerFlow 总览](README.md) · [综合回顾 →](review/README.md)

主智能体读了支付页文件，又让子任务分析监控，最后报告“修复完成”。你需要知道：哪些文件真的改了，子任务是否只做了一半，下一次打开会话还能否继续。

先把正常运行和子任务放在同一张图上，再考虑取消、重启和历史分支。**只有先知道每份状态原本由谁保存，才能判断故障后缺少什么、该恢复什么。**

<a id="1-一次-run-至少涉及四类事实"></a>

## 1. 先走通一个正常 Run

本例固定为：网关接纳用户 `u1` 在会话 `t1` 的请求，创建 `r1`；模型与工具配置有效；文件在可访问工作区内。为先理解运行边界，暂不加入崩溃或恢复。

```text
用户请求
   ↓
网关创建 r1，工作器组装主智能体
   ↓
主模型取得上下文 → 提出读取或修改调用
   ↑                         ↓
   └──────────── 工具检查、执行并回填
   ↓
主模型给出最终回答，运行进入相应终态
```

循环中某次工具还可以是 `task`，把一个自包含问题交给子智能体。先不把它视为第二个用户会话：从父模型看，它仍是一项有参数、有结果的工具。

### 1.1 同一次运行为什么有多份记录

| 对象 | 保存或反映什么 | 本例的问题 |
|---|---|---|
| Gateway 的 Run 记录 | 本次运行处于哪个阶段 | `r1` 已接纳、运行中还是结束？ |
| LangGraph Checkpoint | 智能体继续所需的状态 | 消息、摘要和扩展字段是什么？ |
| Run Journal / RunEventStore | 运行中产生的事件 | 哪次调用、什么结果、怎样展示？ |
| 工作区与外部服务 | 真实副作用 | 文件是否改变，外部消息是否发出？ |

长期记忆是另一条保存路径，可能还在后台排队。运行状态、继续状态、事件和真实文件各回答不同问题，不因为本轮结束就同时完成提交。[运行层约定][runtime] · [工作器][worker]

<a id="2-停止原因为什么不能都叫任务完成"></a>

### 1.2 正常结束与目标满足仍需分别检查

自然最终回答、长度耗尽、安全停止和重复循环都能让运行停止，但后续处理不同。安全终止需抑制不能执行的工具调用，输出截断不能继续执行残缺参数；空停止响应的有限恢复也不是无限重试。

子任务结果可能标为 `completed`，同时带 `token_capped`、`turn_capped` 或 `loop_capped`。因此先看停止原因与可用部分结果，再核对目标，不能只看状态单词。[子任务结果定义][executor]

<details>
<summary>结束保护与错误处理的组装顺序</summary>

`after_model` 逆序分发时，安全处理要先清理不能执行的调用，再让统计与结束处理看到一致结果。主请求的有限模型边界恢复和最终无可见内容兜底，也由实际链路决定。[组装顺序][assembly]

模型错误可能发生在工具提议之前，工具错误却可能已接触外部服务。是否重试要看错误类型、预算与副作用确定性，不能因为安装错误中间件，就认为所有模型、工具和后端共用故障切换政策。[模型错误][llm-errors] · [工具错误][tool-errors]

</details>

<a id="7-子智能体隔离的是什么又共享了什么"></a>

## 2. 普通子任务：有自己的推理过程，不一定有独立文件世界

主智能体可以把“只分析指定监控证据，返回异常原因，不修改文件”交给 `task`。这段委派至少要给出任务、必要输入与结果要求；否则子级没有足够信息独立完成。

```text
父级：形成委派说明 → 调用 task ─────────→ 收到结果，再判断是否可用
                         │                        ↑
子级：                   └→ 模型 → 工具 → 模型 ───┘
```

子级有自己的消息、模型调用、工具约束和预算。原生子图使用 `checkpointer=False`，避免继承父检查点并污染父会话；普通子任务的模型内部步骤不默认作为跨用户轮次可恢复的子会话保存。执行事件仍可记录，父级也可保存委派摘要，这些不等于完整子图检查点。[子执行][executor] · [子任务约定][subagents]

<a id="71-isolated-与-snapshot-是信息选择不是两个独立物理世界"></a>

### 2.1 上下文怎样交给子级

| 模式 | 子级怎样获得背景 | 需要注意什么 |
|---|---|---|
| `isolated` | 依赖完整的委派说明 | 说明必须自包含，不能默认子级知道父对话 |
| `snapshot` | 派发时复制父级必要历史 | 固定的是当时背景，不随父级后续消息变化 |

快照可包含摘要、真实用户与可见助手消息，以及已配对完成的工具历史。父工具历史会表示成静态文本，不冒充子级自己的调用协议；父系统提示、秘密和权限声明也不能原样复制为子模型授权。[上下文快照][snapshot]

用户身份、知识范围与受控执行约束仍通过明确运行路径传递。隔离模型输入，不等于把子级变成没有身份或限制的匿名进程。

### 2.2 共享资源会带来什么后果

子级通常仍可共享父线程工作区与沙箱。两个子任务同时改同一文件，依然可能冲突。独立只读证据收集容易拆分；有输入依赖或重叠可变状态时，应先安排顺序、目录或输出责任，而不是只增加智能体数量。

普通 `task` 可在派发时复制有效的本轮上传状态。空列表明确表示本轮没有新上传，不该换成旧会话全部文件；缺少或损坏状态也不能假装可用。延迟执行的批任务没有同样的父运行上传边界。[上传与共享资源][subagents]

> ⚠️ **上下文隔离不等于文件隔离。** `snapshot` 也不是冻结整个文件系统；同一份文件仍可能被其他参与者修改。

<a id="72-所有子任务共享一个持久隔离循环不是每个子任务都开一个循环"></a>

<a id="73-子消息压缩以后步骤记录不能继续相信旧长度"></a>

<details>
<summary>子任务的事件循环与步骤记录怎样连接父级</summary>

原生子任务被送到进程内专用、持久的异步事件循环，与父请求循环分开；不是每个子任务都新建一个循环。跨循环可以传递合适的上下文，却不能直接借用绑定父循环的 Journal、连接池或 Future（尚未完成结果的对象）。

需要写父级事件时，子任务通过窄范围代理把记录动作调度回父循环，而不是直接修改父 Journal。源码过滤相应循环绑定回调，同时保留适合传递的流式语义。[代理][task-tool] · [循环约定][subagents]

一个工具步骤可能新增多条 ToolMessage，只看最后一条会漏记。历史压缩后长度还会缩短，扫描游标要相应调整，并结合稳定身份或内容去重。开始、步骤、结束事件分别记录，界面按子任务展开，不把全部中间消息塞回父对话。[步骤捕获][steps]

</details>

<a id="8-委派总量执行容量与持久批任务是三层控制"></a>

## 3. 长任务需要区分总量、并发与持久调度

假设同时最多执行三个子任务，却允许模型不停创建新批次，最终仍可能运行一百批。这些数值只为说明控制维度，不是默认配置。

| 限制 | 控制什么 |
|---|---|
| 本次 Run 的委派总量 | 这一轮最多交出去多少工作 |
| 同时执行容量 | 此刻最多有多少子任务占用资源 |
| 单个子任务预算 | 每项最多用多少轮次、时间或 token |

模型看到的能力说明应与启动时固定的执行容量一致，不能文案热更新了，实际控制器仍执行另一套限制。[容量与总量][subagents]

<a id="81-普通-task-与-batch_task-的持久边界不同"></a>

### 3.1 batch_task 保存的是可接管任务，不是每一步模型现场

| 对象 | 保存什么 | 故障恢复的含义 |
|---|---|---|
| 普通子图 | 本次内存状态与事件证据 | 不默认从某个子模型步骤续跑 |
| `batch_task` | 批次、任务项、说明、租约和有界结果 | 未完成项可由批服务重新接管 |
| 父检查点 | 父级继续状态与子任务摘要账本 | 父级知道曾委派什么，不等于拥有子图检查点 |

批模式通过明确工具选择进入，不是提示很长就自动转成持久队列。工作器领取任务项并续租；租约表示一段时间内由谁处理它，完成时按拥有者身份写结果。进程停止、租约过期以后，其他工作器可在尝试预算内接管。接纳失败与实际执行失败也有不同计数语义。[接纳与续租][batch]

> ⚠️ 重新领取任务项，不等于从子模型上一条消息原地继续，也不保证外部动作精确执行一次。重试前仍需根据动作与证据判断重复风险。

<a id="82-什么时候值得委派"></a>

委派有启动、重复发现与汇总成本。只有并行时延、专长或上下文隔离收益值得这些成本，才应使用；每批重新判断，不因上次委派有效就把全部后续工作交给子级。

<a id="3-检查点保存状态但通道的更新语义仍然有效"></a>

## 4. 检查点怎样保存“接下来从哪里继续”

### 4.1 保存状态以前，先明确怎样应用更新

**通道**是状态中的一个字段及其更新规则。例如消息按 ID 合并，某些引用去重追加。恢复不仅要知道新值，还要知道它会替换旧值还是与旧值合并。

假设当前消息 `[A, B, C, D]`，希望恢复为 `[A, B]`：

| 写入方式 | 可能得到什么 | 为什么 |
|---|---|---|
| 普通消息更新 `[A, B]` | `[A, B, C, D]` | 只更新同 ID 消息，没有删除 C、D |
| `Overwrite([A, B])` | `[A, B]` | 明确整体替换该通道 |

DeerFlow 用只变更状态的图写新检查点。图中只有不执行业务的节点，沿用实际智能体的状态结构与检查点机制，不调度模型或工具。这让恢复后的头部处在空闲状态。

自定义中间件可贡献字段，因此必须使用线程实际智能体的完整状态结构；只用基础 `ThreadState`，可能丢掉扩展字段。它们虽没有出现在简化消息表中，仍属于要恢复的状态。[状态变更图与访问器][checkpoint]

<a id="4-full-与-delta-不只是存储大小不同"></a>

### 4.2 full 与 delta 怎样表示同一份历史

`full` 保存完整累积状态；`delta` 对适用累积通道保存新增写入，并周期保存快照。用只追加消息的算术模型理解：

| 步骤 | 此刻完整消息 | 每步全量保存 | 仅计每步新增 |
|---|---|---:|---:|
| 1 | A、B | 2 条 | 2 条 |
| 2 | A、B、C、D | 4 条 | 2 条 |
| 3 | A、B、C、D、E、F | 6 条 | 2 条 |
| 合计 | 最终仍是 6 条消息 | 12 条次 | 6 条次 |

“条次”计重复序列化，不是最终对话长度。这是教学估算，真实 delta 还含周期快照、元数据与后端开销，不能当成实测节省一半。

读取增量时，要从可用快照结合后续增量恢复完整状态，这叫**物化**。原始 saver（检查点存储器）返回的对象可能只有增量标记，不能直接当完整消息。`CheckpointStateAccessor` 负责选择正确状态结构、检查模式兼容并返回物化结果；只查元数据也要走保留兼容检查的入口。[模式约定][runtime] · [统一读取][checkpoint]

<a id="41-模式兼容不是双向对称"></a>

### 4.3 模式切换不是双向对称

该快照默认 `full`。模式与增量快照频率在进程内固定，改变需要重启；共享检查点数据库的进程也需一致解释。

`delta` 进程可把旧 `full` 检查点作为重建起点；`full` 进程不能把 delta 原始数据当完整状态，反向切换须先物化与转换。缺少消息字段不能默认成空列表继续，否则会掩盖模式错误。[兼容与迁移][runtime]

<a id="checkpoint-recovery"></a>
<a id="5-取消编辑重跑和历史分支怎样保持一致"></a>

## 5. 恢复：先选对过去，再写成可继续的状态

<a id="52-找旧检查点要沿亲缘关系不是只看时间"></a>

### 5.1 检查点有亲缘关系，不只是一串时间戳

假设 `C0` 保存用户问题，`C1` 保存旧回复。后来从 `C0` 重新回答，形成另一分支 `C2`：

```text
C0：用户问题
├─ C1：旧回复
└─ C2：重新生成的回复  ← 当前分支
```

`C0` 是两个分支的共同祖先，`C1` 与 `C2` 是兄弟。要找 `C2` 的历史，应沿其 `parent_config` 指向的父检查点回溯，不能因为 `C1` 时间接近就把它当祖先。

只有明确的旧数据缺少父链接等兼容条件，才允许有界时间顺序兜底。循环、悬空父节点、目标不匹配或存储错误，要作为错误处理，不能选一份“差不多”的状态。[亲缘查找][lineage]

<a id="42-为什么-delta-的恢复不能随意从旧点分叉"></a>

### 5.2 为什么这个快照的 delta 恢复不直接另开分支

上图只说明亲缘关系，并不表示两种模式都采用同一种恢复算法。这个固定实现的 delta 重建会读取沿途祖先的待处理增量；共享祖先上可能还有写向被放弃分支的内容。例如从 `C0` 重答，本应得到“用户问题、新回复”，却可能把 `C1` 的旧回复也带进来。[具体限制与原因][runtime]

DeerFlow 不另写一套祖先增量重放规则，而是在相应根会话恢复路径采取下面的办法：

```text
已有历史：C0 → C1 → C2（当前头部）
目标：回到 C0 的内容，再重新执行

1. 通过访问器，把 C0 读成完整状态
2. 不从 C0 另开一个兄弟分支
3. 在 C2 后写 C3，把全部通道恢复为所选状态
4. 从 C3 继续，产生新的运行结果

最终亲缘：C0 → C1 → C2 → C3 → 新结果
C3 的内容回到所选状态，但历史亲缘继续向前
```

这叫**线性恢复**：状态可以恢复为过去的值，检查点链却在当前头部继续增长。归并通道用 `Overwrite`，只存在于当前头部的较新字段按实际结构恢复默认值，不能构造默认值时用 `None`。旧运行仍在祖先历史中，不是删除所有过去。

该限制针对这里的 delta 根会话恢复路径，不是宣称所有增量存储都不能分支。`full` 不靠同样的祖先增量重放，可保留分叉语义。[工作器恢复实现][worker]

<a id="51-回滚点必须是完整的运行前状态"></a>

### 5.3 取消回滚需要完整的运行前状态

工作器开始执行前捕获完整可物化状态、检查点位置与相应待处理写。捕获失败就禁用相应回滚能力，不能拿半份数据当安全恢复点。

取消并选择回滚时，`full` 可基于运行前检查点形成新头；`delta` 则在当前头部完整恢复捕获的通道，避免引入兄弟增量。实际智能体扩展字段与服务端绑定也要保留，不能从客户端任意字段重建授权。[捕获与回滚][runtime] · [工作器][worker]

编辑旧输入再运行，会先形成临时替代历史。新运行失败、超时或中断时，需要恢复运行前状态，并在流结束前通知客户端恢复值，否则界面会停留在没有成功完成的新历史。

<a id="53-为什么历史分支不能复制今天的工作区"></a>

### 5.4 消息回到过去，不代表文件也回到过去

假设第一轮还没有 `report.md`，第二轮才生成文件，第三轮又修改它。现在从第一轮分支，直接复制当前工作区会把未来文件带进去。

没有每轮完整文件快照时，DeerFlow 的历史轮次分支不复制当前工作区；最新轮次分支才可尽力复制当前文件。此时正确的结论是“消息可恢复，但没有依据还原完整历史文件”，而不是用当前文件冒充过去。[线程生命周期][thread]

> ⚠️ **状态回滚不撤销外部世界。** 文件修改、已发送消息和远端数据库变化，需要另行核验，必要时做业务幂等或补偿。检查点、日志与长期记忆都不是副作用的自动逆操作。

<a id="6-日志与实时流为什么不能直接代替检查点"></a>

## 6. 继续状态与历史界面怎样对齐

`RunJournal` 把模型、工具与运行回调组织成可持久事件；RunEventStore 为界面提供历史。实时 token 片段便于逐字显示，却不必全部成为永久消息记录。检查点回答怎样继续，事件回答发生过什么，两条路径必须使用一致的身份解释。[Journal][journal]

<a id="61-同一次模型响应回调两次不能变成两条答案"></a>

### 6.1 同一次响应的两次回调，不是两条答案

供应商可能先回调模型响应，随后按同一模型运行 ID 补充用量。Journal 合并相邻的对应信息，保留首份响应内容与适用的用量补充，避免重复展示和统计。晚到回调不能任意改写已追加历史。

这是产品侧计量处理，不证明供应商实际收费两次。诊断时先区分“真调用两次”和“一次调用回调两次”。[响应合并约定][runtime]

<a id="62-历史界面与检查点需要共享轮次身份"></a>

### 6.2 分支继承与断线续读都需要边界

分支继承检查点消息，却没有相应事件时，界面可能只显示新轮次。因此需要补齐继承历史对应事件，并为不同用户轮次提供适当运行身份，不能全部共用一个可被整体替换的 ID。[线程历史][thread]

客户端断线后可按序号继续获取事件。所需区间已经丢失时，应报告重放缺口，让客户端重新读取持久状态，再建立一致视图，不能从最早剩余事件假装无缝继续。[事件流协议][stream]

<a id="63-补齐悬空工具调用只修复了消息协议"></a>

### 6.3 补上工具结果消息，不证明动作没有发生

中断可能留下工具调用却没有配对结果。`DanglingToolCallMiddleware` 在后续模型调用前补齐相应协议表示，避免供应商拒绝请求。

但补出的错误只修复消息协议。如果外部服务已经接受操作，结果只是丢在返回途中，真实动作仍需查服务端或执行证据。这正是“模型可以继续”与“业务状态已经查清”的区别。[悬空调用处理][dangling]

<a id="10-取消以后谁负责把已经取得的资源释放完"></a>

## 7. 取消后，已取得的资源由谁收尾

取消请求不保证同步操作已经停止，也不保证连接、锁与沙箱已释放。第三篇的 MCP owner task 和沙箱租约，在这里都要完成自己的收尾责任。

多处源码使用 shield-and-drain，可理解为**保护清理并等它完成，再传播取消**。例如子执行先关流，再释放沙箱持有与执行容量；MCP 由自己的拥有者退出；持久化初始化也要释放已取得的锁和连接。[运行资源约定][runtime] · [子任务资源约定][subagents]

这不是让一切操作无限等待。有些后台状态等待有宽限期并移交清理者，有些仍持有资源的清理不能靠超时遗弃。需要逐项明确谁拥有、取消如何传播、何时移交与最终谁回收，不给整个系统套一个统一超时。[异常等待与移交][task-tool]

<a id="11-怎样知道两次运行用了同一套系统"></a>

## 8. 比较两次运行以前，先确认实际组件

相同模型名不等于相同系统。提示、工具定义、技能、中间件顺序、上下文政策与配置都可能不同。`AssemblyDescriptor`（组装描述）记录相关身份与哈希，帮助解释差异；昂贵部分在有需要的观察者时才计算，避免无人使用的诊断开销。[组装描述][assembly]

扩展中间件要在完整链组装后合并并检查顺序，否则观察者可能看不到最终请求，或者错误规范化与进度记录的先后被倒置。[顺序约束][ordering]

哈希适合判断内容是否不同，不能从哈希还原完整输入。真正回放还需要对应请求、状态与执行证据，不能把一个摘要标识当成完整回放数据。

<a id="9-收据可判定条件和业务质量为什么不能合成一个通过"></a>

## 9. 验收：执行过、文件存在和业务正确是三件事

子任务说“报告写好了”，先检查动作声明是否有对应收据，再检查目标文件，最后判断内容质量。

| 检查 | 能确认什么 | 仍不能确认什么 |
|---|---|---|
| 收据引用有效 | 声明有对应执行记录 | 记录的动作已满足全部要求 |
| 文件存在 | 指定目标存在 | 文件非空、论证正确 |
| 文件非空或写入读回 | 满足相应可判定条件 | 业务推理无误 |
| 测试执行证据成立 | 对应测试命令与结果有依据 | 测试覆盖全部业务 |

`acceptance_checks.py` 对存在、非空、写入读回及特定测试执行证据等叶条件作检查。叶条件是能单独判断的一项要求；无法判断的自然语言条件标为 `UNVERIFIED`，不能自动算通过。源码区分 `checked`（是否完成检查）与 `holds`（条件是否成立）。[验收检查器][acceptance]

例如输出中出现 `pytest` 不证明真执行了测试，零测试也不是测试通过；读取应有字节界限，目录、符号链接或不能安全确定的目标不随意当普通文件。

批任务这里的附加验收具有建议性。检查器故障或自然语言条件未验证，不自动把可用执行结果变成应重试的执行失败。是否阻断交付，要继续看调用方与任务要求；不能推出系统没有其他强制门禁。[批服务调用方][batch] · [验收资源管理][batch-acceptance]

<a id="12-评测应围绕故障窗口而不是只数测试文件"></a>

## 10. 用故障窗口检验整条过程

先定义支付修复任务的验收：没有发布；文件修改有依据；能说明做过和未做过的验证。再改变一个条件，看系统能否正确解释状态。

| 变化或故障 | 应核对什么 | 单靠什么不够 |
|---|---|---|
| 多轮后摘要压缩 | 当前约束、工具配对与后续可执行性 | token 数下降 |
| 副作用完成后响应丢失 | 先查真实状态，不盲目重放 | 一条错误 ToolMessage |
| 子任务输出到一半取消 | 停止原因、部分结果和资源持有 | 界面显示取消 |
| 从旧轮次分支 | 祖先正确，不引入未来文件 | 分支接口成功 |
| 事件区间丢失 | 重新读取持久状态建立视图 | 前后端各自单测通过 |
| 记忆索引坏了或队列未提交 | 区分可降级检索与未持久写入 | 没有抛异常 |

测试也分层：纯函数检查状态合并与候选门控；中间件测试检查角色、拒绝和错误；检查点与数据库集成检查恢复；确定性回放复现给定模型与工具轨迹；浏览器端到端检查服务、流与界面组合。真实模型、MCP、远程沙箱和生产部署还需各自条件。[上游回放指南][replay]

同时观察任务结果、失败位置与资源开销：完成多少，在哪层失败，模型、工具与委派调用多少，花多少 token、时间与存储。拒绝率高但所有任务都做不成，不是有效系统；成本低但约束丢失，也不是优化成功。没有实测时，这些是评测设计，不是已经取得的提升结果。

## 本章小结

正常 Run 驱动模型与工具，普通子任务有独立推理但可共享工作区，持久批任务另有接管边界。检查点保存继续状态，事件记录历史，文件与外部服务保有真实结果。恢复时先找对祖先与模式，再核对外部动作；验收始终区分停止、执行证据与业务质量。

## 🎯 面试怎么回答

**Q：Agent 崩溃后怎样恢复，避免重复副作用？**

> 先恢复可继续状态，再查尚不确定的外部动作。DeerFlow 通过检查点访问器适配 full 与 delta，恢复时按通道语义替换，保留真实扩展字段。该快照的 delta 根会话恢复还要避免共享祖先增量混入，所以在当前头部写回物化状态。检查点不撤销文件或外部服务，仍需收据、日志和外部状态核对，业务再提供幂等或补偿。

**Q：子 Agent 不保存检查点，是不是无法做可靠长任务？**

> 普通子图是一次性执行，不继承父检查点，但步骤事件与结果仍可留证据，父级可保留委派账本。显式 batch_task 则持久保存任务项、租约和预算，允许未完成项重新接管。调度恢复不等于从子模型某一步续跑，也不保证外部动作精确一次。

## ⚠️ 高频易错点

- **把回滚状态当成撤销全部动作。** 外部世界可能已经改变。
- **把最近时间当成正确祖先。** 兄弟分支不是彼此的历史。
- **把 completed 当成目标满足。** 还要看停止原因、结果和验收条件。
- **把共享沙箱当成全部上下文共享。** 信息选择和资源隔离不同。
- **把条件成立当成论证正确。** 文件与测试证据有各自证明范围。

**任务 A：** 第二轮才生成报告，第三轮修改它；用户从第一轮分支，没有文件系统历史快照。消息与工作区分别应怎样处理？

<summary>任务 A 提示与答案</summary>

消息沿正确祖先恢复。不能复制当前报告冒充第一轮文件；缺少历史文件快照，就承认不能完整还原该时刻的工作区，而不是判断消息恢复一定失败。

</details>

**任务 B：** 批任务已完成，空文件满足 `file:report.md exists`，另一个条件是“论证正确”，没有质量检查结果。能否交付为全部通过，是否自动按执行失败重试？

<details>
<summary>任务 B 提示与答案</summary>

在路径和读取条件有效的前提下，空文件满足存在，不满足非空；论证正确应标未验证。不能宣称业务验收通过，也不能把建议性检查未验证自动转成执行失败重试。补充质量验证后再决定交付或返工。

</details>

**任务 C：** 当前链是 `C0 → C1 → C2`，要在 delta 根会话路径恢复到 `C0`。为什么不直接在 C0 旁边再开一条链？请写出新头内容与亲缘关系。

<details>
<summary>任务 C 提示与答案</summary>

共享祖先的待处理增量可能带入被放弃分支的写入。先物化 C0，再在 C2 后写新头 C3，按实际状态结构恢复全部通道并重置新字段。C3 内容恢复到所选状态，亲缘继续为 C0、C1、C2、C3。它没有删除旧历史，也没有回滚外部文件。

</details>
