# 历史与恢复｜保存、压缩与重新接续

[← 上一章](04-agent-collaboration.md) · [本产品目录](README.md) · [下一章 →](06-memory-pipeline.md)

模型和工具已经产生了历史，现在才讨论这些记录怎样留下、怎样缩小到模型窗口，以及崩溃后怎样继续。规范日志、查询索引、模型窗口和磁盘文件是四个不同对象。

<a id="persistence"></a>
## 一条结果何时算保存下来

工具结果先到内存，再写入存储。程序返回“收到结果”时，写入可能已经完成，也可能还在排队。恢复能力取决于实际完成的保存步骤。

`ThreadStore` 用 ThreadId 作为稳定身份，把线程存储接口与具体介质分开。公开本地实现使用文件与 SQLite：Rollout（运行历史记录）提供历史重放材料，线程元数据索引支持查询；列表页能显示标题，不等于所有模型历史都已保存。[存储接口][src-store]、[本地实现][src-local-store]。

用一条工具结果 `r1` 的**教学时序**区分：

```text
内存收到 r1 → 提交保存 r1 → 等待保存达到约定边界
                                       ↓
                                 可供后续恢复读取
```

有的调用上下文允许先排队返回，之后通过持久化屏障确认；`Standard` 要求保存完成后返回。`flush_thread` 等待此前排队材料达到接口要求的持久、可读状态。“屏障”在这里是等待此前写入完成的确认点。[源码：`PersistContext` 与 `flush_thread`][src-store]。

| 观察结果 | 可以断言什么 | 仍不能断言什么 |
|---|---|---|
| 内存已接纳结果 | 活跃流程得到了结果 | 崩溃后一定可恢复 |
| 允许后台保存的调用返回 | 材料可以已排队 | 未确认写入一定落稳 |
| 相应 flush 成功 | 达到该接口的持久、可读边界 | 远端副作用与历史在同一个事务中 |
| 正常关闭成功 | 相应待写处理完成 | 崩溃时也有同样清理机会 |

初始化失败时的 `discard_thread` 不强制保存未持久化的准备材料；正常关闭与丢弃有不同目的。恢复还需要重新建立连接等活跃资源，不能直接复用已经消失的内存句柄。

### 本地保存的实际顺序：日志在前，SQLite 投影在后

创建或恢复本地线程先取得单写者所有权，并登记活跃记录器。追加时按该线程历史模式过滤需要保存的条目，写入规范 Rollout 日志并 flush；分页历史模式随后把这份已落稳日志投影到 SQLite。这里的投影就是便于查询的派生视图：投影失败可以落后于日志，不能领先于日志。因此“列表或历史查询暂时没更新”与“规范记录没有保存”不是同一种故障。

`Persist` 可以在尚无轮次条目时保存初始线程元数据，`AppendItems` 保存正常事件，`Flush` 等待已排队材料。关闭完成后移除活跃记录器，迟到写入失败；初始化丢弃走另一条路径，不伪装成正常保存。[真实写入顺序](https://github.com/openai/codex/blob/cda82a2c6853b484e0ba56d38f13902adfb2a6a1/codex-rs/thread-store/src/local/live_writer.rs)

恢复先定位当前规范日志，并检查归档状态。调用者可能提前读过一份历史；预读取快照只有在其 revision 与当前日志 revision 匹配时才复用同线程历史，否则重载最新模型上下文。这样在“读取”与“取得写者权”之间发生历史改写时，不会继续用过期副本恢复。这个检查保证恢复材料的新鲜度，不会使外部命令与历史写入自动形成原子事务。

<a id="paired-results"></a>
## 调用和结果怎样在历史里保持对应

回到调用 `c1`。模型请求读取文件，宿主得到文件内容；二者用 `call_id` 关联。多次相同工具并行执行时，结果可能先后返回，编号仍能说明结果属于哪次调用。

```text
调用：c1，读取 pagination.py
结果：c1，读取成功，返回相应内容
调用：c2，运行测试
结果：c2，进程退出，返回失败摘要
```

上面是关系示意，不是统一工具输出格式。真实类型和封装见 [registry.rs 的 `AnyToolResult`][src-registry]。大结果还可能带有影响后续截断的预算元数据。为判断测试是否完成，保留退出状态和关键差异比只留下日志开头更有用；这是结果设计要求，不代表每个工具都采用相同摘要算法。

中断或筛选可能留下只有调用、没有结果的历史。`normalize.rs` 可以为缺失结果的函数调用补入表示中止的合成结果；孤立结果和工具搜索等协议类型按各自规则处理。[源码：配对与规范化][src-normalize]。

> ⚠️ **注意：合成 `aborted` 只补全模型输入结构。** 它不执行工具，也不证明外部动作没有发生。恢复时的实际状态检查见[历史与恢复章](05-history-and-recovery.md#recovery)。

<a id="budget-cache"></a>
## 先分配容量，再考虑能复用多少计算

token 是模型处理输入与生成时的计数单位，不等于字符数。一次请求要给指令、历史、工具说明、新结果和后续生成留空间。

用一组**教学预算，不是 Codex 默认值**计算：窗口 32,000 token，预留生成 6,000，安全余量 2,000，输入可规划 `32,000 − 6,000 − 2,000 = 24,000 token`。固定指令和工具说明已占 5,000，历史与新结果合计便剩约 19,000。实际计数和触发条件要结合模型、输入类型与配置；不能把这个减法当成实现的全部预算逻辑。[窗口判断的调用处][src-turn]。

连续请求常有相同的前缀。保持内容和标识稳定，有助于服务端复用前缀计算。源码中，规范化合成结果的标识由来源标识稳定推导，注释将其与重试、恢复时的提示缓存联系起来。[源码：合成标识][src-normalize]。

| 手段 | 复用或减少的对象 | 仍须检查什么 |
|---|---|---|
| 前缀缓存 | 重复输入的部分计算 | 输入是否仍适用、是否超出窗口 |
| 答案缓存 | 已有答案 | 当前请求能否安全复用答案 |
| 上下文选择 | 无关或不必要的输入 | 是否误删关键条件与证据 |

缓存不是记忆，也不是正确性检查。项目约定过时，即使计算命中缓存也可能给出错误判断。

<a id="compaction"></a>
## 压缩怎样腾出空间，又保住尚未完成的工作

旧历史已经很长时，在末尾再加摘要只会更长。Compaction（上下文压缩）需要构造较小的替换历史，让后续请求从它继续。

分页任务可以有这样的**摘要设计示意**：

| 压缩前的重要信息 | 替换后需要保留的含义 |
|---|---|
| 用户不允许改变公开接口 | 后续修改仍受这个约束 |
| 已修正偏移表达式 | 不必再次把同一修改当作未开始 |
| 参数校验尚未完成 | 不能仅凭第一页正确就结束 |
| 某些测试没成功启动 | 不能将“尝试运行”写成“已通过” |

具体压缩结果由相应实现和模型产生，上表不是 Codex 保证生成的固定字段。它帮助判断“分页已处理”为什么不足以支持继续工作。

```text
旧历史 → 准备压缩输入 → 生成替换材料
                            ↓
            替换历史并处理检查点与比较基线
                            ↓
              补回必要指令、环境和当前任务
                            ↓
                      继续模型请求
```

压缩流程包含前后钩子、替换历史和检查点元数据，普通路径与远端路径也随提供者能力而不同。[`compact.rs`][src-compact]中，`InitialContextInjection` 区分必要上下文何时补回：采样前或手动压缩可以使相关基线失效，让随后常规流程重新注入；轮次中途压缩则要直接把当前步骤需要的信息放回合适位置，不能等一个并不存在的新用户输入。

失败也要看发生位置：采样前的新输入尚未进入通常历史路径，核心需要专门保留；轮次中失败可能阻止继续采样；本轮完成后的压缩失败，不自动撤销已完成的任务结果。[源码：`run_turn` 的各阶段处理][src-turn]。

> ⚠️ **注意：结构一致不代表摘要语义无损。** 调用配对正确、历史能恢复，仍可能漏掉“不能改接口”。宿主保留事实与审核状态提供另一层支持，但不是所有任务细节都自动获得同样保护。

### 三种缩小窗口的路径不能合成“模型写一段摘要”

1. **TokenBudget 路径**：启用该功能时，压缩入口先执行前置 Hook，然后直接开始新上下文窗口，发出开始/完成事件，再执行后置 Hook。这条路径本身不发起摘要模型请求；不能因为界面有压缩事件，就推断产生过自然语言摘要。[窗口重置](https://github.com/openai/codex/blob/cda82a2c6853b484e0ba56d38f13902adfb2a6a1/codex-rs/core/src/compact_token_budget.rs)
2. **本地压缩路径**：从当前历史构造压缩输入，请求摘要。压缩输入自身超窗时，逐步删去最早条目后重试，保留较新材料；取消和预算耗尽按对应错误结束。成功后用保留的用户消息和摘要构建较小替换历史。轮后压缩需要非空助手摘要，不能用空结果宣布完成。[本地生成与替换](https://github.com/openai/codex/blob/cda82a2c6853b484e0ba56d38f13902adfb2a6a1/codex-rs/core/src/compact.rs)
3. **远端 V2 路径**：先裁剪过大的函数结果，使压缩请求可容纳；携带本次工具说明、基础指令、历史元数据和压缩触发项。远端返回结构化压缩产物，宿主再按该协议处理并构建替换历史；它不是把普通聊天最后一段文字随便当摘要。[请求构建](https://github.com/openai/codex/blob/cda82a2c6853b484e0ba56d38f13902adfb2a6a1/codex-rs/core/src/compact_remote_v2_attempt.rs)、[返回与替换](https://github.com/openai/codex/blob/cda82a2c6853b484e0ba56d38f13902adfb2a6a1/codex-rs/core/src/compact_remote_v2.rs)

远端 V2 还保留一组可明确识别的来源消息：真实用户消息、Hook 提示，以及配置允许保留的客户端开发者消息；部分 Agent 消息另受类型和单条预算限制，子级过程回报和完成通知不按同一规则原样保留。候选先分组，应用保留策略，再按总 token 与图片预算裁剪，最后追加压缩产物。服务端流没有返回要求的 Compaction 条目时直接报错，不安装一份假定成功的历史。

三条路径都要接回后续请求。按压缩时点决定直接补入当前步骤的初始上下文，还是让比较基线失效、由下一请求完整注入。当前实现还把压缩输入中的目标消息身份带到替换元数据，供宿主保持目标相关状态。保留身份不意味着摘要能无损保留每个细节。

若轮后压缩因额度用尽失败，已经完成的回答仍保留，同时发出用量限制错误以停止自动工作。这与轮前压缩失败阻止本次采样不同；排障要看失败发生在任务链的哪一个位置。

<a id="recovery"></a>
## 崩溃发生在动作和记录之间，恢复应先检查现实

设分页补丁已经写入文件，但工具成功结果还没有记入历史，进程就崩溃了：

```text
收到工具请求
    ↓
文件发生修改
    ↓       ← 此处崩溃：动作可能已成，历史未确认
记录工具结果
    ↓
完成必要持久化
    ↓
继续模型判断与验收
```

这是故障分析模型，不是本次复现的 Codex 缺陷。它说明外部动作与内部记录不共享事务时，历史可以落后于现实。

恢复时按下面顺序判断：

1. 读取恢复历史，确认哪次动作缺少可靠结果。
2. 读取实际文件或差异；远端动作则查询已有标识对应的状态。
3. 区分尚未执行、已知成功、已知失败与结果未知。
4. 根据实际状态补记录、继续验证或安全重试；无法核实时保留不确定状态。

直接重做可能重复应用补丁，甚至覆盖用户在崩溃后补充的修改。Idempotency（幂等）是重复处理同一业务请求不产生额外效果，需要相应业务标识与处理机制；持久化和重试本身不会自动提供它。

`ThreadStore` 提供恢复、历史和最新模型上下文加载等接口，但部分能力的默认实现可以明确不支持。要依据实际后端判断能恢复哪些材料。[源码：存储能力与默认分支][src-store]。跨系统幂等的完整设计回到 [Agent 通用课程](../../../curriculum/09-agent/README.md)与[后端课程](../../../curriculum/05-backend-engineering/README.md)。

> ⚠️ **注意：历史恢复、合成中止结果、执行后拒绝与取消都不代替这一步现实核对。** 它们分别改变内部记录或后续执行，不能据此认定外部动作已被撤销。

<a id="retry"></a>
## 模型请求、工具动作、记忆任务为什么不能共用一句“重试”

| 重试对象 | 需要解决的失败 | 不能顺带保证什么 |
|---|---|---|
| 模型传输与请求 | 连接中断或其他可重试请求错误 | 业务工具已经安全重做 |
| 工具执行 | 例如特定沙箱拒绝后的受控再次尝试 | 任何错误都能提高权限绕过 |
| 后台记忆任务 | 提取、整理、租约与状态提交失败 | 入口调用完成就已经写成记忆 |

工具分支回看[执行许可](02-tools-and-processes.md#permissions)，记忆分支回看[整理结束检查](06-memory-pipeline.md#writer-permissions)。它们已有不同的对象和副作用，不能用一个统一次数解释。

模型请求的 `responses_retry.rs` 先判断错误是否可重试，再决定等待、计数或切换备用传输。固定实现还有一个不消耗普通有限重试计数的连接失败分支，同时要求：相关功能开启、请求属于 Sampling（模型采样）、错误为 `ConnectionFailed`、不是内部会话，且提供者不是 Amazon Bedrock。[源码：完整重试条件][src-retry]。

该功能在固定快照中默认开启，等待从 5 秒递增，单次上限 60 秒。按这段规则连续进入五次等待，单计等待就是 `5 + 10 + 20 + 40 + 60 = 135 秒`。这是教学计算，不包含请求耗时，也不是完成时间承诺。[功能默认值][src-features]。

当前实现还读取服务端的重试时间建议：普通重试按该截止时间等待，切换备用传输也不能绕过它；时间建议不会增加配置中的有限重试额度。采样收到内容过滤错误时，会先记录相应指导，再判断是否可重试。

普通有限重试耗尽后还可能转向 WebSocket 到 HTTP 等备用传输；具体由分支条件决定。连接专用分支没有普通次数上限，不等于进程永远不会退出，更不等于所有 API 错误都会无限重试或走同一降级路径。
