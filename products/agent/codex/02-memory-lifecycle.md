# 记忆｜历史怎样变成可以复用、也可以纠正的经验

[← 上一篇：工具](03-tool-lifecycle.md) · [模块入口](README.md) · [下一篇：工程与评测 →](04-engineering-evaluation.md)

第一次修分页时，Agent 在错误目录运行测试，提示找不到模块；切到练习目录后才成功启动。第二天再次修改这个项目，值得复用的是正确的测试入口，而不是一句“这个项目测试失败”。

这就是记忆与复制旧对话的区别：**从发生过的事情里提取适用的经验，整理后供新任务使用，再用当前证据检查它是否仍然正确。** 本篇先走通一条经验的生成与读取，再看启动条件、版本和失败保障。

<a id="memory-kinds"></a>
## 1. 先分清规则、当前输入、历史与经验

同一个分页项目，可以同时有以下四类信息：

| 材料 | 回答什么问题 | 本例中的内容 |
|---|---|---|
| `AGENTS.md` 等项目指令 | 应该遵守什么？ | 不改公开接口，按约定运行测试 |
| 当前模型上下文 | 下一次判断需要看什么？ | 用户需求、刚读到的实现与测试结果 |
| 对话与执行历史 | 之前实际记录了什么？ | 在错误目录失败、换目录后重新运行 |
| 整理后的记忆材料 | 哪些经验以后值得参考？ | 这个项目的测试入口与适用条件 |

指令是约束来源，历史是处理经验的输入，记忆是从证据中整理出来的材料。它们都可能进入上下文，但用途和可信依据不同。记忆读写在公开实现中分别由[读取扩展][src-extension]与[写入库][src-write]承担，不应先假定它们是一套向量数据库检索。

<a id="memory-example"></a>
## 2. 沿一条经验，看清每个阶段产出了什么

以下正常路径假设记忆功能、环境与状态存储满足要求，并且历史已符合处理条件；实际触发时机与开关在后文说明。表中内容是**教学材料，不是模型真实产出，也不是固定输出 Schema**。

| 阶段 | 输入 | 得到的材料或判断 |
|---|---|---|
| 原始历史 | 错误目录导致测试未启动；换目录后运行了测试 | 有一段带上下文的工作记录 |
| 提取 | 阅读这段历史 | 候选经验：测试应在该练习目录运行 |
| 整理 | 候选经验与已有材料 | 合并重复记录，保留项目范围和具体方法 |
| 新任务读取摘要 | 当前选择的记忆材料 | 知道这个项目有一条测试入口经验 |
| 按需读取详情 | 摘要给出的线索 | 取得工作目录和命令，再核对当前项目 |

可以把有用经验与无用结论并排看：

```text
无用结论：这个项目测试失败。

可供核验的经验示意：
  适用范围：当前仓库的分页练习
  观察：从错误目录运行时，测试没有成功启动
  目录：practice/coding/exercises/09-ai-coding-lab/
  方法：进入该目录，再运行 python -m unittest discover -v
  使用前检查：目录、测试入口和项目约定是否已经变化
```

提取回答“这段历史有什么值得留下”，整理回答“这些经验怎样与已有材料共同使用”。新任务读取又是第三件事：没有读取到材料，就不能仅凭文件存在断言模型已经用上记忆。[提取实现][src-phase1]、[整理实现][src-phase2]、[摘要注入][src-prompts]。

<a id="extraction"></a>
## 3. 提取处理一段历史，空结果也可能是正常结束

Extraction（提取）将某段历史转成候选经验。第一阶段先选择符合来源、历史年龄、最小空闲时间及数量限制的候选，再以有上限的并发请求模型，解析结构化输出并记录结果。输入也受容量预算约束。[源码：`phase1.rs` 的候选领取、模型调用与结果提交][src-phase1]。

没有新经验的闲聊，检查后可以不保存。强行要求“每次必须写三条”，反而容易把偶然失败或猜测变成长期结论。

| 结果 | 表明什么 | 合理的后续 |
|---|---|---|
| 成功且有输出 | 有可保存的结构化提取结果，状态提交成功 | 成为整理候选 |
| 成功但无输出 | 检查已完成，没有应保存的材料 | 不因为空就无限重试 |
| 失败 | 读取、模型调用、解析或状态提交等未完成 | 记录原因，按重试条件处理 |

程序成功只说明这次处理完成了约定步骤。内容是否真实、是否过时，仍要结合来源、时间与当前任务判断。来源时间、工作目录和原历史因此不是装饰性备注，而是判断经验适用范围的依据。

如果两个后台处理者同时发现同一历史，直接各自处理就会重复成本。状态库先让工作者领取任务，并返回所有权令牌与租约：令牌识别谁拥有这份工作，租约规定负责权何时失效。后续成功或失败提交还要带上令牌。这样工作者崩溃后可以接管，旧工作者也不能无条件提交过期结果。

> ⚠️ **注意：租约不是跨系统事务。** 它管理任务负责权，并没有把模型请求、文件系统和状态库合成一次不可分割的动作；仍要检查各步骤的失败位置。

<a id="consolidation"></a>
## 4. 整理面向共享经验，而不是再总结一次聊天

一次任务发现页码从 1 开始，另一次确认空数据返回空列表，第三次纠正旧约定。三个摘要按时间排在一起，仍可能重复或冲突。

Consolidation（整理）把选中的提取结果与已有记忆材料放在一起处理。因为多个任务可能修改同一工作区，第二阶段先领取全局整理任务，再接触共享文件。一次正常过程是：

1. 准备记忆工作区与用于比较的 Git 基线。
2. 选择受数量和保留条件限制的提取结果，同步对应摘要和该版本需要的输入。
3. 比较工作区变化，检查已有整理产物是否有效。
4. **无变化且产物有效**时可以直接结束；否则生成差异材料，启动整理 Agent。
5. 整理结束后检查状态、关闭实例、验证产物并确认所有权，再更新成功基线和任务状态。

这里的 Git 基线记录“上次确认成功的记忆工作区状态”，不是自动替用户项目提交代码。[源码：`phase2.rs` 的工作区比较与结束路径][src-phase2]。

| 判断信息 | 它回答什么 | 为什么不能独立决定成功 |
|---|---|---|
| 水位线 | 处理进度到哪里？ | 来源删除或文件损坏也可能需要整理 |
| 工作区差异 | 材料与成功基线相比变了什么？ | 无差异仍可能存在无效产物 |
| 产物校验 | 必需文件与格式是否有效？ | 有效格式不保证经验真实 |
| 当前所有权 | 仍由这个工作者负责吗？ | 模型报告完成不能替代负责权 |

所以不是“水位没变就跳过”，也不是“模型说完成就提交”。先看输入是否变化，再看产物和任务状态，才知道该继续哪一步。

<a id="writer-permissions"></a>
## 5. 整理 Agent 为什么需要专门的权限和结束检查

整理 Agent 的任务是更新记忆材料，不是继续修改分页项目。源码为它使用临时会话，关闭自身记忆生成和使用，清空 MCP 服务器，并关闭协作、应用及相关插件能力，避免整理工作继续派生更多整理任务。[源码：整理 Agent 配置][src-phase2]。

沙箱边界取决于父环境：使用 Codex 管理的权限配置时，整理分支限制写入到记忆根目录并关闭网络；父环境明确使用禁用沙箱或外部沙箱时，则保留相应选择。审批设为“不询问”只说明不等待交互批准，不代表资源访问无限制。

这与[工具篇的审批和执行环境](03-tool-lifecycle.md#permissions)是同一组职责：后台任务更需要可执行的权限边界，不能只靠提示词要求“别碰其他文件”。

结束时还可能遇到下面几种状态：

| 已发生的事 | 实现或恢复时要处理什么 |
|---|---|
| 模型报告完成，但产物无效 | 不能只凭完成文本标记成功 |
| 结束处理前租约丢失 | 旧工作者不能重置成功基线 |
| 整理实例关闭失败 | 源码保留已有租约直到过期，避免立即与新工作者竞争 |
| 基线已重置，数据库成功标记失败 | 记录这个中间失败，不宣称文件与数据库原子提交 |

[源码：结束处理、心跳与基线更新][src-phase2]提供这些判断的具体位置。

> ⚠️ **注意：产物有效与经验正确是两次检查。** 文件存在且格式正确，仍可能写着已经过期的测试命令；后续使用必须回到实际项目验证。

<a id="memory-reading"></a>
## 6. 新任务先读摘要，再按需取得详情

读取扩展取得所选版本的 `memory_summary.md`，按预算处理，形成开发者指令片段。文件不可读、为空或处理后不能形成有效内容时，不产生这份摘要指令。[源码：摘要读取与模板][src-prompts]、[扩展注入][src-extension]。

对分页任务，摘要可以让模型知道“存在一条相关测试经验”。模型随后寻找详情，取得目录和命令，再核对当前文件。**摘要负责提供入口，详细材料提供依据，当前任务决定经验是否适用。** 这是一种按需阅读方式，不是每次加载全部记忆。

启用专用工具后，`memories` 命名空间提供：

| 工具 | 用途 | 完成后仍需做什么 |
|---|---|---|
| `list` | 列出材料 | 选择相关项，不等于已经读过内容 |
| `search` | 查找线索 | 回读命中上下文 |
| `read` | 按范围取得内容 | 确认读取范围与适用条件 |
| `add_ad_hoc_note` | 添加补充笔记 | 区分新记录与已整理、已验证的经验 |

这些工具具有数量、行范围或 token 等约束。找不到材料、无效参数等可以反馈模型调整；该适配层将底层 I/O（输入输出）错误归入致命错误路径，不能把任何错误都当成换关键词即可恢复。[工具注册与参数处理][src-tools]、[名称与预算定义][src-read-lib]。

<a id="entry-version"></a>
## 7. 没有记忆出现时，沿启动、版本和读取条件排查

前面的流程解释了有合格输入时怎样处理。真实会话还必须通过入口检查，不能把“源码有这项功能”当成“当前一定在运行”。

| 层次 | 固定快照中的条件或行为 |
|---|---|
| 功能注册 | `memories` 属于稳定功能，但源码默认关闭 |
| 写入入口 | 排除临时会话、关闭功能和非根 Agent；还检查状态库、目录准备与额度 |
| 读取扩展 | 使用已有记忆要求 `use_memories` |
| 专用读取与笔记工具 | 在读取扩展条件成立后，还要求 `dedicated_tools` |

[功能注册表][src-features]、[写入入口][src-start]和[读取扩展][src-extension]分别承担这些检查；关闭读取不能仅凭这一点推出所有后台生成路径都没运行。

在 App Server 的已核验路径中，带输入的新 Turn 成功启动且主要执行环境配置后，会调用记忆后台任务入口；追加到已有轮次的输入被区分处理。因此它不是“每说一句话立刻存一条记忆”，也不能只凭函数名中的 `startup` 推断为进程启动时只执行一次。[真实调用方：`turn_processor.rs`][src-turn-processor]。入口启动异步工作后，当前交互与记忆产出仍有各自的完成状态。

版本也会改变材料位置和处理方式。写入侧按 `MemoryVersion::V1` 或 `V2` 选根目录，双写时分别处理；读取侧保留线程已绑定版本，避免初始摘要与后来读取来自不同命名空间。[版本选择][src-start]、[读取绑定][src-extension]。

<details>
<summary>按目录排障时再查：哪些产物与版本有关</summary>

| 材料 | 用途与边界 |
|---|---|
| 状态库中的提取结果 | 来源、提取内容与处理状态，供整理阶段选择 |
| `rollout_summaries/` | 从选中提取结果同步出的单段工作摘要 |
| `raw_memories.md` | V1 整理输入之一；V2 同步分支不重建它 |
| `memory_summary.md` | 读取侧的摘要入口，不能当作全部详细经验 |
| 详细记忆材料 | 按版本与实际文件结构读取，不强套统一文件清单 |
| `phase2_workspace_diff.md` | 给整理 Agent 的工作区差异，不是用户任务报告 |

V1/V2 的提取输入与输出处理也有分支，不只是目录名不同。读取侧采用不同摘要模板并处理片段字节上限。找不到某个熟悉文件时，先确认线程版本、目录和实际产物，再判断故障。[提取分支][src-phase1]、[同步分支][src-phase2]、[模板与截断][src-prompts]。

</details>

<a id="conflict-cleanup"></a>
## 8. 经验冲突或删除来源时，要明确改的是哪一层

项目 A 约定页码从 1 开始，项目 B 约定从 0 开始。A 的偏移公式在 A 中正确，在 B 中可能就是错误。搜索命中只说明找到了相关材料，不说明它适用于当前任务。

使用经验时，先核对项目、时间与条件，再检查当前明确约定、代码和测试；确认错误后，修正相应派生材料，避免下一次再次误用。这是建立在前述来源与读写结构上的使用原则，不是一个自动裁定所有冲突的事实数据库。

删除同样要分层：删除原始材料、让来源退出整理候选、移走同步摘要、修正整理后的经验，以及清理备份或日志，分别作用于不同对象。第二阶段会同步选中输入并处理材料变化，但不提供“删除一个来源就立即抹去所有介质上的派生内容”的通用保证。[整理同步与清理分支][src-phase2]。

> ⚠️ **注意：敏感信息的清理不能只看一个文件消失。** 需要明确保存范围、读取权限、保留期与派生清理路径。目录限制和输入过滤是具体防线，不是秘密永远不会被保存的证明。

<a id="memory-evaluation"></a>
## 9. 记忆有没有用，要看任务而不是文件数量

更多记忆文件或更多检索命中，都可能只是更多活动。真正的收益是帮助正确完成任务，同时没有引入错误经验。

| 教学对照条件 | 观察什么 |
|---|---|
| 同项目再次修边界问题 | 是否找到正确测试入口、保留公开接口，是否减少重复调查 |
| 换成从 0 编页的项目 | 是否核验新约定，而非直接搬用旧公式 |
| 旧经验错误，当前测试明确 | 是否根据当前证据纠正 |
| 禁用记忆作为对照 | 结果、工具次数与 token 成本如何变化 |

比较时固定任务、代码基线、模型设置和测试条件，记录记忆输入。结果正确性、错误经验引入与资源成本分别观察。上表是待运行的评测设计，不包含真实模型收益数字。

## 本篇小结

历史先经过提取形成候选经验，再由整理阶段更新共享材料；新任务从摘要进入，按需取得详情。开关、版本、任务所有权、产物校验和预算决定这条链是否真正生效。正确记住还要求经验适用、错误可修正、派生材料可维护。

## 🎯 面试怎么回答

**问：Codex 长期记忆怎样生成和使用？**

> 🎯 它将生成与读取分开：从合格历史提取候选经验，再与已有材料整理成可阅读的记忆；新任务先读摘要，再按需取得详情。后台任务有领取、租约、产物和版本检查，但经验是否正确仍要由当前任务证据验证。

**追问：没有变化是否就不用整理？**

> 🎯 不能只看进度水位。跳过整理还要确认工作区没有变化、产物有效；材料删除、产物损坏或失去任务所有权，都需要单独处理。

## ⚠️ 易错点回顾

- ⚠️ **历史不是经验：** 保留发生过什么，与提取可复用结论是不同处理。
- ⚠️ **启动不是写成：** 功能开启、后台任务启动、产物有效和读取成功分别确认。
- ⚠️ **命中不是适用：** 先核对项目与当前约定，再决定是否复用旧经验。

## 自测：判断材料应该怎样继续流动

**任务一。** 已开启记忆功能与 `dedicated_tools`，但关闭 `use_memories`。读取侧是否注入摘要、注册专用工具？能否据此断言后台提取没运行？

<details>
<summary>答案与解释</summary>

读取扩展条件不成立，不注入摘要，也不提供这组工具。后台生成有独立入口与条件，还要核对写入调用方、会话来源、状态库及任务状态，不能只根据读取配置推断。

</details>

**任务二。** 一次整理没有工作区差异，但产物无效；另一次模型报告完成，却已失去租约。两者能否标记成功？

<details>
<summary>提示</summary>

分别找出“无需整理”和“可以提交成功”还缺什么条件。

</details>
<details>
<summary>答案与解释</summary>

无差异跳过还要求产物有效，前者不满足；后者已经失去所有权，不能仅凭完成文本重置成功基线。两者都还要满足相应结束检查。

</details>

**任务三。** A 项目从 1 编页，B 项目从 0 编页，每页两项。用 `[10, 20, 30]` 设计一个最小检查，区分有用经验与错误迁移。

<details>
<summary>答案与解释</summary>

要求 B 的第 0 页返回 `[10, 20]`，观察 Agent 是否先核对 B 的约定，而非套用 A 的公式。这是适用范围和结果正确性检查，不是检索吞吐量测试；一次通过也不证明全部经验都正确。
