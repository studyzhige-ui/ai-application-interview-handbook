# 交付与复盘｜读懂整条执行证据

[← 上一章](06-memory-pipeline.md) · [本产品目录](README.md)

前六章的运行机制最后都要转成可检查的交付。本章用一段完整记录读法连起派发、执行、结果就绪、模型消费与结束，再回顾上下文、工具、协作和记忆。这里只做阅读推演，不要求新增项目或实验。

<a id="execution-trace"></a>
## 一段完整记录应该怎样读

以下是教学时序，不是实测日志。分页测试工具与模型流可能重叠，不能只按屏幕出现顺序判断工作耗时。

| 观察时刻 | 已建立的事实 | 谁消费它 |
|---|---|---|
| 本轮输入接纳 | 用户要求进入本轮，首步条件确定 | 请求构建器 |
| 工具调用派发 | 调用已登记，但可能仍在等连接或门控 | 工具运行时 |
| 进入执行门控 | 开始处理参数、Hook 和实际工具逻辑 | 处理器与审核链 |
| 返回进程 P | 命令仍运行，只有当前输出 | 后续轮询调用 |
| 进程退出，结果就绪 | 可以取得退出码与对应输出 | 等待收集的模型循环 |
| 流结束、在途结果收齐 | 本次调用结果进入后续历史 | 下一次模型请求 |
| 无后续且 Stop Hook 放行 | 本轮可以结束 | 客户端交付流程 |
| 相应存储屏障完成 | 记录达到该接口可恢复边界 | 重启后的读取流程 |

普通工具错误也能有“结果就绪”事件；致命错误没有同样的可回填结果。若取消时工具已到终态，运行时尽量收取真实结果，而不是覆盖成中止。因此诊断要分别量出派发等待、处理时间、结果就绪后等待模型收集的时间。[派发与结果就绪](https://github.com/openai/codex/blob/cda82a2c6853b484e0ba56d38f13902adfb2a6a1/codex-rs/core/src/tools/parallel.rs)

固定快照增加了采样、工具阻塞、压缩等阶段的追踪跨度，便于区分“模型慢”和“工具仍在收尾”。本地 Rollout Trace 是需显式开启的诊断机制，不能把源码中的观测点当作本次已经采集过的运行证据。[阶段观测](https://github.com/openai/codex/blob/cda82a2c6853b484e0ba56d38f13902adfb2a6a1/codex-rs/core/src/session/turn.rs)

<a id="completion"></a>
## 先说清什么叫完成，再检查系统提供了什么

分页任务的约定不仅是第一页正确，还包括参数合法性、空结果、返回新列表且不修改原输入。每个约定都需要相应证据，不能从一句“测试过了”反推全部要求已满足。

| 验收层 | 应检查的事实 | 常见误判 |
|---|---|---|
| 结果 | 返回值、异常和输入不变符合约定 | 第一页对了就忽略其他边界 |
| 过程 | 读取正确文件，测试确实启动并结束 | 进程标识或启动返回等于测试通过 |
| 安全与范围 | 只改允许文件，不删除断言、不越权写入 | 结果正确就抵消越权修改 |
| 资源 | 调用、token、等待与重试成本合理 | 调用更少就一定更好 |

正常完成时，证据大致这样形成：

```text
读取任务与测试 → 复现并解释失败 → 写入允许范围的补丁
                                        ↓
                         对当前代码运行同一测试
                                        ↓
                          查看退出结果与实际差异
                                        ↓
                         给出有证据的完成或未完成结论
```

这是一套任务验收方法，不是宣称 Codex 内置了必定阻止错误总结的验证器。公开循环、钩子和追踪提供执行与观察入口，具体完成条件仍由任务、代码和测试决定。[主循环：`run_turn`][src-turn]。

有限测试也不是软件正确性的数学证明。现有测试之外的边界若尚未检查，应保持可见，而不是用一串 PASS 把范围扩大。

<a id="task-evidence"></a>
## 把调用链放回分页修复

先读约定和原测试，再追实现的偏移与参数处理；修改允许范围内的代码后，在正确目录运行同一测试，最后核对差异。这条过程链需要不同证据：

| 动作 | 应取得的可检查内容 |
|---|---|
| 读取约定 | 页码、每页数量、非法参数、返回列表与输入不变规则 |
| 定位缺陷 | 旧表达式的实际结果及与预期的差异 |
| 写入补丁 | 允许文件中的真实改动，没有删除断言或无关修改 |
| 运行测试 | 测试确实启动、进程退出、结果对应当前代码 |
| 交付 | 差异和测试共同支持完成声明 |

并不是所有模型都必须按完全相同的工具次序操作，但这些事实不能由一段总结替代。[交付章](07-delivery-and-review.md#completion)解释这些证据怎样共同支持结论。

<a id="trace"></a>
## 排障时，沿记录找到动作，而不只读模型总结

如果模型声称测试通过，首先需要找到真实命令、目录、退出状态与输出，再检查这些结果有没有进入后续模型请求。

Rollout Trace（运行轨迹诊断）先记录原始事件与载荷引用，再离线归约。Reducer（归约器）将它们整理成线程、轮次、模型请求、工具调用、代码单元、终端活动及相互关系。[源码设计说明：追踪结构与不变量][src-trace]。

| 记录 | 适合回答什么 |
|---|---|
| 模型请求与响应 | 模型实际得到什么、生成什么？ |
| 工具与终端事件 | 调用是否派发，进程是否退出，输出是什么？ |
| Code Mode 代码单元与嵌套调用 | 哪段脚本触发哪次工具，哪些中间结果没交给模型？ |
| 父子 Agent 关系 | 任务发给谁，结果返回哪一个父线程？ |
| 持久历史 | 恢复可以从哪些已保存材料重建？ |

Code Mode 的调用方式已在[扩展章](03-extensions-and-discovery.md#discovery-code-mode)说明。在这里，重点是追到嵌套调用，而不是把脚本最后一句“执行失败”当作根因。

诊断包中存在原始输出，不代表模型收到同样字节；模型得到截断结果，也不能反推原始材料不存在。应沿实际引用检查。此本地追踪入口需要显式设置，采用尽力记录，与遥测分开；没有记录可能是未启用或记录失败，不能单凭缺日志断言没有动作。

> ⚠️ **注意：诊断包可能包含提示、工具参数、输出和路径。** 分享前检查敏感内容与授权范围；“本地诊断不同于遥测”不等于整个产品从不联网。

<a id="evaluation"></a>
## 比较方案前，先区分执行了哪一层验证

| 验证层 | 典型证据 | 不能替代什么 |
|---|---|---|
| 静态与语法检查 | 链接、源码路径、脚本编译 | 真实模型或工具运行 |
| 本地单元测试 | 分页返回值、异常、输入不变 | Agent 的调查、权限和选择能力 |
| 模拟模型或服务 | 固定响应下的顺序和错误分支 | 真实模型及服务故障特征 |
| 真实 Codex 任务 | 版本、配置、轨迹、差异、测试 | 所有并发与恢复条件 |
| 多连接与跨系统故障实验 | 中断、重复交付和恢复记录 | 未测试环境和负载 |
| 生产观察 | 有权限取得的指标与坏例 | 未采集范围的完整可靠性 |

上游存在测试，只说明有这段检查代码；运行后才构成本次执行证据。报告应分别记录失败、跳过、预期故障和未执行项。

方案比较也要保持条件一致。假设同一组 100 个教学任务，成功数从 60 增到 85，单任务耗时从 60 秒增到 120 秒：成功率增加 25 个百分点，每任务多等 60 秒。是否值得，要结合失败代价、允许等待与任务期限判断，不能只拿一个指标排名。这些是模拟数字，不是 Codex 实测。

另一个模型可以辅助评分，但应检查评分与人工认可结果是否一致。有可执行测试与可核对差异的部分，不应让一句模型评价替代证据。

<a id="failure-review"></a>
## 用一个坏例找到应该修哪一层

看一条**模拟时间线**：三次相同测试命令都因找不到解释器而失败，模型随后宣布“测试通过”。

先确认三次的实际退出结果：这里没有一次测试成功启动，因此不能讨论测试用例通过率。接着检查失败结果是否进入下一次请求，是否被截断、配错调用或在摘要里改写。最后检查模型为何原样重复、停止条件为何允许无证据结束。

这样可以把改进定位到执行环境、工具错误表示、上下文组装、停止验证或任务说明，而不是一开始就决定“再写一个更强提示词”。修复后用相同故障条件回归，观察是否仍会虚报完成。

<a id="review-map"></a>
## 第二遍回顾：沿同一条任务链找证据

```text
任务及验收条件
    ↓
指令、历史、环境和工具形成单次请求
    ↓
模型提出动作 → 参数与权限检查 → 执行
    ↓
结果回填并完成相应持久化
    ↓
继续采样、必要压缩或结束
    ↓
差异与测试支持任务结论

发生中断：恢复记录 → 核对外部状态 → 决定继续或重试
增加协作：交付收据 → 实际执行 → 结果验收 → 父任务整合
后续复用：合格历史 → 提取与整理 → 新任务按需读取记忆
```

Code Mode 增加脚本与嵌套调用层，子 Agent 增加任务交接层。它们都应能放回这条链，解释输入在哪里、动作由谁完成、证据怎样返回。

## 多角度回顾

### 请求与上下文：本篇小结

同一任务会发出多次请求，工具结果使下一次判断获得新依据。Codex 用运行历史组织过程，用 StepContext 固定单次请求的条件，再处理指令刷新、状态差异、调用配对、容量和压缩。模型输入、宿主状态、持久历史与外部现实各有职责。

### 请求与上下文：🎯 面试怎么回答

**问：Codex 怎样管理长任务上下文？**

> 🎯 核心是把“持续历史”和“本次请求”分开。每次请求固定设置、环境与工具视图，再把必要历史和结果交给模型。长到需要压缩时，替换历史并补回继续任务所需的约束，而不是不断追加文本。正确性要同时检查结构配对和语义保留。

**追问：恢复历史为什么不代表任务已经恢复正确？**

> 🎯 历史说明记录过什么，文件和远端服务说明实际发生过什么。动作已完成但结果未记录时，两者可能不同；恢复后要先核对实际状态，再决定继续或重试。

### 请求与上下文：⚠️ 易错点回顾

- ⚠️ **Turn 与一次采样混淆：** 先按调用—结果—再次请求数清步骤，一轮可以包含多次采样。
- ⚠️ **快照与权限混淆：** 原快照保留解释依据，动作仍需通过取消、审批和环境限制。
- ⚠️ **压缩与追加混淆：** 压缩产生替换历史；还要检查约束、未完成工作和比较基线。

### 请求与上下文：自测：改变条件，再推导下一步

**任务一。** 请求 A 捕获 P1 与 T1；模型生成期间切到 P2。A 的调用按哪份视图解释？下一次请求用什么？旧调用是否必定执行？

<details>
<summary>提示</summary>

分别判断已经发送的内容、下一次准备的内容和实际执行许可。

</details>
<details>
<summary>答案与解释</summary>

A 保留原 StepContext，下一次可以捕获 P2 的新环境与目录。原快照不能倒改，但动作可以因取消、审批或环境约束被阻止；一致解释不等于必须执行。

</details>

**任务二。** 历史只有调用 `c7`，磁盘文件却已变化；规范化补出 `aborted`。它证明什么？恢复时至少检查什么？

<details>
<summary>答案与解释</summary>

它只修复可发送的调用—结果关系，不证明未发生修改。读取文件或差异确认实际改动，再核对可靠测试记录或运行相关测试，分别判断“改过”和“改对”。

</details>

**任务三。** 教学窗口 40,000 token，生成预留 8,000，安全余量 2,000，指令与工具占 7,000。历史与新结果可规划多少？容量足够能否继续沿用过时约定？

<details>
<summary>答案与解释</summary>

`40,000 − 8,000 − 2,000 − 7,000 = 23,000 token`。这是教学预算，实际按模型核验。容量只说明装得下，过时约定仍要更新。

</details>

### 工具与扩展：本篇小结

工具链先把模型调用交给正确实现，完成参数、权限、执行与结果回填；工具多了以后，再通过注册、暴露和搜索控制入口。Code Mode 组织多个动作，Skill 提供工作方法。钩子、并行与取消都作用在这条已有链上，各自处理不同的状态。

### 工具与扩展：🎯 面试怎么回答

**问：Codex 的工具调用为什么不只是模型输出 JSON？**

> 🎯 JSON 只表达调用意图。宿主还要用该请求的工具视图找到实现，检查参数与许可，再执行并按调用编号回填结果。发现、授权、执行成功和任务通过验收是不同阶段，不能互相替代。

**追问：工具返回错误后，怎样决定是否重试？**

> 🎯 先看失败位置。执行前的参数问题可以修正，明确禁止不能绕过；执行后丢失结果或被钩子阻止，要先核对实际副作用。特定沙箱重试还必须满足权限与审批条件。

### 工具与扩展：⚠️ 易错点回顾

- ⚠️ **搜索不是执行：** 命中工具说明后，还要构造调用并读取实际结果。
- ⚠️ **可见不是获准：** 三种暴露入口只决定怎样找到或调用，具体动作仍受权限约束。
- ⚠️ **结果错误不等于动作未发生：** 先定位前置阻止、执行失败还是后置拒绝，再判断下一步。

### 工具与扩展：自测：用失败位置判断下一步

**任务一。** A 为 `Deferred`，B 为 `DeferredModelOnly`；它们都能被搜索。在 Code Mode 已启用且其他策略允许时，脚本能否调用两者？搜索不到 A 时先查哪几个层次？

<details>
<summary>答案与解释</summary>

A 的暴露方式允许嵌套调用，B 不允许。搜索不到 A，先核对模型与命名空间是否支持搜索，再查本次路由和延迟暴露，最后看查询与工具名称、描述是否匹配；还可继续查来源就绪和策略过滤。不能由一次搜索失败直接推断连接损坏。

</details>

**任务二。** 补丁已写入，后置钩子阻止结果。模型只看到错误，安全下一步是什么？它与前置钩子阻止有什么区别？

<details>
<summary>提示</summary>

先标出处理函数有没有运行。

</details>
<details>
<summary>答案与解释</summary>

先读实际差异并验证当前代码，再决定继续。后置钩子运行时动作已经可能发生；前置阻止时本次处理函数尚未执行。这个区别只针对本次调用，不代表此前从未发生任何动作。

</details>

**任务三。** A、B 支持并行，C 不支持，三者共用一个门控；另一进程 D 正在改同一文件。说明互斥范围，并判断“门控通过就没有文件冲突”是否成立。

<details>
<summary>答案与解释</summary>

A、B 可共同持有读锁，C 的写锁与它们互斥。D 不受该门控保护；并行声明本身也不能证明业务资源无冲突，因此还需修改范围与最终差异检查。

</details>

### 执行与交付：本篇小结

持续执行需要资源归属、明确保存边界与失败后的真实状态核对。协作和扩展增加了参与者，却没有替换任务验收。模型总结、工具返回、持久记录和测试各自支持不同结论，只有证据与目标匹配时才能宣布完成。

### 执行与交付：🎯 面试怎么回答

**问：Codex 比“模型加几个工具”多了什么工程工作？**

> 🎯 它需要在多次请求之间管理资源、权限、历史和执行状态，长任务还要压缩、保存与恢复。关键不是组件更多，而是动作、记录和验收分别有明确边界；协作增加交接后，仍需用实际差异、测试和轨迹证明结果。

**追问：有持久化和重试，为什么仍会重复执行？**

> 🎯 外部动作可能先完成，内部成功记录还没保存就崩溃。恢复历史不一定知道现实状态，所以要先查询已有动作或差异，再按业务幂等条件决定是否重做；flush 只能确认对应存储的写入边界。

### 执行与交付：⚠️ 易错点回顾

- ⚠️ **接纳不是完成：** 进程编号、子线程收据和排队返回，都要继续核对实际终态。
- ⚠️ **正常关闭不是崩溃恢复：** 前者有清理机会，后者只能依赖已经保存且可读取的材料。
- ⚠️ **单元测试不是 Agent 验证：** 分页函数正确，不证明模型调查、授权、恢复与协作都正确。

### 执行与交付：自测：给出证据，而不是一个结论

**任务一。** 子 Agent 已接纳输入，但父 Agent 没收到结果，子 Agent 当前未加载。能否标成完成？应补查什么？

<details>
<summary>答案与解释</summary>

不能。核对子任务运行与持久记录、实际完成状态和输出证据，必要时按支持的方式加载或观察；接纳、加载、处理和验收互不等同。拿到完成文本后还要核对差异与测试。

</details>

**任务二。** 外部记录已经写入，内部成功结果未持久化就崩溃。恢复只见未确认调用，处理顺序是什么？

<details>
<summary>答案与解释</summary>

先用已有标识或查询条件核对外部状态，再补记录、继续或安全重试。无法核实时保留未知状态。`flush_thread` 只确认线程存储，不把外部服务纳入同一个事务，也不自动提供业务幂等。

</details>

**任务三。** 报告说：“读过上游恢复测试，Python 分页参考答案通过，因此 Codex 断线恢复与生产安全已验证。”应如何改写？

<details>
<summary>答案与解释</summary>

上游测试属于代码阅读；Python 参考答案属于本地单元测试。真实 Codex 运行、多连接故障、跨系统恢复与生产安全没有由此得到验证，应分别列为未执行，并补充相应版本、配置、轨迹和实验记录后再判断。

</details>
