# AI Backend Engineering｜面试易错点

> 这些错误大多来自“把局部机制说成绝对规律”。Production 面试最重要的是边界。

## Network / Protocol

1. ❌ UDP 一定比 TCP 快。 → ✅ Trade-off 取决于可靠性、拥塞控制、应用语义和网络环境。
2. ❌ HTTP/3 用 UDP，所以不可靠。 → ✅ QUIC 在 UDP 上实现可靠 Stream、拥塞控制和安全机制。
3. ❌ HTTPS 就是 HTTP + RSA。 → ✅ TLS 通过证书/密钥交换建立安全会话，数据主要使用对称加密。
4. ❌ TCP 可靠，所以业务请求不会重复。 → ✅ Response 丢失后的 Retry 仍会重复 Side Effect。
5. ❌ Keep-Alive 就是不关连接。 → ✅ 连接仍受 Idle/Lifetime/Server/Network 限制。
6. ❌ SSE 比 WebSocket 低级。 → ✅ 通信方向不同，Server→Client Streaming 时 SSE 往往更简单。
7. ❌ WebSocket 连接就是 Agent Session。 → ✅ Transport Connection 与 Durable Run/Session State 应分离。
8. ❌ Reconnect 就等于 Resume。 → ✅ Resume 需要 Event Cursor / Durable State。

## Concurrency / Pool / Backpressure

9. ❌ Coroutine 很轻，所以可以无限并发。 → ✅ Downstream、Pool、Memory、Rate Limit 仍有限。
10. ❌ Thread Pool 越大吞吐越高。 → ✅ 过多 Thread 会增加切换、内存和下游压力。
11. ❌ I/O 任务线程数按 CPU 核数×2。 → ✅ 要结合等待比例、下游容量和 Load Test。
12. ❌ 无限 Queue 更不容易丢任务。 → ✅ 会把 Overload 变成长等待、OOM 和 Timeout。
13. ❌ Pool 满就调大。 → ✅ 可能是 Query 变慢或 Connection Leak 的症状。
14. ❌ DB Pool 20 就是整个服务最多 20 连接。 → ✅ 多 Worker/Pod 会乘法放大。
15. ❌ Semaphore 就是 Rate Limit。 → ✅ 它限制同时并发，不限制单位时间总量。
16. ❌ 429 说明系统设计失败。 → ✅ 过载时明确拒绝是保护机制。
17. ❌ Queue 可以永远吸收突发流量。 → ✅ 长期生产率大于消费率一定积压。
18. ❌ Backpressure 就是加 MQ。 → ✅ MQ 只是 Buffer，仍需限流、Reject、Degrade 和 Consumer Capacity。

## Timeout / Retry / Resilience

19. ❌ 一个 30s Timeout 可以覆盖所有阶段。 → ✅ Connect/Pool/Read/End-to-end 语义不同。
20. ❌ Timeout 后任务已经停止。 → ✅ Downstream 可能继续执行。
21. ❌ 每层 3s Timeout = 全链路 3s。 → ✅ 多层会叠加，应该传播 Deadline。
22. ❌ 500 都能 Retry。 → ✅ 必须按错误语义分类。
23. ❌ Retry 三次就很安全。 → ✅ 全服务大量请求仍可能形成 Retry Storm。
24. ❌ Exponential Backoff 不需要 Jitter。 → ✅ 同步重试波峰仍可能出现。
25. ❌ 每层自己 Retry 更可靠。 → ✅ 会产生乘法放大。
26. ❌ Circuit Breaker 会修复下游。 → ✅ 它只是快速停止调用，给双方恢复空间。
27. ❌ Fallback 一定等价于 Primary。 → ✅ Schema、质量、成本、行为可能不同。
28. ❌ Failover 有备用实例就够了。 → ✅ Backup Capacity、State、Routing、Health 也必须验证。

## Idempotency / Side Effect

29. ❌ POST 天生不能幂等。 → ✅ 可以通过业务 Operation Key 设计幂等。
30. ❌ UUID 就是 Idempotency Key。 → ✅ 关键是同一逻辑操作 Retry 时保持同一 Key。
31. ❌ Lock 能保证幂等。 → ✅ Lock 解决并发执行权，不解决后续重复请求。
32. ❌ 同一个 Idempotency Key 不需要比较参数。 → ✅ 否则可能错误复用不同业务请求。
33. ❌ `if not exists: execute` 就能去重。 → ✅ 并发下有 Race，需要原子 Claim / Unique Constraint。
34. ❌ Exactly-once 可以轻易跨 MQ+DB+External API 保证。 → ✅ 要明确语义边界，通常依赖幂等与对账。
35. ❌ 请求 Timeout 就说明 Side Effect 没发生。 → ✅ 这是 Unknown Outcome。
36. ❌ 幂等记录可以永久保存无需治理。 → ✅ 要定义重复窗口和 Retention。

## MQ / Kafka / Long Task

37. ❌ 上 MQ 就不会丢消息。 → ✅ Producer/Broker/Consumer 都有 Failure Window。
38. ❌ Ack 等于整个业务事务完成。 → ✅ Ack 只代表消息消费边界推进。
39. ❌ At-least-once 等于重复一定发生。 → ✅ 表示可能重复，因此 Consumer 必须能承受。
40. ❌ DLQ 就处理完了。 → ✅ 仍需 Alert、Root Cause、Repair、Replay Policy。
41. ❌ Kafka Topic 全局有序。 → ✅ 通常只保证 Partition 内顺序。
42. ❌ Consumer 越多越快。 → ✅ 传统 Group 受 Partition 数限制。
43. ❌ Lag 高直接加 Consumer。 → ✅ 先看 Partition Skew、Downstream、Rebalance、Poison Message。
44. ❌ Replay Kafka 历史 Event 不会有副作用。 → ✅ External Action 可能重复。
45. ❌ Heartbeat 就是 Checkpoint。 → ✅ Heartbeat 只说明 Worker 活着，Checkpoint 记录执行状态。
46. ❌ Lease 防止所有重复执行。 → ✅ 旧 Worker 复活仍可能重复 Side Effect。
47. ❌ Cancel Request 就能撤销已经发出的外部操作。 → ✅ 需要业务补偿/状态查询。
48. ❌ BackgroundTasks 可以替代 Durable Worker。 → ✅ 进程重启后易失。

## Consistency / State

49. ❌ 先删 Cache 再写 DB 一定正确。 → ✅ 并发 Reader 可能把旧值回填。
50. ❌ 先写 DB 再删 Cache 就强一致。 → ✅ 删除失败仍有 Stale Window。
51. ❌ 延迟双删是万能答案。 → ✅ Delay、Crash、第二次失败都存在。
52. ❌ 最终一致性就是“过会自己好”。 → ✅ 必须有 Retry/CDC/TTL/Reconciliation 等收敛机制。
53. ❌ Compensation 就是反向 SQL。 → ✅ 它是新的业务动作。
54. ❌ Redis 比 MySQL 快，所以 Runtime/业务状态都放 Redis。 → ✅ 先定义 State Ownership 和 Durability。
55. ❌ Agent Checkpoint 可以代替业务数据库。 → ✅ Runtime State 与 Business Truth 边界不同。
56. ❌ Cache 丢了不能恢复也没关系。 → ✅ 那它实际承担了 Source of Truth 职责。

## Auth / Routing / Deployment

57. ❌ Authentication = Authorization。 → ✅ 一个确认身份，一个判断权限。
58. ❌ JWT 就等于无状态认证系统。 → ✅ Revocation/Refresh/Permission/Device/Key Rotation 仍需设计。
59. ❌ Prompt 可以做 Permission。 → ✅ Server Policy 才是硬边界。
60. ❌ Sticky Session 就是多实例 Session 解决方案。 → ✅ 实例故障/扩缩容仍有问题。
61. ❌ Service Discovery 和 Load Balancing 是一回事。 → ✅ 一个发现实例，一个选择实例。
62. ❌ Stateless Service 完全没有本地状态。 → ✅ 仍有 Pool/Cache/In-flight，只是不拥有唯一长期业务事实。
63. ❌ UUID 永远不适合作主键。 → ✅ 要结合 DB、写入局部性、访问模式和版本方案。
64. ❌ Docker 就是轻量 VM。 → ✅ 通常共享 Host Kernel，隔离模型不同。
65. ❌ Kubernetes 自动让应用高可用。 → ✅ 应用级 Timeout/Idempotency/State 仍需自己设计。
66. ❌ Readiness 和 Liveness 可以写同一个“所有依赖都健康”。 → ✅ 语义不同，错误 Liveness 会制造重启雪崩。
67. ❌ 多 Pod 一定提高系统容量。 → ✅ DB/Provider 等共享下游可能更早饱和。
68. ❌ Rolling Update 自动保证兼容。 → ✅ DB/Event/API Schema 仍需向后兼容。

## Observability / Operations / Security

69. ❌ 日志越多越可观测。 → ✅ 需要结构化、可关联、可查询、无敏感数据。
70. ❌ 平均延迟 200ms 说明体验很好。 → ✅ P99 可能极差。
71. ❌ Trace ID 可以替代 Task ID。 → ✅ Trace 是遥测链路，Task/Run 是业务/执行身份。
72. ❌ CPU 高就直接扩容。 → ✅ 先定位 workload / loop / GC / retry / change。
73. ❌ Linux used memory 高就是内存泄漏。 → ✅ Page Cache、Allocator、Working Set 都要区分。
74. ❌ `rm` 大日志一定释放磁盘。 → ✅ deleted-but-open file 仍占空间。
75. ❌ Host 有空闲内存，所以 Container 不会 OOM。 → ✅ cgroup limit 独立约束。
76. ❌ Dynamic Config 越灵活越好。 → ✅ 错配置可瞬间全量扩散，需要 Version/Validate/Rollback。
77. ❌ Microservice 比 Monolith 更高级。 → ✅ 是 Trade-off，不是成熟度排名。
78. ❌ Canary 只看 5xx。 → ✅ AI 还要看质量和成本指标。
79. ❌ ORM 自动消灭 SQL Injection。 → ✅ Raw SQL / unsafe expression 仍可能出问题。
80. ❌ CORS 就是 CSRF 防护。 → ✅ 两者威胁模型不同。
81. ❌ URL 字符串 allowlist 就足够防 SSRF。 → ✅ DNS/Redirect/Network Egress 仍需防护。
82. ❌ Container 就是强安全沙箱。 → ✅ privileged、host mount、kernel 等仍有风险。
83. ❌ Secret 放 Environment 就完成 Secret Management。 → ✅ 还要 Provision/Rotate/Revoke/Audit。
84. ❌ LLM Output 是系统内部生成所以可信。 → ✅ 仍是 Untrusted Data，必须校验授权。

## Cross-language

85. ❌ Spring DI 与 FastAPI Depends 完全等价。 → ✅ 解决相似问题，但容器和生命周期机制不同。
86. ❌ Java HashMap 的树化机制就是 Python dict。 → ✅ 只能类比哈希表概念，不能混淆实现。
87. ❌ ThreadLocal 在线程池里会自动清理。 → ✅ 必须显式 remove/clear。
88. ❌ JVM OOM 就是 Heap 不够。 → ✅ Direct/Metaspace 等也可能耗尽。
89. ❌ Goroutine 就是 OS Thread。 → ✅ Go Runtime 把大量 G 调度到有限 M 上。
90. ❌ Channel 可以代替 Kafka。 → ✅ 一个是进程内并发原语，一个是分布式消息系统。
