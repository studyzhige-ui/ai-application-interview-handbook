## 1. 从浏览器输入 URL 到返回结果，中间发生了什么？

先区分名称解析、连接、TLS 身份与加密、HTTP 请求路由、应用处理和响应。已有连接可以复用，不是每次都重新握手。最后还要区分业务是否已提交与客户端是否收到响应；网关超时不能证明业务未执行。

## 2. 前端要展示用户最近一组通知，为什么选择 WebSocket，而不是轮询？

先确定变化频率、可接受延迟和是否双向交互。低频变化可以轮询，单向持续推送可用 SSE，需要双向交互再考虑 WebSocket。无论哪种协议，都需用户隔离、稳定事件身份和可查询状态；断线重连以后依据保存窗口补发或返回快照，而不是只把连接重新建立。

## 3. 线程池如何配置，异步为什么还会把服务拖慢？

先辨别计算与等待、是否阻塞事件循环，再限制执行者、已接纳任务和下游资源。线程池大小不是数据库容量，信号量也不自动限制已经创建的等待任务。超时不一定停止线程，应在真实工作终结时归还并发名额。

## 4. 怎样防止一个用户拖垮模型服务？

先约束可接纳的输入大小、请求速率、在途任务和模型预算，再按用户或团队公平分配。共享队列满时要拒绝或有界等待，失败时也保留明确策略。限流器失联选择放行还是拒绝，应按业务风险决定，不能把故障策略当成默认正确。

## 5. 工具超时后是否应该重试？熔断和降级有什么不同？

先判断错误是否可能恢复、剩余总预算是否足够，以及操作是否可安全重放。只在明确一层做有限次数退避重试，避免多层放大。熔断暂时减少对故障依赖的调用，降级改变可提供的能力；切换供应商仍需核对结果未知的副作用。

## 6. 接口幂等、Redis 锁和 Kafka 消费幂等分别保证什么？

先为同一业务动作定义稳定身份和参数绑定。本地修改用唯一约束与事务形成防重边界，重复交付查回已有结果。锁只协调谁可以尝试执行，租约失效不会杀掉旧工作者；Kafka 的生产或事务语义也不会自动覆盖外部 API 和数据库。

## 7. 消息已经确认了，任务为什么还可能重复或丢失？

先问是谁确认了什么：生产确认、消费确认和业务提交是不同事件。业务提交后确认丢失会重复，业务完成前确认可能使后续失败无法靠消息重投恢复。任务与通知意图可通过本地 Outbox 同时提交，但转发者和消费者仍要防重、重试和核对。

## 8. Kafka 积压如何处理，增加消费者一定有效吗？

对传统分区消费组，先看分区数、键分布、处理耗时和下游瓶颈；同组消费者不能任意共同处理同一分区。并行处理还要保证只提交已经安全完成前缀之后的位置。增加消费者若超过可分配分区或挤压下游，不会自然提高有效吞吐。共享组是另一种交付模型，不能照搬传统分区独占结论。

## 9. 进程重启后，长任务怎样继续，如何处理失败的中间文件？

保存任务身份、固定输入、进度和结果位置，用消息或扫描重新发现。领取和完成都校验状态与代际，业务进度与检查点保持可重放关系。临时文件不能冒充已发布结果；完整校验后发布引用，按活跃任务和保留策略清理孤儿与失败产物。

## 10. MySQL 与 Redis 不一致怎么办？JWT 能直接解决多实例会话吗？

## 11. SQL 变快但接口仍慢，Linux 和 Kubernetes 该看什么？

先用同一请求的时间线分开排队、连接等待、SQL、模型和响应，结合成功率、吞吐与尾延迟判断瓶颈。进程层再查 CPU、内存、I/O、连接和文件描述符，容器层核对配额。探针决定路由或重启，不修复慢查询，也不能代替长任务恢复。

## 12. Java、Spring、Go 的题与通用后端机制怎样对应？

先说共同问题，再说明实现差异：Spring 容器管理依赖与作用域，代理调用影响横切逻辑是否生效；Java 同步器和并发容器保护具体共享状态，ThreadLocal 需要在复用线程中正确清理；JVM 内存区域不只有堆；Go 用 G/M/P 调度 goroutine，channel 是进程内通信而不是持久 MQ。
