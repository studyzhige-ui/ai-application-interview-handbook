# Backend 机制实验

[模块主页](../README.md) · [复习与综合自测](../review/README.md)

这些实验把“看起来失败”和“状态真的改变”分开观察。它们不启动 Web 服务、真实 MQ、Redis、MySQL、Kubernetes 或外部支付系统，也不需要密钥。

## 环境与运行

需要 Python 3.13，使用标准库 `sqlite3`、`unittest` 和线程池。教材按 Python 3.13 行为编写；本轮执行环境是 Python 3.13.5、SQLite 3.46.1。SQLite 的单写者串行化不等同于 InnoDB 行锁，实验结果不能外推为 MySQL 性能结论。

在仓库根目录依次运行：

```bash
cd curriculum/03-backend-engineering
python examples/backend_lab.py
python -m unittest discover -s examples -p "test_*.py" -v
python examples/sync_snippets.py
```

第一个命令进入模块，第二个运行演示，第三个运行测试，第四个检查正文片段与统一实现是否相同。最后一项默认只检查；维护者修改统一实现后可使用 `python examples/sync_snippets.py --apply` 更新正文片段，再重新检查和测试。

## 初始条件、动作与预期结果

演示为每次运行创建独立临时目录和空数据库。输入是团队 `team-a` 的 `doc-42` 及同一操作键；没有上一次运行留下的行。先保存文档，再使用同键同参数重试，随后演示旧、新两个任务领取代际的完成写入。

```text
第一次: {'doc_id': 'doc-42', 'version': 1}
同键重试: {'doc_id': 'doc-42', 'version': 1}
文档数/操作数/事件数: 1 1 1
代际: 1 2
旧工作者写回: False
新工作者写回: True
```

第一、二行是返回给调用者的结果；第三行是数据库中真实行数，不是“打印两次所以执行两次”。文档、操作结果与 Outbox 在同一事务提交，同键重试查回原结果。后两行是条件修改是否改变一行，False 不表示工作者的所有外部动作已被撤销。

演示结束会关闭连接、删除自己的临时目录；线程池测试会等待受控工作终结后关闭线程。每个测试也创建独立目录，反复运行不会污染下一次。`init_db(path)` 本身只建表，不清空已有数据库；手动调用时请另建测试路径，不要指向业务文件。

## 实验与正文的对应

| 观察对象 | 真实执行还是模拟 | 正文位置与可检查结果 |
|---|---|---|
| 有界线程池 | 真实 Python 线程与 Future | 并发章：调用方超时后，线程未结束，接纳名额仍占用 |
| 令牌补充与剩余预算 | 显式逻辑时间模型 | 背压、超时章：修改时刻和成本，预测返回值；不是分布式限流器 |
| 本地事务防重 | 真实 SQLite 文件与事务 | 幂等章：同键同参数只保留一个文档版本和一个事件；不同参数冲突 |
| 六个并发调用 | 六个独立连接、同一 SQLite 文件 | 唯一键与事务保证逻辑结果一致；不证明行级并发吞吐 |
| 另一个进程提交后读取 | 真实子进程正常提交、退出，父进程读取 | 证明跨进程读取提交数据，不是强杀、断电或磁盘故障实验 |
| 旧工作者完成写入 | 真实条件 SQL；逻辑租约时钟 | 任务章：过期或旧代际被拒绝，仅保护此任务记录 |
| 外部动作后本地失败 | 内存 FakeProvider 反例 | 幂等章：重复调用可能产生两次副作用；未测试真实供应商 |
| 缓存旧值回填与版本丢失 | Python 容器中的故障时间线 | 一致性章：展示反例，不等于运行 Redis 与 CDC 系统 |

## 改变条件再判断

把工作线程的调用方等待时间缩短，预测总在途数是否随之减少。把同一操作键的内容改掉，预测它应该创建新版本还是拒绝冲突。将任务完成时刻设置为租约截止之后，预测即使尚无新领取者时旧写入能否成功。

先写预测再运行相应测试；不要为得到某个数字而修改实现。完整代码在 [backend_lab.py](backend_lab.py)，测试在 [test_backend_lab.py](test_backend_lab.py)。它们不包含生产任务系统必需的实际发布器、权限服务、时钟协议与跨系统核对流程。文档保存函数也未实现多人编辑的预期版本冲突检查；新键生成新版本不等于防止旧编辑覆盖，具体区别见幂等章。
