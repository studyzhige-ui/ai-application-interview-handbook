# Vector Database｜面试易错点

> 这些错误很多不是“完全不会”，而是把一句口诀说得太绝对，导致一追问就露出边界混淆。

---

# 一、Vector / Metric

## 1. “Embedding 就是 Vector DB”

错误。

```text
Embedding Model
→ 生成 Vector

Vector DB
→ 存储 / Index / Search / Filter / Lifecycle
```

模型和基础设施是两层。

---

## 2. “维度越高一定越好”

错误。

Dimension 增加也会带来：

- Memory；
- Storage；
- Distance Compute；
- Network；
- Index Build Cost。

表达能力和系统成本必须一起看。

---

## 3. “文本向量一定用 Cosine”

错误。

Metric 取决于模型训练 / 推荐口径、Normalization 和 Index 支持。Cosine、Dot Product、L2 不能脱离向量处理方式讨论。

---

## 4. “Cosine 和 Dot Product 永远一样”

错误。

只有在特定 Normalization 条件下，它们的排序关系才可能等价或接近。

---

## 5. “距离越大越相似”

要看 Metric。

```text
Similarity Score：通常越大越相似
Distance：通常越小越接近
```

不同产品 API 返回值语义也可能不同，不能只看数字大小。

---

# 二、Exact / ANN

## 6. “ANN 就是不准确的搜索”

过度简化。

ANN 是通过 Index / Search Strategy 少探索候选，允许可控 Recall Loss 来换 Latency / Cost。

---

## 7. “数据量大就绝对不能 Exact Search”

也不绝对。

还要看：

- Hardware；
- QPS；
- Dimension；
- Filter 后候选规模；
- Batch Search；
- SLA。

Exact 仍然常作为 Ground Truth 和小规模方案。

---

## 8. “ANN 的 Recall 就是 RAG 最终 Recall”

错误。

ANN Index Recall 只是基础设施层指标。RAG 还受 Chunk、Embedding、Query Rewrite、Hybrid、Rerank 等影响。

---

# 三、HNSW

## 9. “HNSW 是树”

错误。

它是 Hierarchical Navigable Small World **Graph**。

---

## 10. “HNSW 多层的作用只是省内存”

错误。

多层最核心是提高导航效率：高层做粗粒度长距离跳转，底层做局部精搜。

---

## 11. “M 越大一定越好”

错误。

M 增大通常可能改善连接丰富度和 Recall，但也增加 Memory、Build Cost 和搜索成本。

---

## 12. “efSearch 越大越快”

通常相反。

更大的搜索候选宽度通常提高 Recall，但增加 CPU / Latency。

---

## 13. “efConstruction 只影响查询速度”

错误。

它主要影响 Build 阶段候选搜索宽度、图质量和 Build Cost；更好的图也可能间接改善查询质量。

---

## 14. “HNSW 适合所有规模和所有写入模式”

错误。

要看 Memory、更新/删除、Build、Filter、多租户和产品实现。

---

# 四、IVF / Quantization

## 15. “IVF 就是 KMeans”

不完整。

KMeans 常用于训练 coarse centroids，但 IVF 更完整的概念是：

```text
Coarse Partition
→ Inverted Lists
→ Query Probe 部分 Lists
```

---

## 16. “nlist 越多越好”

错误。

过多 partition 可能增加训练、管理和候选不均衡问题；要结合数据规模和分布。

---

## 17. “nprobe 越大越快”

通常相反。

扫描更多 Lists 往往 Recall 更高，但查询成本更高。

---

## 18. “PQ 是另一种相似度函数”

错误。

PQ 是 Vector Quantization / Compression 方法，用短编码近似原向量，降低 Memory / Storage 和近似距离计算成本。

---

## 19. “压缩只有好处”

错误。

Quantization Error 会损失距离精度，可能影响 Recall / Ranking。

---

# 五、Index Selection

## 20. “HNSW 一定比 IVF 好”

错误。

Index Selection 要看：

```text
Scale
Recall
Latency
Memory
Build Cost
Update Pattern
Filter
Hardware
```

---

## 21. “面试问 Index 选型就背参数”

不够。

应该先讲工作负载，再讲算法，再讲参数和 Benchmark。

---

## 22. “一个环境调好的参数可以永久复用”

错误。

Dataset Size、Data Distribution、Filter、Hardware、QPS、Embedding Model 变化都可能改变最优参数。

---

# 六、Metadata / Filter

## 23. “Metadata Filter 和 SQL WHERE 完全一样”

概念上都做条件过滤，但 Vector DB 里 Filter 与 ANN 的执行顺序和 Index 结合方式会直接影响 Recall / Latency。

---

## 24. “Post-filter 不影响结果质量”

错误。

ANN 先取 K 个再过滤，可能删掉大量结果，导致最终候选不足。

---

## 25. “Tenant Isolation 用 tenant_id 字段就够了”

危险。

还需要 Query Layer 强制注入、权限控制、测试和审计；高风险场景可能用独立 Namespace / Collection / Partition。

---

## 26. “Partition 越多查询越快”

错误。

过度分区会增加管理、路由、Small Segment 和 Fan-out 成本。

---

# 七、Update / Lifecycle

## 27. “Vector Update 就是在原向量上改几个 float”

通常不是这么理解。

业务更新常意味着：

```text
Source Change
→ Re-embedding
→ Upsert / New Version
→ Old Version Cleanup
```

ANN Index 的更新语义还取决于产品实现。

---

## 28. “Delete 一定立即物理删除”

错误。

可能先 Tombstone / Logical Delete，再等待 Compaction / Rebuild。

---

## 29. “Embedding Model 换版本不影响旧 Index”

非常危险。

新旧模型可能属于不同 Vector Space，混搜未必有意义。需要 Version、Re-embedding 和 Migration Plan。

---

## 30. “Rebuild 只影响后台，不影响线上”

不一定。

Rebuild 会消耗 CPU / Memory / Disk / Network，也可能和在线查询抢资源，因此需要 Blue-Green / Shadow / Throttling 等策略。

---

# 八、Distributed / Performance

## 31. “Replica 和 Shard 是一回事”

错误。

```text
Shard：拆数据
Replica：复制数据
```

目标不同。

---

## 32. “Shard 越多吞吐越高”

不一定。

更多 Shard 也意味着：

- Router；
- Fan-out；
- Network；
- Merge；
- Metadata；
- Rebalance。

---

## 33. “召回下降就调高 efSearch”

这是典型盲调。

还要检查：

```text
Embedding
Metric
Normalization
Filter
Index Version
Delete / Update
Ground Truth
```

---

## 34. “P50 很快说明系统很快”

生产面试要看 Tail Latency。

尤其：

```text
P95 / P99
```

更容易暴露 Fan-out、GC、I/O、热点和资源争用。

---

## 35. “向量本身占用的内存就是系统总内存”

错误。

还要算：

- Index Graph / List；
- Metadata；
- ID；
- Segment；
- Cache；
- Runtime Overhead；
- Replica。

---

# 九、Product / Architecture

## 36. “FAISS 是 Vector Database”

更准确地说，FAISS 首先是 ANN / Similarity Search Library，并不天然等于具有完整数据库能力的 Vector DB。

---

## 37. “pgvector 不专业，所以一定不能用”

错误。

如果数据规模、SLA 和现有 PostgreSQL 架构适配，使用 Extension 可能显著降低系统复杂度。

---

## 38. “Dedicated Vector DB 一定性能最好”

不能脱离 workload 和 benchmark 断言。

选型不仅看单次 ANN benchmark，还要看 Filter、Update、HA、Multi-tenancy 和运维成本。

---

## 39. “Elasticsearch Vector 只适合 Keyword Search”

过时或过度简化。

现代 Search Engine 可以支持 Vector Search。真正要比较的是当前版本能力、Hybrid 需求、Scale 和现有 Search Stack。

---

## 40. “选型就是 Milvus vs Qdrant 谁更快”

不够。

首先要决定你是否需要：

```text
Library
Relational Extension
Search Engine
Dedicated Vector DB
```

然后再在类别内比较具体产品。

---

# 十、Graph / RAG Boundary

## 41. “Vector Similarity 就等于知识关系”

错误。

语义接近不等于存在明确的 `CITES`、`BELONGS_TO`、`DEPENDS_ON` 等 Edge。

---

## 42. “Graph DB 可以直接替代 Vector DB 做模糊语义搜索”

不是它的核心查询模型。

---

## 43. “用了 Graph + Vector 一定效果更好”

错误。

Graph Extraction、Schema、Entity Resolution 和维护都增加成本，必须用真实 Evaluation 证明收益。

---

## 44. “Hybrid Search 属于 Vector DB 核心知识”

在本 Handbook 的 Ownership 里不是。

```text
Vector DB：ANN Infrastructure
RAG：Dense / Sparse / Hybrid / RRF / Rerank / Evaluation
```

这样避免重复和边界混乱。

---

## 45. “Vector DB 速度快，所以 RAG 一定好”

错误。

RAG 失败可能来自：

- Parse；
- Chunk；
- Embedding；
- Query Rewrite；
- Sparse / Hybrid；
- Rerank；
- Context；
- Generation。

Vector DB 只是其中一层。

---

# 最后记住五句话

```text
1. Metric 要和模型 / Normalization 对齐。
2. ANN 是 Recall 与成本的 Trade-off，不是“随机近似”。
3. HNSW / IVF 参数必须放回算法机制理解。
4. Production Vector DB 的难点在 Filter、Lifecycle、Scale 与运维，不只在 Index。
5. Vector DB 负责向量基础设施，RAG 负责完整 Retrieval System。
```
