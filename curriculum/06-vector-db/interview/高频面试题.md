# Vector Database｜高频面试题

> 这份材料用于第三遍复习：把已经理解的知识压缩成可口述答案。
>
> 题目优先覆盖冻结 `S001–S279` HUMAN-A 中真实出现的 Vector DB Canonical，再补知识体系必需的 Production 追问。

---

# 1. 基础与 Similarity

## Q1：Vector DB 是什么？为什么 AI Application 会需要它？

**30 秒回答：**

Vector DB 的核心是保存高维向量并高效执行相似性搜索。Embedding 把文本、图片等对象映射到向量空间后，我们常需要从百万到十亿级向量中找最相近的 Top-K。普通业务数据库虽然也能存数组，但未必提供专门的 ANN Index、Metadata Filter、Index Lifecycle、Shard / Replica 等向量检索基础设施，所以当规模、Latency 和运维需求上来后，会使用专用 Vector DB 或支持向量索引的现有数据库。

**继续追问：**

- Vector DB 是不是 Source of Truth？
- 为什么不直接 MySQL 存 JSON Array？
- 小数据量为什么可能根本不需要专用 Vector DB？

---

## Q2：Embedding 和 Vector DB 是什么关系？

Embedding Model 负责把语义对象映射成向量；Vector DB 负责存储这些向量、构建 ANN Index、执行 Similarity Search、Filter 和 Lifecycle 管理。

不要混成：

```text
Embedding = Vector DB
```

模型原理 Primary 在 LLM Foundation。

---

## Q3：Cosine、Dot Product、L2 有什么区别？

**回答框架：**

- Cosine：主要比较方向 / 夹角；
- Dot Product：方向与模长都会影响结果；
- L2：欧氏距离；
- 如果向量先做 L2 Normalization，Cosine 与 Dot Product 的排序关系会更接近；
- Metric 必须和模型训练 / 推荐口径及 Index 配置一致。

⚠️ 不要说“文本永远用 Cosine”。

---

## Q4：Normalization 有什么作用？

Normalization 把向量模长缩放到统一尺度。它会改变 Dot Product / L2 的几何含义，并可让某些 Metric 之间产生等价或单调关系。工程上必须明确：

```text
模型输出是否已经 normalized
→ 入库前是否 normalize
→ Query 是否同样 normalize
→ Index Metric 用什么
```

不一致会造成 Retrieval Regression。

---

## Q5：Vector Dimension 越大越好吗？

不是。Dimension 由模型决定其表达能力与表示空间，但基础设施角度维度越大通常意味着：

```text
更多 Memory / Storage
更多 Distance Compute
更高 Network 成本
更大的 Index Build Cost
```

所以不能单独用“维度越高语义越强”做系统判断。

---

# 2. Exact Search 与 ANN

## Q6：什么是 Top-K Nearest Neighbor？

给定 Query Vector，根据指定 Similarity / Distance，从数据集中找最相近的 K 个向量。

Vector DB 的核心 Query Path 可以抽象为：

```text
Query Vector
→ Candidate Search
→ Distance / Similarity
→ Top-K
```

---

## Q7：为什么不能总用暴力 Exact Search？

Exact Search 通常需要比较大量甚至全部向量，计算量近似随 `N × dimension` 增长。小规模时简单且精确，但在百万、千万、十亿级数据和高 QPS 下，Latency / CPU / Memory Bandwidth 会成为问题。

因此 ANN 用：

> **少量 Recall 损失换显著更低的搜索成本。**

---

## Q8：ANN 牺牲了什么，换来了什么？

主要牺牲 Exact Recall，换取：

- 更低 Latency；
- 更少 Distance Computation；
- 更高 QPS；
- 更好的大规模可扩展性。

核心不是“近似更不准”，而是可控地做 Recall / Latency / Memory Trade-off。

---

## Q9：怎样评估 ANN Index 本身好不好？

Index 层至少关注：

```text
Recall@K against Exact Ground Truth
Latency P50 / P95 / P99
QPS
Memory
Index Build Time
Storage
Update Cost
```

但完整 RAG Retrieval Evaluation 还要进入 MRR / NDCG、Query Set、Rerank 和最终任务指标，Primary 在 RAG。

---

# 3. HNSW

## Q10：HNSW 的基本原理是什么？

**建议回答：**

HNSW 是 Graph-based ANN。它把向量组织成多层近邻图，高层更稀疏、适合长距离快速导航，搜索时从高层 Entry Point 逐层下降，逐渐接近 Query 所在区域，到底层再做更细的局部搜索。它避免扫描全部向量，以图导航换取高 Recall 和低 Latency。

---

## Q11：HNSW 为什么要有多层？

如果只有一层局部近邻图，远距离导航可能很慢。高层提供更稀疏的长距离连接，类似 Highway；底层更密集，负责局部精细搜索。

---

## Q12：HNSW 的 `M`、`efConstruction`、`efSearch` 分别影响什么？

- `M`：图连接度，影响 Memory、Build Cost 和搜索质量；
- `efConstruction`：建图时搜索候选宽度，越高通常图质量越好但 Build 更贵；
- `efSearch`：查询时候选搜索宽度，越高通常 Recall 越高，但 Latency / CPU 也更高。

最重要的是说出：

> `efSearch` 是典型 Query-time Recall / Latency knob。

---

## Q13：HNSW 的缺点是什么？

常见问题：

- Graph Memory 开销大；
- Build Cost 不低；
- Update / Delete / Compaction 语义依产品实现复杂；
- 大规模、强 Filter、多租户时需要综合考虑 Partition / Shard；
- 参数调优不是一次性固定答案。

---

# 4. IVF / Quantization

## Q14：IVF 的基本原理是什么？

IVF 先用 Coarse Quantizer 把 Vector Space 分成多个 List / Cluster。Query 来时先找到较近的 Centroid，再只搜索 `nprobe` 个相关 List，而不是扫全部向量。

本质：

```text
先粗分区
→ 再缩小候选范围
```

---

## Q15：`nlist` 和 `nprobe` 怎样影响 Recall 和 Latency？

- `nlist`：Index 有多少 coarse partitions；
- `nprobe`：Query 实际访问多少 partitions。

`nprobe` 越大通常 Recall 越高，但扫描候选更多，Latency 也上升。

`nlist` 也不是越大越好，需要结合数据量、分布和训练质量。

---

## Q16：HNSW 和 IVF 怎么选？

不要只答“HNSW 快、IVF 省内存”。

应该比较：

```text
Dataset Scale
Recall Target
Latency
Memory Budget
Index Build Cost
Update Pattern
Filter
Hardware
Product Implementation
```

HNSW 常有较好的低延迟高 Recall，但 Graph Memory 成本高；IVF 通过 coarse partition 控制候选范围，更容易和 Quantization 结合。最终需要 Benchmark。

---

## Q17：PQ / Product Quantization 是什么？为什么需要？

PQ 把高维向量拆成多个子向量，每个子空间用有限 Codebook 量化，最终用短 Code 代替原始 float Vector。

收益：

```text
显著减少 Memory / Storage
可加速近似距离计算
```

代价：

```text
Quantization Error
→ Recall / Ranking 可能下降
```

# 5. Index Selection

## Q18：怎样选择 Vector Index？

回答顺序建议：

1. 数据量；
2. Dimension；
3. Recall 目标；
4. P95 / P99 Latency；
5. QPS；
6. Memory / Storage；
7. Update / Delete 频率；
8. Filter Selectivity；
9. Build / Rebuild 成本；
10. 产品实际 Benchmark。

最后再说选择 HNSW、IVF、Quantized Index 或 Exact。

# 6. Metadata / Filter / Multi-tenancy

## Q19：Vector DB 为什么需要 Metadata Filter？

因为真实业务不是“在全世界所有向量里找相似”。通常还要满足：

```text
tenant_id
permission
language
doc_type
time_range
version
```

因此 ANN 必须和结构化条件结合。

---

## Q20：Pre-filter 和 Post-filter 有什么区别？

**Pre-filter：** 先通过结构化条件缩小数据范围，再进行 Vector Search。

**Post-filter：** 先做 ANN，再把不满足条件的结果删掉。

Post-filter 的问题是：

```text
取回 20 个
→ 过滤掉 18 个
→ 最终只有 2 个
```

因此 Filter Selectivity 会直接影响候选策略。

---

## Q21：多租户 Vector DB 怎样隔离？

可以组合：

- Metadata `tenant_id`；
- Namespace / Collection / Partition；
- Query Layer 强制注入 Tenant Filter；
- ACL / RBAC；
- 审计与自动化测试。

关键点：

> Tenant Isolation 是 Security Constraint，不能只靠“开发时记得带 filter”。

---

# 7. Lifecycle / Update / Scale

## Q22：Vector DB 怎么处理 Update / Delete？

要区分产品语义。很多 ANN Index 不一定原地高效修改，常见方式可能涉及：

```text
Upsert
Logical Delete / Tombstone
Background Merge / Compaction
Index Rebuild
```

因此删除是否立即物理消失、何时不再可见、何时真正回收资源都需要看实现。

---

## Q23：Embedding Model 升级后怎么办？

不能默认把新旧向量继续混在一起。

更稳妥的流程：

```text
Embedding Model v2
→ Re-embedding
→ New Index / Namespace
→ Offline Evaluation
→ Online Shadow / Canary
→ Traffic Switch
→ Retire v1
```

同时要管理 Model Version、Index Version 和 Source Version。

---

## Q24：Shard 和 Replica 有什么区别？

Shard 是数据水平分片，解决容量和并行计算；Replica 是副本，解决高可用和读扩展。

典型 Query：

```text
Router
→ relevant shards
→ shard-local ANN
→ merge Top-K
```

Shard 越多也会增加 Fan-out 和 Merge Cost。

---

## Q25：Vector DB 召回突然下降怎么排查？

按层排：

```text
Query / Embedding
→ Normalization / Metric
→ Filter
→ Index Parameter
→ Index Build / Version
→ Delete / Update
→ Shard / Segment
→ Ground Truth / Evaluation Set
```

不要第一反应就是调高 `efSearch`。

---

## Q26：Vector DB 查询突然变慢怎么排查？

看：

- P50 / P95 / P99；
- Filter Selectivity；
- ANN 参数；
- Candidate 数量；
- CPU / Memory / Cache；
- Disk / Network；
- Shard Fan-out；
- Segment 数量；
- Compaction / Build 是否抢资源；
- Concurrent Query 数量。

先定位瓶颈，再调参数。

# 8. Product / Architecture Selection

## Q27：FAISS、pgvector、Elasticsearch Vector、Milvus / Qdrant 怎么选？

先按“产品类别”回答，而不是背品牌优缺点：

```text
FAISS：ANN Library
pgvector：Relational DB Extension
Elasticsearch Vector：Search Engine + Vector
Milvus / Qdrant：Dedicated Vector Database
```

再结合：

```text
现有技术栈
数据规模
Metadata Filter
Keyword Search
Transaction 需求
HA / Sharding
Update Rate
运维复杂度
```

做选择。

---

## Q28：什么时候没必要独立上 Vector DB？

如果数据量小、QPS 低、已有 PostgreSQL 足够、Filter / Transaction 更重要，或者单机 Library 就能满足 SLA，独立 Vector DB 可能只会增加系统复杂度。

---

## Q29：Vector DB 和 Graph DB 有什么区别？

Vector DB 优化：

> 相似性近邻搜索。

Graph DB 优化：

> 显式 Node / Edge Relationship 和图遍历。

Embedding 中语义接近不等于存在 `CITES / DEPENDS_ON / OWNED_BY` 等明确关系。复杂系统可以组合两者。

---

## Q30：Vector DB 在 RAG 里负责到哪里？

**建议回答：**

> Vector DB 负责向量的存储、Similarity Search、ANN Index、Metadata Filter、Index Lifecycle 和 Scale；Dense/Sparse 组合、Query Rewrite、Hybrid Retrieval、RRF、Rerank、Top-K Strategy、Retrieval Evaluation 属于 RAG Retrieval System。把这两层分开，才能定位“Index 有问题”还是“整个 Retrieval Pipeline 有问题”。


```text

+
```
