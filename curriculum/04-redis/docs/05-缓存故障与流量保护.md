# 05｜缓存帮不上忙时，怎样保护数据来源

[← 上一章](04-缓存读取与更新.md) · [Redis 首页](../README.md) · [下一章 →](06-多级缓存与结果复用.md)

缓存正常时，大部分请求不用查数据库。可某个热门商品突然没了缓存，许多人同时回源；或者大量请求查询根本不存在的商品，缓存始终帮不上忙。

这些问题经常被叫作穿透、击穿和雪崩。名称可以最后记，先看清：**缓存为什么没有挡住重复工作，多少请求因此走向了数据来源。**

## 1. 穿透：反复查询不存在的数据

有人反复查询 999 号商品，Redis 没有，数据库也没有。如果每次都把“没找到”直接返回、不留任何记录，下次仍然走完整查库过程。这就是缓存穿透的一种典型路径。

一种简单处理是**负缓存**：短暂保存“这条记录不存在”的结论。它必须与“缓存中没有记录”区分，也不能随便借用空字符串，因为空字符串可能是合法内容。

负缓存只保护已经查过的不存在项。不断换随机 ID，仍可能制造大量回源，因此要结合输入检查和请求限制。刚创建的数据也可能遇到旧的“不存在”缓存，应在创建时失效或根据业务选择较短期限。

### 布隆过滤器为什么只能说“可能存在”

数据规模较大时，可以先用布隆过滤器筛查 ID。它通过若干计算，把每个已加入 ID 映射到几个 0/1 标记位置。

假设 A 使用位置 1、4，B 使用位置 4、6；加入它们后，1、4、6 都是 1。C 恰好使用 1、6，检查时也都命中，但 C 可能从未加入——不同 ID 共用位置造成了**误判存在**。

因此，有必需位置为 0，可以否定它曾被加入；全为 1 只能说可能加入过，仍需进一步查。把这个性质用于数据库，前提是所有应当存在的 ID 已正确同步到过滤器。新数据漏同步，算法不会替应用补救。[布隆过滤器](https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/)

> ⚠️ 过滤器判断的是自己的记录，不能单独证明当前数据库完整状态，更不能代替资源权限检查。

## 2. 击穿：一个热点过期，所有人同时重建

热门商品的缓存刚到期，五百个请求一起查不到，便各自查询数据库并建立同一份缓存。问题不是查询不存在的数据，而是**同一项昂贵工作被同时做了五百次**。

可以让一个执行者负责重建，其他请求短暂等待它的结果，或使用仍被允许的旧值。这种合并相同在途请求的做法通常叫**单飞（single flight）**。它减少重复劳动；等待要有上限，负责重建的人失败后也要能退出和重新选择。

若允许短暂陈旧，还可以保留旧值，并另记业务有效期：到期后触发一次刷新，不立即让所有读者失去内容。这通常称为逻辑过期或后台刷新。

它适合允许陈旧的介绍文字，不适合无限沿用已撤销权限。刷新反复失败时，需要最大陈旧期限；“还保留旧值”不等于“永远可以返回旧值”。

## 3. 雪崩：许多缓存同时失效

两种常见原因是：大量键在相近时刻到期，或者整个缓存服务不可用。结果都是许多不同查询一起压向数据库，影响面比单个热点更大。

同时创建的缓存可以错开到期时间，即给 TTL 加适当抖动。若业务规定最多保留 60 秒，可以在允许范围内分散，例如 45–60 秒，而不是擅自在 60 秒后再加十分钟。

但抖动只处理到期集中，不能修好缓存服务本身的故障。服务不可用时，还需限制回源数量、使用可接受的本地副本，或者暂时降低服务能力。

## 4. 为什么“缓存坏了就全部查库”可能扩大故障

设每秒一万次请求，缓存命中率 95%。正常只有约五百次需要查库。缓存故障后全部回源，就突然变成一万次；数据库并不会因此自动获得二十倍处理能力。

这是教学估算，说明流量转移的方向。保护来源可以按顺序考虑：先限制正在执行的回源量，再给等待设置上限；允许旧内容时提供受控旧副本；不能接受时明确拒绝或降级，而不是让请求无限堆积。

缓存重新启动也会出现大量首次未命中。只预热最重要的热点、分批重建，比一口气把所有数据读一遍更可控。

## 5. 将名字放回原因与动作

| 故障 | 先确认什么 | 核心处理方向 |
|---|---|---|
| 穿透 | 数据本来是否存在 | 保存负结果、正确筛查、限制无效请求 |
| 击穿 | 是否同一热点被反复重建 | 合并重建、有限等待或允许的旧值 |
| 雪崩 | 是否大范围一起回源 | 分散到期、限制整体回源、故障降级 |

**理解练习：** 一个热点每次过期都会出现洪峰，把所有缓存的 TTL 改成随机数就够了吗？随机数能减少多键同时到期，但不能阻止这个热点到期时被五百人一起重建。选择措施要对应原因。

## 本章小结

穿透处理不存在，击穿处理重复重建，雪崩处理大范围流量转移。工具有交集，但不能因为听过布隆过滤器、锁或随机 TTL，就认为三类问题已经得到同样的解决。

## 🎯 面试怎么回答

**怎样讲清缓存穿透、击穿、雪崩？**

> 先解释请求路径：不存在的数据反复查库是穿透，同一热点失效后同时重建是击穿，许多键或整个缓存层失效后广泛回源是雪崩。分别检查负结果、重建合并和来源容量，再选择保护措施。

## 易错点

> ⚠️ 随机 TTL 不等于单热点保护；分布式锁也不是所有缓存故障的唯一答案。

> ⚠️ 缓存连接错误与正常未命中是两种情况，故障时不能无条件把全部请求打向数据库。
