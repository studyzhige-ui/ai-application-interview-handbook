# 03｜数据什么时候应该消失

[← 上一章](02-键与常用数据类型.md) · [Redis 首页](../README.md) · [下一章 →](04-缓存读取与更新.md)

商品缓存十分钟后需要重新获取，验证码三分钟后不应再有效。如果不主动删除，这些数据会一直留着。Redis 可以为键设置期限；但内存紧张时，数据也可能在期限之前被移走。

这两种消失分别叫**过期**和**淘汰**。把它们放在一起理解，才能判断“键读不到了”究竟可能发生了什么。

## 1. TTL 表示这份数据还允许存在多久

TTL 是 Time To Live，即剩余生存时间。`SET lab:code 1234 EX 180` 同时保存值并设置三分钟期限；`EX 180` 不是命令运行超时。

查看 `TTL lab:code` 会得到剩余秒数。它不断减少，不需要恰好等于 180。特殊值也有明确含义：-1 表示键存在但没有期限，-2 表示键不存在。PTTL 用毫秒表示同一类信息。

普通 GET 只读取，不续期。给已有键设期限用 EXPIRE，取消期限用 PERSIST；如果要读取一个 String 并明确刷新期限，可使用 GETEX。这些行为由命令决定，不由 Redis 猜用户是否“还在活跃”。[期限规则](https://redis.io/docs/latest/commands/expire/)

## 2. 写入会不会改变原来的期限

这里需要区分**替换整份值**与**修改现有内容**：

| 操作 | 键级期限如何处理 |
|---|---|
| 普通 SET 替换值 | 默认移除原 TTL |
| SET 同时指定 EX 等新期限 | 使用新期限 |
| SET 带 KEEPTTL | 保留已有期限 |
| INCR、HSET 等修改现有内容 | 通常保留原键级期限 |

例如一个十分钟过期的用户缓存，刷新内容时只写了 SET 而没带期限，就可能变成永久键。反过来，HSET 改一个字段通常不会使整份对象重新获得十分钟。

> ⚠️ 整个 Hash 的期限与某个字段的期限是两层规则。Redis 7.4 起的 HEXPIRE 可让指定字段单独到期；若整个键先到期，里面所有字段都会消失。是否需要字段期限，应由“字段是否独立失效”决定，而不是所有 Hash 都设置一套更复杂的计时。[HEXPIRE](https://redis.io/docs/latest/commands/hexpire/)

## 3. 到期后，Redis 怎样清理

为每个键单独安排一个精确定时任务并不划算。Redis 结合两条路径：读取时发现过期，就不再正常返回旧值；另外周期性检查一部分到期键，回收那些一直无人访问的数据。

前者通常叫**惰性过期**，后者叫**主动过期**。只有第一种时，无人访问的过期键可能长期占空间；只靠高频全库检查，又会消耗太多处理时间。组合的目的就是在回收速度和 CPU 成本之间取舍。

所以“业务上已经失效”与“操作系统看到内存已经下降”不是同一时刻。先记住有效性由过期判断，物理回收还有自己的过程，不必为了使用三分钟验证码先研究内存分配器。

## 4. 没到期也可能被淘汰

Redis 的可用内存有限。`maxmemory` 用来限定参与数据内存管理的预算；需要腾空间时，淘汰策略决定哪些键可以牺牲。[官方淘汰说明](https://redis.io/docs/latest/develop/reference/eviction/)

先决定候选范围，再决定选谁：

| 策略范围 | 含义 | 直接后果 |
|---|---|---|
| allkeys | 所有键都可能成为候选 | 没有 TTL 也可能被提前移走 |
| volatile | 只在带键级 TTL 的键中选择 | 有期限并不是受保护，反而是候选条件 |
| noeviction | 不为腾空间而淘汰键 | 需要更多内存的写入可能被拒绝；读取仍可工作 |

如果 volatile 范围内没有可淘汰的候选，也不会自动改去淘汰无期限键；需要更多内存的写入仍可能失败。

LRU（最近最少使用）偏向移走较久没被访问的键；LFU（最不经常使用）偏向移走使用频率低的键，并考虑频率随时间衰减。Redis 用采样等近似方法，避免维护昂贵的全库精确排序。随机选择、按剩余期限选择也是其他策略，不必先背完整配置名单。

假设一份无法重建的任务记录也有 TTL，把它与可丢缓存混放在 volatile 策略的实例，并不能保护这份记录不被提前移走。**淘汰策略作用于实例，不因键名前缀不同就自动划出独立保护区。**

## 5. 期限、容量与是否值得缓存，要一起决定

一份查询结果很大、以后却几乎没人再读，把它缓存进去可能挤掉真正常用的小结果。除了“留多久”和“淘汰谁”，还应问“是否值得进入缓存”，这称为缓存准入。

如果经常使用的数据长期超过容量，就可能反复淘汰、重新获取、再写回。只把 TTL 改短未必改善问题；先看是否缓存了低价值大结果，再判断容量或模型是否需要调整。

期限也来自业务，而不是统一填一小时。需要最大存活时间的登录态，不能靠每次活跃无限续期；签名 URL 到期后，Redis 中的文字还在，也不会延长它的访问资格。

**理解练习：** 一个键“十分钟内可用”，却在两分钟后读不到，列出过期配置被改、主动删除、内存淘汰这几种不同原因。仅知道设置过 TTL，不能排除其他原因。

## 本章小结

过期回答何时失效，淘汰回答内存不足时允许移走谁。覆盖、原地修改和读取对期限的影响不同；先决定哪些数据允许消失，再选择期限和容量策略。

## 🎯 面试怎么回答

**TTL 与内存淘汰有什么不同？**

> TTL 是键自身的有效期，淘汰是内存压力下的取舍。allkeys 可能移走无期限键，volatile 也可能提前移走有期限键，noeviction 则可能拒绝分配。必须结合数据能否重建选择。

## 易错点

> ⚠️ 普通 SET 可能使有期限的键变成无期限键；刷新缓存时不要漏掉过期要求。

> ⚠️ maxmemory 不是整个进程的绝对物理内存上限，缓冲与后台工作仍需余量。

<details>
<summary>1. GET 一次，会让三分钟验证码重新获得三分钟吗？</summary>

不会。普通读取不续期；是否允许延期应由业务决定并显式执行。

</details>

<details>
<summary>2. 一个没有 TTL 的缓存，在 allkeys-lru 下是否一定不会消失？</summary>

不是。allkeys 的候选范围不要求带 TTL，可能为了腾空间提前移除。

</details>

<details>
<summary>3. 为什么不建议用一套可淘汰缓存策略管理无法重建的任务记录？</summary>

任务记录提前消失可能让工作结果无法核对，而不仅是一次缓存未命中。它与可重建副本的损失后果不同。

</details>
