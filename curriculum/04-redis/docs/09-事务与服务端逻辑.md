# 09｜多步修改怎样避免互相干扰

[← 上一章](08-内部编码与数据规模.md) · [Redis 首页](../README.md) · [下一章 →](10-持久化与恢复.md)

库存是 1，两个请求都先读到 1，都判断可以买，再分别扣减。每条命令可能都合法，组合起来却把一份库存卖了两次。

问题出在“读取、判断、修改”之间。Redis 提供不同工具处理这种组合，但它们的保证不同：**单条操作、连续执行一组命令、检查读到的状态是否变化、在服务器内判断后修改**，不能混成一个“原子”。

## 1. 能用一条命令完成，就不要先读再覆盖

两个客户端都想把计数从 10 加一。A 读到 10，B 也读到 10，随后各写入 11，最终只有 11 而不是 12。

改成各执行一次 INCR，每次增加都在服务端一次完成，最后就是 12。在这里，**原子性**指操作不会被其他普通客户端命令插入中间。它不自动延伸到应用在两次命令之间做的计算，也不是数据已被保存到磁盘的同义词。

如果任务有“库存必须足够”的条件，单纯 DECR 还不够，因为它不替你执行这条业务判断。

## 2. MULTI/EXEC：先收集命令，再连续执行

MULTI 开始排队，后续命令回复 QUEUED，表示先登记；EXEC 才把队列按顺序执行并返回各项结果。

<!-- redis-lab: core_transaction -->
```redis
MULTI
SET lab:tx:a one
SET lab:tx:b two
EXEC
```
<!-- redis-expect: ["OK", "QUEUED", "QUEUED", ["OK", "OK"]] -->

前两次 QUEUED 不能当作已经写入。EXEC 期间，这组正常排队命令不会被另一个客户端的普通命令插入。DISCARD 丢弃的是还没执行的队列，不会撤销过去已提交的修改。

错误还需分阶段：

| 错误发生在哪 | 会怎样 |
|---|---|
| 排队时参数数量等已不合法 | EXEC 拒绝执行这组事务 |
| 执行时才发现某个值类型不对 | 这一项报错，其他命令仍可能成功 |

**Redis 事务不提供通用错误回滚。** 若第一条 SET 成功、第二条对错误类型执行 LPUSH，不能假定第一条会被撤销。[事务规则](https://redis.io/docs/latest/develop/using-commands/transactions/)

## 3. WATCH：别人可以写，但旧计划不能直接提交

A 依据库存 10 计划写成 9，期间 B 已把库存改成 8。A 再写 9，会覆盖 B 的结果。WATCH 让 A 在提交前检测观察期间有没有变化：

| 步骤 | A 的行为 | B 或最终状态 |
|---:|---|---|
| 1 | WATCH 库存，再 GET，得到 10 | 库存 10 |
| 2 | 计算计划值 9 | B 写入 8 |
| 3 | MULTI，将 SET 9 入队，再 EXEC | 检测到变化，整组因冲突不执行 |
| 4 | 重新读取并重新决策 | 库存仍是 8 |

WATCH 不阻止 B 写入，所以叫**乐观并发控制**：先尝试，提交前检查冲突。键的过期、淘汰等变化也可能使观察失效。使用时应在同一连接完成观察到提交，冲突后有界重试，而不是一直重复旧的 SET 9。

## 4. Lua：把有限判断放在 Redis 内完成

如果判断只依赖 Redis 中少量数据，可以把逻辑作为一个短脚本发送给 Redis。下面只解释一件事：整数库存足够才扣减，成功返回 `{1,剩余量}`，不足返回 `{0,当前量}`，缺失或坏输入返回错误。

输入契约：恰好一个 KEYS（`KEYS[1]` 是库存键），一个 ARGV（`ARGV[1]` 是扣减数量文本）。库存使用规范十进制整数字符串（如 "5"，不使用 "05" 或 "5.0"），库存与数量均限定为不超过一百万的非负/正整数，避免示例把浮点与整数精度边界混进库存逻辑。键存在且必须是可由 GET 读取的 String。

<!-- teaching-lua: bounded -->
```lua
if #KEYS ~= 1 or #ARGV ~= 1 then
  return redis.error_reply('expected one key and one amount')
end
local amount = tonumber(ARGV[1])
if not amount or amount < 1 or amount > 1000000 or amount % 1 ~= 0 then
  return redis.error_reply('invalid amount')
end
local raw = redis.call('GET', KEYS[1])
if not raw then return redis.error_reply('stock missing') end
local stock = tonumber(raw)
if not stock or stock < 0 or stock > 1000000 or stock % 1 ~= 0
   or tostring(stock) ~= raw then
  return redis.error_reply('invalid stock')
end
if stock < amount then return {0, stock} end
local remaining = redis.call('DECRBY', KEYS[1], amount)
return {1, remaining}
```

`tonumber` 把参数文本转成数字，失败得到 nil；`% 1` 检查整数；redis.call 调 Redis 命令；return 结束脚本并把值交回客户端。所有业务校验都在第一次修改前。错误类型的 GET 会直接报错，因为还没写入也不会留下半次扣减；这不等于任意先写后错的脚本能回滚。

设开始时库存键内容为 `"5"`，传入 amount=`"2"`，依次读 5、判断足够、执行 DECRBY，回复数组 `[1,3]`，键变成 `"3"`；随后 amount=`"4"` 得到 `[0,3]`，库存保持 3。每次最多执行一次 GET 和一次 DECRBY，没有集合遍历。这是规则推演，非本次服务器实测。

调用形状是 `EVAL 脚本文本 1 lab:stock 2`：1 表示接下来有一个键，剩下的 2 进入 ARGV。脚本所有访问键都应显式经 KEYS 声明，不能从某个值悄悄拼出未声明键；Cluster 的多键脚本还须同槽。其他普通客户端命令不能插在脚本的检查与扣减之间，但同一脚本因重试执行两遍仍会扣两遍。[服务端脚本](https://redis.io/docs/latest/develop/programmability/eval-intro/)

实际客户端通常 SCRIPT LOAD 取得摘要，再以 EVALSHA 调用；遇到 NOSCRIPT 要按协议重新加载。加载缓存不是业务结果持久化，流水发送时也不能在未知前项结果的情况下假定缓存一定存在。连续调用方法见[可选脚本实验](../examples/labs.md#lab-scripts)。

脚本缓存可以通过 EVALSHA 按摘要调用，但重启或切换后可能需要重新加载；Functions 则提供命名函数库的部署、复制和持久化管理。它们改变代码管理方式，不把 Redis 变成应承载全部业务的应用服务器。

## 5. 如何选择，以及保证在哪里结束

| 要解决的问题 | 优先考虑 |
|---|---|
| 简单计数或已支持的条件修改 | 一条足够表达需求的原生命令 |
| 已确定的一组命令需要连续执行 | MULTI/EXEC |
| 应用必须读值后计算，能接受冲突重试 | WATCH 配合事务 |
| 小范围判断与修改能在 Redis 内完成 | 短 Lua 或 Function |
| 只是批量读写、减少等待 | Pipeline，不把它当正确性方案 |

这些工具都不会让外部订单或付款接口与 Redis 一起提交。同一个扣减脚本执行两次，仍可能扣两次；要把它认成同一业务操作，需要稳定标识和结果记录，这才是幂等问题。

**理解练习：** 分别解释“计数丢更新”“根据旧库存提交”“一项命令类型错误”“已执行但回复丢失”。先指出错误在哪个阶段，再选工具，避免统一回答“加事务”。

## 本章小结

单命令原子、连续执行、冲突检查和服务端判断解决不同问题。Redis 事务和脚本不提供通用回滚，也不自动保护外部动作或重复请求。

## 🎯 面试怎么回答

**WATCH 与 Lua 怎样区别？**

> WATCH 让客户端先读后计算，提交时检测变化，冲突则重读重试；Lua 将有限的读、判断、修改放在服务端连续执行。前者会有重试成本，后者要限制脚本时长，两者都不是任意错误自动回滚。

## 易错点

> ⚠️ QUEUED 只表示已入队，EXEC 还需查看逐项结果。

> ⚠️ 原子操作执行两次不等于只产生一次业务效果，网络重试需要另行判断。

## 本章自测

<details>
<summary>1. WATCH 是否阻止其他客户端修改？</summary>

不阻止。它在 EXEC 前检查观察期间的变化，有冲突就放弃这组提交。

</details>

<details>
<summary>2. 事务里一条 LPUSH 执行时因类型错误失败，之前成功的 SET 怎样？</summary>

不会因为这个错误自动撤销。应检查每项回复和最后状态。

</details>

<details>
<summary>3. 为什么库存检查与扣减不能只放进普通 Pipeline？</summary>

流水发送主要优化等待，不把条件判断与修改绑定成不可交错的业务步骤。

</details>
