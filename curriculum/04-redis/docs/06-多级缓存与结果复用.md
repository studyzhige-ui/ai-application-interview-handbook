# 06｜本地缓存与 AI 结果缓存：什么可以复用

[← 上一章](05-缓存故障与流量保护.md) · [Redis 首页](../README.md) · [下一章 →](07-执行模型与Pipeline.md)

一份很少变化的配置，每次都去 Redis 读取，仍然要经过网络。如果把它留在应用本地，可以再省一次访问。AI 问答也有类似想法：相同甚至相似的问题，能否直接复用以前的答案？

两者都在减少重复工作，但增加的风险不同：**多一层缓存，增加副本同步问题；放宽命中条件，增加错误复用问题。**

## 1. 本地缓存省掉哪一步

本地缓存存在当前应用进程里，读取它不需要向 Redis 发请求。通常先查本地，未命中才查共享 Redis，再未命中才回源。常见名字 L1、L2，只表示第一层、第二层。

三份应用会有三份本地内容。来源和 Redis 已经更新，不会自动修改这些进程内的副本。因此每层都要有容量和期限，更新时还要安排失效。

例如更新后通知各应用清除旧值，可以加快传播；某个应用离线错过通知，就需要在重连时刷新，或依靠有限 TTL、版本核对避免一直读旧。Redis 的客户端缓存跟踪提供一种失效通知能力，但客户端仍需正确处理失联与重新连接。[客户端缓存](https://redis.io/docs/latest/develop/reference/client-side-caching/)

## 2. 别把两层命中率直接相加

一千个请求，第一层命中七百；剩下三百进入 Redis，其中二百四十命中，六十回源。

第一层命中率是 70%；第二层的 80% 以进入第二层的三百次为分母。总命中率为 `(700 + 240) / 1000 = 94%`，不是 150%。

增加本地缓存是否值得，要看省掉的网络访问和 Redis 压力，是否超过副本失效的复杂度。访问本就很少、内容又经常改变时，多一层未必有收益。

## 3. 精确结果缓存：相同的输入，究竟包括什么

复用查询结果时，仅比较用户输入文字可能不够。A 团队和 B 团队都问“退款规则”，各自能看的资料可能不同；同一团队更新过知识后，也未必还能使用旧答案。

缓存键应反映真正影响结果和权限的条件，例如租户、允许材料的版本、问题以及相关处理版本。**先确定可信范围，再找可复用结果**，不能先把别人的答案交给模型，再期待模型自行忽略。

来源本身的期限也不能被缓存延长。一条图片链接 10:05 失效，10:04:50 才写入缓存，便不能只因为设了 60 秒 TTL 就承诺到 10:05:50 仍可访问。缓存期限应受来源剩余有效期约束。

## 4. 语义缓存：相似问题的答案未必通用

精确缓存要求完整的缓存身份匹配；语义缓存进一步尝试复用“意思接近”的问题。

常见做法是把问题转换为一组数值，用距离或相似度寻找历史问题，再判断能否复用。这组表示通常称为向量或 Embedding。这里先理解“用可比较的表示找候选”即可，不必提前掌握向量索引实现。

“个人客户能否退款”和“企业客户能否退款”很接近，但适用规则可能不同。相似度高只是发现候选，不是证明答案对当前用户正确。除了期限和权限，语义缓存还必须面对**错误命中**。

## 5. 怎样判断复用真正有益

准备一组能判断“旧答案是否可用于新问题”的样本，包括正确改写，也包括相似但答案不同的反例。改变阈值时，同时观察四件事：复用了多少、复用里错了多少、整体答案质量，以及省下多少时间和成本。

提高阈值常会减少命中，却不能证明剩下的全部正确。数据或模型改变后，也需要重新验证。不能只展示命中率增长，而不检查错误答案是否也增长。

有副作用的动作还要单独判断。复用旧天气查询结果是缓存；用户新要求发一封邮件，返回上次“发送成功”却不实际发送，是错误行为。同一封邮件因网络失败而重试，则应核对是否已经发送过——这叫幂等处理，与新请求的结果缓存不同。

**理解练习：** 为一份全局配置、一个临时链接和一个权限相关答案，分别说明哪些请求可以共用、何时失效。先确定适用范围，再考虑本地缓存或相似度检索。

## 本章小结

多级缓存增加需要维护的副本，语义缓存增加判断答案能否替代的责任。缓存收益应与失效成本和错误复用一起衡量，不能只追命中率。

## 🎯 面试怎么回答

**语义缓存比精确缓存多了什么风险？**

> 相似请求可能适用不同规则，因而复用错误答案。先限制权限和版本范围，再用正例与反例评估阈值、错误复用和节省；高相似度不能单独决定结果可用。

## 易错点

> ⚠️ 本地缓存失效通知可能被错过，需要有限期限或重连校验，不能假定一发通知全部同步。

> ⚠️ 缓存一个成功结果，不证明一项新的外部动作已经执行。
