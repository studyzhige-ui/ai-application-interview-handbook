# 07｜Redis 为什么快，请求又为什么会慢

[← 上一章](06-多级缓存与结果复用.md) · [Redis 首页](../README.md) · [下一章 →](08-内部编码与数据规模.md)

读取一个小计数，Redis 执行得很快，应用却等了几十毫秒。问题不一定在数据结构：请求可能还在等连接，或者来回走了很多次网络。

理解“为什么快”，要同时看服务器怎样做事，以及应用怎样向它提出请求。把这两件事分开，才知道优化应该发生在哪里。

## 1. 一次调用的时间，不全花在执行命令上

从应用准备读取，到最终拿到值，可能依次经过：等待可用连接、发送请求、服务端排队和执行、返回结果、客户端解码。服务器执行只是其中一段。

Redis 常见访问主要操作内存中的数据，而且直接提供计数、字段更新和有序范围等操作，减少了把全部数据拉回应用处理的需要。但大结果仍要被遍历、编码和发送；内存快不能让这些工作消失。

## 2. “单线程”说的是哪项工作

许多普通数据命令主要在共享数据集的主执行路径上串行完成。这样不必让许多线程同时修改同一份数据，也便于明确单条操作的执行边界。

整个进程却不是只有这一个工作者。网络 I/O（输入输出）可以使用额外线程，日志同步、异步释放等有后台路径，快照还可能由子进程处理。**命令修改数据的执行方式，与进程一共有多少线程，不是同一个问题。**[运行与延迟](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)

串行执行也有代价：前面一条命令长时间占用执行路径，后面的短请求也要等。长脚本、大范围集合操作因此不仅影响发起它的一个用户。

## 3. 很多连接，为什么不需要每条都一直占一个线程

多数连接有时在等待新数据。I/O 多路复用让操作系统报告“哪些连接现在可读或可写”，事件循环再处理这些就绪连接。

可以把过程理解为：等待一批连接事件，处理其中有事可做的，再进入下一轮。Linux 中常见的 epoll 是提供这种能力的接口之一。

“连接已经可读”不表示命令已执行，也不表示命令会并行执行。Reactor 是这种按就绪事件分派工作的设计思路；掌握角色和过程即可，不需要为了理解 Redis 先学另一套网络框架。

## 4. Pipeline：别每发一条就停下来等

假设应用要取一百个独立配置。逐条发送并等待，会反复支付网络往返时间。Pipeline（流水发送）则先连续发送多条命令，再按协议取得对应回复。

```text
逐条：发 A → 等 A → 发 B → 等 B → 发 C → 等 C
批量：发 A → 发 B → 发 C → 取得各自回复
```

教学假设每次往返 2 毫秒、执行 0.05 毫秒，无其他等待；一百次串行调用约为 `100 × (2 + 0.05) = 205` 毫秒。Pipeline 可以减少逐条等待，但不消除实际执行和传输，也不保证命令恰好装进一个网络包。[Pipeline](https://redis.io/docs/latest/develop/using-commands/pipelining/)

它解决性能，不保证整批操作不会被其他客户端穿插。某条报错，其他条也可能成功。某些客户端将 Pipeline 和事务包装在同一个接口中，使用时要看具体配置，不能仅按方法名字判断保证。

如果需要前一个结果才能决定后一个请求，就不能在结果未知时直接组成同一批。先区分独立请求和有数据依赖的动作。

Redis 通过 RESP 协议编码命令与回复。可先把请求理解成由命令名和参数字节串组成的数组；回复可能是简单字符串 OK、整数、新旧值的字节串、空回复、数组或错误。前面 HSET 的 0 是整数，GET 的 `"0"` 是内容，nil 是缺失，错误则另有类型。RESP 用长度描述字节串，所以零字节和换行也可作为内容，不靠一行文本猜边界。客户端负责解码；Pipeline 则按每条请求对应回复，不能只检查最后一项。

## 5. 复用连接和控制批次，都是有限资源问题

连接池保留一组可重复使用的连接：请求借用，完成后归还。池满以后，有的客户端报错，有的允许有限等待；它不是一个无限扩张的缓冲区。

Pipeline 批次也不能无限大。请求和回复会占缓冲，批次越大，错误后要核对的范围越大，最前面的结果也可能更晚被应用看到。按数量、字节和等待时间控制批次，比只追吞吐数字更稳妥。

> ⚠️ 一批 INCR 已执行一部分后断连，重新发送整批可能重复增加。网络异常不能证明整批都没发生，性能批处理不提供自动回滚或幂等。

**理解练习：** 一次请求 80 毫秒，其中等连接 50、网络与传输 25、执行 1、其余 4。假设这些阶段顺序执行且不重叠，把执行从 1 毫秒减到 0.5，最多只省 0.5 毫秒。先定位最大的等待，再选优化。

## 本章小结

Redis 常见操作的低延迟来自内存、数据结构和执行路径；应用仍会付出连接、排队和网络成本。Pipeline 与连接池改善访问方式，不代替并发正确性。

## 🎯 面试怎么回答

**Redis 为什么快？**

> 常见命令直接操作合适的内存结构，路径较短，事件驱动管理许多连接，主要串行的数据修改减少部分竞争成本。但慢命令、网络、池等待和后台工作仍影响延迟，不能仅说“因为单线程”。

**Pipeline 是事务吗？**

> 不是。Pipeline 主要减少逐条等待网络；整批连续执行、条件提交和失败处理是另外的机制。具体客户端可能把它们组合，需要查参数和结果语义。

## 易错点

> ⚠️ I/O 就绪、命令开始执行、客户端收到结果，是不同时间点。

> ⚠️ 批次越大不一定越好，响应大小、单批延迟和重试后果都需要限制。

## 本章自测

<details>
<summary>1. 大量连接同时在线，是否意味着 Redis 同时执行同样多条写命令？</summary>

不是。连接并发与命令执行是两层问题，许多连接只是在等待事件。

</details>

<details>
<summary>2. 数据很小但访问仍慢，应该先看什么？</summary>

分开观察连接等待、网络、服务端排队执行和客户端处理，不直接归因于值的大小。

</details>

<details>
<summary>3. 什么时候不适合把几条请求直接流水发送？</summary>

后续参数依赖前一条读取结果时，无法提前完整确定请求；应保留必要等待或改变计算位置。

</details>
