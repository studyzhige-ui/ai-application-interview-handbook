# 12｜一台装不下以后，数据怎样分到多台

[← 上一章](11-复制与Sentinel.md) · [Redis 首页](../README.md) · [下一章 →](13-分布式锁.md)

副本可以增加冗余，但每个副本仍保存相应主节点的数据。若一台主节点装不下全部内容，单纯多复制几份，并没有解决“数据太多”的问题。

这时需要**分片**：让多台主节点各保存一部分键。Redis Cluster 使用哈希槽，把键的位置与机器的分工分开。

## 1. 键先找到槽，槽再找到节点

Redis Cluster 定义了 16384 个槽。通常对键使用 CRC16 计算并对 16384 取模，得到槽号；每台主节点负责其中若干槽。

```text
商品键 → 槽号 500 → 当前由主节点 A 负责
用户键 → 槽号 9000 → 当前由主节点 B 负责
```

示例槽号只是帮助理解，不是这些文字键的实测计算结果。**槽是固定的分组编号，不是一个单独的文件或服务器。**

扩容时，将某些槽以及相应数据迁到新节点即可；键到槽的规则不必因机器数量改变而重算。它不是直接对节点数量取模，也不同于经典的一致性哈希环。[Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)

## 2. 为什么一个热键仍可能卡住

Cluster 分散的是不同键，一个键不会因此自动拆成几份可在多个主节点共同修改的数据。

如果一个热门配置承担了大部分读流量，负责它的节点仍可能忙，其他节点却空闲；如果所有用户都挤进同一个巨大 Hash，它也不会被自动按字段分散。要改善这类问题，仍需调整数据模型、本地缓存或实际操作方式。

因此“容量分散得均匀”和“请求分散得均匀”是两个目标。

## 3. 多键一起修改时，为什么要求同槽

已经学过的事务、脚本在一个 Redis 执行范围内处理数据。若两个键分别由不同主节点管理，就不能直接把它们当成同一处内存里的一个原子操作。

需要一起操作时，可以用 Hash Tag（哈希标签）明确让相关键同槽，例如：

```text
cart:{u42}:items
cart:{u42}:meta
```

两者使用相同的 `u42` 部分计算槽号。花括号在这里有专门含义，普通冒号没有；实际复杂括号边界按规范处理。

> ⚠️ 标签是在主动集中相关数据。给所有租户都用同一个标签，可能把分片退回一个热点，不能为了避免跨槽错误而让全部键抱团。

## 4. 数据迁走后，客户端怎样跟上

客户端维护槽到节点的位置关系。如果请求发到了不负责这个槽的节点，会收到相应重定向：

| 回复 | 含义 | 客户端处理重点 |
|---|---|---|
| MOVED | 该槽应到另一个负责节点 | 跟随并刷新相关路由信息 |
| ASK | 迁移阶段，这一次请求临时去目标节点 | 按协议先 ASKING，再发命令；不是永久更新全部映射 |

这是支持 Cluster 的客户端要处理的协议，不是看到错误就随机换一台机器。客户端拆分跨槽读取也只是多次请求，不能据此得到跨节点事务。

迁移要搬实际数据，还要处理期间的访问与变化。大键、写流量和网络都会影响成本；在线迁移不等于零性能影响。不同版本的迁移工具可以不同，基本判断仍是数据是否完整、路由是否正确、负载是否可承受。

把 ASK 放进迁移时间线：槽 s 原归 A，准备转给 B。先让 B 对 s 标为 IMPORTING，A 对 s 标为 MIGRATING，然后逐个搬键。

- 请求到 A，键尚在 A：A 仍处理它。
- 请求到 A，键已不在 A：A 返回 ASK 指向 B，避免在源重新创建已迁走位置的数据。
- 客户端在 B 的同一连接先发 ASKING，再发这一次命令；B 临时接受该槽请求，客户端此时不永久改槽归属。
- 数据搬完并更新槽归属后，旧路由到 A 的请求收到 MOVED，客户端才刷新稳定路由。

同槽多键命令在部分键已搬、部分未搬时也可能暂时无法整体执行并返回 TRYAGAIN，不能拆成两个节点的操作冒充原子性。这是经典逐键迁移协议；目标工具若采用其他迁移实现，仍应核对实际状态与对应官方协议。

## 5. 分片、高可用与安全仍需分别检查

每个分片可以有副本并进行相应故障切换，但异步复制的丢写窗口没有因分片数量增加而消失。Cluster 也不依靠多逻辑数据库隔离用户，它只支持数据库 0；权限仍需应用与服务账户控制。

Cluster 自己交换节点故障与槽归属信息，并由符合条件的副本请求负责槽的主节点多数授权提升，不再借用 Sentinel 的 quorum 配置。多数授权用于拓扑决策，不意味着每次业务写都是多数持久提交。某个主节点失效且没有可提升副本时，其槽无法正常服务；默认要求完整槽覆盖的配置还可能让整个集群停止正常请求，允许部分覆盖时才可能继续服务健康槽。网络少数侧也不能仅因尚有一个节点活着就无限继续写入。分片提高容量，故障时能服务哪些键仍取决于多数连通性、副本和覆盖策略。

节点之间还有 Cluster bus 通信。除了客户端端口，也要限制这些节点间端口的访问并按环境配置保护，不能只给应用连接加密码就把其他通道公开。具体版本安全变更见[固定版本说明](https://github.com/redis/redis/releases/tag/8.10.2)。

**理解练习：** 同一用户的购物项与元信息需要共同修改，可以考虑同标签；一百万条互相独立的商品缓存，却未必应该同标签。分别解释集中带来的收益与代价。

## 本章小结

Cluster 把键到槽、槽到节点分成两层。它解决数据分散和相应路由，单键热点、多键原子范围、复制与网络保护仍需各自处理。

## 🎯 面试怎么回答

**Redis Cluster 和 Sentinel 怎样选？**

> 单主容量足够、主要需要故障接替时，可以考虑主副本加 Sentinel；需要把键空间分散到多个主节点时再考虑 Cluster。Cluster 引入槽位、路由和多键限制，不因听起来更高级就应该优先使用。

## 易错点

> ⚠️ 同槽是特定多键操作的前提，不是越多键共槽越好。

> ⚠️ 自动分片不自动拆大值或单个热键，也不消除复制故障窗口。

## 本章自测

<details>
<summary>1. 新增一个主节点，为什么不必修改 16384？</summary>

固定的槽编号仍在，调整的是哪些节点负责哪些槽。

</details>

<details>
<summary>2. MOVED 与 ASK 为什么不能一律当作永久改地址？</summary>

ASK 服务于迁移中的本次临时转向，处理方式与更新稳定槽映射不同。

</details>

<details>
<summary>3. 把两个不同节点的读请求在客户端合并返回，就得到原子读取吗？</summary>

没有。客户端仍执行了多个请求，期间可能发生变化，需另行定义一致性要求。

</details>
