# 04｜把 Redis 用作缓存：读与更新怎样配合

[← 上一章](03-过期与内存淘汰.md) · [Redis 首页](../README.md) · [下一章 →](05-缓存故障与流量保护.md)

商品介绍保存在业务数据库里，Redis 只留一份常用副本。读取时很容易想到“先看 Redis”；真正难的是：数据库内容变了，这份副本怎样不再误导用户？

本章只围绕一份商品介绍，把读取和更新接起来。缓存故障与大量并发在这两条路径建立之后再讨论。

## 1. 一次命中和一次未命中

**命中**（hit）表示缓存中取得了符合使用条件的副本；**未命中（miss）**表示这次无法从缓存得到它。未命中后重新读取数据来源，叫**回源**。

```text
应用读取商品 → 查 Redis
                ├─ 命中 → 返回副本
                └─ 未命中 → 查业务数据库 → 缓存结果 → 返回
```

这叫旁路缓存（Cache Aside）：应用主动安排查缓存、回源和写缓存。Redis 不会仅凭一个空回复就自动替你查询业务数据库。

例如第一次取 42 号商品时缓存为空，应用查库得到“笔记本”，缓存十分钟；下一次可以直接使用副本。数据库若没有这件商品，怎样暂存“不存在”是另一条明确规则，不能把 miss 直接当作商品不存在。

### 其他缓存模式改变的是谁负责读写

| 模式 | 一次请求的责任 | 必须补上的保证 |
|---|---|---|
| Cache Aside（旁路） | 应用读缓存，miss 后应用读库并回填 | 应用维护失效与并发窗口 |
| Read Through（读穿） | 应用读缓存抽象层，由该层负责 miss 加载 | 加载器知道权威来源、权限和失败行为 |
| Write Through（写穿） | 应用通过统一写入层，同步把更新写入来源与缓存 | 该层须定义顺序、部分成功与确认时机 |
| Write Behind/Back（写回） | 先接收缓存层更新，稍后异步写来源 | 队列/日志须可靠，明确重放、顺序和缓存故障后的未落库写 |

例如订单金额写回时若缓存丢了、来源还没保存，损失的是已接受的事实，不再只是一次 miss。模式名称只移动责任，不自动创造 MySQL 与 Redis 的原子事务；普通 Redis GET/SET 自身也没有这些数据库加载器。

## 2. 缓存副本必须说明哪些请求可以共用

同一件公开商品的介绍可以由许多用户共用；同一段私人笔记则未必。构造缓存键时，要把会改变结果或可见范围的信息考虑进去，例如租户、商品编号和内容版本。

租户可以先理解为系统中各自拥有数据的一组用户。把 `t1` 写进键名便于区分，但应用仍要确认当前请求确实允许访问 t1；名字本身不执行授权。

TTL 给副本设置期限，却不自动判断内容是否过时。十分钟 TTL 表示这份缓存最多保留十分钟，不是承诺数据库更新后立即可见；回填时读到了多旧的数据，也影响最终的新鲜度。

## 3. 更新时，为什么常先改数据库再删缓存

数据库既然是本例的权威来源，修改必须先在那里成功。随后删除相应缓存，让下一次读取重新取得新版本，是常见的基础路径。

直接“更新数据库，再更新缓存”并非一定更好：两个写者可能在不同时间完成缓存更新，较旧的结果反而最后覆盖新结果。删除不必重建一份完整副本，还避免为无人读取的内容持续填缓存。

但先写库再删缓存仍是两次独立操作。数据库成功、缓存删除失败时，旧值还在。因此需要能重试失效操作或按期限重新读取；对新鲜度要求高的业务，应有更可靠的失效记录或同步流程。

## 4. 删除成功后，旧值为什么还可能回来

考虑一个已经开始读取、却迟迟没完成回填的请求：

| 次序 | 读取者 A | 更新者 B | Redis |
|---:|---|---|---|
| 1 | 未命中，从库取得旧标题 | | 空 |
| 2 | 暂停，尚未写缓存 | 写入新标题并提交 | 空 |
| 3 | | 删除缓存完成 | 空 |
| 4 | 恢复，把之前读到的旧标题写入 | | 再次变旧 |

**A 没读错它当时的数据，B 也完成了删除，错误来自两个过程的交错。** 所以“删成功”不能推出之后永远没有旧副本。

能够控制写入和回填流程时，可以给数据附上可信版本，拒绝用旧版本覆盖新版本；例如已确认应使用版本 8，就不再接受版本 7 的回填。这个办法还需要有可靠的位置知道“应使用哪个版本”，不是只在 JSON 里多写一个数字就完成了保护。

一个容易追踪的正面方案是**不可变版本键**：权威存储记录商品当前版本 8，读取者先在符合新鲜度要求的路径上确定版本，再读 `product:42:v8`。读者 A 早先取得版本 7，即使晚到，也只能填 `product:42:v7`，不能覆盖 v8 的值。新请求确定版本 8 后只访问 v8，旧键按期限回收。

代价是如何取得当前版本仍要安排；若把“当前版本指针”也长期缓存在 Redis，就会重新引入陈旧。对强新鲜度路径，本例从权威来源取版本；允许陈旧的展示可以缓存指针但须承认其期限。版本键解决晚回填覆盖，不能让正在处理版本 7 的旧请求在时间上变成版本 8 的请求。

延迟再删一次，可以缩小某些晚回填窗口，但无法用任意固定等待覆盖所有暂停和失败。数据库事务、Redis 删除、失效消息之间没有天然的跨系统事务；完整组合由 Backend 的一致性设计继续展开，本章先把必须解决的窗口说清楚。

## 5. “及时更新”到底要求多及时

缓存是否可以陈旧，要看它参与的是“展示”还是“关键判断”。例如资料简介短暂旧几秒通常只影响展示；用户是否仍有下载权限，则可能需要在执行动作前重新确认当前权限，不能沿用同样的缓存容忍度。

先约定用户能接受的结果，再选择机制：允许有限陈旧的展示，用期限和失效流程管理；不能接受旧值的关键判断，走能够确认当前业务事实的路径。缓存是在节省重复读取，不是替代授权、额度或其他业务校验。

**理解练习：** 对“资料简介”和“下载权限”分别说明谁是权威、允许旧多久、权威数据变化后怎样让缓存失效。然后用上表检查自己的方案：旧读者恢复时，是否还有机会把旧值写回来？

## 本章小结

旁路缓存由应用安排命中、回源和回填。更新时要先明确权威来源，再处理失效失败与旧读晚回填；可接受的新鲜度决定需要增加哪些保护。

## 🎯 面试怎么回答

**先更新数据库再删除缓存，就一定一致吗？**

> 这是常见起点，但删除失败、旧读晚回填仍会留下旧副本。要根据允许陈旧范围选择重试、可靠失效或版本控制；关键业务判断不能只依靠“缓存应该已经更新”。

## 易错点

> ⚠️ 缓存不存在，不等于业务数据不存在；缓存查到一个值，也不等于它适合当前权限与版本。

> ⚠️ 数据库提交和缓存删除是两个动作，任何一项成功都不能代替另一项的确认。

应用负责。Redis 的空回复只说明缓存查询结果，并没有自动执行后续查库。

</details>

<details>
<summary>2. 旧读晚回填为什么不能只靠“删除成功”排除？</summary>

读取者可能先取得旧值，在更新者提交并删除后才回填，从而重新写回旧内容。

</details>

<details>
<summary>3. 为什么展示信息与关键权限判断可能使用不同读路径？</summary>

两者允许陈旧的后果不同。关键权限判断需要满足当前授权规则，不能用展示缓存的容错范围代替业务确认。

</details>
