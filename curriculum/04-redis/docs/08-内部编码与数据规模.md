# 08｜内存怎样花出去：编码、大小与数据表示

[← 上一章](07-执行模型与Pipeline.md) · [Redis 首页](../README.md) · [下一章 →](09-事务与服务端逻辑.md)

一份用户资料只有几十个字节，存入 Redis 后占用却不止这些。另一个 Hash 内容更多，使用的内部结构还可能不同。要判断容量，不能只把业务文字长度相加。

本章把“提供什么操作”与“怎样在内存里实现”分开，再据此理解大键和更紧凑的数据表示。

## 1. 类型是操作约定，编码是内部做法

Hash 对外提供字段读写，不代表内部永远是一张哈希表。只有几个字段时，字段和值紧凑地放在一块，逐个检查的成本不高，还能减少指针和节点开销；对象变大后，再用适合快速查找的结构。

这类内部表示叫**编码**。TYPE 查看逻辑类型，OBJECT ENCODING 查看当前表示；编码改变后，客户端仍可用 HGET 读字段。

### String：SDS 管长度与容量

Redis 的一般字符串使用 **SDS（简单动态字符串）** 管理字节、长度和分配容量。逻辑长度另行保存，不用扫描到第一个零字节，所以内容可以包含零字节，称为二进制安全。设长度为 3、容量为 8，追加两个字节时先确认剩余空间足够，再写入并把长度改成 5；若空间不足则分配更大区域并搬运原内容。预留容量减少反复追加时的重新分配，但某次扩容仍会复制已有字节。这个 3/8 只是机制示意，不是固定分配阈值。

能用内部整数表示的 String 可采用 int 编码；短字符串还可采用对象头与内容相邻的紧凑分配（embstr），较长或修改后可转为 raw。接口仍是 String，不因编码不同改变 GET 的值。具体头结构与阈值按版本核对，不把早期 SDS 文档的 C 结构当成今天的布局。

### 字典：哈希定位与渐进 rehash

普通大 Hash 与 Set 等场景需要**字典（dict）**。先把键哈希到桶，碰撞时还要比较真实键，哈希相同不代表键相同。桶过挤会增加查找成本，扩容通过新桶数组重新分布条目。

若一次搬完百万项，会长时间占住执行路径。渐进 rehash 让新旧两张桶表暂时并存，分小步搬桶；新加入项进入新表，查找需考虑尚未迁完的两边，搬完后再释放旧表。因此平均快速查找要付出哈希、碰撞与迁移成本，rehash 也会带来暂时的双表内存，而不是一次改容量数字就完成。

### 紧凑容器：listpack、quicklist、intset

**listpack** 把小整数或字符串用变长编码连续排在一块内存，元素带有足以解析长度和向后定位的信息，减少每个元素独立节点与指针开销。代价是按字段查找可能线性扫描，中间插入还可能移动后续字节。小 Hash 把字段和值放进其中，小 ZSet 按顺序保存成员与分数；规模受限时，这些线性工作可以比大量独立分配更合算。

**quicklist** 用链式节点连接多个紧凑块。两端操作只影响附近块，中间访问仍需找到对应节点；块太大时内部搬移成本上升，太小时指针开销上升。List 可以在较小时直接使用 listpack，变大后采用 quicklist 等适合的表示，所以“List 是每个元素一个双向链表节点”不准确。

**intset** 把小规模纯整数成员保存为有序整数数组，通过二分找成员，插入时可能移动后面的元素；出现更宽整数会提升统一编码宽度，加入不能表示为整数的成员或超过适用规模则转用其他集合编码。转换保留 Set 的唯一性，但物理占用会跳变。新版本的小字符串 Set 也可用 listpack，不把 intset→字典当作所有版本唯一的转换路线。

这些结构解释了为什么“大量小对象”与“少量大对象”即使业务字节相同，也不一定占相同内存。[内存优化与编码条件](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)

## 2. ZSet 为什么要兼顾两种找法

排行榜同时要回答“Alice 多少分”和“分数在 80 到 90 之间有哪些人”。按成员快速找到对应值的字典结构适合第一问，但它本身不提供按分数的顺序。

较大 ZSet 的经典实现结合字典和跳表。跳表在有序链之上增加跨越节点的连接：先在较高层跨过一段范围，再下降到更细的位置；找到起点后，沿底层顺序读取结果。

```text
较高层：起点 ─────→ 60 ─────────→ 90
底层：  起点 → 20 → 40 → 60 → 70 → 80 → 90
```

这是原理示意，不是固定的分层规则。字典负责成员定位，跳表支持有序查找；小 ZSet 也可能使用紧凑表示。即使找到起点较快，返回一万项仍要读取并发送这一万项，不能忽略结果规模。

沿图查第一个分数至少 75 的成员：从高层先到 60，下一跳 90 已超过目标，向下；底层由 60 走到 70，再到 80，80 才是起点。查 75～90 则接着取 80、90。随机层高让节点在平均意义上有足够的跨越连接，查找、插入、删除的期望成本为 O(log N)，并非每次最坏情况都保证如此。

修改 Alice 的 score 时，字典帮助找到这个成员的当前分数，排序结构则要维持新的 `(score,member)` 位置；必要时移除旧位置再插入新位置。跳表链接还保存**跨度**，表示跨过多少底层节点，查询排名时沿查找路径累加跨度，就不必从头逐个计数。同分再比较 member，避免多个成员的顺序不确定。字典定位与有序结构是一份逻辑数据的协作视图，更新必须一起维护。[目标版本 ZSet 实现](https://github.com/redis/redis/blob/8.10.2/src/t_zset.c)

## 3. 省内存的前提，是业务允许换一种表示

若只是记录一百万名用户是否签到，可以为每个用户分配一个连续位置，用 0 表示未签到、1 表示已签到。这叫 **Bitmap（位图）**。一百万位的原始内容约为 125000 字节，还不包含 Redis 的附加开销。

它的前提是位置映射可控。直接拿极大的稀疏用户编号作位置，即使只设置少数几个 1，也可能扩展出很大空间。多个日期做交集时，同一位置也必须对应同一个用户。

只需要估算不同访客有多少，可以使用 **HyperLogLog**，用有界的统计结构换取误差。它不能列出全部成员，也不能判断某个指定用户是否来过。官方约 0.81% 的标准误差不是每一次结果的硬误差上限。[HyperLogLog](https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/)

精确成员、开关状态和近似数量是三种需求。不能只看哪个省空间，就把它们互相替换。BITFIELD 的有限位宽整数、共享字段模板等更细做法，保留在[数据表示选读](../examples/labs.md#lab-encoding-extra)，不作为这里的默认优化步骤。

## 4. BigKey 与 HotKey 是两个方向的问题

**大键**（BigKey）是值或集合大到明显增加单次处理成本；**热键**（HotKey）是访问集中到少数键。一个很小的配置可以特别热，一份巨大历史也可以很少访问。

读大 String 要传输全部内容，读大集合的全量结果要遍历许多元素，删除与复制也会变重。可以按用户、时间或业务实体拆分数据，或者只保留最近窗口，但拆分后原来一次操作可能变成多次，聚合和并发也要重新设计。

热读可以通过本地缓存或请求合并减少访问；热写要考虑是否可以按实体拆分。把一个计数分成十份再相加，会改变读取方式，不能继续假定它具有单个原子总数的相同语义。

这里先识别问题；在[问题定位](17-安全与问题定位.md)中，再讨论怎样安全扫描、迁移和清理，而不是为了理解大键先运行一次全库诊断。

## 5. 为什么删除后，进程内存不一定立即下降

实际占用除了值，还包括键、容器结构和内存管理的附加空间。Redis 已释放某个对象后，分配器可能保留页面供下次使用，而不是马上归还操作系统。

所以，业务字节数、Redis 的 used_memory 和操作系统看到的进程驻留内存 RSS 不是同一个口径。MEMORY USAGE 可帮助估计某个键的内存，但不能据一个数字判断全实例还有多少可靠余量。

DEL 可能直接承担较多对象释放工作。UNLINK 先从键空间移除，把适合异步释放的工作交给后台；它改善某些删除延迟，但不会消灭总回收成本，也不承诺 RSS 立刻降低。[UNLINK](https://redis.io/docs/latest/commands/unlink/)

**理解练习：** 一个 20 MB 的值每分钟读一次，另一个 1 KB 的值每秒读八千次。分别说出主要成本，解释为什么前者更需要控制单次大小，后者更需要减少访问集中。数字用于推演，不是通用阈值。

## 本章小结

内部编码在存储开销和访问成本间取舍。大键看单项重量，热键看流量集中；位图和近似统计能节省空间，但必须保留业务真正需要的能力。

## 🎯 面试怎么回答

**ZSet 底层就是跳表吗？**

> 逻辑上它既要按成员查找，又要按分数取范围。较大对象的经典实现结合字典和跳表，小对象可以使用紧凑编码；不能将逻辑类型与一种永久不变的表示画等号。

## 易错点

> ⚠️ Bitmap 的空间受最大偏移影响，不是只按有几个 1 计算。

> ⚠️ 内容字节数不是实例总内存；UNLINK 返回也不代表所有物理内存已归还。
