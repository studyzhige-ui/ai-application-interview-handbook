# 18｜从需求出发，完成一份 Redis 设计

[← 上一章](17-安全与问题定位.md) · [Redis 首页](../README.md) · [综合回顾](../review/README.md)

现在用一个完整但有限的需求检验这些知识：做一个多实例资料助手，用户能登录、读取常用资料说明，并查看自己任务的最近通知。部分只读查询会调用较慢的外部服务，希望复用合适的结果。

不是先往图上放 Cluster、锁和消息队列。**先把每份数据的意义与丢失后果写清楚，再选择最少且足够的机制。**

## 1. 先固定这次设计的条件

本章案例约定：资料正式内容和任务历史已有可靠存储；常用资料说明允许短暂陈旧，但权限检查不能因缓存故障被跳过；页面只显示一个有限的最近通知窗口，完整通知历史另存；外部只读结果是否可复用，由任务的新鲜度和权限范围决定。

服务有多个应用实例，因此登录状态和共享额度不能只保存在某一个实例的内存。下面直接推导 Redis 承担的部分，不要求先实现登录、文档解析或模型推理。

## 2. 按访问方式选择值，按后果选择生命周期

| 数据 | Redis 中可以怎样表示 | 数据不在了怎么办 |
|---|---|---|
| 常用资料说明 | 按资料与版本保存 String，整体读取 | 限制并发地回源，再重建 |
| 登录会话 | String 或 Hash，按实际更新方式选择 | 按会话规则重新认证，不相信旧客户端声明 |
| 每用户最近通知窗口 | 有界 List，消息带稳定标识 | 从历史重建窗口，不能凭窗口补齐全部历史 |
| 外部服务共享限流 | Counter、ZSet 或桶状态 | 按成本与安全要求拒绝、等待或有限降级 |
| 可复用只读结果 | 含权限和版本条件的结果缓存 | 在下游容量允许时重新计算 |

表格没有为每种数据都选择最长 TTL。资料缓存期限来自陈旧容忍度，会话期限来自登录规则，通知窗口长度来自展示需要。它们可以都放在 Redis，但不应因此采用相同淘汰与故障策略。

## 3. 沿一次请求检查遗漏的责任

以“读取资料说明”为例：应用先验证用户身份和资料权限，再检查匹配当前范围的缓存。命中则返回；未命中则在容量允许时读取正式数据，保存副本并返回。

这里需要分别回答：

1. 多个请求同时未命中，是否会重复取得同一份昂贵数据？
2. 正式数据更新后，旧副本怎样失效；晚到的旧读取会不会重新填入？
3. Redis 不可用时，正式存储是否承受得住全部请求？

若这些风险实际存在，就分别加入合并重建、更新与失效流程、回源限制。不要因为三个问题都重要，就不分场景地给每次读取加锁、加事务和重试。

## 4. 用小量级估算看见成本

容量先写成通用关系：

```text
正文近似大小 ≈ 用户数 U × 每用户窗口条数 W × 每条平均字节数 B
```

例如仅作为教学假设，5000 名用户、每人最近 30 条、每条正文平均 400 字节，则正文约为：

```text
5000 × 30 × 400 = 60000000 字节，约 60 MB（十进制）
```

这不是 Redis 实际需要的总内存。还要加键名、列表和对象管理开销、其他数据、客户端缓冲，并为持久化与系统运行留余量。实际部署应抽样测量，不把 60 MB 当成容器内存上限。

吞吐也要按路径估算。若一次业务请求需要多次 Redis 往返，先看是否能减少读取或合理批处理；单个热点仍要观察访问分布，不因为总内存足够就忽略单节点压力。

## 5. 用两个故障场景验证设计，而不是只看正常结果

**场景一：通知已经加入最近列表，确认消息之前工作者崩溃。** 新工作者可能再次接到同一通知。设计必须说明用什么稳定标识识别它，怎样避免重复插入，以及历史与窗口更新之间失败时怎样核对。

**场景二：资料正式版本已更新，但缓存删除失败。** 页面可能继续显示旧说明。设计要说明允许多久、如何补偿失效，以及关键权限或业务确认是否绕过这份展示缓存重新核对。

这些不是 Redis 自动保证的事务。案例中，通知先在可靠历史按稳定事件 ID 确认，Redis 窗口只是可重建展示副本；遇到重复投递，先核对 ID，窗口更新失败可从历史重建。资料更新则保存可重试的失效记录，允许的展示陈旧到期限为止；权限检查始终独立核对。这样即使不实际制造故障，也能沿中断位置解释系统还知道什么。

## 6. 什么时候增加副本、分片或更换存储

如果主要问题是单节点故障后恢复服务，可考虑复制与故障切换；如果数据和分散负载超过单节点能力，再考虑 Cluster。它们不自动消除已确认写丢失，也不把一个热点键均分到所有节点。

如果核心负载需要不同的持久化、容量成本或查询模型，就比较其他存储方案。比较 Redis 与 Aerospike 等 KV 系统时，应核对具体版本和配置的存储位置、操作模型、故障保证与成本，不从“哪个更流行”得出结论。理解这份案例不需要先学习另一套产品的全部命令。

Redis 也提供搜索、向量等能力；是否采用要看索引、过滤、更新和容量需求。本课程把原生键与状态机制作为主线，并不表示 Redis 没有其他能力，也不要求为了功能齐全把所有任务都放在同一实例。

## 7. 回看这份设计为什么成立

这份案例的资料正文、权限和通知历史以可靠存储为准；Redis 按租户与资料版本组织展示副本，以有限 TTL 和失效重试约束陈旧，热点 miss 合并回源；最近通知用有界窗口但可由历史重建；会话丢失要求重新认证；外部昂贵调用先经共享额度原子接纳，Redis 故障时按明确规则拒绝或有限等待。

如果预计资料每秒读取 1000 次、正常命中率 95%，回源约 50 次。若来源只容许 100 次每秒，就把回源控制在这个预算内，超出的请求只可用仍在允许陈旧期的副本或明确降级，不能在缓存故障时把全部 1000 次直接送过去。这些是假设下的推导，不是已经跑出的压测指标。

每个选择都沿着同一条因果线：

```text
需要保存什么 → 怎样查与改 → 什么时候失效
                      ↓
            并发、容量和故障会破坏什么
                      ↓
              用什么机制限制和验证
```

方案可以不使用分布式锁，也可以不部署 Cluster。只要能说明选择与不选择的原因，并且没有把缓存命中、命令成功或消息确认误当成整个业务成功，就已经走出了“Redis 是一个很快的缓存”这一句话。

## 本章小结

Redis 设计从数据和访问需要出发，沿着生命周期、并发、恢复和故障验证展开。工具越多不代表方案越完整；完整的是每个关键结果都有明确依据，每个失败窗口都有可解释的行为。

## 🎯 面试怎么回答

**怎样说明你在项目里为什么使用 Redis？**

> 先指出反复读取或多实例共享的具体状态，说明为什么这种值类型和生命周期合适，再交代权威来源、并发修改、容量和失败行为。最后用真实测量与故障测试说明方案效果，不只说它很快。

**是不是应用越复杂，就越应该把更多状态放 Redis？**

> 不是。先区分可重建副本与唯一记录，评估查询方式和故障后果。Redis 可以承担多种状态，但持久事实、外部副作用、权限和运行恢复仍需明确负责者，不由一个存储名称自动保证。

## 易错点

> ⚠️ 只有正常请求成功，不能证明重复消息、缓存失效失败或重启后仍正确。

> ⚠️ 正文容量估算不包含所有 Redis 和系统开销，不能直接用作部署内存上限。
