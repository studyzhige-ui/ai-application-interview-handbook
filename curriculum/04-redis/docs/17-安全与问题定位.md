# 17｜出问题时，从哪里找到证据

[← 上一章](16-会话与运行状态.md) · [Redis 首页](../README.md) · [下一章 →](18-综合设计与回顾.md)

应用报告“Redis 请求用了 500 毫秒”，Redis 的慢日志却只记录 2 毫秒。两份记录不一定矛盾：一份可能包括排队、取得连接和网络往返，另一份只观察服务器执行命令。

排查不是把 INFO、SLOWLOG、SCAN 和 ACL 全部跑一遍，而是沿一条顺序推进：**先确认现象发生在哪一段，再缩小到具体对象；需要遍历时控制观察成本，需要修改时先定义一致性与回退；结果未知时再决定是否重试，最后确保只有合适的身份能执行这些动作。**

## 1. 先把一次请求拆开测量

沿一次请求，可以区分：应用内排队、等待连接、发送与网络等待、服务器排队和执行、接收与处理响应。有重试时，总耗时还包含前面的失败尝试。

SLOWLOG 主要记录服务器执行命令的时间，不包含与客户端通信的全部时间。因此，客户端的 500 毫秒不能直接减去某条慢日志的 2 毫秒，就断言其余全部是网络问题；还要确认它们对应同一次操作，并逐段观测。[SLOWLOG](https://redis.io/docs/latest/commands/slowlog/)

| 已观察到的情况 | 接下来优先核对 | 不能直接下的结论 |
|---|---|---|
| 应用等待高，Redis 负载不高 | 连接获取、应用排队、重试 | Redis 必然需要扩容 |
| 某类命令耗时高 | 对象大小、返回范围和执行复杂度 | 所有命令都慢 |
| 只有一个节点繁忙 | 键访问是否集中、槽与流量分布 | 分片数量越多越好 |
| 持久化期间延迟上升 | fork、写时复制与磁盘相关记录 | 所有持久化都应关闭 |

这些是调查方向，必须通过对应记录验证。一次相关性不等于已经找到根因。

## 2. 再判断问题是否来自数据规模或访问集中

如果键数量稳定、内存却增长，可以抽查值是否变大、列表是否忘记裁剪；如果临时键越来越多，可以检查 TTL 是否丢失。对象规模已经稳定，而 RSS 与已分配内存差距较大时，再研究分配器和碎片。

常用工具应与问题配对：INFO memory 看实例内存概况，MEMORY USAGE 查看单个键的占用估计，类型对应的长度命令帮助判断集合规模。它们各自回答不同问题，不是都运行一遍就算完成排查。

扫描大键的客户端工具也会增加访问负载。先确认运行目标和采样范围，在已有证据指向的键空间中逐步调查，不在最繁忙时无上限遍历所有对象。

## 3. 需要遍历时，先保证观察动作不会制造新故障

要找出某个前缀下的键，KEYS 会集中遍历整个键空间，大实例上可能长时间占用执行路径。SCAN 则把一次完整迭代拆成多次调用：每次返回本轮结果和下一次要继续使用的游标。

```text
从游标 0 开始 → 取得一批结果和新游标 → 用新游标继续 → 返回游标 0 时结束
```

MATCH 过滤名称，COUNT 提示每次期望的工作量；它不是“保证每页恰好返回这么多条”。某次结果为空但游标非 0，仍需继续。

遍历期间数据可能变化，也可能重复返回某个元素，因此处理应允许重复，不把扫描结果当成静止数据库的一张一致快照。SCAN 遍历键，HSCAN 遍历一个 Hash 的字段；增量迭代减轻单次阻塞，但没有取消总工作量。[SCAN 的保证](https://redis.io/docs/latest/commands/scan/)

## 4. 需要改动时，先定义一致性与回退边界

假设许多实体集中在一个大型聚合键中（大 Hash 是常见例子），准备迁移成按实体分别保存的键。若一边复制、一边继续修改旧结构，较晚更新的值可能在复制之后才写入。直接切换并删除旧结构，就会丢掉这次更新。

迁移方案先回答“写入是否可以暂停”。允许短暂暂停时，可以在暂停范围内完成最终复制、核对与切换；不允许暂停时，需要在复制之外记录期间的增量，再追到一个可确认的切换位置。

| 阶段 | 必须确认的事实 |
|---|---|
| 复制已有数据 | 键、字段、值以及需要保留的期限有没有正确转换 |
| 追平复制期间的变化 | 新写入与删除是否都有去向，旧版本是否会覆盖新版本 |
| 切换读取与写入 | 新数据已可用，旧写入路径不再悄悄产生遗漏 |
| 保留回退再清理 | 回退读取的数据是否仍足够新，哪些旧对象确实可以删除 |

UNLINK 可以减轻一部分释放内存的阻塞，但不能替你确认数据已经迁完整。删除前要确定对象归属和版本，不因名字带“旧”就默认安全。

这是迁移必须满足的条件，不是一份凭几行命令就能套用的在线双写方案。具体记录增量与切换的实现，要根据实际写入入口和一致性要求设计。

## 5. 请求结果未知时，再决定是否重试

一个 INCR 请求没有及时收到回复，可能尚未执行，也可能已经增加，只是回复丢失。直接再 INCR，可能多加一次。先判断操作是否允许重复，再确定核对或重试策略。

假设同时有 1000 个请求失败，每个都立即重试 3 次，包含首次尝试一共可能产生 4000 次请求。退避、随机间隔和总重试预算是为了控制这种放大，而不只是让日志少报错。

对可重建缓存，可以在限制回源量后暂时绕过；会话与权限失败时不能随意放行；任务归属不确定时，继续启动工作可能更危险。故障处理要回到数据语义，不能给所有 Redis 错误使用同一个兜底。

## 6. 最后限制谁能观察和修改什么

Redis 不应直接暴露给不可信网络。网络隔离限制谁能连接，认证确认连接者身份，ACL 进一步限制该身份能执行哪些命令、访问哪些键或频道，TLS 保护传输过程。它们不是一个密码的不同叫法。

例如应用只需要读写自己的缓存，就不应同时获得清空全库、任意配置修改和其他服务键空间的权限。运维工具也要区分只读检查与变更，避免复制一段排障命令就对生产执行破坏性操作。[ACL](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/)

键名、日志、快照和回复都可能暴露信息。不要把原始访问令牌直接放在可观察的键名里；值中的秘密同样需要访问控制，不能因为藏进 Value 就认为安全。

复制、Sentinel 和 Cluster 节点之间也有独立通信路径。保护客户端端口不等于已经保护集群总线；具体配置应按部署版本核对，而不是把本地练习的连通方式直接公开使用。

**理解练习：** 只有应用延迟升高，服务器慢日志没有对应增加。写出两个合理假设，为每个假设选择一项需要补充的测量，并说明什么结果会推翻它。答案不应只是“检查网络”。

## 本章小结

排查先拆分测量范围，再把现象缩小到具体对象。观察要控制成本，变更要定义一致性与回退，结果未知时不能盲目重试；最后用网络边界、身份和 ACL 限制谁能执行这些动作。工具只是证据入口，不替代这条诊断顺序。

## 🎯 面试怎么回答

**Redis 突然变慢，先查什么？**

> 先看客户端计时包含哪些阶段，核对连接等待、网络与服务器执行，再按证据检查对象规模、热点、持久化和系统资源。慢日志短不能直接证明问题全在网络；调整后要用相同负载和测量范围比较。

**在线拆分大型聚合键，怎样避免丢失迁移期间的更新？**

> 先决定能否暂停写入。在线迁移需要已有数据复制、迁移期间的增量和明确切换位置，再核对值、删除与期限，保留可用回退后才清理旧结构。SCAN 和 UNLINK 只是遍历与释放工具，不提供迁移一致性。

## 易错点

> ⚠️ SCAN 游标没有结束时不能因本轮结果为空就停止；COUNT 不是固定页大小。

> ⚠️ 请求超时不证明写入没发生，重复执行前必须考虑操作语义。

</details>

<details><summary>3. SCAN 返回空结果但游标不是 0，应该怎样处理？</summary>

继续使用返回的游标迭代，直到游标变为 0。允许重复处理，不能把整个过程当成一致快照。

</details>
