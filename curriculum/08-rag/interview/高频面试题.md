# RAG 高频面试题

> 基于冻结 `S001–S279` HUMAN-A 的 RAG Canonical 与完整知识体系整理。频率来自独立招聘流程；本文件用于面试化表达，不替代 `docs/` 系统学习。

## 一、Boundary / Pipeline

### 1. 为什么需要 RAG？什么时候 Long Context / Fine-tuning 更合适？
30 秒回答：RAG 主要解决外部、可更新、可引用知识注入；Long Context 适合单次上下文可完整提供的问题；Fine-tuning 更适合行为、风格和稳定任务模式适配，不适合作为频繁更新事实库。选择取决于知识新鲜度、可引用性、成本、上下文规模和行为适配目标。

### 2. Production RAG 的完整链路是什么？
`Corpus → Parse/OCR → Clean → Chunk → Embedding/Sparse Index → Retrieve → Fusion → Rerank → Context → LLM → Citation → Evaluation → Freshness/Permission/Trace`。

### 3. 建 RAG 前为什么先做 Corpus Audit？
因为数据来源、重复、版本、权限、结构和真实规模会决定 Parsing、Chunk、Index、Freshness 与安全方案；脏数据上调 Retrieval 参数没有意义。

### 4. PDF / OCR / Layout 怎样统一处理？
先判断电子文本还是扫描图像，再建立统一 Parsed Document Model，保留 page、block、heading、table、image 与 source lineage，而不是把所有文档直接 flatten 成字符串。

## 二、Chunking

### 5. 为什么 Chunking 是 RAG 核心？
它定义 Retrieval Unit，直接影响 Recall、Precision、Context Noise、Index Size 和最终 Generation。

### 6. Fixed / Recursive / Semantic / Structure-aware 怎么选？
先匹配 Corpus 天然结构：FAQ 按 QA、Markdown 按 Heading、法规按条款、代码按 AST；普通文本可从 Recursive 起步。Semantic 更复杂，只有 Evaluation 证明收益才引入。

### 7. Chunk Size 怎么设？
没有固定最佳值。通过真实 Query Dataset 比较不同 Size/Overlap 的 Recall、Context Token、Duplicate Rate 和 End-to-end Quality。

### 8. Overlap 越大越好吗？
不是。它缓解边界切断，但会增加重复 Embedding、重复 Candidate 和 Context Noise。

### 9. Parent-child 有什么价值？
小块负责精准召回，命中后回取大 Parent / Neighbor，分离 Retrieval 与 Generation 粒度。

### 10. Semantic Boundary Failure 怎么处理？
用 Structure-aware Chunk、Parent-child、Neighbor Expansion 和关系 Metadata 修复条件/结论/例外被切断的问题，并通过 Bad Case 回放验证。

---

## 三、Query Transformation

### 11. Query Rewrite 有什么用？
把口语、代词、上下文依赖表达转换成更适合检索的 Query，但必须保留 Raw Query 防止 Semantic Drift。

### 12. 什么时候应该 Clarify 而不是 Rewrite？
当缺失信息直接决定检索范围或答案正确性，如地区、版本、产品时，应先向用户澄清。

### 13. Multi-query 和 Decomposition 区别？
Multi-query 是同一意图多种表达；Decomposition 是把复杂问题拆成多个子任务。

### 14. HyDE 是什么？
先生成假想答案/文档，再对它 Embedding 用于检索真实文档。假想内容不是 Evidence，只是 Retrieval Representation。

### 15. No-hit 怎么定义？
不是只有 0 结果，而是 Evidence 不足以支持可靠回答；可结合 score、coverage、version、permission、query type 决定 Refuse / Clarify / Fallback。

## 四、Dense / Sparse / Hybrid

### 16. Dense Retrieval 擅长什么？
语义相似但词面不同的 Query/Document 匹配。

### 17. Dense 的短板是什么？
错误码、产品编号、稀有实体、版本号和精确短语。

### 18. BM25 为什么在向量时代仍重要？
它提供精确词项信号，尤其适合错误码、编号、专有名词和短 Query，与 Dense 互补。

### 19. 为什么需要 Hybrid Retrieval？
真实 Query 同时包含语义和精确匹配需求，Dense + Sparse 能覆盖不同 Failure Slice。

### 20. Dense Score 和 BM25 Score 为什么不能直接加？
二者数值含义和分布不同，应使用 RRF、归一化融合或 Reranker。

### 21. RRF 是什么？
基于各路相对排名计算融合分，常见形式 `Σ 1/(k+rank)`，适合异构检索器。

---

## 五、Rerank / Top-K / Context

### 22. 为什么需要 Rerank？
Retriever 以低成本保 Recall；Reranker 在较小候选集上做更精细 Query-Passage 相关性判断，提高最终 Precision。

### 23. 加 Rerank 后反而变差怎么查？
先确认 Ground Truth 是否在 Rerank 输入候选；若在，再检查 Domain Mismatch、Truncation、Query Drift、Score 配置和 Candidate Diversity。

### 24. Top-K 怎么设？
分阶段设置 Candidate Budget：Retrieval 偏大保 Recall，Rerank 和 Context 逐步缩小；通过 Recall、End-to-end Quality、Latency 和 Token Cost 曲线实验。

### 25. Context Construction 为什么不是简单拼 Top-K？
还要做去重、Parent/Neighbor Expansion、Source Diversity、Freshness/Permission 检查、排序和 Token Budget。

### 26. Grounding 和 Citation 的区别？
Grounding 关注 Claim 是否受 Evidence 支持；Citation 关注 Claim 能否映射回具体 Source/Chunk/Version。

## 六、Evaluation

### 27. Recall@K、MRR、NDCG 分别回答什么？
Recall@K 看相关 Evidence 是否进入候选；MRR 看第一个相关结果多靠前；NDCG 适合多个不同相关等级的排序质量。

### 28. RAG End-to-end 要测什么？
至少 Correctness、Faithfulness、Answer Relevance、Citation、Completeness、Refusal，同时保留 Retrieval 指标做分层归因。

### 29. Evaluation Dataset 从哪里来？
优先真实线上 Query、历史 Bad Case 和业务专家标注；合成数据可补长尾，但不应完全替代真实分布。

### 30. LLM Judge 可靠吗？
可以扩展评测规模，但自身有偏差。应固定 Judge Model/Prompt，和人工标注做 Calibration，并版本化。

### 31. 如何证明 Hybrid / Rerank 优化真的有效？
建立稳定 Baseline，做单变量 Ablation，跑固定 Regression Dataset，再通过 Online A/B 验证质量、延迟和成本。

### 32. RAG Bad Case 怎么定位？
`Source → Parse → Chunk → Retrieve → Rerank → Context → Generation` 分层排查。关键检查：正确 Evidence 是否存在、是否进入候选、是否进入最终 Context。

## 七、Production

### 33. 知识库如何做增量更新？
稳定 document/chunk identity + change detection，只重建受影响文档，删除旧 Chunk，更新多索引，并通过 active version / snapshot 控制切换。

### 34. Embedding Model 升级怎么办？
新旧向量空间不要混写，构建新 Index、离线评测、Blue-Green 切流并保留 Rollback。

### 35. 企业 RAG 怎么做权限？
给 Chunk 带 tenant/ACL metadata，尽量在 Retrieval 阶段 Pre-filter；Cache Key 也要包含 Permission Scope 与 Knowledge Version。

### 36. 百 GB / TB 级语料怎么建库？
把 Ingestion 拆成异步可重试阶段，使用幂等、Checkpoint、Backpressure；针对 OCR、Embedding Rate Limit、Index Write 等瓶颈独立扩展。

### 37. RAG Latency 怎么定位？
拆 stage：Rewrite、Dense/Sparse、Fusion、Rerank、Context、LLM TTFT/Decode，分别看 P50/P95/P99。

### 38. RAG Cache 放哪里？
Embedding、Retrieval、Rerank、Answer 都可缓存，但越靠近最终答案，受 Knowledge Version、Permission、Prompt/Model 和 User Context 影响越大。

### 39. GraphRAG 解决什么？
适合显式实体关系和多跳关系检索，但需要解决实体抽取、消歧、关系质量和图更新成本，不是 Vector RAG 的通用替代品。

### 40. Agentic RAG 和固定 RAG 区别？
固定 RAG 预定义一次检索链；Agentic RAG 由 Runtime 根据当前 Evidence 决定是否继续检索、改写、分解或停止，需要 Step/Cost Budget、No-new-evidence 和 Refusal Policy。

## 最后一个 2 分钟回答框架

如果面试官说：**“讲讲你的 RAG 项目。”**

建议顺序：

```text
业务问题 / Corpus
→ 为什么 RAG
→ Parsing / Chunk
→ Retrieval Baseline
→ Hybrid / Rerank
→ Evaluation Dataset / Metrics
→ 一个真实 Bad Case
→ Freshness / Permission / Scale
→ 最终指标与 Trade-off
```

不要只说：

> “我用了 LangChain + Milvus + BGE + Reranker。”

面试官真正想知道的是：为什么这样设计、失败过什么、怎么证明它有效。
