# RAG 面试易错点

> 这份清单专门收集“听起来像答案、但实际上过度简化或边界错误”的说法。

## Corpus / Parsing

1. ❌ RAG 就是 Vector DB + LLM。  
   ✅ RAG 还包含 Corpus、Parsing、Chunk、Query、Hybrid、Rerank、Context、Grounding、Evaluation、Freshness、Permission。

2. ❌ PDF 直接 `extract_text()` 就完成 Parsing。  
   ✅ 还要处理 OCR、Layout、Table、Reading Order、Image 和 Lineage。

3. ❌ 扫描 PDF 和电子 PDF 用同一条文本抽取路径。  
   ✅ 扫描件通常需要 OCR / Vision 路径。

4. ❌ 所有 HTML 标签都应该删除。  
   ✅ Heading、Table、List 等结构可能是重要语义。

5. ❌ Dedup 只节省存储。  
   ✅ 还影响 Candidate Coverage、Rerank、Context Noise 和 Citation。

6. ❌ 相似文档都可以去重。  
   ✅ 版本、型号、地区差异可能是关键事实。

## Chunking

7. ❌ Chunk 越小越精准。  
   ✅ 过小会切断语义并增加索引规模。

8. ❌ Chunk 越大越完整，所以越好。  
   ✅ 过大会稀释语义并增加 Context Noise。

9. ❌ 512 token 是通用最佳值。  
   ✅ 参数依赖 Corpus / Query / Retrieval / Model，必须实验。

10. ❌ Overlap 越大越安全。  
    ✅ 过大会制造重复索引与重复 Context。

11. ❌ Semantic Chunk 一定优于 Recursive。  
    ✅ 复杂策略只有在 Evaluation 证明收益时才值得。

12. ❌ Parent-child 就是多存一份文本。  
    ✅ 核心是分离检索粒度与生成上下文粒度。

13. ❌ Recall 命中相关 Chunk 就代表 Evidence 完整。  
    ✅ Semantic Boundary Failure 可能只召回半条规则。

14. ❌ Chunk 只需要 `text + embedding`。  
    ✅ Production 需要 ID、Version、Section、Lineage、ACL、Embedding Version 等。

## Query

15. ❌ 所有 Query 都应该先 LLM Rewrite。  
    ✅ Rewrite 有 Drift 风险，精确 Query 可能被破坏。

16. ❌ Rewrite 后原 Query 没用了。  
    ✅ 必须保留用于回放、并行检索和 Drift Debug。

17. ❌ Query 信息不足也应该尽量搜。  
    ✅ 关键条件缺失时 Clarification 更可靠。

18. ❌ Multi-query = Decomposition。  
    ✅ 前者是同意图多表达，后者是复杂问题拆子任务。

19. ❌ HyDE 生成的假想答案可以直接当知识。  
    ✅ 它只能作为检索表示，最终 Evidence 必须来自真实 Source。

20. ❌ No-hit 就是 Top-K 为空。  
    ✅ 有候选但证据不足、过期、无权限也属于不可可靠回答。

## Retrieval

21. ❌ Dense 一定比 BM25 高级。  
    ✅ Dense 和 Sparse 使用不同信号，互补而非替代。

22. ❌ Cosine 0.8 = 80% 正确概率。  
    ✅ Similarity 不是 calibrated probability。

23. ❌ 错误码、SKU、版本号也应该主要靠 Dense。  
    ✅ 精确词项通常更适合 Sparse / Keyword。

24. ❌ BM25 只由公式决定。  
    ✅ Analyzer、Tokenization、Field 权重同样关键。

25. ❌ Hybrid = Dense Score + BM25 Score。  
    ✅ 原始分数尺度通常不可直接比较。

26. ❌ Hybrid 一定提升最终答案。  
    ✅ Candidate 增多也可能增加 Noise、Latency 和 Rerank 难度。

27. ❌ RRF 使用原始 Score。  
    ✅ RRF 核心基于 Rank。

28. ❌ 只调 RRF 的 k 就能解决融合问题。  
    ✅ Candidate Budget 和各路 Recall 同样重要。

## Rerank / Top-K / Context

29. ❌ Reranker 能救回没召回的正确文档。  
    ✅ 不在候选集里就无法精排。

30. ❌ Reranker 越大越好。  
    ✅ 还要权衡 Domain、Latency、Cost。

31. ❌ Rerank 后变差就是 Reranker 模型不行。  
    ✅ 先查 Candidate、Truncation、Rewrite、配置和 Diversity。

32. ❌ Retrieval Top-K 就是最终 Context Top-K。  
    ✅ 不同阶段目标不同，应逐层缩小。

33. ❌ K 越大越安全。  
    ✅ 会增加 Noise、Latency 和 Token Cost。

34. ❌ 最终 Context 直接拼 Top-K。  
    ✅ 还要去重、Expansion、Source Diversity、Version/Permission 和 Budget。

35. ❌ Retrieved Text 可以当高优先级 Prompt。  
    ✅ Retrieved Content 应视为 Untrusted Data。

## Grounding / Evaluation

36. ❌ 有 Citation 就等于没有 Hallucination。  
    ✅ Citation 可能不支持对应 Claim。

37. ❌ 引用整个文档 URL 就够了。  
    ✅ 更可靠的是映射到 Version / Chunk / Section / Page。

38. ❌ Recall 提升就说明 RAG 提升。  
    ✅ 最终 Context 和 Generation 可能反而退化。

39. ❌ 一个 RAG 总分就能代表质量。  
    ✅ 应分 Retrieval、Faithfulness、Correctness、Citation、Refusal 等。

40. ❌ LLM Judge 就是真值。  
    ✅ Judge 自身有 Bias，需要 Human Calibration。

41. ❌ 合成 Query 足够代表真实用户。  
    ✅ 真实线上 Query 和 Bad Case 更能代表分布。

42. ❌ Evaluation Dataset 可以随实验变化。  
    ✅ 应版本化并保持可比较。

43. ❌ 一次改多个组件只要最终分高就行。  
    ✅ 无法做因果归因，应 Baseline + Ablation。

44. ❌ 平均分提升就没有 Regression。  
    ✅ 关键 Slice 或 Critical Case 可能退化。

45. ❌ RAG 答错首先换 Embedding Model。  
    ✅ 应先分层做 Bad Case Attribution。

46. ❌ 所有答案错都叫 Hallucination。  
    ✅ 可能是 Source、Parsing、Chunk、Retrieval、Rerank、Context 或 Freshness 问题。

## Production

47. ❌ 更新文档只要写入新 Chunk。  
    ✅ 旧 Chunk、Sparse Index、Cache 也要清理或版本切换。

48. ❌ 新旧 Embedding 可以混在同一 Index。  
    ✅ 向量空间可能不兼容，应版本化 / Blue-Green。

49. ❌ 文件名没变就代表内容没变。  
    ✅ 应用 Content Hash / Version / Event 检测。

50. ❌ 权限可以在生成后检查。  
    ✅ 无权内容最好不进入 Retrieval Candidate 和 LLM Context。

51. ❌ 多租户 Answer Cache 只按 Query 做 Key。  
    ✅ 需要 Permission Scope / Knowledge Version 等边界。

52. ❌ Post-filter 一定安全且简单。  
    ✅ 可能候选不足，也可能让无权内容进入中间层。

53. ❌ Large-scale Ingestion 并发越高越快。  
    ✅ OCR、Embedding Rate Limit、Index Write 等会产生 Backpressure。

54. ❌ 只监控 RAG API 总耗时。  
    ✅ 应分 Rewrite / Retrieve / Fusion / Rerank / LLM 等阶段。

55. ❌ Answer Cache 是最优先的缓存。  
    ✅ 它受 Version、Permission、Prompt、Model、User Context 影响最大，失效最复杂。

56. ❌ 有日志就等于有 Observability。  
    ✅ 需要结构化 Query/Candidate/Score/Version/Latency Trace 才能回放。

57. ❌ GraphRAG 一定优于 Vector RAG。  
    ✅ 只在显式关系、多跳等场景更有价值，并带来图构建和更新成本。

58. ❌ Agentic RAG = 使用 LangGraph。  
    ✅ 核心是 Runtime 动态决定是否检索、重写、继续或停止。

59. ❌ Agentic RAG 可以无限检索直到找到答案。  
    ✅ 必须有 Step/Cost Budget、No-new-evidence 和 Stop/Refusal Policy。

60. ❌ Production RAG 最重要的是选哪个框架。  
    ✅ 更重要的是数据质量、Retrieval/Eval、Freshness、Permission、Trace 和 Failure Recovery。

---

## 最后自检

如果你的项目介绍仍然主要是：

> “用了 LangChain、Milvus、BGE、Reranker……”

还不够。

应该能够继续解释：

```text
为什么这样 Chunk？
为什么需要 Hybrid？
Rerank 变差怎么定位？
Dataset 从哪里来？
怎么证明 Recall 提升？
知识怎么更新？
权限怎么做？
答案怎么回源？
线上 Bad Case 怎么重放？
```
