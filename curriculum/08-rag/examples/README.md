# RAG 机制实验｜排名、证据与版本状态

[← RAG 模块](../README.md) · [综合复习](../review/README.md)

实验使用与正文相同的虚构北辰云政策，观察问题经过排名、预算和版本处理后，证据怎样变化。不需要 API 密钥、数据库或模型下载；Python 是验证机制的示例语言，不是 RAG 的技术限制。

## 运行与重置

语法与标准库兼容基线为 CPython 3.13 及以上。用 `python --version` 确认环境；实际运行范围分别记录在 [课程修订记录](../../../guide/project/rag-reader-revision.md)和 [讲解精修验收](../../../guide/audits/rag-clarity-refinement-2026-09-27.md)，兼容声明不代表每个版本都已执行。

在仓库根目录运行，PowerShell 与常见终端均可：

```bash
python curriculum/08-rag/examples/rag_lab.py
python curriculum/08-rag/examples/refinement_lab.py
python -m unittest discover -s curriculum/08-rag/examples -v
```

前两条输出 JSON，第三条运行全部标准库测试。原实验检查排名、预算与修订状态；补充实验核对正文 BM25 表格、已知条件缺口和发布决策。测试会读取实际 Markdown 中的数值表或 Python 片段，不另抄一份正文来声称一致。

这些程序不连接远端、不写知识库。每次运行重新创建内存状态；交互练习时，用 `ledger = RevisionLedger()` 或重新创建发布记录重置。正文短代码依赖同目录模块，交互练习先进入 `curriculum/08-rag/examples`，再启动 Python。

## 同一组数据

原排名与版本实验的实现来源为 [rag_lab.py](rag_lab.py)，[test_rag_lab.py](test_rag_lab.py)导入它，不维护第二套算法。

| ID | 文档身份 | 文本的作用 | 演示预算单位 |
|---|---|---|---:|
| A | P1，v2 | 购买后 14 天内可申请普通退款 | 70 |
| B | P1，v2 | 专属资源订单例外，需人工复核 | 40 |
| C | P2，v1 | 发票更正，与本题不相关 | 60 |
| D | P3，v1 | 账户停用，与本题不相关 | 30 |

问题是：“标准版订阅购买了 10 天，已经开通专属资源，能按普通规则退款吗？”A 与 B 是人工标注的必要证据，供离线检查，不是系统自动发现的充分性答案。

Dense 样本为 A、C、B，词项样本为 B、A、D。它们是人为设定的排名，不是真实向量模型或 BM25 的运行结果。成本 70、40、60、30 是预算单位，不是实际 Token。

## 实验一：改变排序，观察改变了什么

默认 RRF 名次从 1 开始、常数为 60，预期顺序 A、B、C、D。回到 [第 07 章](../docs/07-RetrievalStack.md)核对 A、B 的贡献。

再调用 `rrf([["X", "Y"], ["Y", "Z"]], constant=1)`。先手算 X、Y、Z 的分数和顺序，检查未出现于某一路的对象有没有错误获得贡献。

<details><summary>参考结果</summary>

Y=1/3+1/2=5/6，X=1/2，Z=1/3，顺序 Y、X、Z。RRF 只改变已有候选排序，不生成新证据。

</details>

## 实验二：为什么精排后不能立即截断

默认演示使用坏排序 A、C、B、D。预算 110，先 Top2 得到 A、C，再装入就只剩 A；保留候选后遍历，跳过放不下的 C，还能装入 B。

任务：确认 `early_top2_context` 和 `keep_candidates_context`；再将顺序改为 C、D、A、B。贪心装包是否总能保证证据完整？

<details><summary>参考结果与边界</summary>

默认分别得到 `["A"]` 和 `["A", "B"]`；新顺序得到 C、D，使用 90 单位，A、B 都放不下。因此贪心只演示顺序和预算，不是语义覆盖优化器。相关判断过程见 [第 08 章](../docs/08-Rerank与CandidateBudget.md)与 [第 09 章](../docs/09-EvidenceDelivery.md)。

</details>

## 实验三：用同一标签比较指标

只有 A 时，Recall=0.5、Hit=1、完整覆盖=0；A、B 都在时三者均为 1。按 [第 10 章](../docs/10-RetrievalEvaluation.md)核对 Precision 的固定 K 分母与 NDCG 理想排序。

任务：只返回 A、相关集合也是 A，但 K=5，Precision 是多少？空相关集合返回 `None` 表示什么？

<details><summary>参考结果</summary>

本实验固定用 K 作分母，因此 Precision=0.2。空相关集合不适合计算 Recall，应转入有独立标签的不可回答与拒答评测，不能伪造 Recall=1。

</details>

## 实验四：迟到、重复、删除与回滚

依次处理 P1 的修订 8、7、9（删除）、8，预期 `accepted`、`stale`、`accepted`、`stale`，末态保留修订 9 的删除标记。同修订相同内容返回 `duplicate`，同修订不同内容抛出 `ValueError`。

把旧知识集合交给当前权限对象过滤，当前已撤销 P1，预期只返回 C、D。

<details><summary>结果证明到哪里</summary>

只验证单进程按给定顺序执行的状态规则，没有真实数据库事务、并发比较更新、持久化或授权服务。多 Worker 和进程重启必须连接真实存储另外测试。

</details>

## 实验五：把数值、支持缺口和切换决策分开验证

[refinement_lab.py](refinement_lab.py)与 [test_refinement_lab.py](test_refinement_lab.py)服务第 07、09、12 章。运行补充演示后，逐项核对：

| 观察项 | 预期 | 验证边界 |
|---|---|---|
| 词频为 1、2、4、8 | 1.000000、1.375000、1.692308、1.913043 | 本文 BM25 公式的演算，不是 Lucene API 实测 |
| tf=1，长度变为平均值两倍 | 0.709677 | 只改变长度条件 |
| 产品、期限已支持，资源状态未检查 | 缺口为 `resource_status` | 判断状态由人提供，函数不读懂政策，也不预先知道 B |
| 从 100 开始，只确认 102、103 完成 | 连续完成进度仍为 100 | ACK 被假设为各必要资源真正可用，不是“收到任务” |
| 补齐 101—103 并通过就绪条件 | 发布记录改为 g2，发布序号 8 | 纯状态转换，不是真实数据库原子比较更新 |
| 按已提交记录作恢复决策 | 104 发往 g2；旧请求仍用 c1，新请求用 c2 | 只模拟决策，不验证日志持久化和真实进程恢复 |

先故意只确认 102、103，尝试发布；再补齐 101。随后把 `resources_ready` 改成 `False`，或使用过期发布序号 7 重复切换。测试要求这些错误条件被拒绝，而不是总能得到“发布成功”。

`support_gaps` 接收的是人工给定的支持状态，不会抽取问题条件或判断原文是否蕴含结论。即使返回空列表，也只说明给定判断表里没有未支持项；不证明判断正确或不存在未知例外。

`publish` 是纯函数：真实控制存储必须把读取、条件检查和记录更新放进一个原子操作，还要核实派发已暂停、在途任务已结束以及各资源可见。内存中重新构造一份记录，不是持久恢复测试。

## 从机制实验到真实系统

接入真实解析器、Tokenizer、Embedding、词项检索、重排与数据库时，记录模型、服务端、客户端、数据和配置版本，再测过滤后的召回、截断、负收益重排、写入可见性、并发、撤权与恢复。

外部语义模型、真实原子发布、权限传播和多服务集成都不在这些确定性实验的验证范围内。
