# 13｜锁过期了，旧工作者为什么还可能继续

[← 上一章](12-Cluster与分片.md) · [Redis 首页](../README.md) · [下一章 →](14-通知与Streams.md)

两台工作者都要刷新同一份昂贵结果，我们希望同一时间只有一台负责。进程内的锁只能约束该进程，不能直接让另一台机器等待，于是需要大家共同认可的所有权记录。

Redis 可以保存一份有期限的锁记录。但真正需要分析的是：**期限到了，旧工作者还没有停，谁来阻止它继续修改结果？**

## 1. 获取锁：同时表达“空闲”和“有效期”

常见形式是 `SET lock_key owner_token NX PX 30000`：键不存在才写入，写入时同时给三十秒期限。这里 NX 表示不存在条件，PX 使用毫秒。

owner token 标识本次申请，通常为每次申请准备难碰撞的标识；不能所有工作者都写 1，也不应反复复用一个机器名。期限让工作者崩溃后锁不会永久留下，这种有限时间的权利也称为**租约**。

不能先 SETNX 再 EXPIRE：进程在两条之间崩溃，就可能留下无期限记录。申请失败时可以拒绝或有限等待重试，不能紧密循环制造新的热点。[锁的基本协议](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

## 2. 释放时，只删除仍属于自己的锁

A 曾经取得锁，后来暂停；租约到期后 B 已获得同一个锁键。A 恢复时直接 DEL，会删除 B 的锁。

所以释放必须把“当前值仍是我的 token”和“删除”绑定在一个原子操作中。先 GET 判断再单独 DEL 也不够，因为检查后仍可能暂停，锁又被另一工作者取得。

短 Lua 可以表达这个比较后删除；Redis 8.4 起的 `DELEX key IFEQ token` 则提供直接的条件删除。具体接口不同，保护的规则相同：不能误删别人的当前记录。[DELEX](https://redis.io/docs/latest/commands/delex/)

## 3. 没误删别人的锁，也可能已经写坏业务

设 A 获得十秒租约，却暂停了十五秒：

| 时刻 | 锁记录 | 工作者行为 |
|---|---|---|
| 起初 | 属于 A | A 开始工作 |
| 十秒后 | A 的租约到期 | A 仍暂停 |
| 随后 | B 获得新租约 | B 写入新结果 |
| 十五秒后 | 当前权利已不是 A | A 恢复，继续写入旧结果 |

即使 A 最后没有删除 B 的锁，旧结果也可能已经覆盖 B。**Redis 中的权利记录变了，不会直接终止另一台机器正在执行的代码。** 安全释放与业务安全是两层问题。

## 4. 续约与 fencing 分别保护哪一层

续约由客户端或应用定期检查 token，再原子延长期限。它让正常长任务不必一次申请很长时间；但执行续约的线程也会暂停，网络也会失败，因此“看门狗”不能消除上表中的所有窗口。

需要资源拒绝旧工作者时，可以引入 **fencing token（隔离令牌）**：每次获得权利有可靠递增的代际。若 B 的代际是 42，资源已接受 42，A 再携带旧的 41 写入，资源直接拒绝。

普通 owner token 区分是哪次申请；fencing token 还表达先后，且必须由**真正被修改的资源**记录并检查。仅把代际放进日志，什么也没有保护。

> ⚠️ 代际必须与获权协议正确关联，且故障恢复后不能倒退。异步复制的 INCR 本身也可能在切换时回退，不能只生成一个递增数字就宣称完成可靠 fencing。资源尚未看到新代际时的行为、同代际重复操作，也需要完整协议定义。

## 5. 故障切换和重复请求仍要处理

A 获锁成功但还没复制，主节点故障；新主没有这把锁，B 再次申请成功。两人都曾得到成功，说明一个异步副本不自动提供严格互斥。

Redlock 通过多个独立节点上的多数获取与有效时间计算降低某些风险，但仍有时间、暂停和资源模型等前提。减少重复计算与保护不可重复付款，需要的安全程度不同，不能背成一种算法适用于所有业务。

**幂等**则回答“同一操作重复到达，是否还得到符合要求的同一业务结果”。锁已经正常释放后，重复请求仍能再次获锁，所以锁不代替稳定操作标识、唯一约束或已完成结果核对。

## 6. 先看能否更直接地表达要求

计数加一先用 INCR；同一任务只能从待处理变成执行中，可以考虑数据库条件更新；同一订单不能重复创建，可以考虑唯一约束和操作记录。跨进程互斥是一个工具，不是所有并发题都必须先套 Redis 锁。

**理解练习：** 沿 A、B 时间线分别放入“token 检查”“续约”“资源检查代际”“业务幂等”。说清每项能挡住哪个错误，而不是回答一串工具名。

## 本章小结

锁获取、期限、安全释放、旧工作者写入和故障切换是连续的问题。租约记录协调权利，但资源侧检查与幂等仍决定过期或重复操作能否造成错误。

## 🎯 面试怎么回答

**Redis 锁有 TTL 和唯一 token 就完全正确吗？**

> 它解决有限时间获取和归属检查，但旧任务可能暂停超过租约后继续写，切换也可能丢失锁记录。应根据资源风险考虑续约、资源侧 fencing 和幂等，不能只证明能加锁就声称业务绝对安全。

## 易错点

> ⚠️ GET 检查后再 DEL 仍有竞争窗口，比较与删除需要原子绑定。

> ⚠️ 续约并不使任务免于暂停，锁记录消失也不会自动取消外部操作。

## 本章自测

<details>
<summary>1. 安全释放能够阻止旧工作者继续写数据库吗？</summary>

不能。它只保证不误删当前锁，数据库修改需要自己的条件或代际校验。

</details>

<details>
<summary>2. 锁释放后，同一个业务请求再来，Redis 会自动认出重复吗？</summary>

不会。需要稳定操作标识和结果核对；锁只协调特定时段的进入。

</details>

<details>
<summary>3. fencing token 只存在请求里，下游不检查，能提供防护吗？</summary>

不能。必须由被保护资源实际记录并拒绝旧代际，还要有可靠的代际来源。

</details>
