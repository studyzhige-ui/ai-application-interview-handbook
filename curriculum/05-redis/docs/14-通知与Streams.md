# 14｜消息发出以后，怎样知道还有什么没做

[← 上一章](13-分布式锁.md) · [Redis 首页](../README.md) · [下一章 →](15-共享限流.md)

配置更新后，只想提醒在线服务尽快刷新；创建了一份文档处理任务，却希望工作者晚一点上线也能取得任务。两者都叫发消息，要求却不一样。

先分清“通知正在听的人”与“留下可以继续处理的记录”，再理解 Redis 的 Pub/Sub 和 Streams。

## 1. Pub/Sub 是在线通知

发布者向一个频道 PUBLISH，当前订阅该频道的客户端可以收到。订阅者离线期间的消息，不会等它上线后自动补发。

这适合配置刷新、页面在线通知等场景，但使用者需要接受或弥补错过通知的情况。例如缓存收到失效消息就清除，漏消息时还可用有限 TTL 或重新校验版本。

PUBLISH 回复订阅数量，不是“这些业务都已经处理成功”。**消息被交给连接，与订阅者完成工作，是两件事。** 关键任务不能只依赖一次在线广播。[Pub/Sub](https://redis.io/docs/latest/develop/pubsub/)

## 2. Stream 先把事件保留下来

Stream 把事件追加到一个有序结构，每条有 ID 和内容。XADD 写入事件，XRANGE 查看范围，XREAD 从指定位置之后继续读取。

例如记录依次为 1000-0、1001-0。客户端已处理到 1000-0，下次从该位置之后读取，就能取得 1001-0。实际常用服务器生成 ID，不需要把这些教学数值作为固定规则。

历史存在于 Stream 中，才有机会在断开后继续读；它能否跨重启保住，还取决于持久化和复制。给临时实例换一种数据类型，不会自动获得磁盘保证。

持续读取要保存进度，不能每次都从“此刻末尾”开始，否则两次请求之间新增的消息可能被跳过。XREAD 的 `$` 适合初次从当时末尾等新消息，后续应使用已取得的具体位置。[XREAD](https://redis.io/docs/latest/commands/xread/)

## 3. 消费组多管理了一本交付账

多个工作者需要分担任务时，消费组记录哪些事件已被交给谁、哪些还没有确认。不同组可以独立处理同一 Stream，同组工作者则可分担新事件。

沿着一条任务看状态：

| 步骤 | Stream 中的事件 | 消费组中的记录 |
|---|---|---|
| 追加任务 42 | 事件存在 | 尚未交付 |
| 交给 Alice | 事件仍存在 | Alice 有一条待确认任务 |
| Alice 完成并 XACK | 事件仍存在 | 这条待确认记录被移除 |

这些待确认项由待确认列表（Pending Entries List，PEL）跟踪。**XACK 改的是交付账，不默认删除原事件，更不会替应用判定外部工作真的成功。** 应在业务要求的处理完成后再确认。[XACK](https://redis.io/docs/latest/commands/xack/)

## 4. Alice 消失以后，Bob 怎样接手

如果 Alice 收到任务后崩溃，事件留在待确认状态。Bob 读取组内新消息，不会因此自动获得所有旧 Pending。应用需要检查待确认记录，按规则接管，例如对空闲超时的任务使用 XAUTOCLAIM。

空闲多久才接管，应根据任务耗时与恢复要求选择。Alice 也可能只是慢或暂时暂停，而不是已死亡；接管修改交付记录，不会把 Alice 的进程停掉。

因此 Bob 接手时，同一条事件可能已经被 Alice 执行过。尤其是“工作成功，但确认之前断开”，重试更不能直接当成首次执行。需要用稳定业务标识检查结果或去重。[XAUTOCLAIM](https://redis.io/docs/latest/commands/xautoclaim/)

## 5. 保留多长历史，决定能恢复多远

Stream 一直增长会占用空间，因此要限制保留时间或长度。XTRIM、XADD 的裁剪选项解决保留问题；近似长度限制不等于永远恰好某个条数。

如果待确认任务对应的原内容已经裁掉，仅剩一个 ID 也无法重建任务。选择期限时，要考虑工作者最长离线时间、失败重试窗口以及其他消费组是否还需要这条内容。

> ⚠️ 收到、处理成功、确认、删除是四个不同事件。不能因为用了 XACK，就声称消息永不丢失且业务只执行一次。

## 6. 根据需要选择，而不是按名字升级

在线提醒可从 Pub/Sub 开始；需要短期历史和读取位置可用 Stream；需要分摊与接管再使用消费组。长期大规模事件平台还需比较保留成本、分区、恢复与运维能力，而不是看到消费组就断言等价于某种专业 MQ。

SSE 或 WebSocket 是把信息交给用户端的传输方式，Pub/Sub 或 Stream 是服务端怎样通知或保存事件，两者可以配合，不是同一层的替代品。

**理解练习：** 工作者完成任务后，在 XACK 前断线。画出事件内容与消费组记录分别剩下什么，再说明新工作者为何要先核对业务结果。完整命令顺序在[消息实验](../examples/labs.md#lab-messages)，正文不要求先读懂多层回复数组。

## 本章小结

Pub/Sub 通知在线订阅者，Stream 保留可读事件，消费组记录交付与确认。恢复依赖历史仍在，避免重复副作用依赖业务核对，而不是一个 ACK 自动完成。

## 🎯 面试怎么回答

**Pub/Sub 与 Streams 最大区别是什么？**

> 前者不为离线订阅者保留历史，后者把事件保存为带 ID 的结构，可继续读取并使用消费组。是否可靠还要看持久化、保留和处理协议；确认与业务幂等不能省略。

## 易错点

> ⚠️ XACK 通常不删除原事件；提前裁剪可能让待确认任务失去内容。

> ⚠️ 接管待办不代表旧工作者已经停止，应准备重复处理。

<details>
<summary>1. PUBLISH 返回 1，是否说明一个服务已完成刷新？</summary>

不是，只表示匹配到的订阅客户端数量，不能代表业务执行成功。

</details>

<details>
<summary>2. 工作已完成但还没确认，新的消费者为什么可能重复执行？</summary>

消费组仍记录待确认，恢复流程可能重新分配。需要根据稳定业务标识核对已完成结果。

</details>

<details>
<summary>3. 消息只保留一小时，消费者离线一天，能保证补齐吗？</summary>

不能。超出保留范围的事件可能已经不存在，必须另外选择足够的存储或恢复策略。

</details>
