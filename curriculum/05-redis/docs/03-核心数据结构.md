# 03｜String / Hash / List / Set / ZSet

传统 Redis 面试最爱问“五种基本数据结构”。

但真正应该学会的是：

> **不同 Value Type 在表达什么数据关系？常见 Command 有什么复杂度？什么时候会因为选型错误变成 BigKey、HotKey 或高延迟？**

---

## 1. 总体对比

| 类型 | 直觉 | 典型用途 |
|---|---|---|
| String | 一个 Key 对一个字节序列 | Cache、Counter、Token、Lock Value |
| Hash | 一个 Key 下多个 Field | User/Profile、对象属性 |
| List | 有序可重复序列 | 简单队列、最近记录 |
| Set | 无序唯一集合 | 去重、成员关系、集合运算 |
| ZSet | Member 唯一 + Score 排序 | 排行榜、Delay/Time 排序、滑动窗口 |

这些不是“Java/Python 容器换个名字”，而是 Redis 服务器端原生数据结构与命令模型。

---

# 2. String

最基础：

```text
SET model:gpt-5:price 10
GET model:gpt-5:price
```

String 可以保存：

- 文本；
- JSON；
- 二进制；
- 整数；
- 浮点数字符串。

## 2.1 Counter

```text
INCR usage:user:1001
INCRBY credits:user:1001 -10
```

服务器端 `INCR` 比客户端：

```text
GET
+1
SET
```

更安全。

## 2.2 条件写

```text
SET lock:job:1 token NX PX 30000
```

后面分布式锁会继续讲。

## 2.3 适合 Cache

```text
SETEX profile:1001 300 '{...json...}'
```

但整块 JSON 的问题是：

```text
只改一个字段
→ 可能要整块读改写
```

这时 Hash 可能更合适。

---

# 3. Hash

```text
HSET user:1001 name Alice age 22 city Shanghai
HGET user:1001 name
HGETALL user:1001
```

适合表达：

```text
一个对象
└─ 多个 Field
```

例如：

```text
agent_run:r1
├─ status = running
├─ step = 7
├─ model = gpt-x
└─ owner = worker-3
```

## 3.1 Hash vs JSON String

Hash：

```text
HSET user:1 city Beijing
```

只改一个 Field。

JSON String：

```text
GET
反序列化
改 city
重新序列化
SET
```

但 Hash 也不是永远更好：

- Field 很多时仍可能是 BigKey；
- 需要原样缓存完整 Payload 时 String 更简单；
- 客户端 JSON Schema 可能更统一。

---

# 4. List

List 是按顺序排列的元素序列。

常见：

```text
LPUSH queue:a task1
RPUSH queue:a task2
LPOP queue:a
RPOP queue:a
```

可以表达简单 FIFO / LIFO。

例如 FIFO：

```text
RPUSH tasks t1
RPUSH tasks t2
LPOP tasks
```

## 4.1 List 的优势

- 两端 push/pop 很自然；
- 有顺序；
- 支持阻塞 pop 等队列式使用。

## 4.2 List 不是通用 MQ

如果你需要：

```text
消费组
消息确认
Pending
Replay
更复杂的持久消费语义
```

应该进一步看 Redis Streams，甚至评估 Kafka / RabbitMQ 等专门 MQ。

不要因为 List 能排队就说：

> “Redis 可以完全替代 MQ。”

---

# 5. Set

Set 表达：

```text
无序
唯一
成员集合
```

例如：

```text
SADD tenant:1:online_users 1001 1002
SISMEMBER tenant:1:online_users 1001
```

常见操作：

```text
SADD
SREM
SISMEMBER
SCARD
SINTER
SUNION
SDIFF
```

适合：

- 去重；
- 权限/标签成员关系；
- 共同关注；
- 黑白名单。

⚠️ 大集合上一次性做巨大 `SMEMBERS` 或复杂集合运算，也可能造成延迟和大响应。

---

# 6. ZSet / Sorted Set

ZSet：

```text
Member 唯一
+
Score
+
按 Score 排序
```

例如排行榜：

```text
ZADD leaderboard 100 user:1
ZADD leaderboard 250 user:2
ZADD leaderboard 180 user:3
```

查询前几名：

```text
ZREVRANGE leaderboard 0 9 WITHSCORES
```

## 6.1 为什么 ZSet 很重要

它能把：

```text
成员判断
+
排序
+
Range Query
```

组合在一起。

常见：

- 排行榜；
- 时间窗口；
- 延迟任务候选集合；
- Sliding Window Rate Limit；
- 按优先级排序。

---

# 7. 复杂度意识

不要只背：

> “Redis 很快。”

你要看具体 Command。

典型直觉：

```text
GET / SET / HGET / SISMEMBER
→ 常见 O(1)

ZADD / ZRANK 等有序结构操作
→ 常见 O(log N) 量级

全量返回大集合 / 大 List
→ O(N) 或与返回元素数相关
```

所以性能问题经常不是：

```text
Redis 本身慢
```

而是：

```text
Value 太大
Command 复杂度太高
返回 Payload 太大
访问过热
```

# 8. 一个 AI 场景怎么选

## Session

```text
session:{id}
```

可以：

- String JSON；
- Hash。

看是否需要局部字段更新。

## Conversation 最近消息

小规模简单列表：

```text
List
```

但完整长期聊天历史通常不应该无限塞一个 List。

## Tenant 可用 Tool 集合

```text
Set
```

## Rate Limit 滑动窗口

```text
ZSet
```

## Model Usage Counter

```text
String + INCRBY
```

# 9. 为什么“一个用户一个超大 Hash”可能出问题

初学者容易设计：

```text
all_users
└─ field user:1
└─ field user:2
└─ ...
```

随着用户数增加：

```text
单 Key 极大
→ BigKey
→ 迁移/删除/复制成本上升
→ 集群上整个 Key 只能落在一个 Slot
→ 热点集中
```

更合理常是：

```text
user:1
user:2
user:3
```

按实体拆 Key。

# 10. 面试怎么答

## Q：Redis 五种常见数据结构分别适合什么？

🎯 **建议回答：**

> String 适合 Cache、Counter、Token 和简单 Value；Hash 适合对象字段；List 适合有序序列和简单队列；Set 适合唯一成员、去重和集合关系；ZSet 在 Set 基础上增加 Score 排序，适合排行榜、时间窗口和滑动限流。实际选型还要看命令复杂度、Value 大小和是否会形成 HotKey / BigKey。

## Q：Hash 一定比 JSON String 好吗？

> 不一定。Hash 适合字段级读写；如果应用总是整体获取和整体替换对象，String JSON 可能更简单。还要考虑序列化、字段数量、BigKey 风险和客户端模型。

# 11. 本章自测

<details>
<summary>1. 为什么滑动窗口限流常用 ZSet？</summary>

因为可以把请求 ID 作为 Member、时间戳作为 Score，然后按 Score 删除窗口外事件并统计窗口内数量。

</details>

<details>
<summary>2. List 能不能直接等价成 Kafka？</summary>

不能。List 可以实现简单队列，但持久消费、消费组、Ack、Replay、跨分区等语义与专业 MQ 不同。

</details>

<details>
<summary>3. 为什么一个超大 Hash 可能是坏设计？</summary>

会形成 BigKey；删除、复制、迁移、网络响应和 Cluster 分片都受单 Key 边界限制，也可能成为 HotKey。

</details>
