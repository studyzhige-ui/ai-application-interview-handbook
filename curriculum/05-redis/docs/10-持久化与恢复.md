# 10｜服务重启后，数据从哪里回来

[← 上一章](09-事务与服务端逻辑.md) · [Redis 首页](../README.md) · [下一章 →](11-复制与Sentinel.md)

Redis 把常用数据放在内存，访问很方便；服务停止以后，这份内存却不能作为恢复依据。要在重新启动后找回数据，需要事先把足够的信息保存到持久介质。

**持久化**解决“重启后怎样重建数据”。Redis 的两条主要思路是保存某一时刻的完整状态，或者记录后续发生的变化，分别对应 RDB 和 AOF。

## 1. RDB：回到拍下快照的那个时刻

假设 10:00 保存时，计数是 10；10:01 增加到 13；10:02 服务故障，而没有更新的保存结果。只用 10:00 的 RDB 恢复，就只能恢复到 10。

RDB 是数据快照，不记录快照之后没保存的修改。它便于作为一个时间点的恢复基线，但两次快照之间的写入可能丢失。

后台保存通常由 BGSAVE 触发。它让子进程基于创建时的数据视图写快照，主进程继续服务。这个过程常涉及 **fork** 和**写时复制（COW）**：父子进程开始共享内存页，父进程以后修改页面时，再为相应内容付出复制成本。

所以后台保存不等于完全没有暂停和额外内存。创建进程、频繁写入带来的复制以及磁盘写入，都可能影响延迟和峰值。[持久化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

## 2. AOF：为恢复记录写入变化

AOF 追加能够重建数据的写入记录。恢复时读取这些记录，把数据恢复到已被可靠保留下来的状态。

要分清三个进展：Redis 内存里已经修改，写入内容已经交给操作系统，存储设备已经兑现持久同步。应用收到了命令成功，并不代表它们在所有配置下同时完成。

`appendfsync` 控制 Redis 如何安排同步：always 更频繁地等待同步，通常增加写入开销；everysec 通常按约每秒同步作折中；no 则由操作系统安排，不由 Redis 主动保证每秒同步。

常说 everysec 可能丢最近约一秒，是常见运行条件下的理解，不是对任意磁盘停顿和故障的绝对上限。持久性最终也依赖操作系统与存储设备的行为。

## 3. 为什么日志还要重写

一个值先后被写成 1、2、3、4，重建当前状态并不一定需要保留这四次历史写法。AOF 重写根据当时的数据生成更紧凑的恢复基线，减少冗余和恢复成本；新产生的写入仍需接着记录。

Redis 7 起的多段 AOF 由基线、增量文件和清单共同组成，基线还可使用 RDB 格式。**RDB 与 AOF 不只是二选一，也不能把现代 AOF 永远当成一个可以随手复制的纯文本文件。** 备份或恢复时要保留完整文件集合。

## 4. 先决定允许丢多少，再选保存方式

| 数据用途 | 需要先回答的问题 |
|---|---|
| 可从业务库重建的介绍缓存 | 冷启动后大量回源能否承受，是否需要预热 |
| 登录会话 | 丢失后是否允许用户重新认证 |
| 唯一任务结果或操作记录 | 最近写丢失会不会导致重复执行或事实无法核对 |

纯缓存有时可以不持久化，但重建也有成本。唯一记录需要更严格的恢复目标，不能只写一句“开启 AOF”就结束设计。恢复时间同样重要：文件存在，却需要很久才能载入，也可能不满足业务要求。

## 5. 备份与恢复演练是另一层保护

误删除可能被写入 AOF，也可能进入下一份快照。保存当前状态，不等于保留一个永远正确的旧版本。备份需要独立的历史恢复点、保留期限和访问控制。

恢复后还应检查业务状态。库存回到了旧值，外部订单可能已经真实成立；不能因为数据能读出来，就直接把失败前的所有工作再做一次。

**理解练习：** 在纸上画出“保存计数 10 → 改成 13 → 故障 → 恢复”。分别说明仅 RDB、已同步相关 AOF、另有旧备份能提供什么。需要实机观察时再做[独立恢复实验](../examples/labs.md#lab-recovery)，不在正在服务的实例随意停机。

## 本章小结

RDB 提供时间点快照，AOF 保存重建所需变化，备份保留独立历史。保存与同步有时间边界，恢复数据后还必须核对真实业务是否可以继续。

## 🎯 面试怎么回答

**RDB 与 AOF 怎样比较？**

> RDB 保存时间点状态，丢失窗口取决于保存进度；AOF 保留写入变化，可靠程度受同步策略影响，并需重写控制体积。两者可配合，选择要看允许丢失、恢复时间和资源开销，还需要独立备份。

## 易错点

> ⚠️ 后台快照仍有 fork、写时复制和磁盘成本，不是零影响操作。

> ⚠️ 持久化会保存误操作，不能代替保留历史版本的独立备份。

</details>

<details>
<summary>2. 为什么 AOF 重写可以减少冗余？</summary>

它依据当前数据构造恢复基线，不需要把所有已被后续修改覆盖的历史操作原样保留。

</details>

<details>
<summary>3. 数据恢复成功后，为什么不能盲目重试所有外部操作？</summary>

外部动作可能已成功，而恢复状态回到了更早时刻。必须按操作标识和外部事实核对，防止重复副作用。

</details>
