# Redis 高频面试题

> 使用方法：先自己口述，再展开参考答案。不要把 30 秒答案当成正文替代品。

## 1. Redis 为什么快？

<details><summary>参考答案</summary>

Redis 主要以内存访问为核心，提供针对数据结构优化的服务器端命令；核心客户端命令执行长期采用 mostly single-threaded 的串行模型，减少共享状态锁竞争和上下文切换，再通过 Event Loop / I/O Multiplexing 管理大量连接。实际延迟仍会受慢命令、BigKey、fork/COW、网络 RTT、Swap 和 CPU 饱和影响。

**追问：** Redis 是不是只有一个线程？为什么慢 Lua 会卡其它请求？

</details>

## 2. Redis 常见数据结构怎么选？

<details><summary>参考答案</summary>

String 适合 Cache/Counter/Token；Hash 适合对象字段；List 适合有序序列和简单队列；Set 适合唯一成员和集合关系；ZSet 通过 Score 排序，适合排行榜和时间窗口。选型还要考虑命令复杂度、Value 大小和 BigKey/HotKey 风险。

</details>

## 3. ZSet 底层是不是跳表？

<details><summary>参考答案</summary>

大规模 ZSet 的经典实现会结合字典和跳表，以同时支持 Member 查找和 Score 有序范围查询；小对象可能采用更紧凑的内部编码，所以不应该说“所有 ZSet 永远就是一个跳表”。

</details>

## 4. Redis 单个命令为什么通常原子？

<details><summary>参考答案</summary>

核心命令执行路径主要串行，一条普通命令执行时不会被另一条普通命令插入中间。但 `GET → 应用计算 → SET` 是多阶段业务流程，不能因为每条命令单独原子就说整体原子。

</details>

## 5. I/O Multiplexing 是什么？

<details><summary>参考答案</summary>

把大量 Socket 交给 OS 统一监听，只返回当前可读/可写的 Ready Event，再由 Event Loop 处理，而不是一个连接绑定一个阻塞线程。在 Linux 上常讨论 epoll。它解决的是连接事件发现，不负责让 Redis 命令并行执行。

</details>

## 6. TTL 的过期删除怎么做？

<details><summary>参考答案</summary>

Redis 组合 Lazy Expiration 与 Active Expiration。访问 Key 时发现过期会懒删除，同时后台周期性抽样清理过期 Key，在 CPU 成本和内存回收之间平衡。

</details>

## 7. TTL 和 Eviction 有什么区别？

<details><summary>参考答案</summary>

TTL/Expiration 是 Key 自己的业务生命周期；Eviction 是实例达到 `maxmemory` 后为了腾空间主动淘汰 Key。两者触发原因不同。

</details>

## 8. Redis 有哪些内存淘汰策略？

<details><summary>参考答案</summary>

可按 allkeys、volatile、noeviction 理解。allkeys 会在所有 Key 中按 LRU/LFU/Random 等选；volatile 只在带 TTL 的 Key 中选；noeviction 内存满后拒绝需要更多内存的写。策略必须和“哪些数据允许被淘汰”匹配。

</details>

## 9. 缓存穿透、击穿、雪崩分别是什么？

<details><summary>参考答案</summary>

穿透是请求数据本身不存在，每次都越过缓存访问 DB，可用参数校验、Negative Cache、Bloom Filter；击穿是单个热点 Key 失效造成并发回源，可用 SingleFlight/Mutex、逻辑过期；雪崩是大量 Key 同时失效或 Redis 整体不可用，需 TTL Jitter、HA 和下游限流/熔断/降级。

</details>

## 10. Bloom Filter 为什么只能说“可能存在”？

<details><summary>参考答案</summary>

多个元素的 Hash Bit 会重叠，因此命中所有 Bit 可能来自别的元素，存在 False Positive；正常正确维护时，不存在的 Bit 可以证明一定不存在。

</details>

## 11. BigKey 和 HotKey 有什么区别？

<details><summary>参考答案</summary>

BigKey 是 Value/Collection 过大，会影响网络、命令执行、删除、复制和迁移；HotKey 是访问流量高度集中，即使只有 1KB 也能把单个 Slot/Node 打满。两者治理方法不同。

</details>

## 12. Redis Cluster 为什么解决不了 HotKey？

<details><summary>参考答案</summary>

一个 Key 只属于一个 Hash Slot，而一个 Slot 在稳定状态由一个 Primary 负责；增加 Cluster 节点只能分散不同 Key，不能自动把同一个热点 Key 横向拆开。

</details>

## 13. RDB 和 AOF 有什么区别？

<details><summary>参考答案</summary>

RDB 是时间点 Snapshot，通常更紧凑、恢复快，数据丢失窗口取决于 Snapshot 周期；AOF 记录写操作，恢复时 Replay，数据安全窗口由 fsync 策略决定，并需要 Rewrite 控制文件膨胀。

</details>

## 14. 为什么 Replica 不是 Backup？

<details><summary>参考答案</summary>

误删除、错误写入也会复制到 Replica；Backup 需要独立历史副本、Retention 和 Restore Point，解决逻辑错误和灾难恢复，而不是只解决节点故障。

</details>

## 15. Redis Replication 是强一致吗？

<details><summary>参考答案</summary>

默认主要是异步复制。Primary 可能在 Replica 尚未同步时就回复客户端成功，因此 Failover 时存在最近写丢失窗口。`WAIT` 可以降低风险，但不会把 Redis 变成严格 CP 强一致系统。

</details>

## 16. Sentinel 解决什么？

<details><summary>参考答案</summary>

为非 Cluster 的 Primary/Replica 部署提供监控、故障判断、自动 Failover 和配置发现。它提升 Availability，但底层复制仍可能异步，因此不保证零数据丢失。

</details>

## 17. Sentinel 和 Cluster 有什么区别？

<details><summary>参考答案</summary>

Sentinel 主要给完整 Keyspace 的单 Primary 架构提供 HA；Cluster 还把 Keyspace 分成 16384 Hash Slot，由多个 Primary 水平分片，并为每个分片做 Replica/Failover。

</details>

## 18. Redis Cluster 为什么是 Hash Slot？

<details><summary>参考答案</summary>

Key 先映射到固定 Slot，再由 Node 负责 Slot。扩缩容时只迁移一部分 Slot，把 Key 到 Slot 与 Slot 到 Node 两层解耦，避免节点数变化导致整个 Keyspace 重算分片。

</details>

## 19. Hash Tag 有什么用？

<details><summary>参考答案</summary>

Key 中 `{...}` 的内容可用于控制 Slot，让多个相关 Key 落同一 Slot，从而支持需要同节点执行的 Multi-key、Transaction 和 Lua。但过度使用会降低分片均衡。

</details>

## 20. Redis Transaction 和 MySQL Transaction 一样吗？

<details><summary>参考答案</summary>

不一样。MULTI/EXEC 让 queued commands 连续执行，不被其它普通命令插入；但运行时错误通常不会让之前已执行命令自动通用 Rollback，也没有 InnoDB 那种 Undo/MVCC 事务模型。

</details>

## 21. WATCH 是什么？

<details><summary>参考答案</summary>

WATCH 是乐观并发控制，不阻止别人修改 Key；在 EXEC 时检查被观察 Key 是否从 WATCH 后发生变化，变化则事务 abort，由客户端重新读取和重试。

</details>

## 22. Pipeline 和 Transaction 的区别？

<details><summary>参考答案</summary>

Pipeline 主要批量发送命令降低网络 RTT；Transaction 关注 MULTI/EXEC 的连续执行与 WATCH 冲突控制。Pipeline 本身不提供事务原子性，也不会因某条失败自动回滚整批。

</details>

## 23. Lua 为什么适合库存扣减、限流、锁释放？

<details><summary>参考答案</summary>

这些逻辑都需要多步骤 read-check-write 原子执行。Lua 把逻辑放到 Redis 服务器内一次执行，避免客户端多命令 Race 和多次 RTT。但脚本必须短小，长 Lua 会阻塞其它命令。

</details>

## 24. Redis 分布式锁最基础怎么实现？

<details><summary>参考答案</summary>

`SET lock_key unique_token NX PX ttl`。NX 保证不存在才写，TTL 防永久死锁，unique token 标识 Owner。释放时必须原子比较 token 后删除，不能直接 DEL。

</details>

## 25. 为什么 TTL + Lua Release 还不是完整正确的锁？

<details><summary>参考答案</summary>

旧 Owner 可能暂停超过 TTL；锁过期后新 Owner 获得锁，旧 Owner 恢复后仍继续产生 Side Effect。需要考虑 Renewal、Fencing Token、Idempotency、状态机和 Failover 窗口。

</details>

## 26. Fencing Token 是什么？

<details><summary>参考答案</summary>

每次获得锁时获取单调递增版本号，下游只接受不小于已见版本的写。即使旧 Owner 恢复，它的旧 token 也会被下游拒绝，从而防 stale write。

</details>

## 27. Redis Pub/Sub 和 Stream 有什么区别？

<details><summary>参考答案</summary>

Pub/Sub 是在线广播，离线 Subscriber 会错过历史消息；Stream 有 Entry ID、Consumer Group、Pending/Ack，可支持更可靠的消费和 Replay。是否替代 Kafka 还要看吞吐、Retention、分区和事件平台需求。

</details>

## 28. 为什么 Redis 常用于 Session？

<details><summary>参考答案</summary>

多实例服务需要共享登录状态，Redis 延迟低且天然支持 TTL，很适合 Session。仍需设计 Sliding/Absolute Expiration、多租户隔离、权限变更失效和 Redis 故障策略。

</details>

## 29. Redis 里的 Agent State 和 Agent Memory 是一个概念吗？

<details><summary>参考答案</summary>

不是。State 是某次 Run 的当前 step、owner、lease、retry 等执行态；Memory 是跨轮/跨任务需要保存和召回的信息语义。Redis 可以是两者的 Storage Backend，但不定义上层 Runtime/Memory 逻辑。

</details>

## 30. Redis 如何实现 Sliding Window 限流？

<details><summary>参考答案</summary>

用 ZSet 保存请求，timestamp 作为 Score、唯一 request id 作为 Member。请求到来时删除窗口外成员、统计窗口内数量、判断是否超限、未超限则加入当前请求。多步骤通常用 Lua/Function 原子执行。

</details>

## 31. Redis 做限流挂了怎么办？

<details><summary>参考答案</summary>

提前定义 Fail-open/Fail-closed。本质是业务策略：普通流量保护可短暂 Fail-open 并有本地兜底；安全、额度硬边界可能 Fail-closed。不能把 Redis 故障时的行为留空。

</details>

## 32. Local Cache + Redis 怎么做一致性？

<details><summary>参考答案</summary>

通常接受短暂 Stale：本地 L1 用短 TTL，Redis 做共享 L2，再用 Pub/Sub/配置推送失效，必要时加 Version。高一致业务不应完全依赖多级 Cache。

</details>

## 33. Semantic Cache 和普通 Cache 有什么不同？

<details><summary>参考答案</summary>

普通 Exact Cache 基于精确 Key；Semantic Cache 用 Embedding Similarity 判断不同 Query 是否可复用结果，因此除 Staleness 外还会有 False Semantic Hit，需要结合 Tenant/Permission/Knowledge Version 和离线 Dataset 验证 Threshold。

</details>

## 34. Redis 突然变慢怎么排查？

<details><summary>参考答案</summary>

先分 Client/Network/Server：看连接池等待和 RTT，再看 Redis CPU、SLOWLOG/Latency、BigKey/HotKey、O(N) 命令、Lua；同时排查 RDB/AOF fork、COW、磁盘 I/O、Expiration/Eviction、Swap 和 Failover。不要直接归因“单线程”。

</details>

## 35. 为什么 Agent 项目里同时需要 MySQL、Redis、Vector DB？

<details><summary>参考答案</summary>

MySQL 是长期结构化业务 Source of Truth；Redis 是低延迟、带生命周期的 Cache/Session/Counter/Hot Runtime State；Vector DB 面向 Embedding/ANN 语义检索。关键是按数据语义和可靠性分层，而不是按“谁更快”选存储。

</details>
