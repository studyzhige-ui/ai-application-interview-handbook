# Redis 面试易错点

这些不是“冷知识”，而是最容易因为背口诀而说错的地方。

## 1. “Redis 是单线程”

更准确：核心客户端命令执行长期主要是 mostly single-threaded；Redis 进程还有后台线程/进程相关工作，现代版本部分网络 I/O 也可使用线程。

## 2. “单线程所以 Redis 快”

过度简化。内存访问、高效数据结构、事件驱动、短命令路径、少锁竞争共同作用。

## 3. “Redis 所有命令都是 O(1)”

错误。`KEYS`、全量集合操作、范围查询、复杂集合运算等都可能是 O(N) 或与返回规模相关。

## 4. “Redis 在内存，所以不会卡”

BigKey、慢命令、长 Lua、fork/COW、AOF I/O、Swap 都会制造延迟。

## 5. “Hash 就是哈希表，ZSet 就是跳表”

逻辑类型和内部编码要分开。小对象可能使用紧凑表示，具体编码也会随版本优化。

## 6. “TTL 到点就精确立即物理删除”

Redis 组合 Lazy + Active Expiration，不是每个 Key 一个精准定时器。

## 7. “Expiration = Eviction”

Expiration 来自 TTL；Eviction 来自 maxmemory 内存压力。

## 8. “LRU 是精确全局 LRU 链表”

Redis 采用近似/采样思想，不维护一个昂贵的全局精确排序。

## 9. “缓存 Hit Rate 99% 就一定健康”

还要看 Miss Cost、P99、BigKey、Eviction、Downstream QPS 和 Cache Pollution。

## 10. “Bloom Filter 命中 = 一定存在”

错误。命中只能说明可能存在；存在 False Positive。

## 11. “穿透、击穿、雪崩都差不多”

穿透：数据不存在；击穿：单热点失效；雪崩：大范围失效/缓存整体故障。

## 12. “Redis Cluster 自动解决 HotKey”

一个 Key 仍只属于一个 Slot，单 HotKey 流量仍集中在一个 Primary。

## 13. “BigKey 就是 Key 名字长”

主要指 Value/Collection 规模大，影响网络、命令、删除、复制和迁移。

## 14. “DEL BigKey 没问题”

大量对象释放可能阻塞，需评估 `UNLINK` 或渐进拆分。

## 15. “有 RDB 就不会丢数据”

RDB 是时间点 Snapshot，最近一次 Snapshot 后仍有数据丢失窗口。

## 16. “AOF 永不丢数据”

仍取决于 fsync 策略和故障时机。

## 17. “Replica 就是 Backup”

逻辑错误、误删除也会复制；Backup 需要独立历史恢复点。

## 18. “Replication = 强一致”

Redis 默认主要异步复制，Failover 可能丢最近 acknowledged write。

## 19. “WAIT 以后就是 CP 强一致”

官方明确不是。它提高副本确认程度，但不把 Redis 变成严格强一致系统。

## 20. “有 Replica 就自动 Failover”

Replica 是副本基础；自动故障切换需要 Sentinel / Cluster 等协调。

## 21. “Sentinel = Cluster”

Sentinel 主要做非分片 HA；Cluster 还承担 Hash Slot Sharding。

## 22. “Redis Cluster 用一致性 Hash”

官方 Cluster 采用 16384 Hash Slot 模型。

## 23. “Hash Tag 越多越好”

Hash Tag 可以让相关 Key 同 Slot，但也可能造成 Slot/流量集中。

## 24. “MULTI/EXEC 和 MySQL BEGIN/COMMIT 一样”

错误。Redis Transaction 没有 InnoDB 那种通用 Undo Rollback 语义。

## 25. “WATCH 会把 Key 锁住”

WATCH 是乐观并发控制，不阻止别人写；提交时检测变化后 abort。

## 26. “Pipeline 就是批量事务”

Pipeline 主要减少 RTT，不提供事务原子性。

## 27. “Pipeline 越大越快”

过大 Batch 会增加 Buffer、单批延迟、错误处理和重试成本。

## 28. “Lua 越复杂越强”

长脚本会占用主命令执行路径，阻塞其它请求。Lua 应短小、确定、有限。

## 29. “SETNX + EXPIRE 两条命令可以加锁”

中间 Crash 会形成没有 TTL 的永久锁。应使用单条 `SET ... NX PX`。

## 30. “释放 Redis 锁直接 DEL”

可能误删已经被新客户端获得的锁。必须校验 Owner Token 后原子删除。

## 31. “有 TTL 就不会出现双持锁”

旧 Owner 可能暂停超过 TTL，新 Owner 获得锁后旧 Owner 恢复继续执行。

## 32. “WatchDog 能保证绝对正确”

暂停超过 TTL 时续约线程也无法运行。

## 33. “Owner Token = Fencing Token”

Owner Token 用于证明当前锁归属；Fencing Token 是单调版本，下游用来拒绝 stale owner。

## 34. “Redis Lock = Idempotency”

Lock 防同时执行；完成释放后重复请求仍可能再次执行。Idempotency 是另一层语义。

## 35. “有 Redis Lock 就不需要数据库事务”

Lock 是并发互斥，Transaction 是数据原子提交，两者不替代。

## 36. “Pub/Sub 可以做可靠队列”

Subscriber 离线时会错过消息，没有持久 Ack / Replay 语义。

## 37. “Streams 有 Consumer Group，所以就是 Kafka”

仍要比较吞吐、Retention、Partition、Replay、生态和运维目标。

## 38. “Session 放 Redis 后就自动安全”

还要设计 Tenant Isolation、TTL、权限失效、TLS/ACL 和 Redis 故障策略。

## 39. “Agent State = Agent Memory”

Runtime State 是当前执行进度/Owner/Lease；Memory 是跨轮/跨任务保存和召回的信息语义。

## 40. “Redis 可以作为所有 Agent Checkpoint 的唯一存储”

取决于恢复和副作用要求。长任务精确 Resume 还要考虑 Durable Checkpoint、状态机和 Idempotency。

## 41. “Semantic Cache 只要相似度高就能命中”

还要考虑 Tenant、Permission、Knowledge Version、Prompt/Model Version 和 False Semantic Hit。

## 42. “Redis 做 Rate Limit，Redis 挂了就统一放行”

必须按业务提前定义 Fail-open / Fail-closed；成本控制和安全额度的策略可能完全不同。

## 43. “Redis 慢一定是服务端单线程满了”

可能是应用连接池、网络、BigKey、fork、AOF、Swap、Failover、Retry Storm 等。

## 44. “自动 Retry 总是提高可用性”

同步重试会放大故障；写操作还可能已经成功但响应丢失，重复执行存在副作用。

## 45. “Redis 和 MySQL 哪个快就用哪个”

存储选型首先看数据语义、Source of Truth、生命周期、查询模式、可靠性和成本，不是只比延迟。
