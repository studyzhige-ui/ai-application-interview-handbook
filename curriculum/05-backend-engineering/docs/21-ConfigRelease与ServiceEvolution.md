# 配置和版本怎样安全改变

[← 部署、探针与停机怎样配合应用](20-ContainerK8s与Deployment.md) · [模块主页](../README.md) · [把通用机制映射到 Java、Spring 与 Go →](22-CrossLanguageRuntimeMapping.md)

限流阈值从 20 改成 200，代码一行没改，下游却被压垮。新版本换了状态格式，回滚程序后又读不懂新数据。配置、代码、数据和服务边界都能改变行为，但不能用同一种“发布成功”来验收。

这一章按影响范围展开：先让一份配置安全生效，再验证小范围行为变化，随后处理旧数据与旧任务，最后判断什么时候值得改变服务边界。

## 1. 配置是应用的输入，必须有明确来源

应用可能读取默认值、配置文件、环境变量和远程配置。谁覆盖谁由项目或框架约定，不存在通用顺序。启动时应形成可检查的 **有效配置** ，即真正被应用采用的值，并校验范围、单位和字段关系。

例如某项目约定环境变量覆盖文件、文件覆盖默认值；超时统一用毫秒，检查总预算大于清理预留，接纳容量不小于工作线程数。这是示例策略，真实项目要明确自己的规则。

非敏感配置可记录值、来源与版本，帮助定位请求为何使用旧阈值。密钥不能跟随完整配置进入日志；密钥轮换按权限、审计和撤销要求另外管理。

## 2. 配置文件变了，不代表运行中请求已安全切换

相关字段要作为一份完整配置生效：先读取、解析并校验整组，再发布 **不可变快照** ，也就是发布后不再逐字段修改的配置对象。一次请求固定使用某份快照，避免前半段按旧预算、后半段按新规则。

| 时刻 | 新到达请求 | 已开始请求 |
|---|---|---|
| 只完成新配置解析，尚未发布 | 仍使用旧快照 | 继续原快照 |
| 新快照通过整体校验并发布 | 获取新快照 | 按明确策略完成原工作 |

快照切换并不等于资源已经更换。连接池、认证材料等可能需重建；旧资源要等其持有者退出后排空关闭，不能只换全局引用就丢掉清理责任。

Kubernetes ConfigMap 的消费方式也不同：环境变量不自动改变运行中进程的值；普通卷更新有传播过程，应用还需重新读取；通过 `subPath` 挂载的文件不接收同样的自动更新。[ConfigMap 更新语义](https://kubernetes.io/docs/concepts/configuration/configmap/)

## 3. 灰度验证要比较同类请求

**Canary（小范围试发布）** 让部分流量先使用新版本，观察后再扩大。用户、输入规模和时间窗口需尽量可比；新版本只接简单输入，延迟更低不证明它更快。

上线前确定停止条件和恢复方法。AI 服务的模型、提示词、检索参数与代码都可能改变结果，因此还要看质量、安全拒绝和外部副作用，不只看 HTTP 错误率。

**Feature Flag（功能开关）** 把行为开启与程序发布分开，需要负责人、默认值、有效期和清理计划。关闭开关能阻止新动作，却不撤销已经执行的动作，仍需核对持久状态。

## 4. 回滚代码，不等于回滚数据

旧服务只认识 `status`，新服务想拆成 `phase` 与 `outcome`。若先删旧字段再发布，回退旧程序也无法恢复正常读写。

**Expand–Contract（先扩展、后收缩）** 把变化拆成兼容阶段：

1. 增加兼容结构，使旧程序仍可运行。
2. 发布能处理新旧表示的代码；过渡期间明确哪份是事实、谁负责同步。
3. 迁移并核对存量数据，也验证旧程序的回退路径。
4. 确认旧读写者和旧消费者退出后，再收缩不需要的表示。

双写不是自行消失的过渡期，不一致仍需发现与修复。消息和任务输入也要有版本：新工作者可能遇到几天前的任务，应兼容读取、显式迁移或明确拒绝不支持版本，不能靠未约定的默认值猜意思。

<a id="6-状态越来越多时先避免组合失控"></a>

## 5. 状态越来越多时，先避免组合失控

把上传、执行、审批与付款组合成一个枚举，就容易出现“上传完成且审批中但付款未知”这样的组合状态。可按责任分成几个维度，再明确允许转换和跨维度条件，而不是为每种页面展示都新增一个持久状态。

例如分别保存审批与执行阶段，同时约束“审批未通过，不得执行外部写入”。拆成两个字段没有自动实现这条约束，检查与修改还应在相应原子边界内完成，必要时使用期望状态或版本条件。

状态重组要同步 API、历史任务、消息消费者、操作后台、观测和恢复工具。新功能通过测试之外，还要回放旧输入与未完成任务，才能判断变化后是否仍可恢复。

<a id="5-服务拆分首先划分业务责任"></a>

## 6. 服务拆分首先划分业务责任

模块内含义清楚之后，再考虑是否移到独立服务。单体可有清晰模块，多个微服务也可互相纠缠。先明确 **业务不变量** ，即变化前后必须一直成立的条件：哪些数据要共同提交，谁有权修改，其他模块如何请求变化。

**DDD（领域驱动设计）** 使用业务概念划分模型与责任； **Bounded Context（限界上下文）** 限定一套概念的适用范围。例如生成模块的“完成”表示内容已生成，结算模块的“完成”可能表示账单已结清，不能用一个共享 status 混合含义。

模块移到网络另一端，会增加超时、鉴权、版本、重试与跨系统一致性问题。独立扩容、发布、团队责任或隔离收益足以承担这些成本时，拆分才可能合适。服务数量不是成熟度指标。

## 本章小结

配置先形成有效值，再整组发布；灰度用可比请求验证。数据、状态与旧任务按兼容阶段演进，程序回滚不等于撤销持久变化。业务责任清楚之后，才判断是否值得跨网络拆成服务。

## 🎯 面试怎么答

**怎样保证配置或版本变化可以安全回退？**

> 明确配置来源、版本与整体约束，单次操作使用一致快照。小范围比较同类流量的错误、延迟、质量和副作用。数据与排队任务采用兼容演进，旧读写者退出后才收缩；关闭新行为与撤销既有效果分开处理，不能只凭二进制可回滚就宣称安全。

## ⚠️ 易错点

> ⚠️ 配置中心发布成功，不表示所有进程与在途任务已安全切换。

> ⚠️ 新字段可读，不表示旧程序还能正确处理新状态。

> ⚠️ 微服务增加网络和一致性边界，不自动改善职责划分。
