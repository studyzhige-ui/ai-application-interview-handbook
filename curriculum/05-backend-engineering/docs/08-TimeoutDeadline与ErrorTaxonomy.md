# 等多久，超时之后还发生什么

[← 到达速度超过处理能力时怎么办](07-Backpressure与RateLimit.md) · [模块主页](../README.md) · [怎样识别同一次操作，避免重复副作用 →](09-APIIdempotency与SideEffect.md)

客户端愿意为一次问答等待 5 秒。服务先排队 2 秒，又给检索 3 秒、模型 5 秒。每个调用都“配置了超时”，总等待却已经违背用户预算。问题不在有没有 timeout 参数，而在这些等待是否围绕同一个结束时刻安排。

## 1. 超时限制一段等待，截止时间限制整个过程

**Timeout（超时）** 通常是某次等待最多持续多久；**Deadline（截止时间）** 是整个工作最晚应结束的时刻。本机可用单调时钟记录起点，防止系统墙上时间调整扰乱耗时计算。

教学预算从时刻 0 到 5 秒。排队和前置处理已经消耗 3.2 秒，还要留 0.3 秒用于收尾，则新外部调用最多只剩 `5−3.2−0.3=1.5 秒`。不能在每一层重新得到一份完整的 5 秒。

```text
总预算：5.0 秒
已消耗：3.2 秒
收尾预留：0.3 秒
本次可分配：1.5 秒
```

这里的数字是教学策略，不是推荐所有服务采用 5 秒。真实预算要结合用户体验、依赖延迟分布和业务结果决定。流式回答还应区分首个有效内容出现时间与完整回答结束时间。

## 2. 连接、获取、读写超时可能不是总时间

HTTP 客户端可以分别限制建连、获取连接池、写数据块、读数据块的等待。以 HTTPX 为例，read timeout 关注等待下一块数据的时间，不是整个响应从头到尾的总期限。因此一个不断缓慢返回小块内容的服务，可能没有触发读超时，却超出用户的总等待预算。[HTTPX 超时分类](https://www.python-httpx.org/advanced/timeouts/)

应同时决定总截止时间和每个阶段的上限。阶段上限不能超过当前剩余预算，但允许根据阶段意义更短。例如池内已经排队太久时，继续占住入口等待未必有价值。

## 3. 预算怎样传到另一台机器

不能把 A 机器的 `monotonic()` 数值原封不动发给 B 当绝对时间。单调时钟的起点是本机解释的，不构成跨机器共同时间轴。

可以传递扣除已耗时间后的剩余预算，并在下一跳重新形成当地截止时间；传输和代理处理仍需纳入有效预算。使用已有 RPC 实现时，要核对其传播方式与语言默认行为。gRPC 将传播的截止时间转换为扣除已耗时间的超时间隔，以处理跨机时钟差异，但应用自己启动的工作仍须响应取消。[gRPC 截止时间传播](https://grpc.io/docs/guides/deadlines/)

## 4. 超时后要分开三份状态

| 状态 | 超时时能够断言什么 |
|---|---|
| 调用方等待 | 调用方的预算已用完，不愿继续等 |
| 本地执行资源 | 需要发起取消与清理，是否已结束还要检查 |
| 远端业务动作 | 可能没开始、执行中或已经提交，不能只凭超时确定 |

如果同步工作仍在线程里运行，调用者退出不等于工作终止。数据库会话也可能仍在执行语句，必须按驱动与数据库的取消、事务和连接清理语义处理。不能归还一条仍处于不明事务状态的连接，让下个请求继承问题。

**取消是协作过程**：上游表达不再需要结果，下游检查取消信号、停止可停止的工作、清理资源。已经发送的通知或已经提交的外部动作不会因为本地抛异常自动消失。[asyncio 取消与清理](https://docs.python.org/3.13/library/asyncio-task.html#task-cancellation)

## 5. 错误分类应指导动作，而不只是美化错误码

输入不合法通常需要调用者修正；没有权限需要停止；暂时容量不足可能允许稍后再试；网络超时可能带来结果未知。即使它们最后都经过一个 API 错误响应，也不应归为同一种自动重试。

对外错误可以包含稳定的错误类型、可关联请求标识以及必要的重试建议；详细堆栈和内部地址留在受控日志里。错误码表示什么，要写入接口约定，而不是仅靠 HTTP 状态码猜是否安全重做。

测量 p99 时也要说明对象和窗口。例如“成功的模型调用中 p99 为 800 毫秒”不等于“全部请求中超过 500 毫秒的比例已知”，更不能凭这个分位点直接推算大多数请求会超时。需要完整的延迟分布以及失败、取消样本的统计口径。

### 代理报错，不等于已经知道业务是否执行

客户端经过网关访问应用时，502 表示代理从上游收到无效响应，504 表示代理没有及时收到完成请求所需的上游响应；它们描述代理观察到的失败，不直接证明数据库未提交。503 则表示服务暂时无法处理请求，例如过载或维护。定位时先确认状态码由哪一层产生，再关联上游日志和业务操作键。[HTTP 5xx 语义](https://httpwg.org/specs/rfc9110.html#status.502)

假设应用已写入订单，却在返回响应前超过网关预算，用户可能收到 504 而订单已经存在。正确做法是查该次业务操作的结果，必要时在幂等保护下恢复；不能因为看到某个 5xx 就无条件重新下单。

## 本章小结

各阶段等待必须使用同一剩余预算。超时、取消请求、资源终结和远端业务结果是不同状态；错误分类应决定修正、停止、核对还是安全重试，而不只是包装异常名称。

## 🎯 面试怎么答

**给每个下游调用设置 5 秒超时，为什么还不够？**

> 每一跳重新计时会让总等待相加。应建立整体截止时间，进入阶段前扣除已耗时间并预留收尾，同时区分池等待、建连、读写空闲超时与完整响应期限。超时后还要取消可停止工作、清理资源，并把可能已提交的动作标为需要核对，不能直接认定失败后重做。

## ⚠️ 易错点

> ⚠️ 同一进程的单调时钟值不能直接作为跨机器绝对截止时间。

> ⚠️ read timeout 可能只限制块间空闲，并不限制整个流总长。

> ⚠️ 等待超时、取消发出、任务停止和外部回滚不是同义词。
