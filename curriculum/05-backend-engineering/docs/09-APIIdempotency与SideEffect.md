# 怎样识别同一次操作，避免重复副作用

[← 等多久，超时之后还发生什么](08-TimeoutDeadline与ErrorTaxonomy.md) · [模块主页](../README.md) · [什么时候值得再试，怎样防止故障放大 →](10-RetryCircuitBreaker与Failover.md)

客户端创建文档后没有收到响应，于是再发一次。服务收到的字节是两份，用户意图却只有一次。幂等设计先识别“同一次操作”，再决定重复到达时怎样处理；只加锁或随机生成编号，都没有回答这个问题。

## 1. 幂等描述效果，不要求每次响应完全相同

**幂等（idempotency）** 指重复执行同一请求，其预期业务效果与执行一次相同。HTTP 的 PUT、DELETE 和安全方法具有相应幂等语义；第一次删除返回成功，第二次返回不存在，响应不同并不自动破坏资源已删除的效果。[HTTP 幂等方法](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

POST 不向通用客户端承诺幂等，业务仍可为它设计稳定操作键与结果记录。相反，把扣款放进 GET，也不会因方法名而变安全。实现应遵守自己宣称的语义。

本例另作一个接口约定：保留窗口内，同键同参数返回原先保存的结果。这比只约束效果更具体，不是所有幂等操作都要逐字返回同一响应。

## 2. 什么信息能够代表同一次操作

先分清编号的对象。客户端保存 doc-42 时，第一次网络请求超时，第二次继续同一保存意图：

| 编号 | 标识什么 | 此次重试怎样处理 |
|---|---|---|
| `doc_id` | 被修改的文档 | 仍是 doc-42，但同一文档可以有许多次合法修改 |
| `operation_key` | 一次逻辑业务操作 | 沿用 K，不能重试时另生成一个键 |
| `request_id` | 一次网络尝试 | 两次尝试可以用不同编号，便于排障 |
| `task_id` | 一项被接受、需要持续跟踪的执行任务 | 查询和恢复沿用任务身份；领取尝试另用代际区分 |

本例由客户端在第一次提交前生成 K。服务按 `团队 + 操作类型 + 操作键` 确定范围，并保存影响业务结果的规范化参数摘要。团队来自可信身份，不是未经验证的请求体。

| 再次到达的请求 | 处理原则 |
|---|---|
| 同作用域、同键、同参数，已有结果 | 授权后返回已有结果 |
| 同作用域、同键、不同参数 | 报告参数冲突，不执行另一件事 |
| 同作用域、同键，仍在处理 | 返回处理中或有界等待，不并行重复执行 |
| 新键 | 当作新业务操作，仍受业务唯一约束限制 |

摘要用于发现同一个键被误用于另一份输入。哪些字段参与、空值和默认值怎样规范化，应写成约定，不能假设所有语言序列化的 JSON 天然相同。

操作记录的寿命决定重复保护窗口。只保留一天却允许三天后无约束重放，旧键可能被当作新操作。应选择更长保存、业务唯一约束或禁止超窗自动重试。供应商也有各自的保留与错误结果复用规则，必须核对。[Stripe 幂等请求规则示例](https://docs.stripe.com/api/idempotent_requests)

## 3. 本地业务修改，怎样和防重记录一起成立

两次并发请求不能都先查“没有记录”，再各自修改业务。需要由存储在竞争时作唯一决定，例如给操作作用域建立唯一约束。下面是过程，不是独立 SQL 脚本：

```text
开始本地事务
  争取写入唯一操作记录
  更新本地业务数据
  保存确定结果
提交事务
提交成功后才报告完成
```

修改必须在 **同一可原子提交的存储边界** 内。提交前失败，业务与操作记录一起回滚；提交后响应丢失，重试读取原结果。唯一冲突后要正确结束失败事务，再按数据库可见性核对记录，不能一直拿旧快照说“没有结果”。[InnoDB 提交与回滚](https://dev.mysql.com/doc/refman/9.7/en/innodb-autocommit-commit-rollback.html)

[配套实验](../examples/README.md)把文档、结果和待发事件放进同一 SQLite 事务，测试六个独立连接同时提交同一键。实验只实现一种文档保存操作，以团队和操作键组成主键；增加其他操作类型时还要扩展作用域。SQLite 写事务串行化不是 InnoDB 行锁，不能照抄后宣称已完成 MySQL 并发验收。

## 4. 外部副作用为什么不能用同一结论

假设业务还要向外部系统发送付费通知：

| 时刻 | 外部系统 | 本地记录 |
|---|---|---|
| 1 | 尚未收到动作 | 处理中 |
| 2 | 已通知并扣费 | 仍在等响应 |
| 3 | 响应丢失，本地重启 | 没有确定结果 |

重做可能再发一次，直接记失败又会隐藏已完成事实。本地事务无法回滚外部已发送的通知。

安全继续需要依据：供应商接受同一幂等键，或可按外部操作编号可靠查询，或存在能核对账本的人工与补偿流程。一次“没找到”可能仍与旧请求竞争，不能忽略外部保证就立即重做。结果不明时保留 unknown 或待核对状态，不伪造成功或失败。

> ⚠️ 租约到期只表示执行权需要重新评估，不证明原工作者没做过外部动作。重新领取之前仍要处理结果未知。

## 5. 锁、幂等与条件更新分别防什么

锁减少同一时刻进入受保护范围的执行者，但释放以后，同一请求仍可重新拿锁。幂等记录识别跨时间重复，版本条件拒绝基于旧状态修改。三者可以组合，不能互相替代。

两名编辑者都读到文档版本 3，分别用新键 K1、K2 保存。它们不是重复请求，幂等记录不会合并。防止旧编辑覆盖时，应在实际更新中检查 `expected_version=3`：先成功者更新到 4，后者仍要求 3，影响行数为 0，应报告冲突。预期版本也要参与参数摘要，不能同键重试时悄悄更改。

实验的 `save_document` 只演示防重与本地事务，新键会产生新版本， **没有实现上述编辑冲突检查** 。用于多人编辑时必须补齐条件与测试。

再看任务接管：A 曾持有租约，B 后来拿到新代际。A 的旧写回由资源检查代际拒绝，B 遇到重复通知则由稳定业务键防重。“拿到锁”一条日志，不能证明这两个问题都解决了。租约和旧工作者的前置模型可回看 [Redis 分布式锁](../../04-redis/docs/13-分布式锁.md)。

## 6. 对象编号与操作编号怎样选择

生成方式应服从编号的用途。数据库自增 ID 依赖数据库协调；随机 UUID 可由多节点独立生成，但仍需考虑随机质量与业务约束。UUIDv7 带有时间有序布局，不能把所有 UUID 都说成无时间顺序，也不能把 v7 当严格全局因果时钟。[UUID 类型与 v7](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7)

采用时间、节点标识和序列号组成的 ID 时，还要处理节点身份冲突、时钟回退和序列耗尽。这些决定生成是否正确； **每次重试都生成新 UUID，仍会把同一操作变成多个键** ，没有解决业务防重。

## 本章小结

先区分对象、操作、网络尝试和执行任务，再定义幂等作用域、参数绑定与保留窗口。本地修改靠唯一约束与事务一起提交；外部动作需要外部幂等或核对协议。锁与版本条件分别处理执行竞争和旧状态修改。

## 🎯 面试怎么答

**有副作用的接口怎样防止重试导致重复？**

> 同一业务意图使用可信作用域内的稳定操作键，重试比较关键参数。本地唯一记录、业务效果与结果放在同一事务；重复到达查结果或返回处理中。外部动作还需供应商幂等或可靠查询，结果未知时不能盲目重做。记录寿命必须覆盖允许重放的时间。

## ⚠️ 易错点

> ⚠️ 对象随机 ID 不识别重试，锁释放后也可重复执行。

> ⚠️ 幂等效果相同，不要求所有响应码相同。

> ⚠️ 租约过期或一次查询没找到，都不能证明旧外部动作不存在。
