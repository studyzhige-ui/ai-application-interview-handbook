# 把应用故障追到 Linux 资源

[← 从慢请求的证据定位瓶颈](18-Observability与PerformanceDiagnosis.md) · [模块主页](../README.md) · [部署、探针与停机怎样配合应用 →](20-ContainerK8s与Deployment.md)

请求持续超时，应用日志只写着“资源不可用”。这时要把问题追到运行它的操作系统：进程是在计算、等待磁盘，还是耗尽了文件描述符？Linux 命令的价值不是名字多，而是每一步都能缩小故障范围。

以下命令为 **只读诊断示例** ，需要相应 Linux 工具和权限。所有输出与数值均是教学构造，不是线上实测；PID、路径和地址必须换成真实目标。不要为了复现案例在生产环境制造泄漏或清空目录。

## 1. 先确认正在观察谁

同一台机器可能有多个工作者与版本。先核对进程号 **PID** 、启动时间、程序及所属容器，避免拿旧进程解释新请求。假设部署信息指出目标 PID 为 1234：

```sh
ps -p 1234 -o pid,ppid,stat,etime,comm
```

`-p` 选择进程，`-o` 选择要看的列。示意输出：

```text
    PID    PPID STAT     ELAPSED COMMAND
   1234       1 Sl      00:18:42 python
```

从左向右读：目标是 1234，父进程是 1；`S` 表示处于可中断睡眠，`l` 表示多线程；已运行 18 分 42 秒；程序名为 python。程序名不足以确定它就是目标服务，还要与部署记录核对。[ps 字段和状态](https://man7.org/linux/man-pages/man1/ps.1.html)

`R` 表示运行中或可运行，`D` 常见于不可中断等待，`Z` 是已退出但尚未被父进程回收的僵尸状态。一次看到 S 不代表服务异常，一次看到 R 也不证明 CPU 持续饱和，应与请求时间连续对照。

容器与宿主机可能使用不同 PID。命名空间、工具安装及 `/proc` 权限也影响可见性；没有输出时先查观察条件，不能直接认定进程不存在。

## 2. 高负载不一定是 CPU 算满

**Load Average（平均负载）** 统计可运行任务与不可中断等待任务等负载情况，不是 CPU 使用百分比。要结合 CPU 数量和采样窗口判断。[Linux loadavg](https://man7.org/linux/man-pages/man5/proc_loadavg.5.html)

| 观察到的组合 | 下一步重点 |
|---|---|
| CPU 持续高，R 状态多 | 定位计算线程，用语言栈或采样分析找热点 |
| CPU 不高，负载高且 D 状态多 | 核对磁盘和其他内核等待，不先认定计算能力不足 |
| 宿主机空闲，容器仍处理慢 | 核对容器的 CPU 配额和限流计数 |

`vmstat 1` 每秒观察一次运行队列、阻塞、交换与 CPU 分类；首份报告与后续间隔报告的统计窗口不同，不把它直接当作刚刚一秒。装有 sysstat 时，可用 `iostat -xz 1` 看设备等待与利用。单个百分比仍不能独立证明根因。

cgroup v2 的 `cpu.stat` 等信息可核对容器是否被配额限制。宿主 CPU 空闲，不保证该容器可获得更多执行时间。[cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

## 3. 内存增长，要分清对象、驻留与限制

进程虚拟地址空间不等于实际驻留内存。 **RSS（驻留集大小）** 反映驻留部分；运行时堆、原生分配、线程栈和文件映射等都可能贡献占用。`/proc/<PID>/status` 提供进程级线索，来源定位还要结合映射和语言工具。[进程状态字段](https://man7.org/linux/man-pages/man5/proc_pid_status.5.html)

内存碎片是空间组织问题，不都叫泄漏：分配块内部可能没用完，可用块也可能分散；分配器还可能保留释放后的内存供复用。对象数量下降而 RSS 不立刻下降，不能单凭这一点判断仍有业务引用泄漏。

容器发生 **OOM（内存不足）** 时，先看所属 cgroup 的限制、使用与事件计数，再查并行任务数、单任务数据量和未释放缓冲。宿主机还有内存，不能否定容器已触及自身限额。

大视频、PDF 和分块上传应限制 **同时驻留的数据** 。流式处理、有限批次和背压共同控制峰值；先切块，再一次性把全部块读入内存合并，并不会自动节省峰值内存。

## 4. 文件描述符与连接，要看目标进程的限制

**文件描述符（FD）** 是进程引用打开文件、套接字等资源的编号。持续创建连接却不释放，可能在 CPU 尚可时先耗尽 FD。

```sh
cat /proc/1234/limits
```

从示意输出中挑出这一行：

```text
Limit                     Soft Limit           Hard Limit           Units
Max open files            1024                 4096                 files
```

软限制是当前执行的额度，硬限制约束软限制可调整到的范围；这里不能因为看到 4096 就按 4096 规划。`ulimit -n` 通常显示当前 shell 的限制，不代替目标服务实际继承的限制。[目标进程 limits](https://man7.org/linux/man-pages/man5/proc_pid_limits.5.html)

再数目标进程当前打开多少描述符：

```sh
ls -1 /proc/1234/fd | wc -l
```

`ls -1` 每行列出一个编号，`wc -l` 数行数。要保留错误输出：若目录不可读、进程已退出或管道报错，不能把得到的 0 当成“没有打开文件”。这是瞬时采样，枚举期间数量也可能变化。[FD 目录](https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html)

想看资源种类，再使用 `ls -l /proc/1234/fd` 查看符号链接目标。`socket:[...]` 指向套接字，普通路径指向文件。`ss -s` 是当前网络命名空间的汇总，不是 1234 独占的连接数；有权限时用 `ss -tanp` 查看 TCP 状态和所属进程，再核对含 `pid=1234` 的行。[ss 选项](https://man7.org/linux/man-pages/man8/ss.8.html)

**CLOSE_WAIT** 表示已收到对端关闭方向的通知，本地尚未完成相应关闭。持续增加时应追查应用释放路径；偶尔存在不等于泄漏。 **TIME_WAIT** 是 TCP 正常关闭中的保护状态，数量多要结合连接建立速率和端口压力分析，不能直接当泄漏改内核参数。

## 5. 磁盘“有文件”和“占空间”不是同一视角

`df -h` 看文件系统空间，`df -i` 看 inode 使用情况，`du` 统计路径可见对象。大量小文件可能先耗尽 inode；文件已删除但仍被进程打开时，路径可能消失，空间却要等最后引用关闭才释放。

因此日志清理后空间没回来，应核对打开文件和日志轮转方式，不是继续删更多目录。临时上传按任务归属、活跃状态和过期策略清理；恢复还依赖某个文件时，不能直接清空整个目录。

## 6. 按证据推进一次排障

把前面的检查串起来。教学条件：服务偶发“无法建立新连接”，进程监控约 30% CPU，请求到达速率基本不变。目标进程的软限制是 1024，按相同间隔得到以下记录：

| 采样时刻 | 打开的 FD | 其中 socket 类型 | 观察事实 |
|---|---:|---:|---|
| 10:00:00 | 510 | 420 | 尚有较多余量 |
| 10:00:30 | 810 | 720 | 30 秒新增 300，主要都是 socket |
| 10:01:00 | 1016 | 926 | 约为软限制的 99.2%，余量很小 |

这支持“目标进程的套接字资源持续累积”这一假设，但 **1016 还没有单独证明已经触发上限** 。还要把失败时刻的 `EMFILE`（进程打开文件过多）等错误，与 FD 采样对齐。只说“连接失败”也可能是池耗尽、对端拒绝或 DNS 故障。

接着在该进程的 `ss -tanp` 行中，持续看到同一下游方向的 CLOSE_WAIT。简化的教学输出如下，地址是文档保留地址，不是真实服务：

```text
State       Recv-Q Send-Q Local Address:Port   Peer Address:Port    Process
CLOSE-WAIT  0      0      192.0.2.20:53110      203.0.113.41:443      users:(("python",pid=1234,fd=901))
```

该行把“TCP 状态”关联到“1234 的 FD 901”。`Recv-Q`、`Send-Q` 是对应排队数据量，不是连接总数；一行也不能证明全部 926 个 socket 都处于该状态。

下一步才进入应用：核对流式响应正常结束、调用取消、异常中断三条路径，是否都关闭响应与连接。若 FD 正常，则回到连接池等待、网络和对端错误继续排查，不为迎合假设只盯着 CLOSE_WAIT。

必要时用有权限、可控范围的 `strace` 或抓包验证系统调用与通信。跟踪可能增加开销并暴露敏感数据，应限制对象、时间和采集内容。

修复后使用相同负载重新观察：FD 是否回到稳定范围，连接失败是否减少，取消与异常是否仍正常收尾。提高上限可能延后报错；如果数量继续单调增长，释放问题没有被修好。

## 本章小结

先找对进程和时间窗口，再区分计算、等待、驻留内存、容器限制、FD 与存储视角。命令输出只是证据：读懂字段、提出假设、再用下一项证据验证，最后在同样条件下检查修复效果。

## 🎯 面试怎么答

**Linux 服务很慢，你会怎样排查？**

> 先确认进程、版本、时间和症状，再结合 CPU、负载、线程状态和容器限制判断在算还是在等。按证据检查内存、FD、连接、磁盘和应用栈；例如 FD 接近目标进程软限制，还需关联错误与套接字状态，不能只看 shell 的 ulimit。修复后在相同负载下复核资源与端到端结果。

## ⚠️ 易错点

> ⚠️ 高 Load Average 不等于 CPU 使用率高，宿主空闲不等于容器没有限额。

> ⚠️ 对象释放后 RSS 不立即下降，不能单凭这一点认定泄漏。

> ⚠️ 全机 ss 汇总不是目标进程连接数；诊断命令报错也不是正常的零结果。

> ⚠️ 删除路径不一定立即释放仍被进程打开的文件空间。
