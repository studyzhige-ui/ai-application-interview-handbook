# 一次请求完成了什么，后端负责到哪里

[模块主页](../README.md) · [哪些状态必须保存，恢复时相信哪一份 →](02-DataLayering与StateOwnership.md)

用户把一份文档交给团队知识库。页面先显示“已接收”，随后显示“处理中”，最后显示“可以检索”。这三句话不是同一个结果：文件可能已经存好，处理任务可能还在排队，检索索引也可能尚未更新。

后端首先要做的不是选择组件，而是让这些说法对应真实状态：谁有权提交，服务接受了什么，哪一步已经完成，发生故障后从哪里查证。这里把 **Backend（后端）** 理解为服务端接收请求、协调数据与计算、执行权限和资源限制、对外提供可核验结果的部分。模型生成只是其中一种工作。

## 1. 沿一份文档走完最小过程

先设三类对象。`team-a` 是经过身份校验得到的团队范围；`doc-42` 是文档；`job-42` 是一次处理任务。文档版本变化可能产生新任务，因此文档和某次处理不能共用含义模糊的编号。

1. 客户端提交文档信息。服务检查身份、大小和格式，再判断成员是否有权修改。知道编号不代表拥有权限。
2. 服务把必须保留的信息提交到存储中。如果承诺接受可靠任务，就应有之后能重新找到的任务记录，而不只是进程内变量。
3. 执行者领取任务、读取输入、完成处理并记录结果。它可以与接收请求的进程不同。
4. 客户端按任务编号查询。满足业务定义的完成条件才展示成功；否则返回处理中、失败或待核对状态。

最小实现也可以由数据库保存任务，执行者定期领取；不要求每个项目先安装消息队列。是否需要队列，取决于吞吐、通知延迟和重放等要求。

## 2. 三种返回方式，改变的是用户如何等待

| 方式 | 同一连接中得到什么 | 连接结束以后需要什么 |
|---|---|---|
| 请求—响应 | 查询结果或已完成的短操作结果 | 已提交数据仍可再次查询 |
| 流式响应 | 逐段内容、进度或事件 | 决定是否继续计算、是否保留事件 |
| 接受长期任务 | 接受状态和任务编号 | 持久任务记录、执行者和查询入口 |

**Streaming（流式传输）** 解决结果逐步到达，不自动解决进程崩溃恢复。 **异步任务** 让提交者不必一直等，不表示任务本身变快。两者可组合：任务持续执行，用户通过可重连的流观察它。

HTTP `202 Accepted` 表示已经接受、尚未完成处理，不证明任务必定成功。接口应提供查询位置并说明状态含义。[HTTP 202 语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)

## 3. 请求经过的每一段，都可能有自己的等待

浏览器把域名解析成可连接的地址，建立或复用连接。请求可能先到代理，再到应用，随后等数据库连接、执行 SQL、调用模型，最后传回结果。

```text
客户端
  │ 请求及凭证
  ▼
代理或网关 ── 选择应用实例
                   │
                   ▼
              应用校验与调度
              ├─ 等待可用资源
              ├─ 读取或提交数据
              └─ 调用模型或其他服务
                   │
                   ▼
               响应或事件
```

**反向代理** 替后方服务接收连接并转发请求； **网关** 通常还集中承担路由、认证接入或流量策略。它们可以由同一软件承担，不必是两个产品。 **应用实例** 是运行中的服务进程或部署副本，不是业务任务。

教学假设：同一串行请求共花 1 秒，排队 600 毫秒、数据库 100 毫秒、模型 250 毫秒、其余 50 毫秒。数据库减半，总时间只是从 1000 降到 950 毫秒。拆开等待才能确定优化位置，换框架不直接消除 600 毫秒排队。

## 4. 执行完成与用户知道完成，是两件事

服务提交文档后，发回结果时连接断开。数据库有新文档，客户端却只见超时。客户端不能据此判断没保存，服务也不能把重试无条件当作新的业务动作。

| 观察位置 | 能确定的事实 | 不能据此确定的事实 |
|---|---|---|
| 客户端超时 | 预算内没拿到结果 | 服务完全没执行 |
| 数据库提交成功 | 这次本地事务已提交 | 外部系统和客户端均已知道 |
| 客户端收到任务编号 | 服务按接口约定接受任务 | 所有阶段已经成功 |

**副作用** 是改变外部可观察状态的动作，例如更新文档、扣款、发送通知。 **结果未知** 不是确定失败，而是调用者暂时无法区分没执行和执行后响应丢失。识别同一操作、保存结果和提供查询入口，正是为了解决这个问题。

<a id="5-当前需要掌握的前提怎样连接后续机制"></a>

框架负责把请求交给处理函数，后端设计还要决定接纳多少工作、记录哪些结果、怎样恢复。即使动作由 Agent 提出，最终数据访问与副作用也要接受服务端权限检查，模型的建议不是执行许可。

## 本章小结

从用户承诺反推职责：接受、业务提交和客户端收到结果要分别判断。短请求、流式连接和长期任务有不同生命周期；可靠后端把它们与权限、资源及可恢复状态连接起来。

## 🎯 面试怎么答

**能调用大模型的接口，离可靠后端还差什么？**

> 先定义接受、完成和失败，再沿请求检查身份权限、输入、资源等待、数据提交和外部调用。长任务需要独立持久状态。超时只表示没及时拿到结果，有副作用时还需稳定操作身份、状态查询和安全重试，并用正常与故障路径验证这些行为。

## ⚠️ 易错点

> ⚠️ 返回 202 不等于完成任务，生成 UUID 也不等于持久化或防重。

> ⚠️ 框架支持并发，不表示数据库、模型配额和等待队列无限大。

## 本章自测

### 1. 文档已提交，响应丢失，客户端重发。客户端知道什么，服务端需要查什么？

<details>
<summary>提示</summary>

把执行与结果传达分开。

</details>

<details>
<summary>参考答案与解释</summary>

客户端只知道没收到结果。服务端应按同一业务操作查询持久记录；每次重发都当新操作，可能重复创建或计费。

</details>

### 2. 同一串行请求的排队、SQL、模型耗时为 700、100、200 毫秒。只把 SQL 降到 50 毫秒，总耗时是多少？

<details>
<summary>参考答案与解释</summary>

总计 950 毫秒，只少了 50 毫秒。再查排队位置、资源持有和到达、处理速率，不能只看总耗时认定 CPU 或数据库不足。

</details>
