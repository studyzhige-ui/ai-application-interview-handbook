# 谁能访问什么，权限怎样贯穿请求与任务

[← 多份数据不一致时，怎样恢复业务正确性](14-Consistency与Compensation.md) · [模块主页](../README.md) · [不可信输入怎样被限制在安全边界内 →](16-BackendSecurity.md)

Alice 属于 team-a，Bob 属于 team-b。Bob 得到了 Alice 文档的编号 doc-42，还拿着自己合法登录后的令牌。服务应该承认 Bob 是谁，却拒绝他读取这份文档。身份和权限是两件事，“用户已经登录”不是数据访问的终点。

## 1. 先建立身份，再判断这次动作是否被允许

**Authentication（认证）** 确认调用者身份； **Authorization（授权）** 判断该身份能否对某个对象执行某项动作。授权需要同时考虑调用者、资源、操作以及业务状态。

读取文档时，服务先验证凭证，形成可信主体，再检查主体是否属于文档团队、是否有读取权。更新还可能要求编辑角色、未锁定状态或特定审批。 **请求中写着 team-a 只是用户提供的输入，不能因此变成可信身份。**

用伪 SQL 表示最小数据边界：`SELECT ... WHERE doc_id = ? AND tenant_id = ?`。第二个参数来自经过验证并授权的团队上下文。一个人加入多个团队、对象共享等情形还需要相应规则，这条过滤不能代替所有权限模型。

随机 ID 也不是访问许可。是否用 403 或 404 隐藏对象存在性，是接口策略；无论响应怎样，都不能返回未授权内容。列表、导出、批量接口、缓存和后台任务必须遵守同一访问边界。

## 2. Session 与 Token，怎样让下一次请求认出用户

**Session（会话）** 常通过一个不透明的随机标识关联服务端状态。浏览器带上标识，服务查出当前用户和会话有效性。服务端能集中撤销会话，但查状态的依赖与容量需要管理。多实例应共享必要状态或采用明确的路由方案，不能依赖某个进程永远不重启。

**Token（令牌）** 是调用者持有的凭证。它可以是不透明字符串，也可以用 JWT 格式承载声明；JWT 不是所有令牌的同义词。 **Bearer Token（持有者令牌）** 通常意味着持有即可使用，因此传输、保存与日志脱敏都重要。

常见的签名 JWT 允许服务验证发行者的签名，但不会自动保密载荷。解码得到 JSON 不等于验签，更不等于授权。[JWT 安全规范](https://www.rfc-editor.org/rfc/rfc8725.html)

### 签名 JWT 的三段分别承载什么

常见紧凑 JWS 形式为 `header.payload.signature`。前两段是 JSON 字节的 Base64url 编码，例如头部说明算法与密钥标识，载荷含 `sub`（主体）、`iss`、`aud`、`exp` 等声明。Base64url 是表示方法，不是加密；不应把隐私信息放进去后认为别人看不懂。

签名或 MAC 针对的是前两段编码文本用点连接后的精确字节。接收方按照预先允许的算法和可信密钥验证：若有人把载荷里的 `sub` 从 Bob 改成 Alice，却没有相应密钥，就不能为修改后的字节生成有效验证值。仅解码出 Alice 的名字没有任何身份保证。

共享密钥算法要求签发方与验证方都妥善保护同一秘密；非对称签名允许签发方保留私钥，验证方使用公钥。密钥轮换时可能需要可信的 `kid` 到公钥映射，但令牌自己提供的 `kid` 只是选取线索，不能让它指向任意外部密钥。三段结构也不代表所有 JWT 都采用这一格式：加密 JWE 有不同结构，本章讨论常见签名形式。[JWS 紧凑表示](https://www.rfc-editor.org/rfc/rfc7515.html#section-3.1)

## 3. 验证 JWT，不只问签名对不对

服务应预先限制算法与密钥来源，核对发行者 `iss`、目标受众 `aud`、有效时间及该类令牌要求的其他声明。不能让不可信的 `alg` 或密钥地址替服务决定验证规则，也不能把给另一服务的令牌直接用于当前 API。

不同用途需要分别验证。例如登录流程中的 ID Token 用于说明用户身份，不应因为也是 JWT，就当成业务 API 的 Access Token。主体与团队声明也要按发行方约定解释，不能信任任意同名字段。

验签完成后仍要判断对象权限。角色声明可能早于权限变更；要求立即撤权时，需要服务端状态查询、权限版本检查或其他撤销机制，而不是只等长期令牌过期。

### 从验证后的主体到一条具体授权规则

**RBAC（基于角色的访问控制）** 用角色组织动作权限，例如 editor 可以更新文档；**ABAC（基于属性的访问控制）** 进一步依据主体、对象和环境属性作决定，例如“属于同一团队、文档未归档且访问来自允许环境”。它们可以组合，角色只是规则输入，不必取代对象级判断。

对 Bob 更新 doc-42 的请求，可以依次检查：凭证有效得到主体 Bob → 查询 Bob 在目标团队的成员关系 → 确认 editor 权限 → 读取 doc-42 的真实团队和版本 → 在允许条件下更新。不能让请求体中的 `tenant_id` 或 `role` 直接覆盖其中任一步。若检查与修改之间文档状态可能变化，应把必要条件放进受保护的更新边界，而不是检查完就无限期信任旧判断。

## 4. OAuth 授权与登录怎样关联

**OAuth 2.0** 解决客户端怎样取得访问资源的授权，不单独定义完整用户登录身份。 **OpenID Connect（OIDC）** 在其上增加身份层，定义 ID Token 等规则。[OIDC Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html)

例如资料助手请求读取用户的云盘。先分清参与者：用户通过浏览器作决定；资料助手是请求授权的客户端；授权服务器发放授权码和令牌；云盘资源服务器检查访问令牌后提供资源。客户端可以有浏览器端和后端，二者承担哪一步要按部署确定。

**授权码不是访问令牌。** 授权码是一次性的兑换凭据，客户端还需到令牌端点兑换，才能获得访问资源的令牌。用户在授权服务完成身份验证，也不等于把账号密码交给了资料助手。

### PKCE 怎样把两次请求关联起来

**PKCE（代码交换证明密钥）** 让兑换者证明：自己持有本次授权开始时准备的秘密。以 S256 方式为例：

1. 客户端为这次流程生成高随机性的 `code_verifier`，保留在对应流程的受保护上下文中。它不是用户密码，也不是跨所有请求共用的固定密钥。
2. 客户端计算 `code_challenge`：对 verifier 做 SHA-256，再用不带填充的 Base64url 编码。授权请求发送 challenge 和方法 S256，不在这次前端跳转中发送 verifier。
3. 用户完成相应授权后，授权服务器返回一次性授权码，并将它与这次 challenge 和相关客户端信息关联。
4. 客户端到令牌端点提交授权码与原 verifier。服务器按同样方法计算 challenge 并比较；不匹配就拒绝兑换，通过 PKCE 及其他必要检查后才发放令牌。

```text
首次授权：客户端保留 verifier V，发送 challenge C
兑换令牌：客户端提交授权码和 V
服务端检查：用收到的 V 算出的 challenge 是否等于先前的 C
```

因此，仅截获授权码的人通常没有 V，无法通过同一次流程的校验。这里的核心是 **先绑定 challenge，后验证 verifier** ，不是“请求里多放一个字符串”。[RFC 7636：PKCE 流程与校验](https://www.rfc-editor.org/rfc/rfc7636.html#section-4)

> ⚠️ PKCE 不替代全部安全检查。客户端仍需可靠关联发起请求与回调，例如使用符合部署要求的 state 校验；重定向地址、授权服务器身份、客户端认证及 OIDC 的相应检查也各有职责。不要记录 verifier、授权码或完整令牌。[OAuth 安全最佳实践](https://www.rfc-editor.org/rfc/rfc9700.html)

### 访问与续期使用不同凭据

**Access Token（访问令牌）** 交给资源服务器使用； **Refresh Token（刷新令牌）** 用于按规则换取新访问令牌，不应当作普通 API 的访问凭据。刷新令牌需要适合部署的保存、撤销和重放保护，例如轮换或发送者约束。能够续期不等于永久有权访问资源。

RFC 9700 要求不使用资源所有者密码凭证授权方式。这不表示历史系统瞬间失效，而是不能继续推荐第三方客户端直接收集用户密码作为现代授权设计。

## 5. 权限要穿过缓存、流和任务

若按 `doc_id` 缓存完整私有响应，并在命中时跳过权限判断，就可能向另一团队泄露。可以缓存范围明确、与用户无关的数据，再在返回前授权；也可按可信访问范围设计键与失效规则。机械给每个键拼 user_id，不能替代完整权限判断。

长连接建立时校验身份，不代表之后永久有效。令牌过期、成员移除或资源权限改变后，要按要求重新校验、限制订阅或关闭连接。重连与历史事件补发也要检查当前访问权。

Alice 在 10:00 有导出权限，10:05 被移出团队，任务 10:10 才执行。若要求撤权立即生效，执行者必须在读取与结果交付前复核，而不是只相信提交时快照。确有业务要求继续执行已经正式授权的任务时，应采用明确政策并留审计，不能默默沿用旧权限。

## 6. 用户确认应该确认哪一个动作

“允许 Agent 操作”不是无限授权。确认应绑定具体对象、动作、参数、有效时间和必要的资源版本。批准的是导出 team-a 的公开摘要，执行时就不能改成导出全部员工资料。

格式正确、权限允许、业务条件成立和用户已确认是不同检查。Schema 校验只能确认金额字段符合类型，不能确认余额足够；有写权限也不意味着可以跳过额度或审批。高风险动作应在实际提交边界再次核对条件，并关联批准与业务操作身份。

## 本章小结

认证确认是谁，授权判断能做什么。Session 与 Token 支持后续请求携带凭证，JWT 验证其声明，OAuth 与 OIDC 分别组织授权与身份流程。PKCE 关联授权与兑换，但对象权限、撤权和执行时复核仍要独立落实。

## 🎯 面试怎么答

**通过 JWT 验证以后，为什么还需要权限检查？**

> JWT 验证确认凭证及其声明符合既定规则，还要核对受众和用途。是否可访问具体对象，要结合当前主体、团队范围、动作与业务状态判断。角色可能已撤销，任务可能延迟执行，缓存也可能跨用户泄露，因此读取、执行和结果交付仍需要相应授权。

**PKCE 为什么能降低授权码被截获的风险？**

> 客户端先保留随机 verifier，只发送变换后的 challenge；服务端把 challenge 绑定到本次授权码。兑换时再用 verifier 重新计算并比较。只有授权码、没有该 verifier 的兑换者不能通过校验；其他回调关联与令牌检查仍按协议执行。

## ⚠️ 易错点

> ⚠️ JWT 解码不等于验签，签名载荷也不默认保密。

> ⚠️ 授权码、访问令牌、刷新令牌用途不同，不能互换。

> ⚠️ 旧审批不覆盖后来改变的对象、参数或资源版本。

### 3. 兑换请求带来了正确授权码，却换了另一个 verifier。服务端应怎样判断？

<details>
<summary>参考答案与解释</summary>

按绑定的方法计算 challenge，与该授权码关联的 challenge 比较。不匹配就拒绝；不能只看授权码存在便发令牌。

</details>

### 机制对照：只把 JWT 载荷中的 sub 改成 Alice，为什么解码成功仍不能证明 Alice 已登录？

<details>
<summary>参考答案与解释</summary>

编码不是认证。签名或 MAC 绑定原来的头部和载荷字节，修改载荷后需要重新产生有效验证值。服务还要检查发行者、受众与时间，再针对真实对象授权。

</details>
