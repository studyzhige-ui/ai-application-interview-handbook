# 从字节到安全请求：TCP、TLS 与 HTTP

[← 哪些状态必须保存，恢复时相信哪一份](02-DataLayering与StateOwnership.md) · [模块主页](../README.md) · [怎样传递结果，断线后怎样继续 →](04-ServiceCommunication与StreamingReliability.md)

你向服务发送“保存文档”，网络却可能丢包、乱序或被旁路观察。应用希望看到完整请求，也希望知道连接的是正确的服务。TCP、TLS 和 HTTP 分别解决这条链上的不同问题，不能把其中一种保证推广成“整个业务可靠”。

## 先找到地址：DNS 不负责传送请求

访问 `api.example.com` 时，程序需要先得到目标地址。应用通常向操作系统配置的解析器查询，解析器可以使用尚未过期的缓存；没有可用结果时，递归解析服务沿域名层级寻找有权回答的服务器，再返回 A（IPv4）或 AAAA（IPv6）等记录。根与上级域通常告诉它“下一步问谁”，并非替每个业务域名保存最终地址。

假设地址记录 TTL 为 60 秒，解析器取得结果 20 秒后再次被询问，仍可能返回旧缓存中的地址。修改权威记录不会主动撤销所有客户端缓存；程序还可能复用先前已建立的连接。因而发布新地址、DNS 缓存更新与旧连接结束，是三个不同事件。

“名称不存在”（NXDOMAIN）、解析服务暂时失败和查询超时也不同。没有得到地址时，还没开始向目标业务服务建连；此时不能把错误归为接口返回 500。DNS 解决命名，TCP 解决传输，TLS 再核对目标服务身份。[DNS 层级、解析与缓存](https://www.rfc-editor.org/rfc/rfc1034.html)

## 1. TCP 交付字节流，不替应用划分消息

**TCP（传输控制协议）** 向应用提供有序、可靠的字节流。发送方把字节编号；接收方报告已经连续收到哪里；发生丢失时，发送方按协议重传。先收到后面的字节，也不能把缺失片段当作正常数据跳过。[TCP 的服务模型](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2)

假设应用先写入 `abc`，再写入 `def`，接收端一次读取可能得到 `abcdef`，也可能先得到 `ab` 再得到 `cdef`。这不是 TCP 弄乱了消息，而是它只承诺字节顺序，不承诺一次写对应一次读。应用协议需要长度、分隔符或帧结构来划定消息，HTTP 就有自己的消息与帧规则。

**UDP（用户数据报协议）** 保留数据报边界，但自身不提供 TCP 同样的有序可靠字节流。应用可以容忍丢失，也可以在 UDP 上构建可靠协议。不能只记“UDP 快、TCP 慢”；要看可靠性工作由哪层完成，以及网络条件和延迟目标。

### 确认的是连续字节，不是“第几个请求”

假设接收端接下来等待编号 1000，发送端发出两段：1000—1499 和 1500—1999。第一段丢失，第二段先到：接收端可以暂存后段，但连续确认位置仍停在 1000。补齐前段后，才能把连续确认推进到 2000，即“下一个希望收到的字节”。选择确认 SACK 可以进一步告诉发送端哪些后段已到，减少无谓重传；它不改变应用看到有序字节流的规则。

发送端在超时或相应丢失反馈下重传。同一批字节可能在网络中出现多份，接收端按序号辨认重复，不向应用重复交付同一段字节。若应用在新连接上重新提交一次保存请求，那是新的一批字节；TCP 无法据此判断两个请求是否属于同一业务操作。

## 2. 建立连接，是双方协商初始序列状态

先只看普通 TCP 建连。客户端初始序列号为 x，服务端为 y：

```text
客户端                         服务端
   ── SYN，seq=x ────────────────>
   <── SYN+ACK，seq=y，ack=x+1 ───
   ── ACK，ack=y+1 ──────────────>
```

SYN 用于同步序列状态，本身占用一个序列号，因此确认值有 `+1`。第二步回复服务端的初始状态，并确认客户端的 SYN；第三步让服务端确认客户端已收到自己的初始状态。发出了回复，不等于已被对端确认。[连接建立](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.5)

连接建立也不是永久可达证明。机器突然断电或网络静默丢包时，不一定立即有关闭消息。应用仍需等待预算，必要时用心跳观察对端是否响应。

## 3. 关闭、流控与拥塞，是三个不同问题

TCP 可以分别关闭两个方向。A 发送 FIN 表示自己不再发送；B 确认后仍可能发送剩余数据。B 也发送 FIN 并被确认后，双方方向才都结束。常见“四次挥手”表达两组关闭与确认，报文可能合并，不保证抓包总有四个独立包。

**半关闭** 是一个方向正常关闭； **半开连接** 是双方对连接是否存在的认知不一致，不要混淆。[关闭连接](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6)

**流量控制** 避免发送速度超过接收端可接纳能力，接收窗口告诉发送端还能接收多少。 **拥塞控制** 避免把网络路径压垮，发送端依据确认、丢失等反馈调节发送量。应用读得慢与网络拥塞都可能造成慢，但原因不同；TCP 流控也不会自动限制已进入业务队列的任务。[拥塞控制基础](https://www.rfc-editor.org/rfc/rfc5681.html)

### TIME_WAIT 在等待什么

主动关闭的一方通常进入 TIME_WAIT，保留一段时间的连接状态。假设最后一个 ACK 丢失，对方会再次发送 FIN；保留状态的一方仍能重新确认。等待也让旧连接残留的报文有时间消失，降低相同端点组合被复用后与新连接混淆的风险。

因此看到 TIME_WAIT 不等于连接泄漏，也不是某个业务线程还在执行。大量短连接可能带来端口与内核资源压力，应先看连接频率和复用方式；CLOSE_WAIT 则表示已收到对方关闭、应用本端尚未完成关闭，排查方向不同。具体计时与复用受协议与系统配置约束。[TCP 关闭状态](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6)

## 4. TLS 让链路保密，并验证对端身份

建立 TCP 连接只表示能交换字节，还没有回答“连到的是谁、途中能否被窥视或篡改”。 **TLS（传输层安全协议）** 提供通信加密、完整性保护和对端认证能力。

先分清两个工作。 **身份认证** 检查对端是否有权代表目标服务； **密钥协商** 让双方得到保护本次通信的密钥。公钥可以公开，私钥应由持有者保管；数字签名可帮助验证握手确由对应私钥持有者参与，而不是把公钥当作秘密。

以浏览器访问指定域名、采用 TLS 1.3 证书认证的常见完整握手为例：

| 阶段 | 谁发出什么 | 对方据此做什么 |
|---|---|---|
| 客户端发起 | 支持的协议参数与临时密钥交换信息 | 服务端选择可共同使用的参数 |
| 服务端回应 | 选定参数与自己的密钥交换信息 | 双方各自在本地导出相应握手密钥，不把最终密钥直接明文发送 |
| 服务端证明身份 | 证书、对握手内容的签名及握手校验信息 | 客户端核对身份和握手完整性 |
| 客户端确认 | 自己的握手校验信息 | 服务端按协议确认本次握手，应用数据使用相应通信密钥保护 |

这张表说明职责，不是每个数据包的精确顺序；会话恢复等路径也不能直接套用。

客户端验证证书时，要检查目标名称、有效期和信任链。 **信任链** 把服务证书逐级连接到客户端已信任的签发机构；握手签名则帮助确认对端实际掌握相关私钥。否则，仅复制一份公开证书不应足以冒充服务。

密钥交换与身份签名不是同一件事。TLS 1.3 后续大量数据主要由对称加密保护，而不是“用证书里的 RSA 公钥加密所有业务数据”。握手部分信息本身也会受到相应密钥保护。[TLS 1.3 握手与认证](https://www.rfc-editor.org/rfc/rfc8446.html#section-2)

> ⚠️ 关闭证书验证，会失去对端身份检查。应核对证书、域名、信任链和系统时间，而不是把 `verify=False` 当正常修复。

TLS 保护这段传输，不判断当前用户是否有权读取 doc-42。代理终止 TLS 后，代理到应用是另一段链路；浏览器的小锁图标不能证明所有内部跳转均已加密。

## 5. HTTP 版本改变传输组织，不改变业务完成含义

HTTP 描述请求方法、目标资源、状态码、头部与消息内容。下面比较连接和流的组织方式，不把版本当性能排名。

| 协议 | 主要承载 | 多请求怎样共享资源 | 边界 |
|---|---|---|---|
| HTTP/1.1 | TCP；HTTPS 还使用 TLS | 复用连接，常见客户端用多个连接并发 | 串行响应或排队可能限制并发；复用不等于永久连接 |
| HTTP/2 | TCP；常见部署使用 TLS | 多个 stream（流）在一条连接多路复用 | TCP 字节缺口仍可能影响这条连接上的多个流 |
| HTTP/3 | UDP 上的 QUIC | QUIC 提供可靠的独立流并集成 TLS 安全机制 | 特定流丢失不必阻塞其他流交付，但仍共享拥塞等资源 |

**队头阻塞** 指后续工作必须等前面的缺口或任务完成。HTTP/2 拆开应用层流，但仍共享 TCP 有序字节流；HTTP/3 把可靠交付安排到 QUIC 的各个流中，不是取消可靠性或所有等待。[HTTP/2 标准](https://httpwg.org/specs/rfc9113.html)；[HTTP/3 与 QUIC](https://www.rfc-editor.org/rfc/rfc9114.html#section-2)

HTTPS 的 HTTP/1.1、HTTP/2 使用 TLS 与 TCP；HTTP/3 使用集成 TLS 握手的 QUIC，再由 UDP 承载。不能给 HTTP/3 额外套 TCP。

### HTTP/2 的“交错”究竟是什么

一次请求属于一个 stream，每个 HEADERS、DATA 等帧带有流标识。连接可以依次承载“流 1 的响应头 → 流 3 的响应头 → 流 3 的数据 → 流 1 的数据”，接收方再按标识拼回各自消息，不要求流 1 的整份响应结束才开始流 3。

但这些帧仍被编码进同一条 TCP 字节流。若承载流 1 某帧的字节丢失，后面已经到达的流 3 帧也可能暂时不能交给 HTTP/2 解析器。这是传输层的连续字节要求。流控又是另一件事：HTTP/2 同时有连接级和流级 DATA 窗口，某个流自己的窗口耗尽不等于其他流窗口也耗尽；连接窗口耗尽则会限制所有流继续发送 DATA。请求已经并发，并不意味着每条请求都独占带宽与接收空间。[HTTP/2 帧与流控](https://httpwg.org/specs/rfc9113.html#FlowControl)

## 6. 回到业务：字节可靠，为什么还会重复操作

TCP 可能已经把请求交给服务，服务也提交了文档，却在响应到达客户端前断开。新连接上的重试是新的 HTTP 请求，传输协议不知道它和上一次是否属于同一逻辑操作。

字节层重传与业务重试不能混用一个结论。业务仍需识别同一操作、保存完成状态，并处理结果未知；连接复用只是减少建连成本。

### 请求被重定向时，会发生另一轮请求

旧地址用 `Location` 指向新地址后，客户端需决定是否跟随，再向新目标请求。301 表达永久迁移，302 表达临时迁移；历史兼容行为允许它们把 POST 改成 GET。需要保留方法时，应按永久或临时语义选择 308 或 307。跳转还涉及请求体、凭据与新目标的权限边界，不只是换 URL。[HTTP 重定向语义](https://httpwg.org/specs/rfc9110.html#status.301)

## 本章小结

TCP 交付有序字节，TLS 验证身份并保护链路，HTTP 定义请求与响应语义。消息边界、持续存活、业务授权与只执行一次，不能由任一传输层保证自动推出。

## 🎯 面试怎么答

**HTTP/2 与 HTTP/3 的主要差别是什么，为什么仍要业务幂等？**

> HTTP/2 在 TCP 上复用多个流，TCP 的字节缺失可能影响它们；HTTP/3 使用 QUIC，将可靠交付安排到各流并集成 TLS，但仍受拥塞和服务容量约束。任一种协议下，业务成功后响应都可能丢失，重复请求仍需业务操作标识和结果记录处理。

## ⚠️ 易错点

> ⚠️ 一次 send 不保证对应一次 recv，消息边界由应用协议定义。

> ⚠️ 半关闭与半开不同；没有 FIN 不证明对端仍正常。

> ⚠️ TLS 服务身份验证不等于用户资源授权，证书签名也不是加密全部正文。

区分字节流读取与消息结束条件。

不能据此认定丢失。按应用协议累计到完整长度或帧；超时、关闭和无效帧另行处理，不能从一次 read 大小猜边界。

### 2. HTTP/3 的 A 流丢包，B 流数据已齐。B 一定无延迟吗？A 的业务一定没执行吗？

<details>
<summary>参考答案与解释</summary>

都不能推出。B 仍受共享拥塞、流控和调度影响；A 的业务可能已执行，只是响应尚未完整到达。

</details>

### 3. 服务发送了证书，为什么客户端还要验证名称、信任链与握手签名？

<details>
<summary>参考答案与解释</summary>

公开证书可被复制。名称和信任链用于判断证书是否适用于目标身份，握手签名用于验证相关私钥持有者参与了本次握手；不能只凭“收到证书”认定可信。

</details>

### 机制对照：DNS 已换成新地址，为什么仍可能访问旧实例？HTTP/2 流 1 的字节丢失为何可能影响流 3？

<details>
<summary>参考答案与解释</summary>

DNS 缓存可能尚未过期，已有连接也不会自动迁移。HTTP/2 各流的帧共享 TCP 有序字节流，前面字节缺口可能暂时阻止后面的帧交付；这与某个流自己的 HTTP/2 流控窗口不同。

</details>
