# 不可信输入怎样被限制在安全边界内

[← 谁能访问什么，权限怎样贯穿请求与任务](15-AuthSession与TenantBoundary.md) · [模块主页](../README.md) · [多个服务实例怎样被找到和选中 →](17-ServiceDiscovery与LoadBalancing.md)

资料助手允许用户提交网页地址，后端下载后解析；也能导出文档，调用命令行转换工具。危险不在功能名字，而在一个变化：用户输入开始决定服务器访问哪里、查询什么、执行什么。

先沿输入看到实际动作，再判断哪一层必须限制它。格式正确并不意味着动作已经得到授权。

## 1. 输入通过格式校验，不等于执行可以被授权

URL 可符合语法，却指向内部管理服务；文件名可以是字符串，却落到不允许的目录；金额可以是整数，却超过用户额度。格式校验、业务判断、授权和资源限制是不同检查。

接口应尽量暴露明确能力，例如“转换本任务已上传的 PDF”，而不是让用户指定任意程序和路径。服务器先从已授权对象记录找到真实文件，再把输入填进允许的参数位置。

## 2. SQL 参数化把数据与语句结构分开

拼接字符串会让输入参与 SQL 结构。参数化查询把模板与数据值分开，由驱动按规则绑定。例如实验用 `WHERE doc_id=? AND tenant=?` 的绑定方式，而不是把文档名直接拼进 SQL。[SQL 注入防护](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)

占位符通常绑定 **值** ，不能任意代替列名、表名或排序方向。允许用户选择排序时，把有限选项映射到服务端固定列名，不允许原始输入变成语句结构。数据库账号还应按最小权限配置，降低错误后的影响。

参数化不解决越权。一条语法安全的查询，没有团队与对象授权限制，仍可能返回他人数据。这两层要同时成立。

## 3. SSRF 是服务器被引导去访问不该访问的目标

**SSRF（服务端请求伪造）** 的执行者是服务器：用户提供地址，服务利用自己的网络位置发起请求。若它能到达内部管理或凭证接口，风险超出普通网页下载。

只允许固定供应商时，可用明确允许列表；必须访问公开网页时，还需限制协议、端口、解析后地址与真实连接去向。IPv4/IPv6、地址重新解析、跳转都在检查范围内，并在受控出口实施限制。[SSRF 防护](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)

用一个允许公开网页下载的教学任务说明：

| 数据经过的位置 | 允许路径 | 应拒绝的变化 |
|---|---|---|
| 接收网页地址 | 协议、端口符合允许规则 | 仅因是合法 URL 就放行其他协议 |
| 解析并准备连接 | 解析结果和实际连接目标均符合公开访问策略 | 解析后落到禁止的本地或内部地址 |
| 收到重定向 | 不跟随，或重新检查每次新目标 | 只查第一次，之后任意跳转 |
| 读取响应 | 在时间、大小和内容规则内完成 | 无界读取，耗尽内存或连接 |

例如网页 A 起初允许访问，但返回的下一目标 B 不在许可范围，任务应在请求 B **之前** 停止。检查时解析安全、连接时却换了地址，也不能算通过；地址约束要落实到真实连接或出口层，而不只是一次字符串检查。

受限下载服务或出口代理可集中承担这些规则。网页内容交给后续解析器时，也仍是不可信输入。

> ⚠️ 这里给出的是防护目标和决策过程，不是已实现的通用安全下载器。一个 URL 正则或单次 IP 判断，不能证明覆盖全部解析与连接边界。

## 4. CSRF 与 XSS，不要和 SSRF 混在一起

**CSRF（跨站请求伪造）** 利用浏览器可能自动携带目标站点凭证。用户已经登录，却在其他站点触发了非预期修改；服务若只看 Cookie，可能把它当成用户意图。

按应用模型组合 CSRF Token、来源检查、适当 SameSite Cookie 策略及敏感动作确认，状态修改不应藏进安全方法 GET。 **CORS（跨源资源共享）** 主要控制浏览器跨源读取等行为，不是后端授权，也不能单独充当通用 CSRF 防护。[CSRF 防护](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

**XSS（跨站脚本）** 使不可信内容进入页面的可执行上下文。模板转义、按输出位置编码及必要 HTML 清理，让数据继续作为数据。模型生成的 HTML 也需要相同处理；内容安全策略可做纵深防护，不能替代安全输出。[XSS 防护](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)

先认执行者：SSRF 是服务器去访问目标，CSRF 是浏览器携带凭证发出非预期请求，XSS 是不可信脚本在页面中执行。因此不能拿浏览器 CORS 配置去限制服务器访问内网。

## 5. 命令、文件与容器都要限制真实能力

命令行调用优先避免 shell，使用固定程序和参数数组。但目标程序仍可能把输入当成危险选项，所以还要约束参数语义、工作目录、权限和资源，适用时使用结束选项标记。[命令注入防护](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html)

以转换本任务 PDF 为例，客户端只提交任务编号和允许的转换类型，服务器负责取路径和组装命令：

| 检查 | 允许继续的依据 | 拒绝时应保护什么 |
|---|---|---|
| 输入文件归属 | 文件属于已授权任务 | 不读取其他团队或任务文件 |
| 程序与选项 | 服务端固定程序，选项来自有限映射 | 不接受用户自定程序或任意选项 |
| 输出位置 | 由任务身份映射到受控目录，核对实际路径和链接 | 不覆盖其他目录或他人产物 |
| 资源与发布 | 时间、大小、数量在预算内，完整校验后发布 | 失败不暴露半成品，清理仅属于该任务的临时对象 |

文件路径还需处理符号链接、解压后的目录与展开比例，不能只查字符串前缀。分块上传要同时限制整项任务总量，合并前核对归属、顺序与完整性；单块很小不证明总量可控。

容器隔离进程视图与部分资源，不是无条件安全沙箱。特权模式、宿主挂载、运行时控制接口、过大凭证权限和内核漏洞会放大后果。减少真实权限，比禁止几个关键词可靠。[Kubernetes 安全检查表](https://kubernetes.io/docs/concepts/security/security-checklist/)

## 6. 密钥与审计也属于生命周期

密钥通过受控配置或密钥服务注入，按用途和环境隔离；轮换要定义新旧密钥共存与撤销。日志、Trace、异常和模型上下文不应泄露完整凭证，也不要为排障长期记录全部请求头和用户文档。[密钥管理](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)

模型输出仍是待校验提议。主体权限、对象、参数、预算、批准与提交条件，应由执行边界的确定性代码检查。提示词写“不要泄露”，不能限制一个拥有全部导出权限的实际工具。

验收同时跑允许与拒绝路径：合法文件可转换，越界或超预算输入被拒绝；失败后不遗留可访问的敏感半成品。上面的过程没有运行浏览器、网络或容器安全测试，不能把目标说明写成部署已经安全。

## 本章小结

沿不可信输入到实际动作的路径设置边界。参数化保护语句结构，授权保护对象，出口规则保护网络去向，文件与进程限制保护真实执行能力。格式、提示词或容器名称都不能替代这些检查。

## 🎯 面试怎么答

**Agent 网页读取和工具执行应怎样防护？**

> 把能力收窄到具体业务动作，验证主体、对象与参数。下载时在解析、跳转、实际连接和出口限制去向；转换时使用固定程序、受控路径和最小权限。敏感动作绑定批准，限制资源，保护密钥，并验证合法路径可用、越界路径被拒绝。模型建议不能直接成为授权。

## ⚠️ 易错点

> ⚠️ SSRF、CSRF、XSS 的执行主体不同，各层防护不能互换。

> ⚠️ 参数化 SQL 不代替授权，shell=False 不代替程序选项和路径检查。

> ⚠️ 限制单个文件或分块，不等于限制一次任务的资源总量。

每次新目标及实际解析、连接都需检查；可禁止跳转，或在受控下载器和出口逐跳限制。初始地址合法，不证明 B 仍在允许范围。
