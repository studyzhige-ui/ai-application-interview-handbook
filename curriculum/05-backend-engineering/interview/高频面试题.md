## 1. 从浏览器输入 URL 到返回结果，中间发生了什么？

区分名称解析、连接、TLS 身份与加密、HTTP 路由、应用处理和响应。连接可复用，不是每次重做握手。TLS 认证与密钥协商各有职责，业务提交和客户端收到响应又是不同事实；网关超时不证明业务没执行。

追问：301、302 为什么可能改变请求方法？HTTP/2 为什么仍受 TCP 丢包影响？TLS 为什么不能只看收到一张证书？

## 2. 前端要展示用户最近一组通知，为什么选择 WebSocket，而不是轮询？

先看频率、延迟和是否双向交互。低频可轮询，单向持续推送可用 SSE，双向才考虑 WebSocket。协议之外仍需用户隔离、稳定事件身份和可查状态；重连依据保留窗口补发或返回快照，不只是重建连接。

## 3. 线程池如何配置，异步为什么还会把服务拖慢？

先区分计算与等待，确认调用是否阻塞事件循环，再分别限制执行者、接纳任务与下游资源。提交者或调度者收集 Future 结果与异常；调用方超时不等于线程停止，名额绑定本地工作终结，远端结果另行核对。

追问：done 为 True 为什么不等于成功？单线程池里等待同池新任务会怎样？

回看：[并发与 Future](../docs/05-Concurrency与ThreadPool.md) · [连接容量](../docs/06-ConnectionPool与ResourceCapacity.md) · [背压](../docs/07-Backpressure与RateLimit.md)

## 4. 怎样防止一个用户拖垮模型服务？

约束输入大小、速率、在途任务与模型预算，再按用户或团队分配。队列满时拒绝或有界等待，限流器不可用时按风险选择放行或拒绝，不能把故障策略当作默认正确。

追问：请求数相同但成本相差百倍呢？加队列为什么没提高吞吐？

回看：[连接容量](../docs/06-ConnectionPool与ResourceCapacity.md) · [背压与限流](../docs/07-Backpressure与RateLimit.md) · [执行安全](../docs/16-BackendSecurity.md)

## 5. 工具超时后是否应该重试？熔断和降级有什么不同？

检查错误可恢复性、总预算和安全重放依据，再选明确一层有限退避重试。熔断减少故障依赖调用，降级改变可提供能力；切换供应商也不能忽略旧动作结果未知。

追问：每层尝试三次会怎样？恢复探测为什么也限量？

## 6. 接口幂等、Redis 锁和 Kafka 消费幂等分别保证什么？

稳定业务键识别同一动作，本地唯一约束与事务形成防重提交边界。锁协调谁能尝试执行，租约失效不会杀掉旧工作者；Kafka 交付或事务语义也不自动覆盖外部 API。多个消息 ID 仍可能代表同一业务操作。

追问：外部已写成功，本地没记结果，凭什么继续？

回看：[操作身份](../docs/09-APIIdempotency与SideEffect.md) · [消息确认](../docs/11-MQ与DeliverySemantics.md) · [Kafka](../docs/12-KafkaPartition与Backlog.md) · [可靠任务](../docs/13-ReliableAsyncTask.md)

## 7. 消息已经确认了，任务为什么还可能重复或丢失？

先问谁确认什么：生产确认、消费确认和业务提交不同。业务提交后确认丢失会重复，完成前确认可能让失败工作无法重投。Outbox 可与本地业务共同提交，但转发与消费仍需防重、重试与核对。

追问：何时数据库扫描已足够，何时值得引入 MQ？

回看：[交付语义](../docs/11-MQ与DeliverySemantics.md) · [任务恢复](../docs/13-ReliableAsyncTask.md)

## 8. Kafka 积压如何处理，增加消费者一定有效吗？

先确认消费模型。传统分区消费组受可分配分区数约束，应检查键倾斜、耗时和下游瓶颈；并行执行不能跨过未完成记录提交。共享组有另一套记录分配方式，但也不自动解决业务顺序和外部副作用。

追问：后面的记录先完成，能提交到最后吗？持续到达时如何计算清空时间？

回看：[积压增长](../docs/07-Backpressure与RateLimit.md) · [Kafka 分配与提交前沿](../docs/12-KafkaPartition与Backlog.md)

## 9. 进程重启后，长任务怎样继续，如何处理失败的中间文件？

保存任务身份、固定输入、进度与结果位置，用消息或扫描重新发现。领取和完成检查状态与代际，进度与检查点保持可重放关系；临时产物不冒充已发布结果，校验后发布，按任务归属清理。

## 10. MySQL 与 Redis 不一致怎么办？

确定事实源与新鲜度要求，分清删除失败、旧读回填和副本落后。普通缓存旁路需要可靠失效与修复；较严格路径可先查权威版本，再读取同版本不可变缓存或正文。版本依据不能随缓存丢失，缺少所选版本时不能拿旧值代替。

追问：这套读取省了什么、没有省什么？权威版本不可用时怎么办？在途旧读者仍能完成吗？

回看：[一致性与版本化读取](../docs/14-Consistency与Compensation.md) · [状态归属](../docs/02-DataLayering与StateOwnership.md)

## 11. JWT 能直接解决多实例会话和权限撤销吗？

JWT 可让实例按发行者规则验证签名和声明，但不会自动传播最新权限，也不代替对象授权。集中会话、权限版本与撤销策略按业务要求设计；缓存命中、长连接、任务执行和结果交付都不能绕过必要检查。

追问：用户排队时被移出团队怎么办？Access Token 与 ID Token 能互换吗？PKCE 的两个请求怎样关联？

回看：[认证、会话与授权](../docs/15-AuthSession与TenantBoundary.md) · [不可信输入](../docs/16-BackendSecurity.md)

## 12. SQL 变快但接口仍慢，Linux 和 Kubernetes 该看什么？

用同一请求时间线拆开排队、连接等待、SQL、模型和响应。进程侧再看 CPU、内存、FD、连接和磁盘，容器侧核对配额。FD 接近软限制只是风险证据，还需关联错误、资源类型与释放路径。探针控制路由或重启，不修复应用根因。

追问：宿主空闲但容器限流呢？摘流后旧连接怎么办？FD 多但 CPU 不高应怎样继续验证？

回看：[路由](../docs/17-ServiceDiscovery与LoadBalancing.md) · [观测](../docs/18-Observability与PerformanceDiagnosis.md) · [Linux 输出解读](../docs/19-LinuxTroubleshooting.md) · [部署](../docs/20-ContainerK8s与Deployment.md)

## 13. Java、Spring、Go 的题与通用后端机制怎样对应？

选择岗位对应语言作答。Spring 管依赖、作用域与代理调用；Java 锁和并发容器保护特定共享操作，ThreadLocal 需在复用线程中清理，JVM 内存不只有堆；Go 用 G/M/P 调度，Channel 和 context 不代替持久任务与外部恢复。

追问：自调用绕过什么？并发容器为何仍有多步竞态？Go 有 Channel 为何还用锁？

回看：[Java/Spring 分支](../docs/22-CrossLanguageRuntimeMapping.md#java-path) · [Go 分支](../docs/22-CrossLanguageRuntimeMapping.md#go-path)
