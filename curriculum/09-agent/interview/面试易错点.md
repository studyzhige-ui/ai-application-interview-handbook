# Agent｜面试易错点

[← 模块目录](../README.md) · [高频题](高频面试题.md) · [面试前速查](面试前速查表.md)

本页按 24 章回看容易混淆的边界。它不代替章末同名部分；原有知识范围保留，重复表述按新正文统一。

## 01｜[Agent 系统的全貌：先知道谁在做什么](../docs/01-AgentSystemAndResponsibilities.md)

| 易错说法 | 校正与原因 |
|---|---|
| 用了工具就是 Agent | 固定流程也能使用工具；区别在后续路径的控制权。 |
| Harness 只是 system prompt | 文字不能替程序真正执行、保存、限制或终止动作。 |
| 每个 Agent 都需要长期记忆和向量库 | 需要由跨任务复用与检索需求推导，而不是凑组件。 |
| 架构图上的方框必须独立部署 | 方框首先表示责任，部署由规模与隔离要求决定。 |

## 02｜[Workflow、Agent 与 Harness 的边界](../docs/02-WorkflowAutonomyAndRuntimeBoundary.md)

| 易错说法 | 校正与原因 |
|---|---|
| 固定流程含一次 LLM 分类就是自主 Agent | 主要控制路径仍可能完全由程序决定。 |
| Orchestrator、Runtime、Harness 必须是独立服务 | 是职责词，不是强制部署单元。 |
| 模型能力强，程序就可以少做权限检查 | 更强推理不建立真实权限。 |
| 复杂框架等于生产成熟度 | 要测试任务状态、恢复、可观测性与退出能力，而非只看功能表。 |

## 03｜[Agent 循环、执行层级与新消息](../docs/03-AgentLoopAndExecutionScopes.md)

| 易错说法 | 校正与原因 |
|---|---|
| Turn 在所有产品里都等于一次模型调用 | 必须查看产品定义；Codex Turn可含多次推理与工具交互。 |
| 新消息总应立即打断所有动作 | 先识别意图和当前动作是否可安全中断。 |
| 循环 return 就是业务成功 | 可能等待、取消、耗尽预算；要有明确终态及验收。 |
| 事件越多，模型越懂运行过程 | 很多事件服务程序或排障，全部喂模型会制造噪声。 |

## 04｜[工具契约：模型可以请求什么，程序必须检查什么](../docs/04-ToolContractAndValidation.md)

| 易错说法 | 校正与原因 |
|---|---|
| Schema通过就能安全调用 | 还要检查目标含义与当前身份的权限。 |
| 把函数代码或数据库密码塞进工具描述 | 模型只需说明书；执行实现和凭证留在可信程序。 |
| 只读标注代表完全无风险 | 只读也可能泄露隐私；不可信标注不能当授权依据。 |
| 工具返回200就完成业务 | 还要判断结果是否满足契约及任务验收。 |

## 05｜[工具注册、模型可见说明与按需发现](../docs/05-ToolRegistrationAndDiscovery.md)

| 易错说法 | 校正与原因 |
|---|---|
| 注册就是给模型安装函数 | 注册在应用中发生；模型得到说明并产生调用候选。 |
| 延迟加载完成后会发送全部宿主字段 | 完整Schema不等于完整实现、权限对象或凭证。 |
| 看不见的工具必然不在注册表 | 注册表可以大于本轮可见工具集。 |
| 工具召回不准就是参数描述不好 | 也可能候选筛选阶段已漏掉正确工具。 |
| 工具清单被缓存就无需调用时检查 | 权限、版本和可用性仍可能改变。 |

## 06｜[工具结果与错误：哪些告诉模型，哪些由程序处理](../docs/06-ToolExecutionAndFailure.md)

| 易错说法 | 校正与原因 |
|---|---|
| 异常都可让模型自己修 | 模型不能修复凭证权限、宿主状态损坏或已发生的外部动作。 |
| timeout表示没有执行 | 可能已成功但回包丢失，需核对。 |
| 工具自己说可重试就立即重试 | 需要可信程序结合副作用与预算判定。 |
| 日志、用户消息、模型Tool Result可以共用全部原始内容 | 它们的权限、长度与用途不同，应分别投影。 |

## 07｜[副作用、并发与取消传播](../docs/07-ToolConcurrencyAndCancellation.md)

| 易错说法 | 校正与原因 |
|---|---|
| 取消本地请求等于远端动作停止 | 只能确认本地停止等待，远端需单独核对。 |
| 只读工具没有任何风险 | 可能泄露敏感数据、消耗配额或导致过载。 |
| 同名工具互斥，不同名就独立 | 冲突取决于共享资源。 |
| 进度显示100%就是业务成功 | 仍要等待结果契约及业务验收。 |

## 08｜[计划、ReAct 与停止：怎样让每一步朝目标推进](../docs/08-PlanningGoalAndControl.md)

| 易错说法 | 校正与原因 |
|---|---|
| Plan等于全部State | Plan只记录未来步骤与清单状态，不包含全部活动调用、结果和授权。 |
| 新计划必须覆盖旧模型消息 | 通常追加更新事件并替换当前视图，两者分开。 |
| ReAct必须输出私有思考 | 关键是行动与观察反馈，不需要展示隐藏推理。 |
| 预算耗尽也是完成 | 它只是停止原因，应明确未完成状态。 |
| 每个Agent都需要独立Planner服务 | 简单任务可隐式规划，按任务需要选择。 |

## 09｜[上下文编排：模型这一刻到底收到什么](../docs/09-ContextAssemblyAndCache.md)

| 易错说法 | 校正与原因 |
|---|---|
| 编排就是每轮重排历史 | 编排可以仅做稳定投影与尾部追加。 |
| tools不在messages所以不占预算 | 模型使用的工具说明同样需要处理。 |
| 当前Plan被覆盖，历史Plan也应覆盖 | 当前视图与历史轨迹不同。 |
| 摘要能替代所有恢复数据 | 它可能有损，权威回执与必要状态另存。 |
| 保存全文到Trace就实现外部化 | 外部化需要可授权读取的产物；诊断日志不是默认产物库。 |

## 10｜[上下文压缩：什么时候压、压什么、怎样继续](../docs/10-CompactionAndContinuation.md)

| 易错说法 | 校正与原因 |
|---|---|
| Resume就是摘要 | Resume是恢复执行，Summary才是摘要。 |
| 压缩就是摘要加到历史尾部 | 必须构造更短替代视图，否则仍然占原预算。 |
| Claude固定三层所有版本一样 | 多种路径受快照和特性开关控制。 |
| 压缩Prompt要求structured所以一定JSON | 有组织文本与机器Schema是两回事。 |
| 摘要中保存回执足够防重复 | 恢复应依赖可靠操作记录与外部核对。 |

## 11｜[记忆生命周期：怎样记得有用，又能忘掉错误](../docs/11-MemoryLifecycle.md)

| 易错说法 | 校正与原因 |
|---|---|
| 所有聊天都值得长期保存 | 当前过程和噪声不一定有未来价值，且有隐私成本。 |
| Compaction后就产生长期Memory | 当前输入缩减与未来复用不同。 |
| 冲突记忆最新的总是正确 | 需比较来源和适用范围。 |
| 删除原记录就一定彻底忘记 | 索引、缓存、导出和备份需按保留政策处理。 |
| 记忆来自历史所以是权威事实 | 历史模型判断也可能错误，要能核对。 |

## 12｜[状态与持久化：程序怎样记得工作做到哪里](../docs/12-StateHistoryAndPersistence.md)

| 易错说法 | 校正与原因 |
|---|---|
| State就是Plan的pending/done | 还包括等待的操作、取消、结果、权限与产物等当前情况。 |
| 持久化就是把全部内存存下来 | 保存可恢复的必要信息，连接与协程通常重建。 |
| 有Session ID就有访问权 | 身份与授权必须来自可信控制链。 |
| Trace越全，恢复越可靠 | 诊断与恢复目标不同，关键事实需可靠存储。 |
| 任何事件必须版本号 | 唯一标识和变更版本不同，只为实际问题引入。 |

## 13｜[检查点与恢复：两次保存之间崩溃怎么办](../docs/13-CheckpointResumeAndRecovery.md)

| 易错说法 | 校正与原因 |
|---|---|
| 每秒检查点就没有故障窗口 | 跨系统副作用仍不与本地存档天然原子。 |
| 恢复先把旧Prompt再发一次 | 先核对当前状态、取消与未决副作用。 |
| 补偿等于数据库回滚 | 补偿是新业务动作，也会失败且未必可逆。 |
| 租约到期旧Worker一定停止 | 需在写入边界拒绝旧所有者，不靠时间想象。 |
| 保存全部Trace便能精确重现世界 | 模型、服务和外部事实都可能变化，重演有明确范围。 |

## 14｜[权限、批准与沙箱：三道不同的问题](../docs/14-PermissionApprovalAndSandbox.md)

| 易错说法 | 校正与原因 |
|---|---|
| Schema合法就是有权限 | 结构与授权依据不同。 |
| 用户同意便能越过组织禁令 | 批准不能扩大批准者本身没有的权限。 |
| 容器就是绝对安全沙箱 | 隔离依赖配置和威胁模型。 |
| 全部弹确认框最安全 | 审批疲劳和未绑定参数会使确认失效。 |
| 只读意味着不能泄漏 | 读取敏感数据并外传也是风险。 |

## 15｜[注入与信息保护：数据为什么不能变成命令](../docs/15-InjectionAndContainment.md)

| 易错说法 | 校正与原因 |
|---|---|
| 内部文档都是可信指令 | 内容来源和控制权限是两回事。 |
| 检测器没报警就安全 | 未知模式可能绕过，应有资源边界。 |
| 输出拦截能撤销发送过的消息 | 它通常只能管当前输出，已发生副作用另处理。 |
| 密钥在环境变量就不会泄漏 | Shell、日志和工具返回可能读取或外传。 |
| 所有高风险信息都保存方便追责 | 收集本身会增加泄漏风险，应有目的、权限与期限。 |

## 16｜[MCP、Skill与Hook：外部能力怎样接进来](../docs/16-MCPArchitectureAndLifecycle.md)

| 易错说法 | 校正与原因 |
|---|---|
| MCP Client就是LLM | 它是Host中的协议组件，LLM另由Host调用。 |
| MCP Server只能远程部署 | 本地进程也可以提供MCP。 |
| tools/list会运行所有工具 | 它发现说明，执行需tools/call。 |
| clientInfo证明了用户身份 | 只是兼容/诊断元数据，认证另行处理。 |
| MCP等于SSE | 协议语义与传输机制不同。 |
| 协议无状态等于业务没有状态 | 资源与长任务可以有状态，不同抽象层。 |
| Skill和Hook都是工具的一种名字 | 它们分别管理知识使用与生命周期扩展。 |

## 17｜[意图、模型与能力路由：把请求交给合适的对象](../docs/18-RoutingAndProviderResilience.md)

| 易错说法 | 校正与原因 |
|---|---|
| Router一律用最大LLM | 先规则与简单基线，有复杂语言需求再比较模型。 |
| Fallback只是换模型名 | 上下文和能力契约可能不兼容。 |
| 模型错误就重启整个Agent | 会重复已完成工具和副作用。 |
| 总体分类准确率高就够 | 高风险类别误路由与未知意图也需验证。 |

## 18｜[多Agent与A2A：分工、交接和跨系统任务](../docs/19-MultiAgentAndA2A.md)

| 易错说法 | 校正与原因 |
|---|---|
| 多Agent必定更强 | 收益需覆盖协调成本和新的失败模式。 |
| A2A就是Agent互相发字符串 | 它定义发现、消息、任务、产物与交互语义。 |
| 用了Subagent就一定走A2A | 内部控制可以用私有接口。 |
| Agent Card等于认证 | 它声明信息，身份和访问授权另验证。 |
| 取消Task等于撤销远端动作 | 已有结果和副作用仍要核对。 |
| MCP绝不支持长任务 | 当前规范可有任务扩展，需按版本比较。 |

## 19｜[Trace与排障：记录够用的信息，而不是保存整个世界](../docs/20-TraceReplayAndDiagnosis.md)

| 易错说法 | 校正与原因 |
|---|---|
| Trace是恢复数据库 | 它通常允许采样和过期，关键业务状态另存。 |
| Context/Prompt必须每个Span全量记录 | 可以引用一次受控配置，深度快照按需要采集。 |
| 有完整日志就能重现外部世界 | 外部服务与模型有变化和不确定性。 |
| 所有数据保留越久越好 | 成本、隐私、权限与保留目的都需明确。 |
| 诊断日志失败应一律终止业务 | 通常不应；真正强制可靠的审计/回执需独立规定。 |

## 20｜[Agent评测：从“跑完了”到“有证据说明做好了”](../docs/21-EvaluationBenchmarkAndImprovement.md)

| 易错说法 | 校正与原因 |
|---|---|
| 模型说完成就算成功 | 完成需要外部验收证据。 |
| 只看平均成功率 | 长尾、风险类别和成本分布可能被掩盖。 |
| 有Trace就已经评测 | Trace提供过程，评测依据标准判断好坏。 |
| 所有坏例子都靠更长Prompt修复 | 可能是权限、数据、工具或恢复机制问题。 |
| 收集所有对话就是数据飞轮 | 需要授权、归因、回归与治理。 |

## 21｜[Coding Agent：读懂仓库、最小修改与可验证交付](../docs/22-CodingAgentDelivery.md)

| 易错说法 | 校正与原因 |
|---|---|
| 代码生成器就是完整Coding Agent | 还需要资源理解、实际执行与交付验证。 |
| 检索到了片段就能直接修改 | 要读实际上下文和影响面。 |
| 测试过了就是全部正确 | 仅证明相应检查范围。 |
| 失败就清空整个Git工作区 | 可能破坏用户修改，应限本次所有权。 |
| 为了通过测试可以随便删断言 | 测试应表达需求，不应掩盖错误实现。 |

## 22｜[生产Agent架构：从一个进程到可运营服务](../docs/23-ProductionRuntime.md)

| 易错说法 | 校正与原因 |
|---|---|
| Production必须很多微服务 | 部署拆分依据独立扩容、隔离和故障需求。 |
| 每个Run永久绑一个容器最好 | 可能浪费资源并耦合生命周期，应按任务选择。 |
| 增加Worker能解决供应商限流 | 可能制造更大限流与重试压力。 |
| 进度流就是可靠任务状态 | 流可断开，业务状态应有适当权威存储。 |
| Trace不可用就不能知道任务成功 | 成功由业务状态与验收证据确认。 |

## 23｜[框架与自研怎么选：按官方核心语义做比较](../docs/24-FrameworkSelection.md)

| 易错说法 | 校正与原因 |
|---|---|
| 框架越重越Production | 抽象不匹配会增加复杂度。 |
| 自研Loop一定更专业 | 实现与维护可靠性也有成本。 |
| 有Session就是完整业务恢复 | 会话项与执行/副作用状态不同。 |
| LangChain永远只是线性Chain | 当前官方Agent入口基于LangGraph，需按版本说明。 |
| Node/Edge就是Agent的本质 | 它是实现控制流的一种抽象。 |
| 使用产品源码等于集成了产品所有保证 | 部署、配置、任务契约和验证仍由自己的系统负责。 |
