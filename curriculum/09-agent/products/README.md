# 成熟 Agent 产品源码学习

[← Agent 模块](../README.md)

通用教材回答的是“一个 Agent Runtime（Agent 运行时）通常需要解决哪些问题”；这里回答的是另一个更具体的问题：

> **真实产品的源码到底怎样把这些问题做成一套能运行、能恢复、能扩展、能排障的系统？**

这两层不能倒过来。我们不会先拿课程里的 Context（上下文）、Memory（记忆）、Tool（工具）分类去要求源码“长成这个样子”，而是先从产品自己的入口、进程边界、核心对象、存储和扩展机制出发，再观察上下文、记忆和工具分别落在哪些真实模块里。

---

## 1. 源码学习先遵守两条原则

### 1.1 先认清产品真实边界，再讲某个机制

成熟 Agent 往往不只有一个 `core` 目录。用户输入可能先经过 CLI（命令行界面）、TUI（终端用户界面）或 App Server（应用服务器），随后进入线程管理、模型请求、工具执行、执行环境、持久化和扩展系统。

所以源码学习的第一步不是搜索 “memory” 或 “tool”，而是先回答：

~~~text
产品有哪些入口？
↓
入口把请求交给谁？
↓
谁创建 / 恢复长期会话？
↓
谁驱动一次用户任务？
↓
模型请求在哪里形成？
↓
真实副作用在哪里执行？
↓
历史和状态在哪里落盘？
↓
扩展能力从哪里接入？
~~~

只有这条主干确认以后，Context、Memory、Tool 等机制才有正确位置。

### 1.2 “仓库里写着”不等于“当前实现就是这样”

源码仓库里的 README、注释和模板很重要，但它们也可能晚于代码更新。产品文档因此采用下面的核验优先级：

~~~text
固定 commit 的目录树
→ 真实调用点与数据流
→ 与调用点对应的测试
→ 类型 / 注释
→ README 与说明文档
~~~

如果 README 与当前代码不一致，文档要明确指出差异，不能为了让叙述整齐而选择更像教材的那一份。

## 2. 写作标准：Writer like a reader

这一层继续遵守本仓库已经在 Python、Agent 等模块反复修订出的原则：**写作者站在第一次读这套系统的人一边。**

首次出现的重要英文术语要给出中文含义，例如 `Thread（线程 / 持续会话容器）`、`Turn（一次用户任务推进）`、`Step Context（单次模型采样快照）`。源码类名、函数名和文件路径保留英文，因为读者最终要回到代码；但不能用一串英文标识符替代解释。

正文也不以“字段清单”作为主要表达方式。一个结构体有十几个字段时，先讲它为什么存在、什么时候创建、哪些字段共同保证哪条不变量，再用表格给需要查阅的字段。列表可以帮助定位，但列表前后必须有完整自然语言。

每个重要机制至少回答四件事：

~~~text
为什么需要它？
→ 正常路径怎样流动？
→ 哪个状态在什么时候发生变化？
→ 失败或边界情况会怎样？
~~~

源码事实和工程推导也必须分开。比如“Codex 当前 Tool Search 使用 BM25”是源码事实；“如果未来有五万个工具，可以继续做分层检索”是基于源码的工程推导，不能写成 Codex 已经在五万个工具规模上采用了某种架构。

---

## 3. 什么叫“阅读完整源码”

“完整”不等于逐行复述仓库里的每一个文件。一个大型产品仓库包含 UI 绘制、安装脚本、发布流程、平台兼容代码等大量外围实现；把它们逐个列出来，反而会遮住 Agent Runtime 的主线。

这里的完成标准是：

> **凡是会改变 Agent 行为、能力边界、长期状态、恢复方式、安全决策或可观测性的源码层，都要进入系统地图；正文中的重要结论，都能回到固定 commit 的真实调用链或测试。**

因此产品学习至少核验：

| 源码层 | 要回答的问题 |
|---|---|
| 产品入口与协议 | 用户请求怎样进入系统，不同客户端是否共享同一运行时 |
| 会话 / 线程与执行循环 | 长期对象怎样创建、恢复；一次用户任务怎样推进 |
| 上下文与模型请求 | 模型每次真正看到什么，怎样增量更新与压缩 |
| 工具与执行环境 | 能力怎样注册、发现、授权、隔离、执行和回填 |
| 记忆与长期知识 | 历史怎样变成未来可复用信息，怎样纠错和遗忘 |
| 扩展系统 | MCP、Skills、插件、Guardian 等怎样接入宿主生命周期 |
| 持久化与恢复 | 历史、元数据、检查点怎样保存；Resume / Fork 怎样重建 |
| 多 Agent | 子 Agent 怎样创建、通信、共享与隔离 |
| 诊断与验证 | Metrics、Trace、测试分别能证明什么，不能证明什么 |

## 4. 固定学习结构

不同产品可以有不同的内部实现，但为了便于横向比较，每个产品保留同一组学习入口：

| 文件 | 主要任务 |
|---|---|
| `README.md` | 先从产品入口和源码模块建立系统地图，说明哪些结论是源码事实 |
| `01-context-lifecycle.md` | 追踪一次模型调用的上下文从输入、编排、增长到压缩和恢复 |
| `02-memory-lifecycle.md` | 追踪长期记忆从发现、写入、整理到召回、纠错与遗忘 |
| `03-tool-lifecycle.md` | 追踪工具从能力接入、模型发现到权限、执行和结果回填 |
| `04-engineering-evaluation.md` | 把系统重新合起来看故障、持久化、多 Agent、可观测性和评测 |

这是**学习导航**，不是声称源码仓库本身就按这四个目录组织。

## 6. 推荐学习方式

第一次仍建议先完成 [Agent 通用课程](../README.md)，建立基本语言。进入源码产品层以后，不要背文件名，而是不断追问“这个对象在整条链上负责哪一段”。

推荐顺序是：

~~~text
产品系统总览
→ Context 生命周期
→ Memory 生命周期
→ Tool 生命周期
→ 工程、恢复与评测
→ 再回到通用课程比较不同设计选择
~~~

读完一个产品之后，真正应该得到的能力不是“我看过它有哪些类”，而是能从入口开始解释：**一条用户输入怎样变成一次受控执行；中途的信息、能力与状态怎样流动；失败以后为什么还能继续；下一次启动又怎样恢复到正确的位置。**
