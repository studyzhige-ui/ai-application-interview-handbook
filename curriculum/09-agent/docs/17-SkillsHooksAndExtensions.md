# 17. Skills、Hooks 与 Plugins：知识怎样加载，规则怎样触发

[← 上一章](16-MCPArchitectureAndLifecycle.md) · [Agent 目录](../README.md) · [下一章 →](18-RoutingAndProviderResilience.md)

助手已经能读资料、写报告，还差两种不同的能力：每次写报告时能找到组织的核查方法；每次准备发布时，程序能自动运行必要检查。

前者是“这类任务怎样做”的知识，后者是“执行到这个时刻要发生什么”的扩展。不要把它们都当成工具的另一个名字。

## 1. 用同一份报告分清四个对象

| 对象 | 主要回答 | 报告任务中的例子 |
|---|---|---|
| Tool（工具） | 能执行什么具体动作 | 读取文件、生成草稿 |
| Skill（技能包） | 某类任务怎样组织步骤与资源 | 引用规则、核查步骤、模板与辅助脚本 |
| Hook（生命周期钩子） | 运行到哪个时刻触发什么处理 | 发布前核对范围，结束后发送通知 |
| Plugin（插件） | 怎样打包、分发和启用一组扩展 | 安装一套报告技能与相关钩子 |

MCP 是外部能力的协议接入方式，已经在前章解释；它可以与这里的对象配合，但不替代任务知识、事件触发或包管理。

这些用词在产品中并非完全统一。应根据实际加载、触发和执行行为理解，不把一张分类表当成行业强制实现。

Command（命令入口）通常由用户显式触发应用行为，例如 `/review` 可以启动报告核查。一个命令可以加载技能或调用工具；入口、知识与执行仍是不同责任。

## 2. Skill 先让系统知道用途，再按需读取详情

[Agent Skills 规范](https://agentskills.io/specification)用技能说明与可选脚本、参考材料和资源组织可复用任务知识。一个教学用技能目录可以长这样：

```text
report-review/
├─ SKILL.md       用途、适用条件与核查步骤
├─ references/    引用规则与详细说明
├─ scripts/       可选的检查脚本
└─ assets/        报告模板
```

不是每个技能都需要全部目录。重点是：先以名称和用途发现候选，选中后读取 SKILL.md，再按需要取详细资料或执行脚本。

```text
任务需要核查报告
→ 找到适用 Skill 的简要说明
→ 加载核查步骤
→ 需要引用格式时再读对应参考
→ 需要自动检查时调用受控工具运行脚本
→ 核对结果
```

这种 **Progressive disclosure（渐进披露）** 减少每次输入全部知识的负担。但读到技能指令，不等于脚本已经执行；脚本有同样的权限、环境与结果验证要求。

> ⚠️ 技能文档写“请联网下载工具”不自动获得联网资格。Skill 提供方法，真实权限仍由宿主执行规则决定。

## 3. Hook 由事件触发，不靠模型想起来

设定“发布报告前必须检查收件人与批准记录”。若只是技能文档中的一句建议，模型可能没有调用检查；如果它是运行时的必要前置门，发布动作每次都必须经过它。

Hook 让程序在某个生命周期点调用扩展处理器，例如工具执行前、执行后、压缩前或任务结束。这里的名称是概念示意，不是所有框架相同的事件 API。

| 触发位置 | 可以做什么 | 做不到什么 |
|---|---|---|
| 工具执行前 | 校验、拒绝、补充受控环境 | 不能仅凭模型自报批准放行 |
| 工具执行后 | 校验结果、脱敏、记录审计 | 不能假装撤销已发生副作用 |
| 任务结束后 | 通知、指标和清理 | 不应静默启动新的无关任务 |

钩子能否修改输入或状态、能否阻断、按什么顺序运行、超时后怎样处理，都要由运行时明确。否则扩展会形成看不见的控制流。[Claude Code hooks 文档](https://code.claude.com/docs/en/hooks)提供具体事件与处理器的例子，不应直接套到其他框架。

## 4. 失败是否阻断，要看它承担的责任

“可选通知发送失败”和“发布前批准校验失败”不能都吞掉，也不必都杀死整个任务。

| 失败 | 合理处理 | 原因 |
|---|---|---|
| 可选完成通知不可用 | 记录并继续交付已确认结果 | 通知不是核心验收前提 |
| 必要授权检查不可用 | 拒绝继续发布或等待处理 | 不能在未确认授权时执行 |
| 技能文件缺失 | 报告能力不可用，选择已允许替代路径 | 不能自行扩大能力修复 |
| 扩展返回损坏状态 | 隔离扩展，拒绝破坏主状态 | 插件不应覆盖核心事实 |

失败时允许继续称为 fail-open，默认拒绝称为 fail-closed。该选哪一种，要看风险与业务承诺，不是给所有 Hook 使用统一 `except: pass`。

必要安全能力不能只靠用户可随意禁用的可选插件。核心门应由可信运行路径保证；插件可以提供策略或实现，但不能让卸载操作悄悄取消全部防护。

## 5. Plugin 管理的是安装与生命周期

插件可以封装技能、命令、工具接入和钩子；不同宿主支持范围不同。安装后需要发现扩展、校验配置、绑定允许的事件与资源，再启用。禁用或卸载时，要停止后续触发，并明确如何处理正在执行的工作。

升级也不是只改版本号。工具参数、技能步骤或 Hook 的状态写入规则改变，可能使旧会话和原批准不再兼容。可以让正在运行的任务固定原配置，或明确暂停迁移；不能在中途静默替换行为。

扩展来自第三方时，要检查来源、可执行代码、网络和凭证范围。安装一份有价值的知识包，不等于应该信任它运行任意命令。

## 本章小结

Skill 按任务加载方法，Hook 按事件执行处理，Plugin 管理打包与启用，Tool 真正执行动作。加载、触发和执行的区别决定权限、失败和升级怎样处理。

## 🎯 面试怎么回答

### Skill 和 Tool 有什么区别？

Skill 组织某类任务的方法与资源，Tool 执行具体动作。技能可能引用多个工具或脚本，按需加载知识不代表代码已经执行，也不提供额外权限。

### Hook 为什么不能随意改变状态？

它在运行时事件上自动触发，如果没有明确顺序、允许修改范围和失败语义，会形成隐藏控制流。必要检查要不可绕过，后置 Hook 不能撤销已有副作用。

### Plugin 升级时要注意什么？

核对工具、技能和钩子的兼容行为，以及正在运行任务使用的配置。必要时固定旧版本或暂停迁移，并限制扩展访问资源；不能把安装包更新当成无风险文字替换。

<a id="14-高频易错点"></a>
<a id="pitfalls"></a>

## ⚠️ 易错点

> ⚠️ Skill 被加载只表示知识可用，脚本是否执行要看真实工具调用与结果。

> ⚠️ Hook 在动作之后拒绝返回值，不等于动作没有发生。

> ⚠️ Plugin 是分发与扩展组织方式，名字不证明可信或拥有特殊权限。

## 本章自测

<details><summary>1. 报告 Skill 写了“检查全部引用”，是否证明引用已经检查？</summary>

没有。要执行相关读取或检查，取得可核对结果；文档描述不等于行动事实。

</details>

<details><summary>2. 完成通知 Hook 失败与必要批准检查失败，应采用同一种处理吗？</summary>

不应。前者可以按约定降级，后者不能在未确认时继续敏感动作。失败行为由责任与风险决定。

</details>

<details><summary>3. 插件升级把工具参数的含义改变，旧 Run 还能静默继续吗？</summary>

不能直接假设兼容。固定原配置、重新发现或暂停迁移，并检查变化是否影响授权与批准。

</details>
