# 11. 记忆：把有用经验带到以后，也能纠错和忘记

[← 上一章](10-CompactionAndContinuation.md) · [Agent 目录](../README.md) · [下一章 →](12-StateHistoryAndPersistence.md)

用户说：“以后给我的中文报告，先写结论，再写证据。”本次任务把它放入上下文就能使用；下一次新会话却未必还有这句话。

记忆解决的是有选择的未来复用。它不仅要能存和查，还要知道适用于谁、是否仍有效，以及用户改主意后怎样更新。

## 1. 从一条偏好走完生命周期

| 阶段 | 报告偏好的变化 | 程序要确认什么 |
|---|---|---|
| 候选 | “这次先写结论” | 是当次要求，还是长期偏好 |
| 范围确认 | “以后我的中文报告都这样” | 用户、文档类型和适用语言 |
| 保存 | 内容、来源与范围被记录 | 后续任务能够读取，隐私允许 |
| 召回 | 新报告开始时取得相关偏好 | 是否仍适用，是否与当前指令冲突 |
| 更新 | “客户 A 的报告先写证据” | 增加范围例外，而非误改所有报告 |
| 删除 | 用户不希望继续保存 | 原记录及相关索引、缓存按规则失效 |

**Memory（记忆）是为后续交互保留并维护的信息。** “A 已读、B 待查”主要是当前进度；“上传成功返回 report42”是业务回执。它们虽然也可能持久保存，但不能都靠长期记忆去猜当前任务是否完成。

## 2. 什么值得写入，什么时候写入

每轮结束就把整段对话永久向量化，会同时保存猜测、重复、临时情绪和敏感信息，后续检索难以区分哪些仍值得使用。

写入前至少判断：未来是否有用途，适用范围是否清楚，来源是否可核对，保存是否被允许，是否已经存在等价记录，以及如何过期或纠正。

用户明确要求记住时可以立即处理；某项事实确认后可以写；也可以在旧会话空闲后离线提取。没有通用的“第 N 轮升级为长期记忆”。真正的长期化，是进入未来任务可按规则读取的位置，而不是刚刚生成了一段摘要。

小系统可以用有范围的文本文件；规模更大、需要权限检索和更新时再用数据库或索引。**Vector DB 是可选实现，不是记忆本身。**

## 3. 记录结构服务理解和纠错

一条可用记录可以写成下面的业务表示，不要求照抄字段：

```text
内容：中文报告优先给结论
范围：用户 U 的通用中文报告；客户 A 除外
来源：用户明确确认的交互记录
状态：有效
复核：若本次明确要求不同，以本次要求为准
```

来源让你能回答“为什么相信它”，范围防止把一个人的偏好应用到别人身上，状态与失效关系防止旧记录继续回流。时间和版本用于判断变化，不是每读一次都要新建一份记录。

模型给出很高置信度，也不证明记录正确。高风险事实，例如生产环境地址或付款状态，应回到权威系统复核；记忆可以提示去哪查，不能替代实时授权与业务回执。

## 4. 先按用途理解分类，不必先建四张表

| 常见称呼 | 保存什么 | 边界 |
|---|---|---|
| Working memory（工作记忆） | 当前任务正在用的目标、证据和计划 | 常与当前上下文或状态重叠 |
| Episodic memory（经历记忆） | 某次排障、选择或任务的经验 | 当时成立，不自动适用于今天 |
| Semantic memory（事实记忆） | 项目事实、偏好和规范 | 要保留来源、范围与时效 |
| Procedural memory（过程记忆） | 怎样部署、怎样核查的步骤 | 可能由指令文件或 Skill 承载 |

这些是用途视角，不是行业统一数据库 Schema。一个事实也可能同时出现在历史记录、当前状态和模型输入中；重要的是明确每份表示服务什么决定。

RAG 是取回资料并辅助生成的方式，也可以用于检索记忆。不能把“外部知识用 RAG、历史信息用 Memory”理解成两个互斥技术；它们在来源和维护责任上有区别，实现可以组合。

## 5. 召回以后，还要检查适用性

当前要写客户 A 的英文报告，通用“中文报告先结论”的偏好就不该机械套用。先按可信用户和项目过滤，再按任务找相关记录，最后检查当前指令、例外与新鲜度，把合适内容交给上下文编排。

反复保存“喜欢简短”“不想长铺垫”等同范围信息，可以做 **Consolidation（整合）**，合并成更清楚的偏好。但要保留必要来源关系，不能把“这次用英文”整合成“以后永远使用英文”。

| 发现的问题 | 例子 | 处理 |
|---|---|---|
| 记错了 | 用户说中文，提取成英文 | 查来源纠正，失效错误派生记录 |
| 真正冲突 | 同一范围出现不兼容要求 | 比较来源与适用条件，必要时澄清 |
| 只是不同场景 | 客户 A 与其他报告格式不同 | 保留范围例外 |
| 已过期 | 项目测试命令已变更 | 读取当前配置，更新旧经验 |

“最新一条赢”不是通用规则。近期网页内容不能覆盖用户偏好，用户当前明确要求也不能被旧记忆盖过。无法确认时保留不确定性，不强行总结成唯一事实。

## 6. 隔离、删除与评估同样属于记忆能力

多用户系统要在存储和查询时使用可信身份，不能只在 Prompt 写“不要读别人的记忆”。向量索引、缓存与导出也必须遵守同样范围。

用户删除原记录后，旧索引和缓存如果仍召回它，效果上并没有忘记。备份和审计的保留政策需要明确，但不能继续把已删除内容当可用偏好注入。

评估不只看命中率：用后续任务比较开启和关闭记忆时是否减少重复询问、提高相关任务质量，是否引入旧错误或跨用户泄露。再做纠错与删除实验，确认改错或删除以后旧值不再覆盖新要求。

[Claude Code 的记忆文档](https://code.claude.com/docs/en/memory)展示文件型实现的一种选择；不同产品提取和召回时机不同，不应把某条流水线当所有 Agent 的必选方案。

<a id="summary"></a>

## 本章小结

记忆的价值来自后续可用，而不是存得多。写入有范围和来源，读取有适用性检查，错误能纠正、旧值能失效、用户能够删除。分类和存储方式服务这些责任。

## 🎯 面试怎么回答

### Agent 记忆怎样设计？

先定义值得复用的信息与范围，再决定何时提取、怎样保存来源、如何按任务召回。读取后检查当前指令和时效，长期支持整合、纠错与删除；向量库只是可选组件。

### 冲突或过期记忆怎么办？

先区分记错、真正冲突和不同场景，检查来源、范围与时间。过期事实回到当前权威系统确认；旧记录及索引缓存要失效，不能只在提示词追加一句忽略。

### 怎样验证记忆有用？

比较后续任务质量、重复询问、错误召回、隐私泄露和成本，并测试纠错与删除能否生效。召回很多记录不等于它们适用或真实。

<a id="16-高频易错点"></a>
<a id="pitfalls"></a>

## ⚠️ 易错点

> ⚠️ 持久保存不等于长期有效，当前回执也不应该只作为模糊经验记录。

> ⚠️ 工作记忆等分类是用途视角，不必机械对应四种数据库或四个服务。

> ⚠️ 删除原文本不自动删除派生索引和缓存，要验证后续是否仍然召回。

## 本章自测

<details><summary>1. “这次报告用英文”能自动保存成全局长期偏好吗？</summary>

不能。它首先是本次要求，长期复用要有明确范围或可靠确认，不能扩大解释。

</details>

<details><summary>2. 老记忆记录测试命令 A，当前项目配置写 B，先怎样做？</summary>

核对当前项目配置及适用版本。旧记忆可提供调查线索，但不能覆盖更直接的当前事实。

</details>

<details><summary>3. 用户撤销偏好后下一次仍按旧格式输出，除了原记录还应查什么？</summary>

相关检索索引、缓存、派生整合记录以及本次上下文是否仍包含旧偏好，逐条按来源关系失效。

</details>
