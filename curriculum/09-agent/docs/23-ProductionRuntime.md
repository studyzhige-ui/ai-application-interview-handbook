# 23. 生产运行：从任务承诺推导部署，而不是先画微服务

[← 上一章](22-CodingAgentDelivery.md) · [Agent 目录](../README.md) · [下一章 →](24-FrameworkSelection.md)

单个用户、几秒钟的只读任务，在一个进程里完成很合理。现在产品要求报告运行半小时、页面关闭后继续、进程重启后恢复，并同时服务多个用户。原来 HTTP 函数里的局部变量，还能承担这些承诺吗？

生产设计从这些具体承诺出发。组件要解决实际故障和容量问题，不是为了把架构图画满。

## 1. 先分开连接寿命与任务寿命

页面连接负责提交请求与接收进度，任务可能比连接活得更久。可以先返回一个任务标识，让用户查询状态、重连取得后续结果或明确请求取消。

```text
提交任务 → 校验身份与范围 → 接受并返回 run_id
                                 ↓
                           任务独立推进
                                 ↓
                查询状态 / 接收进度 / 取得产物
```

断开 SSE 或浏览器关闭，是否取消任务由产品约定。不能一边承诺后台继续，一边把唯一状态保存在请求函数里；也不能把网络断开直接当作用户要求取消。

运行记录要区分排队、执行、等待、成功、失败、取消与部分结果。接口不需要照抄固定 URL，但这些交互语义应清楚。

## 2. 需要恢复时，让执行者可以替换

Worker（任务执行进程）负责推进循环，可以持有临时连接和缓存。重启后仍需要的任务身份、取消、操作记录与产物，则放在适当可靠的存储里。

新 Worker 接管时，先确认执行权和未决动作，再重建环境与上下文。完整恢复机制见第 13 章；部署层的责任是确保接管真的使用这套流程，而不是队列重投递以后从头再做。

“控制程序、执行环境、持久任务记录”可以分开理解：控制程序决定下一步，执行环境运行命令或工具，任务记录让工作不依赖某个进程永远存活。这些职责可以同进程实现，也可以因隔离和扩缩容需要拆开。

## 3. 增加 Worker 前，先找到真正容量限制

更多 Worker 不会增加模型服务配额或数据库能力。假设模型端每次只允许十个并发请求，同时启动一百个任务，剩余请求可能排队、限流并放大重试。

需要按任务和下游实际容量安排准入、队列与并发上限。多租户场景还要避免一个用户耗尽全部额度；优先级和配额是产品选择，不应由模型随意修改。

| 瓶颈 | 先观察 | 可能的控制 |
|---|---|---|
| 模型配额 | 等待、限流、重试量 | 模型并发限制与排队 |
| 工具服务 | 请求时延、错误与积压 | 按依赖限制调用，控制重试 |
| 代码环境 | 启动耗时、CPU 与内存 | 资源上限，必要时预热 |
| 状态存储 | 提交时延与冲突 | 缩小必要写入，检查并发协议 |

背压让上游知道当前无法承接更多工作，而不是无限堆积活动任务。通用队列与限流算法在后端课程维护；这里要把它们落实到 Run、工具与子任务预算。

## 4. 工具、模型和执行环境怎样接入

模型适配统一请求和错误语义，工具执行器落实授权、结果与副作用规则。规模或审计需要时可以集中为网关；小系统可以是进程内模块，不要求先独立部署。

代码任务可能需要沙箱：分配受限工作区、提供最小凭证、限制文件网络与资源，结束后清理。环境池预热可以减少启动延迟，却增加空闲成本，应按真实工作量选择。

沙箱与 Session 的寿命不必相同。用户需要长期下载报告，就应在临时环境销毁前转存产物，并保留权限和引用；不能把唯一结果留在临时目录。

```text
用户界面与任务入口
        ↓
可靠任务记录 ↔ 任务调度与 Worker 循环
                         ├─ 模型适配
                         ├─ 工具与权限控制
                         └─ 必要的受限执行环境
        ↓
产物存储与结果查询

诊断追踪关联各阶段，但不是唯一业务记录
```

## 5. 按故障域决定应该继续还是停止

| 故障 | 需要回答的问题 | 不能默认假设 |
|---|---|---|
| 页面或入口断开 | 已接受任务是否独立继续 | 连接没了等于任务取消 |
| Worker 崩溃 | 能否按可靠记录安全接管 | 重投递就是安全重做 |
| 模型服务不可用 | 能否排队、兼容后备或停止 | 换模型不改变任务能力 |
| 工具响应丢失 | 动作是否已经发生 | 超时等于未执行 |
| 关键状态存储不可用 | 新副作用还能否被可靠登记与核对 | 先写外部、以后总能补回 |
| 一般诊断导出失败 | 是否允许降级观测继续 | 所有日志都必须阻断业务，或所有审计都可丢 |

关键安全审计有不可丢要求时，应定义可靠审计通道；一般性能 Trace 可以有不同策略。不能为了诊断便利，把每次工具输出、全部输入和秘密都永久写入同一存储。

租户身份应贯穿任务、记忆、工具凭证、产物与诊断访问。只在某张表加 tenant_id，不能防止执行侧取错另一个用户的凭证。

## 6. 用已经学过的责任检查架构遗漏

现在可以把责任放到同一张表，而不是第一次学习时就背八个英文平面。

| 责任 | 需要能够回答 | 主责知识 |
|---|---|---|
| 控制 | 下一步、等待和停止由谁决定 | 循环、规划与预算 |
| 上下文 | 本次给模型什么，为什么 | 编排与压缩 |
| 状态 | 已发生什么，哪些仍未知 | 持久化与恢复 |
| 能力 | 哪些工具可用，怎样发现 | 契约、注册与扩展 |
| 执行 | 谁真正执行，怎样处理失败 | 工具结果、并发与取消 |
| 安全 | 谁有权做，环境限制什么 | 授权、批准、沙箱与注入防护 |
| 协作 | 子任务和共享资源由谁负责 | 委派、所有权与汇聚 |
| 观测与评测 | 为什么失败，怎样证明改善 | Trace、评分和回归 |

这是一份检查清单，不是八个必须独立部署的服务。一个责任可能由多个组件共同实现，一个组件也可能承担多种责任。

## 7. 运营看每个合格任务的总表现

除了普通请求时延，还要观察排队时间、活动任务、完成时长、恢复成功、工具与模型调用量、资源利用和安全事件。费用包括模型、检索、工具、沙箱、存储、重试和人工处理，不只有 Token 单价。

把预算用完后的行为写清：暂停、延期、请求用户决定，或交付注明缺口的结果。不能无限执行直到供应商拒绝，也不能降级后悄悄降低验收标准。

生产变更先用代表任务和故障窗口回归，再按风险小范围发布，观察质量、成本与失败类型。架构图上有队列、检查点和 Trace，只说明设计了组件名称，不证明它们组合后可以正确恢复。

## 本章小结

从连接、恢复、容量和隔离承诺推导组件边界。执行者可替换，关键事实可核对，产物不依赖临时环境；用已有八类责任检查遗漏，但不机械微服务化。

## 🎯 面试怎么回答

### 生产 Agent 后端怎样设计？

先明确任务时长、连接和恢复承诺、并发与权限，再组织入口、可靠任务记录、调度循环、模型与工具接入、执行环境和产物。规模小时可以同进程，独立扩容或隔离需要时再拆。

### 为什么多开 Worker 可能更慢？

瓶颈可能是模型配额、工具或存储。更多并发增加争用、限流和重试，应按阶段容量准入、排队与背压，而不是只增加进程数。

### Trace 不可用一定要停止吗？

取决于数据责任。一般诊断可按策略降级，关键业务记录和必需安全审计不能无依据丢失。成功状态应来自可靠业务事实与验收，而不是只有诊断 Span。

<a id="22-高频易错点"></a>
<a id="pitfalls"></a>

## ⚠️ 易错点

> ⚠️ HTTP 连接、任务、Worker 和沙箱各有生命周期，不能默认同时创建和结束。

> ⚠️ 状态存储故障时继续产生无法核对的外部副作用，可能扩大恢复风险。

> ⚠️ 架构责任表不是部署清单，拆服务必须带来明确的隔离或容量收益。

## 本章自测

<details><summary>1. 用户关闭页面，但产品承诺报告继续运行，哪些内容不能只在 HTTP 函数里？</summary>

必要任务身份、当前进度、取消与操作记录、产物引用等应由任务运行机制可靠管理，连接只是交互通道。

</details>

<details><summary>2. 模型端只允许十个并发，增加到一百个 Worker 能自动提高吞吐吗？</summary>

不能。可能增加排队、限流和重试，应根据依赖容量限制并发并测量真正瓶颈。

</details>

<details><summary>3. 沙箱销毁后报告链接失效，违反了什么设计要求？</summary>

若承诺保留交付物，就应在清理临时环境前转存到适当持久位置，维护可授权访问的引用。

</details>
