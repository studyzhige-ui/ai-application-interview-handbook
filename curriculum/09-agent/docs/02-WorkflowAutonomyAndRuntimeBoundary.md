# 02. Workflow 与 Agent：哪些决定交给模型

[← 上一章](01-AgentSystemAndResponsibilities.md) · [Agent 目录](../README.md) · [下一章 →](03-AgentLoopAndExecutionScopes.md)

“用了大模型”与“让模型决定下一步”不是一回事。一个程序可以先用模型分类，再按写好的分支处理；另一个程序则可能根据新证据决定继续查什么。两者都能有用，但需要承担的成本和风险不同。

我们继续使用资料报告任务，比较它们怎样处理同一个变化。

<a id="core-1"></a>

## 1. 固定的是控制规则，不是每次得到的答案

假设任务规定：依次读取 A、B，提取发布日期，日期不一致就返回“需要人工确认”。程序可以提前写好全部分支。

```text
读 A → 读 B → 提取日期 → 是否一致？
                          ├─ 是：生成报告
                          └─ 否：交给用户确认
```

这就是 **Workflow（工作流）**：主要控制路径由开发者预先安排。提取日期可以使用模型，输入也可以是自然语言，仍不改变“下一步由预定义规则决定”的事实。

工作流并不意味着只有一条直线。它可以有条件分支、循环和并行；区别在于选择哪些路径的规则由谁规定。

## 2. 当调查路径无法提前列完

如果用户要求“尽量核清差异来源”，A、B 的冲突可能有不同原因：文件过期、时区不同、不同地区分批发布，或某份资料只是草案。把所有调查路径提前写完可能很困难。

可以给模型有限的调查能力，让它根据已读内容提出下一步：

| 新观察 | 合理的行动候选 | 程序仍负责什么 |
|---|---|---|
| B 写明是草案 | 查询批准版本 | 限定可读目录，检查工具参数 |
| A 缺少年份 | 向用户澄清或查相关记录 | 不把猜测标为已确认 |
| 找到正式公告 | 比较是否解释了冲突 | 检查来源、任务要求与预算 |
| 授权材料都不能确定 | 停止调查并说明缺口 | 不扩大权限、不无限搜索 |

**Agent 把部分行动选择交给模型，但不把全部控制权交出去。** 模型选择调查方向，程序约束允许能力、执行成本和终止条件。[Anthropic 对工作流与 Agent 的区分](https://www.anthropic.com/engineering/building-effective-agents)也强调控制方式，而不是步骤数。

## 3. 怎样决定是否值得增加自主权

先用最简单、能满足要求的方案建立基线。然后观察它究竟在哪失败：

1. 资料齐全，只是输出漏引用：先改生成说明和结果校验。
2. 固定提取经常遇到已知几种格式：先比较规则、模型节点和明确分支。
3. 必须根据新观察选择未知资料或反复试验：再考虑受控 Agent 循环。

不能从“文本不够好”直接跳到“增加规划器和多个 Agent”。新增组件应该对应已确认的缺口。

| 方案 | 控制方式 | 主要收益 | 新增代价 |
|---|---|---|---|
| 单次模型调用 | 输入就绪后生成一次 | 简单，容易比较输出 | 不会主动取得缺失信息 |
| 含模型节点的工作流 | 阶段和分支预定义 | 路径可预期，故障位置清楚 | 未列出的调查路径需另设计 |
| 受控 Agent | 模型根据观察选择行动 | 适应开放任务和动态环境 | 路径不确定，成本与风险可能累积 |

输入是否结构化、任务是否很长，都只是线索，不是分类定律。开放文本也能走固定流程，长任务也可能完全不需要模型自主规划。

> ⚠️ “更自主”不等于“更可靠”。应在相同任务集上比较质量、时间、费用和失败后果，而不是只看演示是否聪明。

## 4. 很多系统需要的是混合控制

对报告任务，可以允许模型自主读取已授权资料，但发送给外部客户前仍要确认收件人和报告内容。调查与提交采用不同控制方式，并不矛盾。

```text
程序确认身份、范围和输入
          ↓
模型在允许范围内调查与起草
          ↓
程序校验产物，必要时请求人工批准
          ↓
受控发送并核对回执
```

高风险操作并非只能由人手工完成；但是否自动化必须有明确规则和验证能力。用户也不能通过批准得到自己原本没有的访问权。

自主权因此可以按动作划分：允许选资料，不允许扩大目录；允许修改草稿，不允许直接发布；允许提出付款建议，不允许自行扣款。比起给整个 Agent 标一个“高自主等级”，这些界限更能指导实现。

## 5. 控制职责与实现工具不要混淆

**编排器（Orchestrator）** 关心交给哪个节点或角色、怎样推进；**工作流引擎（Workflow Engine）** 通常提供预定义流程的执行、调度和状态支持。它们可能是运行时内部的一部分，也可能由框架同时提供，不能因为名称不同就强拆服务。

提示词设计改善模型收到的指令；上下文工程决定本次输入还包含哪些资料和观察；Harness 工程还要把候选行动接到真实执行、限制与验证。三者相互配合。例如，提示词说明“不要改原件”，上下文提供正确资料，文件工具权限真正限制写入。

框架适配应在这些职责明确以后进行。否则很容易因为框架有一个 Planner 节点，就把本来只需固定读取的任务变成规划系统。

<a id="summary"></a>

## 本章小结

判断工作流与 Agent，先看谁决定后续行动。自主权应由任务的不确定性和验证条件推导，并按具体动作限制。简单方案暴露了真实缺口，才有理由增加动态性。

## 🎯 面试怎么回答

### 工作流里每个节点都调用模型，它一定是 Agent 吗？

不一定。节点、分支和继续条件主要由程序预定义时，它仍是含模型节点的工作流。关键是是否让模型根据观察动态选择后续路径，而不是模型调用次数。

### 什么时候不应该增加 Agent 自主权？

固定输入、路径和校验已能满足需求时，不应只为技术标签增加不确定性。错误代价高而又缺乏验证与隔离能力的动作，也不宜开放给模型自由决定。

### 为什么生产应用经常混合工作流和 Agent？

探索阶段需要动态判断，但身份、权限、验收和高风险提交通常需要确定性规则。按动作划分自主范围，既能使用模型处理不确定信息，也能限制它影响真实系统的方式。

<a id="13-高频易错点"></a>
<a id="pitfalls"></a>

## ⚠️ 易错点

> ⚠️ 工作流可以有循环和分支，不能把“有循环”单独当成 Agent 的定义。

> ⚠️ 一次摘要漏字段不自动说明缺少规划能力，应先定位生成或校验问题。

> ⚠️ 模型、编排器、运行时和框架不是必须互斥的部署层，先比较职责再比较实现。

## 本章自测

<details><summary>1. 审批流程有 20 步，所有分支都预定义，需要叫 Agent 吗？</summary>

不需要。步骤多不改变控制规则的来源。可以直接使用工作流表达。

</details>

<details><summary>2. 两份资料冲突后，要根据内容决定查批准记录还是查地区政策，为什么可能适合 Agent？</summary>

下一步取决于动态观察，固定枚举可能不够。可以让模型选择调查方向，但必须限定资料范围、预算和无法确认时的退出方式。

</details>

<details><summary>3. 能自主起草但不能自主发送，是否说明设计不完整？</summary>

不是。起草和发送的风险不同，可以对发送单独批准并校验目标。自主权不必在所有动作上相同。

</details>
