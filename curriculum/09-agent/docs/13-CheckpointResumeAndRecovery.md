# 13. 检查点与恢复：保存之后、崩溃之前发生了什么

[← 上一章](12-StateHistoryAndPersistence.md) · [Agent 目录](../README.md) · [下一章 →](14-PermissionApprovalAndSandbox.md)

报告已经上传，程序却在保存成功回执前崩溃。重启后只能读到“尚未上传”的旧进度，应不应该再传一次？

这不是让模型回忆对话就能解决的问题。我们需要区分保存时的状态、外部真正发生的动作，以及程序还不能确定的部分。

## 1. 检查点记录位置，不会回退外部世界

**Checkpoint（检查点）** 保存一个可继续的位置及必要状态或引用；**Resume（恢复执行）** 读取这些记录并重新推进任务。

```text
C1：A、B 已处理，草稿存在，尚未上传
        ↓
请求上传 → 远端生成 report42
        ↓
本地尚未保存新回执，进程崩溃
        ↓
新进程只能读到 C1
```

C1 真实描述的是保存时的情况，不是重启时外部世界的情况。报告不会因本地回到 C1 而从远端消失。检查点越频繁，可以减少重算，但不能自动消除外部成功与本地保存之间的窗口。

## 2. 把一个业务动作和多次尝试分开

对于不能盲目重复的上传，先建立稳定的逻辑操作 `op7`。同一个 op7 可以因网络问题有多次尝试，但应仍表示“上传这份报告到这个目标”，不能每次重试都变成新动作。

```text
保存 op7 的意图、目标与请求内容指纹
        ↓
使用 op7 请求下游执行
        ↓
下游创建 report42，或返回原 op7 的结果
        ↓
保存 op7 → report42 的可靠回执
        ↓
C2：上传已确认，可进入交付
```

`call_id` 关联模型工具请求与结果，`operation_id` 识别业务动作，`attempt_id` 区分网络尝试。它们目的不同，但接口简单时不必复制三份相同字段；关键是不能用新尝试身份代替原动作身份。

**幂等** 在这里指重复请求不会重复产生该业务效果。下游必须真正支持对应契约，键要在有效期内，请求含义也要一致。只在本地写一个 `idempotency_key` 字段，不会让远端自动去重。

## 3. 按故障窗口决定恢复策略

| 恢复时拥有的证据 | 可以怎么做 | 不能怎么推断 |
|---|---|---|
| 只读步骤可重取，且当前版本可接受 | 重新读取 | 假定读取结果仍与过去相同 |
| 有可靠成功回执并能核对对象 | 补齐状态，不重复创建 | 因旧检查点未完成就重做 |
| 请求可能发出，没有确定结果 | 查询原操作，或按有效幂等契约重试 | 把没有回执当成没有执行 |
| 下游不能查询或去重 | 暂停、人工核对或采用预先设计的业务流程 | 反复新建操作直到看见成功 |

操作账本（Side-effect Ledger）记录逻辑身份、目标、是否已确认和外部引用等必要事实。它不是所有调试日志的全集，也不必和检查点同频率保存。

> ⚠️ 本地仍写着 planned，也不一定证明请求从未发送。可能是发出后还没更新状态就崩溃。必须结合调度保证、下游查询或幂等能力判断，不能仅凭一个旧状态盲重做。

## 4. 恢复先核对，再请求模型继续

恢复程序可以依次处理：

1. 读取任务身份、当前取消和待批准状态，确认调用者有权恢复。
2. 检查自己是否拥有推进权，状态与工具配置是否兼容。
3. 核对未决外部动作，补齐已知事实或保留未知。
4. 重新取得所需工作区、产物引用和连接。
5. 按当前有效权限与预算重建模型输入，从允许的位置继续。

若用户在崩溃后取消任务，新处理者不能只读取消前的检查点就恢复执行。等待人工批准时，应保存具体待批动作，批准回来后复核目标与条件，而不是永远依赖一个内存中的等待协程。[Agents SDK HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/)提供了一种暂停、序列化运行状态和继续的实现。

检查点适合放在结果已确认、状态变更已提交等清楚的阶段边界。廉价只读步骤可以粗一些；高风险操作、取消与批准需要按其风险及时保存。不是所有 CPU 指令或每条进度日志都应成为检查点。

## 5. 补偿不是数据库回滚

预订资源后任务失败，可以新发一个取消预订操作；邮件已被阅读，却不能回滚成“从未看过”。这就是 **Compensation（补偿）**：用新的业务动作缓解已经发生的结果。

补偿也可能失败，需要自己的授权和重试规则。原动作结果未知时，先核对；否则可能对根本没有发生的动作实施反向操作。多步流程按既定顺序补偿，与 Saga 的思想相近，但 Agent 不应凭自然语言临时发明一套分布式事务保证。

## 6. 恢复、分叉和重放不是同一操作

| 操作 | 目的 | 外部动作会怎样 |
|---|---|---|
| Resume | 同一任务继续 | 先核对已发生部分 |
| Fork（分叉） | 从某个状态开始另一条探索 | 已发邮件和数据库不会被复制或撤销 |
| State replay（状态重建） | 应用已有事件恢复状态 | 通常不重新执行真实工具 |
| Model replay（模型重演） | 用选定输入再次请求模型 | 输出不保证完全相同 |
| Action replay（动作重放） | 再做工具动作 | 需要重新判断权限、幂等和环境 |

分叉要确定允许继承哪些指令、记忆与工作区引用，并分配新身份和预算。复制一份对话，不等于复制整个外部世界。

框架也有具体恢复单位。例如 [LangGraph 的中断文档](https://docs.langchain.com/oss/python/langgraph/interrupts)说明恢复时节点可从开头执行，中断前代码会再运行。因此有检查点仍需要保护节点中的副作用，不能承诺回到任意程序行。

## 7. 新处理者接管，不代表旧处理者已经停止

Worker A 网络暂时断开，租约过期，B 接管；A 随后恢复，可能仍想写入。仅有超时时间，不能物理阻止 A。

可以在实际写入边界检查新的所有权代次或 fencing token（隔离旧写者的令牌），拒绝旧所有者提交。状态更新也可结合版本检查。若下游不支持这个边界，就不能宣称租约已经保证所有外部动作单写。

恢复能力最终要用故障窗口测试：在请求前、外部成功后、本地回执前分别中断，观察是否重复、是否丢失取消、是否如实保留未知。组件名齐全不等于恢复协议正确。

<a id="summary"></a>

## 本章小结

检查点只记录保存位置；操作记录和下游契约补上两点之间的事实。恢复先核对取消、所有权、权限和未知动作，再继续。补偿、分叉和重放有不同含义，不能把外部世界当成可随意回退的内存。

## 🎯 面试怎么回答

### 工具成功但检查点没写，怎样避免重复执行？

用稳定业务操作身份和可靠回执记录，恢复后查询原操作或按有效下游幂等契约重试。已确认则补齐状态；不能确认又不能安全去重时暂停核对，而不是生成新键重做。

### 检查点应保存什么？

保存重启后继续所需的位置、目标约束、未决操作、产物与必要控制状态或引用。具体字段从恢复承诺推导，不是全量内存和日志。关键操作记录可以独立于阶段检查点保存。

### 为什么租约还需要 fencing？

租约过期只改变谁应拥有执行权，不保证旧进程已经停止。实际写入边界需要识别并拒绝旧代次，否则新旧处理者仍可能同时提交。

<a id="17-高频易错点"></a>
<a id="pitfalls"></a>

## ⚠️ 易错点

> ⚠️ 提高检查点频率不消除跨系统成功与本地保存之间的故障窗口。

> ⚠️ 幂等键必须对应稳定动作并受下游契约支持，不能每次重试换新键。

> ⚠️ 取消和补偿不会让已发生的动作消失；未知结果应先核对，不伪装成失败。

## 本章自测

<details><summary>1. C1 显示未上传，下游按 op7 查到 report42，应该怎样恢复？</summary>

核对 report42 属于原动作，补齐本地回执与进度，不再创建新上传；同时检查任务是否已经取消。

</details>

<details><summary>2. 只有旧 planned 状态，下游不支持查询或幂等，能够证明没执行吗？</summary>

不能。发送后更新本地状态之前也可能崩溃。应保持未知并按业务核对，不能靠新上传确认旧上传。

</details>

<details><summary>3. 用事件重建状态时，为什么不应该再次调用所有历史工具？</summary>

事件已经表示动作发生过，再执行会产生新的副作用。状态重建通常只应用记录；动作重放需要另行授权和安全判断。

</details>

<details><summary>4. A 租约过期而 B 已接管，A 恢复后怎样避免覆盖 B？</summary>

在状态或下游实际写入边界检查所有权代次或 fencing token，拒绝旧所有者；不能仅相信 A 会及时看到取消。

</details>
