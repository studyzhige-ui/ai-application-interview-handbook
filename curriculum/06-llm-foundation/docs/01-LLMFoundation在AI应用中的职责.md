# 01｜模型在 AI 应用中负责什么

[模块首页](../README.md) · [Token、上下文与长文本 →](02-TokenContext与LongContext.md)

用户问：“订单 A 明天能送到吗？”客服助手回答：“可以，预计明天送达。”这句话读起来很自然，但数据库里的订单 A 还没有发货，也没有预计送达时间。

问题到底是模型不够强，还是应用没有把订单状态交给模型？如果连输入里有什么都没有检查，就去调参数、换模型，很可能花了更多钱，仍然稳定地答错。

**本模块要建立的是模型侧的因果关系：输入怎样被表示，答案怎样产生，计算为什么消耗时间和显存，以及这些机制怎样影响应用决策。** 不要求先会训练大模型，也不把模型当成只需调用的黑盒。

## 1. 先区分模型、模型服务和业务应用

模型可以看作一个带有大量已学习参数的计算过程。**参数**是训练得到的数值，例如矩阵中的权重；**推理**是固定这些参数，用新输入计算输出。一次普通聊天请求不会因为你纠正了模型，就自动修改这些权重。

业务应用通常不能直接把一句话交给“裸模型”。它要选择信息、组织请求，再检查结果：

```text
用户：订单 A 明天能到吗？
    ↓
应用查询订单：未发货；预计送达时间为空
    ↓
应用组织模型输入：问题、订单事实、回答要求
    ↓
模型服务运行模型，返回生成内容
    ↓
应用检查事实与格式，展示结果
```

这里有三个不同主体：

| 主体 | 在这个例子中做什么 | 不能据此推断什么 |
|---|---|---|
| 模型 | 根据看到的内容生成回答 | 不等于已经读取数据库，也不等于回答属实 |
| 模型服务 | 接收请求、安排计算、返回结果 | 接口可用不等于业务已经成功 |
| 业务应用 | 查询有权访问的订单、组织信息、验证与展示 | 不能把未验证的生成文本直接当作订单状态 |

对当前例子，合理结果是“订单尚未发货，目前没有预计送达时间，无法确认明天送到”。这不是因为换了一句更聪明的提示词，而是先补上了真实信息，并限制结论不能超出证据。

> ⚠️ 注意：模型生成“已退款”三个字，不会使支付系统完成退款。模型提出的工具调用也只是待处理的请求；权限检查、真实执行和结果确认由应用负责。工具调用的完整生命周期在 Agent 模块讲解。

## 2. 模型为什么能够续写，却不能天然保证事实正确

以本课程主要讨论的自回归语言模型为例，它先把输入拆成 **Token（模型使用的离散文本单元）**，再根据已有序列计算下一 Token 的分数。选择一个 Token 后，把它接到序列后面，继续计算。

“订单 A 尚未”之后接“发货”，只是帮助理解的文本例子，不代表真实分词一定按这些词切开。重要的是依赖关系：后一步的输入包含前面已经选择的内容。

```text
已有内容 → 下一 Token 的候选分数 → 选择一个候选
   ↑                                  │
   └───────── 把选中的 Token 接回 ──────┘
```

模型的语言能力来自训练，不是由上述循环本身凭空产生。预训练让模型从大量样本中学习语言与知识关联；后续训练可以进一步调整任务遵循和行为。训练得到的能力仍不同于对当前订单的实时查询：训练时见过什么，不代表此刻拿到了哪一位用户的最新状态。

因此，**生成概率描述“在当前条件下怎样续写”，不能直接当作“这个业务事实为真的概率”。** 完整的序列加工和生成选择，分别在第 3～5 章展开。[自回归结构依据](https://arxiv.org/html/1706.03762v7#S3)

## 3. 用一次失败找出应该改哪一层

继续检查订单 A 的错误回答。先保留这次请求实际使用的输入和返回结果，再沿着数据流找第一个偏离要求的位置。

| 检查到的状态 | 说明什么 | 优先处理方向 |
|---|---|---|
| 输入没有订单状态 | 模型缺少当前事实 | 补充查询结果，而不是要求模型猜测 |
| 输入带的是另一位用户的订单 | 信息选择或权限边界出错 | 修正应用的数据读取与隔离 |
| 正确状态在输入中，但模型仍承诺明天送达 | 证据使用或生成判断出错 | 检查任务要求、模型能力及结果验证 |
| 模型返回“无法确认”，应用却展示“明天送达” | 模型之后的处理出错 | 排查解析、状态映射和界面展示 |

这张表不是宣称每个问题只有一种修法。它要求先找到事实：**谁在什么条件下，对什么输入做了什么，结果从哪一步开始错误。** 有了这个位置，才谈 Prompt、检索、模型选型或业务代码。

把所有错误都叫“幻觉”，会丢失这种定位能力；把所有延迟都归因于“模型大”，也会混淆排队、输入处理和输出生成。

## 4. 从这里建立怎样的学习主线

先学输入与计算，再学运行成本，最后判断怎样改进效果：

```text
Token 与上下文：模型实际读到了什么
    ↓
Transformer 与 Attention：已有信息怎样参与计算
    ↓
生成与缓存：下一个 Token 怎样产生，哪些计算可以复用
    ↓
模型服务与 API：如何测量、接入和选择
    ↓
检索模型与多模态：不同输入、输出目标怎样改变模型角色
    ↓
Prompt、事实治理与训练：面对明确缺口，选择合适的干预
```

本课程以**采用因果注意力的 Decoder-only（仅解码器）模型**建立主要计算模型，再说明检索模型、多模态模型及其他实现的差异。这里的“因果”指当前位置不能读取未来 Token，不是说模型天然具有可靠的因果推断能力。

讨论缓存容量时还会明确“普通 K/V 表示、全注意力”等条件。使用其他架构时，要回到该模型的实现和文档；不能把教学模型的一个公式套到所有模型上。

矩阵只需先理解为按行、列组织的数值，后面会解释用到的运算。反向传播证明、分布式训练和 GPU 内核实现不是当前主线；但它们造成的成本和使用边界不能省略。

## 5. 与前后模块怎样衔接

前面的 Vector DB 负责怎样存储和搜索向量。本模块第 9 章解释向量怎样从文本得到；它的开头提供可独立阅读的最小桥梁，不要求为学习向量数据库先学完所有模型章节。

后面的 RAG 负责把外部资料变成可追溯证据，并选择哪些证据交给模型。Agent 负责围绕任务持续运行，控制工具、权限和状态。三者不是互相替代的产品名称：

| 需要解决的问题 | 主要讲解位置 |
|---|---|
| 文本怎样得到检索向量，候选怎样被模型评分 | 本模块第 9 章 |
| 向量搜索怎样兼顾召回、速度和更新 | Vector DB |
| 文档怎样解析、召回、重排、引用与评测 | RAG |
| 工具何时执行、失败怎样恢复、状态如何持久保存 | Agent 与 Backend |

## 本章小结

模型根据输入计算输出，模型服务安排计算，业务应用提供事实并承担实际动作的正确性。学习模型基础，是为了把输入、行为、成本和失败联系起来，而不是背诵一串架构名称。

## 🎯 面试怎么回答

**问：做 AI 应用为什么还要理解模型内部机制？**

> 因为应用决策会受到模型机制的直接约束。分词和上下文决定实际输入，序列生成决定输出依赖，缓存与推理阶段决定延迟和并发。我会用这些机制定位问题，再选择改输入、模型、服务还是业务流程。比如订单状态缺失时应先查询事实，而不是只调低随机性；模型说操作成功，也必须由真实系统结果确认。

## ⚠️ 易错点

把模型参数、当前上下文和应用长期记忆混成一件事，会误以为“说过一次就永久记住”。它们分别是学习得到的数值、当前可见输入，以及应用另行管理的状态。

把模型可生成工具参数理解成“模型已经执行工具”，会越过权限和结果验证。先区分生成请求与动作完成，再讨论 Agent。

## 自测

**任务 1：** 一个助手看到“订单未发货”，回答“已送达”；另一个助手实际收到的输入里没有订单数据。分别指出首先要核对的对象，以及为什么不能都用“换模型”处理。

<details><summary>提示</summary>

比较两次调用中模型实际获得的证据，不从最终句子反推输入。

</details>

<details><summary>答案与解释</summary>

前者先检查完整输入中的任务要求、冲突信息、截断情况，以及模型如何使用正确证据；后者先修复事实供给。更强模型可能改善证据使用，却不能凭空保证取得未被提供的私有订单状态。

</details>

**任务 2：** API 返回了一条退款工具调用，参数格式合法，但执行程序还没有调用支付服务。请写出此时已完成与未完成的两件事。

<details><summary>答案与解释</summary>

已完成：模型生成了可解析的调用请求。未完成：应用授权并实际执行退款，且确认支付系统结果。不能展示“退款成功”。

</details>
