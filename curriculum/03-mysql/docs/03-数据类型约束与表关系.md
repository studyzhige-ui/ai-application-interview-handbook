# 03｜字段、约束与表之间的关系

[← 用 SQL 查询、增加、修改和删除记录](02-单表查询与增删改.md) · [MySQL 目录](../README.md) · [把多张表查在一起，把多条记录汇总起来 →](04-关联查询与分组统计.md)

任务清单开始由整个团队使用。给每条任务加上负责人姓名看起来很直接，但“小林”改名以后，要修改多少条任务？如果只改了一半，另一个人查询时应该相信哪一个名字？

表设计先解决这些日常问题：什么是独立记录，什么通过编号关联，哪些值可以缺失，哪些错误应由数据库直接拒绝。它不是从几十个字段类型开始背诵。

## 1. 负责人和任务各有自己的记录

从本章起，使用三名成员、六条任务。它们与第 02 章的 `first_tasks` 是不同的教学表；后续章节默认回到这里的初始数据，只有明确写着“接着上一步”时才继承修改。先看成员与任务的完整输入：

| members.id | tenant_id（团队） | name |
|---:|---:|---|
| 1 | 10 | 小林 |
| 2 | 10 | 小周 |
| 3 | 20 | 小陈 |

<a id="task-model"></a>

| tasks.id | tenant_id | owner_id | title | status | priority | created_at |
|---:|---:|---:|---|---|---:|---|
| 1 | 10 | 1 | 整理笔记 | pending | 2 | 2026-09-01 09:00:00 |
| 2 | 10 | 1 | 修复登录 | done | 1 | 2026-09-01 10:00:00 |
| 3 | 10 | 2 | 练习 SQL | pending | 3 | 2026-09-02 09:00:00 |
| 4 | 10 | NULL | 写周报 | pending | 1 | 2026-09-02 10:00:00 |
| 5 | 20 | 3 | 导入文档 | pending | 2 | 2026-09-03 09:00:00 |
| 6 | 10 | 2 | 整理测试 | done | 2 | 2026-09-04 09:00:00 |

`members.id` 与 `tasks.id` 是各自表的 BIGINT 主键；两表的 tenant_id 是非空 BIGINT。成员 name 是非空 VARCHAR(40)；任务 owner_id 是可空 BIGINT，title 是非空 VARCHAR(100)，status 是非空 VARCHAR(16)、默认 pending，priority 是非空 INT、默认 1，created_at 是非空 DATETIME。本课程统一把这些时间字段解释为 UTC；DATETIME 自身不替我们执行这个约定。

这份起始模型只有上述主键、非空和默认规则；下面讨论的组合唯一键与外键是进一步加上的约束，不能把设计建议误认成初始表已经强制执行的规则。[seed.sql](../examples/seed.sql) 是相同输入的可选运行形式，理解后面的 SQL 不必先执行它。

`tasks.owner_id` 保存成员编号，不保存一整份成员资料。小林改名时，修改 `members` 的一条记录即可；需要姓名的查询，再通过编号找到它。这叫**一对多**：一个成员可以负责多条任务，每条任务在本例至多有一名负责人。

如果一条任务允许多人参与，就需要另外一张“任务—成员”关联表，每行记录一次对应关系。这是**多对多**，不是给任务不断加上 `owner_1`、`owner_2` 等列。先依据业务关系决定怎样拆表，才能知道查询时应怎样关联。

本例 `members` 中每行表示一个团队成员。如果同一个人能加入多个团队，可以进一步区分“用户”和“成员关系”，而不是假设一张成员表适用于所有产品。

## 2. 类型规定能放什么，NULL 表示没有值

列的数据类型应贴合含义。编号和计数通常用整数；标题用有长度上限的文字；金额需要精确小数；时间需要明确日期与时区约定。

| 含义 | 常用类型 | 一个需要知道的边界 |
|---|---|---|
| 整数编号、计数 | `INT`、`BIGINT` | 有取值上限，不是无限增长的数字 |
| 标题、状态文字 | `VARCHAR(n)` | n 是字符上限，不是预先占满的字节数 |
| 精确金额 | `DECIMAL(p,s)` | p 是总位数，s 是小数位数 |
| 日期时间 | `DATETIME`、`TIMESTAMP` | 时区转换和取值范围不同 |
| 大段内容、扩展属性 | `TEXT`、`JSON` | 能存不代表适合每次列表查询都读取 |

例如 `DECIMAL(8,2)` 允许总共 8 位数字，其中 2 位在小数点后，适合精确保存 `123.45` 这样的数。

时间还要有共同约定：DATETIME 保存给定的日期时间字段，不自动按会话时区转换；TIMESTAMP 会在写入和读取时按会话时区与 UTC（协调世界时）转换。同一个时刻在两个时区可以显示不同钟点，不能只比较显示文字判断数据是否改变。选型时再核对范围，不必先背全部时间类型。[日期时间类型](https://dev.mysql.com/doc/refman/9.7/en/datetime.html)说明了这项转换。

这些类型各服务什么值，比一次记完所有范围更重要。[官方数据类型说明](https://dev.mysql.com/doc/refman/9.7/en/data-types.html)用于选型时核对范围。文字比较还涉及排序规则：例如是否把大小写不同的名称视为相同。字符集 `utf8mb4` 负责表示字符，排序规则负责比较，两者职责不同。

任务 4 的负责人为 `NULL`，意思是尚未填写负责人，而不是“负责人编号为 0”。`NULL` 也不等于空字符串。判断有没有负责人，要写：

<a id="sql-owner_missing"></a>

<!-- mysql-example: owner_missing -->
```sql
SELECT id, title FROM tasks WHERE owner_id IS NULL;
```

结果是 `(4, '写周报')`。普通 `=` 比较遇到 NULL，结果是未知，不是“相等为真”。由于 WHERE 只保留为真的行，`owner_id = NULL` 不能用来查缺值。[NULL 的官方规则](https://dev.mysql.com/doc/refman/9.7/en/working-with-null.html)。

## 3. 约束把明确规则交给数据库检查

**约束是数据库在写入时检查的条件。** 不满足要求时拒绝这次写入，而不是保存后再等别人发现。

主键 `PRIMARY KEY` 为每行提供唯一且非空的身份；`NOT NULL` 要求列有值；`UNIQUE` 禁止重复的实际键值；`CHECK` 检查声明的条件。例如额度必须非负，可以同时写 `quota INT NOT NULL` 和 `CHECK (quota >= 0)`。

为什么需要两条？`NOT NULL` 拒绝“没填写”，CHECK 拒绝“填写了负数”。它们不是重复保护：CHECK 表达式得到未知时也可以通过，因此单独的 `quota >= 0` 不能代替非空要求。[CHECK 的规则](https://dev.mysql.com/doc/refman/9.7/en/create-table-check-constraints.html)。

唯一性同样要说明范围。“成员的外部编号不能重复”可能是全站不能重复，也可能只是同一个团队内不能重复。后一种应约束 `(tenant_id, external_code)` 这个组合。两个团队的相同外部编号并不冲突。

> ⚠️ MySQL 的可空唯一列可以出现多个 NULL。要求每条记录都有且只有一个不同编号时，需要同时使用 NOT NULL 与 UNIQUE；NOT NULL 则仍允许空字符串，不能当作“文字不能为空”的全部校验。

## 4. 外键维护关系，业务决定允许哪些关系

任务引用成员编号 1，是因为成员表确实有这条记录。**外键可以表达这种引用要求**：任务表作为子表写入非空负责人编号时，被引用的成员表作为父表，必须存在对应编号。父记录被删除时如何处理，也要选择拒绝、级联等合适策略，而不是让任务无声变成无主数据。

多团队还有另一层要求：任务 1 属于团队 10，不能误指向团队 20 的成员。只检查负责人 id 存在不够。可以让父表声明 `(tenant_id,id)` 的唯一组合，再由任务的 `(tenant_id,owner_id)` 引用它，校验双方团队一致。

对应的约束可以明确写成：

```sql
ALTER TABLE members ADD UNIQUE KEY uq_member_tenant (tenant_id, id);
ALTER TABLE tasks ADD CONSTRAINT fk_task_owner
  FOREIGN KEY (tenant_id, owner_id) REFERENCES members (tenant_id, id);
```

初始六条任务都满足它，包括 owner_id 为 NULL 的任务 4；把团队 10 的任务指给成员 3，会因父表没有 `(10,3)` 而拒绝。默认不级联删除，删除仍被任务引用的成员也会失败，应由业务先处理任务归属。外键检查的是关系，不负责当前用户授权。

是否使用数据库外键还要结合迁移和系统边界评估；不使用外键时，这项完整性责任也不会自动消失。可选的[约束实验](../examples/experiments.md#lab-03)给出相同问题的隔离操作。

## 5. 从修改异常理解规范化

假设把任务参与关系存成 `(task_id, member_id, task_title, member_name)`，其中 `(task_id,member_id)` 唯一标识一次参与。它是一个**候选键**：能唯一识别记录，且不能再删去其中一列。选作 PRIMARY KEY 的候选键叫主键；其他候选键仍可表达业务唯一性。

在这项业务中，给定 task_id 就能确定 task_title，给定 member_id 就能确定 member_name。这叫**函数依赖**，记作 `task_id → task_title`。它描述业务规则，不是“这六条数据碰巧没有重复”。混在一张表里会出现三类异常：

- 小林改名，要改他的每一条参与记录，漏改一条就有两个名字：更新异常。
- 新成员还没有任务，无法自然插入一条参与记录来保存姓名：插入异常。
- 删掉小林最后一条参与关系，连他的姓名也丢了：删除异常。

规范化就是把这些依赖放回合适的关系：

| 层次 | 在本例检查什么 | 改法 |
|---|---|---|
| 1NF | 一格是否混着要独立查询的多个成员编号 | 不存 `"1,2,3"`，一行表达一次参与 |
| 2NF | 非键属性是否只依赖组合候选键的一部分 | task_title 放 tasks，member_name 放 members，关联表只保留关系属性 |
| 3NF | 非键属性是否又依赖另一个非键属性 | 若成员带 department_id、department_name，且部门编号决定名称，就拆出 departments |

这里用的是常见无复杂候选键的判断模型；更精确地说，2NF 排除非主属性对候选键的部分依赖，3NF 要求每个非平凡依赖的决定项是超键，或被决定属性属于某个候选键。无需为了使用三张表先背更多范式，但不能把“列越少越规范”当定义。

多对多关联表可写成 `task_members(task_id, member_id, role)`，主键为 `(task_id,member_id)`，role 表示该成员在该任务里的职责，依赖的是整个组合。多租户时还要像负责人关系一样约束两端团队相同。

受控反规范化则是明知重复仍保留一份，例如任务摘要复制成员显示名，以减少高频 JOIN。先指定成员表为权威，再规定更新传播、允许陈旧时间和重建方式；否则只是把上面的异常重新引入。

## 本章小结

表按独立对象组织，通过编号表达关系。类型定义值的形式，NULL 表示缺值；主键、非空、唯一、CHECK 和外键各检查不同规则，不能相互替代。

## 🎯 面试怎么回答

### 你从哪里开始设计业务表？

先明确记录代表什么、对象之间的关系和主要读写动作，再选择字段类型、身份和约束。比如负责人资料集中保存，任务用编号关联；业务唯一性明确到团队或全局范围，而不是先堆字段。

## ⚠️ 易错点

> ⚠️ 外键能校验引用存在，但不替应用判断当前用户有没有访问权限。

> ⚠️ JSON 能保存扩展属性，不等于核心状态、金额和身份都应藏在 JSON 中。

## 本章自测

<details>
<summary>1. 为什么任务只存负责人编号，而不复制全部成员资料？</summary>

同一个成员可能对应多条任务，集中保存资料减少重复修改和更新不一致；查询时可按编号取得姓名。

</details>

<details>
<summary>2. 直接用 owner_id=0 代表“未分配”，会增加什么约定？</summary>

需要另外约定 0 永远不是成员编号，并让查询、外键和所有写入遵守它。NULL 直接表达缺值，通常更清楚；不是说业务在任何场景都禁止哨兵值。

</details>

<details>
<summary>3. 只用负责人 id 外键，会自动保证任务与成员同团队吗？</summary>

不会。它只验证编号存在；同团队关系要在组合约束或可靠业务校验中另外表达。

</details>
