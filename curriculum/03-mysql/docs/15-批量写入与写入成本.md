# 15｜批量写入：Batch、事务与写入成本

[← 数据增长以后，怎样维护主键、索引和表结构](14-主键索引与表结构演进.md) · [MySQL 目录](../README.md) · [复制与读写分离：多份数据何时一致 →](16-复制与读写分离.md)

一次写三行和连续写三次，看起来结果一样，但数据库承担的固定开销并不完全一样。数据量继续增大以后，真正要控制的是：**一条语句多大、一笔事务多大，以及索引和日志要维护多少工作。**

这一章只讨论 MySQL 写入路径。文件解析、任务调度、断点续跑和背压属于更大的后台任务系统；这里只说明它们为什么不能被误写成数据库事务本身。

## 1. 先分清一条语句和一笔事务

假设需要写入一千行数据。

```text
1000 条单行 INSERT
```

和：

```text
10 条 INSERT，每条 100 行
```

都要把一千行真正写进表，但第二种方式减少了客户端与服务器之间的往返，也减少了重复解析等固定工作。

事务是另一层边界。一百条 INSERT 可以每条各自提交，也可以放进同一事务一次提交。减少提交次数能够摊薄一部分日志同步和事务管理开销，但事务越大，失败时需要回滚的修改也越多。

所以调优时至少分开三个问题：

| 控制项 | 主要影响 | 过大时的代价 |
|---|---|---|
| 单条语句包含多少行或字节 | 网络往返、解析与执行批次 | 包大小、内存与单语句耗时增加 |
| 一笔事务包含多少修改 | COMMIT 次数与原子边界 | Undo/Redo/Binlog 增长、回滚更重、锁持有更久 |
| 同时有多少写事务 | 总吞吐 | 连接、磁盘、日志与热点记录竞争 |

“每批 1000 行”只有在说明它是**语句批次还是事务批次**以后才有意义。

## 2. 一次批量 INSERT 仍然要维护每一行的数据责任

下面的一次过程从空表 `import_items` 开始：`source_key VARCHAR(40) PRIMARY KEY` 是稳定来源标识，`title VARCHAR(100) NOT NULL` 是标题。独立于任务表和账户表，结果应是 a、b、c 三条：

<a id="sql-batch_commit"></a>

<!-- mysql-example: batch_commit -->
```sql
START TRANSACTION;
INSERT INTO import_items(source_key, title)
VALUES ('a', '第一份'), ('b', '第二份'), ('c', '第三份');
COMMIT;
SELECT source_key FROM import_items ORDER BY source_key;
```

`VALUES` 后有三个括号，因此这一条 INSERT 产生三条记录。使用一条语句不代表数据库只做一次行级工作：每一行仍然要满足类型和约束，并维护聚簇索引及相关二级索引。

如果表有很多二级索引，每写一行就要同时维护更多有序结构；主键完全随机时，写入位置也可能更加分散。前面的主键与索引知识，到这里开始直接影响写吞吐。

> ⚠️ 为了导入更快而随手删除业务唯一约束或关键索引，会改变系统正确性和线上查询能力。离线新表与正在服务流量的在线表必须分开评估。

对于文件型数据，MySQL 还提供 `LOAD DATA` 一类专门加载能力，可以减少大量独立 SQL 的协议和解析开销。使用时仍要核对文件读取端、编码、分隔符、NULL 语义与权限，不把“专门批量工具”理解成绕过数据规则。[LOAD DATA](https://dev.mysql.com/doc/refman/9.7/en/load-data.html)。

## 3. 为什么事务不能无限变大

把更多行放进一笔事务，确实可能减少 COMMIT 次数；但大事务也会同时放大：

- Undo 与 Redo；
- Binlog 体积与提交突发；
- 锁持有时间；
- 回滚成本；
- 副本后续应用压力。

因此不存在一个所有表、所有硬件都通用的“最佳 1000 行”。合理批次要根据单行大小、索引数量、日志与磁盘能力，以及允许的失败范围实测。

一次只看前几秒峰值也不够。写入持续一段时间以后，如果磁盘刷脏页、日志同步或副本应用跟不上，吞吐和延迟会发生变化。真正要找的是系统**能够持续承受的写入速度**，而不是瞬时最高数字。

[InnoDB 批量加载建议](https://dev.mysql.com/doc/refman/9.7/en/optimizing-innodb-bulk-data-loading.html)提供了具体加载优化方向；首次学习只需要先理解这些优化都围绕“减少重复工作，同时控制写放大和事务代价”。

## 4. 提交结果未知时，不能把超时直接当作回滚

客户端发出 COMMIT 后连接中断，可能有两种事实：

```text
服务器尚未提交
```

也可能是：

```text
服务器已经提交，只是成功响应没有送到客户端
```

因此网络超时只能说明**客户端不知道结果**，不能证明数据库一定回滚。

如果业务可能重试同一批输入，就需要稳定的业务标识或唯一约束来查询“这批是否已经生效”，再决定是否重放。重复设置同一个确定值可能可以设计成幂等；重复执行 `count = count + 1` 则会产生额外效果，不能因为使用了 Upsert 就自动称为安全重试。

例如已经存在 `('a','第一份')`，再次收到同一来源的新标题，可以明确使用覆盖语义：

```sql
INSERT INTO import_items(source_key, title)
VALUES ('a', '第一份修订') AS incoming
ON DUPLICATE KEY UPDATE title = incoming.title;
```

第一次变成 `('a','第一份修订')`，重复同一输入仍是同一标题；它不是新增两行。如果改为冲突时 `count=count+1`，重放仍会再次累加。普通 INSERT 遇到唯一冲突会报错；`INSERT IGNORE` 可能把某些错误降为警告，不能拿它当已核对内容一致；REPLACE 是替换式删除/插入语义，不等价于普通 UPDATE。选择哪种写法，应先确定冲突代表重试、新版本还是数据错误。[Upsert 语义](https://dev.mysql.com/doc/refman/9.7/en/insert-on-duplicate.html)

这也是数据库与长任务系统的边界：长时间导入通常还需要保存任务进度、失败原因、重试次数和上游限速，但这些属于**应用任务的生命周期**。MySQL 在这里提供的是已提交数据、约束与事务事实；完整 checkpoint、resume 和 backpressure 在学完数据系统以后由 Backend 模块统一组织。

## 本章小结

批量写入同时受语句批次、事务批次和并发数量影响。减少往返和提交可以提高吞吐，但每行的约束、索引与日志维护仍然存在；事务过大又会放大锁、日志和回滚成本。提交响应丢失时，先核对数据库事实，再决定是否重试。

## 🎯 面试怎么回答

### 大量数据怎样高效写入 MySQL？

先区分单条语句大小、事务大小和并发度，用多值 INSERT 或合适的批量加载减少重复开销；再检查主键、二级索引、Redo/Binlog 和持续刷盘能力。批次没有固定最佳值，要用真实负载测可持续吞吐；提交结果未知时，靠稳定业务键核对结果后再安全重试。

## ⚠️ 易错点

> ⚠️ 一条 INSERT 写很多行，不代表索引和约束只检查一次。

> ⚠️ 事务越大不一定越快；减少提交次数与放大日志、锁和回滚成本是同一组取舍。

> ⚠️ COMMIT 超时表示结果未知，不等于服务器已经回滚。

## 本章自测

<details>
<summary>1. 一条 INSERT 写一百行，与一百条 INSERT 放在同一个事务里完全相同吗？</summary>

不相同。两者事务边界可以一样，但前者还减少了语句往返与重复解析等固定工作。

</details>

<details>
<summary>2. 为什么不能把全部数据放进一个巨大事务，只为减少 COMMIT 次数？</summary>

因为 Undo、Redo/Binlog、锁持有、回滚和副本应用压力都会一起放大；失败恢复范围也更大。

</details>

<details>
<summary>3. 客户端没有收到 COMMIT 成功响应，为什么不能直接重放一遍？</summary>

服务器可能已经提交。直接重放会重复产生业务效果，应先通过稳定业务标识或约束核对数据库事实，再决定后续操作。

</details>
