# 04｜InnoDB 索引怎样组织数据：Page 与 B+Tree

> [!TIP]
> **🎯 本章目标**
>
> 深刻理解索引为什么能大幅减少读取，以及 InnoDB 怎样把“索引”落到物理 Page 与 B+Tree 结构上。学完后能够清晰推导：一张表为什么会有多棵独立的索引树、B+Tree 相对其他数据结构为何是数据库的最优选、点查与范围扫描怎样沿 Page 链条推进、聚簇索引与二级索引为何会产生“回表”、以及主键宽度和离散度为何会深刻影响整套索引的存储与写入性能。

## 0. “使用索引”在 InnoDB 里到底发生了什么？

考虑一张拥有 5000 万行记录的 `tasks` 表：

```sql
SELECT *
FROM tasks
WHERE id = 38194721;
```

SQL 仅声明了“提取 `id = 38194721` 这一行”。若没有辅助索引结构，数据库只能遍历全表检查 5000 万个候选者。

索引的本质是：**额外维护一套按 Key 严格有序的访问结构，使检索能以对数级步进不断排除不可能的分支，直达目标区间。** 在 InnoDB 中，该结构由物理 **Index Page（索引页）** 组成：查询自顶层的 Root Page 出发，经由 Internal Page（内部非叶页）逐级收敛 Key 范围，最终停靠在 Leaf Page（叶子页）。而 Leaf Page 保存的具体内容，则取决于这是组织完整行数据的**聚簇索引**，还是仅记录索引键与主键的**二级索引**。

> [!IMPORTANT]
> **💡 核心认知：InnoDB 索引不是单个“地址查找文件”，而是一棵由物理数据页（Page）互联构成的有序 B+Tree。内部节点负责多路导航，叶子节点保存索引记录；不同索引的叶子记录不同，由此派生出截然不同的数据访问路径。**

## 1. Index 到底是什么，一张表为什么会有多棵索引树？

**Index（索引）是为了加速记录定位而额外维护的独立有序数据结构。** 在 InnoDB 中，每个索引各自拥有一棵独立的 B+Tree 树形结构：一张表有且仅有一棵聚簇索引树，还可以拥有多棵独立的二级索引树。

初学者常把 `PRIMARY KEY`、`UNIQUE`、联合索引、聚簇索引混为一谈，实际上它们是作用于不同维度的正交属性：

| 评估维度 | 常见分类 | 描述侧重 |
|---|---|---|
| **Key 列数** | 单列索引、联合索引 | 决定 Key 由单一列还是多列组合构成 |
| **约束语义** | 主键索引、唯一索引、普通索引 | 决定 Key 在业务和数据库中是否允许重复与为 NULL |
| **物理组织关系** | 聚簇索引 (Clustered)、二级索引 (Secondary) | 决定叶子节点保存的是**整行真实数据**还是**二级 Key + 主键** |

例如声明 `PRIMARY KEY (id)`，它在逻辑上是单列索引与主键唯一索引，在 InnoDB 物理层则承担了该表的 **聚簇索引**；而声明 `UNIQUE INDEX uk_code (tenant_id, external_code)`，它既是联合索引与唯一索引，在物理层则是一棵独立的 **二级索引树**。

```text
tasks 表
├── 聚簇索引树 (PRIMARY)           → 按 id 排序，叶子节点存整行完整数据
├── 二级索引树 (idx_owner_id)      → 按 owner_id 排序，叶子节点存 (owner_id, id)
└── 二级索引树 (idx_tenant_status) → 按 (tenant_id, status) 排序，叶子节点存 (tenant_id, status, id)
```

**为什么每张表需要多棵树？** 因为不同的业务查询需要按不同的列顺序定位。行数据只能按照主键维护一套绝对物理顺序；当业务需要高频按 `owner_id` 检索时，只能另建一棵以 `owner_id` 为 Key 排序的独立树结构。索引绝非免费，增加一棵树即意味着增加物理空间开销，并在每次 `INSERT / UPDATE / DELETE` 时都要同步修改多棵树。

## 2. 为什么数据库索引常用 B+Tree？

数据库索引选用 B+Tree 的核心原因，是在 16 KiB 物理页存储架构下实现了超高扇出（Fan-out）与极矮树高（通常 3～4 层覆盖数千万行），将磁盘寻道次数压缩到极低；同时叶子节点集中存储数据并由双向链表贯通，提供了极高局部性的连续范围扫描能力。

```text
Level 2 (Root Page)              [ 20 | 50 ]
                                 /     |     \
                                ↓      ↓      ↓
Level 1 (Internal Page)    [5|10|15] [25|35] [60|75|90]
                             / | \     / \     / | \
                            ↓  ↓  ↓   ↓   ↓   ↓  ↓  ↓
Level 0 (Leaf Pages)      [Leaf 1] ↔ [Leaf 2] ↔ [Leaf 3] ↔ [Leaf 4] ...
```

---

### 2.1 物理节点与页（Page）的关系

- **Page（数据页）**：InnoDB 磁盘管理与内存缓存的最小基本物理单元，默认大小为 **16 KiB**。
- **树节点即为一个 Page**：B+Tree 的一个 Node 在物理上就是一个 16 KiB 的 Page。
- **高扇出（High Fan-out）**：一个 Internal Page 仅保存导航 Key 和子页指针，体积很小。一个 16 KiB 的内部页通常能容纳上千个路由指针（扇出可达 1000 以上）。只需 3~4 层的极矮树高，就能轻松索引数千万乃至数十亿条数据行。

---

### 2.2 数据结构横向对决：为何不是二叉树、B 树或 Hash？

| 数据结构 | 核心机制 | 数据库场景致命短板 | 适用场景 |
|---|---|---|---|
| **二叉搜索树 / 红黑树** | 每个节点最多 2 个分支，树高为 $O(\log_2 N)$ | 无法适应 Page 块存储。若数据量千万级，树高动辄 20~30 层，单次寻道需遍历几十个不连续的 Page，I/O 开销急剧放大 | 内存数据结构 |
| **B 树 (B-Tree)** | 多路平衡树，内部节点和叶子节点均保存完整数据行 | 内部节点塞入数据行后，单页能容纳的导航指针锐减（扇出暴跌），树高大幅增加；且叶子节点缺乏连续双向链表，范围检索需频繁中序回溯 | 少量点查为主的专用引擎 |
| **Hash 索引** | 内存哈希桶点查 $O(1)$ | 不支持范围查询（`BETWEEN`、`>`、`<`）、不支持前缀模糊匹配、无法天然服务 `ORDER BY` 排序 | 纯内存表等值点查 |
| **B+Tree** | **内部页纯导航（超高扇出保证树矮）；叶子页存数据且双向互联（范围扫描极快）** | 写入时存在维护有序性与页分裂的开销 | 通用关系型数据库磁盘与缓存引擎 |

---

### 2.3 Buffer Pool：解耦逻辑访问与物理磁盘 I/O

逻辑上经过 Root → Internal → Leaf 访问了 3 个 Page，**绝不等于发生了 3 次物理磁盘 I/O**。InnoDB 在内存中开辟了 **Buffer Pool** 缓存热点数据页。在稳定生产环境中，Root Page 与绝大多数 Internal Page 几乎 100% 常驻内存，底层只有少数未命中的 Leaf Page 才会触发真实的存储寻道。

## 3. B+Tree 怎样查找、范围扫描和发生 Page Split？

B+Tree 的查找与扫描建立在“键值严格有序”的物理基础之上：点查通过自顶向下的页内二分排除分支收敛至叶子页；范围扫描在叶子页定位起点后沿双向链表连续顺序推进；当插入遇到满页时，则通过页分裂（Page Split）分配新页并拆分数据。

---

### 3.1 点查与范围扫描的推进过程

- **点查（Point Lookup）**：从 Root Page 开始，对页内键值做二分收敛，选出命中的唯一子指针进入下一层 Internal Page；层层排除无涉分支，直至 Leaf Page 定位到该 Key。
- **范围查询（Range Scan）**：
  1. 首先走点查路径，准确定位到范围下界的 Leaf Page；
  2. 在该叶子页内遍历顺序记录；
  3. 达到本页末尾后，**直接顺着叶子节点的双向链表指针载入相邻下一个 Leaf Page 继续扫描**，直到越过上界。全程无需再回退到 Root 或 Internal 节点！

---

### 3.2 页分裂（Page Split）：写入维护的物理代价

插入新记录时，记录必须落入按 Key 排序的特定 Leaf Page。
- 若目标 Page 尚有空闲空间，直接在页内按顺序插入记录；
- 若目标 Page 空间已满，InnoDB 必须向表空间申请一个全新 Page，将原页中约一半的数据迁移到新页中，调整同级叶子链表指针，并向上层父节点插入新的导航路由指针。这个过程即为 **Page Split（页分裂）**。

```text
原满页：[10, 20, 30, 40]  (欲插入 25，空间不足)
                 ↓ 触发页分裂
Leaf A: [10, 20]  ↔  Leaf B: [25, 30, 40]
                 ↓
          父级内部页插入新导航路由
```

> [!WARNING]
> **页分裂不仅带来数据搬迁、新页分配与父节点指针更新的开销，还会导致页填充率降低与物理存储碎片化。** 官方手册明确指出：按主键自增顺序插入时，页填充率稳定在 15/16 左右（约 93.75%）；而在高频离散随机插入时，页填充率分布在 1/2 到 15/16 之间（50%～93.75%），造成可观的内存与磁盘空间浪费。

## 4. 聚簇索引、二级索引和回表到底是什么关系？

聚簇索引与二级索引的根本区别在于叶子节点存储的数据形态：聚簇索引的叶子节点即为物理数据行本身，二级索引的叶子节点则存储“索引列键值 + 对应的主键值”；若二级索引查询未覆盖所需列，必须拿着主键回到聚簇索引二次寻址，这一过程称为回表（Table Lookup）。

| 索引形态 | 叶子节点 (Leaf Record) 保存的内容 | 缺失字段时的数据流转 |
|---|---|---|
| **聚簇索引 (Clustered)** | **主键 Key + 隐藏系统列 + 整行完整业务数据** | 本身已包含整行数据，命中叶子节点即查全，无需额外寻址 |
| **二级索引 (Secondary)** | **二级索引列 Key + 对应的主键 Key** | 若查询列包含二级索引未收录的字段，必须拿主键回聚簇树二次检索（**回表**） |

若建表时未显式声明 `PRIMARY KEY`，InnoDB 会自动挑选第一个非空唯一索引（`NOT NULL UNIQUE`）作为聚簇索引；若依然没有，则在底层隐式生成一个 6 字节的自增隐藏行标识符（`GEN_CLUST_INDEX`）构建聚簇索引。

二级索引之所以保存主键值而非数据行的物理磁盘地址，是为了保持存储解耦：当聚簇索引因页分裂或数据重组发生记录物理搬迁时，无需全表联动修改所有二级索引的叶子指针。

```text
查询：SELECT id, title FROM tasks WHERE owner_id = 1;

[二级索引 idx_owner 树]
  Root → Internal → Leaf 定位到:
  (owner_id=1, id=10), (owner_id=1, id=30)
         │
         │ (二级索引缺乏 title 列，触发回表！)
         ↓
[聚簇索引 PRIMARY 树]
  拿着 id=10 沿主键树点查 → 提取 title='学习 MySQL'
  拿着 id=30 沿主键树点查 → 提取 title='准备面试'
```

---

### 4.1 离散回表的性能开销边界

走二级索引不代表绝对高速。若二级索引命中了 50 万条主键，就意味着要发起 50 万次聚簇索引的点查跳跃。这些主键对应的行散落在不同的聚簇数据页上，会产生海量的离散随机读（Random I/O），整体代价往往远高于直接全表顺序扫描。

---

## 5. 主键为什么会影响整套 InnoDB 索引？

主键设计直接决定整张 InnoDB 表的物理性能上限：由于所有二级索引的叶子节点都必须隐式包含主键值，宽主键会成倍膨胀二级索引体积并侵蚀 Buffer Pool 缓存容量；而主键的单调递增性则直接决定了聚簇索引写入是连续追加还是引发频繁的随机页分裂。

---

### 5.1 主键宽度对二级索引的乘数放大效应

因为每条二级索引记录都必须隐式携带主键值。若主键采用 64 字节的字符串，表上建有 5 个二级索引，每个二级索引在存入一条记录时都要复制这 64 字节的主键。主键越宽，所有二级索引的叶子记录随之变宽，单个 16 KiB 页面能容纳的记录数急剧下降，导致二级索引树变高、体积膨胀数倍，并在 Buffer Pool 中抢占宝贵的内存缓存空间。

---

### 5.2 递增主键 vs 随机主键（如 UUID）

- **趋势递增主键（如 AUTO_INCREMENT 或雪花算法）**：新插入的行总是追加在聚簇索引最右侧的叶子页上。前一个页写满后直接封箱，新页顺序挂接，页分裂极少且写入局部性极高，能够充分榨干 Buffer Pool 的写入合并红利。
- **完全随机主键（如标准 UUIDv4）**：新写入的键值离散分布在整个聚簇树的各个角落。每次插入都会击中不同的随机叶子页，需要频繁将不同的页从磁盘换入内存；且由于目标页常常空间已满，会在全表各处引发密集的页分裂与物理碎片，严重拉垮写入吞吐。

---

## 本章总结

InnoDB 的索引体系以 16 KiB 的 Page 为物理砖瓦，以 B+Tree 为架构模型。高扇出的内部节点造就了极矮的树高，实现了对数级的点查收敛；叶子层按 Key 严格有序并通过双向链表相连，提供了无与伦比的范围扫描能力。

聚簇索引将数据行直接锚定在叶子节点上，是物理存储的本体；二级索引则通过记录主键作为寻址跳板，为多维度检索提供入口。查询缺少字段时引发的回表是二级索引的核心成本源。主键作为贯穿二级索引的物理锚点，其“窄小性”与“单调递增性”直接决定了整张表的空间利用率、缓存命中率与写入性能上限。

## 🎯 面试怎么回答

### 为什么 InnoDB 选用 B+Tree 作为索引结构，而不是 Hash 或红黑树？

> [!TIP]
> 1. 与 Page 存储完美适配：B+Tree 单节点为一个 16 KiB 数据页，内部节点纯存导航键，形成上千的高扇出，千万级数据仅需 3 层树高，大幅压减寻道层级；红黑树分支少树过高，磁盘 I/O 成本不可接受；  
> 2. 兼顾点查与范围检索：Hash 虽等值点查快，但完全失去有序性，无法支持范围扫描与排序；B+Tree 叶子节点按键排序且通过双向链表贯通，范围查询仅需定位起点后顺序遍历即可。

### 树高 3 层的 B+Tree 意味着需要进行 3 次磁盘 I/O 吗？

> [!TIP]
> 不意味着。树高仅代表逻辑寻址经过的 Page 层级。InnoDB 的 Buffer Pool 会将高频访问的数据与索引页常驻内存。实际场景中根页和内部节点页通常 100% 命中内存，只有未命中的叶子页才会产生真实的物理磁盘读取。

### 聚簇索引和二级索引在物理存储上有何本质不同？

> [!TIP]
> 聚簇索引的叶子节点存储的就是包含事务系统列在内的完整数据行，即“索引即数据”；二级索引的叶子节点仅存储二级索引列与对应行的主键值。若二级索引无法覆盖查询所需的所有字段，必须先提取主键再进入聚簇索引二次寻址，此过程即为回表。

### 什么是页分裂（Page Split）？什么情况下会触发？

> [!TIP]
> 页分裂是指向索引树插入新记录时，若新记录按排序必须落入的物理数据页已经耗尽可用空间，InnoDB 必须申请新页、将原页部分数据搬迁至新页、并更新父级导航与兄弟节点链表指针的物理重构过程。离散随机的主键写入是频繁触发页分裂和存储碎片化的首要诱因。

### 为什么在 InnoDB 中强烈推荐使用短小的、自增的主键？

> [!TIP]
> 1. 节省空间：主键会被整张表的所有二级索引隐式冗余携带，主键越宽，所有二级索引膨胀越剧烈，内存能缓存的索引记录越少；  
> 2. 保证写入局部性：自增主键保证新行总是顺序追加在聚簇索引右侧叶子页，写入密集且缓存命中率极高，页填充率可达 15/16；若采用随机 UUID，数据散落全表导致频繁随机读写与密集页分裂。

## ⚠️ 易错点

> [!WARNING]
> **逻辑访问 Page 数量不等于物理 I/O 次数。** Buffer Pool 会消化绝大多数非叶子节点的访问。

> [!WARNING]
> **没有显式主键不代表没有聚簇索引。** InnoDB 会依次退化选用第一个非空唯一键，若仍没有则自动构建 6 字节的隐藏聚簇主键（GEN_CLUST_INDEX）。

> [!WARNING]
> **二级索引存的是主键，不是物理磁盘行地址。** 数据行发生重组迁移时，无需全量更新二级索引叶子节点的物理指针。

> [!WARNING]
> **走二级索引不代表查询一定快。** 命中记录数过大引发海量离散回表时，优化器很可能会主动放弃索引退回全表扫描。

> [!WARNING]
> **自增主键并不等于绝对没有页分裂。** 当最右侧末尾数据页写满时，依然会开辟新页挂载，只是分裂模式高度规律受控。

> [!WARNING]
> **UUID 并非完全不可用。** 业务需要分布式无中心生成 ID 时可选用时间单调递增的新型有序 UUID（如 UUIDv7），兼顾分布式唯一性与树写入局部性。

## 🧩 本章自测

<details>
<summary><strong>1. InnoDB 内部节点（Internal Page）与叶子节点（Leaf Page）的核心职责差异是什么？</strong></summary>

内部节点纯存导航键与子页指针，追求高扇出压低树高；叶子节点存储真正的索引数据（聚簇索引存整行，二级索引存主键）。

</details>

<details>
<summary><strong>2. 默认 innodb_page_size 是多大？它与树节点是何关系？</strong></summary>

默认为 16 KiB。在物理层面，B+Tree 的一个 Node 节点实体就对应一个 16 KiB 的 Page 数据页。

</details>

<details>
<summary><strong>3. 为什么 B+Tree 的范围扫描性能远超传统平衡二叉树？</strong></summary>

B+Tree 定位到起点叶子后，沿叶子节点的双向链表顺序拉取相邻页即可；二叉树必须频繁进行复杂的中序遍历回溯。

</details>

<details>
<summary><strong>4. 如果建表时没有显式定义主键，InnoDB 会怎样处理？</strong></summary>

InnoDB 会优先选择第一个所有列均声明为 NOT NULL 的唯一索引（UNIQUE）作为聚簇索引；若完全不存在符合条件的唯一索引，InnoDB 会在底层自动生成一个 6 字节的自增隐藏行标识符（GEN_CLUST_INDEX）构建聚簇索引。

</details>

<details>
<summary><strong>5. 为什么说主键宽度会直接影响 Buffer Pool 的有效容量？</strong></summary>

主键被所有二级索引引用，宽主键导致所有二级索引体积成倍放大，占据大量数据页，使 Buffer Pool 能够缓存的有效数据行急剧减少。

</details>

<details>
<summary><strong>6. 离散随机插入（如 UUIDv4）对数据页填充率有何影响？</strong></summary>

随机写入导致各处数据页过早频繁分裂，破坏物理紧凑性，页填充率通常在 1/2 到 15/16 之间波动（低至 50%），造成大量内存与磁盘碎片浪费。

</details>

<details>
<summary><strong>7. 为什么说单表可以有多棵索引树？</strong></summary>

因为每棵二级索引都必须根据自己的索引列维持一套完全独立的有序排列，因此需要构建独立的物理 B+Tree。

</details>

<details>
<summary><strong>8. B-Tree 与 B+Tree 最关键的结构分野是什么？</strong></summary>

B-Tree 在内部节点也混杂存储数据行，导致内部节点扇出降低；B+Tree 内部节点纯导航、数据全沉底在叶子层且叶子互连。

</details>

<details>
<summary><strong>9. 为什么查询主键不需要回表？</strong></summary>

因为主键索引即聚簇索引，其叶子节点物理上已经保存了整行记录的所有列。

</details>

<details>
<summary><strong>10. 二级索引的叶子节点为什么保存逻辑主键值，而不是数据行的物理磁盘地址？</strong></summary>

为了保持存储解耦。如果保存物理磁盘地址，一旦聚簇索引发生页分裂、行重组或碎片整理导致记录物理地址变更，所有二级索引树中对应的指针都必须同步联动修改，写入代价将不可承受；保存逻辑主键值使得行的物理搬迁对二级索引完全透明。

</details>

## 📌 本章最终要留下的七句话

1. **InnoDB 索引是一棵由 16 KiB 数据页（Page）互联构成的物理 B+Tree。**
2. **内部节点纯存导航指针造就超高扇出，千万级数据仅需 3 层极矮树高。**
3. **点查依赖逐层区间排除，范围扫描依赖叶子双向链表顺序推进。**
4. **Buffer Pool 解耦了逻辑页寻址与物理磁盘 I/O，内部节点通常常驻内存。**
5. **聚簇索引叶子即完整行数据，二级索引叶子存“二级键 + 主键”。**
6. **二级索引缺失字段时借助主键再探聚簇树即为回表，海量离散回表代价极高。**
7. **主键被所有二级索引隐式携带，短小且单调递增的主键是全表高性能的基石。**
