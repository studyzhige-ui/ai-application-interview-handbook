# 11｜并发修改：条件更新、锁与死锁

[← 并发读取：隔离级别与 MVCC](10-隔离级别与MVCC.md) · [MySQL 目录](../README.md) · [日志、提交与故障恢复 →](12-日志提交与恢复.md)

A 和 B 都读到余额 100。A 准备扣 30，算出 70；B 准备扣 20，算出 80。A 写入 70 后，B 把自己早先算出的 80 写回，最终余额是 80，而不是期望的 50。

数据库可以依次执行两次写入，但仍执行了业务上不合适的覆盖。**并发安全不仅是“同时写时排队”，还要保证每次修改依据的条件仍然成立。**

## 1. 能用一次条件修改表达，就别拆成无保护的读后写

扣余额可以把“够不够”和“扣多少”放在同一条 SQL 里：`UPDATE accounts SET credits=credits-30 WHERE id=1 AND credits>=30`。数据库在修改当前记录时检查条件，而不是把应用早先计算出的一个绝对值直接盖上去。

如果业务必须基于读到的完整旧状态作判断，可以带上**版本号**：

<a id="sql-optimistic_update"></a>

<!-- mysql-example: optimistic_update -->
```sql
UPDATE accounts
SET credits = credits - 30, version = version + 1
WHERE id = 1 AND version = 0 AND credits >= 30;
SELECT ROW_COUNT() AS changed_rows;
```

初始 `version=0`。第一个更新把版本改为 1；第二个仍要求版本为 0 的更新匹配不到记录，返回 0。应用据此重新读取或拒绝冲突，不能假装完成。这叫乐观并发检查：先尝试，提交修改时检查期望版本还在不在。

**它不意味着数据库内部不使用锁。** UPDATE 仍需要协调记录修改；版本条件只是把“我依据哪个旧状态”明确写了出来。业务重复请求还可能需要唯一键识别，那解决的是“同一动作是否已做”，与版本冲突不同。

## 2. 必须先读再决定时，用锁保护这段操作

A 在事务中用 SELECT ... FOR UPDATE 读取账户 1，它会取得相应记录锁。在 A 提交或回滚以前，B 要修改同一记录就需要等待。

| 时刻 | A | B |
|---|---|---|
| 1 | 开始事务，锁定读取账户 1 | |
| 2 | 检查当前余额并准备修改 | 尝试修改账户 1，等待 |
| 3 | 提交或回滚，释放锁 | 才能继续；仍需完成自己的事务 |

**共享锁 S** 允许多个兼容的共享读取；**排他锁 X** 与其他事务的 S、X 记录锁冲突。FOR SHARE 是共享锁定读，FOR UPDATE 是排他锁定读。但 RC、RR 下普通一致性 SELECT 通常可通过 MVCC 看合适版本，不必等待这把记录 X 锁。

InnoDB 的行级锁建立在索引记录上。索引决定扫描路径，也可能影响加锁范围；没有有效索引时锁住更多扫描记录，不应简单叫作“自动把行锁升级成表锁”。[InnoDB 锁机制](https://dev.mysql.com/doc/refman/9.7/en/innodb-locking.html)。

> ⚠️ 不要在持锁时等待模型或用户确认。锁保护需要原子的短数据库过程，不应把外部慢操作一起圈进去。

## 3. 保护记录与保护一个范围，有什么不同

索引有 10、20、30 三个值。锁住已经存在的 20，仍不能单靠这把记录锁阻止别人插入 15。若业务需要保护查询范围，就还要考虑记录之间的位置。

```text
索引值：           10       20       30
一个间隙：             (10,20)
一个 Next-Key：         (10,20]
```

**记录锁**保护已有索引记录；**间隙锁**主要阻止向相应间隔插入；**Next-Key 锁**把一个记录及其前面的间隙一起保护。它们让范围型锁定操作不只管眼前已有几行，也约束可能新增的位置。

RR 下，命中已存在的完整唯一键时，通常可以仅锁对应记录；唯一键没查到、只匹配联合唯一键的一部分或做范围扫描，则不能套用同一结论。RC 的间隙锁通常较少，外键与重复键检查等仍有例外。

判断具体锁范围，要给出引擎、隔离级别、索引、条件和语句，必要时检查实际锁记录。`WHERE id BETWEEN 10 AND 20` 描述结果条件，并不保证内部每条锁边界恰好也是这两个数字。

多工作者领取任务时，FOR UPDATE SKIP LOCKED 可以跳过已锁记录，让其他工作者继续取别的任务；NOWAIT 则在拿不到相应行锁时报错。它们是等待策略，不是完整任务系统：领取提交后进程仍可能失败，过期重领和外部动作防重还需设计。[锁定读选项](https://dev.mysql.com/doc/refman/9.7/en/innodb-locking-reads.html)。

## 4. 死锁与普通等待的关键差别，是形成了环

A 已锁账户 1，B 已锁账户 2；A 再要账户 2，开始等 B；B 再要账户 1，又开始等 A。现在双方都在等对方先结束，这叫死锁。

```text
A 持有账户1，等待账户2
        ↑          ↓
B 等待账户1，持有账户2
```

启用死锁检测时，InnoDB 会选择一个事务作为牺牲者回滚，打破等待环。不能预先认定总是 A 或总是 B 被回滚；应用收到错误后，需要以完整业务单元重新评估是否重试。

死锁和锁等待超时也不同：检测到死锁通常回滚被选中事务的全部修改；锁等待超时默认通常只回滚失败语句。业务要求整组失败时，应显式结束事务，不能因为收到超时就以为所有先前修改都没了。[错误回滚范围](https://dev.mysql.com/doc/refman/9.7/en/innodb-error-handling.html)。

避免死锁可以从统一多记录访问顺序、短事务和合适索引入手，再配合有界且安全的重试。诊断使用 SHOW ENGINE INNODB STATUS 看最近死锁，或通过 Performance Schema 观察当前锁与等待，最终仍要回答谁持有什么、为何以相反顺序申请。

<details>
<summary>跨进程协调时，再区分三种锁的生命周期</summary>

事务行锁在提交或回滚时释放；用唯一记录占位形成的任务归属可以长期保存，但要处理失效和清理；GET_LOCK() 一类命名锁属于会话级机制，不随普通事务提交自动释放。

它们都可以协调连接同一服务器的进程，却不能自动阻止失效的旧工作者继续修改外部系统。外部执行还需要合适的版本令牌或幂等协议。元数据锁又保护表结构，ALTER TABLE 等待它，与数据记录锁不是同一个问题。

</details>

## 本章小结

条件更新与版本检查拒绝不合适的修改，锁保护需要互斥的当前操作。范围保护要结合索引与隔离级别，死锁恢复则以完整业务事务和安全重试为单位。

## 🎯 面试怎么回答

### 怎样避免并发扣减互相覆盖？

不把应用旧读得到的绝对值直接盖回去。能表达时用原子条件更新；需要先读再决定时用事务锁，或在更新时检查期望版本。无论哪种都要判断是否真正成功。

### 数据库发生死锁怎么办？

先正确结束失败事务，按完整业务单元做有界重试，避免外部副作用重复。再根据持锁和等待关系统一访问顺序、缩短事务、改善索引，不能只增加超时时间。

## ⚠️ 易错点

> ⚠️ 版本检查不是禁用锁，SKIP LOCKED 也不是保证任务必定完成的队列。

> ⚠️ S/X 记录锁兼容关系不能机械套到所有间隙锁或元数据锁。

> ⚠️ 死锁与默认锁等待超时的回滚范围不同。

## 本章自测

<details>
<summary>1. 两个请求都算好新余额再写回，为什么串行执行写入仍可能错？</summary>

后写入的绝对值依据旧读计算，会覆盖前一个业务结果；排队本身不修复计算依据。

</details>

<details>
<summary>2. A 等 B 就一定死锁了吗？</summary>

不是。单向等待可能在 B 释放后正常继续；还需要 B 也依赖 A 等形成等待环。

</details>

<details>
<summary>3. 为什么锁住值 20 不等于阻止插入 15？</summary>

15 是两个已有键之间的空位置，记录锁只保护已有记录；限制插入需要相关范围保护。

</details>
