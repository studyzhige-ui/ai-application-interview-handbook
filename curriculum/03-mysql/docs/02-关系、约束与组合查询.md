# 02｜关系、约束与查询表达：多个对象怎样组织并查询出正确结果

> [!TIP]
> **🎯 本章目标**
>
> 从“一张表保存一类数据”继续深入到真正的关系模型：能够判断多个业务对象应该怎样拆成表，知道一对一、一对多、多对多怎样落到 Schema；能够把明确的数据规则交给数据库约束；能够用 `JOIN / GROUP BY / HAVING / EXISTS / DISTINCT / ROW_NUMBER()` 表达常见集合问题；最后建立对 ORM 或 AI 生成 SQL 的批判性验收能力，确保结果真正符合业务语义。

## 0. 为什么把所有信息塞进一张表，迟早会出问题？

假设任务表一开始直接冗余保存负责人姓名：

| id | title | owner_name |
|---:|---|---|
| 101 | 学习 MySQL | Alice |
| 102 | 完成项目 | Alice |
| 103 | 修改简历 | Bob |

看似简单，但当 Alice 改名为 Alicia 时，同一个客观事实（Alice 的姓名）被保存了两次。若程序只更新了一条，数据就会出现分裂（Task 101 负责人是 Alicia，Task 102 却是 Alice），产生严重的“数据不一致”。

更合理的设计是让成员信息只在权威位置保存一份：`members` 表记录 `id = 1, name = Alicia`，而 `tasks` 表仅记录 `owner_id = 1`。

但拆表之后，新的工程问题接踵而至：
- `owner_id = 1` 指向的成员真的存在吗？
- 一个人可以负责多少任务？一个任务可以有多少参与者？
- 前端需要展示“任务 + 负责人姓名”时，怎样把表重新组合？
- 怎样统计每种状态的任务数量？为什么“查每个成员最新的一条任务”普通 `GROUP BY` 不管用？
- ORM 或 AI 自动生成了一条复杂 SQL，怎样严谨判断其执行结果没有偏差？

> [!IMPORTANT]
> **💡 本章核心认知：关系型建模不是盲目把字段拆成很多表，而是让每个事实拥有唯一的权威归属，再通过关系、约束和查询将它们严密连接起来。**

## 1. 多个业务对象怎样建模成关系？

建模的核心是明确两点：**每张表的一行到底代表什么业务事实，以及这些事实之间是一对一（1:1）、一对多（1:N）还是多对多（N:N）。** 能够独立变化的事实独立建表，事实之间的关联通过稳定标识连接。

---

### 1.1 先问：这一行到底代表什么？

在任务系统中存在两类独立事实：`members`（一行代表一个成员）与 `tasks`（一行代表一条任务）。成员有姓名、部门；任务有标题、状态。如果将成员属性平铺进任务，成员每次信息变更都会引发大面积任务行更新。

因此建模第一准则：**成员事实归 `members`，任务事实归 `tasks`，两者关系通过 `tasks.owner_id` 引用连接。同一个会变化的事实，尽量只有一个权威存储位置。**

---

### 1.2 一对多（1:N）：在“多”的一端保存“一”的身份

若一个成员可以负责多条任务，而一条任务只有一个负责人，这就是典型的 **1:N** 关系。设计准则是在“多”的一侧（`tasks`）保存“一”的主键（`owner_id → members.id`）。

```text
members (id=1, name='Alice')
  ├── tasks (id=101, title='学习 MySQL', owner_id=1)
  └── tasks (id=102, title='完成项目',   owner_id=1)
```

这样不论 Alice 的个人信息如何变动，任务只需维护外键引用，避免冗余更新。

---

### 1.3 一对一（1:1）：关注生命周期与访问模式

若一个用户最多对应一份档案（`users` 与 `user_profiles`），即为 **1:1** 关系。1:1 并不意味着必须物理拆表，是否拆分取决于工程考量：
- 字段生命周期是否独立（如账号高频使用，而实名档案极少访问）；
- 是否涉及不同的数据安全权限；
- 是否包含大文本/高开销字段。

若选择物理拆表，独立扩展表 `user_profiles` 的外键列 `user_id` 必须同时声明为 `PRIMARY KEY` 或 `UNIQUE NOT NULL`，才能在物理存储层面强制保证 1:1，防止数据退化为 1:N。

---

### 1.4 多对多（N:N）：关系本身也要成为独立记录

若一条任务可有多名成员参与，一个成员也可参与多条任务，这就构成了 **N:N**。绝对不能在任务表中硬编码 `member_1, member_2` 这类字段，因为参与人数没有上限。

标准解法是引入**关联表（Junction Table）**，让关系本身成为独立事实：

```sql
-- 任务成员关联表
CREATE TABLE task_members (
    task_id BIGINT NOT NULL,
    member_id BIGINT NOT NULL,
    role VARCHAR(20) NOT NULL DEFAULT 'member',  -- 关系自身的属性
    joined_at DATETIME NOT NULL,
    PRIMARY KEY (task_id, member_id)
) ENGINE = InnoDB;
```

## 2. 哪些业务规则应该交给数据库约束？

适合交给数据库约束的规则，都有一个共同特性：**数据库仅凭当前准备写入的行以及被引用的外键表数据，就能立即做出确定性判断。**

---

### 2.1 基础约束：`NOT NULL`、`UNIQUE` 与 `CHECK`

- **`NOT NULL`**：约束该列必须有已知值。若业务允许任务暂时无负责人，应显式允许 `owner_id BIGINT NULL`。
- **`UNIQUE`（唯一约束）**：先明确唯一性的生效范围。例如业务工号 `external_code` 在全系统可能重复，但在租户内部必须唯一，此时应建立组合唯一约束 `UNIQUE (tenant_id, external_code)` *(注：MySQL 唯一键允许多个 `NULL` 存在，若要求既唯一又必填，需同时叠加 `NOT NULL`)*。
- **`CHECK`（值范围约束）**：适用于行内静态值的校验，如 `CHECK (priority IS NULL OR priority BETWEEN 1 AND 5)` 或 `CHECK (status IN ('pending', 'doing', 'done'))`。

---

### 2.2 `FOREIGN KEY` 与级联边界

外键用于强制被引用的对象在物理上必须存在，如 `FOREIGN KEY (owner_id) REFERENCES members(id) ON DELETE RESTRICT`。

常见删除动作语义：
- `RESTRICT / NO ACTION`：只要存在子表引用，坚决禁止删除父记录（推荐作为绝大多数业务默认值）；
- `CASCADE`：级联删除子记录（需极为慎重，避免误删历史关键数据）；
- `SET NULL`：删除父记录时将外键置空。

> [!TIP]
> **多租户联合外键：** 若要求“任务与负责人不仅存在关联，且必须属于同一个团队”，单列外键是不够的。应建立组合外键 `FOREIGN KEY (tenant_id, owner_id) REFERENCES members(tenant_id, id)` 才能在数据库层锁死跨租户引用的漏洞。

| 规则类型 | 数据库约束能否独立保障 | 实施建议 |
|---|---|---|
| ID 唯一、字段非空、数值区间 | 能 | PRIMARY KEY、NOT NULL、CHECK |
| 租户内唯一、组合引用的存在性 | 能 | UNIQUE(组合)、FOREIGN KEY(组合) |
| 当前用户是否有权限执行该操作 | 不能 | 应用层鉴权拦截 |
| 扣减库存与流水写入要么都成要么都败 | 不能单靠表约束 | 事务（ACID）保障 |
| 第三方支付平台是否到账 | 不能 | 外部回调与状态机防重 |

## 3. JOIN 到底在表达什么关系？

`JOIN` 的本质是：**依据连接条件（ON），为左表的每一行在右表中寻找匹配行，并按连接类型决定最终结果集的保留规则。**

---

### 3.1 `INNER JOIN`、`LEFT JOIN` 与 `RIGHT JOIN`

- **`INNER JOIN`（内连接）**：仅保留左右两侧均成功匹配的组合。若某条任务 `owner_id IS NULL`，内连接后该任务会被直接排除。
- **`LEFT JOIN`（左外连接）**：无条件保留左表的全部行。若右表无匹配，右表投影列自动补 `NULL`。
- **`RIGHT JOIN`（右外连接）**：`LEFT JOIN` 的镜像操作，保留右表全部行。实际工程中通常通过调整书写顺序统一使用 `LEFT JOIN` 以增强可读性。

```sql
-- 保留所有任务，即使任务尚未指派负责人
SELECT t.id, t.title, m.name AS owner_name
FROM tasks AS t
LEFT JOIN members AS m
    ON m.id = t.owner_id AND m.tenant_id = t.tenant_id
WHERE t.tenant_id = 10;
```

---

### 3.2 外连接中 `ON` 与 `WHERE` 的语义边界

对于 `LEFT JOIN`，过滤条件放在 `ON` 还是 `WHERE` 具有截然不同的求值阶段：
- **放在 `ON` 中**：控制的是“右表怎样才算匹配成功”。例如 `ON m.id = t.owner_id AND m.name = 'Alice'`，如果某任务负责人是 Bob，左表任务依然保留，只是 `owner_name` 显示为 `NULL`。
- **放在 `WHERE` 中**：作用于连接完成后的整个候选结果集。若写 `WHERE m.name = 'Alice'`，那些原本右表补 `NULL` 的未匹配行在 `WHERE` 中求值得到 `UNKNOWN` 并被过滤剔除，导致外连接实际退化为内连接。

---

### 3.3 结果集行数放大陷阱

若一个任务对应 3 名参与成员（1:N），在执行 `tasks JOIN task_members` 后，任务 101 会在结果集中连续出现 3 行。**JOIN 之后的一行代表“一组匹配结果”，不再等同于左表原始记录。** 这是初学者写统计查询最容易导致数值翻倍的元凶。

---

## 4. 面对集合问题，应该选择哪种 SQL？

集合计算的选型关键是明确**最终交付的一行数据代表什么粒度**：明细汇总为摘要使用 `GROUP BY` 与聚合函数，结果集整行去重使用 `DISTINCT`，父子存在性探测使用 `EXISTS`，而组内排序选优（如每组最新一条）则必须使用窗口函数。

---

### 4.1 `GROUP BY` 与 `HAVING`：明细压缩为分组摘要

`GROUP BY` 将多行明细压成一行组摘要。分组后的 SELECT 列表中只能出现分组列、聚合函数（`COUNT/SUM/AVG/MIN/MAX`）或与分组列存在确定性函数依赖的列（如按主键分组）。
- **`COUNT(*)` vs `COUNT(col)`**：`COUNT(*)` 统计匹配的绝对行数；`COUNT(col)` 会自动排除该列为 `NULL` 的行。
- **`WHERE` vs `HAVING`**：`WHERE` 在分组前筛选原始行；`HAVING` 在分组完成后筛选聚合结果。
  ```sql
  SELECT status, COUNT(*) AS total
  FROM tasks
  WHERE tenant_id = 10           -- 分组前先过滤团队
  GROUP BY status
  HAVING COUNT(*) >= 2;          -- 分组后只保留不少于2条的状态
  ```

---

### 4.2 `DISTINCT` 与 `EXISTS`：去重与存在性判断

- **`DISTINCT`**：对结果集整行去重。它属于查询呈现层，绝不能用于掩盖因为表结构设计缺失或错误 JOIN 产生的重复脏数据。
- **`EXISTS / NOT EXISTS`**：只关心“关联记录是否存在”，子查询中使用 `SELECT 1`，引擎只要命中第一条匹配就立即返回真并短路退出，性能与表达直观度通常优于关联后去重。
  ```sql
  -- 寻找至少存在一条待办任务的成员
  SELECT m.id, m.name FROM members AS m
  WHERE EXISTS (
      SELECT 1 FROM tasks AS t WHERE t.owner_id = m.id AND t.status = 'pending'
  );
  ```
  *(注：当子查询结果集包含 `NULL` 时，`id NOT IN (1, NULL)` 等价于 `id <> 1 AND id <> NULL`，三值逻辑求值恒为 `UNKNOWN` 导致整条查询返回 0 行，此时应坚决采用 `NOT EXISTS`)*。

---

### 4.3 `ROW_NUMBER()`：组内排名与“每组取最新一条”

业务高频需求：“查出每个负责人最新的一条任务（含标题与时间）”。  
若尝试写成 `SELECT owner_id, title, MAX(created_at) FROM tasks GROUP BY owner_id;`，由于 `title` 既非分组列也不与 `owner_id` 存在主键函数依赖，在默认启用的 `ONLY_FULL_GROUP_BY` 模式下会直接拦截报错（`ERROR 1055`）；即便在历史旧版本中强行关闭该模式，返回的 `title` 也是组内随机选取的值，无法保证与时间最大的那一行保持对应。

正确解法是使用**窗口函数**，在保留完整明细的同时进行分区编号：

```sql
SELECT id, owner_id, title, created_at
FROM (
    SELECT id, owner_id, title, created_at,
           ROW_NUMBER() OVER (
                PARTITION BY owner_id
                ORDER BY created_at DESC, id DESC
           ) AS rn
    FROM tasks
    WHERE owner_id IS NOT NULL
) AS ranked
WHERE rn = 1;
```

---

### 4.4 多表 `UPDATE`：按关联关系批量修改

```sql
UPDATE tasks AS t
JOIN members AS m ON m.id = t.owner_id
SET t.owner_id = NULL
WHERE m.status = 'inactive' AND t.status = 'pending';
```

通过 JOIN 准确定位需要修改的数据集合并一次性完成状态流转，比先查出 ID 再循环单条更新性能高数倍。

## 5. ORM 或 AI 生成 SQL 后，怎样验证语义和输入边界？

验收生成式 SQL 的核心标准不是“语法能否执行”，而是“执行语义是否与业务契约严格一致”。必须通过结构化检查流逐一核验连接保留语义、空值三值逻辑、分组投影确定性与排序列唯一性，并坚持在应用层使用参数绑定防范注入风险。

```text
1. 明确业务预期 (想要什么，一行应该代表什么)
   ↓
2. 检查连接语义 (INNER 是否漏行？LEFT 是否被 WHERE 截断？1:N 是否导致行数放大？)
   ↓
3. 检查 NULL 边界 (IS NULL 是否正确？NOT IN 是否因 NULL 逻辑失效？)
   ↓
4. 检查分组与排序 (GROUP BY 是否缺失非聚合列？ORDER BY 是否缺乏唯一主键导致分页抖动？)
   ↓
5. 检查参数边界 (数据值是否均采用 ? 绑定？动态列名/排序方向是否使用固定白名单？)
```

---

### 5.1 语义与集合边界验收

- **连接与空值截断**：仔细比对 `LEFT JOIN` 的关联条件是否被误写进 `WHERE` 导致连接退化；涉及可选列的集合排查时，警惕 `NOT IN` 中混入 `NULL` 导致的判定全空，优先改写为 `NOT EXISTS`。
- **分页抖动防御**：`ORDER BY created_at DESC LIMIT 20 OFFSET 20`，若大量数据创建时间相同，无序并列会导致前后页重复或漏查。必须显式补齐稳定次级排序列：`ORDER BY created_at DESC, id DESC`。

---

### 5.2 输入安全与动态 SQL 防御

- **参数绑定陷阱**：占位符 `?` 只能代指数据值。若前端支持动态选择排序列，绝不能拼接变量，而应在业务代码中利用字典白名单做映射转换：
  ```python
  ALLOWED_SORT = {"created": "created_at", "priority": "priority"}
  order_column = ALLOWED_SORT.get(user_input, "id")  # 白名单严格收敛
  ```

## 本章总结

关系建模的起点是确立“每张表的一行代表什么独立事实”。能独立变化的事实独立设表，1:N 通过多端保存外键，N:N 借助关联表落地，避免多处维护副本产生数据割裂。

对于行内与引用层面的静态不变规则，应充分利用数据库内建约束（`NOT NULL / UNIQUE / CHECK / FOREIGN KEY`）守住底层防线；而动态鉴权、复合状态流转与外部系统一致性则交由应用逻辑与事务保障。

在查询层面，`JOIN` 按关系编织数据，务必分清 `ON` 与 `WHERE` 在外连接中的生效边界；处理多行集合问题时，按需选用 `GROUP BY`（汇总）、`DISTINCT`（结果去重）、`EXISTS`（存在判定）与 `ROW_NUMBER()`（明细组内选优）。最后，建立对生成式 SQL 的边界审查能力，把稳输入白名单与分页确定性，是保证工程落地的必要素养。

## 🎯 面试怎么回答

### 一对一、一对多、多对多通常怎样落表？

> [!TIP]
> 核心是定义一行所代表的业务事实。1:N 在“多”的一侧保存“一”的主键作为外键；N:N 引入独立的关联表，每一行表达一次关联事实并承载关系属性；1:1 是否拆表则权衡字段生命周期、读写频率差异、字段宽度与权限安全，避免无意义的机械拆解。

### 哪些规则适合交给数据库约束？

> [!TIP]
> 凡是数据库单凭行内数据或关联外键就能就地校验的静态规则，都应首选数据库约束，如字段非空（`NOT NULL`）、作用域唯一（`UNIQUE`）、枚举区间（`CHECK`）和父子引用（`FOREIGN KEY`）。而涉及用户动态权限、长事务跨表一致性或外部调用等场景，则由应用逻辑与事务协调。

### `INNER JOIN` 和 `LEFT JOIN` 有什么区别？

> [!TIP]
> `INNER JOIN` 仅返回两端条件均匹配的交集行；`LEFT JOIN` 以左表为主体全量保留，右表若无匹配则以 `NULL` 填充。选择的关键依据是业务上“未关联合适数据的孤立记录是否需要在最终报表中呈现”。

### `ON` 和 `WHERE` 在外连接中有何区别？

> [!TIP]
> `ON` 在连接阶段评估右表是否能够与左表配对；`WHERE` 则在整个连接结果集生成后执行全局过滤。在 `LEFT JOIN` 中，若将右表过滤条件移至 `WHERE`，会导致原本右表补 `NULL` 的行被当场剔除，外连接将退化为内连接。

### “每组取最新一条记录”为什么不能简单使用 `GROUP BY`？

> [!TIP]
> `GROUP BY` 仅能计算出每组的最大时间值，但无法推导其它非聚合字段（如标题、内容）应当匹配哪一行记录。在开启 `ONLY_FULL_GROUP_BY` 时该写法会直接报错。正确解法应当使用窗口函数 `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)` 在组内编号后提取 `rn = 1`。

### 针对 ORM 或 AI 生成的 SQL，核心验收指标有哪些？

> [!TIP]
> 1. 语义一致性：检查外连接是否漏查、1:N 连接是否引发意外的行数膨胀；  
> 2. 空值边界：验证 `NULL` 对 `IS NULL` 及 `NOT IN` 逻辑的影响；  
> 3. 排序与分页：检查排序列是否具有唯一确定性，避免深度分页时结果漂移；  
> 4. 安全合规：确保数据变量全量参数化，动态结构（表/列名）走严格后端白名单校验。

## ⚠️ 易错点

> [!WARNING]
> **规范化不是拆表越多越好。** 目标是消除事实的多重冗余维护，过度拆表会增加不必要的 JOIN 成本。

> [!WARNING]
> **`UNIQUE` 务必圈定作用域。** 多租户系统中的用户编号、订单流水号，通常是 `(tenant_id, code)` 联合唯一，单列唯一会导致严重业务冲突。

> [!WARNING]
> **外键不自动防御多租户渗透。** 任务与负责人关联时，必须联合租户 ID 建立复合外键，否则可能引用到竞争对手租户名下的成员。

> [!WARNING]
> **`LEFT JOIN` 右表条件慎入 `WHERE`。** 这会导致外连接失去保留左表记录的作用，变为内连接。

> [!WARNING]
> **连接导致行数翻倍并非数据库 BUG。** 1:N 关联本就会产生多行笛卡尔组合，进行求和/计数统计前必须先明确行粒度。

> [!WARNING]
> **`DISTINCT` 不可作为兜底补丁。** 不应通过 DISTINCT 掩饰因错误关联产生的多余行，而应纠正底层 SQL 关联逻辑。

> [!WARNING]
> **`NOT IN` 遭遇子查询 `NULL` 会引发全空结果。** 存在空值可能时，优先选用 `NOT EXISTS`。

> [!WARNING]
> **分页排序必须具备全局确定性。** 业务排序列存在重复时，末尾必须追加主键作为次级排序。

<summary><strong>2. 为什么学生和课程的多对多关系必须设立关联表？</strong></summary>

采用复合唯一约束：`UNIQUE (tenant_id, external_code)`。

</details>

<details>
<summary><strong>4. `LEFT JOIN` 后将右表字段过滤放入 `WHERE`，为何会丢失左表行？</strong></summary>

未匹配行在右表字段填充为 `NULL`，进入 `WHERE` 进行等值判断时评估为假，导致整行被剔除。

</details>

<details>
<summary><strong>5. 1:N 连接后调用 `COUNT(*)` 统计到的是什么？</strong></summary>

统计的是关联展开后的组合结果行总数，并非左表原本的唯一样本数量。

</details>

<details>
<summary><strong>6. `COUNT(*)` 与 `COUNT(col)` 统计差异是什么？</strong></summary>

`COUNT(*)` 计入所有行；`COUNT(col)` 自动剔除该列取值为 `NULL` 的行。

</details>

<details>
<summary><strong>7. 为什么判断关联存在性首选 `EXISTS` 而非 `JOIN + DISTINCT`？</strong></summary>

`EXISTS` 只要在子查询中探测到首条满足条件的数据便立即返回真，省去了全量连接和中间去重的工作量。

</details>

<details>
<summary><strong>8. 提取各组最新一条记录，标准做法是什么？</strong></summary>

使用窗口函数 `ROW_NUMBER() OVER (PARTITION BY 分组列 ORDER BY 排序列 DESC, 主键 DESC)` 赋予行号，外层过滤 `rn = 1`。

</details>

<details>
<summary><strong>9. AI 生成的代码能跑通，为何依然存在上线风险？</strong></summary>

语法正确无法证明业务逻辑正确，可能存在漏外连接、笛卡尔积膨胀、空值逻辑漏洞或分页顺序不稳定。

</details>

<details>
<summary><strong>10. 为什么不能写 `ORDER BY ?` 让前端直接传参？</strong></summary>

SQL 预处理占位符 `?` 仅允许承载数据字面量，表名与列名属于 SQL 标识符（Identifier），`ASC/DESC` 属于语法关键字（Keyword）。标识符与关键字均不能使用参数占位符，动态传参必须由后端通过显式白名单校验后映射拼装。

</details>

## 📌 本章最终要留下的六句话

1. **关系建模先确定“每一行代表什么独立事实”，再划分 1:1、1:N 还是 N:N 关系模式。**
2. **静态行内规则及引用完整性由数据库约束兜底，动态权限与跨服务事务由应用层承担。**
3. **`JOIN` 是行级组合；在 `LEFT JOIN` 中严禁将右表关联条件错写进 `WHERE` 导致连接退化。**
4. **集合运算先定行粒度：`GROUP BY` 压缩明细，`EXISTS` 快速探活，窗口函数精准取优。**
5. **“每组选一条”严禁依赖 `GROUP BY` 碰巧取值，必须使用窗口函数显式赋予序号。**
6. **对机器生成 SQL 保持严谨验收：审查连接放大、空值逻辑、确定性分页与参数白名单。**
