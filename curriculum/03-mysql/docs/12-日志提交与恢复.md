# 12｜日志、提交与故障恢复

[← 并发修改：条件更新、锁与死锁](11-并发修改锁与死锁.md) · [MySQL 目录](../README.md) · [分页：先跳过，还是从上次的位置继续 →](13-分页与查询成本.md)

数据库说“提交成功”时，究竟把什么保存下来了？如果必须等所有修改过的数据页都写回原来的位置，小事务也可能要等很多分散写入。

InnoDB 使用日志让“确认提交”和“把所有数据页写到最终文件”不必发生在同一时刻。理解这条路径，Redo、Undo、Binlog 才不会混成三种用途相同的备份。

## 1. 先区分旧值、页修改和对外变化

| 机制 | 保存信息为了回答什么 | 主要用途 |
|---|---|---|
| Undo（撤销日志） | 怎样撤销修改或重建旧版本 | 事务回滚、MVCC |
| Redo（重做日志） | 哪些页修改需要在故障后重做 | InnoDB 崩溃恢复 |
| Binlog（二进制日志） | 数据库发生过哪些可传播的变化 | 复制、CDC、结合备份恢复 |

Undo 和 Redo 服务于 InnoDB 存储与事务；Binlog 是 MySQL Server 层的日志。一次更新可能涉及三者，但它们回答的不是同一个问题。

例如余额由 100 改到 70，事务失败时需要撤销这笔修改，旧快照也可能仍需读 100；机器崩溃后需要恢复已记录的页修改；副本或搜索系统则需要获知这个已提交变化。这三种需求解释了为什么不是“一份日志包办”。

## 2. 为什么日志可以先写，数据页可以后写

数据页在缓冲池里被修改后，内存内容与磁盘原位置不一致，这种页叫**脏页**。如果等待所有脏页立即写回，提交就会受许多分散页面的 I/O 影响。

Redo 保存重建修改所需的信息，更适合追加写入。**WAL（预写日志）的关键要求，是在相关脏页写回以前，先使必要日志达到安全的持久化位置。** 提交路径满足相应持久性策略后，可以确认事务；脏页由后台逐步写回。

```text
修改内存页，记录必要的 Undo 和 Redo
    ↓
提交路径协调日志与事务状态，并按配置持久化
    ↓
确认提交；相关脏页之后再逐步写回最终位置
```

崩溃后，Redo 帮助重做尚未完整写到数据文件的变化，事务状态与 Undo 再参与处理未完成事务。**Redo 也可能包含未提交事务的修改**，不能把恢复简化成“只重放成功事务”。[官方恢复过程](https://dev.mysql.com/doc/refman/9.7/en/innodb-recovery.html)。

持久性还取决于刷盘配置。`innodb_flush_log_at_trx_commit=1` 使用较严格的提交日志持久化路径；值为 2 时，提交写到操作系统缓存、同步由周期任务完成；值为 0 时写出与同步主要由周期任务完成。进程故障、系统故障、断电影响不同，不能把典型周期写成“最多严格丢一秒”。

日志也不是无限追加的历史档案。**LSN** 表示 Redo 序列中的进展；某脏页需要较早的日志才能恢复，相关日志就不能被循环覆盖。后台把所需脏页写到数据文件后，**Checkpoint（检查点）** 才能安全向前推进，旧日志空间逐步可复用。检查点不是“此刻所有事务都提交”，也不是每次都把全库脏页一次刷完。若产生 Redo 比刷脏推进快，剩余空间逼近极限，前台写入会受到压力；加大日志容量能缓冲突发，却不能长期弥补磁盘跟不上。[Redo 与检查点](https://dev.mysql.com/doc/refman/9.7/en/innodb-checkpoints.html)

多个事务可通过**分组提交**摊薄同步成本，因此并不是每笔事务都独占一次物理刷盘。存储设备还必须真实履行持久化请求，配置名称本身不保证硬件永远正确。

## 3. 为什么还需要 Redo 与 Binlog 协调提交

如果 InnoDB 已确认一笔事务，而 Binlog 没有它，副本和后续重放会缺少这笔变化；反过来，Binlog 有了事务、InnoDB 却最终回滚，同样不一致。

为避免两边对同一事务作出相反决定，启用相应日志的正常提交路径需要**内部两阶段提交**。可以先用这条简化线理解：

```text
InnoDB 进入准备状态
        ↓
写入并按策略持久化对应 Binlog 事务
        ↓
完成 InnoDB 提交
```

准备状态的意义，是故障发生时还能依据有效日志判断应完成提交还是回滚，而不是让一边不可撤销地先成功。真实实现还涉及分组提交等阶段，图不是每次磁盘操作的精确序列。

按这条路径列出故障点，就能看见准备状态的用途。以下假设开启 Binlog、日志采用严格持久化策略且介质未损坏，用事务标识关联两边：

| 崩溃时可靠保留下来的证据 | 恢复决定 | 原因 |
|---|---|---|
| 未形成可恢复的 prepare | 未完成事务按恢复规则回滚 | 没有进入可提交准备状态 |
| 已 prepare，无完整有效的对应 Binlog 事务 | 回滚 | 对外提交依据尚未成立 |
| 已 prepare，Binlog 有完整有效事务，但尚无最终 commit 标记 | 完成提交 | 已能确认协调者的提交决定，不能只因标记没写完就撤销 |
| 提交已完成 | 保持提交，必要时重做数据页 | 数据页可以仍落后于日志 |

恢复时先用 Redo 重建必要引擎状态，再根据事务状态与有效 Binlog 决定准备事务的结局；这并不表示把所有含有一段 Binlog 字节的事务都提交。不完整尾部、非严格刷盘和介质损坏不能套成同样的承诺。即使最终恢复为提交，客户端也可能没收到回应，下一章之后的批量写入会继续讨论“结果未知”。[崩溃恢复的事务协调](https://dev.mysql.com/doc/refman/9.7/en/innodb-recovery.html)

`sync_binlog=1` 配合严格的 Redo 刷盘策略，提高日志与提交状态的持久性基础，也增加同步成本。[Binlog](https://dev.mysql.com/doc/refman/9.7/en/binary-log.html)与[InnoDB 持久性配置](https://dev.mysql.com/doc/refman/9.7/en/innodb-parameters.html#sysvar_innodb_flush_log_at_trx_commit)分别说明这些责任。

> ⚠️ 这里协调的是 MySQL 内部的 InnoDB 与 Binlog，不自动包含 Redis、消息队列或支付服务。名字相似，不能把本地提交机制直接当成跨系统事务。

## 4. 误删后的恢复，还需要备份和正确的日志边界

02:00 做了一份一致备份，10:37 发生误删。恢复不是重启数据库就回到 02:00，而是先在隔离实例恢复备份，再从与备份对应的日志位置重放，停在错误事务之前，最后核对业务数据。

Binlog 提供后续变化，备份提供起始状态。两者都需要实际保留、可读取，并且边界衔接。不能仅凭“10:36:59”猜停止点：同一秒可能有多笔事务，还要核对准确事务位置与时区。[时间点恢复](https://dev.mysql.com/doc/refman/9.7/en/point-in-time-recovery.html)。

普通副本也会复制误删，所以副本不替代备份。重启测试、误删恢复与断电恢复验证的是不同故障，不能互相冒充。

页写到一半可能把新旧扇区拼成损坏页。Redo 描述如何在合法页状态上重做修改，不承诺能从任意损坏的页头、偏移和内容还原整页。Doublewrite 先保存完整页的恢复副本，再写最终数据位置；发生相关部分写时先修复一个有效页，再由 Redo 推进。它们不是两遍相同的业务写入，不应为提升吞吐就无条件关闭。

## 本章小结

Undo 帮助回退和读历史，Redo 支持页修改恢复，Binlog 提供可传播变化。提交依赖日志协调与持久化策略；误删恢复另需一致备份、连续日志和准确事务边界。

## 🎯 面试怎么回答

### 为什么提交成功不等于所有数据页都已刷盘？

恢复所需日志先满足持久化要求后，可以在崩溃时重建尚未写回的页修改，因此数据页可后台刷新。承诺还受刷盘策略与存储语义约束，不能扩大到任何故障都不丢。

### 两阶段提交解决什么问题？

协调 InnoDB 事务状态与 Server 的 Binlog，避免一个认为事务提交、另一个缺失对应记录。它是 MySQL 内部的提交协调，不是自动实现 MySQL 与外部系统强一致。

## ⚠️ 易错点

> ⚠️ Redo 不是只记录提交成功的事务；恢复还需要处理未完成事务。

> ⚠️ Binlog 不是自足的全量备份，复制也不能替代误删恢复方案。

## 本章自测

<details>
<summary>1. 为什么数据库不必每次提交都写完所有脏页？</summary>

必要日志已能重建未完整写回的修改，脏页可随后刷新，从而减少提交路径对分散写入的等待。

</details>

<details>
<summary>2. 副本有完整复制，为什么仍可能一起误删？</summary>

误删也是源上已提交的变化，普通复制会忠实应用它，需要独立历史备份和重放方案恢复。

</details>

<details>
<summary>3. 为什么 InnoDB 的提交决定需要与 Binlog 协调？</summary>

若一边认为事务成功，另一边却缺失对应有效记录，本地状态与复制、重放依据就可能不一致。内部两阶段提交使故障恢复能判断应完成提交还是回滚。

</details>
