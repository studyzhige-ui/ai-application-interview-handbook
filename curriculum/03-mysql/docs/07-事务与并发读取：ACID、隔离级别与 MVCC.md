## 0. 业务动作只要由多步操作构成，为什么在并发与故障下面临双重失控？

在单机单线程环境下，数据处理是简单而线性的：一个动作按顺序执行，读取到的必定是上一次写入的真实结果。

但在真实的生产系统中，绝大多数具有商业意义的操作都由多条 SQL 协同完成（例如资金转账至少需要扣减转出账户、增加转入账户两个写操作），并且时刻面临两大物理现实的挑战：
1. **执行中途随时可能发生故障**：扣减资金后，服务器可能断电、进程可能被强杀、网络可能超时中断，或者第二条写操作触发唯一性报错。如果操作停留在“只做了一半”的残缺状态，系统就会产生坏账与资产对账不平；
2. **多个操作在时间线上并发交织**：当一个操作正在修改数据且尚未提交时，其他业务线程可能正在并发读取同一行；或者当一个业务事务在两次读取之间，另一个业务更新并提交了数据甚至插入了新数据。如果不对并发读取施加隔离保护，系统就会暴露出脏读、不可重复读和幻读等数据混乱。

为了解决这两大失控风险，关系型数据库提供了两套紧密配合的机制底座：
- **事务机制（Transaction）**：将多条 SQL 捆绑为一个不可分割的逻辑执行单元，提供全有或全无（All-or-Nothing）的原子性保护与持久化承诺；
- **多版本并发控制（MVCC）与隔离级别**：在不依赖重量级全局读写锁的前提下，为并发事务划定清晰的数据可见性边界，实现“读不阻塞写、写不阻塞读”的高吞吐并发读取。

> [!IMPORTANT]
> **💡 核心认知：事务（Transaction）解决了单业务链路中“多步操作不能只完成一半”的完整性风险；而隔离级别与 MVCC 则解决了多业务链路并发执行时“当前事务究竟能看见什么数据版本”的可见性难题。二者共同构成了关系型数据库应对复杂并发业务的数据安全基石。**

## 1. 为什么多条 SQL 需要组成一个 Transaction？

多条 SQL 需要组成一个事务，根本原因在于大多数业务动作由多步写操作构成，而 MySQL 默认开启单语句自动提交（`autocommit=1`）。若不显式开启事务将其绑定为一个执行单元，一旦中途遭遇宕机崩溃、网络超时或语句报错，系统就会停留在“前半段成功写入、后半段丢失”的半完成状态，破坏业务守恒规则。事务机制通过 `COMMIT` 与 `ROLLBACK` 保证这组操作全有或全无，对外隐藏中间状态，确保业务不变量在并发与故障下始终闭合。

---

### 1.1 自动提交（autocommit）的默认行为与失控场景

在默认连接配置下，MySQL 的系统变量 `autocommit` 为 `1`（开启状态）：

```sql
SHOW VARIABLES LIKE 'autocommit'; -- 默认值为 ON (1)
```

当 `autocommit = 1` 时，客户端发出的每一条单独的 DML 语句（`INSERT`、`UPDATE`、`DELETE`）都被当作一个独立的事务。语句一旦执行成功，MySQL 内部会立即自动执行隐式提交，物理修改立即固化并对全系统可见。

考虑电商业务中的转账动作，涉及两个写操作：
1. 扣减 A 账户余额：`UPDATE accounts SET balance = balance - 100 WHERE id = 'A';`
2. 增加 B 账户余额：`UPDATE accounts SET balance = balance + 100 WHERE id = 'B';`

在单语句自动提交模式下，两条语句的执行是孤立的：

```text
[客户端]                                              [MySQL 服务端]
   │                                                         │
   ├── 1. UPDATE accounts SET balance = balance - 100 ... ──>│ 执行扣减
   │                                                         │ 自动隐式 COMMIT (A 账户已少 100 元)
   │<── OK (受影响行数: 1) ──────────────────────────────────┤
   │                                                         │
   * 突发系统异常：应用服务器宕机 / 网络断开 / 目标账户 B 不存在报错 *
   │                                                         │
   X  第二条增加 B 账户余额的 SQL 从未到达数据库并执行 X
```

此时，A 账户的 100 元已经持久化扣除，但 B 账户从未收到加款。系统内部的资产总额凭空蒸发了 100 元。没有任何数据库机制能自动推测并回滚第一条已经提交的语句。

---

### 1.2 显式事务的控制生命周期

为了保证多步业务操作的原子性，必须显式开启事务，将多条语句纳入同一个生命周期管控：

```sql
-- 1. 显式开启事务
START TRANSACTION;

-- 2. 执行第一步业务写操作
UPDATE accounts SET balance = balance - 100 WHERE id = 'A';

-- 3. 执行第二步业务写操作
UPDATE accounts SET balance = balance + 100 WHERE id = 'B';

-- 4. 无异常则显式提交；若中途捕获任何报错，则执行 ROLLBACK
COMMIT;
```

显式事务的生命周期包含三种状态跃迁：
- **开启（Active）**：通过 `START TRANSACTION`（或 `BEGIN`）显式关闭当前会话的单语句自动提交模式，后续的所有写操作都属于该事务；
- **提交（Committed）**：所有业务操作均成功执行后，发出 `COMMIT` 命令。存储引擎将所有修改正式固化并持久化，对其他事务公开可见；
- **回滚（Aborted / Rolled Back）**：如果任意一条 SQL 执行失败、应用抛出异常，或者客户端显式发出 `ROLLBACK` 命令，存储引擎会利用 Undo Log 撤销该事务期间所做的所有行修改，将数据完整恢复到事务开启前的状态。

```text
       START TRANSACTION
              │
              ▼
       [ 活跃态 Active ] ───(执行业务 SQL 1, 2, 3...)
              │
      ┌───────┴───────┐
 (全部成功)        (发生异常/失败)
      │               │
      ▼               ▼
   COMMIT          ROLLBACK
      │               │
      ▼               ▼
[ 已提交 Committed ] [ 已回滚 Aborted ]
```

### 1.3 业务不变量（Business Invariant）

为什么数据库不能只提供单个数据的修改，而必须提供事务？因为业务系统存在**业务不变量（Business Invariant）**。

业务不变量是业务系统在任何静止时刻都必须绝对满足的客观事实与守恒定律。例如：
- 资金转账时：`转出方扣减金额 == 转入方增加金额`，系统资金总和守恒；
- 电商下单时：`订单明细中扣减的商品库存总数 == 订单商品购买数量`；
- 财务记账时：`借方发生额合计 == 贷方发生额合计`。

业务不变量的破坏往往不是由单条错误的 SQL 造成的，而是因为**在从一个合法状态跃迁到下一个合法状态的过程中，被外部观察到了中间状态，或者因为崩溃永久滞留在了中间状态**。事务的作用，就是将状态跃迁的过程封装为一个原子黑盒。

## 2. Transaction Boundary 应该怎样划，业务一致性由谁共同保证？

划定事务边界的标准是**以“能够完整闭合业务不变量的最小范围”为原则**：边界过小会导致原子性断裂引发状态不一致；边界过大会导致事务持有行排他锁时间过长，造成锁竞争、阻塞与连接池耗尽。同时，**绝对不能将外部网络调用（RPC、第三方 HTTP、短信通知）包裹在本地事务之内**。

业务一致性由数据库底层能力与应用层业务逻辑分工协作共同保障：
1. **数据库守底线**：通过主键、唯一索引、NOT NULL、CHECK 约束拦截非法结构，通过事务机制保证多步物理操作全有或全无；
2. **应用层闭环规则**：负责动态业务规则校验，并通过编写带前提保护的**条件更新（Conditional Update）**，将前置校验与物理写入合二为一，防止高并发下的数据覆盖。

```text
事务范围过小 ───> 业务不变量被切断，产生状态不一致与半完成状态
事务范围过大 ───> 持有行锁时间过长，造成锁竞争、阻塞与连接池耗尽
```

---

### 2.1 边界过小：状态不一致与半完成泄漏

如果为了追求单次 SQL 执行迅速，将原本属于同一业务动作的多步操作拆分到多个独立事务中提交，就会直接失去原子性保护：

```text
[事务 1]: UPDATE accounts SET balance = balance - 100 WHERE id = 'A'; COMMIT;
   ↓ (此时网络中断或服务器崩溃，事务 2 未能执行)
[事务 2]: UPDATE accounts SET balance = balance + 100 WHERE id = 'B'; COMMIT;
```

在事务 1 提交后、事务 2 开始前的微秒时间窗口内，A 账户的钱已被扣除，但 B 账户尚未收到。不仅系统整体资金出现临时亏空，若事务 2 因故障永远没有执行，该不一致状态就会变为永久性破坏。

---

### 2.2 边界过大：长事务（Long Transaction）的连锁性能损耗与风险

在实际工程中，一种高频反模式是将整个 Controller 或 Service 方法直接声明全局事务（如 Spring 的 `@Transactional`），把参数解析、复杂报表计算、外部接口调用等全部包裹进同一个大事务中。

事务从执行第一条修改 SQL 的那一刻起，就会在数据库中申请**行排他锁（X 锁）**，并占用连接池中的物理连接。如果事务耗时从 5ms 延长到 5s，会引发严重的连锁系统性能故障：
1. **行锁阻塞范围急剧放大**：只要该大事务未提交，其修改过的所有记录上的行锁都不会释放。其他任何并发业务如果试图修改这些记录，都会被迫陷入排队等待，极易引发大面积请求超时与数据库死锁；
2. **应用连接池迅速被打满**：物理连接必须全程绑定该线程直至事务提交。高并发下，所有工作线程都在等待漫长的事务结束，连接池中的连接被瞬间耗尽，导致后续无关请求均因拿不到连接而报错拒绝服务；
3. **撤销日志（Undo Log）历史链严重堆积**：长事务的存在会阻止 MySQL 清理旧版本数据，导致回滚段急剧膨胀，拖垮整库的多版本读取性能。

---

### 2.3 核心红线：本地事务管不了外部副作用

划定事务边界最严格的一条工程红线是：**绝对不能将外部网络调用（如微服务 RPC、第三方支付接口、短信通知、MQ 发送）包裹在本地数据库事务之内。**

```text
START TRANSACTION;
1. UPDATE orders SET status = 'paid' WHERE id = 101;
2. 调用外部 HTTP 接口向第三方支付平台确认扣款 ... (若此时网络超时挂起 10 秒)
3. 发送短信通知用户 ...
COMMIT;
```

将外部调用放入事务具有致命缺陷：
1. **网络调用的不可控耗时会把短事务直接变成长事务**，长时间占用行锁与数据库连接；
2. **本地事务的 `ROLLBACK` 根本无法撤销已发生的外部副作用**。如果在第 3 步发送短信失败抛出异常，数据库本地事务会回滚，订单状态恢复为未支付，但第 2 步的银行扣款已在外部生效，数据库回滚无法让银行把扣除的资金退回。

#### 标准工程解法：收缩本地事务，副作用后置
将本地数据操作与外部副作用严格解耦：
- 本地事务仅负责更新数据库状态并快速提交；
- 外部 RPC、短信发送或异步事件放在事务成功提交（`COMMIT`）之后执行；
- 若外部调用失败，通过应用层的重试、对账任务或反向补偿流程解决，绝不寄希望于数据库回滚外部世界。

```text
[步骤一：快速执行本地事务]
START TRANSACTION;
UPDATE orders SET status = 'paid' WHERE id = 101;
COMMIT; -- 立即提交，释放行锁与连接

[步骤二：事务成功后，触发外部动作]
sendSmsNotification(); -- 即使发送失败，只做告警或重试，不影响订单状态
```

### 2.4 业务一致性保障体系：数据库守底线，应用层闭环规则

业务一致性是由应用层和数据库分工协作共同保证的：**数据库负责守住底线，应用层负责闭环规则**。

```text
                      业务一致性保证体系
                              │
       ┌──────────────────────┴──────────────────────┐
       ▼                                             ▼
[数据库层：提供安全底座]                      [应用层：实现规则闭环]
- Schema 约束 (主键/唯一/非空)                - 合理划定事务边界 (原子提交)
- CHECK 约束与外键关系                        - 条件更新 (带状态防护的 SQL)
- 事务机制 (提供原子性与隔离性)               - 编排业务校验与前后逻辑
```

#### 数据库 Schema 约束的底线防御
数据库原生约束（PRIMARY KEY、UNIQUE、NOT NULL、CHECK 与 FOREIGN KEY）由存储引擎在写入时直接校验并硬性拦截非法取值，构筑了实体标识、空值防御与静态数值区间的物理底线。

然而，数据库原生约束的表达能力是有限的。它们通常只能检查单表、单行的静态取值，无法感知复杂的动态业务逻辑（例如：“普通用户每日转账总额不能超过 5 万元”、“促销活动期间库存扣减按阶梯规则计算”）。

#### 条件更新（Conditional Update）：让 SQL 自身带上成立前提
在并发环境下，单靠事务本身无法防止业务规则被打破。

考虑一个典型的错误写法：代码先通过 `SELECT balance FROM accounts WHERE id = 'A'` 查出余额为 100，然后在 Java 代码中判断 `if (balance >= 100)` 通过，最后执行 `UPDATE accounts SET balance = balance - 100`。
若两个并发请求同时读到余额为 100，两边代码的 `if` 校验都会通过，导致该账户被扣减两次，余额变为 -100！

为了防止这种破坏业务一致性的并发修改，标准的工程实践是采用**条件更新（Conditional Update）**，将业务的前提判断直接嵌入到写语句的 `WHERE` 条件中：

```sql
-- 将业务前提“余额必须大于等于待扣减金额”写入 SQL 自身
UPDATE accounts 
SET balance = balance - 100 
WHERE id = 'A' AND balance >= 100;
```

执行后，应用层检查该语句**实际影响的行数（Affected Rows）**：
- 若影响行数为 1：说明扣减成功，业务前提在行锁保护下成立；
- 若影响行数为 0：说明余额不足（或者账户不存在），条件不满足，立即向用户返回余额不足错误并触发事务回滚。

条件更新把“校验条件”与“执行修改”合为一体，借助行排他锁保证了判断过程的原子性，是保障业务一致性的核心手段。

---

## 3. ACID 到底保证什么？

ACID 是关系型数据库在并发和故障场景下保证数据正确性的四大语义契约：
1. **原子性（Atomicity）**：保证事务内的所有操作要么全做、要么全不做，中途发生应用崩溃、语法错误或网络断开时绝不留下半完成的残缺状态；
2. **一致性（Consistency）**：保证事务执行前后，数据始终满足所有预定义的完整性约束与业务规则；一致性是事务最终要达成的业务目标，而 A、I、D 是实现这一目标的底层技术手段；
3. **隔离性（Isolation）**：保证并发执行的多个事务彼此不受干扰，通过不同隔离级别限制脏读、不可重复读和幻读等并发异常；
4. **持久性（Durability）**：保证事务一旦 `COMMIT` 成功，所做的修改即永久生效，即使随后发生系统断电或服务器崩溃，数据也绝对不会丢失。

```text
      ┌─ A (Atomicity)   原子性 ── 规避“半完成”故障
      │
ACID ─┼─ I (Isolation)   隔离性 ── 规避“并发相互干扰”故障
      │
      ├─ D (Durability)  持久性 ── 规避“断电崩溃丢失”故障
      │
      └─> 最终达成：
         C (Consistency) 一致性 ── 维持业务规则与数据完整性
```

| 契约维度 | 核心语义 | InnoDB 底层支撑机制 | 违背时的典型故障表现 |
|---|---|---|---|
| **A (Atomicity)<br>原子性** | 事务内的所有操作要么全做、要么全不做 | **Undo Log（回滚日志）**：记录历史反向变更，异常时物理回滚活跃事务 | 资金转账只扣了款却没到账；订单生成了却没扣库存 |
| **C (Consistency)<br>一致性** | 事务执行前后，数据始终满足既定约束与业务规则 | **Schema 约束 + AID 共同托底 + 应用层规则闭环** | 账户余额出现负数；外键指向了不存在的主表记录 |
| **I (Isolation)<br>隔离性** | 并发执行的多个事务彼此中间状态互不影响 | **MVCC 多版本并发控制 + 行级锁（Record/Gap Lock）** | 读到了其他事务未提交的脏数据；并发扣库存导致超卖 |
| **D (Durability)<br>持久性** | 事务一旦成功提交（COMMIT），其修改便永久生效 | **Redo Log（WAL 预写日志） + 两阶段提交落盘** | 客户端收到支付成功提示，服务器宕机重启后数据凭空消失 |

---

### 3.1 厘清因果：C 是业务目的，AID 是数据库手段

在 ACID 四个要素中，**C（一致性）与其他三个字母不在同一个抽象层面上**：
- **A（原子性）、I（隔离性）、D（持久性）** 是数据库系统本身通过底层算法和存储结构向应用提供的**核心机制与技术承诺**；
- **C（一致性）** 则是系统最终要达成的**业务目标与状态结果**。

数据库做到了原子性（不留半完成状态）、隔离性（不被并发打乱顺序）和持久性（不因宕机丢失数据），仅仅是为达成业务一致性创造了必要的技术条件。如果没有应用层写出符合业务逻辑的 SQL，数据库即便完美履行了 AID，整体业务数据依然可能发生不一致。

## 4. 脏读、不可重复读、幻读分别是什么，隔离级别怎样约束它们？

脏读、不可重复读与幻读是并发事务在不同隔离程度下暴露的三类读异常：
1. **脏读（Dirty Read）**：当前事务读到了另一个并发事务**尚未提交（Uncommitted）**的修改数据。一旦该并发事务后续发生异常回滚，当前事务读取到的就是从未正式提交确认的临时脏数据；
2. **不可重复读（Non-repeatable Read）**：在同一个事务内，使用相同条件前后两次读取**同一行现有记录**，得到了不同的字段值。这是因为两次读取之间，另一个并发事务**修改或删除了该行并成功提交**；
3. **幻读（Phantom Read）**：在同一个事务内，使用相同的范围条件前后两次读取，后一次读取发现了之前不存在的**新增记录（如同凭空出现的幻影）**。这是因为两次读取之间，另一个并发事务**新增了符合该范围条件的记录并成功提交**。

SQL 标准定义了四种隔离级别来逐步约束这三类异常：
- **Read Uncommitted（读未提交，RU）**：允许读取未提交数据，三类异常均可能发生；
- **Read Committed（读已提交，RC）**：只允许读取已提交数据，解决脏读，但允许不可重复读与幻读；
- **Repeatable Read（可重复读，RR，MySQL 默认）**：保证同一事务内多次读取同一数据保持一致，解决脏读和不可重复读，并通过 MVCC 在快照读下消除幻读；
- **Serializable（可串行化）**：在关闭自动提交时将普通 `SELECT` 隐式转换为 `SELECT ... FOR SHARE`（加共享 Next-Key 锁），实现严格读写互斥，彻底消除所有读异常，但读写并发吞吐大幅下降。

隔离级别的本质是**数据可见性严格度与系统并发吞吐之间的权衡**。

---

### 4.1 并发时间线推演：三类异常的发生场景

通过同一条时间线对比三个场景的执行过程：

#### 场景一：脏读（读取了未确认即被撤销的数据）

| 时刻 | 事务 A (转账业务) | 事务 B (报表统计) |
|:---:|---|---|
| **T1** | `START TRANSACTION;` | — |
| **T2** | `UPDATE accounts SET balance = 500 WHERE id = 1;`<br>*(余额从 100 改为 500，未提交)* | — |
| **T3** | — | `START TRANSACTION;` |
| **T4** | — | `SELECT balance FROM accounts WHERE id = 1;`<br>*(读到 500，**脏读发生**)* |
| **T5** | `ROLLBACK;`<br>*(事务 A 异常回滚，真实余额恢复为 100)* | — |
| **T6** | — | `COMMIT;` |

事务 B 在 T4 时刻读到了临时值 500 并用于后续计算，但事务 A 在 T5 回滚，数据库里的真实余额依然是 100。事务 B 基于不存在的数据做出了决策。

#### 场景二：不可重复读（同一行数据前后读取不一致）

| 时刻 | 事务 A (商品改价) | 事务 B (订单结算) |
|:---:|---|---|
| **T1** | — | `START TRANSACTION;` |
| **T2** | — | `SELECT price FROM goods WHERE id = 10;`<br>*(读到价格 100)* |
| **T3** | `START TRANSACTION;` | — |
| **T4** | `UPDATE goods SET price = 200 WHERE id = 10;` | — |
| **T5** | `COMMIT;`<br>*(事务 A 修改并提交)* | — |
| **T6** | — | `SELECT price FROM goods WHERE id = 10;`<br>*(再次读取，读到价格 200，**不可重复读发生**)* |
| **T7** | — | `COMMIT;` |

事务 B 在同一个事务内先后执行两次相同的单行查询，第一次读到 100，第二次读到 200，破坏了事务内部对单行数据状态的确定性认知。

#### 场景三：幻读（范围查询集合凭空多出记录）

| 时刻 | 事务 A (新增注册用户) | 事务 B (用户数量审计) |
|:---:|---|---|
| **T1** | — | `START TRANSACTION;` |
| **T2** | — | `SELECT * FROM users WHERE age > 30;`<br>*(检索出 2 条符合条件的记录)* |
| **T3** | `START TRANSACTION;` | — |
| **T4** | `INSERT INTO users VALUES (3, '张三', 35);` | — |
| **T5** | `COMMIT;`<br>*(事务 A 插入并提交)* | — |
| **T6** | — | `SELECT * FROM users WHERE age > 30;`<br>*(再次检索，凭空出现第 3 条记录，**幻读发生**)* |
| **T7** | — | `COMMIT;` |

不可重复读强调的是**现有某一行数据的属性被修改（UPDATE/DELETE）**；而幻读强调的是**符合范围条件的记录集合数量发生了变化，出现了新的数据行（INSERT）**。

### 4.2 四种隔离级别的防护矩阵

| 隔离级别 | 脏读（Dirty Read） | 不可重复读（Non-repeatable Read） | 幻读（Phantom Read） | 典型应用与说明 |
|---|:---:|:---:|:---:|---|
| **Read Uncommitted (RU)** | ❌ 发生 | ❌ 发生 | ❌ 发生 | 性能最高，但无任何并发安全保障，工程中几乎不用 |
| **Read Committed (RC)** | ✅ **解决** | ❌ 发生 | ❌ 发生 | Oracle、PostgreSQL 默认；互联网大厂广泛使用 |
| **Repeatable Read (RR)** | ✅ **解决** | ✅ **解决** | 🟡 **快照读解决** | MySQL InnoDB 默认隔离级别 |
| **Serializable** | ✅ **解决** | ✅ **解决** | ✅ **解决** | autocommit 关闭时将普通读隐式加共享 Next-Key 锁，实现严格读写互斥 |

## 5. MVCC 为什么能减少读写阻塞？

MVCC（多版本并发控制）之所以能减少读写阻塞，核心在于**将并发读写解耦到了不同的物理与逻辑版本上**：写操作修改聚簇索引最新记录并在 Undo Log 中追加历史版本，而普通读操作（一致性快照读）无需申请任何行锁，直接通过 Read View 沿 Undo 版本链回溯对当前事务合法的历史快照。读写双方在不同版本上并行操作，彻底消除了传统封锁模型下“读锁写、写锁读”的互斥阻塞。

MVCC 的底层运作依赖三大核心构件：
1. **聚簇索引行的隐藏系统列**：记录修改该行的事务 ID 与回滚指针；
2. **Undo 版本链（Version Chain）**：由 `DB_ROLL_PTR` 串联起的单向旧数据历史版本链表；
3. **Read View（一致性读视图）**：事务发起快照读时生成的可见性快照，用于裁定版本链上的哪个版本对当前事务可见。

---

### 5.1 行记录的隐藏系统列

在 InnoDB 的聚簇索引中，每一行物理记录除了用户自定义的业务列之外，内部都会被自动附加三个隐藏系统列：

| 隐藏列名称 | 物理长度 | 核心职责 |
|---|:---:|---|
| **`DB_ROW_ID`** | 6 字节 | 行 ID。若表没有显式定义主键且无唯一非空索引，InnoDB 会用它生成隐式聚簇索引主键。 |
| **`DB_TRX_ID`** | 6 字节 | 事务 ID。记录最后一次对本行记录执行 `INSERT`、`UPDATE` 或 `DELETE`（标记删除）的事务标识符。 |
| **`DB_ROLL_PTR`** | 7 字节 | 回滚指针。指向该行对应的 Undo Log 历史版本记录，用于在需要时回溯先前的旧值。 |

---

### 5.2 Undo 版本链（Version Chain）

当一行记录被不同事务接连修改时，最新的数据行直接保存在 B+Tree 聚簇索引的叶子节点中，而每次修改前的旧字段值会被写入 Undo Log。新记录的 `DB_ROLL_PTR` 指针会指向刚刚写入的这笔 Undo Log 记录。

多笔事务修改后，在物理上形成了一条按事务提交时序从新到旧单向串联的 **Undo 版本链**：

```text
[聚簇索引最新物理行]
  id = 1 | name = '赵六' | DB_TRX_ID = 400 | DB_ROLL_PTR ──┐
                                                           │ (指向 Undo Log)
  ┌────────────────────────────────────────────────────────┘
  ▼
[Undo Log 历史版本 1]
  id = 1 | name = '王五' | DB_TRX_ID = 300 | DB_ROLL_PTR ──┐
                                                           │
  ┌────────────────────────────────────────────────────────┘
  ▼
[Undo Log 历史版本 2]
  id = 1 | name = '李四' | DB_TRX_ID = 200 | DB_ROLL_PTR ──┐
                                                           │
  ┌────────────────────────────────────────────────────────┘
  ▼
[Undo Log 初始插入记录]
  id = 1 | name = '张三' | DB_TRX_ID = 100 | DB_ROLL_PTR = NULL
```

- **最新数据**永远存在于聚簇索引叶子节点中；
- **历史快照**只存在于 Undo Log 中；
- 链表是有方向的：从最新的行记录出发，沿着 `DB_ROLL_PTR` 只能向更早的历史版本单向遍历。

---

### 5.3 Read View 的核心结构与可见性判定算法

当一个事务执行普通查询（快照读）时，InnoDB 会在内存中为该查询生成一个 **Read View（一致性读视图）**。Read View 是系统当前所有活跃事务的快照清单，包含四个最核心的字段：

```text
Read View 结构体
├── creator_trx_id: 创建该 Read View 的事务自身 ID
├── m_ids:          生成 Read View 瞬间，系统里所有“已启动但尚未提交”的活跃事务 ID 列表
├── min_trx_id:     m_ids 列表中最小的事务 ID (活跃事务下限)
└── max_trx_id:     生成 Read View 瞬间，系统即将分配给下一个新事务的全局递增 ID (系统事务上限)
```

#### 可见性裁定四步法
当当前事务扫描到某条物理记录（或沿版本链回溯）时，它会取出该版本的 `DB_TRX_ID`（记为 `trx_id`），严格按以下流程判定该版本是否对自己可见：

```text
                         判断该版本的 trx_id
                                  │
          ┌───────────────────────┴───────────────────────┐
          ▼                                               ▼
trx_id == creator_trx_id ?                     trx_id < min_trx_id ?
   [ 是：当前事务自身修改 ]                         [ 是：生成视图前已提交 ]
          │                                               │
          ▼                                               ▼
       【可见】                                        【可见】
          │ (否)                                          │ (否)
          └───────────────────────┬───────────────────────┘
                                  ▼
                        trx_id >= max_trx_id ?
                       [ 是：生成视图后新开启的事务 ]
                                  │
                                  ▼
                              【不可见】
                                  │ (否)
                                  ▼
                        trx_id 在 m_ids 列表中 ?
                                  │
                    ┌─────────────┴─────────────┐
                    ▼                           ▼
                 [ 是 ]                       [ 否 ]
          生成视图时尚在活跃未提交               生成视图时已提交完毕
                    │                           │
                    ▼                           ▼
                【不可见】                     【可见】
```

如果一个版本被判定为不可见，查询引擎便顺着该版本的 `DB_ROLL_PTR` 沿着链表回溯检查上一版本，直到找到第一个可见版本并提取数据；若追溯到链表末尾仍无可见版本，则说明该行在当前视图下不可见（视同记录不存在）。

---

## 6. RC 和 RR 为什么会看到不同版本？快照读和锁定读为什么不能混为一谈？

RC（读已提交）与 RR（可重复读）在底层均依赖 MVCC，二者行为差异的根本原因在于**生成 Read View 的时机与复用策略不同**：
1. **RC 级别：每次执行快照读（SELECT）都会重新生成一个全新的 Read View**。这意味着在事务执行期间，只要其他并发事务提交了修改，后续的 SELECT 就会因为生成了新视图而立即看到最新提交的数据，从而导致不可重复读；
2. **RR 级别：通常只在事务内的第一次执行快照读时生成 Read View，并在整个事务后续的一致性读中一直复用该视图**。无论后续其他事务何时提交，当前事务始终基于第一次查询时的活跃事务快照判定可见性，从而天然实现了“可重复读”；
3. **自身修改始终可见**：无论在 RC 还是 RR 下，当前事务自身执行的 INSERT、UPDATE、DELETE 对后续查询始终可见（因为 `trx_id == creator_trx_id` 判定优先级最高）。

同时，**不能将快照读与当前读混为一谈**。在 RR 级别下：
- **快照读（Consistent Read）**：基于 MVCC 版本链读取，不加锁，完全解决幻读；
- **当前读（Current Read / Locking Read）**：必须读取最新提交数据并加锁，MVCC 无法防范当前读下的幻读，必须依赖间隙锁（Gap Lock）和 Next-Key Lock 机制。

---

### 6.1 同一时序下 RC 与 RR 的 Read View 行为对照

假设数据初始状态为 `id=1, name='张三', DB_TRX_ID=100`（已提交）。

| 时刻 | 事务 A | 事务 B (trx_id=300) |
|:---:|---|---|
| **T1** | `START TRANSACTION;` | `START TRANSACTION;` |
| **T2** | — | `UPDATE t SET name = '李四' WHERE id = 1;`<br>*(写入聚簇行，DB_TRX_ID=300，旧值入 Undo)* |
| **T3** | `SELECT name FROM t WHERE id = 1;`<br>*(第一次快照读)* | — |
| **T4** | — | `COMMIT;`<br>*(事务 B 提交)* |
| **T5** | `SELECT name FROM t WHERE id = 1;`<br>*(第二次快照读)* | — |
| **T6** | `COMMIT;` | — |

#### 在 RC 模式下的推演：
- **T3 时刻（第一次读）**：生成 Read View 1，活跃事务列表 `m_ids=[300], min_trx_id=300, max_trx_id=301`。
  - 聚簇索引最新版本为 `name='李四', DB_TRX_ID=300`；
  - `300` 落在活跃列表 `m_ids` 中（未提交），判定为**不可见**；
  - 顺着 `DB_ROLL_PTR` 回滚指针找到旧版本 `name='张三', DB_TRX_ID=100`。由于 `100 < min_trx_id (300)`，判定可见，返回 `'张三'`。
- **T4 时刻**：事务 B 提交，`DB_TRX_ID=300` 成为已提交事务。
- **T5 时刻（第二次读）**：**RC 重新生成全新的 Read View 2**！
  - 此时事务 B 已提交，当前活跃列表 `m_ids=[]`，`min_trx_id = max_trx_id = 301`；
  - 检查最新版本 `DB_TRX_ID=300`。比对可见性判定算法：`DB_TRX_ID (300) < min_trx_id (301)`，命中**步骤 2**（创建当前 Read View 之前该事务已提交），直接判定为**可见**！返回 `'李四'`。
- **结论**：同一个事务 A 内，两次读取结果从 `'张三'` 变为 `'李四'`，发生了不可重复读。

#### 在 RR 模式下的推演：
- **T3 时刻（第一次读）**：生成 Read View 1，`m_ids=[300], min_trx_id=300, max_trx_id=301`。
  - 同样通过回滚指针读取旧版本，返回 `'张三'`。
- **T4 时刻**：事务 B 提交。
- **T5 时刻（第二次读）**：**RR 严格复用 T3 时刻生成的 Read View 1**！
  - 检查聚簇索引最新版本 `name='李四', DB_TRX_ID=300`；
  - 虽然事务 B 在物理上已提交，但在复用的 Read View 1 中，`300` 依然包含在历史 `m_ids=[300]` 活跃列表中，被判定为**不可见**；
  - 顺着 `DB_ROLL_PTR` 找到旧版本 `name='张三', DB_TRX_ID=100`，判定可见，依然返回 `'张三'`。
- **结论**：同一个事务 A 内，两次读取结果始终稳定为 `'张三'`，保证了可重复读。

---

### 6.2 为什么很多生产架构将隔离级别设置为 RC？

MySQL 官方默认隔离级别为 RR，但许多大型互联网公司会将全局隔离级别调整为 RC，主要考量是**并发吞吐与锁冲突的权衡**：
1. **行锁保护范围更窄**：在 RR 级别下，为了防范幻读，范围查询和更新会引入间隙锁（Gap Lock）和 Next-Key Lock，锁住记录之间的间隙，极易引发锁冲突和并发死锁；而在 RC 级别下，默认不使用间隙锁（仅用于外键检查与唯一性冲突），只锁住实际匹配的单行记录；
2. **配合行格式 binlog（binlog_format=ROW）**：历史版本 MySQL 依赖 RR 主要是为了防止 `STATEMENT` 格式 binlog 在主从复制时发生主从不一致；在普遍采用 `ROW` 格式 binlog 的现代架构下，RC 已经能保证主从绝对一致；
3. **更贴近业务直觉**：绝大多数业务系统希望读取到其他事务已经正式提交的最新数据，RC 的实时性更高。

---

### 6.3 快照读（Snapshot Read）与当前读（Current Read）的本质区别

在 InnoDB 中，读取操作在物理执行上被严格划分为两类：

| 类型 | 包含的常见 SQL 语句 | 物理读取行为 | 是否使用 MVCC |
|---|---|---|:---:|
| **快照读<br>(Snapshot Read)** | 普通 `SELECT`（不带 `FOR UPDATE` / `FOR SHARE`） | 基于 Read View 读取版本链上的历史快照数据，**不加任何锁** | **是** |
| **当前读<br>(Current Read)** | `SELECT ... FOR UPDATE`<br>`SELECT ... FOR SHARE`<br>`INSERT` / `UPDATE` / `DELETE` | 必须读取目标数据在聚簇索引上的**最新提交版本**，并加行排他锁或共享锁 | **否** |

DML 语句（`UPDATE`、`DELETE`）必须是当前读，因为如果修改基于旧版本执行，就会把其他事务刚提交的最新修改直接覆盖冲掉。

---

### 6.4 经典穿透实验：快照读转当前读的“幻读突变”

在 RR 级别下，一个非常经典的能观察到幻读现象的时序如下：

```sql
-- 初始状态：表 t 中只有 id=1 的数据
CREATE TABLE t (id INT PRIMARY KEY, val INT);
INSERT INTO t VALUES (1, 10);
```

| 时刻 | 事务 A | 事务 B |
|:---:|---|---|
| **T1** | `START TRANSACTION;` | `START TRANSACTION;` |
| **T2** | `SELECT * FROM t WHERE id = 5;`<br>*(结果为空，快照读生成 Read View)* | — |
| **T3** | — | `INSERT INTO t VALUES (5, 50);` |
| **T4** | — | `COMMIT;`<br>*(事务 B 插入并提交成功)* |
| **T5** | `UPDATE t SET val = 100 WHERE id = 5;`<br>*(影响行数: 1 行！当前读读到最新行并成功修改，DB_TRX_ID 改写为事务 A)* | — |
| **T6** | `SELECT * FROM t WHERE id = 5;`<br>*(查出: `(5, 100)`！**幻读突现**)* | — |
| **T7** | `COMMIT;` | — |

**为什么 T6 能查出来？**
在 T5 时刻，事务 A 执行了 `UPDATE`（属于当前读），它必须读到事务 B 刚刚插入并提交的 `id=5`。执行更新后，该行聚簇索引上的 `DB_TRX_ID` 被改写为事务 A 自己的 ID！
当事务 A 在 T6 再次发起普通的快照读时，根据 Read View 判定规则：`trx_id == creator_trx_id`（该版本由当前事务自身修改），直接判定为可见。原本“不存在”的记录，在事务 A 内部凭空出现了，这就是典型的幻读。

该实验表明：**MVCC 仅能保证单纯快照读的集合稳定性；一旦业务动作涉及当前读与写操作，防范幻读的职责便脱离 MVCC，转由间隙锁与 Next-Key Lock 等行级锁机制承担。**

## 知识回顾：业务事务与并发读取的因果闭环

1. **从多步操作到事务边界**：多步业务操作在自动提交模式下天然面临状态不一致风险，显式事务通过将状态转换封装为全有或全无的黑盒，守护了业务不变量；而事务边界必须以刚好闭合不变量为准则，严禁将外部不可回滚的网络 RPC 包裹在本地事务之中。
2. **业务一致性的分工底座**：ACID 中 C（一致性）是最终目标，AID 是底层手段。数据库通过 Schema 约束与事务保证物理底线，应用层则通过条件更新（Conditional Update）在行锁保护下校验业务前提，二者结合才能防止超卖与覆盖。
3. **并发读取的隔离演进**：并发交叉读写必然引发脏读、不可重复读与幻读。SQL 标准以 RU/RC/RR/Serializable 逐步收紧可见性，其实质是数据确定性与并发吞吐的权衡。
4. **MVCC 的读写解耦架构**：InnoDB 为聚簇索引增加隐藏列 `DB_TRX_ID` 与 `DB_ROLL_PTR`，配合 Undo Log 构成单向历史版本链。普通快照读无需任何行锁，直接通过 Read View 判定可见性，彻底解决了传统读写互斥阻塞。
5. **RC 与 RR 的视图时机差异**：RC 语句级生成 Read View 导致不可重复读，RR 事务级首次生成并全程复用实现可重复读与快照防幻读。
6. **快照读与当前读的防线交接**：快照读防幻读依托 MVCC 版本链回溯，而当前读（`SELECT FOR UPDATE`、`UPDATE`）必须触碰最新物理行，防幻读职责随即脱离 MVCC，完整交接给间隙锁（Gap Lock）与 Next-Key Lock。

## 🎯 面试怎么回答

### 为什么业务开发中必须使用事务？如果不使用会带来什么后果？

> [!TIP]
> 业务操作通常由多条 SQL 共同构成。MySQL 默认开启自动提交（`autocommit=1`），每条写语句都会即时生效。如果不使用显式事务，一旦系统在执行中途发生网络超时、程序异常或服务断电，就会停留在“部分语句生效、部分语句未执行”的半完成状态，直接破坏资金守恒或库存一致性等业务不变量。事务将这组操作绑定为一个执行单元，保证它们要么全部提交生效，要么全部回滚撤销。

### 事务边界应该怎样设计？为什么不能在事务里调用外部 RPC 接口？

> [!TIP]
> 事务边界遵循“最小化且足以闭合业务不变量”的原则。边界过小会导致中间状态泄漏引发状态不一致；边界过大会导致行锁持有时间过长、阻塞并发请求并耗尽数据库连接池。不能在本地事务中调用外部接口的原因有两点：一是网络延迟不可控，极易将短事务拉长为长事务，拖垮整库性能；二是本地事务回滚根本无法撤销已在外部生效的网络副作用（如第三方扣款或发短信）。标准做法是把外部调用后置于本地事务提交之后执行。

### 谈谈对 ACID 的理解，它们分别解决什么问题？

> [!TIP]
> ACID 是事务的四大语义契约：  
> 1. 原子性（A）：操作全做或全不做，防范中途崩溃导致的半完成状态；  
> 2. 一致性（C）：事务执行前后数据始终符合既定规则与不变量，它是最终的业务目标；  
> 3. 隔离性（I）：多个事务并发执行时彼此隔离，防范并发交叉读写带来的脏读与冲突；  
> 4. 持久性（D）：一旦 COMMIT 成功，修改永久落盘，系统发生断电或崩溃也不丢失修改。  
> 关系上，一致性（C）是最终目的，AID 则是数据库提供的核心技术手段。

### 业务一致性到底是数据库保证的，还是应用层代码保证的？

> [!TIP]
> 业务一致性由两者协同保证。数据库负责守住底层安全红线，提供原子性、隔离性以及 Schema 约束（主键唯一、非空、外键、CHECK）；但数据库无法理解高级业务规则，应用层必须负责合理划定事务边界、编排业务计算，并通过编写防御性的条件更新 SQL（如 `UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance >= 100`），将条件判定与写入合为一体，防止并发覆盖。

### 什么是 MVCC？它是怎样实现读写并发不阻塞的？

> [!TIP]
> MVCC（多版本并发控制）是 InnoDB 实现高并发读写的核心机制，通过让读写操作访问不同版本的数据来消除互斥阻塞。其底层依赖三大支柱：聚簇索引上的行隐藏列（记录修改事务 ID 的 `DB_TRX_ID` 和指向回滚段的 `DB_ROLL_PTR`）、由 Undo Log 串联起的单向旧版本链，以及执行快照读时生成的 Read View。写操作修改最新数据行并在 Undo Log 中追加历史版本，读操作不加锁，直接依据 Read View 沿版本链回溯对当前事务可见的历史版本，实现“读不阻塞写、写不阻塞读”。

### RC 和 RR 隔离级别在 MVCC 实现上有何根本不同？

> [!TIP]
> RC（读已提交）与 RR（可重复读）的根本区别在于 Read View 的生成与复用时机不同。在 RC 级别下，事务内每一次执行 SELECT（快照读）都会重新生成一个全新的 Read View，因此其他事务一旦提交修改，后续查询就能立即感知，导致不可重复读；而在 RR 级别下，通常只在事务内第一次执行快照读时生成 Read View，并在后续事务执行期间全程复用该视图，其他事务后续无论何时提交修改均被判定为不可见，从而实现了可重复读。

### MySQL 的 RR 级别彻底解决幻读了吗？请说明边界。

> [!TIP]
> 不能用一句话概括为彻底解决。RR 级别仅在普通快照读下通过复用 Read View 规避了幻读；但在当前读（如 `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`）场景下，查询必须读取聚簇索引上的最新提交数据，MVCC 此时不生效，防范幻读必须依赖间隙锁（Gap Lock）和 Next-Key Lock 锁住区间、阻止并发 INSERT。此外，若一个事务先执行普通 SELECT 查不到某行，并发事务插入并提交该行后，当前事务执行 UPDATE 修改到了该新行（将行的 `DB_TRX_ID` 变更为当前事务自身），随后再次执行普通 SELECT 就会查出该行，发生幻读突变。

## ⚠️ 易错点

> [!WARNING]
> **切勿在事务方法内部调用远程微服务 RPC 或耗时 HTTP。** 网络抖动会将本地事务直接拉长数秒甚至数十秒，引发严重的行锁竞争与应用连接池枯竭，且外部调用的副作用在本地事务回滚时无法被撤销。

> [!WARNING]
> **MySQL 执行 DDL 会触发隐式提交。** 在事务内部如果执行了 `CREATE TABLE`、`ALTER TABLE` 或 `TRUNCATE TABLE`，MySQL 会自动先提交当前活跃事务，后续即便显式调用 `ROLLBACK` 也无法撤销已经隐式提交的操作。

> [!WARNING]
> **单凭 `@Transactional` 无法解决高并发超卖。** 普通事务只保证原子提交，若先查询余额、在应用层做条件判断再更新，并发下仍会发生并发覆盖。必须结合条件更新（`WHERE balance >= 100`）或排他锁保障互斥。

> [!WARNING]
> **长事务会严重阻碍 Undo Log 历史版本回收。** 任何一个长期未提交的活跃事务，都会导致所有早于该事务的 Undo Log 版本无法被后台清理，进而引发回滚段膨胀并拖慢全库查询。

> [!WARNING]
> **MVCC 绝不是在内存或磁盘上对全库做物理拷贝快照。** 所谓“快照”只是由逻辑上的 Read View 和按需回溯的 Undo Log 版本链动态计算出来的，内存与物理开销极小。

> [!WARNING]
> **`START TRANSACTION` 之后并不会立刻生成 Read View。** 普通的 `START TRANSACTION` 只是开启了事务上下文，Read View 默认要等到该事务执行**第一条 SELECT 一致性读语句**时才会延迟生成。如果需要开启事务瞬间立即锁定 Read View，必须显式执行 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。

> [!WARNING]
> **当前读完全不走 MVCC 版本链。** `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 必须直接读取聚簇索引上的最新物理行并加行排他锁，绝不会顺着 Undo Log 回滚指针找历史版本。

<details>
<summary><strong>1. autocommit 变量的默认值是什么？它对单条写操作有什么影响？</strong></summary>

默认值为 1（ON）。这意味着每条独立的 DML 语句执行完毕后，数据库都会自动执行一次隐式的 `COMMIT`，修改立即对外部可见且无法自然撤销。

</details>

<details>
<summary><strong>2. 客户端在开启事务后、执行 COMMIT 前突然断电断网，数据库会怎样处理？</strong></summary>

数据库服务端检测到该客户端 TCP 连接断开或会话超时后，会自动为该未完成的活跃事务执行 `ROLLBACK` 操作，还原已做的修改并释放所持有的所有行锁。

</details>

<details>
<summary><strong>3. 为什么说“长事务是线上系统的隐形杀手”？</strong></summary>

长事务会长期持有修改行的排他锁，阻塞其他并发写入；它全程占用连接池中的物理连接，容易耗尽连接导致服务不可用；同时它会阻止 Undo Log 垃圾回收，使回滚段持续膨胀。

</details>

<details>
<summary><strong>4. 如果必须在业务中调用第三方支付接口，正确的事务编排方式是怎样的？</strong></summary>

本地数据库事务必须与外部网络调用解耦：本地数据更新要在事务中快速完成并立即提交释放资源；外部调用放在本地事务提交之后执行；若外部调用失败，通过后续异步重试或反向业务补偿处理。

</details>

<details>
<summary><strong>5. 什么是条件更新（Conditional Update）？它解决了什么并发问题？</strong></summary>

条件更新是指把业务前提直接写入更新语句的 `WHERE` 条件中（如 `UPDATE accounts SET balance = balance - 10 WHERE id = 1 AND balance >= 10`）。它将检查与写入合一，在行锁保护下防止并发请求同时读取同一旧值导致的并发覆盖与余额穿透。

</details>

<details>
<summary><strong>6. 聚簇索引中每行记录自带的两个最核心隐藏列是什么？它们各自有什么作用？</strong></summary>

分别是 `DB_TRX_ID` 和 `DB_ROLL_PTR`。`DB_TRX_ID` 记录最近一次修改该行记录的事务 ID；`DB_ROLL_PTR` 是回滚指针，指向 Undo Log 中该记录修改前的旧版本数据，用于串联版本链。

</details>

<details>
<summary><strong>7. Read View 结构体中包含哪四个最核心的属性？</strong></summary>

包含 `creator_trx_id`（创建视图的事务自身 ID）、`m_ids`（生成视图瞬间所有活跃未提交的事务 ID 列表）、`min_trx_id`（`m_ids` 中的最小值）、`max_trx_id`（系统即将分配给下一个事务的全局 ID）。

</details>

<details>
<summary><strong>8. 如果一条记录的 DB_TRX_ID 小于 Read View 的 min_trx_id，它对当前事务是否可见？为什么？</strong></summary>

可见。因为 `min_trx_id` 是生成 Read View 时所有尚未提交的活跃事务中的最小值，小于它的事务必然在生成该视图之前就已经完全提交，其修改理应可见。

</details>

<details>
<summary><strong>9. 为什么说 RC 隔离级别下无法实现可重复读？</strong></summary>

因为在 RC 级别下，事务内的每一条 SELECT 快照读都会重新构建一个全新的 Read View。一旦其他事务在两次 SELECT 之间提交了修改，后一个 Read View 就会把该事务判定为已提交，从而读取到修改后的新值。

</details>

<details>
<summary><strong>10. 在 RR 隔离级别下，一个事务执行普通 SELECT 看不到某新行，为什么执行 UPDATE 后再次 SELECT 就能看到了？</strong></summary>

因为 UPDATE 属于当前读，强制读取并更新了并发事务新插入且提交的行；更新操作将该行的 `DB_TRX_ID` 覆写为当前事务自身 ID；随后再次执行快照读时，命中 `trx_id == creator_trx_id`（自己修改的自己可见）规则，导致新记录在结果集中突然出现。

</details>

## 📌 本章最终要留下的六句话

1. **单语句自动提交各自为战，事务将多步操作绑定为全有或全无。**
2. **事务边界求小不求大，刚好闭合业务不变量即可，严禁包裹外部 RPC。**
3. **一致性是最终业务目标，原子性、隔离性与持久性是底层技术手段。**
4. **业务一致性需软硬兼施：底线靠约束与事务，并发防护靠条件更新。**
5. **RC 次次读次次建新视图，RR 首次读建视图用到终。**
6. **RR 快照读靠版本链防幻读，当前读必须靠 Next-Key 锁间隙。**
