# 19｜把数据库知识用在 AI 应用的数据模型中

[← 分片：确认单机边界之后再拆数据](18-分片与扩容.md) · [MySQL 目录](../README.md) · [Redis →](../../04-redis/README.md)

一个问答应用看起来只有“用户提问、系统回答”，但重新打开页面时，要找回会话；一次回答可能触发几次工具执行；文档更新后，还需要知道引用的是哪一版。

这些不是一类记录。我们沿一次使用过程，把**对象身份、当前状态、已发生的历史和外部结果**分开，检查前面的关系、约束、索引和事务怎样一起发挥作用，而不从二十张表的字段名单开始。

## 1. 用户看到的一个会话，至少有两种数据

会话记录描述这次长期交互属于谁、标题是什么；消息则不断追加。一条会话可能有上千条消息，但会话列表通常只显示标题和更新时间，不需要把所有消息读出来。

| 对象 | 主要回答什么 | 常见读取方式 |
|---|---|---|
| 会话 | 这是哪一次交互，属于哪个用户或团队 | 查询某用户最近的会话 |
| 消息 | 某次交互里说过什么 | 按会话和顺序读取消息 |

因此会话与消息适合表达成一对多关系。消息保存会话编号，查询历史时按这个编号筛选，再按明确顺序分页；会话列表则走另一条查询路径。是否拆开，不是因为 AI 有特殊数据库规则，而是两种记录的增长和访问方式确实不同。

多团队应用还要校验消息与会话属于同一团队。可以使用组合关系约束，同时由服务验证请求者有权访问；数据库里存在 `tenant_id` 列并不会自动完成身份授权。完整 SQL 放在[关系模型实验](../examples/experiments.md#lab-19)，不需要再用一遍长建表语句才能理解这个关系。

普通短文本直接存入关系库很自然。大型文件或工具结果可以在这里保存地址、大小与校验信息，将内容放在对象存储。取舍依据是访问、事务与恢复要求，不是“所有文本必须放外面”。

## 2. 一次执行的当前状态，与它已经做过什么分开

同一个会话可以发起多次执行。一次执行常称为 **Run**，例如从收到问题开始，检索资料、调用工具，最后生成回答。

Run 当前状态用于快速回答“完成了吗”；步骤或事件记录用于回答“为什么失败、失败前做过什么”。它们不是同一份不断覆盖的字段：

```text
Run 当前状态：失败
      │
      └─ 步骤历史：检索完成 → 工具调用超时 → 等待结果核对
```

仅有“失败”两个字无法判断是否应重跑工具；仅有很多日志，页面每次又不该从头推导当前状态。可以分别保存，再在必要的数据库事务中维护对应关系。

**日志也不等于恢复检查点。** 检查点需要足够信息让执行器安全继续，例如已确认的工具结果、下一步和程序所需状态；具体内容由执行系统定义。不要因为保存了开始和结束事件，就承诺能从任意步骤恢复。

状态变化可以通过条件更新保护。例如只有期望旧状态或版本仍然成立，才接受这次完成结果，避免迟到的“开始执行”把已经完成的状态盖回去。允许的转移来自业务规则，VARCHAR 只负责保存文字。

## 3. 工具和计费都要先定义“同一个动作”

系统调用外部服务发了一封邮件，但响应在网络中丢失。本地只记着“调用中”。这时既不能认定邮件没发出，也不能不检查就再发一封。

工具执行记录应帮助回答：对应哪个业务动作，请求内容是什么，是否经过必要批准，有没有外部回执，结果已确认还是未知。操作标识用于核对同一动作；外部系统是否接受这个标识进行防重，则是另一个必须明确的能力。

> ⚠️ 本地唯一键可以防止重复创建执行记录，却不能自动防止外部邮件发送两次。超时后应先按协议核对结果，不能把数据库记录的唯一性当成跨系统恰好执行一次。

使用量也需要类似区分。只把总 Token 数加上 1234，无法说明它来自哪次调用、是否重复统计。先保存可追踪的使用事件，再汇总日用量，能让每个总数找到依据。

但一次界面请求可能真的发起两次供应商调用。业务请求 ID、外部调用 ID 和本地账单事件 ID 各有含义；本地把两次归为一条展示记录，不会让供应商自动只收一次费用。唯一约束应保护明确定义的计费动作，而不是任意挑一个看起来唯一的字符串。

## 4. 文档、内容版本与处理任务有不同生命周期

文档 7 更新时，新内容是版本 2，但新索引还在构建。原来的版本 1 能继续服务，不能因为出现一条新版记录就当作全部替换完成。

| 记录角色 | 需要回答的问题 |
|---|---|
| 文档身份 | 属于哪个知识库、谁有权限管理 |
| 内容版本 | 具体哪份内容，引用和校验对应什么 |
| 处理任务 | 某次解析、切分与建索引成功了吗 |
| 激活版本 | 查询目前应该使用哪个已验证版本 |

如果新版本失败，可以保持原来的激活版本并处理失败原因。验证通过后，再修改数据库中的激活指针；检索请求也要带上正确版本。MySQL 能原子修改自己的记录，不会让所有外部检索节点同一时刻完成切换。

删除同样跨生命周期。先在权威访问边界阻止继续使用被删除或撤权的内容，再可靠地清理索引、缓存与对象存储；不能把异步清理完成以前的越权风险留给模型提示词处理。

这些数据适合由能表达关系、约束和事务的系统维护。本例选择 MySQL，缓存和检索表示按用途另行组织；这是架构选择，不是“其他数据库只能存临时数据”的品牌定律。

## 5. 从读写动作验收模型，而不是从表数验收

画完表以后，再沿用户动作走一遍：创建会话与追加消息需要什么，工具超时后凭什么判断，文档新版失败时读者会看到哪一版，删除能否追到全部相关数据。

每次检查都要找到具体依据：身份关系、唯一键、状态条件、事务边界或外部确认协议。某个事实只能靠“应该不会发生”解释，往往意味着模型或处理流程还有缺口。

无需提前创建所有审批、评测和记忆表。需要增加能力时，再从它保存什么事实、怎样访问、失败后怎样恢复推导。学习数据库的目标是能作这种判断，而不是复制一份看起来完整的产品 Schema。

## 6. MySQL 到这里负责到哪里

真实应用还会把部分高频读取放进 Redis，把向量检索放进 Vector DB，把大文件放进对象存储。MySQL 课程到这里先完成一个更基本的判断：**哪些数据是需要关系、约束、事务和长期恢复依据的权威事实。**

后续系统会同时保存数据库事实和缓存副本，但一个 InnoDB `COMMIT` 只能原子提交当前数据库事务，不能自动让 Redis、消息队列、向量索引或外部 API 同时成功。学完 Redis 以后，Backend 模块再系统处理缓存读写协作、双写失败窗口、可靠事件、重试与跨系统恢复。

> ⚠️ 这里提前建立的是责任边界，不要求此刻掌握 Redis 的 TTL、淘汰、缓存击穿或一致性方案。先把权威事实和本地事务学清，再讨论派生副本怎样失效与重建。

## 本章小结

会话与消息、当前状态与步骤历史、业务操作与外部结果、文档身份与版本，分别承担不同查询和正确性责任。表结构必须与实际读写和恢复协议配合，不能以表数证明完整；MySQL 事务只保证本地数据库边界，跨系统协作留到后续模块。

## 🎯 面试怎么回答

### 怎样设计 Agent 应用的数据表？

先沿使用过程区分会话、消息、Run、步骤和工具操作，再定义身份关系、唯一动作、状态更新与恢复所需信息。索引从访问方式推导，外部动作要独立确认，大内容按实际需要分层。

### 向量索引里已有内容，为什么还需要关系元数据？

仍需明确所属用户、权限、内容版本、处理结果和激活版本。检索表示负责找相关内容，权威记录负责生命周期与约束；两者通过稳定标识关联。

## ⚠️ 易错点

> ⚠️ 一条“调用中”记录不能证明外部动作没有完成，网络结果未知要单独处理。

> ⚠️ 记录了历史不代表具备任意续跑能力；恢复状态需由执行系统明确。

## 本章自测

<details>
<summary>1. 为什么会话列表不应该每次加载所有消息？</summary>

列表只需少量会话属性，消息是独立增长的历史；分开查询可让每条访问只拿需要的数据。

</details>

<details>
<summary>2. 版本 2 建索引失败，版本 1 应立即删除吗？</summary>

不能按“新版存在”判断。应依据激活、验证、保留与回退策略，避免把失败版本直接变成服务版本。

</details>

<details>
<summary>3. 工具记录唯一，为什么还不能证明邮件只发送一次？</summary>

唯一性只约束本地表；外部调用可能重复或结果未知，还需要外部幂等标识、结果核对等协议。

</details>
