# 13｜分页：先跳过，还是从上次的位置继续

[← 日志、提交与故障恢复](12-日志提交与恢复.md) · [MySQL 目录](../README.md) · [数据增长以后，怎样维护主键、索引和表结构 →](14-主键索引与表结构演进.md)

任务列表每页只显示两条，第一页很快，翻到很后面却越来越慢。直觉上，每次都只取两条，工作量不是应该相同吗？

问题在于，“最后返回两条”没有说明数据库为了找到它们，先经过了多少记录。本章把页码与位置两种方式放在同一份数据上比较。

## 1. 页码分页：先找到，再跳过

仍使用任务表。团队 10 的记录按创建时间降序、编号降序排列如下：

| 顺序 | id | created_at |
|---:|---:|---|
| 1 | 6 | 2026-09-04 09:00:00 |
| 2 | 4 | 2026-09-02 10:00:00 |
| 3 | 3 | 2026-09-02 09:00:00 |
| 4 | 2 | 2026-09-01 10:00:00 |
| 5 | 1 | 2026-09-01 09:00:00 |

每页两条，第二页需要跳过前两条：

<a id="sql-offset_page"></a>

<!-- mysql-example: offset_page -->
```sql
SELECT id, created_at FROM tasks
WHERE tenant_id = 10
ORDER BY created_at DESC, id DESC
LIMIT 2 OFFSET 2;
```

结果是 3、2。`OFFSET 2` 表示丢掉结果序列最前面的两条，不是按编号加二，也不是直接寻址到文件中的某个固定字节。

如果偏移量变成十万，数据库通常要沿执行路径找到并越过十万条前置结果，才能取出本页。途中还可能有过滤、排序和回表。**LIMIT 限制返回多少条，不保证只检查这么多条。** [LIMIT 的执行与优化](https://dev.mysql.com/doc/refman/9.7/en/limit-optimization.html)。

这里先问“为了返回这一页，做了哪些工作”，而不是只问“用了哪个索引”。合适索引能让扫描有序，但没有自动消除跳过十万条的成本。

## 2. 位置分页：从上一页最后一条继续

第一次查询仍取最前面的两条：

<a id="sql-keyset_first"></a>

<!-- mysql-example: keyset_first -->
```sql
SELECT id, created_at FROM tasks
WHERE tenant_id = 10
ORDER BY created_at DESC, id DESC
LIMIT 2;
```

得到 6、4。记住最后一条的完整排序位置：`(2026-09-02 10:00:00, 4)`。下一次不再说“跳过两条”，而是说“从这条后面继续”：

<a id="sql-keyset_second"></a>

<!-- mysql-example: keyset_second -->
```sql
SELECT id, created_at FROM tasks
WHERE tenant_id = 10
  AND (created_at < '2026-09-02 10:00:00'
       OR (created_at = '2026-09-02 10:00:00' AND id < 4))
ORDER BY created_at DESC, id DESC
LIMIT 2;
```

仍得到 3、2。条件看起来比 OFFSET 长，但只表达两个情况：

1. 创建时间更早，排在任务 4 后面。
2. 创建时间相同，但编号更小，也排在任务 4 后面。

这叫 **Keyset／Seek 分页**。在匹配的索引上，可以从已知排序键附近继续访问，而不是每页从头计数。团队内的这种访问，可考虑以 `(tenant_id, created_at, id)` 组织索引，再通过执行计划核对。

为什么还要带 `id`？因为创建时间可能相同。如果只保存时间，下一页使用“小于这个时间”会跳过同一时刻尚未返回的记录；使用“小于等于”又可能重复。唯一编号让边界足够明确。

接口中的 `next_cursor` 通常只是对这个位置和必要查询条件的编码，不是另一种数据库索引。它应该绑定本次查询的筛选条件，服务端仍要重新检查权限。

## 3. 根据浏览方式选择，而不是消灭 OFFSET

| 使用方式 | 更自然的选择 | 需要接受的代价 |
|---|---|---|
| 小表、浅页码、低频后台 | OFFSET | 越深的页通常越贵 |
| 消息历史、连续向后浏览 | Keyset | 不便直接跳到任意页码 |
| 必须导出某一时刻的完整数据 | 固定数据集或明确快照，再设计分批读取 | 需要额外管理一致性与资源占用 |

**稳定排序和固定数据版本不是一回事。** Keyset 能明确下一页的起点，但两次请求之间，记录仍可能删除，排序字段也可能被修改。它不自动保证整段浏览看到同一个历史世界。

<details>
<summary>仍要保留页码时：怎样减少跳过期间的回表</summary>

若原路径通过二级索引读取大量记录，并为每条取出索引没有的正文，可以先在窄索引里确定本页编号，再只取最终几条的完整内容。这叫延迟回表。

它节省的是无用的整行读取，不是 OFFSET 的计数工作。按聚簇主键扫描整行与按二级索引大量回表又不同，不能给任何分页 SQL 外包一层 JOIN 就宣称变快。

</details>

## 4. 总数也是查询，不是附送信息

页面同时显示“共多少条”，通常还要执行一次精确统计。InnoDB 需要结合事务可见性和查询条件计算，不能对任何筛选都直接读取一个现成准确数字。[COUNT 的行为](https://dev.mysql.com/doc/refman/9.7/en/aggregate-functions.html#function_count)。

业务只需要知道是否还有下一页时，可以多取一条：页面需要 20 条就查最多 21 条，有第 21 条便说明还有后续。是否需要精确总数，是产品要求与数据库成本之间的选择。

同样，分页性能的验证不只测第一页。应比较浅页与深页，核对返回记录相同、扫描和排序工作怎样变化，再观察延迟。几条教学数据适合判断结果，不适合宣称线上性能提升了某个比例。

---

## 本章小结

分页先确定结果顺序，再选择按数量跳过还是按排序位置继续。Keyset 减少不断增长的跳过工作，但不自动冻结数据；精确总数、随机跳页和完整导出应各自说明要求。

## 🎯 面试怎么回答

### 为什么大 OFFSET 慢，怎样优化？

它必须找到并跳过大量前置结果，LIMIT 只限制最终返回。先让过滤和排序匹配索引，再根据业务选择延迟回表或 Keyset。前者减少无用整行读取，后者改变翻页方式；两者都要核对结果与实际访问成本。

## ⚠️ 易错点

> ⚠️ 游标里有时间还不够，排序存在并列时需要保存足以唯一定位边界的键。

> ⚠️ 编码后的游标不是权限凭证，也不是一致性快照。

## 本章自测

<details>
<summary>1. 按本章顺序，第二页为什么是 3、2？</summary>

第一页取走 6、4。OFFSET 跳过前两条；Keyset 选择排在任务 4 后面的记录，两者在未发生数据修改时都得到 3、2。

</details>

<details>
<summary>2. 只把查询改成 Keyset，能保证浏览期间所有数据都不变吗？</summary>

不能。它定义继续读取的位置，不冻结记录；跨请求的一致版本需要另外设计。

</details>

<details>
<summary>3. 延迟回表与 Keyset 分别减少什么？</summary>

延迟回表减少跳过阶段不必要的完整行读取；Keyset 避免每页从起点跳过全部前页。

</details>
