# 03｜一条 SQL 是怎样执行的

> [!TIP]
> **🎯 本章目标**
>
> 建立从 SQL 文本到物理执行的完整运行心智：知道 MySQL Server 怎样理解 SQL、Optimizer 为什么需要选择执行路径、Execution Plan 的本质是什么、Executor 和 InnoDB 分别扮演什么角色；深刻理解为什么同一句 SQL 在不同数据规模和分布下会产生不同的执行计划；并建立 `INSERT / UPDATE` 等写操作穿透到存储引擎的高层执行模型。

## 0. SQL 已经写对了，为什么还需要关心“怎么执行”？

考虑这条高频业务查询：

```sql
SELECT id, title
FROM tasks
WHERE tenant_id = 10
  AND status = 'pending'
ORDER BY created_at DESC
LIMIT 20;
```

从逻辑业务语义看，它已经足够明确：“提取团队 10 的待办任务，按时间倒序排列，取前 20 条”。

但 MySQL 必须在物理执行层面回答一系列严苛问题：从哪里开始检索？要不要走索引，有多个索引时选哪个？预计要扫描多少候选数据？排序能不能借用索引已有顺序，还是需要内存临时排序？多表关联时先驱动哪张表？

这些物理决策不会改变 SQL **要什么结果**，却直接决定了数据库为了交付结果需要付出多少 I/O 与 CPU 代价。数据量只有几十行时全表扫毫无痛感，而面对数千万数据时，不同执行方案的耗时可能相差数万倍。

> [!IMPORTANT]
> **💡 核心认知：SQL 负责声明“要什么”，MySQL 负责推导“具体怎么做”。逻辑语义完全相同，物理执行路径可以天差地别。**

## 1. 一条 SQL 从进入 MySQL Server 到返回结果经历什么？

一条 SQL 发送给 MySQL 后，在物理上经历“Server 层解析验证 → 优化器生成执行计划 → 执行器步进调度 → 存储引擎存取数据”四个核心阶段。Server 层负责统一理解语法并决策最优路径，真正的底层磁盘与内存数据交互则全部委托给存储引擎（如 InnoDB）完成。

```text
SQL 文本 → 语法解析与对象校验 → 优化器 (Optimizer) 生成执行计划 (Plan) → 执行器 (Executor) 调度推进 → 存储引擎 (InnoDB) 存取数据 → 客户端
```

---

### 1.1 语法解析与对象校验：Server 正确理解 SQL

当 MySQL 收到 `SELECT id, title FROM tasks WHERE id = 101` 时：
1. **词法与语法分析（Lexer & Parser）**：将字符流构造成抽象语法树（AST）。如果将 `SELECT` 错写成 `SELEC`，解析阶段直接拦截并抛出语法错误，绝不会触碰底层数据表。
2. **语义与对象校验（Semantic Checker）**：校验语法树中的库、表、列是否存在，当前连接是否具备访问权限。如果表里没有该列，则报列不存在错误。

---

### 1.2 优化器（Optimizer）与执行计划（Execution Plan）

当语法与对象合法后，Optimizer 介入工作。对于 `WHERE tenant_id = 10`，若表上存在不同单列或联合索引，优化器面临多重抉择：扫描全表再由 Server 过滤？还是通过索引树定位候选主键后再回表？若有多表关联，先扫哪个表作为驱动表？

**优化器的职责，是在保证结果集绝对正确的前提下，找出预估物理开销最小的 Execution Plan（执行计划）。**

**Execution Plan** 即为优化器最终拍板的方案蓝图，它清晰定义了：各个表的访问顺序（Join Order）、每张表采用的访问路径（Access Path）、使用的具体索引、预估扫描的行数，以及是否需要引入额外的临时表或文件排序（Using filesort）。

---

### 1.3 执行器（Executor）与存储引擎（InnoDB）协作

计划敲定后，交由 **Executor** 推进。Executor 不重新做路径决策，它严格按计划调用存储引擎的标准接口（Handler API）逐行获取数据，在内存中完成最终的行过滤、投影和排序流转，最后将结果行组装后流式返回给客户端。

> [!TIP]
> **EXPLAIN 工具：** 虽无法直接窥探内存中的抽象计划树，但可通过在语句前加上 `EXPLAIN`（如 `EXPLAIN SELECT ...`）把优化器选定的访问类型（`type`）、命中索引（`key`）、预估行数（`rows`）与额外信息（`Extra`）输出为结构化报表。

## 2. 同一条 SQL 为什么可能有不同执行方法？

SQL 属于声明式语言，只描述期望的结果集，不绑死具体的物理执行步骤。MySQL 优化器以统计信息（Statistics）为输入，利用成本模型（Cost Model）在单表访问路径（Access Path，全表扫还是走索引）与多表连接顺序（Join Order，哪个表驱动哪个表）的众多合法组合中，动态推导并挑选预估总代价最小的执行计划。

---

### 2.1 Access Path（访问路径）：单表怎么拿数据？

Access Path 描述在具体单表上检索记录的底层方式：
- **全表扫描（Table Scan / ALL）**：从头到尾按页读取整张表的所有记录；
- **主键/唯一索引点查（const / eq_ref）**：单条索引树寻址，效率最高；
- **非唯一索引等值查找（ref）**：定位特定键值的连续叶子节点；
- **索引范围扫描（range）**：在索引树定位起点后沿叶子链表连续读取。

“表上有索引”仅仅意味着为优化器增加了一条可选的 Access Path，并不代表它一定会被采纳。若满足条件的记录占了整表的 80%，走二级索引再回表造成的随机读开销往往远高于直接顺序扫描整表。

---

### 2.2 Join Order（关联顺序）：多表先处理谁？

在多表关联查询中，优化器拥有调整关联顺序的自主权。假设 A 表 100 行，B 表 1,000,000 行，若先查 A 表（以小表驱动大表），每次仅需用 A 表结果去 B 表索引定位，总代价极小；若反向以 B 表全表驱动，中间结果会剧烈膨胀。因此，`FROM A JOIN B` 并不代表物理上一定先读 A 后读 B。

---

### 2.3 统计信息（Statistics）、选择性（Selectivity）与基数（Cardinality）

优化器不能把每种候选方案都实机跑一遍，它依赖存储引擎定期采样的统计信息做静态推演：
- **基数估算（Cardinality Estimate）**：预估某个索引上有多少不重复的有效取值。表级基数默认假设数据均匀分布。
- **选择性（Selectivity）**：某个条件能将全表候选集过滤压缩的比例。通常高选择性条件（如精确过滤到几十行）更倾向于走索引。
- **数据倾斜（Data Skew）的影响**：若 `status` 字段 90% 是 `done`，10% 是 `pending`，极少数是 `failed`。针对具体的查询常量，优化器会借助索引区间探测（Index Dive）或列直方图（Histogram）探测真实的倾斜比例；因此 `WHERE status = 'failed'` 极可能走索引，而 `WHERE status = 'done'` 则大概率直接走全表扫描。

---

### 2.4 成本模型（Cost Model）与计划漂移

优化器将 I/O 读取成本与 CPU 计算成本代入公式，折算出一个无量纲的评价值——**Cost**。候选方案中 Cost 最低者胜出。

> [!WARNING]
> **Cost 是内部比较基准，绝非毫秒执行时间！**  
> `Cost = 25` 不代表耗时 25ms。由于统计信息是抽样维护的，若真实数据产生严重倾斜或长期未更新统计信息，优化器便可能依据错误的基数估算选出低效计划（即发生“计划选错”或“计划漂移”）。

---

## 3. `INSERT / UPDATE` 等写语句怎样进入 InnoDB？

写语句（INSERT / UPDATE / DELETE）同样必须经历完整的 Server 解析与优化流程，其关键区别在于执行器最终分派给存储引擎的是数据修改指令。UPDATE 与 DELETE 必须先借助优化器确定的访问路径定位目标行，而 INSERT 则必须同步承担向所有二级索引插入新节点的写放大开销。

```text
写 SQL 文本 → Server 语法解析与约束校验 → 优化器确定目标行定位路径 → 执行器调度写入 → InnoDB 修改记录与维护索引
```

---

### 3.1 写入链路与索引维护代价

- **`INSERT`**：Server 解析目标表列及值，校验类型与非空约束后将新行递交引擎。InnoDB 不仅要向聚簇索引的数据页写入主键记录，还必须**同步向这张表所有的二级索引树插入新索引项**。表上索引越多，单次 INSERT 的写放大与随机 I/O 开销就越明显。
- **`UPDATE / DELETE`**：更新与删除是“查”与“改”的结合体。引擎必须首先借助 Access Path 定位到目标行（这一步同样依赖执行计划！），随后进行字段修改。若更新修改了索引列（如把任务状态从 `pending` 改为 `done`），不仅数据页本身要改，该索引树对应的旧节点需要被标记删除并在新位置插入新节点。

---

### 3.2 写路径核心机制分工

一次完整的物理写操作在 InnoDB 内部由四项底层机制协同完成：
- **Page & B+Tree**：数据与索引在物理页中如何排列与分裂；
- **Lock & MVCC**：并发事务读写时如何保证互斥与可见性；
- **Undo Log**：记录历史反向版本，用于事务回滚与一致性非锁定读；
- **Redo Log (WAL)**：先行记录物理重做日志，保障掉电宕机后的数据零丢失。

---

## 本章总结

SQL 语言的声明式特征决定了逻辑阅读顺序不等于底层物理执行步骤。MySQL Server 承担了语法解析、对象校验和执行器调度的职责；优化器通过统计信息预估各种 Access Path 与 Join Order 的综合成本，拍板输出 Execution Plan。

执行计划并非一成不变，数据量级、键值分布和统计信息状态都会动态改写优化器的成本结论。写语句在执行层同样需要经历解析与目标行检索，并且写操作的物理开销与当前表的索引数量强相关。建立这套端到端的执行模型，是后续深入索引调优与慢查询排查的必要基石。

## 🎯 面试怎么回答

### 一条 SQL 从客户端发送到最终返回，经历了哪些主要阶段？

> [!TIP]
> 1. 客户端通过连接器建立会话；  
> 2. MySQL Server 进行语法分析生成语法树，并通过语义校验验证表、列权限与有效性；  
> 3. 优化器基于成本模型评估不同的访问路径与连接顺序，生成最优执行计划；  
> 4. 执行器按计划分步调用存储引擎 API 获取数据；  
> 5. InnoDB 引擎在 Buffer Pool 或磁盘中完成数据页存取，将数据回传给执行器并最终流式交付给客户端。

### 优化器（Optimizer）的主要职责是什么？

> [!TIP]
> 优化器的核心职责是在逻辑结果不变的前提下，推导并生成物理代价最小的执行计划。它负责决策单表的访问路径（走全表还是特定索引）、多表关联的驱动顺序（Join Order）、排序操作的实现方式（借助索引还是使用临时表排序 filesort），是性能表现的核心中枢。

### 为什么同一句 SQL 在不同环境或不同数据量下，执行计划会发生变化？

> [!TIP]
> 执行计划取决于优化器对物理成本的动态估算。表的总数据量、数据倾斜程度、索引是否存在、统计信息抽样的新鲜度都会改变候选方案的 Cost 评价值。因此同一语句在测试库和小表时可能走索引，随着生产库数据膨胀或分布改变，可能自动切换为全表扫描。

### 优化器评估出的 Cost 具体含义是什么？

> [!TIP]
> Cost 是优化器成本模型给出的内部无量纲衡量指标，综合了内存/磁盘 I/O 块读取量与 CPU 比较过滤开销。Cost 仅供不同候选计划横向比对优劣，绝对不等于执行耗时（毫秒数），也不能直接代表磁盘硬件吞吐。

### 为什么对表建立过多索引会拖慢写性能？

> [!TIP]
> 每次执行 `INSERT` 时，除了在聚簇索引插入数据行，引擎还必须同步向每一个二级索引的 B+ 树写入新叶子记录；执行 `UPDATE` 若修改了索引关联字段，也需要同步维护对应索引树节点的删除与重排。过多的索引会导致显著的写放大与离散 I/O 开销。

## ⚠️ 易错点

> [!WARNING]
> **SQL 书写顺序绝非执行顺序。** 优化器有权依据成本模型自由调整连接次序与过滤位置。

> [!WARNING]
> **有索引并不等于一定会使用索引。** 若条件过滤出的数据比例过高，二级索引回表开销远超直接顺序扫描，优化器会主动弃用索引。

> [!WARNING]
> **Cost 不是执行耗时。** 切勿将 `cost = 100` 视为 100 毫秒，它是基于统计信息的数学计算估值。

> [!WARNING]
> **低基数（枚举值少）并不绝对等于无法走索引。** 若数据存在剧烈倾斜（如 99% 为成功，1% 为失败），查询小概率的失败样本依然能高效触发索引。

> [!WARNING]
> **统计信息失真会导致执行计划严重劣化。** 生产环境大批量导数或删数后若未及时刷新统计信息，优化器可能做出严重错误的执行决策。

> [!WARNING]
> **写操作同样存在执行计划。** `UPDATE` 和 `DELETE` 的定位阶段同样受到优化器控制，缺乏合适索引会导致全表行锁或全表扫描。

<summary><strong>1. SQL 语句中的语法错误在哪个阶段被抛出？</strong></summary>

在 Server 的解析（Parser）阶段，直接在构建语法树时报错阻断，未进入优化器或引擎。

</details>

<details>
<summary><strong>2. 优化器、执行计划、执行器三者的逻辑递进关系是什么？</strong></summary>

优化器做出决策并产出执行计划；执行计划是指导方案蓝图；执行器负责执行调度并调用引擎获取数据。

</details>

<details>
<summary><strong>3. 什么是 Access Path？常见类型有哪些？</strong></summary>

访问路径是指单表提取候选数据的方法。常见有全表扫描（ALL）、唯一索引点查（const/eq_ref）、非唯一索引等值匹配（ref）和范围扫描（range）。

</details>

<details>
<summary><strong>4. 为什么驱动表通常选小表而不是大表？</strong></summary>

以小表作为外层循环的驱动表，能大幅压缩总关联判定轮次，借助被驱动表的高效索引可以快速收敛中间结果集。

</details>

<details>
<summary><strong>5. 统计信息（Statistics）失真会有什么后果？</strong></summary>

会导致基数与过滤性计算偏差，进而使成本模型选出代价高昂的劣质执行计划，引发慢查询甚至服务打满。

</details>

<details>
<summary><strong>6. 执行器是否会私自更改执行计划里选定的索引？</strong></summary>

不会。执行器严格遵循优化器生成的计划步进执行，没有路径选型的决策权。

</details>

<details>
<summary><strong>7. 修改非索引列与修改索引列，在物理层有何成本差异？</strong></summary>

修改非索引列仅涉及数据页中该行记录的就地修改或重写；修改索引列则必须同步调整所有受影响索引树的键值顺序与叶子节点，带来额外的重构与 I/O 开销。

</details>

<details>
<summary><strong>8. 为什么不能根据 SQL 文本推断固定耗时？</strong></summary>

执行耗时受数据规模、分布、缓存命中率、并发锁竞争与执行计划动态选择综合影响，文本层面仅表达逻辑语义。

</details>

<details>
<summary><strong>9. EXPLAIN 的核心定位是什么？</strong></summary>

它是观察优化器所选定执行计划的窗口工具，用于确认实际选用的索引、连接机制与预估行数。

</details>

<details>
<summary><strong>10. 写操作在进入存储引擎后，主要涉及哪几大物理子机制？</strong></summary>

数据页与 B+ 树的物理写入与分裂；行级锁与并发控制；Undo Log 版本构建；Redo Log 预写日志保障持久性。

</details>

## 📌 本章最终要留下的六句话

1. **SQL 描述“要什么结果”，Execution Plan 描述“MySQL 准备怎样在物理上达成”。**
2. **Server 层负责解析校验并协调执行，优化器负责制定方案，InnoDB 负责底层真实页操作。**
3. **Access Path（访问路径）与 Join Order（关联顺序）是执行计划的两大支柱。**
4. **统计信息是优化器推导成本的依据，失真的统计信息会导致计划选错。**
5. **Cost 是方案横向对比的综合开销估值，切勿与现实执行耗时画等号。**
6. **写操作伴随查询定位开销，表上多余的二级索引是写入性能劣化的直接放大器。**
