> 
> 掌握海量数据增长与业务持续演进下的数据库稳定性架构：深刻理解数据规模扩张如何恶化 Working Set（工作集）、缓存命中率、宽行存储与维护成本；建立主键选型容量防线（`INT` vs `BIGINT`）与基于不可见索引（Invisible Index）的安全退役生命周期；深入掌握现代 Online DDL（`INSTANT`、`INPLACE`、`COPY`）的底层原理与兼容性演进模式；掌握千万级大表的分批游标读写、反压控制（Backpressure）与断点 Checkpoint 续跑机制；掌握不停机数据迁移与回填的核心契约：全量快照 + 增量追赶（Snapshot + Incremental Catch-up）、校验对账、灰度切流（Cutover）与回退窗口。

## 0. 为什么最初“完美”的数据库设计，在海量数据与持续演进下终将失效？

在业务启动之初，任何技术选型往往都运行得非常顺畅：

```sql
CREATE TABLE orders (
    id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    amount DECIMAL(10, 2) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

表内只有几万行数据时，整张表的所有数据与索引都能完整常驻在内存 Buffer Pool 中。所有的点查与范围查询都能在 1 毫秒内响应；执行一次 `ALTER TABLE orders ADD COLUMN status TINYINT;` 仅需几毫秒；即使直接执行 `DELETE FROM orders WHERE created_at < '2025-01-01'` 进行批量清理，也不会对主从复制造成任何可见影响。系统处于一种“静态最优”的假象之中。

然而，随着业务高速增长与持续迭代，数据量突破千万乃至数亿级别，原有的设计假设被逐一击穿：
1. **容量红线隐蔽逼近**：自增 `INT UNSIGNED` 悄然逼近 42.9 亿上限，一旦溢出就会引发主键冲突，导致线上所有新插入全部报错拒绝；
2. **元数据锁级联排队**：在活跃大表上执行一个简单的 DDL，遭遇未提交的慢事务就会陷入元数据锁（MDL）写等待，瞬间级联阻塞后续所有并发读写，在数秒内耗尽连接池；
3. **批处理击穿日志与主从**：执行单次大事务批量删除或深分页 `LIMIT offset, size`，会引发严重的脏页刷盘反压，并造成从库产生长达数十分钟的复制延迟；
4. **停机维护不再可行**：业务要求 7×24 小时不间断高可用，已不可能申请长达数小时的停机维护窗口来进行物理重建或数据迁移。

面对规模膨胀与持续迭代的双重挤压，系统必须具备在运行中自适应平滑演进的能力：
- 怎样为主键与索引建立全生命周期监控，在容量耗尽或写放大失控前完成平滑升级与安全退役？
- 在千万级活跃表上，怎样根据 DDL 算法特性执行在线变更（Online DDL）并防范 MDL 锁阻塞？
- 面对海量历史数据的归档与清洗，怎样基于游标分页、动态反压与 Checkpoint 实现受控断点续跑？
- 当单表与单库逼近物理极限必须分拆时，怎样通过双写、追平与校验对账实现不停机无损迁移与安全回退？

> [!IMPORTANT]
> **💡 核心认知：静态的最优设计终将被数据增长与业务演进击穿。工程师的核心职责不是设计一张“永远不需要改动的表”，而是构建一套“能够安全、无损、不停机持续演进”的工程防御体系——让表结构在线无锁变更、索引安全验证退役、批处理受控反压限流，并在系统跨越单机极限时平滑完成不停机迁移与秒级回退。**

## 1. 为什么表刚建时很快，数据增长后却越来越难维护？

数据增长导致系统性能恶化与维护困难，其物理根因不在于“行数本身”，而在于**工作集（Working Set）超出了内存缓冲池（Buffer Pool）承载上限导致冷热数据频繁换入换出、单行膨胀（宽行）恶化了聚簇索引扇出、统计信息失真导致执行计划偏斜、以及大表运维操作（如 DDL、备份与从库复制）在物理锁与 I/O 维度的级联阻塞**。

---

### 1.1 工作集（Working Set）与 Buffer Pool 缓存击穿

在数据库运行中，并不是所有数据都具有同等的访问频率：
- **工作集（Working Set）**：指在特定业务时间窗口内，频繁被读取或修改的“活跃数据页集合”。

在数据量较小阶段（例如整张表仅 1GB），操作系统的物理内存与 MySQL 的 Buffer Pool（例如 16GB）足以容纳整张表的所有索引与数据页。所有查询与更新几乎全部在内存中闭环，磁盘 I/O 仅体现为顺序写 Redo Log，平均耗时仅为微秒级。

```text
[初期：数据体量 < Buffer Pool]
数据总量: 1GB  ───> 全部常驻 16GB Buffer Pool (100% 内存命中，零磁盘随机读)

[后期：数据体量 >> Buffer Pool]
数据总量: 100GB ──> 工作集突破 16GB 上限 (LRU 频繁换入换出，剧烈磁盘随机读)
```

当表规模持续膨胀至 100GB 以上时，工作集往往随之扩大并击穿 Buffer Pool 容量上限。InnoDB 内部的 LRU（Least Recently Used）淘汰链表开始剧烈抖动：每一次随机查询或批处理扫描，都会将内存中宝贵的热点数据页淘汰出局，并将磁盘上的冷页加载进内存。原本纯内存的纳秒/微秒级响应，退化为受制于磁盘 I/O 延迟（毫秒级）的物理寻道，并发读写吞吐瞬间跌落数个数量级。

---

### 1.2 分布偏斜（Distribution Shift）与统计信息失真

在表体量膨胀的过程中，业务数据的物理分布往往发生实质性漂移（Distribution Shift）：例如历史订单的状态均为“已完成”，而最近新增的大量活跃订单集中在“待支付”或“处理中”。

MySQL 优化器依赖基于采样的统计信息（存储在 `mysql.innodb_table_stats` 与 `mysql.innodb_index_stats` 中）计算成本模型：
- 当单表达到数千万行时，默认的非持久化或低采样率统计（如默认采样 20 个叶子页）极易产生估算失真；
- 统计信息的偏斜会导致优化器严重低估扫描行数，将低选择性的二级索引误判为最优路径，或者放弃索引走全表扫描，导致执行计划突然劣化（Plan Regression）。

---

### 1.3 宽行（Wide Row）膨胀与冷热混存

业务迭代的另一个隐形代价是表的物理“横向膨胀”（宽行设计）：
- 为了配合敏捷开发，开发者不断向核心业务表添加新字段（如 `remark VARCHAR(2000)`、`ext_json TEXT`）；
- 单行记录的物理字节数急剧扩大，导致单个 16KB 数据页能够容纳的物理行数锐减（从原本的数百行降至十几行甚至几行）；
- 当超长字段超过行内存储阈值时，数据还会被溢出存储到独立的 Off-page（溢出页）中。

```text
[窄行聚簇索引页]  16KB 包含 100 行记录  ──> 扫描 1000 行仅需读取 10 个数据页
[宽行聚簇索引页]  16KB 包含 5 行记录    ──> 扫描 1000 行必须读取 200 个数据页 (I/O 放大 20 倍)
```

更严重的问题在于**冷热数据物理混存**：如果核心表的 95% 数据是超过 1 年不再变更的历史冷数据，而高频访问的仅是最近 7 天的热数据，由于它们交织存储在同一个 B+Tree 表空间文件中，数据库无法在物理层面将冷数据卸载至低成本存储介质，导致全量备份、索引重建与系统扩容的硬件成本居高不下。

---

### 1.4 维护成本的物理质变

数据规模从万级跃升到千万级以上时，日常数据库运维操作会发生物理维度的质变：

| 运维操作 | 小表表现（< 10 万行） | 千万级大表表现（> 1000 万行） | 核心物理瓶颈 |
|---|---|---|---|
| **添加二级索引** | 毫秒级返回，无感完成 | 耗时数十分钟甚至数小时 | 产生大量排序与索引树重组 I/O，可能耗尽 `tmpdir` |
| **全表逻辑备份** | 数秒完成，无锁平滑导出 | 耗时数小时，导出大文本引发内存抖动 | 导出大表持续占据只读快照，Undo 版本链积压严重 |
| **主从数据复制** | 从库实时追平，零延迟 | 一旦主库执行大更新，从库延迟飙升数百秒 | 从库单线程或并行调度遇到大事务回放串行化 |
| **实例故障恢复** | 秒级完成 Crash Recovery | 扫描超大表空间，数据页恢复耗时拉长 | 脏页基数庞大，双写缓冲与 Redo 重演周期变长 |

## 2. 主键和索引也有生命周期吗？

主键和索引具有明确的工程生命周期，必须随数据规模演进而动态治理：**主键的核心在于容量防线与物理聚簇效率（`INT` 溢出导致写瘫痪，乱序 UUID 引发严重页分裂；高并发通常选用有序递增的 Snowflake ID 或 `BIGINT AUTO_INCREMENT`）；二级索引的核心在于“空间、写放大与查询收益”的长期权衡，必须建立“准入评估 -> 生产灰度 -> 设为不可见索引（Invisible Index）验证安全 -> 最终物理 DROP”的完整生命周期管理链条**。

---

### 2.1 主键容量红线与选型代价

主键是 InnoDB 聚簇索引的物理组织骨架。在表设计初期，最容易被低估的隐患是整数类型的取值上限：

- **`INT` 类型容量上限**：有符号 `INT` 上限为 $2^{31}-1 \approx 21.47$ 亿；无符号 `INT UNSIGNED` 上限为 $2^{32}-1 \approx 42.94$ 亿；
- **自增溢出事故机制**：当表数据持续写入，自增序列达到上限最大值后，后续的 `INSERT` 语句将无法分配新 ID，MySQL 会直接抛出主键重复报错：
  ```sql
  ERROR 1062 (23000): Duplicate entry '4294967295' for key 'PRIMARY'
  ```
  此时该表的所有写入操作全部瘫痪。而在数千万或上亿行的大表上紧急执行 `ALTER TABLE tbl MODIFY id BIGINT` 需要锁表或长时间重建整表，属于重大的生产事故。因此，**在一切预期存在中长期数据增长的核心业务表中，主键 ID 必须在建表阶段直接声明为 `BIGINT UNSIGNED`（上限达 $1.84 \times 10^{19}$）**。

#### 主键选型物理对比

```text
[BIGINT 自增 / 雪花 ID：单向单调递增]
物理叶子页：[ 1 ] -> [ 2 ] -> [ 3 ] -> [ 4 ] -> [ 5 ] ──> 顺序追加，页面填充率高达 15/16，零页分裂

[UUID v4：无序随机字符串]
物理叶子页：[ 37a ] <- 插入 [ 12b ] (触发中途挪动与 50% 页分裂) -> [ 89f ] ──> 碎片化严重，内存浪费
```

| 主键类型 | 空间占用 | 写入聚簇友好度 | 二级索引附带成本 | 适用场景 |
|---|:---:|:---:|:---:|---|
| **BIGINT AUTO_INCREMENT** | 8 字节 | **极高**。严格单调自增，页面顺序追加填充，零页分裂 | **低**。二级索引叶子节点仅额外存储 8 字节 | 单库单表、自增序列足以满足的单体服务 |
| **雪花算法 (Snowflake ID)** | 8 字节 (BIGINT) | **极高**。趋势递增（时间戳高位），写入聚簇性好 | **低**。同为 8 字节整型 | 分布式微服务架构、需要客户端预生成 ID 的系统 |
| **UUID v4 (随机无序)** | 36 字符 / 16 字节 | **极差**。完全随机散列，高频触发 B+Tree 页分裂 | **极高**。二级索引叶子节点膨胀，缓存利用率减半 | 严禁作为高并发写入大表的聚簇主键 |

---

### 2.2 索引膨胀的物理代价：写入放大与缓冲池污染

部分团队存在“只要查询可能用到，就建一个索引”的误区。随着数据体量增长，索引过多会带来沉重的物理反噬：

1. **写入放大（Write Amplification）**：
   每张表上增加一个二级索引，每次执行 `INSERT` 时，存储引擎都必须额外在另一棵 B+Tree 的叶子节点中写入一条记录；每次执行 `UPDATE` 时，若修改了索引列，必须在旧索引树中标记删除旧版本并插入新版本。一个拥有 6 个二级索引的表，一次逻辑插入等同于 7 次物理树结构的修改；
2. **Buffer Pool 内存污染**：
   二级索引在物理磁盘上占用独立表空间。当无用或低频索引过多时，后台更新和随机查询会把大量冷索引页载入 Buffer Pool，严重挤占核心热点数据页的常驻空间；
3. **优化器解析开销上升**：
   表中索引数量超过 10 个以上时，优化器在生成执行计划时枚举组合路径的耗时会显著上升，单次 SQL 解析的 CPU 成本随之增加。

---

### 2.3 不可见索引（Invisible Index）：无损下线验证防线

在传统运维中，清理一个怀疑未被使用的废弃索引存在巨大心理负担：万一某个未被发现的低频离线报表或边缘业务依赖该索引，一旦物理 `DROP INDEX`，线上查询会瞬间退化为聚簇索引全表扫描并打满 CPU；而在千万级大表上重新执行 `CREATE INDEX` 往往需要耗费数十分钟甚至数小时，救援成本极高。

从 MySQL 8.0 开始，官方引入了**不可见索引（Invisible Index）**特性，彻底解决了这一运维困局：

```sql
-- 1. 将怀疑废弃的索引标记为不可见 (瞬间完成，仅修改数据字典元数据)
ALTER TABLE orders ALTER INDEX idx_user_status INVISIBLE;

-- 2. 恢复索引可见性 (若发现业务有依赖，毫秒级快速挽救)
ALTER TABLE orders ALTER INDEX idx_user_status VISIBLE;
```

#### 不可见索引的运行机制与工程治理闭环

```text
                   索引生命周期治理流水线
                             │
[ 1. 评估准入 ] ──> 业务评审查询模式与选择性，建立覆盖索引
                             │
[ 2. 线上监控 ] ──> 通过 sys.schema_unused_indexes 识别长期未被使用的索引
                             │
[ 3. 设为不可见 ] ──> 执行 ALTER INDEX ... INVISIBLE (进入 7~14 天安全观察期)
        │             * 优化器视而不见，但存储引擎仍在后台静默维护写入 *
        ▼
   [ 出现慢查异常? ] ── 是 ──> 立即执行 ALTER INDEX ... VISIBLE (毫秒级复原)
        │ 否
[ 4. 物理销毁 ] ──> 观察期满且系统平稳，执行 DROP INDEX 彻底释放磁盘与写放大
```

- **核心运行机制**：当索引被设为 `INVISIBLE` 后，查询优化器在生成执行计划时会彻底忽略该索引，将其视作不存在；**但在存储引擎内部，该索引依然正常维护——即所有的 `INSERT`、`UPDATE`、`DELETE` 依然会正常同步写入该索引树**；
- **工程安全价值**：索引设为不可见后，系统进入 7~14 天的安全观察窗口期。如果业务无任何异常慢查询报警，证明该索引确实无查询依赖；如果发生慢查故障，一行指令即可将其重新置为 `VISIBLE`，零代价恢复。确认安全后，再择机执行物理 `DROP INDEX`，彻底终结写放大与磁盘占用。

---

## 3. Schema Evolution 怎样兼容旧代码和历史数据？

在业务不停机的前提下推进 Schema 演进，必须遵循**“向前向后双向兼容的代码演进、最小化物理阻塞的 Online DDL 算法选型、以及大表第三方影子表（Ghost / OSC）平滑切换”**三大准则：新增列必须具备默认值或允许 NULL 以兼容旧版本代码读取；在线修改表结构优先利用 MySQL 9.7 的 `ALGORITHM=INSTANT`，对不支持秒级变更的重构采用 `INPLACE` 或 `gh-ost`；严格监控并防范 MDL（元数据锁）排队导致的级联连接池被打满。

---

### 3.1 Online DDL 三大执行算法与并发矩阵

在早期的 MySQL 中，任何 `ALTER TABLE` 都会导致全局锁表并阻塞所有读写操作。现代 MySQL（如 9.7 LTS）的 InnoDB 引擎支持三种不同层级的 DDL 执行算法：

```text
                      Online DDL 算法谱系
                              │
       ┌──────────────────────┼──────────────────────┐
       ▼                      ▼                      ▼
[ ALGORITHM=INSTANT ]   [ ALGORITHM=INPLACE ]   [ ALGORITHM=COPY ]
毫秒级元数据修改        引擎内原地重构           创建影子表全量物理拷贝
零锁表、零数据重写      允许并发读写，记增量Log  全程阻塞并发写入，开销极大
```

| DDL 算法 | 物理执行过程 | 允许并发 DML（读/写） | 耗时与系统开销 | 适用场景 |
|---|---|:---:|---|---|
| **`INSTANT`** | 仅修改数据字典元数据，不触动任何已有数据页 | ✅ 读写完全不受影响 | **毫秒级**，瞬间完成 | 绝大多数加列、删列、修改列默认值、重命名列 |
| **`INPLACE`** | 在存储引擎内部原地重组数据页或新建二级索引，写操作记录至临时日志 | ✅ 允许并发读写 (`LOCK=NONE`) | 随着表体量线性增加，耗时数分钟 | 新增二级索引、修改列数据类型长度（允许就地扩展时） |
| **`COPY`** | 创建临时新表，全量拷贝历史数据，最后重命名替换 | ❌ 仅允许并发读，**完全阻塞并发写** | 极大。耗时最长，产生大量双倍磁盘空间与 I/O | 不支持就地修改的复杂列类型转换、更改存储引擎 |

在生产环境中执行 DDL 时，严禁依赖系统隐式推导，推荐显式指定算法与锁级别以防止意外降级锁表：

```sql
-- 推荐：显式声明期望的算法与锁级别，若当前操作不支持则直接报错中止，避免意外锁表
ALTER TABLE orders 
ADD COLUMN delivery_note VARCHAR(255) NULL, 
ALGORITHM=INSTANT;

-- 若操作需要创建二级索引，显式要求 INPLACE 且禁止加写锁：
ALTER TABLE orders 
ADD INDEX idx_delivery_time (delivery_time), 
ALGORITHM=INPLACE, LOCK=NONE;
```

---

### 3.2 元数据锁（MDL，Metadata Lock）的级联阻塞链路

即便指定了 `LOCK=NONE` 的 Online DDL，在执行初期与结束时刻，依然存在**元数据锁（MDL，Metadata Lock）级联阻塞与连接池耗尽的严重风险**。

MDL 的设计初衷是保证 DDL 与并发 DML 之间的结构一致性：
- 任何普通事务执行 `SELECT` 或 `UPDATE` 时，会持有表级的 **MDL 读锁（Shared Lock）**，事务提交时才释放；
- `ALTER TABLE` 语句在开始解析表结构时，必须申请 **MDL 写锁（Exclusive Lock）**。

```text
[事务 A (正在跑长慢查)] ── 持有 MDL 读锁 ────────────┐
                                                     ▼
[DDL 语句 (ALTER TABLE)] ─ 申请 MDL 写锁 ──> [陷入等待队列] (因 A 未提交)
                                                     ▲
[事务 B, C, D (高频业务读写)] 申请 MDL 读锁 ─────────┘ (被排队的 DDL 彻底阻塞！)
```

#### 事故演进过程：
1. 事务 A 启动了一条耗时较长的慢查询，持有表的 MDL 读锁；
2. DBA 或自动化发布流水线触发了 `ALTER TABLE`，申请 MDL 排他写锁，由于事务 A 未结束，DDL 陷入等待；
3. **MySQL 的锁调度协议规定：排队中的排他写锁优先级高于后来的读锁**。随后冲入的上千个正常业务查询（事务 B、C、D）试图申请 MDL 读锁，全部被堵在等待队列中；
4. 应用程序的数据库连接池在数秒内被耗尽打满，造成整个线上服务不可用。

#### 生产防御四项铁律：
1. **强制设置 DDL 锁等待超时**：执行 DDL 的会话必须显式设置 `SET lock_wait_timeout = 5;`（默认是 31536000 秒，即整整 1 年）。如果 5 秒内无法获取 MDL 锁，立即报错退出，绝不在队列中死等；
2. **避开业务高峰期执行**：选择流量低谷时段推进结构变更；
3. **查杀未提交的长事务**：执行 DDL 前排查 `information_schema.innodb_trx`，确保没有持续活跃的未提交长事务；
4. **验证无慢查堆积**：确保当前表没有处于慢查询扫描中的并发会话。

---

### 3.3 字段演进兼容规范

代码发布与数据库 DDL 执行在物理上不可能绝对原子同步，架构设计必须推行**双向兼容（Expand and Contract）**的标准演进流程：

```text
[阶段 1: Expand (扩张)]  数据库新增字段 (必须允许 NULL 或带有安全默认值)
         │              * 旧版本代码运行中，旧代码不关心新列，写入正常 *
         ▼
[阶段 2: Deploy (发布)]  新版本代码上线，新代码开始读取并写入新列
         │
         ▼
[阶段 3: Backfill (回填)]后台异步批处理任务将历史数据的该列补全真实业务值
         │
         ▼
[阶段 4: Contract (收缩)]约束收紧 (必要时收紧为 NOT NULL)，旧逻辑彻底废弃
```

- **严禁代码使用 `SELECT *`**：应用程序实体映射（ORM）必须显式声明查询字段列表。若使用 `SELECT *`，一旦数据库新增列，旧代码在反序列化或执行 ResultMapping 时极易因字段数量与实体不匹配而抛出解析异常。

### 3.4 第三方 Online Schema Change 方案对比：pt-osc vs gh-ost

对于超大表（如上亿行）且 MySQL 原生 `ALGORITHM=INSTANT` 不支持的复杂结构重构（如字段类型变更、表空间收缩），业界普遍采用第三方影子表方案：

| 方案 | **pt-online-schema-change (Percona)** | **gh-ost (GitHub)** |
|---|---|---|
| **底层实现机制** | 在原表上创建 `AFTER INSERT/UPDATE/DELETE` **触发器（Trigger）** 同步数据到临时影子表 | **无触发器（Trigger-less）**。伪装成 MySQL 从库，监听并读取 **Binlog** 事件流重放到影子表 |
| **对原库并发影响** | 触发器会增加原表主事务的执行延迟，高频写入时行锁竞争激烈，容易引发锁冲突与死锁 | 对原表写入无额外事务开销，异步消费 Binlog，资源消耗极其平滑 |
| **动态节流能力 (Throttling)** | 仅支持固定步长暂停，无法灵活动态调整 | **支持交互式在线控制**：可随时通过控制台动态调节拷贝速率、暂停、恢复 |
| **主从复制友好度** | 大量触发器写操作随 Binlog 传到从库，容易加剧主从复制延迟 | 写入控制平滑，能实时探测从库延迟并主动退避 |
| **生产选型推荐** | 适合传统环境、无 Binlog ROW 权限的受限系统 | **现代千万级以上大表在线 DDL 的首选工业标准** |

## 4. 大表怎样分批读写，而不是一次把内存、事务和日志打满？

对千万级大表进行批量读写或数据清洗时，核心原则是**“使用基于唯一递增索引的游标分段分页（Cursor Pagination）取代传统 `OFFSET`，并将操作收敛为精细批次（Batch Size 通常为 1000~5000 行）、单批独立提交事务、并根据主从复制延迟（`Seconds_Behind_Source`）实施动态反压（Backpressure）限速”**。一次性大事务会导致行锁长时间不释放、Redo Log 检查点频繁触发同步刷脏反压（Furious Flushing）、Undo Log 极度膨胀阻碍 Purge 线程、以及从库复制延迟雪崩。

---

### 4.1 传统分页 vs 游标分段读（Cursor Scan）

在进行数据归档、数据清洗或历史回填时，常见反模式是使用传统分页遍历全表：

```sql
-- 典型反模式：随页码增大逐渐演变为性能黑洞
SELECT * FROM large_orders ORDER BY id LIMIT 5000000, 2000;
```

`LIMIT offset, size` 的物理执行机制是“顺序扫描并抛弃前 $N$ 行”。当处理推进到 500 万行时，每读取 2000 行都需要先扫描并丢弃 500 万行物理记录，整体处理时间随着批次推进呈二次方剧烈上升，最终导致单次查询超时失败。

#### 工业标准范式：游标分段扫描（Keyset / Seek）

```sql
-- 标准范式：基于唯一递增主键执行定点 Seek，性能始终恒定在毫秒级
SELECT * FROM large_orders 
WHERE id > :last_max_id 
ORDER BY id ASC 
LIMIT 2000;
```

```text
[游标分页物理跳转模型]
首次执行: WHERE id > 0     ORDER BY id ASC LIMIT 2000 ──> 返回最大 id = 2000
下一批次: WHERE id > 2000  ORDER BY id ASC LIMIT 2000 ──> 沿 B+Tree 直接唯一定位 id=2001，扫描 2000 行
下一批次: WHERE id > 4000  ORDER BY id ASC LIMIT 2000 ──> 物理扫描开销恒定，绝不重复读取历史页
```

通过记住上一批次返回记录的最大主键 `id`，下一次直接以 `WHERE id > :last_max_id` 为扫描起点。在 B+Tree 聚簇索引中，这是复杂度为 $O(\log N)$ 的精确定位，无论数据表拥有 1 万行还是 1 亿行，每个批次的物理扫描耗时均保持绝对稳定。

---

### 4.2 批次尺寸（Batch Size）的物理权衡

单批次处理的数据行数不是越小越好，也不是越大越好，而是需要在**网络开销**与**数据库事务开销**之间达成严密平衡：

```text
                           Batch Size 物理权衡天平
                                     │
      ┌──────────────────────────────┴──────────────────────────────┐
      ▼                                                             ▼
[ Batch Size 过小 (如每批 10 行) ]           [ Batch Size 过大 (如每批 100 万行) ]
- 网络往返 RTT 开销占比过高                   - 事务持有数十万行排他锁，阻塞其他业务
- 每次提交事务均需 fsync 刷日志，吞吐低下      - 瞬间挤占 Redo Log 空间，引发剧烈刷脏反压
- 处理总耗时被网络通信拖垮                    - 单个大事务传到从库，从库复制延迟飙升数分钟
```

#### 工程实战黄金区间：
- **常规更新 / 归档删除**：建议单批次控制在 **1000 ~ 5000 行**，单次事务执行与提交耗时应稳定在 **50ms ~ 100ms** 之内；
- **纯批量插入（Bulk Insert）**：建议单批次控制在 **500 ~ 2000 行**，单次 SQL 文本尺寸控制在 1MB ~ 4MB，避免超出 `max_allowed_packet`。

---

### 4.3 动态反压机制（Dynamic Backpressure）

在主从读写分离或带有下游 CDC 复制的架构中，后台批处理脚本如果全速运行，即使单批次很小，连续高频的写入也会在主库瞬间产生大量 Binlog 事件。由于从库的重放速度受限于单表锁依赖或物理 I/O，**主从复制延迟指标 `Seconds_Behind_Source` 会迅速恶化**，直接导致线上读写分离业务全面读到脏数据。

成熟的批处理任务必须内置**动态反压控制（Dynamic Backpressure）**机制：

```text
                         批处理动态反压控制闭环
                                   │
                           [ 执行单批次修改 ]
                                   │
                         [ 提交本地微事务 COMMIT ]
                                   │
                    [ 采集从库状态: Seconds_Behind_Source ]
                                   │
              ┌────────────────────┴────────────────────┐
              ▼                                         ▼
   [ 延迟 <= 1 秒 (健康状态) ]               [ 延迟 > 1 秒 (产生积压) ]
   休眠 10ms ~ 50ms (平滑退避)               休眠 1000ms 并暂停下一批次派发
              │                                         │
              └────────────────────┬────────────────────┘
                                   ▼
                         [ 进入下一批次游标处理 ]
```

通过在每个批次处理后探测一次从库延迟，一旦检测到从库复制延迟上升，批处理线程主动退让休眠，直到从库追平延迟后再恢复执行。以牺牲后台归档任务的非关键耗时，为线上高优先级业务换取绝对的数据一致性保障。

---

### 4.4 批量导入最佳实践：多值 INSERT 与 LOAD DATA

在处理大量新数据灌库时，不同语法在 MySQL 内部的处理链路存在数倍到数十倍的性能差距：

```sql
-- 1. 极低效做法：单行多次执行 (每行都经历完整的网络 RTT、SQL 解析、优化与单事务提交)
INSERT INTO tbl (id, val) VALUES (1, 'A');
INSERT INTO tbl (id, val) VALUES (2, 'B');

-- 2. 推荐做法：多行合并提交 (一次网络交互，单次语法解析，批量向 B+Tree 插入)
INSERT INTO tbl (id, val) VALUES (1, 'A'), (2, 'B'), (3, 'C');

-- 3. 极致性能做法：LOAD DATA (直接面向存储引擎的物理数据装载，绕过大部分 Server 层解析开销)
LOAD DATA LOCAL INFILE '/data/bulk_data.csv' 
INTO TABLE tbl 
FIELDS TERMINATED BY ',' 
LINES TERMINATED BY '\n' 
(id, val);
```

- **`LOAD DATA` 的性能优势**：由 MySQL 引擎原生支持的数据泵协议，内部自动开启页面预分配与批量日志追加，通常比应用程序执行批处理 `INSERT` 提速 5 到 10 倍，是海量离线数据初始化的首选方案。

## 5. 批处理失败后怎样从断点恢复又不重不漏？

保证长时间批处理任务在进程异常中断或网络故障后能够安全断点续跑，核心在于**将“业务数据修改”与“任务进度检查点（Checkpoint）”建立严格的原子性关联，并在设计上强制推行“基于业务主键或版本号的幂等写操作”，以“至少一次（At-least-once）执行配合幂等写入”达成应用层等价的 Exactly-once 最终一致性**。若进度记录与数据写入脱节，就会导致断点恢复时出现数据漏跑或重复累加。

---

### 5.1 检查点（Checkpoint）的物理设计模式

长时间批处理（如处理 5000 万历史订单的迁移）往往需要运行数小时，期间应用服务随时可能经历容器重启、发布更新或网络闪断。系统绝不能从头重跑，必须依靠精确的检查点（Checkpoint）记录断点进度。

#### 模式一：事务级原子检查点（推荐，用于单库同源批处理）

如果批处理的源表与状态都在同一个 MySQL 数据库实例中，**最稳固的做法是将“业务修改”与“进度更新”绑定在同一个本地数据库事务中提交**：

```sql
-- 创建批处理进度状态表
CREATE TABLE batch_task_checkpoint (
    task_name VARCHAR(64) PRIMARY KEY,
    last_processed_id BIGINT NOT NULL DEFAULT 0,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- 执行单个批次：业务修改与检查点推进在同一个事务中原子生效
START TRANSACTION;

-- 1. 执行当前批次的业务操作 (如归档更新)
UPDATE orders 
SET archive_status = 1 
WHERE id > 10000 AND id <= 12000 AND archive_status = 0;

-- 2. 同步推进任务检查点
UPDATE batch_task_checkpoint 
SET last_processed_id = 12000 
WHERE task_name = 'order_archiving_task' AND last_processed_id = 10000;

-- 3. 共同原子提交
COMMIT;
```

在此模式下，绝不可能出现“业务数据已改，但进度没存上”或“进度已推进，但业务数据被回滚”的半完成断裂。一旦应用节点异常重启，任务直接读取 `SELECT last_processed_id FROM batch_task_checkpoint` 作为起始条件，进度分毫不差。

#### 模式二：外部系统解耦检查点（用于跨系统清洗）

如果数据是流向外部系统（如 Elasticsearch 或 Kafka），无法使用单机本地事务包裹，则必须遵循**“先确保业务下游处理成功，再向前持久化 Checkpoint”**的顺序推进。这属于典型的“至少一次（At-least-once）”投递模型，断点重跑时必定会重复拉取上一次 Checkpoint 后的尾部数据，因此必须依赖下一节所述的幂等性设计。

---

### 5.2 状态机推进与租约机制

为了支持多工作节点（Worker）并发处理或者在 Worker 宕机后能够自动被其他节点接管，任务表通常引入状态机与心跳租约（Lease）：

```sql
CREATE TABLE batch_task_shards (
    shard_id INT PRIMARY KEY,
    start_id BIGINT NOT NULL,
    end_id BIGINT NOT NULL,
    current_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL, -- PENDING, RUNNING, COMPLETED, FAILED
    owner_worker VARCHAR(64) NULL,
    lease_expire_at TIMESTAMP NULL
);
```

- **抢占与防僵死**：Worker 节点通过原子条件更新抢占分片：
  ```sql
  UPDATE batch_task_shards 
  SET status = 'RUNNING', owner_worker = 'node_01', lease_expire_at = NOW() + INTERVAL 30 SECOND 
  WHERE shard_id = 1 AND (status = 'PENDING' OR (status = 'RUNNING' AND lease_expire_at < NOW()));
  ```
  如果 Worker 节点发生 GC 卡顿或宕机未能在 30 秒内续约，租约自动超时，其他健康 Worker 能够安全接管该分片并从 `current_id` 断点继续推进。

---

### 5.3 幂等性（Idempotence）是断点恢复的终极屏障

在分布式批处理环境下，真正的物理 Exactly-once 传输是不存在的。网络丢包重试与节点重启故障恢复必然带来重复投递。**整个批处理管道必须将“重跑同一批次任意次结果保持恒等”作为绝对刚性契约**。

#### 幂等设计的反面与正面范式：

```sql
-- ❌ 严禁使用非幂等操作：断点重跑会导致数值重复累加！
UPDATE account_statistics 
SET sync_count = sync_count + 1 
WHERE account_id = 1001;

-- ✅ 必须使用绝对状态覆写（幂等）：重跑 100 次状态依然稳定
UPDATE orders 
SET process_status = 'ARCHIVED', archived_at = '2026-10-13 18:00:00' 
WHERE id = 5001;

-- ✅ 插入必须依赖业务主键进行冲突覆写（Upsert）：
INSERT INTO orders_archive (id, user_id, amount, created_at)
VALUES (5001, 102, 99.00, '2026-10-13 12:00:00') AS new_row
ON DUPLICATE KEY UPDATE 
    amount = new_row.amount;
```

只要操作本身具备幂等性，系统发生故障后即使退回上一个 Checkpoint 重新处理一部分已处理过的数据，系统也不会产生重复插入、数据翻倍或账实不符的问题。

## 6. 历史回填或迁移怎样衔接全量与增量，并安全切换？

历史数据回填与不停机数据迁移的工业级标准，是采用**“基于快照与增量日志接力（Snapshot + Incremental Catch-up）的平滑追赶机制，配合双写双读灰度验证与防脑裂切流（Cutover）流程，并在切流后保留反向同步与回退窗口”**。系统首先记录导出瞬间的 Binlog 位点并拉取全量历史数据，全量完成后从该位点启动增量事件流追平延迟；通过分段 Checksum 校验确保账实相符后，先切读、后切写，确保任何不可预期的故障均能在秒级安全回滚。

---

### 6.1 数据迁移经典四步架构流水线

无论是单库大表分拆、底层硬件机房迁移、还是将表结构重构为全新 Schema，不停机在线迁移都遵循经典的四步流水线：

```text
[ 阶段 1：全量基线快照 Snapshot ]
  1. 记录源库当前全局位点或 GTID: snapshot_pos = 100500
  2. 利用快照读 (一致性读取) 分批导出全量存量数据并导入目标库
        │
        ▼
[ 阶段 2：增量日志流式追赶 Catch-up ]
  3. 从位点 100500 开始启动 Binlog 增量同步流，持续重放到目标库
  4. 目标库延迟逐渐收窄至毫秒级 (达到稳态)
        │
        ▼
[ 阶段 3：数据一致性对账验证 Verification ]
  5. 分段进行 Checksum 校验，自动发现并修补差异数据，确保两库数据 100% 镜像一致
        │
        ▼
[ 阶段 4：平滑切流与反向回退保护 Cutover ]
  6. 读流量灰度切换 -> 源库短暂只读 -> 追平残余日志 -> 写流量切至目标库
  7. 开启反向同步 (目标库 -> 源库)，保留 48 小时回退窗口
```

---

### 6.2 全量快照与增量流的接力边界

全量与增量无缝接力的关键在于**“如何处理快照导出期间并发产生的数据更新”**：
- 导出数千万存量数据可能需要持续 2 小时；
- 在这 2 小时内，源库仍然在高速处理用户的并发写入；
- 如果在全量导出开始时锚定了位点 `snapshot_pos`，那么在导出期间被并发修改的数据，也会作为增量事件记录在 `snapshot_pos` 之后的 Binlog 中。

#### 消除时序重叠的工程法则：下游强制幂等覆写（Upsert）
目标库在消费增量 Binlog 时，必须将所有的插入转换为**主键幂等覆写**（如使用 ROW 格式 Binlog，更新事件按主键覆盖，插入事件按 `INSERT ... ON DUPLICATE KEY UPDATE` 执行）。
全量导入过程中先落盘了旧快照，随后增量流会按照绝对的物理提交时序将该记录覆盖刷新为最新状态；即使增量流重放了已经在全量阶段灌入的数据，幂等性也确保了数据不会产生分歧。

---

### 6.3 数据一致性对账机制（Checksum / Diff）

在正式切流前，必须从数学和物理上证明两套数据库的数据绝对一致。由于数据量达到数千万甚至数亿级别，直接执行全表逐行对比会消耗巨额带宽并打爆网络。

#### 推荐方案：基于主键分段求哈希指纹（Bucket Checksum）

```sql
-- 对主键区间 [100000, 200000) 内的数据计算聚合异或哈希值
SELECT 
    COUNT(*) AS row_cnt,
    BIT_XOR(CRC32(CONCAT_WS('#', id, user_id, status, amount, updated_at))) AS checksum_val
FROM orders 
WHERE id >= 100000 AND id < 200000;
```

1. **宏观对比**：在源库与目标库分别针对同一个主键区间执行上述哈希聚合查询；
2. **段级验证**：如果两边的 `row_cnt` 与 `checksum_val` 完全一致，说明该 10 万行区间内的数据内容绝对一致，无需拉取细节；
3. **定位修复**：如果某个区间的 `checksum_val` 不一致，仅需针对该 10 万行区间拉取主键与更新时间戳进行局部 Diff 比对，针对性补全或覆盖差异行，极大压缩对账开销。

---

### 6.4 切流（Cutover）与反向同步回退窗口

切流是整个迁移生命周期中风险最高的动作。合格的生产迁移方案必须具备**“秒级无损回滚”**的防线：

```text
               切流期反向同步与双向防线
                        │
 [ 步骤 1: 读切流 ] ──> 将只读查询灰度切到目标库，观察连接池与慢查询
                        │
 [ 步骤 2: 停写源库 ] ──> 源库设置 read_only = 1 (业务写操作短暂秒级维护)
                        │
 [ 步骤 3: 追平残余 ] ──> 等待目标库彻底追平源库最后几笔 Binlog (延迟归零)
                        │
 [ 步骤 4: 写切流 ] ──> 业务应用写流量正式切换至目标库，恢复正常读写
                        │
 [ 步骤 5: 建立反向同步 ] 开启 CDC (目标库 ──> 源库)，源库作为备胎从库待命
                        │
      ┌─────────────────┴─────────────────┐
      ▼                                   ▼
[ 运行稳定 (48 小时后) ]         [ 目标库突发未知严重故障 ]
下线源库，释放旧资源             瞬间将写流量回切源库 (零数据丢失安全回退)
```

1. **灰度读切流**：优先将只读报表或非核心读请求切至目标库，验证目标库索引是否完备、查询执行计划是否符合预期；
2. **写切流与微秒级对齐**：
   - 业务网关短暂拦截写请求（或将源库置为只读 `SET GLOBAL read_only = 1;`）；
   - 观察同步组件，确保目标库的消费延迟彻底归零（源库所有已提交事务全部被目标库应用）；
   - 将应用的数据源连接地址切换至目标库，开启写操作；
3. **反向增量同步（Reverse Catch-up）——核心安全底线**：
   - 在写流量切至目标库的瞬间，**必须立刻建立反向增量同步通道（将目标库的新写入通过 Binlog 同步回旧源库）**；
   - 此时旧源库退化为从库，持续实时镜像目标库的所有最新变更；
   - **回退窗口价值**：如果在切流后的 24~48 小时内，目标库遭遇未预期的性能雪崩、存储引擎兼容性缺陷或隐蔽 Bug，运维团队可以毫无顾虑地**将业务写流量瞬间切回旧源库**，期间在目标库产生的所有新数据已经完整同步回旧库，达成真正的零数据丢失安全脱险。

## 知识回顾：数据增长与平滑演进的因果闭环

1. **规模增长的物理退化**：单表膨胀的本质不是数字变大，而是 Working Set 击穿 Buffer Pool 导致的磁盘随机 I/O 放大、宽行导致的聚簇页扇出骤降、以及大表运维锁与日志开销的指数级上升。
2. **主键与索引的演进防线**：核心表主键必须提前筑牢 `BIGINT` 容量防线以杜绝 42 亿溢出写瘫痪，推荐趋势递增的高性能主键；无用二级索引带来严重的写放大与缓存污染，应通过 `INVISIBLE` 观察窗口期实现平滑下线。
3. **Schema Evolution 的无锁之道**：Online DDL 优先争取 `INSTANT` 秒级元数据修改，次选 `INPLACE`；务必设置 `lock_wait_timeout` 防范 MDL 级联锁崩；复杂大表变更依赖 `gh-ost` 无触发器影子表。
4. **大表批处理的反压受控模型**：彻底废弃深分页 `LIMIT offset, size`，推行基于稳定键的游标扫描（Cursor Seek）；批次规模权衡在 1000~5000 行，并在提交后基于从库 `Seconds_Behind_Source` 执行动态反压限速。
5. **断点续跑与幂等闭环**：批处理通过单机事务或状态机租约将 Checkpoint 与业务修改原子关联；断点重跑必须由底层写操作的天然幂等性（Upsert / 状态覆盖）托底，达成等价的 Exactly-once 最终一致。
6. **不停机迁移的四步与回退防线**：基于 Snapshot 导出 + Binlog 增量追平完成数据预热；采用主键分段 Checksum 哈希验证数据一致性；切流时必须建立反向同步（新库 -> 旧库），保留 48 小时回退窗口确保绝对安全。

## 🎯 面试怎么回答

### 为什么大表直接执行 ALTER TABLE 可能会导致全站不可用？怎样安全修改表结构？

> [!TIP]
> 根本原因在于元数据锁（MDL）的排队级联阻塞机制。执行 `ALTER TABLE` 需要申请 MDL 排他写锁；若此时表上有未结束的慢查询持有 MDL 读锁，DDL 就会被阻塞等待。而 MySQL 规定写锁请求优先级高于后续读锁请求，导致后续涌入的所有正常业务查询全部被堵在 MDL 读锁队列中，数秒内耗尽连接池导致服务瘫痪。安全修改表结构的标准策略包括：1. 显式设置会话超时 `SET lock_wait_timeout = 5` 防止死等；2. 优先利用 `ALGORITHM=INSTANT` 实现毫秒级元数据修改；3. 避开高峰期并提前杀掉未提交长事务；4. 超大表复杂重构使用 `gh-ost` 等基于 Binlog 的无触发器影子表方案。

### 主键为什么不建议使用 UUID？如果在数据量爆发后自增 INT 溢出了怎么办？

> [!TIP]
> UUID v4 是随机散列的字符串，直接作为聚簇主键会导致数据在物理磁盘上完全乱序写入，频繁触发 B+Tree 页分裂与节点搬移，产生大量存储碎片并导致 Buffer Pool 内存利用率暴跌；此外二级索引叶子节点都需要存储主键，UUID 会导致所有二级索引体积成倍膨胀。自增 `INT UNSIGNED` 上限为 42.9 亿，一旦耗尽将抛出主键重复报错并彻底拒绝写入。若已发生溢出危机，紧急处理需利用 `gh-ost` 或主从切换灰度将字段升级为 `BIGINT`；防范方案是在业务建表之初统一强制使用 `BIGINT UNSIGNED` 或趋势递增的雪花算法（Snowflake ID）。

### 什么是不可见索引（Invisible Index）？它在索引生命周期治理中有什么价值？

> [!TIP]
> 不可见索引是 MySQL 8.0+ 引入的特性，通过 `ALTER TABLE tbl ALTER INDEX idx INVISIBLE` 可以将索引对优化器隐藏，优化器在生成执行计划时视其为不存在，但在底层存储引擎中依然对写操作正常同步维护。它的核心工程价值是提供零成本的索引退役观察窗口：在物理删除疑似废弃的索引前，先将其设为不可见观察数周，若出现未预期的慢查询报警，仅需一行指令即可将其重新置为 `VISIBLE` 毫秒级复原；若确认平稳无影响，再择机物理 `DROP`，彻底消除了盲目删除索引引发线上大面积慢查询的严重风险。

### 怎样对千万级大表进行安全的数据归档或批量删除，避免打满日志与阻塞主从？

> [!TIP]
> 严禁执行单次大事务删除（如 `DELETE FROM tbl WHERE status = 0 LIMIT 1000000`），这会导致长时间持有排他锁、Redo 满溢触发同步刷脏、Undo 极度膨胀以及从库产生严重复制延迟。标准做法是小批次游标处理与反压节流：1. 使用 `WHERE id > :last_id AND status = 0 ORDER BY id ASC LIMIT 2000` 按主键游标精确定位分批；2. 单个批次独立开启事务并提交，控制耗时在 100ms 内；3. 在每个批次提交后主动探测从库的 `Seconds_Behind_Source`，若从库延迟超过 1 秒则主动休眠退让，直至从库追平后再推进下一批。

### 为什么大表批处理不能用 LIMIT offset, size 翻页？正确的做法是什么？

> [!TIP]
> 传统 `LIMIT offset, size` 在底层执行时，存储引擎必须完整按顺序扫描并跳过前 `offset` 行物理记录，然后才返回 `size` 行。当翻到数百万行之后，每次请求的扫描代价都与已处理数据量成正比，整体开销呈二次方递增，处理极度缓慢。正确的做法是游标分页（Keyset / Seek）：记录上一批次返回的最大主键 ID，通过 `WHERE id > :last_max_id ORDER BY id ASC LIMIT :size` 定点跳转。利用 B+Tree 索引的 $O(\log N)$ 树遍历能力直达目标叶子节点，无论翻到多少亿行，单批次物理执行耗时始终恒定。

### 批处理任务中，怎样保证断点续跑时数据“不重不漏”？

> [!TIP]
> 核心是“原子推进检查点 + 业务操作天然幂等”。在同库批处理场景下，将业务数据更新与 `checkpoint` 进度表的推进置于同一个本地数据库事务中提交，确保业务与进度状态原子绑定。同时，业务数据修改必须设计为天然幂等逻辑：更新操作使用状态覆盖或确定性赋值，插入操作使用 `INSERT ... ON DUPLICATE KEY UPDATE`。这样即便因网络超时或节点宕机导致从上一个 Checkpoint 开始重放部分批次，重复执行也不会造成状态翻转或数据翻倍，在物理的 At-least-once 机制上达成应用层等价的 Exactly-once 效果。

### 生产环境不停机迁移数据库大表的标准流程是怎样的？如何保证零丢失与随时回滚？

> [!TIP]
> 工业级标准分为四步：1. **全量快照**：在源库记录一致性位点（Binlog 位点或 GTID），并发分批导出全量数据并灌入目标库；2. **增量追赶**：从此前锚定的位点启动 CDC 监听 Binlog 增量事件流，通过主键幂等持续回放至目标库，直至延迟追平到毫秒级；3. **数据对账**：利用基于主键分段求哈希指纹（Bucket Checksum）的校验工具对比源库与目标库，修复少量差异行；4. **安全切流与反向回退**：只读查询灰度切流，随后源库短暂置为只读等待延迟彻底归零，将写流量切换至目标库，**并在此瞬间反向开启由新库同步到旧库的 CDC 链路**，保留 24~48 小时回退窗口，若新库发生未预期的严重故障，可瞬间回切旧库且不丢失任何新产生的数据。

## ⚠️ 易错点

> [!WARNING]
> **千万别在生产核心表上把主键定义为 INT。** 业务初期低估增长很容易导致自增 ID 在达到 42.9 亿时抛出主键冲突错误，直接导致全站写入停摆。核心表务必一步到位使用 `BIGINT UNSIGNED`。

> [!WARNING]
> **切忌在业务高峰期无超时保护执行 ALTER TABLE。** 即便当前变更支持 Online DDL，若未设置 `lock_wait_timeout`，一旦遇到正在执行的慢查就会陷入排他 MDL 等待，进而阻塞后续所有的普通业务读写并秒级耗尽连接池。

> [!WARNING]
> **大表新增字段严禁给非空字段配置计算型复杂默认值。** 尽量将新列声明为允许 NULL 或简单静态默认值，以此确保触发 `ALGORITHM=INSTANT` 毫秒级元数据修改；若涉及历史数据回填，应在代码上线后通过后台异步批处理逐步完成。

> [!WARNING]
> **严禁在生产大表上执行无主键游标的 LIMIT offset, size 循环归档。** 随着 offset 增大，磁盘扫描量与执行耗时将呈指数级爆炸，极易引发大面积超时。必须强制使用 `WHERE id > :last_id` 游标扫描。

> [!WARNING]
> **清理废弃索引时切勿直接 DROP INDEX。** 必须先执行 `ALTER INDEX ... INVISIBLE` 将其设为不可见，在持续 7~14 天的完整业务周期（包括离线报表和周末高峰）观察确认无慢查后，再最终物理删除。

> [!WARNING]
> **批处理归档或删除绝不能封装在一个超大事务中。** 一次性删除 100 万行会长时间持有大量行排他锁、耗尽 Redo 空间引发强制刷脏阻塞业务、并导致从库产生长达数分钟的复制延迟。必须严格按 1000~5000 行分批提交。

> [!WARNING]
> **不停机数据迁移切流前，必须提前搭建反向增量同步。** 仅有正向同步（旧库到新库）的切流是单行道，一旦新库出现严重性能衰竭或数据类型隐蔽 Bug，缺乏反向同步（新库到旧库）将导致新数据无法回流，丧失秒级安全回滚能力。

## 🧩 本章自测

<details>
<summary><strong>1. 为什么说单表数据量增大后，最先被击穿的往往是内存 Working Set 而不是磁盘容量？</strong></summary>

因为现代磁盘存储空间相对廉价且容量充裕，但内存 Buffer Pool 是极其稀缺且昂贵的物理资源。当活跃业务请求的数据范围超出 Buffer Pool 能够缓存的上限时，内存命中率骤降，LRU 链表发生剧烈换入换出，原本纯内存毫秒以下的微观操作全部退化为等待物理磁盘的随机寻道 I/O，系统吞吐量急剧暴跌。

</details>

<details>
<summary><strong>2. 为什么无序的随机 UUID 作为聚簇主键会导致 B+Tree 的存储效率大幅降低？</strong></summary>

因为聚簇索引在物理磁盘上是按照主键严格顺序存放的。随机 UUID 导致每次插入都在索引的不同未知位置，迫使 InnoDB 频繁执行页面拆分（Page Split）和物理数据搬移。这不仅导致数据页平均填充率从原本的 15/16 暴跌到接近 50% 产生严重空间碎片，还会使得所有二级索引叶子节点因携带庞大的 UUID 主键而严重膨胀。

</details>

<details>
<summary><strong>3. 不可见索引（Invisible Index）被设置为 INVISIBLE 后，执行 INSERT 还会对该索引树进行维护吗？为什么这样设计？</strong></summary>

会维护。该特性只对优化器生效，优化器在解析 SQL 时忽略不可见索引，但底层存储引擎在执行写入时依然会对其进行完整的 B+Tree 维护。这样设计的核心目的就是为了提供无损的快速回退能力：一旦发现业务受影响，重新设为 `VISIBLE` 仅需修改数据字典即可毫秒级生效，而无需耗时耗力重新扫描全表构建索引。

</details>

<details>
<summary><strong>4. 在使用 Online DDL 时，ALGORITHM=INSTANT 与 ALGORITHM=INPLACE 最核心的物理区别是什么？</strong></summary>

`INSTANT` 仅仅修改数据字典中的元数据定义，完全不扫描、不触动、不重写物理磁盘上的已有数据页，因此无论表有多大都能在几毫秒内执行完毕；而 `INPLACE` 必须在存储引擎内部遍历数据页、原地构建新的索引结构或重组数据文件，虽然允许并发读写，但物理执行时间与表的数据量直接正相关。

</details>

<details>
<summary><strong>5. 什么是元数据锁（MDL）的“排他锁阻塞读锁”特性？生产中该如何防御？</strong></summary>

当一个 DDL 语句申请排他 MDL 写锁时，如果有长事务持有 MDL 读锁，DDL 会排队等待。MySQL 规定处于等待队列中的排他写锁优先级高于后续新到达的共享读锁，导致随后所有的普通 `SELECT` 查询全部被阻塞排队，秒级打满连接池。防御方案是：在执行 DDL 会话前强制设置 `SET lock_wait_timeout = 5;`，若超时直接报错放弃，绝不长期排队。

</details>

<details>
<summary><strong>6. 为什么在千万级大表中执行大批量归档时，必须监控从库的 Seconds_Behind_Source 并实施反压？</strong></summary>

因为主库的大批量写入会被写入 Binlog 并传输到从库。从库在回放同一张表的写操作时，往往受到单表锁依赖或物理 I/O 上限的约束，回放速度通常低于主库的多并发生产速度。若主库不间断高速批量写入，从库的 Relay Log 会严重积压，导致复制延迟急剧上升，直接破坏线上读写分离架构中用户读取数据的一致性。

</details>

<details>
<summary><strong>7. 游标分页（Keyset Pagination）为什么能够彻底解决 OFFSET 深分页的性能黑洞？</strong></summary>

因为 `OFFSET N` 的物理机制是扫描并抛弃前 $N$ 行数据，执行成本随 $N$ 的增长而线性放大；而游标分页利用 `WHERE id > :last_max_id`，直接借助 B+Tree 索引根节点到叶子节点的精确定位能力，每次都能在 $O(\log N)$ 时间内直达目标起始记录，随后仅顺序扫描批次所需的固定行数，物理 I/O 开销与数据表整体规模彻底解耦。

</details>

<details>
<summary><strong>8. 在批处理任务中，为什么说仅记录当前批次处理成功并不代表系统具备原子性断点恢复能力？</strong></summary>

如果检查点记录的推进与业务数据的物理提交属于两个独立动作，系统在二者之间遭遇突发宕机或异常断电时，就会产生状态错位（如业务数据已提交但位点未写入，或位点已更新但业务数据回滚）。要做到安全断点恢复，要么将业务修改与检查点记录放在同一个单机数据库事务中提交，要么确保所有批处理写操作天然具备幂等性（基于主键的 Upsert 或绝对状态覆写）。

</details>

<details>
<summary><strong>9. 基于分段哈希（Bucket Checksum）进行大表迁移对账的核心原理是什么？</strong></summary>

将整张大表按主键范围切分为固定尺寸的区间段（如每 10 万行一段），在源库和目标库上分别利用 `BIT_XOR(CRC32(...))` 聚合函数对段内所有行的字段拼接字符串计算一个标量哈希指纹。若两库的段哈希值完全相同，则证明段内数十万行数据绝对一致；仅当哈希指纹不一致时，才针对该分段拉取行级数据对比，从而以极低的带宽与计算开销完成亿级大表对账。

</details>

<details>
<summary><strong>10. 在不停机在线迁移切流时，为什么必须在写切换生效后立刻开启反向同步（新库 -> 旧库）？</strong></summary>

因为即便前期经过充分测试与对账，新库在承接全量线上业务写流量后，依然存在因未知硬件缺陷、慢查询并发冲突或存储引擎 Bug 导致系统雪崩的极端风险。反向同步能够实时将新库产生的数据增量写回旧库，一旦新库出现严重隐患，运维团队可以在几秒钟内将业务写流量安全切回旧库，而不会丢失切流期间产生的任何新增数据。

</details>
