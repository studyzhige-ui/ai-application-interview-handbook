## 0. 事务边界划定后，为什么并发写仍可能出现状态覆盖与大面积阻塞？

在工程实践中，许多开发者常陷入一个危险的直觉误区：“既然开启了事务，并发修改自然就是安全的”。

真实业务中的写操作极少是凭空写入固定值，绝大多数写操作都遵循**“读-改-写”（Read-Modify-Write）**的业务逻辑：
1. 先读取当前记录的状态（例如查询账户余额、商品库存、优惠券剩余配额）；
2. 在应用内存中根据业务规则计算新值（例如校验余额是否充足、扣减金额）；
3. 将计算出的新值写回数据库（例如 `UPDATE accounts SET balance = new_val WHERE id = 1`）。

在单线程环境下，这一过程绝对正确。但在多事务并发执行时，两个事务可能在同一微秒基于**完全相同的旧值**做出决策。即使数据库事务各自保证了单步执行的原子性，后提交的事务也会毫无感知地把先提交事务的计算结果彻底覆盖，导致**丢失更新（Lost Update）**与账实不符。

为了阻止并发写冲突，系统必须建立写互斥机制。然而，互斥必然引入代价：
- 当一个事务修改数据时，它到底在物理存储上锁住了什么？为什么执行一条看似简单的 `UPDATE` 会锁住完全不相干的行甚至不存在的区间？
- 为什么并发写会引发大面积的锁等待（Lock Wait）甚至死锁（Deadlock）回滚？
- 在瞬时高并发秒杀或热点账户场景下，排他锁造成的行级串行化排队该如何破局？

> [!IMPORTANT]
> **💡 核心认知：事务的原子性（ACID 的 A）只保证单事务内部操作“全做或全不做”，不等于并发调度的正确性。并发修改的安全性必须依赖写操作的前提保护（乐观锁：读时不加锁、写回时校验状态或版本号）或物理互斥（悲观锁：读取时直接施加排他锁阻止并发写入）。而 InnoDB 的锁机制紧密寄生于索引访问路径之上——锁的范围不是由业务意图决定的，而是由执行计划实际扫描的物理范围决定的。**

## 1. 为什么“用了事务”仍可能出现丢失更新或覆盖？

“用了事务”仍可能出现丢失更新，根本原因在于**普通的数据库事务只保证提交的原子性（操作全做或全不做），并不阻止多个事务并发读取相同的旧数据并基于旧数据执行盲写覆盖**。在典型的“读-改-写”（Read-Modify-Write）业务流程中，事务 A 与事务 B 同时读取到了同一行的旧状态；事务 A 在内存中计算并写回提交；紧接着事务 B 也基于自己读到的旧状态写回并提交，事务 A 刚刚提交的修改就被事务 B 毫无感知地直接覆盖冲掉。

丢失更新在数据库理论与工程实践中分为两类：
1. **第一类丢失更新（回滚覆盖，Lost Update）**：事务 A 正在修改某行，事务 B 也修改了该行并提交；随后事务 A 发生异常执行 `ROLLBACK`，把数据还原到了事务 A 开启前的初始值，导致事务 B 已正式提交的修改被一并抹除。在现代所有主流数据库（包括 MySQL 的所有隔离级别）中，因为对写入行强制施加排他锁，第一类丢失更新已被物理消除；
2. **第二类丢失更新（提交覆盖，Overwriting Update）**：事务 A 与事务 B 同时读取同一行；事务 A 修改并提交；随后事务 B 也基于先前读到的旧值完成修改并提交，事务 B 的提交完全覆盖了事务 A 的提交。这是工程开发中最容易忽视的高频并发数据覆盖陷阱。

---

### 1.1 并发时间线推演：第二类丢失更新的发生过程

以账户扣款业务为例，账户初始余额为 100 元。事务 A 与事务 B 分别尝试扣减 60 元与 70 元。在业务逻辑上，总余额不足以支持两笔扣减，理想结果应为一笔成功、一笔因余额不足失败。

但在没有并发前提保护的代码中（先查出余额、应用判断、再计算赋值）：

| 时刻 | 事务 A (扣款 60 元) | 事务 B (扣款 70 元) |
|:---:|---|---|
| **T1** | `START TRANSACTION;` | `START TRANSACTION;` |
| **T2** | `SELECT balance FROM accounts WHERE id = 1;`<br>*(读到余额 100)* | — |
| **T3** | — | `SELECT balance FROM accounts WHERE id = 1;`<br>*(快照读，同样读到余额 100)* |
| **T4** | 应用计算 `100 - 60 = 40`<br>`UPDATE accounts SET balance = 40 WHERE id = 1;`<br>*(事务 A 写入新计算值)* | — |
| **T5** | `COMMIT;`<br>*(事务 A 提交生效，库中余额为 40)* | — |
| **T6** | — | 应用基于旧值 100 计算 `100 - 70 = 30`<br>`UPDATE accounts SET balance = 30 WHERE id = 1;`<br>*(**盲写覆盖**：直接覆写库中已生效的 40)* |
| **T7** | — | `COMMIT;`<br>*(事务 B 提交，库中最终余额为 30，**事务 A 扣款凭空蒸发**)* |

#### 结果复盘：
系统总共完成了两笔扣款（60 + 70 = 130 元），但最终数据库余额显示为 30 元。事务 A 扣除 60 元的事实被事务 B 的盲写彻底覆盖。两个事务都在各自独立的事务边界内完成了“原子提交”，没有触发任何 SQL 错误，但整体数据状态发生了严重的账实不符与业务不变量破坏。

### 1.2 为什么快照读和 MVCC 无法防范丢失更新？

在 RR 隔离级别下，MVCC 保证了可重复读，事务内多次执行快照读看到的数值始终稳定。但这恰恰加剧了丢失更新的隐蔽性。

MVCC 解决的是**读操作不阻塞写操作**，为读操作呈现的是**历史快照**。如果应用程序拿着历史快照的数据做输入，在内存中完成算术运算，再将运算结果通过 `UPDATE accounts SET balance = :computed_val` 写回，数据库的写操作只会机械地执行当前读与物理覆写，根本无从感知应用层计算的前提是否已经被并发事务打破。

```text
[读阶段] 事务从 MVCC 历史快照获取数值 (balance = 100)
    │
    ▼
[算阶段] 应用服务器在本地内存完成业务逻辑决策 (100 - 70 = 30)
    │
    ▼
[写阶段] 机械写回绝对数值 (SET balance = 30) ──> 【盲写覆盖了其他并发更新】
```

要彻底消灭丢失更新，必须打破“先盲读、后盲算、再盲写”的分离链路。工程上通常沿着两种相反的哲学思路展开：
- **乐观并发控制（乐观锁）**：假设并发冲突极少发生，读取数据时不加任何物理排他锁，只在最终写回的一瞬间校验数据是否被他人改动过（通过业务条件或版本号判断）；
- **悲观并发控制（悲观锁 / 锁定读）**：假设并发冲突必然发生，在第一次读取数据时就立即申请数据库物理排他锁，强行阻止其他事务在此期间修改或锁定同一行。

## 2. 条件更新和乐观锁怎样防止基于旧状态写入？

条件更新和乐观锁防止基于旧状态写入的核心在于**将“检查前置状态”与“执行物理修改”原子化合并到同一条 SQL 语句中，并利用更新影响的行数（Affected Rows）裁定修改是否成功**。乐观锁本质上不是数据库原生提供的某种物理锁对象，而是一种由应用层驱动的并发控制策略：读数据时不加锁，写回时让数据库在底层行排他锁保护下完成条件比对。如果目标行当前的状态已不再满足业务前提，更新操作自动失效（影响行数为 0），应用层借此感知并发冲突并执行回滚或重试。

在工程落地上，主要分为两种标准模式：
1. **基于业务前提的原语化条件更新**：直接将业务不变量作为 `WHERE` 过滤条件，结合原地相对增减；
2. **基于显式版本号的乐观锁（Optimistic Locking）**：在表中增加自增版本号（`version`）或时间戳字段，每次更新强制校验并递增版本。

---

### 2.1 原语化条件更新：原地增减与前提防护

对于数值扣减、状态机流转等明确的单行操作，最优雅、最高性能的方式是利用 SQL 自身原语，避免在应用内存中计算绝对值：

```sql
-- 将“余额校验”与“相对扣减”合并为单条原子写语句
UPDATE accounts 
SET balance = balance - 60 
WHERE id = 1 AND balance >= 60;
```

#### 物理执行过程与 Affected Rows 裁定
`UPDATE` 属于当前读（Current Read）。当这条 SQL 执行时：
1. 存储引擎首先定位到 `id = 1` 的聚簇索引记录，并为其加上**行排他锁（X 锁）**；
2. 在持有行锁的互斥状态下，读取该行的最新提交值；
3. 执行引擎校验 `WHERE balance >= 60`：
   - **若条件满足**：物理执行扣减，行记录更新，返回 `Affected Rows = 1`；
   - **若条件不满足**（如已被其他事务扣减至低于 60）：不修改数据，返回 `Affected Rows = 0`。

应用层根据驱动返回的受影响行数做出严格裁定：

```java
// Java / MyBatis 伪代码
int affectedRows = accountMapper.deductBalance(accountId, 60);
if (affectedRows == 0) {
    // 明确捕获业务冲突：余额不足或被并发修改
    throw new BusinessException("余额不足，扣款失败");
}
```

在 1.1 节的时序中，如果事务 A 与事务 B 均采用此语句，事务 A 执行扣减后余额变为 40；事务 B 执行时读取最新值 40，条件 `balance >= 70` 不成立，影响行数返回 0。系统精准拦截了透支，丢失更新被彻底解决。

### 2.2 显式版本号机制（Optimistic Locking）

当业务修改涉及多个非数值字段、或者无法用简单的相对算式表达时（例如修改用户资料、多字段复合表单提交），标准解法是引入**版本号机制（Version Column）**。

#### 表结构设计
```sql
CREATE TABLE goods (
    id INT PRIMARY KEY,
    name VARCHAR(64) NOT NULL,
    price DECIMAL(10,2) NOT NULL,
    version INT NOT NULL DEFAULT 0 -- 乐观锁版本号
);
```

#### 读-改-写标准协作流程
1. **第一步（读数据与当前版本）**：
   ```sql
   SELECT id, name, price, version FROM goods WHERE id = 10;
   -- 读出: price = 100.00, version = 5
   ```
2. **第二步（应用层业务逻辑运算）**：应用层进行复杂校验或多字段属性组装；
3. **第三步（带版本校验的原子写回）**：
   ```sql
   UPDATE goods 
   SET price = 120.00, version = version + 1 
   WHERE id = 10 AND version = 5;
   ```
4. **第四步（检查受影响行数）**：
   - 若 `Affected Rows == 1`：说明在此期间没有其他事务修改过该行，更新成功，版本号推进至 6；
   - 若 `Affected Rows == 0`：说明在此期间已有其他事务抢先修改并提交了数据（该行当前 `version` 已不再是 5）。当前修改自动作废，应用层选择向用户提示“数据已被他人修改，请刷新后重试”，或者重新读取最新版本并自动重试计算。

```text
       事务 A (读 version=5)                       事务 B (读 version=5)
              │                                           │
       (本地完成逻辑计算)                          (本地完成逻辑计算)
              │                                           │
  UPDATE ... WHERE version=5                  UPDATE ... WHERE version=5
              │                                           │
       [ 抢先获得行锁 ]                            [ 排队等待 A 提交 ]
       更新成功, version 变为 6                           │
       Affected Rows = 1                                  │
       COMMIT                                             ▼
                                                   [ 获得行锁，读最新数据 ]
                                                   发现当前 version=6 ≠ 5
                                                   更新失败！
                                                   Affected Rows = 0 (冲突拦截)
```

乐观锁在数据库层面没有任何长期的锁等待开销，极其适合**读多写少、并发冲突概率低**的业务场景。

## 3. 什么时候需要锁定读 / 悲观并发控制？

当业务面临**高并发高冲突的热点争抢**，或者业务逻辑要求**先读取数据并在后续多步决策中绝对阻止其他事务并发修改**时，必须使用锁定读（悲观并发控制）。因为在这些场景下，乐观锁会导致海量请求因版本失效而剧烈空转（活锁），单条条件更新也无法跨多步保护读取状态；通过 `SELECT ... FOR UPDATE` 施加行排他锁让请求有序排队，才能以最低的系统开销确保长链路决策的正确性。

具体映射到系统设计中，主要包含三类场景：
1. **热点库存与配额的高冲突争抢**：高竞争下乐观锁重试会导致活锁雪崩（绝大多数请求在消耗 CPU 后失败），排他锁排队能保障确定的服务吞吐底线；
2. **读写强依赖的多步骤分支事务**：业务逻辑需要依据当前读取的数据快照执行跨表写入或状态预占，后续操作无法浓缩为单条原子条件更新；
3. **关键状态流转的排他保护**：在当前事务提交或回滚前，必须严格禁止任何并发事务介入修改目标记录。

---

### 3.1 锁定读语法：FOR UPDATE 与 FOR SHARE

InnoDB 提供了两种显式的悲观锁定读语法，用于将原本不加锁的快照读转换为**当前读（Current Read）**并施加行级物理锁：

```sql
-- 1. 排他锁锁定读 (Exclusive Lock, X 锁)
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

-- 2. 共享锁锁定读 (Shared Lock, S 锁)
SELECT * FROM accounts WHERE id = 1 FOR SHARE; -- (历史语法: LOCK IN SHARE MODE)
```

#### 锁兼容性矩阵
InnoDB 行级锁在物理上遵循经典的读者-写者互斥协议：

| 现有持锁状态 \ 申请锁类型 | **Shared (S 锁)** | **Exclusive (X 锁)** |
|---|:---:|:---:|
| **已持有 Shared (S 锁)** | ✅ 兼容（允许并发读取） | ❌ 互斥（排队等待） |
| **已持有 Exclusive (X 锁)** | ❌ 互斥（排队等待） | ❌ 互斥（排队等待） |

- **`FOR UPDATE`（X 锁）**：表示“当前事务准备修改这行记录”。其他事务既不能修改它，也不能对其施加任何锁定读（无论是 `FOR UPDATE` 还是 `FOR SHARE`）。其他事务执行普通的快照读 `SELECT` 仍可正常读取（通过 Undo Log 版本链，不被阻塞）；
- **`FOR SHARE`（S 锁）**：表示“当前事务只读，但必须阻止其他事务修改它”。多个事务可以并发获取同一行的 S 锁，但在所有 S 锁释放之前，任何试图获取 X 锁的更新都会被阻塞挂起。

---

### 3.2 悲观锁定的物理生命周期与代价

悲观锁的本质是以**降低并发吞吐为代价换取绝对的执行确定性**。开发者必须对悲观锁的生命周期有深刻的物理认知：

```text
START TRANSACTION; 
       │
       ▼
SELECT ... FOR UPDATE; ──> [ 成功获取行排他锁 (X 锁) ]
       │
       ├── 执行复杂业务计算...
       ├── 执行分支写操作...
       │
       ▼
COMMIT / ROLLBACK;    ──> [ 行排他锁正式释放 ]
```

> [!WARNING]
> **行锁一旦申请成功，绝对不会在语句执行完毕后立即释放，而是必须一直持有到整个事务正式 `COMMIT` 或 `ROLLBACK` 为止！**
> 如果在一个包裹了 `SELECT ... FOR UPDATE` 的长事务中执行耗时操作，其他所有试图修改同一行的并发事务都会全部卡在锁等待队列中，直接造成连接池打满与级联超时。

## 4. InnoDB 到底锁住什么，为什么访问路径会改变锁范围？

在 InnoDB 存储引擎中，**行锁在物理上从来不是直接锁在“数据记录或业务主键”这个逻辑概念上的，而是锁在扫描时所命中的 B+Tree 索引记录（Index Record）与索引间隙之上的**。正因为锁寄生于索引，**访问路径（Access Path，即执行计划实际使用的索引与扫描范围）从根本上决定了锁的范围与形态**。

如果一条更新语句没有走任何有效索引，MySQL 无法在物理索引树上精准定点加锁，就会退化为全表扫描，将聚簇索引上的所有记录以及所有记录之间的间隙全部加锁，从而造成“锁住整张表”的严重并发写阻塞。

---

### 4.1 InnoDB 三种核心行锁算法

在 RR（可重复读）隔离级别下，InnoDB 的行锁包含三种具体形态：

```text
                  InnoDB 行锁形态谱系
                          │
       ┌──────────────────┼──────────────────┐
       ▼                  ▼                  ▼
[ Record Lock ]     [ Gap Lock ]     [ Next-Key Lock ]
   记录锁              间隙锁            临键锁 (默认)
锁定物理索引单行   锁定记录之间的开区间  锁定行 + 前方间隙
     [row]             (gap)             (gap, row]
```

1. **Record Lock（记录锁）**：仅仅锁住索引树上的某一个具体物理叶子节点。例如唯一索引等值查询命中了已经存在的记录时，只需加单行 Record Lock；
2. **Gap Lock（间隙锁）**：锁住两个索引记录之间的开区间 `(A, B)`，或者第一条记录之前、最后一条记录之后的无穷大开区间 `(B, +∞)`。**间隙锁的唯一使命就是阻止并发事务在这一区间内执行 `INSERT`**，从而在当前读场景下杜绝幻读；
3. **Next-Key Lock（临键锁）**：**InnoDB 在 RR 级别下的默认行锁算法**。它是记录锁与间隙锁的组合，锁定的是一个**左开右闭区间 `(A, B]`**，即同时锁住记录 `B` 本身以及 `B` 前方的间隙。

> [!NOTE]
> **快照读与锁定读的幻读防护边界**：在普通快照读下，幻读由 MVCC 的 Read View 历史版本可见性裁定解决，读操作不加任何锁；而在锁定读（当前读，如 `SELECT ... FOR UPDATE`、`UPDATE`）模式下，由于必须触碰并锁定物理最新数据，历史快照失效，防范幻读的职责完全交接给 Gap Lock 与 Next-Key Lock 物理屏障，通过直接阻塞并发 `INSERT` 来阻止新行产生。

### 4.2 访问路径推导：不同 SQL 怎样在 B+Tree 上划定锁范围？

假设有一张表 `t`，包含主键 `id`（聚簇索引）与普通索引 `c`：

```sql
CREATE TABLE t (
    id INT PRIMARY KEY,
    c INT,
    d INT,
    KEY idx_c (c)
);
-- 预置数据: (1, 10), (5, 50), (10, 100), (15, 150)
```

在 RR 级别下，不同访问路径对加锁范围的影响遵循以下精准推导规则：

#### 场景一：主键 / 唯一索引等值查询（存在记录）
```sql
SELECT * FROM t WHERE id = 5 FOR UPDATE;
```
- **推导过程**：通过主键 B+Tree 唯一索引定点检索，发现 `id = 5` 的记录确实存在。
- **锁降级机制**：Next-Key Lock 原本范围为 `(1, 5]`，但因为主键具有绝对唯一性，不可能在 `id = 5` 的前隙插入新的 `id = 5`，因此**临键锁自动降级为单纯的 Record Lock**，仅锁住 `id = 5` 这一单行。间隙不加锁，完全不影响并发向 `id ∈ (1, 5)` 插入新数据。

#### 场景二：主键 / 唯一索引等值查询（不存在记录）
```sql
SELECT * FROM t WHERE id = 7 FOR UPDATE;
```
- **推导过程**：在主键 B+Tree 上寻找 `id = 7`，未找到。向右扫描遇到第一条大于 7 的记录是 `id = 10`。
- **锁形态**：原本的 Next-Key Lock 范围为 `(5, 10]`。但由于 `id = 7` 不存在，为了防止并发插入 `id = 7`，同时又无需锁定不存在的记录本身，**锁退化为纯间隙锁 Gap Lock `(5, 10)`**。此时任何事务向该区间执行 `INSERT (如 id=6, 8, 9)` 均会被阻塞挂起。

#### 场景三：普通非唯一二级索引等值查询
```sql
SELECT * FROM t WHERE c = 50 FOR UPDATE;
```
- **推导过程**：`c` 是非唯一二级索引，叶子节点取值可以重复。
- **锁范围扩散**：
  1. 首先在二级索引 `idx_c` 上扫描命中 `c = 50`，加上 Next-Key Lock `(10, 50]`；
  2. 为了防止并发事务在 `c = 50` 后面插入相同的 `50`，扫描必须继续向右探测，直到读到第一条不相等的记录 `c = 100`，在该记录上加上间隙锁 `(50, 100)`；
  3. 同时，对二级索引回表命中的聚簇索引主键 `id = 5` 加上单行 Record Lock。
- **结论**：总共锁定了二级索引的 `(10, 100)` 整个连续间隙！任何试图向该间隙插入 `c ∈ (10, 100)` 的操作全被阻塞。

#### 场景四：无索引更新（全表扫描退化）
```sql
UPDATE t SET d = 99 WHERE d = 88;
```
- **推导过程**：列 `d` 没有建立任何索引。
- **级联加锁后果**：优化器只能选择主键聚簇索引执行全表扫描。扫描过程必须遍历每一行物理记录，导致聚簇索引上的**所有记录被全部加上 Next-Key Lock，整张表的所有数据行与所有间隙彻底被锁死**！在整个事务提交前，其他并发事务对该表的任何 `INSERT`、`UPDATE`、`DELETE` 全部被阻塞。

### 4.3 隔离级别对锁范围的根本剪裁：RC vs RR

为什么现代互联网大厂普遍将全局隔离级别调整为 RC？从锁范围的物理开销上可以得到清晰解释：

| 机制维度 | **Read Committed (RC)** | **Repeatable Read (RR)** |
|---|---|---|
| **默认行锁算法** | **仅 Record Lock（记录锁）** | **Next-Key Lock（记录锁 + 间隙锁）** |
| **间隙锁（Gap Lock）** | 默认彻底关闭（仅在外键约束检查与唯一性冲突时使用） | 默认全程开启，用于强行防御当前读下的幻读 |
| **全表扫描加锁处理** | **非匹配行锁释放与半一致性读**：<br>1. 扫描过程中不满足 `WHERE` 条件的行评估后**立即释放行锁**；<br>2. 遇已被他事务加锁的行时触发 **Semi-Consistent Read**（读取 Undo 最新已提交快照评估，不满足则跳过锁等待） | 扫描经过的所有行及其间隙全部持有 Next-Key Lock 直至事务提交 |
| **并发锁冲突概率** | **极低**。锁仅覆盖实际匹配修改的行 | **极高**。范围锁与间隙锁极易产生交叠与死锁 |

## 5. Lock Wait 和 Deadlock 有什么区别，失败后怎样恢复？

锁等待（Lock Wait）与死锁（Deadlock）的本质区别在于**是否存在资源申请的循环等待依赖环**：
1. **锁等待（Lock Wait）是单向的线性排队**：事务 A 持有资源 1，事务 B 申请资源 1 被阻塞挂起。只要事务 A 提交或回滚释放锁，事务 B 就能立即获取锁并恢复执行；若事务 A 长时间未释放，事务 B 等待超过预设阈值（`innodb_lock_wait_timeout`，默认 50 秒），事务 B 报错超时退出；
2. **死锁（Deadlock）是闭合的有向循环依赖环**：事务 A 持有资源 1 并申请资源 2，而事务 B 持有资源 2 同时申请资源 1。双方互相等待对方释放资源，进入理论上永不自行解脱的僵死状态。

面对两者的失败恢复策略也有根本不同：锁等待超时后默认仅回滚当前超时的单条语句，应用层必须显式回滚整个活跃事务并由业务决定是否重试；而死锁发生时，InnoDB 会通过 Wait-for Graph 算法毫秒级检测出闭环，主动挑选成本最低的事务作为牺牲者（Victim）执行全事务强制回滚并释放其持有的所有锁，应用层应捕获 `ERROR 1213` 并通过指数退避机制自动发起全事务幂等重试。

```text
[锁等待：线性排队]
事务 A (持有行 1) <── 阻塞等待 ── 事务 B (申请行 1) ──> (等待超时或 A 释放)

[死锁：循环依赖环]
事务 A (持有行 1) ─── 申请 ───> 资源 2
   ▲                              │ (已被持有)
   │ (已被持有)                   ▼
资源 1 <─── 申请 ─── 事务 B (持有行 2)
```

---

### 5.1 死锁发生场景物理推演

最经典且高频的死锁场景是两个并发事务以**相反的时序申请多行资源的排他锁**：

| 时刻 | 事务 A | 事务 B |
|:---:|---|---|
| **T1** | `START TRANSACTION;` | `START TRANSACTION;` |
| **T2** | `UPDATE accounts SET balance = balance - 10 WHERE id = 1;`<br>*(成功获取 id=1 的 X 锁)* | — |
| **T3** | — | `UPDATE accounts SET balance = balance - 20 WHERE id = 2;`<br>*(成功获取 id=2 的 X 锁)* |
| **T4** | `UPDATE accounts SET balance = balance + 10 WHERE id = 2;`<br>*(**陷入阻塞等待**：等待事务 B 释放 id=2 的锁)* | — |
| **T5** | — | `UPDATE accounts SET balance = balance + 20 WHERE id = 1;`<br>*(申请 id=1 的锁，**闭合死锁环形成！**)* |
| **T6** | — | **InnoDB 侦测到死锁并干预：**<br>`ERROR 1213: Deadlock found`<br>*(事务 B 被选为 Victim 强制回滚释放锁；事务 A 成功解除阻塞继续执行)* |

---

### 5.2 如何排查活跃锁等待与读懂死锁日志？

在排查并发锁故障时，首先必须区分**当前正在发生的活跃锁等待**与**已结束并回滚的死锁事后分析**：

1. **当前正在发生阻塞（活跃锁等待排查）**：
   此时死锁尚未形成或事务正在线性排队超时，`SHOW ENGINE INNODB STATUS` 无法呈现完整的实时等待链路。必须通过 `performance_schema` 实时排查阻塞与被阻塞线程：
   ```sql
   -- 查看当前处于等待状态的锁与阻塞源头事务
   SELECT 
       r.trx_id waiting_trx_id, r.trx_mysql_thread_id waiting_thread,
       r.trx_query waiting_query,
       b.trx_id blocking_trx_id, b.trx_mysql_thread_id blocking_thread,
       b.trx_query blocking_query
   FROM performance_schema.data_lock_waits w
   JOIN information_schema.innodb_trx b ON b.trx_id = w.blocking_engine_transaction_id
   JOIN information_schema.innodb_trx r ON r.trx_id = w.requesting_engine_transaction_id;
   ```
2. **事务已报错 ERROR 1213（死锁事后现场取证）**：
   死锁发生后引擎已自动选出 Victim 强制回滚。此时执行以下指令查看最近一次死锁的现场快照（若需完整持久化所有死锁日志，可开启 `innodb_print_all_deadlocks = ON` 自动输出到错误日志中）：
   ```sql
   SHOW ENGINE INNODB STATUS\G
   ```

在该输出的 `------------------------ LATEST DETECTED DEADLOCK ------------------------` 段落中，InnoDB 会清晰打印两个事务的完整现场证据：

```text
*** (1) TRANSACTION:
TRANSACTION 128456, ACTIVE 2 sec starting index read
mysql tables in use 1, locked 1
LOCK WAIT 2 lock struct(s), heap size 1136, 1 row lock(s)
MySQL thread id 42, OS thread handle 140234, query id 891 updating
UPDATE accounts SET balance = balance + 10 WHERE id = 2
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS space id 58 page no 4 n bits 72 index PRIMARY of table `test`.`accounts` 
trx id 128456 lock_mode X locks rec but not gap waiting
Record lock, heap no 3 PHYSICAL RECORD: n_fields 4; ... id=2 ...

*** (2) TRANSACTION:
TRANSACTION 128457, ACTIVE 1 sec starting index read
MySQL thread id 43, OS thread handle 140235, query id 892 updating
UPDATE accounts SET balance = balance + 20 WHERE id = 1
*** (2) HOLDS THE LOCK(S):
RECORD LOCKS space id 58 page no 4 n bits 72 index PRIMARY of table `test`.`accounts` 
trx id 128457 lock_mode X locks rec but not gap
Record lock, heap no 3 PHYSICAL RECORD: ... id=2 ...
*** (2) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS space id 58 page no 4 n bits 72 index PRIMARY of table `test`.`accounts` 
trx id 128457 lock_mode X locks rec but not gap waiting
Record lock, heap no 2 PHYSICAL RECORD: ... id=1 ...

*** WE ROLL BACK TRANSACTION (2)
```

#### 日志三步解码法：
1. **看事务 1 正在等谁**：`(1) WAITING FOR THIS LOCK` 明确标出事务 1 正在等待 `index PRIMARY` 上 `id = 2` 的 X 锁；
2. **看事务 2 持有什么、在等谁**：`(2) HOLDS THE LOCK(S)` 证明事务 2 正持有 `id = 2`，而 `(2) WAITING FOR THIS LOCK` 标明事务 2 又在反向等待事务 1 持有的 `id = 1`；
3. **看决裁结果**：`*** WE ROLL BACK TRANSACTION (2)` 确认系统回滚了修改量更小（代价更低）的事务 2。

### 5.3 生产环境防死锁与失败恢复设计

在工程架构中，消除与应对死锁遵循三道标准防线：

1. **统一资源加锁顺序（根本防线）**：
   业务代码在操作多行记录时，**必须对主键或唯一键进行确定性排序后再依次加锁**。例如无论业务是从 A 向 B 转账，还是从 B 向 A 转账，代码层统一按 `Math.min(idA, idB)` 先锁小 ID，再锁大 ID。加锁顺序一旦全局单向化，资源依赖环在数学上便不可能成立；
2. **压缩事务尺寸，快进快出**：
   严禁长事务。将数据准备、外部调用彻底移出事务外，让事务内仅包含纯粹的 SQL 写操作，将持锁时间压缩在毫秒级内，大幅降低并发碰撞窗口；
3. **应用层幂等重试（兜底恢复）**：
   在分布式与高并发系统中，死锁无法 100% 杜绝，它被视为正常的并发冲突失败。**应用层必须将捕捉 `ERROR 1213`（Deadlock）并配合 Exponential Backoff（指数退避）的安全重试作为标准基础设施**。由于被牺牲的事务已被数据库完整 `ROLLBACK`，重新开启新事务从头执行具备天然安全性（前提是事务具备业务幂等性）。

## 6. 热点计数和高频写为什么需要重新设计更新方式？

热点计数和高频写之所以不能直接依赖单行数据库行锁，是因为**行排他锁（X 锁）对同一行记录的并发写在物理上是严格串行化的；当瞬时并发达到数千 QPS 时，大量事务的连接线程会全部堵塞在等待这单一行锁的队列中，引发应用连接池耗尽、MySQL 内部锁系统严重自旋互斥、以及 CPU 线程上下文切换雪崩**。

此时系统的瓶颈已经不再是“数据是否正确”，而是“物理锁管理开销拖垮了整个数据库实例”。要解决热点并发写，必须打破“所有并发请求同时去争抢单一行排他锁”的集中式设计。

---

### 6.1 方案对比：三种标准架构优化路径

| 优化架构方案 | 核心工程做法 | 吞吐能力提升 | 一致性与工程代价 | 适用场景 |
|---|---|:---:|---|---|
| **1. 原地原子增量** | 抛弃应用读-改-写，使用单条 `UPDATE tbl SET cnt = cnt + 1 WHERE id = 1` | 3x ~ 5x | 强一致。依然受限于单行锁串行耗时（约 1000~3000 QPS 物理上限） | 中等并发、库存扣减、简单防覆盖 |
| **2. 分桶计数器<br>(Slot / Bucketing)** | 将原本 1 行记录在表中拆分为 $N$ 个槽位（如 $N=20$），更新时随机写入 `slot = hash(uid) % N`；查询总数时执行 `SUM(cnt)` | **$N$ 倍线性提升** | 强一致。查询总数变慢（需汇总多行）；余额/库存防穿透校验变复杂 | 点赞数、投票数、大促全局商品已售件数 |
| **3. 异步批量合并<br>(Batch Aggregation)** | 请求先打入内存缓冲（Redis / 应用本地内存），累加计数；后台定时任务按周期（如每 100ms）或按批量打包，发往数据库执行单次合并 `UPDATE cnt = cnt + M` | **100x+ 极高** | 弱一致（最终一致性）。断电宕机存在极短窗口计数值丢失风险 | 视频播放量、文章阅读数、非资产类指标统计 |

### 6.2 分桶计数器（Bucketing）实现模型

```sql
-- 将热点文章 1001 的阅读量拆为 10 个物理槽位 (slot: 0 ~ 9)
CREATE TABLE article_views_slot (
    article_id INT NOT NULL,
    slot INT NOT NULL,
    view_count INT NOT NULL DEFAULT 0,
    PRIMARY KEY (article_id, slot)
);

-- 并发写时：由应用层计算随机槽位（例如 Java 的 ThreadLocalRandom.current().nextInt(10)）
-- 传入具体整数参数执行更新，避免在 SQL WHERE 条件中使用非确定性 RAND() 函数导致扫描与复制问题：
UPDATE article_views_slot 
SET view_count = view_count + 1 
WHERE article_id = 1001 AND slot = ?;

-- 读取总阅读量时：聚合汇总
SELECT SUM(view_count) FROM article_views_slot WHERE article_id = 1001;
```

通过简单的行拆分，原本集中在单行的锁等待压力被瞬间稀释至原来的 $\frac{1}{10}$，消除了热点单行排他锁的排队瓶颈。

## 7. MySQL 锁能不能直接当通用分布式锁？

MySQL 锁**不能直接当作通用的高可用分布式锁使用**。尽管基于唯一索引冲突（`INSERT ... ON DUPLICATE`）、命名锁（`GET_LOCK()`）或事务行排他锁（`FOR UPDATE`）可以在轻量级系统中充当临时的互斥协调工具，但数据库锁的物理机制与分布式锁的核心需求存在**根本性的架构失配**：

1. **生命周期强绑定单物理连接与事务**：
   InnoDB 行锁依赖数据库连接（Session）。如果持锁期间应用服务器发生 GC 停顿或网络抖动，导致 MySQL 服务端检测到会话断开（Connection Timeout），MySQL 会自动终止该会话并**强制回滚事务、瞬间释放行锁**。而此时持有锁的应用工作线程可能依然在继续执行任务，分布式互斥性彻底被打破；
2. **缺乏租约（Lease）与防护令牌（Fencing Token）机制**：
   标准的分布式锁协议（如基于 Redis Redlock 或 ZooKeeper/etcd 的实现）必须具备显式的租约超时兜底与递增的 Fencing Token，以防止因客户端挂起导致的“双写脑裂”。MySQL 原生行锁无法向外部系统颁发具备自增代数的协调凭证；
3. **本地数据库管不了不可逆的外部物理世界**：
   数据库锁只能保护**单机数据库实例内部的数据修改**。如果业务持锁的目的是去调用外部第三方支付网关、向消息队列发送不可撤回的消息，无论数据库怎么加锁，一旦网络发生分区或超时，数据库锁都无法阻止外部系统产生不可逆的副作用。

```text
               分布式协调系统的边界
                         │
       ┌─────────────────┴─────────────────┐
       ▼                                   ▼
[ 适合使用 MySQL 锁的场景 ]          [ 必须使用独立分布式协调的场景 ]
- 协调单库内多表操作的执行顺序       - 跨物理微服务、跨多数据源协同
- 低频、防重复点击的轻量防重         - 需要毫秒级失效租约与健康心跳探活
- 不愿引入额外中间件的边缘小项目     - 保护外部不可逆系统 (RPC / 支付网关 / MQ)
                                     - 需要 Fencing Token 杜绝脑裂的强一致场景
```

## 知识回顾：并发修改与锁机制的因果闭环

1. **从原子性陷阱到写前提保护**：事务原子性仅防中途崩溃，不防“读-改-写”的旧值盲写覆盖；解决第二类丢失更新的根本手段是将业务前提嵌入写操作自身，通过原语化条件更新或版本号乐观锁，以 Affected Rows 裁定并发修改是否合法。
2. **乐观与悲观的工程分水岭**：乐观锁适用于低冲突、单步写场景；当业务涉及多步骤跨表推演、热点秒杀高冲突、或必须强行杜绝状态漂移时，必须使用 `SELECT ... FOR UPDATE` 悲观锁定读。
3. **锁对索引访问路径的绝对寄生**：InnoDB 行锁在物理上锁在索引叶子记录与间隙上。主键等值命中降为单行 Record Lock；唯一索引未命中退化为间隙锁；二级索引等值扩展为 Next-Key Lock 加相邻间隙；无索引更新则直接退化为锁全表。
4. **隔离级别的锁剪裁**：RC 默认关闭间隙锁，极大降低了死锁概率与锁持有开销；RR 为了在当前读下防范幻读，强制维持 Next-Key Lock。
5. **死锁的本质与治理**：死锁是资源等待的闭合有向环。治理死锁的核心是推行全局统一的加锁时序、压缩事务尺寸，并在应用层落地捕获错误后的指数退避幂等重试。
6. **热点写与分布式协调的架构边界**：单行行锁具有物理串行化瓶颈，高频计数应采用分桶或异步批量合并；MySQL 锁受限于数据库会话生命周期与外部副作用无能为力，不可滥用于复杂分布式协调。

## 🎯 面试怎么回答

### 为什么业务开启了事务，并发修改时依然会出现数据被覆盖？

> [!TIP]
> 事务的原子性只保证单事务内部操作全做或全不做，不保证并发调度的正确性。在“读-改-写”业务中，多个事务基于相同的快照旧值在内存中计算，随后依次写回，后提交的事务会直接盲写覆盖先提交事务的结果，引发第二类丢失更新。根本原因在于快照读读取的是历史版本，如果写操作不带前置前提校验，数据库无法识别业务逻辑已经被破坏。

### 什么是条件更新？它和乐观锁有什么关系？

> [!TIP]
> 条件更新是指将业务前提直接嵌入写语句的 `WHERE` 条件中（如 `UPDATE accounts SET balance = balance - 10 WHERE id = 1 AND balance >= 10`），借助存储引擎对更新行施加的排他锁，将“状态校验”与“物理修改”合为一体。乐观锁是条件更新的一种标准化实现形式，通常在表中引入 `version` 字段，更新时校验 `WHERE id = 1 AND version = old_version`，并通过驱动返回的受影响行数（Affected Rows）判定修改是否成功，以此规避长期的锁等待。

### 既然有了乐观锁，为什么还需要 SELECT ... FOR UPDATE 悲观锁？

> [!TIP]
> 乐观锁仅适用于单步写即可闭合的低冲突场景。在秒杀等高并发高竞争场景下，大量请求并发访问同一行，乐观锁会导致几千个请求同时因版本失效而报错重试，引发活锁并剧烈浪费 CPU；而在涉及跨表多步判断、必须根据读取结果执行分支逻辑的长链路中，乐观锁无法提供跨语句的排他保证。此时使用 `SELECT ... FOR UPDATE` 施加排他锁让并发请求有序排队，整体吞吐更可控，业务正确性更有保障。

### InnoDB 的行锁究竟锁住了什么？为什么无索引更新会引发锁全表？

> [!TIP]
> InnoDB 的行锁在物理上从来不是锁在记录本身，而是锁在扫描时经过的 B+Tree 索引记录（Record Lock）与索引区间的间隙（Gap Lock / Next-Key Lock）之上的。锁的范围直接取决于执行计划的访问路径（Access Path）。如果更新语句没有走任何有效索引，存储引擎只能遍历主键聚簇索引执行全表扫描，导致聚簇索引上所有的记录以及所有记录之间的间隙全部被施加 Next-Key Lock，物理上等同于锁死了整张表。

### 锁等待（Lock Wait）与死锁（Deadlock）有什么区别？生产上怎样解决死锁？

> [!TIP]
> 锁等待是单向的线性排队，等待锁释放或超时报错；死锁是多个事务之间形成了互相等待对方释放资源的闭合依赖环，必须由 InnoDB 的 Wait-for Graph 算法检测出环路，并强制回滚成本最低的事务作为牺牲者。解决死锁的核心方案包括：业务层严格按固定顺序（如主键升序）对多行加锁以打破循环依赖、收缩事务减少持锁时间、以及在应用层实现捕获 Deadlock 错误后的指数退避幂等重试。

### 为什么大促秒杀时不能直接对单行库存执行 UPDATE 扣减？有哪些解法？

> [!TIP]
> 单行记录的排他锁在物理上是严格串行化的。瞬时高并发冲入时，大量工作线程全部堵在单一行锁的等待队列中，会导致应用连接池被瞬间打满、数据库线程上下文切换暴增，进而引发雪崩。标准解法包括：将单行库存拆分为多个槽位（分桶计数器，Bucketing）分散行锁压力；或者将高频写前置到 Redis 进行原子扣减，后台异步批量合并更新到 MySQL。

### 能不能把 MySQL 的排他锁直接当作微服务架构下的分布式锁？

> [!TIP]
> 不能。MySQL 行锁的生命周期严格绑定在单条物理连接和数据库会话上。如果应用发生长时间 GC 停顿或网络抖动，数据库会因连接超时而自动关闭会话并回滚事务释放行锁，此时原线程可能仍在执行任务，导致互斥性失效；此外，MySQL 锁无法提供租约续期机制与防脑裂的 Fencing Token，且根本无法拦截外部网络 RPC 等不可逆的物理副作用。

## ⚠️ 易错点

> [!WARNING]
> **别把事务的原子性（A）当成并发互斥的银弹。** 开启 `@Transactional` 无法阻止两个线程同时读到相同库存并在内存中算错。多步修改必须依赖条件更新或排他锁。

> [!WARNING]
> **无索引的 UPDATE 是大面积写阻塞的主要源头。** 缺乏索引支撑的更新语句会触发聚簇索引全表扫描，将全表所有记录和间隙加上 Next-Key Lock，瞬间阻塞整张表的所有并发写入。

> [!WARNING]
> **`SELECT ... FOR UPDATE` 必须在显式事务中使用。** 如果在默认 `autocommit=1` 且未开启事务的情况下执行该语句，锁在当前查询语句执行完毕的一瞬间就会被隐式提交释放，根本起不到保护后续修改的作用。

> [!WARNING]
> **死锁不是代码写错导致的系统级宕机故障，而是并发下的正常竞争结果。** 生产系统不能寄希望于 100% 杜绝死锁，应用层必须具备捕获死锁报错并自动重新发起整个事务的幂等重试机制。

> [!WARNING]
> **更新语句中受影响行数（Affected Rows）为 0 不等于发生异常。** 在条件更新与乐观锁场景下，返回 0 是业务前提不满足的明确物理信号，代码中必须主动判断并抛出业务异常触发回滚，绝不能忽略返回值。

> [!WARNING]
> **间隙锁在 RC 隔离级别下默认关闭。** 如果业务必须依赖间隙锁防范当前读下的幻读，绝不能随意将数据库隔离级别降为 RC，否则当前读在范围查询下会暴露并发插入。

> [!WARNING]
> **多个字段同时乐观更新时严禁版本回退。** 版本号必须单调递增（`version = version + 1`），严禁使用客户端计算后的任意数值盲写，否则会彻底瓦解 CAS 校验链。

<details>
<summary><strong>1. 什么是第二类丢失更新？请举一个简短的账户转账例子。</strong></summary>

第二类丢失更新是指两个事务同时读取某行的旧值，事务 A 修改并提交后，事务 B 也基于先前读到的旧值完成修改并提交，事务 B 彻底覆盖了事务 A 已生效的修改。例如余额为 100，A 扣 20 算得 80 提交；B 并发扣 30 算得 70 提交，最终余额为 70，A 扣除的 20 元凭空丢失。

</details>

<details>
<summary><strong>2. 为什么条件更新可以解决高并发下的超卖问题？</strong></summary>

条件更新将校验与写入合一（如 `WHERE id = 1 AND stock >= count`）。由于 UPDATE 是当前读，数据库在施加行排他锁的互斥保护下读取最新库存并执行判断。并发请求被迫排队，库存不足时受影响行数返回 0，杜绝了超卖。

</details>

<details>
<summary><strong>3. 乐观锁在什么场景下性能反而会急剧劣于悲观锁？</strong></summary>

在极高并发且写入冲突极其集中的热点场景（如热门秒杀商品）下。乐观锁会导致绝大多数并发请求因版本号冲突而不断失败并触发重试，造成系统 CPU、网络资源急剧空耗的“活锁”现象，性能远不如让请求在悲观锁下有序排队。

</details>

<details>
<summary><strong>4. 在 RR 隔离级别下，执行 SELECT * FROM t WHERE id = 10 FOR UPDATE（id 为主键且记录存在），实际加的是什么锁？为什么？</strong></summary>

加的是单行记录锁（Record Lock）。虽然 RR 默认使用 Next-Key Lock，但对于主键和唯一索引的等值查询，当命中已存在的物理行时，由于唯一性约束保证了不可能在该行前隙插入相同的键值，系统会自动将 Next-Key Lock 降级为单纯的 Record Lock。

</details>

<details>
<summary><strong>5. 什么是间隙锁（Gap Lock）？它的核心存在价值是什么？</strong></summary>

间隙锁锁定的是两个物理索引记录之间的开区间 `(A, B)`。它的唯一核心价值是阻止其他并发事务在这一区间内执行 `INSERT` 插入新行，从而在当前读（Current Read）模式下彻底杜绝幻读。

</details>

<details>
<summary><strong>6. 为什么执行没有建立索引的 UPDATE 语句会导致整个业务系统大面积阻塞？</strong></summary>

因为没有走索引，MySQL 只能走主键聚簇索引扫描整张表。扫描过程中会对表中的每一行记录及其相邻间隙全部施加 Next-Key Lock，导致整张表的所有记录与所有区间都被锁定，直到事务提交，期间任何并发写入全部被挂起。

</details>

<details>
<summary><strong>7. 锁等待超时参数 innodb_lock_wait_timeout 默认是多少秒？超时后事务会自动整体回滚吗？</strong></summary>

默认是 50 秒。超时发生时，MySQL 默认只回滚当前等待超时的单条 SQL 语句，整个事务并不会自动全部回滚。应用层必须显式捕获该异常并决定是否执行 `ROLLBACK`。

</details>

<details>
<summary><strong>8. 发生死锁时，InnoDB 依据什么原则挑选哪一个事务作为牺牲者（Victim）执行回滚？</strong></summary>

InnoDB 会计算事务的撤销日志量（Undo 记录数）和修改的权重，优先挑选事务体量较小、已经写入的 Undo 数据量最少、回滚成本最低的事务作为牺牲者回滚，以最小化物理恢复代价。

</details>

<details>
<summary><strong>9. 解决多行更新死锁最标准的代码设计规范是什么？</strong></summary>

按确定的全局顺序对数据主键进行排序后再加锁。例如在业务层将所有待锁定的记录按 `id` 升序排列，无论业务方向如何，所有线程都严格按照从小到大的顺序申请行锁，从拓扑上消除循环依赖环。

</details>

<details>
<summary><strong>10. 为什么 MySQL 的行锁不能直接充当保护第三方支付调用的分布式锁？</strong></summary>

行锁的生命周期依赖于数据库物理连接与会话。如果应用线程发生 GC 卡顿或网络波动，MySQL 服务端会判定连接超时而自动关闭连接并回滚事务释放锁；此时应用线程可能误以为自己依然持锁而在外部发起扣款，且本地事务回滚根本无法撤销已向外部银行发出的网络请求。

</details>

2. **乐观锁适合读多冲突少，高频热点争抢必须果断上排他锁排队。**
3. **行锁从来不锁业务名，索引叶子与间隙才是锁的物理真身。**
4. **无索引的更新锁全表，等值主键降级为单行，非唯一索引锁一片。**
5. **死锁是并发的家常便饭，统一时序治其本，退避重试保其底。**
6. **本地行锁管不了外部世界，高并发计数靠分桶，跨系统协调归分布式。**
