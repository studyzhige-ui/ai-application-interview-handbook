# 17｜CDC：把已提交的变化可靠地交给下游

[← 复制与读写分离：多份数据何时一致](16-复制与读写分离.md) · [MySQL 目录](../README.md) · [分片：确认单机边界之后再拆数据 →](18-分片与扩容.md)

文档名称已经在数据库里改了，搜索结果却仍显示旧名称。保存操作并没有失败，只是搜索系统保存着另一份数据，不会因为 MySQL 提交就自动更新。

这时需要一条变化传播的路径：数据库确认发生了什么，再让下游据此修改自己的副本。**CDC（变化数据捕获）负责发现并传出这些变化；它不让两个系统瞬间变成同一个事务。**

## 1. 从“同时写两边”改为“依据已提交变化继续处理”

应用可以先修改 MySQL，再调用搜索系统更新名称。但第二步失败时，数据库已经是新版，搜索仍是旧版；把顺序反过来，又可能先更新搜索、最后数据库回滚。问题不只是操作顺序，而是两边不能共同原子提交。

基于 Binlog 的 CDC 采用另一种安排：

```text
MySQL 事务提交
       ↓
Binlog 中有对应变化
       ↓
CDC 连接器读取并记录位置
       ↓
下游应用变化，更新自己的数据
```

请求先完成数据库内的事务，传播失败后还可以根据保留的变化记录继续处理，不必只依赖原来那个请求进程活着。[Binlog](https://dev.mysql.com/doc/refman/9.7/en/binary-log.html)是这里的变化来源；具体捕获、进度和重放由连接器等组件负责。

中间可以有消息队列，用于缓冲和供多个消费者读取，也可以直接连接目标系统。CDC 与消息队列不是两个同义词：前者负责捕获变化，后者负责承接和传递消息。

## 2. 消费者要知道改谁、改什么，以及处理到哪里

假设业务把文档 7 从版本 2 更新为版本 3，标题改为“新版说明”。可以先用四项信息理解一条事件：

| 信息 | 本例的值 | 用来作什么决定 |
|---|---|---|
| 对象身份 | 团队 10、文档 7 | 定位应修改的下游对象 |
| 变化内容 | 更新标题为“新版说明” | 决定写入什么；删除则执行相应清理 |
| 业务版本 | 3 | 判断是不是比已知状态更新 |
| 消费位置 | 某个可恢复的日志位置 | 中断以后从哪里继续读取 |

这里的版本 3 是**应用明确维护的业务版本**，不是说 Binlog 自动给每行附上同名字段。日志位置也不等于业务版本：一次事务可以改多行，同一个对象可以连续变化，二者服务不同目的。

真实事件有哪些前后列值，取决于日志设置与连接器格式。知道“这是一个行更新”也不等于已经知道完整业务含义，例如它是审批通过、补录还是数据修复。

当下游需要明确的业务事件，可以在业务事务里同时写一条待发布记录，说明“文档新版已提交”。这个表常称为 **Outbox（待发事件表）**，之后可以由 CDC 读取并发布。它与业务修改一起提交，但外部发布仍可能重复或延迟。

## 3. 重复、乱序与删除，分别会怎样破坏结果

先看重复。消费者已更新搜索系统，还没保存进度就崩溃。恢复后从旧位置继续，同一事件会再来一次。反过来先保存进度、后更新目标，若中途崩溃，又可能永久漏掉目标更新。因此，**处理结果和进度不能共同提交时，必须设计重复处理安全，而不是只交换两步顺序。**

按对象键把同一标题写成相同值，通常不会增加一次额外效果；“用量加一”或“再发通知”则不同，需要额外识别这个动作是否已经处理。先查询、再写入也可能与另一个消费者竞争，关键检查和修改要由目标系统原子执行。

乱序解决的是另一个问题：版本 3 已经应用，迟到的版本 2 不能把它改回去。可以在目标系统中原子地比较业务版本，再决定是否更新。

| 已知状态 | 到达事件 | 本例的处理 |
|---|---|---|
| 版本 2 | 更新到版本 3 | 接受新版 |
| 版本 3 | 再次更新到版本 3 | 不重复产生效果 |
| 版本 3 | 更新到版本 2 | 拒绝倒退 |
| 版本 3 | 版本 4 删除 | 删除内容，保留必要的新旧边界 |
| 已删除，边界为 4 | 迟到的版本 3 更新 | 不让文档复活 |

删除时若连版本边界也一起丢掉，迟到旧事件可能被当成新对象重新插入。带版本的删除标记是一种处理办法；标记保留多久，还必须与事件可能重放多久配合。这是本例的消费策略，不是所有 CDC 产品默认保证。

## 4. 第一次建立下游，还需要把历史与增量接起来

新建搜索索引时，仅从最新日志开始订阅是不够的：一年前写入、此后从未更新的文档，不会凭空重新产生事件。因此要先取得历史数据，再追上扫描期间发生的变化。

危险做法是花几小时扫描全表，扫描结束后才记录“此刻的日志位置”。某条记录被扫描后又发生更新，这次更新可能既不在扫描结果里，又位于选定增量起点之前，于是遗漏。

正确做法需要协调**一致快照与日志位置**：知道历史快照对应哪条变化边界，确保衔接期间的日志仍可读取，再按协议完成全量与增量追平。不能用一个随手记录的时间戳代替这项保证。[Debezium 的 MySQL 连接器文档](https://debezium.io/documentation/reference/stable/connectors/mysql.html)给出了一种具体的快照、位点与恢复实现；这里解释通用问题，不要求先安装整套平台。

## 5. 持续运行，要能解释“落后了”和“恢复不了”

下游处理得比源写入慢，延迟会逐步增大。先分开观察捕获、排队和目标写入，确认瓶颈在哪一段，再限制输入、调整批量或增加可并行的处理能力。反复重启不能解决持续的速度差。

表结构也会变化。源新增字段成功，不代表旧消费者已会解析它；恢复时还可能重放旧格式事件。需要保留兼容规则，并明确哪些变化要与消费者一起发布。

> ⚠️ 消费者停得太久，原来的 Binlog 可能已过保留期。恢复位置还在，不代表对应日志还在；此时可能需要重新建立快照，不能声称一定可以从任意历史点继续。

对知识库来说，“元数据已保存”和“新索引已就绪”应分别记录。业务可以接受传播延迟，但需要知道在等待什么、何时算就绪、失败如何发现。这比把异步链路统称为“已经同步”更有操作依据。

## 本章小结

CDC 从已提交变化驱动下游，减少请求内直接双写的耦合。它仍需要处理重复、顺序、删除边界、历史与增量衔接，以及日志保留和消费进度。

## 🎯 面试怎么回答

### CDC 能否保证下游恰好处理一次？

不能只凭采用 CDC 就这样承诺。目标更新成功但进度未保存时可能重放；需要按目标操作设计幂等或事务协调，并处理乱序与删除。捕获、投递与业务执行是不同保证。

### CDC 与 Outbox 是替代关系吗？

不是。Outbox 在业务事务里显式保存待发布事件，CDC 可以读取该表并向外传播。两者可以配合，但数据库内共同提交不等于外部交付已经完成。

## ⚠️ 易错点

> ⚠️ 业务版本不是日志位点；字段相似也不能混用它们的排序和恢复含义。

> ⚠️ 版本比较与目标修改必须原子执行，先查再写仍有并发窗口。

## 本章自测

<details>
<summary>1. 目标已更新，进度未保存时崩溃，恢复后有什么风险？</summary>

同一事件可能再次处理。覆盖同一确定状态与累加、通知的重复效果不同，需要相应幂等策略。

</details>

<details>
<summary>2. 为什么删除后还可能需要保留版本标记？</summary>

否则迟到旧更新可能重新创建对象，造成删除后复活；边界还要覆盖允许的重放周期。

</details>

<details>
<summary>3. 全量扫描结束后才取最新日志位置，可能漏在哪里？</summary>

某条记录扫描后发生的修改，可能早于该增量起点，既未进入历史快照结果也不会再被消费。

</details>
