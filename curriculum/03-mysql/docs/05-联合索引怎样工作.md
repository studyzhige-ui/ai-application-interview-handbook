# 05｜联合索引怎样服务真实查询

> [!TIP]
> **🎯 本章目标**
>
> 彻底告别对“最左前缀、范围失效、覆盖索引、ICP、文件排序、索引失效”等孤立口诀的死记硬背。从联合索引唯一的**多列复合字典序**出发，深刻推导真实查询在**定位区间、页内过滤、排序消除和列覆盖**四个阶段的底层行为；最终掌握根据一组高频业务 SQL 矩阵反推设计最优联合索引的工程能力。

## 0. 同一棵联合索引，为什么换一种查询写法作用就变了？

任务列表有一个常见查询：

```sql
SELECT id, created_at, title
FROM tasks
WHERE tenant_id = 10
  AND status = 'pending'
ORDER BY created_at DESC
LIMIT 20;
```

为了服务它，通常建立三列联合索引：

```sql
CREATE INDEX idx_tasks_tenant_status_created
ON tasks (tenant_id, status, created_at);
```

该索引包含了查询涉及的全部字段，容易让人产生错觉：“只要查询条件包含这三个字段，这棵索引就能完美生效”。

但稍作变动，情况就会产生质变：
- 若去掉中间的状态过滤：`WHERE tenant_id = 10 ORDER BY created_at DESC`，因为跳过了第二列 `status`，`ORDER BY` 无法直接利用索引顺序，退化为临时文件排序（`Using filesort`）；
- 若索引列顺序定义为 `(tenant_id, created_at, status)`，执行 `WHERE tenant_id = 10 AND created_at >= '2026-10-01' AND status = 'pending'` 时，排在范围条件 `created_at` 之后的 `status` 突然无法用于进一步缩小扫描区间；
- 若只查索引已包含的列：`SELECT tenant_id, status, created_at FROM tasks WHERE tenant_id = 10`，整条查询瞬间免除所有回表开销（`Using index`）。

原因只有一个：**联合索引绝不是把几个单列索引简单打包，而是一棵在物理上严格遵循这几列复合字典序的单一有序 B+Tree。**

> [!IMPORTANT]
> **💡 本章核心认知：一切联合索引的行为特征（最左前缀、范围截断、排序兼容、ICP、覆盖优化），均是这套多列复合字典序在不同查询条件下的自然物理推导。**

## 1. 多列复合字典序：为什么最左前缀会自然出现？

联合索引 `(A, B, C)` 遵循**字典序（Lexicographical Order）**：首先按 `A` 排序；当 `A` 相同时，按 `B` 排序；只有当 `A` 与 `B` 均相同时，才按 `C` 排序。

以 `idx_tasks_tenant_status_created (tenant_id, status, created_at)` 为例，叶子节点索引项在物理上的真实排列如下：

| tenant_id | status | created_at | id (隐式主键) | 物理相对顺序 |
|---:|---|---|---:|---|
| 9 | pending | 10-01 08:00 | 31 | ... |
| **10** | **done** | 10-01 09:00 | 12 | 团队 10 内状态为 done 的区间 |
| **10** | **done** | 10-03 08:30 | 18 | 同上 |
| **10** | **pending** | 10-01 10:00 | 21 | 团队 10 内状态为 pending 的区间 |
| **10** | **pending** | 10-02 09:00 | 25 | 同上 |
| 11 | pending | 10-01 07:00 | 35 | ... |

---

### 1.1 前缀定位的推进过程

- **只给 `WHERE tenant_id = 10`**：因为 `tenant_id` 是最左列，所有 `tenant_id = 10` 的索引项物理聚集在一段连续空间内，引擎能立即锁定该范围；
- **追加 `AND status = 'pending'`**：在 `tenant_id = 10` 的封闭区间内，记录完全按 `status` 排序，因此能进一步将扫描范围精确收敛至更狭窄的连续切片；
- **只给 `WHERE status = 'pending'`**：从表中可以清晰看出，`status = 'pending'` 零散分布在租户 9、10、11 的各个独立分组中，全局上并不连续，B+Tree 无法凭此做区间二分收敛。这就是跳过最左列无法利用索引快速定位的物理根源。

> [!NOTE]
> **条件书写顺序无关紧要：** `WHERE status = 'pending' AND tenant_id = 10` 与先写 `tenant_id` 效果完全相同。优化器会自动根据索引列定义重组条件，不会受 SQL 文本先后顺序的干扰。

## 2. 范围、LIKE 与类型转换：为什么会改变定位能力？

评估一个条件是否“破坏索引”，唯一标准是：**当前条件能否继续利用该索引在物理上的既有顺序，直接圈定一段连续的物理页扫描区间。**

---

### 2.1 范围条件（`>`、`<`、`BETWEEN`）对后续列的定位截断

假设索引定义为 `(tenant_id, created_at, status)`，执行查询：

```sql
WHERE tenant_id = 10
  AND created_at >= '2026-10-01'
  AND status = 'done';
```

1. `tenant_id = 10` 锁定了团队区间；
2. `created_at >= '2026-10-01'` 圈定了时间从 10 月 1 日开始向后的连续范围；
3. 但在这一连续时间区间内，包含许多不同时刻（10-01 09:00, 10-01 10:00, 10-02 08:00...）。在每一个具体时刻内部 `status` 虽有相对顺序，但在整个时间范围跨度上，所有的 `status='done'` 是离散穿插在不同时间点之下的！

因此，第三列 `status` **无法再帮助缩小初始扫描区间**。范围条件截断了后续列用于“缩小范围（Index Seek）”的能力。但注意：**`status` 虽无法缩小扫描区间，却依然可以在扫描该区间时在索引页内就地进行比对过滤（Index Filter / ICP）**，绝非毫无价值。

---

### 2.2 模糊匹配（LIKE）与表达式计算

- **`LIKE 'abc%'` vs `LIKE '%abc'`**：B+Tree 按字符从左至右逐字比较。`'abc%'` 前缀固定，等价于区间范围检索（`>= 'abc' AND < 'abd'`），能高效圈定物理区间；而 `'%abc'` 首字符未知，目标散落在全树各处，无法执行区间收敛。
- **对索引列进行函数包装（如 `DATE(created_at) = '2026-10-01'`）**：树中索引项存储的是原始时间戳，并未预先计算过 `DATE()` 函数值，引擎无法按函数值二分。应将其改写为等价的原始列范围表达式：`WHERE created_at >= '2026-10-01 00:00:00' AND created_at < '2026-10-02 00:00:00'`。
- **隐式类型转换**：若字符串列 `user_code VARCHAR` 发生数值比较 `WHERE user_code = 12345`，MySQL 遵循规则会将字符串列隐式转换为数值比较（类似于对列施加 `CAST(user_code AS DOUBLE)`），同样破坏索引原生字符序。

## 3. 联合索引的四个服务阶段：定位、过滤、排序与取列

联合索引在单次查询中能提供的工程价值可以精细拆分为四个层次：

```text
① 定位 (Index Seek)   → 借最左连续等值 + 首个范围条件，大幅收敛 B+Tree 初始扫描边界
        ↓
② 过滤 (Index Filter & ICP) → 在已锁定的区间内，就地读取后续索引列排除无效记录，避免无效回表
        ↓
③ 排序 (Index Order)  → 利用叶子节点物理有序性，直接交付排序结果，免除内存临时文件排序
        ↓
④ 取列 (Covering Index) → 所需列全在索引内，直接提取返回，彻底抹平回表开销
```

---

### 3.1 覆盖索引（Covering Index）与索引下推（ICP）的协同

- **覆盖索引（Covering Index）**：查询的列（SELECT、WHERE、ORDER BY）全部被二级索引包含。引擎仅在二级索引树上便可拿到完整结果，`Extra` 显示 **`Using index`**，回表次数降为 0。
- **索引下推（Index Condition Pushdown, ICP）**：当查询仍需回表（例如需要未收录的 `title`），但部分筛选列在二级索引内（如 `status`）。MySQL Server 将这部分过滤条件直接下推给 InnoDB 存储引擎，引擎在遍历二级索引叶子页时，先在索引内部就地校验 `status='done'`，不合格者直接丢弃，仅对合格项回表捞取数据。`Extra` 显示 **`Using index condition`**，大幅减少了无效回表次数。

| 特性 | 是否彻底免除回表 | 核心机制与优化目标 |
|---|---|---|
| **Covering Index** | **是**（0 次回表） | 只要当前索引已包含所需所有投影列，便无须接触聚簇树 |
| **ICP** | 否（仍需回表） | 将无法缩短区间的索引列条件下推到 InnoDB 存储引擎层，在回表前先就地过滤无效候选 |

## 4. 联合索引怎样同时服务过滤和排序？

单列索引 `INDEX(A)` 与 `INDEX(B)` 是两棵互不相干的独立树，优化器即便动用 `Index Merge` 分别扫描后再求交集，也无法天然提供多列排序。

联合索引消除 `ORDER BY` 的核心法则是：**WHERE 条件中的等值过滤，必须把排序列前面的所有索引列全部严格固定为常数。** 同时，多列排序的方向必须与索引定义保持完全一致（或全部完全相反以倒序遍历）；若一列升序一列降序（如 `ORDER BY col1 ASC, col2 DESC`）且未建立降序索引，同样无法消除 filesort。

对于索引 `(tenant_id, status, created_at)`：
- 查询 `WHERE tenant_id = 10 AND status = 'pending' ORDER BY created_at DESC`：前两列被固定为单点，剩余切片内按 `created_at` 严格有序，可直接反向扫描叶子链表完成排序，**零 filesort**；
- 查询 `WHERE tenant_id = 10 ORDER BY created_at DESC`：跳过了 `status`，在租户 10 内部记录先按状态分群，状态不同的两组记录在时间上相互交错，全局失去单调性，优化器只能将所有行调入内存进行文件排序（`Using filesort`）。

## 5. 怎样根据真实查询设计联合索引？

联合索引设计没有死板的排他定律，必须遵循“自顶向下从查询矩阵反推”的工程路径：

```text
1. 梳理核心高频 SQL 矩阵 (按访问量与响应敏感度排序)
   ↓
2. 提取公共前缀：将各查询最频繁出现的精确等值条件作为最左列 (如 tenant_id)
   ↓
3. 安排范围条件与排序列：
   - 若 Top-N 排序（ORDER BY + LIMIT）是主要瓶颈，排序列紧随等值列之后；
   - 若精确筛选是主要瓶颈，将范围列紧随等值列之后；
   ↓
4. 权衡覆盖开销：评估为核心查询追加少量列实现 Covering 的利弊 (避免宽文本/JSON)
   ↓
5. 综合全表索引数量控制：单表二级索引通常建议收敛在 4~6 个以内，控制写放大
```

### 经典设计权衡：
面对两个常见查询：
- **查询 1**：`WHERE tenant_id=? AND status=? ORDER BY created_at DESC LIMIT 20`
- **查询 2**：`WHERE tenant_id=? AND created_at >= ?`

设计索引为 `(tenant_id, status, created_at)` 可以完美服务查询 1（过滤+排序全消除）；但对于查询 2，缺少 `status` 会导致无法直接定位时间区间。若此时将索引定义为 `(tenant_id, created_at, status)`，虽能完美服务查询 2（等值 + 范围连续命中），但对于查询 1：虽然排序列 `created_at` 紧随 `tenant_id` 依然能消除 filesort，第三列 `status=?` 却无法做索引等值定位，必须在扫描 `created_at` 倒序节点时逐行过滤 `status`，放大了扫描行数。工程决策需权衡两者调用频次与延迟容忍度，或针对极核心链路分别构建针对性索引。

## 本章总结

联合索引的底层只有唯一的一套物理多列字典序。从最左列开始连续供给的等值条件，能层层压榨和缩小 B+Tree 的初始定位区间；遇到范围条件时，区间的进一步收敛虽然停止，但后续索引列依然能通过索引下推（ICP）在页内就地过滤，显著消除无效回表。

索引对查询的支撑贯穿全生命周期：从初始寻道（Seek）、页内过滤（Filter）、免排交付（Order）到覆盖取数（Covering）。在索引设计时，坚决摒弃“区分度高一律放最左”的僵化条条框框，必须以业务高频 SQL 矩阵为基准，在等值过滤、范围检索、Top-N 排序以及写放大维护成本之间寻求全局最优解。

## 🎯 面试怎么回答

### 什么是联合索引的最左前缀原则？底层物理成因是什么？

> [!TIP]
> 联合索引 `(A, B, C)` 遵循严格的多列字典序，底层 B+Tree 首先按 A 排序，A 相同时按 B 排序，前两列均相同时才按 C 排序。只有提供从最左列开始连续不断的等值条件，才能在树中顺次缩小并锁定一段连续的物理页区间。若跳过左侧列，右侧键值在全表中处于离散分片状态，无法直接通过树做范围区间收敛，这就是最左前缀的物理成因。

### 联合索引中遇到范围查询（>、<、BETWEEN），后面的列就彻底失效了吗？

> [!TIP]
> 绝非彻底失效。范围条件确实会打断后续列继续“缩小 B+Tree 初始扫描区间（Index Seek）”的能力；但在已锁定的扫描区间内部，后续列依然可以充当“索引过滤器（Index Filter）”，通过索引下推（ICP）机制在存储引擎层直接剔除不匹配的索引记录，从而极大幅度减少无效回表次数。

### 覆盖索引（Covering Index）和索引下推（ICP）有何本质区别？

> [!TIP]
> 1. 优化目标不同：覆盖索引的目的是“彻底消除回表”，只要查询所需的字段均被索引收录，即直接从二级索引返回数据；ICP 的目的是“在依然需要回表的前提下，尽量少回表”；  
> 2. 执行机制不同：覆盖索引无需触碰聚簇索引；ICP 则是存储引擎在利用索引列筛掉部分行后，将合格项的主键拿去聚簇索引回表取整行。

### 为什么在联合索引中，等值条件通常建议放在范围条件之前？

> [!TIP]
> 因为等值条件能精准收敛并锁定一个单一逻辑分组，使紧随其后的列依然能够继承该分组内的物理有序性；若将范围条件放在最前，会直接圈定一个多值区间，导致区间内部后续列的数据排列错乱分散，后续所有列将彻底失去缩小检索区间的能力。

### 多个单列索引能不能替代一个联合索引？

> [!TIP]
> 不能。多个单列索引各自维护独立的单一维度排序树，即便触发 Index Merge（索引合并）在内存中求交集，也存在额外的归并计算开销；更重要的是，单列索引完全无法提供联合索引天然具备的多列前缀精确定位、多列复合排序消除（消除 filesort）以及多列联合覆盖能力。

## ⚠️ 易错点

> [!WARNING]
> **最左前缀由索引定义决定，非 WHERE 书写顺序。** 优化器会自动按索引列调整条件匹配。

> [!WARNING]
> **切勿把“无法缩小范围”等同于“索引失效”。** 范围条件后的索引列仍能承担页内过滤（ICP）与覆盖取列职责。

> [!WARNING]
> **覆盖索引不是一种物理类型。** 它是查询需求与特定索引覆盖能力契合的一种执行状态。

> [!WARNING]
> **消除 ORDER BY 依赖等值列连续锁定。** 若排序列之前存在范围条件或跳过的列，物理有序性被打断，必将产生 filesort。

> [!WARNING]
> **索引并非越宽越好。** 盲目把大文本或非必要字段塞入联合索引做覆盖，会导致单页容纳记录剧减，加剧内存抖动与写入维护成本。

> [!WARNING]
> **低基数字段并非绝对不能入索引。** 在数据高度倾斜场景下（如 99% 成功、1% 失败），对该字段的小概率值检索依然具备极高的区间收敛过滤价值。

## 🧩 本章自测

<details>
<summary><strong>1. 联合索引 `(a, b, c)`，查询 `WHERE b=1 AND c=2` 能否走索引？</strong></summary>

无法使用最左前缀进行高效的区间快速定位（Index Seek）。但在特定覆盖或全索引扫描（Index Full Scan / Skip Scan）场景下优化器可能依然会遍历这棵树，但其定位性能与等值前缀不可同日而语。

</details>

<details>
<summary><strong>2. 联合索引 `(a, b, c)`，查询 `WHERE a=1 AND b>10 ORDER BY c` 是否会产生 filesort？</strong></summary>

会产生 filesort。因为 `b>10` 是范围条件，在圈定的范围内部包含多个不同的 b 值，每个 b 值内部虽按 c 有序，但全局并不单调，无法直接利用物理顺序完成排序。

</details>

<details>
<summary><strong>3. `LIKE 'abc%'` 与 `LIKE '%abc'` 底层寻址差异是什么？</strong></summary>

前者首字符固定，可映射为区间范围查询 `['abc', 'abd')` 定位叶子连续区间；后者前缀未知，无法收敛区间。

</details>

<details>
<summary><strong>4. 何为 EXPLAIN 中的 `Using index condition`？</strong></summary>

代表启用了索引下推（ICP）机制，存储引擎在遍历二级索引时，就地利用索引中携带的字段过滤条件，过滤通过后才发起回表。

</details>

<details>
<summary><strong>5. 什么是索引覆盖？在 EXPLAIN 中如何辨识？</strong></summary>

查询所需字段全在索引内，无需回表。在 EXPLAIN 的 `Extra` 列中会明确出现 **`Using index`**。

</details>

<details>
<summary><strong>6. 为什么对索引列套用 `DATE(col)` 函数会导致无法使用索引范围？</strong></summary>

索引树按原始时间戳排序，未建立函数计算结果的映射树，优化器无法将计算结果与原始键做区间二分。

</details>

<details>
<summary><strong>7. 为什么字符串列传入数值比较可能会破坏索引？</strong></summary>

MySQL 会隐式将字符串列逐行转为数值再做比对，等价于对索引列施加了转换函数，破坏了基于字符原生字典序的区间定位能力。

</details>

<details>
<summary><strong>8. 索引 `(a, b)` 面对 `WHERE a=1 ORDER BY b DESC` 能否消除排序？</strong></summary>

可以。a 被固定为单值常数，内部按 b 单调有序，反向遍历该段叶子链表即可直接完成倒序交付，无 filesort。

</details>

<details>
<summary><strong>9. 为什么说“区分度最高放最左”不是万能金律？</strong></summary>

若某字段区分度极高但极少出现在高频查询的等值前缀中，或高频业务严重依赖按租户 ID（区分度相对低）分流和排序，强行把高区分度列放最左会破坏整体查询族的覆盖性。

</details>

<details>
<summary><strong>10. 联合索引最多可以建多少列？工程上建议多少列？</strong></summary>

MySQL 规范单索引最多支持 16 列。工程实践中建议控制在 2~4 列以内，过宽的索引会导致页面扇出降低、树高膨胀以及写放大开销剧增。

</details>

## 📌 本章最终要留下的六句话

1. **联合索引是一棵遵循复合字典序的 B+Tree，最左前缀是物理排列的自然产物。**
2. **等值前缀层层收敛区间，首个范围条件截断后续列继续缩减区间的物理能力。**
3. **范围截断不等于列废弃：后续列依然能充当页内过滤（ICP）与免回表取列。**
4. **覆盖索引（Covering）彻底消除回表，索引下推（ICP）显著遏制无效回表。**
5. **消除 `ORDER BY` 的铁律是：排序列左侧的所有索引列必须全被等值条件锁死。**
6. **索引设计绝非单条 SQL 的私事，必须以高频查询矩阵为基准权衡过滤、排序与写放大。**
