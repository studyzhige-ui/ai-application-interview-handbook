# 04｜把多张表查在一起，把多条记录汇总起来

[← 字段、约束与表之间的关系](03-数据类型约束与表关系.md) · [MySQL 目录](../README.md) · [从查对结果到少做工作：执行计划与索引 →](05-SQL执行与索引基础.md)

任务表保存了负责人编号，页面却要显示姓名；管理者还想知道待办和完成各有多少。前一个需求需要把表关联起来，后一个需要把多条记录汇总起来。两种操作都基于前面已经认识的六条任务，不另换一套复杂业务。

## 1. JOIN 按匹配条件组合记录

例如任务 1 的 `owner_id=1`，到成员表找到 `id=1`，就可以把“小林”放到查询结果中。这就是关联查询的基本动作。

<a id="sql-left_join"></a>

<!-- mysql-example: left_join -->
```sql
SELECT t.id, m.name
FROM tasks AS t
LEFT JOIN members AS m
  ON m.id = t.owner_id AND m.tenant_id = t.tenant_id
WHERE t.tenant_id = 10
ORDER BY t.id;
-- (1,小林), (2,小林), (3,小周), (4,NULL), (6,小周)
```

`t` 和 `m` 是表的短名称，`t.id` 表示任务表的编号，`m.name` 表示成员姓名。`ON` 后面是匹配条件：负责人编号相同，并且团队相同。`WHERE` 则选出本次要看的团队 10。

| 任务编号 | 查到的姓名 |
|---:|---|
| 1 | 小林 |
| 2 | 小林 |
| 3 | 小周 |
| 4 | NULL |
| 6 | 小周 |

**LEFT JOIN 保留左侧任务，即使没有匹配成员，也用 NULL 补右侧结果。** 因此任务 4 仍在。INNER JOIN 只保留匹配成功的组合，任务 4 就会消失。JOIN 不会把两张源表永久合成一张表，它构造的是本次查询结果。[JOIN 语义](https://dev.mysql.com/doc/refman/9.7/en/join.html)。

> ⚠️ 关联可能扩大行数。若右表一个条件匹配三行，左表一条记录会对应三条结果。不要在未弄清一对多关系时，直接用关联后的 COUNT(*) 当原始任务数。

还要看筛选发生在哪：在上述 SQL 的 WHERE 中再加 `m.name='小林'`，没有负责人和其他负责人的任务都会被去掉。若需求是“保留全部任务，只在负责人叫小林时显示姓名”，条件应放进 ON。二者回答的是不同问题，不是优化器写法偏好。

## 2. 分组统计：先分组，再为每组算一个结果

团队 10 有五条任务，状态依次是待办、完成、待办、待办、完成。要数各有几条，可以这样写：

<a id="sql-grouped_count"></a>

<!-- mysql-example: grouped_count -->
```sql
SELECT status, COUNT(*) AS total
FROM tasks
WHERE tenant_id = 10
GROUP BY status
HAVING COUNT(*) >= 2
ORDER BY status;
-- done:2；pending:3
```

结果为 `done：2`、`pending：3`。过程分清以后，语法就容易记：

1. WHERE 先选出团队 10 的五行。
2. GROUP BY 按状态分成两组。
3. COUNT(*) 分别数每组有几行，`AS total` 给结果列起名。
4. HAVING 只留下数量至少为 2 的组，ORDER BY 确定结果顺序。

**WHERE 筛选原始行，HAVING 筛选分组结果。** 如果只想统计待办，先在 WHERE 中限制状态即可，不必先统计所有状态再删掉不需要的组。

除了计数，SUM 求和、AVG 求平均、MIN/MAX 取最小最大值。它们对 NULL 的处理需要与业务含义对应：COUNT(*) 数行，COUNT(owner_id) 只数负责人非空的行。因此六条任务的两个计数分别是 6 和 5。

不能同时选择一组的 `COUNT(*)` 和一个没有确定含义的任务标题，然后期待标题“自动选最新”。分组减少为每组一行，组内哪条明细应被选中是另一个问题。[分组约束](https://dev.mysql.com/doc/refman/9.7/en/group-by-handling.html)。

## 3. “有没有”和“数多少”不必写成同一个查询

想找至少有一条待办的成员，只需判断有没有对应任务：

<a id="sql-exists_query"></a>

<!-- mysql-example: exists_query -->
```sql
SELECT m.id, m.name FROM members AS m
WHERE EXISTS (
  SELECT 1 FROM tasks AS t
  WHERE t.owner_id = m.id AND t.tenant_id = m.tenant_id
    AND t.status = 'pending'
)
ORDER BY m.id;
-- 1 小林；2 小周；3 小陈
```

结果是三位成员。对每个成员，EXISTS 判断括号内是否能找到匹配任务；`SELECT 1` 只放一个常量，不是在统计任务数。NOT EXISTS 则表示找不到。这种表达也不会因为一个成员有两条待办而重复列出该成员。

不要把 NOT EXISTS 无条件换成 NOT IN。比如 `2 NOT IN (1, NULL)` 无法确认 2 不等于那个未知值，结果是未知，WHERE 不会保留它；NOT EXISTS 则判断有没有匹配的行。

如果已经在查任务，只想取得不重复的负责人编号，可以使用 `SELECT DISTINCT owner_id ...`。DISTINCT 对查询结果去重，不会删除源数据。

<details>
<summary>同类需求进一步：在一行中统计完成数，或取每个团队最新一条</summary>

要同时返回总数和完成数，可以把完成任务映射成 1、其他任务映射成 0，再求和：

<a id="sql-conditional_count"></a>

<!-- mysql-example: conditional_count -->
```sql
SELECT COUNT(*) AS total,
       SUM(CASE WHEN status = 'done' THEN 1 ELSE 0 END) AS completed
FROM tasks WHERE tenant_id = 10;
-- total=5，completed=2
```

CASE 是按条件选择一个值，SUM 把选出的数相加。没有任何行时 SUM 返回 NULL，需要显示 0 可用 COALESCE 选取第一个非 NULL 值。

“每个团队最新的一条”则必须保留被选中行的身份。练习表的 `created_at` 保存创建时间：团队 10 最晚的是 9 月 4 日创建的任务 6，团队 20 只有 9 月 3 日的任务 5。先在各团队内部按时间与编号排序并编号，再筛第 1 条：

<a id="sql-window_latest"></a>

<!-- mysql-example: window_latest -->
```sql
WITH ranked AS (
  SELECT id, tenant_id,
         ROW_NUMBER() OVER (
           PARTITION BY tenant_id ORDER BY created_at DESC, id DESC
         ) AS rn
  FROM tasks
)
SELECT tenant_id, id FROM ranked WHERE rn = 1 ORDER BY tenant_id;
-- (10,6), (20,5)
```

WITH 给中间结果命名，PARTITION BY 把窗口分成不同团队，ROW_NUMBER 为组内记录编号；外层取 rn=1。结果为 `(10,6)`、`(20,5)`。这个实现用于此类明细选择，不要求先背全部窗口函数。

</details>

## 4. 由应用提交查询，仍要守住结构和值的边界

应用里的“查询某条任务”通常是固定 SQL 配上变化的参数。**参数化查询把 SQL 结构和值分开交给数据库驱动**，避免把用户的文字拼进可执行结构。这是语言无关的原则。

例如，结构描述“团队编号等于一个参数，并且任务编号等于另一个参数”，实际值是团队 10、任务 3。Java、Python 等驱动的调用形式和占位符可能不同，但都不应先把参数拼成 SQL 字符串再执行。

表名、列名、升降序属于查询结构，通常不能作为普通值绑定。允许用户选排序字段时，应把外部选项映射到明确允许的列，而不是直接接受任意文本。ORM 也不能让原生 SQL 拼接自动安全。参数化与预编译的机制可对照[官方预处理语句](https://dev.mysql.com/doc/refman/9.7/en/sql-prepared-statements.html)。

如果页面先查 100 条任务，再为每条单独查询成员，会发送 101 次请求，这常叫 **N+1 查询**。JOIN 或一次批量查成员可以减少往返；是否更快还要结合返回规模和计划。至此，正确的结果、正确的参数和合适的查询粒度都建立了，再去研究索引才有对象。

## 本章小结

JOIN 组合匹配记录，GROUP BY 与聚合把多行变成摘要，EXISTS 判断关联是否存在。先明确结果形状，再选语句；应用调用还要把 SQL 结构与值分开。

## 🎯 面试怎么回答

### WHERE、ON 和 HAVING 有什么区别？

ON 决定表之间怎样匹配，WHERE 筛选进入后续处理的行，HAVING 筛选聚合后的组。外连接中把右表条件从 ON 移到 WHERE 可能删除原本应该保留的未匹配行。

### 怎样避免 SQL 注入？

值使用驱动参数绑定，动态列名等结构使用允许列表，同时限制账号权限。是否使用 ORM 或哪种应用语言，都不能替代这些边界。

## ⚠️ 易错点

> ⚠️ COUNT(*) 和 COUNT(可空列) 可能不同；关联后的行数也不一定等于左表记录数。

> ⚠️ NOT IN 的候选集合含 NULL 时会引入未知结果，不能无条件替代 NOT EXISTS。

<summary>1. 任务 4 在 LEFT JOIN 中保留、INNER JOIN 中消失，原因是什么？</summary>

它没有负责人，无法匹配成员。左连接保留它并补 NULL，内连接只保留成功匹配。

<details>
<summary>2. 为什么“每组任务数至少 2”写在 HAVING？</summary>

数量是分组后才计算出的结果；WHERE 的角色是筛原始记录，不能直接以这一组的 COUNT(*) 为条件。

</details>

<details>
<summary>3. 把用户选择的排序列直接拼进 SQL，再绑定 WHERE 参数，够安全吗？</summary>

不够。绑定保护的是值，排序列是结构，仍须通过明确的允许映射选择。

</details>
