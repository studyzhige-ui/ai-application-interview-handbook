# 15｜产品与架构选择：先决定需要哪类能力

[← 14 性能与容量：用证据定位瓶颈](14-性能容量与Production诊断.md) · [模块目录](../README.md) · [16 图数据库边界：相似、关系与完整系统 →](16-GraphDB边界与系统设计.md)

“Faiss、pgvector、Elasticsearch、Milvus、Qdrant 选哪个？”这个问法把几类不同东西放在一起了。一个是在进程中调用的搜索库，一个是现有数据库的扩展，另一些提供独立服务。

先决定**系统需要谁承担哪些职责**，再选择具体产品。比较的不是品牌知名度，而是你需要自己补齐多少能力，以及引入了什么新的边界。

## 1. 搜索库：应用拥有更多控制，也承担更多工作

Faiss 提供向量索引和搜索算法，适合算法实验、离线处理或由应用管理生命周期的检索。它支持索引保存与加载，因此不能说“库完全不能持久化”。但保存一个索引文件，不等于已经拥有多用户服务、授权、跨进程写入协调和故障恢复流程。

例如两个请求同时搜索一个稳定的 CPU 索引，与一个线程搜索、另一个线程修改索引，是不同并发问题。应查所用索引与版本的线程安全保证，在应用层安排锁、快照替换或写入序列化，不能因 Python 函数能够调用就假设自动安全。[Faiss FAQ](https://github.com/facebookresearch/faiss/wiki/FAQ)区分了搜索与写入并发边界。

库也可能提供某些过滤选择器或 ID 映射；“不是数据库”不等于“任何过滤都做不了”。关键是这些能力是否满足应用需要，以及服务层由谁负责。

## 2. 数据库扩展：让向量靠近现有业务数据

pgvector 为 PostgreSQL 增加向量类型、距离操作与近似索引。若资料元数据和业务关系已经在 PostgreSQL，把向量放在同一个数据库可以减少一套外部同步链路，并沿用现有事务、权限和运维体系。

代价是向量查询、建索引与业务事务可能争用资源。关系表中的 WHERE 也不自动意味着近似索引在最理想的小集合上运行，需要检查实际执行计划、过滤和迭代扫描。不能用“SQL 能表达”替代“性能已经满足”。[pgvector 0.8.6 README](https://github.com/pgvector/pgvector/blob/v0.8.6/README.md)给出准确的功能与查询限制。

## 3. 搜索引擎：当全文与向量都很重要

Elasticsearch 同时提供全文检索、结构化过滤和向量检索能力。已有成熟搜索基础设施，且关键词、语言分析、过滤和向量是共同需求时，复用它有明显的工程候选价值。

但全文与向量分数不一定同尺度，融合、候选深度和过滤仍要设计；有关键词索引不代表 RAG 的多路召回自动完成。它的 kNN API 也区分最终结果、分片候选和过滤位置。[官方 kNN 说明](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-knn-query)用于核对这些语义。

产品持续增加压缩、磁盘和模型集成选项，因此不宜写死“搜索引擎只支持某一种 ANN”。本模块不展开完整搜索引擎运维；全文机制和融合的应用主线归 RAG。

## 4. 专用向量服务：把检索维护交给独立系统

Milvus、Qdrant 等专用服务提供记录管理、向量搜索和相关服务能力，但不是同一个架构的不同名字。第 13 章已建立新增数据、历史查询与后台维护的通用分工，并提供 Milvus 的可选对照；Qdrant 的点、payload、集合及写入完成语义也有自己的 API。

独立服务便于单独配置资源和维护，但增加网络、认证、监控、备份，以及与业务事实源同步的边界。把文档状态写入关系库，再写向量服务，是跨系统操作；第一步成功不能证明第二步完成，需要可重试同步和对账。

具体产品可能集成生成嵌入、全文或混合检索功能，不能把第 01 章的概念分工误解为“一个产品永远只能承担其中一步”。是否启用这些功能、模型如何配置、云端与自建是否一致，应查目标版本，而不是按分类名称推断。

## 5. 开源自建与托管服务分别核对

同一品牌的本地库、单节点、分布式开源版和托管产品，可能具有不同认证、备份、扩缩容、配额和功能可用范围。托管减少部分运维工作，但不能替应用决定权限范围、资料版本和质量指标。

课程的数值实验不绑定数据库，实际索引实验固定 Faiss 版本，服务操作实验选 Qdrant 作为一个具体例子。它们是为了观察机制，不是推荐所有项目采用同一技术栈。

## 6. 把选型结论落实到具体版本

“产品支持”还不够，要核对准备运行的版本与部署模式。例如第 10 章的迭代扫描有版本起点，开源版与托管版的能力范围也可能不同。

实际验证保留三项信息：

1. **查阅依据。** 官方页面适用的版本、关键条件和核验日期。
2. **运行对象。** 实际安装的库、服务端、客户端及部署配置。
3. **实验范围。** 验证了记录操作、索引效果还是多节点恢复，哪些仍未运行。

课程目标、发布依据与实际运行状态集中维护在 [References 版本基线](../../../references/vector-db/README.md#版本基线)，实验按对应版本执行。版本不符时单列结果或停止，而不是换一个环境继续沿用原来的通过结论。版本表是查阅入口，不是架构选择时需要背诵的知识。

## 7. 用一段决策说明代替品牌排名

假设团队已有 PostgreSQL，数据规模可控，向量查询频率不高，且向量和业务状态经常共同更新。可以把 pgvector 列为首个验证候选，检查过滤、事务竞争和延迟；不是因为它在所有场景性能最好，而是可能减少额外系统边界。

若随后实际负载证明检索与业务事务互相影响，或检索需要独立扩展，再比较独立服务的收益与同步、运维成本。相反，一个只做离线检索分析的任务，可能根本不需要常驻数据库服务，库和索引文件就足够。

## 本章小结

库、数据库扩展、搜索引擎和专用服务，承担的职责不同。算法名称和产品能力不能混为一谈，开源与托管也不能互相代替验证。技术选择应写出已有系统、约束、候选、实验和不满足条件时的演进路径。

## 🎯 面试怎么回答

**问：为什么用某个向量产品，而不是另一种？**

我先区分需要算法库还是持久服务，以及现有关系数据、全文检索和运维条件。库给我更多控制但要自己承担服务生命周期；数据库扩展可能减少同步边界；独立向量服务便于单独扩展，却新增跨系统一致性和运维成本。最终用真实过滤、负载、更新和恢复验证目标版本，而不是引用排行榜或声称某类产品天生不具备一项能力。

## ⚠️ 易错点

- **看能力，也看谁负责。** 库能保存索引，不代表应用已经完成服务、授权和故障恢复。
- **能表达不代表已高效执行。** 过滤、组合检索与业务事务竞争需要实际计划和负载验证。
- **版本和部署不能混报。** 托管不等于开源，单节点不等于集群；弃用也不等于立即失效。

## 自测

**任务。** 一个应用每天离线重建一次索引，只有一个分析进程，没有在线增删和多用户权限要求。另一个应用要持续更新、租户隔离并从节点故障恢复。请比较两者选择搜索库时需要额外承担的工作。
