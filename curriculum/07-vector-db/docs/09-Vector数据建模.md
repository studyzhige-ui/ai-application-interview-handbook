# 09｜向量数据建模：让结果找得到来源

[← 08 索引选择：把机制放回工作负载](08-IndexSelection.md) · [模块目录](../README.md) · [10 元数据过滤：在允许的范围内找近邻 →](10-MetadataFilter.md)

搜索返回记录 A，分数很好。但应用找不到对应原文，或者取到了已经改版的段落，这次搜索仍然不可用。向量数据建模要保证：**一条结果能回到正确对象、正确版本和正确访问范围。**

本章先建立记录和基础操作，再讨论集合组织；不从一张几十个字段的生产字段清单开始。

## 1. 向量对应什么对象

沿用团队知识库。文档 `travel` 有若干段，每段可以单独被检索。一条记录至少需要区分三个对象：原始文档、文档中的片段，以及片段所使用的表示。

| 信息 | 具体示例 | 解决的问题 |
|---|---|---|
| 记录标识 | `travel:v3:chunk2:spaceA` | 精确定位一条可覆盖、读取或删除的记录 |
| 来源标识 | `doc_id=travel`、`chunk_id=2` | 把搜索结果映射回原始资料 |
| 来源版本 | `source_version=3` | 避免旧向量配上新原文 |
| 向量空间 | `embedding_space=spaceA` | 确认查询表示与记录可以比较 |
| 访问归属 | `tenant_id=alpha` | 将授权范围变成查询条件 |
| 向量 | 教学值 `[1,0]` | 计算相似度 |

上例把来源版本放进记录标识，因此不同版本可以并存；同一版本重试时复用同一标识。也可以为片段使用跨版本稳定 ID 并覆盖更新，两种发布方式的旧记录清理不同，第 4 节会对照说明。

页码、章节、原文位置等信息在需要精确引用时补充。不要以为所有文档都有页码；网页可以记录段落或位置标识。元数据字段应服务查询、更新和追溯，而不是越多越好。

这些名称是业务设计示例，不是所有产品规定的字段模式。产品可能要求数值或 UUID（通用唯一标识符）主键，应用可以维护逻辑标识到物理标识的映射。例如 [Qdrant Points 文档](https://qdrant.tech/documentation/manage-data/points/)明确区分 point id、vector 与 payload（附带字段）。

## 2. 先分清几种基础操作

先把操作分成三类：新增或改变记录、读取记录、删除记录。它们对状态的影响不同。

| 操作 | 接收什么 | 完成什么 |
|---|---|---|
| Insert（插入） | 新标识及完整记录 | 新增一条记录；重复标识的处理依产品规则 |
| Retrieve（按标识读取） | 指定记录标识 | 返回该条记录或明确的未找到结果，不改变记录 |
| Search（相似搜索） | 查询向量、条件和 K | 按相似度返回候选及分数，不改变记录 |
| Upsert（不存在则插入，存在则更新） | 标识与记录内容 | 新增或更新同一标识的记录 |
| Metadata update（元数据更新） | 标识、要修改的字段及新值 | 修改附带字段；是否保留未提供字段由 API 定义 |
| Delete（删除） | 标识或明确条件 | 删除指定范围内的记录 |

### 跟着 A 完成一次读写过程

这是**操作语义演示，不是 SDK 调用或服务实测**。为让每一步结果确定，约定操作依次完成、后续读取已能看到变更、没有其他写者。A 和 C 均属于 alpha；只改标签的操作保留其他字段，本例 upsert 则替换完整记录。

初始只有 A：向量 `[1,0]`、标签“制度”、来源版本 1。接下来按顺序操作：

<a id="record-state-example"></a>

| 步骤 | 操作与输入 | 操作后可观察结果 |
|---:|---|---|
| 1 | 插入 C：`[0.8,0.6]`、标签“流程”、来源版本 1 | A 不变；C 新增，记录总数为 2 |
| 2 | 只把 A 的标签改为“待复核” | A 的向量仍为 `[1,0]`，来源版本仍为 1；C 不变 |
| 3 | upsert A 的完整新记录：`[0,1]`、标签“新制度”、来源版本 2，保留 alpha 归属与来源标识 | A 被替换，但记录总数仍为 2 |
| 4 | 按 ID 读取 A | 返回 A 的 `[0,1]`、标签“新制度”和来源版本 2；不修改状态 |
| 5 | 在 alpha 内用 `q=[1,0]` 做精确平方 L2 搜索，K=1 | A 距离为 2，C 为 0.4，因此只返回 C |
| 6 | 删除 A，再按 ID 读取 A | 明确未找到 A；C 仍存在，记录总数为 1 |

第 4、5 步并不矛盾：**按 ID 读取问“A 是否存在、内容是什么”，相似搜索问“谁最接近本次查询”。** A 存在，但这次排在 C 后面。读取遇到网络错误，也不能当成第 6 步那样的“未找到”。

> ⚠️ 注意：上表已约定替换、字段保留和可见性，实际 API 必须核对这三项。若 upsert 替换完整记录，只传一个字段就可能丢掉其余内容；若确认只表示请求已接收，后续查询也未必立即看到新状态。[Qdrant 点与向量更新说明](https://qdrant.tech/documentation/manage-data/points/)可作为具体实现参照。

## 3. 稳定标识防重复，不自动防乱序

假设网络超时，客户端不知道 A 是否已经写入。使用相同标识重复提交相同内容，可以避免每次生成新标识造成重复记录。这叫幂等：同一操作重复执行，不额外产生业务效果。

但版本 2 写入完成后，延迟的版本 1 又到达，普通“最后到达者覆盖”仍可能把 A 改旧。**幂等处理同一动作的重复，版本规则决定不同更新谁该生效。** 本章先建立这一差别；删除后旧写入回流、并发版本检查与重放顺序由第 12 章结合具体时间线处理。

## 4. 文档变短，旧片段不会自行消失

文档版本 1 被分成三块：`travel:v1:c1`、`c2`、`c3`。版本 2 只有两块。只写入 v2 的 c1、c2，并不能推导出 v1 的三块都已经清除。

一种清晰的发布方式是先完整写入新版本，核对片段清单，再把该文档的可查询版本切到 v2，随后清理旧版本。另一种是使用稳定片段标识覆盖，并显式删除不再存在的尾部片段。二者都必须知道“当前版本完整包含哪些片段”。

```text
旧清单：c1、c2、c3
新清单：c1、c2
差集：  c3 需要明确退役，而不是等待 upsert 猜测
```

内容散列（content hash，也常用于校验和检查）把一段内容映射成一个便于比较的值。周期同步时，在编码模型和处理规则不变的前提下，应用可以先比较同一文档的内容散列：未变化的内容通常不必重新编码；变化了才进入处理和索引更新。散列相同不能提供绝对无碰撞保证，重要数据还应按所用算法与风险要求核验。

但散列只回答“内容是否看起来相同”，不回答“哪一次更新更晚”。源站删掉文档后，单靠比较仍存在文档的散列也不会发现这次删除；应用还需要删除事件或完整来源清单的差集，以及来源版本。相同内容也可能属于不同文档、不同租户，不能用一个全局散列主键把它们的权限和来源错误合并。

## 5. 三种版本不要混成一个 version

| 版本 | 记录哪一种变化 | 一个例子 |
|---|---|---|
| 来源版本 | 原文或业务事实变化 | 报销期限从七天改为三十天 |
| 嵌入空间版本 | 编码器、前处理、维度或距离约定变化 | 换用另一套不兼容的编码方式 |
| 索引构建版本 | 同一向量集合的结构或参数变化 | 提高 HNSW 建图搜索宽度并重建 |

这种区分直接决定更新成本：只换图结构，可以复用兼容的向量；更换表示空间，则需要重新编码，并为查询选择配套编码器。记录清楚“哪一种变了”，比给所有变化共用一个 version 更容易定位问题。

## 6. Collection、Schema 与命名空间

Collection（集合）通常是保存同类向量记录的容器；Schema（模式）描述字段类型、向量维度及索引规则。Namespace（命名空间）可以用于组织不同数据范围，但不同产品对它的隔离保证并不相同。

决定是否分开存放时，先问：表示空间是否兼容？权限、生命周期和容量是否需要独立管理？没有必要为每篇文档创建一个集合；也不能把不同模型的同维向量随意放入同一个检索空间。

元数据的索引也有成本。经常参与租户、类型或时间过滤的字段值得按访问模式建立索引；只用于结果展示的大段文本不一定需要同等索引。要分别看“保存了该字段”“能按该字段过滤”“过滤是否有合适索引”。

## 本章小结

可用的记录不仅有向量，还要有标识、来源、版本和访问范围。先掌握插入、读取、搜索、更新与删除的状态变化，再设计集合。稳定标识防重复，版本控制防旧数据回流；文档变短必须显式退役旧片段。

## 🎯 面试怎么回答

**问：向量数据库怎样建模？**

我先确定检索单元是文档还是片段，再为它设计稳定标识，并保存来源位置、来源版本、嵌入空间与租户等必要元数据。写入与更新要明确替换还是合并、重复请求和乱序事件怎样处理。文档重新分块还要核对新旧片段清单并清理旧记录。集合按照表示兼容、权限、生命周期和规模组织，不按文档数量机械拆分。

## ⚠️ 易错点

- **没被搜到不等于不存在。** 用按 ID 读取核对指定记录，用相似搜索检查排名和过滤。
- **更新先分清对象。** 标签、向量、来源与权限各有作用；完整替换时不能漏传仍需保留的字段。
- **重复和版本要分开。** 稳定 ID 可以防止重复记录，但不能自动处理旧版本回流或文档变短的残留片段。

## 自测

**任务 1。** 一个文档原有 4 块，新版本只有 3 块。程序只 upsert 了稳定标识 c1、c2、c3，并把它们的来源版本改为 2。请给出剩余错误、修复动作和验证方式。

<details><summary>答案与解释</summary>

c4 仍是旧记录，可能继续参与搜索。应根据完整新清单显式退役或删除 c4，同时确保查询只读已发布的完整版本。核对按文档列举的片段及版本，并用会命中 c4 旧内容的查询验证它不再可见；不能只看前三次 upsert 的返回值。

</details>

**任务 2。** 回到第 2 节，在 upsert A 之前暂停。此时 A=`[1,0]`，C=`[0.8,0.6]`。用 q=`[1,0]`、平方 L2、K=1 搜索会返回谁？仅把 A 的标签改成“待复核”，且查询没有标签条件，结果会因此改变吗？

<details><summary>答案与解释</summary>

返回 A：A 的平方距离是 0，C 是 0.4。只改标签不改变这次距离排序；若查询增加标签条件，合法集合才可能发生变化。不要把“元数据更新”和“向量更新”当成同一操作。

</details>
