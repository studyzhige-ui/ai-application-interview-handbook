# 05｜从候选分数到一段回答：生成与解码

[← Attention 与位置信息](04-Attention与Position.md) · [模块首页](../README.md) · [KV Cache 与两阶段推理 →](06-KVCache与PrefillDecode.md)

同一个问题问两次，回答的措辞不同。把随机性调低以后，它又可能两次都给出同一个错误日期。要解释这两种现象，需要把“模型算出什么”和“系统选择什么”分开。

上一章的 Attention 更新每个位置的表示。经过最后一层和语言模型输出头后，模型给词表中的候选 Token 各算一个分数。本章从这些分数出发，走完选择、接回输入、继续生成和停止的过程。

## 1. 一次前向计算与整段生成不是一回事

**前向计算（forward pass）** 是让输入经过模型，得到输出分数；**解码（decoding）** 是在生成任务中，根据这些分数决定输出序列的方法。

在普通自回归生成中，假设已有输入对应 Token 序列 `[A, B]`：

| 时刻 | 已知序列 | 使用哪个位置的分数 | 决定什么 |
|---|---|---|---|
| 第一次选择 | A、B | B 位置的词表分数 | 下一个 Token，例如 C |
| 第二次选择 | A、B、C | C 位置的词表分数 | 再下一个 Token，例如 D |
| 第三次选择 | A、B、C、D | D 位置的词表分数 | 继续内容，或结束标记 |

这个表描述信息依赖，不表示每一步都必须重新计算整个前缀。第 06 章用缓存复用历史计算。输入处理结束时已经能得到第一枚输出 Token 所需的分数，不必凭空增加一个“先跑一次空 Decode”的步骤。

训练时答案已经存在，可以同时计算多个位置的预测误差；生成时后面的真实内容尚未知。这是“训练能并行，普通生成仍有逐步依赖”的原因。

## 2. Logits 怎样变成概率

**Logit（未归一化分数）** 可以是任意实数，不是概率，也不保证在 0 到 1 之间。Softmax（归一化指数函数）把一组分数转换成非负、总和为 1 的数。

设教学用词表只有三个候选，分数分别是 `2、1、0`：

```text
指数值：e²、e¹、e⁰ ≈ 7.389、2.718、1
总和：约 11.107
概率：约 0.6652、0.2447、0.0900
```

真实词表大得多，以上数字只是可手算示例，不是任何模型的测量输出。

最高概率候选仍可能表达错误事实。这里的概率是在当前模型与输入条件下“接这个 Token 有多合适”，不是“这段话有多真实”的校准置信度。

## 3. 贪心选择与随机采样

**贪心解码（greedy decoding）** 每步选分数最高的候选。在上面的例子中，它选第一项。它只保证当前一步得分最高，不保证整段序列的概率乘积最大，更不保证答案正确。

**采样（sampling）** 则按概率随机抽取。概率约为 0.09 的第三项不是不可能出现，而是长期重复抽样时机会较小。不同位置的采样会改变后续输入，所以早期一处不同，可能带来后面整段回答不同。

某些任务还会使用 **Beam Search（束搜索）**：保留若干条得分较好的部分序列，继续扩展并筛选。它增加搜索计算和状态，得分也可能需要长度处理；并不是聊天应用必然优于采样的默认方案。这里保留它是为了区分“每步只留一条”与“同时保留多条”，不展开搜索实现。

## 4. Temperature 改变分布，不增加新知识

**Temperature（温度）** 是对分数进行缩放的参数。对正温度 `T`：

```text
p_i = exp(logit_i / T) / 所有候选指数值之和
```

同一组 `[2, 1, 0]`，得到：

| 温度 | 第一项 | 第二项 | 第三项 | 发生了什么 |
|---:|---:|---:|---:|---|
| 0.5 | 0.8668 | 0.1173 | 0.0159 | 概率更集中 |
| 1.0 | 0.6652 | 0.2447 | 0.0900 | 原来的分布 |
| 2.0 | 0.5065 | 0.3072 | 0.1863 | 较低分候选的机会增加 |

正温度缩放没有改变这三个候选的分数排序。因此，在分数不变且没有并列的条件下，只做贪心选择时，调正温度不会改变选中的项；温度主要改变采样分布。

> ⚠️ 注意：不能把 `T=0` 直接代进除法。某些接口用 `temperature=0` 表达近似贪心或最小随机性，另一些模型限制或不支持该参数。应查具体模型接口；不能把这个约定当成数学公式，也不能据此保证跨版本、硬件和服务端调度完全复现。

下面是**可独立运行的数值示例**，仅依赖 Python 标准库。它返回新概率列表，不修改输入，不调用模型。减去最大分数不会改变 Softmax 结果，却能避免直接对很大的正数求指数。实验程序会直接提取本代码块，不再维护第二份实现。

<!-- example: softmax -->
```python
import math

def probabilities(logits: list[float], temperature: float = 1.0) -> list[float]:
    if not logits or any(not math.isfinite(x) for x in logits):
        raise ValueError("logits must be non-empty and finite")
    if not math.isfinite(temperature) or temperature <= 0:
        raise ValueError("temperature must be finite and positive")
    largest = max(logits)
    weights = [math.exp((x - largest) / temperature) for x in logits]
    total = sum(weights)
    return [x / total for x in weights]

assert [round(x, 4) for x in probabilities([2, 1, 0])] == [0.6652, 0.2447, 0.09]
assert [round(x, 4) for x in probabilities([2, 1, 0], 0.5)] == [0.8668, 0.1173, 0.0159]
```

`math.isfinite` 排除无穷值和非数值 NaN；正式参数校验使用 `ValueError`。最后两个 `assert` 只用于检查示例结果，不承担生产参数校验。这里刻意不实现掩码输入，掩码的机制已经在第 04 章建立。

## 5. Top-k 与 Top-p 怎样删选候选

两者都可以在采样前缩小候选集合，但选择规则不同。

假设已经得到按概率从大到小排列的分布：

| 候选 | A | B | C | D |
|---|---:|---:|---:|---:|
| 概率 | 0.50 | 0.30 | 0.15 | 0.05 |

**Top-k** 固定保留前 `k` 项。`k=2` 保留 A、B，丢掉 C、D；保留项总概率 0.80，重新归一化后为 `0.625、0.375`。

**Top-p（核采样）** 保留累计概率达到阈值 `p` 的最小前缀集合。`p=0.80` 保留 A、B；`p=0.90` 时前两项不够，需要再保留 C，总和 0.95，再在这三项中归一化采样。因此候选数量由分布决定，不固定等于某个 k。

换成 `[0.92, 0.04, 0.03, 0.01]`，`p=0.90` 只保留第一项。即使叫“采样”，此时也没有多个候选可抽。

温度与候选过滤可以组合，但执行顺序、至少保留多少项、参数是否受支持由具体实现决定。为定位问题，先只改变一个主要参数，再做固定数据集对照。语义依据见 [Transformers 的生成策略](https://huggingface.co/docs/transformers/v5.17.0/en/generation_strategies)。

## 6. 重复、结构和停止分别约束什么

重复惩罚会根据已经生成的内容调整后续分数，用来减少某些循环或重复模式。常见的 frequency penalty（频率惩罚）按出现次数调整，presence penalty（出现惩罚）主要看是否出现过；一些实现中的 repetition penalty（重复惩罚）则按原分数的符号重新缩放。它们不是同一个公式，具体作用范围、计算次序和默认值需核对实际接口。过强惩罚还可能破坏需要重复的术语、代码变量或正式名称。

**结构化输出**则针对允许的输出形式。例如根据 JSON Schema 限制字段和类型，某些实现会在解码时屏蔽当前不合法的续写。它约束“怎样写”，不自动证明“字段内容是真的”。接口是否支持、支持哪个 Schema 子集，仍需按模型核对。

一次生成常见的终止原因需要分开处理：

| 终止情况 | 应用应该怎样理解 |
|---|---|
| 模型生成结束标记 EOS | 模型选择停止；仍要验证业务内容 |
| 达到输出长度上限 | 可能在句子或对象中间截断，不能按完整答案处理 |
| 命中配置的停止序列 | 按接口约定停止；停止文本是否保留因实现而异 |
| 转交工具调用 | 应用进入工具处理流程，不等于外部动作完成 |
| 拒绝回答、错误或取消 | 各有处理分支，不能统一当成成功文本 |

## 7. 流式传输与推测解码不要混在一起

**流式传输（streaming）** 让应用在完整输出结束前收到部分结果，通常改善感知等待，但不自动减少模型计算。网络事件可能包含半个工具参数片段、多个 Token 的文本，或只含状态信息。一个分片不是天然等于一个 Token。

**推测解码（speculative decoding）** 改变的是计算安排：先用较便宜的方式提出若干后续候选，再让目标模型一起验证，接受符合条件的前缀，遇到不接受的部分则修正。因此，自回归的信息依赖不等于目标大模型永远每次前向只能推进一个 Token。

经典算法在其接受、拒绝和重采样规则成立时保持目标分布；不能据此宣称所有近似加速实现都严格等价，或任何工作负载都会加速。参见 [Speculative Decoding 原论文](https://arxiv.org/abs/2211.17192)。

## 8. 本章小结

模型先算分数，解码规则再决定输出。温度缩放分布，Top-k 和 Top-p 缩小候选集合，停止规则控制何时结束。它们改变生成行为，不替代知识获取与事实验证。普通解码有顺序依赖，缓存、流式输出与推测解码则分别处理重复计算、结果交付和计算安排。

## 9. 🎯 面试怎么回答

**问：Temperature、Top-k、Top-p 有什么区别？**

> 模型先得到词表 logits。正温度通过缩放分数改变 Softmax 分布，低温让概率集中，高温让低分项有更多采样机会。Top-k 固定保留前 k 个候选；Top-p 按累计概率阈值选择数量可变的候选，再归一化采样。它们都不提供新事实。线上还要核对模型实际支持的参数、终止原因，并用固定样本做回归；不能把 temperature=0 当成真实性或跨环境确定性的保证。

## 10. ⚠️ 易错点

- 把 Token 概率当成整句事实置信度。两者不是同一件事。
- 以为 Top-p 固定保留 p 比例的词表。它限制的是累计概率质量，不是词表数量比例。
- 达到长度上限以后，把半段 JSON 当成正常返回。需要检查终止状态，再校验结构。
- 以为流式分片越多就说明生成 Token 越多。分片由接口和网络交付决定，计数应有明确口径。
