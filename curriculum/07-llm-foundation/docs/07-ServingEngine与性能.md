# 07｜模型服务与性能：把等待、吞吐和显存分开判断

[← KV Cache 与两阶段推理](06-KVCache与PrefillDecode.md) · [模块首页](../README.md) · [模型 API 与选型 →](08-ModelAPI与Selection.md)

一个请求在本地很快完成，接入几十个用户后却开始排队。模型权重明明装得下，为什么还会显存不足？换成低精度后文件更小，为什么用户没有觉得更快？

这些问题需要把单次模型计算放进模型服务（serving）的调度与资源管理中。本章先用不同长度的请求解释动态批处理，再分别讨论 KV 分页、量化和性能测量，不用一个“加速”标签掩盖它们的不同作用。

## 1. 固定一批请求，为什么会浪费可用位置

假设某实现每批最多同时处理三条序列，A、B、C 分别需要生成 2、5、8 枚 Token。这里只比较普通 Decode 的迭代占用，暂不计输入处理和调度开销。

如果批成员固定，A 结束后对应位置不能接入新请求，B、C 还要继续。A 已经完成，不是它本人必须等待 C 才能收到输出；浪费的是这个批中本来可能复用的处理容量。

**Continuous Batching（连续批处理）** 在迭代边界重新安排活跃序列：完成的退出，待处理的新请求在资源允许时加入。

| 迭代结束后 | 固定成员的批 | 连续批处理可做的安排 |
|---|---|---|
| 第 2 轮，A 结束 | A 的位置不再产出有效 Token | 加入准备好的 D |
| 第 5 轮，B 结束 | B 的位置也闲置 | 加入准备好的 E |
| 第 8 轮，C 结束 | 此批结束 | C 退出，其他序列按状态继续 |

这不是把几条 HTTP 请求拼成一个大 JSON。它发生在模型服务内部，而且加入请求仍受 Prefill、Token 数量预算、KV 容量和调度策略限制，不能承诺完成一条就“无条件立即”补满。

## 2. 输入处理与输出生成为什么需要共同调度

长输入的 Prefill 可能占用较长一次计算。如果它长时间阻塞正在输出的请求，用户会看到文字突然停顿。因此调度器不仅决定“谁进入批”，还要决定每轮分配多少输入和输出工作。

一种办法是 **Chunked Prefill（分块预填充）**：把长输入拆成若干计算块，与 Decode 交错安排。这里切的是计算工作，不是重新定义文档语义，也不是把长文档拆成互不相干的独立问答。

另一种部署方式将 Prefill 和 Decode 分配到不同资源池。它能分别适配两种负载，却需要传输或共享 KV，并处理路由、排队与额外故障点。如果传输成本盖过收益，拆开不一定更快。应用岗要能提出比较条件，而不是把“分离”视为必选架构。

## 3. PagedAttention 怎样减少缓存浪费

假设每条序列按最大 1000 Token 预留一整段连续 KV 空间，实际只用了 100，就会闲置大量空间。序列长度变化和动态退出还会让显存管理更难。

**PagedAttention（分页注意力）** 把 KV 按固定大小的块组织，再用映射表把序列的逻辑块对应到实际物理块。注意力计算通过映射找到需要的 K/V，序列不必占据一整段连续的物理显存。

```text
序列的逻辑块：  第 0 块    第 1 块    第 2 块
                  │          │          │
块表映射：        7          2         11
                  │          │          │
物理显存：      块 7       块 2       块 11
```

假设每块容纳 16 Token，长度 35 需要 `ceil(35/16)=3` 块（ceil 表示向上取整），容量 48 Token，最后一块有 13 个位置暂未使用。分页减少大块预留和碎片，但不是数学上完全零浪费；块表、尾块和实现元数据仍有代价。

分页也能支持某些前缀块共享；继续写入共享块时必须维护正确的引用与写入隔离。**PagedAttention 包括适配分页存储的注意力计算，不是仅仅一张内存表；但它并不以改变标准注意力的语义来获得这部分收益。** 参见 [PagedAttention 原论文](https://arxiv.org/abs/2309.06180)。

## 4. 三种经常混淆的优化

| 方法 | 主要改变什么 | 没有自动解决什么 |
|---|---|---|
| FlashAttention | 通过分块与减少高带宽显存访问，执行精确注意力计算 | 不会自动让所有历史 KV 消失 |
| PagedAttention | KV 的分页布局、寻址与复用 | 不会自动改变模型 KV 头数 |
| GQA、MQA | 多个查询头共享 K/V 的模型结构 | 不是对任意检查点随便开关的纯调度优化 |

方法可以组合，但收益来自不同位置。FlashAttention 的机制依据见 [原论文](https://arxiv.org/abs/2205.14135)。比较时要记录实际启用的内核和缓存方式，不能仅从框架名称推断实现。

## 5. 显存不足时，引擎到底做什么

显存除了权重，还要放活跃 KV、临时中间结果和计算工作空间。权重装得下，不意味着任意长度和数量的请求都能同时执行。

空闲 KV 不够时，服务需要决定：让新请求等待或拒绝它，还是先让部分运行中请求腾出资源。后者称为**抢占**。被抢占的请求以后继续执行，必须重新取得所需状态，不能凭空接着算。

一种方式是释放部分状态，恢复时重算；另一种是把状态卸载到其他存储层，之后再读回。重算花计算时间，卸载与恢复花传输时间，两者都可能延长等待。应同时检查活跃序列数、长度、缓存占用与抢占情况，再判断并发上限是否合理。

<details><summary>实现核对：vLLM 0.30.0 V1 的默认重算与可选卸载</summary>

该版本的 V1 文档将默认抢占方式写为 `RECOMPUTE`，与旧实现的 `SWAP` 区分；它也提供需要明确配置的 KV Offloading。因此“默认重算”不等于“不支持卸载”，“有卸载能力”也不等于所有请求都默认使用。

同版文档说明，支持条件下默认启用分块 Prefill。需要部署时查 [优化说明](https://docs.vllm.ai/en/v0.30.0/configuration/optimization/) 和 [KV Offloading](https://docs.vllm.ai/en/v0.30.0/features/kv_offloading_usage/)，不要把一个版本的默认值套给其他引擎。本章未执行该引擎的负载测试。

</details>

## 6. 量化到底缩小哪一部分

**Quantization（量化）** 用更低精度表示某些数值。先问被量化的对象：是权重、激活，还是 KV？三者占用和误差传播的位置不同。

权重存储从每参数 2 字节降到理想的 4 bit，即 0.5 字节，裸数据理论上是四分之一；但分组尺度、零点、对齐和未量化层会增加实际大小。Weight-only（仅权重）量化并不表示所有中间计算都在 4 bit 中完成，也不会自动压缩 KV。

**PTQ（训练后量化）**是在模型训练完后做量化与必要校准；**QAT（量化感知训练）**则让训练提前考虑量化误差。这说明低精度模型可能怎样得到，不要求使用模型的应用团队都自行实现量化训练。[机制依据](https://docs.pytorch.org/ao/stable/workflows/qat.html)

更小的权重可能降低传输与读取成本；端到端速度还取决于硬件低精度支持、计算内核、反量化开销、批量和当前瓶颈。因此需要同时比较质量、显存和目标负载的延迟，不能只比较文件大小。

## 7. 先确定测量边界，再谈延迟

以下采用客户端请求发出作为起点，以输出 Token 到达作为时间点，另记录最终完成事件：

| 指标 | 本章的定义 | 它帮助定位什么 |
|---|---|---|
| TTFT，首 Token 延迟 | 请求开始到第一枚输出 Token 到达 | 网络、排队、输入处理等首段等待 |
| ITL，Token 间隔 | 相邻两枚输出 Token 到达的间隔 | 输出是否出现停顿 |
| TPOT，平均每输出 Token 耗时 | 首 Token 后到末 Token 的时间，除以 `输出数−1` | 后续输出平均节奏 |
| 端到端延迟 | 请求开始到明确的完成事件 | 用户等到完整结果的时间 |
| 吞吐 | 测量窗口内完成的请求数或 Token 数除以秒数 | 整体处理能力 |

若输出为 1 枚 Token，TPOT 的分母为 0，应记为不适用，而不是强行写 0 毫秒。若只获得网络文本分片，测得的是分片间隔；没有可靠 Token 时间点时不能冒充逐 Token ITL。

**假设计时示例：** 第一枚 Token 在 0.8 秒到达，第 101 枚在 2.8 秒到达，完成事件在 2.9 秒到达。

```text
TTFT = 0.8 秒
TPOT = (2.8 − 0.8) / (101 − 1) = 0.02 秒 = 20 毫秒
最后一枚 Token 到达时间 = 0.8 + 100 × 0.02 = 2.8 秒
完整请求耗时 = 2.9 秒
```

最后的 0.1 秒并未包含在本章 TPOT 中。不同压测工具可能用请求完成时间近似，或采用不同吞吐分母；报告要保留实际定义。不能把 TTFT 当成纯 Prefill 时长，也不能把总 Token 吞吐当成每个用户的生成速度。

## 8. 怎样比较一个改动是否有效

先定义业务成功标准与服务目标，例如“正确完成抽取，且绝大多数请求在指定时间内开始输出”。**SLO（服务目标）** 是团队选择的可度量目标，不是模型机制自动给出的默认值。

然后固定数据分布：输入和输出长度、到达速率、并发、模型与精度、缓存冷热状态。记录任务质量、错误率、TTFT 与总延迟的 P50/P95/P99、输入输出 Token 吞吐、显存和单位成功任务成本。P95 指有 95% 的测量值不超过这个值，不代表最慢请求被排除后就没有风险。

负载超过稳定处理能力时，排队会不断增长。增大批量可能提高吞吐，也可能让单轮计算或等待更长；缩小输入预算可能改善首段延迟，也可能删掉重要证据。两种优化都要把质量和延迟放在同一组对照里。

托管 API 用户虽然看不到内部 GPU，仍可分别记录输入输出长度、缓存报告、限流、重试、首段与全程延迟。它们支持做模型路由和并发预算，但不足以直接证明厂商内部用了哪种调度算法。

## 9. 本章小结

连续批处理解决不同长度请求的动态安排，分页改善 KV 的显存利用，量化改变指定数值的表示。性能结论必须有版本、负载和测量边界。模型放得下、单请求快、吞吐高、尾延迟好是不同判断，不能互相替代。

## 10. 🎯 面试怎么回答

**问：模型能放进 GPU，为什么并发一高就不稳定？**

> 权重只是显存的一部分。每条活跃序列还会增长 KV，长输入和输出会共同抬高占用；调度与临时工作空间也需要余量。我会按真实长度分布核算容量，检查排队、抢占和取消是否有效，再对照连续批处理、分页、量化等配置。验收同时看任务质量、首 Token、输出节奏和尾延迟，不把单请求演示或吞吐提升当成生产稳定性的证明。

## 11. ⚠️ 易错点

- 把短请求完成后无法补充批成员，写成短请求一定不能提前返回。
- 把分页等同于零开销，或者把权重量化等同于 KV 量化。
- 将某个旧版引擎的默认策略写成所有版本事实。
- 用空载、热缓存、很短输出的单个请求，推断真实并发下的延迟。

## 12. 自测

**任务 1：** 假设分页块可容纳 8 Token，一条长度为 19 的序列需要多少块、预留多少位置、尾块闲置多少位置？回答中不能声称这就是实际 GPU 字节数。

<details><summary>答案与解释</summary>

需要 3 块，可容纳 24 Token，尾块闲置 5 个位置。换算显存还要知道每 Token 的 KV 字节数和块管理开销。

</details>

**任务 2：** 某请求首 Token 在 0.5 秒到达，第 51 枚在 2.0 秒到达，完成事件在 2.1 秒到达。按本章口径求 TTFT、TPOT、端到端延迟。只有一枚输出的请求怎样记 TPOT？

<details><summary>答案与解释</summary>

TTFT 为 0.5 秒，TPOT 为 (2.0−0.5)/50=0.03 秒，即 30 毫秒，端到端为 2.1 秒。只有一枚输出时 TPOT 不适用，应保留这个状态。

</details>
