# 07. 装饰器与上下文管理器

[← 上一章：迭代与生成器](06-迭代器-生成器-yield.md) · [模块主页](../README.md) · [下一章：类与对象协议 →](08-面向对象-魔术方法.md)

记录日志时，不希望每个函数都复制相同代码；打开文件时，也不希望每条返回路径都手工关闭文件。这两种需求都包含“在工作之前和之后做事”，但管理的边界不同：

**Decorator（装饰器）扩展函数／类的行为；Context Manager（上下文管理器）管理一段代码块的进入与退出。**

本章先用函数对象、参数和闭包推导装饰器，再从异常退出时如何清理资源推导 `with`。自定义类的协议实现放在下一章，异常分类与文件细节放在第 09 章。

## 1. 从函数对象到装饰器：每一步都能拆开

### 1.1 函数可以被赋值和传递

```python
def hello():                 # 创建一个函数对象
    print("hello")           # 被调用时输出 hello

f = hello                    # 让另一个名字引用同一个函数；没有执行函数体
f()                          # 调用函数，输出 hello
```

既然函数可以赋值，也可以作为参数传进另一个函数。接收方可以创建一个新函数，让它在将来调用时先做扩展工作，再调用原函数。

### 1.2 原函数、装饰器、包装函数各是什么

```python
def decorator(func):         # 装饰器：接收原函数对象
    def wrapper():           # 包装函数：将来调用时实际运行的函数
        print("before")      # 原函数之前执行
        func()               # 通过闭包中保存的引用调用原函数
        print("after")       # 原函数正常返回后执行
    return wrapper           # 返回包装函数对象，而不是在这里调用它


def hello():                 # 原函数：只保留自己的业务主体
    print("hello")           # 业务行为

hello = decorator(hello)     # 用原函数创建 wrapper，再把名字 hello 改绑到 wrapper
hello()                      # 依次输出 before、hello、after
```

```text
装饰阶段：原 hello → decorator → 创建并返回 wrapper → 名字 hello 改绑
调用阶段：hello() → wrapper → before → 原函数 → after
```

原函数没有消失，包装函数通过 `func` 保留对它的引用。这里不是“修改原函数的源代码”，而是改变名字最后绑定到哪个可调用对象。

### 1.3 @ 是定义后应用装饰器的语法

以下例子继续使用上面定义的 `decorator`：

```python
@decorator                   # 函数定义完成后，等价于 hello = decorator(hello)
def hello():                 # 定义原函数
    print("hello")           # 原来的业务代码

hello()                      # before、hello、after
```

`@decorator` 是 **Syntactic Sugar（语法糖）**，让常见的绑定操作有更直接的写法。装饰器在定义阶段应用，不是每次业务调用时都重新应用一次。装饰器语法也可以应用到类，第 08 章会介绍类对象。

## 2. 通用包装：输入、输出与说明信息都要保持

### 2.1 wrapper 为什么接收 *args、**kwargs

```python
from functools import wraps  # 标准库工具，帮助保留被包装函数的信息


def decorator(func):         # 接收任意一个待包装函数
    @wraps(func)             # 将原函数的名称、文档等信息保留到包装函数上
    def wrapper(*args, **kwargs):      # 收集本次业务调用的参数
        print("before")               # 执行前置行为
        result = func(*args, **kwargs) # 展开参数，调用原函数
        print("after")                # 原函数正常返回后执行
        return result                 # 将原结果交回调用方，不无意改变返回值
    return wrapper                    # 返回包装函数对象


@decorator                   # 定义后应用装饰器
def add(a, b):               # 原函数有两个参数
    """返回两个数的和。"""   # 函数文档，可通过 __doc__ 查看
    return a + b             # 返回数值结果

print(add(2, b=3))           # before、after，然后输出 5
print(add.__name__)          # add，而不是 wrapper
print(add.__doc__)           # 返回两个数的和。
```

定义处用星号收集，调用原函数时用星号展开。只写 `func()` 会丢掉输入；只调用原函数却不 `return`，会让调用方收到 `None`。这两种错误都改变了原函数的行为契约。

### 2.2 functools.wraps 保留什么、不保留什么

**Metadata（元信息）** 是函数名称、文档等描述信息。没有 `wraps` 时，名字虽然还叫 `add`，它引用的新函数的 `__name__` 却可能是 `wrapper`。`wraps` 帮助保留 `__name__`、`__doc__` 等，并设置 `__wrapped__` 指向原函数，方便调试、反射和框架工具识别。

它不自动保证包装正确：参数、返回值、异常以及同步／异步语义，都仍由 wrapper 的实现负责。

## 3. 装饰器的两种嵌套：配置与叠加

### 3.1 带参数装饰器：三个时间点对应三层函数

```python
from functools import wraps  # 保留元信息


def repeat(n):               # 第一层：接收配置参数，即重复次数
    if n < 1:                # 本例要求次数至少为 1
        raise ValueError("n 必须至少为 1")  # 无效配置直接报告错误
    def decorator(func):     # 第二层：接收待装饰的原函数
        @wraps(func)         # 关联原函数说明信息
        def wrapper(*args, **kwargs):      # 第三层：接收实际业务调用参数
            result = None                  # 保存最后一次结果
            for _ in range(n):             # 按配置重复 n 次
                result = func(*args, **kwargs)  # 每次调用原函数
            return result                  # 返回最后一次调用结果
        return wrapper                     # 返回业务包装函数
    return decorator                       # 返回已经保存 n 的装饰器


@repeat(3)                   # 先得到装饰器，再把它应用到 hello
def hello():                 # 原业务函数
    print("hello")           # 每次调用打印一次

hello()                      # 打印三次 hello
```

```text
repeat(3)         → 得到一个记住 n=3 的装饰器
repeat(3)(hello)  → 得到一个记住原函数的 wrapper
wrapper()        → 才真正运行原函数三次
```

所以展开是 `hello = repeat(3)(hello)`。装饰器的配置参数与业务函数的调用参数不是同一组输入，不在同一个时间点消费。

⚠️ 这用于解释语法，不是完整重试器。重复打印容易观察，重复写入或扣款可能产生副作用；工程重试还需要错误分类、次数上限和幂等边界。

### 3.2 多个装饰器：先包装内层，先调用外层

```python
from functools import wraps  # 保留原函数信息


def layer(label):            # 创建带可见标签的装饰器
    def decorate(func):      # 接收下一层函数
        @wraps(func)         # 保留元信息
        def wrapper():       # 本例只处理无参数函数
            print(label, "进入")  # 当前层先进入
            result = func()       # 调用下一层
            print(label, "退出")  # 下一层返回后退出
            return result         # 转交返回值
        return wrapper            # 返回这一层包装
    return decorate               # 返回装饰器

A = layer("A")               # 准备装饰器 A
B = layer("B")               # 准备装饰器 B

@A                           # 最外层
@B                           # 靠近函数的一层先应用
def f():                     # 原函数
    print("业务")            # 原函数主体

f()                          # A 进入 → B 进入 → 业务 → B 退出 → A 退出
```

绑定关系是 `f = A(B(f))`。**定义时，靠近函数的装饰器先包装；调用时，最外层先进入。** 不要把这两个顺序混成一句“装饰器从上往下执行”。

## 4. 正常后置行为与退出清理：不能混为一谈

### 4.1 异常会跳过普通的后续语句

前面的 `func()` 后面直接写 `print("after")`，只有原函数正常返回才会执行。原函数抛异常时，这条普通后置语句可能被跳过。

**Exception（异常）** 是程序报告无法正常继续的一种机制。`try/finally` 把收尾放进正常返回、提前返回和异常传播都会经过的退出路径；第 09 章完整讲错误分类。这里先掌握一个边界：**必须清理时用 finally，而不是依靠后置语句恰好执行到。**

### 4.2 一个保留返回值与异常语义的计时器

```python
import time                  # 提供计时工具
from functools import wraps  # 保留函数元信息


def timer(func):             # 接收要计时的函数
    @wraps(func)             # 保留名称、文档等信息
    def wrapper(*args, **kwargs):  # 接收调用输入
        start = time.perf_counter()  # 记录适合测量耗时的时钟值
        try:                        # 尝试执行业务
            return func(*args, **kwargs)  # 正常时把原函数结果交回
        finally:                    # 成功或异常退出都记录耗时
            cost = time.perf_counter() - start  # 计算经过的时间
            print(f"cost: {cost:.6f}s")          # .6f 表示保留六位小数
    return wrapper                  # 返回计时包装
```

这里没有吞掉业务异常，清理后异常仍向外传播。进程强杀、解释器崩溃或机器断电不属于正常语言控制流，不能承诺这种情况下 `finally` 仍物理执行。

### 4.3 装饰器也不一定创建新 wrapper

日志、权限检查、缓存、计时、重试、Web 路由注册和 API 鉴权都可以使用装饰器。但装饰器也可以只把函数登记到注册表，再返回原函数本身。

因此，**装饰器是一种接收对象、返回用于重新绑定结果的可调用对象；“返回一个新包装函数”只是最常见实现，不是唯一实现。** 它的质量要看扩展之后的契约，而不是只看有无 `@`。

## 5. 上下文管理器：把资源使用限制在一个范围内

### 5.1 with 管的是获取、使用、释放

以下文件例子假设当前工作目录已有 `data.txt`；第 09 章提供从创建文件开始的完整实验。

```python
with open("data.txt", "r", encoding="utf-8") as f:  # 打开文本文件并进入管理范围
    content = f.read()                             # 在范围内读取全部文本
# 离开 with 后文件已关闭，但 content 这个字符串仍可使用。
```

`"r"` 表示读取，`encoding="utf-8"` 规定如何把字节解释为文本。`as f` 接收进入阶段返回的对象。文件句柄、锁、连接都不只是“一个变量”，还涉及资源的占用与释放。

不用 `with` 时，文件关闭的核心意图近似写成：

```python
f = open("data.txt", "r", encoding="utf-8")  # 成功取得文件资源
try:                                        # 在资源有效期间使用
    content = f.read()                      # 读取可能成功，也可能失败
finally:                                    # 无论使用阶段怎样退出
    f.close()                               # 都执行关闭
```

`with` 的价值不是纯粹缩短代码，而是把生命周期边界显式组织起来。

### 5.2 上下文管理协议：进入与退出各接收什么

```text
获得上下文管理器
→ __enter__()：进入；返回值交给 as 后的名字
→ 执行 with 代码块
→ __exit__(异常类型, 异常对象, 回溯信息)：退出并清理
→ 继续正常代码，或让异常继续传播
```

**Traceback（回溯）** 记录异常经过的执行位置；没有异常时，三个异常参数都是 `None`。

`__exit__` 返回真值，可以表示异常已经处理，不再向外传播；返回假值或 `None` 则不抑制异常。如果 `__enter__` 自己失败，尚未成功进入，不会自动再调用这个管理器的 `__exit__`；进入阶段要负责自己的部分获取失败。

因此 with 不是“自动吞错误”，也不是“资源保证永远成功获取”。具体 `MyContext` 类实现移到[第 08 章](08-面向对象-魔术方法.md)的“把协议实现出来”，先学类与 `self` 再逐行看实现。

### 5.3 用生成器写：contextlib.contextmanager

```python
from contextlib import contextmanager  # 将符合约定的生成器函数转换为上下文管理器工厂


@contextmanager              # 应用标准库提供的装饰器
def resource():              # 定义进入与退出流程
    print("acquire：获取资源") # with 进入阶段执行
    try:                     # 统一管理退出清理
        yield "resource"     # 只产出一次，将这个值交给 as 后的名字
    finally:                 # 正常退出或异常退出都到这里
        print("release：释放资源")  # 清理资源


with resource() as r:         # 进入范围，r 接收 'resource'
    print(r)                 # 在范围内使用资源
```

输出顺序是获取、使用、释放。生成器必须恰好 `yield` 一次：第一次暂停时把控制权交给 with 代码块，代码块退出时再恢复生成器或把异常送回暂停点，完成退出处理。

**必须清理的逻辑写在 finally 里**。仅仅“放在 yield 后面”不足以保证异常路径执行它；捕获异常却不继续抛出，也可能无意中抑制错误。

## 6. 怎么选、怎样与后续知识连接

| 对比 | 装饰器 | 上下文管理器 |
|---|---|---|
| 主要边界 | 函数／类 | 一段代码块与资源 |
| 典型语法 | `@decorator` | `with ...:` |
| 常见用途 | 日志、缓存、权限、计时、注册 | 文件、锁、连接、事务、追踪范围 |
| 核心问题 | 扩展行为但保持接口契约 | 管理进入、使用、退出 |

二者可以组合：外层函数使用计时装饰器，内部用 with 管理文件。它们没有互相替代关系。第 08 章把协议写到类里，第 09 章展开异常与文件；第 12 章涉及异步时，还要使用与异步行为兼容的包装和 `async with`，不能机械套用同步版本。

本章依据：[functools.wraps](https://docs.python.org/3.14/library/functools.html#functools.wraps)、[contextlib](https://docs.python.org/3.14/library/contextlib.html)、[with 语句](https://docs.python.org/3.14/reference/compound_stmts.html#the-with-statement)。

## 7. 🎯 高频面试题

### Q1：什么是装饰器？

🎯 **回答框架**：装饰器本质上是一个接收函数或类并返回新函数或类的可调用对象。它可以在不修改原函数主体的情况下扩展行为，常用于日志、缓存、鉴权、计时等。`@decorator` 可以理解为语法糖。

补充边界：上面描述的是常见包装形式；装饰器也可以返回原对象，例如只做注册，不一定必须返回一个新身份的函数。

### Q2：为什么要用 `functools.wraps`？

为了尽量保留被装饰函数的元信息，如 `__name__`、`__doc__` 等，也利于调试和工具识别。

### Q3：`with` 做了什么？

它使用上下文管理协议，在进入代码块时调用进入逻辑，在离开代码块时执行退出和资源清理逻辑，即使发生异常也能更可靠地释放资源。

## 8. ⚠️ 易错点

- 错误：装饰器全部逻辑都在每次业务调用时执行。正确：区分定义时应用装饰器与调用时运行包装。
- 错误：有 wrapper 就保持了原函数行为。正确：还要检查参数转发、返回值、异常和元信息。
- 错误：普通后置语句等价于清理。正确：异常会跳过后续语句，统一清理使用 finally。
- 错误：所有装饰器都必须创建新函数。正确：只做登记时也可以返回原对象。
- 错误：with 自动吞掉所有异常。正确：异常是否抑制由退出协议的返回值决定。
- 错误：contextmanager 中 yield 后的语句必然清理。正确：必须清理的部分放入 try/finally，并遵守一次 yield 的约定。
