# 11. 内存管理、垃圾回收与 GIL

[← 上一章：结构化数据](10-结构化数据-JSON与校验.md) · [模块主页](../README.md) · [下一章：线程、进程与协程 →](12-线程-进程-协程-async-await.md)

前面讨论“哪些名字指向同一个对象”，现在继续问：**当业务不再需要对象时，谁还在引用它？对象何时可以释放？多个线程同时操作对象又会发生什么？**

引用计数、垃圾回收和 GIL 不应作为三个孤立名词背诵。前两者处理对象生命周期，后者涉及解释器并发执行与内部状态保护；共享的是对象模型，不是同一种职责。

```text
对象与引用 → 删除绑定 → 对象是否仍可达
→ 引用计数与循环垃圾回收 → 业务生命周期泄漏
→ 多线程访问解释器状态 → GIL 的作用与限制
→ 根据等待、计算和共享状态选择并发方案
```

## 1. 语言规则、解释器实现、业务生命周期先分三层

| 层次 | 要回答的问题 | 典型内容 |
|---|---|---|
| Python 语言语义 | 名字和对象怎样关联？操作代表什么？ | 引用、绑定、可变性、del、with |
| CPython 实现 | 怎样实现分配、回收和内部同步？ | 引用计数、循环 GC、内存分配器、GIL／自由线程构建 |
| 业务生命周期 | 数据应该保留多久，由谁释放引用？ | 缓存上限、会话到期、任务结束、历史清理 |

**CPython** 是 Python 的一种实现。不能把它的内存管理策略说成所有 Python 实现都必须如此，也不能把业务“已经不用”当成解释器已经能够判断的事实。

本章主要解释常见 CPython 的基础模型；自由线程构建可能采用不同的计数与延迟回收细节，涉及具体版本的行为以对应文档为准。

## 2. 引用计数：还有谁持有这个对象

### 2.1 多一个名字，就多一条可到达路径

```python
a = []                       # 创建列表，a 引用它
b = a                        # b 也引用同一个列表
holder = [a]                 # 容器也保存对这个列表的引用，不只有变量名能持有它

del a                        # 删除名字 a 的绑定
print(b)                    # []：列表仍被 b 和 holder[0] 引用
print(holder[0] is b)        # True：两条路径通向同一个列表
```

**Reference Counting（引用计数）** 的直觉是跟踪对象被持有的情况。在常见带 GIL 的 CPython 中，大量普通对象的引用计数降到零时，会及时进入释放过程。

```text
名字 a ──┐
名字 b ──┼──> 列表对象
holder[0]┘

删除 a 只去掉其中一条箭头，其他箭头仍然存在。
```

实际引用来源还可能是函数栈、对象属性、默认参数、闭包、缓存等。不要只数屏幕上两个变量名，就以为知道运行时精确引用计数。

### 2.2 del 的三种常见目标

```python
items = [[1], [2]]            # 外层列表保存两个子列表引用
shared = items[0]             # 额外保留第一个子列表

del items[0]                 # 删除外层的一项引用，列表后续元素会相应移动
print(items)                # [[2]]
print(shared)               # [1]：被删位置原来指向的对象仍被别的名字持有
```

```python
class Box:                   # 用普通属性演示属性删除
    pass                     # 不增加方法

box = Box()                  # 创建实例
box.value = [1, 2]           # 实例属性持有列表
saved = box.value            # 再保存一条引用
del box.value                # 删除属性关联，不直接命令列表销毁
print(saved)                # [1, 2]
```

`del name` 删除名字绑定，`del obj.attr` 删除属性，`del items[i]` 让容器执行删除项的操作。它们可能使某些对象不再被引用，但 `del` 本身不是“强制释放指定对象”的命令；自定义类型还可以控制属性／元素删除行为。

### 2.3 引用计数的优势与边界

优势是很多普通对象能在引用消失后及时处理，不需要一律等到周期扫描。边界是**一组对象互相引用时，单看计数可能都不为零**。

同时，“计数归零通常及时释放”不是所有版本、对象与构建方式的一刀切保证：解释器可能有长寿／不朽对象，自由线程模式也涉及延迟计数或回收。文件、锁等资源仍应通过显式生命周期管理，不依赖某次垃圾回收时机。

## 3. 循环引用：没有外部入口，却还互相持有

### 3.1 为什么计数不为零也可能是垃圾

```python
a = []                       # 创建列表 A
b = []                       # 创建列表 B
a.append(b)                  # A 保存对 B 的引用
b.append(a)                  # B 保存对 A 的引用

del a                        # 删除外部名字 a
del b                        # 删除外部名字 b；A、B 内部仍互相引用
```

```text
外部入口消失以后：
      A ─────> B
      ↑        │
      └────────┘
```

**Reachable（可达）** 表示还能沿程序存活的引用路径访问到对象。现在这组对象内部仍有引用，但整体已经没有可供业务到达的外部入口；单靠“引用计数是否为零”不足以发现这一点。

### 3.2 循环 GC 补的是这一类缺口

**GC（Garbage Collection，垃圾回收）** 在这个语境中常特指 CPython 用来补充引用计数的循环垃圾回收机制。它跟踪相关容器对象，分析其中的引用关系，识别不可达的循环等对象组。

```text
引用计数：常见的引用消失后处理
循环 GC：识别整体已不可达、内部却互相持有的对象关系
```

这里用可达性解释“为什么能回收”，不表示 CPython 每次都对所有对象从根完整扫描。具体跟踪、分代与阈值策略随版本变化；应用基础首先要分清职责。

```python
import gc                    # 导入循环垃圾回收接口
collected = gc.collect()     # 请求一次收集，返回本次收集相关的数量信息
print(collected)             # 具体数字取决于整个解释器状态，不是固定示例输出
```

### 从组内引用推导“有没有外部入口”

对 A↔B 这一组候选容器，可以用一份**临时计数**理解循环检测：复制候选对象的引用计数，再扣除候选组内部的引用。扣的是分析账本，不是实际修改对象的引用计数。

| 情形 | A 的引用来源 | B 的引用来源 | 扣除组内引用后 |
|---|---|---|---|
| `a` 仍在 | 外部 a 加 B | A | A 有外部剩余，B 暂为 0 |
| `a`、`b` 都删除 | B | A | A、B 都为 0 |

第一种情况不能因为 B 的临时计数为 0 就回收 B：A 从外部可达，沿 A→B，B 也必须保留。收集器还要从有外部剩余的候选继续传播可达性。第二种情况整组都没有外部入口，才成为不可达候选。实际算法还需处理最终化、复活等细节；这里解释的是为什么“彼此持有”不等于“业务还能到达”。这也说明 GC 不需要每次扫描解释器全部对象，候选集合与扫描策略是实现选择。

### 3.3 为什么手动 collect 不是默认优化方案

频繁收集可能增加扫描、暂停和 CPU 开销；仍被业务容器引用的对象也不会因为你调用 collect 就被随意删除。资源泄漏还可能来自未关闭的文件、连接或第三方本地库，不一定是循环 GC 问题。

因此先定位增长对象与持有者，再考虑收集策略。不要把“内存高”自动翻译为“GC 不够勤快”。

## 4. 有 GC，业务内存为什么仍然可能一直增长

### 4.1 解释器不知道业务认为数据已经过期

```python
history = []                 # 一个长期存在的历史容器

def save_result(result):     # 每次请求都会调用
    history.append(result)   # 不断保存引用，没有容量和到期边界

save_result({"answer": "A"}) # 保存第一份结果
save_result({"answer": "B"}) # 保存第二份结果
print(len(history))         # 2；服务运行久了仍可能继续增长
```

这不是“对象不可达但 GC 没找到”，而是对象仍然可达。解释器不能代替业务判断应该留下最近十条、保留一天还是立即删除。

常见长期持有者包括全局 dict、没有容量限制的 Cache（缓存）、Background Task（长驻任务）、Callback（回调）／Closure（闭包）、Session（会话）与 Agent State（Agent 状态）。

AI 应用中尤其要注意大 PDF／OCR 中间结果、Embedding Batch（向量化批次）、工具返回内容、对话历史，以及 SDK Response / Stream Buffer（响应对象／流缓冲区）。问题不是这些对象不能存在，而是没有明确所有者、容量和结束条件。

### 4.2 先问“谁在持有”，再问“怎样回收”

```text
观察内存随请求数量、时间或数据规模如何变化
→ 定位持续增长的对象／分配位置
→ 找仍然持有这些对象的容器、任务、闭包或缓存
→ 设计到期、容量、释放与取消逻辑
→ 验证增长是否有界，再考虑实现级调优
```

标准库 `tracemalloc` 可以辅助观察 Python 分配位置与快照差异；它不覆盖所有本地库内存，不能把它的一份结果当进程内存全景。**RSS（驻留内存）** 也不等于当前存活 Python 对象总大小：内存分配器可能保留已释放空间供后续复用，因此对象减少不一定让进程占用立刻下降。

## 5. GIL：限制的是谁在同时执行什么

### 5.1 先定义线程与字节码，避免只背锁的全称

**Thread（线程）** 是操作系统调度执行的一个单位，同一进程里的线程通常共享大量内存。**Bytecode（字节码）** 是 CPython 执行 Python 代码时使用的一种中间指令表示。

**GIL（Global Interpreter Lock，全局解释器锁）** 在传统带 GIL 的 CPython 中，主要约束同一解释器里同时执行 Python 字节码的线程。常见单解释器程序可以理解为：通常同一时刻只有一个线程持有 GIL 执行这部分工作。

限定条件很重要：说的是**解释器模式、同一解释器、Python 字节码**，不是“所有 Python 实现”“整个进程所有本地计算”或“机器上只能有一个核工作”。

### 5.2 为什么有这种取舍

GIL 长期简化了 CPython 对引用计数、对象操作和许多共享解释器状态的同步。这减少了一类内部并发复杂度，同时限制传统模式下纯 Python CPU 密集代码的线程并行。

```text
解释器内部同步更容易组织
            ↕ Trade-off（取舍）
纯 Python 计算不能简单靠多个线程同时执行来线性加速
```

“因为 Python 不线程安全”太笼统：需要问的是解释器内部保护什么、业务代码还需要保护什么。

### 5.3 现代构建边界：不能说 Python 永远有同样的 GIL

CPython 从 3.13 起提供可选的 **Free-threaded Build（自由线程构建）**。它与默认带 GIL 构建不是同一个执行模式；扩展库支持、运行时配置和兼容性也影响实际行为，某些扩展还可能让 GIL 重新启用。

因此面试与性能分析先说明解释器版本、构建方式及当前启用状态。不把一条传统 CPython 经验当成永久的语言定律，也不把自由线程构建理解为“所有既有代码自动线程安全、自动提速”。

## 6. 从 GIL 推导并发选择，而不是背结论

### 6.1 I/O 等待时，线程仍然有价值

**I/O-bound（输入输出等待密集）** 任务的时间主要耗在等待 HTTP、数据库、Redis、文件或 LLM API 等外部操作。许多阻塞 I/O 会释放 GIL，让其他线程推进。

```text
线程 A：发出网络请求 → 等待返回 → 继续处理
线程 B：                执行其他可推进的工作
```

所以“有 GIL，多线程就没用”是错误推论。是否有效仍取决于库是否在恰当位置释放 GIL、实际瓶颈和并发开销。

### 6.2 纯 Python 计算与本地库计算要区分

**CPU-bound（计算密集）** 的纯 Python 工作，在传统 GIL 模式下通常不应期待用多个线程直接实现多核加速；多进程／进程池是常见选择。

**Native Code（本地编译代码）** 则可能在计算期间释放 GIL，或由库内部启动本地线程。因此 NumPy、推理前后处理等工作能否多核执行，要查具体操作与库实现，不能只看调用它的文件扩展名是 `.py`。

```text
问的不是“Python 能不能多核”
而是：现在执行的是哪一层代码？是否持有 GIL？库内部是否并行？
```

### 6.3 GIL 不是业务事务锁

以下是需要保护的多步骤意图，不是保证原子的操作：

```text
检查 cache 中是否没有 key
→ 计算新值
→ 把值写入 cache
```

两个线程可能都先检查到“没有”，随后重复计算并互相覆盖。某一个 dict 内部操作受到保护，也不等于三个步骤组成一笔不可分割的事务。

```python
from threading import Lock   # 用业务锁明确保护共同维护的条件

cache = {}                   # 多个调用方可能共享的状态
lock = Lock()                # 所有相关线程需要共同使用同一把锁


def get_or_build(key, build): # build 是负责创建值的函数对象
    with lock:               # 把检查、计算、写入放进同一临界区
        if key not in cache: # 在受保护范围内检查
            cache[key] = build()  # 创建并保存；本例为讲清原子意图，使用简单粗粒度锁
        return cache[key]    # 返回已存在或刚创建的值
```

**Critical Section（临界区）** 是需要互斥访问的代码范围。真实的慢构建不一定适合拿着一把全局锁完成，可能需要按键协调、任务共享或队列；本例展示的是“保护哪一段业务条件”，不是最优性能方案。

共享状态可以通过 Lock（互斥锁）、Queue（队列）、不可变数据或 Owner / Actor（单一所有者／消息处理）等设计管理。自由线程模式和库的内部锁也不会自动代替这些业务不变量。

## 7. 把生命周期和执行模型一起选

| 场景 | 常见起点 | 为什么 |
|---|---|---|
| 大量 LLM／HTTP／DB 等待 | asyncio 或线程 | 利用等待时间推进其他任务 |
| 只有同步阻塞接口的 SDK | 线程池桥接 | 不让事件循环线程被阻塞调用占住 |
| 纯 Python 的重计算解析 | 多进程／ProcessPool | 在传统 GIL 模式下使用独立解释器进程 |
| NumPy／本地推理前处理 | 看库实现再测量 | 是否释放 GIL、内部线程数量各不相同 |
| 大对象长期驻留 | 先查引用与缓存生命周期 | 活对象不会由 GC 替业务擅自清除 |

## 8. 🎯 面试怎么回答

### Python 内存管理

> Python 语言层面是对象和引用语义；在常见 CPython 实现里，主要使用引用计数管理对象生命周期，并配合循环垃圾回收处理不可达循环引用。`del` 删除的是绑定，不等于强制销毁对象。有 GC 也不代表不会发生业务层内存泄漏，只要对象仍被 Cache、全局变量或长任务引用就不会回收。

### GIL

> 在传统 CPython/GIL 模式中，同一解释器进程通常同一时刻只有一个线程执行 Python 字节码。它简化了 CPython 内部共享状态同步，但限制纯 Python CPU-bound 多线程并行。I/O-bound 多线程仍然有价值；CPU-heavy 任务常考虑多进程或会释放 GIL 的 native library。GIL 不等于业务代码天然线程安全。

表述边界：上面按常见单解释器进程讨论，关键范围是同一解释器；还需区分自由线程构建和本地库行为。

## 9. ⚠️ 易错点

- `del` ≠ 立即销毁对象；
  正确理解：它删除名字、属性或容器项等关联，对象可能仍由其他引用持有。
- GC ≠ 所有对象都靠定期扫描回收；
  正确理解：常见 CPython 的循环收集是对引用计数的补充。
- 有 GC ≠ 不会内存泄漏；
  正确排查：持续可达的缓存、会话和任务状态需要业务管理容量与到期。
- GIL 是 CPython 实现概念，不是 Python 语言定义；
  正确表达：说明解释器与构建模式，不作永久化推断。
- 有 GIL ≠ 多线程没用；
  正确理解：大量 I/O 等待和释放 GIL 的本地操作仍可能受益。
- 有 GIL ≠ 业务代码线程安全；
  正确做法：对多步骤共享条件使用明确同步或所有权设计。
- CPU-bound 是否能并行还要看 native library 是否释放 GIL。
  正确判断：区分纯 Python 字节码、本地计算和库内部并发，再实测。

<details>
<summary>1. 为什么循环引用可能需要额外 GC？</summary>

因为一组对象即使整体已经不可达，内部仍可能互相持有引用，使引用计数不归零；循环 GC 用可达性分析帮助识别这类对象图。

</details>

<details>
<summary>2. 有 GC 为什么 Python 服务仍可能内存越来越大？</summary>

如果对象仍被全局容器、Cache、Session、Callback 或长任务引用，它们对 GC 来说仍然是“活对象”。这属于业务生命周期或引用管理问题。

</details>

<details>
<summary>3. GIL 为什么不能替代 Lock？</summary>

GIL 约束的是解释器层执行，不提供业务多步骤操作的事务语义；多个线程仍可能在共享状态读改写之间交错执行，因此仍可能发生竞态。

</details>
