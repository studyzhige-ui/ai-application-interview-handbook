# 08. 面向对象、Duck Typing、Protocol 与魔术方法

[← 上一章：装饰器与资源管理](07-装饰器-上下文管理器.md) · [模块主页](../README.md) · [下一章：异常、文件与模块 →](09-异常-文件-模块与导入.md)

前面一直在使用别人定义好的对象：列表能追加，迭代器能取下一项，上下文管理器能进入和退出。现在反过来问：**怎样定义自己的对象，让它保存状态、提供操作，并参与这些已有语法？**

这才是本章的主线。先学类与实例，再讲属性和方法；最后理解继承、行为契约以及 Python 的对象协议，不从四个抽象名词开始背。

```text
类定义一种对象 → 创建具体实例 → 实例保存状态并提供方法
→ 复用／替换行为 → 明确接口契约
→ 通过魔术方法接入 len、for、with 等语法
```

## 1. 类与实例：给状态和操作一个共同的归属

### 1.1 从一条记录到一个可操作的对象

**Class（类）** 描述一类对象的结构与行为，**Instance（实例）** 是具体创建出来的对象。实例不是与对象并列的另一种东西：它就是这个类的对象。

```python
class Person:                # 定义 Person 类，也就是一种自定义类型
    def __init__(self, name, age):  # 对新实例进行初始化
        self.name = name           # 在这个实例上保存 name 属性
        self.age = age             # 在这个实例上保存 age 属性

    def introduce(self):     # 定义实例提供的方法
        return f"I am {self.name}"  # 读取当前实例的名字

p = Person("Tom", 22)        # 创建并初始化一个实例，p 引用它
q = Person("Amy", 20)        # 再创建另一个实例，两者有独立状态
print(p.name)                # Tom：通过点号读取属性
print(q.introduce())         # I am Amy：通过点号调用方法
```

**Attribute（属性）** 是通过 `obj.name` 等形式访问的对象相关信息；**Method（方法）** 是对象提供的可调用行为。先把它们理解为“这个对象有什么”和“这个对象能做什么”。

### 1.2 self 不是隐藏的特殊关键字

`self` 是实例方法的第一个形参，社区习惯这样命名。调用 `p.introduce()` 时，Python 会把 `p` 作为这个参数传入；对本例可以近似理解为 `Person.introduce(p)`。

```python
print(p.introduce())         # I am Tom：通过实例访问得到绑定方法
print(Person.introduce(p))   # I am Tom：显式传入实例，帮助看清 self 的来源
```

所以 `self.name` 不是类统一的一份变量，而是在访问当前这个实例的属性。**Bound Method（绑定方法）** 可以理解为已经关联了具体实例的方法。

### 1.3 __new__ 与 __init__：创建和初始化分两步

```text
调用 Person(...)
→ __new__ 创建并返回实例
→ 在适用情况下，__init__ 初始化这个实例
→ 调用结果交给 p
```

`__init__` 收到的是已经创建好的 `self`，它不负责“返回新实例”，正常应返回 `None`。`__new__` 才负责创建并返回对象；普通业务类大多只需实现 `__init__`，不必一开始就覆盖创建过程。

## 2. 属性：谁拥有状态，谁就承担生命周期

### 2.1 实例属性与类属性

```python
class Person:                # 这一段重新定义 Person，用于观察属性归属
    species = "human"        # 类属性：由类提供的共同信息
    def __init__(self, name): # 每创建一个实例都会执行
        self.name = name     # 实例属性：各实例分别保存

p = Person("Tom")            # 第一个实例
q = Person("Amy")            # 第二个实例
print(p.name, q.name)        # Tom Amy：名字独立
print(p.species, q.species)  # human human：都能找到类上的共同信息
```

对于这种普通属性，实例没有自己的同名属性时，会沿类等路径查找。`p.species = "changed"` 通常会在 p 上建立同名实例属性，而不自动改变 `Person.species`；数据描述符等更细的查找规则不宜用这句话一概覆盖。

### 2.2 可变类属性为什么导致多个实例共享

```python
class BadTeam:               # 错误设计：希望每个团队独立，却把列表放在类上
    members = []             # 只创建一份类级列表

left = BadTeam()             # 第一个实例
right = BadTeam()            # 第二个实例
left.members.append("Tom")  # 找到共同的类级列表，并原地修改它
print(right.members)        # ['Tom']：right 也看到这份共享对象
```

正确的独立实例状态：

```python
class Team:                  # 每个实例拥有自己的成员列表
    def __init__(self):      # 每次创建实例都会执行
        self.members = []    # 本次创建新的列表，并保存到当前实例

left = Team()                # 独立列表 A
right = Team()               # 独立列表 B
left.members.append("Tom")  # 只修改 A
print(right.members)        # []
```

这不是另一种新陷阱，而是第 03 章的共享引用模型再出现：列表创建在哪个时间点，被哪些对象共同引用，决定修改传播到哪里。

### 2.3 _name、__name 与 property：表达边界，而不是绝对私有

`_name` 约定“内部使用”；`__name` 在类定义内触发 **Name Mangling（名称改写）**，主要减少子类意外命名冲突。例如 `__token` 会被改写成带类名的形式，并非真正安全的访问控制。`__name__` 这种前后都有双下划线的特殊名字，与仅前缀双下划线不是同一规则。

**property（属性描述接口）** 允许使用属性式访问，同时在读写时加入逻辑：

```python
class Person:                # 以年龄校验为例
    def __init__(self, age):  # 初始化也走同一条校验路径
        self.age = age       # 触发下方 setter，而不是绕过校验直接写 _age

    @property                # 把 age 方法定义为读取属性的逻辑
    def age(self):           # 读取 p.age 时运行
        return self._age     # 从内部存储返回值

    @age.setter              # 定义向 p.age 赋值时运行的逻辑
    def age(self, value):     # value 是要写入的新值
        if value < 0:        # 本例只演示非负约束，不是完整类型验证器
            raise ValueError("age 不能为负数")  # 拒绝无效值
        self._age = value    # 校验通过后写入内部属性

p = Person(20)               # 初始化通过 setter 校验
p.age = 21                   # 保留自然的属性赋值语法
print(p.age)                 # 21
# p.age = -1                 # 错误示例：会抛 ValueError；正确做法是提供满足约束的年龄
```

### 2.4 __slots__：限制常规属性并控制存储开销

```python
class Point:                 # 用来保存大量二维坐标的简单对象
    __slots__ = ("x", "y")   # 为这两个实例属性预留存储位置
    def __init__(self, x, y): # 初始化
        self.x = x           # 保存横坐标
        self.y = y           # 保存纵坐标

point = Point(1, 2)           # 创建实例
# point.z = 3                # 本例不允许随意增加 z，会抛 AttributeError
print(point.x, point.y)      # 1 2
```

**`__dict__`** 通常用于存放普通实例的动态属性；`__slots__` 在合适的类布局下避免每个实例都需要一份这样的属性字典，可能降低大量实例的内存开销。但继承关系、是否显式保留 `__dict__` 等会改变结果，不能说“只要写了 slots，所有子类就绝对没有 dict”。

## 3. 三类方法：根据操作对象决定参数

```python
class NumberBox:             # 保存一个整数的示例类
    def __init__(self, value):  # 初始化实例
        self.value = value     # 保存实例状态

    def doubled(self):       # 实例方法，隐式接收当前实例 self
        return self.value * 2  # 依赖这个实例保存的值

    @classmethod             # 类方法，隐式接收调用所关联的类 cls
    def from_text(cls, text): # 一个替代构造入口
        return cls(int(text)) # 转为整数，再调用当前类创建实例

    @staticmethod            # 静态方法，不隐式接收 self 或 cls
    def is_even(value):      # 只是与类主题相关的普通计算
        return value % 2 == 0  # 返回是否为偶数

box = NumberBox.from_text("3")  # 用类方法创建实例
print(box.doubled())             # 6：使用实例状态
print(NumberBox.is_even(4))      # True：不需要先创建实例
```

| 类型 | 隐式输入 | 典型职责 |
|---|---|---|
| Instance Method（实例方法） | self | 读取／修改某个实例的状态 |
| Class Method（类方法） | cls | 类级行为、Alternative Constructor（替代构造入口） |
| Static Method（静态方法） | 无 | 与类语义相关，但不需要实例／类状态的函数 |

`cls` 和 `self` 都是命名约定；选择方法类型看真正依赖什么状态，而不是看哪个写法更复杂。

## 4. 复用与替换：从继承走到多态

### 4.1 封装、继承、多态、抽象分别解决什么

**Encapsulation（封装）** 把状态和相关操作组织在一起，通过明确接口使用它们；不是说所有属性都必须隐藏。

**Inheritance（继承）** 让子类复用并扩展父类行为；**Override（覆盖）** 是子类提供自己的同名实现。

```python
class Animal:                # 定义共同的行为入口
    def speak(self):         # 父类实现
        return "..."         # 默认表达

class Dog(Animal):           # Dog 继承 Animal
    def speak(self):         # 覆盖父类实现
        return "wang"        # 子类行为

class Cat(Animal):           # 另一个子类
    def speak(self):         # 同一个方法名，不同实现
        return "miao"        # 子类行为


def make_sound(animal):      # 调用方依赖 speak 行为
    return animal.speak()    # 不需要每种类型写一条 if 分支

print(make_sound(Dog()))     # wang
print(make_sound(Cat()))     # miao
```

**Polymorphism（多态）** 表示同一调用接口可以对应不同对象的具体行为。**Abstraction（抽象）** 则让调用者依赖必要的能力与约束，而不必知道实现细节。四者可以共同出现，但不是四个等价术语。

### 4.2 super 按 MRO 继续查找，不是固定找“直接父类”

**MRO（Method Resolution Order，方法解析顺序）** 决定多继承时到哪里找方法。

```python
class A:                     # 共同祖先
    def chain(self):         # 最后提供基础结果
        return ["A"]         # 链条的终点

class B(A):                  # 第一条继承路径
    def chain(self):         # 先记录 B，再让 MRO 后续实现继续
        return ["B"] + super().chain()  # 不硬编码调用 A

class C(A):                  # 第二条继承路径
    def chain(self):         # 同样协作式调用下一层
        return ["C"] + super().chain()  # 不硬编码调用 A

class D(B, C):               # 同时继承 B、C
    pass                     # pass 是空语句，不增加新的实现

print([cls.__name__ for cls in D.mro()])  # ['D', 'B', 'C', 'A', 'object']
print(D().chain())                       # ['B', 'C', 'A']
```

在这个 D 实例上，B 里的 `super()` 下一站是 C，不是 B 代码表面上写的父类 A。协作式多继承还要求各层签名与调用习惯兼容，不能只背一个 MRO 名字。

## 5. Duck Typing：不继承同一父类，也可以协作

### 5.1 调用者需要的是行为，不一定是血缘关系

**Duck Typing（鸭子类型）** 的直觉是“能够像鸭子那样行动，就按这种能力使用它”。在 Python 里，调用方常关注对象有没有合适的行为，而不是先要求它属于指定继承树。

```python
class FileWriter:            # 为集中讲接口，本例只打印模拟的文件输出，不实际写磁盘
    def write(self, data):   # 提供 write 这个行为
        print("file", data)  # 模拟文件写入

class MemoryWriter:          # 与 FileWriter 没有共同的自定义父类
    def __init__(self):      # 初始化内存存储
        self.items = []      # 为本实例创建独立列表
    def write(self, data):   # 同样提供 write 行为
        self.items.append(data)  # 保存到内存


def save(writer, data):      # 不检查具体类，依赖 write 契约
    writer.write(data)       # 让传入对象完成写入

memory = MemoryWriter()      # 创建一种具体实现
save(memory, "hello")       # 用同一个上层函数调用它
print(memory.items)          # ['hello']
save(FileWriter(), "hello") # file hello：替换实现而不修改 save
```

收益是 **Low Coupling（低耦合）**：调用方依赖能力而非某个实现；测试时可换成 **Fake / Mock（测试替身／模拟对象）**；外部服务可通过 **Adapter（适配器）** 接入同一接口。

### 5.2 灵活也会把错误延迟到真正调用时

```python
# save(object(), "hello")   # 错误示例：普通 object 没有 write，执行到该路径才会抛 AttributeError
save(MemoryWriter(), "hello")  # 正确：传入提供所需行为的对象
```

**AttributeError（属性错误）** 只是其中一种失败。方法拼错、参数签名不兼容、返回值含义不同，也都会让“看起来一样”的接口无法协作。因此大型工程通常结合类型提示、Protocol／ABC 和测试，而不是只在运行时碰运气。

## 6. 把隐式约定写明确：类型提示、Protocol 与 ABC

### 6.1 先读懂注解，不把它当自动校验

```python
def greet(name: str) -> str:  # name: str 描述期望输入；-> str 描述期望返回类型
    return f"Hello, {name}"  # 函数体仍决定真正运行行为
```

**Type Hint（类型提示）** 供编辑器、静态检查器和读者理解契约。Python 不会仅因为注解写了 `str` 就自动拒绝所有其他输入；运行时校验是第 10 章的另一层职责。

### 6.2 typing.Protocol：结构满足即可兼容

```python
from typing import Protocol  # 导入用于描述结构化类型契约的基类

class Writer(Protocol):      # 声明：符合 Writer 的对象需要这种 write 行为
    def write(self, data: str) -> None:  # 接受文本，不返回业务结果
        ...                 # 这里只声明接口；三个点不是可执行写入实现


def save(writer: Writer, data: str) -> None:  # 用类型提示声明依赖的能力
    writer.write(data)                       # 运行时仍进行普通方法调用
```

**Structural Typing（结构化类型）** 关注成员与签名是否满足契约。一个实现无需显式继承 `Writer`，只要类型结构兼容，静态工具就可以接受它。为了让检查更有效，具体实现也应给出清晰注解。

Protocol 不是外部数据的 Schema 校验器。即使使用 `@runtime_checkable` 允许特定的运行时检查，也主要检查成员存在等有限结构，不会完整证明参数类型、返回值和业务语义都正确。

### 6.3 ABC：显式继承与抽象方法约束

```python
from abc import ABC, abstractmethod  # 导入抽象基类工具

class WriterBase(ABC):        # 声明一个抽象基类
    @abstractmethod          # 子类需要实现这个抽象方法，才能正常实例化
    def write(self, data: str) -> None:  # 规定方法入口
        ...                 # 本例不提供实际写入实现

class ConsoleWriter(WriterBase):     # 明确声明继承关系
    def write(self, data: str) -> None:  # 实现抽象方法
        print(data)                     # 输出文本

ConsoleWriter().write("hello")  # hello
# WriterBase()                  # 错误示例：抽象方法未具体实现，不能直接实例化
```

**ABC（Abstract Base Class，抽象基类）** 常用于明确的继承体系和共享实现。Protocol 更自然地表达“不要求共同父类的可替换接口”；ABC 更适合还需要共同实现或运行时抽象类约束的情况。ABC 也有虚拟子类等机制，不应把它绝对简化成“只允许真实继承一种方式”。

### 6.4 Liskov：同名方法还远远不够

**Liskov Substitution（里氏替换原则）** 在应用里的直觉是：换一个实现，不应让依赖原契约的调用者失效。

```text
实现 A.generate → 返回 str
实现 B.generate → 返回 None
```

这两者即使都有 `generate`，上层也未必能互换。完整行为契约还包括**参数含义、返回值含义、异常、副作用、生命周期**。类型检查可以发现一部分问题，测试与设计仍然需要负责剩余语义。

## 7. 魔术方法：把自己定义的类接入 Python 语法

### 7.1 这些方法不是魔法，而是固定协议入口

**Magic / Special Method（魔术／特殊方法）** 是 Python 在某些操作中使用的约定入口。它们通常前后都有双下划线。

| 方法 | 接入什么行为 |
|---|---|
| `__len__` | `len(obj)` 获取长度 |
| `__iter__` | `iter(obj)` 获取迭代器 |
| `__next__` | `next(obj)` 取得下一项 |
| `__getitem__` | `obj[key]` 索引或键访问 |
| `__call__` | `obj(...)` 让实例可调用 |
| `__enter__`、`__exit__` | `with` 进入与退出 |
| `__eq__` | `==` 相等比较 |
| `__hash__` | `hash(obj)` 哈希行为 |
| `__repr__` | 面向开发者的对象表示 |

例如 `len(obj)` 不是要求所有对象都长得像列表，而是对象类型提供了相应长度协议。定义 `__eq__` 后也要重新审视哈希契约；Python 不会保证一个重写了值相等规则的类还能直接沿用身份哈希。

### 7.2 把协议实现出来：手写 Counter 迭代器

这是第 06 章介绍过的迭代器状态，现在可以读懂类实现了：

```python
class Counter:               # 一个自身保存遍历进度的迭代器
    def __init__(self, limit):  # 创建实例时保存状态
        self.current = 0       # 尚未产出任何数字
        self.limit = limit     # 保存最大产出值

    def __iter__(self):      # iter(counter) 调用的入口
        return self          # 迭代器返回自身，不自动重置 current

    def __next__(self):      # next(counter) 调用的入口
        if self.current >= self.limit:  # 已经没有下一项
            raise StopIteration         # 使用协议约定的结束信号
        self.current += 1    # 推进状态
        return self.current  # 产出本次数字

for value in Counter(3):     # for 自动调用 iter 与 next
    print(value)             # 依次输出 1、2、3
```

这里类负责显式保存 `current`；第 06 章的生成器由解释器保存局部变量和暂停位置。它们参与同一个迭代协议，只是管理状态的实现不同。

### 7.3 把协议实现出来：MyContext 上下文管理器

```python
class MyContext:             # 为了观察顺序，使用打印模拟资源操作
    def __enter__(self):     # 进入 with 时调用
        print("enter")       # 模拟获取资源
        return self          # with ... as ctx 中 ctx 将接收这个实例

    def __exit__(self, exc_type, exc_value, traceback):  # 离开代码块时调用
        print("exit")       # 模拟释放资源
        return False         # 不抑制代码块中的异常，存在异常时继续传播

with MyContext() as ctx:     # 创建管理器并进入
    print("working")        # enter → working → exit
```

`exc_type` 是异常类型，`exc_value` 是异常对象，`traceback` 是回溯信息；正常退出时它们为 None。把这段与第 07 章的 `@contextmanager` 对照，可以看出同一个生命周期契约的两种写法。

## 8. AI 应用中的行为契约，不只有方法名字

| 角色 | 常见行为 | 还要约定什么 |
|---|---|---|
| Provider Adapter（模型服务适配器） | `generate` 生成、`stream` 流式输出、`count_tokens` 计数 | 返回文本或流、错误语义、超时、连接生命周期 |
| Retriever（检索器） | `search(query, top_k)` 搜索 | 查询含义、结果结构、排序与数量边界 |
| Tool（工具） | `validate(args)` 校验、`execute(args)` 执行 | 权限、副作用、参数与返回结构 |

不同服务方或本地实现可以提供相同接口，上层依赖行为契约而不是具体类。涉及异步接口时，契约还需要明确“返回的是可等待的调用”还是普通结果；第 12 章再读 `async def generate(...)` 的具体执行语义。

生产代码的 Error Contract（错误契约）、Timeout（超时）、Return Type（返回类型）、Lifecycle（生命周期）与 Permission（权限）都不能靠同名方法自动补齐。

本章依据：[类与继承教程](https://docs.python.org/3.14/tutorial/classes.html)、[Python 数据模型](https://docs.python.org/3.14/reference/datamodel.html)、[typing.Protocol](https://docs.python.org/3.14/library/typing.html#typing.Protocol)、[abc](https://docs.python.org/3.14/library/abc.html)。

## 9. 🎯 面试怎么回答：Duck Typing

> Duck Typing 表示调用方更依赖对象是否提供需要的行为，而不是强制它继承某个具体类。它提高可替换性和低耦合，但纯动态方式会把很多接口错误推迟到运行时。大型 Python 工程通常会结合 Type Hint、`typing.Protocol`、ABC 和测试，把隐式行为契约变得更明确。Protocol 偏结构化兼容，ABC 更偏显式继承和共用抽象实现。

---

## 10. ⚠️ 易错点

- Duck Typing ≠ 不需要接口设计；
  正确理解：可以不共享父类，但调用双方仍需遵守明确行为契约。
- 方法名一样 ≠ 完全可替换，还要看参数、返回值和错误语义；
  正确做法：把类型、异常、副作用和生命周期一起写进接口约定。
- Protocol 主要帮助表达/检查结构契约，不等于 Runtime Schema Validation；
  正确边界：运行时外部输入校验需要单独实现，第 10 章会说明。
- ABC 和 Protocol 不是谁“更高级”，而是抽象方式不同；
  正确选择：看是否需要结构化兼容、显式继承、共享实现与实例化约束。
- 双下划线不是安全访问控制；
  正确理解：前缀双下划线的名称改写主要减少意外命名冲突。
- `super()` 按 MRO 工作，不等于“直接父类”。
  正确验证：查看具体类的 `mro()`，在多继承中沿实际解析顺序推导。

## 11. 本章自测

<details>
<summary>1. Duck Typing 最大的收益和风险分别是什么？</summary>

收益是调用方依赖能力而不是具体类型，替换和扩展更容易；风险是接口不兼容可能推迟到运行时才暴露，因此大型工程常结合类型提示、Protocol/ABC 和测试。

</details>

<details>
<summary>2. `typing.Protocol` 与 ABC 的核心区别是什么？</summary>

Protocol 更偏结构化接口，只要对象具备所需属性/方法即可兼容；ABC 更强调显式继承和抽象基类体系，也更适合提供共享实现或名义层级。

</details>

<details>
<summary>3. 为什么 Provider A/B 都有 `generate()` 仍可能不能互换？</summary>

接口契约不仅包括方法名，还包括参数、返回值、异常、副作用和生命周期语义。如果这些不一致，上层仍可能失败。

</details>
