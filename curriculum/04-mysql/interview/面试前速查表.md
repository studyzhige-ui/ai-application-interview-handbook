## 基础操作先分清对象

| 要求 | 关键语义 |
|---|---|
| 取哪些列、哪些行 | SELECT 清单与 WHERE 各负其责 |
| 取前几条 | 先 ORDER BY，再明确 LIMIT；并列用稳定键 |
| 缺值 | IS NULL，不用 = NULL |
| 表之间组合 | ON 决定匹配；LEFT JOIN 保留左侧未匹配行 |
| 汇总 | GROUP BY 分组；HAVING 筛组；COUNT(*) 数行 |
| 修改 | UPDATE 的 SET 指定新值，WHERE 指定对象 |
| 应用参数 | 值绑定；动态结构用允许列表 |

## 🔍 查询与索引

```text
结果语义 → 候选访问路径 → 统计/成本 → 实际执行与测量
```

| 概念 | 核心判断 |
|---|---|
| B+Tree | 页内多路导航降低树高；叶子有序支持范围读取，缓存影响实际I/O。 |
| 聚簇索引 | 叶子保存行记录，主键影响数据组织与其他索引。 |
| 二级索引 | 叶子包含索引键和定位行所需的主键信息。 |
| 覆盖 | 当前查询所需列能从所选索引获得，不是独立索引类型。 |
| ICP | 取完整行前先用索引内能判断的条件过滤。 |
| 联合索引 | 字典序；分开分析定位、过滤、覆盖和排序。 |
| EXPLAIN | 同时看访问、行数、排序、连接与估算；ANALYZE会执行，不在生产随意试。 |
| 深分页 | 跳过前面结果仍有成本；稳定游标以最后一个排序键继续。 |

## 🔒 事务与并发

| 概念 | 核心判断 |
|---|---|
| 原子业务单元 | 必须一起成功的修改放进同一事务，同时检查每一步业务条件。 |
| RC | 每次普通一致性读取得相应的新读视图。 |
| RR | 同一事务普通一致性读通常复用第一次建立的读视图；自身写入和锁定读另看。 |
| MVCC | 当前版本不可见时，利用Undo寻找可见历史；不自动解决覆盖写。 |
| 记录锁/间隙锁 | 锁对象由索引和访问路径决定；是否限制范围插入要补隔离与语句条件。 |
| 死锁/超时 | 死锁通常回滚整个受害事务；默认锁等待超时通常只回滚语句。 |
| 条件更新 | affected rows必须结合谓词和驱动语义解释，0行不能冒充业务成功。 |

## 💾 日志、恢复与传播

```text
Undo：回滚与历史版本
Redo：重做与崩溃恢复，可能包含未提交修改
Binlog：Server变化日志，支撑复制、PITR与CDC
```

内部2PC协调引擎与Binlog，不原子覆盖外部Redis或HTTP请求。提交成功不要求所有数据页已经落盘；提交确认丢失则要用业务键核对结果。

复制关注接收、持久化、应用三个时刻。半同步不等于副本已经可读，复制不等于备份。CDC关注一致快照与增量边界、重复、顺序、删除、位置与恢复。

## 🧩 设计与组合

先看读写关系，再定类型、主键、唯一约束、外键和索引。JSON不是省略业务建模的理由；参数化保护输入值，动态标识符另用白名单。

分片用容量换复杂度，不能只说取模；批量导入按批次决定事务和恢复边界，不能把job_id或检查点当成自动幂等。

## ⚠️ 跨系统边界

```text
InnoDB事务提交
≠
Redis / MQ / Vector DB / 外部API同时成功
```

MySQL 阶段先明确权威事实和本地原子边界。缓存失效、跨系统双写和可靠事件传播要在学完 Redis 后结合 Backend 再系统回答。
