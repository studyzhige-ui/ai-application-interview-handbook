# 10｜并发读取：隔离级别与 MVCC

[← 事务：哪些修改必须一起成立](09-事务与ACID.md) · [MySQL 目录](../README.md) · [并发修改：条件更新、锁与死锁 →](11-并发修改锁与死锁.md)

你在事务里查到余额 100。同事随后把它改成 120 并提交，你再查一次，应该看到 100 还是 120？两种结果都可能有合理用途：报表希望前后采用同一份数据，另一类业务则希望每次都看到更新后的已提交值。

**隔离级别规定并发事务怎样观察和影响彼此；MVCC 解释 InnoDB 怎样提供其中的历史版本读取。** 先用同一条时间线理解差别，再看背后的机制。

## 1. 两次读取的差异，是规则不同而不是结果随机

下面固定条件：InnoDB 表，A 没有写入，读的是普通 SELECT；B 修改以后明确提交；A 的两次读取在同一个尚未结束的事务内。

| 顺序 | 事务 A | 事务 B |
|---|---|---|
| 1 | 开始事务，读取余额，得到 100 | |
| 2 | | 把余额改成 120 |
| 3 | | 提交 |
| 4 | 再次读取余额 | |

在 **READ COMMITTED（读已提交，RC）** 下，A 第二次读到 120：每次普通一致性读使用新的已提交视图。

在 **REPEATABLE READ（可重复读，RR）** 下，A 第二次仍读到 100：它复用该事务第一次一致性读建立的视图。B 确实提交了，A 只是继续按原来的可见范围读取，不是数据库遗失了新值。[一致性读规则](https://dev.mysql.com/doc/refman/9.7/en/innodb-consistent-read.html)。

**快照或读视图，可以先理解为“这次读取允许看见哪些已提交修改的规则”。** 它不意味着把整个数据库复制一份给 A。两会话实验的完整命令与切换步骤在[实验页](../examples/experiments.md#lab-10)，读主线时先按四行表推演即可。

## 2. MVCC 怎样让旧值还可读取

B 将 100 改成 120，不能立刻抹去所有历史信息，因为 A 可能仍按旧视图读取。InnoDB 借助 Undo（撤销日志）保留重建旧版本所需的信息；当前行也带有修改事务与回滚指针等线索。

```text
当前版本：120，由事务 B 修改
    ↓ 利用 Undo 还原
旧版本：100，来自更早的已提交修改
```

A 再读时，先判断当前版本是否对自己的 **Read View（读视图）** 可见。如果 B 的修改不属于 A 的旧视图，就继续寻找更早的可见版本，最后返回 100。这就是 **MVCC（多版本并发控制）** 在本例中的作用。

这套办法允许很多普通读不等待正在修改当前记录的写者。代价是需要保存必要的历史信息，而不是取消了所有锁。[InnoDB 多版本机制](https://dev.mysql.com/doc/refman/9.7/en/innodb-multi-versioning.html)。

视图判断也不只是比事务编号大小。建立视图时已经提交的修改可见，当时仍活跃的其他写事务不可见，即使它后来提交，原视图也不因此改变。视图建立后出现的新事务不在旧可见范围；自己的修改则可以由自己读到。

聚簇记录中的 DB_TRX_ID 记录修改事务，DB_ROLL_PTR 指向还原历史的线索。读视图结合当时活跃写事务集合、编号界限和自身身份作判断。比界限更早的已结束事务可快速判断，中间范围还要看是否仍活跃。Undo 不是每次都保存整行完整副本，不要把图中的箭头当成准确物理布局。

## 3. “可重复读”有明确的读取条件

**普通 RR 事务通常在第一次一致性读时建立视图，不是在 START TRANSACTION 的瞬间就固定全部结果。** 如果 A 只是开始了事务，还没读取，B 已把 120 提交，A 第一次读取就可以看到 120。需要显式在事务开始时建立一致快照时，有专门语法，但不是普通 BEGIN 的自动含义。

第二个边界是自己的修改。A 读到 100 后自己改成 105，再读能看到 105；不能用“永远只看第一次的值”解释 RR。自己的新值与其他行的旧可见版本组合时，也未必对应数据库历史上的一张物理照片。

第三个边界是**锁定读**。A 想读取接下来准备修改的记录，可以使用：

<a id="sql-isolation_locking_read"></a>

<!-- mysql-example: isolation_locking_read -->
```sql
SELECT credits FROM accounts WHERE id = 1 FOR UPDATE;
```

在前面的 B 已提交、没有其他冲突的条件下，这类 FOR UPDATE 读取当前记录 120，并获得相应锁，而不是返回旧视图里的 100。UPDATE、DELETE 也不能直接套用普通 SELECT 的快照模型。

> ⚠️ 锁定读要放在需要跨语句保护的显式事务内，事务结束会释放相应锁。实验结束必须 COMMIT 或 ROLLBACK，不能把遗留事务当成下次操作卡住的随机故障。

## 4. 四种隔离级别，要与具体异常对应

**脏读**是读到他人尚未提交的修改，之后对方可能回滚；**不可重复读**强调重复读取同一已有记录时内容改变；**幻读**强调相同条件下的记录集合因并发变化而改变，例如待办由两条变成三条。

| 级别 | 对普通读取的基本理解 |
|---|---|
| READ UNCOMMITTED | 可能读到他人未提交的修改，不能依赖它是最终成立的事实 |
| READ COMMITTED | 不读他人未提交值，但两次读取可看到不同的已提交状态 |
| REPEATABLE READ | 复用事务内一致性视图；需要区分普通读、自身修改和锁定读 |
| SERIALIZABLE | 施加更强的串行化约束，通常增加读写冲突、等待或重试 |

InnoDB 默认隔离级别是 RR，实际环境可以修改，因此诊断要检查会话值。SERIALIZABLE 约束的是并发执行效果，不是物理上只允许一个事务运行。[隔离级别](https://dev.mysql.com/doc/refman/9.7/en/innodb-transaction-isolation-levels.html)。

“RR 是否解决幻读”必须先说明目的。按同一快照查报表，后来插入的数据对旧视图不可见；若要阻止别人向一个范围插入，则需要相应锁定读或 UPDATE、DELETE 等数据操作的范围锁机制。**看不到新行与不允许别人插入新行不是同一件事。**

## 5. 读取的一致性有成本，也不代替写入控制

A 长期不结束旧视图，仍可能需要过去的版本。负责清理历史的 Purge 就不能提前删除这些仍有用途的信息；其他事务继续修改时，历史保留压力可能增长。因此长事务不只是多占一条连接。

选择 RC 或 RR，要看是否需要在一个事务里保持多次读取一致，以及能接受怎样的等待和重试。报表、任务领取、余额扣减不必采用同一种读取方式。

MVCC 回答“我能看到哪个版本”。两个请求都基于旧余额计算后写回，仍可能覆盖彼此的业务结果。这类问题要用条件更新、版本检查或锁来保护，不能从“支持 MVCC”直接推导所有并发修改都正确。

## 本章小结

RC 与 RR 的普通读差异来自视图生命周期。MVCC 用事务信息、Undo 和 Read View 找可见版本；自己的修改和锁定读另有规则，长视图也有历史保留成本。

## 🎯 面试怎么回答

### RC 与 RR 怎样用 MVCC 解释？

RC 每次普通一致性读建立新视图，RR 通常复用首次一致性读的视图。当前行不对视图可见时，沿 Undo 寻找旧版本。还要说明快照创建时机、自身写入和锁定读，不能只说 RR 永远读旧值。

### MVCC 能代替锁吗？

不能。它主要帮助普通一致性读选择版本，减少读写阻塞；写者之间的修改、锁定读和范围保护仍需要协调。

## ⚠️ 易错点

> ⚠️ 事务开始不等于普通 RR 视图已经建立；“开始”“第一次读”“提交”必须分开。

> ⚠️ RR 的普通快照读不主动禁止其他事务插入；范围保护属于锁的责任。

<summary>1. A 开始 RR 事务但没查询，B 提交 120，A 第一次普通 SELECT 读什么？</summary>

在给定无其他修改条件下读 120，因为第一次一致性读才建立视图。

</details>

<details>
<summary>2. A 已读到 100，B 提交 120，A 的普通读和 FOR UPDATE 为什么可以不同？</summary>

普通读仍用旧视图，FOR UPDATE 读取并保护当前记录。它们服务不同目的。

</details>

<details>
<summary>3. 为什么读者不加记录锁，长期不结束也会给系统带来压力？</summary>

旧视图仍可能需要历史版本，使相关 Undo 不能及时清理。

</details>
