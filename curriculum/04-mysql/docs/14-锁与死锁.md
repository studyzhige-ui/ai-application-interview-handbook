# 14. Record Lock、Gap Lock、Next-Key Lock 与 Deadlock

前两章解决了：

```text
隔离级别决定“并发读的规则”
MVCC 决定“普通一致性读看哪个版本”
```

这一章继续回答：

> **当事务要修改当前数据，或者要保证某个范围不能被别人插入时，InnoDB 怎么协调并发？**

这时主角从“版本”切换成“锁”。

---

## 1. 先讲人话：锁是在保护“当前世界”

假设两个 Worker 同时抢一条 `PENDING` 任务。

如果都只是：

```sql
SELECT id
FROM agent_runs
WHERE status='PENDING'
LIMIT 1;
```

它们可能同时读到同一条。

如果业务要求：

```text
我一旦决定处理这条任务
其他 Worker 就不能同时把它也当成自己的
```

就需要进入：

- Locking Read；
- Conditional Update；
- 或其它并发控制。

锁解决的是：

> **谁能在什么时候读 / 改“当前可操作的数据”。**

---

# 2. Shared Lock 与 Exclusive Lock

先建立最基础直觉。

## Shared Lock（S）

多个事务可以一起“共享读取”被保护的数据，但不能随便修改。

```sql
SELECT ... FOR SHARE;
```

## Exclusive Lock（X）

一个事务准备修改数据时，需要排他控制。

```sql
SELECT ... FOR UPDATE;
UPDATE ...;
DELETE ...;
```

直觉：

```text
S + S  通常可兼容
S + X  冲突
X + X  冲突
```

面试中不需要把完整锁兼容矩阵背成表格，先理解“共享读 vs 排他写”。

---

# 3. InnoDB 的“行锁”其实锁的是索引记录

常见说法：

> InnoDB 支持行锁。

更准确地说：

> **InnoDB 的行级锁建立在索引记录之上。**

所以查询是否能走合适索引，会直接影响：

```text
扫描多少 index record
→ 可能锁多少 record / range
→ 并发冲突多大
```

这就是为什么：

> 索引设计不仅影响查询性能，也可能影响锁范围。

---

# 4. Record Lock

Record Lock 可以理解为：

> **锁住一个已经存在的索引记录。**

例如：

```sql
SELECT *
FROM agent_runs
WHERE id = 100
FOR UPDATE;
```

如果 `id=100` 是唯一主键精确查找，在 RR 下通常重点锁住这条实际记录，而不是整个范围。

直觉：

```text
... 99 | [100 locked] | 101 ...
```

---

# 5. Gap Lock

Gap Lock 锁的不是某一条现有记录，而是：

> **索引记录之间的“间隙”。**

例如索引值：

```text
10   20   30
```

Gap 可以想成：

```text
(-∞,10)
(10,20)
(20,30)
(30,+∞)
```

锁住 `(10,20)` 的 Gap 后，其他事务可能不能在这个间隙插入新的索引值。

为什么需要它？

因为如果你只锁现有记录：

```text
当前范围里没有 15
```

另一个事务仍可能：

```sql
INSERT ... value=15;
```

于是范围结果就变化了。

---

# 6. Next-Key Lock

Next-Key Lock 可以先把它理解成：

```text
Record Lock + 前面的 Gap
```

它保护：

> 一个索引记录，以及这个记录之前的一段范围。

例如：

```text
10    20    30
      ↑
```

某个 Next-Key Range 可以理解成类似：

```text
(10, 20]
```

这种“范围 + 记录”保护是 InnoDB 在 RR 下处理很多范围型锁定读的重要机制。

---

# 7. 为什么唯一索引精确查找和范围查询锁得不一样

假设：

```sql
SELECT *
FROM agent_runs
WHERE id = 100
FOR UPDATE;
```

如果：

```text
id 是 unique index
条件是唯一等值查找
```

数据库已经能确定：

> 不可能再插入另一条 `id=100`。

因此没有必要像范围扫描一样保护大量 Gap。

但如果：

```sql
SELECT *
FROM agent_runs
WHERE created_at >= '2026-09-01'
FOR UPDATE;
```

这是范围型扫描。

为了防止其它事务往扫描区间插入满足条件的新记录，锁范围就会更复杂。

所以面试里“到底锁几行”不能只看 WHERE 写了什么，要看：

```text
Isolation Level
+ Index
+ Search Condition
+ Access Path
+ Statement Type
```

---

# 8. 没索引会发生什么

如果：

```sql
UPDATE agent_runs
SET status='FAILED'
WHERE some_unindexed_column = 'x';
```

没有合适索引时，InnoDB 可能需要扫描大量记录。

结果不只是：

```text
查询慢
```

还可能意味着：

```text
锁涉及更多扫描到的索引记录
→ 并发冲突扩大
```

所以：

> **索引是并发控制设计的一部分。**

---

# 9. Gap Lock 为什么在 RC 下更少

在 InnoDB `READ COMMITTED` 中，Gap Lock 的使用比 RR 更少，主要保留在一些例如：

- Foreign Key Constraint Checking；
- Duplicate Key Checking；

等必要场景。

这也是 RC 经常能降低某些范围锁冲突和 Deadlock 概率的原因之一。

但这不代表：

> “RC 没有锁。”

UPDATE / DELETE 等依旧需要 Record-level Locking。

---

# 10. Locking Read：FOR UPDATE / FOR SHARE

当你要：

```text
先读
→ 根据结果做决定
→ 再更新
```

普通 Snapshot Read 往往不够。

例如：

```sql
START TRANSACTION;

SELECT status
FROM agent_runs
WHERE id=100
FOR UPDATE;

-- 判断状态
UPDATE agent_runs
SET status='RUNNING'
WHERE id=100;

COMMIT;
```

`FOR UPDATE` 表达的是：

> 我不是只想看看历史快照，我准备操作这条当前记录。

---

# 11. NOWAIT 与 SKIP LOCKED

生产任务队列里经常遇到：

```text
Worker A 已锁住任务 1
Worker B 查任务时要不要一直等？
```

MySQL 支持锁定读并发控制选项，例如：

```sql
SELECT ... FOR UPDATE NOWAIT;
```

如果拿不到锁：

```text
立即失败
```

或者：

```sql
SELECT ... FOR UPDATE SKIP LOCKED;
```

可以跳过已经被其它事务锁住的记录。

这对多个 Worker 并发 Claim Task 很有用。

但要注意：

> `SKIP LOCKED` 返回的是一个“跳过被锁记录”的非完整视图，它适合队列式消费，不适合所有一致性查询。

---

# 12. Deadlock 是什么

Deadlock = 多个事务形成循环等待。

最经典例子：

```text
Transaction A
锁 row 1
等待 row 2

Transaction B
锁 row 2
等待 row 1
```

形成：

```text
A → 等 B
B → 等 A
```

永远无法自行继续。

---

# 13. 死锁为什么“有锁就可能有”

很多人把 Deadlock 当成程序 Bug：

> “出现死锁说明数据库设计错了。”

不完全对。

只要系统有：

```text
并发事务
+ 多资源加锁
+ 加锁顺序不完全一致
```

就天然可能 Deadlock。

正确工程态度不是追求“永远不发生”，而是：

```text
降低概率
+
快速检测
+
失败事务可 Retry
```

---

# 14. InnoDB 如何处理 Deadlock

InnoDB 可以检测事务之间的等待环。

发现 Deadlock 后，会选择一个事务作为 victim 回滚，从而打破循环。

应用层通常会收到 Deadlock Error。

因此生产代码应该认识：

> **Deadlock 是一种可恢复的并发失败类型。**

很多业务可以：

```text
Rollback
→ Random Backoff
→ Retry 整个 Transaction
```

而不是直接把服务打挂。

# 15. 怎么降低 Deadlock

## 15.1 固定访问顺序

错误：

```text
A: lock user → lock order
B: lock order → lock user
```

更好：

```text
所有业务统一：user → order
```

减少循环等待机会。

## 15.2 缩短 Transaction

不要：

```text
BEGIN
查 DB
调用 LLM 30 秒
调用 HTTP API
等人工确认
再 UPDATE
COMMIT
```

这会让 Lock 持有时间异常长。

应该尽量让 Transaction 只包住真正必须原子的 DB 操作。

## 15.3 建正确 Index

减少扫描行：

```text
扫描更少
→ 锁更少
→ 冲突更小
```

## 15.4 不需要锁时不要 FOR UPDATE

只需要旧 Snapshot 的读取，不要为了“安全”到处加锁。

## 15.5 Retry

即使设计很好，Deadlock 仍可能发生。

应用层应该有明确 Retry Policy。

# 16. 如何定位 Deadlock

面试回答不要只说：

> `SHOW PROCESSLIST`。

更完整的思路：

```text
应用 Error / Trace
→ 找发生 Deadlock 的事务
→ 查看 InnoDB Deadlock 信息
→ 分析 SQL / Index / Lock Order
→ 找出访问顺序和扫描范围
```

常见入口包括：

```sql
SHOW ENGINE INNODB STATUS;
```

以及 Performance Schema / Error Log 等更系统的观测手段。

真正要回答的是：

```text
谁持有什么 Lock？
谁在等什么？
为什么扫描 / 锁到了这里？
能否缩小范围或统一顺序？
```

# 17. AI Application 场景：多个 Worker Claim Agent Run

可以设计成：

```sql
START TRANSACTION;

SELECT id
FROM agent_runs
WHERE status='PENDING'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;

UPDATE agent_runs
SET status='RUNNING'
WHERE id=?;

COMMIT;
```

多个 Worker：

```text
Worker A 锁任务 1
Worker B 自动跳过任务 1 → 拿任务 2
Worker C → 拿任务 3
```

这种设计比：

```text
SELECT 出来后在 Python 内存里抢锁
```

更符合数据库并发边界。

但如果你要的是高吞吐分布式任务平台，还要继续考虑：

- Lease；
- Timeout；
- Retry；
- Heartbeat；
- MQ；
- Idempotency；

这些属于 AI Backend Engineering / System Design。

# 18. 面试怎么答

## Q：Record Lock、Gap Lock、Next-Key Lock 区别？

🎯 推荐回答：

> Record Lock 锁已有索引记录；Gap Lock 保护索引记录之间的间隙，主要用于限制向范围内插入；Next-Key Lock 可以理解为 Record Lock 加上相邻 Gap 的组合，常用于 RR 下范围型锁定读。具体锁范围要结合索引、查询条件、隔离级别和执行计划判断，不能只看 SQL 文字。

## Q：怎么减少 Deadlock？

> 统一多个资源的访问顺序、缩短事务、给查询建立合适索引减少扫描和加锁范围、不必要的读取不要使用锁定读，并让应用把 Deadlock 当作可 Retry 的事务失败处理。

---

# 19. 高频易错点

⚠️ **InnoDB 行锁直接锁“物理行”。**  
更准确是围绕索引记录建立行级锁语义。

⚠️ **Gap Lock 就是在锁一条不存在的行。**  
更准确是锁索引值之间的间隙，阻止特定范围插入。

⚠️ **RR 所有 SELECT 都加 Next-Key Lock。**  
普通一致性 SELECT 通常是 MVCC 非锁定读。

⚠️ **出现 Deadlock 就是 MySQL 出 Bug。**  
并发多资源加锁天然可能形成循环等待。

⚠️ **加 `FOR UPDATE` 更安全，所以越多越好。**  
错误，它会增加锁等待和并发成本。

# 20. 本章自测

<details>
<summary>1. 为什么没有合适索引可能扩大锁冲突？</summary>

因为 InnoDB 的行级锁围绕索引记录工作。没有合适索引时语句可能扫描更多记录，从而让更多记录或范围参与锁定，增加并发冲突。

</details>

<details>
<summary>2. Gap Lock 的核心价值是什么？</summary>

保护索引记录之间的间隙，限制其它事务向被保护范围插入新记录，从而支撑 RR 下某些范围型锁定读的并发一致性。

</details>

<details>
<summary>3. 为什么统一事务访问顺序能降低 Deadlock？</summary>

循环等待通常来自不同事务以相反顺序获取多个资源。统一访问顺序能让事务更容易排成单向等待队列，而不是形成环。

</details>

<details>
<summary>4. SKIP LOCKED 为什么适合任务队列，却不适合普通一致性查询？</summary>

因为它会主动跳过被其它事务锁住的记录，返回的不是“完整满足条件的数据集合”。这很适合多个 Worker 各取不同任务，但不适合需要完整业务视图的查询。

</details>
