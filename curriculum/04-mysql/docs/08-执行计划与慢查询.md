# 08｜读懂执行计划，找到查询真正慢在哪里

[← 联合索引怎样定位、排序和减少回表](07-联合索引覆盖与下推.md) · [MySQL 目录](../README.md) · [事务：哪些修改必须一起成立 →](09-事务与ACID.md)

索引已经建了，查询还是慢，接下来改哪里？先别继续加索引。需要分清：查询是否只能扫描很大范围，优化器是否选了另一条路，还是语句正在等待锁或连接。

这一章把“为什么这样选”和“怎样查看证据”放在同一条排查路径上。工具是用来回答问题的，不是一张要逐项背下来的字段表。

## 1. 先固定 SQL、参数和数据，再谈慢在哪里

同样是查某团队任务，只有十条记录的团队和有百万条记录的团队，并不是同一个负载。排查要拿到实际 SQL、参数特点、表结构、索引和返回规模，不能随手换一组参数就认定问题消失。

用下面的任务查询观察计划：

<a id="sql-plan_baseline"></a>

<!-- mysql-example: plan_baseline -->
```sql
SHOW CREATE TABLE tasks;
EXPLAIN FORMAT=TRADITIONAL
SELECT id, title
FROM tasks
WHERE tenant_id = 10 AND status = 'pending'
ORDER BY created_at DESC, id DESC
LIMIT 2;
```

SHOW CREATE TABLE 显示表结构，EXPLAIN 展示准备采用的执行计划。这里指定传统表格格式，便于对应字段。**普通 EXPLAIN 主要解释计划与估计，不通过完整执行这条 SELECT 测量真实耗时。**

先问四个问题就够了：从哪张表读，以什么方式读，预计处理多少，还需要做哪些额外工作。

| 问题 | 重点字段 | 一种可能的解释 |
|---|---|---|
| 访问什么 | table | 当前计划节点处理哪张表 |
| 如何定位 | type、key | 通过某索引等值、范围访问，或扫描表/索引 |
| 预计有多少工作 | rows、filtered | 候选规模和通过剩余过滤的比例估计 |
| 还要做什么 | Extra | 覆盖、ICP、额外排序、临时表等 |

`type=range` 表示范围访问，`index` 常是全索引扫描，`ALL` 是全表扫描。它们不是脱离规模的速度排名：扫描六行小表可能很合理，扫描百万条索引项也可能很慢。[EXPLAIN 输出](https://dev.mysql.com/doc/refman/9.7/en/explain-output.html)。

## 2. 没选索引，先区分能力和成本

有三种需要分别处理的情况。

**第一种：条件不能方便地利用原有顺序定位。** 普通索引按完整时间值排列，但查询写成 `DATE(created_at)='2026-09-01'`，先对列取日期后再比较。可以改成下面的条件片段，直接给出原始时间值的区间：

```sql
WHERE created_at >= '2026-09-01 00:00:00'
  AND created_at <  '2026-09-02 00:00:00'
```

它仍表示 9 月 1 日，在练习数据里匹配任务 1、2，也更容易利用普通时间索引。片段接在查询后使用，不是独立语句。

这不是“函数绝对不能索引”。表达式索引可以服务特定表达式；需要时设计，不必把所有变体变成入门要求。

**第二种：只用到部分排序前缀。** `(a,b,c)` 只给出 `a=1 AND c=3`，可以先定位 a，但 b 未固定使 c 分散。c 仍可能用于过滤，不能说整棵索引没用。

**第三种：路径可行，但估计不划算。** 返回大部分行且需要很多非索引列时，大量回表可能比扫描聚簇记录贵。优化器会结合统计信息选择；统计偏离真实分布时，选择也可能不理想。

常见语法都要放回这三个判断中：固定前缀 LIKE 比前导通配更容易定位；字符串列与数值比较可能发生影响语义和路径的隐式转换；OR、IS NULL、否定条件并不是自动关闭索引的开关。不要用一组禁用符号口诀代替范围分析。

## 3. 实际执行结果，怎样与估计比较

EXPLAIN 中 rows 主要是估计，不是精确运行计数。环境允许时，可以用 **EXPLAIN ANALYZE** 执行查询并观察实际过程：

<a id="sql-analyze_recent"></a>

<!-- mysql-example: analyze_recent -->
```sql
EXPLAIN ANALYZE FORMAT=TREE
SELECT id, title
FROM tasks
WHERE tenant_id = 10 AND status = 'pending'
ORDER BY created_at DESC, id DESC
LIMIT 2;
```

先看 TREE 怎样表示层次。下面是教学示意，不是本课程实测输出：

```text
Limit：最后取两条
  Sort：把筛出的记录排序
    Filter：保留团队 10 的待办
      Table scan：从任务表取得候选
```

从最内层向外看，可以知道候选经过筛选和排序后才被限量；有合适索引时，可能换成索引范围读取并省去额外排序。不要把这一张示意图当成所有查询的固定执行路径。

每个节点还可以展示估计与测量，例如：

```text
(cost=... rows=10)
(actual time=0.10..0.30 rows=2 loops=4)
```

前一行估计十条，后一行显示每次循环平均约两条、总共四次循环。时间单位是毫秒，两端分别对应首条输出与该算子完成的耗时；多循环时要结合平均值和 loops 理解，不能只看到 rows=2 就说整条 SQL 只访问两行。

TREE 格式用缩进表示操作之间的嵌套。较上层节点常包含下层工作，**不能把所有节点耗时相加当成总耗时**。传统 Extra 中，`Using index` 常表示列覆盖，`Using index condition` 是 ICP，`Using filesort` 表示额外排序，不必然真的落磁盘。[测量与格式规则](https://dev.mysql.com/doc/refman/9.7/en/explain.html)。

> ⚠️ ANALYZE 会真正运行查询。只在已评估成本的隔离环境执行；带锁或其他副作用的语句还需单独审查，不能当成“只看一下”。

<details>
<summary>读计划时再查：候选索引、键长和统计信息</summary>

possible_keys 是候选索引，key 是最终选择；候选有值、最终没选，并不意味着索引损坏。key_len 可辅助判断使用的键部分，但受类型、字符集和是否可空影响，不靠背固定字节数判断。

ANALYZE TABLE 更新相关统计，不会自动修好 SQL；直方图可以帮助描述部分不均匀分布。JSON 计划有版本差异，应核对对应格式，不要求首次学习时维护完整字段字典。

</details>

## 4. 优化后要验证同一件事，而不是只看“用了索引”

假设原路径先按负责人取很多任务，再过滤团队和状态，最后排序取两条。针对常用等值条件与时间顺序设计联合索引后，可能直接定位较小范围并提前取够。这才是优化理由：**具体哪一步少做了工作**，而不是索引数量增加了。

保留改动前后的结果、计划和数据条件，再比较实际耗时与扫描；还要检查写入是否变重、其他查询是否受影响。热缓存与冷缓存、单请求与并发不能混为同一组对照。FORCE INDEX 可用于有依据的诊断，但不应成为没理解计划时的第一反应。

如果 SQL 已从 800 毫秒降到 50 毫秒，而请求还要等连接 300 毫秒、外部服务 900 毫秒、返回处理 100 毫秒，那么在这些阶段串行的教学假设下，总耗时从 2100 变为 1350 毫秒，而不是 50 毫秒。真实链路若有并行，要分析决定总时长的关键路径。

锁等待、连接等待、资源饱和和返回规模同样值得查；索引只解决其中一部分问题。这里的目的不是把整套后端观测系统搬进 MySQL，而是建立一个边界：**查询变快，只能证明查询这一段少花了时间，不能自动证明整个请求的主要瓶颈已经消失。**

## 本章小结

排查从可重现的查询开始，区分访问能力、部分利用与成本选择。EXPLAIN 看估计计划，ANALYZE 看实际过程，最后以相同结果和可比较负载验证改动。

## 🎯 面试怎么回答

### 怎样定位慢 SQL？

先确认 SQL、参数、数据规模和表索引，再看计划中的访问范围、回表、排序与估计。允许实测时比较实际行数、循环和耗时，区分执行与等待。修改后保证结果相同，并回归读写代价。

## ⚠️ 易错点

> ⚠️ key 不为空不等于扫描少；rows 的估计也不能冒充本次实测值。

> ⚠️ 优化器不选索引可能合理，强制索引不能替代对数据分布的理解。

> ⚠️ SQL 只占请求的一部分，查询优化后的接口延迟仍要按阶段分析。

## 本章自测

<details>
<summary>1. 六行小表出现 ALL，是否必然需要改？</summary>

不必。全部扫描的成本可能很小，应看数据与目标，不为改变标签而增加维护成本。

</details>

<details>
<summary>2. 为什么 actual rows 要和 loops 一起看？</summary>

多次循环时行数通常按每次循环平均展示，只看单个数会忽略重复执行的工作量。

</details>

<details>
<summary>3. 串行请求其他阶段合计 1300 毫秒，SQL 降至 50 毫秒，总耗时是什么？</summary>

按给定假设是 1350 毫秒；改善 SQL 不会自动减少其他阶段。

</details>
