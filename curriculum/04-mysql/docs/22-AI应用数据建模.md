# 22. AI Application Data Modeling

这一章把前面 21 章真正收回来。

你已经知道：

```text
SQL 怎样执行
索引为什么快
事务怎样保证正确
MVCC / Lock 怎样处理并发
Redo / Binlog 怎样恢复和复制
数据量大了怎样 Replication / Sharding / CDC / Bulk Write
```

现在要回答：

> **一个真实 AI Application / Agent Backend，哪些数据应该放 MySQL，表应该怎样拆，哪些字段需要强约束，哪些内容不适合直接塞进关系库？**

这是从“会 MySQL”跨到“会设计 AI 后端数据层”的最后一步。

---

## 1. 先讲人话：不是所有 AI 数据都应该存 Vector DB

很多初学项目会变成：

```text
Vector DB = 万能数据库
```

实际上 AI Application 常见数据可以分成三类。

## 结构化业务事实

```text
User
Tenant
Permission
Subscription
Conversation
AgentRun
Billing
Task State
```

很适合 MySQL。

## 高频临时状态

```text
Session
Cache
Rate Limit
Short-lived Lock
Ephemeral Agent State
```

更适合 Redis 等系统。

## 语义检索数据

```text
Chunk Embedding
Semantic Index
Metadata Filter
```

更适合 Vector DB / Search System。

所以典型架构是：

```text
MySQL   = 业务事实 / 长期结构化状态
Redis   = 高频短期状态 / Cache
VectorDB = 语义检索索引
Object Storage = 大文件 / Artifact
```

---

# 2. MySQL 应该成为哪些数据的 Source of Truth

一个很实用的判断：

> **如果这个状态丢了以后，业务无法可靠恢复，或者它需要事务 / 唯一约束 / 权限 / 审计，那么它通常很适合由 MySQL 作为 Source of Truth。**

例如：

```text
Tenant 是否存在
User 属于哪个 Tenant
Knowledge Base 属于谁
Agent Run 当前状态
一次 Usage 是否已经计费
Document 是否删除
Tool Approval 是否通过
```

这些都不是简单 Cache。

# 3. 一个完整 AI Application 数据域

可以先拆成：

```text
Identity
├─ users
├─ tenants
└─ memberships

Conversation
├─ conversations
└─ messages

Agent Runtime History
├─ agent_runs
├─ agent_steps
└─ tool_executions

Knowledge Base
├─ knowledge_bases
├─ documents
└─ document_versions

Usage / Billing
├─ usage_records
└─ billing_events

Evaluation
├─ eval_datasets
├─ eval_cases
└─ eval_runs
```

注意：

> 这不是“标准答案 Schema”，而是帮助你从业务域拆实体。

# 4. Tenant / User / Membership

多租户系统不要只建：

```text
users
```

而忽略企业关系。

一个常见模型：

```text
tenants
users
memberships
```

`memberships` 可以表示：

```text
user_id
+
tenant_id
+
role
```

这样一个 User 可以属于多个 Tenant。

并且：

```text
Permission
Billing
Knowledge Base
Conversation
```

都可以围绕 Tenant Boundary 设计。

---

# 5. Conversation 与 Message 为什么应该分表

Conversation：

```text
一条会话的 Metadata
```

Message：

```text
持续追加的大量消息
```

查询模式不同：

```text
Conversation List
→ 最近 20 个会话

Message History
→ 某会话最近 100 条消息
```

所以：

```text
conversations
messages
```

分开是自然的。

Message 表常见索引：

```text
(conversation_id, created_at, id)
```

非常适合 Cursor Pagination。

---

# 6. Message Content 一定直接放 MySQL 吗？

不一定。

普通文本消息：

```text
几 KB
```

直接放 MySQL 很自然。

但如果：

```text
超长 Prompt
大型 Tool Result
PDF Extraction
几十 MB Trace
```

可以考虑：

```text
MySQL
→ metadata + object_uri + hash + size

Object Storage
→ large payload
```

这样核心查询不会被大字段拖重。

# 7. Agent Run 是“当前状态”还是“历史事件”？

两者通常都需要。

## 当前状态表

```text
agent_runs
```

包含：

```text
status
started_at
finished_at
model
cost
error_code
```

用于快速回答：

> 这个 Run 现在是什么状态？

## 事件 / Step 表

```text
agent_steps
```

包含：

```text
step_no
step_type
input_ref
output_ref
started_at
finished_at
```

用于：

```text
Trace
Debug
Audit
Replay
Evaluation
```

这体现了：

```text
Current State
vs
Historical Event
```

两种数据模型的区别。

# 8. Tool Execution 为什么值得单独建模

Tool Call 是 Agent 系统最危险的 Side Effect 边界之一。

可以有：

```text
tool_executions
- id
- run_id
- step_id
- tool_name
- request_hash
- status
- approval_state
- started_at
- finished_at
- error_code
```

它的价值是：

```text
是否真的调用过？
调用了几次？
是否重复？
是否已经产生外部副作用？
失败能否安全重试？
```

这会直接连接 Agent Harness 的：

```text
Idempotency
Checkpoint
Resume
Permission
Audit
```

# 9. Knowledge Base Metadata 与 Vector Data 分层

一个常见错误：

> Document 一上传，就只往 Vector DB 写 Chunk，MySQL 什么也不留。

更稳妥的模型：

```text
MySQL
knowledge_bases
  ↓
documents
  ↓
document_versions
  ↓
ingestion_jobs
```

记录：

```text
owner
permission
filename
version
checksum
status
created_at
```

Vector DB 存：

```text
chunk_id
embedding
search metadata
```

并通过：

```text
document_id / version_id
```

关联。

这样 MySQL 保持：

> **业务事实和生命周期。**

Vector DB 保持：

> **检索索引。**

---

# 10. 为什么 Document Version 很重要

假设：

```text
policy.pdf v1
```

更新成：

```text
policy.pdf v2
```

如果直接覆盖：

```text
document_id=123
```

很难回答：

```text
Vector DB 里哪些 Chunk 属于旧版？
用户答案引用的是哪个版本？
重建索引失败怎么回滚？
```

所以可以显式：

```text
document_id
version_id
```

让生命周期更清晰。

---

# 11. Ingestion Job 为什么要独立

Document 是业务对象。

Ingestion 是处理过程。

两个概念不要混在一行里。

```text
documents
→ 当前业务文档

ingestion_jobs
→ 某次 Parse / Chunk / Embedding / Index 任务
```

Job 可以记录：

```text
QUEUED
PROCESSING
SUCCEEDED
FAILED
retry_count
checkpoint
error_message
```

这让：

- Retry；
- Resume；
- Observability；
- 多版本重建；

更自然。

---

# 12. Usage / Billing 为什么要 Append-oriented

如果只在 users 表里维护：

```text
total_tokens = total_tokens + 1234
```

你最终很难回答：

```text
这 1234 Token 是哪次 Run 花的？
哪个 Provider？
哪个 Model？
是否重复计费？
```

更自然是先记录细粒度 Usage Event：

```text
usage_records
- tenant_id
- user_id
- run_id
- provider_request_id
- input_tokens
- output_tokens
- cost
```

然后再聚合：

```text
Daily Usage
Monthly Billing
```

原始事实和聚合结果分开。

---

# 13. Billing 为什么需要 Unique / Idempotency Key

Provider Request 发生网络 Timeout：

```text
模型其实成功了
客户端不知道
→ Retry
```

如果账单逻辑只靠：

```text
每次请求都 INSERT 一条
```

可能重复收费。

可以基于：

```text
provider_request_id
run_id + step_id
idempotency_key
```

建立业务唯一约束。

这就是 Schema Design 与 Backend Idempotency 的交叉点。

---

# 14. Agent Memory 应不应该全部放 MySQL

不能一刀切。

Memory 可能包括：

```text
短期 Working Memory
长期 User Preference
Semantic Memory
Fact Memory
Summary
```

可能分层：

```text
Redis
→ 当前 Session / Working Set

MySQL
→ Long-term Memory Metadata / Structured Fact / Audit

Vector DB
→ Semantic Retrieval Index
```

真正 Primary 属于 Agent Harness 的 Memory Architecture，本章只说明：

> **长期结构化事实可以由 MySQL 做 Source of Truth，向量库只是检索表示。**

---

# 15. Permission 为什么应该有关系数据基础

比如：

```text
Tenant A 的用户绝不能检索 Tenant B 的知识库
```

权限信息如果只靠 Prompt：

```text
“请不要访问其它租户数据”
```

完全不可靠。

MySQL 可以明确：

```text
user
membership
role
resource_owner
resource_permission
```

然后在 Retrieval 前做真正的授权过滤。

---

# 16. Soft Delete 与 Knowledge Lifecycle

文档删除后：

```text
MySQL document → DELETED
```

还需要：

```text
Vector Chunk Delete
Object Delete / Retention
Cache Invalidate
CDC Event
```

因此 MySQL 状态可以是生命周期起点，但不能假装一次 SQL DELETE 自动清理所有外部系统。

# 18. 一个最小 Schema 示例

```sql
CREATE TABLE conversations (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    title VARCHAR(255) NOT NULL,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    INDEX idx_tenant_user_updated (tenant_id, user_id, updated_at, id)
);

CREATE TABLE messages (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    conversation_id BIGINT NOT NULL,
    role VARCHAR(32) NOT NULL,
    content TEXT NOT NULL,
    token_count INT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL,
    INDEX idx_conversation_created (conversation_id, created_at, id)
);

CREATE TABLE agent_runs (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    conversation_id BIGINT,
    status VARCHAR(32) NOT NULL,
    idempotency_key VARCHAR(128),
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    UNIQUE KEY uk_tenant_idem (tenant_id, idempotency_key),
    INDEX idx_tenant_user_created (tenant_id, user_id, created_at, id)
);
```

这只是教学起点，不是让所有项目原样复制。

# 19. 面试怎么答

## Q：为什么 Agent 项目里同时需要 MySQL、Redis、Vector DB？

🎯 推荐回答：

> 三者解决不同数据问题。MySQL 负责需要事务、约束、长期持久化和审计的结构化业务事实，例如用户、Tenant、Conversation、Agent Run 和 Document Lifecycle；Redis 更适合 Cache、Session、限流和短期 Runtime State；Vector DB 保存 Embedding 和语义检索索引。通常 MySQL 是很多业务对象的 Source of Truth，Vector DB 是可重建的 Retrieval Index，而不是反过来。

## Q：RAG 文档为什么还要存 MySQL？

> Vector DB 只擅长检索 Chunk。文档的 Owner、Permission、Version、Checksum、Ingestion Status、删除状态等属于业务事实，更适合放 MySQL。这样可以明确控制版本和生命周期，并通过 document_id / version_id 关联向量索引。

---

# 20. 高频易错点

⚠️ **AI 数据全部放 Vector DB。**  
Vector DB 是检索索引，不是完整业务数据库。

⚠️ **Redis 可以替代 MySQL 保存 Agent 全部状态。**  
短期状态可以，长期业务事实和审计通常需要更可靠的数据模型。

⚠️ **Message、Run、Tool Event 都放一个 JSON。**  
会失去清晰实体边界、索引和生命周期控制。

⚠️ **Vector Index 是 Source of Truth。**  
多数 RAG 系统中它应该可由业务文档和版本重新构建。

# 21. 本章自测

<details>
<summary>1. 为什么 Vector DB 不适合成为用户、权限和 Billing 的唯一数据库？</summary>

这些数据需要明确的关系、事务、唯一约束、权限边界和审计；向量数据库的核心能力是高维向量检索，而不是完整关系业务建模。

</details>

<details>
<summary>2. 为什么 Knowledge Base 建议把 Document Version 显式建模？</summary>

这样可以明确旧版和新版 Chunk 的归属、支持索引重建和回滚，并保证回答引用、权限和删除操作都能追到具体版本。

</details>

<details>
<summary>3. 为什么 Agent Run 和 Agent Step 通常值得分开？</summary>

Run 表适合表示当前整体状态和高频查询，Step/Event 表适合记录不断增长的执行历史、Trace、Debug 和 Replay。两者的访问模式和生命周期不同。

</details>
