# 05. 聚簇索引与二级索引

这一章是后面“回表、覆盖索引、主键为什么要短”的共同基础。

真实面试对应 `MYSQL-005`，核心问题是：

> **InnoDB 的数据到底放在哪里？Primary Key Index 和 Secondary Index 的叶子节点分别保存什么？**

---

## 1. 先讲人话：InnoDB 的“表数据”和主键索引绑在一起

很多初学者脑中的数据库是：

```text
Table Data 文件
+
Primary Key Index 文件
+
Secondary Index 文件
```

然后 Index 只是一个“指针目录”。

对 InnoDB 来说，这个模型不够准确。

更好的理解是：

> **InnoDB 每张表都有一个 Clustered Index，行数据组织在这个 Clustered Index 的叶子记录中。**

通常：

```text
PRIMARY KEY
=
Clustered Index Key
```

所以用主键查整行：

```sql
SELECT *
FROM agent_runs
WHERE id = 123;
```

可以粗略理解为：

```text
Clustered B+Tree
  ↓
找到 id = 123 的 Leaf Record
  ↓
这里就有这行需要的数据
```

---

# 2. 什么是 Clustered Index

假设表：

```sql
CREATE TABLE agent_runs (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    status VARCHAR(32) NOT NULL,
    model_name VARCHAR(64) NOT NULL,
    created_at DATETIME NOT NULL
) ENGINE=InnoDB;
```

抽象结构：

```text
             Clustered Index
                   │
             [Internal Pages]
                   │
                   ▼
┌────────────────────────────────────┐
│ Leaf Record                        │
│ id=123                             │
│ user_id=10001                      │
│ status=RUNNING                     │
│ model_name=...                     │
│ created_at=...                     │
│ + InnoDB internal fields           │
└────────────────────────────────────┘
```

也就是说：

> Clustered Index 的 Leaf 不只是 `id → 地址`，而是承载行记录本身。

因此 InnoDB 表的数据组织天然围绕 Clustered Index。

---

# 3. 如果没有 Primary Key 呢

InnoDB 仍然需要 Clustered Index。

官方文档给出的选择顺序可以概括为：

```text
有 PRIMARY KEY
→ 用 PRIMARY KEY

没有 PRIMARY KEY
→ 选择第一个所有 Key Column 都 NOT NULL 的 UNIQUE Index

还没有
→ InnoDB 创建隐藏的 GEN_CLUST_INDEX / Row ID
```

🎯 **面试表达**：

> InnoDB 每张表都有 Clustered Index。显式 Primary Key 通常就是 Clustered Key；没有主键时会尝试使用合适的唯一非空索引，再没有则生成隐藏的聚簇索引。因此业务表通常应该主动定义清晰的 Primary Key，而不是把这个决定留给隐式行为。

---

# 4. 什么是 Secondary Index

除了 Clustered Index 之外的普通 InnoDB Index，可以理解为 Secondary Index。

例如：

```sql
CREATE INDEX idx_user_created
ON agent_runs(user_id, created_at);
```

它的 Leaf Record 不是整行。

简化表示：

```text
(user_id, created_at, primary_key)
```

例如：

```text
10001 | 2026-09-10 10:01 | id=123
10001 | 2026-09-10 10:05 | id=130
10001 | 2026-09-10 10:20 | id=188
```

关键点：

> **InnoDB Secondary Index Record 会携带对应 Row 的 Primary Key。**

这就是“回表”产生的根源。

---

# 5. 什么是回表

查询：

```sql
SELECT *
FROM agent_runs
WHERE user_id = 10001;
```

假设 Optimizer 使用：

```sql
idx_user_created(user_id, created_at)
```

执行可以粗略理解成两步：

```text
Step 1
Secondary Index
(user_id, created_at, id)
        ↓
找到 id=123, 130, 188 ...

Step 2
拿每个 Primary Key
        ↓
再次查 Clustered Index
        ↓
取 status / model_name / 其它列
```

第二步就是常说的：

> **Back-to-table / 回表。**

如果命中 10 行，回表不一定是问题。

如果命中 500 万行，就可能非常昂贵。

---

# 6. 为什么主键应该尽量短

现在终于能严谨解释这句话。

假设两个方案。

### 方案 A

```sql
id BIGINT PRIMARY KEY
```

8-byte 整数。

### 方案 B

```sql
id VARCHAR(128) PRIMARY KEY
```

很长的字符串。

如果有 8 个 Secondary Index：

```text
idx_a Leaf → 带 Primary Key
idx_b Leaf → 带 Primary Key
idx_c Leaf → 带 Primary Key
...
```

长 Primary Key 会被重复存进所有 Secondary Index Record。

于是：

```text
Primary Key 更宽
→ Secondary Index Record 更宽
→ Index 占用更多空间
→ 每个 Page 能放的 Record 更少
→ Buffer Pool 缓存效率下降
→ I/O / Fan-out 可能受影响
```

官方 Optimization 文档也明确指出，长 Primary Key 会增加所有 Secondary Index 的空间占用。

🎯 所以“主键短”不是审美偏好，而是整个索引体系的空间与访问成本问题。

---

# 7. 为什么主键常推荐单调递增

先看 Auto Increment：

```text
100
101
102
103
104
```

新记录通常倾向于向 B+Tree 右侧追加。

随机 Key：

```text
9812
17
5501
99
700002
```

可能不断落入树中不同 Leaf Page。

随机插入更容易：

- 打散写局部性；
- 修改更多不同 Page；
- 当目标 Page 空间不足时触发 Page Split；
- 增加 Fragmentation 和缓存压力。

但这不是说：

> “所有系统必须使用自增整数主键。”

真实系统还会考虑：

- 分布式 ID；
- ID 暴露问题；
- 多机生成；
- 时间有序 UUID；
- Snowflake；
- 数据迁移；
- Sharding Key。

因此第 10 章会把 Primary Key Design 单独展开。

---

# 8. Secondary Index 的排序到底是什么

假设：

```sql
INDEX idx_status_created (status, created_at)
```

可以把 Index Key 先理解成：

```text
(status, created_at, primary_key)
```

排序先按 `status`，相同再按 `created_at`，Primary Key 还用于唯一定位行。

于是：

```sql
WHERE status = 'RUNNING'
ORDER BY created_at
```

有机会利用 Index 的有序性。

但：

```sql
WHERE created_at > ...
```

没有约束最左 `status` 时，能否怎样使用这个 Index，就进入“联合索引 / Leftmost Prefix / Skip Scan / Cost Choice”等更复杂语义。

下一章专门讲。

---

# 9. 为什么 Secondary Index 查主键值可能不用回表

查询：

```sql
SELECT id, created_at
FROM agent_runs
WHERE user_id = 10001;
```

假设 Index：

```sql
INDEX idx_user_created(user_id, created_at)
```

Secondary Index Leaf 已经有：

```text
user_id
created_at
primary_key(id)
```

查询需要的列都在那里。

于是有机会：

```text
只扫描 Secondary Index
→ 直接返回
```

不需要再去 Clustered Index。

这就是 Covering Index 的基础。

⚠️ “Covering Index”不是一种单独的物理索引类型。

更准确地说：

> **对于某条 Query，所需列能全部从当前 Index 获得，因此这个 Index 对该 Query 形成覆盖。**

---

# 10. Secondary Index 更新时发生什么

如果修改普通非索引列：

```sql
UPDATE agent_runs
SET model_name = 'new-model'
WHERE id = 123;
```

不一定需要修改所有 Secondary Index Key。

但如果更新被索引列：

```sql
UPDATE agent_runs
SET status = 'SUCCEEDED'
WHERE id = 123;
```

那么：

```text
idx_status_created 中旧 Key
  ↓
需要被 delete-mark / 后续清理

新的 status Key
  ↓
插入新的 Secondary Index Record
```

所以：

> **“给频繁更新字段建很多索引”会增加写维护成本。**

这也是 Index Design 的 Trade-off。

---

# 11. MVCC 为什么会让 Secondary Index 更复杂

先看一个未来章节才完整解释的事实：

Clustered Index Record 内部带有事务相关隐藏信息，可以结合 Undo 构造历史版本。

Secondary Index Record 的 MVCC 处理方式不同。

官方文档说明，当 Secondary Index Record 处于某些更新 / delete-mark 状态时，InnoDB 可能需要回到 Clustered Index 检查事务信息并找到正确的历史版本。

这告诉我们：

> **“Covering Index 一定永远不访问 Clustered Index”也不是无条件绝对真理。**

在普通优化讨论中可以用 Covering 模型理解，但深入到 MVCC 可见性时，要知道 Storage Engine 还可能因为版本判断访问 Clustered Record。

---

# 12. 一张最终对比表

| 项目 | Clustered Index | Secondary Index |
|---|---|---|
| 每张 InnoDB 表数量 | 1 | 可以多个 |
| 通常 Key | Primary Key | 用户定义 Index Key |
| Leaf 主要保存 | Row Record | Index Key + Primary Key |
| 查整行 | 定位后直接拿 Row | 可能需要再查 Clustered Index |
| 是否产生“回表”概念 | 自身不叫回表 | 常见 |
| 主键长度影响 | 自己 | 所有 Secondary Index 都可能受影响 |

# 13. 面试怎么答

## Q：什么是聚簇索引？

> InnoDB 每张表都有一个 Clustered Index，通常以 Primary Key 作为 Key，行记录组织在它的叶子节点中，所以通过聚簇索引定位后就能获得该行数据。没有显式 Primary Key 时，InnoDB 会尝试使用合适的唯一非空索引，否则生成隐藏聚簇索引。

## Q：什么是二级索引？为什么会回表？

> Secondary Index 的叶子记录保存 Secondary Key 和对应 Primary Key，而不是完整业务行。当 Query 还需要索引中不存在的列时，先通过 Secondary Index 找到 Primary Key，再通过 Clustered Index 获取整行，这一步就是回表。

## Q：为什么 Primary Key 不建议太长？

> 因为 InnoDB Secondary Index Record 会保存 Primary Key。主键越长，不只 Primary Index 更大，所有 Secondary Index 都会重复承担更大的 Key 空间，影响 Index Size、Page Fan-out、Buffer Pool 和 I/O。

---

# 14. 高频易错点

⚠️ **“聚簇索引就是 Primary Key”**  
更准确：InnoDB 通常使用 Primary Key 作为 Clustered Index；如果没有 Primary Key，还有替代选择规则。

⚠️ **“Secondary Index Leaf 保存 Row 的磁盘地址”**  
InnoDB 的关键模型是保存 Primary Key，通过 Primary Key 再查 Clustered Index。

⚠️ **“覆盖索引是一种索引类型”**  
它是针对某条 Query 的覆盖关系。

⚠️ **“用 Secondary Index 查询一定回表”**  
如果查询所需列全部能从该 Index 得到，则可能不需要普通意义上的回表。

# 15. 本章自测

<details>
<summary>1. 为什么 InnoDB Secondary Index 要保存 Primary Key？</summary>

因为 InnoDB 的完整 Row Record 组织在 Clustered Index 中。Secondary Index 需要一个稳定方式定位对应行，因此 Leaf Record 保存 Primary Key，再用它进入 Clustered Index。

</details>

<details>
<summary>2. 为什么长 Primary Key 会放大空间成本？</summary>

因为 Primary Key 会复制到各个 Secondary Index Record。Secondary Index 越多，这个放大效应越明显。

</details>

<details>
<summary>3. `SELECT id, created_at WHERE user_id=?` 为什么可能不回表？</summary>

如果使用 `(user_id, created_at)` Secondary Index，Leaf 已包含 `user_id`、`created_at` 和 Primary Key `id`，查询需要的列全部可从 Index 获取。

</details>

<details>
<summary>4. 没有显式 Primary Key，InnoDB 就没有 Clustered Index 吗？</summary>

不是。它会尝试选第一个所有 Key Column 都 NOT NULL 的 UNIQUE Index；仍没有时生成隐藏的 `GEN_CLUST_INDEX`。

</details>
