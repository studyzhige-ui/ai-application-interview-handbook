# 15. redo、undo、binlog 与两阶段提交

前几章讲了事务怎么并发，这一章回答另一个核心问题：

> **事务提交时，数据页、事务回滚、崩溃恢复、复制和下游同步分别靠什么？**

MySQL 面试里最容易出现的一类错误，就是把所有“日志”都混成一句：

> “redo 保证原子性，undo 保证持久性，binlog 用来恢复。”

这种回答通常会越讲越乱。

这一章先建立最重要的职责边界。

---

## 1. 先看总图

```text
                  一次事务修改
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      Undo           Redo          Binlog
        │              │              │
   回滚 / MVCC      Crash Recovery   Replication / PITR
```

更准确地说：

```text
Undo
→ 记录“怎样回到之前版本”所需的信息
→ Transaction Rollback
→ MVCC Historical Version

Redo
→ 记录“已经对 InnoDB 页面做过哪些修改”所需的信息
→ WAL / Crash Recovery
→ Durability

Binlog
→ MySQL Server 层的逻辑变化事件
→ Replication
→ Point-in-time Recovery
→ CDC / 下游消费基础
```

它们有协作，但不是同一个东西。

---

# 2. 为什么不能每次 COMMIT 都先把所有 Data Page 随机写完

假设一次事务修改很多页面：

```text
Page A
Page B
Page C
Page D
```

如果提交必须等待：

```text
把每个 Dirty Page 都写回最终数据文件
```

随机 I/O 成本会很高。

InnoDB 使用 WAL 思想：

```text
先保证恢复所需 Redo 持久化
→ 事务可以达到 Durability Boundary
→ Dirty Page 之后再逐步 Flush
```

所以：

> **COMMIT 成功不等于所有修改过的数据页都已经立即写回最终位置。**

---

# 3. Redo Log：为了 Crash Recovery

官方定义非常直接：Redo Log 是磁盘上的数据结构，用于在 Crash Recovery 中修正尚未完整写入数据文件的修改。

可以把正常流程简化成：

```text
UPDATE
  ↓
修改 Buffer Pool 中 Page
  ↓
产生 Redo Record
  ↓
COMMIT 时按配置确保必要 Redo Flush
  ↓
未来某个时间 Dirty Page Flush
```

如果：

```text
Redo 已经持久化
但 Dirty Page 还没完全落盘
机器 Crash
```

重启后：

```text
读取 Redo
→ Replay 必要修改
→ 恢复到已提交状态
```

这就是 WAL 的价值。

---

# 4. Redo 为什么比直接刷所有数据页更适合提交路径

因为 Redo 写入更接近：

```text
顺序追加
```

而数据页可能散落在不同位置。

提交路径如果依赖大量随机 Page Flush，会非常昂贵。

所以 Redo 把：

```text
“提交时必须持久化什么”
```

和：

```text
“最终 Data Page 什么时候刷回”
```

解耦了。

---

# 5. Redo ≠ Binlog

这两个经常一起出现，所以特别容易混。

## Redo

主要属于：

```text
InnoDB Storage Engine
```

关注：

```text
页面修改
Crash Recovery
Durability
```

## Binlog

主要属于：

```text
MySQL Server 层
```

关注：

```text
数据库变化 Event
Replication
PITR
CDC
```

简单记忆：

```text
Redo：InnoDB 自己怎么把崩溃后的数据恢复回来？
Binlog：MySQL 怎样把已经发生的变化传播 / 重放出去？
```

---

# 6. Undo：回滚 + 历史版本

Undo 已经在前一章讲过。

它解决两件大事：

```text
1. Transaction Rollback
2. MVCC Consistent Read
```

例如：

```sql
UPDATE agent_runs
SET status='FAILED'
WHERE id=100;
```

如果事务后来 ROLLBACK，需要知道如何恢复之前状态。

同时旧 Snapshot 也可能需要看到修改前版本。

所以：

```text
Undo
≠
只是一份“错误恢复日志”
```

它也是 MVCC 的历史版本基础。

---

# 7. Binlog：Replication 与 PITR 的共同基础

Binary Log 记录会改变数据库内容的事件。

它的重要用途包括：

```text
Source → Replica Replication
```

以及：

```text
Backup
+
从 Backup 之后重放 Binlog
→ Point-in-time Recovery
```

所以你可以把它理解成：

> **MySQL 对外传播“数据库发生过哪些变化”的关键事件流。**

这也是 CDC 章节的基础。

---

# 8. Binlog Format 需要知道到什么程度

应用工程面试常见三类概念：

```text
STATEMENT
ROW
MIXED
```

### STATEMENT

记录 SQL Statement。

优点：

```text
日志可能更紧凑
```

但某些非确定性行为会让重放语义复杂。

### ROW

记录行变化 Event。

优点：

```text
更接近“哪一行变成什么”
适合稳定复制和 CDC
```

代价可能是：

```text
大量批量更新时日志体积更大
```

### MIXED

根据情况选择。

现代应用工程讨论 CDC 时，通常重点理解 Row-based Event。

---

# 9. 为什么 Redo + Binlog 会有一致性问题

关键在于：

```text
它们属于不同层
```

假设事务要提交。

如果：

```text
Redo 已确认提交
但 Binlog 还没写
→ Crash
```

数据库本地可能有这笔事务，但 Replica / CDC 看不到。

反过来：

```text
Binlog 已经有事务
但 InnoDB 最终回滚
```

Replica 可能重放一个 Source 本地没有真正提交的数据。

所以必须协调：

> **InnoDB Transaction State 与 Binlog Event State。**

这就是内部两阶段提交存在的重要原因。

---

# 10. 两阶段提交：Prepare → Commit

面试层面可以建立下面的简化模型：

```text
InnoDB Prepare
      ↓
Binlog Write / Flush
      ↓
InnoDB Commit
```

关键思想不是背三个单词，而是：

> **让 InnoDB 和 Binary Log 能在 Crash Recovery 时判断“这个事务到底应该提交还是回滚”。**

如果事务进入 Prepared 状态，并且可以确认对应 Binlog 已经成功写入，那么 Crash Recovery 可以完成提交；否则可以回滚 / 截断到有效位置。

---

# 11. 为什么不能简单说“两阶段提交保证 Redis 一致性”

这里的两阶段提交是：

```text
MySQL Server / Binlog
+
InnoDB
```

之间的内部一致性协调。

它不自动包含：

```text
Redis
Kafka
外部支付 API
Vector DB
Agent Tool Side Effect
```

所以：

```text
MySQL 内部 2PC
≠
跨服务 Distributed Transaction
```

这是 AI Backend 面试里非常容易混淆的边界。

---

# 12. `innodb_flush_log_at_trx_commit`

面试不一定要求背完整配置矩阵，但要知道：

> Redo 是否在每次 COMMIT 都真正同步到持久介质，是一个 Durability / Performance Trade-off。

最强持久性配置通常讨论：

```text
innodb_flush_log_at_trx_commit = 1
```

直觉：

```text
每次事务 COMMIT
→ Redo 做最严格的持久化路径
```

其它值可能减少同步 I/O，但扩大 Crash 时丢最近事务的风险窗口。

---

# 13. `sync_binlog`

Binlog 同样有 Flush Policy。

官方建议最高 Durability / Replication Consistency 场景常见：

```text
sync_binlog = 1
innodb_flush_log_at_trx_commit = 1
```

但它们增加同步磁盘 I/O 成本。

所以生产系统是在做：

```text
Durability
vs
Throughput / Latency
```

的工程权衡。

---

# 14. Group Commit 为什么重要

如果每个事务都单独：

```text
fsync
```

提交吞吐会被磁盘同步能力限制。

Group Commit 的思想是：

```text
多个 Transaction
      ↓
形成一组
      ↓
共享一次或更少的同步成本
```

这样可以显著提高并发提交吞吐。

所以不要把数据库性能只理解成：

```text
Query 是否走 Index
```

Write-heavy 系统还要看：

```text
Commit Rate
Redo / Binlog Flush
Group Commit
Transaction Size
```

---

# 15. Crash Recovery 到底大致做什么

可以建立简化模型：

```text
mysqld Crash
   ↓
Restart
   ↓
Redo Replay
   ↓
恢复尚未落到 Data Page 的已记录修改
   ↓
处理未提交 / prepared 事务
   ↓
结合 Binlog 判断应 Commit / Rollback 的事务
```

不是：

> “重启后直接把 Binlog 从头 replay 一遍恢复数据库。”

InnoDB 本地 Crash Recovery 的核心是 Redo；Binlog 在复制 / PITR 以及协调事务提交状态上发挥不同角色。

---

# 16. Point-in-time Recovery（PITR）

假设：

```text
02:00 做 Full Backup
10:37 误删数据
```

可以：

```text
恢复 02:00 Backup
+
重放之后的 Binlog 到 10:36:59
```

这就是 PITR 的基本思想。

所以：

```text
Backup ≠ Binlog
Binlog ≠ Backup
```

它们通常组合使用。

---

# 17. AI Application 场景：为什么 CDC 喜欢消费 Binlog

假设 Agent 平台里：

```text
MySQL 是 source of truth
```

下游要更新：

```text
Search Index
Analytics
Feature Store
Audit Stream
```

如果应用代码每次写 MySQL 后手工再调用 4 个系统：

```text
写 DB
→ 写 Search
→ 写 Analytics
→ 写 Cache
```

会产生大量 Dual-write Failure Window。

CDC 思路是：

```text
MySQL Commit
→ Binlog
→ CDC Consumer
→ 下游系统
```

这样能把“数据库变化事实”作为统一事件来源。

具体一致性和 Exactly-once 问题，会在第 20 章讲。

# 18. 面试怎么答

## Q：redo、undo、binlog 有什么区别？

🎯 推荐回答：

> Undo 主要记录回滚和 MVCC 历史版本所需的信息；Redo 是 InnoDB 的 WAL / Crash Recovery 基础，用来保证已提交修改即使数据页尚未刷盘也能在崩溃后恢复；Binlog 属于 MySQL Server 层，记录数据库变化事件，主要用于复制、PITR 和 CDC。它们职责不同，但事务提交时 Redo 和 Binlog 需要协调。

## Q：为什么需要两阶段提交？

> 因为 InnoDB Redo 和 Server 层 Binlog 属于两套状态。如果其中一边认为事务成功、另一边没有相应记录，Crash 后会导致本地数据与复制日志不一致。内部两阶段提交通过 Prepare、Binlog 持久化和最终 Commit 协调两者，使 Crash Recovery 能判断 Prepared Transaction 应提交还是回滚。

---

# 19. 高频易错点

⚠️ **Redo 用于 Rollback。**  
主要不是，Rollback 关键看 Undo。

⚠️ **Undo 只负责事务回滚。**  
还支持 MVCC 历史版本。

⚠️ **Binlog 是 InnoDB 专属日志。**  
它属于 MySQL Server 层。

⚠️ **COMMIT = 所有 Data Page 都写盘。**  
错误，WAL 允许先保证 Redo 持久化，再后台刷 Dirty Page。

⚠️ **MySQL 2PC 解决 MySQL + Redis 一致性。**  
不是，它协调的是 InnoDB 与 Binlog。

# 20. 本章自测

<details>
<summary>1. 为什么 Redo 可以提高写入效率？</summary>

因为提交不必等待所有随机 Dirty Page 都写回最终数据文件，而可以先顺序记录并持久化恢复所需的 Redo；数据页之后再后台 Flush，Crash 后通过 Redo 恢复。

</details>

<details>
<summary>2. Undo 为什么同时和 Atomicity、MVCC 有关？</summary>

事务失败时需要 Undo 信息恢复旧值；普通一致性读也可能需要沿历史版本看到旧数据，所以 Undo 同时服务 Rollback 和 MVCC。

</details>

<details>
<summary>3. 两阶段提交主要解决谁和谁的一致性？</summary>

主要协调 InnoDB Transaction / Redo 状态和 MySQL Server Binary Log 状态，避免本地已提交数据与 Binlog 记录不一致。

</details>

<details>
<summary>4. `sync_binlog=1` 和 `innodb_flush_log_at_trx_commit=1` 为什么可能影响性能？</summary>

因为更严格的 Durability 通常意味着更频繁的同步持久化操作，增加 fsync 等 I/O 成本；Group Commit 可以在一定程度上摊薄提交成本。

</details>
