# 06. 联合索引与最左前缀

`MYSQL-006` 有 **10 个独立 HUMAN-A**，而且它几乎从来不是一句“什么叫最左匹配”就结束。

面试官真正喜欢给的是：

```sql
INDEX idx_abcd (A, B, C, D)
```

然后问：

```sql
WHERE A = ? AND B = ?
WHERE B = ?
WHERE A > ? AND B = ?
WHERE A = ? AND C = ?
WHERE A = ? ORDER BY B, C
```

你不能只背一句：

> “范围查询以后索引就失效。”

这句话太粗糙，而且经常会把 **定位范围、继续参与过滤、覆盖、排序** 几种不同作用混在一起。

---

## 1. 先讲人话：联合索引是一套“按列顺序排序”的结构

假设：

```sql
INDEX idx_tenant_user_created (
    tenant_id,
    user_id,
    created_at
)
```

它不是：

```text
index(tenant_id)
+
index(user_id)
+
index(created_at)
```

而是一棵按照组合 Key 排序的 B+Tree。

你可以先把 Key 理解成：

```text
(tenant_id, user_id, created_at)
```

排序规则是：

```text
先比较 tenant_id
tenant_id 相同，再比较 user_id
user_id 相同，再比较 created_at
```

例如：

```text
(1, 10, 09:00)
(1, 10, 10:00)
(1, 20, 08:00)
(2, 10, 07:00)
(2, 10, 12:00)
```

这张有序关系就是理解 Leftmost Prefix 的核心。

---

# 2. 什么叫 Leftmost Prefix

对于：

```text
(A, B, C)
```

天然可以形成左侧连续前缀：

```text
(A)
(A, B)
(A, B, C)
```

官方文档也明确说明，多列索引可以用于完整列集合，或它的左侧连续前缀。

所以：

```sql
WHERE A = 1;
```

可以很好利用。

```sql
WHERE A = 1 AND B = 2;
```

可以。

```sql
WHERE A = 1 AND B = 2 AND C = 3;
```

可以。

但：

```sql
WHERE B = 2;
```

不能按传统 Leftmost Prefix Lookup 直接定位 `(A,B,C)` 中的连续范围，因为 A 未知。

💡 **新手理解**：

电话簿如果排序规则是：

```text
姓 → 名 → 出生日期
```

你知道“姓=张”，可以很快找到张姓范围；再知道“名=伟”，可以继续缩小。

但只知道“名=伟”，由于不同姓氏下面都可能有“伟”，无法直接把所有“伟”定位成一个连续区间。

---

# 3. SQL 条件书写顺序 ≠ Index 列顺序

这是非常高频的误区。

Index：

```sql
INDEX idx_ab (A, B)
```

以下两个 SQL：

```sql
WHERE A = 1 AND B = 2
```

```sql
WHERE B = 2 AND A = 1
```

逻辑条件相同，Optimizer 不会因为你把 `B` 写在前面就机械放弃 `idx_ab`。

所以：

> **Leftmost Prefix 说的是 Index Key 的排序顺序，不是 WHERE 文本从左到右的书写顺序。**

⚠️ 不要回答：

> “WHERE 必须按联合索引顺序写。”

---

# 4. 等值条件为什么最容易连续利用 Key Part

假设：

```sql
INDEX idx_abc (A, B, C)
```

查询：

```sql
WHERE A = 1
  AND B = 2
  AND C = 3;
```

可以理解：

```text
A=1
→ 在 A=1 的连续范围里
B=2
→ 继续缩小到 (A=1,B=2)
C=3
→ 再继续定位
```

每一步都能把 B+Tree 的连续范围继续缩小。

---

# 5. 范围条件以后到底发生什么

这是面试最容易说错的部分。

假设：

```sql
INDEX idx_abc (A, B, C)
```

查询：

```sql
WHERE A = 1
  AND B > 10
  AND C = 3;
```

常见八股：

> “B 是范围，所以 C 索引失效。”

更准确应该拆成两个问题。

## 5.1 B+Tree Lookup Range 能缩小到哪里？

前面可以根据：

```text
A = 1
B > 10
```

确定一个索引扫描范围。

但在：

```text
A=1, B>10
```

这个 Range 内，记录首先按 B 排序；每个不同 B 下 C 再排序。

因为 B 已经不是一个固定值，所以 `C=3` 通常不能像前面的 Equal Key Part 一样，把整个扫描范围继续压成一个单一连续区间。

这才是经典“范围以后不能继续用于同一种 Prefix 定位”的核心。

## 5.2 那 C 完全没用了吗？

不一定。

如果 C 也在 Index Record 中，MySQL 可能通过 **Index Condition Pushdown（ICP）** 等方式，在读取完整 Row 前先用 Index 中可用的字段继续过滤。

也就是说要区分：

```text
用于构造 Index Range / Lookup
≠
用于 Index-level Filter
≠
用于 Covering Query
≠
用于 ORDER BY
```

🎯 **更成熟的面试表达**：

> 联合索引遇到范围条件后，后续列通常不能继续像前面的等值前缀那样收窄一个连续的索引查找范围，但后续列不等于“完全失效”。如果列存在于索引中，它仍可能用于 ICP 过滤、覆盖查询等。要结合 EXPLAIN 看具体 Access Path，而不是一句“范围后全部失效”。

---

# 6. `A > 1 AND B = 0` 怎么分析

这正是冻结真人面经里出现过的题型。

Index：

```sql
INDEX idx_abcd (A, B, C, D)
```

Query：

```sql
WHERE A > 1
  AND B = 0;
```

### 第一步：A 能否用于 Index Range？

可以。

```text
A > 1
```

可以确定从某个 A 下界开始的 Range。

### 第二步：B=0 能否把所有结果继续缩成一个连续范围？

通常不能像 `A=固定值 AND B=0` 那样。

因为 Range 里是：

```text
A=2 下的所有 B
A=3 下的所有 B
A=4 下的所有 B
...
```

`B=0` 在这些不同 A Group 里分散出现。

### 第三步：B 是否可能继续被用来过滤？

可能。具体看执行计划、ICP 等优化。

这就是为什么只说“B 失效”信息量很低。

---

# 7. `A = 1 AND C = 3` 怎么分析

Index：

```text
(A, B, C)
```

Query：

```sql
WHERE A = 1
  AND C = 3;
```

`A=1` 可以定位一个连续范围。

但 B 未知，所以不能按 `(A,B,C)` 的连续排序直接把 `C=3` 再压缩成传统 `(A,C)` 的 Lookup Range。

不过：

- C 仍存在于 Index 中；
- 可能参与 Index-level Filtering；
- 如果 Query 所需列都在 Index 中，仍可能形成覆盖。

因此：

> 中间缺列不代表整个 Index 完全不能使用，而是“能利用到什么程度”发生变化。

---

# 8. 联合索引和 ORDER BY

Index 的价值不只在 Filter。

假设：

```sql
INDEX idx_user_created (
    user_id,
    created_at
)
```

Query：

```sql
SELECT id, created_at
FROM agent_runs
WHERE user_id = 10001
ORDER BY created_at DESC
LIMIT 20;
```

在 `user_id=10001` 的固定范围内，Index 又按 `created_at` 有序。

所以有机会直接利用 Index Order，避免额外排序并快速拿到前 20 条。

这是一种非常高价值的索引设计。

---

# 9. 为什么列顺序不能只看“谁选择性高”

常见经验：

> “联合索引把选择性最高的列放最左。”

这也不能当绝对规则。

索引列顺序要同时看：

```text
1. 哪些条件总是一起出现？
2. Equal 还是 Range？
3. 是否有 ORDER BY / GROUP BY？
4. 是否需要覆盖？
5. Query 的访问频率怎样？
6. Tenant / User 这种业务前缀是否是强约束？
7. 是否有多个查询可以复用同一个 Index Prefix？
```

例如多租户表：

```text
(tenant_id, user_id, created_at)
```

即使 `tenant_id` 全局选择性不是最高，它可能是所有查询必须先隔离的业务维度。

这时把它放前面可能非常合理。

---

# 10. 三个单列索引能替代一个联合索引吗

不完全等价。

假设：

```sql
INDEX idx_a (A)
INDEX idx_b (B)
INDEX idx_c (C)
```

和：

```sql
INDEX idx_abc (A, B, C)
```

不是同一个东西。

MySQL 在某些场景可以使用 Index Merge，但联合索引可以天然提供：

- 组合 Key 的有序定位；
- Leftmost Prefix；
- 组合范围；
- 排序能力；
- Covering Opportunity。

所以不能回答：

> “反正三个列都有 Index，效果和联合索引差不多。”

---

# 11. 重复索引 / 冗余索引

假设已有：

```sql
INDEX idx_abc (A, B, C)
```

又建：

```sql
INDEX idx_a (A)
```

很多时候 `idx_a` 可能是冗余的，因为 `(A)` 是 `idx_abc` 的 Leftmost Prefix。

但不能机械删除所有 Prefix Index。

还需要考虑：

- `idx_abc` 是否非常宽；
- `idx_a` 是否更小、更适合某些高频 Query；
- 写入成本；
- Optimizer 实际选择；
- 特殊排序 / Covering；

再决定。

工程上还是一句话：

> **用真实 Workload + EXPLAIN / Benchmark 验证。**

# 12. 一个完整设计例子

需求：

> 查询某 Tenant 下某用户最近 20 次 Agent Run。

SQL：

```sql
SELECT id, status, created_at
FROM agent_runs
WHERE tenant_id = ?
  AND user_id = ?
ORDER BY created_at DESC
LIMIT 20;
```

候选 Index：

```sql
INDEX idx_tenant_user_created (
    tenant_id,
    user_id,
    created_at
)
```

分析：

```text
tenant_id = ?     Equal
user_id = ?       Equal
created_at        Order
LIMIT 20          可快速停止
```

这就是“从 Query Pattern 推导 Index”，而不是“看到三个 WHERE/ORDER 字段就各加一个索引”。

# 13. 面试怎么答

## Q：什么是最左匹配？

> 联合索引按定义的列顺序进行字典序排序，例如 `(A,B,C)` 先按 A、A 相同再按 B、再按 C。因此可以天然按 `(A)`、`(A,B)`、`(A,B,C)` 这样的左侧连续前缀建立有效查找范围。缺少前面的 Key Part 时，后面的列通常无法直接形成同样的连续 Lookup Range。

## Q：范围查询以后后面的列是不是完全失效？

> 不能简单说完全失效。范围条件通常会限制后续 Key Part 继续收窄传统连续 Index Range，但后续列如果在 Index 中，仍可能参与 ICP、覆盖查询或其它优化。应区分 Range Construction、Index Filter、Covering 和 Sorting，再用 EXPLAIN 验证具体计划。

## Q：WHERE 条件必须按联合索引顺序写吗？

> 不需要。Leftmost Prefix 描述的是 Index Key 的排序与可利用前缀，不是 SQL 文本里 AND 条件的书写顺序，Optimizer 会分析等价谓词。

---

# 14. 高频易错点

⚠️ **“WHERE 必须 A、B、C 按顺序写。”**  
错误。

⚠️ **“只要跳过一个列，整个联合索引都不能用。”**  
前面的连续 Prefix 仍可能使用；后续列还可能用于 Filtering / Covering。

⚠️ **“范围以后的列完全没作用。”**  
过度简化。

⚠️ **“选择性最高的列永远放第一。”**  
忽略 Query Pattern、排序、租户边界和 Prefix 复用。

⚠️ **“多个单列索引等价于联合索引。”**  
错误。

# 15. 本章自测

<details>
<summary>1. `(A,B,C)` 为什么能支持 `A=1 AND B=2`？</summary>

因为 `(A,B)` 是该联合索引的 Leftmost Prefix，Key 先按 A 排序，A 相同再按 B，可以形成连续的查找范围。

</details>

<details>
<summary>2. `(A,B,C)` 为什么 `WHERE B=2` 不能直接按传统 Leftmost Prefix 查找？</summary>

因为 A 未知。不同 A Group 内都有自己的 B 排序，所有 `B=2` 不构成一个单一连续的 `(A,B,C)` Key Range。

</details>

<details>
<summary>3. `A=1 AND B>10 AND C=3` 中 C 是否“完全失效”？</summary>

不能这么说。B Range 后 C 通常无法继续像 Equal Prefix 一样缩小 Range，但 C 仍可能通过 ICP 在索引层过滤，或用于 Covering。具体看执行计划。

</details>

<details>
<summary>4. 为什么 `(tenant_id,user_id,created_at)` 可能比“选择性最高的列优先”更合理？</summary>

因为真实 Query 可能总是以 Tenant 做业务隔离，再按 User 查询并按 created_at 排序。索引设计要服务真实访问路径，而不是只比较单列 Cardinality。

</details>
