# 05｜从查对结果到少做工作：执行计划与索引

[← 把多张表查在一起，把多条记录汇总起来](04-关联查询与分组统计.md) · [MySQL 目录](../README.md) · [B+ 树怎样组织数据：聚簇索引与二级索引 →](06-B+树与数据组织.md)

同一句查询，在六条任务里几乎立刻返回，在几百万条任务里却可能要等很久。要求的结果没有变，变的是数据库为找到结果需要做多少工作。

从这一章起，我们把两个问题分开：**SQL 说明要什么结果，执行计划说明怎样得到结果；索引则为某些查询提供更省工作的查找方式。**

## 1. 一条 SQL 怎样从文字变成数据操作

读者已经能解释这句查询的结果：

<a id="sql-index_before"></a>

<!-- mysql-example: index_before -->
```sql
SELECT id FROM tasks
WHERE tenant_id = 10 AND status = 'pending' ORDER BY id;
```

它应返回编号 1、3、4。服务器收到语句后，需要理解表和列、判断语法与访问权限，再选择一种可执行的读取方式。这个选择出来的方案叫**执行计划**。

```text
客户端发送 SQL
    ↓
服务器解析、检查语句
    ↓
优化器选择执行计划
    ↓
执行器组织读取、过滤、关联等步骤
    ↓
存储引擎提供数据，结果返回客户端
```

**优化器负责选做法，执行器负责组织实际执行；InnoDB 是负责数据与索引等存储工作的引擎。** 它们是职责分工，不是三种互相替代的软件。这张图也不是源码中每个函数的精确调用顺序。

同一结果可以有不同做法。例如先扫描全部任务再判断团队，或先利用团队索引只检查该团队的任务。优化器会估计各条可行路径的成本，选择其中一种，而不是从左到右机械执行 WHERE 里的条件。[执行计划的官方说明](https://dev.mysql.com/doc/refman/9.7/en/execution-plan-information.html)。

## 2. 索引怎样减少查找

没有帮助定位的结构时，查“负责人为小林的任务”，可能需要逐条检查负责人编号。**索引是为查找维护的数据结构**：把检索值按适合访问的方式组织起来，使数据库更容易找到相关记录。

以 `owner_id` 索引为例，可以先这样看待其中的对应关系：

| 负责人编号 | 可定位的任务编号 |
|---:|---|
| 1 | 1、2 |
| 2 | 3、6 |
| 3 | 5 |

这是理解对应关系的示意，不是实际磁盘格式。查 `owner_id=1` 时，可以先定位这一组，再找任务 1、2，而不从每条任务的标题和状态开始检查。

<a id="sql-secondary_setup"></a>

<!-- mysql-example: secondary_setup -->
```sql
CREATE INDEX idx_tasks_owner ON tasks (owner_id);
```

`CREATE INDEX` 表示建索引，`idx_tasks_owner` 是我们取的索引名，`ON tasks (owner_id)` 指定哪张表的哪个列。这个普通索引允许多条任务有相同负责人；名字里的 `idx` 只是命名习惯。

索引不能改变查询答案。有无索引，负责人为 1 的任务仍是 1、2；它改变的是寻找它们的工作量。索引后续怎样找到完整记录，会在树和数据组织中具体展开。

## 3. 为什么不是所有查询都值得使用索引

假设有 100 万条任务，其中某成员只有 20 条。沿负责人索引找到这 20 条通常比扫描全部记录省事。再假设 90 万条任务都已经完成，而查询要求返回这 90 万条的全部内容，另走状态索引未必合算。

原因不是状态字段“天生不能索引”，而是它在这个查询中没缩小多少候选范围，还可能多做一次定位完整行的工作。

这里有两个常被混用的概念：**基数**是不同值的数量；**条件的筛选能力**关注本次具体条件留下多少记录。只有三个状态，也可能有一个仅出现十次的失败状态。不能只看“不同状态很少”就否定所有相关查询。

索引还可能提供结果顺序，或直接提供查询需要的列。因此它的价值不只有“找到一行更快”，而是能否减少本次读取、排序和取列的工作。最终还要结合实际数据与计划判断。

## 4. 查询省的工作，写入时要付一部分代价

新建一条任务以后，负责人索引也必须加入对应项；修改负责人时，旧对应关系要移除，新关系要建立。**索引占空间，也需要随写入维护。** 为每个字段建立索引，不等于给整个系统免费提速。

这时再看常见名称，就不会把不同层次混为一谈：主键和唯一索引关注身份或唯一约束；单列和联合索引关注键由几列组成；聚簇和二级索引关注行与索引怎样组织。一个索引可以同时是“唯一、联合、二级索引”。

判断是否建索引，先说出它服务的查询和预计省掉的工作，再看存储、写入和维护代价。六行练习表足以说明关系，但不适合测出生产规模的性能收益；不能因为一次测试很快就声称提升了多少倍。[索引用途与代价](https://dev.mysql.com/doc/refman/9.7/en/mysql-indexes.html)。

## 本章小结

SQL 规定结果，执行计划选择访问方法。索引帮助定位、排序或提供列值，但要付出维护和空间成本。先理解它省在哪，再判断是否值得使用。

## 🎯 面试怎么回答

### 索引为什么能加速查询？

它组织了适合查找的键，使数据库能缩小候选范围，有时也能利用顺序或直接取得所需列。收益取决于具体查询与数据，写入时则需要维护这份结构。

### 优化器是不是看到索引就使用？

不是。它比较可行访问路径的估计成本；如果大部分记录都要返回，或额外取行成本很高，扫描表也可能是合理选择。

## ⚠️ 易错点

> ⚠️ 不同值多不等于每个值都稀少，判断要结合实际分布和查询条件。

> ⚠️ “索引被使用”不等于扫描少，也不等于业务结果已经正确。

## 本章自测

<details>
<summary>1. 同一查询加索引后，正确结果应该改变吗？</summary>

不应该。索引改变访问方法，不改变查询语义；顺序若未显式规定则不能依赖碰巧出现的顺序。

</details>

<details>
<summary>2. 只有三种状态，索引就一定没价值吗？</summary>

不一定。某种状态可能很少，或者它与其他条件、排序一起组成有效路径。

</details>

<details>
<summary>3. 为什么新增任务也会受索引数量影响？</summary>

新行对应的索引项也要更新，索引越多通常意味着更多存储和维护工作。

</details>
