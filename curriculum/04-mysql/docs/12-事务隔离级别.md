# 12. 四种事务隔离级别

上一章讲了事务为什么存在，这一章开始回答并发世界里最关键的问题：

> **两个事务同时运行时，一个事务到底能看到另一个事务什么？**

如果这件事没有规则，数据库虽然支持 `BEGIN / COMMIT`，业务仍然会出现各种难以解释的读写现象。

这一章的目标不是背一张“脏读 / 不可重复读 / 幻读”表，而是建立一条真正能推演 SQL 的思路。

---

## 1. 先讲人话：隔离级别是在调“并发自由度”

想象两个事务：

```text
Transaction A                  Transaction B
-------------                  -------------
读取 agent_run
                               修改 agent_run
                               COMMIT
再次读取 agent_run
```

A 第二次读到什么？

可能：

- 还是第一次看到的旧值；
- 看到 B 已提交的新值；
- 甚至在最低隔离级别看到 B 尚未提交的值。

所以 Isolation Level 本质上是在定义：

```text
并发性能
   ↕
读的一致性 / 可重复性
   ↕
锁与等待
```

不同业务会选择不同平衡点。

---

## 2. InnoDB 的四种隔离级别

MySQL InnoDB 支持 SQL 标准描述的四种隔离级别：

```text
READ UNCOMMITTED
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

MySQL InnoDB 默认隔离级别是：

```text
REPEATABLE READ（RR）
```

查看当前会话：

```sql
SELECT @@transaction_isolation;
```

设置当前事务 / 会话时，面试不需要死背所有语法，但要知道隔离级别是可以配置的。

---

# 3. 先认识三类经典并发现象

## 3.1 Dirty Read：脏读

A 读到了 B **还没提交**的数据。

```text
B: UPDATE credits = 0
   还没 COMMIT

A: SELECT credits
   读到了 0

B: ROLLBACK
```

A 刚才看到的是一个最终根本没有成立过的状态。

这叫 Dirty Read。

---

## 3.2 Non-repeatable Read：不可重复读

同一个事务里，两次读取同一行，结果不同。

```text
A: SELECT status  → RUNNING

B: UPDATE status='SUCCESS'
B: COMMIT

A: SELECT status  → SUCCESS
```

A 的两次读取不一致。

---

## 3.3 Phantom Read：幻读

重点不是“同一行值变了”，而是**满足某个范围条件的行集合变了**。

```text
A: SELECT *
   FROM agent_runs
   WHERE user_id = 10001;
   → 10 rows

B: INSERT INTO agent_runs(user_id, ...)
   VALUES (10001, ...);
B: COMMIT

A 再做同一个范围查询
```

如果看到 11 行，就出现了 Phantom Row。

💡 新手记忆：

```text
Non-repeatable Read
→ 原来那一行“内容变了”

Phantom Read
→ 条件范围里“行集合变了”
```

---

# 4. 四种级别先建立总体感觉

| Isolation | Dirty Read | Non-repeatable Read | Phantom 风险 | 直觉 |
|---|---|---|---|---|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | 几乎不隔离 |
| READ COMMITTED | 避免 | 可能 | 可能 | 每次读最新已提交快照 |
| REPEATABLE READ | 避免 | 普通一致性读可重复 | 需区分快照读与锁定读 | 同事务尽量保持同一快照 |
| SERIALIZABLE | 避免 | 避免 | 强约束 | 并发自由度最低 |

⚠️ 这张表只是入口，不足以回答 MySQL 真正的追问。

真正重要的是：

> **普通 `SELECT` 和 `SELECT ... FOR UPDATE` 不是同一种读。**

---

# 5. READ UNCOMMITTED

这是最低隔离级别。

一个事务可能读取另一个事务尚未提交的数据。

实际业务里通常很少使用，因为：

```text
你读到的数据
可能下一秒就被对方 ROLLBACK
```

理解它的主要价值，是帮助你知道 Dirty Read 到底是什么。

---

# 6. READ COMMITTED（RC）

RC 的关键直觉：

> **每一次普通一致性读取，都可以建立一个新的已提交快照。**

例如：

```text
A BEGIN
A SELECT → status=RUNNING

B UPDATE → SUCCESS
B COMMIT

A SELECT → status=SUCCESS
```

所以：

- 不会读取 B 未提交的数据；
- 但同一个事务的两次普通读取可能不一样。

这就是为什么 RC 允许 Non-repeatable Read。

---

# 7. REPEATABLE READ（RR）

这是 InnoDB 默认级别。

最重要的入口理解：

> **同一个事务中的普通 Consistent Read 通常使用同一 Read View / Snapshot。**

例如：

```text
A BEGIN
A 第一次普通 SELECT
→ 建立快照，看到 status=RUNNING

B UPDATE → SUCCESS
B COMMIT

A 再普通 SELECT
→ 仍按原快照看到 RUNNING
```

因此普通一致性读具有 Repeatable Read 的效果。

但这里马上出现面试最爱追问的坑：

> `SELECT ... FOR UPDATE` 呢？

它不是普通 Snapshot Read。

---

# 8. Snapshot Read 与 Locking Read 必须分开

## 8.1 普通 Consistent Read

```sql
SELECT *
FROM agent_runs
WHERE id = 100;
```

在典型 InnoDB MVCC 场景中，它是非锁定一致性读。

关注的是：

```text
Read View
→ 哪个版本对我可见？
```

---

## 8.2 Locking Read

```sql
SELECT *
FROM agent_runs
WHERE id = 100
FOR UPDATE;
```

或者：

```sql
SELECT ... FOR SHARE;
```

它的目标不是“看历史快照就行”，而是：

> **我要读取接下来准备操作的数据，并限制其他事务对相关记录的并发修改。**

这类读取会进入 Lock 语义。

所以不要把 RR 简化成：

> “事务内永远只能看到开始时的旧数据。”

这是错的。

---

# 9. RR 到底“解决幻读”了吗？

这句话必须谨慎。

很多八股直接说：

> “MySQL RR 通过 MVCC 解决幻读。”

不够准确。

应该拆成两类场景。

## 9.1 普通快照读

在同一 Read View 下：

```text
第一次查 10 行
别人插入第 11 行并 COMMIT
第二次快照读仍按原 Snapshot
```

你可能仍只看到原来的 10 行。

这里 MVCC Snapshot 让结果保持一致。

## 9.2 Locking Read / UPDATE / DELETE 范围操作

如果你要真正阻止别人在某个扫描范围内插入新记录，仅靠历史快照不够。

InnoDB 在 RR 下对很多范围型锁定读 / 更新，会使用：

```text
Record Lock
Gap Lock
Next-Key Lock
```

来限制插入。

所以更成熟的回答是：

> **RR 下普通一致性读主要通过 MVCC Snapshot 保持可重复；涉及锁定读和范围修改时，InnoDB 还会通过 Gap / Next-Key Lock 等机制处理并发插入和 Phantom 问题。**

下一章和再下一章会分别拆 MVCC 与 Lock。

---

# 10. SERIALIZABLE

直觉上可以理解为：

> **让事务更接近按顺序执行。**

在 InnoDB 中，SERIALIZABLE 会比 RR 更积极地引入读锁语义，降低并发自由度。

它提供更强隔离，但代价通常是：

```text
更多 Lock
更多 Wait
更低并发
更高 Deadlock / Timeout 管理压力
```

所以不是：

> “越高越好。”

隔离级别是业务正确性与并发性能之间的设计选择。

---

# 11. 一个非常重要的推演：RC vs RR

假设：

```text
初始 status = RUNNING
```

Transaction A：

```sql
START TRANSACTION;
SELECT status FROM agent_runs WHERE id=1;
-- 等待
SELECT status FROM agent_runs WHERE id=1;
COMMIT;
```

中间 Transaction B：

```sql
UPDATE agent_runs
SET status='SUCCESS'
WHERE id=1;
COMMIT;
```

### RC

A：

```text
第一次 RUNNING
第二次 SUCCESS
```

### RR 的普通一致性读

A：

```text
第一次 RUNNING
第二次仍 RUNNING
```

这就是最核心的差异之一：

```text
RC：每次 Consistent Read 可看到新的已提交 Snapshot
RR：同一事务普通 Consistent Read 通常保持 Snapshot 一致
```

---

# 12. 第一次快照什么时候建立？

这是非常容易说错的地方。

不要机械背：

> “RR 在 `BEGIN` 时就一定创建 Read View。”

更准确的理解是：

> **普通一致性读的 Snapshot / Read View 与实际 Consistent Read 行为有关，不应该简单等同于执行 `BEGIN` 的瞬间。**

如果业务真的要求“从事务开始就固定某个快照”，需要理解具体事务启动和一致性快照机制，而不是靠一句口号。

本手册后续在 MVCC 章只讲面试和应用工程真正需要掌握的可见性模型，不把内部实现细节神化成背诵题。

---

# 13. 为什么线上系统常讨论 RC 和 RR

因为大多数 OLTP 系统真正关心的是：

```text
一致性读是否可重复
Lock 范围多大
Deadlock 概率
Undo 历史版本压力
业务是否真的需要同事务重复读保持完全一致
```

RC 往往：

```text
Snapshot 更新更频繁
Gap Lock 使用更少（特定约束检查除外）
并发冲突可能更少
```

RR 则提供更强的事务内一致性读体验。

不能脱离业务说：

> “RC 一定比 RR 好”

或：

> “RR 一定更安全。”

# 14. AI Application 场景：Worker 抢任务

假设多个 Worker 竞争：

```text
status = 'PENDING'
```

错误思路：

```sql
SELECT id
FROM agent_runs
WHERE status='PENDING'
LIMIT 1;

-- 应用层决定后再 UPDATE
```

多个 Worker 可能同时选中同一条。

真正要解决的是：

```text
任务挑选
+
并发 Claim
+
锁定 / 状态更新
```

这时：

- Isolation Level 只是背景；
- 还要使用 Locking Read、Conditional Update、`SKIP LOCKED` 等并发控制方法。

所以面试如果只回答“我们数据库是 RR，所以不会重复消费”，是不成立的。

# 15. 面试怎么答

## Q：MySQL 四种隔离级别是什么？

🎯 可以这样答：

> InnoDB 支持 READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ、SERIALIZABLE，默认是 REPEATABLE READ。RU 可能脏读；RC 每次一致性读可以建立新的已提交快照，所以同事务可能不可重复读；RR 的普通一致性读在事务内通常保持同一快照，通过 MVCC 提供可重复读；涉及锁定读和范围更新时还要结合 Record / Gap / Next-Key Lock 理解。SERIALIZABLE 隔离更强，但锁和等待更多。

## Q：RR 是否完全没有幻读？

> 不能只回答“有”或“没有”。普通 Snapshot Read 在同一 Read View 下可以保持结果集合一致；锁定读和范围修改则需要依赖 InnoDB 的 Next-Key / Gap Lock 等机制限制并发插入。因此要先区分快照读和锁定读。

---

# 16. 高频易错点

⚠️ **RC 会读到未提交数据。**  
不会，那是 READ UNCOMMITTED 的问题。

⚠️ **RR 的所有读取都只看旧快照。**  
错误，Locking Read / DML 不是简单快照读。

⚠️ **MVCC 单独解决所有幻读。**  
过度简化，范围 Lock 语义也很关键。

⚠️ **隔离级别越高越好。**  
更强隔离通常伴随更高锁冲突和并发代价。

⚠️ **事务开始瞬间一定已经建立了 Read View。**  
不要这么机械描述。

# 17. 本章自测

<details>
<summary>1. READ COMMITTED 与 REPEATABLE READ 最直观的区别是什么？</summary>

RC 下每次普通一致性读取可以读取新的已提交快照；RR 下同一事务中的普通一致性读通常保持同一快照，因此更容易做到重复读取结果一致。

</details>

<details>
<summary>2. 为什么分析 RR 时必须区分普通 SELECT 和 SELECT ... FOR UPDATE？</summary>

普通 SELECT 通常走 MVCC 的非锁定一致性读，重点是版本可见性；`FOR UPDATE` 是锁定读，关注最新可操作数据和并发修改保护，会进入锁语义，两者不能用同一套“快照”口号解释。

</details>

<details>
<summary>3. Phantom Read 与 Non-repeatable Read 有什么区别？</summary>

不可重复读通常强调同一条已有记录的值在两次读取中发生变化；幻读强调满足某个范围条件的记录集合因为并发插入/删除等发生变化。

</details>

<details>
<summary>4. 为什么“RR 通过 MVCC 完全解决幻读”不够准确？</summary>

因为普通快照读可借助一致性快照保持结果稳定，但锁定读和范围修改还涉及 Record / Gap / Next-Key Lock 等锁机制。必须根据读取类型讨论。

</details>
