# 08｜一致性与幂等：怎样守住不可破坏的业务条件

<a id="08consistencyidempotencytransaction-与-compensation"></a>

[← 上一章](07-PartitionRouting与Fanout.md) · [模块入口](../README.md) · [下一章 →](09-QueueBackpressure与LongRunningTask.md)

最后一件商品被两个人同时购买；另一位用户支付成功后没收到响应，点击了重试。这是两种不同的竞争：前者是不同操作争夺同一资源，后者是同一操作重复到达。

系统设计需要先写出不能被破坏的条件，再选择事务、版本、幂等和跨系统恢复。只说“保证强一致”还不足以判断方案是否正确。

## 1. 把一致性要求写成可以检查的条件

**业务不变量（invariant）**指每次合法状态变化后都必须成立的条件。例如库存初始为 100，可以定义：

```text
可售数量 + 有效预占数量 + 已售数量 = 100
三项都不能为负数
一次合法购买最多形成一个有效订单
```

这里暂不考虑补货和退货；加入这些动作后，要同时扩展守恒式和状态变化。排行榜允许延迟几秒，与库存不能超卖，是不同要求，不能用一个“最终一致”覆盖。

再区分读取语义：用户写完后能看到自己的修改、所有读者以同一顺序观察更新、派生索引最终收敛，都有不同的强度和代价。本章不把它们简化为数据库品牌标签。

## 2. 同一存储边界内，检查与修改一起成立

若两个请求都先读到库存 1，再分别写入库存 0，就可能各创建一张订单，造成超卖。正确方向是让存储在竞争发生时裁定：只有仍有库存才扣减，并让订单身份与库存变化处于一致的提交边界。

下面是逻辑过程，不是某种数据库可直接执行的脚本：

```text
开始事务
  争取本次购买的唯一操作记录
  仅当可售库存大于 0 时减 1
  建立对应订单或预占记录
  保存确定的处理结果
提交事务
```

任一步不满足条件则按协议结束事务，不留下“扣了库存但没有订单”的本地半完成状态。唯一约束、条件更新和事务隔离的实际行为要按数据库核验；课程的存储基础在 [MySQL](../../03-mysql/README.md)。

## 3. 重复请求与并发修改，不能只靠一种编号解决

同一用户同一次购买使用稳定操作键 K，重试仍沿用 K。两个人各自购买则分别使用 K1、K2，不能为了防重把它们合并。

幂等记录通常绑定可信作用域、操作类型、键和关键参数。并发重复请求需要唯一约束或等价的原子争用，不能都先查“没有记录”再各自执行业务。已有结果可复用，仍在处理可返回处理中，同键不同参数必须拒绝或报告冲突。

操作记录只保存一天，却允许三天后无条件重放，会让旧键重新成为“新操作”。应让保留窗口覆盖允许重试范围，或依靠长期业务唯一约束、限制超窗重放等方法补齐。

[HTTP 幂等语义](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)讨论的是请求的预期效果，不要求重复请求每次返回同一个响应码。业务 API 需要另行说明结果复用、处理中和参数冲突的行为。

## 4. 超时只说明没等到响应，不说明对方没做

库存事务提交成功，响应却在网络中丢失。客户端重试时，服务器通过 K 找到已提交结果，就可以返回同一订单，而不是再扣一次库存。

外部支付、发邮件或创建工单更复杂：本地数据库不能把外部世界包含在自己的普通事务中。

| 外部事实 | 本地看到的现象 | 安全处理方向 |
|---|---|---|
| 明确未接受请求 | 收到可靠的拒绝结果 | 修正条件或按错误分类决定是否重试 |
| 已完成且有可靠回执 | 保存了外部操作编号和结果 | 补齐本地状态，不重复执行 |
| 可能已完成 | 超时、断线或进程退出 | 保留 UNKNOWN，依赖外部防重或可靠查询核对 |

**UNKNOWN（结果未知）不是失败的同义词。** 若供应商既不支持幂等，也不能可靠查询结果，就不能承诺盲目重做既不会漏做、也不会重复。需要人工核对、业务补偿或接受明确的风险策略。

一次查询“没有找到”还可能与原请求仍在执行相竞争，除非外部协议明确证明原操作已终止，否则不能据此立即生成新操作键重做。[AWS：使用幂等 API 安全重试](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

## 5. Outbox、消息防重与外部防重各自保护哪里

事务发件箱让本地业务更新与待发事件一起提交，避免本地已成功却没有派发依据。消费者按事件或业务身份防重，避免重复交付造成重复本地效果。外部调用还要使用外部系统认可的操作身份或核对方式。

这三层不是同一个保证。消息系统宣称的“恰好一次”通常有具体读写和事务边界，不能据此断言邮件只会发送一次。端到端业务效果取决于最后执行副作用的资源能否参与对应协议。

## 6. 租约与 fencing：旧执行者为什么仍然危险

**租约（lease）**是在有限时间内认可某个执行者持有执行权；**隔离旧执行者的代际令牌（fencing token）**是让实际资源拒绝过时写入的依据。

假设 A 持有代际 20 后暂停，租约过期，B 取得 21。A 恢复后仍可能继续运行。若资源只检查“请求来自 A”，就可能接受旧写入；若资源在提交边界确认请求代际仍是当前有效代际，20 就会被拒绝。

> ⚠️ **发出一个更大的数字不等于旧执行者已被隔离。** 真正修改资源的地方必须原子校验代际，并按协议知道已生效的新拥有者。外部供应商不接受这种令牌时，本地 fencing 不能自动阻止旧邮件发送，仍需外部幂等或结果核对。

幂等识别同一动作，版本或代际拒绝旧状态决定，锁与租约约束并发进入。三者可组合，但不能互相冒充。

## 7. 补偿和对账，让跨系统流程继续收敛

**补偿（compensation）**是执行一个新的业务动作，修复先前动作造成的影响，例如预占超时后释放库存。它不是把世界恢复到从未发生过的状态：邮件无法真正“没发过”，支付退款也可能有费用、时延和失败。

**对账（reconciliation）**是比较多个系统的可靠记录，发现遗漏或矛盾并安排修复。订单显示待支付，但支付平台已有成功交易，应核对操作身份后更新订单，而不是让用户再付一次。

修复动作自己也需要身份、状态与重试边界。不能让“补偿失败后再补偿”变成无限递归。对账还需要负责人、积压告警和处理时限；“最终会一致”应有可观察的收敛目标，不是允许永久悬挂。

## 8. 怎样检验正确性，而不只检验成功路径

对库存检查守恒和非负，对操作检查唯一业务效果，对消息检查重复到达，对外部调用注入“成功后丢响应”，对工作者注入“租约过期但继续提交”。

应把状态和副作用分别断言：任务状态为成功，不能单独证明外部没有重复；外部已成功，也不能证明本地记录可恢复。配套[机制实验](../review/README.md#机制实验)用确定性模型检验这些条件，不冒充真实数据库隔离或多机并发验证。

## 本章小结

正确性先由不变量表达，再落到实际存储和外部资源的提交边界。本地事务与唯一约束解决一类竞争，幂等识别重复意图，版本和代际拒绝过时决定；跨系统未知结果需要核对，补偿与对账负责有依据地收敛。

## 🎯 面试怎么答

**问：怎样设计有副作用操作的可靠重试？**

> 我先定义不变量和稳定业务操作身份。本地修改、操作记录与结果在同一事务中成立；同键参数冲突不能重做。外部成功但本地没记下时保留未知，通过供应商幂等或可靠查询核对。租约接管还要在资源边界拒绝旧代际，补偿和对账则作为有状态、可验收的新流程。

## ⚠️ 容易混淆的地方

- 幂等键不阻止两个不同操作基于同一个旧版本覆盖，版本检查也不识别同一业务重试。
- 锁过期不等于旧工作者停止，fencing 不被资源执行就没有隔离效果。
- 最终一致需要明确收敛路径，补偿不是数据库回滚。
