# 01｜系统设计：从用户的一次操作推导整套方案

<a id="01system-design-的职责与完整答题框架"></a>

[← 模块入口](../README.md) · [下一章 →](02-Requirement与SLO.md)

一个团队希望做报告助手：成员提交资料，系统生成报告，主管确认后再发送给客户。把界面、数据库和模型 API 接起来，并不代表这个产品已经能够交付。用户关掉网页后报告还在不在？同一次提交重试会不会生成两份报告？系统显示“已发送”时，外部邮件服务究竟完成了哪一步？

**系统设计要把用户的承诺变成可以执行、可以检查的安排。** 它不仅回答选什么组件，还要说明数据由谁负责、工作怎样推进，以及失败后凭什么继续。

## 1. 先区分三种不同的“成功”

沿着一次报告任务，可以观察到三个时刻：

| 时刻 | 系统发生了什么 | 此时可以向用户承诺什么 |
|---|---|---|
| 接受提交 | 保存了任务身份、输入和提交者 | 这项任务可以查询，不会只存在于当前网页 |
| 生成完成 | 报告文件已保存，内容检查通过 | 用户能够读取这个版本的报告 |
| 发送确认 | 外部发送动作得到可核对的结果 | 按外部系统的语义报告“已受理”或“已送达” |

三个时刻不能用同一个 `success=true` 代替。数据库保存成功，不证明模型已经生成；模型返回文字，不证明文字正确；邮件服务接受请求，也不必然证明客户已经读到。

因此，系统设计首先要明确 **完成的对象** 。报告生成和对外发送可以是两个独立操作，分别有身份、权限、状态和失败处理。这样，发送失败不必重新生成已经确认的报告，生成重试也不应顺带再发一封邮件。

## 2. 先写约束，再引入组件

假设产品明确提出以下要求。这些是本课程的教学场景，不是实际业务测量：

- 同一团队的成员只能读取获准访问的资料与报告。
- 提交任务后可以离开网页，稍后继续查看结果。
- 同一次发送意图，即使网络重试，也不能产生重复发送。
- 等待人工确认时可以暂停，确认的是指定报告版本与指定收件人。

现在才推导系统需要什么。

任务要跨网页和进程存活，就需要保存任务事实的持久存储；报告文件可能比任务记录大，应把文件内容和查询用的元数据分开。工作可能比一次 HTTP 等待更久，就需要把“接受任务”和“执行任务”解耦，由后台执行者继续推进。对外发送不可随意重复，就需要稳定的操作身份及外部结果核对。读取与发送的权限不同，就要在各自实际执行的位置校验，不能只检查登录。

注意，这些推导尚未要求某个数据库品牌，也没有要求每个职责都部署成微服务。 **逻辑职责先清楚，物理拆分再由容量、故障隔离和团队维护成本决定。**

## 3. 画一条能够解释的正常路径

下面的框表示职责，不表示必须分别部署的服务。

```text
成员提交资料
    │
    ▼
接口：确认身份、权限与输入
    │
    ▼
任务存储：保存任务、输入版本和待执行意图
    │
    ▼
后台执行者：取资料、调用模型、检查结果
    │
    ▼
报告存储：保存文件与版本，提交“生成完成”状态
    │
    ▼
主管确认指定版本与收件人
    │
    ▼
发送执行者：记录操作身份、调用外部服务、核对结果
```

解释图时，不要只念框的名称。任选一条边，说明它携带什么。例如“后台执行者取任务”携带的是任务编号；执行者再按编号读到输入版本、所属团队和允许执行的动作。队列通知丢失时，权威任务记录仍应能帮助找回未执行工作。具体可靠通知机制会在数据流与一致性章节建立。

读者也应能反向追踪结果：用户看到的报告来自哪个任务、用了哪些资料版本、由哪个执行步骤生成。无法沿结果回到输入的图，还不足以解释系统行为。

## 4. 用一次失败检查架构，而不是再加一个框

假设发送执行者已经调用邮件服务，邮件服务完成发送，但回执丢失，执行者随后重启。此时：

1. 外部世界可能已经发生变化。
2. 本地只知道“尝试过发送”，并不知道确定结果。
3. 直接重做可能重复发送，直接标失败可能隐藏已经完成的事实。

需要的是可核对的外部操作身份、供应商防重或查询能力，以及无从确认时的人工处理路径。只添加“重试组件”没有解决这个问题。

> ⚠️ **注意：不知道结果，不等于结果失败。** 状态可以保留为“待核对”；不能为了让状态图只剩成功和失败，就把不确定性藏起来。

这里先理解这个失败窗口。后面的幂等、队列和 Agent 综合设计，会分别解释如何识别同一操作、如何接管执行以及如何组合成完整恢复流程。

## 5. 一份设计应怎样逐步展开

设计不是一次性画出最终大图，而是让前面的结论成为后面选择的依据：

1. **澄清用户动作与完成条件。** 先确定服务做什么、不做什么，以及哪些结果不能接受。
2. **估算工作量。** 把用户动作换算成请求、数据、模型调用与资源占用，不用“高并发”代替数字。
3. **确定数据与状态责任。** 哪份数据具有最终决定权，哪些副本可以重新生成，哪些动作需要被唯一识别？
4. **走通正常路径。** 写清谁在什么时候读写哪些状态，用户何时能观察到结果。
5. **找最紧的资源与最危险的失败。** 围绕它们讨论缓存、分区、排队、重试、隔离和恢复，而不是平均铺陈组件。
6. **给出取舍与验证。** 说明简单方案为什么不足，复杂方案新增了什么成本，怎样用实验和指标检查承诺。

一次迭代可以退回前面的步骤。例如，估算发现模型配额根本不足，就要重新讨论实时承诺、排队与预算，不能只在原图上继续加服务器。

## 6. 本模块负责组合，不重复所有底层课程

MySQL、Redis、向量数据库负责存储与检索内部机制；Backend 负责请求、消息和执行可靠性的共同基础；RAG 负责证据质量；Agent 负责跨步骤决策与恢复。系统设计把这些能力放进同一组业务约束，检查它们组合后是否仍然成立。

例如，知道“唯一约束可以拒绝重复记录”是数据库知识；判断“发送意图在哪保存、重复请求返回什么、外部发送成功但本地断电怎么办”则需要跨系统组合。正文会保留后一问题所需的最小前提，再把深入实现指向主讲模块。

参考：[Google SRE 的非抽象大型系统设计方法](https://sre.google/workbook/non-abstract-design/)，用于理解从具体工作负载与假设出发，而不是先堆产品名称。

## 本章小结

先定义用户可观察的完成，再从约束推导数据、执行与权限边界。正常路径说明怎样完成，失败时序说明哪里可能失去依据；容量与验证使这些安排不只是纸面架构。

## 🎯 面试怎么答

**问：拿到一道陌生的系统设计题，你会怎样开始？**

> 我先明确用户要完成的操作、成功条件和不可接受的结果，再估算工作量，确定权威数据及操作身份。随后沿一次请求解释状态变化，并在关键写入前后放入故障，检查重试、恢复和权限。组件选择应当能回到具体约束，还要说明替代方案、增加的成本和验证方法。

## ⚠️ 容易混淆的地方

- 接受任务、生成结果、外部动作完成是不同事实，不能共用一个模糊的成功状态。
- 图中的职责边界不等于必须拆成独立微服务；部署拆分需要额外理由。
- 失败处理要恢复可核对的事实，不是默认再调用一次。

## 本章自测

### 1. 报告生成后，主管修改了收件人，但没有重新确认。请指出发送前必须核对的两个绑定关系，并解释为什么“曾经批准过”不足够。

应提交：报告版本、收件人与批准记录之间的关系，以及不匹配时的处理。

<details><summary>提示</summary>

从批准的对象出发，而不是只检查一个 approved 布尔值。

</details>

<details><summary>参考答案与解释</summary>

批准至少绑定指定报告版本和指定收件人，也应绑定批准者权限与有效范围。任何影响已批准动作的参数变化都应使原批准不再足以授权执行，暂停并重新确认，而不是沿用旧批准发送。

</details>

### 2. 一个只有十名用户、每项任务两秒且允许失败重做的内部只读助手，是否必须使用独立队列与多组 Worker？

应提交：一个更简单的起点，以及使你决定升级的具体条件。

<details><summary>提示</summary>

区别逻辑责任和独立部署；不要把规模当成唯一条件。

</details>

<details><summary>参考答案与解释</summary>

可以从单个服务和明确的请求生命周期开始。需要跨断线或重启继续、任务时间变长、资源竞争明显，或出现不能重复的外部动作时，再增加持久任务、独立执行和恢复机制。用户少并不自动意味着可以忽略高风险副作用。

</details>
