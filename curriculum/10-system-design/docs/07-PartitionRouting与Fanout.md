# 07｜分区、路由与聚合：数据拆开后，一次查询要找谁

<a id="07partitionroutingfan-out-与-rebalance"></a>

[← 上一章](06-Cache与HotPath.md) · [模块入口](../README.md) · [下一章 →](08-Consistency与Idempotency.md)

任务表越来越大，团队准备把数据放到四台机器。按任务 ID 哈希后，记录数很均匀，可“查看某团队最近任务”的接口反而变慢了：它必须询问四台机器，再合并结果。

分区解决的不是单纯的“放得下”，还要让常见请求找到正确的数据，同时控制热点、跨分区交互和迁移风险。

## 1. 先区分拆数据与复制数据

**分区（partition）**把一个逻辑数据集合按规则分成多个子集。**分片（shard）**常用于描述分布在不同存储节点上的数据分区，具体产品用词可能不同。**副本（replica）**则保存某个分区的另一份数据，主要服务于容错或读取；复制一份数据不等于增加一份互不重复的数据容量。

**命名空间（namespace）**只是逻辑组织或隔离单位，不能仅从名称推断它拥有独立机器、配额或故障域。

对四分区、每分区三副本的方案，逻辑数据仍只分成四份，却保存了十二份分区副本。容量估算要分别计算逻辑规模、复制开销与故障后剩余资源。

## 2. 分区键必须同时回答两个问题

第一个问题是数据与写入能否分散，第二个问题是查询能否根据已知条件路由。

| 候选规则 | 分布特点 | 团队任务查询的代价 | 主要边界 |
|---|---|---|---|
| 按任务 ID 哈希 | ID 足够分散时较均匀 | 不知道目标分区，可能全量扇出 | 团队内查询与事务被拆散 |
| 按团队 ID | 同团队数据集中 | 通常可定位一个分区 | 大团队可能成为热点 |
| 按创建时间范围 | 便于时间裁剪与过期清理 | 查询近期只读相关范围 | 当前时间段集中承受写入 |
| 团队内再分桶 | 可以拆大团队 | 查询要访问该团队多个桶 | 路由与聚合更复杂 |

“哈希均匀”描述的是一个分布属性，不是所有访问模式都高效。时间分区也不是天然不好：若查询和保留策略都按时间组织，它可能节省大量扫描。

先列主要查询，例如“按 ID 查任务”“团队最近 20 条”“按日期导出所有任务”，再比较路由、扫描和跨分区协调成本。不要为了一个低频后台导出，牺牲每次用户请求的路径。

## 3. Fan-out 把一次请求变成多次工作

**扇出（fan-out）**是把一个请求分发给多个目标。查询四个分区并发执行，各自用时 20、25、30、180 毫秒，等待全部结果时，仅等待阶段就至少要 180 毫秒，再加路由、传输和合并成本，而不是四个时间的平均值。

若每个分区在给定时限内完成的概率都是 99%，并且暂作相互独立的教学假设，四个都完成的概率是 `0.99⁴ ≈ 96.06%`。实际故障常有相关性，不能直接把这当生产概率；它说明“每个依赖看起来不错”仍可能得到较差的整体尾延迟。

一个分区超时后，要依据查询语义决定：等到总 deadline、返回明确不完整的结果，还是失败。若任务是“审计全部退款”，静默漏掉一个分区不可接受；若是推荐候选，业务可能允许有标识的部分结果。

## 4. 全局 Top K，什么时候只取每片 Top K 就够

假设记录各属于一个分区，所有分区使用完全相同的确定性排序，包括相同的并列裁定规则；每片都精确返回符合条件的前 K 条。那么把所有局部 Top K 合并，再取全局 Top K，是足够的。

原因是：一个没有进入所在分区 Top K 的对象，至少已被同分区 K 个对象排在前面，因此不可能进入全局前 K。这个结论来自排序关系，不需要默认“每片必须多取几倍”。

但条件改变，结论也会改变：近似向量检索可能漏召回；各片分数不可比较；合并后还要去重或过滤；每个实体由跨片数据汇总得分。此时需要相应的过取、协调、精确复核或误差评估，而不是套用上述证明。

例如三个分区分别按统一分数返回前 2 项 `[9, 8]`、`[10, 7]`、`[6, 5]`，全局前 2 是 10、9。如果在合并后才过滤，结论就不再由前面的证明保证。例如 A 的完整顺序为 [10, 9, 8]、B 为 [7, 6, 5]，各取前 2 后再删去无权访问的 10、9，合并器会错误地选出 7、6，漏掉合法的 8。因此应在适当的候选生成阶段执行权限条件，或继续取足合法候选。

## 5. 读热点与写热点，怎样选择扩展方式

热门报告的只读访问可以在满足权限和新鲜度要求的情况下使用缓存或副本；同一个任务的状态更新却需要统一裁定。增加十个写入者，不会让同一个原子状态转移自然并行十倍。

对大团队，可以采用专属分区、团队内分桶或单独资源池，但要重新评估查询代价。对计数等可分解的数据，可以分片累积后汇总；对不能超额的配额，则要在分配时保持守恒，不能把全局上限复制给每个分区各用一遍。

复制还有一致性代价。读副本可能尚未看到刚写入的任务；需要读己之写时，可以在适用条件下读权威节点、等待副本达到指定位置，或返回明确的会话一致性标识。具体复制语义由所选数据库版本决定。

## 6. 扩容是在迁移所有权，不是只改除数

直接把 `hash(id) % 4` 改成 `% 5`，许多键的目标都会改变。路由表、虚拟分区或一致性哈希可以减少或管理迁移，但不会自动迁移数据，也不会自动协调新旧写入者。

一个可检查的迁移过程要回答：

1. **复制什么。** 为待迁移范围建立基线副本，并记录数据版本或日志边界。
2. **追上什么。** 复制期间的新增、修改和删除不能丢，要追增量并确认没有未处理空洞。
3. **谁可以写。** 切换所有权时阻止旧拥有者继续接受冲突写入，或通过受控转发处理旧路由。
4. **何时可读新位置。** 验证数据完整性、版本、新鲜度与性能后再更新路由。
5. **怎样退出。** 保留有限回退与旧请求完成窗口，再清理旧副本。

这是职责清单，不是所有存储通用的在线迁移实现。数据库原生再平衡协议、应用级停写切换和双写迁移有不同保证；不能只写“新旧双写”就省略失败、乱序和删除的处理。

## 7. 怎样验证拆分真的有用

压测应保留真实热点分布，不只生成均匀随机 ID。分别测单分区查询、跨分区查询、大团队、迁移期间写入和故障后重路由。

除平均吞吐外，还要比较尾延迟、跨片请求数、每片负载、复制滞后、迁移带宽和部分失败率。数据分得更均匀，却让常见查询多了十倍网络交互，可能不是一个净收益方案。

更细的索引与检索执行回看 [Vector DB](../../06-vector-db/README.md)，数据复制、事务和访问索引回看 [MySQL](../../04-mysql/README.md)。本章保留跨分区的整体推导，不重复产品内部机制。

## 本章小结

分区键同时决定分布和路由。扇出扩大工作量、尾延迟与部分失败范围；局部 Top K 能否组成全局答案取决于精确排序、过滤与聚合条件。扩容必须协调数据、增量和写入所有权，不能只把节点数量加一。

## 🎯 面试怎么答

**问：怎样判断一个分区方案是否合理？**

> 我先按主要查询检查能否定位分区，再看容量、热点、事务和生命周期。跨片请求要计算扇出、合并与尾延迟，并明确部分结果能否接受。扩容时说明基线复制、增量追平、写入所有权和路由切换，最后用非均匀负载及迁移故障验证收益。

## ⚠️ 容易混淆的地方

- 副本不是独立逻辑容量，命名空间也不自动代表物理隔离。
- 每片精确 Top K 的充分性有条件，不能把近似、后置过滤或跨片汇总混进同一证明。
- 一致性哈希管理位置变化，不代替数据迁移与旧写入者控制。
