# System Design｜高频面试题

> 这里的问题粒度故意比 19 个教材知识块更细。先口述，再展开答案。

---

## 1. 设计方法

### Q1：拿到一道 System Design 题，第一步做什么？
<details><summary>查看参考答案</summary>
先澄清 Functional Requirement、SLO、规模、Consistency/Freshness、安全和 Scope，再做数量级估算。不要一上来选数据库或堆组件。
</details>

### Q2：为什么 Capacity Estimation 重要？
<details><summary>查看参考答案</summary>
它决定问题是单机、分片还是架构层级变化，并帮助定位 CPU、Memory、Storage、Network、Token/Provider Quota 等真正瓶颈。
</details>

### Q3：怎样定义 Source of Truth？
<details><summary>查看参考答案</summary>
当多个状态副本冲突时最终以哪个状态为权威。Primary State、Derived State、Ephemeral State 要分开。
</details>

### Q4：什么是 Hot Path？
<details><summary>查看参考答案</summary>
最频繁、最延迟敏感或最昂贵的执行路径。优化应优先围绕它，而不是平均处理所有路径。
</details>

### Q5：为什么 System Design 最后必须讲 Verification？
<details><summary>查看参考答案</summary>
因为“看起来合理”不等于真实有效，需要 SLO、Load Test、Invariant Check、Trace、Evaluation 或 A/B 证明设计达到目标。
</details>

## 2. State / Consistency / Reliability

### Q6：Idempotency 和 Distributed Lock 有什么区别？
<details><summary>查看参考答案</summary>
Idempotency 保证同一业务操作重复请求不会产生重复效果；Lock 控制同时谁能进入临界区。很多 Retry 场景首先需要幂等，而不是锁。
</details>

### Q7：为什么 Timeout 之后不能直接认为操作失败？
<details><summary>查看参考答案</summary>
客户端只知道没拿到响应，服务端可能已经执行成功，所以 Retry 可能重复副作用。
</details>

### Q8：Outbox 解决什么问题？
<details><summary>查看参考答案</summary>
解决业务 DB 已提交但事件发布失败的双写窗口，通过同事务记录 Outbox，再异步可靠发布。
</details>

### Q9：什么时候用 Compensation？
<details><summary>查看参考答案</summary>
跨外部系统的副作用无法数据库 Rollback 时，通过新业务动作修复，例如退款、取消工单。
</details>

### Q10：为什么 Retry 会引发 Cascading Failure？
<details><summary>查看参考答案</summary>
依赖已经过载时，Retry 会增加额外流量，形成 Timeout→Retry→更高 Load 的正反馈。
</details>

### Q11：Load Shedding 是什么？
<details><summary>查看参考答案</summary>
容量不足时尽早拒绝部分低优先级或超额请求，保护系统让剩余请求仍能在合理延迟内成功。
</details>

### Q12：Failover 为什么还要讨论 RTO/RPO？
<details><summary>查看参考答案</summary>
Failover 只能说明能切换；RTO 描述恢复时间，RPO 描述可能丢失多少最近数据。
</details>

## 3. Scale / Cache / Queue

### Q13：Cache Aside 有什么一致性问题？
<details><summary>查看参考答案</summary>
DB 和 Cache 是独立状态系统，Update/Delete/Refill 有并发与失败窗口，通常通过 TTL、Version、Invalidate、Retry、Reconciliation 管理，而非天然强一致。
</details>

### Q14：HotKey 怎么治理？
<details><summary>查看参考答案</summary>
先确认真实分布，再考虑 Local Cache、Request Coalescing、Key Replication/Sharding、Precompute、Rate Limit 等，同时说明一致性与失效代价。
</details>

### Q15：为什么 Queue 不能解决长期过载？
<details><summary>查看参考答案</summary>
如果 arrival rate 长期大于 service rate，Queue 会无限增长；必须扩容、降载、限流或降低任务成本。
</details>

### Q16：Long-running Task 怎样防 Worker Crash？
<details><summary>查看参考答案</summary>
Durable Task State + Lease/Heartbeat + Checkpoint/Resume，并用 Idempotency/Fencing 防止 Reclaim 后重复执行。
</details>

### Q17：什么情况下需要 Partition？
<details><summary>查看参考答案</summary>
单机容量/QPS不足、需要查询路由或租户隔离时。Shard Key 要同时考虑分布、访问模式、热点和扩容，不只是 hash 均匀。
</details>

### Q18：为什么 Shard 越多不一定查询越快？
<details><summary>查看参考答案</summary>
跨 Shard Fan-out 增加 Network、Merge、Partial Failure 和 Tail Latency。
</details>

## 4. 真人 Scenario

### Q19：设计秒杀 / 库存系统，先讲什么？
<details><summary>查看参考答案</summary>
先定义 invariant：confirmed orders 不超过库存、重复请求不能重复扣减，再谈 Admission、原子预占、订单状态、异步处理、补偿、对账和压测验证。
</details>

### Q20：Redis 扣库存成功但 DB 创建订单失败怎么办？
<details><summary>查看参考答案</summary>
必须有 reservation/order 状态，走 Retry、Compensation 或 Reconciliation，不能只依赖 Redis 结果。
</details>

### Q21：设计 Distributed Rate Limiter，最关键 Trade-off 是什么？
<details><summary>查看参考答案</summary>
Global Accuracy 与 Latency/Availability。中央强同步更准但依赖更重；本地 Token Allocation 更快但可能短期配额利用不均或有误差。
</details>

### Q22：设计多实例 Token Refresh，如何防 Stampede？
<details><summary>查看参考答案</summary>
一个 owner refresh，其他实例等待或安全使用旧 Token；用 lease/version/result cache 处理 owner crash 和 refresh failure。
</details>

### Q23：二维码登录怎么建模？
<details><summary>查看参考答案</summary>
状态机 CREATED→SCANNED→CONFIRMED→EXCHANGED/EXPIRED，短 TTL、一次性交换、手机身份校验和 nonce 绑定。
</details>

### Q24：排行榜怎么处理全局 HotKey？
<details><summary>查看参考答案</summary>
可以按 region/category/shard 做 partial ranking 再合并或 snapshot，用允许的 Freshness 换写入压力。
</details>

### Q25：Feed 为什么有 Fan-out on Write / Read？
<details><summary>查看参考答案</summary>
Write Fan-out 读快但大 V 写放大；Read Fan-out 写轻但读时 Merge 重，Celebrity 常用 Hybrid。
</details>

### Q26：Autocomplete 为什么不能只用 SQL LIKE `%keyword%`？
<details><summary>查看参考答案</summary>
Prefix/Infix/Fuzzy/Pinyin 有不同索引语义，低延迟交互还要考虑 Debounce、Hot Prefix 和高请求频率。
</details>

### Q27：Notification Platform 怎样保证可靠投递？
<details><summary>查看参考答案</summary>
Durable task/status、Provider idempotency/status id、Retry taxonomy、Dedup、Queue/Backpressure，并区分 accepted/sent/delivered/read。
</details>

### Q28：20M 行数据迁移为什么不用 Deep OFFSET？
<details><summary>查看参考答案</summary>
OFFSET 越深扫描成本越高，通常使用 Keyset/Seek + Checkpoint，并考虑 Snapshot 期间 Delta Catch-up。
</details>

### Q29：1TB PDF RAG 怎样扩展？
<details><summary>查看参考答案</summary>
分阶段 Durable Ingestion、OCR/Parse、Chunk、Embedding Batch、Index Generation、Backpressure、Incremental Update、Permission、Evaluation 和 Cutover/Rollback。
</details>

### Q30：设计 LLM Gateway，为什么不能只做代理转发？
<details><summary>查看参考答案</summary>
还要统一 Auth、Quota、Provider Adapter、Routing、Streaming、Error、Cost、Failover、Trace，并处理 Provider Capability 差异。
</details>

### Q31：多租户 AI Platform 怎样防 Noisy Neighbor？
<details><summary>查看参考答案</summary>
Per-tenant token/concurrency/run/tool/cost quota，Queue fairness、Worker pool/resource isolation，大租户必要时 Dedicated Capacity。
</details>

### Q32：Enterprise RAG 的 Permission 放哪里？
<details><summary>查看参考答案</summary>
应进入 Retrieval/Namespace/Filter，并让 ACL 从 Source 传播到 Chunk；不能等 LLM 看完内容后再 UI 过滤。
</details>

### Q33：Production Agent Backend 为什么需要 Durable Run？
<details><summary>查看参考答案</summary>
Agent 可能跨连接、Worker Crash 和部署，Run/Step/Checkpoint/Side Effect 必须持久化，HTTP 只是交互通道。
</details>

### Q34：Long-running Agent 最危险的故障窗口是什么？
<details><summary>查看参考答案</summary>
外部 Tool 已成功，但 Checkpoint 保存前崩溃；Resume 后重复调用，需要 operation id/idempotency/result lookup。
</details>

### Q35：AI Customer Service Agent 怎么分 RAG 和 Tool？
<details><summary>查看参考答案</summary>
政策/FAQ 用 RAG；实时订单/账户事实用 Tool；退款等高风险写操作走 Tool + Auth/Approval/HITL。
</details>

### Q36：陌生 Vertical Agent 题怎么快速设计？
<details><summary>查看参考答案</summary>
先找 Goal、Authoritative State、Knowledge、Action Tool、Durable State、High-risk Side Effect、Human Handoff 和 Verification，再映射到统一 Agent/RAG/Backend 原语。
</details>
