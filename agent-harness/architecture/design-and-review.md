# Agent 设计、讲解与自测｜把知识地图变成可用的方法

[架构总纲](README.md) · [概念归位表](concept-atlas.md) · [执行与状态](lifecycle-and-state.md) · [资料依据](sources.md)

> 目的：使用同一框架讲知识、介绍项目、从零设计和定位失败。下面的模板是教材设计工具，不是某家厂商的规定答法。

## 1. 从零设计时，按这个顺序作决定

| 决策 | 应回答的问题 | 必须写出的结果 |
|---|---|---|
| 任务契约 | 为谁做什么？环境有什么？允许做什么？怎样算完成？ | 目标、非目标、输入、输出、权限、验收和约束 |
| 控制权 | 哪些路径确定，哪些要根据新信息决定？ | 程序控制与模型判断的明确边界 |
| 最小能力 | 需要理解、检索、执行、核验或协作中的哪些能力？ | 能力列表及每项存在的理由 |
| 四层职责 | 入口、运行、接入、资源分别由谁负责？ | 职责图、接口和依赖 |
| 状态与事实 | Task、Run、会话、Operation 怎么关联？什么必须持久化？ | 对象模型、状态所有权、恢复依据 |
| 行动安全 | 谁授权？哪些动作须确认？执行在哪里发生？ | 权限、审批、隔离与审计链 |
| 故障与规模 | 超时、重启、重复请求、并发、限流时怎么办？ | 失败策略、容量假设和预算 |
| 验证与演进 | 怎样证明有效，怎样检测退化？ | 评测集、上线门槛、版本和回滚方案 |

不应该一开始就选向量库、框架或多 Agent 拓扑。技术选择应是上述决策的结果。

同样，不需要第一天就把所有模块做成服务。先建立逻辑边界，再根据长任务、并发、隔离和独立扩容需求决定部署边界。

## 2. 每个模块都必须回答同一组问题

```text
它补上了什么缺口？
属于什么类型，主要责任在哪？
输入和输出是什么？
依赖谁、被谁调用？
何时需要，何时可以不用？
失败时会损害什么？
怎样验证它带来的收益和正确性？
```

例如，讲 compaction：运行层需要在上下文预算内持续推理，Context Manager 可以采用压缩机制；它依赖已有历史和可回读资料，输出新的模型工作视图；需要验证关键约束与未决事项是否保留，不能把它当作任务持久化或副作用核对机制。

讲 RAG：系统缺少任务所需证据时，需要信息获取方案；离线准备、检索接口、上下文组织和索引资源分属不同责任；收益应通过证据与任务质量检验，不以“是否装了向量库”判断。

讲 Sandbox：某些行动需要在隔离环境执行；Sandbox 限制环境能力和潜在损害，不负责判断任务是否完成，也不自动决定某个业务动作是否合法。

## 3. 介绍 Agent 项目时，不按组件清单排列

可使用下列通用叙事骨架，只填写真实做过的设计和验证，不补造规模或成绩：

> 我们解决的是【任务】，成功标准是【验收条件】。因为【不确定环节】无法完全提前固定路径，所以把它交给模型动态处理；【关键规则】仍由程序控制。
>
> 应用层负责【入口、业务阶段与交付】，运行层负责【Loop、上下文、状态与生命周期】，接入层封装【模型、信息、动作和状态接口】，资源层提供【事实来源与执行环境】。
>
> 我们最需要守住的边界是【权限或副作用风险】，通过【具体控制】实现。针对【实际失败】，补充了【机制】，并用【真实评测与运行证据】验证效果。

不要只说“用了某框架”。应该解释它承担哪些责任、哪些问题仍由自己的系统处理，以及框架替换后哪些接口和数据需要保持稳定。

## 4. 面试开放性设计题的开场

> 我会先明确任务目标、输入环境、自主权限和验收标准，再判断采用确定性流程、单 Agent 还是混合控制。系统按应用、运行、接入、资源四层划分逻辑责任：应用组织业务任务，运行层驱动模型与工具的反馈闭环并维护进度，接入层封装外部能力，资源层提供真实数据和执行环境。安全与质量贯穿整个过程。接下来我会展开状态模型、动作授权、失败恢复，以及怎样用真实结果做评测；最后才根据需要增加长期记忆、多 Agent 或更复杂的基础设施。

这只是回答的骨架。好的设计还需要依据题目明确约束、提出假设并说明取舍，不能把同一张图当作所有问题的最终答案。

## 5. 用架构归因，而不是看到失败就换模型

| 现象 | 优先检查的责任 | 可能的改进方向 |
|---|---|---|
| 回答流畅但没有完成工作 | L1 契约、L2 完成判定 | 明确产物与验收，核验外部状态 |
| 不断重复相似动作 | L2 控制与状态 | 无进展检测、目标约束、动作记录、预算 |
| 检索不到或引用错误信息 | L3 信息接口、L4 知识资源、L2 使用方式 | 来源覆盖、权限过滤、检索策略、时效、证据组织 |
| 工具参数总是用错 | L3 工具契约、L2 调用决策 | 改善语义与粒度、限制参数、提供可用错误信息 |
| 压缩后忘记限制或未决事项 | L2 Context 与 State 边界 | 保护关键字段、恢复引用、增加跨压缩回归 |
| 重启后重复产生副作用 | L2 恢复、L3 / L4 动作契约 | 稳定操作标识、幂等、未决动作核对 |
| 看到了别人的资料 | 四层身份与数据边界 | 核查检索、Memory、Artifact、凭证与 Trace 隔离 |
| 多 Agent 更慢且更贵 | L2 拓扑与总预算 | 检查分工必要性、上下文复制、重复劳动和结果合并 |
| 质量突然下降 | 全链版本与质量面 | 对比模型、Prompt、工具、技能、索引和环境变更 |

这些是排查起点，不是根据单一症状直接下结论。先用可观察证据缩小范围，再做最小实验。

## 6. 三种反馈回路不要混淆

**任务内反馈**是本次 Loop 根据工具结果修正下一步。**跨任务记忆**是后续任务复用经授权保留的信息。**系统改进**是通过评测和受控发布修改 Prompt、模型、工具、流程或数据。

三者的时间尺度、写入权限与验收方式不同。系统不应因一次失败就自动改写生产权限策略，也不能把所有用户交互默认转成永久记忆或训练数据。

## 7. 一个通用的评测计划

先用任务契约定义结果正确性，再分别验证信息、动作、安全、恢复和成本。不要只测试理想路径。

建议用例至少包含正常完成、信息不足、工具失败、外部结果未知、重复请求、执行中取消、状态恢复、上下文压缩、权限不足以及不可信输入。系统具备多 Agent 或长期记忆时，再增加委派边界、结果冲突、记忆污染和删除后的检索测试。

使用确定性检查验证能够客观判定的事实和产物；对主观质量采用经过校准的人工或模型评分，并抽检偏差。对具有随机性的执行，应关注多次试验的分布，而不是一次恰好成功。

改动后进行组件检查、端到端回归和必要的真实环境验证。保留任务、模型与配置版本、工具契约、环境条件和评分规则，使改进可以追溯。Agent 评测的原始讨论见 [S07](sources.md#s07)，完整机制见[正式评测章节](../docs/20-AgentEvaluationBenchmark.md)。

## 8. 如何逐步增加复杂度

| 已经观察到的需求或瓶颈 | 才考虑增加什么 | 先问什么 |
|---|---|---|
| 任务缺少模型已有知识之外的证据 | 检索与 RAG | 来源是否存在、可信、可授权访问？ |
| 信息需要在后续任务复用 | 长期记忆 | 是否允许保存，如何纠错、过期和删除？ |
| 任务跨多步且路径不可预先固定 | Agent Loop 与目标控制 | 是否有反馈和合理的停止条件？ |
| 任务跨上下文或跨 Worker | 交接记录、checkpoint、恢复 | 外部动作与产物怎么核对？ |
| 需要执行代码、命令或复杂界面操作 | 适当执行环境与隔离 | 是否可以先用更窄的受控 API？ |
| 子任务可分离且确有收益 | 多 Agent 与协作管理 | 怎样证明收益超过协调与成本开销？ |
| 并发与资源竞争成为瓶颈 | 队列、配额、背压与独立扩容 | 瓶颈究竟在模型、工具、状态还是环境？ |

这个表不是“所有项目最终都要走完”的路线。没有需求时保持简单，是设计选择而不是缺陷。

## 10. 折叠自测

<details>
<summary>1. 为什么业务场景不能与 Memory、Sandbox 并列成组件？</summary>

业务场景是决定目标、范围、约束和验收的设计输入；Memory 是信息保留与复用机制，Sandbox 是执行资源和隔离边界。它们属于不同抽象类型。

</details>

<details>
<summary>2. 为什么 Harness 不能代表整个 Agent 产品？</summary>

Harness 以受控执行为核心。产品还需要任务契约、交互与业务流程、真实系统和数据、部署责任以及验收和运营。某个 Harness 实现可以覆盖多项职责，但不会自动定义业务目标。

</details>

<details>
<summary>3. RAG 为什么跨层，而不是独立一层？</summary>

RAG 是获取和使用证据的方案。数据与索引属于资源，检索通过接入接口暴露，运行逻辑决定何时查找并组织上下文，应用定义证据与交付要求。跨层不意味着没有边界。

</details>

<details>
<summary>4. 模型想调用一个工具，是否代表它拥有调用权限？</summary>

不代表。工具可见性、参数合法性、身份授权、审批以及底层资源限制分别需要检查。模型提出动作不等于实际动作获准。

</details>

<details>
<summary>5. Thread、Turn、Item、Event 是同一层级吗？</summary>

不是。Codex 用 Thread 组织会话，Turn 表达一次用户输入触发的工作，Item 表达类型化输入输出。一个 Item 可以通过多个生命周期 Event 被观察。不要推广为所有框架的统一定义。

</details>

<details>
<summary>6. 保存完整聊天记录，为什么还不能保证恢复正确？</summary>

还要知道未决动作、审批绑定、外部回执、状态版本、预算和产物引用。即使这些本地信息齐全，外部动作也可能已执行但响应丢失，需要核对真实状态。

</details>

<details>
<summary>7. Compaction 成功是否意味着长任务一定能继续成功？</summary>

不是。压缩仅处理模型工作视图。任务还需要清晰进度、有效引用、可靠环境、目标和验收，以及对外部副作用的恢复机制。

</details>

<details>
<summary>8. 工具超时后最先问什么？</summary>

先判断前一次是否可能已经执行，以及有没有稳定操作标识、状态查询或幂等契约。不能把所有超时都解释为未执行，再直接重复写操作。

</details>

<details>
<summary>9. Multi-agent 为什么不是新的架构层？</summary>

它是执行与协作拓扑。每个参与者仍需要相应的运行、接入和资源；整个应用仍需任务契约、授权与验收。增加 Agent 数量不消除这些责任。

</details>

<details>
<summary>10. 一个只调用受控 API 的 Agent，必须有向量库和代码沙箱吗？</summary>

不必须。向量库取决于检索需求和数据特性；独立代码执行环境取决于动作方式与隔离需求。成熟度应由任务效果和工程边界判断，而不是由组件数量判断。

</details>

<details>
<summary>11. Trace、运行时核验与 Eval 有什么不同？</summary>

Trace 提供可观察执行证据；运行时核验判断这次结果是否满足条件；Eval 在一组任务上检验质量和变化。记录详细不代表结果正确，单次通过也不代表整体可靠。

</details>

<details>
<summary>12. 怎样判断自己真正形成了 Agent 架构认知？</summary>

能够不先罗列技术名词，而从任务与控制权推导四层职责；能说明状态与事实在哪里、动作如何受控、失败如何恢复、结果如何验收；并能解释为什么某个模块不需要。

</details>

## 11. 最后一条原则

> **讲知识，要讲归属；讲项目，要讲因果；做设计，要讲取舍；评系统，要讲证据。**
