## 1. Agent 不是一堆能力的相加

本笔记讨论 LLM 驱动的软件 Agent。一个实用工作定义是：

> **Agent 在给定目标与约束下，根据观察到的信息动态选择下一步，通过受控行动获得反馈，持续推进任务。Agent 系统则把这个过程组织成可交付、可治理、可验证的软件产品。**

这一定义强调动态控制与反馈，不要求必须有长期记忆、向量数据库、独立规划器、多 Agent 或代码沙箱。Workflow 与 Agent 的区分可参考 Anthropic 的控制路径讨论；这是有用的工程区分，而不是对所有产品命名的裁决。[S08](sources.md#s08)

必须同时分清四个对象：

| 对象 | 主要责任 | 不等于什么 |
|---|---|---|
| Model | 根据输入进行推理、生成或提出行动 | 不等于会可靠经营整个任务的软件系统 |
| Agent | 一个具有目标、可用能力和行动选择逻辑的执行角色 | 不等于某个固定框架的类 |
| Harness / Runtime | 让模型、上下文、工具和执行状态持续协作 | 不等于整个业务产品 |
| Agent Application / System | 组织任务、交互、运行、数据、执行环境与治理 | 不等于在模型外套一层 API |

Harness 和 Runtime 在业界经常交叠使用。本文用“运行层”表达稳定职责，用 Harness 指承担这些职责的具体执行系统；不要强求每个产品对这两个词做完全相同的区分。

## 2. 唯一主图：任务契约在前，四层架构在中，治理贯穿

```text
设计输入：业务场景
             ↓
         任务契约
  为谁做什么、允许做什么、怎样算完成
             ↓
      能力与自主权设计
  哪些交给模型判断，哪些必须由程序控制
             ↓

┌────────────────────────────────────────────┐
│ L1 应用层：把 Agent 组织成业务产品            │
│ 任务入口、业务流程、用户交互、结果交付、人工接管 │
├────────────────────────────────────────────┤
│ L2 运行层：让一次 Agent 执行受控地进行         │
│ Agent Loop、上下文组织、执行状态、调度与恢复    │
├────────────────────────────────────────────┤
│ L3 接入层：把外部能力变成稳定的可调用接口       │
│ 模型适配、检索接口、工具适配、状态与记忆存取接口 │
├────────────────────────────────────────────┤
│ L4 资源层：提供真实能力、数据和执行环境         │
│ 模型服务、知识与数据库、业务系统、文件与沙箱     │
└────────────────────────────────────────────┘

贯穿四层：
安全治理：身份、权限、审批、隔离、审计
质量运营：观测、评测、成本、可靠性、持续改进
```

三个首要约定：

**业务场景是设计输入，不是软件模块。** 场景决定任务、风险和约束，不应与 Memory、Sandbox 并列成组件。

**这里是逻辑分层，不是四个微服务。** 一个进程可以承担全部职责。分层表达谁负责什么、通过什么契约协作，不规定机器数、目录数或部署拓扑。

**层、模块、机制不是同一类东西。** 运行层是职责边界，Context Manager 是模块，compaction 是该模块可以采用的机制。

还需要两个补充约定。图中的上下位置不代表重要性：模型服务放在资源层，只表示它是上层使用的能力来源。图也不是必须逐层经过的网络协议栈：普通应用流程可以通过接入接口访问资源，不必为一次确定性查询强行启动 Agent Loop。

## 3. 先学会给概念“标注类型”

| 类型 | 它回答什么 | 示例 |
|---|---|---|
| 设计输入 / 契约 | 解决什么问题，在什么约束下算成功？ | 目标、环境、自主权、验收标准 |
| 能力 | 系统需要会做什么？ | 理解、检索、规划、执行、核验、协作 |
| 层 | 哪一类责任应该由谁拥有？ | 应用层、运行层、接入层、资源层 |
| 模块 | 哪个软件单元承担具体责任？ | Context Manager、Tool Router、Scheduler |
| 机制 / 策略 | 这个单元怎样工作？ | compaction、retry、offloading、rerank |
| 运行对象 | 系统需要识别、保存或关联什么？ | Task、Run、Thread、Turn、Item、Artifact |
| 模式 / 拓扑 | 多个执行单元怎样组合？ | Workflow、ReAct、manager-worker、handoff |
| 接口 / 协议 | 两个边界怎样交换信息或动作？ | Tool Schema、MCP、A2A、事件协议 |
| 资源 / 环境 | 能力在哪里提供，事实在哪里保存？ | 模型服务、数据库、外部服务、Sandbox |
| 横切要求 | 每一层都需要满足什么？ | 安全、可靠性、观测、评测、成本 |

因此，“Agent 由 Planning、Memory、Tool、Sandbox、Eval 五层组成”混合了不同抽象维度。它可以是一份能力清单，但不是清楚的职责分层。

一个概念可以跨层实现，但仍能给出清晰归属：**标明主要责任，以及它依赖的其他层；不要为了表格整齐而强迫它只能属于一个方框。**

## 4. 设计输入：先建立任务契约

任务契约不是把用户原话复制进 Prompt。它要把需求变成可以实施和验收的约束。

| 契约要素 | 需要回答的问题 | 应形成的产物 |
|---|---|---|
| 服务对象与目标 | 谁把什么工作交给系统，期望得到什么结果？ | 任务定义、目标、输出类型 |
| 范围与环境 | 有哪些数据、接口、工作空间？哪些事情不做？ | 输入边界、环境依赖、非目标 |
| 信息条件 | 信息是否完整、实时、可信？是否需要追问？ | 证据要求、澄清条件 |
| 行动与自主权 | 可以查什么、改什么、委派什么？哪些动作须批准？ | 能力与授权矩阵 |
| 风险与约束 | 失败代价、数据范围、预算、时限是什么？ | 风险约束、资源预算 |
| 完成与退出 | 如何证明完成？何时等待、停止或转人工？ | 验收谓词、终止与升级规则 |
| 非功能要求 | 延迟、并发、恢复、隔离、可追踪性有什么要求？ | SLO、故障假设、容量估算输入 |

“能生成一个回答”和“能完成一个动作”必须是不同契约。“发出请求”和“外部动作完成”也必须分开。

对于无法完全自动验证的任务，应明确可核验部分、抽样或人工验收部分，以及系统必须保留的不确定性。不能拿模型自己的“已经完成”替代验收。

## 5. 能力与自主权：决定哪些判断交给模型

能力设计先用动词描述：**理解输入、获得证据、分解目标、选择动作、执行动作、核验结果、请求协作、保留有用信息。** 之后才决定是否需要 RAG、Memory、Planner 或 Multi-agent。

自主权至少有四个独立维度：读取范围、写入范围、控制流程的自由度、持续执行与委派的边界。它不是从“低级”到“高级”的单一分数。

| 控制选择 | 适合的条件 | 必须明确的边界 |
|---|---|---|
| 单次模型调用 | 一次理解或生成已足够 | 输出验证与失败处理 |
| 确定性 Workflow | 主要步骤可预先定义 | 模型只参与指定节点 |
| 单 Agent Loop | 下一步依赖执行中获得的新信息 | 工具范围、预算、停止与审批 |
| Workflow + Agent | 既有固定关口，又有不确定调查或生成环节 | 哪些状态转换由程序强制控制 |
| Multi-agent | 有明确可分工性、上下文隔离或独立能力边界 | 任务分配、权限传播、结果合并、总预算 |

这些是组合选择，不是成熟度排名。默认从足以满足契约的最简单形态开始，用失败证据决定是否增加复杂度。[S08](sources.md#s08)

## 6. L1 应用层：组织任务和交付

**责任：把一次用户意图或外部触发，变成有明确归属、过程和结果的任务。**

应用层可以提供聊天、表单、CLI、IDE、API、计划触发或事件触发。它负责入口身份与任务绑定、产品业务流程、交互呈现、结果和产物交付，以及澄清、确认、取消、人工接管入口。

典型模块是 Task Service、Application Workflow、Conversation UI、Artifact Viewer 和 Human Review UI。这些是示意责任，不要求真的使用这些类名。

它向运行层下发的应该是任务规格、执行上下文与授权范围，而不是只给一段没有边界的字符串；运行层返回进度事件、等待请求、结果或明确的失败状态。

**边界：业务流程不等于 Agent Loop。** 应用流程定义任务经历哪些必要阶段；Loop 决定当前执行阶段下一步怎么推进。一个业务任务可以跨多个交互轮次、多个运行尝试，甚至多个会话。

这一层最典型的错误是把“生成结束”“用户页面断开”“当前 Turn 结束”都等同于业务任务完成。

深入：[System Design](../../system-design/README.md)、[FastAPI](../../fastapi/README.md)。Codex 的多界面与共享运行核心可作为产品入口和执行核心分离的实例。[S02](sources.md#s02)

## 7. L2 运行层：驱动受控执行

**责任：在多次模型调用、工具执行、等待和恢复之间，维护任务进度与控制。**

运行层可以按责任拆成以下模块。它们不必都是独立服务，也不必在初版全部实现为独立类。

| 运行责任 | 典型模块 | 可选机制 |
|---|---|---|
| 驱动下一步 | Loop Controller / Orchestrator | 直接循环、计划后执行、重规划、分支与并行 |
| 组织模型可见信息 | Context Manager | 选择、预算、裁剪、compaction、offloading、缓存布局 |
| 保存执行进展 | State / Session Manager | 事件记录、checkpoint、版本控制、恢复 |
| 调度和生命周期 | Run Manager / Scheduler | 排队、配额、超时、取消、等待、worker 接管 |
| 协调动作执行 | Tool Dispatcher | 参数校验、授权关口、审批、错误分类、结果归并 |
| 约束目标与完成 | Goal / Completion Controller | 停止条件、无进展检测、验收、升级处理 |

模型可以提出计划、工具参数、答案或完成候选；运行时负责将这些提议放进明确的控制流程。**行动选择权不等于最终授权权。**

最小逻辑闭环是：

```text
读取任务与状态 → 组织上下文 → 调用模型 → 解释下一步
      ↑                                  ↓
记录反馈与进度 ← 受控执行 / 等待用户 / 核验完成候选
```

Codex 官方文章解释了模型推理与工具交互构成的循环；生产系统还必须围绕循环处理状态、安全和生命周期。[S01](sources.md#s01)

深入：[Loop 与事件](../docs/03-AgentLoopRuntimeState.md)、[Planning](../docs/08-PlanningGoalStopBudget.md)、[Context](../docs/09-ContextAssemblyBudget.md)、[恢复](../docs/13-CheckpointResumeReliability.md)。

## 8. L3 接入层：提供稳定能力契约

**责任：让运行逻辑不必理解每个供应商、数据库和业务系统的细节。**

| 接口族 | 应封装什么 | 不应冒充什么 |
|---|---|---|
| 模型接口 | 请求、流式输出、工具调用格式、能力差异、错误与用量 | 模型决策本身 |
| 信息接口 | 搜索、读取、检索、来源、权限过滤、时间和版本 | 现实中唯一可信的事实来源 |
| 动作接口 | 工具发现、输入输出契约、外部调用、结果与错误语义 | 无约束的任意系统访问 |
| 状态接口 | 会话、事件、checkpoint、memory、artifact 的读写 | 状态机与记忆写入策略本身 |

模型看到的 Tool Description、Runtime 调用的 Handler、真正实施动作的外部服务，是三个不同位置。工具是否好用，既与描述有关，也与动作粒度、参数约束、结果质量和失败语义有关。[S06](sources.md#s06)

MCP 是一种接入协议选择，不是完整的规划、记忆或恢复系统。模型路由策略通常由运行逻辑或平台策略决定，Provider Adapter 负责兑现调用；不要把“怎么选”和“怎么接”混成一个问题。[S10](sources.md#s10)

深入：[Tool Contract](../docs/04-ToolContractSchemaValidation.md)、[工具发现](../docs/05-ToolRegistryRouterDiscovery.md)、[工具执行](../docs/06-ToolExecutionFailure.md)、[模型路由与适配](../docs/17-RoutingProviderResilience.md)。

## 9. L4 资源层：提供模型、事实与执行场所

**责任：提供实际能力、保存数据、承载计算，以及产生真实副作用。**

模型服务提供推理和生成能力；数据库与对象存储保存不同性质的信息；搜索索引支持信息发现；业务服务拥有领域事实；文件、进程、浏览器或代码执行环境承载实际操作。

Sandbox 是执行资源和隔离边界，不是 Agent 的同义词。只调用受控外部 API 的系统，不必为了符合一张图而增加通用代码执行能力。反过来，允许执行不可信代码或控制浏览器时，就需要按威胁模型设计适当隔离，不能只在 Prompt 中要求小心。

资源生命周期不必等于任务生命周期：模型请求可以短暂，任务可以长期存在，worker 可以替换，执行环境可以重建，持久记录继续存在。Anthropic 的 2026 年架构文章展示了这种会话、Harness 与执行环境解耦的产品实现。[S04](sources.md#s04)

深入：[MySQL](../../mysql/README.md)、[Redis](../../redis/README.md)、[Vector DB](../../vector-db/README.md)、[LLM Foundation](../../llm-foundation/README.md)、[Sandbox](../docs/14-PermissionApprovalSandbox.md)。

## 10. 安全治理：每层都有决策点和执行点

安全不是在输入上加一个“敏感词检查器”。在这套参考架构中，至少要把身份、授权、审批、隔离与审计贯穿到真实动作。

| 位置 | 要守住的边界 |
|---|---|
| 应用层 | 谁提出任务，代表哪个租户，确认了什么，如何撤销或接管 |
| 运行层 | 当前 Run 能调用哪些能力，子 Agent 能继承什么权限，何时暂停 |
| 接入层 | 参数是否合法，凭证作用域是否匹配，是否允许访问目标资源 |
| 资源层 | 真实服务端校验、文件和网络限制、隔离、资源配额 |

外部文档、网页、工具结果和记忆内容需要携带来源与信任边界，不能因进入上下文就升级成系统授权。防注入设计既要减少误导，也要限制误导成功后的损害。

Approval 是对具体动作的许可，不是一次点击后永久放开所有操作。Sandbox 限制环境行为，不会自动证明动作符合业务规则。Guardrail 可以提供检测或风险判断，但不能替代可信代码和底层服务的强制授权。[S13](sources.md#s13)

深入：[Permission / Approval / HITL](../docs/14-PermissionApprovalSandbox.md)、[Injection / Secrets / Containment](../docs/15-GuardrailsInjectionContainment.md)。

## 11. 质量运营：证明有效，并让系统持续改善

质量不是模型“看起来很聪明”。任务契约应决定观测指标、评测用例和上线门槛。

**运行时核验**判断这一次结果是否满足条件；**离线与在线评测**衡量一组任务上的表现和变化；**Trace**保留可观察执行证据；**监控**发现整体运行异常。这四件事相关，但不能互相替代。

应同时观察任务成功、事实与证据质量、动作正确性、权限违规、恢复能力、延迟和成本。一个工具返回成功不一定意味着任务成功；一段流畅文本也不一定对应正确的最终环境状态。[S07](sources.md#s07)

建议建立明确改进闭环：

```text
真实失败 → 归因到层与责任 → 最小修改 → 分层评测
        → 端到端回归 → 小范围发布 → 监测与回滚
```

改进可能发生在任务范围、工具设计、检索质量、上下文选择、控制逻辑、恢复机制或模型选择上，不应默认“加更长的 Prompt”或“再加一个 Agent”。

深入：[Trace](../docs/19-TraceReplayObservability.md)、[Eval](../docs/20-AgentEvaluationBenchmark.md)、[Production Runtime](../docs/22-ProductionAgentRuntime.md)、[System Design](../../system-design/README.md)。

## 12. 如何从这张静态图走到运行中的系统

同一个框架需要三个互补视图，不是三套互相竞争的架构。

**职责视图**就是四层图：谁负责什么。**执行视图**描述一次任务的调用、等待与反馈顺序。**状态视图**描述保存哪些事实，哪些对象可以重建，以及谁拥有真实状态。

运行时最需要区分：当前模型上下文、任务执行状态、长期记忆、外部业务事实。它们可以关联，但不能用一个名为 `memory` 的容器掩盖所有差异。

在 Codex 的对象模型中，Thread 包含多个 Turn，Turn 包含多个有类型的 Item。本文另外用 Task 表示业务任务、Run 表示受管理的一次执行；不同框架对这些词的含义可能不同，不应强行一一等同。[S03](sources.md#s03)

完整对象表、生命周期和恢复时间线见[执行过程与状态模型](lifecycle-and-state.md)。

## 13. Codex 的价值：验证责任边界，不照搬产品实现

| 可观察到的实现 | 对本框架的启发 |
|---|---|
| 多种客户端与 App Server | 产品入口、交互协议与共享执行核心可以分离 |
| Core 中独立的 context、tools、session 等职责 | Harness 不只是一个 while 循环，也不等于所有基础设施 |
| Thread / Turn / Item 与事件 | 用户工作过程需要显式对象和生命周期 |
| 工具协调中的审批和沙箱逻辑 | 模型请求执行与实际授权执行需要分开 |

这里的映射是教材抽象，不是源码目录一比一翻译。公开仓库不能被当作完整托管产品后台的公开实现，也不能从一个模块存在推断所有版本默认启用它。具体源码入口与固定提交见 [S16](sources.md#s16)。

## 15. 最终记忆卡

> **先问任务：为谁做什么，能做什么，怎样算完成。**
>
> **再定控制：哪些判断交给模型，哪些关口必须由程序掌握。**
>
> **再看四层：应用组织任务，运行驱动过程，接入连接能力，资源承载事实与行动。**
>
> **贯穿两件事：行动是否受控，结果是否可验证。**
>
> **遇到任何新概念，先标注类型，再定位责任，最后解释机制和取舍。**
