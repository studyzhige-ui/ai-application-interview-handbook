# 22. 生产Agent架构：从一个进程到可运营服务

[← 上一章](21-CodingAgentWorkflow.md) · [模块目录](../README.md) · [下一章 →](23-FrameworkMappingBuildVsBuy.md)

> 本章要解决：根据任务时长、风险和容量逐步增加组件，不把完整组件清单当每个项目的起点。

## 1. 单进程不是错误，承诺不匹配才是错误

一个用户、短任务、允许失败后重来，单进程调用模型和只读工具完全可以是合理产品。问题出在承诺“运行半小时、断线继续、重启恢复、多人隔离”，却仍把唯一任务状态放在HTTP处理函数的局部变量里。

先写服务要承诺什么：是否跨连接运行、允许丢失多少工作、能否重复操作、多少并发、数据能保存多久。然后从承诺推导组件，而不是看到成熟产品有Sandbox Pool就先建一套。

## 2. 各组件为什么出现

| 需求变化 | 新的责任 | 常见实现，不是唯一选择 |
|---|---|---|
| 请求超过普通连接寿命 | 任务创建与状态查询分离 | 返回任务ID，独立事件流 |
| 工作要活过进程重启 | 可靠状态/操作记录 | 事务数据库、文件记录或框架检查点 |
| 多Worker领取任务 | 调度与所有权 | 队列、租约和写入校验 |
| 工具执行不可信代码 | 独立受限环境 | 沙箱池或隔离进程/虚拟环境 |
| 多租户同时使用 | 身份、配额与数据边界 | 贯穿入口、状态、产物和工具 |
| 需要定位故障与质量 | 诊断与评测接口 | 有限Trace、指标、回归集 |

这些组件是前面机制的组合。通用MQ、限流、连接池的算法回AI Backend学习，本章只说明它们在Run、Tool和模型预算中的职责。

## 3. 一条可恢复任务路径

```text
入口校验任务与身份 → 创建可靠任务记录 → 入队
→ Worker取得执行权 → 载入状态、检查取消与未决操作
→ 编排上下文、调用模型与受控工具
→ 保存必要进度/回执 → 发布用户可见进度
→ 按验收结束 → 保留产物和必要记录
```

API/Streaming Gateway（入口/流式网关）负责请求和用户交互；Run Service（任务执行服务）管理业务生命周期；Harness Worker执行循环；Model/Tool Adapter对接能力；Durable Store（可靠存储）保留恢复事实；Trace/Eval服务诊断与质量。可以同进程实现若干责任，不要求每个框都是微服务。

用户断线可以停止这条订阅，而不取消已接受的长任务；是否取消由产品明确。重连按任务身份查状态，进度事件可补取或重新查询，不能把一次WebSocket当唯一事实。

## 4. 扩容时先找真正瓶颈

增加Worker只在瓶颈是本地执行容量时有用。若模型配额已满，更多Worker会增加排队和限流；若沙箱启动慢，应看环境池；若状态库写入过慢，盲增并发会恶化恢复保存。Capacity（容量）要分别看入口速率、活跃Run、模型并发、工具并发、队列等待与租户热点。

Backpressure（背压）让上游按下游承载能力减速，Admission control（准入控制）决定是否接受更多工作。对长任务可限制总运行数和租户预算，避免递归子Agent耗尽费用。Cost per successful task（每个成功任务成本）比单次模型单价更有解释力。

## 5. 隔离脑与手，仍要定义接口

Harness负责决策与控制，执行环境负责真正访问文件、进程和网络，可靠记录使二者可替换。拆开有助于隔离风险和独立扩容，但需要处理环境创建、产物引用、取消、超时与清理。不是把两个服务拆开就天然耐故障。

Worker A失联后B接手，必须核对旧操作和执行所有权；环境销毁不能删除唯一交付物；租户A的记忆、凭证与产物不能被B误用。版本记录只服务实际兼容与资源变化，不意味着所有事件保存全量现场。

## 6. 用一条失败时间线检查架构

```text
报告上传已成功 → Worker没来得及保存回执 → 进程重启
→ 队列重新投递 → 新Worker读取原操作ID
→ 查询下游得到已有报告 → 补齐状态 → 交付
```

如果系统没有下游查询/去重，架构图再漂亮也不能证明不会重复上传。反过来，诊断Trace暂时不可用不应使已确认的报告事实消失；关键业务状态与可采样观测仍要分开。

<summary>两个成熟产品怎样作为对照，而不是指定架构模板</summary>

Codex固定Session、工具Router、执行环境与rollout记录提供可组合的职责实例；Claude Code QueryEngine、工具目录、会话存储和取消路径也是运行支撑实例。它们告诉我们模型之外需要处理哪些实际工作，不表示你的Web服务必须照抄内部目录或默认拓扑。

部署在CLI、开发机、云沙箱或企业后端时，连接寿命、资源访问和故障承诺不同。读产品源码应先还原其环境，再提取能迁移的机制。框架具体提供哪些API与持久语义，下一章用官方接口对照。

</details>

## 面试怎么答

这些是依据本章机制设计的训练问法，不新增真人来源；先用自己的话回答，再看参考答案。

### 1. 生产Agent Backend怎么设计？

<details>
<summary>参考答案</summary>

从任务时长、恢复、并发和权限承诺出发，分清入口交互、可靠任务状态、Worker循环、模型/工具接入、执行环境与产物。长任务用任务ID和独立进度查询；关键副作用有核对依据；容量按模型、工具和存储分别控制。不是一开始把所有责任拆微服务。

</details>

### 2. 为什么断开SSE不一定取消任务？

<details>
<summary>参考答案</summary>

连接负责传输，任务生命周期由产品契约决定。已接受长任务可以继续运行，重连查询权威状态；真正取消需要明确操作并传播到执行子工作，不能把丢连接等同业务终止。

</details>

### 3. 为什么增加Worker可能更慢？

<details>
<summary>参考答案</summary>

瓶颈可能是模型配额、工具服务或存储；更多Worker增加争用、排队和重试。应看阶段容量与租户热点，用背压和准入控制，而不是只调进程数。

</details>

### 4. 怎样跨Worker恢复而不重复副作用？

<details>
<summary>参考答案</summary>

可靠保存任务身份、取消和未决操作，协调执行权，接手先核对原操作及回执，再重建环境和上下文继续。租约不自动杀死旧Worker，写入边界要防旧所有者继续提交。

</details>

## 高频易错点

| 容易混淆的说法 | 为什么不对，应怎样理解 |
|---|---|
| Production必须很多微服务 | 部署拆分依据独立扩容、隔离和故障需求。 |
| 每个Run永久绑一个容器最好 | 可能浪费资源并耦合生命周期，应按任务选择。 |
| 增加Worker能解决供应商限流 | 可能制造更大限流与重试压力。 |
| 进度流就是可靠任务状态 | 流可断开，业务状态应有适当权威存储。 |
| Trace不可用就不能知道任务成功 | 成功由业务状态与验收证据确认。 |

## 章节自测

先闭卷作答。答案不仅给结论，也解释判断依据；答不出时回到本章相应过程，不必从整套课程开头重读。

### 自测 1：短只读任务是否必须入队并建数据库？

<details>
<summary>查看参考答案</summary>

不必，只要故障和容量承诺允许简单同步实现。复杂度应由需要推导。

</details>

### 自测 2：队列重复投递会不会自动重复报告？

<details>
<summary>查看参考答案</summary>

若执行有稳定操作身份与下游幂等/核对，可避免新逻辑副作用；队列本身不保证所有业务动作只做一次。

</details>

### 自测 3：沙箱被清理，报告还应能交付吗？

<details>
<summary>查看参考答案</summary>

若产品承诺保留产物，就应在清理前转存到合适持久位置并保留授权引用，不能把唯一结果留在临时目录。

</details>

### 自测 4：多个租户共用Worker，只在Prompt写隔离够吗？

<details>
<summary>查看参考答案</summary>

不够，身份必须贯穿数据查询、凭证、工具和产物访问；模型文本不构成隔离。

</details>

### 自测 5：每次模型调用更便宜，却任务总成本更高，为什么？

<details>
<summary>查看参考答案</summary>

可能需要更多步骤、重试、工具和失败返工，应比较每成功任务成本及质量。

</details>

### 自测 6：架构图有Checkpoint、Queue和Trace，是否已证明可恢复？

<details>
<summary>查看参考答案</summary>

没有，需明确保存和外部副作用的时间线，并实际测试故障窗口。组件名存在不等于协议正确。

</details>
