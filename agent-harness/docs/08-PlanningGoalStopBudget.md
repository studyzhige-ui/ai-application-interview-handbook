# 08. 计划、ReAct 与停止：怎样让每一步朝目标推进

[← 上一章](07-ToolSideEffectCancellation.md) · [模块目录](../README.md) · [下一章 →](09-ContextAssemblyBudget.md)

> 本章要解决：计划存在哪里、怎样随观察更新、何时停止？不要把计划当作已完成事实。

## 1. 计划是未来打算，状态是现在情况

继续用文件报告：计划可以是“先读A，再查B的冲突，最后写报告”；当前情况则可能是“A已读，B无权限，报告未写”。前者告诉我们想怎么走，后者告诉我们实际走到哪里。计划只占状态的一部分，不能替代已读资料、活动工具和真实结果。

Planning（规划）可以只是模型内部选择，也可以变成显式清单。显式清单的价值是让用户与程序看见意图，便于更新和验收；代价是需要维护，不能每一步都写一份冗长计划。只有三份固定短文件时，一个简单循环已经足够。

## 2. ReAct 与先规划再执行有什么不同

ReAct（推理与行动交替）的要点不是展示模型隐藏思考，而是每次行动获得新观察后再选择下一步。Plan–Execute–Replan（规划—执行—重规划）则把相对稳定的阶段显式组织起来，两者可以组合。

| 同一任务的情况 | 较合适的控制方式 | 原因 |
|---|---|---|
| 已知三个文件都需要读 | 固定读取流程 | 无需让模型重新决定已知步骤 |
| 读A才知道缺少B中哪个证据 | 观察后选择下一步 | 后续动作取决于刚得到的信息 |
| 修改多个模块，需要阶段检查 | 显式计划加阶段性重规划 | 便于跟踪依赖和偏离目标 |

例如原计划是“读A→读B→汇总”，但B返回权限拒绝。正确的下一步不是无限重试B，而是把该步骤标成受阻，判断能否按契约部分交付或需要用户授权。**不能把“模型把任务标记完成”当成外部工作真的完成。**

## 3. 计划怎样更新，旧计划会不会一直占上下文

这里要分两个视图。程序的“当前计划”可以被新版本清单替换；会话历史中的“模型曾提出计划P1，随后调整为P2”则是已经发生的记录。二者不矛盾。更新计划通常通过一条新消息或工具调用追加到历史，程序据此更新当前视图，而不是回头改写每一条旧消息。

```text
用户任务U1
→ 模型调用更新计划(P1)
→ 工具确认
→ 读取A获得新证据
→ 模型调用更新计划(P2：B受阻，先整理A)
→ 工具确认
→ 按P2继续
```

下一个任务U2可以产生P3。程序应把它关联新任务，清楚结束或替换旧计划；不能让旧任务未完成的条目无声混入新任务。历史怎样成为下一次输入、压缩以后怎样保留当前计划，见下一章与第10章。这里先掌握“**当前视图可更新，旧消息通常追加保留**”。

## 4. 控制循环需要哪些停止理由

成功、等待和终止不是同一个按钮。

| 观察 | 应做的判断 | 对用户怎样表达 |
|---|---|---|
| 报告与引用通过验收 | 可以完成 | 交付结果及检查范围 |
| 缺关键输入或审批 | 暂停等待，而不是随机继续 | 说明需要什么 |
| 预算耗尽但未完成 | 有原因地停止 | 交付进度与未完成事项 |
| 重复行动没有新证据 | 重规划、澄清或停止 | 说明受阻原因 |
| 用户要求取消 | 停止新动作并核对在途动作 | 说明取消范围和已发生结果 |

Budget（预算）不只有`max_steps`。模型调用、工具调用、总耗时、Token（模型计费/计算单元）、金额和子任务数量可能分别约束。先选任务真正敏感的几项，不需要把所有指标都变成强制字段。

判断死循环也不能只看“同一工具调用了三次”。分页读取可以连续调用同一个工具且每次有新资料；真正值得阻断的是相同输入、相同错误、没有进度持续重复。记录最近动作摘要和无进展次数即可，不需要保存所有历史结果来做这个判断。

## 5. 防止做着做着变成另一件事

Goal drift（目标漂移）是原本只整理报告，后来因为发现格式不统一开始修改原件。防止漂移要保留目标、非目标与验收条件，在计划调整时核对，而不只是加一句“请专注”。用户新约束改变后，程序要决定生效边界；不能让正在进行的危险动作等到下一次模型调用才知道它已不被允许。

<details>
<summary>实际产品中的计划：Codex update_plan 与 Claude Code TodoWrite 并不是通用计划字段</summary>

Codex固定快照`tools/handlers/plan.rs`的`PlanHandler`注册名为`update_plan`的工具。模型提交清单参数，处理器解析后发出`PlanUpdate`事件，给模型返回简短确认。提交的清单已在工具调用记录里，不等于每次都把同一清单搬到System Prompt最前面。该快照还区分产品的Plan Mode（规划模式），其分支会拒绝这个清单工具；不能把“有update_plan”与“进入Plan Mode”混成同一能力。

Claude Code用户快照的`TodoWriteTool`在旧Todo路径启用时，读取`appState.todos[agentId或sessionId]`，更新当前清单，返回带旧/新清单的宿主数据；映射给模型的是确认文本。全部完成时当前清单可清空，但工具调用历史不会因此改写。开启Todo V2时采用另一组Task工具。另有计划文件与Plan Mode路径，`compact.ts`会在压缩后按需恢复计划附件。

因此产品里可以同时有“模型历史中的计划说明”“界面当前待办”“规划模式中的文件”。先确认你讨论哪一种，才回答它存在哪里。源码文件与所用开关决定行为，不应编造一个两产品共用的`plan`存储字段。

</details>

## 面试怎么答

这些是依据本章机制设计的训练问法，不新增真人来源；先用自己的话回答，再看参考答案。

### 1. ReAct和Plan–Execute怎么选？

<details>
<summary>参考答案</summary>

先看下一步能否事先确定。动态调查适合行动后观察再决策，复杂但有稳定阶段的任务可以显式规划并在阶段结束重规划。两者可组合。计划不代表成功，停止仍按验收、权限、预算与新观察判断。

</details>

### 2. 计划更新会不会破坏Prompt Cache？

<details>
<summary>参考答案</summary>

要区分更新当前计划视图和改写历史。常见做法把新计划作为新消息或工具调用追加到尾部，程序更新当前视图，尽量保留已有前缀；若把可变计划每轮重写在最前面则会影响前缀复用。实际还受工具集合、系统指令、压缩和供应商缓存规则影响。

</details>

### 3. 怎样检测Agent死循环？

<details>
<summary>参考答案</summary>

结合最近动作签名、相同错误和实际进展，而不是禁止重复工具。分页有新数据可以继续；反复同查询无结果应计为无进展，要求换策略、澄清或停止。总时间和费用预算兜底，但不能只加大步数掩盖循环。

</details>

### 4. 计划说done了，为什么不能直接结束？

<details>
<summary>参考答案</summary>

done首先是声明。应检查报告、引用、测试或业务回执是否满足验收；如果没有证据，状态仍未完成。程序可以拒绝完成候选并把缺口反馈给模型，或在无法推进时结束为未完成而非伪造成功。

</details>

## 高频易错点

| 容易混淆的说法 | 为什么不对，应怎样理解 |
|---|---|
| Plan等于全部State | Plan只记录未来步骤与清单状态，不包含全部活动调用、结果和授权。 |
| 新计划必须覆盖旧模型消息 | 通常追加更新事件并替换当前视图，两者分开。 |
| ReAct必须输出私有思考 | 关键是行动与观察反馈，不需要展示隐藏推理。 |
| 预算耗尽也是完成 | 它只是停止原因，应明确未完成状态。 |
| 每个Agent都需要独立Planner服务 | 简单任务可隐式规划，按任务需要选择。 |

## 章节自测

先闭卷作答。答案不仅给结论，也解释判断依据；答不出时回到本章相应过程，不必从整套课程开头重读。

### 自测 1：读B被拒绝后，计划里应改什么？

<details>
<summary>查看参考答案</summary>

把B标为受阻，并说明影响的验收条件，再选择澄清、授权或部分交付。不要把它当普通临时错误无限重试，也不能直接标完成。

</details>

### 自测 2：计划从P1改到P2，P1是否必须删除？

<details>
<summary>查看参考答案</summary>

不必。当前计划视图指向P2，历史保留P1到P2的变化；上下文过长时才选择性压缩。保留历史不代表每轮必须注入全部历史。

</details>

### 自测 3：调用同一搜索工具五次是否一定是死循环？

<details>
<summary>查看参考答案</summary>

不是。如果查询和证据不断推进，可能合理。要看无进展、重复输入和相同错误，而不是只统计工具名。

</details>

### 自测 4：多了模型规划，任务质量却不变而成本翻倍，怎么办？

<details>
<summary>查看参考答案</summary>

与确定性基线比较，在没有质量或能力收益的范围移除不必要规划。Agent化不是越多越好。

</details>

### 自测 5：用户要求只读，计划中出现修改原件，谁来阻止？

<details>
<summary>查看参考答案</summary>

模型可收到约束，但真正阻止需要工具权限和资源访问边界；规划检查及时发现问题，执行门不能依赖模型始终听话。

</details>

### 自测 6：Codex update_plan返回确认，模型还能知道清单内容吗？

<details>
<summary>查看参考答案</summary>

它刚提交的工具调用包含计划参数，历史中有这段信息；确认结果不必重复整个清单。不能从短确认推断计划丢了，也不能推断它被固定在System Prompt。

</details>
