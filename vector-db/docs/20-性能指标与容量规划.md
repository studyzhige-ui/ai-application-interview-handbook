# 20. Recall / Latency / Memory / QPS / Build Cost

Vector DB 的“性能好”不能只用一句：

> 查询很快。

真正的 Production 评估至少要同时看：

```text
Recall
Latency
QPS
Memory
Storage
Build Time
Update Cost
Filter Cost
```

---

## 1. Recall：ANN 有没有漏近邻

最基础的 ANN Recall 可以基于 Exact Ground Truth：

```text
Exact Top-K
vs
ANN Top-K
```

例如：

```text
Exact: A B C D E F G H I J
ANN:   A B C D E X F Y H I
```

找回 8/10：

```text
Recall@10 = 0.8
```

注意：

> 这只是 ANN Index 层 Recall，不等于 RAG 对“相关文档”的业务 Recall。

后者属于 RAG Evaluation。

---

# 2. Latency：不要只看 Average

至少看：

```text
P50
P95
P99
```

Vector Query 常包含：

```text
Routing
Filter
ANN Search
Shard Fan-out
Network
Merge
Payload Fetch
```

Average 可能很好，但某些：

```text
Hot Shard
High-selectivity Filter
Compaction
Cache Miss
```

会把 P99 拉高。

---

# 3. QPS 和 Latency 是一起看的

单 Query 5ms 不代表：

```text
1000 QPS 下仍然 5ms
```

随着并发增加：

```text
CPU Saturation
Memory Bandwidth
Queueing
Network
Shard Hotspot
```

都会出现。

所以 Benchmark 应画：

```text
QPS → P95/P99 Latency 曲线
```

而不是只测单线程最快值。

---

# 4. Memory 怎么估

最基础 raw vector：

```text
N × D × bytes_per_element
```

例如：

```text
100 million × 1536 × 4 bytes
≈ 614 GB
```

再加：

```text
HNSW graph
Metadata
ID
Allocator overhead
Cache
Replica
```

所以 Production Memory 常远高于 raw vector size。

---

# 5. HNSW 为什么要特别算 Graph Memory

每个节点还需要保存邻居 ID。

粗略看：

```text
N × average_degree × id_size
```

只是图边就可能很大。

再考虑：

```text
multi-layer
allocator
metadata
```

所以：

> HNSW 的高 Recall / 低延迟，经常是用额外 Memory 换来的。

---

# 6. Storage 和 Memory 不一定相同

有些系统：

```text
Vector / Index 主要 in-memory
```

有些：

```text
Disk / SSD + Cache
```

有些：

```text
Object Storage 持久化
+
Compute Node Load Index
```

所以容量规划必须知道产品架构，不能只看数据文件大小。

---

# 7. Build Cost 为什么重要

Index 构建可能需要：

```text
小时
甚至更久
```

要看：

```text
Build Throughput
CPU / GPU
Memory Peak
Temporary Storage
Network
```

如果 Index 每天都要 Rebuild，而 Build 需要 12 小时：

```text
Lifecycle 已经不可接受
```

所以 Build Time 是一等指标。

---

# 8. Update Cost

如果系统每天：

```text
新增 20%
删除 10%
```

那么只测静态 Query Benchmark 没意义。

还需要：

```text
Insert TPS
Upsert TPS
Delete Latency
Index Maintenance
Compaction Debt
Query during write
```

---

# 9. Filter Cost

同一个 ANN Index：

```text
No Filter P95 = 10ms
```

但：

```text
tenant + permission filter
```

可能变成：

```text
40ms
```

原因可能是：

```text
filter evaluation
candidate shortage
extra ANN expansion
payload index miss
```

所以必须测真实 Filter。

---

# 10. 一个容量规划模板

先收集：

```text
N = Vector Count
D = Dimension
Element Type
Metadata Size
Replica Count
Expected Growth
QPS
Filter Distribution
Recall Target
P99 SLA
Update TPS
Delete Rate
```

然后估：

```text
Raw Vector
+ Index Overhead
+ Metadata
+ Replica
+ Headroom
```

最后用真实 Benchmark 修正模型。

---

# 11. 面试怎么答

## Q：Vector DB 选型时看哪些指标？

🎯 **建议回答**：

> 我不会只看单 Query Latency。首先用 Exact Search 建 Ground Truth 测 ANN Recall，再测不同并发下的 P50/P95/P99、QPS、Memory、Index Size、Build Time 和 Update/Delete Cost；如果业务有 tenant 或 permission filter，还要测真实 Filter Selectivity。容量上先按 N×D×element size 估 raw vector，再加 ANN Index、Metadata、Replica 和 headroom。

---

# 12. 高频易错点

⚠️ **QPS 越高代表系统越快。** 必须同时看 Latency 和 Recall。

⚠️ **raw vector 大小就是内存需求。** 会严重低估。

⚠️ **Benchmark 只测 Query，不测 Build / Update。** 对动态系统不够。

⚠️ **P50 很好就代表用户体验稳定。** P99 可能很差。

---

# 13. 本章自测

<details><summary>1. 为什么 Recall、Latency、QPS 必须一起看？</summary>

因为提高搜索工作量可能提高 Recall 但降低吞吐、增加延迟；单独优化任一指标都可能牺牲其它指标。
</details>

<details><summary>2. 为什么 Vector DB 容量不能只用 N×D×4 bytes？</summary>

因为还要加 ANN Index、图边、Metadata、ID、Allocator、Cache、Replica 和运行 headroom。
</details>
