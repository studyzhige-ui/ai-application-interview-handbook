# 22. FAISS / pgvector / Elasticsearch Vector / Milvus / Qdrant 怎样选

这是冻结真人面经里 Vector DB 最强的主题之一。

但这一章不做“产品排行榜”，而是建立一个更稳定的架构判断：

> **你到底需要一个 ANN Library、关系数据库扩展、搜索引擎里的 Vector 能力，还是专用 Vector Database？**

产品能力会随版本变化，因此具体 API / 默认 Index 以官方文档为准；这里重点讲稳定边界。

---

## 1. 先分四种架构类别

```text
A. ANN Library
B. Relational DB Extension
C. Search Engine + Vector
D. Dedicated Vector DB
```

代表性例子：

```text
FAISS            → ANN Library
pgvector         → PostgreSQL Extension
Elasticsearch    → Search Engine + Vector
Milvus / Qdrant  → Dedicated Vector DB / Vector Search Engine
```

真正的选型从“类别”开始，而不是从 Logo 开始。

---

# 2. FAISS：先理解它是 Library

FAISS 是高效向量 Similarity Search / Clustering Library。

它非常适合：

```text
算法实验
离线检索
本地 / 单服务内 ANN
Exact Ground Truth
自定义 Pipeline
```

它提供大量 Index / CPU / GPU 能力，但它本身不等于一个完整 Production Database Service。

你通常仍需要自己解决：

```text
Service API
Persistence Lifecycle
Metadata / Auth
Replication
Shard Routing
Online Update
Monitoring
Backup / Recovery
Multi-tenancy
```

因此：

> **“FAISS 能搜向量”不等于“FAISS 就是完整 Vector DB”。**

官方：<https://github.com/facebookresearch/faiss>

---

# 3. pgvector：Vector 能力放进 PostgreSQL

pgvector 是 PostgreSQL 的 Vector Similarity Search Extension。

当前官方 README 明确提供：

```text
Exact Nearest Neighbor
HNSW
IVFFlat
```

它最大的架构优势不是“ANN 一定最快”，而是：

> **Vector 和关系数据可以继续处在 PostgreSQL 的 Transaction / Schema / SQL / Join 生态里。**

很适合：

```text
已有 PostgreSQL
Vector 数据规模可控
关系 Metadata 很重要
希望少引入一个独立系统
```

例如：

```text
documents
users
tenants
permissions
embedding
```

可以在一个数据库中统一管理。

要注意：

```text
ANN / Filter / Scale
```

仍然需要真实 Benchmark，不能因为“已经有 Postgres”就默认任何规模都最合适。

官方：<https://github.com/pgvector/pgvector>

---

# 4. Elasticsearch：当全文搜索本来就是核心能力

Elasticsearch 本身是搜索引擎平台，目前官方支持 `dense_vector` 和 kNN / ANN Vector Search，也支持把全文、结构化 Filter 和 Vector Search 放在同一个 Search Stack 里。

如果你的业务本来就强依赖：

```text
BM25 / Keyword Search
Analyzer
Full-text Search
Filter / Aggregation
Search Operations
+
Vector Search
```

那么 Elasticsearch Vector 往往是自然候选。

优势不是：

> “它是最纯的 Vector DB。”

而是：

> **它能把传统 Search 与 Vector Search 放在同一搜索基础设施里。**

当前官方文档也明确支持 HNSW / Quantized Vector Index 等能力，但默认策略会随版本变化，因此教材不背具体默认值。

官方：<https://www.elastic.co/docs/solutions/search/vector>

---

# 5. Milvus：专用分布式 Vector Database

Milvus 官方定位是面向大规模 Vector Similarity Search 的开源云原生 Vector Database。

当前架构文档强调：

```text
分布式
Compute / Storage Disaggregation
Scale-out
Collection / Partition
Insert / Upsert / Delete
Vector + Scalar Query
```

如果系统已经进入：

```text
大规模向量
独立 Retrieval Service
多节点扩展
Index Lifecycle
高吞吐 Ingestion
复杂 Vector Infrastructure
```

专用 Vector DB 会比“自己拼一个 ANN Library Service”省掉大量基础设施工作。

但代价是：

```text
新系统的部署
运维
资源模型
数据同步
一致性边界
```

官方：<https://milvus.io/docs>

---

# 6. Qdrant：Vector Search + Payload / Filter 是核心能力

Qdrant 是面向 Vector Search 的数据库 / Search Engine，核心数据抽象是 Vector Point + Payload。

当前官方文档特别强调：

```text
HNSW
Payload
Payload Index
Filter-aware Search
Disk / Memory Storage Options
```

如果业务高度依赖：

```text
Vector Search
+
结构化 Payload Filter
+
相对轻量的专用 Vector Service
```

它是常见候选之一。

同样不要把“某个 Benchmark 很强”直接当成项目答案，仍需带你的：

```text
Filter Distribution
Update Pattern
Dataset
SLA
```

做测试。

官方：<https://qdrant.tech/documentation/>

产品选型至少要看：

Dimension

# 8. 一个决策树

```text
只是本地 ANN / 算法实验？
├─ Yes → FAISS 类 Library
└─ No

已经深度使用 PostgreSQL，规模与 SLA 可承载？
├─ Yes → pgvector 候选
└─ No

全文 / BM25 / Analyzer / Search Platform 是核心？
├─ Yes → Elasticsearch Vector 候选
└─ No

需要独立、大规模 Vector Infrastructure？
└─ Milvus / Qdrant / 其它专用 Vector DB
   → 再按 Filter / Scale / Update / Ops Benchmark
```

这不是机械规则，而是帮助梳理主矛盾。

---

# 9. 为什么已有基础设施非常重要

理论上：

```text
专用 Vector DB 功能更多
```

但如果团队已经有：

```text
Postgres HA
Monitoring
Backup
DBA / SRE
Migration Tool
```

而数据量只有几百万：

```text
引入新 Vector DB
```

可能增加的运维复杂度大于收益。

反过来，如果：

```text
10 亿向量
1000 QPS
复杂 Filter
多租户
持续 Rebuild
```

继续把所有压力压在已有关系库，也未必合理。

---

# 10. 为什么 Benchmark 必须用自己的数据

公开 Benchmark 很有参考价值，但不能直接替代项目测试。

因为结果受：

```text
Dataset Distribution
Dimension
Metric
Filter
Top-K
Recall Target
Hardware
Index Parameters
Update Ratio
```

影响。

你的系统真正关心：

```text
在 Recall >= X 的前提下
P99 <= Y
Memory <= Z
```

而不是某个产品在陌生数据集上的最高 QPS。

# 11. 面试怎么答

## Q：Milvus、FAISS、pgvector、Elasticsearch Vector 怎么选？

🎯 **建议回答**：

> 我先按架构类别区分。FAISS 是 ANN Library，适合算法实验或自己构建 Search Service；pgvector 把 exact/HNSW/IVFFlat 放进 PostgreSQL，适合已有 Postgres、关系 Metadata 和事务能力重要、规模可控的系统；Elasticsearch 适合全文搜索、BM25、Filter 和 Vector 本来就需要在同一 Search Stack 里结合；Milvus、Qdrant 这类专用 Vector DB 更适合把 Vector Retrieval 作为独立基础设施来扩展。最终我会用自己的数据和 Filter 分布测 Recall、P99、Memory、Build、Update 和运维成本，而不是只看产品 Benchmark。

---

# 12. 高频易错点

⚠️ **FAISS = Vector Database。** 更准确地说它首先是 Similarity Search Library。

⚠️ **pgvector 只能 Exact Search。** 当前官方支持 HNSW 和 IVFFlat ANN。

⚠️ **Elasticsearch 只能 BM25，不能 ANN。** 当前官方已经提供 dense vector / kNN / HNSW 相关能力。

⚠️ **专用 Vector DB 一定比 pgvector 更好。** 取决于规模、团队和系统约束。

⚠️ **产品选型只看 QPS。** 还必须看 Recall、Filter、Update、Build、Ops 与成本。

# 13. 本章自测

<details><summary>1. FAISS 和专用 Vector DB 的核心区别是什么？</summary>

FAISS 主要提供向量检索算法 / Index Library；专用 Vector DB 还承担 Service、持久化、Schema/Metadata、分布式、更新删除、监控和生命周期等数据库能力。
</details>

<details><summary>2. 什么场景下 pgvector 是很自然的选择？</summary>

已有 PostgreSQL，向量规模和 SLA 可承载，希望把关系 Metadata、事务和 Vector Search 放在同一数据库中，并希望减少新增基础设施时。
</details>

<details><summary>3. 为什么 Elasticsearch Vector 对 Hybrid Search 场景有天然吸引力？</summary>

因为全文搜索、Analyzer、Filter 等传统 Search 能力本就在同一 Search Platform 中，Vector Search 可以与已有检索基础设施结合。完整 Hybrid Retrieval Strategy 仍在 RAG 模块学习。
</details>
