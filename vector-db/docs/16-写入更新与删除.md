# 16. Insert / Upsert / Update / Delete

Demo 里的 Vector DB 常常只有：

```text
insert
query
```

Production 一定会遇到：

```text
文档更新
Chunk 重切
权限撤销
Embedding 升级
用户删除数据
```

所以必须学习 Vector Index 怎样变化。

---

## 1. Insert：新增向量并不只是 Append

如果是 Flat Index：

```text
Append vector
```

相对直接。

但 ANN Index 可能还要：

```text
HNSW → 找邻居、建图边
IVF  → 找最近 Centroid、进入 List
PQ   → 计算 Quantized Code
```

所以 Insert Throughput 与 Index Type 相关。

---

# 2. Upsert 是什么

Upsert 通常表示：

```text
ID 不存在 → Insert
ID 已存在 → Replace / Update
```

但不同产品对：

```text
Vector Update
Metadata Update
Partial Update
```

支持方式不同。

工程上不要假设：

> 所有 Vector DB 都能像关系数据库一样任意原地 UPDATE。

---

# 3. Vector Update 为什么更复杂

如果向量从：

```text
v_old
```

变成：

```text
v_new
```

它在向量空间的位置改变了。

这意味着：

```text
HNSW 图邻居可能要变
IVF Cell 可能要变
Quantized Code 也要变
```

因此“更新一个 float 数组”实际可能是：

```text
remove old index entry
+
insert new index entry
```

具体实现依产品而定。

---

# 4. Metadata Update 和 Vector Update 要分开看

例如：

```text
permission_group 改了
```

向量本身没变。

如果产品支持 Metadata-only Update：

```text
不必重新 Embedding
```

但如果：

```text
Chunk 内容变了
```

则通常需要：

```text
重新 Embedding
→ 更新 Vector
```

所以更新 Pipeline 应先判断：

```text
Content Changed?
Metadata Only?
Embedding Contract Changed?
```

---

# 5. Delete 为什么可能不是立刻物理删除

ANN Index 内部有复杂结构。

如果每次 Delete 都立即：

```text
重排所有结构
```

成本可能很高。

所以很多系统会采用：

```text
Logical Delete / Tombstone
```

Query 时跳过已删除记录，后台再：

```text
Compaction / Rebuild
```

真正回收空间。

具体实现随产品不同，但这个生命周期思想非常普遍。

---

# 6. Delete 必须有业务 Source Mapping

假设用户要求删除：

```text
doc_1001
```

Vector DB 中可能有：

```text
chunk_1001_0
chunk_1001_1
...
chunk_1001_80
```

如果只保存了随机 Vector ID，没有 `doc_id`：

```text
很难准确删完
```

所以前面的 Metadata / Primary Key Design 会直接影响删除能力。

---

# 7. 文档更新的两种常见策略

## 7.1 In-place Version Replacement

```text
找到旧 chunks
→ delete / upsert
→ 写入新 chunks
```

优点：

```text
简单
```

风险：

```text
更新过程中可能出现旧新混合
```

## 7.2 Versioned Write + Switch

```text
旧 version=v1 保留
新 version=v2 完整写入
→ validation
→ current_version 切换
→ 后台清理 v1
```

优点：

```text
更容易原子切换 / rollback
```

代价：

```text
临时双份存储
```

---

# 8. Upsert 并不自动解决并发一致性

两个 Worker 同时更新同一文档：

```text
Worker A → version 7
Worker B → version 8
```

如果 B 先写完，A 后写完：

```text
旧版本可能覆盖新版本
```

需要：

```text
version check
idempotency key
job generation
source-of-truth state
```

这些是 Backend Reliability 与 Vector Lifecycle 的交叉问题。

---

# 9. Delete 后为什么仍可能“搜到旧数据”

可能原因：

```text
异步删除未生效
Replica 延迟
Cache 未失效
Old Index 仍被 Query
Version Filter 缺失
Compaction 尚未物理清理
```

所以删除验证不能只看：

```text
Delete API 返回 200
```

还要验证：

```text
Query path
Index generation
Replica
Cache
```

---

# 10. 面试怎么答

## Q：Vector DB 的 Update / Delete 有什么特殊？

🎯 **建议回答**：

> Vector 不是普通字段，因为它还参与 ANN Index。Vector Update 可能意味着图邻接、IVF Cell 或 Quantized Code 都要变化，所以很多实现本质上接近删除旧索引项再插入新项。Delete 也可能先做 logical tombstone，再由后台 compaction 或 rebuild 回收。Production 里我会保留 doc_id、content_version、embedding_version 等映射，确保能准确更新和删除整批 Chunk。

---

# 11. 高频易错点

⚠️ **Upsert 就一定是原地修改 Index。** 取决于产品和 Index。

⚠️ **Delete 成功就代表磁盘空间立即释放。** 不一定。

⚠️ **只要 ID 唯一就不需要 Version。** 并发更新与模型升级仍需要版本治理。

# 12. 本章自测

<details><summary>1. 为什么 Vector Update 可能比 Metadata Update 重很多？</summary>

因为 Vector 的空间位置改变，会影响 ANN 索引结构；Metadata-only Update 未必需要重新定位向量。
</details>

<details><summary>2. 为什么 Versioned Write + Switch 更容易回滚？</summary>

因为旧版本仍完整保留，新版本验证成功后只需切换 current version；失败时可以继续使用旧版本。
</details>
