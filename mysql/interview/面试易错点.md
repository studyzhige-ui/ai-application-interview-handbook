# MySQL 面试易错点

> 这份文档不是“技巧集”，而是专门清理最容易在面试里说错的过度简化。

---

## 1. “有索引就一定走索引”

错误。

Optimizer 会根据统计信息和成本估算选择访问路径。小表、低选择性条件、需要大量回表等情况下，全表扫描可能更便宜。

---

## 2. “没走索引 = 索引失效”

不准确。

要区分：

```text
条件无法有效构造 Index Range
vs
Index 可用但 Optimizer 认为成本更高
```

---

## 3. “联合索引遇到范围条件，右边列全部失效”

过度简化。

右侧列可能不能继续缩小同一个 Range，但仍可能参与 ICP、覆盖、排序等。分析要区分不同阶段。

---

## 4. “B+Tree 三层就一定只做三次磁盘 I/O”

错误。

树高取决于数据量、Key 大小、Page Fill 等；上层 Page 还可能已经在 Buffer Pool。不要把示意图当固定物理事实。

---

## 5. “覆盖索引是一种特殊索引类型”

不准确。

Covering 描述的是某个 Query 的所需列是否都能从当前索引获取，是 Query 与 Index 的关系。

---

## 6. “ICP = 不回表”

错误。

ICP 是尽量先在 Index Record 上过滤，再决定是否读取完整行；如果查询列不被覆盖，最终仍可能回表。

---

## 7. “UUID 不能做 MySQL 主键”

错误。

它可以做，只是随机、较长的聚簇主键会带来 Page Split、局部性差、Secondary Index 变宽等成本。要说 Trade-off，不要说禁止。

---

## 8. “Consistency 就是某一个 Log 保证的”

错误。

ACID 的 Consistency 是数据不变量目标，依赖 Atomicity / Isolation / Durability、Schema Constraint 和正确业务逻辑共同维持。

---

## 9. “事务 = 并发安全”

错误。

`BEGIN/COMMIT` 只定义事务边界。并发安全还要看 Isolation、Lock、SQL Pattern、Conditional Update、业务 Unique Constraint 等。

---

## 10. “RR 的所有读取都看同一个旧快照”

错误。

普通 Consistent Read 和 Locking Read / DML 语义不同。`SELECT ... FOR UPDATE` 不能用一句“只看旧 Snapshot”解释。

---

## 11. “MVCC 完全解决幻读”

过度简化。

普通一致性读依赖 Snapshot；锁定读和范围更新还需要 Record / Gap / Next-Key Lock 等机制。

---

## 12. “ReadView 在 BEGIN 时一定创建”

不要机械这么说。

ReadView 与 Consistent Read 的实际建立 / 使用语义有关，不能简单等同事务开始语句。

---

## 13. “Undo 只用于回滚”

错误。

Undo 同时为 MVCC 历史版本提供信息。

---

## 14. “有 MVCC 就不需要锁”

错误。

MVCC 主要处理普通一致性读的版本可见性；Writer-Writer、Locking Read、范围操作仍需要锁。

---

## 15. “InnoDB 行锁就是直接锁物理 Row”

不够准确。

InnoDB 的行级锁围绕 Index Record 实现，因此访问路径和索引设计会影响锁范围。

---

## 16. “RR 下所有 SELECT 都有 Gap Lock”

错误。

普通 Consistent Read 通常是非锁定 MVCC 读。Gap / Next-Key Lock 主要需要结合 Locking Read / DML 和访问条件讨论。

---

## 17. “Deadlock 说明数据库设计失败”

错误。

多事务、多资源加锁天然可能出现循环等待。正确做法是降低概率、让数据库检测并 Rollback Victim，以及让应用安全 Retry。

---

## 18. “Redo 用于回滚”

错误。

Rollback 关键依赖 Undo；Redo 主要用于 WAL / Crash Recovery / Durability。

---

## 19. “Binlog 是 InnoDB 日志”

错误。

Binlog 是 MySQL Server 层日志；Redo / Undo 属于 InnoDB 事务与存储机制。

---

## 20. “COMMIT 成功 = 所有 Data Page 已刷到最终数据文件”

错误。

WAL 允许先保证恢复所需 Redo 的持久化，再后台逐步 Flush Dirty Page。

---

## 21. “MySQL 内部 2PC 解决 MySQL + Redis 一致性”

错误。

内部两阶段提交主要协调 InnoDB / Redo 与 Binary Log；Redis、MQ、外部 API 不在这个本地提交协议里。

---

## 22. “LIMIT 20 只扫描 20 行”

错误。

`OFFSET 100000 LIMIT 20` 可能需要先找到并跳过大量前置记录。

---

## 23. “所有分页都应该改 Cursor”

错误。

小数据、浅分页、后台管理页面使用 OFFSET 完全合理。Seek / Cursor 解决的是深分页和连续浏览的成本问题。

---

## 24. “Schema 越规范化越好”

错误。

Normalization 让数据关系更清晰，但某些读路径可以通过受控冗余、Read Model、Cache 换性能。关键是明确一致性维护成本。

---

## 25. “JSON 灵活，所以 AI 数据都存 JSON”

错误。

需要约束、索引、排序、事务和统计的核心业务字段更适合关系列；JSON 更适合变化快的扩展属性。

---

## 26. “Replication = Backup”

错误。

误删也会复制。Backup / PITR / Delayed Replica 与 Replication 解决不同风险。

---

## 27. “有 Replica 就高可用”

错误。

还需要 Failure Detection、Promotion、Fencing、Routing、Topology Management。

---

## 28. “所有 SELECT 都读 Replica”

错误。

Read-after-write、余额、权限等需要新鲜数据的请求可能必须读 Source 或等待 Replica 追上。

---

## 29. “Sharding = `hash(key) % N`”

远远不够。

真正困难的是：

```text
Sharding Key
Hot Shard
Cross-shard Query
Global Unique
Transaction
Re-sharding
Migration
```

---

## 30. “数据量大就应该 Sharding”

错误。

先做 Schema / Index / Archive / Read Replica / Scale-up。Sharding 是确认单节点瓶颈后的复杂度交换。

---

## 31. “CDC 天然 Exactly-once”

错误。

Consumer 应按重复事件、Crash Recovery、Offset / Checkpoint 设计 Idempotency。

---

## 32. “MySQL Commit = Elasticsearch / Vector DB 已同步”

错误。

CDC 通常是 Eventual Consistency，要显式管理 Lag 和 `PROCESSING / READY / FAILED` 状态。

---

## 33. “Batch 越大写得越快”

错误。

超大 Transaction 会放大 Undo、Redo/Binlog、Rollback、Lock 和 Replica Lag。Batch Size 要 Benchmark。

---

## 34. “MySQL、Redis、Vector DB 选一个最强的就行”

错误。

它们解决不同的数据模型：

```text
MySQL → Business Truth / Transaction
Redis → Cache / Session / Ephemeral State
Vector DB → Semantic Index
```

---

## 35. “Cache Aside 保证强一致”

错误。

仍有并发回填旧值、删除失败等窗口，通常追求可控最终一致。

---

## 36. “延迟双删 = 一致性问题终结”

错误。

它只是降低某些 Race Window，还要考虑第二次删除失败、延迟参数、Crash、TTL 和补偿。

---

# 最后一个原则

面试遇到绝对化句子时，先警惕：

```text
一定
永远
完全
所有
从不
```

数据库机制几乎总需要加上：

```text
在什么 Isolation？
什么 Index？
什么 Query？
什么版本？
什么 Workload？
什么 Consistency Requirement？
```

这正是“理解原理”和“背八股”的分界线。
