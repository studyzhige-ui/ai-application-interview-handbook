## 一、索引与查询

### 1. 为什么 InnoDB 索引使用 B+Tree？【13 sources】

<details>
<summary>30 秒回答</summary>

B+Tree 更适合页式存储和磁盘 / SSD 访问：扇出大、树高低，内部节点主要保存 Key 和 Pointer，因此同样数据量下需要更少 Page Access；叶子按 Key 有序并串联，点查、范围查询和排序都很友好。相比红黑树，它显著降低树高；相比 Hash，它又支持范围扫描和有序访问。

</details>

### 2. 聚簇索引和二级索引有什么区别？【3 sources】

<details>
<summary>30 秒回答</summary>

InnoDB 聚簇索引叶子保存完整行，表数据本身按聚簇索引组织；二级索引叶子通常保存二级索引 Key 加 Primary Key。通过二级索引查询非覆盖列时，先定位 Primary Key，再回聚簇索引取完整 Row，这就是回表。

</details>

**继续追问：** 没显式主键怎么办？为什么随机 UUID 会影响所有 Secondary Index？

---

### 3. 联合索引怎样工作？最左前缀是什么？【10 sources】

<details>
<summary>30 秒回答</summary>

联合索引 `(a,b,c)` 是按 `a→b→c` 的字典序组织，不是三棵独立索引。因此能高效利用的访问路径取决于能否先确定左侧排序前缀。不要把它背成“遇到范围后后面列全部失效”；要区分 Range Construction、后续列是否用于 Index Condition Pushdown、是否覆盖以及排序能否利用。

</details>

**继续追问：** `a=1 AND b>10 AND c=3` 怎么走？`ORDER BY b,c` 能否利用？

### 4. 什么是回表、覆盖索引和 ICP？【8 sources】

<details>
<summary>30 秒回答</summary>

二级索引找到 Primary Key 后，如果查询列不在当前索引里，需要回聚簇索引取完整行，这叫回表。查询所需列都能从索引取得时可以形成 Covering Query，减少回表。ICP 则是在存储引擎拿到索引记录后，先用能够在索引中判断的条件过滤，再决定是否读取完整行，从而减少不必要回表。

</details>

### 5. 哪些情况会让 Optimizer 不使用索引？【11 sources】

<details>
<summary>30 秒回答</summary>

要分两类：一类是访问条件本身难以构造有效索引范围，例如对索引列做不合适函数、隐式类型转换、前导 `%` LIKE 等；另一类是索引明明可用，但 Optimizer 根据统计信息和成本估算认为全表扫描更便宜。不能把“不走索引”全部叫索引失效。

</details>

**继续追问：** `OR` 一定不走索引吗？小表为什么可能全表扫？怎么用 EXPLAIN 验证？

### 6. Slow SQL 怎么定位？【11 sources】

<details>
<summary>30 秒回答</summary>

先确认真正的慢 SQL 和执行时间分布，再用 `EXPLAIN` / `EXPLAIN ANALYZE` 看 Access Type、使用哪个 Index、估算 Rows、实际 Rows、Join 顺序、Extra、是否 filesort / temporary；结合表统计、数据分布和业务参数定位是扫描过多、回表过多、排序、Join、锁等待还是下游问题。优化后要重新测真实 P95 / P99，而不是只看“用了索引”。

</details>

---

### 7. 为什么 UUID 不适合作为 InnoDB 聚簇主键的常见默认选择？【3 sources】

<details>
<summary>30 秒回答</summary>

随机、较长的 Primary Key 会让聚簇索引插入位置分散，更容易 Page Split、降低局部性，同时 Primary Key 还会出现在所有 Secondary Index 叶子中，因此主键越长，二级索引也越大。不是说 UUID 永远不能用，而是要理解它作为 Clustered PK 的空间和写入成本。

</details>

## 二、事务 / MVCC / 锁

### 8. ACID 分别是什么，InnoDB 怎样支持？【4 sources】

<details>
<summary>30 秒回答</summary>

Atomicity 表示事务整体提交或回滚，Undo 等机制参与；Isolation 由隔离级别、MVCC 和 Lock 协作；Durability 主要依赖 Redo / WAL 与 Crash Recovery；Consistency 是最终业务和数据约束目标，不应机械对应某一个日志，它依赖 A/I/D、Constraint 和正确应用逻辑共同维护。

</details>

---

### 9. 四种事务隔离级别怎么比较？【14 sources】

<details>
<summary>30 秒回答</summary>

InnoDB 支持 RU、RC、RR、SERIALIZABLE，默认 RR。RU 可能脏读；RC 的每次普通一致性读取可建立新的已提交快照，因此可能不可重复读；RR 的普通一致性读通常在同事务保持同一 Snapshot，提供可重复读取；SERIALIZABLE 更积极使用锁，隔离更强但并发更低。分析 RR 还必须区分快照读和锁定读。

</details>

---

### 10. MVCC 是什么？【9 sources】

<details>
<summary>30 秒回答</summary>

MVCC 是多版本并发控制。InnoDB 修改记录时保留 Undo 历史版本信息，普通一致性读通过 ReadView 判断当前版本是否可见；不可见就沿 Undo 找更老的可见版本。这样很多 Reader 不必与 Writer 互相加行锁，提高读写并发。RC / RR 的一个关键差异就是 ReadView 生命周期。

</details>

**继续追问：** Undo 只用于回滚吗？长事务为什么影响 Purge？MVCC 能避免 Lost Update 吗？

---

### 11. RR 是否解决幻读？【6 sources 相关锁信号】

<details>
<summary>30 秒回答</summary>

要区分读类型。普通 Consistent Read 在同一 ReadView 下可以通过 MVCC Snapshot 保持结果集合稳定；`SELECT ... FOR UPDATE`、UPDATE、DELETE 等锁定读 / 范围修改要依赖 Record / Gap / Next-Key Lock 控制并发插入。因此“RR 通过 MVCC 完全解决幻读”过度简化。

</details>

---

### 12. Record Lock、Gap Lock、Next-Key Lock 区别？【6 sources】

<details>
<summary>30 秒回答</summary>

Record Lock 保护已有索引记录；Gap Lock 保护索引记录之间的间隙，主要限制向范围插入；Next-Key Lock 可理解为记录锁和相邻 Gap 的组合。具体锁多少范围要结合 Isolation Level、Index、查询条件、实际 Access Path 和 Statement Type，不能只看 SQL 文本。

</details>

---

### 13. Deadlock 怎么产生、怎么解决？【1 direct source，体系必会】

<details>
<summary>30 秒回答</summary>

多个事务持有不同资源并形成循环等待就产生 Deadlock。InnoDB 会检测等待环并回滚一个 victim。工程上要通过统一资源访问顺序、缩短事务、建立合适索引减少锁范围、避免不必要 `FOR UPDATE` 降低概率，同时让应用把 Deadlock 作为可 Retry 的事务失败处理。

</details>

## 三、日志 / 恢复 / 复制

### 14. redo、undo、binlog 区别？【5 sources】

<details>
<summary>30 秒回答</summary>

Undo 主要用于 Rollback 和 MVCC 历史版本；Redo 是 InnoDB 的 WAL / Crash Recovery 基础，让已提交修改即使数据页尚未刷盘也能恢复；Binlog 是 MySQL Server 层的数据库变化事件，主要用于 Replication、PITR 和 CDC。它们职责不同，但事务提交时 Redo 和 Binlog 需要协调。

</details>

---

### 15. 为什么需要 redo / binlog 两阶段提交？【1 direct source，体系必会】

<details>
<summary>30 秒回答</summary>

因为 InnoDB Redo 和 Server 层 Binlog 是两套状态。如果本地事务已经提交但 Binlog 没有，或 Binlog 有记录而 InnoDB 最终回滚，都会造成本地数据与复制日志不一致。内部 Prepare → Binlog → Commit 协调二者，让 Crash Recovery 能判断 Prepared Transaction 应完成提交还是回滚。

</details>

---

### 16. MySQL Source / Replica 复制怎么工作？【3 sources】

<details>
<summary>30 秒回答</summary>

Source 把数据库变化写入 Binlog，Replica 获取并重放这些 Event 来维护副本。常见复制是异步的，因此 Source 已提交时 Replica 可能还没有 Apply，产生 Replication Lag。读写分离必须根据一致性要求决定哪些读能走 Replica，尤其要处理 Read-after-write。

</details>

## 四、Scale / Production

### 17. `LIMIT 100000,20` 为什么慢？【4 sources】

<details>
<summary>30 秒回答</summary>

LIMIT 只限制最终返回行数，大 OFFSET 仍需要定位并跳过大量前置结果，如果还伴随回表或 filesort 成本更高。可以通过覆盖索引降低跳过阶段开销，更根本的方案是 Keyset / Seek Pagination，根据上一页最后一个稳定排序 Key 继续扫描。

</details>

---

### 18. 什么时候需要 Sharding？【10 sources】

<details>
<summary>30 秒回答</summary>

不会一开始就分库分表。先通过 Schema / Index、读写分离、归档和单机扩容解决问题；当单实例存储、写吞吐、单表维护或恢复成本成为真实瓶颈时才考虑 Sharding。之后核心问题是 Sharding Key、数据和流量倾斜、Hot Shard、跨分片 Query / Pagination、Global Unique、Transaction 和 Re-sharding。

</details>

---

### 19. Sharding Key 怎么选？

<details>
<summary>30 秒回答</summary>

根据主要访问路径、强事务边界以及数据 / 流量分布选。希望高频查询尽量单 Shard、强关联数据尽量共置，同时避免某些大 Tenant / Hot Key 集中到一个 Shard。Sharding Key 是业务建模决策，不只是 `hash % N`。

</details>

---

### 20. CDC 是什么？【4 sources】

<details>
<summary>30 秒回答</summary>

CDC 用于捕获数据库已提交的数据变化并同步给下游。MySQL 常从 Binlog 捕获事件，再送到 Kafka、Search、Analytics 或 Vector Index Pipeline。真正难点包括重复事件、顺序、Schema Evolution、全量 Snapshot + 增量切换、Lag、Replay 和 Consumer 幂等。

</details>

---

### 21. 一亿条数据怎么快速写 MySQL？【1 direct source，工程体系必会】

<details>
<summary>30 秒回答</summary>

先区分新表离线导入还是在线表。使用 Multi-row Insert / LOAD DATA 减少 Round Trip，合理 Batch 和 Transaction Size 降低 Commit 成本又避免超大事务；检查二级索引、随机主键、Redo/Binlog 和磁盘 Flush；同时观察 Replica Lag，并让 Pipeline 具备 Checkpoint、Idempotency、Retry 与 Backpressure。最终通过 Benchmark 找可持续吞吐。

</details>

## 五、AI Application 数据层

### 22. Agent 项目为什么同时需要 MySQL、Redis、Vector DB？

<details>
<summary>30 秒回答</summary>

MySQL 负责需要事务、约束、长期持久化和审计的结构化业务事实，例如 User、Tenant、Conversation、Agent Run 和 Document Lifecycle；Redis 适合 Cache、Session、Rate Limit 和短期 Runtime State；Vector DB 负责 Embedding 和语义检索索引。通常 MySQL 是业务 Source of Truth，向量索引应该可以由文档和版本重新构建。

</details>

---

### 23. MySQL + Redis 怎样保持一致？【20 sources，Primary 在 Backend】

<details>
<summary>30 秒回答</summary>

通常先明确 MySQL 是 Source of Truth，Redis 是可重建 Cache，目标是可控的最终一致。Cache Aside 常在写时先提交 MySQL 再删除 Cache，读时 Cache Miss 回源并重建。仍有并发回填旧值、删除失败等 Failure Window，因此结合 TTL、Retry、Outbox / MQ 或 Binlog CDC 做异步 Invalidation，并用幂等与监控控制 Stale Window；权限、余额等高风险数据需要更严格策略。

</details>

---

### 24. 如何设计 Agent Run / Tool Execution 表？

<details>
<summary>30 秒回答</summary>

我会区分 Current State 与 Historical Event。`agent_runs` 保存 Run 当前状态和高频查询字段，`agent_steps` / `tool_executions` 保存逐步执行历史、Tool Side Effect、Approval、Error 和 Trace；大 Payload 可以只在 MySQL 保 Metadata / URI，原文放 Object Storage。根据 Tenant、Run、时间等访问模式建立联合索引，并用业务 Unique Key 支持幂等。

</details>
