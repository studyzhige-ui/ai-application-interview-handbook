# 09｜AI Coding：从可复现失败到可验证交付

[← 上一章：在线笔试](08-online-assessment.md) · [Coding 首页](../README.md) · [实作项目](../exercises/09-ai-coding-lab/README.md)


需求只有一句：“第一页的数据不对，帮忙修一下。”你还不知道哪个文件负责分页，也不知道是参数、计算还是测试出了问题。AI 可以立刻写出一版分页函数，但它怎样知道这版函数符合原项目的约定？

**工程型 AI Coding 的难点，不只是生成代码，而是确定应该改什么，以及怎样证明改对了。** 本章用一个很小的分页项目练这件事：先复现问题，再沿调用找到原因，完成最小修改，最后用测试与代码差异验收。

## 1. 工程任务比函数题多了哪些责任

算法题通常已经告诉你函数名、参数和要返回什么。工程任务不一定给这么完整的起点：你需要找到入口，读懂已有行为，再判断哪些行为是缺陷、哪些必须保持。

因此，调查不是写代码前的拖延。它是在减少一种常见风险：新函数本身看起来正确，却接错了接口，或者破坏了原来正常的调用。

如果看不懂函数输入与返回、容器变化、节点或类、模块导入、Traceback 和测试预期，生成更多代码只会增加需要审查的未知内容。本章前置知识来自第 01–08 章；Git 的具体操作可回[Git 与 GitHub Desktop](../../tooling/git-github-desktop-guide.md)，不在算法章夹带一套版本控制教程。

## 2. 先把需求改写成可验证条件

本章实作是一个三文件分页小项目，不需要账号、网络或第三方依赖。完整题面、初始代码、测试与折叠参考实现放在[练习目录](../exercises/09-ai-coding-lab/README.md)。初始实现故意有缺陷，测试失败是练习的起点。

先用一组看得见的数据解释需求。items 是 `[10,20,30]`，每页 2 项时，第一页应是 `[10,20]`，第二页是 `[30]`，第三页已经没有数据，应返回 `[]`。

再把容易产生分歧的地方说清楚：页码从 1 开始，page 必须为正整数；page_size 默认 2，允许 1～5 的整数；非法参数抛 ValueError；不修改原列表，返回新列表。这样，“修好了”就有了可核对的依据。

这比“给 API 增加 page_size 限制”更明确。真实 API 还需确认默认值、最小最大值、错误响应、兼容性、权限与已有调用方，不能让 AI 自行猜测。验收条件应来自任务或已有契约，不是从当前实现反推“它怎样做都算对”。

## 3. 调查仓库：从入口沿数据流阅读

练习文件关系是：

```text
README.md                 任务契约、运行方法、折叠参考实现
pagination.py             paginate 的当前实现
test_pagination.py       调用 paginate，检查正常与失败行为
```

不必先把整个仓库每个文件都读完。先顺着一个失败输入走：测试怎样调用 paginate，传入了什么，paginate 怎样计算 start，又返回了哪一段列表。这个具体路径，比没有目标地浏览目录更容易建立理解。

大仓库里也一样：README 与依赖配置帮助确认运行方式，入口和调用方帮助确认数据从哪里来，测试帮助确认原来的行为要求。搜索得到文件名只是起点，仍要读上下文。

给 AI 的调查请求可以是：“先不修改。定位分页入口、实现、调用方和测试，说明当前行为与契约差在哪里，列出仍未验证的假设。”收到路径后仍要读实际代码，不能把模型猜测当作仓库事实。

## 4. 先运行现状，再解释失败

在练习目录执行下面命令；`-m` 表示把后面的模块当作程序运行，unittest 是 Python 标准库测试框架，discover 寻找测试，-v 显示每个测试名。

```bash
python -m unittest discover -v
```

测试文件中的 `class PaginationTests(unittest.TestCase)` 是继承测试框架提供的测试类。方法名以 test_ 开头便于发现；self.assertEqual 比较实际与预期，self.assertRaises 检查给定调用是否抛指定异常。它们是测试框架的方法，不是新的分页算法。

先挑一个最容易解释的失败，不要一次修所有现象。默认第一页却没拿到 `[10,20]`，就沿着 page=1、page_size=2 进入函数：初始代码把 start 算成 `1*2=2`，于是跳过了前两项。

这时问题已经不是“分页好像坏了”，而是“从 1 开始的页码，被直接当成从 0 开始的块编号”。另一个测试若发现非法 page_size 没有报错，则是校验缺失，不是同一处下标计算能顺带解决的。

第 01 章 Traceback 的读法在这里继续适用：直接失败的行只是起点，错误输入可能来自上游。长日志有多个异常块时分别理解。真实测试出现“expected 400, got 500”是行为不匹配的线索，不代表只把状态码改成 400 就完成修复。

## 5. 最小修改：先修正确性，再考虑结构变化

先修刚才已经确认的偏移：第一页应跳过 0 项，第二页跳过 page_size 项，因此 start 应与 `page-1` 对应。

```diff
- start = page * page_size
+ start = (page - 1) * page_size
```

这只修了位置计算，不代表整个需求完成。还要按约定校验页码和每页大小，并验证空数据、末页、越界页与原输入不变。把这些改动围绕同一个任务组织起来，不需要顺手更换框架或重写无关目录。

主动抛异常使用 raise；它与 assert 不同，是函数对非法调用的公开行为，不能用可能被优化选项关闭的 assert 代替生产参数校验。

```python
def checked_size(value):
    if type(value) is not int or not 1 <= value <= 5:
        raise ValueError("page_size must be an integer from 1 to 5")
    return value

assert checked_size(2) == 2
try:
    checked_size(0)
except ValueError as error:
    assert "page_size" in str(error)
else:
    raise AssertionError("应当拒绝 0")
```

except 后的 as error 把异常对象交给局部名字；else 表示 try 没发生异常才执行。本例把类型校验放在数值比较之前，依靠 or 短路，避免对字符串等错误类型直接比较。bool 虽然与整数有关系，但本练习契约只接受 type(...) 为 int 的普通整数。

让 AI 按计划实现时，明确哪些公开行为不可改变，哪些测试必须保留。涉及多个文件时也应组成一个逻辑一致的修改，不是一边产生互不兼容的版本，一边让测试替你猜最终意图。

## 6. 验证：命令、结果和覆盖范围都要真实

先重跑原先失败的测试，确认它在没有削弱断言的情况下变绿；再跑相关回归，检查默认行为、最小与最大合法值、非法值、空数据、末页和越界页。通过有限测试仍不代表所有输入已经证明正确，需要结合契约与实现解释。

“看起来应该通过”是静态判断；真正运行过且退出码为 0 才是该次测试通过。AI 没有运行环境时必须说明未运行，不能把预测包装成证据。仓库级完整检查、线上行为与某个单元测试也是不同验证范围，不能互相替代。

本例的初始测试本来就应失败，修复后才应全部通过。参考答案保存在 Markdown 折叠中，不会自动覆盖你的代码；应先独立修改，再与参考实现比较。

## 7. Review：看真实差异，不只看 AI 的总结

差异 diff 表示修改前后哪些行变化。检查文件是否都属于任务、公开接口是否保持、依赖是否无故增加、错误是否被吞掉、测试是否验证需求而非迎合实现。模型声称“只改参数校验”，不等于它真的没有删除别的逻辑。

至少从正确性、范围、复杂度、异常处理、安全与测试六个角度检查。安全方面关注硬编码密钥、未经约束的 SQL/shell 执行、权限扩大和输入泄漏；本练习没有这些外部行为，不能因此推断真实服务无需检查。

对分页例子，切片返回的是新外层列表，内部可变对象仍可能共享；不要宣称它完成了深拷贝。检查实现是否与题面要求一致，而不是额外添加没有被要求的复杂复制。

## 8. 与 AI 协作的阶段怎样衔接

调查时，可以问：“先不修改，追踪默认第一页的调用，告诉我实际值与预期从哪一步开始不同。”这比“帮我修一下”更容易得到可核对的信息。

确认 start 的问题以后，再要求按已知契约修改并运行测试。测试仍失败时，把实际失败名、输入和输出交回去，而不是只重复“继续修”。最后切换到审查：停止增加代码，检查差异有没有超出任务，测试是否被削弱，原有调用是否仍然成立。

这一流程不是一组越长越好的万能提示词，而是使每一步有输入、有产物、有验证。复杂任务可以分成局部可验证步骤，但不能把“测试正在运行”或“代码已生成”当作任务完成。也不能因为一个不相关检查失败，就不说明范围地宣布全部修改失败。

## 9. 从小任务走向陌生仓库

先完成单文件缺陷，再增加参数校验或输出格式等小功能，再追跨文件调用，再进入只给需求不告诉修改点的陌生仓库，最后练限时的完整调查、实现、测试与交付。每一级增加一种责任，避免第一天同时面对大框架、业务、依赖和 AI 生成代码。

外部实践入口保留[牛客 AI 新题型](https://www.nowcoder.com/exam/oj?page=1&tab=AI%E6%96%B0%E9%A2%98%E5%9E%8B%E7%AF%87&topicId=-9001)与 [AI Coding 题库](https://www.nowcoder.com/problem/aicoding/?channelPut=www_oj_aicoding)。平台界面、题量与规则以实际页面为准，本课程不据此宣称任何固定招聘形式。

练后记录第一次让 AI 做了什么、哪个假设错了、如何发现、哪个测试证明了行为、最终差异有无无关内容，以及没有 AI 时自己能否读懂实现。评分不是唯一反馈。

## 10. 本章小结与面试怎么答

从一行代码到一个工程任务，核心习惯没有改变：先确定输入和期望，再恢复真实执行过程，依据证据修改。AI 能加快调查与实现，但最终仍要读它改了什么、运行了什么、还有什么没有验证。

**问：你怎样判断 AI 生成的代码真的完成了任务？**

> 🎯 我会先对齐验收条件，复现原问题，再检查修改是否只影响必要范围。修复后重跑失败测试和相关回归，审查实际 diff，并明确报告验证范围。代码已生成、模型说应该通过，都不等于完成。

## 11. ⚠️ 容易混淆的地方

- 测试变绿不一定是实现修好了，也可能是断言被删除或改弱；需要同时看测试差异。
- 报错不再出现，不代表异常被正确处理；吞掉异常可能只是把问题藏起来。
- 新列表不等于深拷贝。分页切片保留新的外层，但内部可变对象仍可能共享。
- 一组单元测试通过，只证明该次运行与覆盖范围，不等于仓库全部检查或线上行为都已验证。

## 12. 章节自测与实作验收

**实践任务：** 完成配套分页项目。交付应包含修改后的函数、实际执行的测试结果，以及一段解释：缺陷如何产生，修改为什么正确，哪些边界已验证，哪些验证没有执行。

<details><summary>查看验收要点</summary>

第一页从下标 0 开始，start 应与 page-1 对应；校验先于运算；page_size 上界和类型按契约处理；切片允许超过末尾得到 []；原列表不应被修改。保留初始测试并补充你发现的边界，而不是删除失败测试。

</details>

<details><summary>为什么只改 start 的公式，还不能宣布分页修复完成？</summary>

它只覆盖页码与下标的对应关系。非法参数是否按约定报错、原输入是否保持、空数据与越界页如何返回，仍要分别核对。修复一个已知现象，不等于所有验收条件自动成立。

</details>
