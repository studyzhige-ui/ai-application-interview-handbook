# 09｜AI Coding：AI 可以写代码，但你仍然负责把任务交付

[← 上一章：Online Assessment](08-online-assessment.md) · [Coding 首页](../README.md) · [Hot100 Map](../hot100-map.md)

> 传统算法题通常给你一个清晰的问题和函数；AI Coding 更接近真实开发：**给你需求、Bug 或陌生代码库，你需要借助 AI 理解上下文、找到修改点、完成实现、运行测试、Debug，并验证最终结果。**

截至 2026-09-18，牛客已经提供 AI Coding 相关题库 / 新题型入口；其公开赛事说明也把技术赛道描述为围绕真实开发任务，借助 AI 完成需求理解、方案、代码修改、调试测试并提交可运行结果。外部平台会持续变化，本章只抽取稳定能力，不依赖某一版 UI。

---

## 1. AI Coding 和 Hot100 到底差在哪里

Hot100 更像：

```text
一个明确问题
→ 选择算法
→ 写一个函数
→ Judge
```

AI Coding 更像：

```text
需求 / Bug / TODO
↓
陌生 repository
↓
找到相关文件
↓
理解已有设计
↓
决定最小改动
↓
让 AI 协助实现
↓
运行测试 / 程序
↓
读失败
↓
继续修改
↓
人工验收
```

所以 AI Coding 不是“Prompt Engineering 替代编程”。

如果你看不懂：

- Python；
- traceback；
- 函数和类；
- 文件 / 模块；
- Git diff；
- 测试；
- 基本数据结构和复杂度；

AI 写得越多，你反而越难判断它是否正确。

---

## 2. 第一原则：先理解任务，再让 AI 修改

拿到需求时，不要第一句话就是：

> “帮我把这个项目做完。”

先自己提取 Acceptance Criteria（验收条件）：

```text
输入是什么？
用户 / 调用方应该看到什么行为？
哪些行为不能改变？
异常情况怎么处理？
测试怎样判断完成？
有没有性能 / 兼容 / 安全约束？
```

例如：

```text
需求：给一个 API 增加 page_size 限制
```

不要马上改。

先明确：

```text
默认值是多少？
最小值？
最大值？
非法值返回什么？
现有调用方是否受影响？
已有测试在哪里？
```

---

## 3. 第二原则：先调查 repository，不要猜文件

一个陌生项目先看：

```text
README
项目根目录
依赖文件
入口文件
src / app / package
tests
配置文件
```

然后回答：

```text
程序从哪里启动？
这个需求属于哪个模块？
调用链大概是什么？
现有测试覆盖哪里？
有没有类似实现可以复用？
```

这是 Repository Navigation。

AI 很适合帮助调查，但提示应当约束阶段：

```text
先不要修改代码。
请定位与 <需求> 最相关的文件、入口和测试，
说明调用关系，并列出你仍不确定的假设。
```

这样比一上来让它“大改项目”更容易控制。

---

## 4. 第三原则：把任务拆成最小可验证步骤

大任务：

```text
“实现用户搜索功能”
```

可以拆：

```text
1. 找到现有用户数据访问层
2. 明确查询接口
3. 实现核心查询
4. 接到 service / API
5. 添加正常测试
6. 添加边界 / 无结果测试
7. 运行相关测试
8. 再运行更大范围回归
```

每一步都应该能回答：

> **我怎样知道这一步真的完成了？**

如果没有验证方式，这一步仍然太模糊。

---

## 5. 一个更稳定的 AI Coding Loop

```text
Understand
理解需求和验收条件
        ↓
Inspect
读仓库、相关文件、测试
        ↓
Plan
给出最小修改计划
        ↓
Implement
只改当前必要范围
        ↓
Run
运行测试 / 程序 / 静态检查
        ↓
Observe
读真实输出和错误
        ↓
Fix
基于证据修改
        ↓
Review
检查 diff、边界、无关改动
        ↓
Verify
重新运行 + 对照原始需求验收
```

AI Coding 的核心不是某一句神奇 Prompt，而是这个反馈闭环。

---

## 6. 不要让 AI 把“猜测”说成“事实”

AI 可能说：

> “测试已经通过。”

但它如果没有真正运行，就只是在预测。

你要区分：

```text
静态判断
“看起来应该通过”

真实验证
pytest 实际退出码为 0
```

推荐要求：

```text
请运行与本次修改直接相关的测试。
告诉我实际执行的命令、通过 / 失败结果和失败信息。
不要把未运行的检查描述为已通过。
```

最终判断以真实运行证据为准。

---

## 7. 学会看 Diff，而不是只看 AI 最后一段解释

假设 AI 说：

> “我只修改了参数校验。”

真正应该检查：

```text
哪些文件变了？
每个文件改了什么？
有没有删除已有逻辑？
有没有顺手重构无关代码？
有没有新增依赖？
有没有改公开 API？
```

一个小需求却出现 20 个无关文件变化，是明显风险信号。

原则：

> **优先最小、局部、可验证的 diff。**

不是说重构永远不好，而是“完成需求”和“顺手重构世界”不要混在同一次修改里。

---

## 8. Debug：让失败信息驱动下一步

测试失败：

```text
FAILED tests/test_user.py::test_create_user
AssertionError: expected 400, got 500
```

不应该：

```text
“AI，再修一下。”
```

应该先抽取事实：

```text
哪个测试？
预期什么？
实际什么？
在哪个调用栈抛错？
输入是什么？
修改前是否通过？
```

再让 AI 定位：

```text
这是当前失败输出。
先解释最可能的失败路径，定位相关代码；
不要立即修改。
如果有多个可能原因，按证据排序。
```

Debug 的核心仍然是：

> **观察 → 假设 → 验证**，而不是随机生成更多代码。

---

## 9. AI 生成代码的人工 Review 清单

至少检查：

### Correctness

- 是否满足原始需求？
- 正常路径正确吗？
- 边界和失败路径呢？

### Scope

- 是否有无关修改？
- 是否改变了不该改变的公开行为？

### Complexity

- 是否为了简单任务写了明显过慢的算法？
- 是否引入没必要的大量内存 / 网络请求？

### Error Handling

- 异常是被正确处理，还是 `except Exception: pass` 吞掉了？

### Security

- 有没有硬编码密钥？
- 用户输入有没有直接进入危险执行 / SQL / shell？
- 权限边界有没有被扩大？

### Tests

- 测试是在验证需求，还是只是让当前实现“绿”？
- 是否包含失败 / 边界情况？

## 10. 好的提示不是“越长越好”，而是让阶段清楚

### 调查阶段

```text
先不要修改代码。
阅读与这个需求相关的入口、实现和测试。
告诉我：
1. 当前调用链；
2. 最可能修改的文件；
3. 已有测试；
4. 仍不确定的地方。
```

### 计划阶段

```text
基于刚才的调查，给一个最小修改计划。
每一步说明修改目的和验证方式。
不要顺手做无关重构。
```

### 实现阶段

```text
按计划实现第 1 步和第 2 步。
保持现有公开接口不变。
修改后运行直接相关测试。
```

### Review 阶段

```text
现在不要继续改代码。
Review 当前 diff：
- 是否满足原始需求；
- 是否有无关改动；
- 是否漏掉边界；
- 测试是否真正覆盖验收条件。
```

这些不是“万能 Prompt”，而是在强迫工作流分阶段。

## 11. AI Coding 仍然需要你自己会读代码

至少要能回答：

```text
函数输入和返回值是什么？
这个变量在哪里定义？
这个类被谁实例化？
异常从哪里抛出？
测试调用了哪个入口？
一个配置值从哪里进入系统？
```

如果这些完全不会，AI 每次修改都像黑盒。

所以本章放在 Coding 路线最后，而不是第一章。

---

## 12. AI Coding 练习阶梯

不要第一天就挑战大型仓库。

### Level 1｜单文件 Bug

给一个 30～80 行 Python 文件：

```text
有 failing test
→ 定位
→ 修复
→ 运行
```

### Level 2｜小功能

例如：

```text
给已有函数增加参数校验
增加一种输出格式
实现一个 TODO
```

### Level 3｜跨文件任务

```text
API
→ service
→ storage
→ tests
```

学会追调用链。

### Level 4｜陌生 repository

只给需求，不告诉改哪个文件。

### Level 5｜限时 AI Coding

完整：

```text
读题
→ 调查
→ 计划
→ AI 协作
→ 实现
→ 测试
→ 人工验收
→ 提交
```

## 15. 最终 Exit Gate

完成整个 Coding V1 后，你应该能够：

- 从陌生需求提取 Acceptance Criteria；
- 先调查 repository，再决定修改点；
- 找到入口、相关模块和测试；
- 把任务拆成可验证的小步骤；
- 明确要求 AI 先调查 / 计划，而不是一次性大改；
- 看懂并 Review AI 的 diff；
- 运行真实测试，而不是相信“应该通过”；
- 根据 traceback / failing test 做证据驱动 Debug；
- 检查 Correctness / Scope / Complexity / Error Handling / Security / Tests；
- 完成牛客等平台的一批 AI Coding 真实练习；
- 最终对交付结果负责，而不是把责任转给模型。

整条 Coding 路线到这里形成闭环：

```text
从一行 Python
→ 自己写小程序
→ ACM
→ 数据结构
→ Problem Solving
→ Hot100
→ 真实 OA
→ AI Coding 工程任务
```

这才是本轨道要建立的“编程基本功”。
