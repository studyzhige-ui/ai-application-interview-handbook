# 09｜AI Coding：从可复现失败到可验证交付

[← 上一章：在线笔试](08-online-assessment.md) · [Coding 首页](../README.md) · [实作项目](../exercises/09-ai-coding-lab/README.md)


需求只有一句：“第一页的数据不对，帮忙修一下。”你还不知道哪个文件负责分页，也不知道是参数、计算还是测试出了问题。AI 可以立刻写出一版分页函数，但它怎样知道这版函数符合原项目的约定？

**工程型 AI Coding 的难点，不只是生成代码，而是确定应该改什么，以及怎样证明改对了。** 本章用一个很小的分页项目练这件事：先复现问题，再沿调用找到原因，完成最小修改，最后用测试与代码差异验收。

## 1. 工程任务比函数题多了哪些责任

算法题通常已经告诉你函数名、参数和要返回什么。工程任务不一定给这么完整的起点：你需要找到入口，读懂已有行为，再判断哪些行为是缺陷、哪些必须保持。

因此，调查不是写代码前的拖延。它是在减少一种常见风险：新函数本身看起来正确，却接错了接口，或者破坏了原来正常的调用。

调查时至少需要看懂：函数收到什么、返回什么，数据在哪一步改变，以及测试预期什么结果。看不懂这些关系时，先追一条具体调用，不急着让 AI 生成更多代码。

Git 操作不熟，可以回看[Git 与 GitHub Desktop](../../tooling/git-github-desktop-guide.md)。本章重点是判断要改什么、怎样验证，而不是再学习一套版本控制命令。

## 2. 先把需求改写成可验证条件

本章使用一个三文件分页项目，不需要账号、网络或第三方依赖。完整题面、初始代码、测试和折叠参考实现都在[练习目录](../exercises/09-ai-coding-lab/README.md)。

> ⚠️ 初始实现故意有缺陷，原测试应当失败。目标是修正实现后让测试通过，不要把“测试失败”本身当作文件损坏。

先用可手算的数据明确“分页正确”是什么意思。`items = [10, 20, 30]`，每页 2 项：

| 页码 | 应返回的内容 | 原因 |
|---:|---|---|
| 1 | [10, 20] | 前两项 |
| 2 | [30] | 剩下的一项 |
| 3 | [] | 已经没有数据 |

再明确参数和边界：

- `page`：页码从 1 开始，必须为正整数，默认值为 1。
- `page_size`：每页数量，默认值为 2，只允许 1～5 的整数。
- 非法参数：抛出 `ValueError`。布尔值、浮点数、字符串和 `None` 都不作为合法整数参数。
- 输入输出：不修改原列表，返回新的外层列表。空数据或超过末页时返回 `[]`。

这些条件一起决定验收结果，不能只检查默认第一页。

真实 API 的任务，还要确认错误响应格式、兼容性、权限以及现有调用方的要求。

> ⚠️ 验收条件来自任务或已有约定，不能从待修复的实现反推“它现在怎么做都算对”。条件不清楚时，应先查证，不让 AI 擅自选择默认行为。

## 3. 调查仓库：从入口沿数据流阅读

练习文件关系是：

```text
README.md                 任务契约、运行方法、折叠参考实现
pagination.py             paginate 的当前实现
test_pagination.py       调用 paginate，检查正常与失败行为
```

先追一条具体路径，不必无目的地读完所有文件：

1. 找到失败测试，确认它怎样调用 `paginate`。
2. 记下传入的 `items`、`page` 和 `page_size`。
3. 进入 `paginate`，用这些实际值算出 `start`。
4. 检查返回切片，与测试的预期结果比较。

这样可以定位从哪一步开始，程序行为偏离了要求。

大仓库里的文件更多，但仍有各自的阅读目的：

- README 和依赖配置：确认怎样启动、怎样运行测试。
- 入口与调用方：确认数据从哪里来，参数经过了什么处理。
- 实现与测试：确认已有行为，以及调用方期望什么。

搜索命中文件名，只说明找到了候选位置，还要读上下文才能确认它是否相关。

可以这样要求 AI 调查：

> 先不修改代码。定位分页入口、实现、调用方和测试。追踪默认第一页的输入，说明实际行为与要求从哪一步开始不同，并标出尚未验证的假设。

> ⚠️ AI 给出路径和解释后，仍要核对实际文件。合理的猜测不等于仓库已经存在这样的实现。

## 4. 先运行现状，再解释失败

在练习目录的终端中运行：

```bash
python -m unittest discover -v
```

命令中的几个部分分别有明确作用：

| 部分 | 作用 |
|---|---|
| `python -m unittest` | 以程序形式运行 Python 标准库的 unittest 测试框架 |
| `discover` | 搜索符合约定的测试文件和测试方法 |
| `-v` | 显示更详细的结果，包括每个测试名 |

再看测试文件中的常见写法：

- `PaginationTests(unittest.TestCase)`：定义一个继承测试框架功能的测试类。
- 名字以 `test_` 开头的方法：需要被执行的测试。
- `self.assertEqual`：比较实际结果与预期是否相等。
- `self.assertRaises`：检查调用是否抛出指定的异常。

这些是测试工具，不是分页计算的新语法规则。

先追默认第一页这个失败：

1. 测试传入 `page = 1`、`page_size = 2`。
2. 初始实现计算 `start = page * page_size`，得到 2。
3. 切片从下标 2 开始，返回 `[30]`，而不是预期的 `[10, 20]`。

第一个偏离要求的位置已经找到了：第一页本应从下标 0 开始，却从下标 2 开始。

页码从 1 开始，分块偏移却从 0 开始，这是两套编号没有对应好。

> ⚠️ 非法 `page_size` 没有报错，是另一项校验问题。修改偏移公式不会自动补上参数校验，要分别核对验收条件。

读测试失败时，把两种信息分开：

- **断言不匹配：** 测试期望什么，实际得到了什么。
- **异常轨迹：** 哪行执行失败，参数怎样沿调用传到了那里。

> ⚠️ 失败行不一定就是应该修改的行。例如测试报告“预期 400，实际 500”，只能说明行为不匹配。需要追查为什么产生 500，不能只把返回码改成 400 就宣布修复。

## 5. 最小修改：先修正确性，再考虑结构变化

先修刚才已经确认的偏移：第一页应跳过 0 项，第二页跳过 page_size 项，因此 start 应与 `page-1` 对应。

```diff
- start = page * page_size
+ start = (page - 1) * page_size
```

位置计算修正后，还要完成同一任务中的其他条件：

- 按约定拒绝非法页码和每页数量。
- 检查空数据、末页和越界页的返回值。
- 检查返回结果没有修改原输入。

这些改动可以放在同一个逻辑完整的修复里，不需要顺手换框架或重构无关目录。

函数要主动拒绝非法调用时，使用 `raise` 抛出异常。下面先单独展示每页数量的校验：类型不对，或者整数不在 1～5 范围内，都抛出 `ValueError`。

> ⚠️ `raise` 是这里约定的错误处理行为。不能用可能被优化选项关闭的 `assert` 代替正式参数校验。

```python
def checked_size(value):
    if type(value) is not int or not 1 <= value <= 5:
        raise ValueError("page_size must be an integer from 1 to 5")
    return value

assert checked_size(2) == 2
try:
    checked_size(0)
except ValueError as error:
    assert "page_size" in str(error)
else:
    raise AssertionError("应当拒绝 0")
```

先看校验条件为什么这样排列：

1. `type(value) is not int` 检查是不是本题允许的普通整数类型。
2. 类型不对时，左边为真，`or` 短路，不再做范围比较。
3. 类型正确时，才判断是否不满足 `1 <= value <= 5`。
4. 任一条件为真，就执行 `raise ValueError(...)`。

类型判断放在前面，避免拿字符串等错误类型直接与数字比较。按本题约定，`True` 和 `False` 也要拒绝，不能当作页数。

代码下面的 `try` 用来测试非法值：

- 抛出 `ValueError` 时，进入 `except`。`as error` 把异常对象交给名字 `error`，方便检查信息。
- 没有抛出异常时，进入 `else`。这意味着 0 被错误接受，于是主动让测试失败。

> ⚠️ 这里 `else` 属于 `try` 语句，含义是“try 正常结束，没有抛出异常”，不是 `if` 的真假分支。

让 AI 按计划实现时，明确哪些公开行为不可改变，哪些测试必须保留。涉及多个文件时也应组成一个逻辑一致的修改，不是一边产生互不兼容的版本，一边让测试替你猜最终意图。

## 6. 验证：命令、结果和覆盖范围都要真实

修复以后，按两个范围验证：

1. **原故障是否消失。** 重跑原先失败的测试，不删除或削弱原断言。
2. **相关行为是否保持。** 检查默认调用、合法边界、非法参数、空数据、末页和越界页。

最后把实现再与任务契约核对。有限测试通过，仍不能替代对实现和边界的解释。

报告验证时，分清三件事：

| 信息 | 应写清楚什么 |
|---|---|
| 命令 | 实际运行的完整命令，以及运行目录 |
| 结果 | 实际通过或失败，失败测试和错误信息是什么 |
| 范围 | 只运行了分页测试，还是也运行了其他相关检查 |

> ⚠️ “看起来应该通过”是静态判断，不是执行证据。没有运行就写未运行。某个单元测试通过，也不代表全仓库检查或线上行为都已验证。

本例的初始测试本来就应失败，修复后才应全部通过。参考答案保存在 Markdown 折叠中，不会自动覆盖你的代码；应先独立修改，再与参考实现比较。

## 7. Review：看真实差异，不只看 AI 的总结

**Diff 是修改前后代码的差异。** 读它可以确认实际改动，而不是只听 AI 的总结。

检查时先回答：这些文件都与分页任务有关吗？每处修改解决哪条验收条件？如果某一处无法对应到任务，就要进一步确认是否必要。

> ⚠️ 模型说“只修改参数校验”，不代表它没有删除其他逻辑。以实际差异为准。

再按下面几类问题审查：

| 角度 | 要检查的问题 |
|---|---|
| 正确性 | 是否满足所有验收条件，而不只是一个样例？ |
| 范围 | 是否改动了无关文件、公开接口或依赖？ |
| 成本 | 是否引入不必要的全量遍历、复制或请求？ |
| 异常处理 | 是否按约定报错，而不是悄悄吞掉异常？ |
| 安全 | 是否暴露密钥、扩大权限，或把输入交给危险操作？ |
| 测试 | 是否验证原需求，有没有为了变绿而改弱断言？ |

本练习没有数据库、网络和命令执行，真实服务则还要检查 SQL、shell 等输入边界。

> ⚠️ 分页切片只创建新的外层列表，内部可变对象仍可能共享引用。这满足本练习要求，但不能描述成“完成了深拷贝”。也不要擅自增加题面没有要求的复杂复制。

## 8. 与 AI 协作的阶段怎样衔接

调查时，可以问：“先不修改，追踪默认第一页的调用，告诉我实际值与预期从哪一步开始不同。”这比“帮我修一下”更容易得到可核对的信息。

确认原因后，再推进下一阶段：

1. **实现。** 按已确认的契约修改偏移和校验，运行相关测试。
2. **根据失败修正。** 提供实际失败名、输入和输出，追查仍未满足的条件。
3. **审查。** 暂停增加功能，检查改动范围、测试差异和原有调用。
4. **交付。** 报告修改、实际验证结果，以及仍未验证的范围。

只有“继续修”三个字，不包含新的证据，也不说明上一轮的哪个假设有问题。

每个阶段都要留下可核对的结果：调查提供实际调用关系，修改提供代码差异，验证提供执行结果。

> ⚠️ “代码已生成”或“测试正在运行”都不是完成状态。如果某项检查失败，应说明失败范围及与本次改动的关系，既不能略过，也不能不加区分地把全部结果都判成失败。

## 9. 从小任务走向陌生仓库

练习可以逐级增加责任：

1. 单文件缺陷：给出失败测试，练定位与修复。
2. 小功能：增加参数校验或输出格式，练验收条件。
3. 跨文件任务：沿调用关系寻找修改点。
4. 陌生仓库：只给需求，自己调查入口与相关测试。
5. 限时交付：在时间约束下完成调查、修改、测试和审查。

每次增加一种主要难度，比同时面对陌生业务、大框架和大量生成代码更容易看清自己的缺口。

外部实践入口保留[牛客 AI 新题型](https://www.nowcoder.com/exam/oj?page=1&tab=AI%E6%96%B0%E9%A2%98%E5%9E%8B%E7%AF%87&topicId=-9001)与 [AI Coding 题库](https://www.nowcoder.com/problem/aicoding/?channelPut=www_oj_aicoding)。平台界面、题量与规则以实际页面为准，本课程不据此宣称任何固定招聘形式。

练习后复盘三组问题：

- **调查是否可靠？** 第一次让 AI 做了什么，哪个假设后来被证明不成立？
- **验证是否有效？** 哪个输入或测试暴露了问题，修改后实际运行了什么？
- **结果是否可理解？** 是否有无关改动，不依赖 AI 解释时，自己能否读懂最终代码？

这些记录比一个最终分数更能说明下次需要改进哪一步。

## 10. 本章小结与面试怎么答

从一行代码到一个工程任务，核心习惯没有改变：先确定输入和期望，再恢复真实执行过程，依据证据修改。AI 能加快调查与实现，但最终仍要读它改了什么、运行了什么、还有什么没有验证。

**问：你怎样判断 AI 生成的代码真的完成了任务？**

> 🎯 我会先对齐验收条件，复现原问题，再检查修改是否只影响必要范围。修复后重跑失败测试和相关回归，审查实际 diff，并明确报告验证范围。代码已生成、模型说应该通过，都不等于完成。

## 11. ⚠️ 容易混淆的地方

- 测试变绿不一定是实现修好了，也可能是断言被删除或改弱；需要同时看测试差异。
- 报错不再出现，不代表异常被正确处理；吞掉异常可能只是把问题藏起来。
- 新列表不等于深拷贝。分页切片保留新的外层，但内部可变对象仍可能共享。
- 一组单元测试通过，只证明该次运行与覆盖范围，不等于仓库全部检查或线上行为都已验证。

## 12. 章节自测与实作验收

**实践任务：** 完成配套分页项目，交付以下三项内容：

1. 修改后的函数及代码差异。
2. 实际执行的测试命令和结果。
3. 缺陷产生原因、修复依据、已验证边界和未验证范围。

<details><summary>查看验收要点</summary>

- 第一页从下标 0 开始，起点是 `(page - 1) * page_size`。
- 先校验类型和范围，再做偏移计算与切片。
- 起点达到或超过列表末尾时，切片返回 `[]`。
- 原列表不被修改，返回新的外层列表。
- 保留初始测试，并补充调查中发现的遗漏边界。

> ⚠️ 删除失败测试、吞掉异常，或者改变预期来迎合当前实现，都不能作为满足原需求的证据。

</details>

<details><summary>为什么只改 start 的公式，还不能宣布分页修复完成？</summary>

它只覆盖页码与下标的对应关系。非法参数是否按约定报错、原输入是否保持、空数据与越界页如何返回，仍要分别核对。修复一个已知现象，不等于所有验收条件自动成立。

</details>
