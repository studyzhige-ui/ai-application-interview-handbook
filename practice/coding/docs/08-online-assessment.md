# 08｜在线笔试：把算法放进完整交付约束

[← 上一章：Hot100 综合训练](07-hot100.md) · [Coding 首页](../README.md) · [可选参考：AI Coding →](09-ai-coding.md)


函数已经在本地算对，提交后却收到 Wrong Answer。原因可能很小：把组数当成数组长度，漏读了一行，或者多打印了“答案是”三个字。

在线笔试 OA（Online Assessment）把这些责任放到了一起：不仅要想出算法，还要在给定时间内正确读题、读输入、处理边界并输出。**会解题与能交出完整程序，中间还有一段需要专门练习的连接。**

下面就用一道固定长度区间求和题走完整条过程。你已经学过它需要的容器、循环和输入操作，注意力可以放在这些部分怎样配合。

## 1. 先分清错误可能发生在哪一层

完整程序可能在不同位置出错，调查方向也不同：

| 现象 | 先检查什么 |
|---|---|
| 程序读到的值就不对 | 读取了几行，每个字段代表什么 |
| 数值正确，但提交不通过 | 输出格式是否符合要求 |
| 普通样例正确，某类输入错误 | 边界条件和状态更新 |
| 小数据能完成，大数据超时 | 实际执行的总工作量 |

这只是排查入口，不是单凭现象就能确定根因。

- **WA（Wrong Answer，答案错误）**：输出没有通过评测。输入解析、算法和输出格式都有可能导致它。
- **TLE（Time Limit Exceeded，超过时间限制）**：程序没有在规定时限内完成，需要调查工作量和实际耗时。

> ⚠️ WA 不等于“算法思路一定错了”，TLE 也不等于“Python 一定太慢”。先复现和收集证据，再决定修改哪一层。

读题时，重点找三类约束：

1. **数据规模：** n、m 的范围，以及元素值的范围。
2. **输入与结果保证：** 是否多组，是否允许负数或空数据，是否保证有解。
3. **实现限制：** 是否允许修改输入，时间和空间限制是多少。

`n <= 20` 与 `n <= 200000` 对总工作量的要求不同，但仍要结合题意选择算法，不能只根据 n 猜模板。

## 2. 完整任务：区间长度固定的最大和

**任务：** 在一个整数列表里，找出长度恰好为 k 的连续子数组，返回其中最大的和。这是本章自定义练习。

**输入与约束：**

- 第一行给出 n、k。
- 第二行恰好有 n 个整数，元素可以为负数。
- 保证 `1 <= k <= n`，因此至少有一个合法窗口。

**输出：** 最大和，一个整数。

样例输入：

```text
5 2
1 -2 3 4 5
```

样例应输出 9。先枚举四个合法窗口，确认题意：

| 窗口 | 和 |
|---|---:|
| [1, -2] | -1 |
| [-2, 3] | 1 |
| [3, 4] | 7 |
| [4, 5] | 9 |

每次重新加 k 个数可以得到正确结果，但相邻窗口重复用了许多元素。

窗口向右移动一格，只改变两个位置。例如从 `[1, -2]` 移到 `[-2, 3]`：

1. 旧和为 -1。
2. 减去离开的 1，得到 -2。
3. 加上新来的 3，得到新和 1。

中间的 -2 不必重算。代码用 `current` 保存当前窗口的和，用 `best` 保存已经检查过的窗口中的最大和。

朴素解的时间上界为 O(nk)。复用窗口和后，初始化算 k 项，之后每次移动只做常数次运算，总时间为 O(n)。

```python
def max_window_sum(nums, k):
    current = 0
    for i in range(k):
        current += nums[i]
    best = current
    for right in range(k, len(nums)):
        current += nums[right] - nums[right - k]
        best = max(best, current)
    return best

assert max_window_sum([1,-2,3,4,5], 2) == 9
assert max_window_sum([-5,-2,-8], 2) == -7
assert max_window_sum([7], 1) == 7
assert max_window_sum([1,2,3], 3) == 6
```

看循环里的两个下标：

- `right` 是新进入窗口的位置。
- `right - k` 是这次离开窗口的位置。

例如 `k = 2`、`right = 2` 时，加入 `nums[2]`，移走 `nums[0]`。`current += nums[right] - nums[right - k]` 就是把刚才的减法和加法写在一行。

> ⚠️ `best` 要从第一个真实窗口的和开始，不能默认设为 0。例如 `[-5, -2, -8]`、`k = 2` 的最大和是 -7，0 并不是任何合法窗口的答案。

这个做法允许负数，因为每次移出的元素和移入的元素由固定长度决定，不需要根据和的大小决定边界方向。时间为 O(n)，额外空间为 O(1)。

## 3. 算法通过以后，再加输入和输出

把程序分成两种职责：

- `max_window_sum` 接收数据并返回答案，不读取键盘，也不打印。
- `solve` 读取并解析输入，调用算法，再输出结果。

下面是同一题的完整程序，可以直接保存为 `.py` 文件运行。

<!-- run: {"stdin":"5 2\n1 -2 3 4 5\n","stdout":"9\n"} -->
```python
def max_window_sum(nums, k):
    current = 0
    for i in range(k):
        current += nums[i]
    best = current
    for right in range(k, len(nums)):
        current += nums[right] - nums[right - k]
        best = max(best, current)
    return best

def solve():
    n, k = map(int, input().split())
    nums = list(map(int, input().split()))
    assert len(nums) == n and 1 <= k <= n
    answer = max_window_sum(nums, k)
    print(answer)

if __name__ == "__main__":
    solve()
```

> ⚠️ 这里的 `assert` 用来在本地检查我们是否正确理解输入协议，不是面向不可信输入的正式校验。提交时应遵循题目的输入保证和平台要求。

> ⚠️ 评测读取的是标准输出。不要额外打印“答案是”等提示，也不要在要求空格分隔时输出带方括号的 Python 列表表示。

输入协议变化时，先改读取层，不急着改算法：

- **T 组：** 第一行读组数，每轮读取该组的 n、k 和数组，再调用一次算法。
- **EOF 结束：** 明确每组占两行，只有一组完整读完后才调用算法，继续尝试读取下一组。

> ⚠️ “读到 EOF”不等于“每一行是一道独立题”。本题一组占两行，不能逐行各算一次。

## 4. 样例之外怎样制造测试

先选择能暴露不同错误的输入，而不是随意换几个数字：

| 测试情况 | 想检查什么 |
|---|---|
| 一个元素，k 为 1 | 最小输入是否正确 |
| k 为 1，或 k 等于 n | 两种窗口边界 |
| 全负数 | 最大值的初始化是否偷偷假定非负 |
| 全相同或有重复值 | 是否错误去重或遗漏位置 |
| 最优窗口在最左或最右 | 是否漏算第一个或最后一个窗口 |

> ⚠️ 本题保证 `1 <= k <= n`。不要擅自为 `k = 0` 设计一个提交格式，但必须先确认题目确实给了这项保证。

还可以做**对拍**：对同一个小输入，分别运行容易检查的朴素解和优化解，比较结果是否一致。

下面对每个小列表，尝试全部合法 k。`brute` 逐个窗口重算，`fast` 则复用上个窗口的和。

```python
def brute(nums, k):
    best = sum(nums[:k])
    for left in range(1, len(nums) - k + 1):
        best = max(best, sum(nums[left:left + k]))
    return best

def fast(nums, k):
    current = sum(nums[:k])
    best = current
    for right in range(k, len(nums)):
        current += nums[right] - nums[right - k]
        best = max(best, current)
    return best

cases = [[1,-2,3], [-5,-2,-8], [0,0,0], [7], [4,1,4,1]]
for nums in cases:
    for k in range(1, len(nums) + 1):
        assert fast(nums, k) == brute(nums, k)
```

> ⚠️ 这里的 `fast` 用 `nums[:k]` 初始化，会创建长度为 k 的临时列表，因此峰值额外空间为 O(k)。上一节逐项累加的版本没有这份切片，额外空间才是 O(1)。要看实际代码，而不是只记算法名称对应的复杂度。

> ⚠️ 对拍可以找出两个实现不一致的输入，但两个版本也可能共享同一个错误假设。因此还要手算样例、检查约束，并解释优化为什么成立。

## 5. WA 与 TLE 的调查顺序

**收到 WA 时，按顺序缩小范围：**

1. 检查读取的行数和字段含义，必要时在本地打印解析后的变量。
2. 对照要求检查输出格式，删除提交中的调试输出。
3. 手算一个失败样例，和程序每轮状态比较，找到第一次不同的位置。
4. 回到该位置，检查边界条件或算法依据是否成立。

浮点题还要核对精度要求。Python 整数不像固定 32 位整数那样有相同的溢出上限，但大整数的计算和内存仍有成本，不能据此忽略数据规模。

**收到 TLE 时，先检查工作量增长的位置：**

- 每轮是否重新查找、排序，或从列表前端删除元素？
- 是否不断复制越来越长的列表或字符串？
- 搜索是否重复访问状态，递归是否反复求同一个子问题？

先找到耗时路径，再决定换结构、改算法还是优化输入。

> ⚠️ 快读能减少输入开销，但不能从根本上修复对当前规模明显过慢的平方算法。

错误日志记录“哪项假设错了”，而不是整段抄答案。例如：

```text
任务：固定长度窗口的最大和
失败：全负数输入时返回 0
错误假设：best = 0 默认了最大和不会小于 0
修正依据：从第一个合法窗口的和初始化
下次检查：求最大值前，确认初始值是不是一个合法候选
```

## 6. 卡住时，分清是工具不熟还是思路不清

先区分两种卡点：

- **知道要做什么，不知道怎样调用。** 例如知道要取最早加入的一项，却想不起 `popleft`，可以回查队列操作。
- **还不知道应该做什么。** 例如无法决定按什么顺序处理节点，应先分析任务和状态，继续翻 API 目录不能代替这一步。

| 已经明确的需求 | 回查时要确认什么 |
|---|---|
| 字符或数字的频次 | dict 的值代表次数；Counter 可以代做计数 |
| 按到达顺序处理 | deque 的 append 入队、popleft 出队 |
| 持续取最小优先项 | heapq 的堆顶与 push/pop，而不是全量排序 |
| 在有序数据中找边界 | bisect 返回插入点，不保证目标存在 |
| 输入到何时结束 | 是已知组数、EOF，还是题目规定的哨兵 |

第一次遇到某个不熟悉的方法，可以就地确认它接收什么、返回什么、会不会改变原对象。无需停下当前任务去学完整个库，但也不能把一个不清楚含义的调用塞进程序里碰运气。

## 7. 从单题正确到整场时间管理

限时训练可以分三个阶段：

1. **不限时做对。** 先解决语言操作、输入输出和基本实现问题。
2. **单题限时。** 在一个时间窗口内完成读题、分析、编码和测试。
3. **整场模拟。** 同时管理多题的时间，减少外部提示，提交后复盘。

基础操作还不熟时，直接整场模拟往往只能知道“来不及”，不容易看清究竟缺哪一步。

整场开始时先浏览题意与限制，把题目分为能立即开始、需要思考但有方向、暂时没有方向三类。先完成把握较大的题，同时留下检查边界和输出的时间。

> ⚠️ 不要为了抢时间跳过输入协议。一开始把 T 当成 n，后面的算法即使正确也无法挽救这个输入错误。

Hot100 可先选熟悉题改完整程序，如 3、53、56、54、200、207、215、70、322，随后进入真实陌生题。避免在输入尚不熟时，把算法难度与环境难度同时拉满。

## 8. 本章小结与面试怎么答

完整程序的正确性由多部分共同组成：题意理解、输入解析、算法、边界、输出格式和规模下的成本。把算法函数保持为“接收数据并返回结果”，再单独接入输入输出，会更容易定位哪一层出了问题。

**问：样例通过，但提交失败，你会怎样排查？**

> 🎯 先核对读取的行数和字段含义，再检查输出格式，然后手算最小失败样例并追踪状态。若小数据正确、大数据超时，就分析重复查找、复制和嵌套工作的总量，而不是先换语言或快读。

## 9. ⚠️ 容易混淆的地方

- 最大值初始化为 0 隐含了答案非负，可能被全负数击中。
- 多组题每组需要重新建立的状态，应在组循环内初始化。
- 对拍能发现实现不一致，不能代替正确性理由；两个实现也可能共享同一个错误假设。
- 用切片初始化和不用切片初始化，额外空间可能不同，必须按实际代码分析。
