# 05. 底层编码与内存效率

这一章不是要把你训练成 Redis 源码工程师，而是建立一个重要直觉：

> **同一个逻辑数据类型，在不同规模下可能使用不同内部表示；Redis 会在访问效率和内存占用之间做权衡。**

如果没有这层认识，后面 BigKey、内存碎片、为什么某些结构突然变慢，都很难真正理解。

---

## 1. 逻辑类型 ≠ 唯一底层结构

你看到的是：

```text
Hash
List
Set
ZSet
```

Redis 内部可能根据：

- 元素数量；
- 元素大小；
- 值是否是整数；
- 版本实现；

选择更紧凑或更适合扩展的编码。

所以不要背成：

```text
Hash = 哈希表
ZSet = 跳表
List = 链表
```

这种说法太绝对。

---

# 2. String 与 SDS 直觉

Redis 字符串不是简单依赖 C 风格 `\0` 结尾字符串来完成所有语义。

Redis 使用自己的动态字符串抽象（常见源码术语 SDS），核心目的包括：

- 保存长度；
- 二进制安全；
- 更高效的长度获取；
- 方便扩容；
- 减少重复内存操作。

💡 **二进制安全**意味着：

String Value 不只能放普通文本，也可以放任意字节序列。

---

# 3. 小对象为什么常用紧凑编码

假设一个 Hash 只有：

```text
name=Alice
age=22
```

如果一开始就建立完整 Hash Table，元数据和指针开销可能比业务数据还大。

因此 Redis 会针对小结构采用更紧凑的表示，例如现代版本常见 listpack 等紧凑结构。

随着数据增长，再转成更适合大规模随机访问的结构。

这体现一个通用工程思想：

```text
small object
→ memory efficiency first

large object
→ access scalability first
```

---

# 4. Set 的内部表示为什么可能不同

如果 Set 里全是整数并且数量较小，Redis 可以使用更紧凑的整数集合表示。

如果成员更多、类型更一般：

```text
→ Hash-based representation
```

所以逻辑上同样是：

```text
Set
```

内部成本可能不同。

这也是为什么你不能只看：

```text
SCARD = 1000
```

就准确推断内存大小。

元素长度、编码和 allocator 都会影响。

---

# 5. ZSet 为什么常联想到 Skip List

Sorted Set 要同时满足：

```text
Member 唯一查找
+
按 Score 排序
+
Range Query
```

大规模 ZSet 的经典内部思路会组合：

```text
Hash-like lookup
+
Skip List-like ordered structure
```

这样：

- Member 查找快；
- Score 排序可维护；
- Range Query 较高效。

但小 ZSet 也可能使用更紧凑的表示。

所以面试更稳的说法是：

> 大规模 ZSet 经典实现会利用字典 + 跳表等结构，而不是说“所有 ZSet 永远就是一个跳表”。

---

# 6. List 也不是“永远双向链表”

Redis List 的内部实现经历过版本演进。

对面试而言，不应死背某个历史结构名，而应该理解目标：

```text
两端操作高效
+
顺序访问
+
尽量控制内存碎片与指针开销
```

现代实现通常结合压缩连续存储块与链式组织思想。

🎯 更重要的是知道：

> List 的逻辑语义稳定，但具体内部编码会随着 Redis 版本优化。

---

# 7. 为什么 BigKey 不只是“元素很多”

BigKey 有两种常见形态：

## 7.1 一个 String 非常大

```text
cache:huge_json → 20MB
```

问题：

- 网络传输大；
- 序列化大；
- 删除/复制有成本；
- 单次请求占用主线程更久。

## 7.2 一个集合元素很多

```text
all_users → 数百万成员
```

即使单个元素很小：

- 全量读取可能巨大；
- 删除/迁移/复制耗时；
- Cluster 中仍属于一个 Key / Slot。

所以 BigKey 判断不只看：

```text
Key 名字
```

而要看：

```text
Value bytes
元素数量
单次 Command 复杂度
访问模式
```

---

# 8. 内存使用不等于业务数据大小

如果你存：

```text
100 bytes payload
```

实际内存可能还包括：

- Redis Object Metadata；
- Key；
- Value Encoding Metadata；
- Pointer / Bucket；
- Allocator Overhead；
- Fragmentation。

所以：

```text
业务 JSON 1GB
```

不意味着 Redis 实例只需要 1GB 内存。

生产容量规划必须留余量。

---

# 9. Memory Fragmentation 是什么直觉

内存分配和释放后，可能出现：

```text
Redis 逻辑已释放很多对象
但进程 RSS 没有同比例下降
```

原因可能包括 allocator 的页/arena 管理和碎片。

所以观察 Redis 内存不能只看一个数字。

要区分：

```text
used_memory
RSS
fragmentation
```

具体指标会在 Troubleshooting 章节深入。

---

# 10. 为什么“压缩编码”不是永远更快

紧凑结构优势：

```text
省内存
Cache locality 好
```

但结构变大后：

```text
查找/插入/移动成本可能升高
```

因此 Redis 内部编码选择本质上在做：

```text
Memory
vs
CPU
vs
Access Pattern
```

这和数据库内部所有数据结构设计一样，是 Trade-off。

---

# 11. 面试怎么答

## Q：ZSet 底层是不是跳表？

🎯 **建议回答：**

> 逻辑上 ZSet 要同时支持 Member 唯一查找和按 Score 排序。大规模 ZSet 的经典实现会结合字典和跳表来兼顾查找与有序范围查询；但 Redis 对小对象可能使用更紧凑编码，因此不应该把“ZSet 永远就是一个跳表”说成绝对事实。

## Q：为什么 Redis 一个很小的业务对象也会有额外内存开销？

> 除 Payload 外还有 Key、对象元数据、底层容器、指针/哈希桶、内存分配器以及碎片，因此容量规划不能只按原始业务字节数计算。

# 12. 本章自测

<details>
<summary>1. 为什么逻辑数据类型和底层编码要分开理解？</summary>

逻辑类型定义 API/语义，底层编码是实现优化，可以根据数据规模和版本变化。只背一个固定底层结构容易把历史实现当成永恒事实。

</details>

<details>
<summary>2. BigKey 一定是大 String 吗？</summary>

不是。一个包含海量成员的 Hash/Set/List/ZSet 也是 BigKey，即使单个元素很小。

</details>

<details>
<summary>3. 为什么内存容量不能只按业务 Payload 大小估算？</summary>

还存在 Key、对象/编码元数据、容器、allocator overhead 和内存碎片等额外开销。

</details>
