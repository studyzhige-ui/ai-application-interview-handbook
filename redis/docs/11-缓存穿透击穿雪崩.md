# 11. Cache Penetration / Breakdown / Avalanche

这是 Redis 面试里最常见的一组问题之一。

但不要把它背成三个中文名词。

真正应该理解的是：

> **它们分别描述 Cache Miss 的不同失控模式。**

---

## 1. 一张总表

| 问题 | 核心原因 | 典型后果 |
|---|---|---|
| Penetration 穿透 | 请求的 Key 根本不存在 | 每次都绕过缓存打 DB |
| Breakdown / Stampede 击穿 | 单个热点 Key 失效 | 大量并发同时回源同一个热点 |
| Avalanche 雪崩 | 大量 Key 同时失效或 Redis 整体不可用 | 下游流量大规模放大 |

三者共同点：

```text
Cache 没兜住请求
→ Downstream Pressure 爆炸
```

但故障形态不同，所以治理方法也不同。

---

# 2. Cache Penetration

假设攻击者不停查：

```text
user_id = -1
user_id = -2
user_id = -3
```

这些数据：

```text
Redis 没有
MySQL 也没有
```

每次流程：

```text
Redis Miss
→ MySQL Miss
→ return not found
```

下一次还是一样。

这就是穿透。

---

# 3. 穿透怎么治理

## 3.1 参数校验

明显非法 ID：

```text
user_id <= 0
```

直接在入口拒绝。

最便宜的请求，是根本不访问下游。

## 3.2 Negative Cache

把“不存在”短暂缓存：

```text
user:missing:123 = NOT_FOUND
TTL = 30s
```

降低重复穿透。

## 3.3 Bloom Filter

如果已知合法 ID 集合非常大，可以在 Redis / DB 前增加 Bloom Filter：

```text
可能不存在
→ 直接拒绝

可能存在
→ 再查 Cache / DB
```

但 Bloom Filter：

```text
可能 False Positive
不会正常产生 False Negative（前提是结构正确维护）
```

所以它只能说：

> “这个元素可能存在。”

不能证明：

> “这个元素一定存在。”

---

# 4. Cache Breakdown / Stampede

假设：

```text
model:config:gpt-x
```

是一个超级热点 Key。

平时：

```text
10 万 QPS 全部 Hit Redis
```

某一刻 TTL 到期：

```text
10 万请求一起 Miss
→ 一起查 DB / Config Service
```

下游瞬间被打爆。

这就是热点 Key 击穿 / Stampede。

---

# 5. 击穿怎么治理

## 5.1 Mutex / SingleFlight Rebuild

第一个请求：

```text
拿 rebuild lock
→ 查 DB
→ 回填 Cache
```

其它请求：

```text
等待 / 返回旧值 / 降级
```

避免 1000 个请求同时重建。

## 5.2 Logical Expiration

物理 Key 暂时不删：

```text
value + logical_expire_at
```

发现逻辑过期：

```text
一个 Worker 异步重建
其他请求先读旧值
```

适合：

```text
允许短暂 Stale
但不能瞬间击穿
```

## 5.3 提前刷新

热点数据在真正失效前主动 Refresh。

---

# 6. Cache Avalanche

雪崩是更大范围的 Miss Storm。

常见原因：

## 6.1 大量 Key 同时 TTL 到期

```text
所有 Key 都 EX 3600
```

一小时后一起过期。

## 6.2 Redis 整体故障

```text
Cluster / Network / Node Failure
```

缓存突然不可用。

## 6.3 大规模 Eviction

内存不足导致热点大范围被淘汰。

---

# 7. 雪崩怎么治理

## 7.1 TTL Jitter

```text
base + random
```

错开失效时间。

## 7.2 高可用 Redis

Replication / Sentinel / Cluster。

但 HA 不能保证零故障窗口。

## 7.3 下游保护

非常关键：

```text
Rate Limit
Circuit Breaker
Bulkhead
Degrade
Queue
```

因为：

> 缓存防线失效后，DB 不能无限承受放大流量。

## 7.4 Local Cache

极热点少量数据可加本地缓存作为第二层保护。

---

# 8. 三者最容易混淆的地方

## 穿透

```text
数据本来就不存在
```

## 击穿

```text
数据存在
但某个热点 Key 恰好失效
```

## 雪崩

```text
大量 Key / 整体 Cache 同时失效
```

一句话：

```text
不存在 → 穿透
一个热点失效 → 击穿
一大片失效 → 雪崩
```

但面试时不要只说口诀，要能讲出流量路径。

---

# 9. 为什么“加锁”不是万能答案

热点 Key 失效时可以 Mutex Rebuild。

但如果：

```text
DB 本身已经挂了
```

加锁只能变成：

```text
大家一起等一个永远失败的重建者
```

所以还需要：

- Timeout；
- Retry Budget；
- Stale Value；
- Circuit Breaker；
- Degrade。

Cache Failure 本质上是 Backend Resilience 问题的一部分。

---

# 10. AI 场景例子

## Tool Result Cache

热点天气 Tool：

```text
weather:shanghai
```

如果 TTL 整点过期：

```text
大量 Agent 同时调用外部 Weather API
```

这就是击穿。

可以：

```text
TTL Jitter
+ Stale-while-revalidate
+ SingleFlight
```

## Semantic Cache

如果 Embedding Similarity Threshold 太宽：

```text
错误命中
```

这不是传统穿透/击穿，而是 Cache Correctness 问题。

所以 AI Cache 还要额外考虑语义错误复用。

---

# 11. 面试怎么答

## Q：穿透、击穿、雪崩分别是什么？

🎯 **建议回答：**

> 穿透是请求的数据本身不存在，导致每次 Cache Miss 都继续查 DB，可以用参数校验、短 TTL Negative Cache、Bloom Filter 等治理。击穿是单个热点 Key 失效，大并发同时回源，可以用 SingleFlight/互斥重建、逻辑过期和提前刷新。雪崩是大量 Key 同时失效或 Redis 整体故障导致大范围回源，需要 TTL Jitter、高可用、多级缓存以及限流/熔断/降级保护下游。

---

# 12. 高频易错点

⚠️ **Bloom Filter 能证明数据存在。**  
错误，只能说可能存在。

⚠️ **缓存击穿 = 缓存雪崩。**  
范围不同，一个是热点 Key，一个是大范围。

⚠️ **加分布式锁就解决所有缓存问题。**  
错误，下游故障、超时、旧值策略仍要设计。

⚠️ **TTL 随机化只能解决穿透。**  
主要用于缓解大量 Key 同时过期导致的雪崩。

# 13. 本章自测

<details>
<summary>1. 查询一个根本不存在的 user_id，为什么属于穿透？</summary>

因为 Redis 和 DB 都没有这个数据，每次请求都会持续穿过缓存访问 DB。

</details>

<details>
<summary>2. 为什么逻辑过期可以缓解热点击穿？</summary>

因为旧值仍可暂时服务请求，只让少量请求负责异步重建，避免所有并发同时回源。

</details>

<details>
<summary>3. Redis 整体不可用时，为什么仅有高可用还不够？</summary>

Failover 仍可能有故障窗口，应用必须有 Timeout、Rate Limit、Circuit Breaker、Degrade 等保护，避免下游被流量击穿。

</details>
