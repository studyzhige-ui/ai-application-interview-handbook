# 04. Bitmap / Bitfield / HyperLogLog / Geo / Stream

如果只停在 String / Hash / List / Set / ZSet，会错过 Redis 很重要的一层能力：

> **很多常见业务模式已经被抽象成专门的数据结构或命令模型。**

这些结构不一定每个都高频面试，但它们能帮助你理解 Redis 为什么不只是“内存 KV”。

---

## 1. Bitmap：用 Bit 表示大量布尔状态

假设要记录每天是否签到：

```text
user 1001：第 1 天签到
user 1002：第 1 天没签到
user 1003：第 1 天签到
```

如果每个人存一个完整整数/字符串，开销可能很大。

Bitmap 可以把状态压到 Bit：

```text
0 / 1
```

常见命令：

```text
SETBIT
GETBIT
BITCOUNT
BITOP
```

典型场景：

- 签到；
- 活跃用户；
- Feature Flag 大规模布尔状态；
- 是否看过/是否完成。

⚠️ Bitmap 的“位置”通常依赖一个稳定整数 ID 映射，不适合直接拿随机 UUID 当巨大 offset。

---

# 2. Bitfield：把一段 Bit 当小整数

Bitmap 更偏：

```text
一个 Bit = 一个布尔状态
```

Bitfield 可以在一个 String 里把不同 Bit 段解释成整数。

例如：

```text
8 bit counter
16 bit status
```

适合非常紧凑的计数或状态编码。

但可读性、调试成本更高，因此不要为了节省几个字节就过度设计。

---

# 3. HyperLogLog：低内存基数估计

问题：

> “今天有多少不同用户访问？”

精确做法：

```text
Set
```

把每个 User ID 都加入集合。

但用户量巨大时，Set 的内存随元素数增长。

HyperLogLog 提供：

> **近似 Cardinality / 去重数量估计。**

常见命令：

```text
PFADD
PFCOUNT
PFMERGE
```

适合：

- UV；
- 独立设备数；
- 大规模唯一值数量。

代价：

```text
不是精确集合
不能拿它列出所有成员
存在估计误差
```

所以如果业务要求：

> “告诉我具体有哪些用户。”

HyperLogLog 就不合适。

---

# 4. Geospatial：地理位置索引

Redis 提供 Geo 相关命令，可以存经纬度并查询附近成员。

典型：

```text
门店位置
骑手位置
附近设备
```

你不必为了 AI Agent 岗把 Geo 算法细节学很深，但要知道：

> Redis 的 Value 能力不仅是传统五种容器，还包含面向特定问题的高级命令模型。

---

# 5. Stream：日志式消息结构

Redis Stream 是这一章最值得认真学的扩展结构。

直觉上可以理解成：

```text
append-only sequence
+
entry id
+
consumer group
+
pending / ack
```

示意：

```text
stream:agent-events
  1700000000-0  {run:r1, event:started}
  1700000001-0  {run:r1, event:tool_call}
  1700000002-0  {run:r1, event:done}
```

常见概念：

```text
XADD
XREAD
XREADGROUP
XACK
Consumer Group
Pending Entries
```

这已经比 List 的简单 push/pop 更接近消息系统。

---

# 6. Stream 仍然不等于“Redis 就是 Kafka”

两者都能处理事件流，但系统设计目标不同。

Redis Stream 更适合：

- 已经大量使用 Redis；
- 中等规模内部流；
- 低延迟消息；
- 简化架构；
- 需要 Consumer Group / Ack，但不需要 Kafka 级别日志平台能力。

Kafka 更典型地面向：

- 大吞吐持久日志；
- 长时间 Retention；
- 多消费方 Replay；
- 大规模分区扩展；
- 数据平台/事件平台。

所以：

> “Redis 有 Stream”只能说明它具备消息能力，不能直接推出“专业 MQ 都没必要”。

完整选型归 AI Backend Engineering。

---

# 7. 为什么这章放在核心数据结构之后

因为知识依赖是：

```text
先理解 Key → Typed Value → Command
→ 再理解 String / Set / ZSet 等通用结构
→ 才能看懂 Bitmap、HLL、Stream 是怎样利用同一思想解决特定问题
```

而不是因为这些结构面经更高频。

---

# 8. AI Application 里可能怎么用

## HyperLogLog

估算：

```text
每天有多少不同用户调用 Agent
```

## Bitmap

```text
某租户的 Feature Enable Matrix
```

## Stream

```text
Agent Runtime Event
Tool Execution Event
Async Ingestion Event
```

但要先问：

```text
是否需要强持久？
是否要长期 Replay？
是否要求跨 Region？
是否已经有 Kafka？
```

---

# 9. 面试怎么答

## Q：Redis 除了五种常见数据结构还有什么？

🎯 **建议回答：**

> 现代 Redis 还有 Bitmap/Bitfield、HyperLogLog、Geo、Streams 等能力。Bitmap 适合大规模布尔状态，HyperLogLog 适合低内存基数估计，Streams 提供日志式消息、Consumer Group、Pending/Ack 等语义。实际是否使用要看精度、持久性、消息规模和系统边界。

# 10. 本章自测

<details>
<summary>1. Set 和 HyperLogLog 的核心区别是什么？</summary>

Set 保存精确成员，可以判断具体成员；HyperLogLog 主要用于低内存估算唯一元素数量，不能列出完整成员，并存在估计误差。

</details>

<details>
<summary>2. Redis Stream 为什么比 List 更像消息系统？</summary>

因为 Stream 有 Entry ID、Consumer Group、Pending、Ack 等消费语义，而 List 更接近简单有序队列。

</details>

<details>
<summary>3. 有了 Redis Stream 是否就一定不需要 Kafka？</summary>

不是。两者在吞吐、Retention、Replay、分区扩展、生态和运维目标上不同，应该按系统需求选型。

</details>
