# 20. Distributed Lock：从 SET NX EX/PX 开始

分布式锁是 Redis 真人面经里最强的高频主题之一。

但这一章仍然从最基础的问题开始：

> **为什么单机锁不够？Redis Lock 到底在保护什么？**

---

## 1. 单机 Lock 为什么不够

假设服务部署 3 个实例：

```text
API-1
API-2
API-3
```

每个实例都有：

```python
threading.Lock()
```

但：

```text
API-1 的 Lock
看不到 API-2 的 Lock
```

所以如果多个实例都可能处理同一份共享资源：

```text
单进程锁无法协调跨进程 / 跨机器并发
```

这时才需要分布式协调。

---

# 2. 最简单的 Redis Lock

常见基础写法：

```text
SET lock:job:123 owner-token NX PX 30000
```

四个关键点：

```text
SET
NX → 仅 Key 不存在时写入
PX → 设置 Lease TTL
owner-token → 标识锁属于谁
```

如果返回成功：

```text
拿到锁
```

如果 Key 已存在：

```text
没拿到
```

---

# 3. 为什么不能 SETNX 后再 EXPIRE

错误写法：

```text
SETNX lock:key token
# process crashes here
EXPIRE lock:key 30
```

如果客户端在两条命令之间崩溃：

```text
锁已经创建
但没有 TTL
→ 永久死锁
```

所以必须使用：

```text
SET key token NX PX ttl
```

一次原子命令完成“加锁 + 过期时间”。

---

# 4. 为什么必须有 TTL

如果持锁者：

```text
拿到锁
→ 崩溃
```

没有 TTL：

```text
没人再能拿锁
```

TTL 让锁成为 Lease：

```text
持有权只在有限时间内有效
```

所以 Redis 分布式锁更准确地理解成：

> **带租约时间的互斥权。**

---

# 5. 为什么 Value 必须是唯一 Token

错误：

```text
SET lock:key 1 NX PX 30000
```

谁拿到锁都写 `1`。

释放时：

```text
DEL lock:key
```

无法证明：

> 当前删除的人是不是锁的拥有者。

正确思路：

```text
owner-token = UUID / request-specific random value
```

释放时：

```text
只有 Value == my-token
才能 DEL
```

---

# 6. 为什么不能 GET 后直接 DEL

错误：

```text
GET lock:key → my-token
# lock expires here
# another client acquires new lock
DEL lock:key
```

时间线：

```text
A GET 看到自己的 token
A 卡顿
A 锁过期
B 获得新锁
A 恢复
A DEL 把 B 的锁删了
```

所以：

```text
compare owner
+
delete
```

必须原子。

经典做法：

```text
Lua Script
```

现代新版本也可能提供 compare-delete 类原生命令，但兼容理解仍应掌握 Token + Atomic Delete 原理。

---

# 7. 加锁失败怎么办

常见策略：

## 7.1 Fail Fast

```text
拿不到
→ 直接返回 conflict
```

适合：

- 重复提交；
- 同一个 Job 不能并行。

## 7.2 Retry with Backoff

```text
等待
→ Retry
```

要有：

- 最大等待时间；
- Backoff；
- Jitter；
- Cancellation。

不能无限 spin：

```text
while not lock:
    retry immediately
```

否则 Redis 自己被打成 HotKey。

---

# 8. Lock Key 怎么设计

假设保护 Agent Run：

```text
lock:agent_run:{run_id}
```

锁粒度太大：

```text
lock:all_agent_runs
```

会让无关任务互相阻塞。

锁粒度太细：

```text
无法保护真正共享的不变量
```

所以要问：

> **我真正要互斥保护的 Resource / Invariant 是什么？**

---

# 9. Distributed Lock 不能替代 Transaction

假设业务：

```text
扣 MySQL 余额
→ 写订单
```

加一个 Redis Lock：

```text
不能自动让两个 DB 写入原子提交
```

Lock 只解决：

```text
并发互斥
```

Transaction 解决：

```text
数据原子提交 / 回滚
```

两者不是替代关系。

---

# 10. Redis Lock 也不是 Idempotency

两个重复请求：

```text
Request A 完成
→ 释放锁
Request B 稍后到达
→ 重新拿锁
→ 再执行一次
```

所以 Lock 只能防：

```text
同时执行
```

不能自动防：

```text
先后重复执行
```

防重复通常还需要：

```text
Idempotency Key
Business State
Unique Constraint
Dedup Record
```

# 11. AI Application 场景

## 防止同一个 Agent Run 被两个 Worker 同时 Claim

```text
SET lock:run:{id} worker-token NX PX 30000
```

但仅靠锁还不够：

```text
Worker 执行 2 分钟
TTL 30 秒
```

会发生什么？

这就是下一章 Lock Correctness 的主题。

## 防止同一个 Knowledge Base 重复 Ingestion

可以按：

```text
lock:kb:{kb_id}:ingest
```

但如果任务很长，也需要 Lease Renewal / Job State。

# 12. 面试怎么答

## Q：Redis 分布式锁基本怎么实现？

🎯 **建议回答：**

> 最基础可以用 `SET lock_key unique_token NX PX ttl` 原子创建带租约的锁。Token 必须唯一，用来证明 Owner；释放时不能直接 DEL，而要原子地判断 Value 仍然等于自己的 Token 再删除，经典实现用 Lua。TTL 用来防持锁进程崩溃后永久死锁，但 TTL 也会带来锁过期后旧 Owner 继续执行的问题，因此完整正确性还需要 Lease、Renewal、Fencing 等进一步讨论。

## Q：为什么不能 SETNX + EXPIRE 两条命令？

> 两条命令之间客户端可能崩溃，导致锁创建成功却没有 TTL，形成永久锁，所以必须一个 SET 命令同时完成 NX 与 TTL。

---

# 13. 高频易错点

⚠️ **SETNX + EXPIRE 就够了。**  
有 Crash Window。

⚠️ **拿到锁后 DEL 就行。**  
可能误删别人的新锁。

⚠️ **有 TTL 就保证锁正确。**  
TTL 只解决永久死锁，还会引入 Lease Expiry Race。

⚠️ **Lock = Idempotency。**  
不是。

# 14. 本章自测

<details>
<summary>1. 为什么 Redis Lock Value 要用唯一 Token？</summary>

为了在释放时证明当前 Key 仍属于自己，防止误删其他客户端后来获得的新锁。

</details>

<details>
<summary>2. 为什么 TTL 是必须的？</summary>

持锁客户端崩溃后，如果没有 TTL，锁可能永远无法释放。

</details>

<details>
<summary>3. 为什么 Lock 不能替代 Idempotency？</summary>

Lock 主要防同时执行；前一个请求完成释放锁后，后续重复请求仍可以再次获得锁并重复执行。

</details>
