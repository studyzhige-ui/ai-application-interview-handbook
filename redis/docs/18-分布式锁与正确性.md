# 18. Redis 分布式锁：从 Acquire 到 Lease、Renewal、Failover 与 Fencing

Redis 分布式锁是高频面试题，但只会：

```text
SET key value NX PX ttl
```

远远不够。

一个完整的锁知识块应该从“为什么需要跨进程互斥”一路走到：

```text
Acquire
→ Owner Identity
→ Lease / TTL
→ Safe Release
→ Renewal
→ Pause / Expiry Race
→ Failover
→ Fencing
→ Lock vs Idempotency
→ 什么时候不该用 Redis Lock
```

这就是为什么原来的“分布式锁基础”和“锁正确性”应该合成同一章：

> **如果只学会拿锁，却不理解锁失效后的业务正确性，就等于没有真正学会分布式锁。**

---

## 1. 为什么单机 Lock 不够

假设服务有三个实例：

```text
API-1
API-2
API-3
```

每个实例都有：

```python
threading.Lock()
```

它只能协调本进程内部线程。

如果 API-1 和 API-2 同时处理同一个业务资源：

```text
API-1 的本地锁
无法阻止 API-2
```

所以当多个进程/机器需要共同协调某个共享资源时，才需要分布式协调机制。

---

## 2. 最小 Redis Lock

常见基础写法：

```text
SET lock:job:123 owner-token NX PX 30000
```

其中：

```text
NX          → Key 不存在时才写
PX 30000    → Lease 30s
owner-token → 当前持有者唯一身份
```

成功表示当前客户端获得一个有限时间的互斥租约。

### 为什么不能 `SETNX` 后再 `EXPIRE`

错误写法：

```text
SETNX lock:key token
# crash here
EXPIRE lock:key 30
```

如果进程在中间崩溃，锁可能永不过期。

所以“创建锁 + TTL”必须在一个原子操作里完成。

---

## 3. TTL 不是装饰，而是 Lease

如果没有 TTL：

```text
Client A acquire
→ A crash
→ lock 永远存在
```

TTL 让锁变成：

> **只在有限时间内有效的所有权声明。**

这就是 Lease。

但 Lease 同时引入新的正确性问题：

```text
任务可能还没做完
锁先过期了
```

这正是后面最关键的 Race。

---

## 4. 为什么 Value 必须是唯一 Owner Token

错误设计：

```text
SET lock:key 1 NX PX 30000
```

每个客户端都写相同 Value。

释放时：

```text
DEL lock:key
```

无法证明：

> 删除锁的人，还是不是当前 Owner？

正确做法是：

```text
owner-token = request / process specific random value
```

比如 UUID。

---

## 5. 为什么不能 GET 后再 DEL

看这条时间线：

```text
A GET lock → A-token
A pause
A lock expires
B acquire → B-token
A resumes
A DEL lock
```

A 会误删 B 的锁。

因此：

```text
compare owner
+
delete
```

必须是一个原子操作。

经典实现使用 Lua / Function：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
```

核心语义不是“Lua 很高级”，而是：

> **Owner Check 和 Delete 不能被其它命令插入。**

---

## 6. 加锁失败怎么办

### Fail Fast

```text
lock exists
→ return conflict / duplicate in progress
```

适合：

- 同一个 Job 不能重复执行；
- 用户重复提交；
- 并发任务可以直接拒绝。

### Retry with Backoff

```text
wait
→ retry
```

要有：

- 最大等待时间；
- Exponential Backoff；
- Jitter；
- Cancellation；
- 重试次数上限。

不要：

```text
while not lock:
    retry immediately
```

否则锁 Key 自己会变成 HotKey。

---

## 7. 最经典的 Lease Expiry Race

这是分布式锁真正的核心题。

```text
T0  A acquire lock, TTL=30s
T1  A starts work
T2  A pauses for 40s
T3  lock expires
T4  B acquires same lock
T5  B starts work
T6  A resumes
```

此时：

```text
A 和 B 都可能继续操作业务资源
```

注意：

> A 即使不会误删 B 的锁，也仍然可能产生 stale side effect。

因此：

```text
safe release
≠
full business correctness
```

---

## 8. Renewal / WatchDog 解决什么

如果任务耗时不确定，可以让持锁者定期续租：

```text
TTL = 30s
每 10s：
    verify owner
    extend lease
```

这样长任务无需一开始配置一个极大的 TTL。

但 Renewal 并不是绝对正确性证明。

如果进程：

```text
pause > TTL
```

就来不及续租。

### 续租也必须校验 Owner

错误：

```text
PEXPIRE lock:key 30000
```

旧客户端恢复后可能给别人新获得的锁续期。

正确逻辑是：

```text
if GET lock == my-token:
    extend ttl
```

并且这个 compare + extend 仍需要原子执行。

---

## 9. Fencing Token 为什么比“我还持锁”更强

真正想阻止过期 Owner 写下游，可以为每次锁持有生成单调递增版本：

```text
A acquire → fencing=41
B acquire → fencing=42
```

下游只接受：

```text
version >= last_seen_version
```

于是旧 A 恢复后：

```text
A writes with 41
Downstream already saw 42
→ reject
```

这比单纯依赖：

```text
A 自己认为是否还持有锁
```

更可靠。

### 关键前提

Fencing Token 必须被**真正的下游资源执行**。

例如：

```text
MySQL row version
Job coordinator epoch
Object generation
```

如果下游不检查版本，Token 只是一个无意义数字。

---

## 10. Primary Failover 会怎样影响锁

假设：

```text
A acquire on Primary
Primary replies success
lock has not replicated yet
Primary crashes
Replica promoted
```

新 Primary 上可能没有这把锁。

于是：

```text
B acquire succeeds
```

A 仍然可能继续工作。

这说明：

> **Redis 异步复制环境中的锁，要明确接受什么故障安全模型。**

不能只说：

> Redis 有主从，所以锁高可用且绝对正确。

---

## 11. Redlock 应该怎么理解

Redlock 试图在多个彼此独立的 Redis 节点上获取多数锁，以降低单节点故障带来的风险。

面试里真正应该理解的是：

- 它仍依赖 Lease 和时间假设；
- 获取过程有超时和有效期计算；
- 多数节点并不自动消除所有 stale owner 问题；
- 对严格安全场景仍需评估 Consensus、DB Conditional Write、Fencing 等方案。

不要把 Redlock 背成：

> “生产分布式锁唯一正确答案。”

---

## 12. Lock 和 Idempotency 不是一回事

### Lock

解决：

```text
同一时间谁可以进入临界区？
```

### Idempotency

解决：

```text
相同动作重复执行后，业务结果是否仍保持正确？
```

即使加锁成功：

```text
worker crash after side effect
→ retry
```

仍可能重复产生副作用。

所以 Production 业务通常需要组合：

```text
Lock
+
Idempotency Key
+
Unique Constraint
+
State Machine
+
Conditional Write
+
Compensation
```

具体组合取决于业务风险。

---

## 13. 什么场景不该默认用 Redis Lock

先问：

### 能不能用数据库唯一约束？

例如：

```text
one order_id can create only one payment record
```

Unique Constraint 可能比分布式锁更直接。

### 能不能用 Conditional Update？

```sql
UPDATE jobs
SET status = 'running'
WHERE id = ? AND status = 'pending';
```

受影响行数本身就是抢占结果。

### 能不能设计成 Idempotent？

如果重复执行本来就安全，就不一定需要全局互斥。

### 能不能串行化到单消费者？

同一个业务 Key 路由给同一个 Partition/Consumer，也可能解决协调问题。

> **分布式锁是一种工具，不是看到并发问题后的默认答案。**

---

## 14. AI Application 场景

### 防止重复 Agent Run

```text
lock:agent_run:{run_id}
```

可以避免多个 Worker 同时执行同一 Run。

但还要考虑：

```text
Tool side effect happened
→ process crashes
→ new worker retries
```

所以 Agent Runtime 仍需要 Checkpoint / Idempotency / Compensation。

### Knowledge Base Rebuild

可以锁：

```text
kb_reindex:{kb_id}
```

避免同一知识库重复执行昂贵 rebuild。

### Scheduled Job

多个实例竞争同一批定时任务时，可以用 Lease 选择 Owner，但真正高可靠调度还需要任务状态机。

## 15. 一条完整 Failure Timeline

面试时建议画：

```text
A acquire lease=30s, fence=101
↓
A starts external work
↓
A pauses
↓
lease expires
↓
B acquire lease, fence=102
↓
B writes downstream
↓
A resumes
↓
A tries downstream write with 101
↓
downstream rejects stale fencing token
```

如果你能解释这条时间线，才算真正理解“锁正确性”。

## 16. 常见错误

### 错误 1：有 TTL 就不会死锁，所以锁是正确的

TTL 解决永久占锁，不解决 stale owner 恢复后的副作用。

### 错误 2：唯一 Token 解决所有问题

Token 主要帮助安全释放和续租；不能阻止过期 Owner 继续访问外部系统。

### 错误 3：WatchDog 等于绝对安全

WatchDog 只能降低正常长任务 Lease 到期风险，不能消除长暂停、网络分区和 Failover。

### 错误 4：加了分布式锁就不需要幂等

锁和幂等解决不同问题。

### 错误 5：所有跨实例并发都必须用 Redis Lock

很多问题可以由唯一约束、CAS、状态机、Partition 或幂等设计更直接解决。

## 17. 面试怎么答

### Q：Redis 分布式锁怎么实现？

🎯 **建议回答：**

> 基础实现使用 `SET key unique_token NX PX ttl` 原子创建带 Lease 的锁；释放时必须原子校验 Owner Token 后删除，避免误删别人新获得的锁。长任务可以做 Owner-aware Renewal，但还要考虑 Lease 过期、进程暂停、Primary Failover 等 Race。对不能接受 stale owner 副作用的场景，应进一步使用 Fencing Token 或更强的一致性协调方案，并且业务层仍要有幂等或条件写。

### Q：TTL 到期但业务没执行完怎么办？

> 可以用 WatchDog/Lease Renewal 降低正常长任务过期风险，但这不能完全解决长暂停；如果旧 Owner 恢复后仍可能写下游，需要 Fencing 或下游 Conditional Write 拒绝旧版本。

### Q：为什么锁和幂等要同时考虑？

> Lock 控制“谁现在执行”，Idempotency 控制“重复执行后结果是否正确”。Crash、Retry、外部副作用都可能绕过单纯锁语义。

## 18. 章节自测

<details>
<summary>1. 为什么不能 SETNX 后再 EXPIRE？</summary>

两条命令之间如果进程崩溃，会留下没有 TTL 的永久锁，因此创建锁和设置 Lease 必须原子完成。

</details>

<details>
<summary>2. Owner Token 解决什么，不能解决什么？</summary>

它能帮助安全释放和续租，证明“当前操作是不是原 Owner”；但不能阻止 Lease 已过期的旧 Owner 恢复后继续写外部系统。

</details>

<details>
<summary>3. WatchDog 为什么不能证明锁绝对正确？</summary>

因为进程可能暂停超过 TTL，或者发生网络分区/Failover；续租机制本身也有失败窗口。

</details>

<details>
<summary>4. Fencing Token 真正生效的前提是什么？</summary>

被保护的下游系统必须记录并拒绝旧版本 Token，否则 Fencing Token 只是一个数字。

</details>

<details>
<summary>5. 为什么 Failover 可能造成双持锁？</summary>

Primary 确认锁写入后，如果该写入尚未复制到 Replica 就崩溃，Replica 提升后可能看不到旧锁，于是另一个客户端可以重新获取。

</details>

<details>
<summary>6. 哪些方案可能比 Redis Lock 更合适？</summary>

数据库唯一约束、Conditional Update / CAS、幂等 Key、状态机、单 Partition 串行消费，或者对强协调需求使用更适合的一致性系统。

</details>
