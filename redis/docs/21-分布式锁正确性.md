# 21. Lock Correctness：Owner、Lease、Renewal、Failover、Fencing

上一章实现了一个“基础 Redis Lock”：

```text
SET lock_key token NX PX ttl
```

真正困难的问题从这里才开始：

> **锁存在，不代表被锁保护的业务一定正确。**

分布式系统会出现：

- Stop-the-world / GC pause；
- 网络抖动；
- 进程卡死；
- Lease 过期；
- Primary Failover；
- 时钟和超时边界；
- 外部 Side Effect。

---

## 1. 最经典的 Lease Expiry Race

```text
A 获得锁，TTL = 30s
A 开始处理任务
A 卡顿 40s
锁在 30s 时过期
B 获得同一个锁
B 开始处理
A 在 40s 恢复
```

现在：

```text
A 和 B 都认为自己可以执行
```

即使 A 最后“不误删 B 的锁”，业务仍可能双执行。

所以：

> **Owner Token 只保护安全释放，不足以阻止过期 Owner 继续产生副作用。**

---

# 2. Renewal / WatchDog 解决什么

如果任务可能比固定 TTL 长：

```text
持锁者定期续约
```

例如：

```text
TTL 30s
每 10s 确认仍是 Owner
→ 延长到 30s
```

这就是 Lease Renewal / WatchDog 思路。

但它仍然不是绝对正确性证明。

如果：

```text
进程暂停超过 TTL
```

续约来不及，锁仍然会过期。

---

# 3. Renewal 自己也必须校验 Owner

错误：

```text
PEXPIRE lock:key 30000
```

如果旧客户端恢复后直接续约，而锁已经被 B 获得：

```text
A 可能替 B 延长 Lease
```

更稳的续约必须原子检查：

```text
if GET lock == my_token
then PEXPIRE
```

通常使用 Lua / Function 或等价原子能力。

---

# 4. Fencing Token 为什么重要

要真正阻止旧 Owner 在 Lease 失效后写下游，可以引入：

```text
Fencing Token
```

每次拿锁都获得单调递增版本：

```text
A → token 41
B → token 42
```

下游资源只接受：

```text
token >= last_seen
```

所以 A 即使恢复：

```text
A token 41
下游已经见过 42
→ reject
```

这把正确性从：

```text
“我觉得我还持锁”
```

提升为：

```text
“下游能拒绝过期 Owner”
```

---

# 5. Fencing Token 的难点

Redis 单 Key 锁本身可以生成 Counter：

```text
INCR lock:sequence
```

但真正关键是：

> **被保护的下游系统必须理解并 enforce fencing token。**

例如：

```text
MySQL row version
Object Storage generation
Job coordinator epoch
```

如果下游完全不检查版本：

```text
Fencing Token 只是一个数字，没有保护作用
```

---

# 6. Failover 对单实例 Lock 的影响

假设：

```text
A 在 Primary 上获得 lock
Primary 回复成功
lock 尚未复制到 Replica
Primary crash
Replica promote
```

新 Primary 上：

```text
lock 不存在
```

B 又可以拿锁。

于是：

```text
A 和 B 同时执行
```

这来自 Redis 异步复制的 acknowledged-write-loss window。

所以：

> **基于单 Primary 的 Redis Lock 在 Failover 下要明确接受什么安全模型。**

---

# 7. Redlock 要怎么理解

Redlock 的目标是：

```text
在多个彼此独立的 Redis 节点上
尝试获取多数锁
```

希望降低单节点故障/Failover 导致重复持锁的风险。

面试不应该只背算法步骤，更重要的是理解：

- 它依赖 Lease / 时间假设；
- 需要多数独立实例；
- 获取过程有超时与有效期计算；
- 它并不是所有“严格安全”场景的唯一答案。

对于：

```text
金融扣款
基础设施主控权
不可重复外部副作用
```

应该继续问：

> 是否需要 Consensus System、DB Conditional Write、Fencing Token 或更强协调语义？

---

# 8. 分布式锁最重要的不是“锁库选型”

面试官真正可能在问：

```text
你理解 Failure Timeline 吗？
```

应该能画：

```text
T0 A acquire
T1 A pause
T2 lease expires
T3 B acquire
T4 B writes
T5 A resumes
T6 A writes stale result
```

然后说明：

```text
Owner Token
解决 release safety

Renewal
降低 lease 过期概率

Fencing
保护下游拒绝 stale owner
```

---

# 9. Redis Lock vs DB Conditional Update

有些场景根本不需要分布式锁。

例如：

```sql
UPDATE jobs
SET status = 'RUNNING', owner = 'w1'
WHERE id = 123
  AND status = 'PENDING';
```

检查 affected rows：

```text
1 → claim 成功
0 → 已被别人 claim
```

这是数据库条件写 / Compare-and-set 思路。

优势：

```text
状态真相和并发控制在同一个 Source of Truth
```

所以成熟回答不是：

> “分布式并发一定用 Redis Lock。”

而是：

> “先看不变量在哪个系统里，能否用原子状态转移解决。”

---

# 10. Lock vs Lease vs Idempotency vs Transaction

| 机制 | 主要解决 |
|---|---|
| Lock | 同时只能一个执行者进入 |
| Lease | Lock 有时间边界，崩溃后可自动失效 |
| Fencing | 下游拒绝过期 Owner |
| Idempotency | 重复执行不产生重复副作用 |
| Transaction | 一组数据修改的原子提交/回滚 |

真实系统常常需要组合，而不是四选一。

---

# 11. AI Agent 场景

假设多个 Worker 争抢一个 Agent Run。

只用 Redis Lock：

```text
worker A 拿锁
→ Tool 调用了支付 API
→ A 卡顿
→ 锁过期
→ B 接管
→ 再调用一次支付
```

即使锁本身没有误删：

```text
外部支付已经重复
```

因此需要：

```text
Lock / Lease
+
Run State Machine
+
Idempotency Key
+
Tool Side-effect Dedup
+
Checkpoint / Resume
```

完整语义属于 Agent Harness / Backend Engineering。

# 12. 面试怎么答

## Q：Redis 锁设置 TTL 后就安全吗？

🎯 **建议回答：**

> TTL 解决的是客户端崩溃后永久死锁，但会引入 Lease 到期问题：旧持锁者可能暂停超过 TTL，锁过期后新客户端获得锁，而旧客户端恢复后仍继续执行。Owner Token 只能防误删新锁；长任务通常需要 Renewal，安全要求更高时还应考虑 Fencing Token，让下游拒绝旧 Owner，以及 Idempotency / 状态机等业务保护。

## Q：为什么 Redis Failover 会影响锁正确性？

> 因为复制通常异步。Primary 成功创建锁并回复客户端后，如果锁还没复制到 Replica 就故障，Replica 提升后可能看不到这把锁，另一个客户端就能再次获取。

---

# 13. 高频易错点

⚠️ **TTL + Lua Release = 完美分布式锁。**  
仍有 Lease Expiry 和 Failover 问题。

⚠️ **WatchDog 能解决所有暂停。**  
暂停超过 TTL 时仍可能失效。

⚠️ **Fencing Token 只要生成出来就有用。**  
下游必须 enforce。

⚠️ **任何并发控制都先上 Redis Lock。**  
很多业务可以用 DB Conditional Update / Unique Constraint 更简单地解决。

# 14. 本章自测

<details>
<summary>1. Owner Token 与 Fencing Token 的职责有什么区别？</summary>

Owner Token 证明“当前锁 Value 是否还是我”，主要用于安全释放/续约；Fencing Token 是单调版本，下游用它拒绝过期 Owner 的 stale write。

</details>

<details>
<summary>2. WatchDog 为什么不是绝对正确性方案？</summary>

如果进程/机器暂停时间超过 Lease TTL，续约线程也无法运行，锁仍会过期并被别人获得。

</details>

<details>
<summary>3. 什么情况下数据库条件更新可能比分布式锁更合适？</summary>

当被保护的业务状态本来就在数据库中，且可以通过状态条件/版本号/唯一约束原子完成竞争控制时，直接在 Source of Truth 做 CAS 往往更简单可靠。

</details>
