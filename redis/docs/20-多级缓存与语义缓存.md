# 20｜Multi-level Cache 与 Semantic / Result Cache

单层 Redis Cache 不是缓存体系的终点。

真实系统里常见：

```text
Process Local Cache
        ↓
      Redis
        ↓
  MySQL / Remote API
```

AI Application 又会进一步出现：

```text
Exact Cache
Tool Result Cache
Semantic Cache
```

这章重点是：**不同缓存层解决什么，以及一致性风险如何变化。**

---

## 1. 为什么需要 Local Cache + Redis

Redis 很快，但仍然有：

```text
网络 RTT
序列化
连接池
Redis 节点负载
```

如果某个配置每个请求都读，而且更新极少：

```text
Local Cache
```

可以把绝大多数访问留在进程内。

例如：

```text
model pricing config
feature flag
static tenant plan
```

---

# 2. Multi-level Cache 的典型读路径

```text
Request
  ↓
L1 Local Cache
  ├─ hit → return
  └─ miss
       ↓
L2 Redis
  ├─ hit → fill L1 → return
  └─ miss
       ↓
Source of Truth
       ↓
fill Redis
       ↓
fill Local
```

优点：

- 极热点读延迟更低；
- Redis QPS 降低；
- Redis 短时抖动有一定缓冲。

代价：

> **副本层数越多，一致性越复杂。**

---

# 3. Local Cache 最大问题：每个实例都有自己的副本

```text
API-1 local = old
API-2 local = new
API-3 local = old
```

Redis 已经更新，并不代表三个进程本地缓存立刻一致。

常见治理：

- Short TTL；
- Pub/Sub Invalidation；
- Version；
- Periodic Refresh；
- 配置中心推送。

真正强一致通常不适合依赖多级 Cache。

---

# 4. Cache Invalidation 为什么是难题

读很容易：

```text
hit → return
```

难的是：

```text
Source of Truth 变了
→ 哪些副本必须失效？
→ 失效通知会不会丢？
→ 同时有请求怎么办？
```

层级越多：

```text
DB
Redis
API Local Cache
CDN
Browser
```

就越要明确 Freshness Contract。

---

# 5. Exact Result Cache

最简单：

```text
normalized_input_hash
→ exact output
```

例如 Tool：

```text
weather(city=Shanghai, date=2026-09-11)
```

Key：

```text
cache:weather:<args_hash>
```

前提：

```text
相同输入在 TTL 内可以复用
```

---

# 6. Semantic Cache 是什么

LLM / RAG 场景中，两句话可能字面不同但语义接近：

```text
“Redis 为什么快？”
“为什么 Redis 性能这么高？”
```

Semantic Cache 尝试：

```text
Query → Embedding
→ 找相似历史 Query
→ similarity > threshold
→ 复用 Answer
```

这已经不是简单 KV Cache。

---

# 7. Semantic Cache 最大风险：错误命中

Exact Cache 的错误通常是：

```text
Stale
```

Semantic Cache 还可能：

```text
语义看起来像
但真实意图不同
```

例如：

```text
“退款规则是什么？”
“企业客户退款规则是什么？”
```

如果忽略 Tenant / User / Product Context，可能把错误答案复用。

所以 Cache Key / Filter 还要加入：

- Tenant；
- Permission；
- Product Version；
- Knowledge Version；
- Model/Prompt Version；
- Language / Locale。

---

# 8. Semantic Cache 的 Threshold 怎么设

不能只说：

```text
0.9 就行
```

应该通过 Dataset 验证：

```text
False Hit Rate
Cache Hit Rate
Answer Correctness
Latency Saved
Cost Saved
```

Threshold 过低：

```text
命中多，但错误复用多
```

过高：

```text
很安全，但几乎没命中
```

这和 RAG Retrieval Evaluation 思路相通。

---

# 9. Tool Result Cache 要看 Side Effect

可缓存：

```text
GET weather
GET exchange_rate snapshot
Read-only metadata
```

不应该直接缓存并复用：

```text
charge_card()
create_order()
send_email()
```

因为这些 Tool 有 Side Effect。

所以：

> **Cache 主要复用“结果”，不能用来假装副作用已经正确执行。**

---

# 10. 多级缓存什么时候不值得

如果：

- Redis 已经足够低延迟；
- QPS 不高；
- 数据更新频繁；
- 强一致要求高；

Local Cache 只会增加：

```text
Invalidation Complexity
```

因此多级缓存应该由瓶颈驱动，而不是架构模板驱动。

---

# 11. 面试怎么答

## Q：Local Cache + Redis 怎么保证一致？

🎯 **建议回答：**

> 多级缓存很难做到简单强一致，常见方法是 Redis 作为共享 L2，本地 L1 使用短 TTL，再配 Pub/Sub 或配置推送做 Invalidation，必要时带 Version。要允许短暂 Stale，并明确 Source of Truth。如果业务要求强一致，就不应该把关键判断完全建立在多级缓存上。

## Q：Semantic Cache 和普通 Redis Cache 有什么区别？

> 普通 Exact Cache 通常要求 Key 完全相同；Semantic Cache 用 Embedding/Similarity 判断不同 Query 是否可复用结果，因此除了 Staleness 还存在 False Semantic Hit，需要通过离线 Dataset 验证 Threshold，并把 Tenant、Permission、Knowledge Version 等 Context 纳入边界。

---

# 12. 本章自测

<details>
<summary>1. 多级缓存为什么比单层缓存更难？</summary>

副本数量增加，每个进程本地缓存可能处于不同版本，失效通知和 TTL 都可能有窗口，因此一致性复杂度显著上升。

</details>

<details>
<summary>2. Semantic Cache 最独特的风险是什么？</summary>

不仅可能陈旧，还可能因相似度判断错误，把语义相近但真实意图不同的请求错误命中到旧答案。

</details>

<details>
<summary>3. 为什么有副作用的 Tool 不能直接用 Result Cache 代替执行？</summary>

因为缓存一个旧结果不能证明这次业务副作用已经真正发生，可能破坏订单、支付、邮件等执行语义。

</details>
